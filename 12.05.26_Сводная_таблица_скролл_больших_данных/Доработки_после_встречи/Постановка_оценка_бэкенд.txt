Сводная таблица. Проработка решения и оценка трудозатрат: Оптимизация отображения больших данных. Бэкенд

***

h3. Контекст.

В рамках задачи оптимизации отображения больших данных в сводной таблице (см. исходную постановку) требуется провести технический разбор проблемы. *Текущая архитектура взаимодействия фронтенда и бэкенда* является одним из ключевых узких мест производительности.

Сводная таблица (краткое описание для ориентации):

* Сводная таблица — виджет, позволяющий пользователю группировать данные по нескольким измерениям *строк* и *столбцов* (например: округ → регион → город; год → месяц → день).
* Каждое раскрытие узла на фронтенде инициирует *отдельные запросы* к бэкенду — по одному на каждое значение данного уровня иерархии.
* При использовании функции «Развернуть всё» / «Развернуть до уровня N» количество одновременных запросов растёт *экспоненциально*: N значений на первом уровне → N запросов; разворот следующего уровня → до N² запросов и т.д.
* Бэкенд, на текущий момент, принимает отдельные плоские-запросы с условиями и возвращает плоские выборки. Агрегация и построение иерархии производится на фронтенде.

----
h3. Цель задачи.

Изучить текущую механику запросов сводной таблицы, проработать возможные подходы к оптимизации на стороне бэкенда и подготовить оценку трудозатрат.

----
h3. Требуется:

h4. 1. Для корректной оценки необходимо синхронизироваться с Алексеем Меркушенковым по итогам его фронтовой проработки — получить список конкретных требований к API.

h4. 2. Анализ направлений оптимизации.

Рассмотреть и оценить реализуемость следующих подходов:

 * *Серверная подготовка / кэширование*: предварительный расчёт и сохранение промежуточной структуры сводной на бэкенде (in-memory кэш, Redis или аналог) для исключения повторных тяжёлых вычислений при перелистывании страниц несколькими пользователями. Необходимо оценить механику инвалидации и управления сессиями подготовленных данных.
 * *Трансляция иерархических запросов на уровень СУБД*: оценить возможность и целесообразность формирования более сложных SQL-запросов (с группировкой, pivot-подобными конструкциями) на стороне бэкенда вместо многократных плоских выборок. Учитывать требование независимости от типа СУБД.

h4. 3. Оценка трудозатрат

Для каждого рассматриваемого подхода (или их комбинации) предоставить оценку трудозатрат:

 * Проектирование и согласование API-контракта с фронтендом.
 * Реализация серверной логики.

Отдельно указать: реализуемо ли решение поэтапно и какой минимальный объём доработок на бэкенде даст ощутимый прирост производительности уже в короткой итерации.

----
h3. Ограничения.

 * Экспорт данных работает вне пагинации — данное изменение *не затрагивает* логику экспорта.
 * Всю бизнес-логику визуального представления (положение итогов, форматирование ячеек и т.п.) переносить на бэкенд *не требуется*.
 * Независимость от типа СУБД *обязательна* — любое решение на уровне запросов должно быть транслируемым через текущий механизм построения SQL (с учётом его возможной доработки).
