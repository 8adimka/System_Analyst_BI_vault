(Алексей Меркушенков)
Сводная таблица. Проработка решения и оценка трудозатрат: Оптимизация отображения больших данных. Фронтенд

***

h3. Контекст.

В рамках задачи оптимизации отображения больших данных в сводной таблице (см. исходную постановку) требуется провести технический разбор проблемы. 
Приоритетное направление проработки: *структурная пагинация* по строкам (по нижнему уровню иерархии), с сохранением текущего режима отрисовки как опционального.

Технические факты, влияющие на реализацию:

* Виртуализация на уровне DOM *уже реализована*: строки вне видимой области не создаются как DOM-элементы. Этот ресурс в значительной мере исчерпан.
* Данные загружаются *лениво* по мере раскрытия узлов — каждое разворачивание инициирует отдельные запросы к бэкенду.
* При использовании функций «Развернуть всё» / «Развернуть до уровня N» число запросов к бэкенду растёт *экспоненциально* (N значений на уровне → N запросов; следующий уровень → N² запросов), что приводит к деградации производительности как на фронте, так и на бэкенде.
* Фронтовый кэш имеет проблему накопления без своевременной очистки — это потенциальный источник деградации производительности при длительной работе с таблицей.
* Иерархия существует *как по строкам, так и по столбцам*; оба измерения могут расти неограниченно.
* Мемоизация компонентов как ресурс оптимизации *пока не задействована*.

----
h3. Цель задачи:

Проработать техническое решение отображения больших данных в сводной таблице на стороне фронтенда и подготовить оценку трудозатрат.

----
h3. Требуется:

h4. 1. Анализ и техническое предложение.

Изучить текущую архитектуру сводной таблицы и сформулировать конкретный план реализации *структурной пагинации по строкам* или иного преспективного подхода к оптимизации работы Сводной таблицы при отображении больших данных. 
Возможные вопросы для проработки:

 # Каков предлагаемый алгоритм разбиения строк по страницам с учётом иерархии? Как будет определяться граница страницы при разрыве внутри одной ветки дерева?
 # Какие именно запросы к бэкенду формируются сейчас при раскрытии узла? Чего не хватает в текущем API для поддержки пагинации (параметры, структура ответа)?
 # Как будет храниться *состояние раскрытости* при переходе между страницами?
 # Как затронет пагинация по строкам *горизонтальное измерение*? Предлагается ли пагинация по столбцам как отдельная опция, или горизонтальный рост остаётся без ограничений в данной итерации?
 # Насколько реализуем вариант инкрементального применения функции «Развернуть до уровня N» — только к строкам текущей страницы?

h4. 2. Оценка промежуточных быстрых решений.

Независимо от сроков полной реализации — оценить *потенциал* быстрых улучшений производительности без архитектурных изменений:

 * Мемоизация компонентов.
 * Улучшение логики очистки фронтового кэша.
 * Батчинг запросов при «Развернуть всё»: вместо N отдельных запросов — один агрегированный или иные перспективные способы быстрой оптимизации производительности сводной таблицы.

h4. 3. Оценка трудозатрат.

Предоставить оценку по следующим позициям:

 * Оценка быстрых решений (мемоизация + кэш) — без изменений в API.
 * Структурная пагинация по строкам: фронтовая часть (при условии готовности бэкенда к поддержке).
 * _Опциональная_ пагинация по столбцам (при необходимости — отдельная строка оценки).
 * Адаптация существующей функциональности «Развернуть до уровня N» под постраничный режим.

----
h3. Ограничения.

 * Режим без пагинации *сохраняется* как опция (тумблер в настройках виджета) — текущее поведение не удаляется.
 * Экспорт данных работает вне зависимости от состояния пагинации — полный набор данных, без разбиения.
 * Пагинация *структурная*: единица счёта — листовой узел нижнего уровня иерархии; родительские заголовки дублируются в начале страницы при разрыве ветки.
