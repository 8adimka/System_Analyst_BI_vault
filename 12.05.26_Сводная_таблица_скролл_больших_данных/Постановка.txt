Сводная таблица. Оптимизация отображения больших данных

----
h3. Контекст и описание проблемы.

На текущий момент механизм отрисовки сводной таблицы предполагает рендеринг всех данных на одной странице. При увеличении объема данных (особенно, при использовании функционала «развернуть все уровни») возникают следующие критические проблемы:

# *Оптимизация.* Значительные задержки при первичной отрисовке. При добавлении высокозагруженных полей на полку детализации таблица начинает значительно подтормаживать уже на нескольких тысячах строк.
# *UI.* Интерфейс нередко «зависает» при попытке манипуляции с глубокой иерархией.
# *Потенциальное отсутствие масштабируемости.* Функциональность «Развернуть все уровни» (реализована, но временно скрыта; автор — Алексей Меркушенко) при наборе данных ~10 000 строк вызывает полное зависание интерфейса. При объёмах 100 000+ строк текущая архитектура отрисовки нежизнеспособна.

h4. Корневая причина

Сводная таблица отрисовывается целиком в рамках одного DOM-дерева. Вся выборка строк загружается и рендерится единовременно: браузеру приходится поддерживать в DOM полный набор элементов, что приводит к высокому потреблению памяти и блокировкам.

----
h3. Цель задачи

Обеспечить корректную и производительную работу сводной таблицы при произвольном объёме данных за счёт поэтапной (или постраничной) загрузки строк, не нарушая существующей логики иерархического раскрытия.

----
h3. Рассматриваемые подходы:

h4. Вариант A — Постраничная пагинация

Внизу сводной таблицы появляется панель управления страницами. Пользователь явно переключается между страницами данных.

*Ключевые требования к варианту A:*

* Панель пагинации располагается под таблицей и содержит:
** кнопки «Предыдущая» / «Следующая»;
** кнопки перехода в начало / в конец;
** поле ручного ввода номера страницы (с валидацией: значение "< 1" → переход на первую страницу; значение "> max" → переход на последнюю);
** отображение текущего диапазона строк и общего числа строк (например: «строки 31–40 из 50»);
** интерфейс для выбора количества строк отображаемых на одной странице (например: 10, 50, 100, 500, 1 000).
* Включение пагинации управляется через панель настроек виджета (тумблер «Пагинация»):
** При включённом тумблере появляются поля для управления пагинацией.
** При выключённом тумблере таблица возвращается к текущему поведению (отрисовка без разбиения).
* Подсчёт строк ведётся по *нижнему уровню* иерархии (листовые узлы) независимо от текущего состояния раскрытия.
* При разбиении на страницы иерархические заголовки (родительские узлы), чьи дочерние строки переходят на следующую страницу, *дублируются* в начале этой страницы для сохранения контекста.
* Функциональность «Развернуть до уровня N» применяется только к строкам текущей страницы.

*Преимущества:*
- Предсказуемое, понятное пользователю поведение.
- Возможность прямого перехода на нужную страницу.
- Ограниченный объём DOM на каждый момент времени.

*Риски / открытые вопросы:*
- Сложность отображения иерархии при разбивке группы между страницами (дублирование заголовков).
- Необходимость хранения/передачи информации о состоянии развёрнутости между страницами.
- Выбор стратегии пагинации на уровне бэкенда: offset-based / keyset / фильтр в памяти — влияет на производительность при больших объёмах и произвольном переходе к странице.

----
h4. Вариант B — Бесконечный скролл с дозагрузкой (виртуализация)

Таблица загружает данные порциями по мере прокрутки пользователем вниз. В DOM постоянно поддерживается ограниченное «окно» строк; строки за пределами видимой области выгружаются.

*Ключевые требования к варианту B:*

* При прокрутке вниз следующая порция строк подгружается автоматически (lazy loading).
* Строки, вышедшие за пределы буферного окна (вверх), выгружаются из DOM для экономии памяти; при прокрутке обратно вверх — подгружаются повторно.
* Позиция скроллбара отражает реальный размер всего набора данных (виртуальный скролл), а не только загруженного фрагмента.
* Функциональность «Развернуть до уровня N» применяется инкрементально: сначала разворачиваются строки текущего буфера, остальные — по мере подгрузки.

*Преимущества:*
- Привычная парадигма для работы с лентами и большими списками.
- Нет необходимости думать о «страницах»: данные воспринимаются как непрерывный поток.
- Потенциально более естественная интеграция с иерархическим раскрытием (нет разрыва дерева между страницами).

*Риски / открытые вопросы:*
- Реализация виртуализации иерархических деревьев (в отличие от плоских списков) существенно сложнее.
- Невозможно напрямую перейти к произвольной позиции в таблице.
- Управление буфером (что хранить, что выгружать) в контексте разворачивания/сворачивания узлов — задача нетривиальная.
- Оценка трудоёмкости подлежит обсуждению.

----
h3. Вопросы для обсуждения.

# Какова оценка трудоёмкости для каждого из вариантов — фронтенд и бэкенд отдельно?
# Насколько реализуемо корректное вычисление «числа строк по нижнему уровню» при переменной глубине раскрытия иерархии?
# Как должны передаваться параметры пагинации в API-запросе (offset + limit, cursor-based, подзапрос)?
# Технически возможна ли реализация обоих режимов в рамках одного спринта, или необходимо выбрать один?
# Существующая функциональность «Развернуть до уровня N» (Алексей Меркушенко) — насколько сложно адаптировать её под поэтапную загрузку данных?

h3. Критерии приёмки (AC):

h4. AC.1: Производительность при больших данных
* *Дано:* сводная таблица содержит ≥ 10 000 листовых строк.
* *Когда:* пользователь открывает виджет.
* *Тогда:* первоначальная отрисовка занимает не более 3 секунд; интерфейс не блокируется.

h4. AC.2: Корректная работа «Развернуть до уровня N»
* *Дано:* включена пагинация / бесконечный скролл.
* *Когда:* пользователь нажимает «Развернуть до уровня N».
* *Тогда:* операция применяется к текущей странице (вариант A) или к текущему буферу (вариант B) без зависания UI.

h4. AC.3: Подсчёт строк (только вариант A)
* *Дано:* таблица с иерархией глубиной ≥ 2 уровней, часть узлов раскрыта.
* *Когда:* отображается панель пагинации.
* *Тогда:* число строк рассчитывается по листовым узлам; отображается диапазон «строки X–Y из Z».

h4. AC.4: Переход на страницу (только вариант A)
* *Дано:* таблица содержит N страниц, N > 5.
* *Когда:* пользователь вводит в поле номер страницы M.
* *Тогда:*
** M в диапазоне [1; N] → таблица переходит на страницу M.
** M < 1 → переход на первую страницу.
** M > N → переход на последнюю страницу.
** Нечисловой ввод → ввод игнорируется, поле сбрасывается.

h4. AC.5: Дублирование иерархических заголовков (только вариант A)
* *Дано:* дочерние строки узла разбиты между страницами.
* *Когда:* пользователь переходит на страницу, начинающуюся с дочерних строк.
* *Тогда:* родительский заголовок отображается первой строкой страницы.

h4. AC.6: Тумблер «Пагинация» в настройках виджета (вариант A)
* *Дано:* открыта панель настроек сводной таблицы.
* *Когда:* пользователь переключает тумблер «Пагинация».
* *Тогда:*
** Включён → под таблицей отображается панель управления страницами; появляется поле «Строк на странице».
** Выключён → таблица работает в текущем режиме без разбиения.

h4. AC.7: Отсутствие регрессий
* *Дано:* таблица с малым объёмом данных (< 100 строк) и выключённой пагинацией.
* *Когда:* пользователь работает с таблицей.
* *Тогда:* поведение идентично текущей реализации; изменений не наблюдается.
