h3. Контекст и проблематика.

В аналитическом портале Modus BI сейчас используется {{access token}} в формате JWT. После успешной аутентификации пользователь получает токен и выполняет с ним запросы к основному порталу и ФВД.

После авторизации через внешние провайдеры, в том числе LDAP/AD, права пользователя могут измениться во внешней системе (уже после выдачи токена). При этом ранее выданный {{access token}} продолжает давать доступ в рамках тех прав, которые были актуальны на момент авторизации. Актуализация ролей и прав происходит только при повторной авторизации пользователя.

Из-за этого в рамках активной сессии нет бесшовного механизма обновления прав:
* если права пользователя уменьшили во внешней системе, портал продолжает работать со старым набором прав до повторной авторизации или истечения текущего токена;
* если права пользователя расширили, пользователь не получает новые возможности без повторного входа;
* при истечении {{access token}} пользователь вынужден повторно вводить логин и пароль, что может мешать комфортной работе на портале.

Требуется ввести механизм {{refresh token}} в дополнение к существующему {{access token}}, чтобы портал мог обновлять сессию и перечитывать права пользователя без принудительного выхода из системы.

----

h3. Цель задачи.

*Требуется:*
# Добавить поддержку {{refresh token}} в механизм аутентификации и сессии аналитического портала.
# При обновлении {{access token}} через {{refresh token}} перечитывать актуальные права пользователя из используемого провайдера аутентификации по логике, аналогичной повторному логину.
# Обеспечить бесшовное продление активной сессии пользователя в основном портале и ФВД без повторного ввода логина и пароля, если {{refresh token}} валиден.
# Обеспечить применение изменений прав в обе стороны: как при уменьшении, так и при расширении прав пользователя.

_Пользовательская история:_
Как пользователь аналитического портала, я хочу продолжать работу после обновления сессии без повторной авторизации, чтобы изменения моих прав применялись автоматически и не прерывали текущую работу с порталом.

----

h3. 1. Описание текущего поведения.

* После успешной авторизации портал выдаёт пользователю {{access token}}.
* {{access token}} используется frontend-частью для выполнения запросов к backend API.
* Права пользователя фиксируются на момент авторизации и учитываются при формировании токена/сессии.
* Если права пользователя изменились во внешнем провайдере аутентификации после выдачи токена, портал не перечитывает их в рамках текущей активной сессии.
* Чтобы получить актуальный набор прав, пользователь должен повторно авторизоваться.
* В основном портале и ФВД используется единый JWT-механизм доступа, поэтому проблема актуальна для обоих контуров.

----

h3. 2. Описание целевого поведения.

h4. 2.1. Общая логика токенов.

* После успешной авторизации backend должен возвращать пользователю пару токенов:
** {{access token}} — короткоживущий токен для выполнения обычных запросов к API;
** {{refresh token}} — токен для получения нового {{access token}} без повторного ввода логина и пароля.
* {{access token}} используется только для доступа к существующим бизнес-операциям портала.
* {{refresh token}} используется только для обновления сессии/токена и не должен использоваться как токен доступа к обычным операциям API.
* При успешном обновлении backend должен выдать новый {{access token}} с актуальным набором ролей и прав пользователя.
* Если выбранная backend-реализация предусматривает ротацию {{refresh token}}, вместе с новым {{access token}} должен возвращаться новый {{refresh token}}, а предыдущий {{refresh token}} должен становиться недействительным.

h4. 2.2. Актуализация прав.

* При каждом обновлении {{access token}} через {{refresh token}} backend должен перечитывать актуальные права пользователя из текущего провайдера аутентификации.
* Для LDAP/AD необходимо перечитывать актуальные данные пользователя и его групп/ролей из LDAP/AD по логике, используемой при повторном логине.
* Для других провайдеров аутентификации необходимо использовать существующую provider-specific логику получения и синхронизации прав, если она применяется при логине.
* Для локальной авторизации, если она используется, необходимо перечитывать актуальное состояние пользователя и его прав из внутренних данных портала.
* Изменения прав должны применяться при ближайшем успешном обновлении {{access token}}. Мгновенный отзыв уже выданного {{access token}} до истечения его срока жизни в рамки данной задачи не входит.

h4. 2.3. Поведение пользователя.

* Если {{refresh token}} валиден и обновление прошло успешно, пользователь остаётся в активной сессии без перехода на экран авторизации.
* Если права пользователя были расширены, после обновления токена пользователь должен получить доступ к новым разрешённым действиям без повторного логина.
* Если права пользователя были уменьшены, после обновления токена пользователь должен потерять доступ к действиям и разделам, которые больше не разрешены.
* Если пользователь находится на странице или в компоненте, доступ к которому был потерян после обновления прав, портал должен применить существующее поведение для отсутствия прав: закрыть действие, показать отказ в доступе или перенаправить пользователя в доступный раздел.
* Если обновление токена не выполнено из-за истечения, отзыва или невалидности {{refresh token}}, пользователь должен быть переведён в состояние неавторизованного пользователя по текущим правилам портала.

----

h3. 3. Рамки задачи.

h4. 3.1. Входит в рамки задачи.

* Доработка backend-механизма аутентификации/сессии для поддержки {{refresh token}}.
* Доработка логики логина, чтобы после успешной авторизации выдавалась пара {{access token}} + {{refresh token}}.
* Доработка backend-операции обновления токена с перечитыванием актуальных прав пользователя.
* Доработка frontend-логики основного портала для бесшовного обновления {{access token}}.
* Доработка frontend-логики ФВД, если ФВД использует отдельную точку входа и собственную auth-обвязку.
* Обработка ошибок обновления токена и истечения сессии.
* Проверка сценариев уменьшения и расширения прав пользователя без повторного логина.

h4. 3.2. Не входит в рамки задачи.

* Реализация отдельного API для принудительного сброса сессии выбранного пользователя.
* Реализация административного интерфейса со списком активных сессий пользователей.
* Мгновенный отзыв уже выданного {{access token}} в момент изменения прав во внешней системе.
* Доработки на стороне AD/LDAP или другого внешнего провайдера аутентификации заказчика.
* Изменение модели ролей и прав портала, если текущая модель уже поддерживает получение прав при логине.

----

h3. 4. Требования к реализации.

h4. 4.1. Frontend-часть.

* Frontend должен хранить и использовать {{access token}} и {{refresh token}} в соответствии с текущей моделью безопасности портала. {{refresh token}} не должен попадать в обычные бизнес-запросы к API.
* Frontend должен определять необходимость обновления {{access token}}:
** до истечения срока действия токена, если срок можно определить заранее;
** при получении ответа о невалидном/истёкшем {{access token}}, если backend поддерживает такой сценарий.
* При обновлении токена пользователь не должен терять текущий экран, несохранённые изменения, состояние фильтров, выбранные значения и контекст работы, если refresh выполнен успешно.
* При нескольких параллельных API-запросах с истёкшим {{access token}} frontend не должен запускать неконтролируемую серию refresh-запросов. Должен выполняться один refresh-процесс, после которого ожидающие запросы повторяются с новым {{access token}} либо завершаются ошибкой сессии.
* После успешного refresh frontend должен обновить локальное состояние авторизации и прав пользователя.
* Меню, доступность разделов, кнопок и действий должны соответствовать актуальным правам после обновления токена.
* При неуспешном refresh frontend должен очистить состояние авторизации по текущим правилам портала и перевести пользователя на сценарий повторной авторизации.
* Требования применяются к основному порталу, доступному по {{/}}, и к ФВД, доступному по {{/fvd}}, если оба контура используют единый JWT-механизм доступа.

h4. 4.2. Backend-часть.

* Backend должен поддержать выдачу {{refresh token}} при успешной авторизации пользователя.
* Backend должен реализовать логическую операцию обновления токена в зоне API {{users/login/session/auth settings}}. Точное имя backend-объекта и команды необходимо подтвердить с командой разработки до реализации.
* Операция refresh должна:
** принять {{refresh token}} по защищённому каналу/механизму, принятому в портале;
** проверить валидность, срок действия и состояние {{refresh token}};
** определить пользователя и текущий провайдер аутентификации;
** перечитать актуальные права пользователя из соответствующего провайдера;
** пересобрать набор ролей и прав пользователя в модели портала;
** выдать новый {{access token}} с актуальными правами;
** вернуть новый {{refresh token}}, если используется ротация refresh-токенов.
* Backend не должен выдавать новый {{access token}}, если:
** {{refresh token}} отсутствует, истёк, отозван или невалиден;
** пользователь заблокирован, удалён или больше не может быть сопоставлен с учётной записью портала;
** внешний провайдер аутентификации не подтвердил актуальное состояние пользователя и прав;
** для пользователя не удалось сформировать допустимый набор прав.
* При logout refresh-токен текущей сессии должен становиться недействительным.
* Ошибки refresh должны возвращаться в едином формате ошибок портала и не должны раскрывать секреты, токены, пароли или технические детали внешнего провайдера.
* В логах backend не должны сохраняться значения {{access token}}, {{refresh token}}, пароли и иные секреты. Допустимо логировать технические идентификаторы сессии/пользователя и результат операции без раскрытия секретных значений.

h4. 4.3. API и совместимость.

* Существующие бизнес-операции API должны продолжить принимать {{access token}} без изменения логики вызова со стороны потребителей.
* Изменение ответа логина должно быть обратно совместимым для текущих frontend-контуров портала и ФВД.
* Текущие механизмы проверки ролей и прав на backend должны продолжить работать на основании актуального {{access token}}.
* При обновлении прав нельзя полагаться только на frontend-ограничения. Backend должен проверять права по новому {{access token}} при выполнении защищённых операций.
* Время жизни {{access token}} и {{refresh token}} должно задаваться отдельно. Конкретные значения сроков жизни необходимо подтвердить с командой разработки и владельцем продукта.
* Если в портале есть настройки времени жизни сессии/токена, новая логика должна быть согласована с этими настройками и не должна ломать существующее поведение авторизации.

h4. 4.4. Безопасность.

* {{refresh token}} должен рассматриваться как секрет и защищаться не слабее текущего {{access token}}.
* {{refresh token}} не должен отображаться пользователю, попадать в URL, query-параметры, сообщения об ошибках, клиентские события аналитики и backend-логи.
* При компрометации или повторном использовании недействительного {{refresh token}} backend не должен выдавать новый {{access token}}.
* Реализация должна учитывать работу пользователя в нескольких вкладках одного браузера и не должна приводить к циклическому logout/login или бесконечным попыткам refresh.

----

h3. 5. Пограничные сценарии:

* Права пользователя уменьшены во внешнем провайдере во время активной сессии.
* Права пользователя расширены во внешнем провайдере во время активной сессии.
* Пользователь удалён, заблокирован или больше не найден во внешнем провайдере.
* Пользователь удалён или заблокирован во внутренних данных портала.
* Внешний провайдер аутентификации временно недоступен в момент refresh.
* {{access token}} истёк, но {{refresh token}} валиден.
* {{access token}} валиден, но права во внешнем провайдере уже изменены. В этом случае изменения применяются только при ближайшем refresh.
* {{refresh token}} истёк, отозван, повреждён или отсутствует.
* Одновременно выполняется несколько запросов к API в момент истечения {{access token}}.
* Пользователь работает одновременно в основном портале и ФВД.
* Пользователь выполняет действие, право на которое было отозвано после открытия страницы, но до отправки запроса.
* Пользователь получает новые права на раздел или действие без повторного логина.

----

h3. 6. Риски и зависимости:

* Для LDAP/AD требуется совместное тестирование на инфраструктуре заказчика, так как настройки AD/LDAP, структура групп и атрибутов могут отличаться от тестового окружения Modus BI.
* Частота фактической актуализации прав зависит от срока жизни {{access token}} и момента выполнения refresh.
* Если внешний провайдер аутентификации недоступен в момент refresh, backend может не иметь возможности безопасно выдать новый {{access token}} с актуальными правами.
* Точные имена API-объектов/команд, формат ответа логина, формат refresh-операции и правила ротации {{refresh token}} требуют подтверждения у команды разработки.

h3. 8. Предположения.

* Текущий {{access token}} является JWT и используется единообразно для основного портала и ФВД.
* При повторном логине портал уже умеет получать или пересчитывать актуальные права пользователя из используемого провайдера аутентификации.
* Для refresh необходимо переиспользовать существующую логику логина/синхронизации прав, а не создавать отдельную независимую модель прав.
* Срок жизни {{access token}} достаточно короткий, чтобы обновление прав при ближайшем refresh считалось приемлемым для бизнес-сценариев.

h3. 10. Критерии приёмки (AC):

*AC.1 — Выдача refresh-токена при логине:*
* *Дано:* пользователь проходит успешную авторизацию в портале;
* *Когда:* backend завершает сценарий логина;
* *Тогда:* frontend получает {{access token}} и {{refresh token}};
* *Тогда:* обычные API-запросы продолжают выполняться с {{access token}}.

*AC.2 — Бесшовное обновление access-токена:*
* *Дано:* пользователь работает в основном портале или ФВД, {{access token}} близок к истечению или истёк, а {{refresh token}} валиден;
* *Когда:* frontend выполняет refresh;
* *Тогда:* backend возвращает новый {{access token}};
* *Тогда:* пользователь остаётся в текущей сессии без повторного ввода логина и пароля;
* *Тогда:* текущий экран и рабочий контекст пользователя не сбрасываются.

*AC.3 — Перечитывание прав при refresh:*
* *Дано:* пользователь авторизован через провайдер аутентификации, из которого портал получает роли/права;
* *Когда:* выполняется refresh токена;
* *Тогда:* backend перечитывает актуальные права пользователя из этого провайдера по логике повторного логина;
* *Тогда:* новый {{access token}} содержит или отражает актуальный набор прав пользователя.

*AC.4 — Уменьшение прав без повторного логина:*
* *Дано:* пользователь находится в активной сессии и имеет доступ к защищённому разделу или действию;
* *И:* во внешнем провайдере у пользователя отозвали соответствующее право;
* *Когда:* выполняется ближайший успешный refresh;
* *Тогда:* новый {{access token}} не даёт доступ к отозванному действию;
* *Тогда:* backend отклоняет защищённую операцию, если пользователь пытается выполнить её со старым уровнем прав после refresh;
* *Тогда:* frontend отображает состояние отсутствия доступа по текущим правилам портала.

*AC.5 — Расширение прав без повторного логина:*
* *Дано:* пользователь находится в активной сессии и не имеет доступа к определённому разделу или действию;
* *И:* во внешнем провайдере пользователю добавили соответствующее право;
* *Когда:* выполняется ближайший успешный refresh;
* *Тогда:* новый {{access token}} даёт доступ к добавленному действию;
* *Тогда:* frontend обновляет доступность разделов/действий без повторного ввода логина и пароля.

*AC.6 — Невалидный или истёкший refresh-токен:*
* *Дано:* {{refresh token}} отсутствует, истёк, отозван или повреждён;
* *Когда:* frontend пытается обновить {{access token}};
* *Тогда:* backend не выдаёт новый {{access token}};
* *Тогда:* frontend завершает текущую авторизованную сессию по правилам портала и переводит пользователя к повторной авторизации.

*AC.7 — Logout отзывает refresh-токен:*
* *Дано:* пользователь авторизован и имеет действующий {{refresh token}};
* *Когда:* пользователь выполняет logout;
* *Тогда:* {{refresh token}} текущей сессии становится недействительным;
* *Тогда:* повторный refresh с этим токеном не выдаёт новый {{access token}}.

*AC.8 — Недоступность внешнего провайдера при refresh:*
* *Дано:* пользователь авторизован через внешний провайдер;
* *И:* в момент refresh внешний провайдер недоступен или не возвращает данные, необходимые для подтверждения прав;
* *Когда:* backend выполняет refresh;
* *Тогда:* backend не выдаёт новый {{access token}} на основании непроверенных или устаревших прав;
* *Тогда:* frontend обрабатывает ошибку refresh без бесконечных повторных запросов.

*AC.9 — Параллельные запросы при истечении access-токена:*
* *Дано:* в момент истечения {{access token}} frontend отправляет несколько API-запросов параллельно;
* *Когда:* требуется обновить токен;
* *Тогда:* frontend выполняет один контролируемый refresh-процесс;
* *Тогда:* после успешного refresh ожидающие запросы повторяются с новым {{access token}} либо завершаются единообразной ошибкой, если refresh не выполнен.

*AC.10 — Единое поведение основного портала и ФВД:*
* *Дано:* пользователь работает в основном портале по {{/}} и/или в ФВД по {{/fvd}};
* *Когда:* выполняется refresh токена;
* *Тогда:* оба контура используют актуальный {{access token}} и применяют актуальные права пользователя;
* *Тогда:* пользователь не должен повторно авторизоваться отдельно в одном из контуров, если refresh прошёл успешно.

*AC.11 — Обратная совместимость бизнес-операций API:*
* *Дано:* существующие API-операции портала вызываются с валидным {{access token}};
* *Когда:* внедрён механизм {{refresh token}};
* *Тогда:* формат и логика авторизации обычных бизнес-запросов через {{access token}} не меняются для вызывающей стороны;
* *Тогда:* проверка прав на backend продолжает выполняться по актуальному {{access token}}.
