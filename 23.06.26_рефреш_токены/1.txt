Нужно написать постановку на введение на нашем аналитическом портале refresh токена, в дополнение к существующему access токену.

Информация для постановки на ведение Refresh Token на аналитическом портале.

В нашей системе (аналитический портал Modus BI) существует только access token (JWT). 

В системе партнёров и клиентов, которые авторизуются в нашей системе при помощи протокола LDAP, права пользователей в AD/LDAP могут изменяться, но токен уже выдан пользователю в нашей системе и даёт ему доступ независимо от изменения прав в AD/LDAP. 
Изменения ролей и прав произойдёт только после:
1) повторной авторизации пользователя,
2) при наличии refresh токена, после обновления access токена (происходит незаметно для пользователя).
Второй вариант с refresh токеном значительно более предпочтителен и удобен для пользователя.
Сейчас нет механизма актуализации прав «на лету» в рамках активной сессии.

Суть доработки: ввести механизм refresh token рядом с существующим access token. При обновлении токена происходит перечитывание прав пользователя из внешней системы аутентификации — по аналогии с повторным логином.
Преимущества:
* Работает для всех провайдеров аутентификации, не только LDAP.
* Права обновляются бесшовно для пользователя — без принудительного выхода и повторного ввода логина/пароля.
* Работает в обе стороны: как при уменьшении, так и при добавлении прав — пользователь сразу получает расширенные права без перелогина.

Оценка трудозатрат:
* Фронтенд: 80 часов (доработка онлайн-обновления сессии, чтобы пользователя не выбрасывало каждый час).
* Бэкенд: 160 часов.
** Итого: 240 часов. 

Оценка принята без снижения ввиду неполного понимания механики на момент обсуждения.

Access-токен есть, сейчас надо добавить refresh-token, чтобы JWT нормально работал; при обновлении он перечитывает права, как будто мы перелогиниваемся из внешней системы аутентификации.

При использовании refresh token: права перечитываются из внешней системы аутентификации при каждом обновлении токена. Refresh token полезен всем провайдерам аутентификации на портале (не только LDAP).

Ключевой риск: взаимодействие с заказчиком при совместном тестировании — коммуникация медленная, сроки могут растянуться.

Как системный аналитик с большим стажем, опираясь на подготовленную мной информацию и общий контекст, сформулируй логику работы нашего аналитического портала и необходимые доработки для внедрения refresh в дополнение к уже используемому на портале access токену.

Сформулируй и подготовь понятную постановку, в соответствии с нашими стандартами.

Новая постановка не должна фокусироваться обсуждениях, согласованиях и прочих некритичных деталях в рамках реализации данной доработки. 

Новая постановка должна декларативно давать разработчикам информацию о необходимых доработках, а тестировщикам давать достаточно информации и качественные критерии приёмки, чтобы они понимали как тестировать новую функциональность в рамках портала.

Постановка должна быть верной, согласованной, полной, компактной, но ёмкой и достаточной для разработчиков и тестировщиков. Сохраняй оптимальную разметку и структуру документов, которая уже используется в наших постановках для публикации в Jira.
