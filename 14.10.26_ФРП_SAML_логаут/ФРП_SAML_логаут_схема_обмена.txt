*ФРП: порядок обмена при SAML Single Logout*

Это пояснение к постановке, а не дополнительный объём реализации. Версия и фактические настройки Keycloak ФРП - требуют уточнения.

----

h3. 1. Порядок выхода.

# Пользователь нажимает «Выход» в хедере ГИСП. ГИСП должна запустить завершение своей авторизации и соответствующей SSO-сессии Keycloak. Как именно хедер вызывает Keycloak, из материалов неизвестно: этот участок нужно проверить с командой ГИСП.
# Keycloak определяет участников завершаемой SSO-сессии и направляет порталу {{LogoutRequest}} на согласованный адрес {{SingleLogoutService}}. Передача возможна через браузер или напрямую между серверами. Не следует считать, что собственная сессия Keycloak обязательно полностью удаляется до рассылки уведомлений.
# Портал проверяет подлинность и целостность сообщения, отправителя и применимость запроса, затем сопоставляет SAML-идентификаторы с локальными сессиями. Обработка не должна зависеть только от наличия текущей browser-cookie.
# Портал прекращает авторизованный доступ в пределах запроса. Это включает непригодность связанных средств авторизации для последующих запросов и продления сессии. Удаление cookie либо переход на другую страницу сами по себе этого не обеспечивают.
# Портал формирует {{LogoutResponse}} с результатом обработки и связью с исходным запросом. В стандартном SLO-обмене ответ передаётся IdP через согласованный binding. Успех обработки у портала не подтверждает выход остальных приложений.
# Keycloak продолжает/завершает координацию выхода. Завершение локальной сессии ГИСП и конечную страницу проверяют совместно с заказчиком. Отсутствие ответа портала может означать неполный SLO; из этого нельзя заключить, что сессия самого Keycloak обязательно осталась активной.

Стандартный обмен описан в [OASIS SAML Profiles, раздел 4.4|https://docs.oasis-open.org/security/saml/v2.0/saml-profiles-2.0-os.pdf]. В IdP-initiated сценарии портал отвечает на входящий запрос; 

Отдельный исходящий {{LogoutRequest}} от портала в это сценарии не требуется.

h3. 2. Сообщения и формат передачи.

LogoutRequest и LogoutResponse — XML SAML 2.0, а не JSON API портала. Ключевые данные:
* LogoutRequest: ID, Version, IssueInstant, Issuer; идентификатор субъекта (обычно NameID); SessionIndex при наличии; адрес назначения и временные ограничения согласно контракту.
* LogoutResponse: собственные ID, Version, IssueInstant, Issuer; InResponseTo с ID исходного запроса; Status/StatusCode, включая urn:oasis:names:tc:SAML:2.0:status:Success при успехе.
NameID может быть непрозрачным значением; ФИО, displayname и email не являются его универсальной заменой. 
OASIS Core, §3.2, §3.7; Profiles, §4.4.4.
[https://docs.oasis-open.org/security/saml/v2.0/saml-core-2.0-os.pdf]

Способ упаковки зависит от binding:
* HTTP Redirect: XML → DEFLATE → Base64 → URL encoding; сообщение в параметре SAMLRequest либо SAMLResponse; подпись — SigAlg и Signature.
* HTTP POST через браузер: Base64 XML в поле HTML-формы SAMLRequest либо SAMLResponse; подпись — внутри XML.
* SOAP: XML в SOAP Envelope при прямом серверном обмене; ответ приходит в той же HTTP-транзакции.
RelayState при наличии возвращается в ответе по правилам binding. 
OASIS Bindings, §3.2, §3.4–3.5.
[https://docs.oasis-open.org/security/saml/v2.0/saml-bindings-2.0-os.pdf]

В метаданных SAML адрес и binding выхода описываются SingleLogoutService. Адреса обеих сторон и сертификаты должны соответствовать фактической конфигурации интеграции.
OASIS Metadata, §2.4.
[https://docs.oasis-open.org/security/saml/v2.0/saml-metadata-2.0-os.pdf]

Особенность Keycloak: утверждение «back-channel поддерживается только через POST» нельзя использовать как общее правило. Например, официальный код версии 26.2.5 использует SOAP при настроенном SOAP endpoint и разбирает ответ; иначе предусмотрен legacy POST с SAMLRequest и BACK_CHANNEL_LOGOUT, где тело ответа как LogoutResponse не разбирается. Это пример конкретной версии, не установленная версия ФРП. Для принятого в задаче обмена LogoutRequest/LogoutResponse нужно согласовать совместимый канал; legacy-вариант нельзя молча считать эквивалентным.

h3. 3. Нужно ли дополнительное подтверждение?

Технический ответ портала — *да*: стандартный SAML SLO предусматривает LogoutResponse с результатом обработки. Его отправляет система автоматически, после выполнения локального выхода. Он не заменяется обычной страницей /logout/success или произвольным HTTP 200.

Ещё одно нажатие пользователя на нашем портале — *не требуется*.
