Во вложении материалы по данной постановке.

Текст подготовленной на их основе постановки такой - "*Зависимости:* Требуется тестовый контур AD (от Администратора), настройка интерфейса маппинга (от Frontend-разработчика).

*Описание проблемы:* На данный момент учетные записи пользователей на Аналитическом портале создаются вручную. При успешной LDAP-аутентификации система не синхронизирует профили и права доступа из *Active Directory (AD)*. Необходимо автоматизировать процесс создания новых пользователей и синхронизации прав на основе групп AD.

*Цели задачи:* 
# Реализовать создание локального пользователя при успешном LDAP-bind, если включена соответствующая настройка auto_create_user (уже реализована в других провайдерах) — по умолчанию True. 
# Обеспечить автоматическое назначение/обновление ролей и групп доступа пользователя при каждом входе в систему на основе данных из AD, если включена настройка auto_assign_groups (новый флаг) — по умолчанию True. 

_Важно: флаг auto_assign_groups проверяется и учитывается логикой только при включенном флаге auto_create_user._


*Блок 1.* Автоматическое создание и обновление профиля пользователя;

*Триггер:* Успешная аутентификация пользователя через провайдер LDAP (выполнен успешный bind).
*Логика работы:*
# При успешном bind система запрашивает атрибуты пользователя из AD:
##      objectGUID (или objectSid), 
##      sAMAccountName, 
##      userPrincipalName, 
##      displayName, 
##      givenName, 
##      sn, 
##      mail,
##       memberOf,
##       department,
##       title,
##       userAccountControl.
# Система выполняет поиск пользователя в локальной БД портала по уникальному ключу objectGUID (приоритетно) или sAMAccountName.
*  *Если пользователь найден:* 
**         Система обновляет его базовые атрибуты актуальными данными из AD: отдел (department), должность (title), статус active/disabled (вычисляется из userAccountControl).
**         Дополнительно: права и роли (memberOf) обновляются только при условии, что auto_create_user = True *И* auto_assign_groups = True (см. Блок 2).
* *Если пользователь не найден:*
**         Проверяется значение флага auto_create_user и состояние учетной записи в AD (через атрибут userAccountControl):
***          *Отказ в доступе (403):* Если auto_create_user = false *ИЛИ* учетная запись в AD отключена (флаг UF_ACCOUNTDISABLE в маске userAccountControl).
***          *Создание пользователя:* Если auto_create_user = true *И* учетная запись в AD активна - cоздается новая учетная запись в БД по данным пользователя полученным из AD.
 
*Правила маппинга полей при создании/обновлении*:
*         Логин: login =* sAMAccountName*
*        Почта: email = *mail*
*        ФИО: surname = *sn*, name = *givenName* (если пустые, парсить из displayName)
*       Отдел: department = *department*
*         Должность: position = *title*
*         Внешний ID:  *objectGUID* или objectSid (для надежной связи)
*         Источник:  *LDAP* (пароль в локальной БД не сохраняется)
*         Статус: вычисляется из *userAccountControl* (например, user_state_id = 1 для Active)
*         Срок действия: expiration_date = null (бессрочно)

*Дополнительно:* заполняются данные об организации. Если включен флаг auto_assign_groups = True, происходит маппинг и настройка ролей/прав пользователя по атрибуту *memberOf* (Группы пользователя).


*Блок 2.* Назначение ролей и прав по LDAP-группам (memberOf);

*Триггер:* Успешная аутентификация пользователя через провайдер LDAP *ПРИ УСЛОВИИ* включенных настроек auto_create_user = True *И* auto_assign_groups = True.
*Логика работы:*
#     На стороне бэкенда используется справочник/таблица маппинга (*provider_group*), где сопоставлены *имена групп AD* и *роли/профили* доступа Аналитического *портала*.
#     Система анализирует массив групп из атрибута *memberOf*, полученного из AD.
#     Для каждой группы из *memberOf* выполняется поиск соответствия в таблице маппинга.
#     Синхронизация прав:
#*         Пользователю назначаются *максимальная* роль и все профили доступа, связанные с найденными группами портала.
#*         Группы портала, которые ранее были у пользователя, но больше не числятся в его текущем *memberOf* (с учетом маппинга), должны быть удалены из его профиля.
#     Отсутствие маппинга:
#*         Если ни одна из LDAP-групп пользователя не настроена в таблице маппинга (или memberOf пуст), пользователь авторизуется, но ему назначается базовая роль («Пользователь») и системная папка «Без группы» (то есть он не видит отчетов).
#*         Система должна генерировать оповещение для пользователя: «Обратитесь к администратору для получения расширенных прав».

*Общие требования ко всей реализации (обязательны для всех этапов):*
* Подключение только по LDAPS (TLS 1.2+), пароль никогда *не хранится* локально в БД (поле pswd = null или hash-заглушка). 
* Уникальный ключ привязки к AD — objectGUID (binary → string) или SID (предпочтительно objectGUID). Дополнительно сохраняем dn и userPrincipalName. 
* Все операции с пользователем и группами идемпотентны. 
* При каждом успешном bind (логин + пароль) для пользователя обязательно обновляются атрибуты: отдел (department), должность (title), статус active/disabled (userAccountControl). Состав групп (memberOf) обновляется только с учетом флагов (см. Блок 2). 
* Если auto_create_user = false и пользователь не найден в БД → отказ во входе (403). 
* Соответствие требованиям безопасности: все учётные данные шифруются, логи аудита обязательны (кто/когда создал/обновил права). 
* Возможно потребуется поддержка nested-групп (атрибут tokenGroups вместо простого memberOf) – будет понятно после получения примера данных от клиента.

*Критерии приемки:*
* При включенной настройке auto_create_user новый пользователь успешно создается в БД портала с заполненными атрибутами из AD.
* При выключенной настройке auto_create_user новый пользователь не создается, вход блокируется.
* В локальной БД портала не сохраняются пароли пользователей, авторизующихся через LDAP.
* При каждом успешном входе профиль пользователя (отдел, должность, ФИО, email) обновляется актуальными данными из AD.
* При входе пользователя система корректно парсит атрибут memberOf и, согласно таблице маппинга, выдает соответствующие роли и профили на портале.
* Права пользователя (привязка к локальным группам) синхронизируются строго по AD: лишние удаляются, новые добавляются.
* Пользователь без сопоставленных групп AD авторизуется, но не имеет доступа к бизнес-отчетам (состоит в "Без группы").
* Интеграция работает по защищенному протоколу LDAPS/TLS (требования безопасности выполняются).".

*Требования из ТЗ:*

2. Требования к аутентификации и учетным записям.

2.1. При получении запроса на доступ к объекту, подсистема безопасности требует от субъекта идентифицировать себя, проводит процедуру аутентификации и выполняет процедуру авторизации с использованием параметров хранящихся в таблицах управления доступом. Субъекты имеют доступ только к разрешенным объектам системы.

2.2. Учетные записи IT-решения персонализированны (ставятся в однозначное соответствие конечному пользователю IT-решения). Допускается использование неперсонализированных учетных записей при условии выполнения ими служебных функций (регламентные задания, интеграция со смежными IT-решениями, автоматизированные выгрузки и т.п.).

2.3. Создание и удаление учетных записей субъектов доступа доступно только администратору IT-решения.

2.4. Учетные записи IT-решения соответствуют требованиям Стандарта "на продукт Выполненные требования корпоративных норм информационной безопасности (требования ИБ, предъявляемые к паролям учетных записей пользователей)"

2.5. В части обеспечения управления жизненным циклом учетных записей путем автоматической обработки запросов на создание, удаление, блокировку, разблокировку учетной записи, предусмотрена интеграция с ИС "Управление доступом". Использование IT-решением учетных записей Active Directory является одним из возможных вариантов интеграции данного IT-решения с ИС "Управление Доступом".

2.6. Для информационных систем не поддерживающих сквозную аутентификацию с использованием учетной записи AD должен быть создан шаблон приложения в ИС "Single Sing-On".

2.7. В документах, инициирующих разработку/модернизацию описаны требования, а в проектной/эксплуатационной документации реализация интеграционных механизмов, их структура и цели, которые должны быть достигнуты.

2.8. Информация о служебных и пользовательских учетных записях (логин, пароль) в файлах конфигурации, настроечных файлах, полях БД, реестре и т.п., как на клиентских, так и на серверных компонентах IT-решения храниться в зашифрованном виде.
