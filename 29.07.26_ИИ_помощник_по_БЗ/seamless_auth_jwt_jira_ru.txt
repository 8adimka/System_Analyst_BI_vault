h3. Контекст и цель.

Базовая постановка «Встраивание ИИ-помощника в портал» (см. [https://jira.modusbi.ru/browse/MB-5282], п. 3.4) требует, чтобы пользователь входил в сервис помощника отдельно — по логину и паролю сервиса, внутри боковой панели. Это неудобно: пользователь уже аутентифицирован на портале и получает JWT-токен Modus BI, но должен проходить второй, независимый вход.

*Цель задачи:* научить сервис помощника принимать и проверять JWT-токен портала, чтобы, при наличии действующей сессии на основном портале, панель открывалась сразу с активным диалогом (без формы логина/пароля). Сервис помощника токены не выдаёт — только проверяет; выдача и обновление токена остаются полностью на портале.

Задача является надстройкой над базовой постановкой и оценивается отдельно. При отказе от реализации данной постановки - панель продолжает работать по сценарию с отдельным логином/паролем без изменений.

----

h3. 1. Целевое поведение.

# При открытии панели фронтенд отправляет действующий JWT-токен портала в новый endpoint аутентификации сервиса помощника (без показа формы логина/пароля).
# Сервис помощника проверяет подпись, срок действия, издателя и получателя токена; при успехе извлекает стабильный идентификатор пользователя.
# Если пользователь помощника с этим идентификатором уже существует — сервис привязывает его текущую сессию/диалог; если нет — сервис автоматически создаёт учётную запись помощника при первом обращении, без ручного администрирования.
# Сервис возвращает собственную сессию помощника (как при обычном логине), и далее панель работает по сценариям базовой постановки (диалог, история, вопросы, выход) без изменений.
# Если токен отсутствует, недействителен или просрочен — панель показывает штатную форму логина/пароля из базовой постановки (п. 3.4); бесшовный вход не блокирует резервный сценарий.
# Выход пользователя из Modus BI закрывает панель и завершает сессию помощника (как в базовой постановке, п. 3.4); повторный вход в портал заново инициирует бесшовную проверку токена.
# Изоляция диалогов между пользователями (п. 3.5 базовой постановки) сохраняется: разные пользователи портала не видят историю друг друга ни при бесшовном входе, ни при ручном.

----

h3. 2. Технические требования.

h4. 2.1. Обмен и проверка токена.

* Портал передаёт JWT только напрямую в endpoint помощника по защищённому соединению (TLS); проксирование через BFF рассматривается только если прямой вызов запрещён политикой безопасности (п. 3.8 базовой постановки).
* Проверка подписи — по публичному ключу/JWKS портала (офлайн-валидация) либо через endpoint интроспекции портала, если офлайн-проверка недоступна — выбор фиксируется по результатам технического обследования.
* Токен не сохраняется на бэкенде помощника дольше, чем требуется для проверки и создания собственной сессии; не пишется в логи и телеметрию.
* Фронтенд не хранит JWT портала в {{localStorage}} — токен берётся из текущей сессии Modus BI в момент запроса.
* Ошибки проверки токена возвращают код, аналогичный {{401}} базовой постановки, и приводят к штатному fallback на форму логина/пароля.

***
h4. 2.2. Привязка пользователя и данных.

* Для сопоставления пользователей используется единственный стабильный идентификатор из токена (например, {{sub}} или {{login}}); формат идентификатора фиксируется на техническом обследовании.
* При первом обращении пользователя сервис создаёт учётную запись помощника автоматически; ручной пароль для таких учётных записей не создаётся и не требуется.
* Из токена в сервис помощника передаётся только идентификатор пользователя, необходимый для создания/поиска учётной записи и диалога. Роль, права портала, JWT/cookie сессии портала целиком, отчёт, фильтры и прочий контекст страницы не передаются (соответствует AC.12 базовой постановки).

***
h4. 2.3. Роли и права (минимальный объём первого этапа).

* Для первого этапа вводится один уровень доступа: «пользователь портала с действующим JWT получает стандартный доступ к помощнику», без ролевой дифференциации.
* Дополнительная проверка ролей Modus BI (например, ограничение по группам или тарифам) не реализуется в этой задаче — при необходимости оформляется отдельной подзадачей после появления бизнес-требований к дифференциации доступа.
* Блокировка/отключение доступа конкретного пользователя выполняется на уровне портала (пользователь без действующего JWT не проходит бесшовный вход и получает форму логина/пароля или отказ, если пароль для сервиса помощника не задан).

----

h3. 3. Рамки задачи.

h4. 3.1. Входит в оценку:
* Новый endpoint/режим аутентификации в сервисе помощника, принимающий и проверяющий JWT портала.
* Автоматическое создание учётной записи помощника при первом обращении по токену.
* Доработка фронтенда панели: попытка бесшовного входа перед показом формы логина/пароля, обработка успеха и отказа.
* Обмен ключами/JWKS или настройка интроспекции между порталом и сервисом помощника, включение параметров в конфигурацию поставки (расширение п. 3.9 базовой постановки).
* Обновление документации по безопасности и поставке с учётом нового способа входа.

***
h4. 3.2. Не входит в оценку:
* Ролевая дифференциация доступа и права в разрезе групп/тарифов портала.
* Выдача токенов сервисом помощника (сервис только проверяет токены портала).
* Изменения в базовом сценарии логина/пароля (остаётся как резервный, без изменений).
* Ролевая/платёжная модель централизованного использования LLM.

----

h3. 4. Зависимости и открытые вопросы.

Для оценки необходимо уточнить:
* формат текущего JWT портала, алгоритм подписи, срок действия;
* доступен ли офлайн-способ проверки подписи (JWKS/публичный ключ) или потребуется онлайн-интроспекция;
* поддерживает ли сервис помощника эндпоинт для приёма внешнего токена, либо это также выносится как доработка API;
* правила автосоздания пользователя помощника: какие поля обязательны, нет ли конфликтов с уже существующими вручную созданными учётными записями с тем же логином;

h3. 6. Критерии приёмки (AC):

*AC.1 — Бесшовный вход:*
* Дано: у пользователя действующий JWT портала;
* Когда: он открывает панель помощника;
* Тогда: панель открывается с активным диалогом без формы логина/пароля.

*AC.2 — Fallback при недействительном токене:*
* Дано: JWT отсутствует, невалиден или просрочен;
* Когда: пользователь открывает панель;
* Тогда: отображается штатная форма логина/пароля сервиса помощника (без ошибки интерфейса Modus BI).

*AC.3 — Автосоздание пользователя:*
* Дано: пользователь портала обращается к помощнику первый раз;
* Когда: JWT валиден;
* Тогда: учётная запись помощника создаётся автоматически, без действий администратора.

*AC.4 — Изоляция диалогов:*
* Дано: два разных пользователя портала используют бесшовный вход;
* Когда: каждый открывает панель;
* Тогда: они не видят диалоги друг друга.

*AC.5 — Отсутствие лишней передачи данных:*
* Дано: бесшовный вход выполнен;
* Тогда: сервису помощника не передаются роль пользователя, отчёт, фильтры или сессия портала целиком — только идентификатор, необходимый для проверки и привязки.

*AC.6 — Логаут:*
* Когда: пользователь выходит из Modus BI;
* Тогда: сессия помощника завершается, панель закрывается, повторное открытие требует новой проверки JWT.

*AC.7 — Токен не хранится в браузере:*
* Дано: используется бесшовный вход;
* Тогда: JWT портала не сохраняется в {{localStorage}} на стороне фронтенда панели.
