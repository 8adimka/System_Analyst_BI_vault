h3. Контекст и проблематика.

В Modus BI отсутствует встроенный интерфейс для обращения к ИИ-помощнику — консультанту по базе знаний. Текущий помощник является отдельным сервисом: использует собственный API, собственные учётные записи, RAG-контур с PostgreSQL и векторной базой данных.

Требуется встроить взаимодействие с помощником непосредственно в портал в виде скрываемой боковой панели. Интерфейс чата реализуется средствами Modus BI и взаимодействует с сервисом помощника через API. На первом этапе он будет отвечать на вопросы по документации и базе знаний.

Решение должно поставляться как часть продукта и поддерживать развёртывание в контуре заказчика. Способ размещения, первоначальное наполнение и обновление векторной базы данных выбирается после раздельной оценки предусмотренных вариантов.

В рамках данной постановки пользователь проходит отдельную аутентификацию в сервисе помощника внутри боковой панели. Бесшовная аутентификация через сессии Modus BI оформляется отдельной подзадачей.

----

h3. Цель задачи.

*Требуется:*
# Добавить в шапку портала точку входа в интерфейс ИИ-помощника по базе знаний.
# Реализовать скрываемую боковую панель с собственным интерфейсом чата и интегрировать его с сервисом помощника по API.
# Реализовать в интерфейсе портала вход по логину и паролю сервиса помощника и обеспечить изоляцию диалогов пользователей.
# Отображать в ответах помошника тексты, изображения и ссылки.
# Подготовить сервис помощника и обязательные компоненты к поставке и развёртыванию в контуре заказчика.
# Оценку трудозатрат требуется разделить на общую *обязательную* часть и *альтернативные* варианты размещения/актуализации векторной базы данных.

----

h3. 1. Описание текущего поведения.

* ИИ-помощник по базе знаний не встроен в интерфейс Modus BI.
* Для работы с помощником используется отдельный сервис и отдельная аутентификация.
* В рамках интерфейса портала отсутствует возможность открыть панель чата, управлять диалогом и обрабатывать ответы из API сервиса ИИ-помощника.
* Полный сценарий поставки заказчику включает:
** сервис ИИ-помощника, 
** PostgreSQL, 
** Qdrant.
* Возможности текущего API требуют подтверждения: вход, сессии, диалоги, история, формат текста, источников и изображений, ошибки и сроки хранения.

----

h3. 2. Описание целевого поведения.

# Портал получает из метаданных текущего инстанса признак доступности помощника и базовый URL его API.
# При корректной включённой конфигурации в глобальной шапке отображается кнопка «Помощник».
# По нажатию справа поверх рабочей области открывается боковая панель фиксированной ширины (оверлей). Панель не сдвигает и не сужает содержимое портала — размеры и раскладка нижележащей страницы не меняются. Часть рабочей области, не перекрытая панелью, остаётся полностью интерактивной: пользователь может продолжать просматривать и частично работать с отчётом, дашбордом или другой страницей.
# При отсутствии действующей сессии помощника в панели отображается форма входа с логином и паролем сервиса помощника.
# После успешного входа фронтенд создаёт новый диалог пользователя в текущем браузере или восстанавливает уже активный.
# Пользователь отправляет вопрос. Сервис выполняет поиск по векторному индексу, формирует контекст, обращается к LLM и возвращает финальный JSON-ответ.
# Портал отображает текст ответа, ссылки на изображения и ссылки на использованные статьи базы знаний.
# Закрытие/повторное открытие панели и навигация внутри портала не сбрасывают активный диалог и состояние открытой страницы.
# Пользователь может начать новый диалог и закрыть панель сервиса помощника.
# Ошибка API, истечение сессии, отсутствие релевантных материалов или недоступность изображения обрабатываются внутри панели и не нарушают работу Modus BI.

h3. 3. Требования к реализации.

h4. 3.1. Целевая архитектура.

|| Компонент || Ответственность || Базовое размещение ||
| Фронтенд Modus BI | Кнопка, боковая панель, форма входа, управление диалогом, вызовы API и отображение ответа | Инстанс портала заказчика |
| Метаданные инстанса | Включение функции и адрес API | Инстанс портала заказчика |
| API сервиса помощника | Аутентификация, сессии, диалоги, RAG-пайплайн и формирование ответа | Контур заказчика |
| PostgreSQL помощника | Пользователи, сессии, диалоги, сообщения, состояние индексации | Контур заказчика |
| Qdrant | Векторы фрагментов базы знаний и метаданные источников | По выбранному варианту K1–K3 |
| Индексатор | Получение материалов, чанкинг, построение эмбеддингов и обновление Qdrant | Только для K2 |
| LLM/embedding-провайдер | Эмбеддинг запроса и генерация ответа | Внешний API с реквизитами заказчика; первая поддерживаемая конфигурация — GigaChat |

* Базовый поток: {{браузер → API помощника → PostgreSQL/Qdrant → LLM → API помощника → браузер}}.
* Боковая панель формируется на фронтенде и компонентами Modus BI; веб-интерфейс отдельного приложения помощника в неё не встраивается.
* Локальная поставка работает как одноклиентский инстанс; отдельная сущность организации не требуется.
* В первую поставку входит протестированная работа с GigaChat и ключом заказчика. Другие провайдеры оцениваются отдельно.
* В помощник передаются вопрос и история активного диалога (в соответствии с дотупным API помошника). На данный момент передача данных открытого отчёта, фильтров, наборов данных и сессии Modus BI не планируется.

***

h4. 3.2. Метаданные инстанса.

Конкретные технические имена полей нужно согласовать по действующему контракту Modus BI.

|| Параметр || Тип || Назначение ||
| Признак доступности ИИ-помощника | Логический | Включает кнопку и боковую панель на текущем инстансе |
| Базовый URL API помощника | Строка | Определяет адрес API для фронтенда |

* Функция включена только при логическом {{true}} и валидном URL.
* Отсутствие признака, {{null}}, иной тип или значение, отличное от {{true}}, означает выключенную функцию.
* URL должен быть непустым абсолютным адресом со схемой {{http}} или {{https}}. Портал по {{https}} не должен обращаться к API по {{http}}.
* При выключенной или некорректной конфигурации кнопка не отображается, а ошибки интерфейса отсутствуют.
* Настройки задаются независимо для каждого инстанса.
* В метаданных не хранятся логины, пароли, токены, ключи LLM и реквизиты доступа к базе знаний.
* Дополнительная ролевая проверка Modus BI не добавляется. Фактический доступ определяет сервис помощника после входа.
* В технической оценке определить существующие {{object.name}}, {{command.name}}, путь параметров в ответе и действие, требуемое для повторного получения метаданных.

***

h4. 3.3. Точка входа и боковая панель.

* Разместить кнопку помощника в глобальной шапке рядом с существующими сервисными действиями.
* Использовать текущий стиль кнопок и доступную иконку чата. Для кнопки без текста обязательна подсказка «Помощник по базе знаний».
* Кнопка доступна на экранах с глобальной шапкой, включая главную страницу и просмотр/редактирование отчёта.
* Панель открывается справа поверх рабочей области как оверлей с собственным слоем (z-index), без модального затемнения и без блокировки нижележащего контента. Базовая ширина — около {{420 px}}; ширина и раскладка рабочей области портала под панелью не изменяются.
* На десктопе панель перекрывает только правую часть экрана шириной {{420 px}}; оставшаяся видимая часть рабочей области (отчёт, дашборд, другая страница) остаётся полностью интерактивной — доступны скролл, клики, ввод данных и прочие действия вне зоны, занятой панелью.
* Закрытие панели не требует восстановления ширины рабочей области, так как её размеры не изменялись при открытии; состояние и позиция скролла открытой страницы портала сохраняются без перезагрузки.
* На узком экране панель может занимать до всей доступной рабочей области.
* Панель не должна создавать глобальную горизонтальную прокрутку, не должна вызывать пересчёт раскладки (reflow) рабочей области портала при открытии/закрытии и должна корректно реагировать на изменение размера окна.
* {{Esc}} закрывает панель, если не открыт просмотрщик изображения.

_Состав панели:_

|| Область || Требования ||
| Шапка | «Помощник Modus BI», метка {{BETA}}, «Новый диалог», «Выйти» для авторизованного пользователя, кнопка закрытия |
| Контент | Форма входа, пустое состояние, история активного диалога, ответы и системные сообщения |
| Нижняя область | Многострочное поле вопроса и кнопка отправки; отображаются после входа |

_Основные состояния:_

|| Состояние || Поведение ||
| Требуется вход | Поля «Логин», «Пароль» и кнопка «Войти» |
| Вход выполняется | Поля заблокированы, отображается индикатор |
| Пустой диалог | Краткое описание, примеры вопросов и предупреждение о возможных ошибках ИИ |
| Запрос выполняется | Вопрос уже отображён; повторная отправка заблокирована; отображается процесс обработки |
| Ответ получен | Текст, изображения и сворачиваемый блок источников |
| Материалы не найдены | Предложение уточнить/переформулировать вопрос |
| Ошибка API/сети | Вопрос сохранён; доступно действие «Повторить» |
| Сессия истекла | Локальная сессия очищена; отображается форма входа |
| Изображение недоступно | Заглушка и, при наличии, ссылка на статью |

_Поле вопроса и ответ:_

* {{Enter}} отправляет вопрос, {{Shift+Enter}} добавляет перенос строки.
* Пустой вопрос не отправляется. Во время обработки повторная отправка блокируется.
* Лимит вопроса должен быть одинаковым на фронтенде и бэкенде; ориентир первой версии — {{1000}} символов, итог фиксируется после проверки API.
* При ошибке вопрос остаётся доступным для повторной отправки.
* Отображается только финальный ответ; внутренние рассуждения модели не передаются пользователю.
* Поддержать безопасный поднабор Markdown: абзацы, списки, выделение, код и ссылки. Произвольный HTML не исполняется.
* Предоставить копирование текста ответа.
* Источники показывать в сворачиваемом блоке: название статьи и корректная ссылка, открываемая отдельно с {{noopener}}/{{noreferrer}}.
* Изображения показывать миниатюрами. По нажатию открывать просмотрщик с подписью, масштабированием, переходом между изображениями и закрытием по {{Esc}}.
* Ошибка одного изображения не скрывает текст и остальные источники.
* В пустом состоянии указать, что помощник отвечает по базе знаний, может ошибаться и, в текущей реализации, не видит данные открытого отчёта.

***

h4. 3.4. Аутентификация и пользовательская сессия.

* Аутентификация и авторизация выполняются сервисом помощника по его собственным учётным записям.
* Логин и пароль вводятся в боковой панели и передаются только в endpoint входа помощника по защищённому соединению.
* Портал не передаёт помощнику JWT/cookie Modus BI, пароль портала, роль пользователя или контекст открытой страницы.
* Пароль не сохраняется и не попадает в логи/телеметрию.
* Сервис возвращает собственную сессию или токен. Токены не хранятся в {{localStorage}}; допустимы защищённая {{HttpOnly}}-cookie, память приложения или {{sessionStorage}} в зависимости от текущего API.
* При неверных данных об этом отображается сообщение, пароль очищается.
* При {{401}} локальная сессия очищается и показывается форма входа. При {{403}} отображается отсутствие доступа.
* Действие «Выйти» завершает сессию помощника и очищает локальные данные пользователя.
* При выходе из Modus BI панель закрывается, клиентская сессия помощника очищается; при наличии API logout завершается и серверная сессия.
* В поставке должен быть задокументирован поддерживаемый способ создания, блокировки и сброса пароля пользователя помощника.

***

h4. 3.5. Диалоги и история.

Для первой версии используется один активный диалог на одного пользователя помощника в текущем браузере.

* После входа фронтенд ищет сохранённый {{dialogId}}, привязанный к {{API URL + пользователь помощника}}, и запрашивает историю у API.
* В {{localStorage}} допускается хранить только {{dialogId}} и технический ключ привязки; токены, пароль и тексты сообщений не сохраняются.
* Если диалог отсутствует или истёк, создаётся новый, отображается стандартная стартовая информация нового диалога.
* Закрытие панели и навигация внутри портала не создают новый диалог автоматически.
* Кнопка «Новый диалог» создаёт новый {{dialogId}} и показывает стартовое состояние нового диалога.
* Источник истины для истории — API помощника.
* Вход под другой учётной записью не должен открывать диалог предыдущего пользователя.
* Срок хранения диалогов задаётся сервисом и фиксируется в документации.

***

h4. 3.6. Контракт API и бэкенд помощника.

До разработки необходимо сопоставить требования с текущим Swagger по API. Если возможность отсутствует, доработка включается в оценку бэкенда помощника.

|| Возможность API || Обязательный результат ||
| Вход/выход/проверка сессии | Сессия помощника, текущий пользователь, срок действия, корректные {{401/403}} |
| Создание диалога | Уникальный {{dialogId}} |
| Получение истории | Упорядоченные сообщения активного диалога |
| Отправка вопроса | Приём {{dialogId}}, текста и {{requestId}}; возврат финального ответа |
| Диагностика | {{health/readiness}} и версия API/схемы/активного индекса |

_Минимальная модель ответа:_

|| Поле || Назначение ||
| {{dialogId}}, {{messageId}}, {{requestId}} | Идентификаторы диалога, сообщения и запроса |
| {{answer.text}}, {{answer.format}} | Финальный текст и формат {{markdown/plainText}} |
| {{sources[]}} | Название, URL и идентификатор статьи/раздела |
| {{images[]}} | URL, alt/название, подпись и ссылка на статью |
| {{createdAt}} | Время ответа |
| {{usage}} | Опциональный расход токенов, если доступен |

* Ответ API — JSON. Допускается работа первой версии без стриминга - фронтенд ждёт финальный ответ и показывает единый индикатор. Если активация режима стриминга не потребует серьёзных трудозатрат, предпочтительнее использование режима стриминга.
* Фронтенд и бэкенд используют согласованный конфигурируемый таймаут.
* Ошибки возвращают машинно-читаемый код и безопасный текст. Минимально обрабатываются: неверный запрос, {{401}}, {{403}}, превышение лимита, отсутствующий диалог, таймаут/недоступность LLM или Qdrant, внутренняя ошибка.
* Бэкенд ИИ-помощника должен быть настроен так, чтобы принимать запросы только с тех доменов, которые администратор явно укажет в конфигурации.
* {{requestId}} используется для диагностики и, при поддержке бэкенда, для защиты от дублирования при повторе запроса.

_RAG-пайплайн:_

* Сервис проверяет сессию, получает вопрос и историю активного диалога.
* Embedding вопроса строится той же моделью/версией, что использовалась для активного индекса.
* Параметры поиска в Qdrant задаются конфигурацией сервиса.
* При недостаточном контексте возвращается отдельный результат {{not_found/insufficient_context}}.
* В LLM передаются вопрос, допустимая история и найденные фрагменты с метаданными источников.
* Возвращаются финальный ответ, фактически использованные источники и связанные изображения.
* Ключ GigaChat хранится только на бэкенде помощника.
* PostgreSQL хранит пользователей, сессии, диалоги и сообщения; при K2 — также состояние синхронизации.
* Схема PostgreSQL устанавливается и обновляется версионированными миграциями.
* В логи не попадают пароли, ключи и токены. Для диагностики фиксируются {{requestId}}, длительность, код результата и состояние зависимостей.

***

h4. 3.7. Векторный индекс и актуализация базы знаний.

_Точные требования к индексу (payload, чанкинг, embedding-модель) уточняются по текущей реализации RAG-пайплайна. Ниже — целевая модель, которая должна быть подтверждена в ходе технического обследования._

h5. Три варианта размещения и обновления векторной базы:

* *K1.* Готовый снимок у заказчика (только полное обновление).
Qdrant развёрнут в контуре заказчика. Заказчик не наполняет базу сам — мы поставляем готовый snapshot с manifest, заказчик один раз его разворачивает. Актуальность базы знаний — целиком наша ответственность: когда база знаний меняется, мы собираем новый snapshot и передаём его заказчику. 
Обновление у заказчика — ручная установка новой версии snapshot целиком: старая коллекция не правится, а целиком заменяется на новую, с проверкой перед переключением и возможностью откатиться на предыдущую. Частичных (инкрементальных) обновлений в этом варианте нет — если между поставками snapshot база знаний изменилась, заказчик увидит эти изменения только после установки следующего snapshot.

* *K2.* Локальный Qdrant + локальный индексатор (полное и частичное обновление).
Qdrant *и* индексатор развёрнуты в контуре заказчика. Первичное наполнение можно сделать либо восстановлением из готового snapshot, либо полным импортом силами локального индексатора — выбирается то, что удобнее заказчику. 
Далее есть два режима обновления, и заказчик выбирает, какой поддерживать: 
** (а) ручная полная замена коллекции целиком (как в K1),
** (б) автоматическая инкрементальная синхронизация по расписанию — индексатор сам подтягивает изменённые и удалённые статьи по revision/cursor и обновляет только их. 
За наполнение и актуальность базы в этом варианте отвечает заказчик (точнее, его развёрнутый у себя индексатор), а мы отвечаем за то, чтобы индексатор корректно работал и был совместим с источником базы знаний. Этот вариант требует больше инфраструктуры и работ на стороне заказчика (коннектор к базе знаний, обработка revision, retry, ручной rebuild при сбоях, мониторинг статуса синхронизации), но даёт свежую базу без ручных поставок snapshot.

* *K3.* Централизованный векторный контур на стороне Modus.
Векторная база не покидает инфраструктуру Modus — у заказчика нет ни Qdrant, ни индексатора. 
Сервис помощника заказчика обращается за поиском по защищённому retrieval API или приватному TLS/mTLS-каналу с ограниченными правами; 
административный доступ к Qdrant заказчику не выдаётся. Наполнение, актуальность, версионирование и откат индекса — полностью наша ответственность. 
Мы берём на себя изоляцию клиентов между собой, лимиты, мониторинг, SLA, резервирование и эксплуатационные расходы: недоступность нашего контура — это отказ сервиса помощника у всех подключённых заказчиков, поэтому крайне важна отказоустойчивость.

h5. Сравнение вариантов:

|| Параметр || K1. Snapshot у заказчика || K2. Локальный Qdrant + индексатор || K3. Централизованный контур ||
| Где физически хранится Qdrant | У заказчика | У заказчика | На стороне Modus |
| Кто наполняет базу | Modus (готовит snapshot) | Заказчик (через свой индексатор) | Modus |
| Кто отвечает за актуальность | Modus, по расписанию поставок | Заказчик и его индексатор | Modus |
| Способ обновления | Только полная замена коллекции | Полная замена или инкрементальная синхронизация | Централизованно |
| Нужен ли индексатор у заказчика | Нет | Да | Нет |
| Основная нагрузка по работам | На стороне Modus (сборка snapshot) | На стороне заказчика (коннектор, синхронизация) | На стороне Modus (эксплуатация контура) |
| Административный доступ к Qdrant у заказчика | Есть (локальный) | Есть (локальный) | Отсутствует |

h5. Общие требования к индексу (применимы к K1 и K2, где Qdrant размещён у заказчика):
* Каждый фрагмент содержит стабильный идентификатор статьи и фрагмента, версию/дату статьи, заголовок, путь разделов, URL источника, контрольную сумму, статус публикации, версию чанкинга и embedding-модели.
* Идентификатор точки формируется детерминированно: повторная загрузка обновляет существующий фрагмент, а не создаёт дубликат.
* Изменённые статьи переиндексируются; удалённые или снятые с публикации материалы удаляются из активного индекса.
* Для каждой сборки индекса формируется manifest: версия контента и схемы, версия чанкинга и embedding-модели, размерность, дата сборки, число статей/фрагментов, контрольная сумма.
* Смена embedding-модели, размерности или алгоритма чанкинга требует создания новой коллекции и полной переиндексации — обновление "на месте" не допускается.
* Новая коллекция активируется только после проверки; предыдущая коллекция сохраняется для быстрого отката.
* Ошибка обновления не должна повреждать последнюю рабочую коллекцию — заказчик всегда остаётся с работающим индексом.
* Браузер пользователя не получает прямого доступа к Qdrant ни при одном варианте — все запросы идут через API сервиса помощника.

h5. Дополнительные требования по каждому варианту:
* Для *K1* поставка содержит snapshot, manifest, контрольную сумму и перечень совместимых версий. Обновление выполняется через новую коллекцию с проверкой перед активацией и возможностью откатиться на предыдущую.
* Для *K2* источник базы знаний должен предоставлять полный набор и изменения: стабильный ID, содержимое, URL, revision/updatedAt, статус публикации и признак удаления. Snapshot (если используется для первичного наполнения) и последующая дельта должны использовать одинаковые схему, чанкинг и embedding-модель. Состояние последней успешной синхронизации хранится в PostgreSQL, повторный запуск идемпотентен — повторная синхронизация не создаёт дублей. Если продолжить синхронизацию с revision из manifest нельзя (например, после долгого простоя), выполняется полный rebuild.
* Для *K3* административный API Qdrant не публикуется заказчику напрямую ни в каком виде. Используется только защищённый retrieval API либо приватный TLS/mTLS-канал с минимально необходимыми правами на чтение.


_Выбирается один вариант из K1, K2 или K3 после раздельной оценки трудозатрат._

h4. 3.8. Портальный бэкенд и способ интеграции.

* Признак и URL передаются через существующий механизм метаданных.
* Если контракт уже допускает новые параметры, доработка портального бэкенда не требуется. При расширении контракта обеспечить обратную совместимость.
* Базовый вариант — прямой вызов API помощника из фронтенда с TLS, CORS и собственной сессией помощника.
* Если текущая схема аутентификации или политика безопасности не допускает прямой вызов, отдельно оценить same-origin reverse proxy/BFF в бэкенде Modus BI.
* BFF, если выбран, проксирует вход, диалоги и длительные запросы, не журналирует пароли/токены и корректно обрабатывает таймауты.
* Интеграция с бизнес-объектами Modus BI в этой задаче не создаётся.

h4. 3.9. Поставка, конфигурация и эксплуатация.

_Минимальный состав поставки:_
* пакет/образ API помощника;
* миграции PostgreSQL;
* Qdrant либо требования к совместимой внешней установке;
* индексатор — для K2;
* snapshot и manifest — для K1 (обязательно) и K2 (опционально);
* конфигурация CORS/reverse proxy;
* пример конфигурации без секретов;
* команда первоначальной инициализации и создания пользователя;
* инструкции по установке, обновлению, резервному копированию, восстановлению и диагностике.

_Конфигурация должна включать:_
* подключения PostgreSQL и Qdrant, активную коллекцию/alias;
* LLM/embedding-провайдера, модель, endpoint и ключ;
* источник и расписание базы знаний — для K2;
* разрешённые origin портала;
* сроки жизни сессий/диалогов, таймауты, лимиты и уровень логирования.

* Секреты передаются через поддерживаемый механизм среды развёртывания и не включаются в образ/репозиторий.
* Версии компонентов фиксируются; публикуется совместимость портала, API, схемы PostgreSQL и формата индекса.
* Перезапуск не должен удалять пользователей, диалоги и активный индекс.
* Документация содержит сетевую схему и обязательные исходящие соединения к LLM, базе знаний и изображениям.
* {{health/readiness}} должен различать готовность API, PostgreSQL, Qdrant и обязательных внешних зависимостей.

***

h4. 3.10. Безопасность и устойчивость.

* Производственные соединения с учётными данными, вопросами и ответами выполняются по TLS.
* Markdown, подписи и URL санитизируются. Активными могут быть только разрешённые схемы URL.
* Ключи, пароли и токены не передаются во фронтенд и не возвращаются в ответах.
* Ошибка помощника, БД, LLM или изображения не должна приводить к ошибке глобального интерфейса Modus BI.
* Длительный запрос не блокирует основную область портала.
* Поддерживаются браузеры текущей версии Modus BI, клавиатурная навигация, видимый фокус и доступные подписи полей/иконок.
* На существующих инстансах без новых метаданных функция остаётся выключенной.

h3. 7. Критерии приёмки (AC):

*AC.1 — Функция выключена по умолчанию:*
* *Дано:* новые параметры отсутствуют либо признак не равен {{true}};
* *Когда:* пользователь открывает портал;
* *Тогда:* кнопка помощника не отображается, существующий интерфейс работает без ошибок.

*AC.2 — Независимая конфигурация:*
* *Дано:* на разных инстансах заданы разные значения признака и URL;
* *Когда:* пользователи открывают инстансы;
* *Тогда:* кнопка и адрес API соответствуют конфигурации каждого инстанса.

*AC.3 — Открытие панели:*
* *Дано:* функция включена и URL валиден;
* *Когда:* пользователь нажимает кнопку;
* *Тогда:* справа открывается панель, часть рабочей области (не перекрытая панелью) остаётся полностью интерактивной, а состояние открытой страницы (включая скролл) не сбрасывается.

*AC.4 — Отдельный вход:*
* *Дано:* сессия помощника отсутствует;
* *Когда:* пользователь открывает панель;
* *Тогда:* отображается форма логина/пароля помощника, данные сессии Modus BI для входа не используются.

*AC.5 — Успешный/неуспешный вход:*
* *Дано:* пользователь отправляет учётные данные;
* *Когда:* API подтверждает или отклоняет вход;
* *Тогда:* при успехе доступен активный диалог; при ошибке показано безопасное сообщение, пароль не сохранён.

*AC.6 — Отправка вопроса:*
* *Дано:* пользователь вошёл;
* *Когда:* он отправляет непустой вопрос допустимой длины;
* *Тогда:* вопрос появляется в истории, повторная отправка блокируется, API получает {{dialogId}}, текст и {{requestId}}.

*AC.7 — Ответ, источники и изображения:*
* *Дано:* API вернул успешный JSON;
* *Когда:* фронтенд обрабатывает ответ;
* *Тогда:* безопасно отображаются финальный текст, сворачиваемые источники и миниатюры изображений; ссылки открываются отдельно, изображения доступны в просмотрщике.

*AC.8 — Активный диалог и изоляция:*
* *Дано:* пользователь закрыл/открыл панель или перешёл на другой экран;
* *Когда:* сессия действительна;
* *Тогда:* восстанавливается его активный диалог. Другой пользователь не видит эту историю.

*AC.9 — Новый диалог и выход:*
* *Когда:* пользователь выбирает «Новый диалог» или «Выйти»;
* *Тогда:* создаётся новый {{dialogId}} либо завершается сессия и очищаются локальные данные соответственно.

*AC.10 — Истечение сессии:*
* *Дано:* API возвращает {{401/403}};
* *Тогда:* при {{401}} показывается форма входа, при {{403}} — отсутствие доступа; работа портала не нарушается.

*AC.11 — Нет материалов или недоступна зависимость:*
* *Дано:* поиск не нашёл достаточный контекст либо API/Qdrant/LLM/сеть недоступны;
* *Тогда:* отображается соответствующее состояние и возможность переформулировать/повторить вопрос, исходная страница Modus BI продолжает работать.

*AC.12 — Отсутствие передачи контекста и секретов:*
* *Дано:* пользователь открыл отчёт и обращается к помощнику;
* *Тогда:* помощнику не передаются JWT/cookie Modus BI, роль, идентификатор пользователя портала, отчёт, фильтры или данные; ключ LLM недоступен браузеру.

*AC.13 — Локальная поставка:*
* *Дано:* предоставлены поддерживаемая инфраструктура, конфигурация и ключ GigaChat заказчика;
* *Когда:* администратор выполняет инструкцию чистого развёртывания;
* *Тогда:* API, PostgreSQL и выбранный векторный контур готовы, создан пользователь, портал получает ответ на тестовый вопрос.

*AC.14 — Диагностика и совместимость:*
* *Когда:* администратор запрашивает диагностику;
* *Тогда:* доступны версии API, схемы PostgreSQL и активного индекса, состояние зависимостей и дата/версия базы знаний.

_Дополнительные критерии приёмки для выбранного варианта:_
* *K1:* snapshot восстанавливается в новую коллекцию, проверяется, активируется и допускает откат.
* *K2:* при первичном наполнении из snapshot восстановление проверяется, активируется и допускает откат; полный и инкрементальный импорт обновляют изменённые материалы, удаляют снятые с публикации и не создают дубликаты; синхронизация продолжается с revision из manifest либо запускает полный rebuild при разрыве revision.
* *K3:* запросы разных инстансов изолированы, административный API Qdrant публично не доступен, недоступность центрального контура обрабатывается как ошибка помощника.
