*Бизнес-цель:*
В системе необходимо внедрить обязательное принятие Пользовательского соглашения (EULA) для всех пользователей. 

*Главное архитектурное правило:*
Соглашение должно отображаться строго на *отдельной промежуточной странице ДО выдачи JWT-токена*. 
Пользователь без акцептованного EULA не должен иметь технической возможности обращаться к защищенным методам API с валидным токеном.

---
{panel:title=ВАЖНО: Временные ограничения для коммерческих лицензий (MVP)|borderStyle=dashed|borderColor=#ff9900|bgColor=#fffcf5}
В текущей итерации полноценный флоу показа EULA реализуется *только для триальных лицензий*. 
* Текст соглашения для триальной (_Trial_) лицензии готов: [^EULA_АП_демо_2026.docx].
* Для *коммерческих лицензий* (_Commercial_) применяется механизм *автоакцепта*: EULA пользователю не отображается, явное согласие не запрашивается. При авторизации на коммерческом портале (или при переходе с _Trial_ на _Commercial_) система должна автоматически фиксировать актуальную версию соглашения (_0_) в профиле пользователя и осуществлять бесшовный вход (сразу выдавать JWT-токен).
Разработка и внедрение юридического текста EULA для коммерческих лицензий отложены на следующие этапы.
{panel}

{panel:title=ВАЖНО: Сервисные и интеграционные учётные записи|borderStyle=dashed|borderColor=#0052cc|bgColor=#f0f4ff}
Пользователи, взаимодействующие с системой через API (внешние интеграции, автоматизированные клиенты), а также сервисные учётные записи, используют *стандартный флоу аутентификации* для получения JWT-токена и технически неотличимы на уровне системы от обычных пользователей портала.

Интерактивная страница EULA для таких пользователей *неприменима*.

*Поддерживаемый механизм:* для предоставления API-клиенту возможности получать JWT-токен без прохождения EULA-флоу администратор системы должен *заблаговременно* установить флаг {{skip_eula = true}} в профиле соответствующей сервисной учётной записи. Подробнее — см. раздел «Исключения на уровне учётных записей».

Ответственность за ознакомление API-пользователя с условиями соглашения лежит *за пределами данной постановки* (например, оформляется в рамках партнёрского договора или отдельного онбординг-процесса).
{panel}

h2. Сценарий работы пользователя:
# *Исключения на уровне учётных записей (флаг {{skip_eula}})*.
#* Необходимо реализовать универсальный механизм пропуска всего EULA-флоу для отдельных учётных записей — на основе флага {{skip_eula}} в профиле пользователя (тип: boolean, значение по умолчанию: {{false}}).
#* При значении {{skip_eula = true}} система полностью пропускает все проверки EULA для данной учётной записи и немедленно выдаёт JWT-токен после успешной аутентификации. Промежуточная страница с текстом EULA и кнопками «Принять/Отказаться» *не отображается*.
#* Флаг применяется ко *всем* категориям исключаемых учётных записей, в том числе:
#** *Учётные записи «Публичного доступа» / «Гостевого входа»* — используются для неаутентифицированного доступа внешних лиц (например, просмотр публичных отчётов) и являются общими. Вход под такими учётными записями должен оставаться полностью прозрачным.
#** *Сервисные / интеграционные учётные записи для API-доступа* — используются внешними системами или автоматизированными клиентами, которые физически не могут взаимодействовать с UI-страницей EULA.
#* Идентификация таких учётных записей происходит на стороне сервера на *первом шаге* EULA-проверки — до проверки типа лицензии, версий соглашения и прочих условий.
#* Управление флагом {{skip_eula}} осуществляется исключительно администратором системы через Admin-панель. Пользователь не может самостоятельно изменить значение этого флага.
#* Для учётных записей с {{skip_eula = true}} запись о принятии версии EULA в профиле *не создаётся и не обновляется*.
# Обычный пользователь ({{skip_eula = false}}) проходит первичную аутентификацию одним из доступных способов:
#* Логин/пароль
#* Любой Oauth-провайдер / LDAP
#* Bitrix-интеграция (кнопка «Перейти на портал») и т.д.
# После успешной проверки учётных данных, но *до генерации JWT*, система выполняет EULA-проверку в следующем порядке:
#* *Шаг 3-а (приоритетная проверка):* система проверяет значение флага {{skip_eula}} в профиле пользователя.
#** *Если {{skip_eula = true}}:* все дальнейшие проверки EULA пропускаются. Система немедленно выдаёт JWT-токен. Пользователь бесшовно перенаправляется на целевую страницу.
#** *Если {{skip_eula = false}}:* выполняется переход к шагу 3б.
#* *Шаг 3-б:* система проверяет тип лицензии портала (_Trial_ или _Commercial_) и определяет нужный набор полей для проверки версий EULA.
# Сравнивается текущая мажорная версия EULA на портале (например, {{current_commercial_agreement_version}}) и версия, принятая пользователем ранее (соответственно, {{accepted_commercial_agreement_version}}):
#* *Если текущая версия выше принятой (или пользователь ещё не принял EULA):*
#*# Пользователь маршрутизируется на промежуточную транзитную страницу.
#*# Отображается полный текст EULA (язык в зависимости от текущей локали пользователя) и две кнопки: *«Принять»* и *«Отказаться»*.
#*#* При нажатии *«Отказаться»*: происходит полный _logout_. Пользователя перенаправлять на страницу «Доступ закрыт» (не на страницу авторизации напрямую), чтобы избежать бесконечного редиректа (в том числе внешних провайдеров (Битрикс, LDAP и др.)
#*#* При нажатии *«Принять»*: система сохраняет факт акцепта (обновляет версию в профиле), выдает JWT-токен и пускает пользователя на портал, кнопка «Принять» активируется только после того, как пользователь прокрутил текст до низа (подтверждение факта прочтения).
#* *Если версия актуальна* ({{current_commercial_agreement_version <= accepted_commercial_agreement_version}}): выдается токен, пользователь бесшовно перенаправляется на портал.

Если версия соглашения изменилась, но у пользователя есть действующий JWT-токен — он продолжает работать до следующего входа. Переподписание требуется только при следующей авторизации.

{panel:title=Требования к Backend|borderStyle=dashed|borderColor=#ccc}

* *Хранение и проверка версий:*
** Реализовать целочисленное (мажорное) версионирование соглашения (1, 2, 3...). Минорные версии не поддерживаются. _Любое изменение или исправление = новая мажорная версия._
** В метаданных портала хранить актуальную версию EULA:
*** для типа лицензии _Commercial_ -> {{current_commercial_agreement_version}},
*** для типа лицензии _Trial_ -> {{current_trial_agreement_version}}.
** В профиле пользователя создать поля для хранения принятой версии: 
*** для типа лицензии _Commercial_ -> {{accepted_commercial_agreement_version}},
*** для типа лицензии _Trial_ -> {{accepted_trial_agreement_version}}.
** Сравнение версий должно осуществляться автоматически, с учётом типа лицензии, при каждом входе для *всех* провайдеров авторизации без исключений — при условии {{skip_eula = false}} в профиле пользователя.

* *Флаг пропуска EULA ({{skip_eula}}):*
** В профиле пользователя добавить булево поле {{skip_eula}} (тип: boolean, значение по умолчанию: {{false}}).
** Проверка флага {{skip_eula}} должна быть *первым и приоритетным шагом* в алгоритме EULA-проверки: если {{skip_eula = true}}, все последующие проверки (тип лицензии, сравнение версий) пропускаются, JWT-токен выдаётся немедленно.
** Флаг управляется *исключительно администратором системы* через Admin-панель. Изменение значения флага пользователем (в том числе через API) запрещено.
** Каждое изменение значения флага фиксируется в audit log: идентификатор учётной записи, предыдущее значение, новое значение, время изменения, идентификатор администратора, выполнившего действие.
** Для учётных записей с {{skip_eula = true}} поля {{accepted_commercial_agreement_version}} и {{accepted_trial_agreement_version}} *не создаются и не обновляются*.
** Предустановленные учётные записи «Публичного доступа» и сервисные API-учётные записи должны создаваться с {{skip_eula = true}} по умолчанию.

* *Смена типа лицензии (_Trial_ -> _Commercial)_:*
** Для _Trial_ и _Commercial (Full)_ версий используются разные тексты соглашения (задача: [https://jira.modusbi.ru/browse/MB-3968]).
** Когда тексты соглашений будут готовы, их необходимо _нормализовать_: добавить заголовки, переносы строк, разбивку на параграфы и зафиксировать, в каком формате бэк отдаёт текст (HTML, объект с полями title/paragraphs, или строка с разметкой).
** В случае смены типа лицензии (ключ _Trial_ -> _Commercial_) сравниваются разные поля ({{..._agreement_version}}) в профилях пользователей и в метаданных портала, что должно инициировать повторный показ соглашения в случае смены типа лицензии. Работа пользователей жёстко блокируется (маршрутизация на страницу EULA при следующем входе) до принятия нового текста. *Данное ограничение не распространяется на учётные записи с {{skip_eula = true}}.*

* *Политика White Label (WL):*
** Если портал работает по лицензионному ключу _White Label_, нужно *полностью отключить* механику показа нашего EULA. Данное ограничение является приоритетным — проверка флага {{skip_eula}} в этом режиме не требуется, поскольку EULA-флоу отключён глобально на уровне лицензии.
** Реализация загрузки кастомных текстов соглашения партнером через админку сейчас *не требуется*, но архитектура должна закладывать возможность такого расширения в будущем.
{panel}

{panel:title=Требования к Frontend|borderStyle=dashed|borderColor=#ccc}
* Разработать отдельную изолированную страницу просмотра и акцепта соглашения.
* Страница должна корректно и безопасно функционировать в "транзитном" состоянии — без наличия у клиента JWT-токена в LocalStorage/Cookie.
* *Локализация:* Текст соглашения и интерфейс страницы (кнопки) должны поддерживать несколько локалей и отображаться на языке текущей локали пользователя. Базовый минимум — *Русский и Английский*.
{panel}

h2. Критерии приемки (AC):

* *AC 1: Первичный вход или обновление версии соглашения*
** *Дано:* Пользователь не имеет принятой версии EULA (или, например, {{accepted_commercial_agreement_version < current_commercial_agreement_version}}). Флаг {{skip_eula}} в профиле пользователя равен {{false}}.
** *Когда:* Пользователь успешно проходит аутентификацию (любым способом).
** *Тогда:* JWT-токен не выдается. Пользователь перенаправляется на промежуточную страницу с текстом соглашения на языке его локали и кнопками «Принять» / «Отказаться».

* *AC 2: Успешный акцепт EULA*
** *Дано:* Пользователь находится на промежуточной странице EULA.
** *Когда:* Пользователь нажимает кнопку «Принять».
** *Тогда:* Поле {{..._agreement_version}}, в соответствии с типом лицензии, в профиле пользователя обновляется до актуального. Система выдает JWT-токен и перенаправляет пользователя на главную страницу портала.

* *AC 3: Отказ от принятия EULA*
** *Дано:* Пользователь находится на промежуточной странице EULA.
** *Когда:* Пользователь нажимает кнопку «Отказаться».
** *Тогда:* Токен не выдается. Текущая транзитная сессия уничтожается (_logout_), пользователь перенаправляется на страницу *«Доступ закрыт»* (не на страницу авторизации напрямую — во избежание бесконечного редиректа при использовании внешних провайдеров: OAuth, LDAP, Bitrix и т.д.).

* *AC 4: Вход с уже актуальным соглашением*
** *Дано:* Соответствующее типу лицензии поле в профиле пользователя (например, {{accepted_commercial_agreement_version}}) равно или больше актуальной версии в метаданных портала. Флаг {{skip_eula}} равен {{false}}.
** *Когда:* Пользователь авторизуется.
** *Тогда:* Промежуточная страница не показывается. Пользователь немедленно получает JWT-токен и переходит на портал (бесшовный вход).

* *AC 5: Смена ключа Trial на Full*
** *Дано:* Портал переведен с лицензии _Trial_ на _Commercial_. Пользователь ранее принимал "триальное" соглашение. Флаг {{skip_eula}} в профиле пользователя равен {{false}}.
** *Когда:* Пользователь пытается авторизоваться (или его сессия истекает и он логинится заново).
** *Тогда:* Система распознает смену лицензии и принудительно направляет пользователя на страницу с новым текстом коммерческого EULA. Доступ к порталу заблокирован до акцепта.

* *AC 6: Работа в режиме White Label*
** *Дано:* Портал активирован ключом _White Label_.
** *Когда:* Любой пользователь (включая новых) успешно проходит первичную аутентификацию.
** *Тогда:* Проверка EULA игнорируется полностью (в том числе проверка флага {{skip_eula}} не требуется). Пользователь получает токен и заходит на портал без отображения промежуточной страницы.

* *AC 7: Универсальность способов авторизации*
** *Дано:* Учтены различные провайдеры (любой Oauth, LDAP, интеграция с Bitrix и т.д.). Флаг {{skip_eula}} у пользователя равен {{false}}.
** *Когда:* Пользователь авторизуется через Bitrix по кнопке «Перейти на портал» (или через LDAP).
** *Тогда:* Логика перехвата сессии до выдачи токена и показа EULA отрабатывает идентично стандартной авторизации по логину/паролю.

* *AC 8: Пропуск EULA для учётных записей с флагом {{skip_eula}}*
** *Дано:* В профиле учётной записи установлен флаг {{skip_eula = true}} (учётная запись публичного доступа, сервисная API-учётная запись или любая иная учётная запись, для которой администратор явно включил данный флаг). Портал работает по лицензии Trial.
** *Когда:* Выполняется аутентификация под данной учётной записью (напрямую пользователем, в фоновом режиме системой или автоматизированным API-клиентом).
** *Тогда:* Система на первом шаге EULA-проверки идентифицирует флаг {{skip_eula = true}}. Все дальнейшие проверки EULA пропускаются. Промежуточная страница с текстом EULA не отображается. Учётная запись немедленно получает валидный JWT-токен. В профиле учётной записи запись о принятии версии EULA не создаётся и не обновляется.
