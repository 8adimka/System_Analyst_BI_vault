Какие данные требуются от User Service.

В OIDC основная информация о личности находится в ID Token. Он содержит стандартизированные claims, в частности:

| Claim                | Значение для задачи                                                                     |
| -------------------- | --------------------------------------------------------------------------------------- |
| `iss`                | Кто выдал токен                                                                         |
| `sub`                | Уникальный идентификатор пользователя у данного провайдера                              |
| `aud`                | Какому приложению предназначен токен                                                    |
| `exp`                | Срок действия токена                                                                    |
| `iat`                | Время выдачи                                                                            |
| `preferred_username` | Логин пользователя, если предоставляется                                                |
| `name`               | Отображаемое имя, если предоставляется                                                  |
| `groups` / `roles`   | Возможные нестандартные атрибуты групп и ролей, формат которых определяется реализацией |

Для User Service необходимо получить пример реального обезличенного ответа, чтобы понять, какие атрибуты действительно доступны.

**Лучший идентификатор для сопоставления с учёткой портала — стабильный внешний идентификатор, не зависящий от изменения ФИО, логина или электронной почты.**

В стандартном OIDC таким идентификатором является `sub`, но он уникален в пределах конкретного `iss`. Поэтому правильный ключ привязки — пара:

`(issuer, subject)`

Ещё одна тонкость: OIDC допускает *pairwise subject identifiers*, когда один пользователь получает разные `sub` для разных приложений. Следовательно, `sub`, выданный аналитическому порталу, **не обязательно совпадает с идентификатором того же человека в СВПО**.

Как выполнять сопоставление пользователей.

Рекомендую логически разделить локальную учётную запись и внешнюю идентичность.

```
PortalUser
  id
  login
  status
  ...

ExternalIdentity
  portal_user_id
  provider_code
  issuer
  subject
  linked_at
  ...
```

Тогда каждый пользователь имеет внутренний ID портала, а внешние идентификаторы хранятся отдельно.

Для комбинации `(issuer, subject)` необходимо обеспечить уникальность в пределах активных привязок. Привязка одного внешнего субъекта одновременно к двум действующим локальным пользователям должна приводить к контролируемой ошибке.

**Не рекомендуется автоматически сопоставлять существующие учётные записи только по логину, ФИО или email.** Совпадение таких атрибутов само по себе недостаточно для безопасной привязки.


Если требуется привязка к уже созданному пользователю - администратор заранее записывает проверенный внешний идентификатор к уже существующему пользователю.

При полностью автоматическом создании новых пользователей отдельное окно привязки не требуется.
Автоматическое создание пользователей и управление правами.

Здесь важно не смешивать два самостоятельных процесса:
1) **Provisioning (создание учётной записи)** отвечает на вопрос: «Есть ли у пользователя локальная учётная запись?»
2) **Authorization (управление доступом)** отвечает на вопрос: «Что пользователь может делать в аналитическом портале?»

Для ФКР27 я бы предложил следующие правила как основу постановки.

| Ситуация                                                  | Предлагаемое поведение                                                              |
| --------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Пользователь впервые входит, включено автосоздание        | Создаётся локальная учётная запись с внешней привязкой                              |
| Пользователь впервые входит, автосоздание выключено       | Вход отклоняется, если администратор заранее не создал и не привязал учётную запись |
| Пользователь создан, права назначаются вручную            | Сохраняются права, выданные администратором портала                                 |
| Включена автоматическая синхронизация прав                | Внешние группы сопоставляются с локальными ролями и профилями доступа               |
| У пользователя нет подходящих групп                       | По умолчанию не предоставляется доступ к защищённым ресурсам                        |
| Пользователь заблокирован у провайдера                    | Новые входы запрещены; отдельно определяется отзыв действующих сессий               |
| Внешний идентификатор уже привязан к другому пользователю | Автоматическая привязка блокируется, конфликт направляется администратору           |

Для автоматического назначения прав понадобится отдельная таблица сопоставления:

`ExternalGroupID → PortalRole / PortalProfile`

Группы лучше идентифицировать по неизменяемым ID, если они доступны, а не только по названиям, но реализация планируется по аналогии с уже выполненными схожими работами. Требуется сохранять уже реализованный подход.
