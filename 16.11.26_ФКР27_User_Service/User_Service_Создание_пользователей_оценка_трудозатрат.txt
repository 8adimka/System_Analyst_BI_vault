h3. Контекст и цель.

Последняя информация полученная от заказчика отражена в [родительской постановке|https://jira.modusbi.ru/browse/MB-6447].

На данный момент пользователи переходят из портала ГАСУ в аналитический портал по ссылкам (JWT) с заранее заданными общими учётными записями. Требуется индивидуальный бесшовный вход через User Service и доступ к отчётам по правам фактического пользователя. Переиспользуются существующие провайдеры, внешние привязки и групповое сопоставление с адаптацией независимых режимов создания пользователей и замены прав.

Данная постановка для предварительной оценки трудозатрат; детализация реализации зависит от ожидаемых ответов заказчика в разделе 5.

----
h3. 1. Целевой процесс.

Цель перехода — конкретный отчёт или главная страница аналитического портала — сохраняется после входа. При действующей внешней сессии повторный ввод учётных данных не требуется; при её отсутствии пользователь проходит внешнюю аутентификацию.

User Service может выполнять аутентификацию самостоятельно либо взаимодействовать с отдельным поставщиком удостоверений (IdP). Схема функциональная: протокол и распределение обязанностей внешних компонентов определяются реальным контрактом.

{uml}
sequenceDiagram
    autonumber
    actor U as Пользователь
    participant G as Приват-портал ГАСУ
    participant A as Аналитический портал
    participant E as User Service / IdP
    participant D as БД портала

    U->>G: Выбирает отчёт или главную страницу
    G-->>U: Переход по ссылке на ресурс
    U->>A: Открывает исходный адрес
    Note over A: Сохраняет адрес для возврата после входа

    A->>E: Запрашивает подтверждение внешней личности
    alt Есть действующая внешняя сессия
        Note over U,E: Повторный ввод учётных данных не требуется
    else Внешней сессии нет
        E-->>U: Предлагает пройти аутентификацию
        U->>E: Подтверждает личность
    end
    E-->>A: Результат, внешний ID и доступные атрибуты

    break Личность не подтверждена или ошибка обмена
        A-->>U: Отказ во входе
    end

    Note over A,D: Внешний ID определяет пользователя независимо от прежней локальной сессии
    A->>D: Найти привязку по источнику и внешнему ID
    D-->>A: Найден пользователь / нет привязки / конфликт
    alt Привязка найдена
        Note over A,D: Использовать существующую локальную запись
    else Нет привязки, автосоздание включено
        A->>D: Создать пользователя с внешней привязкой
        D-->>A: Создана локальная учётная запись
    else Нет привязки, автосоздание выключено
        Note over A,D: Нужна предварительная привязка администратором
    else Неоднозначная привязка
        Note over A,D: Автоматический выбор учётной записи запрещён
    end

    break Локальная запись не определена или привязка конфликтует
        A-->>U: Отказ во входе
    end

    A->>D: Проверить статус локального пользователя
    D-->>A: Активен / заблокирован
    break Локальный пользователь заблокирован
        A-->>U: Отказ во входе
    end

    alt Автоматическое назначение прав
        A->>D: Сопоставить внешние группы с ролью и профилями
        D-->>A: Актуализированы роль и профили
    end
    break Ошибка определения обязательных прав
        A-->>U: Отказ во входе
    end

    A->>D: Проверить доступ к запрошенному ресурсу
    D-->>A: Разрешено / запрещено
    alt Доступ разрешён
        A-->>U: Открыть исходный отчёт или главную страницу
    else Доступ запрещён
        A-->>U: Отказ без содержимого отчёта
    end
{uml}

h3. 2. Функциональные требования.

---
h4. 2.1. Идентификация и создание пользователей.

* Предусмотреть провайдер User Service для аналитического портала ГАСУ. Переход должен определять фактического пользователя, в том числе если в браузере уже действует сессия общей или чужой локальной записи. Такая сессия не заменяет подтверждение личности переходящего пользователя.
* Локальная учётная запись и внешняя идентичность различаются логически. Привязка использует стабильный внешний идентификатор с учётом источника идентификации. Изменение логина, ФИО или email не должно создавать дубль или приводить к выбору другой записи.
* Для существующей записи пользователя портала допускается связывание её администратором с внешним пользователем. Иной способ автоматического связывания рассматривается и согласуется отдельно (до согласования, совпадение логина, ФИО или email само по себе не является основанием для автоматического связывания).
* При включённом автосоздании первый вход без привязки создаёт локальную запись с привязкой по внешним данным. Повторный вход использует ту же запись. Состав обязательных данных определяется контрактом интеграции.
* При выключенном автосоздании, допускается использование заранее подготавленной администратором записи пользователя портала с привязкой к пользователю внешней системы. Их отсутствие приводит к отказу во входе без автоматического создания.
* Один внешний субъект одного источника не должен одновременно определять двух действующих локальных пользователей. При конфликте вход прекращается без произвольного выбора записи или автоматической привязки; сведения о конфликте доступны администратору.

---
h4. 2.2. Создание пользователей и назначение прав.

Предусмотреть две независимые настройки: способ создания пользователей и способ назначения прав. Оценка включает все четыре сочетания.

|| Создание пользователей || Назначение прав || Поведение ||
| Автоматическое | Автоматическое | При первом входе создаётся запись с привязкой; роль и профили определяются по внешним группам. |
| Автоматическое | Ручное | При первом входе создаётся запись с привязкой; правами управляет администратор портала. |
| Ручное | Автоматическое | Запись и привязку готовит администратор; роль и профили определяются по внешним группам. |
| Ручное | Ручное | Администратор управляет записью, привязкой и правами. |

* При ручном назначении прав вход через User Service сохраняет назначения администратора.
* При автоматическом назначении после каждого успешного входа, до предоставления отчёта, роль и профили доступа полностью заменяются результатом внешнего сопоставления. Дополнительные ручные назначения, включая персональные разрешения, не сохраняют действие. Персональные объекты пользователя и их содержимое сохраняются.
* Сохранить существующий подход: внешние группы сопоставляются с именами групп настроенного провайдера; по соответствиям определяются роль с действующим приоритетом ролей и связанные профили. Администратор управляет соответствиями средствами портала. Формат внешних групп определяется контрактом User Service.
* При пустом списке групп или отсутствии соответствий применяется базовая роль действующего механизма сопоставления, профили по внешним группам не назначаются. Прежняя роль и ручные назначения не сохраняют доступ к защищённым отчётам.
* Автоматические права обновляются при входе независимо от способа создания пользователей. Фоновая синхронизация не задана.

---
h4. 2.3. Проверка доступа, отказы и восстановление.

* Отчёт предоставляется только после успешного определения локальной записи и её прав. Прямая ссылка не даёт дополнительных прав; при их недостатке портал сообщает об отказе без содержимого отчёта. Другие разрешённые пользователю отчёты остаются доступны.
* Неподтверждённая личность, внешняя или локальная блокировка, недоступность внешней стороны, отсутствие обязательных данных, ошибки идентификации, создания записи или определения автоматических прав не позволяют завершить новый вход. Пользователь получает сообщение о невозможности входа или доступа; общая либо чужая запись не используется как обход ошибки.
* После устранения причины повторная попытка выполняет обычный процесс входа с использованием уже сохранённой привязки без дублирования записи.

----
h3. 3. Зависимости.

Для сквозной проверки необходимы обезличенные примеры обмена, тестовые пользователи с разными правами и пригодный контур интеграции. В плане поставки необходимо учесть обозначенную на встрече зависимость от ранее запланированного рефакторинга аутентификации.

h3. 4. Открытые вопросы:

* Каков фактический контракт User Service: кто выполняет аутентификацию, каковы протокол, стабильный идентификатор с источником, обязательные атрибуты и группы; какой тестовый контур доступен? Ответ заказчика ожидается и определит обмен, данные привязки, ошибки и условия сквозной проверки.
* Каков порядок перехода со старых JWT-ссылок и управления сессиями: сохранение либо отключение ссылок и переходный период, одна либо несколько одновременных сессий, отзыв уже открытых сессий при внешней блокировке? Ответ заказчика ожидается и определит дополнительный объём совместимости и проверок сессий.

h3. 5. Критерии приёмки (AC).

*AC.1. Бесшовный вход.*
* Пользователь переходит из приват-портала ГАСУ на главную страницу или конкретный отчёт аналитического портала.
* При наличии действующей внешней сессии вход выполняется без повторного ввода учётных данных. При её отсутствии пользователь проходит внешнюю аутентификацию.
* После успешного входа открывается исходная страница под учётной записью подтверждённого пользователя, независимо от ранее действовавшей локальной сессии.

*AC.2. Создание и сопоставление пользователей.*
* При автоматическом создании первый вход нового пользователя приводит к созданию локальной учётной записи с внешней привязкой. Повторные входы используют существующую запись без создания дубликатов.
* При ручном создании вход разрешён только пользователям с заранее подготовленной учётной записью и внешней привязкой.
* Изменение логина, ФИО или email не нарушает существующую привязку. При отсутствии необходимой привязки или конфликте идентификаторов вход отклоняется.

*AC.3. Назначение и обновление прав.*
* Поддерживаются все четыре сочетания автоматического и ручного создания пользователей и назначения прав.
* При ручном назначении права, настроенные администратором портала, сохраняются после входа.
* При автоматическом назначении права обновляются при каждом входе на основании внешних групп. Прежние и дополнительные ручные разрешения не предоставляют доступ, если он отсутствует в актуальных назначениях. Персональные объекты пользователя сохраняются.
* При отсутствии подходящих внешних групп применяется базовая роль без ранее предоставленного доступа к защищённым отчётам.

*AC.4. Проверка доступа.*
* Пользователю доступны только отчёты, разрешённые его актуальными правами.
* Переход по прямой ссылке на недоступный отчёт приводит к отказу без раскрытия его содержимого. Остальные разрешённые отчёты остаются доступны.

*AC.5. Обработка ошибок и восстановление.*
* При ошибках аутентификации, блокировке пользователя, недоступности User Service, отсутствии обязательных данных или невозможности определить пользователя и его права вход не завершается.
* Пользователь получает сообщение об ошибке. Вход под общей или чужой учётной записью не допускается.
* После устранения причины повторный вход выполняется штатно, без дублирования существующей учётной записи.
