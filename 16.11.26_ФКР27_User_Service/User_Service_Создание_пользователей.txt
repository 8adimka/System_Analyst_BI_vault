h3. Контекст и проблематика.

На данный момент пользователи переходят из портала ГАСУ в аналитический портал по ссылкам (JWT) с заранее заданными общими учётными записями. Такой вход не обеспечивает достоверную идентификацию фактического пользователя и применение его индивидуальных прав.

----
h3. Цель задачи.

*Требуется:* обеспечить индивидуальный бесшовный вход на аналитический портал ГАСУ через провайдер User Service и обеспечить доступ к отчётам в соответствии с правами пользователя.

----
h3. 1. Текущее поведение.

В существующем механизме внешней аутентификации локальный пользователь может быть связан с внешним идентификатором и конфигурацией провайдера. Назначение роли и профилей по внешним группам в общем потоке зависит от настройки автоматического создания пользователей. При обновлении профилей существующий механизм сохраняет персональные профили.

----
h3. 2. Целевой процесс.

Пользователь, уже авторизованный в приват-портале ГАСУ, переходит по ссылке на главную страницу или конкретный отчёт аналитического портала.

Доверенная инфраструктура ГАСУ подтверждает действующую сессию пользователя и обеспечивает передачу его идентификатора в HTTP-заголовке OAM_REMOTE_USER при обращении к аналитическому порталу.

Аналитический портал получает подтверждённый внешний идентификатор пользователя из доверенного запроса без необходимости повторного ввода логина и пароля.

На основании полученного идентификатора аналитический портал обращается к User Service для получения сведений о пользователе, его группах и ролях.

После получения необходимых данных портал определяет или автоматически создаёт локальную учётную запись, применяет права, создаёт индивидуальную сессию и проверяет доступ к первоначально запрошенному ресурсу.

h3. 3. Требования.

---
h4. 3.1. Подключение и идентификация.

* Предусмотреть провайдер авторизации {{User Service}}, доступный на аналитическом портале ГАСУ. Конкретную схему подтверждения личности и маршрут внешнего входа разработка определяет совместно с сопровождением ГАСУ. Внешние данные принимаются только из доверенного источника; клиентский идентификатор сам по себе не подтверждает личность.
* В качестве внешнего идентификатора пользователя использовать значение, полученное из доверенного HTTP-заголовка OAM_REMOTE_USER. Данное значение передавать в параметре userId методов SOAP API User Service.
* При получении данных пользователя проверять согласованность идентификатора из доверенного заголовка с идентификатором пользователя, возвращённым User Service. Конкретное поле ответа, используемое для проверки, определяется по контракту API.
* Для поиска локальной учётной записи использовать сочетание идентификатора внешнего провайдера и стабильного внешнего ID пользователя. При отсутствии соответствующей записи автоматически создавать новую локальную учётную запись и сохранять привязку к внешнему идентификатору.
* При последующих входах использовать ранее созданную локальную учётную запись. Изменение логина, ФИО или email не должно приводить к созданию дубликата или изменению внешней привязки. Актуальные сведения пользователя могут обновляться на основании данных User Service.
* Администратор может подтвердить привязку существующей индивидуальной учётной записи к внешнему пользователю. Одного совпадения логина, ФИО или email для автоматической привязки недостаточно. Один внешний пользователь одного источника не должен определять несколько локальных записей; при конфликте вход отклоняется без произвольного выбора. Сведения о конфликте доступны администратору.
* Заблокированный локальный пользователь не может войти. При невозможности подтвердить личность, получить обязательные данные, определить или создать запись вход не завершается; пользователь получает об этом понятное сообщение. После устранения причины повторный вход выполняется без создания дубликата.

---
h4. 3.2. Автоматическое назначение прав.

Для провайдера User Service предусмотреть автоматическое назначение прав доступа пользователей аналитического портала на основании актуальных групп и ролей, полученных из User Service.

* Администратор аналитического портала настраивает соответствия между внешними группами и ролями ГАСУ и внутренними ролями и профилями доступа Modus.
* При входе пользователя портал получает актуальные группы и роли через методы getUserGroups и getUserRoles и определяет внутренние назначения на основании настроенных соответствий.
* Если одновременно совпадает несколько настроенных соответствий, профили доступа из них объединяются. Внутренняя роль определяется по предварительно согласованному правилу приоритета ролей Modus.
* Полученные назначения применяются как к автоматически созданным, так и к ранее существовавшим локальным пользователям, связанным с соответствующим внешним идентификатором.
* При каждом входе после подтверждения личности пользователя и получения актуальных данных User Service портал пересчитывает и применяет права до предоставления доступа к запрошенному ресурсу.
* Ранее сохранённые локальные назначения не должны предоставлять дополнительные права сверх результата актуального сопоставления с внешними ролями и группами. При этом личные объекты пользователя и их содержимое сохраняются.
* Если внешние группы и роли успешно получены, но настроенные соответствия отсутствуют, пользователю назначается базовая пользовательская роль без профилей доступа.
* Если получить обязательные сведения о группах или ролях либо определить необходимые назначения не удалось вследствие ошибки интеграции, вход не завершается. Ошибку получения данных нельзя трактовать как отсутствие у пользователя внешних назначений.

Автоматическое назначение прав должно работать независимо от механизма создания локальных пользователей.

Конкретные соответствия внешних ролей и групп внутренним назначениям Modus согласовываются с заказчиком.

---
h4. 3.3. Доступ и сессии.

Портал проверяет права на запрошенный отчёт после определения пользователя портала. Прямая ссылка не предоставляет дополнительных прав. При недостаточных правах показывается соответствующий экран ошибки без содержимого отчёта; другие разрешённые отчёты остаются доступны.

При внедрении бесшовной аутентификации допускается временное сохранение действующего механизма входа по JWT-ссылкам на период разработки, тестирования и перехода на индивидуальные учётные записи.

После успешного внедрения и приёмки нового механизма вход по прежним JWT-ссылкам под общими учётными записями должен быть отключён. Порядок отключения и необходимые миграционные действия согласовываются с заказчиком.

При бесшовном входе каждый пользователь должен идентифицироваться индивидуально на основании подтверждённого внешнего идентификатора ГАСУ.

Политика одновременных сессий аналитического портала сохраняется действующей до принятия отдельного решения о её изменении. Наличие нескольких одновременных сессий не должно приводить к подмене индивидуальной учётной записи пользователя.

h3. 5. Критерии приёмки (AC):

AC.1 — *Бесшовный переход:*
* *Дано:* пользователь ГАСУ с действующей внешней сессией имеет доступ к отчёту; в браузере может быть открыта локальная сессия другого пользователя.
* *Когда:* он переходит из приват-портала на отчёт или главную страницу аналитического портала.
* *Тогда:* портал определяет пользователя ГАСУ, выполняет вход без повторного ввода учётных данных и открывает исходный разрешённый ресурс под его индивидуальной записью.

AC.2 — *Получение подтверждённого идентификатора пользователя:*
* *Дано:* пользователь имеет действующую сессию ГАСУ и переходит по ссылке на аналитический портал.
* *Когда:* запрос поступает на аналитический портал через доверенную инфраструктуру ГАСУ.
* *Тогда:* аналитический портал получает подтверждённый внешний идентификатор пользователя из заголовка OAM_REMOTE_USER и использует его для получения сведений через SOAP API User Service; идентификатор, переданный непосредственно клиентом в обход доверенной инфраструктуры, не принимается в качестве подтверждения личности.

AC.3 — *Создание и повторный вход:*
* *Дано:* подтверждённый внешний пользователь не имеет привязки к локальной записи.
* *Когда:* он входит впервые, а затем повторяет вход, в том числе после изменения логина, ФИО или email.
* *Тогда:* при первом входе создаются одна локальная запись и привязка; при последующих используется та же запись без дубля.

AC.4 — *Существующая запись и конфликт:*
* *Дано:* существует индивидуальная учётная запись аналитического портала, которую требуется связать с внешним пользователем.
* *Когда:* администратор подтверждает привязку, а затем внешний пользователь входит на портал.
* *Тогда:* используется привязанная запись. Совпадение одного логина, ФИО или email без подтверждённой привязки не связывает записи автоматически. При конфликте привязок вход отклоняется, сведения о конфликте доступны администратору.

AC.5 — *Автоматическое назначение и актуализация прав:*
* *Дано:* пользователь имеет локальную учётную запись аналитического портала, ранее назначенную роль и профили доступа. Для внешних ролей и групп настроены соответствия с внутренними назначениями Modus.
* *Когда:* пользователь повторно входит через провайдер User Service, а состав его внешних ролей или групп изменился.
* *Тогда:* портал получает актуальные внешние назначения, пересчитывает и применяет внутреннюю роль и профили доступа до открытия запрошенного ресурса.
* *И:* ранее сохранённые локальные назначения не расширяют доступ сверх результата актуального сопоставления. Личные объекты пользователя и их содержимое сохраняются.

AC.6 — *Нет совпадений и ошибка получения прав:*
* *Дано:* включён автоматический режим прав, ранее пользователю были назначены роль и профили доступа.
* *Когда:* внешний набор успешно получен и пуст либо не содержит настроенных совпадений.
* *Тогда:* пользователь входит с базовой пользовательской ролью без профилей доступа; прежние назначения не расширяют его доступ.
* *И:* если обязательные данные прав получить или определить не удалось, вход не завершается и показывается сообщение; после устранения причины повторный вход возможен.

AC.7 — *Проверка доступа:*
* *Дано:* пользователь имеет доступ к одному отчёту, но не имеет доступа к другому.
* *Когда:* он открывает прямую ссылку на недоступный отчёт.
* *Тогда:* отображается отказ без содержимого отчёта; разрешённый отчёт остаётся доступен.

AC.8 — *Отказ и восстановление:*
* *Дано:* личность не подтверждена, внешний сервис недоступен, обязательные данные отсутствуют, локальный пользователь заблокирован либо запись нельзя определить или создать.
* *Когда:* пользователь пытается войти.
* *Тогда:* вход не завершается, показывается сообщение, общая или чужая запись не используется. После устранения причины повторная попытка выполняется без дублирования существующей привязки.

AC.9 — *Индивидуальные сессии:*
* *Дано:* пользователь ГАСУ имеет индивидуальную локальную учётную запись аналитического портала.
* *Когда:* пользователь выполняет бесшовный вход, в том числе при наличии ранее открытой сессии аналитического портала.
* *Тогда:* вход выполняется под локальной учётной записью, связанной с подтверждённым внешним идентификатором ГАСУ. Использование существующей сессии общей или другой учётной записи не должно приводить к подмене личности пользователя.
* *И:* применяется действующая политика одновременных сессий аналитического портала.

AC.10 — *Отключение прежнего механизма входа:*
* *Дано:* новый механизм бесшовной аутентификации успешно внедрён и принят заказчиком, отключение прежнего механизма выполнено.
* *Когда:* пользователь открывает старую JWT-ссылку, ранее обеспечивавшую вход под общей учётной записью.
* *Тогда:* вход под общей учётной записью по данной ссылке не выполняется.

AC.11 — *Несколько совпадений прав:*
* *Дано:* включён автоматический режим прав; два внешних значения пользователя сопоставлены соответственно с пользовательской ролью и профилем доступа A и с ролью администратора и профилем доступа B.
* *Когда:* пользователь входит через User Service и оба соответствия совпадают.
* *Тогда:* назначается роль администратора согласно действующему приоритету ролей портала, а профили доступа A и B объединяются.
