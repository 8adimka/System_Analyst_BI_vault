# Подготовка постановки

Применяй при запросе написать постановку, тикет, баг или требования. Прочитай `agent-system/standards/jira-style.md` и `requirements-quality.md`; предметные проверки выбирай из `.private/knowledge/legacy/domain-checks.md` только по теме задачи.

Определи тип: дефект/регрессия, продуктовая или техническая доработка, архитектура, интеграция, данные, фильтрация, визуализация, метаданные или интерфейс. Восстанови проблему, роль, текущее/целевое поведение, ценность, рамки и затронутые объекты по материалам и коду. Сохраняй точные технические имена; не переноси контракт из похожей задачи без проверки.

Сформулируй цель через наблюдаемый результат. Опиши только применимые фронтенд/бэкенд/данные/API/SQL/права/совместимость. Дай предусловия, существенные правила, жизненный цикл, негативные сценарии и данные для проверки. AC должны проверять требования, а не вводить скрытую бизнес-логику. Для бага включи воспроизведение и окружение либо явные пробелы.

Адаптируй шаблон к масштабу: компактный текст, h3., обычные списки, технические имена в {{...}}, последовательные AC с Дано/Когда/Тогда. Убери дубли и пустые разделы. Не оборачивай документ в Markdown/код. Неоднозначности вынеси в «Открытые вопросы». В evidence сохрани путь/символ/версию для важных фактов, не перегружая постановку исследовательскими логами.

Перед передачей текста выполни проверку «Ясность и редактура» из `agent-system/standards/requirements-quality.md`: проверь локальную однозначность названий и сокращений, удали логические повторы и нерелевантные уточнения, сохрани условия и различия состояний. Повтор предметного названия допустим, если он устраняет двусмысленность.

Результат — полный текст постановки и отдельные evidence/questions/change_log по схеме координатора; никаких файлов агент самостоятельно не записывает.
