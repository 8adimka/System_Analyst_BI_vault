h3. 1. Цель и контекст.

В рамках задачи [MB-4513|https://jira.modusbi.ru/browse/MB-4513] для редактора SQL в карточке *произвольного набора данных* реализуется расширенный режим с левой панелью +метаданных+ для выбранного Источника.

Для полноценной работы этой панели frontend должен получать не только сведения о наборах данных, но и фактические метаданные источника данных: список обычных пользовательских таблиц и {{view}} с указанием схем, а также поля и типы одного или нескольких объектов.

Существующий функционал портала ограничивает frontend информацией о наборах данных. Для сценария, описанного в задаче MB-4513, этого недостаточно, потому что набор данных является производной сущностью и не всегда отражает актуальное состояние таблиц Источника. При изменениях в источнике или правилах работы с источником frontend не получает полную картину доступных таблиц и полей, из-за чего нельзя корректно построить дерево метаданных, производить автодополнение и вставку объектов источника в SQL/вычисляемые выражения.

*Цель задачи* — реализовать на backend API для получения (read-only) метаданных объектов источника данных и их полей, чтобы frontend мог использовать эти данные в дереве метаданных, автодополнении и вставке объектов источника в редактор {{CodeMirror}}.

На текущем этапе через новый контракт должны предоставляться обычные пользовательские таблицы и {{view}}. Универсальная структура контракта должна позволять в дальнейшем расширять перечень поддерживаемых объектов без изменения базового формата взаимодействия.

{panel:title=Ключевой принцип backend-доработки|borderStyle=dashed|borderColor=#ccc|titleBGColor=#DDEBF7|bgColor=#F8FBFF}
* API должно возвращать именно метаданные объектов выбранного источника данных — в рамках настоящей задачи таблиц и {{view}}, — а не список наборов данных и не результат последней проверки SQL-запроса.
* API должно быть доступным +только на чтение+: в рамках задачи не требуется создавать, изменять, удалять таблицы или загружать строки данных.
* Внешний backend-объект API — {{datasources}}, так как объекты метаданных запрашиваются в контексте конкретного источника данных.
* Необходимые команды — {{metadata.object.list}} и {{metadata.object.get}}.
* Идентификатор источника данных передаётся в {{object.id}}.
* Для каждого поля backend должен возвращать нормализованный {{type}} и исходный {{source_type}} по правилам настоящей постановки.
* API должно сохранять существующую бизнес-логику произвольного набора данных: проверку SQL, обновление выходных полей и сохранение формы.
{panel}

----
h3. 2. Описание текущего поведения.

h4. 2.1. Ограничение доступных метаданных.

Сейчас frontend портала может работать с метаданными наборов данных, но не имеет достаточного backend-контракта для прямого получения:
* списка обычных пользовательских таблиц и {{view}} выбранного источника данных с указанием схем;
* списка полей и их типов для одного или нескольких объектов.

Из-за этого левая панель метаданных в расширенном редакторе SQL не может строиться на актуальном состоянии таблиц источника. Frontend вынужден использовать датасеты или другие косвенные данные, которые не покрывают целевой сценарий полностью.

----
h4. 2.2. Почему сведений о датасетах недостаточно.

Набор данных описывает пользовательский слой для построения отчётов и визуализаций. При этом в произвольном SQL пользователь может обращаться к таблицам источника данных напрямую, до создания набора данных на каждую таблицу или независимо от него.

Проблемный сценарий:
# Пользователь открывает карточку *произвольного набора данных* и пишет SQL в расширенном редакторе.
# Frontend определяет источник данных, выбранный в карточке набора данных.
# Frontend не может показать актуальные таблицы и поля источника.
# Пользователь не получает полноценное дерево метаданных, автодополнение и корректную вставку полей в SQL/вычисляемые выражения.

----
h3. 3. Описание целевого поведения.

h4. 3.1. Общая логика работы.

После доработки backend должен предоставить frontend возможность получать актуальные метаданные объектов выбранного источника данных.

Целевой сценарий:
# Frontend открывает расширенный редактор SQL в карточке *произвольного набора данных*.
# Frontend определяет текущий источник данных из контекста карточки набора данных.
# Frontend вызывает существующую команду {{datasources.list}}, если требуется получить или уточнить идентификатор источника.
# Frontend вызывает команду {{metadata.object.list}}, передавая идентификатор источника в {{object.id}}, и получает обычные пользовательские таблицы и {{view}} текущей базы данных из доступных пользовательских схем.
# Frontend строит дерево с учётом {{name}}, {{schema}} и {{type}} каждого объекта.
# При раскрытии одного или нескольких объектов frontend вызывает batch-команду {{metadata.object.get}} и передаёт в {{data[]}} пары {{name}} + {{schema}}.
# Backend независимо обрабатывает элементы запроса и для каждого успешно полученного объекта возвращает его фактический тип и массив полей с {{name}}, нормализованным {{type}} и исходным {{source_type}}.
# Frontend использует полученные данные для дерева метаданных, автодополнения и вставки имён таблиц, {{view}} и полей в редактор {{CodeMirror}}.

Метаданные объектов должны быть доступны без предварительного выполнения действия {{«Проверить запрос»}} и без зависимости от результата последней успешной проверки SQL.

----
h4. 3.2. Источник истинности для дерева метаданных.

Источником истинности для левой панели расширенного редактора SQL должны быть *метаданные объектов выбранного источника данных* — в рамках настоящей задачи таблиц и {{view}}.

Не должны использоваться как единственный источник данных для этой панели:
* выходные поля текущего SQL-запроса;
* список существующих наборов данных;
* результат последней проверки SQL;
* сохранённые поля произвольного набора данных.

Эти сущности могут оставаться частью текущей бизнес-логики набора данных, но не должны подменять новый backend-контракт {{metadata.object.list}} / {{metadata.object.get}}.

----
h4. 3.3. Применимость для обычной и облачной версии портала.

Данная доработка должна быть доступна как для обычной версии портала, так и для облачной, где также в рамках задачи MB-4513 реализуется дерево метаданных для использования в новом редакторе кода.

Решение должно быть универсальным: frontend получает метаданные объектов напрямую из источника данных и не зависит от того, создан ли для соответствующих таблиц отдельный набор данных.

----
h3. 4. Рамки задачи.

h4. 4.1. Входит в рамки задачи.

В рамках данной задачи требуется:
* реализовать команду {{metadata.object.list}} для получения списка обычных пользовательских таблиц и {{view}} выбранного источника данных;
* реализовать batch-команду {{metadata.object.get}} для получения полей одной или нескольких таблиц / {{view}};
* возвращать для объекта {{name}}, {{schema}}, {{type}}, {{error}} и поля с {{name}}, {{type}}, {{source_type}};
* нормализовать типы полей на backend по единому enum {{number}}, {{string}}, {{date}}, {{undefined}};
* реализовать правила состава объектов, схем, ошибок и нормализации типов SQLite и ClickHouse, зафиксированные в настоящей постановке;
* обеспечить работу контракта для сценария расширенного SQL-редактора в *произвольном наборе данных*;
* обеспечить аналогичную доступность контракта в облачной версии портала, если источник данных поддерживает чтение метаданных объектов;
* сохранить текущие механики чтения источников данных через существующую команду {{datasources.list}};
* сохранить существующую бизнес-логику проверки SQL, обновления выходных полей и сохранения набора данных.

----
h3. 5. API-контракт.

h4. 5.1. Общие требования к формату API.

Структура запросов и ответов должна соответствовать актуальному контракту [^Дерево_метаданных_контракты_команд_2.txt].

* Обе команды используют {{object.name = "datasources"}}.
* Идентификатор выбранного источника данных передаётся в {{object.id}}.
* {{command.id}} для идентификации источника не используется.
* Команды имеют точные имена {{metadata.object.list}} и {{metadata.object.get}}.
* Для имени объекта метаданных используется универсальное поле {{name}}.
* В рамках настоящей задачи поддерживаются объекты типов {{table}} и {{view}}. Поддержка иных типов объектов не входит в рамки задачи.
* Успешный ответ содержит {{data}} в структуре, определённой настоящим разделом.
* Общая транспортная обёртка ответа и HTTP-статусы должны соответствовать действующему протоколу портала и не изменяются в рамках данной задачи.

Примеры ниже фиксируют значимую для доработки структуру {{object}}, {{command}} и {{data}}.

----
h4. 5.2. Определение ID источника данных.

Frontend определяет идентификатор выбранного источника из контекста карточки набора данных. При необходимости может использоваться существующая команда {{datasources.list}}; её контракт в рамках данной задачи не меняется.

Полученный идентификатор передаётся как {{object.id}} в запросах {{metadata.object.list}} и {{metadata.object.get}}.

----
h4. 5.3. Команда {{metadata.object.list}}.

Команда должна возвращать список объектов метаданных текущей базы данных, настроенной в выбранном источнике данных.

В рамках настоящей задачи список включает обычные пользовательские таблицы и {{view}}.

*Запрос:*
{code:json}
{
  "object": {
    "name": "datasources",
    "id": 123
  },
  "command": {
    "name": "metadata.object.list"
  }
}
{code}

*Параметры запроса:*
|| Поле || Обязательность || Описание ||
| {{object.name}} | Да | Значение {{datasources}}. |
| {{object.id}} | Да | Идентификатор выбранного источника данных. |
| {{command.name}} | Да | Значение {{metadata.object.list}}. |

*Успешный ответ:*
{code:json}
{
  "data": [
    {
      "name": "fact_sales",
      "schema": "public",
      "type": "view"
    },
    ...
  ]
}
{code}

*Поля ответа:*
|| Поле || Тип || Обязательность || Описание ||
| {{data[]}} | array | Да | Список доступных объектов метаданных текущей базы данных. |
| {{data[].name}} | string | Да | Оригинальное имя объекта без префиксов и изменения регистра. |
| {{data[].schema}} | string | Да | Имя схемы размещения объекта; для источников без схем или объектов уровня базы данных возвращается пустая строка. |
| {{data[].type}} | string | Да | Тип объекта: {{table}} или {{view}}. |

*Состав списка:*
|| Категория объекта || Включать || {{data[].type}} ||
| Обычная пользовательская таблица | Да | {{table}} |
| Обычный {{view}} | Да | {{view}} |
| {{materialized view}} и иные специальные виды представлений | Нет | — |
| {{foreign table}} / {{external table}} как отдельный класс объекта СУБД | Нет | — |
| Временная таблица | Нет | — |
| Системная таблица или системное представление | Нет | — |

*Требования к результату:*
* возвращаются объекты только из текущей базы данных, настроенной в выбранном источнике;
* возвращаются объекты из всех доступных пользовательских схем текущей базы с учётом прав учётной записи подключения к СУБД;
* системные схемы и системные объекты не возвращаются;
* наличие, отсутствие и состав первичного ключа не влияют на включение объекта;
* объекты других баз данных не возвращаются; это ограничение относится только к дереву метаданных и не запрещает ручное обращение к другой базе в SQL, если СУБД и права подключения это допускают;
* {{name}} и {{schema}} возвращаются отдельно, без добавления префиксов и без изменения регистра;
* таблица и {{view}} различаются только через {{type}}; изменять имя объекта для визуального различения нельзя;
* для СУБД с реальными схемами в {{schema}} возвращается имя схемы;
* для источников без схем или объектов уровня базы данных в {{schema}} возвращается пустая строка;
* для SQLite возвращаются только объекты основной базы {{main}}, при этом {{schema = ""}}; объекты {{temp}} и баз, подключённых через {{ATTACH}}, не включаются;
* для ClickHouse возвращается {{schema = ""}}, поскольку текущая база определяется выбранным источником данных;
* если доступных объектов нет, команда успешно возвращает {{data = []}};
* {{name}} не должно быть пустым; одинаковая пара {{name}} + {{schema}} не должна дублироваться в ответе;
* порядок объектов должен быть стабильным при неизменном состоянии источника;
* команда не возвращает поля, строки данных, параметры подключения и секреты.

----
h4. 5.4. Команда {{metadata.object.get}}.

Команда должна пакетно возвращать метаданные одной или нескольких обычных таблиц / {{view}} выбранного источника данных.

*Запрос:*
{code:json}
{
  "object": {
    "name": "datasources",
    "id": 123
  },
  "command": {
    "name": "metadata.object.get"
  },
  "data": [
    {
      "name": "fact_sales",
      "schema": "public"
    },
    {
      "name": "dim_customers",
      "schema": "public"
    },
    ...
  ]
}
{code}

*Параметры запроса:*
|| Поле || Обязательность || Описание ||
| {{object.name}} | Да | Значение {{datasources}}. |
| {{object.id}} | Да | Идентификатор выбранного источника данных. |
| {{command.name}} | Да | Значение {{metadata.object.get}}. |
| {{data[]}} | Да | Массив запрашиваемых объектов. |
| {{data[].name}} | Да | Значение {{name}} из ответа {{metadata.object.list}}. |
| {{data[].schema}} | Да | Значение {{schema}} из ответа {{metadata.object.list}}, включая пустую строку для источников без схем или объектов уровня базы данных. |

*Ответ для таблиц и представлений:*
{code:json}
{
  "data": [
    {
      "name": "fact_sales",
      "schema": "public",
      "type": "view",
      "error": null,
      "fields": [
        { "name": "salary", "type": "number", "source_type": "UInt32" },
        ...
      ]
    },
    {
      "name": "dim_customers",
      "schema": "public",
      "type": null,
      "error": "not_found",
      "fields": null
    },
    ...
  ]
}
{code}

*Поля ответа:*
|| Поле || Тип || Обязательность || Описание ||
| {{data[]}} | array | Да | Результаты обработки запрошенных объектов. |
| {{data[].name}} | string | Да | Имя объекта из соответствующей пары запроса. |
| {{data[].schema}} | string | Да | Схема объекта из соответствующей пары запроса. |
| {{data[].type}} | string / null | Да | При успехе — фактический тип объекта {{table}} или {{view}}; при ошибке элемента — {{null}}. |
| {{data[].error}} | string / null | Да | {{null}} при успехе либо код ошибки элемента. |
| {{data[].fields}} | array / null | Да | Поля объекта при успехе; при ошибке элемента — {{null}}. |
| {{data[].fields[].name}} | string | Да для успешного элемента | Оригинальное имя поля. |
| {{data[].fields[].type}} | string | Да для успешного элемента | Нормализованный тип: {{number}}, {{string}}, {{date}} или {{undefined}}. |
| {{data[].fields[].source_type}} | string | Да для успешного элемента | Исходный тип СУБД без приведения. |

*Требования к результату:*
* команда должна получать поля как обычной таблицы, так и обычного {{view}}, возвращённого {{metadata.object.list}};
* пара {{name}} + {{schema}} является идентификатором объекта в рамках batch-запроса;
* каждый элемент обрабатывается независимо: ошибка одного объекта не прерывает обработку остальных;
* при {{error != null}} поля {{type}} и {{fields}} возвращаются как {{null}};
* дублирующаяся в запросе пара {{name}} + {{schema}} возвращается в ответе один раз;
* если обработка дубликатов дала успешный и ошибочный результаты, возвращается успешный результат с {{error = null}};
* предварительный вызов {{metadata.object.list}} не требуется, если frontend уже знает корректные {{object.id}}, {{name}} и {{schema}};
* для успешно полученного объекта {{fields}} возвращается массивом, в том числе пустым;
* {{fields[].name}} не должно быть пустым, поля с одинаковым {{name}} в рамках одного объекта не должны дублироваться;
* порядок полей должен быть стабильным при неизменном состоянии объекта;
* команда не возвращает строки данных, параметры подключения и секреты.

----
h4. 5.5. Требования к типам полей.

Для каждого поля успешно полученного объекта backend возвращает:
* {{type}} — нормализованную информационную классификацию;
* {{source_type}} — исходный тип СУБД без приведения.

Enum {{fields[].type}}:
* {{number}};
* {{string}};
* {{date}};
* {{undefined}}.

Значения {{integer}} и {{datetime}} не используются: целые числа относятся к {{number}}, дата-время — к {{date}}.

Общие правила:
* нормализация полностью выполняется на backend; frontend не должен разбирать нативные типы отдельных СУБД;
* {{type}} является информационной классификацией и не выполняет CAST или иное преобразование данных;
* {{source_type}} сохраняет исходное имя, регистр, параметры, вложенность, nullable и часовой пояс, например {{UInt32}}, {{Decimal(18, 2)}}, {{Nullable(String)}}, {{DateTime64(3, 'UTC')}};
* если нативный тип известен, но не имеет однозначного соответствия, возвращается {{type = "undefined"}}, а в {{source_type}} сохраняется фактический тип;
* если нативный тип отсутствует, возвращаются {{type = "undefined"}} и {{source_type = "undefined"}};
* нераспознанный тип одного поля не приводит к ошибке элемента или всей команды.

*SQLite.*

Проверки выполняются регистронезависимо после удаления внешних пробелов и строго в указанном порядке. Backend анализирует объявленный тип, но не фактические значения колонки.

|| Объявленный тип содержит / условие || {{fields[].type}} ||
| Тип отсутствует или пустой | {{undefined}} |
| {{DATETIME}} или {{TIMESTAMP}} | {{date}} |
| {{DATE}} | {{date}} |
| {{BOOLEAN}} или {{BOOL}} | {{number}} |
| {{INT}} | {{number}} |
| {{CHAR}}, {{CLOB}} или {{TEXT}} | {{string}} |
| {{REAL}}, {{FLOA}} или {{DOUB}} | {{number}} |
| {{NUMERIC}} или {{DECIMAL}} | {{number}} |
| {{BLOB}} | {{undefined}} |
| Любое другое объявление | {{undefined}} |

Дополнительные правила SQLite:
* для пользовательского имени типа применяются те же проверки по вхождению токенов;
* {{TIME}} без даты возвращается как {{undefined}};
* физический способ хранения значения не меняет результат нормализации;
* для полей {{view}}, у которых SQLite не возвращает объявленный тип, используется {{undefined}}.

*ClickHouse.*

Тип разбирается по полной структуре, а не простым поиском подстроки.

|| Нативный тип ClickHouse || {{fields[].type}} ||
| {{Int8}}–{{Int256}}, {{UInt8}}–{{UInt256}} | {{number}} |
| {{Float32}}, {{Float64}}, {{BFloat16}} | {{number}} |
| {{Decimal(P, S)}}, {{Decimal32(S)}}, {{Decimal64(S)}}, {{Decimal128(S)}}, {{Decimal256(S)}} | {{number}} |
| {{Bool}} | {{number}} |
| {{String}}, {{FixedString(N)}} | {{string}} |
| {{Enum8}}, {{Enum16}}, {{UUID}}, {{IPv4}}, {{IPv6}} | {{string}} |
| {{Date}}, {{Date32}}, {{DateTime(...)}}, {{DateTime64(...)}} | {{date}} |
| {{Nullable(T)}} | Результат рекурсивного сопоставления {{T}} |
| {{LowCardinality(T)}} | Результат рекурсивного сопоставления {{T}} |
| {{SimpleAggregateFunction(function, T)}} | Результат рекурсивного сопоставления {{T}} |
| {{Array(T)}}, {{Tuple(...)}}, {{Map(...)}}, {{Nested(...)}} | {{undefined}} |
| {{AggregateFunction(...)}}, {{Nothing}}, {{JSON}} / {{Object}}, {{Dynamic}}, {{Variant}}, геометрические, интервальные и иные неописанные типы | {{undefined}} |

Дополнительные правила ClickHouse:
* внешняя составная структура имеет приоритет: {{Array(Int32)}} возвращается как {{undefined}};
* обёртки {{Nullable}}, {{LowCardinality}} и {{SimpleAggregateFunction}} обрабатываются рекурсивно;
* параметры {{Decimal}}, точность {{DateTime64}}, часовой пояс и все обёртки сохраняются в {{source_type}};
* классификация {{Decimal}} как {{number}} не означает преобразование значения во frontend-тип Number и не гарантирует сохранение точности;
* новый или неизвестный тип возвращается как {{undefined}} без падения элемента или всей команды;
* в примерах используется каноническое написание {{UInt32}}; backend возвращает {{source_type}} в исходном виде, полученном от СУБД.

----
h4. 5.6. Ошибки и неуспешные ответы.

Ошибки разделяются на два уровня.

*Ошибка отдельного объекта.*

{{data[].error}} принимает значения:
* {{not_found}} — объект отсутствует в СУБД на момент выполнения;
* {{access_denied}} — недостаточно прав на объект;
* {{internal_error}} — непредвиденный сбой при получении конкретного объекта;
* {{null}} — объект успешно получен.

Ошибка отдельного объекта не прерывает batch-команду {{metadata.object.get}}. Остальные элементы обрабатываются и возвращаются независимо. Для элемента с {{error != null}} backend возвращает {{type = null}} и {{fields = null}}.

*Общая ошибка команды.*

Потеря соединения с СУБД, недоступность источника данных, невалидный {{object.id}} и отсутствие поддержки чтения метаданных объектов у типа источника возвращаются как общая ошибка команды на уровне HTTP/протокола. Одинаковая общая ошибка не должна дублироваться в каждом элементе {{data[]}}.

Нераспознанный тип отдельного поля не является ошибкой: для него применяется {{type = "undefined"}} по правилам п. 5.5.

----
h3. 6. Требования к реализации.

h4. 6.1. Backend-логика.

Backend должен:
* получать список объектов и их поля из метаданных выбранного источника данных, а не из датасетов;
* использовать {{object.id}} как идентификатор выбранного источника данных;
* реализовать точные имена команд {{metadata.object.list}} и {{metadata.object.get}};
* для {{metadata.object.list}} формировать список по правилам п. 5.3;
* для {{metadata.object.get}} принимать массив пар {{name}} + {{schema}} и возвращать независимый результат для каждой уникальной пары;
* сохранять точную форму {{name}}, {{schema}}, {{fields[].name}} и {{fields[].source_type}}, включая регистр, параметры и спецсимволы;
* формировать {{fields[].type}} на backend по правилам п. 5.5;
* не смешивать {{object.id}}, {{command.id}} и поля внутри {{data}};
* не изменять настройки источника данных при выполнении команд;
* не запускать проверку SQL-запроса произвольного набора данных для получения метаданных;
* не создавать временные наборы данных для получения списка объектов и полей;
* переиспользовать существующие механизмы подключения и чтения схемы источников, если они применимы к новому контракту.

Ограничение списка текущей базой данных относится только к дереву метаданных. Доработка не должна вводить запрет на ручное обращение к другой базе в SQL, если это допускают СУБД и права учётной записи подключения.

----
h4. 6.2. Права доступа и безопасность.

Backend должен:
* проверять право пользователя портала на чтение метаданных выбранного источника по существующим правилам доступа;
* формировать состав доступных схем и объектов с учётом прав учётной записи подключения к СУБД;
* не раскрывать метаданные источника пользователю, у которого нет права на выбранный источник;
* не возвращать секреты подключения: пароли, токены, ключи, защищённые параметры и DSN с секретами;
* не возвращать строки пользовательских данных;
* валидировать каждую пару {{data[].name}} + {{data[].schema}} как идентификатор объекта, не допуская её использования как произвольного SQL-фрагмента;
* корректно обрабатывать спецсимволы, кавычки и регистр в именах схем, объектов и полей без SQL-инъекций и без порчи исходных значений.

Отсутствие доступа к выбранному источнику в целом обрабатывается как общая ошибка команды. Недостаточность прав СУБД на отдельный объект batch-запроса {{metadata.object.get}} возвращается как {{data[].error = "access_denied"}}.

----
h4. 6.3. Производительность.

Команды должны быть пригодны для источников с большим количеством объектов и полей.

Требования:
* {{metadata.object.list}} не должен загружать поля объектов;
* {{metadata.object.get}} должен загружать поля только для переданных уникальных пар {{name}} + {{schema}};
* batch-запрос должен сохранять результаты успешно обработанных объектов при ошибке отдельного объекта;
* время выполнения должно оставаться приемлемым для интерактивного раскрытия дерева метаданных;
* при недоступности источника или истечении действующего таймаута backend должен возвращать общую ошибку команды по действующему протоколу.

----
h4. 6.4. Совместимость.

Доработка не должна ломать:
* существующую команду {{datasources.list}};
* существующие команды работы с датасетами;
* существующую команду {{extraction_rules.get}} и её {{fields[]}};
* проверку SQL произвольного набора данных;
* обновление выходных полей после проверки SQL;
* сохранение карточки набора данных;
* работу обычной и облачной версий портала в сценариях, не использующих новый контракт.

----
h3. 7. Пограничные сценарии.

Backend должен корректно обрабатывать следующие сценарии:
* в текущей базе данных нет доступных пользовательских таблиц и {{view}};
* в разных пользовательских схемах есть объекты с одинаковым {{name}};
* обычный {{view}} передан в {{metadata.object.get}};
* объект удалён или переименован между {{metadata.object.list}} и {{metadata.object.get}};
* права учётной записи подключения на отдельный объект отозваны между вызовами команд;
* объект, схема или поле имеют пробелы, спецсимволы, кавычки либо регистрозависимое написание;
* поле имеет известный нативный тип без однозначного нормализованного аналога;
* нативный тип поля отсутствует;
* SQLite-объект относится к {{main}}, {{temp}} или базе, подключённой через {{ATTACH}};
* ClickHouse возвращает объект текущей базы без отдельной схемы;
* ClickHouse-поле содержит вложенные обёртки или составной тип;
* в batch-запросе повторяется пара {{name}} + {{schema}};
* ошибка возникает только для одного из нескольких элементов batch-запроса;
* источник данных или соединение с СУБД недоступны целиком;
* пользователь не авторизован либо не имеет права на выбранный источник;
* команды вызываются в обычной и облачной версиях портала с единым frontend-маркером версии.

h3. 9. Критерии приёмки (AC):

* *AC.1 (Получение списка объектов источника):*
* *Дано:* пользователь имеет доступ к источнику данных с {{ID = 10}};
* *Когда:* frontend отправляет {{object.name = "datasources"}}, {{object.id = 10}}, {{command.name = "metadata.object.list"}};
* *Тогда:* backend возвращает {{data[]}}, где для каждого объекта заполнены {{name}}, {{schema}} и {{type}}, а {{type}} имеет значение {{table}} или {{view}}.

* *AC.2 (Состав списка):*
* *Дано:* текущая база содержит пользовательские таблицы и обычные {{view}} в нескольких доступных схемах, а также системные, временные, foreign/external-объекты и специальные виды представлений;
* *Когда:* выполняется {{metadata.object.list}};
* *Тогда:* возвращаются обычные пользовательские таблицы и {{view}} всех доступных пользовательских схем текущей базы независимо от первичного ключа; остальные перечисленные категории и объекты других баз не возвращаются.

* *AC.3 (Правила схем):*
* *Дано:* команды выполняются для СУБД с реальными схемами, SQLite и ClickHouse;
* *Когда:* backend формирует {{data[].schema}};
* *Тогда:* для СУБД с реальными схемами возвращается оригинальное имя схемы; для SQLite возвращаются только объекты основной базы {{main}}, но {{schema}} содержит пустую строку; объекты {{temp}} и {{ATTACH}} не возвращаются; для ClickHouse {{schema}} также содержит пустую строку.

* *AC.4 (Пакетное получение полей):*
* *Дано:* frontend знает две пары {{name}} + {{schema}}, одна из которых относится к обычной таблице, а другая — к обычному {{view}};
* *Когда:* frontend передаёт эти пары в {{data[]}} команды {{metadata.object.get}} с идентификатором источника в {{object.id}};
* *Тогда:* backend возвращает массив результатов; для каждого успешно полученного объекта заполнены {{name}}, {{schema}}, {{type}}, {{error = null}} и {{fields[]}}, а каждый элемент {{fields[]}} содержит {{name}}, {{type}} и {{source_type}}.

* *AC.5 (Единый контракт типов):*
* *Дано:* объекты содержат поля с однозначно сопоставимыми, неоднозначными и отсутствующими нативными типами;
* *Когда:* выполняется {{metadata.object.get}};
* *Тогда:* {{fields[].type}} принимает только {{number}}, {{string}}, {{date}} или {{undefined}}; исходный тип без изменения сохраняется в {{source_type}}; при отсутствии нативного типа оба свойства равны строке {{undefined}}; неизвестный тип не приводит к ошибке объекта или команды.

* *AC.6 (Нормализация SQLite):*
* *Дано:* тестовая SQLite-таблица содержит объявления типов, покрывающие каждую строку матрицы п. 5.5, а также пустой и пользовательский тип;
* *Когда:* выполняется {{metadata.object.get}};
* *Тогда:* типы нормализуются регистронезависимо после удаления внешних пробелов, в порядке и со значениями, указанными в матрице; фактические значения колонок не анализируются.

* *AC.7 (Нормализация ClickHouse):*
* *Дано:* тестовый ClickHouse-объект содержит скалярные, обёрнутые, составные и неизвестные типы из матрицы п. 5.5;
* *Когда:* выполняется {{metadata.object.get}};
* *Тогда:* полная структура типа нормализуется по матрице, внешняя составная структура имеет приоритет, обёртки обрабатываются рекурсивно, а полная исходная конструкция сохраняется в {{source_type}}.

* *AC.8 (Независимые ошибки элементов):*
* *Дано:* в одном batch-запросе есть доступный объект, отсутствующий объект, объект без прав и объект, для которого возник локальный сбой;
* *Когда:* выполняется {{metadata.object.get}};
* *Тогда:* успешный объект возвращается с {{error = null}}, остальные — соответственно с {{not_found}}, {{access_denied}} и {{internal_error}}; для ошибочных элементов {{type = null}} и {{fields = null}}, а ошибка одного элемента не прерывает остальные.

* *AC.9 (Общая ошибка команды):*
* *Дано:* передан невалидный {{object.id}}, источник недоступен, потеряно соединение с СУБД либо тип источника не поддерживает чтение метаданных объектов;
* *Когда:* выполняется любая из новых команд;
* *Тогда:* backend возвращает общую ошибку на уровне HTTP/протокола и не дублирует её одинаковым значением в каждом элементе {{data[]}}.

* *AC.10 (Дедупликация batch-запроса):*
* *Дано:* в {{data[]}} запроса {{metadata.object.get}} несколько раз передана одна пара {{name}} + {{schema}};
* *Когда:* backend обрабатывает запрос;
* *Тогда:* в ответе возвращается один объект для этой пары; если получены успешный и ошибочный результаты, возвращается успешный результат с {{error = null}}.

* *AC.11 (Метаданные доступны без проверки SQL):*
* *Дано:* пользователь открыл карточку произвольного набора данных и ещё не запускал {{«Проверить запрос»}};
* *Когда:* frontend вызывает {{metadata.object.list}} и {{metadata.object.get}};
* *Тогда:* backend возвращает метаданные источника независимо от результата проверки SQL.

* *AC.12 (Права и отсутствие чувствительных данных):*
* *Дано:* команды вызываются пользователем без права портала на выбранный источник либо пользователем с таким правом через учётную запись подключения с ограниченной видимостью объектов;
* *Когда:* backend обрабатывает запросы;
* *Тогда:* в первом случае возвращается общая ошибка доступа без раскрытия метаданных, во втором {{metadata.object.list}} содержит только объекты, доступные учётной записи подключения; ответы не содержат строки данных, пароли, токены, ключи и другие секреты подключения.

* *AC.13 (Сохранение оригинальных идентификаторов):*
* *Дано:* источник содержит объекты и поля с одинаковыми короткими именами в разных схемах, разным регистром или спецсимволами;
* *Когда:* выполняются {{metadata.object.list}} и {{metadata.object.get}};
* *Тогда:* {{name}}, {{schema}} и {{fields[].name}} возвращаются без добавления префиксов, изменения регистра и искажения значений, {{source_type}} сохраняет исходное описание типа, а объекты различаются по паре {{name}} + {{schema}}.

* *AC.14 (Работа в обычной и облачной версиях портала):*
* *Дано:* выбранный источник доступен в обычной или облачной версии портала и поддерживает чтение метаданных объектов;
* *Когда:* frontend вызывает новые команды по единому контракту;
* *Тогда:* backend возвращает одинаковую структуру {{data}} в обеих версиях.

* *AC.15 (Отсутствие регресса):*
* *Дано:* после внедрения новых команд выполняются существующие команды {{datasources.list}}, команды работы с датасетами и {{extraction_rules.get}}, а пользователь проверяет SQL и сохраняет произвольный набор данных;
* *Когда:* выполняются прежние сценарии портала;
* *Тогда:* существующие API и бизнес-логика проверки SQL, обновления выходных полей и сохранения набора данных работают без изменения.

* *AC.16 (Пустые успешные результаты):*
* *Дано:* в текущей базе нет доступных объектов либо успешно полученный объект не содержит доступных полей;
* *Когда:* выполняется соответственно {{metadata.object.list}} или {{metadata.object.get}};
* *Тогда:* команда завершается успешно и возвращает соответственно {{data = []}} либо элемент с {{error = null}} и {{fields = []}}.
