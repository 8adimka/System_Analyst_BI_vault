h3. 1. Цель и контекст.

На Шаге 1 был создан изолированный переиспользуемый виджет редактора кода на базе {{CodeMirror}} в {{Storybook}}. На Шаге 2 этот виджет был внедрен в {{«Вычисляемые поля»}} и интегрирован с бизнес-логикой соответствующего модуля.

Цель Шага 3 — внедрить новый редактор кода на базе {{CodeMirror}} в интерфейс {{«Наборы данных»}} для сценария настройки *пользовательского произвольного SQL-запроса* к источнику данных и бесшовно интегрировать его с существующей бизнес-логикой формы произвольного набора данных.

{panel:title=Важно:|borderStyle=dashed|borderColor=#ff9900|bgColor=#fffcf5} 
* В рамках данной задачи внедрение выполняется *только* для пользовательских {{«произвольных»}} наборов данных. На {{простые}} и {{составные}} наборы данных данная история не распространяется.
* В данном модуле мы не просто заменяем поле ввода SQL, а вводим единый стандарт редактора для работы с произвольным SQL-запросом, сохраняя текущую логику {{«Проверить запрос»}}, формирования выходных полей набора данных и последующего сохранения формы.
{panel}

{panel:title=Ключевой принцип интеграции:|borderStyle=dashed|borderColor=#ccc|titleBGColor=#DDEBF7|bgColor=#F8FBFF}
* Новый редактор должен использовать уже реализованный переиспользуемый виджет {{CodeMirror}} (адаптированный под текущие задачи), а не отдельную локальную реализацию.
* Источником истины для валидности _SQL-запроса_ остается существующая бизнес-логика модуля и штатное действие {{«Проверить запрос»}}.
* Так как модальное окно редактора перекрывает основную форму с полями набора данных, список *текущих полей набора данных* должен быть доступен прямо внутри модального окна, в левой боковой панели.
* Внедрение должно быть выполнено без регресса для текущего сценария: редактирование SQL → проверка запроса → обновление выходных полей → ручная настройка алиасов/описаний/прочих атрибутов → сохранение набора данных.
{panel}

h3. 2. Функциональные требования к интеграции.

h4. 2.1. Точка входа и замена старого редактора.
* *Текущее состояние:* Поле {{«SQL Запрос»}} открывается по нажатию на иконку {{«глаза»}} напротив соответствующего поля в форме произвольного набора данных.
* *Требование:* Старый редактор SQL в этом сценарии должен быть полностью заменен на новый модальный интерфейс на базе {{CodeMirror}}.
* *Область применения:* Новый редактор будет использоваться только в карточке выбранного *произвольного* набора данных.

h4. 2.2. UI модального окна и компоновка.
* Модальное окно должно быть *укрупненным* и удобным для работы с длинными SQL-запросами.
* Внутри модального окна должна быть реализована двухзонная компоновка:
** *центральная основная зона* — редактор {{CodeMirror}};
** *левая вспомогательная зона* — список текущих полей набора данных, доступных для просмотра и вставки в SQL ({{drag-and-drop}}).
* Основная площадь модального окна должна быть отдана редактору.
* Левая панель должна иметь фиксированную или адаптивно-фиксированную ширину, достаточную для просмотра списка полей без схлопывания названий.
* Окно не должно ломать верстку при изменении размера экрана.
* Для длинных SQL-скриптов и длинного списка полей должны работать *внутренние скроллы* соответствующих областей.
* На узких экранах левая панель может сворачиваться в отдельную область/вкладку, но должна оставаться доступной пользователю без закрытия модального окна редактора.

h4. 2.3. Поведение открытия, применения и закрытия модального окна.
* При открытии модального окна редактор должен получать *актуальное текущее значение* поля {{«SQL Запрос»}} из формы набора данных.
* Если пользователь в модальном окне изменил текст SQL, эти изменения должны существовать как *черновик текущей сессии модального окна* до явного применения.
* Должно быть действие, эквивалентное {{«Применить»}}:
** оно переносит текущий текст SQL из модального окна обратно в форму набора данных;
** после этого модальное окно закрывается.
* Должно быть действие, эквивалентное {{«Отмена»}}:
** оно закрывает модальное окно *без применения* изменений текущей сессии.
* Если пользователь пытается закрыть модальное окно при наличии несохраненных изменений внутри текущей сессии, должно быть корректное _защитное_ поведение (подтверждение закрытия или иное штатное решение, исключающее случайную потерю введенного _SQL_).
* {panel:title=Важно:|borderStyle=dashed|borderColor=#ff9900|bgColor=#fffcf5}
Финальное сохранение набора данных как объекта должно по-прежнему выполняться штатной кнопкой {{«Сохранить»}} основной формы, а не автоматически при закрытии модального окна.
{panel}

h4. 2.4. Интеграция с действием {{«Проверить запрос»}}.
* В модальном окне должно быть доступно действие {{«Проверить запрос»}}.
* Проверка должна выполняться *по текущему тексту SQL из редактора*, а не по последней сохраненной версии.
* При успешной проверке:
** должна отработать текущая бизнес-логика модуля проверки запроса;
** список выходных полей набора данных должен обновиться;
** правая панель полей внутри модального окна также должна обновиться в соответствии с новым результатом запроса;
** пользователь должен получить штатное успешное уведомление.
** {panel:title=Важно:|borderStyle=dashed|borderColor=#ff9900|bgColor=#fffcf5}
В случае нажатия пользователем кнопки {{«Отмена»}}, после успешной проверки SQL-запроса, должен произойти возврат к последней «Сохранённой» версии запроса (без сохранения обновлённого валидированного запроса).
{panel}
* При неуспешной проверке:
** пользователь должен получить понятное сообщение об ошибке;
** текст SQL в редакторе не должен теряться;
** модальное окно не должно закрываться;
** ранее существующий валидный список выходных полей не должен разрушаться некорректным промежуточным состоянием.
* Проверка SQL *не должна* запускаться автоматически на каждый ввод символа. Это должно оставаться явным действием пользователя.

h4. 2.5. Синхронизация выходных полей и сохранение пользовательских атрибутов.
* После успешной проверки SQL обновление выходных полей должно происходить *по текущим правилам бизнес-логики модуля*.
* Для полей, которые сохранились после новой проверки (по текущему правилу идентификации поля, принятому в модуле), должны по возможности сохраняться ранее введенные пользователем атрибуты:
** алиас;
** описание;
** иерархия/группа;
** иные редактируемые свойства поля, если они поддерживаются формой.
* Для полей, которые исчезли из результата запроса, записи должны корректно удаляться из списка выходных полей.
* Для новых полей должны создаваться новые записи с дефолтными значениями, полученными по результату проверки запроса.

h4. 2.6. SQL-диалект и режим подсветки.
* Редактор должен работать в режиме SQL.
* SQL-диалект должен определяться по типу _текущего источника данных_.
* Для источников, для которых в текущей реализации уже есть прямое сопоставление с диалектом {{CodeMirror}}, должно использоваться нативное сопоставление.
* Для источников, для которых нативный диалект {{CodeMirror}} отсутствует, должен использоваться согласованный fallback-режим проекта (например, {{StandardSQL}} либо уже реализованный в проекте _кастомный диалект_).
* Переключение/выбор диалекта не должен ломать базовую подсветку SQL, автодополнение и общую работу редактора.

h4. 2.7. Поддержка кастомных переменных окружения.
В SQL-запросах наборов данных в системе используются пользовательские переменные окружения. Стандартный SQL-парсер может воспринимать их как ошибку.
*Требование:* Необходимо расширить конфигурацию редактора так, чтобы следующие конструкции распознавались как валидный системный синтаксис, подсвечивались отдельно и не помечались как синтаксическая ошибка:
* токены вида {{\!env.NAME!\}};
* токены вида {{\!env.NAME.BEGIN\!}};
* токены вида {{\!env.NAME.END\!}};
* конструкции с резервной (fallback) логикой внутри фигурных скобок, например: \{{{\!env.REGION\!; 2}}\};
* конструкции, где переменная используется внутри более сложного выражения, например: \{{{toDate(\!env.Date\!); '2020-01-01'}}\}.

h4. 2.8. Левая панель с полями текущего набора данных.
* В левой части модального окна должен отображаться список *текущих выходных полей набора данных*.
* Источником данных для этой панели должно быть текущее состояние формы набора данных и/или актуальный результат последней успешной проверки запроса.
* По каждому полю в панели должно отображаться _как минимум_:
** имя поля, используемое системой как идентификатор;
** при наличии — отображаемый алиас;
** при наличии — тип поля.
* Если в текущей модели уже доступны группировки/иерархии полей, они могут быть использованы для визуального группирования списка. Если такой информации нет — допускается плоский список.
* Если у набора данных пока нет доступных полей (например, запрос еще ни разу успешно не проверялся), должна отображаться корректная пустая заглушка с понятным пояснением пользователю.

h4. 2.9. Вставка поля из правой панели в редактор.
* Поля из правой панели должны быть доступны для вставки в SQL непосредственно из модального окна.
* Cпособ вставки в редактор:
** {{Drag-and-Drop}} из правой панели в область редактора.
* Вставка должна происходить *в текущую позицию каретки*.
* Если редактор временно потерял фокус (например, пользователь взаимодействует с правой панелью), должна использоваться последняя известная позиция каретки.
* Если пользователь ранее не фокусировался в редактор, вставка допускается в конец SQL-скрипта.
* Если в редакторе включен мультикурсор, вставка должна выполняться по всем активным курсорам.
* После вставки фокус должен корректно возвращаться в редактор, если это не противоречит UX.
* Вставляемое значение должно быть *техническим идентификатором поля*, пригодным для использования в SQL.
* Если для корректной SQL-вставки требуется экранирование/кавычки в соответствии с диалектом текущего источника, вставка должна использовать синтаксически безопасную форму идентификатора.

h4. 2.10. Поведение каретки и Drag-and-Drop.
* *Базовый вариант (обязательно):*
** при перетаскивании поля в редактор вставка выполняется в последнюю актуальную позицию каретки;
** если редактор не был ранее сфокусирован — вставка выполняется в конец текста;
** при мультикурсоре вставка происходит по всем курсорам.
* *Продвинутый вариант (желательно):*
** отображение drop-позиции/ghost-каретки внутри редактора при наведении перетаскиваемого поля;
** вставка текста ровно по координате drop внутри области редактора при зажатой клавише {{Shift}}.

h4. 2.11. Автодополнение.
* При вводе текста должно работать выпадающее меню автодополнения.
* В обязательный состав подсказок должны входить:
** стандартные SQL-ключевые слова;
** встроенные SQL-функции;
** идентификаторы текущих полей набора данных, доступных в правой панели.
* Автодополнение должно вызываться как при вводе текста, так и по явной горячей клавише (например, {{Ctrl+Space}}).
* Если текущая архитектура модуля уже предоставляет доступ к метаданным источника данных без отдельного расширения backend-контракта, допускается расширение подсказок таблицами/колонками источника. Но это *не является обязательным условием закрытия данной истории*.

h4. 2.12. Подсветка ошибок и сообщения пользователю.
* Если в базовом виджете уже реализована локальная подсветка базовых синтаксических проблем, она должна быть сохранена и в данном сценарии.
* Локальная подсветка ошибок редактора носит *вспомогательный* характер и не заменяет штатную серверную проверку запроса.
* Если backend проверки запроса возвращает ошибку и позволяет определить проблемное место, это место должно быть визуально акцентировано в редакторе.
* При невозможности точной привязки ошибки к позиции в тексте достаточно показать понятное текстовое сообщение без потери введенного SQL.

h4. 2.13. Базовый UX редактора.
* В сценарии {{«Наборы данных»}} должен быть сохранен базовый UX, реализованный в переиспользуемом виджете:
** нумерация строк;
** подсветка синтаксиса SQL;
** подсветка и автозакрытие скобок/кавычек;
** Undo/Redo;
** поддержка мультикурсорного редактирования;
** корректный вертикальный внутренний скролл;
** стабильная работа с длинными запросами.
* Горячие клавиши стандартных действий редактора не должны конфликтовать с текущими действиями модального окна и основной формы.

{panel:title=Границы реализации.|borderStyle=dashed|borderColor=#ccc|titleBGColor=#FCE4D6|bgColor=#FFF8F2}
В Scope данной истории входит:
* замена старого редактора SQL на {{CodeMirror}} в карточке *произвольного* набора данных;
* модальное окно с правой панелью текущих полей набора данных;
* интеграция со штатным действием {{«Проверить запрос»}};
* вставка полей из правой панели в SQL;
* поддержка системного синтаксиса {{env}}.
{panel}

h3. 3. Критерии приёмки (AC):

* *AC1 (Замена редактора):* В карточке *произвольного* набора данных старый редактор поля {{«SQL Запрос»}} заменен на новый редактор {{CodeMirror}}, который открывается по нажатию на иконку {{«глаза»}}.
* *AC2 (Открытие и загрузка значения):* При открытии модального окна в редактор подставляется актуальный текущий текст SQL из формы набора данных.
* *AC3 (UI модального окна):* Модальное окно укрупнено, содержит редактор слева и панель текущих полей набора данных справа, корректно работает на разных размерах экрана, внутренние скроллы работают без поломки верстки.
* *AC4 (Применение и отмена):* После внесения изменений в SQL-запрос и нажатия кнопки {{«Применить»}}, в случае прохождения валидации данного обновлённого запроса, изменения применяются в форму набора данных без немедленного сохранения самого объекта набора данных; закрытие набора данных, по нажатию кнопки {{«Отмена»}} (или эквивалентному действию) не применяет изменения текущей сессии на набор данных. 
В случае не прохождения валидации обновлённым SQL-запросом и нажатия кнопки {{«Применить»}} - пользователь получает понятное уведомление, сохранение обновлённого запроса не происходит, модальное окно редактора кода не закрывается.
* *AC5 (Проверка запроса):* Кнопка {{«Проверить запрос»}} внутри модального окна проверяет *текущий* текст запроса из редактора. При успехе обновляются выходные поля формы и правая панель полей. При ошибке модальное окно не закрывается, SQL не теряется.
* *AC6 (Сохранение атрибутов полей):* При успешной повторной проверке запроса для совпавших полей не происходит необоснованной потери ранее заполненных пользователем атрибутов (алиас, описание, иерархия и др. поддерживаемые свойства).
* *AC7 (SQL-диалект):* Подсветка SQL и режим редактора корректно определяются по типу источника данных. Для неподдерживаемого нативно диалекта используется согласованный {{fallback}} без поломки базовой работы редактора.
* *AC8 (Кастомные переменные):* Конструкции вида {{\!env.NAME\!}}, {{\!env.NAME.BEGIN\!}}, {{\!env.NAME.END\!}} и конструкции с альтернативной {{fallback}} логикой (внутри фигурных скобок) корректно подсвечиваются и не помечаются как синтаксическая ошибка редактора.
* *AC9 (Левая панель полей):* В модальном окне отображается список текущих полей набора данных, доступен поиск по полям, корректно обрабатывается состояние пустого списка.
* *AC10 (Вставка полей):* Поле из левой панели можно вставить в SQL через {{Drag-and-Drop}}. Вставка происходит в текущую/последнюю позицию каретки, либо в конец текста, если каретка ранее не была установлена.
* *AC11 (Мультикурсор):* Если в редакторе активирован мультикурсор, вставка текста из правой панели выполняется по всем активным курсорам.
* *AC12 (Автодополнение):* При вводе текста работает выпадающее меню автодополнения, содержащее SQL-ключевые слова, SQL-функции и идентификаторы текущих полей набора данных.
* *AC13 (Базовый UX CodeMirror):* Сохранен базовый функционал переиспользуемого виджета: нумерация строк, подсветка SQL, автозакрытие скобок/кавычек, Undo/Redo, мультикурсор, корректный внутренний скролл.
* *AC14 (Без регресса бизнес-логики):* После внедрения нового редактора не сломаны существующие сценарии формы произвольного набора данных: проверка SQL, обновление выходных полей, ручное редактирование атрибутов полей и итоговое сохранение набора данных.
