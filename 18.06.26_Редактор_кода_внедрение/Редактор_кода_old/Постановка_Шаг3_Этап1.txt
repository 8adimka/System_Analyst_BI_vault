h3. 1. Цель и контекст.

На Шаге 1 был создан изолированный переиспользуемый виджет редактора кода на базе {{CodeMirror}} в {{Storybook}}. На Шаге 2 этот виджет был внедрен в {{«Вычисляемые поля»}} и интегрирован с бизнес-логикой соответствующего модуля.

Настоящая история является *Этапом 1* внедрения редактора кода в интерфейс {{«Наборы данных»}}.

Цель Этапа 1 — заменить текущий редактор поля {{«SQL Запрос»}} в карточке *произвольного* набора данных на переиспользуемый виджет {{CodeMirror}}, сохранив действующую бизнес-логику проверки запроса, обновления выходных полей и последующего сохранения формы.

{panel:title=Важно:|borderStyle=dashed|borderColor=#ff9900|bgColor=#fffcf5}
* В рамках данной задачи внедрение выполняется *только* для пользовательских {{«произвольных»}} наборов данных. На {{простые}} и {{составные}} наборы данных данная история не распространяется.
* В рамках данной задачи мы *не* добавляем доступ к метаданным источника данных, дополнительные боковые панели, drag-and-drop из метаданных и прочий расширенный UI-обвес. Это будет вынесено в отдельный *Этап 2*.
* Финальное сохранение набора данных как объекта должно по-прежнему выполняться только штатной кнопкой {{«Сохранить»}} основной формы.
{panel}

{panel:title=Ключевой принцип интеграции:|borderStyle=dashed|borderColor=#ccc|titleBGColor=#DDEBF7|bgColor=#F8FBFF}
* Новый редактор должен использовать уже реализованный переиспользуемый виджет {{CodeMirror}}, а не отдельную локальную реализацию.
* Источником истины для валидности _SQL-запроса_ остается существующая бизнес-логика модуля и штатное действие {{«Проверить запрос»}}.
* На Этапе 1 редактор внедряется в текущий сценарий редактирования SQL без дополнительных боковых панелей и без доступа к метаданным источника.
* Для удобной работы с длинными SQL-запросами редактор должен поддерживать внутренний скролл в соответствии с поведением текущего редавтора.
* Внедрение должно быть выполнено без регресса для текущего сценария: редактирование SQL → проверка запроса → обновление выходных полей → ручная настройка алиасов/описаний/прочих атрибутов → сохранение набора данных.
{panel}

h3. 2. Функциональные требования к интеграции.

h4. 2.1. Точка входа и замена старого редактора.
* *Текущее состояние:* В форме *произвольного* набора данных поле {{«SQL Запрос»}} редактируется через текущий штатный контрол раскрытия/просмотра.
* *Требование:* Старый редактор SQL в этом сценарии должен быть заменен на новый редактор на базе {{CodeMirror}}.
* *Область применения:* Новый редактор используется только в карточке выбранного *произвольного* набора данных.
* Пользовательский сценарий открытия SQL-редактора должен остаться привычным и не должен требовать перехода в отдельный новый раздел интерфейса.

h4. 2.2. Размещение редактора.
* На Этапе 1 редактор должен быть встроен в текущую область формы, где пользователь работает с полем {{«SQL Запрос»}}.
* Для длинных SQL-запросов должен быть доступен внутренний скрол в рамках текущего окна редактора. Внутренний скролл редактора должен работать корректно.
* В рамках текущей задачи не требуется реализовывать переход в полноэкранный режим. Также не требуется добавлять метаданные, дополнительные панели или отдельную бизнес-логику.

h4. 2.3. Поведение редактора и синхронизация с формой.
* При инициализации редактор должен получать *актуальное текущее значение* поля {{«SQL Запрос»}} из формы набора данных.
* Изменения, внесенные пользователем в редакторе, должны отражать текущее рабочее состояние формы набора данных.
* Сворачивание редактора и выход из полноэкранного режима не должны приводить к потере введенного SQL.
* Финальное сохранение набора данных как объекта по-прежнему выполняется только штатной кнопкой {{«Сохранить»}} основной формы и по текущим правилам валидации формы.

h4. 2.4. Интеграция с действием {{«Проверить запрос»}}.
* В текущем сценарии должно сохраняться штатное действие {{«Проверить запрос»}}.
* Проверка должна выполняться *по текущему тексту SQL из редактора*.
* При успешной проверке:
** должна отработать текущая бизнес-логика модуля проверки запроса;
** список выходных полей набора данных должен обновиться;
** пользователь должен получить штатное успешное уведомление.
* При неуспешной проверке:
** пользователь должен получить понятное сообщение об ошибке;
** текст SQL в редакторе не должен теряться;
** редактор не должен закрываться;
** ранее существующий валидный список выходных полей не должен разрушаться некорректным промежуточным состоянием.
* Проверка SQL *не должна* запускаться автоматически на каждый ввод символа. Это должно оставаться явным действием пользователя.

h4. 2.5. Синхронизация выходных полей и сохранение пользовательских атрибутов.
* После успешной проверки SQL обновление выходных полей должно происходить *по текущим правилам бизнес-логики модуля*.
* Для полей, которые сохранились после новой проверки (по текущему правилу идентификации), должны по возможности сохраняться ранее введенные пользователем атрибуты:
** алиас;
** тип;
** описание;
** иерархия/уровень;
** иные редактируемые свойства поля, если они поддерживаются формой.
* Для полей, которые исчезли из результата запроса, записи должны корректно удаляться из списка выходных полей.
* Для новых полей должны создаваться новые записи с дефолтными значениями, полученными по результату проверки запроса.

h4. 2.6. SQL-диалект и режим подсветки.
* Редактор должен работать в режиме SQL.
* SQL-диалект должен определяться по типу _текущего источника данных_.
* Для источников, для которых в текущей реализации уже есть прямое сопоставление с диалектом {{CodeMirror}}, должно использоваться нативное сопоставление.
* Для источников, для которых нативный диалект CodeMirror отсутствует, должен использоваться согласованный fallback-режим (например, StandardSQL либо уже реализованный в проекте кастомный диалект).
* Переключение/выбор диалекта не должен ломать базовую подсветку SQL, автодополнение и общую работу редактора.

h4. 2.7. Поддержка системного синтаксиса проекта.
В SQL-запросах наборов данных в системе используются системные конструкции проекта, которые стандартный SQL-парсер может воспринимать как ошибку.

*Требование:* Необходимо расширить конфигурацию редактора так, чтобы следующие конструкции распознавались как валидный системный синтаксис, подсвечивались отдельно и не помечались как синтаксическая ошибка:
* токены вида {{\!env.NAME!\}};
* токены вида {{\!env.NAME.BEGIN\!}};
* токены вида {{\!env.NAME.END\!}};
* конструкции с резервной (fallback) логикой внутри фигурных скобок, например: \{{{\!env.REGION\!; 2}}\};
* конструкции, где переменная используется внутри более сложного выражения, например: \{{{toDate(\!env.Date\!); '2020-01-01'}}\};
* иные серверные/системные переменные проекта, уже допустимые в SQL наборах данных по текущим правилам платформы.

h4. 2.8. Автодополнение и базовый UX редактора.
* При вводе текста должно работать выпадающее меню автодополнения.
* В обязательный состав подсказок должны входить:
** стандартные SQL-ключевые слова;
** встроенные SQL-функции.
* Автодополнение должно вызываться как при вводе текста, так и по явной горячей клавише (например, {{Ctrl+Space}}).
* В сценарии {{«Наборы данных»}} должен быть сохранен базовый UX, реализованный в переиспользуемом виджете:
** нумерация строк;
** подсветка синтаксиса SQL;
** подсветка и автозакрытие скобок/кавычек;
** Undo/Redo;
** поддержка мультикурсорного редактирования;
** корректный вертикальный внутренний скролл;
** стабильная работа с длинными запросами.
* Горячие клавиши стандартных действий редактора не должны конфликтовать с текущими действиями основной формы.

h4. 2.9. Подсветка ошибок и сообщения пользователю.
* Если в базовом виджете уже реализована локальная подсветка базовых синтаксических проблем, она должна быть сохранена и в данном сценарии.
* Локальная подсветка ошибок редактора носит *вспомогательный* характер и не заменяет штатную серверную проверку запроса.
* Если backend проверки запроса возвращает ошибку и позволяет определить проблемное место, это место должно быть визуально акцентировано в редакторе.
* При невозможности точной привязки ошибки к позиции в тексте достаточно показать понятное текстовое сообщение без потери введенного SQL.

{panel:title=Границы реализации.|borderStyle=dashed|borderColor=#ccc|titleBGColor=#FCE4D6|bgColor=#FFF8F2}
В Scope данной истории входит:
* замена старого редактора SQL на {{CodeMirror}} в карточке *произвольного* набора данных;
* сохранение текущей бизнес-логики действия {{«Проверить запрос»}};
* поддержка системного синтаксиса проекта;
* сохранение базового UX переиспользуемого виджета.

В Scope данной истории *не* входит:
* поддержка полноэкранного режима этого редактора;
* доступ к метаданным источника данных из редактора;
* дополнительные боковые панели;
* drag-and-drop объектов в SQL;
* metadata-aware автодополнение таблицами и полями источника;
* отдельное backend-хранение черновиков SQL.
{panel}

h3. 3. Критерии приёмки.

* *AC1 (Замена редактора):* В карточке *произвольного* набора данных старый редактор поля {{«SQL Запрос»}} заменен на новый редактор {{CodeMirror}}.
* *AC2 (Загрузка значения):* При инициализации редактора в него подставляется актуальный текущий текст SQL из формы набора данных.
* *AC3 (Базовый UX CodeMirror):* Сохранен базовый функционал переиспользуемого виджета: нумерация строк, подсветка SQL, автозакрытие скобок/кавычек, Undo/Redo, мультикурсор, корректный внутренний скролл.
* *AC4 (Проверка запроса):* Действие {{«Проверить запрос»}} работает по текущему тексту редактора. При успехе обновляются выходные поля формы. При ошибке SQL не теряется.
* *AC5 (Без автопроверки):* Проверка SQL не запускается автоматически на каждый ввод символа.
* *AC6 (Сохранение атрибутов полей):* При успешной повторной проверке запроса для совпавших полей не происходит необоснованной потери ранее заполненных пользователем атрибутов (алиас, описание, иерархия и др. поддерживаемые свойства).
* *AC7 (SQL-диалект):* Подсветка SQL и режим редактора корректно определяются по типу источника данных. Для неподдерживаемого нативно диалекта используется согласованный {{fallback}} без поломки базовой работы редактора.
* *AC8 (Системный синтаксис):* Системные конструкции проекта, включая {{\!env.NAME\!}}, {{\!env.NAME.BEGIN\!}}, {{\!env.NAME.END\!}} и конструкции с fallback-логикой, корректно подсвечиваются и не помечаются как синтаксическая ошибка редактора.
* *AC9 (Автодополнение):* При вводе текста работает выпадающее меню автодополнения, содержащее SQL-ключевые слова и SQL-функции; автодополнение также доступно по явной горячей клавише.
* *AC10 (Без боковых панелей на Этапе 1):* Во встроенном и полноэкранном режиме редактора отсутствуют метаданные источника, дополнительные боковые панели и drag-and-drop-вставки.
* *AC11 (Без регресса бизнес-логики):* После внедрения нового редактора не сломаны существующие сценарии формы произвольного набора данных: проверка SQL, обновление выходных полей, ручное редактирование атрибутов полей и итоговое сохранение набора данных.
