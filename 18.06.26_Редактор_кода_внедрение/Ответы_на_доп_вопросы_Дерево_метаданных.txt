h3. Ответы и уточнения по дереву метаданных.

Документ фиксирует состав объектов для команд {{datasources / metadata.tables.list}} и {{datasources / metadata.tables.get}}, а также правила нормализации типов SQLite и ClickHouse.

----
h3. 1. Какие объекты должен возвращать список таблиц.

{{metadata.tables.list}} должен возвращать объекты только из *текущей базы данных, настроенной в выбранном источнике данных*.

* Возвращаются объекты из всех доступных *пользовательских* схем внутри текущей базы данных.
* Системные схемы и системные объекты не возвращаются.
* Список формируется с учётом прав учётной записи подключения к СУБД.
* Наличие, отсутствие и состав первичного ключа не влияют на включение объекта в список.
* Объекты других баз данных не возвращаются. Это ограничивает только дерево метаданных и не запрещает пользователю вручную обратиться к другой базе в SQL, если СУБД и права подключения это позволяют.

|| Категория объекта || Включать в текущей итерации || Значение {{data[].type}} ||
| Обычная пользовательская таблица | Да | {{table}} |
| Обычный {{view}} | Да | {{view}} |
| {{materialized view}} и иные специальные виды представлений | Нет в текущей итерации | — |
| {{foreign table}} / {{external table}} как отдельный класс объекта СУБД | Нет | — |
| Временная таблица | Нет | — |
| Системная таблица или системное представление | Нет | — |

Дополнительные правила:
* Оригинальные {{table}} и {{schema}} возвращаются без добавления префиксов и без изменения регистра.
* Таблица и {{view}} различаются отдельным полем {{type}}; изменять имя объекта для визуального различения нельзя.
* {{metadata.tables.get}} должен уметь возвращать поля как обычной таблицы, так и {{view}}, полученного из {{metadata.tables.list}}.
* Для СУБД с реальными схемами в {{schema}} возвращается имя схемы.
* *Для SQLite:* в {{schema}} возвращается {{main}}; {{temp}} и подключённые через {{ATTACH}} базы не включаются.
* *Для ClickHouse:* в {{schema}} возвращается пустая строка, поскольку отдельного уровня схемы нет, а текущая база уже определяется выбранным источником данных. Frontend не создаёт для ClickHouse дополнительный уровень схемы.

----
h3. 2. Обработка ошибок.

Ошибка на уровне отдельного объекта (data[].error) не прерывает выполнение всей команды — остальные объекты batch-запроса обрабатываются и возвращаются независимо. Ошибка, затрагивающая весь запрос целиком (потеря соединения с СУБД, недоступность источника данных, невалидный object.id), возвращается как общая ошибка команды на уровне HTTP/протокола, а не дублируется в каждом элементе data[] как одинаковая ошибка на уровне каждого объекта.

----
h3. 3. Общие правила передачи типов полей.

Для каждого поля {{metadata.tables.get}} backend возвращает два свойства:
* {{type}} — нормализованный тип для frontend;
* {{source_type}} — исходный тип СУБД без приведения.

Для {{fields[].type}} использовать единый словарь:
* {{number}};
* {{string}};
* {{date}};
* {{undefined}}.

Значения {{integer}} и {{datetime}} в текущем контракте *не использовать*: целые числа относятся к {{number}}, дата-время — к {{date}}.

Правила:
* Нормализация выполняется на backend. Frontend не должен разбирать нативные типы отдельных СУБД.
* {{type}} используется только как информационная классификация поля и не выполняет CAST/преобразование данных.
* {{source_type}} сохраняет исходное имя, регистр, параметры, вложенность, признак nullable и часовой пояс, например {{UInt32}}, {{Decimal(18, 2)}}, {{Nullable(String)}}, {{DateTime64(3, 'UTC')}}.
* Если нативный тип известен, но не имеет однозначного соответствия, вернуть {{type = "undefined"}}, а в {{source_type}} сохранить фактический тип.
* Если нативный тип отсутствует, вернуть {{type = "undefined"}} и {{source_type = "undefined"}}.
* Нераспознанный тип одного поля не должен приводить к ошибке всей команды.

----
h3. 4. Правила нормализации SQLite.

SQLite является legacy-сценарием. Для однозначной реализации консервативное сопоставление ниже: распознаются только известные объявления, остальные значения получают {{undefined}}.

Проверки выполняются регистронезависимо, после удаления внешних пробелов и в указанном ниже порядке.

|| Объявленный тип содержит / условие || {{fields[].type}} ||
| Тип отсутствует или пустой | {{undefined}} |
| {{DATETIME}} или {{TIMESTAMP}} | {{date}} |
| {{DATE}} | {{date}} |
| {{BOOLEAN}} или {{BOOL}} | {{number}} |
| {{INT}} | {{number}} |
| {{CHAR}}, {{CLOB}} или {{TEXT}} | {{string}} |
| {{REAL}}, {{FLOA}} или {{DOUB}} | {{number}} |
| {{NUMERIC}} или {{DECIMAL}} | {{number}} |
| {{BLOB}} | {{undefined}} |
| Любое другое объявление | {{undefined}} |

Уточнения:
* {{BOOLEAN}} нормализуется в {{number}}.
* {{NUMERIC}} без дополнительного уточнения нормализуется в {{number}}.
* Для пользовательского имени типа применяются те же правила по вхождению токенов. Если ни одно правило не сработало, возвращается {{undefined}}.
* {{TIME}} без даты отдельно не поддерживается и возвращается как {{undefined}}.
* Backend не анализирует фактические значения колонки и не делает выборку данных для определения типа.
* Если дата/время физически хранится как число или строка, результат всё равно определяется только по объявленному типу: {{DATE}}, {{DATETIME}} и {{TIMESTAMP}} дают {{date}}; {{INTEGER}} даёт {{number}}.
* Для полей {{view}}, у которых SQLite не возвращает объявленный тип, применяется {{undefined}}.

----
h3. 5. Правила нормализации ClickHouse.

Конкретная матрица ClickHouse приведенна ниже. Тип разбирается по полной структуре, а не простым поиском подстроки.

|| Нативный тип ClickHouse || {{fields[].type}} ||
| {{Int8}}–{{Int256}}, {{UInt8}}–{{UInt256}} | {{number}} |
| {{Float32}}, {{Float64}}, {{BFloat16}} | {{number}} |
| {{Decimal(P, S)}}, {{Decimal32(S)}}, {{Decimal64(S)}}, {{Decimal128(S)}}, {{Decimal256(S)}} | {{number}} |
| {{Bool}} | {{number}} |
| {{String}}, {{FixedString(N)}} | {{string}} |
| {{Enum8}}, {{Enum16}}, {{UUID}}, {{IPv4}}, {{IPv6}} | {{string}} |
| {{Date}}, {{Date32}}, {{DateTime(...)}}, {{DateTime64(...)}} | {{date}} |
| {{Nullable(T)}} | Результат рекурсивного сопоставления {{T}} |
| {{LowCardinality(T)}} | Результат рекурсивного сопоставления {{T}} |
| {{SimpleAggregateFunction(function, T)}} | Результат рекурсивного сопоставления {{T}} |
| {{Array(T)}}, {{Tuple(...)}}, {{Map(...)}}, {{Nested(...)}} | {{undefined}} |
| {{AggregateFunction(...)}}, {{Nothing}}, {{JSON}} / {{Object}}, {{Dynamic}}, {{Variant}}, геометрические, интервальные и иные неописанные типы | {{undefined}} |

Примеры:
* {{Nullable(UInt64)}} → {{type = "number"}};
* {{LowCardinality(Nullable(String))}} → {{type = "string"}};
* {{Array(Nullable(Int32))}} → {{type = "undefined"}};
* {{DateTime64(3, 'UTC')}} → {{type = "date"}};
* {{Decimal(38, 10)}} → {{type = "number"}};
* {{Nullable(Nothing)}} → {{type = "undefined"}}.

Дополнительные правила:
* Внешняя составная структура имеет приоритет: {{Array(Int32)}} остаётся {{undefined}}, хотя элемент массива является числом.
* Параметры {{Decimal}}, точность {{DateTime64}}, часовой пояс и все обёртки обязательно сохраняются в {{source_type}}.
* Классификация {{Decimal}} как {{number}} не означает преобразование значения во frontend-тип Number и не гарантирует сохранение точности при последующей обработке.
* Для новых или неизвестных типов ClickHouse используется безопасный fallback {{undefined}} без падения всей команды.
* В примере нового контракта следует использовать каноническое написание {{UInt32}}, а не {{Uint32}}.
* Уникальность batch-элементов: если в запросе get дублируется пара (table, schema), backend возвращает только один объект в ответе. Если для одного из дубликатов обработки возникает ошибка, приоритет отдаётся результату без ошибки (error = null).

----
h3. 6. Минимальные уточнения API-контракта.

* Для {{metadata.tables.list.data[].type}} явно зафиксировать enum: {{table}}, {{view}}.
* Для {{metadata.tables.get.data[].fields[].type}} явно зафиксировать отдельный enum: {{number}}, {{string}}, {{date}}, {{undefined}}.
* Для metadata.tables.get.data[].error зафиксировать enum: not_found (объект отсутствует в СУБД на момент выполнения), access_denied (недостаточно прав на объект), internal_error (непредвиденный сбой при получении конкретного объекта). Значение null означает успешное получение объекта. При error != null поля type и fields возвращаются как null.
