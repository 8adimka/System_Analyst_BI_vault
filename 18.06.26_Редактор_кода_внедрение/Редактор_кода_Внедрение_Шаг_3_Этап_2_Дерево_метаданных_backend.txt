h3. 1. Цель и контекст.

В рамках задачи [https://jira.modusbi.ru/browse/MB-4513] для редактора SQL в карточке *произвольного набора данных* реализуется расширенный режим с левой панелью +метаданных+ для выбранного Источника.

Для полноценной работы этой панели frontend должен получать не только сведения о наборах данных, но и фактические метаданные таблиц источника данных: список таблиц, список полей конкретной таблицы и типы этих полей.

Существующий функционал портала ограничивает frontend информацией о наборах данных. Для сценария, описанного в задаче MB-4513, этого недостаточно, потому что набор данных является производной сущностью и не всегда отражает актуальное состояние таблиц Источника. При изменениях в источнике или правилах работы с источником frontend не получает полную картину доступных таблиц и полей, из-за чего нельзя корректно построить дерево метаданных, производить автодополнение и вставку объектов источника в SQL/вычисляемые выражения.

*Цель задачи* - реализовать на backend API для получения (read-only) метаданных таблиц источника данных и их полей, чтобы frontend мог использовать эти данные в дереве метаданных, автодополнении и вставке объектов источника в редактор {{CodeMirror}}.

{panel:title=Ключевой принцип backend-доработки|borderStyle=dashed|borderColor=#ccc|titleBGColor=#DDEBF7|bgColor=#F8FBFF}
* API должно возвращать именно метаданные таблиц выбранного источника данных, а не список наборов данных и не результат последней проверки SQL-запроса.
* API должно быть доступным +только на чтение+: в рамках задачи не требуется создавать, изменять, удалять таблицы или загружать строки данных.
* Внешний backend-объект API - {{datasources}}, так как таблицы запрашиваются в контексте конкретного источника данных.
* Необходимые команды - {{tables.list}} и {{tables.get}}.
* Идентификатор источника данных передаётся в {{command.id}}.
* Типы полей должны возвращаться в виде, который можно однозначно сопоставить со значениями справочника/эндпойнта {{trivial_type}}.
* API должно сохранять существующую бизнес-логику произвольного набора данных: проверку SQL, обновление выходных полей и сохранение формы.
{panel}

----
h3. 2. Описание текущего поведения.

h4. 2.1. Ограничение доступных метаданных.

Сейчас frontend портала может работать с метаданными наборов данных, но не имеет достаточного backend-контракта для прямого получения:
* списка таблиц выбранного источника данных;
* списка полей и их типов конкретной таблицы;

Из-за этого левая панель метаданных в расширенном редакторе SQL не может строиться на актуальном состоянии таблиц источника. Frontend вынужден использовать датасеты или другие косвенные данные, которые не покрывают целевой сценарий полностью.

---
h4. 2.2. Почему сведений о датасетах недостаточно.

Набор данных описывает пользовательский слой для построения отчётов и визуализаций. При этом в произвольном SQL пользователь может обращаться к таблицам источника данных напрямую, до создания набора данных на каждую таблицу или независимо от него.

Проблемный сценарий:
# Пользователь открывает карточку *произвольного набора данных* и пишет SQL в расширенном редакторе.
# Frontend определяет источник данных, выбранный в карточке набора данных.
# Frontend не может показать актуальные таблицы и поля источника.
# Пользователь не получает полноценное дерево метаданных, автодополнение и корректную вставку полей в SQL/вычисляемые выражения.

----
h3. 3. Описание целевого поведения.

h4. 3.1. Общая логика работы.

После доработки backend должен предоставить frontend возможность получать актуальные метаданные таблиц выбранного источника данных.

Целевой сценарий:
# Frontend открывает расширенный редактор SQL в карточке *произвольного набора данных*.
# Frontend определяет текущий источник данных из контекста карточки набора данных.
# Frontend вызывает существующую команду {{datasources.list}}, если требуется получить или уточнить идентификатор источника.
# Frontend вызывает команду {{tables.list}} и получает список таблиц выбранного источника.
# Frontend отображает таблицы верхним уровнем дерева метаданных.
# При раскрытии таблицы или при необходимости загрузить её поля frontend вызывает команду {{tables.get}} для конкретной таблицы.
# Backend возвращает имя таблицы и массив полей с именем и типом каждого поля.
# Frontend использует полученные данные для дерева метаданных, автодополнения и вставки имён таблиц/полей в редактор {{CodeMirror}}.

Метаданные таблиц должны быть доступны без предварительного выполнения действия {{«Проверить запрос»}} и без зависимости от результата последней успешной проверки SQL.

---
h4. 3.2. Источник истинности для дерева метаданных.

Источником истинности для левой панели расширенного редактора SQL должны быть *метаданные таблиц выбранного источника данных*.

Не должны использоваться как единственный источник данных для этой панели:
* выходные поля текущего SQL-запроса;
* список существующих наборов данных;
* результат последней проверки SQL;
* сохранённые поля произвольного набора данных.

Эти сущности могут оставаться частью текущей бизнес-логики набора данных, но не должны подменять новый backend-контракт {{tables.list}} / {{tables.get}}.

---
h4. 3.3. Применимость для обычной и облачной версии портала.

Данная доработка должна быть доступна как для обычной версии портала, так и для облачной, где также в рамках задачи MB-4513 реализуется дерево метаданных для использования в новом редакторе кода.

Решение должно быть универсальным: frontend получает метаданные таблиц напрямую из источника данных и не зависит от того, создан ли для этих таблиц отдельный набор данных.

----
h3. 4. Рамки задачи.

h4. 4.1. Входит в рамки задачи.

В рамках данной задачи требуется:
* реализовать команду {{tables.list}} для получения списка таблиц выбранного источника данных;
* реализовать команду {{tables.get}} для получения полей конкретной таблицы выбранного источника данных;
* вернуть для таблицы минимально необходимую структуру метаданных: имя таблицы, имена полей и типы полей;
* обеспечить однозначное сопоставление возвращаемых типов полей со значениями {{trivial_type}};
* обеспечить работу контракта для сценария расширенного SQL-редактора в *произвольном наборе данных*;
* обеспечить аналогичную доступность контракта в облачной версии портала, если источник данных поддерживает чтение метаданных таблиц;
* сохранить текущие механики чтения источников данных через существующую команду {{datasources.list}};
* сохранить существующую бизнес-логику проверки SQL, обновления выходных полей и сохранения набора данных.

---
h4. 4.2. Не входит в рамки задачи.

В рамках данной задачи не требуется:
* реализовывать frontend-дерево метаданных, UI расширенного редактора или автодополнение - эти работы относятся к MB-4513;
* менять сценарии создания, проверки и сохранения произвольного набора данных;
* менять структуру существующих датасетов или правила построения отчётов;
* создавать, изменять или удалять таблицы источника данных;
* возвращать строки данных из таблиц;
* добавлять новый механизм управления правами, если достаточно существующих проверок доступа к источнику данных;
* подменять новый контракт данными из датасетов, выходных полей SQL или результата последней проверки запроса.

----
h3. 5. API-контракт.

h4. 5.1. Общие требования к формату API.

Команды должны соответствовать текущей логической модели API портала:
* в теле запроса передаются {{object}}, {{command}} и при необходимости дополнительные параметры;
* успешный ответ содержит {{mode}}, {{status}}, {{message}}, {{data}};
* {{status = 200}} означает успешное выполнение команды;
* значения {{status}}, отличные от {{200}}, означают ошибку и должны сопровождаться понятным {{message}}.

Новый контракт должен использовать объект {{datasources}}, потому что таблицы и поля запрашиваются в контексте конкретного источника данных.

---
h4. 5.2. Определение ID источника данных.

Для выбора источника, к примеру, может использоваться существующая команда. В рамках данной задачи её контракт не меняется.

*Запрос:*
{code:json}
{
    "command": {
        "name": "list"
    },
    "object": {
        "name": "datasources"
    }
}
{code}

*Пример ответа:*
{code:json}
{
    "mode": "online",
    "status": 200,
    "message": "",
    "data": [
        {
            "ID": 10,
            "caption": "ClickHouse",
            "name": "ClickHouse system",
            "parentID": 50,
            "rls": 0,
            "rls_install": 0
        },
        {
            "ID": 28,
            "caption": "ADQM_BI",
            "name": "ADQM_BI",
            "parentID": 50,
            "rls": 0,
            "rls_install": 0
        }
    ]
}
{code}

Либо Frontend определяет нужный Источник из контекста карточки набора данных и использует его {{ID}} как {{command.id}} в командах {{tables.list}} и {{tables.get}}.

---
h4. 5.3. Команда {{tables.list}}.

Команда {{tables.list}} должна возвращать список таблиц выбранного источника данных.

*Назначение команды:*
* получить верхний уровень дерева метаданных для расширенного SQL-редактора;
* вернуть только метаданные таблиц, без полей и без строк данных;
* не зависеть от наличия датасетов, созданных на основании этих таблиц.

*Запрос:*
{code:json}
{
    "command": {
        "name": "tables.list",
        "id": 10
    },
    "object": {
        "name": "datasources"
    }
}
{code}

*Параметры запроса:*
|| Поле || Обязательность || Описание ||
| {{object.name}} | Да | Должно быть равно {{datasources}}. |
| {{command.name}} | Да | Должно быть равно {{tables.list}}. |
| {{command.id}} | Да | {{ID}} источника данных из {{datasources.list}}. |

*Успешный ответ:*
{code:json}
{
    "mode": "online",
    "status": 200,
    "message": "",
    "data": [
        {
            "name": "dim_product"
        },
        {
            "name": "dim_customer"
        },
        {
            "name": "dim_date"
        },
        {
            "name": "fact_orders"
        }
    ]
}
{code}

*Поля ответа:*
|| Поле || Тип || Обязательность || Описание ||
| {{data[]}} | array | Да | Список таблиц источника данных. Если таблиц нет или они недоступны пользователю, возвращается пустой массив. |
| {{data[].name}} | string | Да | Имя таблицы в форме, пригодной для дальнейшего запроса {{tables.get}} и отображения во frontend-дереве метаданных. |

*Требования к результату:*
* {{data[].name}} не должно быть пустым;
* в ответе не должно быть дублей таблиц с одинаковым {{name}};
* порядок таблиц должен быть стабильным при неизменном состоянии источника;
* если источник данных использует схему/каталог и без неё имя таблицы неоднозначно, backend должен вернуть {{name}} в той форме, которая однозначно идентифицирует таблицу для текущего источника и может быть передана в {{object.table}} команды {{tables.get}};
* команда не должна возвращать поля таблиц, строки данных, пароли, токены, параметры подключения и другие секреты.

---
h4. 5.4. Команда {{tables.get}}.

Команда {{tables.get}} должна возвращать метаданные конкретной таблицы выбранного источника данных.

*Назначение команды:*
* получить поля таблицы при раскрытии узла дерева метаданных;
* предоставить frontend имена полей и типы для отображения, автодополнения и вставки в SQL;
* использовать тот же источник данных, который был выбран в карточке набора данных.

*Запрос:*
{code:json}
{
    "command": {
        "name": "tables.get",
        "id": 10
    },
    "object": {
        "name": "datasources",
        "table": "fact_sales"
    }
}
{code}

*Параметры запроса:*
|| Поле || Обязательность || Описание ||
| {{object.name}} | Да | Должно быть равно {{datasources}}. |
| {{object.table}} | Да | Имя таблицы из ответа {{tables.list}}. |
| {{command.name}} | Да | Должно быть равно {{tables.get}}. |
| {{command.id}} | Да | {{ID}} источника данных из {{datasources.list}}. |

*Успешный ответ:*
{code:json}
{
    "mode": "online",
    "status": 200,
    "message": "",
    "data": {
        "name": "fact_sales",
        "fields": [
            {
                "name": "sale_id",
                "type": "number"
            },
            {
                "name": "sale_date",
                "type": "date"
            },
            
            ...
            
            {
                "name": "quantity",
                "type": "number"
            },
            {
                "name": "created_at",
                "type": "date"
            }
        ]
    }
}
{code}

*Поля ответа:*
|| Поле || Тип || Обязательность || Описание ||
| {{data.name}} | string | Да | Имя таблицы, для которой возвращаются поля. Должно соответствовать запрошенному {{object.table}} или канонической форме имени этой таблицы в текущем источнике. |
| {{data.fields}} | array | Да | Список полей таблицы. Структура должна быть совместима по смыслу с {{fields[]}} ответа команды {{extraction_rules.get}}, если в backend уже используется аналогичный механизм чтения полей. |
| {{data.fields[].name}} | string | Да | Имя поля таблицы. |
| {{data.fields[].type}} | string | Да | Нормализованный тип поля, который можно однозначно сопоставить со значениями {{trivial_type}}. |

*Требования к результату:*
* {{data.fields}} должен возвращаться массивом, даже если у таблицы нет доступных полей;
* {{data.fields[].name}} не должно быть пустым;
* {{data.fields[].type}} не должно быть пустым;
* в ответе не должно быть дублей полей с одинаковым {{name}} в рамках одной таблицы;
* порядок полей должен быть стабильным при неизменном состоянии таблицы;
* команда не должна возвращать строки данных таблицы;
* команда не должна требовать предварительного вызова {{tables.list}}, если frontend уже знает корректное имя таблицы и источник.

---
h4. 5.5. Требования к типам полей.

Backend должен возвращать {{data.fields[].type}} в нормализованном виде, пригодном для однозначного маппинга на {{trivial_type}}.

Минимальные ожидания:
* числовые типы источника должны маппиться в числовой trivial-тип;
* строковые типы источника должны маппиться в строковый trivial-тип;
* типы даты/даты-времени источника должны маппиться в trivial-тип даты/времени, используемый в портале;
* булевы, бинарные, JSON, UUID, массивы и иные специфические типы должны маппиться по существующим правилам портала, если такие правила уже определены для {{trivial_type}}.

Если для типа источника нет однозначного сопоставления, backend не должен возвращать произвольное значение. В этом случае необходимо использовать существующий согласованный fallback-тип {{trivial_type}} либо вернуть ошибку с понятным {{message}}, чтобы frontend не строил некорректные подсказки и вычисляемые выражения.

---
h4. 5.6. Ошибки и неуспешные ответы.

Для неуспешных сценариев backend должен возвращать +текущий стандартный формат ошибки+ портала:
{code:json}
{
    "mode": "online",
    "status": 500,
    "message": "Описание ошибки",
    "data": null
}
{code}

Обязательные сценарии обработки ошибок:
|| Сценарий || Ожидаемое поведение ||
| Не передан {{command.id}} | Команда завершается ошибкой, {{message}} указывает на отсутствие идентификатора источника данных. |
| Источник данных не найден | Команда завершается ошибкой, метаданные другого источника не возвращаются. |
| У пользователя нет прав на источник | Команда завершается ошибкой доступа, без раскрытия метаданных источника. |
| Источник временно недоступен | Команда завершается ошибкой с понятным {{message}} о недоступности источника/подключения. |
| Источник не поддерживает чтение таблиц | Команда завершается ошибкой с понятным {{message}} о том, что чтение метаданных таблиц для данного источника не поддерживается. |
| Не передан {{object.table}} для {{tables.get}} | Команда завершается ошибкой, {{message}} указывает на отсутствие имени таблицы. |
| Таблица не найдена или недоступна | Команда {{tables.get}} завершается ошибкой, поля другой таблицы не возвращаются. |
| Не удалось сопоставить тип поля с {{trivial_type}} | Команда не должна возвращать некорректный {{type}}; используется согласованный fallback либо возвращается ошибка с понятным {{message}}. |

----
h3. 6. Требования к реализации.

h4. 6.1. Backend-логика.

Backend должен:
* получать список таблиц и поля таблицы из метаданных выбранного источника данных, а не из датасетов;
* использовать {{command.id}} как идентификатор источника данных;
* использовать {{object.table}} как имя таблицы для команды {{tables.get}};
* сохранять точную форму имён таблиц и полей, включая регистр и спецсимволы, если они значимы для источника;
* не смешивать {{object.id}}, {{command.id}} и поля внутри {{data}};
* не изменять настройки источника данных при выполнении {{tables.list}} и {{tables.get}};
* не запускать проверку SQL-запроса произвольного набора данных для получения метаданных таблиц;
* не создавать временные наборы данных для получения списка таблиц и полей;
* учитывать существующие механизмы подключения и чтения схемы источников, если они уже реализованы в backend.

---
h4. 6.2. Права доступа и безопасность.

Backend должен:
* проверять права пользователя на чтение метаданных выбранного источника данных по существующим правилам доступа к источникам/наборам данных;
* не раскрывать метаданные источника пользователю, у которого нет соответствующих прав;
* не возвращать секреты подключения: пароли, токены, ключи, защищённые параметры, DSN с секретами;
* не возвращать строки пользовательских данных из таблиц;
* валидировать {{object.table}} и не допускать использования имени таблицы как произвольного SQL-фрагмента;
* корректно обрабатывать спецсимволы, кавычки и регистр в именах таблиц и полей без SQL-инъекций и без порчи имени.

---
h4. 6.3. Актуальность и кеширование.

Метаданные, возвращаемые командами {{tables.list}} и {{tables.get}}, должны отражать состояние выбранного источника данных в рамках существующих backend-механизмов чтения схемы.

Если backend использует кеш метаданных, необходимо обеспечить:
* непротиворечивость данных между {{tables.list}} и {{tables.get}};
* отсутствие зависимости от устаревших метаданных датасетов;
* корректное обновление данных после изменения источника или его схемы в соответствии с существующими правилами инвалидации кеша;
* отсутствие ситуации, когда таблица видна в {{tables.list}}, но {{tables.get}} для неё стабильно не может вернуть поля без понятной причины в {{message}}.

---
h4. 6.4. Производительность.

Команды должны быть пригодны для источников с большим количеством таблиц и полей.

Требования:
* {{tables.list}} не должен загружать поля всех таблиц, если для списка таблиц это не требуется;
* {{tables.get}} должен загружать поля только запрошенной таблицы;
* при ошибке одной таблицы backend не должен ломать получение списка остальных таблиц в {{tables.list}}, если источник позволяет получить список таблиц;
* время выполнения команд должно оставаться приемлемым для интерактивного раскрытия дерева метаданных во frontend;
* при долгом ответе источника backend должен использовать существующие таймауты и возвращать понятное сообщение об ошибке.

---
h4. 6.5. Совместимость.

Доработка не должна ломать:
* существующую команду {{datasources.list}};
* существующие команды работы с датасетами;
* существующую команду {{extraction_rules.get}} и её {{fields[]}};
* проверку SQL произвольного набора данных;
* обновление выходных полей после проверки SQL;
* сохранение карточки набора данных;
* работу обычной версии портала и облачной версии портала в сценариях, не использующих новый контракт.

----
h3. 7. Пограничные сценарии.

Backend должен корректно обрабатывать следующие сценарии:
* источник данных существует, но не содержит доступных таблиц;
* таблица существует, но у пользователя нет прав на чтение её метаданных;
* таблица была удалена или переименована между вызовами {{tables.list}} и {{tables.get}};
* таблица имеет имя с пробелами, спецсимволами, кавычками или регистрозависимым написанием;
* в разных схемах/каталогах источника есть таблицы с одинаковым коротким именем;
* таблица содержит поля со спецсимволами или регистрозависимыми именами;
* таблица содержит поле с типом, для которого нет прямого аналога в {{trivial_type}};
* источник данных временно недоступен;
* чтение схемы источника занимает больше ожидаемого времени;
* источник возвращает пустой список таблиц или пустой список полей;
* пользователь не авторизован или не имеет прав на источник;
* команды вызываются в облачной версии портала и в обычной версии портала с единым frontend-маркером версии.

h3. 9. Критерии приёмки (AC):

* *AC.1 (Получение списка таблиц источника):*
* *Дано:* пользователь имеет доступ к источнику данных с {{ID = 10}};
* *Когда:* frontend отправляет запрос {{object.name = datasources}}, {{command.name = tables.list}}, {{command.id = 10}};
* *Тогда:* backend возвращает {{status = 200}} и {{data[]}} со списком таблиц источника, где у каждой таблицы заполнено {{name}}.

* *AC.2 (Список таблиц не строится по датасетам):*
* *Дано:* в источнике есть таблица, для которой не создан отдельный набор данных;
* *Когда:* выполняется {{tables.list}} для этого источника;
* *Тогда:* таблица присутствует в ответе, если она доступна пользователю в метаданных источника.

* *AC.3 (Получение полей таблицы):*
* *Дано:* пользователь получил из {{tables.list}} таблицу {{fact_sales}};
* *Когда:* frontend отправляет {{tables.get}} с {{command.id}} выбранного источника и {{object.table = fact_sales}};
* *Тогда:* backend возвращает {{status = 200}}, {{data.name}} и {{data.fields[]}} с полями таблицы.

* *AC.4 (Типы полей сопоставимы с {{trivial_type}}):*
* *Дано:* таблица содержит поля разных типов источника;
* *Когда:* выполняется {{tables.get}};
* *Тогда:* у каждого элемента {{data.fields[]}} заполнены {{name}} и {{type}}, а значение {{type}} можно однозначно сопоставить со значением {{trivial_type}}.

* *AC.5 (Метаданные доступны без проверки SQL):*
* *Дано:* пользователь открыл карточку произвольного набора данных и ещё не запускал {{«Проверить запрос»}};
* *Когда:* frontend вызывает {{tables.list}} и {{tables.get}};
* *Тогда:* backend возвращает метаданные источника независимо от результата проверки SQL-запроса.

* *AC.6 (Разделение идентификаторов):*
* *Дано:* frontend вызывает {{tables.list}} или {{tables.get}};
* *Когда:* в запросе передан {{command.id}} источника данных;
* *Тогда:* backend использует именно {{command.id}} как идентификатор источника и не требует передачи {{object.id}} или идентификатора датасета для получения таблиц.

* *AC.7 (Ошибка при отсутствии источника):*
* *Дано:* frontend вызывает {{tables.list}} или {{tables.get}} без {{command.id}} либо с несуществующим {{command.id}};
* *Когда:* backend обрабатывает запрос;
* *Тогда:* команда завершается неуспешным {{status}}, возвращает понятный {{message}} и не возвращает метаданные другого источника.

* *AC.8 (Ошибка при отсутствии таблицы):*
* *Дано:* frontend вызывает {{tables.get}} без {{object.table}} либо с таблицей, которой нет в выбранном источнике;
* *Когда:* backend обрабатывает запрос;
* *Тогда:* команда завершается неуспешным {{status}}, возвращает понятный {{message}} и не возвращает поля другой таблицы.

* *AC.9 (Проверка прав доступа):*
* *Дано:* пользователь не имеет прав на выбранный источник данных;
* *Когда:* он вызывает {{tables.list}} или {{tables.get}};
* *Тогда:* backend возвращает ошибку доступа и не раскрывает список таблиц, полей или технические параметры подключения.

* *AC.10 (Отсутствие строк данных и секретов):*
* *Дано:* frontend вызывает {{tables.list}} или {{tables.get}} для доступного источника;
* *Когда:* backend возвращает успешный ответ;
* *Тогда:* ответ содержит только метаданные таблиц/полей и не содержит строки данных, пароли, токены, ключи или другие секреты подключения.

* *AC.11 (Стабильность имён таблиц и полей):*
* *Дано:* источник содержит таблицы и поля с регистрозависимыми именами или спецсимволами;
* *Когда:* выполняются {{tables.list}} и {{tables.get}};
* *Тогда:* backend возвращает имена в форме, пригодной для дальнейшего отображения и передачи обратно в {{tables.get}}, без потери регистра и без искажения имени.

* *AC.12 (Совместимость с существующей логикой набора данных):*
* *Дано:* после внедрения нового API пользователь работает с произвольным набором данных;
* *Когда:* он проверяет SQL, обновляет выходные поля и сохраняет карточку набора данных;
* *Тогда:* существующая бизнес-логика проверки SQL, обновления выходных полей и сохранения работает без регресса.

* *AC.13 (Работа в обычной и облачной версии портала):*
* *Дано:* источник данных доступен в обычной версии портала или в облачной версии портала и поддерживает чтение метаданных таблиц;
* *Когда:* frontend вызывает {{tables.list}} и {{tables.get}} по единому контракту;
* *Тогда:* backend возвращает метаданные в одинаковой структуре ответа для обеих версий портала.

* *AC.14 (Совместимость с {{extraction_rules.get}}):*
* *Дано:* в backend уже существует механизм получения полей, аналогичный {{fields[]}} ответа {{extraction_rules.get}};
* *Когда:* реализуется {{tables.get}};
* *Тогда:* структура {{data.fields[]}} по смыслу совместима с существующим подходом к описанию полей, но минимально обязательно содержит {{name}} и {{type}}.

* *AC.15 (Неизменность существующих API):*
* *Дано:* после внедрения {{tables.list}} и {{tables.get}} выполняются существующие команды {{datasources.list}}, команды работы с датасетами и {{extraction_rules.get}};
* *Когда:* пользователь выполняет прежние сценарии портала;
* *Тогда:* существующие ответы и сценарии не меняются, если они не используют новый контракт явно.
