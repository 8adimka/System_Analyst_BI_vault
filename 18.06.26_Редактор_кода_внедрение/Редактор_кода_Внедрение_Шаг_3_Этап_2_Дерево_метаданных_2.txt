Редактор для SQL и JS кода. Внедрение. Шаг 3 - «Наборы данных». Этап 2: Дерево метаданных

h3. 1. Цель и контекст.

При написании SQL для произвольного набора данных пользователь сейчас не видит доступные схемы, таблицы, {{view}} и поля выбранного источника и вынужден открывать внешние инструменты, чтобы посмотреть метаданные и собрать запрос.

На Этапе 1 в карточку *произвольного* набора данных уже внедрен новый редактор SQL на базе {{CodeMirror}}.

Настоящая история является *Этапом 2* развития данного сценария.

Цель Этапа 2 — добавить для этого редактора {{расширенный режим}} работы с SQL, в котором пользователь получает доступ к метаданным выбранного источника данных и вспомогательным панелям, не теряя при этом текущую бизнес-логику проверки запроса, обновления выходных полей и сохранения формы набора данных.

{panel:title=Важно:|borderStyle=dashed|borderColor=#ff9900|bgColor=#fffcf5}
* В рамках данной задачи расширенный режим внедряется *только* для пользовательских {{«произвольных»}} наборов данных.
* Расширенный режим не заменяет бизнес-логику основной формы и не вводит отдельного процесса сохранения набора данных.
* Финальное сохранение набора данных как объекта по-прежнему выполняется только штатной кнопкой {{«Сохранить»}} основной формы.
* Текущие *выходные поля набора данных* не являются источником данных для левой боковой панели расширенного режима. В левой панели должны использоваться именно *метаданные выбранного источника данных*.
{panel}

{panel:title=Ключевой принцип интеграции:|borderStyle=dashed|borderColor=#ccc|titleBGColor=#DDEBF7|bgColor=#F8FBFF}
* Расширенный режим должен использовать тот же редактор {{CodeMirror}}, который был внедрен на Этапе 1.
* Переход в расширенный режим и выход из него не создают отдельной сессии редактирования: пользователь работает с тем же текущим состоянием в SQL-форме.
* Источником истины для валидности _SQL-запроса_ остается существующая бизнес-логика модуля и штатное действие {{«Проверить запрос»}}, оно должно быть доступно также напрямую из расширенного режима.
* Левая боковая панель расширенного режима предназначена для работы *с метаданными источника данных*.
* Правая боковая панель расширенного режима предназначена для ускоряющих работу служебных вставок и шаблонов.
* Перед самостоятельной разработкой левой панели метаданных необходимо проанализировать и переиспользовать существующие наработки дерева метаданных, реализованные в рамках {{составного набора данных}}, если они применимы к сценарию *произвольного* набора данных.
* Внедрение должно быть выполнено без регресса для текущего сценария: редактирование SQL → проверка запроса → обновление выходных полей → ручная настройка атрибутов полей → сохранение набора данных.
{panel}

h3. 2. Функциональные требования к интеграции.

h4. 2.1. Точка входа в расширенный режим.
* Из базового редактора SQL пользователь должен иметь возможность перейти в {{расширенный режим}} по штатному действию интерфейса - нажатие кнопки "Расширенный редактор" под кнопкой "Проверить запрос".
* При открытии расширенного режима редактор должен получать *актуальное текущее значение* SQL из формы набора данных.
* При выходе из расширенного режима введенный SQL не должен теряться.
* Расширенный режим не должен требовать отдельного действия {{«Применить»}} или {{«Отмена»}}: это тот же редактор в более функциональном режиме отображения.

h4. 2.2. UI расширенного режима и компоновка.
* Расширенный режим открывается в крупном модальном окне, удобном для написания длинных SQL-запросов. Расширенный режим максимально использует доступную область экрана, но не полностью заменяющем страницу. Фон основной формы остаётся видимым/затемнённым как у стандартных модальных окон продукта.
* В расширенном режиме должно быть доступно явное действие возврата в базовый вид редактора — например, кнопка {{«Свернуть редактор»}}. При нажатии модальное окно закрывается, пользователь возвращается к базовому редактору с тем же текстом SQL.
* Внутри расширенного режима должна быть реализована трехзонная компоновка:
** *центральная основная зона* — редактор {{CodeMirror}};
** *левая вспомогательная зона* — панель метаданных выбранного источника данных;
** *правая вспомогательная зона* — панель шаблонов и служебных вставок.
* Основная площадь рабочего пространства должна быть отдана редактору.
* Левая и правая панели должны иметь адаптивно-фиксированную ширину, достаточную для чтения содержимого, с возможностью её настройки/регулировки (потянув за край боковой панели).
* Для длинного SQL-скрипта и длинного содержимого боковых панелей должны работать *внутренние скроллы* соответствующих областей.
* Для удобства работы на узких экранах боковые панели должны иметь возможность сворачиваться, но должны оставаться доступными без выхода из расширенного режима.

h4. 2.3. Левая панель с метаданными источника данных.
* В левой части расширенного режима должен отображаться список метаданных *выбранного источника данных*.
* В верхней части левой панели должно отображаться наименование текущего источника данных, в рамках которого показаны схемы, таблицы, {{view}} и поля.
* Источником данных для этой панели должны быть метаданные текущего подключенного источника, без возможности его смены.
* Получение метаданных должно выполняться через backend-объект {{datasources}} и команды {{metadata.tables.list}} / {{metadata.tables.get}} по актуальному контракту [^Дерево_метаданных_контракты_команд_2.txt].
* Идентификатор выбранного источника данных должен передаваться в {{object.id}}. Для идентификации объекта источника и повторной передачи в {{metadata.tables.get}} frontend должен использовать полученную от backend пару {{table}} + {{schema}}, не изменяя значения и регистр этих полей.
* В панели должны быть доступны как минимум:
** обычные пользовательские таблицы и {{view}} текущей базы данных из всех доступных пользовательских схем, возвращённые backend;
** поля объектов и полученные от backend типы полей.
* {{metadata.tables.list}} должен вызываться без {{data}}. Frontend должен обрабатывать массив {{data[]}}, в котором для каждого объекта возвращаются {{table}}, {{schema}} и {{type}} со значением {{table}} или {{view}}.
* Дерево метаданных должно учитывать схемы источника:
** если {{schema}} заполнена, объекты группируются по узлам схем;
** для SQLite используется возвращаемый backend уровень {{schema = "main"}};
** для ClickHouse, где backend возвращает {{schema = ""}}, дополнительный уровень схемы не создаётся;
** обычная таблица и {{view}} различаются по {{type}} без добавления префикса к имени и без изменения значения {{table}}.
* Объекты с одинаковым {{table}} в разных схемах должны отображаться и обрабатываться независимо.
* Каждый объект раскрывается как узел дерева, показывая список полей. При раскрытии одного или нескольких объектов frontend должен вызывать batch-команду {{metadata.tables.get}} и передавать в {{data[]}} соответствующие пары {{table}} + {{schema}}.
* В ответе {{metadata.tables.get}} frontend должен независимо обрабатывать каждый элемент {{data[]}} и поля {{table}}, {{schema}}, {{type}}, {{error}}, {{fields}}. Для каждого успешно полученного поля должны обрабатываться {{name}}, нормализованный {{type}} и исходный {{source_type}}.
* Frontend не должен самостоятельно разбирать нативные типы отдельных СУБД. {{fields[].type}} используется как информационная классификация поля и принимается только из enum {{number}}, {{string}}, {{date}}, {{undefined}}; {{fields[].source_type}} отображается как исходный тип СУБД без преобразования. Значение {{undefined}} должно корректно отображаться и не должно приводить к ошибке построения дерева.
* Ошибка отдельного объекта {{not_found}}, {{access_denied}} или {{internal_error}} должна отображаться в состоянии соответствующего узла и не должна скрывать успешно загруженные объекты того же batch-ответа. Для ошибочного элемента значения {{type}} и {{fields}} не используются, поскольку backend возвращает их как {{null}}. Общая ошибка команды на уровне HTTP/протокола должна обрабатываться как недоступность метаданных источника в целом.
* Панель должна поддерживать:
** поиск;
** разворачивание и сворачивание узлов схем и объектов;
** корректное состояние загрузки;
** корректную пустую заглушку или сообщение об ошибке, если метаданные временно недоступны.
* Метаданные должны быть доступны пользователю без обязательного предварительного успешного выполнения текущего SQL-запроса.
* Левая панель метаданных должна быть выполнена в светлой стилистике, близкой к панели полей в форме работы с мерами набора данных.

h4. 2.4. Переиспользование дерева метаданных из составного набора данных.

{panel:title=Важно: функционал "Дерево метаданных" уже частично реализован в рамках составного набора данных |borderStyle=dashed|borderColor=#ccc|titleBGColor=#DDEBF7|bgColor=#F8FBFF}
* В интерфейсе {{составного набора данных}} существует частичная реализация дерева метаданных, применимые UI-компоненты и механики которой должны быть переиспользованы.
* В рамках текущей задачи не требуется реализовывать дерево метаданных с нуля, если существующие наработки можно адаптировать для расширенного режима редактора SQL в *произвольном* наборе данных.
* Перед разработкой необходимо провести техническую проверку существующей реализации: источник получения метаданных, структура дерева, поиск, разворачивание/сворачивание узлов, состояния загрузки/ошибки/пустого результата, механизм выбора/перетаскивания элементов и ограничения по типам источников.
* Пригодные части реализации должны быть переиспользованы или вынесены в переиспользуемый компонент/адаптер без изменения пользовательского сценария {{составных наборов данных}}.
* Если часть функциональности из составного набора данных не покрывает требования текущего расширенного режима, недостающие возможности дорабатываются точечно в рамках требований п. 2.3, 2.6 и 2.8, без дублирования уже существующей логики.
* Независимо от объёма переиспользования, получение данных для дерева в *произвольном* наборе данных должно выполняться по контракту [^Дерево_метаданных_контракты_команд_2.txt].
* Переиспользование существующих наработок не должно менять границы задачи: доработка внедряется для *произвольных* наборов данных, а сценарии создания/редактирования {{составных}} наборов данных в рамках этой истории не изменяются.
{panel}

h4. 2.5. Правая панель вспомогательных вставок.
* В правой части расширенного режима должна отображаться вспомогательная панель служебных вставок.
* Минимально обязательный состав правой панели:
** шаблоны переменных окружения;
** шаблоны серверных переменных;
** список распространённых агрегирующих функций: SUM, AVG, MIN, MAX, COUNT, DISTINCT и т.д.
* Для правой панели допускается использование структуры секций, чтобы пользователь мог сворачивать и разворачивать группы вставок.

h4. 2.6. Вставка объектов из боковых панелей в редактор.
* Объекты из боковых панелей должны быть доступны для вставки в SQL в расширенном режиме редактора кода.
* Базовый способ вставки — {{Drag-and-Drop}} в область редактора.
* Дополнительно допускается поддержка альтернативного действия вставки (например, двойной клик), если это не усложняет UX.
* Из левой панели в редактор должны вставляться:
** имена таблиц и {{view}};
** имена полей.
* Из правой панели в редактор должны вставляться:
** шаблоны переменных окружения;
** шаблоны серверных переменных;
** иные поддерживаемые системные и общеупотребимые конструкции.
* При перетаскивании таблицы или {{view}} frontend должен сформировать синтаксически безопасный для текущего SQL-диалекта идентификатор с использованием полученной пары {{schema}} + {{table}}. Непустое значение {{schema}} не должно отбрасываться; при пустом {{schema}} искусственный префикс не добавляется.
* При перетаскивании поля вставляется имя поля. Формат вставки регулируется параметром {{«Указывать наименование таблицы при вставке поля»}} (checkbox, по умолчанию выключен):
** при выключенном параметре вставляется {{field_name}};
** при включённом параметре вставляется {{field_name}} с синтаксически безопасным квалификатором объекта, сформированным из {{schema}} и {{table}}.
* Вставка должна происходить *в текущую позицию каретки*:
** Если редактор временно потерял фокус, должна использоваться последняя известная позиция каретки.
** Если пользователь ранее не фокусировался в редактор, вставка допускается в конец SQL-скрипта.
** Если в редакторе включен мультикурсор, вставка должна выполняться по всем активным курсорам.
** Если для корректной SQL-вставки требуется экранирование/кавычки в соответствии с диалектом текущего источника, вставка должна использовать синтаксически безопасную форму идентификатора.

h4. 2.7. Интеграция с действием {{«Проверить запрос»}}.
* В расширенном режиме должны быть доступны две основные команды: {{«Проверить запрос»}} и {{«Свернуть редактор»}} (возврат в базовый вид). 
* Кнопка {{«Проверить запрос»}} должна быть визуально доступна на уровне рабочей области редактора, чтобы пользователь мог проверить SQL без выхода из расширенного режима. Финальное расположение допускается по UI-гайдам продукта и общим практикам компании.
* Проверка должна выполняться *по текущему тексту SQL из редактора*, а не по какой-либо отдельной промежуточной копии.
* При успешной проверке:
** должна отработать текущая бизнес-логика модуля проверки запроса;
** список выходных полей набора данных должен обновиться по текущим правилам формы;
** должны сохраниться ранее введенные атрибуты совпавших полей по текущим правилам сопоставления;
** пользователь должен получить штатное успешное уведомление.
* При неуспешной проверке:
** пользователь должен получить понятное сообщение об ошибке;
** текст SQL в редакторе не должен теряться;
** расширенный режим не должен закрываться;
** ранее существующий валидный список выходных полей не должен разрушаться некорректным промежуточным состоянием.
* Проверка SQL *не должна* запускаться автоматически на каждый ввод символа.

h4. 2.8. SQL-диалект, автодополнение и системный синтаксис.
* Расширенный режим должен работать в режиме SQL с определением диалекта по типу текущего источника данных.
* Для источников, для которых в текущей реализации уже есть прямое сопоставление с диалектом {{CodeMirror}}, должно использоваться нативное сопоставление.
* Для источников, для которых нативный диалект отсутствует, должен использоваться согласованный fallback-режим (например, StandardSQL либо уже реализованный в проекте кастомный диалект).
* При вводе текста должно работать выпадающее меню автодополнения.
* В обязательный состав подсказок расширенного режима должны входить:
** стандартные SQL-ключевые слова;
** встроенные SQL-функции;
** таблицы и {{view}} выбранного источника данных, полученные через {{metadata.tables.list}} и различаемые с учётом {{schema}};
** поля из метаданных выбранного источника данных.
* Автодополнение должно вызываться как при вводе текста, так и по явной горячей клавише (например, {{Ctrl+Space}}).
* Конфигурация редактора должна корректно распознавать системный синтаксис проекта и не помечать его как ошибку, включая:
** {{\!env.NAME\!}}, {{\!env.NAME.BEGIN\!}}, {{\!env.NAME.END\!}};
** конструкции с fallback-логикой внутри фигурных скобок;
** иные серверные/системные переменные проекта, уже допустимые в SQL наборах данных.

h4. 2.9. Подсветка ошибок и базовый UX.
* Если backend проверки запроса возвращает ошибку и позволяет определить проблемное место, это место должно быть визуально акцентировано в редакторе.
* При невозможности точной привязки ошибки к позиции в тексте должно показываться понятное текстовое сообщение без потери введенного SQL.
* В расширенном режиме должен быть сохранен базовый UX переиспользуемого виджета:
** нумерация строк;
** подсветка синтаксиса SQL;
** подсветка и автозакрытие скобок/кавычек;
** Undo/Redo (даже при переходе между стандартным и продвинутыми режимами);
** поддержка мультикурсорного редактирования;
** корректный вертикальный внутренний скролл;
** стабильная работа с длинными запросами.
* Горячие клавиши стандартных действий редактора не должны конфликтовать с действиями расширенного режима и основной формы.

В Scope данной истории входит:

* левая панель метаданных выбранного источника данных;
* анализ и переиспользование существующих наработок дерева метаданных из {{составного набора данных}} для левой панели расширенного режима, если они технически применимы;
* правая панель служебных вставок и шаблонов;
* вставка объектов из боковых панелей в SQL;
* metadata-aware автодополнение таблицами, {{view}} и полями источника данных с учётом схем;
* сохранение текущей бизнес-логики действия {{«Проверить запрос»}}.

В Scope данной истории *не* входит:
* отдельное backend-хранение черновиков SQL;
* изменение пользовательских сценариев для {{простых}} и {{составных}} наборов данных;
* отдельная панель *выходных полей результата текущего SQL* внутри редактора;
* самостоятельная реализация дерева метаданных с нуля без предварительной проверки существующей реализации в {{составном наборе данных}};
* самостоятельное изменение backend-бизнес-логики проверки запроса, если это не требуется для получения уже существующих метаданных.
{panel}

h3. 3. Критерии приёмки (AC):

* *AC1 (Переход в расширенный режим):* Из базового редактора SQL пользователь может открыть расширенный режим и увидеть в нем тот же текущий текст SQL.
* *AC2 (Синхронность состояния):* Переход в расширенный режим и выход из него не приводят к потере введенного SQL и не требуют отдельных действий {{«Применить»}} или {{«Отмена»}}.
* *AC3 (Компоновка расширенного режима):* Расширенный режим открывается в крупном модальном окне, максимально использующем доступную область экрана, но не полностью заменяющем страницу. Фон основной формы остаётся видимым/затемнённым как у стандартных модальных окон продукта. Расширенный режим содержит центральный редактор, левую панель метаданных и правую вспомогательную панель; внутренние скроллы работают без поломки верстки.
* *AC4 (Метаданные источника):* В левой панели отображаются метаданные выбранного источника данных, полученные командой {{metadata.tables.list}}: схемы, обычные таблицы и {{view}} только текущей базы данных. Объекты с непустой {{schema}} сгруппированы по узлам схем; для ClickHouse при {{schema = ""}} дополнительный уровень схемы отсутствует. Таблицы и {{view}} различаются по {{type}} без изменения имени {{table}}. Каждый объект раскрывается как узел дерева и показывает полученные поля; для поля отображается исходный {{source_type}}, а нормализованный {{type}} используется для информационной классификации. Значение {{undefined}} обрабатывается без ошибки. Доступен поиск, корректно обрабатываются состояния загрузки, пустого результата и ошибки. В верхней части левой панели отображается наименование текущего источника данных.
* *AC5 (Вставка из метаданных):* Пользователь может вставить таблицу, {{view}} или поле из левой панели в SQL через {{Drag-and-Drop}}. Вставка происходит в текущую/последнюю позицию каретки либо в конец текста, если каретка ранее не была установлена. Для одноимённых объектов из разных схем вставляемый идентификатор соответствует выбранной паре {{table}} + {{schema}}; при пустом {{schema}} искусственный префикс не добавляется.
* *AC6 (Вставка из правой панели):* Пользователь может вставить в SQL шаблоны переменных окружения и серверных переменных из правой панели.
* *AC7 (Мультикурсор):* Если в редакторе активирован мультикурсор, вставка текста из боковых панелей выполняется по всем активным курсорам.
* *AC8 (SQL-диалект и безопасная вставка):* Подсветка SQL и режим редактора корректно определяются по типу источника данных; при вставке идентификаторов используется синтаксически безопасная форма для текущего диалекта.
* *AC9 (Автодополнение):* При вводе текста работает выпадающее меню автодополнения, содержащее SQL-ключевые слова, SQL-функции, таблицы, {{view}} и поля из метаданных выбранного источника данных. Одноимённые объекты разных схем различаются с учётом {{schema}}; автодополнение доступно и по {{Ctrl+Space}}.
* *AC10 (Проверка запроса):* Кнопка {{«Проверить запрос»}} внутри расширенного режима проверяет *текущий* текст запроса из редактора. При успехе обновляются выходные поля формы. При ошибке режим не закрывается, SQL не теряется.
* *AC11 (Системный синтаксис):* Конструкции вида {{\!env.NAME\!}}, {{\!env.NAME.BEGIN\!}}, {{\!env.NAME.END\!}} и иные поддерживаемые системные переменные проекта корректно подсвечиваются и не помечаются как синтаксическая ошибка редактора.
* *AC12 (Без регресса бизнес-логики):* После внедрения расширенного режима не сломаны существующие сценарии формы произвольного набора данных: проверка SQL, обновление выходных полей, ручное редактирование атрибутов полей и итоговое сохранение набора данных.
* *AC13 (Переиспользование дерева метаданных):* Для левой панели переиспользованы применимые компоненты и механики дерева метаданных из {{составного набора данных}}; данные для *произвольного* набора данных загружаются по актуальному контракту, при этом пользовательские сценарии {{составных}} наборов данных не изменены и не сломаны.
* *AC14 (Получение полей и обработка batch-ответа):* При раскрытии объектов frontend вызывает {{metadata.tables.get}} с {{object.id}} выбранного источника и массивом {{data[]}} из пар {{table}} + {{schema}}. Для успешного элемента обрабатываются {{fields[].name}}, {{fields[].type}} и {{fields[].source_type}}. Значение {{type = "undefined"}} не ломает отображение дерева. Ошибка {{not_found}}, {{access_denied}} или {{internal_error}} одного элемента отображается только для соответствующего узла и не препятствует отображению успешных элементов того же ответа.
