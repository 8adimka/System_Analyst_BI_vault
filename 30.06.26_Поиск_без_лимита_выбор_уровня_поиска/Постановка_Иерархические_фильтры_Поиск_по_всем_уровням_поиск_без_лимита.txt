h3. Контекст и проблематика.

В рамках основного аналитического портала для компонента «Иерархический фильтр» присутствует настройка «Поиск без лимита». В данный момент в иерархических фильтрах эта опция не работает. При её активации и вводе поискового запроса механизм серверного поиска не срабатывает.
Вместо этого компонент продолжает использовать локальный фронтовый поиск по уже загруженному (и ограниченному) пулу данных, игнорируя настройки серверного поиска.

В отличие от обычных фильтров портала (где безлимитный поиск успешно реализован), иерархический фильтр требует специфической доработки, так как при фильтрации он оперирует динамической структурой из нескольких полей (уровней иерархии).

----
h3. Цель задачи.

Восстановить и доработать функционал серверного поиска для компонента «Иерархический фильтр» на основном портале.

*Требуется:*
# Реализовать полноценную логику опции «Поиск без лимита» (серверный поиск) для иерархических структур.
# Обеспечить автоматическое формирование условий поиска по *всем* уровням заданной конфигурации иерархии в рамках одного запроса на бэкенд.
# Внедрить корректную обработку сопутствующих настроек: «Количество символов для активации режима» и «Не загружать значения».

*User Story:*
* Как аналитик, я хочу иметь возможность включать серверный поиск в иерархическом фильтре, чтобы пользователи могли искать значения по всему справочнику на любом уровне вложенности иерархии по всему объему данных, не ограничиваясь первоначально загруженным пулом записей.

----
h3. 1. Описание текущего поведения (воспроизведение бага).

# Открыть любой отчёт основного портала с иерархическим фильтром, содержащим > 1 уровня иерархии (например, иерархия: *Город → Дата → Категория → Подкатегория*).
# В настройках отображения иерархического фильтра включить переключатель «Поиск без лимита» и задать «Количество символов для активации» = 3. Сохранить. Обновить страницу.
# Открыть выпадающий список иерархического фильтра и ввести 3 символа в поиск.
# *Ожидаемый результат:* запрос уходит на backend со всеми уровнями иерархии, возвращаются записи, совпавшие на любом уровне.
# *Фактический результат:* серверный запрос не отправляется, поиск выполняется на фронтенде по уже загруженному пулу данных.

----
h3. 2. Описание целевого поведения:

При активации настройки *«Поиск без лимита»* в иерархическом фильтре, локальный фронтовый поиск отключается.
Компонент должен осуществлять поиск на стороне сервера (через API), формируя единый запрос, в котором условия поиска применяются ко *всем* полям, составляющим заданную иерархию фильтра (массив {{order}}/{{select}}).

*Пример целевой логики формирования запроса:*
* Если, к примеру, иерархия фильтра состоит из 4-х полей: {{Gorod}}, {{Data}}, {{Kategorija}}, {{Podkategorija}}.
* При вводе пользователем поисковой строки (например, {{Астр}}), backend должен произвести поиск по логике *ИЛИ* (OR) по всем полям иерархии:

{code:sql}
Gorod LIKE '%Астр%' OR Data LIKE '%Астр%' OR Kategorija LIKE '%Астр%' OR Podkategorija LIKE '%Астр%'
{code}

* Результатом выдачи должны стать ветки иерархии, где *хотя бы на одном из уровней* найдено совпадение.

----
h3. 3. Требования к реализации:

h4. 3.1. Frontend-часть (Основной портал):
* *Формирование запроса:* В массив {{where}} поискового запроса должны прокидываться условия не только для верхнего элемента иерархии, а для *всех полей*, участвующих в иерархии фильтра (исходя из настроек компонента).
* *Поддержка дополнительных параметров* настройки «Поиск без лимита» (отображаются только если активна родительская настройка):
** Логика настройки *«Количество символов для активации режима»* должна работать: запрос уходит только если длина введенной строки >= заданному числу.
** Логика настройки *«Не загружать значения»* должна работать: при открытии дропдауна список пуст, данные появляются только после ввода необходимого числа символов и получения ответа от сервера.
* *UX:* При обновлении списка результатов фокус с инпута поиска *не сбрасывается*, перерендер всего компонента с потерей курсора не допускается.
* *Обратная совместимость:* Если «Поиск без лимита» *выключен*, компонент работает строго по прежнему сценарию — фронтовый поиск без каких-либо изменений.

После получения ответа от сервера компонент должен:
# Отобразить найденные записи в виде *иерархического дерева* — аналогично тому, как это работает в режиме фронтового поиска.
# Обеспечить возможность выбора найденной записи с автоматической активацией всех вышестоящих уровней иерархии.

h4. 3.2. Backend-часть:
* *Обработка массива OR:* Backend должен корректно принимать массив полей из иерархии в объекте {{where}} и объединять их оператором *ИЛИ (OR)*.
* *Один запрос:* Поиск по всем уровням иерархии должен выполняться строго в рамках *одного HTTP-запроса*.
* *Дедупликация:* В случае совпадения поисковой фразы на нескольких уровнях одной ветки, ветка не должна дублироваться в итоговом ответе.
* *Регистронезависимость:* Серверный поиск должен работать без учета регистра, аналогично тому, как сейчас работает локальный поиск на клиенте.
* *Обратная совместимость:* Изменения backend-контракта не должны ломать сценарии, где передаётся одно поле (текущие сценарии, обычные фильтры и прочие потребители API).
* *Переиспользование существующего механизма:* Если в backend уже реализован механизм OR-объединения условий (например, используемый в ФВД после предыдущих доработок) — необходимо *переиспользовать его*, а не создавать отдельную частную реализацию под иерархический фильтр.
* *Абстрактность:* Реализация должна быть достаточно универсальной, чтобы OR-поиск по массиву полей можно было задействовать в других компонентах платформы.
* *Сохранение сортировки:* Порядок выдачи, задаваемый настройками компонента ({{order}}-блок), не должен нарушаться при многопольном поиске.
* *Независимость от SQL-диалекта:* Решение должно поддерживать все хранилища, используемые платформой.

h3. 5. Критерии приёмки (AC):
* AC1. *Переключение режимов:* Если настройка «Поиск без лимита» выключена, иерархический фильтр продолжает работать на локальном поиске по загруженному лимиту, без изменений.
* AC2. *Разблокировка серверного поиска:* С включенной настройкой «Поиск без лимита» при каждом изменении поисковой строки отправляется HTTP-запрос к БД.
* AC3. *Отработка лимита символов:* Если задана настройка «Количество символов для активации режима» = *N*, запросы на сервер не уходят до тех пор, пока не будет введено *N* символов.
* AC4. *Серверный запрос отправляется:* При включённом «Поиске без лимита» с активированной настройкой «Количество символов для активации режима» (N = значение) и вводе ≥ N символов - фронтенд отправляет HTTP-запрос на backend.
* AC5. *Поиск по всем уровням:* В {{payload}} запроса передаются все поля, участвующие в иерархии фильтра, а не только корневой элемент.
* AC6. *Многопольный OR-поиск:* Backend корректно обрабатывает полученный массив полей, применяя логику ИЛИ {{OR}}. Найденные значения возвращаются, если совпадение есть на любом из уровней иерархии.
* AC7. *Регистронезависимость:* Серверный поиск находит значения независимо от регистра введенных символов (совпадение с текущим поведением локального поиска).
* AC8. *Ленивая загрузка:* Настройка «Не загружать значения» работает корректно. Изначально список пуст, результаты подгружаются только после ввода текста пользователем и ответа сервера.
* AC9. *Сохранение UX:* При вводе текста и обновлении выпадающего списка фокус ввода не теряется, курсор остается в поисковой строке.
* AC10. *Производительность:* Поиск не вызывает каскада лишних запросов к БД при быстром вводе, зависаний интерфейса или утечек памяти (возможно, следует применять debounce при быстром вводе).
