h3. Контекст и проблематика:

Ранее в Формах ввода данных (ФВД) был реализован функционал «Поиск без лимита» (серверный поиск) для компонента «Выпадающий список». Однако, в ходе эксплуатации и тестирования была выявлена проблема с фильтрацией при наличии дополнительных настроек компонента.

В конструкторе ФВД для выпадающего списка можно настроить *«Информационные поля»* — дополнительные колонки справочника, которые выводятся пользователю для большей информативности. Сейчас при серверном поиске фронтенд отправляет запрос, передавая в массиве {{where}} только *одно* поле (основное, без вспомогательных). 
В результате поиск осуществляется только по основному наименованию, игнорируя значения из выбранных информационных полей.

Следовательно, текущий серверный поиск в ФВД реализован неполно и не воспроизводит ожидаемую логику компонента.
----
h3. 1. Цель задачи:

*Требуется:*
Доработать серверный поиск компонента «Выпадающий список» в ФВД так, чтобы при включенном режиме *«Поиск без лимита»* поиск выполнялся {*}по всем полям, которые должны участвовать в поиске по конфигурации компонента{*}, а объединение условий происходило на бэкенде по логике *ИЛИ (OR)* в рамках *одного* запроса.

*Правило участия полей в поиске:*
 # *Основное поле* выпадающего списка участвует в поиске {*}всегда{*}.
 # *Информационные поля* участвуют в серверном поиске {*}только если{*}:
 ** они выбраны в секции {*}«Информационные поля»{*};
 ** для компонента включена опция {*}«Показ внутри меню»{*}.
 # Если {*}«Показ внутри меню» выключен{*}, серверный поиск выполняется {*}только по основному полю{*}.
 # Данная доработка {*}не должна менять существующую логику отображения и выводимых подсказок{*}; задача касается только корректного формирования и обработки серверного поиска.

*User Story:*
Как пользователь системы, я хочу находить нужную запись в выпадающем списке ФВД не только по основному наименованию, но и по дополнительным реквизитам (информационным полям), если они настроены для участия в поиске, чтобы быстро выбирать запись по любому известному мне атрибуту.
----
h3. 2. Описание целевого поведения:

Если для компонента «Выпадающий список» включён {*}«Поиск без лимита»{*}, то при вводе пользователем поисковой строки система должна выполнять *один* серверный поиск со следующей логикой:
 # Если дополнительные _информационные поля_ {*}не настроены{*}:
 ** поиск выполняется только по основному полю.
 # Если информационные поля {*}настроены{*}, но {*}«Показ внутри меню» выключен{*}:
 ** поиск выполняется только по основному полю;
 ** визуальное отображение дополнительных полей и текущее поведение подсказок сохраняются.
 # Если информационные поля *настроены* и {*}«Показ внутри меню» включен{*}:
 ** поиск выполняется по основному полю и по всем выбранным информационным полям;
 ** объединение условий выполняется по логике {*}OR (ИЛИ){*};
 ** запись должна попасть в результат, если поисковая строка найдена *хотя бы в одном* из участвующих полей.

*Пример целевой логики:*
Есть выпадающий список с основным полем {{name}} и выбранными информационными полями {{ent_name}} и {{{}inn{}}}.
При включенном *«Показ внутри меню»* и вводе строки {{ЛПХ Шишко}} backend должен отобрать записи по логике, эквивалентной (ориентировочно):
{code:sql}
name LIKE '%ЛПХ Шишко%' OR ent_name LIKE '%ЛПХ Шишко%' OR inn LIKE '%ЛПХ Шишко%'
{code}
*Важно:* пример приведён как {*}логическая модель поведения{*}, а не точный формат.
----
h3. 3. Требования к реализации:
h4. 3.1. Backend-часть:
 * Доработать backend-логику, обслуживающую серверный поиск для ФВД (текущий сценарий на базе команды {{data.list}} или соответствующего абстрактного обработчика получения данных).
 * Backend должен уметь принимать *набор поисковых полей* и *одну поисковую строку* и строить по ним единое условие поиска с логическим оператором {*}OR{*}.
 * Поиск по нескольким полям должен выполняться {*}в рамках одного HTTP-запроса{*}.
 * Backend-реализация должна быть {*}обратно-совместимой{*}: текущие сценарии, где передаётся только одно поле поиска, должны продолжать работать без изменений.
 * Backend-реализация должна быть достаточно {*}абстрактной{*}, а не «захардкоженной» только под один конкретный кейс ФВД, +чтобы механизм OR-поиска+ по массиву полей {+}можно было переиспользовать в других частях платформы{+}.
 * При совпадении по нескольким полям одна и та же запись должна возвращаться {*}один раз{*}.
 * Текущая сортировка / порядок выдачи, задаваемые настройками списка, не должны ломаться из-за появления много-польного поиска.
 * Решение не должно быть привязано к одному конкретному SQL-диалекту; необходимо учесть поддерживаемые backend-хранилища ФВД.
 * Если в текущем backend уже существует механизм объединения условий по OR, необходимо {*}переиспользовать его{*}, а не вводить отдельную частную реализацию только для ФВД.

h4. 3.2. Frontend-часть ФВД:
 * Доработать формирование запроса для режима {*}«Поиск без лимита»{*}.
 * При подготовке payload необходимо формировать *массив поисковых полей* по следующему правилу:
 ** всегда включать в поиск *основное поле* компонента;
 ** дополнительно включать *все выбранные информационные поля* только при включенной настройке {*}«Показ внутри меню»{*}.
 * Перед отправкой запроса необходимо выполнять дедупликацию списка полей, чтобы одно и то же поле не попало в payload несколько раз.
 * Поиск должен оставаться {*}debounce{*}-зависимым, чтобы не инициировать лишние запросы при быстром вводе.
 * Логика настройки *«Количество символов для активации режима»* должна сохраниться без изменений.
 * Логика настройки *«Не загружать значения»* должна сохраниться без изменений.
 * При обновлении списка по результатам серверного поиска {*}компонент не должен терять фокус{*}; курсор в поисковой строке должен оставаться на месте.

h4. 3.3. Технические требования и ограничения:
 # *Единый запрос:* Поиск по нескольким полям должен выполняться {*}строго в одном HTTP-запросе{*}.
 # *Обратная совместимость:* Изменение backend-контракта не должно ломать основной портал и существующие сценарии ФВД, использующие текущую версию обработчика.
 # *Должна сохраниться функиональность уже реализованных механизмов:*
 ** переключатель {*}«Поиск без лимита»{*};
 ** порог {*}«Количество символов для активации режима»{*};
 ** переключатель {*}«Не загружать значения»{*};
 ** дебаунс запросов и т.д.
 # *Общие требования:*
 ** Сохранить текущую общую стилизацию и логику выпадающего списка и подсказок в ФВД.
 ** После внедрения доработки, всплывающие подсказки и выпадающий список должны работать не хуже текущего поведения.
 ** Сценарии с большими справочниками должны отрабатываться без визуальных зависаний и без утечек памяти.

h3. 4. Критерии приёмки (AC):
 * AC1. *Без новых настроек:* В UI конструктора ФВД не появляются новые настройки. Используются существующие настройки компонента: «Поиск без лимита», «Количество символов для активации режима», «Не загружать значения», «Информационные поля», «Показ внутри меню» и т.д.
 * AC2. *Обратная совместимость локального режима:* Если «Поиск без лимита» выключен, компонент работает по прежнему локальному сценарию без изменения текущего поведения.
 * AC3. *Правило участия полей:* При включенном серверном поиске основное поле всегда участвует в поиске. Информационные поля участвуют только если они выбраны в настройках компонента и при этом включен переключатель «Показ внутри меню».
 * AC4. *OR-поиск:* Если в поиске участвует несколько полей, бэкенд применяет к ним логическое условие {*}ИЛИ (OR){*}. Запись возвращается, если поисковая строка найдена хотя бы в одном из полей.
 * AC5. *Один запрос:* Поиск по нескольким полям выполняется в рамках *одного* HTTP-запроса. Решение через несколько запросов с фронтенда и последующее объединение результатов на клиенте отсутствует.
 * AC6. *Без дублей:* Если одна запись совпала сразу по нескольким полям, в выдаче она присутствует только один раз.
 * AC7. *Отложенный запуск:* Настройка «Количество символов для активации режима» продолжает работать. Пока введено меньше заданного количества символов, запрос на backend не отправляется.
 * AC8. *Ленивая загрузка:* Если включена опция «Не загружать значения», при открытии формы список пуст. После ввода нужного количества символов появляются только релевантные результаты серверного поиска.
 * AC9. *Сохранение UX ввода:* При вводе текста в строку поиска фокус не теряется, курсор не сбрасывается из-за обновления списка.
 * AC10. *Отсутствие UI изменений:* Визуальный стиль компонента, отображение дополнительных текстов, подсказок и т.д. не ломается и не изменяется визуально.
 * AC11. *Обратная совместимость конфигураций:* Выпадающие списки без настроенных информационных полей продолжают работать штатно и не требуют каких-либо изменений в настройке.
 * AC12. *Производительность:* Компонент протестирован на справочнике > 5 000 элементов; поиск работает стабильно, без заметных просадок производительности, каскада лишних запросов и ошибок в логах.
 * AC13. *Сортировка:* После внедрения много-польного поиска не нарушается текущий порядок сортировки элементов, заданный существующими настройками списка.
 * AC14. *Backend-совместимость:* Изменение backend-логики не ломает существующие сценарии выборки данных, где используется одинарное условие поиска по одному полю.
