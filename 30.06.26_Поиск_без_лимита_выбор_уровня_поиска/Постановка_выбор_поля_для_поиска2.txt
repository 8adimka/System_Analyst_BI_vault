h3. Контекст и проблематика.

В компоненте *«Иерархический фильтр»* требуется использовать режим *«Поиск без лимита»* для поиска значений по всему объёму данных, а не только по первоначально загруженному пулу значений.

Иерархический фильтр строится по нескольким полям, размещённым на полке *«Фильтры»*. Для полноценного поиска сразу по всем уровням иерархии требуется многопольная серверная логика с объединением условий по *OR (ИЛИ)*. Такая логика является более объёмной backend-доработкой и реализуется в рамках постановки MB-4603.

В рамках текущей задачи необходимо обеспечить практическое решение без существенного изменения backend-контракта: при включённой настройке *«Поиск без лимита»* frontend должен по-прежнему передавать на backend *одно поле поиска*, но пользователь должен получить возможность самостоятельно выбрать, по какому уровню иерархии выполнять серверный поиск.

Проблема текущего поведения состоит в том, что пользователь не управляет целевым полем серверного поиска. Из-за этого поиск может выполняться не по тому уровню иерархии, который нужен пользователю в конкретном сценарии, и значения на других уровнях остаются недоступны для поиска.

----
h3. Цель задачи.

*Требуется:*
# Реализовать поддержку режима *«Поиск без лимита»* для компонента *«Иерархический фильтр»* с использованием серверного поиска по одному выбранному полю.
# Добавить в строку поиска иерархического фильтра новый UI-элемент — выпадающий список выбора целевого поля поиска согласно макету.
# Формировать серверный поисковый запрос только по выбранному пользователем полю, без передачи массива полей и без логики многопольного *OR*-поиска.
# Обеспечить корректную работу сопутствующих настроек *«Количество символов для активации режима»* и *«Не загружать значения»*.
# Сохранить обратную совместимость: при выключенной настройке *«Поиск без лимита»* иерархический фильтр должен работать по прежнему локальному сценарию.

*User Story:*
Как аналитик, я хочу включать серверный поиск в иерархическом фильтре и давать пользователям возможность выбирать уровень иерархии, по которому выполняется поиск, чтобы пользователи могли находить значения по всему объёму данных на нужном уровне вложенности.

----
h3. 1. Описание целевого поведения.

При включённой настройке *«Поиск без лимита»* в иерархическом фильтре строка поиска должна состоять из:
* поля ввода поисковой строки с плейсхолдером *«Найти...»*;
* выпадающего списка выбора поля для поиска (в правой части строки);
* списка результатов иерархии под строкой поиска.

Область выбора поля и выпадающий список должны отображать только наименования полей.

Наименование поля для отображения определяется по следующему приоритету:
# заголовок поля, указанный для поля на полке *«Фильтры»*;
# alias поля;
# техническое имя поля, если заголовок и alias недоступны.

Список вариантов формируется по полям, которые участвуют в текущей иерархии фильтра и доступны на полке *«Фильтры»* данного иерархического фильтра.
По умолчанию, всегда выбирается первое поле с полки *«Фильтры»* иерархического фильтра.

Пример вариантов для иерархии *Город → Категория → Подкатегория*:
* *«Город»*;
* *«Категория»*;
* *«Подкатегория»*.

После выбора пользователем одного из вариантов выбранное поле становится целевым полем серверного поиска. При вводе поисковой строки frontend должен отправлять на backend поисковый запрос только по выбранному полю.

При наведении курсора на область выбора поля должен отображаться tooltip *«Искать по указанному полю»*.

Область выбора поля должна быть встроена в правую часть поисковой строки. Текст, введённый в поисковую строку, и плейсхолдер не должны наползать на область выбора поля: при недостаточной ширине текст в поле ввода должен обрезаться внутри своей области с сохранением возможности перемещения курсора по введённому значению.

Результаты должны отображаться в виде иерархического дерева. В выдачу должны попадать ветки иерархии, в которых найдено совпадение на выбранном целевом уровне, с отображением связанных уровней иерархии, необходимых для корректного выбора значения пользователем.

Опция *«Искать везде»* в рамках текущей задачи не реализуется и не должна быть доступна пользователю. Поиск сразу по нескольким уровням иерархии с объединением условий по *OR (ИЛИ)* не входит в объём текущей задачи.

----
h3. 2. Рамки задачи.

h4. 2.1. Что входит в задачу.

* Добавление выпадающего списка выбора целевого поля поиска в строку поиска иерархического фильтра.
* Формирование списка доступных полей поиска из текущей конфигурации иерархического фильтра.
* Отображение названия поля в области выбора по приоритету: заголовок поля на полке *«Фильтры»* → alias поля → техническое имя поля.
* Реализация tooltip, отсутствия видимого разделителя, корректного обрезания текста и адаптивного поведения при узкой ширине контейнера.
* Поддержка переопределения цветов области выбора поля, треугольника раскрытия, встроенного выпадающего списка и выбранного пункта через CSS.
* Передача на backend одного выбранного поля поиска и поисковой строки.
* Поддержка серверного поиска для иерархической структуры в режиме *«Поиск без лимита»* по выбранному уровню.
* Корректная работа настроек *«Количество символов для активации режима»* и *«Не загружать значения»*.
* Сохранение текущего визуального поведения иерархического дерева, выбора значений и раскрытия веток.

---
h4. 2.2. Что не входит в задачу.

* Реализация поиска сразу по всем уровням иерархии.
* Реализация backend-логики объединения условий по *OR (ИЛИ)* для массива поисковых полей и пункта *«Искать везде»*.
* Изменение логики локального поиска при выключенной настройке *«Поиск без лимита»*.
* Изменение механики выбора значения в иерархическом фильтре.
* Изменение логики работы обычных фильтров, выпадающих списков ФВД и поиска по информационным полям ФВД.

----
h3. 3. Требования к реализации.

h4. 3.1. Frontend-часть.

* При выключенной настройке *«Поиск без лимита»* компонент должен работать без изменений: используется текущий локальный поиск по загруженным значениям.
* При включённой настройке *«Поиск без лимита»* в строке поиска иерархического фильтра должен отображаться выпадающий список выбора поля поиска согласно макету.
* Визуально новый элемент должен быть встроен в правую часть строки поиска без видимой вертикальной линии-разделителя и не должен менять остальную структуру выпадающего списка иерархического фильтра.
* Текст выбранного значения должен отображаться в формате *«<Наименование поля>»*.
* В списке вариантов должны отображаться только поля, которые участвуют в текущей иерархии фильтра.
* Порядок вариантов должен соответствовать порядку уровней иерархии в настройке фильтра.
* Для отображения названия поля нужно использовать следующий приоритет значений:
** в первую очередь — заголовок поля, указанный для поля на полке *«Фильтры»*;
** во вторую очередь — alias поля;
** если заголовок и alias недоступны — техническое имя поля, чтобы область выбора не оставалась пустой.
* При наведении курсора на область выбора поля должен отображаться tooltip *«Искать по указанному полю»*.
* Встроенный выпадающий список выбора поля должен соответствовать целевому макету и использовать компактное выделение выбранного пункта. Визуальный индикатор выбранного пункта не должен приводить к наползанию текста пункта или необоснованному увеличению ширины списка.
* Цвет текста области выбора поля, цвет треугольника раскрытия, цвета встроенного выпадающего списка и цвета состояния выбранного пункта должны быть доступны для переопределения через CSS без изменения frontend-логики компонента.
* Текст, введённый в поисковую строку, и плейсхолдер должны оставаться в области поля ввода. Если текст не помещается, он должен обрезаться внутри поля ввода с возможностью перемещения курсора по введённому значению; текст не должен перекрывать область выбора поля.
* При недостаточной ширине контейнера:
** область выбора поля должна оставаться видимой и кликабельной;
** треугольник раскрытия должен оставаться видимым;
** название выбранного поля может сокращаться внутри области выбора поля, но не должно перекрывать поле ввода;
** выпадающий список выбора поля должен открываться в доступной области экрана/контейнера, не выходить за пределы видимой области и сохранять возможность выбора всех доступных вариантов;
** длинные названия полей в выпадающем списке должны обрезаться или переноситься по существующему UI-паттерну компонента, но не должны ломать ширину контейнера.
* По умолчанию выбирается первый уровень иерархии (первая пилюля на полке «Фильтры»).
* Выбранное поле должно сохраняться в состоянии открытого компонента до изменения пользователем или до пересоздания компонента.
* При изменении выбранного поля:
** поисковая строка не должна очищаться автоматически;
** если длина текущей поисковой строки уже соответствует настройке *«Количество символов для активации режима»*, frontend должен выполнить новый серверный поиск по вновь выбранному полю;
** результаты предыдущего поиска должны быть заменены результатами по новому выбранному полю.
* При подготовке payload поискового запроса frontend должен передавать только одно поле поиска — выбранное пользователем в данный момент.
* Frontend не должен передавать массив поисковых полей для текущей задачи.
* Frontend не должен формировать несколько запросов по разным уровням и объединять результаты на клиенте.
* При быстром вводе поисковой строки должна сохраняться текущая механика задержки отправки запросов, если она уже используется в компоненте.
* При обновлении результатов поиска фокус в поле ввода не должен теряться, курсор должен оставаться в поисковой строке.
* Если для иерархического фильтра доступно только одно поле поиска, компонент должен сохранять однопольное поведение. Допускается отображать выбранное значение *«<Наименование поля>»* без возможности выбора других вариантов.
* Если поле было удалено из конфигурации фильтра или стало недоступно, компонент должен выбрать доступное поле по умолчанию и не должен отправлять запрос с невалидным полем.

---
h4. 3.2. Backend-часть.

* Backend должен продолжать обрабатывать сценарий серверного поиска по одному полю.
* В рамках текущей задачи backend не должен требовать передачи массива полей для поиска.
* Логика поиска должна быть эквивалентна поиску по одному выбранному полю:
{code:sql}
selected_field LIKE '%search_text%'
{code}
*Примечание:* пример приведён как логическая модель поведения, а не как требование к конкретному SQL-синтаксису.
* Backend должен возвращать данные в формате, достаточном для отображения результата как иерархического дерева с необходимыми уровнями ветки.
* Если backend получает поле поиска от frontend, это поле должно проверяться на допустимость в рамках текущего набора данных/конфигурации фильтра. Backend не должен выполнять поиск по произвольному полю, отсутствующему в доступной конфигурации.
* Текущие сценарии, где серверный поиск уже выполняется по одному полю, должны продолжать работать без изменения поведения.
* Реализация не должна ломать существующие API-сценарии обычных фильтров и других компонентов, использующих однопольный серверный поиск.
* Актуальный backend-объект и команда получения данных для иерархического фильтра должны быть уточнены у команды разработки. Логически затрагивается существующий обработчик получения данных фильтра / визуализации, в payload которого передаётся условие поиска по одному полю.

---
h4. 3.3. Настройка «Количество символов для активации режима».

* Настройка должна применяться к серверному поиску по выбранному полю.
* Если задано значение {{N}}, запрос на backend не должен отправляться, пока длина введённой поисковой строки меньше {{N}}.
* Когда длина поисковой строки становится больше или равна {{N}}, frontend должен отправить серверный запрос по выбранному полю.
* При смене выбранного поля правило {{N}} также должно соблюдаться.
* Если поисковая строка стала короче {{N}}, новые серверные запросы не должны отправляться. Отображение списка должно соответствовать текущему принятому поведению компонента для режима *«Поиск без лимита»*.

---
h4. 3.4. Настройка «Не загружать значения».

* Если настройка *«Не загружать значения»* выключена, при открытии выпадающего списка компонент может отображать текущий первоначально загруженный набор значений согласно существующей логике.
* Если настройка *«Не загружать значения»* включена, при открытии выпадающего списка значения не должны загружаться до ввода поисковой строки, удовлетворяющей настройке *«Количество символов для активации режима»*.
* После ввода достаточного количества символов должен выполняться серверный поиск по выбранному полю.
* При смене выбранного поля в режиме *«Не загружать значения»* результаты должны обновляться только если поисковая строка удовлетворяет порогу активации.

---
h4. 3.5. Технические требования и ограничения.

* Поиск по выбранному полю должен выполняться в рамках одного HTTP-запроса.
* Не допускается отправка нескольких запросов по разным уровням иерархии с последующим объединением результатов на frontend.
* Не допускается имитация поиска по всем уровням через последовательный перебор полей на клиенте.
* Сортировка и порядок отображения результатов не должны ухудшаться относительно текущего поведения серверного поиска.
* При совпадениях, возвращённых backend, frontend не должен дублировать одну и ту же ветку иерархии в списке результатов.
* Изменение должно быть обратно совместимым со старыми отчётами и фильтрами, созданными до внедрения доработки.
* Для старых отчётов не должна требоваться ручная перенастройка иерархического фильтра.
* Если включение *«Поиска без лимита»* недоступно для конкретной конфигурации или источника данных, компонент должен вести себя согласно текущей логике ограничения функциональности и не должен показывать некорректный выбор поля поиска.
* Ошибки backend при серверном поиске должны обрабатываться по существующей логике компонента: пользователь не должен получать зависший выпадающий список или потерю введённого текста.
* Решение должно учитывать большие справочники: быстрый ввод поисковой строки не должен приводить к каскаду лишних запросов, визуальным зависаниям или утечкам памяти.
* Цветовые параметры нового UI-элемента, встроенного выпадающего списка и состояния выбранного пункта не должны быть жёстко зашиты в inline-стили, если это препятствует переопределению через CSS в рамках принятого подхода к стилизации портала.

----
h3. 4. Пограничные сценарии.

* *Пустая поисковая строка:* если строка пустая или короче порога активации, серверный поиск не выполняется.
* *Одно поле в иерархии:* поиск работает по единственному доступному полю; пользователь не должен видеть некорректные или пустые варианты выбора.
* *Несколько полей в иерархии:* пользователь может выбрать любое доступное поле, и именно оно передаётся в запрос.
* *Переименование поля:* в выпадающем списке должно отображаться актуальное название поля по приоритету: заголовок поля на полке *«Фильтры»* → alias поля → техническое имя поля.
* *Удаление поля из конфигурации:* выбранное ранее поле не должно использоваться, если оно больше не входит в иерархию фильтра.
* *Отсутствие заголовка поля:* если у поля не указан заголовок на полке *«Фильтры»*, в области выбора и списке вариантов используется alias поля; если alias также недоступен — техническое имя поля.
* *Длинный текст в поисковой строке:* введённое значение или плейсхолдер не должны перекрывать область выбора поля; текст обрезается внутри поля ввода с возможностью перемещения курсора.
* *Длинное название поля:* название выбранного поля или пункта списка не должно ломать ширину поисковой строки/выпадающего списка; допускается сокращение текста по существующему UI-паттерну.
* *Слишком узкий контейнер:* область выбора поля и треугольник раскрытия остаются доступными, поле ввода сокращается в доступной ширине, выпадающий список открывается без выхода за пределы видимой области.
* *Совпадение поисковой строки на другом уровне:* если пользователь выбрал поле *«Город»*, совпадения в поле *«Категория»* не должны попадать в выдачу за счёт текущего поиска. Для поиска по *«Категория»* пользователь должен выбрать соответствующий вариант.
* *Смена поля при введённом поиске:* результаты должны обновиться по новому полю без очистки поисковой строки.
* *Быстрый ввод:* компонент не должен отправлять избыточное количество запросов и не должен отображать устаревший ответ поверх более нового результата.
* *Ошибка backend:* компонент должен сохранить введённую поисковую строку и выбранное поле; пользователь должен иметь возможность повторить поиск или изменить запрос.
* *Старый отчёт:* после открытия старого отчёта с иерархическим фильтром компонент должен выбрать поле по умолчанию и работать без ручной миграции настроек.

h3. 6. Предположения:

* Список доступных полей поиска формируется из полей, которые участвуют в текущей иерархии фильтра на полке *«Фильтры»*.
* Выбор поля поиска является runtime-состоянием компонента и не требует добавления новой настройки в конструктор отчёта, если команда разработки не подтвердит необходимость сохранения выбранного поля в метаданных.
* Backend уже поддерживает или может минимально поддержать однопольный серверный поиск для иерархического фильтра без реализации многопольного *OR*-поиска.
* Точный формат payload и название backend-команды должны быть проверены по актуальной реализации компонента.

h3. 7. Открытые вопросы:

* Нужно ли сохранять выбранное пользователем поле поиска после перезагрузки страницы/повторного открытия отчёта, или достаточно хранить выбор только в состоянии текущего открытого компонента?
* Какой backend-объект и команда фактически используются для получения данных иерархического фильтра в режиме серверного поиска?

h3. 8. Критерии приёмки (AC):

*AC.1 — Локальный режим не изменён:*
* *Дано:* в иерархическом фильтре выключена настройка *«Поиск без лимита»*;
* *Когда:* пользователь открывает фильтр и вводит значение в строку поиска;
* *Тогда:* компонент выполняет локальный поиск по текущему загруженному набору значений без нового выпадающего списка выбора поля поиска и без изменения прежнего поведения.

*AC.2 — Отображение выбора поля при серверном поиске:*
* *Дано:* в иерархическом фильтре включена настройка *«Поиск без лимита»*;
* *Когда:* пользователь открывает выпадающий список фильтра;
* *Тогда:* в строке поиска отображается элемент выбора поля в формате *«<Наименование поля>»* согласно целевому макету, без префикса *«Искать в»*.

*AC.3 — Список доступных полей:*
* *Дано:* иерархический фильтр настроен по нескольким полям на полке *«Фильтры»*;
* *Когда:* пользователь раскрывает выпадающий список выбора поля поиска;
* *Тогда:* отображаются только поля текущей иерархии в порядке уровней иерархии;
* *И:* название каждого поля отображается по приоритету: заголовок поля на полке *«Фильтры»* → alias поля → техническое имя поля.

*AC.4 — Выбор целевого поля:*
* *Дано:* пользователь открыл список выбора поля поиска;
* *Когда:* пользователь выбирает вариант *«Категория»*;
* *Тогда:* выбранное поле отображается в строке поиска, а последующие поисковые запросы выполняются по полю *«Категория»*.

*AC.5 — В payload передаётся одно поле:*
* *Дано:* включён *«Поиск без лимита»* и выбрано поле поиска;
* *Когда:* пользователь вводит поисковую строку, удовлетворяющую порогу активации;
* *Тогда:* frontend отправляет на backend один поисковый запрос, в котором указано только выбранное поле поиска.

*AC.6 — Поиск не выполняется по всем уровням одновременно:*
* *Дано:* в иерархии есть поля *«Город»*, *«Категория»*, *«Подкатегория»*;
* *Когда:* пользователь выбрал *«Город»* и ввёл строку, которая совпадает только со значением в поле *«Категория»*;
* *Тогда:* результат не должен появляться за счёт совпадения в *«Категория»*, потому что текущий поиск выполняется только по выбранному полю *«Город»*.

*AC.7 — Отработка порога символов:*
* *Дано:* для фильтра включён *«Поиск без лимита»* и задано *«Количество символов для активации режима»* = {{3}};
* *Когда:* пользователь вводит один или два символа;
* *Тогда:* серверный запрос не отправляется;
* *Когда:* пользователь вводит три и более символа;
* *Тогда:* отправляется серверный запрос по выбранному полю.

*AC.8 — Работа настройки «Не загружать значения»:*
* *Дано:* включены настройки *«Поиск без лимита»* и *«Не загружать значения»*;
* *Когда:* пользователь открывает иерархический фильтр и ещё не ввёл поисковую строку нужной длины;
* *Тогда:* значения не загружаются;
* *Когда:* пользователь вводит поисковую строку нужной длины;
* *Тогда:* загружаются результаты серверного поиска по выбранному полю.

*AC.9 — Смена поля при введённом запросе:*
* *Дано:* пользователь ввёл поисковую строку, по которой уже получены результаты серверного поиска;
* *Когда:* пользователь выбирает другое поле поиска;
* *Тогда:* поисковая строка сохраняется, выполняется новый серверный запрос по новому выбранному полю, а список результатов обновляется.

*AC.10 — Отображение результата как иерархии:*
* *Дано:* backend вернул результаты поиска по выбранному уровню;
* *Когда:* компонент отображает найденные значения;
* *Тогда:* результаты представлены как иерархическое дерево с уровнями, необходимыми для выбора найденного значения.

*AC.11 — Фокус ввода не теряется:*
* *Дано:* пользователь вводит текст в строку поиска;
* *Когда:* frontend получает и отображает новый ответ backend;
* *Тогда:* фокус остаётся в поле ввода, курсор не сбрасывается, введённый текст не очищается.

*AC.12 — Пункт «Искать везде» недоступен:*
* *Дано:* пользователь раскрывает список выбора поля поиска;
* *Когда:* отображаются варианты поиска;
* *Тогда:* пункт *«Искать везде»* отсутствует или недоступен для выбора в рамках текущей задачи.

*AC.13 — Обратная совместимость старых отчётов:*
* *Дано:* открыт отчёт с иерархическим фильтром, созданный до внедрения доработки;
* *Когда:* пользователь включает или использует *«Поиск без лимита»*;
* *Тогда:* компонент работает без ручной миграции настроек, выбирает поле поиска по умолчанию и не ломает существующую конфигурацию фильтра.

*AC.14 — Защита от невалидного поля:*
* *Дано:* поле, ранее доступное в иерархии, удалено или стало недоступно;
* *Когда:* пользователь открывает фильтр и выполняет поиск;
* *Тогда:* frontend не отправляет запрос по удалённому полю, выбирает доступное поле по умолчанию или показывает состояние без доступных вариантов согласно текущему UI-паттерну компонента.

*AC.15 — Производительность и отсутствие лишних запросов:*
* *Дано:* пользователь быстро вводит поисковую строку в режиме *«Поиск без лимита»*;
* *Когда:* компонент формирует серверные запросы;
* *Тогда:* запросы отправляются с учётом текущей механики задержки, устаревшие ответы не должны перетирать более актуальные результаты, интерфейс не зависает.

*AC.16 — Tooltip и отсутствие видимого разделителя:*
* *Дано:* в иерархическом фильтре включён *«Поиск без лимита»*;
* *Когда:* пользователь наводит курсор на область выбора поля;
* *Тогда:* отображается tooltip *«Искать по указанному полю»*;
* *И:* между полем ввода и областью выбора поля нет видимой вертикальной линии-разделителя.

*AC.17 — Текст не перекрывает область выбора поля:*
* *Дано:* пользователь вводит длинное значение в поисковую строку или контейнер фильтра имеет ограниченную ширину;
* *Когда:* введённый текст не помещается в доступную область поля ввода;
* *Тогда:* текст обрезается внутри поля ввода с возможностью перемещения курсора по введённому значению;
* *И:* текст не наползает на область выбора поля и треугольник раскрытия.

*AC.18 — Поведение в узком контейнере и CSS-настройки:*
* *Дано:* иерархический фильтр расположен в узком контейнере;
* *Когда:* пользователь открывает строку поиска и выпадающий список выбора поля;
* *Тогда:* область выбора поля и треугольник раскрытия остаются видимыми и кликабельными, выпадающий список доступен для выбора вариантов и не выходит за пределы видимой области;
* *И:* цвет текста области выбора поля, треугольника раскрытия, встроенного выпадающего списка и состояния выбранного пункта можно переопределить через CSS.
