h3. 1. Цель доработки.

Обеспечить корректную и предсказуемую работу визуализации «Граф» при фильтрации, агрегации и совместном использовании нескольких наборов данных.

Текущая архитектура визуализаций портала предполагает использование одного набора данных на одну визуализацию. Для визуализации «Граф» данный подход оказался неэффективным и приводит к следующим проблемам:

* усложнение структуры данных;
* дублирование информации;
* некорректная работа фильтрации;
* потеря узлов и связей при фильтрации;
* невозможность корректно реализовать классическую графовую модель;
* невозможность полноценно использовать независимые сущности «узлы» и «связи».

Цель данной доработки:

* перевести визуализацию «Граф» на классическую двухтабличную модель построения графов;
* обеспечить поддержку нескольких наборов данных в рамках одной визуализации;
* сохранить полную обратную совместимость со всеми существующими визуализациями;
* обеспечить корректную интеграцию с визуализациями «Таблица» и «Сводная таблица»;
* обеспечить корректную работу всех сценариев фильтрации.

----
h3. 2. Концепция нового решения.

В рамках данной доработки визуализация «Граф» должна перейти на классическую графовую архитектуру:

* отдельный набор данных — «Узлы графа»;
* отдельный набор данных — «Связи графа».

Визуализация должна уметь одновременно использовать несколько наборов данных.

----
h4. 2.1. Набор данных «Узлы графа».

Набор данных содержит:

* все узлы графа;
* свойства узлов;
* параметры отображения узлов.

Каждая строка набора данных соответствует одному узлу.

----
h4. 2.2. Набор данных «Связи графа».

Набор данных содержит:

* связи между узлами;
* свойства связей;
* параметры отображения связей.

Каждая строка набора данных соответствует одной связи между двумя узлами.

----
h3. 3. Основная архитектурная проблема.

В текущей реализации все визуализации используют ссылку на поле набора данных через его наименование ({{name}}).

На текущий момент:

* {{name}} уникально только в рамках одного набора данных;
* {{name}} не гарантирует уникальность между несколькими наборами данных;
* при использовании нескольких наборов данных могут возникать конфликты ссылок на поля.

Это делает корректную работу визуализаций затруднительной и нестабильной при использовании более одного набора данных одновременно.

Для реализации новой архитектуры «Графа» требуется устранить данное ограничение.

----
h4. 3.1. Решение: составной идентификатор поля.

Для визуализации «Граф» вводится составной идентификатор поля в формате:

{{<dataset_id>.<field_name>}}

Требования:

* составной идентификатор гарантирует глобальную уникальность ссылки на поле при работе с несколькими наборами данных;
* составной идентификатор используется исключительно во внутренней логике визуализации «Граф» — в конфигурации, маппинге полей и движке фильтрации;
* в пользовательском интерфейсе по-прежнему отображается {{name}} поля;
* данное решение не затрагивает архитектуру других визуализаций — они продолжают работать с {{name}} без изменений.

Пример:

|| Набор данных || Поле || Составной идентификатор ||
| Nodes ({{ds_nodes}}) | {{node_category}} | {{ds_nodes.node_category}} |
| Edges ({{ds_edges}}) | {{edge_type}} | {{ds_edges.edge_type}} |

----

h4. 4.1. Общая модель.

Визуализация «Граф» должна одновременно использовать два Набора данных:

| Edges | Связи графа |

Каждая строка представляет один узел.

Обязательные поля:

Опциональные поля:

|| Поле || Тип || Описание ||

Допускается использование дополнительных пользовательских атрибутов или кастомная настройка атрибутов в визуализации.

h3. 5. Логика построения визуализации.

h4. 5.1. Построение узлов.

Визуализация должна:

# загрузить Набор данных «Узлы»;
# построить коллекцию узлов;
# использовать {{node_id}} как уникальный ключ.

----
h4. 5.2. Построение связей.

Визуализация должна:

# загрузить Набор данных «Связи»;
# построить коллекцию связей;
# использовать {{edge_id}} как уникальный ключ;
# сопоставить {{source_node_id}} и {{target_node_id}} с {{node_id}}.

----
h4. 5.3. Обработка отсутствующих узлов.

Если связь содержит ссылку на несуществующий узел:

* связь не должна приводить к падению визуализации;
* в логах должна фиксироваться ошибка валидации;
* связь должна быть пропущена;
* визуализация должна продолжить работу.

----
h4. 5.4. Изолированные узлы.

Визуализация должна поддерживать узлы без связей.

Изолированные узлы:

* должны отображаться;
* должны участвовать в фильтрации;
* должны участвовать в поиске;
* должны участвовать в выделении.

----
h3. 6. Фильтрация данных.

h4. 6.1. Основная цель доработки.

Основная цель данной переработки — обеспечить корректную фильтрацию данных для построения визуализации «Граф».

Текущая проблема:

* при использовании одной плоской таблицы фильтрация удаляет строки, содержащие узлы и связи;
* при наличии строки с узлом-источником и связью, но отсутствии строки, содержащей узел-приёмник — визуализация не может корректно построить данную связь:
** граф становится неполным;
** визуализация теряет консистентность.

Новая архитектура должна устранить данную проблему.

----
h4. 6.2. Фильтрация Набора данных «Узлы».

Фильтрация по полям узлов должна:

* применяться только к Набору данных «Узлы»;
* ограничивать набор отображаемых узлов.

После фильтрации узлов:

* визуализация должна автоматически попытаться построить связи;
** при наличии связи, содержащей отсутствующие узлы, такая связь должна быть пропущена и не отрисовываться;
* должны остаться только связи между отображаемыми узлами.

----
h4. 6.3. Фильтрация Набора данных «Связи».

Фильтрация по полям связей должна:

* применяться только к Набору данных «Связи»;
* скрывать только связи;
* не удалять узлы автоматически;
* при наличии узлов без связей — они отображаются как изолированные узлы в штатном порядке.

----
h4. 6.4. Режимы интерактивной фильтрации визуализации «Граф».

h5. 6.4.1. Проблема и мотивация.

При применении фильтра к Набору данных «Узлы» (раздел 6.2) базовая логика фильтрации удаляет из отображения все узлы, не прошедшие фильтр. Это поведение является корректным для большинства аналитических задач, однако для графовой визуализации оно разрушает контекст: узел, оставшийся после фильтрации, теряет все свои связи, поскольку все соседние узлы были удалены.

Целевое поведение при клике на узел или применении фильтра к графу — отображение не только *самого отфильтрованного узла, но и всех узлов, с которыми он непосредственно связан*, вместе с соответствующими рёбрами.

Для поддержки различных аналитических сценариев необходимо предоставить пользователю явный выбор режима фильтрации через настройки визуализации.

h5. 6.4.2. Настройка: Режим охвата фильтрации («С соседями»).

В панели настроек компонента «Граф» добавляется переключатель:

«С соседями» (Тумблер (Toggle), ВКЛ — по умолчанию (1) / ВЫКЛ (0)):

|| Значение || Поведение ||
| «С соседями» — ВКЛ (по умолчанию) | После фильтрации отображаются отфильтрованные узлы и все их непосредственные соседи (+1 уровень), а также все рёбра между ними. |
| «С соседями» — ВЫКЛ | После фильтрации отображаются только узлы, прошедшие фильтр, и только рёбра строго между ними. Узлы, не прошедшие фильтр, скрываются полностью, даже если они связаны с отфильтрованными узлами. |

*Режим «С соседями» — ВКЛ, детальное поведение:*

Когда пользователь применяет фильтр (например, {{node_category = "Премиум"}}) или кликает на конкретный узел при включённом режиме кросс-фильтрации, для корректной отрисовки Графа BI-ядро выполняет запрос в три шага:

# Определяет множество узлов-кандидатов — тех, что прошли фильтр.
# Из Набора данных «Связи» выбирает все рёбра, у которых хотя бы один конец ({{source_node_id}} *ИЛИ* {{target_node_id}}) принадлежит множеству узлов-кандидатов.
# Из этих рёбер извлекает все упомянутые {{node_id}} — они становятся итоговым множеством отображаемых узлов, даже если сами не прошли исходный фильтр.

Пример: Узлы A (Премиум), B (Стандарт), C (Премиум), D (Стандарт). Рёбра: A→B, B→C, B→D.
Фильтр {{category = "Премиум"}} → кандидаты: {{A, C}}. Рёбра, инцидентные {{A, C}}: A→B, B→C. Итоговые узлы: {{A, B, C}}. Итоговые рёбра: A→B, B→C. Узел B отображается как сосед, несмотря на то что категории «Премиум» не имеет.

*Режим «С соседями» — ВЫКЛ, детальное поведение:*

BI-ядро возвращает только узлы, прошедшие фильтр, и только рёбра, у которых оба конца входят в множество отфильтрованных узлов. Узлы, прошедшие фильтр, но не имеющие связей с другими отфильтрованными узлами, отображаются как изолированные.

Тот же пример, строгий режим: Итоговые узлы: {{A, C}}. Ребро A→B — пропускается (B не прошёл). Ребро B→C — пропускается (B не прошёл). Итог: A и C отображаются как изолированные точки без связей между собой (прямой связи A→C нет).

h5. 6.4.3. Настройка: Режим «Направление фильтрации».

В панели настроек компонента «Граф» добавляется переключатель:

«Направление фильтрации» (Выпадающий список (Dropdown), 3 значения):

|| Значение || Поведение ||
| «Все направления» (по умолчанию) | В режиме «С соседями»: фильтр применяется к узлам независимо от их роли в ребре. Узел попадает в результат, если он является источником или приёмником хотя бы одного ребра, связанного с отфильтрованным узлом. |
| «Только исходящие» | В режиме «С соседями»: к отфильтрованным узлам добавляются только узлы, являющиеся {{target_node_id}} в рёбрах, где отфильтрованный узел — {{source_node_id}}. |
| «Только входящие» | В режиме «С соседями»: к отфильтрованным узлам добавляются только узлы, являющиеся {{source_node_id}} в рёбрах, где отфильтрованный узел — {{target_node_id}}. |

*Примечание:* настройка «Направление фильтрации» влияет на состав узлов, добавляемых к отфильтрованным узлам, в режиме «С соседями» — ВКЛ. В режиме «С соседями» — ВЫКЛ (строгий режим) настройка «Направление фильтрации» остаётся недоступна ({{disabled}}).
В строгом режиме отображаются только рёбра между узлами, оба конца которых прошли фильтр — направление ребра не влияет на состав итогового множества узлов.

h5. 6.4.4. Настройка: Режим взаимодействия при клике.

В панели настроек компонента «Граф» добавляется переключатель:

«Режим клика на узел»:

|| Значение || Поведение ||
| «Выделение» (по умолчанию) | При клике на узел активируется локальное выделение средствами ECharts: выбранный узел и его инцидентные рёбра подсвечиваются, остальные узлы становятся полупрозрачными. Данные не перезапрашиваются, состав графа не меняется. |
| «Кросс-фильтрация» | При клике на узел BI-ядро применяет жёсткий фильтр к Набору данных «Узлы» по {{node_id}} кликнутого узла. Граф перерисовывается с учётом текущих настроек режимов «С соседями» и «Направления фильтрации», соседние виджеты дашборда фильтруются по выбранному {{node_id}}. |

*Важно:* в режиме «Кросс-фильтрация» + «С соседями» (ВЫКЛ) — клик на узел приведёт к отображению только самого узла как изолированной точки, поскольку соседи будут отсечены. Это поведение является ожидаемым следствием комбинации настроек и должно быть явно задокументировано в справке для аналитиков.

h5. 6.4.5. Поведение при отсутствии результата.

Если после применения фильтра итоговый набор узлов оказывается пустым:

* визуализация отображает пустое полотно; при наведении появляется информационная подсказка: «Нет данных, соответствующих условиям фильтра»;
* ошибки и падения визуализации не возникает;
* при снятии отсекающего фильтра граф восстанавливает отображение узлов, прошедших фильтрацию, в соответствии с текущими настройками визуализации «Граф».

h4. 6.5. Совместимость фильтрации с другими визуализациями.

Необходимо обеспечить полную совместимость визуализации «Граф» с:

* фильтрами Дашборда;
* интерактивным выделением и кросс-фильтрацией (в том числе из других визуализаций);
* drill-down;
* визуализацией «Таблица»;
* визуализацией «Сводная таблица»;
* и другими визуализациями платформы.

Необходимо доработать API.

Требования:

* API должно поддерживать работу сразу с несколькими Наборами данных;
* Наборы данных должны иметь уникальные идентификаторы ({{dataset_id}});
* внутренние ссылки на поля в конфигурации визуализации «Граф» используют составной идентификатор {{<dataset_id>.<field_name>}}.

h4. 7.3. Модель хранения конфигурации визуализации «Граф».

Необходимо изменить модель конфигурации.

h4. 7.4. Обработка фильтров.

При необходимости доработать движок фильтрации.

Требования:

* фильтры должны корректно применяться к нескольким Наборам данных независимо;
* фильтрация в рамках диаграммы «Граф» должна учитывать роль Набора данных (узлы / связи);
* фильтрация должна корректно работать при кросс-фильтрации из других визуализаций.

*Специфическое требование для режима «С соседями» — ВКЛ:*

При активном режиме «С соседями» BI-ядро должно выполнять расширенную двухшаговую подготовку данных для визуализации «Граф»:

# Применить пользовательский фильтр к Набору данных «Узлы» → получить множество {{node_id}} *кандидатов-узлов*.
# Выполнить дополнительный запрос к Набору данных «Связи»: выбрать все рёбра, где {{source_node_id}} *ИЛИ* {{target_node_id}} входит в множество *кандидатов-узлов*.
#* Извлечь из этих рёбер все упомянутые {{node_id}} и добавить их к итоговому множеству *отображаемых узлов*.

h3. 8. Изменения {{frontend}}.

h4. 8.1. Конфигуратор визуализации «Граф»: новый интерфейс боковой панели.

Необходимо полностью переработать UI боковой панели настройки визуализации «Граф» для поддержки двухтабличного режима.

*Текущее состояние:* боковая панель содержит один выпадающий список выбора Набора данных и список полей этого Набора данных.

*Целевое состояние:*

Боковая панель визуализации «Граф» структурируется следующим образом:

*Раздел «Структура данных»* — заголовок верхнего уровня.

Содержит два подраздела:

*Подраздел «Узлы»:*

* Выпадающий список выбора Набора данных, который будет являться источником узлов графа.
* После выбора Набора данных — под выпадающим списком отображается список полей выбранного Набора данных (аналогично текущей реализации).
* Область списка полей является сворачиваемой (аккордеон): при нажатии на специальную область под выпадающим списком список полей сворачивается — остаётся только подзаголовок «Узлы» и выпадающий список выбора Набора данных. При повторном нажатии список полей разворачивается.

*Подраздел «Связи»:*

* Расположен ниже подраздела «Узлы».
* Выпадающий список выбора второго Набора данных, который будет являться источником связей графа.
* После выбора Набора данных — под выпадающим списком отображается список полей выбранного Набора данных.
* Область списка полей является сворачиваемой (аккордеон) аналогично подразделу «Узлы».

*Поведение аккордеонов:*

* Пользователь может свернуть оба подраздела, развернуть только один из них или развернуть сразу оба.
* Состояние развёрнутости каждого подраздела не зависит от другого.

h4. 8.2. Конфигуратор визуализации «Граф»: полки визуализации.

Набор полок (shelves) визуализации «Граф» переименовывается и дополняется в соответствии с двухтабличной моделью:

h5. 8.2.1. Полка «Узлы» (переименована из «Узел»).

* На полку размещается одна колонка (пилюля) из Набора данных «Узлы», содержащая наименования (идентификаторы) узлов графа.
* Размещённая пилюля соответствует полю {{node_id}} / {{node_label}} — основному идентификатору узла для построения графа.

h5. 8.2.2. Полка «Связи» (переименована из «Связь»).

* На полку размещаются две колонки (пилюли) из Набора данных «Связи»:
** колонка, содержащая идентификатор узла-источника ({{source_node_id}});
** колонка, содержащая идентификатор узла-приёмника ({{target_node_id}}).
* Для каждой размещённой пилюли пользователь должен задать её *Тип* через меню настроек пилюли (нажатие на символ «🢓»):
** «Узел-источник» — колонка содержит идентификатор узла, из которого выходит связь;
** «Узел-приёмник» — колонка содержит идентификатор узла, в который связь входит.
* Диаграмма попарно обрабатывает эти два поля и строит между соответствующими узлами направленную связь.

h5. 8.2.3. Полка «Свойства узлов» (переименована из «Значения»).

* На полку размещаются колонки (пилюли) из Набора данных «Узлы», задающие визуальные параметры отображения узлов.
* Для каждой размещённой пилюли пользователь задаёт её *Тип* через меню настроек пилюли («🢓»):
** «Радиус» — размер узла;
** «Цвет» — цвет узла;
** «Значение» — числовое значение, отображаемое в подсказке (tooltip) или метке узла;
** иные типы по необходимости.

h5. 8.2.4. Полка «Свойства связей» (переименована из «Категории»).

* На полку размещаются колонки (пилюли) из Набора данных «Связи», задающие визуальные параметры отображения связей.
* Для каждой размещённой пилюли пользователь задаёт её *Тип* через меню настроек пилюли («🢓»):
** «Тип связи» — категория / тип ребра;
** «Цвет» — цвет линии связи;
** «Значение» — числовое значение (вес связи), отображаемое в подсказке или на метке ребра;
** иные типы по необходимости.

h5. 8.2.5. Полка «Фильтры» (без изменений).

* Полка остаётся без изменений.
* Отвечает за выбор пилюль, по которым будет производиться фильтрация данных.

h3. 11. Критерии приёмки (AC).

*AC.1* — Визуализация строится на двух независимых Наборах данных.
* *Дано:* настроена визуализация «Граф» с Набором данных «Узлы» (10 строк) и Набором данных «Связи» (15 строк).
* *Когда:* дашборд загружается без каких-либо фильтров.
* *Тогда:* на полотне отображаются все 10 узлов и все корректные связи между ними; отсутствуют дублирующиеся узлы; визуализация не падает и не выводит ошибок.

----
*AC.2.1* — Фильтрация узлов: «С соседями» — ВЫКЛ.
* *Дано:* граф с узлами A, B, C и связями A→B, B→C, A→C; режим «С соседями» — ВЫКЛ.
* *Когда:* пользователь применяет фильтр по Набору данных «Узлы», под условие попадают только A и B.
* *Тогда:* отображаются только узлы A и B; отображается только связь A→B (оба конца прошли фильтр); связи B→C и A→C не отрисовываются; узел C не отображается; ошибок валидации не возникает.

----
*AC.2.2* — Фильтрация узлов: «С соседями» — ВКЛ.
* *Дано:* граф с узлами A (Премиум), B (Стандарт), C (Премиум), D (Стандарт); рёбра связей: A→B, B→C, B→D; режим «С соседями» — ВКЛ (по умолчанию).
* *Когда:* пользователь применяет фильтр {{node_category = "Премиум"}}.
* *Тогда:* отображаются узлы A, B, C (A и C — прошли фильтрацию, B — как сосед); узел D не отображается (не прошёл фильтр и не связан с узлом, прошедшим фильтрацию); отображаются рёбра A→B и B→C; узел D и ребро B→D не отображаются, так как D не входит в итоговое множество узлов.

----
*AC.3* — Фильтрация связей не удаляет узлы.
* *Дано:* граф с узлами A, B, C и связями A→B (тип: «Партнёрство»), B→C (тип: «Аффилированность»).
* *Когда:* пользователь применяет фильтр по Набору данных «Связи»: {{edge_type = "Партнёрство"}}.
* *Тогда:* отображаются все три узла A, B, C; отображается только связь A→B; узлы B и C становятся изолированными и продолжают отображаться.

----
*AC.4* — Обработка битых связей не ломает визуализацию.
* *Дано:* Набор данных «Связи» содержит строку с {{source_node_id = "X"}}, которого нет в Наборе данных «Узлы».
* *Когда:* визуализация загружается.
* *Тогда:* все корректные узлы и связи отрисовываются в штатном режиме; некорректная связь пропускается; в логах браузера и/или серверных логах фиксируется запись об ошибке валидации с указанием {{edge_id}} и отсутствующего {{node_id}}; визуализация не падает.

----
*AC.5* — Глобальные фильтры дашборда применяются корректно.
* *Дано:* на дашборде настроен фильтр по полю {{category = "Премиум"}}; это поле присутствует в Наборе данных «Узлы».
* *Когда:* пользователь выбирает значение в фильтре.
* *Тогда:* в Наборе данных «Узлы» остаются только строки с {{category = "Премиум"}}; граф перестраивается — отображаются только отфильтрованные узлы и связи строго между ними; соседние виджеты (Таблица, Сводная таблица и т.д.) фильтруются по той же логике в зависимости от настроек дашборда.

----

* *Дано:* на дашборде рядом с Графом расположена Таблица, связанная с тем
