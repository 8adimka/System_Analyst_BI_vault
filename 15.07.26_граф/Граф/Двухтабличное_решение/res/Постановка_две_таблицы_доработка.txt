В рамках доработки нашего аналитического портала Modus BI, мною была подготовлена оригинальная постановка по доработке визуализации "Граф".

Оригинальная постановка должна была решить проблемы фильтрации данных, но опиралась на подход - "одна визуализация работает на одном наборе данных. Вот оригинальная постановка для одного набора данных - "h3. 1. Цель
Обеспечить корректную работу фильтрации и предотвратить потерю узлов/связей при построении компонента «Граф». Решение должно работать в рамках текущего системного ограничения *«одна диаграмма — один набор данных» (плоская таблица)*, поддерживать множественные связи, изолированные узлы и обеспечивать корректную логику фильтрации.

----
*Краткое описание текущей проблемы:*
* В текущей реализации набор данных представляет собой _одну плоскую таблицу_, где каждая строка описывает: 
[Узел-источник + Свойства Узла-источника + Узел-приёмник + Свойства связи]. 
* Свойства узла-приёмника не хранятся.
* В текущей архитектуре для построения связи требуются данные из разных строк: строки узла-источника со связью и отдельная строка для узла-приёмника (где он выступает _узлом-источником_). При фильтрации по свойствам мы отсекаем строку _узла-приёмника_, из-за чего система теряет конечную точку и не может отрисовать вектор связи.


h3. 2. Требуемое решение
На данный момент принято решение сохранить архитектурное ограничение *один набор данных на диаграмму*. 
Поэтому актуальное решение - *денормализация таблицы:*
* Каждая строка, представляющая связь, теперь должна содержать *полные свойства обоих концов связи* (узлов {{source_\\*}} и {{target_\\*}}). 
* При фильтрации по узлам (или свойствам узла) фильтрация на уровне BI-системы должна автоматически (по-умолчанию) применяться по *логике OR (_ИЛИ_)* для обоих концов связи.
* Сборка графа на фронтенде после фильтрации производится на основе *всех уникальных узлов*, извлеченных из оставшихся строк (как из колонок префикса {{source_}}, так и из {{target_}}), с корректной агрегацией их свойств.

----
h3. 3. Структура набора данных (Спецификация колонок компонента)
Набор данных, передаваемый в компонент, должен иметь следующий формат (имена фиксируются как системный стандарт компонента):

*Идентификаторы узлов (вершины Графа - обязательные поля):*
* {{source_id}} — уникальный идентификатор узла-источника (string/number).
* {{target_id}} — уникальный идентификатор узла-приёмника (string/number, *может быть NULL* или пустой строкой для изолированных узлов).

*Свойства узлов (дублируются для обоих концов связи):*
* {{source_label}}, {{target_label}} (string) — подпись узла (отображаемое имя).
* {{source_value}}, {{target_value}} (number) — числовое значение (используется для расчета радиуса узла).
* {{source_color}}, {{target_color}} (string) — кастомный цвет узла (RGB/HEX), если задан в данных.
* {{source_tooltip}}, {{target_tooltip}} (string) — HTML-строка для подсказки при наведении на узел.
* {{source_category}}, {{target_category}} (string/number) — категория (для раскраски и легенды).
* Любые другие атрибуты узла добавляются по этому же принципу парных префиксов.

*Атрибуты связи:*
* {{edge_relation}} (string) — тип связи (например, "Партнерство", "Аффилированность").
* {{edge_value}} (number) — вес/значение связи (опционально, для толщины линии).
* {{edge_tooltip}} (string) — HTML-строка для подсказки при наведении на связь.

----
h3. 4. Логика формирования датасета (ETL)
Поскольку мы используем одну плоскую таблицу, ответственность за консистентность свойств узла лежит на источнике данных. Для формирования витрины конструктор запросов BI должен использовать *двойное левое соединение (LEFT JOIN)* к таблице-справочнику узлов.

*Ориентировочный базовый шаблон SQL-генерации:*
{code:sql}
SELECT 
    -- Свойства источника
    n_src.id AS source_id,
    n_src.label AS source_label,
    n_src.category AS source_category,
    ...
    -- Свойства приемника
    n_tgt.id AS target_id,
    n_tgt.label AS target_label,
    n_tgt.category AS target_category,
    ...
    -- Свойства связи
    e.relation_type AS edge_relation,
    e.tooltip AS edge_tooltip
FROM nodes_table n_src
LEFT JOIN edges_table e ON n_src.id = e.source_id
LEFT JOIN nodes_table n_tgt ON e.target_id = n_tgt.id
{code}
_Важно:_ LEFT JOIN гарантирует, что изолированные узлы (не имеющие записей в {{edges_table}}) попадут в выборку (в этих строках все поля {{target_*}} и {{edge_*}} будут NULL).

h3. 5. Пользовательский интерфейс (Дополнительные настройки фильтрации и компонента «Граф»):

# В панели настроек компонента «Диаграмма Граф» добавляется:
#* «Фильтрация включая смежные узлы» (Toggle, по умолчанию Вкл).
#** Вкл = «С соседями (+1 уровень)» — Выводятся отфильтрованные узлы + все узлы, которые имеют с ними связи (даже если соседи не попадают под условия фильтра), а также связи между ними.
#** Выкл = «Строгий режим» — выводятся только те узлы, которые удовлетворяют фильтру, и связи строго между ними.
# В панели настроек компонента «Контейнер с фильтрами» добавляется:
#* «Включение OR-логики между полями» (Toggle, по умолчанию Выкл).
#** Вкл — При включении для компонента «Контейнер с фильтрами» появляется _вспомогательная_ полка значений, куда мы можем положить дополнительные поля между которыми при фильтрации будет приставляться _ИЛИ_ (OR-логика). Т.е. при фильтрации через данный "контейнер с фильтрами" фильтрация будет проводиться среди значений с главной полки значений _ИЛИ_ среди значений из полей, выбранных в _вспомогательной_ полке.
#*** *Важно:* При отображении списка _предложенных значений для фильтрации_ мы должны выводить *сумму всех уникальных значений* ({{DISTINCT}}) по главному выбранному полю и всем полям со _вспомогательной_ полки значений.
#** Выкл — Обычная логика фильтрации (как раньше).

* Когда аналитик добавляет «Контейнер с фильтрами» по свойству (полю) "Город узла-приёмника"(source_city), активирует в этом контейнере настройку «Включение OR-логики между полями» и добавляет на _вспомогательную_ полку значений поле "Город узла-источника"(target_city):
** Система начинает проводить поиск по выбранным городам в поле source_city ИЛИ (OR) в поле target_city.
* Это позволяет для разных фильтров задавать разную логику фильтрации в одном дашборде.

Пример:
* Для контейнера с фильтром «Город» → активируем «Включение OR-логики между полями», добавляем на основную полку значений {{source_city}}, а на вспомогательную полку - {{target_city}} → ищем "Новосибирск" у клиента _ИЛИ_ у партнёра
* Для контейнера с фильтром «Отрасль-клиента» → пользуемся стандартной логикой фильтрации → ищем отрасль "Строительство" только у клиента (target_branch)

* Итоговый фильтр будет искать: 
{code:sql}
WHERE source_city = 'Новосибирск' OR target_city = 'Новосибирск' AND target_branch = 'Строительство'
{code}
Т.е. мы найдем всех клиентов из Отрасли "Строительство", если они сами находятся в "Новосибирске" или если их партнёр из "Новосибирска".

*(_Опционально_)* «Группировка узлов по свойству» (Toggle, по умолчанию Выкл + дополнительный Dropdown для выбора свойства групировки):
* Выкл (_По умолчанию_) — группировка не применяется, используется стандартное поведение диаграммы.  
* Вкл — включается принудительная кластеризация узлов.  
** При включении появляется выпадающий список **«Свойство для группировки»**, содержащий все доступные свойства узлов из датасета (все колонки с префиксами "{{source_*}}" и "{{target_*}}", кроме технических "{{*_id}}").  
** Поведение: узлы, имеющие **одинаковое значение** выбранного свойства (независимо от того, являются они {{source}} или {{target}}), начинают сильнее притягиваться друг к другу и слабо отталкиваться от узлов с другими значениями свойства.  
** Пример: при выборе свойства «Город_клиента» все узлы с одинаковым городом образуют визуальную «кучку», размер которой наглядно отражает количество узлов в группе. Связи между группами сохраняются, но общая картина становится более читаемой.
*Примечание* настройка не меняет состав данных, приходящих из BI-ядра.

h3. 6. Механизмы фильтрации (Уровень BI Core)

Для обеспечения корректного построения Графа на основе плоской денормализованной таблицы, BI-ядро должно динамически транслировать пользовательские фильтры (например, {{Category = 'Премиум'}}) в SQL-запросы. 

Так как свойства источника и приёмника хранятся в одной строке, простое условие {{WHERE}} вернет всю строку целиком (вместе со связанным узлом). Поэтому формирование условий {{WHERE}} и *блока {{SELECT}}* напрямую зависит от выбранных настроек компонента (Раздел 5).

Ниже описана логика работы BI Core при наложении фильтра.

----
6.1. Режим «Все связи» (По умолчанию).
Фильтр применяется к обоим концам связи (как к источнику, так и к приёмнику).
* *1) С настройкой «С соседями (+1 уровень)» (По умолчанию):*
Применяется базовая логика *OR*. В выборке остаются все строки, где искомый узел выступает источником ИЛИ приёмником. Так как возвращается вся строка целиком, в выборку автоматически попадают все связанные с ним узлы (соседи).
* *SQL-логика:*
{code:sql}
WHERE source_category = 'Премиум' OR target_category = 'Премиум'
{code}
_Результат:_ На фронтенд уходит сам узел и все его инцидентные соседи со связями.
* *2) С настройкой «Строгий режим»:*
В итоговую выборку должны попасть:
** а) Связи, где *оба* узла удовлетворяют фильтру.
** б) Изолированные узлы, удовлетворяющие фильтру (где {{target_id IS NULL}}).
** в) *Самое важное:* Узлы, которые удовлетворяют фильтру, но их сосед — нет. В этом случае сосед должен быть отсечен, а подходящий узел выведен как *изолированный*.
* *SQL-логика:*
Ядро должно "занулить" неподходящий конец связи. Если подходящим оказался только приёмник, ядро переносит его в колонки {{source_*}} (т.к. {{source_id}} обязателен), а {{target_*}} делает {{NULL}}.
{code:sql}
SELECT 
    -- Если источник не подходит, ставим на его место подходящий приёмник
    CASE WHEN source_category = 'Премиум' THEN source_id ELSE target_id END AS source_id,
    CASE WHEN source_category = 'Премиум' THEN source_category ELSE target_category END AS source_category,
    
    -- Приёмник оставляем только если он тоже подходит (иначе зануляем = изолируем узел)
    CASE WHEN source_category = 'Премиум' AND target_category = 'Премиум' THEN target_id ELSE NULL END AS target_id,
    ...
FROM dataset
WHERE source_category = 'Премиум' OR target_category = 'Премиум'
{code}
_Результат:_ Граф отрисует связи только между узлами удовлетворяющими фильтру. Узлы "премиум", у которых соседи другого класса, отрисуются просто как точки без стрелок.

----
6.2. Режим «Только входящие связи».
Фильтр применяется с фокусом на узлы-приёмники.

* *1) С настройкой «С соседями (+1 уровень)»:*
В выборке остаются строки, где фильтрации удовлетворяет узел-приёмник. При этом возвращается вся строка целиком, поэтому отрисовывается сам отфильтрованный узел-приёмник и все узлы-источники, которые на него ссылаются.
*SQL-логика:*
{code:sql}
WHERE target_category = 'Премиум'
{code}

* *2) С настройкой «Строгий режим»:*
В итоговой выборке остаётся *только* узел-приёмник, удовлетворяющий фильтру. Узел-источник, имеющий с ним связь, не отрисовывается (связь отсекается). 
*SQL-логика:* Ядро проецирует отфильтрованный приёмник на место источника (делая его изолированным).
{code:sql}
SELECT 
    target_id AS source_id, 
    target_category AS source_category, 
    NULL AS target_id,
    NULL AS edge_relation
FROM dataset
WHERE target_category = 'Премиум'
{code}

----
6.3. Режим «Только исходящие связи».
Аналогично п. 6.2, но фокус на источниках.
* *С соседями:* 
{code:sql}
WHERE source_category = 'Премиум'
{code}
Возвращает источники и их приёмники.
* *Строгий режим:* Ядро зануляет {{target_id}}, оставляя только {{source_id}}. Связи не выводятся.

----
6.4. Кросс-фильтрация (Интерактивность на дашборде).
При включенном _"режиме фильтрации"_, при клике на конкретный узел (например, {{id = 'A'}}) на самом Графе или на соседнем чарте, BI-ядро генерирует условие на основе настроек компонента.
Например:
* *«Все связи» + «С соседями» (По умолчанию):* Покажет узел 'A' и все его связи во всех направлениях.
*SQL:* 
{code:sql}
WHERE source_id = 'A' OR target_id = 'A'
{code}
* *«Только исходящие связи» + «С соседями»:* Покажет узел-источник 'A' и те узлы, на которые он ссылается.
*SQL:* 
{code:sql}
WHERE source_id = 'A'
{code}
* *«Только входящие связи» + «С соседями»:* Покажет узел-приёмник 'A' и те узлы, которые на него ссылаются.
*SQL:* 
{code:sql}
WHERE target_id = 'A'
{code}
* *Любое направление + «Строгий режим»:* _Примечание для аналитиков:_ Применение «Строгого режима» к кросс-фильтрации по конкретному ID приведет к отображению *только самого узла 'A'* (как изолированной точки без связей), так как соседние узлы будут отсечены механизмом зануления (см. п 6.1.2).

----
6.5. Комплексная фильтрация (Несколько разных фильтров по _AND_).
Если пользователь выбирает несколько условий (например, "Категория = Премиум" И "Регион = Москва"), логика обработки (включая зануление в Строгом режиме) должна применяться к *каждому узлу индивидуально*.
* *SQL-логика (концепт для «Все связи» + «С соседями»):*
{code:sql}
WHERE (source_category = 'Премиум' AND source_region = 'Москва')
   OR (target_category = 'Премиум' AND target_region = 'Москва')
{code}
_Результат:_ Отрисуются только те узлы (и их связи), которые одновременно удовлетворяют обоим условиям.

h3. 7. Алгоритм сборки графа на Фронтенде (ECharts)
В компонент визуализации на фронтенде приходит отфильтрованный JSON-массив объектов (строк). Компонент должен распарсить эти "плоские" данные и собрать два массива для ECharts: {{nodes}} (без дубликатов) и {{edges}} (связи).

*Шаг 1: Извлечение и дедупликация узлов (Nodes)*
Использовать структуру {{Map}} (где ключ — ID узла), чтобы избежать дублирования, так как один и тот же узел будет встречаться во множестве строк.
# Итерация по каждой строке массива данных.
# *Проверка источника:* если {{source_id}} еще нет в {{Map}}, создать объект узла, заполнив его полями {{source_\\*}} (id, label, category, value, color, tooltip), и добавить в {{Map}}.
# *Проверка приёмника:* если {{target_id}} корректен (не равен NULL и не пустая строка) и его еще нет в {{Map}}, создать объект узла, заполнив его полями {{target_\\*}}, и добавить в {{Map}}.
_Примечание:_ Если узел уже существует в {{Map}}, его повторное добавление игнорируется.

*Шаг 2: Формирование связей (Edges)*
# Итерация по каждой строке массива данных.
# Если {{target_id}} корректен (не NULL), формируется объект связи:
{{source: row.source_id, target: row.target_id, relation: row.edge_relation, tooltip: row.edge_tooltip}}
# Если между узлами есть несколько связей с разным {{edge_relation}}, создаются независимые объекты связей. ECharts поддерживает multiple edges (кривые Безье).

*Шаг 3: Передача в ECharts*
# Сформированные узлы {{Array.from(Map.values())}} передаются в свойство {{series[0].data}}.
# Массив связей передается в {{series[0].links}}.

h3. 9. Критерии приемки (AC):
# *Фильтрация не рвет связи:* При выборе узла «А» в фильтре, на графе отображается сам узел «А», все узлы, куда идут стрелки от «А», и все узлы, от которых идут стрелки к «А».
# *Изолированные узлы:* Узлы без связей (где target_id = NULL) корректно отрисовываются на полотне графа. При фильтрации по их категории они не пропадают.
# *Направленная фильтрация:* Поддерживается возможность отфильтровать граф так, чтобы остались только узлы-приёмники с нужным свойством.
# *Дедупликация фронтенда:* Независимо от количества строк в JSON, узел с конкретным ID отрисовывается на холсте только один раз. Ошибок о дублировании ID не возникает.
# *HTML в подсказках:* Поля {{*_tooltip}} рендерятся корректно, HTML-теги (например, <b>Премиум</b>) не экранируются как текст, а применяются как форматирование.
# *Множественные связи:* Поддерживается корректная отрисовка двух стрелок (например, «Аффилированность» и «Партнерство») между одной и той же парой узлов.
# *Внутренний фокус:* Если _"режим фильтра"_ у диаграммы Граф *выключен*, то при клике на узел в Графе, встроенными средствами ECharts активируется выделение узла и его инцидентных связей (остальные узлы Графа становятся полупрозрачными/блеклыми). Данные при этом не перезапрашиваются.
# *Кросс-фильтрация:* Если _"режим фильтра"_ у диаграммы Граф *включен*, BI-ядро применяет жесткий SQL-фильтр к датасету по OR-логике (Раздел 6.3). В этом случае Граф перерисовывается и отображает только выбранный подграф (узел + соседи), остальные узлы исчезают из визуализации, а соседние виджеты фильтруются по этому ID.".

Данный подход оказался не оптимальным и переусложнённым. Насколько я понял классический подход работы с Графовыми визуализациями на реляционных базах данных строиться на двух таблицах, поэтому мной была подготовлена обновлённая постановка для того, чтобы в рамках нашей системы визуализация Граф также использовала два набора данных.

Вот моя обновлённая постановка - "Переработка архитектуры визуализации «Граф»

h3. 1. Цель доработки.

Обеспечить корректную и предсказуемую работу визуализации «Граф» при фильтрации, агрегации и совместном использовании нескольких наборов данных.

Текущая архитектура визуализаций портала предполагает использование одного набора данных на одну визуализацию. Для визуализации «Граф» данный подход оказался неэффективным и приводит к следующим проблемам:

* усложнение структуры данных;
* дублирование информации;
* некорректная работа фильтрации;
* потеря узлов и связей при фильтрации;
* невозможность корректно реализовать классическую графовую модель;
* невозможность полноценно использовать независимые сущности «узлы» и «связи».

Цель данной доработки:

* перевести визуализацию «Граф» на классическую двухтабличную модель построения графов;
* обеспечить поддержку нескольких наборов данных в рамках одной визуализации;
* сохранить полную обратную совместимость со всеми существующими визуализациями;
* обеспечить корректную интеграцию с визуализациями «Таблица» и «Сводная таблица»;
* обеспечить корректную работу всех сценариев фильтрации.

h3. 2. Концепция нового решения.

В рамках данной доработки визуализация «Граф» должна перейти на классическую графовую архитектуру:
* отдельный набор данных — «Узлы графа»;
* отдельный набор данных — «Связи графа».

Визуализация должна уметь одновременно использовать несколько наборов данных.

----
h4. 2.1. Набор данных «Узлы графа».

Набор данных содержит:
* все узлы графа;
* свойства узлов;
* параметры отображения узлов.

Каждая строка набора данных соответствует одному узлу.

----
h4. 2.2. Набор данных «Связи графа».

Набор данных содержит:
* связи между узлами;
* свойства связей;
* параметры отображения связей.

Каждая строка набора данных соответствует одной связи между двумя узлами.

h3. 3. Основная архитектурная проблема.

В текущей реализации все визуализации используют ссылку на поле набора данных через его наименование ({{name}}).

На текущий момент:

* {{name}} уникально только в рамках одного набора данных;
* {{name}} не гарантирует уникальность между несколькими наборами данных;
* при использовании нескольких наборов данных могут возникать конфликты ссылок на поля.

Это делает корректную работу визуализаций затруднительной и нестабильной при использовании более одного набора данных одновременно.

Для реализации новой архитектуры «Графа» требуется устранить данное ограничение.

После реализации доработки поле {{name}} должно использоваться как:

Требования:

* для новых наборов данных данное поле автоматически заполняется UUID;
* значение {{name}} не должно использоваться в UI или отображаться пользователю, вместо него в интерфейсе и редакторе выражений должно отображаться {{display_name}}.

h3. 7. Фильтрация данных.

h4. 7.1. Основная цель доработки.

Основная цель данной переработки — обеспечить корректную фильтрацию данных для построения визуализации «Граф».

Текущая проблема:

* при использовании одной плоской таблицы фильтрация удаляет строки содержащие узлы и связи;
* при наличии строки с узлом-источником, связью, но отсутствием строки, содержащей узел-приёмник - визуализация не может корректно построить данную связь;
** граф становится неполным;
** визуализация теряет консистентность.

Новая архитектура должна устранить данную проблему.

----
h4. 7.2. Фильтрация Набора данных «Узлы».

Фильтрация по полям узлов должна:

* применяться только к Набору данных «Узлы»;
* ограничивать набор отображаемых узлов.

После фильтрации узлов:

* визуализация должна автоматически попытаться построить связи;
** при наличие связи, содержащей отсутствующие узлы, такая связь должна быть пропущена и не отрисовываться.
* должны остаться только связи между отображаемыми узлами.

----
h4. 7.3. Фильтрация Набора данных «Связи».

Фильтрация по полям связей должна:

* применяться только к Набору данных «Связи»;
* скрывать только связи;
* не удалять узлы автоматически;
* при наличие узлов без связей - они отображаются как изолированные узлы в штатном порядке.

----
h4. 7.4. Правила итоговой отрисовки.

После применения фильтров:

* отображаются только узлы, прошедшие фильтрацию;
* отображаются только связи, прошедшие фильтрацию;
* связь отображается только если оба узла присутствуют в итоговом наборе.

h4. 7.5. Совместимость фильтрации с другими визуализациями.
