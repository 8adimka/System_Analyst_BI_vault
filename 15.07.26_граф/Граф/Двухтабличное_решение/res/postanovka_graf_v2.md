## 1. Цель доработки

Обеспечить корректную и предсказуемую работу визуализации «Граф» при фильтрации, агрегации и совместном использовании нескольких наборов данных.

Текущая архитектура предполагает использование **одного набора данных** на одну визуализацию. Для визуализации «Граф» данный подход оказался неэффективным и приводит к следующим проблемам:

- усложнение структуры данных и необходимость денормализации;
- дублирование информации в наборе данных;
- некорректная работа фильтрации: при удалении строк фильтром теряются узлы или связи;
- потеря консистентности графа: связь не может быть построена, если узел-приёмник был отфильтрован;
- невозможность корректно реализовать классическую графовую модель (отдельные сущности «узлы» и «связи»).

**Цель данной доработки:**

- перевести визуализацию «Граф» на классическую двухтабличную модель (отдельные наборы данных для узлов и связей);
- обеспечить поддержку нескольких наборов данных в рамках одной визуализации «Граф»;
- сохранить полную обратную совместимость со всеми существующими визуализациями и дашбордами;
- обеспечить корректную интеграцию с визуализациями «Таблица» и «Сводная таблица»;
- обеспечить корректную работу всех сценариев фильтрации.

## 2. Концепция нового решения

Визуализация «Граф» переходит на классическую графовую архитектуру с двумя независимыми наборами данных:

| Набор данных | Назначение |
|---|---|
| **Набор данных «Узлы»** | Содержит все узлы графа, их свойства и параметры отображения |
| **Набор данных «Связи»** | Содержит все связи между узлами, их свойства и параметры отображения |

Визуализация должна уметь одновременно использовать оба этих набора данных.

### 2.1. Набор данных «Узлы»

Каждая строка набора данных соответствует **одному узлу** и содержит:

- идентификатор узла (`node_id`) — обязательное поле;
- свойства и параметры отображения узла (метка, цвет, размер, категория, иконка, tooltip и т.д.) — опциональные поля.

### 2.2. Набор данных «Связи»

Каждая строка набора данных соответствует **одной связи** между двумя узлами и содержит:

- идентификатор связи (`edge_id`) — обязательное поле;
- идентификатор узла-источника (`source_node_id`) — обязательное поле;
- идентификатор узла-приёмника (`target_node_id`) — обязательное поле;
- свойства и параметры отображения связи (метка, цвет, тип, вес, толщина, tooltip и т.д.) — опциональные поля.

## 3. Архитектурное решение: поддержка нескольких наборов данных в одной визуализации

### 3.1. Текущее ограничение

В текущей реализации одна визуализация может быть привязана только к одному набору данных. Данное ограничение является архитектурным и распространяется на backend-хранилище конфигурации, API и frontend.

### 3.2. Требуемые изменения

Для реализации двухтабличной архитектуры «Графа» необходимо расширить платформу, добавив возможность привязки **нескольких наборов данных к одной визуализации**.

**Важно:** данное расширение вводится как инфраструктурная основа. На первом этапе оно используется исключительно для визуализации «Граф». Все остальные визуализации продолжают работать с одним набором данных — поведение существующих компонентов не изменяется.

### 3.3. Идентификация полей из разных наборов данных

При работе с несколькими наборами данных поля разных наборов могут иметь одинаковые имена (`name`). Чтобы исключить конфликты ссылок, все ссылки на поля в конфигурации визуализации «Граф» должны использовать **составной идентификатор**, включающий идентификатор набора данных и имя поля:

```
{dataset_id}.{field_name}
```

**Пример:** `nodes_dataset.node_id`, `edges_dataset.source_node_id`.

Данный механизм применяется во всей конфигурации визуализации «Граф»: маппинге полей на полки, настройках фильтров, tooltip, агрегаций и т.д. Все остальные визуализации, работающие с одним набором данных, продолжают использовать ссылку по имени поля `name` в прежнем виде — логика их работы не изменяется.

## 4. Новая архитектура визуализации «Граф»

### 4.1. Требования к набору данных «Узлы»

| Поле | Тип | Обязательность | Описание |
|---|---|---|---|
| `node_id` | string / number | **Обязательное** | Уникальный идентификатор узла |
| `node_label` | string | Опциональное | Отображаемое имя узла |
| `node_value` | number | Опциональное | Числовое значение узла |
| `node_category` | string | Опциональное | Категория узла |
| `node_color` | string | Опциональное | Цвет узла |
| `node_tooltip` | string | Опциональное | Текст подсказки узла |
| `node_icon` | string | Опциональное | Иконка узла |
| `node_size` | number | Опциональное | Размер узла |
| `node_group` | string | Опциональное | Группа узла |

Пользователь может использовать произвольные колонки набора данных в качестве атрибутов узлов через механизм маппинга на полки (например, «Общая годовая выручка» в качестве «Размера узла»).

### 4.2. Требования к набору данных «Связи»

| Поле | Тип | Обязательность | Описание |
|---|---|---|---|
| `edge_id` | string / number | **Обязательное** | Уникальный идентификатор связи |
| `source_node_id` | string / number | **Обязательное** | ID узла-источника (откуда выходит связь) |
| `target_node_id` | string / number | **Обязательное** | ID узла-приёмника (куда входит связь) |
| `edge_label` | string | Опциональное | Название связи |
| `edge_value` | number | Опциональное | Вес связи |
| `edge_color` | string | Опциональное | Цвет связи |
| `edge_tooltip` | string | Опциональное | Текст подсказки связи |
| `edge_type` | string | Опциональное | Тип связи |
| `edge_width` | number | Опциональное | Толщина линии связи |

Пользователь может использовать произвольные колонки набора данных для атрибутов связей через механизм маппинга на полки.

## 5. Логика построения визуализации

### 5.1. Построение узлов

Визуализация загружает набор данных «Узлы» и строит коллекцию узлов, используя `node_id` как уникальный ключ.

### 5.2. Построение связей

Визуализация загружает набор данных «Связи» и строит коллекцию связей, сопоставляя значения `source_node_id` и `target_node_id` с `node_id` из набора данных «Узлы». `edge_id` используется как уникальный ключ связи.

### 5.3. Обработка отсутствующих узлов (некорректные связи)

Если в наборе данных «Связи» обнаружена строка, содержащая ссылку на несуществующий в наборе данных «Узлы» идентификатор (`source_node_id` или `target_node_id`):

- визуализация **не падает** и не отображает ошибку пользователю;
- данная связь **пропускается** (не отрисовывается);
- в логах браузера и/или серверных логах фиксируется **запись об ошибке валидации** с указанием `edge_id` и отсутствующего `node_id`;
- все корректные узлы и связи отрисовываются в штатном режиме.

### 5.4. Изолированные узлы

Визуализация поддерживает узлы без единой входящей или исходящей связи. Такие узлы:

- **отображаются** на полотне как самостоятельные точки;
- **участвуют** в фильтрации, поиске и выделении наравне с остальными узлами.

## 6. Фильтрация данных

### 6.1. Основная цель

Разделение на два независимых набора данных полностью устраняет проблему потери консистентности графа при фильтрации: фильтрация больше не удаляет строки, которые содержат одновременно и узлы, и связи.

### 6.2. Фильтрация набора данных «Узлы»

Фильтрация по полям набора данных «Узлы» применяется **только к узлам**:

- ограничивает множество отображаемых узлов;
- после фильтрации узлов связи автоматически пересчитываются: показываются только те связи, оба конца которых входят в итоговое множество видимых узлов (точное поведение определяется настройкой режима охвата фильтрации — см. раздел 6.4).

### 6.3. Фильтрация набора данных «Связи»

Фильтрация по полям набора данных «Связи» применяется **только к связям**:

- скрывает связи, не прошедшие фильтр;
- **не удаляет узлы** автоматически;
- узлы, у которых все связи были скрыты фильтром, отображаются как изолированные.

### 6.4. Режимы интерактивной фильтрации

#### 6.4.1. Проблема и мотивация

При базовой фильтрации узлов отфильтрованный узел теряет все связи, поскольку соседние узлы удаляются из отображения. Для аналитических задач часто важно видеть не только сам отфильтрованный узел, но и всё его ближайшее окружение. Для поддержки различных сценариев пользователю предоставляется явный выбор режима фильтрации.

#### 6.4.2. Настройка: Режим охвата фильтрации («С соседями»)

В панели настроек компонента «Граф» добавляется переключатель:

**«С соседями»** (Тумблер / Toggle):

| Значение | Поведение |
|---|---|
| **ВКЛ** (по умолчанию) | После фильтрации отображаются отфильтрованные узлы **и все их непосредственные соседи** (+1 уровень), а также все рёбра между ними. |
| **ВЫКЛ** | После фильтрации отображаются **только узлы, прошедшие фильтр**, и только рёбра строго между ними. Узлы, не прошедшие фильтр, скрываются полностью. |

**Режим «С соседями» — ВКЛ, алгоритм:**

1. Определить множество **узлов-кандидатов** — тех, что прошли фильтр.
2. Из набора данных «Связи» выбрать все рёбра, у которых хотя бы **один конец** (`source_node_id` ИЛИ `target_node_id`) принадлежит множеству кандидатов.
3. Из этих рёбер извлечь **все упомянутые `node_id`** — они становятся итоговым множеством отображаемых узлов, даже если сами не прошли исходный фильтр.

**Пример:**
- Узлы: A (Премиум), B (Стандарт), C (Премиум), D (Стандарт).
- Рёбра: A→B, B→C, B→D.
- Фильтр `category = "Премиум"` → кандидаты: A, C.
- Рёбра, инцидентные A или C: A→B (A входит), B→C (C входит).
- Итоговые узлы: **A, B, C**. Узел B отображается как сосед, хотя категории «Премиум» не имеет.
- Итоговые рёбра: A→B, B→C.
- Узел D и ребро B→D **не отображаются**: D не прошёл фильтр и не является соседом кандидата.

**Режим «С соседями» — ВЫКЛ, алгоритм:**

BI-ядро возвращает только узлы, прошедшие фильтр, и только рёбра, у которых **оба конца** входят в множество отфильтрованных узлов.

**Тот же пример, строгий режим:**
- Итоговые узлы: A, C.
- Ребро A→B — пропускается (B не прошёл).
- Ребро B→C — пропускается (B не прошёл).
- Итог: A и C отображаются как изолированные точки (прямой связи A→C нет).

#### 6.4.3. Настройка: Режим «Направление фильтрации»

В панели настроек компонента «Граф» добавляется настройка:

**«Направление фильтрации»** (Выпадающий список):

| Значение | Поведение в режиме «С соседями» — ВКЛ |
|---|---|
| **«Все направления»** (по умолчанию) | Узел попадает в результат, если он является источником или приёмником хотя бы одного ребра, связанного с отфильтрованным узлом. |
| **«Только исходящие»** | К отфильтрованным узлам добавляются только узлы, являющиеся `target_node_id` в рёбрах, где отфильтрованный узел — `source_node_id`. |
| **«Только входящие»** | К отфильтрованным узлам добавляются только узлы, являющиеся `source_node_id` в рёбрах, где отфильтрованный узел — `target_node_id`. |

> **Примечание:** Настройка «Направление фильтрации» активна **только** при режиме «С соседями» — **ВКЛ**. При режиме «С соседями» — **ВЫКЛ** элемент управления отображается в состоянии `disabled`. В строгом режиме показываются только рёбра, оба конца которых прошли фильтр — направление ребра не влияет на состав итогового множества.

#### 6.4.4. Настройка: Режим взаимодействия при клике на узел

В панели настроек компонента «Граф» добавляется переключатель:

**«Режим клика на узел»**:

| Значение | Поведение |
|---|---|
| **«Выделение»** (по умолчанию) | При клике на узел активируется **локальное выделение** средствами ECharts: выбранный узел и его инцидентные рёбра подсвечиваются, остальные узлы становятся полупрозрачными. Данные **не перезапрашиваются**, состав графа **не меняется**. |
| **«Кросс-фильтрация»** | При клике на узел BI-ядро применяет жёсткий фильтр к набору данных «Узлы» по `node_id` кликнутого узла. Граф перерисовывается с учётом текущих настроек «С соседями» и «Направления фильтрации». Соседние виджеты дашборда фильтруются по выбранному `node_id`. |

> **Важно:** В режиме «Кросс-фильтрация» + «С соседями» **ВЫКЛ** клик на узел приведёт к отображению только самого узла как изолированной точки — соседи будут отсечены. Данное поведение является ожидаемым следствием комбинации настроек и должно быть явно задокументировано в справке.

#### 6.4.5. Поведение при пустом результате фильтрации

Если после применения фильтра итоговое множество узлов оказывается пустым:

- визуализация отображает **пустое полотно** с информационной подсказкой при наведении: *«Нет данных, соответствующих условиям фильтра»*;
- ошибки и падения визуализации не возникает;
- при снятии фильтра граф восстанавливается в соответствии с текущими настройками.

### 6.5. Совместимость фильтрации с другими визуализациями

Визуализация «Граф» должна полностью поддерживать совместную работу с:

- глобальными фильтрами дашборда;
- кросс-фильтрацией из других визуализаций (Таблица, Сводная таблица и т.д.);
- механизмом drill-down.

## 7. Изменения backend

### 7.1. Поддержка нескольких наборов данных в одной визуализации

Необходимо:

- реализовать возможность привязки нескольких наборов данных к одной визуализации;
- реализовать хранение конфигурации нескольких наборов данных в рамках одной визуализации;
- реализовать корректную передачу данных нескольких наборов данных на frontend.

### 7.2. API визуализаций

Необходимо доработать API.

Требования:

- API должно поддерживать работу сразу с несколькими наборами данных для одной визуализации;
- каждый набор данных должен иметь уникальный идентификатор в рамках визуализации (`dataset_role`: `nodes`, `edges`);
- ссылки на поля наборов данных в конфигурации визуализации «Граф» используют составной идентификатор `{dataset_id}.{field_name}`.

### 7.3. Модель хранения конфигурации визуализации «Граф»

Конфигурация визуализации «Граф» должна хранить:

- список привязанных наборов данных с указанием их ролей:
  - `nodes_dataset` — набор данных «Узлы»;
  - `edges_dataset` — набор данных «Связи»;
- маппинг полей на полки визуализации (с использованием составного идентификатора);
- настройки режимов фильтрации («С соседями», «Направление фильтрации», «Режим клика»).

**Пример структуры конфигурации (схематично):**

```json
{
  "type": "graph",
  "datasets": {
    "nodes_dataset": "dataset_id_A",
    "edges_dataset": "dataset_id_B"
  },
  "shelves": {
    "nodes": "nodes_dataset.node_id",
    "edges": [
      { "field": "edges_dataset.source_node_id", "role": "source" },
      { "field": "edges_dataset.target_node_id", "role": "target" }
    ],
    "node_properties": [
      { "field": "nodes_dataset.revenue", "role": "size" },
      { "field": "nodes_dataset.category", "role": "color" }
    ],
    "edge_properties": [
      { "field": "edges_dataset.edge_type", "role": "type" },
      { "field": "edges_dataset.weight", "role": "value" }
    ]
  },
  "settings": {
    "include_neighbors": true,
    "filter_direction": "all",
    "click_mode": "highlight"
  }
}
```

### 7.4. Обработка фильтров

Движок фильтрации дорабатывается для поддержки независимой фильтрации нескольких наборов данных:

- фильтры по полям набора данных «Узлы» применяются исключительно к набору данных «Узлы»;
- фильтры по полям набора данных «Связи» применяются исключительно к набору данных «Связи»;
- фильтры из других виджетов дашборда (кросс-фильтрация) применяются к соответствующему набору данных на основе принадлежности поля.

**Специфическое требование для режима «С соседями» — ВКЛ:**

При активном режиме BI-ядро выполняет расширенную двухшаговую подготовку данных для визуализации «Граф»:

1. Применить пользовательский фильтр к набору данных «Узлы» → получить множество `node_id` узлов-кандидатов.
2. Выполнить дополнительный запрос к набору данных «Связи»: выбрать все рёбра, где `source_node_id` **ИЛИ** `target_node_id` входит в множество кандидатов.
3. Извлечь из этих рёбер все упомянутые `node_id` и добавить их к итоговому множеству отображаемых узлов (с учётом настройки «Направление фильтрации»).

## 8. Изменения frontend

### 8.1. Обновлённый интерфейс панели настроек визуализации «Граф»

Боковая панель конфигуратора визуализации «Граф» перерабатывается под двухтабличную схему.

#### 8.1.1. Раздел «Структура данных»

В боковой панели добавляется раздел с заголовком **«Структура данных»**, содержащий два подраздела:

---

**Подраздел «Узлы»:**

- Заголовок подраздела: **«Узлы»**.
- Выпадающий список для выбора набора данных «Узлы» (аналогичен текущему селектору набора данных).
- После выбора набора данных — список полей выбранного набора данных (колонкой вниз), пригодных для размещения на полки.

**Подраздел «Связи»:**

- Заголовок подраздела: **«Связи»**.
- Выпадающий список для выбора набора данных «Связи».
- После выбора набора данных — список полей выбранного набора данных.

**Сворачивание / разворачивание списков полей (аккордеон):**

Каждый подраздел («Узлы» / «Связи») поддерживает сворачивание списка полей:

- Под выпадающим списком выбора набора данных располагается специальная область-триггер (кнопка/стрелка).
- **При нажатии на триггер** — список полей данного набора данных сворачивается: остаётся видимым только заголовок подраздела («Узлы» / «Связи») и выпадающий список выбора набора данных.
- **При повторном нажатии** — список полей разворачивается.
- Пользователь может:
  - свернуть оба подраздела;
  - развернуть только один из них;
  - развернуть оба одновременно.
- Состояние сворачивания сохраняется в рамках текущей сессии редактирования.

#### 8.1.2. Обновлённый набор полок визуализации «Граф»

Полки визуализации «Граф» пересматриваются следующим образом:

---

**Полка 1: «Узлы»** _(была: «Узел»)_

- Принимает **одну пилюлю** из набора данных **«Узлы»**.
- Пилюля задаёт поле, содержащее наименования (идентификаторы) всех узлов графа (`node_id`).

---

**Полка 2: «Связи»** _(была: «Связь»)_

- Принимает **две пилюли** из набора данных **«Связи»**.
- Каждая пилюля обязательно настраивается через меню пилюли (нажать «🢓»):
  - Настройка **«Тип»**: выбрать значение «Узел-источник» или «Узел-приёмник».
- **«Узел-источник»** — поле, содержащее `source_node_id` (откуда выходит связь).
- **«Узел-приёмник»** — поле, содержащее `target_node_id` (куда входит связь).
- Диаграмма попарно обрабатывает строки и строит связь между указанными идентификаторами узлов.

> Визуализация не строит связи до тех пор, пока на полке «Связи» не размещены пилюли **обоих типов** («Узел-источник» и «Узел-приёмник»). При неполной настройке отображается соответствующая подсказка пользователю.

---

**Полка 3: «Свойства узлов»** _(была: «Значения»)_

- Принимает **произвольное количество пилюль** из набора данных **«Узлы»**.
- Каждая пилюля настраивается через меню пилюли (нажать «🢓»):
  - Настройка **«Тип»**: определяет, как данная колонка используется при отрисовке узлов.
  - Доступные типы: **Радиус**, **Цвет**, **Значение** (и другие, предусмотренные реализацией).
- Пример: поле «Общая годовая выручка» с типом «Радиус» задаёт размер узла пропорционально значению выручки.

---

**Полка 4: «Свойства связей»** _(была: «Категории»)_

- Принимает **произвольное количество пилюль** из набора данных **«Связи»**.
- Каждая пилюля настраивается через меню пилюли (нажать «🢓»):
  - Настройка **«Тип»**: определяет, как данная колонка используется при отрисовке связей.
  - Доступные типы: **Тип связи**, **Цвет**, **Значение** (и другие, предусмотренные реализацией).

---

**Полка 5: «Фильтры»** _(без изменений)_

- Принимает пилюли из любого из двух наборов данных.
- Используется для фильтрации данных визуализации.
- Фильтр применяется к тому набору данных, из которого взято поле.

### 8.2. Механизм отрисовки визуализации «Граф»

Логика построения графа переработана:

- граф строится на основе двух независимых наборов данных;
- узлы и связи обрабатываются независимо;
- рендер устойчив к частично некорректным данным (некорректные связи пропускаются с логированием);
- реализовано попарное сопоставление `source_node_id` и `target_node_id` с `node_id`.

### 8.3. Панель настроек режимов фильтрации

В разделе настроек компонента «Граф» (отдельно от панели полок) добавляются следующие элементы управления:

1. **«С соседями»** — Тумблер (Toggle), значение по умолчанию: **ВКЛ**.
2. **«Направление фильтрации»** — Выпадающий список с вариантами: «Все направления» (по умолчанию), «Только исходящие», «Только входящие». Недоступен (disabled), когда «С соседями» = ВЫКЛ.
3. **«Режим клика на узел»** — Переключатель с вариантами: «Выделение» (по умолчанию), «Кросс-фильтрация».

## 9. Обратная совместимость

### 9.1. Все существующие визуализации (кроме «Граф»)

Работоспособность всех существующих визуализаций **не должна быть затронута** после релиза.

Требования:

- все существующие визуализации продолжают использовать ссылку на поле по `name` в прежнем виде;
- логика работы с одним набором данных не изменяется;
- существующие дашборды **не требуют миграции конфигурации**;
- существующие API-контракты **не нарушаются**;
- сериализация / десериализация конфигураций остаётся совместимой.

### 9.2. Существующие визуализации «Граф»

Существующие дашборды с визуализацией «Граф», созданные до данного релиза (на основе одного набора данных), должны корректно открываться после релиза.

Требования:

- при открытии старой конфигурации «Граф» система должна корректно интерпретировать её в контексте нового интерфейса;
- рекомендуется предусмотреть механизм миграции старых конфигураций «Граф» на новую двухтабличную модель (либо отображение соответствующей подсказки пользователю при открытии устаревшей конфигурации).

- ошибки валидации данных должны корректно логироваться;
- пустой результат фильтрации обрабатывается штатно (см. раздел 6.4.5).

## 12. Критерии приёмки (AC)

### AC.1 — Визуализация строится на двух независимых наборах данных

**Дано:** настроена визуализация «Граф» с набором данных «Узлы» (10 строк) и набором данных «Связи» (15 строк).  
**Когда:** дашборд загружается без каких-либо фильтров.  
**Тогда:** на полотне отображаются все 10 узлов и все корректные связи между ними; отсутствуют дублирующиеся узлы; визуализация не падает и не отображает ошибок.

---

### AC.2.1 — Фильтрация узлов: режим «С соседями» — ВЫКЛ

**Дано:** граф с узлами A, B, C и связями A→B, B→C, A→C; режим «С соседями» — **ВЫКЛ**.  
**Когда:** пользователь применяет фильтр по набору данных «Узлы», под условие попадают только A и B.  
**Тогда:**
- отображаются только узлы A и B;
- отображается только связь A→B (оба конца прошли фильтр);
- связи B→C и A→C не отрисовываются;
- узел C не отображается;
- ошибок валидации не возникает.

---

### AC.2.2 — Фильтрация узлов: режим «С соседями» — ВКЛ

**Дано:** граф с узлами A (Премиум), B (Стандарт), C (Премиум), D (Стандарт); рёбра: A→B, B→C, B→D; режим «С соседями» — **ВКЛ** (по умолчанию).  
**Когда:** пользователь применяет фильтр `node_category = "Премиум"`.  
**Тогда:**
- отображаются узлы A, B, C (A и C — прошли фильтр, B — как сосед);
- отображаются рёбра A→B и B→C;
- узел D и ребро B→D **не отображаются** (D не прошёл фильтр и не является соседом ни одного из кандидатов A и C).

---

### AC.3 — Фильтрация связей не удаляет узлы

**Дано:** граф с узлами A, B, C и связями A→B (тип: «Партнёрство»), B→C (тип: «Аффилированность»).  
**Когда:** пользователь применяет фильтр по набору данных «Связи»: `edge_type = "Партнёрство"`.  
**Тогда:**
- отображаются все три узла A, B, C;
- отображается только связь A→B;
- узлы B и C отображаются как изолированные и продолжают работать штатно.

---

### AC.4 — Обработка некорректных связей не нарушает работу визуализации

**Дано:** набор данных «Связи» содержит строку с `source_node_id = "X"`, которого нет в наборе данных «Узлы».  
**Когда:** визуализация загружается.  
**Тогда:**
- все корректные узлы и связи отрисовываются в штатном режиме;
- некорректная связь пропускается (не отображается);
- в логах браузера и/или серверных логах фиксируется запись об ошибке валидации с указанием `edge_id` и отсутствующего `node_id`;
- визуализация не падает.

---

### AC.5 — Глобальные фильтры дашборда применяются корректно

**Дано:** на дашборде настроен глобальный фильтр по полю `category = "Премиум"`; поле присутствует в наборе данных «Узлы».  
**Когда:** пользователь активирует фильтр.  
**Тогда:**
- в наборе данных «Узлы» остаются только строки с `category = "Премиум"`;
- граф перестраивается с учётом текущих настроек режима «С соседями»;
- соседние виджеты (Таблица, Сводная таблица и т.д.) фильтруются в соответствии с настройками дашборда.

---

### AC.6 — Клик на узел фильтрует соседние виджеты с учётом режима «С соседями»

**Дано:** рядом с «Графом» расположена Таблица, связанная с тем же набором данных; режим клика — «Кросс-фильтрация»; режим «С соседями» — **ВКЛ**.  
**Когда:** пользователь кликает на узел с `node_id = "company_42"`.  
**Тогда:**
- Таблица фильтруется по `node_id = "company_42"`;
- Граф отображает узел «company_42» и всех его непосредственных соседей; рёбра между ними отображаются; остальные узлы скрываются.

**И:** при переключении режима «С соседями» — **ВЫКЛ**:
- Граф отображает только узел «company_42» как изолированную точку без связей;
- Таблица фильтруется по `node_id = "company_42"` аналогично.

---

### AC.7 — Изолированные узлы отображаются и участвуют в фильтрации

**Дано:** набор данных «Узлы» содержит узел D, на который нет ни одной ссылки в наборе данных «Связи».  
**Когда:** дашборд загружается; затем пользователь применяет фильтр по полю `category`, под которое узел D попадает.  
**Тогда:**
- узел D отображается на полотне как изолированная точка при загрузке дашборда;
- при фильтрации узел D остаётся в выборке и не исчезает;
- при клике на D в режиме «Кросс-фильтрация» соседние виджеты фильтруются по его `node_id`.

---

### AC.8 — Обратная совместимость: существующие дашборды работают без изменений

**Дано:** существующий дашборд с любой визуализацией (кроме «Граф»), созданной до данного релиза.  
**Когда:** релиз выкатывается в production.  
**Тогда:**
- все существующие дашборды открываются без ошибок;
- данные отображаются корректно;
- конфигурация не требует ручной правки.

---

### AC.9 — Производительность

**Дано:** набор данных «Узлы» содержит 1 000 строк, набор данных «Связи» содержит 2 000 строк.  
**Когда:** дашборд загружается; затем пользователь применяет фильтр, изменяющий состав узлов.  
**Тогда:**
- первичная отрисовка графа завершается не дольше, чем аналогичная операция в текущей реализации на сопоставимом объёме данных;
- перерисовка после применения фильтра выполняется без видимых зависаний интерфейса;
- браузер не выбрасывает предупреждений о долгих задачах (long tasks) в консоли.

---

### AC.10 — Настройки интерфейса конфигуратора

**Дано:** открыт конфигуратор визуализации «Граф».  
**Когда:** пользователь выбирает набор данных в подразделе «Узлы».  
**Тогда:**
- под выпадающим списком отображается список полей выбранного набора данных;
- пользователь может свернуть и развернуть список полей через область-триггер.

**И:** пользователь выбирает набор данных в подразделе «Связи» и размещает на полке «Связи» две пилюли, назначая им типы «Узел-источник» и «Узел-приёмник»:

- граф корректно строит связи на основе указанных полей;
- при отсутствии пилюли одного из типов отображается подсказка пользователю.
