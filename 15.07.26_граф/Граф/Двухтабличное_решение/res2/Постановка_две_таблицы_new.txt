h3. 1. Контекст и проблематика.

Визуализация «Граф» в текущей архитектуре работает в рамках общего ограничения платформы: одна визуализация использует один набор данных. Для большинства визуализаций это ограничение приемлемо, но для «Графа» оно приводит к системной проблеме: графовая модель естественно описывается двумя сущностями - узлами и связями, а текущая однотабличная схема вынуждает аналитика смешивать их в одной плоской таблице.

Текущий подход приводит к следующим ограничениям:
* данные приходится денормализовать: свойства узлов и свойства связей оказываются в одной строковой структуре;
* в наборе данных появляются дублирующиеся значения;
* фильтрация по строкам может удалять строки, необходимые для отрисовки связанных узлов;
* при фильтрации граф теряет узлы или связи и становится неполным;
* сложно корректно поддерживать изолированные узлы;
* свойства узлов и свойства связей нельзя независимо использовать для отображения, фильтрации и аналитики;
* настройка графа становится неочевидной для аналитика, так как одна таблица должна одновременно выполнять роль таблицы узлов и таблицы связей.

Доработка сфокусирована на поддержке двухтабличной модели именно для визуализации «Граф»: отдельный набор данных для узлов и отдельный набор данных для связей.

----
h3. 2. Цель задачи.

*Требуется:*
# Перевести визуализацию «Граф» на классическую двухтабличную модель данных: «Узлы» + «Связи».
# Реализовать для «Графа» возможность выбора и использования двух наборов данных в одной визуализации.
# Обеспечить корректное хранение конфигурации, в которой каждая пилюля однозначно связана с конкретным набором данных и ролью в графе.
# Сохранить существующую маршрутизацию к источникам данных и ClickHouse через цепочку {{набор данных -> источник данных -> host + port + database}}.
# Обеспечить корректную фильтрацию узлов и связей, включая режимы «С соседями» и «Направление фильтрации».
# Сохранить обратную совместимость существующих дашбордов и визуализаций.

----
h3. 3. Рамки задачи.

В рамках задачи необходимо реализовать:
* для визуализации «Граф» - выбор двух наборов данных с ролями:
** {{Узлы}} - набор данных, содержащий перечень узлов и свойства узлов;
** {{Связи}} - набор данных, содержащий пары связанных узлов и свойства связей;
* доработку левой панели настройки визуализации «Граф» под две секции наборов данных;
* доработку полок визуализации «Граф» под двухтабличную модель;
* хранение в конфигурации «Графа» ролей наборов данных и привязки каждой пилюли к конкретному набору;
* получение данных из двух наборов данных для одной визуализации;
* построение графа из двух независимых результирующих выборок;
* фильтрацию по полям узлов и по полям связей с разной логикой влияния на итоговый граф;
* поддержку интерактивного выделения и кросс-фильтрации при клике на узел;
* обработку неконсистентных данных без падения визуализации;
* обратную совместимость старых дашбордов и старых конфигураций «Графа».

Составные наборы данных и модель, при которой один набор может возвращать несколько связанных таблиц, рассматриваются как отдельное направление. Этот вариант - потенциально перспективный, но требует отдельной формализации и оценки.

----
h3. 4. Архитектурные тезисы.

h4. 4.1. Ссылки на поля.

Целевой принцип:
* {{name}} поля остаётся текущим системным именем поля в рамках набора данных;
* уникальность {{name}} требуется в рамках одного набора данных;
* глобальная уникальность {{name}} между разными наборами данных не требуется;
* при работе «Графа» с двумя наборами данных каждая пилюля должна хранить контекст выбранного набора данных;
* если в наборе «Узлы» и наборе «Связи» есть поля с одинаковым {{name}}, система должна различать их по роли/идентификатору набора данных, а не по одному имени поля.

Для пользователя поля отображаются так же, как в текущем интерфейсе наборов данных. Если на полках «Графа» могут оказаться одноимённые поля из разных секций, интерфейс должен визуально показывать контекст поля: «Узлы» или «Связи».

_Пример целевого поведения:_
* в наборе «Узлы» есть поле {{category}};
* в наборе «Связи» также есть поле {{category}};
* пользователь может использовать оба поля в настройках «Графа»;
* система не смешивает эти поля, потому что одна пилюля относится к роли {{Узлы}}, а другая - к роли {{Связи}}.

h4. 4.2. Существующая маршрутизация.

Существующая цепочка получения данных:

{code}
Пользователь
  -> Дашборд / визуализация
      -> Набор данных
          -> Источник данных
              -> host + port + database
{code}

Источник данных - это запись в PostgreSQL, содержащая реквизиты подключения к ClickHouse или другому поддерживаемому источнику. При открытии дашборда система идёт по существующей цепочке объектов, где источник данных уже содержит необходимые реквизиты подключения.

Для двухтабличного «Графа» требуется использовать ту же цепочку отдельно для каждого выбранного набора данных:
* набор «Узлы» маршрутизируется через свой {{datasource}};
* набор «Связи» маршрутизируется через свой {{datasource}};
* если оба набора данных используют один источник данных, запросы идут в один источник;
* если наборы данных используют разные источники данных, система должна выполнить независимое получение данных и сопоставить результаты на уровне логики «Графа».

Если на первом этапе реализация не может поддержать разные источники данных для наборов «Узлы» и «Связи», это ограничение должно быть явно реализовано в UI и валидации: пользователь должен видеть, что для двухтабличного «Графа» допустимы только совместимые источники данных.

h4. 4.3. Генерация SQL-запросов.

Сохраняется текущий принцип построителя запросов: исходный SQL набора данных не изменяется, а используется как базовый слой, поверх которого BI-ядро строит внешний запрос.

* Для каждого набора данных запрос формируется независимо;
* Фильтры и поля с полок применяются к тому набору данных, из которого взята соответствующая пилюля;
* Результатом получения данных для «Графа» должны быть две логически разделённые выборки: узлы и связи.

----
h3. 5. Целевая модель данных визуализации «Граф».

h4. 5.1. Общая модель.

Визуализация «Граф» в новом режиме использует два набора данных:

|| Роль набора данных || Назначение ||
| {{Узлы}} | Содержит все узлы графа, свойства узлов и параметры отображения узлов |
| {{Связи}} | Содержит связи между узлами, свойства связей и параметры отображения связей |

Каждая строка набора «Узлы» соответствует одному узлу графа.

Каждая строка набора «Связи» соответствует одной связи между двумя узлами.

h4. 5.2. Набор данных «Узлы».

Набор «Узлы» должен содержать поле, которое используется как ключ узла. В интерфейсе это поле размещается на полке «Узлы».

Требования:
* значение ключа узла должно быть уникальным в рамках итоговой выборки узлов после применения агрегаций и фильтров;
* значение ключа узла используется для сопоставления с полями «Узел-источник» и «Узел-приёмник» из набора «Связи»;
* ключ узла может быть строковым или числовым;
* пустые значения ключа узла не должны участвовать в построении графа;
* дополнительные поля набора «Узлы» могут использоваться как свойства узлов.

Примеры свойств узлов:

|| Тип свойства || Назначение ||
| {{Радиус}} | Управляет размером узла |
| {{Цвет}} | Управляет цветом узла |
| {{Значение}} | Используется как числовое значение узла или показатель для tooltip |
| {{Группа}} | Используется для группировки, легенды или дополнительного отображения, если поддержано текущей визуализацией |
| {{Tooltip}} | Используется для подсказки при наведении, если поддержано текущей визуализацией |

h4. 5.3. Набор данных «Связи».

Набор «Связи» должен содержать два поля, значения которых сопоставляются с ключами узлов:
* поле узла-источника;
* поле узла-приёмника.

Оба поля размещаются на полке «Связи». Для каждой пилюли на полке «Связи» пользователь должен указать тип:
* {{Узел-источник}};
* {{Узел-приёмник}}.

Требования:
* в одной строке набора «Связи» пара значений {{Узел-источник}} + {{Узел-приёмник}} описывает одну связь;
* значение {{Узел-источник}} должно сопоставляться с ключом узла из набора «Узлы»;
* значение {{Узел-приёмник}} должно сопоставляться с ключом узла из набора «Узлы»;
* если один из концов связи не найден в наборе «Узлы», такая связь не должна ломать визуализацию;
* дополнительные поля набора «Связи» могут использоваться как свойства связей.

Примеры свойств связей:

|| Тип свойства || Назначение ||
| {{Тип связи}} | Используется для категории связи, легенды или tooltip |
| {{Цвет}} | Управляет цветом линии связи |
| {{Значение}} | Используется как вес связи или показатель для tooltip |
| {{Толщина}} | Управляет толщиной линии связи, если поддержано текущей визуализацией |
| {{Tooltip}} | Используется для подсказки при наведении на связь, если поддержано текущей визуализацией |

h4. 5.4. Идентификатор связи.

Отдельное поле {{edge_id}} не является обязательным для пользовательской настройки, если текущий renderer «Графа» может стабильно формировать технический идентификатор связи из строки набора «Связи».

Если в текущей реализации для корректной работы, логирования или обновления состояния требуется явный идентификатор связи, необходимо:
* либо добавить поддерживаемый тип свойства связи {{Идентификатор связи}};
* либо формировать технический идентификатор на стороне backend/frontend из доступного контекста строки.

Технический идентификатор связи не должен требовать изменения структуры пользовательских наборов данных, если это можно избежать без потери стабильности.

----
h3. 6. Интерфейс настройки визуализации «Граф».

h4. 6.1. Левая панель «Структура данных».

В настройках визуализации «Граф» левая боковая панель должна содержать блок «Структура данных».

Внутри блока размещаются две секции:
* «Узлы»;
* «Связи».

h4. 6.2. Секция «Узлы».

В секции «Узлы» отображается:
# заголовок секции «Узлы»;
# выпадающий список выбора набора данных, который содержит узлы графа;
# список полей выбранного набора данных.

После выбора набора данных список полей работает аналогично текущему списку полей визуализации:
* поля можно перетаскивать на доступные полки «Графа»;
* поля из секции «Узлы» должны быть доступны для полок, которые работают со свойствами узлов и фильтрами;
* поле ключа узла должно размещаться на полке «Узлы».

h4. 6.3. Секция «Связи».

В секции «Связи» отображается:
# заголовок секции «Связи»;
# выпадающий список выбора набора данных, который содержит связи графа;
# список полей выбранного набора данных.

После выбора набора данных:
* поля можно перетаскивать на доступные полки «Графа»;
* поля из секции «Связи» должны быть доступны для полки «Связи», полки «Свойства связей» и полки «Фильтры»;
* поля из секции «Связи» не должны использоваться как ключ узла на полке «Узлы».

h4. 6.4. Сворачивание и разворачивание списков полей.

Для секций «Узлы» и «Связи» необходимо реализовать поведение аккордеона.

Требования:
* пользователь может свернуть список полей набора «Узлы»;
* пользователь может свернуть список полей набора «Связи»;
* пользователь может одновременно развернуть оба списка;
* пользователь может одновременно свернуть оба списка;
* при сворачивании остаются видимыми заголовок секции и выпадающий список выбранного набора данных;
* сворачивание списка полей не должно удалять уже размещённые на полках пилюли;
* состояние свёрнутости можно хранить как UI-состояние и не считать обязательной частью серверной конфигурации, если в платформе такие состояния не сохраняются.

h4. 6.5. Полки визуализации «Граф».

Набор полок визуализации «Граф» должен быть приведён к следующей структуре:

|| Полка || Источник пилюль || Назначение ||
| {{Узлы}} | Только набор «Узлы» | Поле ключа/наименования узла, по которому строится список узлов |
| {{Связи}} | Только набор «Связи» | Две пилюли: {{Узел-источник}} и {{Узел-приёмник}} |
| {{Свойства узлов}} | Только набор «Узлы» | Поля, управляющие отображением узлов |
| {{Свойства связей}} | Только набор «Связи» | Поля, управляющие отображением связей |
| {{Фильтры}} | Набор «Узлы» и набор «Связи» | Поля, по которым выполняется фильтрация графа |

Переименование текущих полок:
* текущая полка «Узел» переименовывается в «Узлы»;
* текущая полка «Связь» переименовывается в «Связи»;
* текущая полка «Значения» переименовывается в «Свойства узлов»;
* текущая полка «Категории» переименовывается в «Свойства связей»;
* полка «Фильтры» сохраняет назначение.

h4. 6.6. Настройки пилюль.

Для пилюль на полках должны быть доступны настройки типа.

Полка «Связи»:
* для каждой пилюли обязателен тип:
** {{Узел-источник}};
** {{Узел-приёмник}};
* на полке должно быть ровно две активные пилюли с разными типами;
* если две пилюли имеют одинаковый тип, визуализация должна показывать ошибку настройки и не строить некорректный граф.

Полка «Свойства узлов»:
* для каждой пилюли пользователь выбирает тип свойства;
* минимальный набор типов:
** {{Радиус}};
** {{Цвет}};
** {{Значение}};
* дополнительные типы могут быть добавлены, если они уже поддерживаются текущим renderer «Графа».

Полка «Свойства связей»:
* для каждой пилюли пользователь выбирает тип свойства;
* минимальный набор типов:
** {{Тип связи}};
** {{Цвет}};
** {{Значение}};
* дополнительные типы могут быть добавлены, если они уже поддерживаются текущим renderer «Графа».

h4. 6.7. Валидация настройки.

Визуализация «Граф» в двухтабличном режиме считается настроенной корректно, если:
* выбран набор данных «Узлы»;
* выбран набор данных «Связи»;
* на полке «Узлы» размещена одна пилюля из набора «Узлы»;
* на полке «Связи» размещены две пилюли из набора «Связи»;
* для пилюль на полке «Связи» указаны разные типы: {{Узел-источник}} и {{Узел-приёмник}};
* на полке «Свойства узлов» нет пилюль из набора «Связи»;
* на полке «Свойства связей» нет пилюль из набора «Узлы»;
* каждая пилюля хранит контекст набора данных, из которого она была выбрана.

Если обязательная настройка не заполнена, визуализация должна показывать понятное сообщение в области настройки или на полотне визуализации. Падения компонента быть не должно.

h3. 7. Конфигурация, backend и API.

h4. 7.1. Хранение конфигурации «Графа».

Необходимо доработать конфигурацию визуализации «Граф» так, чтобы она могла хранить:
* идентификатор набора данных с ролью {{Узлы}};
* идентификатор набора данных с ролью {{Связи}};
* маппинг поля ключа узла;
* маппинг поля узла-источника;
* маппинг поля узла-приёмника;
* маппинг свойств узлов;
* маппинг свойств связей;
* маппинг фильтров с указанием набора данных, к которому относится поле;
* режимы фильтрации и клика, описанные в разделе 9.

Концептуальный пример структуры:

{code:json}
{
  "graph_data_roles": {
    "nodes": {
      "dataset_id": 101,
      "node_key_field": "company_name",
      "node_properties": [
        {
          "field": "annual_revenue",
          "type": "radius"
        },
        {
          "field": "company_category",
          "type": "color"
        }
      ]
    },
    "edges": {
      "dataset_id": 205,
      "source_field": "partner_name",
      "target_field": "client_name",
      "edge_properties": [
        {
          "field": "relation_type",
          "type": "edge_type"
        },
        {
          "field": "deal_amount",
          "type": "value"
        }
      ]
    }
  },
  "graph_filtering": {
    "include_neighbors": true,
    "direction": "all",
    "click_mode": "selection"
  }
}
{code}

_Важно:_ данный пример фиксирует смысл данных, а не обязательный формат API-контракта.

h4. 7.2. API и backend-объекты.

Ориентировочно затрагиваются:
* объект сохранения отчёта/визуализации: {{reports}} или фактический объект конфигурации отчётов;
* команды чтения и сохранения конфигурации: {{get}} / {{update}};
* объект получения метаданных наборов данных: {{datasets}};
* команды получения метаданных: {{get}} / {{list}};
* команда получения данных для визуализации: фактическая команда {{data.*}} / {{query.*}}, используемая текущим BI-ядром.

Требования:
* перед сохранением изменённой конфигурации необходимо читать актуальное состояние через {{get}}/{{list}} по существующему правилу работы с {{update}};
* payload сохранения конфигурации «Графа» должен передавать оба набора данных и их роли;
* payload получения данных должен позволять backend определить, какие поля относятся к набору «Узлы», а какие - к набору «Связи»;
* ответ backend для двухтабличного «Графа» должен сохранять логическое разделение данных на узлы и связи;
* существующие API-контракты для остальных визуализаций не должны быть нарушены.

h4. 7.3. Получение данных.

Для двухтабличного «Графа» backend должен уметь получить данные из двух наборов данных в рамках одного обновления визуализации.

Допустимые варианты реализации:
* один backend-запрос от frontend, внутри которого BI-ядро выполняет два запроса к наборам данных и возвращает общий результат;
* два backend-запроса от frontend к данным разных наборов, если это лучше соответствует текущей архитектуре.

Независимо от способа реализации, frontend должен получить две логические коллекции:
* коллекцию узлов;
* коллекцию связей.

Концептуальный пример ответа:

{code:json}
{
  "status": 200,
  "data": {
    "nodes": [
      {
        "node_key": "company_1",
        "annual_revenue": 1200000,
        "company_category": "Премиум"
      }
    ],
    "edges": [
      {
        "source": "company_1",
        "target": "company_2",
        "relation_type": "Партнёрство",
        "deal_amount": 500000
      }
    ]
  }
}
{code}

h4. 7.4. Вычисляемые поля и меры.

В рамках этой задачи вычисляемые поля и меры должны выполняться в контексте конкретного набора данных.

Требования:
* вычисляемое поле, созданное или выбранное из набора «Узлы», может ссылаться только на поля набора «Узлы»;
* вычисляемое поле, созданное или выбранное из набора «Связи», может ссылаться только на поля набора «Связи»;
* формулы, одновременно обращающиеся к полям набора «Узлы» и набора «Связи», в рамках этой задачи не поддерживаются;
* UI и backend должны валидировать такие сценарии и не сохранять некорректную формулу;
* если текущая платформа не поддерживает вычисляемые поля на уровне конкретной визуализации для двух наборов данных, этот сценарий должен быть явно исключён из первого этапа реализации.

----
h3. 8. Логика построения графа.

h4. 8.1. Первичная загрузка без фильтров.

При загрузке визуализации без активных фильтров система должна:
# получить строки из набора «Узлы»;
# получить строки из набора «Связи»;
# построить множество узлов по полю, размещённому на полке «Узлы»;
# построить множество связей по двум полям на полке «Связи»;
# сопоставить значения {{Узел-источник}} и {{Узел-приёмник}} со значениями ключа узла;
# отрисовать все корректные узлы и все корректные связи.

h4. 8.2. Дедупликация узлов.

Если в итоговой выборке узлов встречается несколько строк с одинаковым ключом узла:
* визуализация не должна создавать дублирующиеся узлы;
* предпочтительно устранить дубли на уровне запроса или агрегации;
* если дубли дошли до фронтенда, _renderer_ должен дедуплицировать узлы по ключу;
* при наличии конфликтующих значений свойств узла поведение должно быть детерминированным и не должно приводить к падению визуализации.

Рекомендуемое поведение при конфликте свойств узла: использовать результат агрегации, заданный в настройках поля. Если агрегация не задана и конфликт не может быть разрешён однозначно, использовать первое значение в порядке ответа и зафиксировать предупреждение в логах.

h4. 8.3. Обработка отсутствующих узлов.

Если строка набора «Связи» содержит ссылку на узел, которого нет в итоговой коллекции узлов:
* связь должна быть пропущена;
* визуализация должна продолжить работу;
* остальные корректные узлы и связи должны быть отрисованы;
* в логах должна фиксироваться диагностическая запись с указанием значения отсутствующего узла и строки/идентификатора связи, если он доступен.

h4. 8.4. Изолированные узлы.

Визуализация должна поддерживать узлы без связей.

Изолированные узлы:
* отображаются на полотне графа;
* участвуют в фильтрации по полям узлов;
* участвуют в поиске, если поиск поддержан текущей визуализацией;
* участвуют в выделении и кросс-фильтрации при клике;
* не должны исчезать только из-за отсутствия строк в наборе «Связи».

----
h3. 9. Фильтрация данных.

h4. 9.1. Общий принцип.

Фильтрация должна учитывать роль набора данных:
* фильтры по полям набора «Узлы» применяются к узлам;
* фильтры по полям набора «Связи» применяются к связям;
* фильтр не должен применяться к другому набору данных только из-за совпадения {{name}} поля;
* каждая фильтрующая пилюля должна сохранять контекст набора данных.

h4. 9.2. Фильтрация по полям узлов.

Фильтрация по полям узлов ограничивает множество узлов-кандидатов.

Дальнейшее поведение зависит от настройки «С соседями»:
* если «С соседями» выключено, отображаются только узлы, прошедшие фильтр, и только связи между ними;
* если «С соседями» включено, к узлам, прошедшим фильтр, добавляются непосредственные соседи по связям с учётом настройки «Направление фильтрации».

h4. 9.3. Фильтрация по полям связей.

Фильтрация по полям связей ограничивает множество отображаемых связей.

Требования:
* фильтр по полям связей применяется к набору «Связи»;
* фильтр по связям не удаляет узлы автоматически;
* узлы, оставшиеся без связей после фильтрации связей, отображаются как изолированные;
* если одновременно применены фильтры по узлам и по связям, сначала определяется множество узлов-кандидатов по фильтрам узлов, затем множество допустимых связей по фильтрам связей, затем применяется режим охвата фильтрации.

h4. 9.4. Настройка «С соседями».

В панели настроек компонента «Граф» необходимо добавить переключатель:
* название: «С соседями»;
* тип: Toggle;
* значение по умолчанию: ВКЛ.

|| Значение || Поведение ||
| ВКЛ | После фильтрации по узлам отображаются узлы, прошедшие фильтр, их непосредственные соседи на один уровень и соответствующие связи |
| ВЫКЛ | После фильтрации по узлам отображаются только узлы, прошедшие фильтр, и только связи, у которых оба конца входят в итоговое множество отфильтрованных узлов |

h4. 9.5. Алгоритм режима «С соседями» - ВКЛ.

При наличии фильтра по полям узлов система должна:
# применить фильтр к набору «Узлы» и получить множество узлов-кандидатов;
# применить фильтры связей к набору «Связи», если такие фильтры есть;
# выбрать из набора «Связи» связи, инцидентные узлам-кандидатам, с учётом направления фильтрации;
# извлечь из выбранных связей все упомянутые значения узлов;
# сформировать итоговое множество отображаемых узлов: узлы-кандидаты + найденные соседи;
# получить свойства всех итоговых узлов из набора «Узлы»;
# отрисовать итоговые узлы и выбранные связи.

Пример:
* узлы: A (Премиум), B (Стандарт), C (Премиум), D (Стандарт);
* связи: A -> B, B -> C, B -> D;
* фильтр по узлам: {{category = "Премиум"}};
* узлы-кандидаты: A, C;
* режим «С соседями»: ВКЛ;
* направление: «Все направления».

Итог:
* отображаются узлы A, B, C;
* B отображается как сосед, хотя сам не прошёл фильтр по категории;
* отображаются связи A -> B и B -> C;
* D и связь B -> D не отображаются.

h4. 9.6. Алгоритм режима «С соседями» - ВЫКЛ.

При наличии фильтра по полям узлов система должна:
# применить фильтр к набору «Узлы» и получить множество узлов-кандидатов;
# применить фильтры связей к набору «Связи», если такие фильтры есть;
# оставить только связи, у которых {{Узел-источник}} и {{Узел-приёмник}} входят в множество узлов-кандидатов;
# отрисовать узлы-кандидаты;
# отрисовать только оставшиеся связи.

Узлы, прошедшие фильтр, но не имеющие связей с другими прошедшими фильтр узлами, отображаются как изолированные.

h4. 9.7. Настройка «Направление фильтрации».

В панели настроек компонента «Граф» необходимо добавить настройку:
* название: «Направление фильтрации»;
* тип: выпадающий список;
* значение по умолчанию: «Все направления».

|| Значение || Поведение в режиме «С соседями» - ВКЛ ||
| «Все направления» | К отфильтрованным узлам добавляются соседи, связанные с ними как входящими, так и исходящими связями |
| «Только исходящие» | К отфильтрованным узлам добавляются только узлы, которые являются {{Узел-приёмник}} в связях, где отфильтрованный узел является {{Узел-источник}} |
| «Только входящие» | К отфильтрованным узлам добавляются только узлы, которые являются {{Узел-источник}} в связях, где отфильтрованный узел является {{Узел-приёмник}} |

Если «С соседями» выключено, настройка «Направление фильтрации» должна быть недоступна или визуально отключена. В строгом режиме направление связи не влияет на состав итогового множества узлов, потому что отображаются только узлы, прошедшие фильтр.

h4. 9.8. Режим клика на узел.

В панели настроек компонента «Граф» необходимо добавить настройку:
* название: «Режим клика на узел»;
* тип: выпадающий список или переключатель;
* значение по умолчанию: «Выделение».

|| Значение || Поведение ||
| «Выделение» | При клике на узел выполняется локальное выделение: выбранный узел и его инцидентные связи подсвечиваются, остальные элементы приглушаются. Данные не перезапрашиваются, состав графа не меняется |
| «Кросс-фильтрация» | При клике на узел BI-ядро применяет фильтр по ключу выбранного узла. «Граф» перестраивается с учётом настроек «С соседями» и «Направление фильтрации». Соседние виджеты дашборда получают фильтр по выбранному узлу согласно существующей логике кросс-фильтрации |

В комбинации «Кросс-фильтрация» + «С соседями» ВЫКЛ клик по узлу должен приводить к отображению только выбранного узла как изолированной точки, если другие узлы не прошли фильтр. Это ожидаемое поведение строгого режима.

h4. 9.9. Пустой результат.

Если после применения фильтров итоговое множество узлов пустое:
* визуализация отображает пустое полотно;
* пользователю показывается сообщение: «Нет данных, соответствующих условиям фильтра»;
* ошибок и падения визуализации не возникает;
* после снятия фильтра граф восстанавливает отображение данных.

----
h3. 10. Интеграция с другими визуализациями и фильтрами дашборда.

h4. 10.1. Фильтры дашборда.

Фильтры дашборда должны применяться к «Графу» с учётом контекста набора данных:
* если фильтр связан с полем набора «Узлы», он применяется к набору «Узлы»;
* если фильтр связан с полем набора «Связи», он применяется к набору «Связи»;
* если поле с одинаковым {{name}} есть в обоих наборах, система должна использовать привязку фильтра к конкретному набору данных, а не выбирать поле по имени без контекста.

h4. 10.2. Кросс-фильтрация из «Графа».

При клике на узел в режиме «Кросс-фильтрация» «Граф» должен передавать в контекст дашборда фильтр по полю, размещённому на полке «Узлы».

Требования:
* соседние визуализации, работающие с тем же набором данных или с совместимым полем, фильтруются по существующим правилам дашборда;
* сам «Граф» перестраивается с учётом настроек «С соседями» и «Направление фильтрации»;
* если соседняя визуализация не имеет связи с полем выбранного узла, её поведение должно соответствовать текущей логике платформы для нерелевантных кросс-фильтров.

h4. 10.3. Кросс-фильтрация из других визуализаций.

Если фильтр приходит в «Граф» из другой визуализации:
* система должна определить, к какому набору данных «Графа» относится фильтруемое поле;
* если поле относится к набору «Узлы», применяется логика фильтрации узлов;
* если поле относится к набору «Связи», применяется логика фильтрации связей;
* если соответствие определить невозможно, фильтр не должен приводить к падению визуализации.

----
h3. 11. Обратная совместимость.

h4. 11.1. Существующие визуализации.

Все существующие визуализации, кроме «Графа», должны продолжить работать без изменений:
* одна визуализация продолжает использовать один набор данных;
* существующие настройки полок не меняются;
* существующие API-контракты для получения данных не должны быть нарушены;
* существующие дашборды не требуют ручной правки.

h4. 11.2. Существующие конфигурации «Графа».

Существующие однотабличные конфигурации «Графа» должны открываться после релиза.

Требования:
* старый «Граф» не должен ломаться из-за появления двухтабличного режима;
* если автоматическая миграция старого «Графа» в двухтабличный режим не реализуется, старая конфигурация должна продолжить работать в legacy-режиме;
* при создании нового «Графа» доступна новая двухтабличная настройка;
* если пользователь открывает старый «Граф» и меняет его на двухтабличную схему, система должна валидировать обязательные настройки новой схемы.

h4. 11.3. Метаданные наборов данных.

В рамках задачи не выполняется миграция метаданных полей:
* поле {{name}} не переопределяется;
* поле {{display_name}} не добавляется;
* существующие наборы данных не пересохраняются ради этой доработки;
* вычисляемые поля, фильтры и меры существующих визуализаций должны работать как раньше.

----
h3. 12. Нефункциональные требования.

h4. 12.1. Производительность.

Требования:
* первичная отрисовка графа на 1000 узлов и 2000 связей должна выполняться без видимых зависаний интерфейса;
* применение фильтра на сопоставимом объёме данных должно выполняться без длительной блокировки UI;
* расширение фильтра «С соседями» не должно формировать неограниченно большой payload без контроля объёма;
* для больших множеств узлов-кандидатов backend должен использовать безопасный для текущей архитектуры способ передачи условий в запрос связей;
* если требуется ввести технический лимит на количество узлов или связей, он должен быть явно согласован и отображён пользователю.

h4. 12.2. Отказоустойчивость.

Визуализация не должна падать при следующих сценариях:
* выбран один из двух наборов данных, но второй ещё не выбран;
* обязательные полки заполнены не полностью;
* в наборе «Связи» есть ссылка на отсутствующий узел;
* в данных есть пустые значения ключа узла;
* после фильтрации нет данных для отображения;
* один из запросов к данным завершился ошибкой.

При ошибке получения одного из наборов данных пользователь должен видеть понятное сообщение, а в логах должна быть диагностическая информация.

h4. 12.3. Ограничение области изменений.

Многодатасетный режим должен быть изолирован в рамках визуализации «Граф» настолько, насколько это возможно в текущей архитектуре. Доработка не должна менять базовое поведение всех визуализаций и не должна заставлять остальные компоненты переходить на новую модель настройки.

----

h3. 14. Предположения.

* Предполагается, что текущая модель пилюль или конфигурации визуализации может быть расширена так, чтобы каждая пилюля хранила контекст набора данных.
* Предполагается, что двухтабличный режим на первом этапе реализуется только для визуализации «Граф».
* Предполагается, что ключ узла в наборе «Узлы» и поля «Узел-источник»/«Узел-приёмник» в наборе «Связи» сравниваются по значениям после приведения типов.
* Предполагается, что вычисляемые поля остаются привязанными к конкретному набору данных и не выполняют кросс-датасетные выражения.

h3. 15. Открытые вопросы.

* Нужно подтвердить точные backend-объекты и команды, через которые сохраняется конфигурация «Графа» и запрашиваются данные визуализации.
* Нужно определить, допускаются ли на первом этапе разные источники данных для наборов «Узлы» и «Связи». Если нет, требуется UI-валидация совместимости источников.
* Нужно согласовать точный формат хранения двух ролей наборов данных в конфигурации визуализации.
* Нужно согласовать полный перечень типов свойств для полок «Свойства узлов» и «Свойства связей» с учётом возможностей текущего renderer «Графа».
* Нужно определить, сохраняется ли состояние свёрнутости секций «Узлы» и «Связи» между открытиями редактора или остаётся только локальным UI-состоянием.
* Нужно отдельно оценить направление с составными наборами данных / моделью данных, если команда решит рассматривать его как альтернативу или следующий этап.

h3. 16. Критерии приёмки (AC).

*AC.1* - В настройках «Графа» доступны две секции наборов данных:
* *Дано:* пользователь открывает настройки визуализации «Граф»;
* *Когда:* пользователь переходит к выбору структуры данных;
* *Тогда:* в левой панели отображается блок «Структура данных» с секциями «Узлы» и «Связи»;
* *И:* в каждой секции есть отдельный выпадающий список выбора набора данных;
* *И:* после выбора набора данных под ним отображается список полей выбранного набора.

*AC.2* - Списки полей можно сворачивать и разворачивать:
* *Дано:* в секциях «Узлы» и «Связи» выбраны наборы данных;
* *Когда:* пользователь сворачивает список полей секции «Узлы»;
* *Тогда:* поля набора «Узлы» скрываются, но заголовок секции и выбранный набор остаются видимыми;
* *И:* размещённые на полках пилюли не удаляются;
* *И:* пользователь может развернуть список обратно.

*AC.3* - Полки «Графа» соответствуют двухтабличной модели:
* *Дано:* пользователь настраивает новый «Граф»;
* *Когда:* пользователь смотрит список доступных полок;
* *Тогда:* отображаются полки «Узлы», «Связи», «Свойства узлов», «Свойства связей», «Фильтры»;
* *И:* полка «Узлы» принимает поле из набора «Узлы»;
* *И:* полка «Связи» принимает две пилюли из набора «Связи»;
* *И:* полки «Свойства узлов» и «Свойства связей» принимают поля только из соответствующих секций.

*AC.4* - Полка «Связи» валидирует типы пилюль:
* *Дано:* на полке «Связи» размещены две пилюли из набора «Связи»;
* *Когда:* пользователь открывает настройки пилюль;
* *Тогда:* для одной пилюли можно указать тип «Узел-источник», для другой - «Узел-приёмник»;
* *И:* если обе пилюли имеют одинаковый тип или один из типов не заполнен, визуализация показывает ошибку настройки и не строит некорректный граф.

*AC.5* - Поля с одинаковым {{name}} в разных наборах не конфликтуют:
* *Дано:* в наборе «Узлы» есть поле {{category}} и в наборе «Связи» есть поле {{category}};
* *Когда:* пользователь добавляет оба поля в настройки «Графа»;
* *Тогда:* система различает поля по контексту набора данных;
* *И:* фильтр или свойство, настроенное по {{category}} из «Узлов», не применяется к {{category}} из «Связей»;
* *И:* фильтр или свойство, настроенное по {{category}} из «Связей», не применяется к {{category}} из «Узлов».

*AC.6* - Доработка не требует {{display_name}} и миграции {{name}}:
* *Дано:* существующий набор данных содержит поля с текущими значениями {{name}};
* *Когда:* релиз с двухтабличным «Графом» установлен;
* *Тогда:* система не требует наличия поля {{display_name}};
* *И:* значения {{name}} не заменяются на UUID;
* *И:* существующие визуализации продолжают открываться без миграции метаданных полей.

*AC.7* - Первичная загрузка строит граф из двух наборов:
* *Дано:* выбран набор «Узлы» с 10 строками и набор «Связи» с 15 строками;
* *И:* на полке «Узлы» указано поле ключа узла;
* *И:* на полке «Связи» указаны поля «Узел-источник» и «Узел-приёмник»;
* *Когда:* пользователь открывает дашборд без фильтров;
* *Тогда:* визуализация отображает 10 узлов;
* *И:* отображает все корректные связи, у которых оба конца найдены среди узлов;
* *И:* дублирующиеся узлы не создаются;
* *И:* визуализация не падает.

*AC.8* - Фильтрация узлов в режиме «С соседями» ВЫКЛ:
* *Дано:* граф содержит узлы A, B, C и связи A -> B, B -> C, A -> C;
* *И:* режим «С соседями» выключен;
* *Когда:* пользователь применяет фильтр по набору «Узлы», под который попадают только A и B;
* *Тогда:* отображаются только узлы A и B;
* *И:* отображается только связь A -> B;
* *И:* связи B -> C и A -> C не отображаются;
* *И:* узел C не отображается.

*AC.9* - Фильтрация узлов в режиме «С соседями» ВКЛ:
* *Дано:* граф содержит узлы A (Премиум), B (Стандарт), C (Премиум), D (Стандарт);
* *И:* граф содержит связи A -> B, B -> C, B -> D;
* *И:* режим «С соседями» включён;
* *И:* направление фильтрации - «Все направления»;
* *Когда:* пользователь применяет фильтр по набору «Узлы»: {{category = "Премиум"}};
* *Тогда:* отображаются узлы A, B, C;
* *И:* B отображается как сосед;
* *И:* D не отображается;
* *И:* отображаются связи A -> B и B -> C;
* *И:* связь B -> D не отображается.

*AC.10* - Направление фильтрации учитывается в режиме «С соседями»:
* *Дано:* граф содержит связи A -> B и C -> A;
* *И:* пользователь фильтрует узел A;
* *Когда:* выбрано направление «Только исходящие»;
* *Тогда:* отображается A, сосед B и связь A -> B;
* *И:* C не добавляется как сосед по входящей связи;
* *Когда:* выбрано направление «Только входящие»;
* *Тогда:* отображается A, сосед C и связь C -> A;
* *И:* B не добавляется как сосед по исходящей связи.

*AC.11* - Фильтрация связей не удаляет узлы:
* *Дано:* граф содержит узлы A, B, C и связи A -> B с типом «Партнёрство», B -> C с типом «Аффилированность»;
* *Когда:* пользователь применяет фильтр по набору «Связи»: {{edge_type = "Партнёрство"}};
* *Тогда:* отображаются узлы A, B, C;
* *И:* отображается только связь A -> B;
* *И:* C остаётся изолированным узлом;
* *И:* визуализация не удаляет узлы только из-за фильтра по связям.

*AC.12* - Клик на узел в режиме «Выделение» не перезапрашивает данные:
* *Дано:* для «Графа» выбран режим клика «Выделение»;
* *Когда:* пользователь кликает на узел A;
* *Тогда:* узел A и его инцидентные связи визуально выделяются;
* *И:* состав графа не меняется;
* *И:* запрос данных не выполняется повторно;
* *И:* соседние виджеты дашборда не фильтруются этим кликом.

*AC.13* - Клик на узел в режиме «Кросс-фильтрация» фильтрует граф и соседние виджеты:
* *Дано:* для «Графа» выбран режим клика «Кросс-фильтрация»;
* *И:* режим «С соседями» включён;
* *Когда:* пользователь кликает на узел с ключом {{company_42}};
* *Тогда:* «Граф» отображает узел {{company_42}} и его непосредственных соседей с учётом направления фильтрации;
* *И:* соседние виджеты дашборда получают фильтр по полю, размещённому на полке «Узлы», если для них применима существующая логика кросс-фильтрации.

*AC.14* - Клик на узел в строгом режиме отображает только выбранный узел:
* *Дано:* для «Графа» выбран режим клика «Кросс-фильтрация»;
* *И:* режим «С соседями» выключен;
* *Когда:* пользователь кликает на узел A;
* *Тогда:* «Граф» отображает только узел A как изолированную точку, если другие узлы не прошли фильтр;
* *И:* это поведение не считается ошибкой.

*AC.15* - Неконсистентные связи не ломают визуализацию:
* *Дано:* набор «Связи» содержит строку, где {{Узел-источник = "X"}}, а узла {{X}} нет в наборе «Узлы»;
* *Когда:* визуализация загружается;
* *Тогда:* некорректная связь пропускается;
* *И:* корректные узлы и связи отрисовываются;
* *И:* в логах фиксируется диагностическая запись с отсутствующим значением узла;
* *И:* визуализация не падает.

*AC.16* - Изолированные узлы отображаются:
* *Дано:* набор «Узлы» содержит узел D, на который нет ссылок в наборе «Связи»;
* *Когда:* дашборд загружается без фильтров;
* *Тогда:* узел D отображается как изолированная точка;
* *Когда:* пользователь применяет фильтр по полю набора «Узлы», под который D попадает;
* *Тогда:* D остаётся в выборке и отображается.

*AC.17* - Пустой результат отображается без ошибки:
* *Дано:* настроенный «Граф» открыт на дашборде;
* *Когда:* пользователь применяет фильтр, после которого нет подходящих узлов;
* *Тогда:* визуализация показывает пустое полотно и сообщение «Нет данных, соответствующих условиям фильтра»;
* *И:* ошибок JavaScript и падения визуализации не возникает;
* *И:* после снятия фильтра граф снова отображает данные.

*AC.18* - Вычисляемое поле не может ссылаться сразу на два набора данных:
* *Дано:* пользователь создаёт или выбирает вычисляемое поле для использования в «Графе»;
* *Когда:* формула пытается одновременно обратиться к полям набора «Узлы» и набора «Связи»;
* *Тогда:* система не сохраняет такую формулу;
* *И:* пользователь видит сообщение о том, что вычисляемое поле должно относиться к одному набору данных;
* *И:* существующие вычисляемые поля в рамках одного набора данных продолжают работать.

*AC.19* - Существующие дашборды работают после релиза:
* *Дано:* существует дашборд, созданный до релиза, с визуализациями, использующими один набор данных;
* *Когда:* релиз с двухтабличным «Графом» установлен;
* *Тогда:* существующие визуализации открываются без ошибок;
* *И:* их конфигурации не требуют ручной правки;
* *И:* поле {{name}} продолжает использоваться в прежнем режиме;
* *И:* отсутствие {{display_name}} не влияет на работу дашборда.

*AC.20* - Старый однотабличный «Граф» не ломается:
* *Дано:* существует дашборд со старой конфигурацией визуализации «Граф» на одном наборе данных;
* *Когда:* пользователь открывает дашборд после релиза;
* *Тогда:* старый «Граф» открывается в совместимом режиме;
* *И:* данные отображаются по прежним правилам;
* *И:* пользователь не обязан переводить граф в двухтабличную схему.

*AC.21* - Производительность на базовом объёме данных:
* *Дано:* набор «Узлы» содержит 1000 строк, набор «Связи» содержит 2000 строк;
* *Когда:* пользователь открывает дашборд с «Графом»;
* *Тогда:* первичная отрисовка завершается без видимых зависаний интерфейса;
* *Когда:* пользователь применяет фильтр по узлам или связям;
* *Тогда:* граф перестраивается без длительной блокировки UI;
* *И:* в консоли браузера нет ошибок, связанных с падением визуализации.
