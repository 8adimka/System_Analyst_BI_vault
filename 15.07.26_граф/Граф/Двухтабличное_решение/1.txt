Вот обсуждаемая постановка - "h3. 1. Цель доработки.

Обеспечить корректную и предсказуемую работу визуализации «Граф» при фильтрации, агрегации и совместном использовании нескольких наборов данных.

Текущая архитектура визуализаций портала предполагает использование одного набора данных на одну визуализацию. Для визуализации «Граф» данный подход оказался неэффективным и приводит к следующим проблемам:

* усложнение структуры данных;
* дублирование информации;
* некорректная работа фильтрации;
* потеря узлов и связей при фильтрации;
* невозможность корректно реализовать классическую графовую модель;
* невозможность полноценно использовать независимые сущности «узлы» и «связи».

Цель данной доработки:

* перевести визуализацию «Граф» на классическую двухтабличную модель построения графов;
* обеспечить поддержку нескольких наборов данных в рамках одной визуализации;
* сохранить полную обратную совместимость со всеми существующими визуализациями;
* обеспечить корректную интеграцию с визуализациями «Таблица» и «Сводная таблица»;
* обеспечить корректную работу всех сценариев фильтрации.

----
h3. 2. Концепция нового решения.

В рамках данной доработки визуализация «Граф» должна перейти на классическую графовую архитектуру:
* отдельный набор данных — «Узлы графа»;
* отдельный набор данных — «Связи графа».

Визуализация должна уметь одновременно использовать несколько наборов данных.

----
h4. 2.1. Набор данных «Узлы графа».

Набор данных содержит:
* все узлы графа;
* свойства узлов;
* параметры отображения узлов.

Каждая строка набора данных соответствует одному узлу.

----
h4. 2.2. Набор данных «Связи графа».

Набор данных содержит:
* связи между узлами;
* свойства связей;
* параметры отображения связей.

Каждая строка набора данных соответствует одной связи между двумя узлами.

----
h3. 3. Основная архитектурная проблема.

В текущей реализации все визуализации используют ссылку на поле набора данных через его наименование ({{name}}).

На текущий момент:

* {{name}} уникально только в рамках одного набора данных;
* {{name}} не гарантирует уникальность между несколькими наборами данных;
* при использовании нескольких наборов данных могут возникать конфликты ссылок на поля.

Это делает корректную работу визуализаций затруднительной и нестабильной при использовании более одного набора данных одновременно.

Для реализации новой архитектуры «Графа» требуется устранить данное ограничение.

----
h3. 4. Требуемая архитектурная доработка платформы.

h4. 4.1. Добавление нового поля {{display_name}}.

Необходимо добавить новое поле в метаданные Наборов данных:
* {{display_name}} - уникальное наименование поля, в рамках датасета.
* например, если пользователь попытается создать два поля с {{display_name = "city"}} в одном датасете — система должна это запрещать валидацией. 

Назначение поля:
* хранение отображаемого имени поля в Наборе данных - т.е. замена поля {{name}}.

----
h4. 4.2. Изменение назначения поля {{name}}.

После реализации доработки поле {{name}} должно использоваться как:
* системный уникальный идентификатор поля в Наборе данных.

Требования:
* {{name}} должен быть глобально уникальным;
* для новых наборов данных данное поле автоматически заполняется UUID;
* значение {{name}} не должно использоваться в UI или отображаться пользователю, вместо него в интерфейсе и редакторе выражений должно отображаться {{display_name}}.

Пример:

|| Поле || Значение ||
| {{name}} | {{2f3d7a9f-9a5b-4a3c-84db-61e1f9df01a3}} |
| {{display_name}} | {{client_name}} |

----
h4. 4.3. Миграция существующих данных.

Необходимо выполнить миграцию.

Алгоритм миграции:
# добавить поле {{display_name}};
# для всех существующих Наборов данных:
## скопировать текущее значение {{name}} в {{display_name}};
## текущее значение {{name}} оставить без изменений;
# для всех новых полей:
## в {{name}} автоматически записывать UUID при создании поля;
## в {{display_name}} записывать отображаемое имя.

----
h4. 4.4. Обратная совместимость.

Необходимо полностью сохранить работоспособность всех существующих визуализаций.

Требования:
* все существующие визуализации продолжают использовать {{name}} как ссылочный идентификатор поля;
* существующие Наборы данных продолжают работать без изменений;
* существующие дашборды не требуют миграции конфигурации;
* существующие API-контракты не должны быть нарушены;
* сериализация/десериализация конфигураций должна оставаться совместимой.

----
h4. 4.5. Изменение отображения имени поля в UI.

Во всех пользовательских интерфейсах платформы необходимо заменить отображение:
* с {{name}}
* на {{display_name}}.

Это касается:
* конструктора Наборов данных;
* конструктора визуализаций;
* отображения полей Наборов данных в редакторе кода для Вычисляемых полей и Мер;
* редактора фильтров;
* настройки агрегаций;
* настройки сортировок;
* настройки drill-down;
* настройки tooltip;
* API получения метаданных;
* любых селекторов полей;
* любых форм настройки визуализаций;
* и т.д.

Пользователь не должен видеть UUID или содержимое поля {{name}} в интерфейсе - используется только для корректных уликальных ссылок на поля Наборов данных.

----
h4. 4.6. Механизм разрешения ссылок на поля (паттерн Symbolic Reference Resolution).

Все ссылки на поля Наборов данных в конфигурациях, фильтрах, выражениях и API используют единый механизм разрешения ссылок.

*Принцип работы:*
* Пользователь всегда работает с {{display_name}} как с символическим именем поля.
* Система при сохранении любой ссылки на поле резолвит {{display_name}} → {{name}} и сохраняет {{name}} как идентификатор.
* При открытии конфигурации, редактора выражений или любого UI-компонента — выполняется обратная трансляция {{name}} → {{display_name}} для отображения пользователю.
* {{display_name}} *никогда не сохраняется* в конфигурациях и выражениях как ссылочный идентификатор.

*Единая логика для всех Наборов данных:*
Механизм работает одинаково для всех Наборов данных — как старых, так и новых:
* Для новых Наборов данных: {{name = "2f3d7a9f-..."}}, {{display_name = "city"}} → пользователь видит {{"city"}}, в конфигурации хранится {{UUID}}.
* Для существующих Наборов данных: {{name = "city"}}, {{display_name = "city"}} → трансляция тривиальна, результат идентичен. Логика та же самая — частный случай совпадения значений.

*Требование к уникальности:*
{{display_name}} должен быть уникальным в рамках одного Набора данных. При попытке создать два поля с одинаковым {{display_name}} в одном Наборе данных система должна возвращать ошибку валидации.

Если связь содержит ссылку на несуществующий узел:

* в логах должна фиксироваться ошибка валидации;
* связь должна быть пропущена;
* визуализация должна продолжить работу.

h4. 6.4. Изолированные узлы.

Визуализация должна поддерживать узлы без связей.

Изолированные узлы:

* должны отображаться;
* должны участвовать в фильтрации;
* должны участвовать в поиске;
* должны участвовать в выделении.

h3. 7. Фильтрация данных.

h4. 7.1. Основная цель доработки.

Основная цель данной переработки — обеспечить корректную фильтрацию данных для построения визуализации «Граф».

Текущая проблема:

* при использовании одной плоской таблицы фильтрация удаляет строки содержащие узлы и связи;
* при наличии строки с узлом-источником, связью, но отсутствием строки, содержащей узел-приёмник - визуализация не может корректно построить данную связь;
** граф становится неполным;
** визуализация теряет консистентность.

Новая архитектура должна устранить данную проблему.

----
h4. 7.2. Фильтрация Набора данных «Узлы».

Фильтрация по полям узлов должна:

* применяться только к Набору данных «Узлы»;
* ограничивать набор отображаемых узлов.

После фильтрации узлов:

* визуализация должна автоматически попытаться построить связи;
** при наличие связи, содержащей отсутствующие узлы, такая связь должна быть пропущена и не отрисовываться.
* должны остаться только связи между отображаемыми узлами.

----
h4. 7.3. Фильтрация Набора данных «Связи».

Фильтрация по полям связей должна:

* применяться только к Набору данных «Связи»;
* скрывать только связи;
* не удалять узлы автоматически;
* при наличие узлов без связей - они отображаются как изолированные узлы в штатном порядке.

----
h4. 7.4. Режимы интерактивной фильтрации визуализации «Граф».

h5. 7.4.1. Проблема и мотивация.

При применении фильтра к Набору данных «Узлы» (раздел 7.2) базовая логика фильтрации удаляет из отображения все узлы, не прошедшие фильтр. Это поведение является корректным для большинства аналитических задач, однако для графовой визуализации оно разрушает контекст: узел, оставшийся после фильтрации, теряет все свои связи, поскольку все соседние узлы были удалены.

Целевое поведение при клике на узел или применении фильтра к графу — отображение не только *самого отфильтрованного узла, но и всех узлов, с которыми он непосредственно связан*, вместе с соответствующими рёбрами.

Для поддержки различных аналитических сценариев необходимо предоставить пользователю явный выбор режима фильтрации через настройки визуализации.

h5. 7.4.2. Настройка: Режим охвата фильтрации («С соседями»).

В панели настроек компонента «Граф» добавляется переключатель:

«С соседями» (Тумблер (Toggle), ВКЛ - по умолчанию (1) / ВЫКЛ (0)):

|| Значение || Поведение ||

| «С соседями» - ВКЛ (по умолчанию) | После фильтрации отображаются отфильтрованные узлы и все их непосредственные соседи (+1 уровень), а также все рёбра между ними. |
| «С соседями» - ВЫКЛ | После фильтрации отображаются только узлы, прошедшие фильтр, и только рёбра строго между ними. Узлы, не прошедшие фильтр, скрываются полностью, даже если они связаны с отфильтрованными узлами. |

Режим «С соседями» — ВКЛ, детальное поведение:

* Когда пользователь применяет фильтр (например, node_category = "Премиум") или кликает на конкретный узел при включённом режиме кросс-фильтрации, для корректной отрисовки Графа BI-ядро выполняет запрос в три шага:

# Определяет множество узлов-кандидатов — тех, что прошли фильтр.
# Из Набора данных «Связи» выбирает все рёбра, у которых хотя бы один конец (source_node_id {{ИЛИ}} target_node_id) принадлежит множеству узлов-кандидатов.
# Из этих рёбер извлекает все упомянутые node_id — они становятся итоговым множеством отображаемых узлов, даже если сами не прошли исходный фильтр.

Пример: Узлы A (Премиум), B (Стандарт), C (Премиум), D (Стандарт). Рёбра: A→B, B→C, B→D.
Фильтр category = "Премиум" → кандидаты: {{A, C}}. Рёбра, инцидентные {{A, C}}: т.к. A→B, B→C. Итоговые узлы: {{A, B, C}}. Итоговые рёбра: A→B, B→C. Узел B отображается как сосед, несмотря на то что категории «Премиум» не имеет.

Режим «С соседями» — ВЫКЛ, детальное поведение:

* BI-ядро возвращает только узлы, прошедшие фильтр, и только рёбра, у которых оба конца входят в множество отфильтрованных узлов. Узлы, прошедшие фильтр, но не имеющие связей с другими отфильтрованными узлами, отображаются как изолированные.

Тот же пример, строгий режим: Итоговые узлы: {{A, C}}. Ребро A→B — пропускается (B не прошёл). Ребро B→C — пропускается (B не прошёл). Итог: A и C отображаются как изолированные точки без связей между собой (прямой связи A→C нет).

h5. 7.4.3. Настройка: Режим «Направление фильтрации».

В панели настроек компонента «Граф» добавляется переключатель:

«Направление фильтрации» (Выпадающий список (Dropdown), 3 значения):

|| Значение || Поведение ||

| «Все направления» (по умолчанию) | В режиме «С соседями»: фильтр применяется к узлам независимо от их роли в ребре. Узел попадает в результат, если он является источником или приёмником хотя бы одного ребра, связанного с отфильтрованным узлом. |

| «Только исходящие» | В режиме «С соседями»: к отфильтрованным узлам добавляются только узлы, являющиеся target_node_id в рёбрах, где отфильтрованный узел — {{source_node_id}}. |
| «Только входящие» | В режиме «С соседями»: к отфильтрованным узлам добавляются только узлы, являющиеся source_node_id в рёбрах, где отфильтрованный узел — {{target_node_id}}. |

Примечание: Настройка «Направление фильтрации» влияет на состав узлов, добавляемых к отфильтрованным узлам, в режиме «С соседями» - ВКЛ. В режиме «С соседями» - ВЫКЛ (строгий режим) настройка «Направление фильтрации» остаётся недоступна ({{disabled}}).
В строгом режиме отображаются только рёбра между узлами, оба конца которых прошли фильтр — направление ребра не влияет на состав итогового множества узлов.

h5. 7.4.4. Настройка: Режим взаимодействия при клике.

В панели настроек компонента «Граф» добавляется переключатель:

«Режим клика на узел»:

|| Значение || Поведение ||

| «Выделение» (по умолчанию) | При клике на узел активируется локальное выделение средствами ECharts: выбранный узел и его инцидентные рёбра подсвечиваются, остальные узлы становятся полупрозрачными. Данные не перезапрашиваются, состав графа не меняется. |
| «Кросс-фильтрация» | При клике на узел BI-ядро применяет жёсткий фильтр к Набору данных «Узлы» по {{node_id}} кликнутого узла. Граф перерисовывается с учётом текущих настроек режимов «С соседями» и «Направления фильтрации», соседние виджеты дашборда фильтруются по выбранному {{node_id}}. |

*AC.1* — Визуализация строится на двух независимых Наборах данных.
* *Дано*: настроена визуализация «Граф» с Набором данных Узлов (10 строк) и Набор данных Связей (15 строк).

*AC.2.1* — Фильтрация узлов: «С соседями» — ВЫКЛ.
* *Дано:* граф с узлами A, B, C и связями A→B, B→C, A→C; режим «С соседями» — ВЫКЛ.
* *Когда:* пользователь применяет фильтр по Набору данных узлов, под условие попадают только A и B.
* *Тогда:* отображаются только узлы A и B; отображается только связь A→B (оба конца прошли фильтр); связи B→C и A→C не отрисовываются; узел C не отображается; ошибок валидации не возникает.

*AC.2.2* — Фильтрация узлов: «С соседями» — ВКЛ.
* *Дано:* граф с узлами A (Премиум), B (Стандарт), C (Премиум), D (Стандарт); рёбра связей: A→B, B→C, B→D; режим «С соседями» — ВКЛ (по умолчанию).
* *Когда:* пользователь применяет фильтр node_category = "Премиум".
* *Тогда:* отображаются узлы A, B, C (A и C — проходят фильтрацию, B — как сосед); узел D не отображается (не прошёл фильтр и не соприкасается с узлом прошедшим фильтрацию); отображаются рёбра A→B и B→C; Узел D и ребро B→D — не отображаются, так как D не входит в итоговое множество узлов.

*AC.3* — Фильтрация связей не удаляет узлы.
* *Дано*: граф с узлами A, B, C и связями A→B (тип: «Партнёрство»), B→C (тип: «Аффилированность»).
* *Когда*: пользователь применяет фильтр по Набору данных связей: `edge_type = "Партнёрство"`.
* *Тогда*: отображаются все три узла A, B, C; отображается только связь A→B; B и C становятся изолированными узлами и продолжают отображаться.

*AC.4* — Обработка битых связей не ломает визуализацию.

Существующая маршрутизация к ClickHouse.
В текущей архитектуре уже реализована цепочка маршрутизации к ClickHouse:

Пользователь
  → Набор данных (Dataset)
      → Источник данных (Data Source)
          → host + port + database → ClickHouse

Источник данных (Data Source) — это запись в PostgreSQL, содержащая реквизиты подключения к конкретному инстансу ClickHouse. При открытии дашборда система не ищет инстанс ClickHouse по абстрактному идентификатору: она идёт по цепочке объектов, и источник уже содержит все необходимые реквизиты. Маршрутизация встроена в метаданные через саму структуру объектов.

Существующая цепочка «дашборд → набор → источник → ClickHouse» остаётся рабочей, но долна быть адаптирована под использование двух наборов данных в одной визуализации или, возможно, подходящим решением для нас будет дать возможность обращаться из одного "Набора данных" к другому.
