h3. 1. Контекст и проблематика.

Визуализация «Граф» в текущей реализации ограничена одним набором данных на визуализацию. Графовая модель естественно описывается двумя сущностями — узлами и связями, поэтому однотабличная схема порождает системные проблемы:

* свойства узлов и связей денормализуются в одну строковую структуру;
* в наборе данных появляются дублирующиеся значения;
* строковая фильтрация может удалять строки, необходимые для отрисовки связанных узлов;
* изолированные узлы сложно поддерживать корректно;
* настройка неочевидна: одна таблица одновременно выполняет роль таблицы узлов и таблицы связей.

При этом текущий механизм получения данных строится вокруг связи визуализации с набором данных: конфигурация панели хранит выбранный набор данных и поля на полках, а получение данных выполняется по выбранному набору данных. Каждый набор данных связан с источником данных, поэтому для двухтабличного «Графа» нужно расширить конфигурацию визуализации так, чтобы она могла хранить два выбранных набора данных и однозначно относить каждую пилюлю к одному из них.

*Цель доработки*: перевести визуализацию «Граф» на классическую двухтабличную модель — отдельный набор данных для узлов и отдельный набор данных для связей — без изменения базового поведения остальных визуализаций.

----
h3. 2. Цель задачи.

# Перевести «Граф» на модель: *набор «Узлы»* + *набор «Связи»*.
# Реализовать выбор и использование двух наборов данных в одной визуализации «Граф».
# Обеспечить хранение конфигурации, в которой каждая пилюля однозначно связана с конкретным набором данных, ролью набора и ролью пилюли в графе.
# Сохранить существующий принцип связи визуализаций с данными отдельно для набора «Узлы» и набора «Связи».
# Обеспечить корректную фильтрацию узлов и связей, включая режимы «С соседями» и «Направление фильтрации».

----
h3. 3. Рамки задачи.

В рамках задачи реализуется:
* выбор двух наборов данных для «Графа» с ролями:
** {{Узлы}} — перечень узлов и свойства узлов;
** {{Связи}} — пары связанных узлов и свойства связей;
* доработка левой панели настройки «Графа» под две секции наборов данных;
* доработка полок «Графа» под двухтабличную модель;
* хранение ролей наборов данных и привязки пилюль в конфигурации визуализации;
* получение данных из двух наборов данных для одной визуализации;
* построение графа из двух независимых результирующих выборок;
* фильтрация по полям узлов и по полям связей с разной логикой влияния на граф;
* поддержка интерактивного выделения и кросс-фильтрации при клике на узел;
* обработка неконсистентных данных без падения визуализации.

*Не входит в рамки:*
* составные наборы данных и модель «один набор — несколько связанных таблиц» — это отдельное направление, требующее отдельной оценки;
* переработка общего механизма вычисляемых полей и перенос вычисляемых выражений в backend-справочник. В рамках этой задачи нельзя ухудшать текущую безопасность, но полноценное изменение хранения вычисляемых выражений должно рассматриваться отдельной технической задачей.

h3. 4. Архитектурные тезисы.

h4. 4.1. Ссылки на поля.

* {{name}} поля остаётся системным именем поля в рамках набора данных.
* Уникальность {{name}} требуется в рамках одного набора данных; глобальная уникальность между наборами не требуется.
* {{name}} может использоваться как ссылка на поле только вместе с контекстом набора данных. Для идентификации конкретного поля набора данных используется пара {{datasetId}} + {{name}} (поле уникально по name в рамках одного датасета). Отдельно существует технический идентификатор пилюли (id вида FieldName_randomSuffix) — это идентификатор конкретного экземпляра размещения поля на полке в конфигурации визуализации; одно и то же поле датасета может быть размещено несколько раз с разными идентификаторами пилюли. При двухтабличном режиме поле однозначно идентифицируется тройкой: 
{{datasetId}} + {{name}} + {{id пилюли}}, где datasetId определяет принадлежность к роли «Узлы» или «Связи».
* {{name}} не является значением ключа узла. Ключ узла — это значение в строках того поля, которое пользователь разместил на полке «Узлы».
* Каждая пилюля хранит контекст выбранного набора данных. В текущей структуре конфигурации у поля уже присутствует {{datasetId}}; для двухтабличного режима необходимо сохранять этот контекст для всех полок и не терять его при сохранении, открытии и изменении визуализации.
* Если в наборах «Узлы» и «Связи» есть поля с одинаковым {{name}}, система различает их по идентификатору набора данных, а не по одному {{name}}.
* Если на полках могут оказаться одноимённые поля из разных секций, UI визуально показывает контекст: «Узлы» или «Связи».

h4. 4.2. Связь наборов данных с источниками.

Существующая цепочка:
{code}
Пользователь
  -> Дашборд / визуализация
      -> Набор данных
          -> Источник данных
              -> host + port + database
{code}

Для двухтабличного «Графа» эта цепочка применяется отдельно к каждому выбранному набору данных:
* если оба набора используют один источник данных — запросы выполняются к одному источнику;
* если наборы используют разные источники данных — система выполняет независимое получение данных и сопоставляет результаты на уровне логики «Графа», без требования SQL-join между источниками.

Если на первом этапе разные источники данных не поддерживаются технически, это ограничение должно быть явно реализовано в UI и валидации. Пользователь должен увидеть понятное сообщение о несовместимости выбранных наборов данных.

h4. 4.3. Генерация SQL-запросов.

* Для каждого набора данных запрос формируется независимо по существующему принципу: исходный SQL набора не изменяется, BI-ядро строит внешний запрос поверх него.
* Фильтры и поля с полок применяются к тому набору данных, из которого взята пилюля.
* В запрос к набору «Узлы» не должны попадать поля, фильтры и вычисления из набора «Связи».
* В запрос к набору «Связи» не должны попадать поля, фильтры и вычисления из набора «Узлы».
* Результатом для логики «Графа» являются две разделённые выборки: узлы и связи. Разделение может выполняться на стороне frontend/data-layer, если данные получаются двумя независимыми запросами.

h3. 5. Модель данных визуализации «Граф».

h4. 5.1. Общая модель.

|| Роль набора данных || Назначение ||
| {{Узлы}} | Все узлы графа, свойства узлов и параметры отображения узлов |
| {{Связи}} | Связи между узлами, свойства связей и параметры отображения связей |

В итоговой выборке набора «Узлы» одна строка должна соответствовать одному отображаемому узлу и его свойствам. Если исходные данные содержат несколько строк с одинаковым ключом узла, они должны быть агрегированы или дедуплицированы по правилам раздела 8.2.

В итоговой выборке набора «Связи» одна строка соответствует одной связи между двумя узлами и свойствам этой связи.

h4. 5.2. Набор данных «Узлы».

Обязательное поле — ключ узла (размещается на полке «Узлы»).

Требования к ключу:
* ключ задаётся выбранным полем набора «Узлы»; в конфигурации поле идентифицируется через {{datasetId}} и {{name}} / существующий технический идентификатор поля;
* значением ключа являются данные в строках выбранного поля, а не само {{name}} поля;
* значение ключа должно быть уникальным в итоговой выборке после агрегаций и фильтров;
* используется для сопоставления с полями «Узел-источник» и «Узел-приёмник» из набора «Связи»;
* может быть строковым или числовым;
* пустые значения не участвуют в построении графа.

Типы свойств узлов:

|| Тип свойства || Назначение ||
| {{Радиус}} | Размер узла |
| {{Цвет}} | Цвет узла |
| {{Значение}} | Числовое значение / показатель для tooltip |
| {{Группа}} | Группировка, легенда |
| {{Tooltip}} | Подсказка при наведении |

h4. 5.3. Набор данных «Связи».

Обязательные поля — {{Узел-источник}} и {{Узел-приёмник}} (размещаются на полке «Связи»).

Требования:
* пара значений {{Узел-источник}} + {{Узел-приёмник}} описывает одну связь;
* оба значения сопоставляются со значениями ключа узла из набора «Узлы»;
* пустое значение в одном из концов связи делает связь некорректной для отрисовки;
* связь с отсутствующим узлом пропускается без ошибки;
* дополнительные поля набора «Связи» могут использоваться как свойства связей.

Типы свойств связей:

|| Тип свойства || Назначение ||
| {{Тип связи}} | Категория связи, легенда, tooltip |
| {{Цвет}} | Цвет линии связи |
| {{Значение}} | Вес связи / показатель для tooltip |
| {{Толщина}} | Толщина линии связи |
| {{Tooltip}} | Подсказка при наведении на связь |

h4. 5.4. Идентификатор связи.

Отдельное поле {{edge_id}} не является обязательным, если механизм рендера может стабильно формировать технический идентификатор связи из контекста строки набора «Связи».

При необходимости явного идентификатора:
* добавляется тип свойства {{Идентификатор связи}};
* или идентификатор формируется на стороне backend/frontend из доступного контекста строки.

Технический идентификатор не должен требовать изменения пользовательских наборов данных, если стабильность можно обеспечить без отдельного пользовательского поля.

h3. 6. Интерфейс настройки визуализации «Граф».

h4. 6.1. Левая панель «Структура данных».

Левая боковая панель содержит блок «Структура данных» с двумя секциями: «Узлы» и «Связи».

h4. 6.2. Секция «Узлы».

# Заголовок секции «Узлы».
# Выпадающий список выбора набора данных с узлами.
# Список полей выбранного набора данных. Поля перетаскиваются на полки, работающие со свойствами узлов и фильтрами; ключ узла размещается на полке «Узлы».

h4. 6.3. Секция «Связи».

# Заголовок секции «Связи».
# Выпадающий список выбора набора данных со связями.
# Список полей выбранного набора данных. Поля перетаскиваются на полки «Связи», «Свойства связей», «Фильтры»; поля из секции «Связи» не используются как ключ узла.

h4. 6.4. Сворачивание секций (_аккордеон_).

* Каждая секция сворачивается независимо; допускается одновременное развёртывание и сворачивание обоих списков.
* При сворачивании остаются видимыми заголовок секции и выпадающий список.
* Сворачивание не удаляет уже размещённые пилюли.
* Состояние свёрнутости — UI-состояние, не обязательно хранить на сервере.

h4. 6.5. Полки визуализации «Граф».

|| Полка || Источник пилюль || Назначение ||
| {{Узлы}} | Только набор «Узлы» | Одна пилюля: поле ключа/наименования узла |
| {{Связи}} | Только набор «Связи» | Две пилюли: {{Узел-источник}} и {{Узел-приёмник}} |
| {{Свойства узлов}} | Только набор «Узлы» | Поля отображения узлов |
| {{Свойства связей}} | Только набор «Связи» | Поля отображения связей |
| {{Фильтры}} | Набор «Узлы» и набор «Связи» | Поля для фильтрации графа с сохранением контекста набора данных |

Переименование полок в новом двухтабличном режиме:
* «Узел» → «Узлы»;
* «Связь» → «Связи»;
* «Значения» → «Свойства узлов»;
* «Категории» → «Свойства связей»;
* «Фильтры» — без изменений.

h4. 6.6. Настройки пилюль.

*Полка «Связи»*: для каждой пилюли обязателен тип — {{Узел-источник}} или {{Узел-приёмник}}. На полке должны быть ровно две пилюли с разными типами. При одинаковых типах или отсутствии типа — ошибка настройки, граф не строится.

*Полка «Свойства узлов»*: для пилюль доступны типы свойств узлов, поддержанные текущим renderer «Графа». Минимально должны быть поддержаны типы {{Радиус}}, {{Цвет}}, {{Значение}}, если они уже используются текущей визуализацией.

*Полка «Свойства связей»*: для пилюль доступны типы свойств связей, поддержанные текущим renderer «Графа». Минимально должны быть поддержаны типы {{Тип связи}}, {{Цвет}}, {{Значение}}, если они уже используются текущей визуализацией.

Типы свойств на полках «Свойства узлов» и «Свойства связей» не являются обязательными для построения графа. Обязательными являются только полка «Узлы» и две пилюли на полке «Связи».

h4. 6.7. Валидация настройки.

Двухтабличный «Граф» считается корректно настроенным, если:
* выбраны оба набора данных — «Узлы» и «Связи»;
* на полке «Узлы» — одна пилюля из набора «Узлы»;
* на полке «Связи» — две пилюли из набора «Связи» с разными типами;
* на полке «Свойства узлов» нет пилюль из набора «Связи»;
* на полке «Свойства связей» нет пилюль из набора «Узлы»;
* каждая пилюля хранит контекст набора данных;
* при совпадении {{name}} в двух наборах данных пилюли не смешиваются и не перезаписывают друг друга.

При некорректной настройке — понятное сообщение в области настройки или на полотне. Падение компонента недопустимо.

h3. 7. Конфигурация, backend и API.

h4. 7.1. Хранение конфигурации.

Конфигурация «Графа» хранит:
* идентификатор набора данных с ролью {{Узлы}};
* идентификатор набора данных с ролью {{Связи}};
* маппинг ключа узла, узла-источника, узла-приёмника;
* маппинг свойств узлов и свойств связей;
* маппинг фильтров с привязкой к конкретному набору данных;
* режимы фильтрации и клика (см. раздел 9).

При доработке необходимо ориентироваться на текущую структуру конфигурации «Графа», где поля хранятся в массивах полок. Для двухтабличного режима требуется не заменить эту модель полностью, а расширить её так, чтобы:
* выбранные наборы данных сохранялись отдельно по ролям {{Узлы}} и {{Связи}};
* каждая пилюля на полках сохраняла {{datasetId}} и роль набора данных;
* одноимённые {{name}} из разных наборов данных не конфликтовали;
* при наличии {{axesDefault}} или аналогичных копий настроек они не противоречили актуальным полкам;
* старые однотабличные конфигурации читались без обязательной миграции.

Концептуальный пример структуры конфигурации:
{code:json}
{
  "graph_data_roles": {
    "nodes": {
      "datasetId": 101
    },
    "edges": {
      "datasetId": 205
    }
  },
  "axes": [
    {
      "type": "node",
      "fields": [
        {
          "datasetId": 101,
          "datasetRole": "nodes",
          "name": "company_name",
          "id": "company_name_generated_pill_id",
          "valueType": "value"
        }
      ]
    },
    {
      "type": "linkage",
      "fields": [
        {
          "datasetId": 205,
          "datasetRole": "edges",
          "name": "source_company",
          "id": "source_company_generated_pill_id",
          "valueType": "source"
        },
        {
          "datasetId": 205,
          "datasetRole": "edges",
          "name": "target_company",
          "id": "target_company_generated_pill_id",
          "valueType": "target"
        }
      ]
    }
  ],
  "graph_filtering": {
    "include_neighbors": true,
    "direction": "all",
    "click_mode": "selection"
  }
}
{code}

_Пример фиксирует семантику и ожидаемый состав данных, не обязательный формат API-контракта._

h4. 7.2. API и backend.

Затрагиваются текущие механизмы:
* сохранение и чтение конфигурации отчёта/визуализации через фактический объект конфигурации отчётов: {{reports}} / {{get}} / {{update}} или текущий эквивалент;
* получение метаданных выбранных наборов данных через {{datasets}} / {{get.full}} и {{list}} или текущий эквивалент;
* получение данных по существующему механизму {{/v1/api/recordsets/{datasetId}}} для каждого набора данных.

Требования:
* перед сохранением изменённой конфигурации читать актуальное состояние через {{get}}/{{list}} по действующему правилу работы с {{update}};
* payload сохранения конфигурации передаёт оба набора данных с ролями;
* payload получения данных для каждого набора данных содержит только поля, фильтры, группировки, сортировки, {{where}} и {{having}}, относящиеся к этому набору данных;
* если используется существующий endpoint {{recordsets/{datasetId}}}, frontend выполняет отдельный запрос для набора «Узлы» и отдельный запрос для набора «Связи»;
* если команда разработки решит реализовать единый backend-запрос для двухтабличного «Графа», его контракт должен быть согласован отдельно и не должен менять контракт {{recordsets/{datasetId}}} для остальных визуализаций;
* API-контракты остальных визуализаций не нарушаются.

h4. 7.3. Получение данных.

Базовый вариант реализации:
* frontend/data-layer формирует запрос к +{{/v1/api/recordsets/{nodesDatasetId}}}+ для набора «Узлы»;
* frontend/data-layer формирует запрос к +{{/v1/api/recordsets/{edgesDatasetId}}}+ для набора «Связи»;
* каждый запрос использует существующую структуру payload: {{group}}, {{order}}, {{select}}, {{where}}, {{having}}, {{series}}, {{limit}} и другие поддержанные поля;
* данные, полученные по первому запросу, интерпретируются как коллекция узлов;
* данные, полученные по второму запросу, интерпретируются как коллекция связей;
* сопоставление узлов и связей выполняется логикой «Графа» по значениям ключевых полей.

Для режима «С соседями» допускается дополнительный запрос к набору «Узлы» для получения свойств соседних узлов, если выбранная реализация сначала получает только узлы-кандидаты и не располагает строками соседей. 
При необходимости дополнительного запроса к набору «Узлы» за свойствами соседних узлов (режим «С соседями» ВКЛ) этот запрос формирует where-условие по полю ключа узла с множеством значений (аналог IN). Необходимо подтвердить, что существующий endpoint recordsets/{datasetId} поддерживает передачу нескольких значений в поле values одного where-элемента. Если поддержка отсутствует — это блокирует реализацию режима «С соседями» с дополнительным запросом и должна быть решена либо расширением API, либо альтернативным подходом (загрузка всего набора «Узлы» без фильтра при первичной загрузке и клиентская фильтрация).

Фактический backend-ответ не обязан иметь оболочку {{nodes}} / {{edges}}, если используются два существующих запроса {{recordsets/{datasetId}}}. Логическое разделение на узлы и связи обеспечивается тем, что каждый ответ связан с ролью набора данных, по которой был выполнен запрос.

h4. 7.4. Вычисляемые поля и меры.

В рамках этой задачи вычисляемые поля и меры остаются в контексте конкретного набора данных.

Требования:
* вычисляемое поле из набора «Узлы» ссылается только на поля набора «Узлы»;
* вычисляемое поле из набора «Связи» ссылается только на поля набора «Связи»;
* кросс-датасетные формулы в рамках задачи не поддерживаются;
* двухтабличный «Граф» не должен создавать новые frontend-формулы, которые одновременно обращаются к полям двух наборов данных;
* если в существующем payload используется {{calc}}, он должен передаваться только в запрос того набора данных, к которому относится соответствующая пилюля;
* полноценный перенос вычисляемых выражений из frontend payload в backend-справочник не входит в рамки этой задачи и должен быть оформлен отдельной задачей, если команда принимает это направление.

----
h3. 8. Логика построения графа.

h4. 8.1. Первичная загрузка без фильтров.

# Получить строки из набора «Узлы».
# Получить строки из набора «Связи».
# Построить множество узлов по значениям поля с полки «Узлы».
# Построить множество связей по значениям полей «Узел-источник» и «Узел-приёмник».
# Сопоставить концы связей со значениями ключей узлов.
# Отрисовать все корректные узлы и корректные связи.

h4. 8.2. Дедупликация узлов.

* Дубли по ключу устраняются предпочтительно на уровне запроса/агрегации.
* Если дубли дошли до frontend, renderer дедуплицирует по ключу.
* При конфликте свойств — использовать результат заданной агрегации; если агрегация не задана — использовать первое значение в порядке ответа и фиксировать предупреждение в логах.
* Поведение при дублях должно быть детерминированным и не должно приводить к падению визуализации.

h4. 8.3. Отсутствующие узлы в связях.

* Связь с отсутствующим узлом пропускается, визуализация продолжает работу.
* Остальные корректные узлы и связи отрисовываются.
* В логах фиксируется диагностическая запись с ограниченным набором данных: значение отсутствующего узла и идентификатор связи, если он доступен. Логирование не должно раскрывать лишние данные за пределами необходимой диагностики.

h4. 8.4. Изолированные узлы.

Узлы без связей:
* отображаются на полотне;
* участвуют в фильтрации, поиске, выделении и кросс-фильтрации;
* не исчезают из-за отсутствия строк в наборе «Связи».

----
h3. 9. Фильтрация данных.

h4. 9.1. Общий принцип.

* Фильтры по полям набора «Узлы» применяются к узлам.
* Фильтры по полям набора «Связи» применяются к связям.
* Фильтр не применяется к другому набору только из-за совпадения {{name}} поля.
* Каждая фильтрующая пилюля хранит контекст набора данных.
* При формировании payload для получения данных фильтр должен попадать только в запрос соответствующего {{datasetId}}.

h4. 9.2. Фильтрация по полям узлов.

Фильтрация по полям узлов ограничивает множество узлов-кандидатов. Дальнейшее поведение — по настройке «С соседями» (см. 9.4–9.6).

Если для отображения соседей нужны свойства узлов, которые не попали в первичную выборку узлов-кандидатов, система должна получить свойства таких узлов из набора «Узлы» по их ключам или использовать уже загруженную полную выборку, если она доступна в выбранном режиме работы.

h4. 9.3. Фильтрация по полям связей.

* Применяется к набору «Связи».
* Не удаляет узлы автоматически; узлы без оставшихся связей отображаются изолированными.
* При одновременных фильтрах по узлам и связям: сначала определяется множество узлов-кандидатов, затем допустимые связи, затем применяется режим охвата.
* Фильтр по связям не должен попадать в запрос набора «Узлы» только из-за совпадения {{name}} поля.

h4. 9.4. Настройка «С соседями».

*Toggle, по умолчанию ВКЛ.*

|| Значение || Поведение ||
| ВКЛ | Отображаются отфильтрованные узлы + их непосредственные соседи (один уровень) + соответствующие связи |
| ВЫКЛ | Отображаются только узлы, прошедшие фильтр, и только связи, у которых оба конца входят в отфильтрованное множество |

Режим «С соседями» добавляет узлы ровно одного уровня смежности (непосредственные соседи), а не рекурсивно все достижимые узлы. Глубина обхода — 1.

h4. 9.4.1. Алгоритм «С соседями» — ВКЛ.

# Применить фильтр к набору «Узлы» → множество узлов-кандидатов.
# Применить фильтры связей к набору «Связи» (если есть).
# Выбрать связи, инцидентные узлам-кандидатам, с учётом «Направление фильтрации».
# Извлечь из выбранных связей все упомянутые значения узлов.
# Итоговое множество: узлы-кандидаты + соседи.
# Получить свойства всех итоговых узлов из набора «Узлы»; при необходимости выполнить дополнительный запрос по ключам итоговых узлов.
# Отрисовать итоговые узлы и выбранные связи.

_Пример:_ узлы A(Премиум), B(Стандарт), C(Премиум), D(Стандарт); связи A→B, B→C, B→D; фильтр {{category = "Премиум"}}; режим «С соседями» ВКЛ, направление «Все».
Итог: отображаются узлы A, B, C и связи A→B, B→C. Узел B отображается как сосед, хотя сам не прошёл фильтр по {{category}}. D и связь B→D не отображаются.

h4. 9.4.2. Алгоритм «С соседями» — ВЫКЛ.

# Применить фильтр к набору «Узлы» → множество узлов-кандидатов.
# Применить фильтры связей к набору «Связи» (если есть).
# Оставить только связи, у которых оба конца входят в множество кандидатов.
# Отрисовать узлы-кандидаты и оставшиеся связи. Узлы без связей — изолированные.

h4. 9.5. Настройка «Направление фильтрации».

*Выпадающий список, по умолчанию «Все направления».*

|| Значение || Поведение в режиме «С соседями» ВКЛ ||
| «Все направления» | Соседи по входящим и исходящим связям |
| «Только исходящие» | Только {{Узел-приёмник}} связей от отфильтрованных узлов |
| «Только входящие» | Только {{Узел-источник}} связей к отфильтрованным узлам |

При «С соседями» ВЫКЛ — настройка недоступна/заблокирована.

h4. 9.6. Режим клика на узел.

*Выпадающий список / переключатель, по умолчанию «Выделение».*

|| Значение || Поведение ||
| «Выделение» | Локальное выделение: узел и инцидентные связи подсвечиваются, остальные приглушаются. Данные не перезапрашиваются |
| «Кросс-фильтрация» | Применяется фильтр по ключу выбранного узла; «Граф» перестраивается; соседние виджеты дашборда получают фильтр по существующей логике |

В режиме «Кросс-фильтрация» фильтр формируется по полю, размещённому на полке «Узлы», и по значению выбранного узла. Этот фильтр относится к набору «Узлы».

h4. 9.7. Пустой результат.

* Пустое полотно + сообщение «Нет данных, соответствующих условиям фильтра».
* Ни ошибок, ни падений. После снятия фильтра — восстановление данных.

----
h3. 10. Интеграция с фильтрами дашборда.

* Фильтр дашборда, связанный с полем набора «Узлы», применяется к узлам; с полем набора «Связи» — к связям.
* При совпадении {{name}} поля в обоих наборах система использует привязку фильтра к конкретному набору.
* Кросс-фильтрация из «Графа» при клике на узел передаёт в контекст дашборда фильтр по полю с полки «Узлы» и значению выбранного узла.
* Кросс-фильтрация из других визуализаций применяется к «Графу» только при наличии однозначного соответствия поля одному из наборов данных «Графа». При невозможности определить набор данных фильтр не должен приводить к падению визуализации.
* Поведение соседних виджетов, для которых фильтр по выбранному узлу неприменим, должно соответствовать существующей логике платформы для нерелевантных кросс-фильтров.

----
h3. 11. Обратная совместимость.

* Все существующие визуализации (кроме нового режима «Графа») продолжают работать без изменений; API-контракты не нарушаются.
* При создании «Графа» доступна двухтабличная настройка.
* Метаданные полей ({{name}}, {{alias}}) существующих наборов данных не изменяются.
* Значения {{name}} не заменяются на глобальные идентификаторы и не требуют миграции существующих наборов данных.

----
h3. 12. Нефункциональные требования.

h4. 12.1. Производительность.

* Первичная отрисовка (_ориентировочные данные_) на 1 000 узлов и 2 000 связей — без видимых зависаний.
* Применение фильтра на сопоставимом объёме — без длительной блокировки UI.
* Режим «С соседями» не формирует неограниченно большой payload; при больших множествах используется безопасный способ передачи условий.
* Если для режима «С соседями» требуется дополнительный запрос за свойствами соседних узлов, он не должен приводить к заметной деградации работы визуализации на базовом объёме 1 000 узлов и 2 000 связей.
* Технический лимит на количество узлов/связей (если вводится) — явно согласован и отображён пользователю.

h4. 12.2. Отказоустойчивость.

Визуализация не должна падать при:
* выбран только один из двух наборов данных;
* обязательные полки заполнены не полностью;
* в наборе «Связи» есть ссылка на отсутствующий узел;
* в данных есть пустые значения ключа узла;
* в данных есть пустые значения одного из концов связи;
* после фильтрации нет данных;
* один из запросов завершился ошибкой.

При ошибке одного из запросов пользователю показывается понятное сообщение, а в логах фиксируется диагностика.

# Предполагается, что двухтабличный режим на первом этапе реализуется только для визуализации «Граф».

# Предполагается, что вычисляемые поля остаются привязанными к конкретному набору данных и не выполняют кросс-датасетные выражения.
# Нужно согласовать точный формат хранения двух ролей наборов данных в конфигурации визуализации с учётом текущих {{axes}}, {{axesDefault}} и существующих свойств пилюль.

# Нужно определить, сохраняется ли состояние свёрнутости секций между открытиями редактора или остаётся только локальным UI-состоянием.
# Нужно подтвердить фактические backend-объекты/команды сохранения конфигурации отчёта, если они отличаются от {{reports}} / {{get}} / {{update}}.

h3. 14. Критерии приёмки (AC):

# *AC.01* При открытии настроек нового двухтабличного «Графа» левая панель содержит блок «Структура данных» с двумя секциями: «Узлы» и «Связи», каждая с выпадающим списком выбора набора данных и списком полей.
# *AC.02* Пилюля из секции «Узлы» не может быть перетащена на полки «Связи» и «Свойства связей»; пилюля из секции «Связи» не может быть размещена на полках «Узлы» и «Свойства узлов».
# *AC.03* На полке «Связи» ровно две пилюли с типами {{Узел-источник}} и {{Узел-приёмник}}; при одинаковых типах или незаполненном типе визуализация отображает ошибку настройки и не строит граф.
# *AC.04* Конфигурация «Графа» хранит: идентификаторы наборов данных с ролями, маппинг ключевых полей, маппинг свойств и фильтров с привязкой к набору данных, режимы фильтрации и клика.
# *AC.05* Каждая пилюля в двухтабличном «Графе» сохраняет {{datasetId}} и контекст роли набора данных. После сохранения и повторного открытия визуализации поля не теряют связь со своим набором данных.
# *AC.06* При загрузке без фильтров frontend/data-layer получает данные набора «Узлы» и данные набора «Связи» через соответствующие {{datasetId}} и строит граф: все 10 узлов тестового набора и все корректные связи отображаются, дублирующихся узлов нет, визуализация не падает.
# *AC.07* Поля с одинаковым {{name}} в наборах «Узлы» и «Связи» не конфликтуют: фильтр или свойство по {{category}} из «Узлов» не применяется к {{category}} из «Связей», и наоборот.
# *AC.08* {{name}} поля используется как ссылка на поле только в контексте набора данных. Ключом узла для построения графа является значение выбранного поля в строках набора «Узлы», а не само {{name}} поля.
# *AC.09* Связь, ссылающаяся на отсутствующий узел или содержащая пустой конец связи, пропускается; корректные узлы и связи отрисовываются; в логах фиксируется диагностическая запись; визуализация не падает.
# *AC.10* Изолированные узлы (без связей) отображаются на полотне и участвуют в фильтрации, выделении и кросс-фильтрации.
# *AC.11* Фильтрация по полям связей не удаляет узлы: при фильтре {{edge_type = "Партнёрство"}} все узлы, полученные из набора «Узлы», остаются на полотне; узлы без оставшихся связей отображаются изолированными.
# *AC.12* Toggle «С соседями» ВКЛ (по умолчанию): при фильтре {{category = "Премиум"}} на графе A(Пр.), B(Ст.), C(Пр.), D(Ст.) со связями A→B, B→C, B→D — отображаются узлы A, B, C и связи A→B, B→C; B отображается как сосед; D и связь B→D не отображаются.
# *AC.13* Toggle «С соседями» ВЫКЛ: при том же фильтре отображаются только узлы A и C; отображается только связь A→C, если она есть; узлы, не прошедшие фильтр, скрыты.
# *AC.14* Настройка «Направление фильтрации» в режиме «С соседями» ВКЛ: при «Только исходящие» и фильтре по узлу A со связями A→B и C→A — отображается A, сосед B и связь A→B; C соседом не добавляется.
# *AC.15* В режиме «С соседями» ВКЛ система получает свойства соседних узлов из набора «Узлы» или использует уже загруженные строки. Соседний узел не должен отображаться без доступных свойств, необходимых renderer для корректной отрисовки.
# *AC.16* При клике на узел в режиме «Выделение» — узел и инцидентные связи подсвечиваются, состав графа не меняется, данные не перезапрашиваются, соседние виджеты дашборда не фильтруются.
# *AC.17* При клике на узел в режиме «Кросс-фильтрация» — «Граф» перестраивается с учётом настроек «С соседями» и «Направление фильтрации»; соседние виджеты дашборда получают фильтр по полю с полки «Узлы» и значению выбранного узла по существующей логике.
# *AC.18* При пустом результате фильтрации отображается пустое полотно с сообщением «Нет данных, соответствующих условиям фильтра»; падения нет; после снятия фильтра граф восстанавливается.
# *AC.19* Фильтр дашборда применяется к набору «Узлы» или «Связи» по привязке поля; при совпадении {{name}} в обоих наборах используется привязка к конкретному набору, а не имя без контекста.
# *AC.20* Все остальные визуализации продолжают работать без изменений; метаданные полей ({{name}} и человекочитаемый {{alias}}) не изменяются; существующие API-контракты не нарушены.
# *AC.21* Визуализация не падает при неполной настройке (не выбран один из наборов данных, полки заполнены частично, один из запросов завершился ошибкой); пользователю показывается понятное сообщение.
