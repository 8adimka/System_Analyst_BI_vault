h1. Работа над ошибками.
При более глубоком рассмотрении проблемы стало понятно, что решение с одной таблицей (один набор данных) - ошибочно в связи с тем, что при таком решении, кроме проблем с фильтрацией (с которой мы уже столкнулись) у нас будут ещё и массовые дублирования данных, что, в следствии, будет порождать проблемы при изменении данных узлов и их свойств.

Представляем, что мы внесли наши изменения и начали хранить в одной строке таблицы: 
1) все данные по узлу-источнику, 
2) все данные по узлу-приёмнику,
3) все характеристики связи.

При этом один и тот же узел может выступать в одном случае узлом-источником, а в другом случае узлом-приёмником. И таких строк (в нашей таблице) с участием этого узла может быть множество - тогда при изменении свойст или данных этого узла мы будем вынуждены пройтись по всей таблице и изменить данные этого узла в КАЖДОЙ строчке с его участием. 
Более того мы должны:
1) сначала пройтись по колонке "узел-источник", найти там искомый узел, изменить его данные,
2) а потом пройтись по колонце "узел-приёмник", найти там искомый узел, изменить его данные.

Вероятность появления неконсистентности данных (при таком подходе) очень высока, ошибки могут возникать и накапливаться.
Поэтому более перспективным решением мне видится введение второй таблицы:
1) Первыя таблица - "Вершины Графа" (узлы),
2) Вторая таблица - "Связи" (connections).

При таком подходе будет минимум ошибок, коллизий, проще работа с фильтрацией данных и такое решение является эталонным при работе с Графом. Более того на Графах завязано много хитрых алгоритмов и линейной алгебры, а используя наше "урезанное" решение с одной таблицей мы можем некоторые из них поломать и сделать работу с Графом не интуитивной (p.s. актуально только для людей хорошо знающих линейную алгебру и мне тоже надо эти знания освежить).

h1. Граф. Доработка диаграммы «Граф» - Переход на двухтабличную архитектуру (Nodes & Edges) и комплексная фильтрация

h3. 1. Цель
Рефакторинг архитектуры данных компонента «Граф». Переход от плоского набора данных к двухтабличной модели (Вершины и Рёбра) для устранения проблем дублирования данных, риска неконсистентности при обновлениях свойств узлов и обеспечения корректной работы комплексных фильтров.

----
h3. 2. Обоснование и проблематика
При использовании одного плоского набора данных один и тот же узел многократно дублируется в строках. Это приводит к Высокому риску рассинхронизации данных при обновлении свойств узла (необходимость апдейта множества строк) и Ограничениям при сложной фильтрации.

*Решение:* Использовать два независимых, но логически связанных набора данных: таблицу Узлов (Nodes) и таблицу Связей (Edges). Комбинируя их через промежуточный конвейер на уровне BI-ядра, мы добьемся гибкой фильтрации без потери связности графа.

----
h3. 3. Новая структура данных компонента

Компонент «Граф» теперь ожидает на вход два JSON-массива (два датасета):

*Набор данных 1: Вершины Графа (Nodes)*
Содержит уникальный список узлов и все их свойства.
* {{id}} (string/number, *обязательно*) — уникальный идентификатор узла.
* {{label}} (string) — подпись узла.
* {{value}} (number) — метрика для размера узла.
* {{category}} (string) — категория для цвета/легенды.
* {{tooltip}} (string) — HTML-подсказка.
* Любые дополнительные атрибуты (например, Город, Должность).

*Набор данных 2: Рёбра Графа (Edges)*
Содержит информацию о связях (Свойства узлов здесь *не хранятся*).
* {{source_id}} (string/number, *обязательно*) — ссылка на id узла-источника.
* {{target_id}} (string/number, *обязательно*) — ссылка на id узла-приёмника.
* {{relation}} (string) — тип связи (например, "Партнерство").
* {{edge_value}} (number) — вес связи.
* {{tooltip}} (string) — HTML-подсказка для связи.

----
h3. 4. Пользовательский интерфейс (Настройки диаграммы)

Для реализации различных сценариев фильтрации, в панель настроек компонента «Граф» добавляется новый параметр:
*Настройка:* *Режим фильтрации смежных узлов (Context Mode)*
* Тип: Dropdown или Radio Button.
* Значения:
** *«Строгий режим» (Strict)* — выводятся только те узлы, которые удовлетворяют фильтру, и связи строго между ними (если есть).
** *«С соседями (+1 уровень)» (With Neighbors)* — (По умолчанию). Выводятся отфильтрованные узлы + все узлы, которые имеют с ними связи (даже если соседи не попадают под условия фильтра), а также связи между ними.
** *«Только входящие связи» (Inbound Only)* — Выводятся отфильтрованные узлы в роли приёмников + их узлы-источники.
** *«Только исходящие связи» (Outbound Only)* — Выводятся отфильтрованные узлы в роли источников + их узлы-приёмники.

----
h3. 5. Алгоритм работы фильтрации (BI Core Pipeline)

Фильтрация происходит на бэкенде (BI Core) в 3 этапа. Фронтенд получает уже готовые и консистентные массивы Nodes и Edges.

*Этап 1: Применение пользовательских фильтров к Узлам и Связям*
Ядро формирует два базовых подзапроса на основе фильтров дашборда:
* {{Filtered_Nodes}} = SELECT * FROM Nodes WHERE (применены все фильтры свойств узлов, напр. City = 'Новосибирск').
* {{Filtered_Edges_Base}} = SELECT * FROM Edges WHERE (применены все фильтры свойств связей, напр. relation = 'Партнерство').

*Этап 2: Вычисление итоговых Связей (Final Edges) на основе "Режима фильтрации"*
В зависимости от выбранной настройки (см. п.4), ядро формирует итоговый список связей:
* *С соседями (+1 уровень):* {code:sql}
SELECT * FROM Filtered_Edges_Base 
WHERE source_id IN (SELECT id FROM Filtered_Nodes) 
   OR target_id IN (SELECT id FROM Filtered_Nodes)
{code}
_Покрывает Сценарий 1: При клике на узел на диаграмме (фильтр id='A'), мы получаем все связи, где он источник или приёмник._

* *Только входящие связи (Inbound Only / Target):*
{code:sql}
SELECT * FROM Filtered_Edges_Base 
WHERE target_id IN (SELECT id FROM Filtered_Nodes)
{code}
_Покрывает Сценарий 2 комплексной фильтрации: мы искали узлы с City='Новосибирск' только в роли приёмников._

* *Строгий режим:*
{code:sql}
SELECT * FROM Filtered_Edges_Base 
WHERE source_id IN (SELECT id FROM Filtered_Nodes) 
  AND target_id IN (SELECT id FROM Filtered_Nodes)
{code}

*Этап 3: Восстановление контекстных Узлов (Final Nodes)*
Чтобы фронтенд смог отрисовать граф без ошибок, в итоговом массиве Узлов должны присутствовать все вершины, упомянутые в итоговом массиве Связей (даже если они отсеялись на Этапе 1).
{code:sql}
SELECT * FROM Nodes 
WHERE id IN (SELECT id FROM Filtered_Nodes)
   OR id IN (SELECT source_id FROM Final_Edges)
   OR id IN (SELECT target_id FROM Final_Edges)
{code}

h3. 6. Отрисовка на Фронтенде (ECharts Renderer)
После отработки алгоритма на бэкенде, фронтенд-компонент получает абсолютно консистентные и очищенные массивы данных.
# Сложный парсинг, денормализация и Map-структуры больше *НЕ НУЖНЫ*.
# Массив {{Final_Nodes}} передается напрямую в {{series[0].data}}.
# Массив {{Final_Edges}} передается напрямую в {{series[0].links}} (замапив {{source_id}} -> {{source}}, {{target_id}} -> {{target}} согласно API ECharts).
# Если пользователь кликает на узел на холсте, компонент отправляет в BI-ядро фильтр по ID узла, и бэкенд прогоняет его через стандартный Pipeline (Этапы 1-3) с учетом выбранного режима.

----
h3. 7. Критерии приемки (AC)
# *Отсутствие дублей:* В итоговом массиве Nodes нет дублирующихся ID, свойства узлов обновляются в БД в одном месте.
# *Клик по узлу:* При клике на узел «А» (при включенном режиме «С соседями») граф перестраивается, отображая узел «А», всех его прямых соседей и связи между ними.
# *Направленная фильтрация:* При выборе фильтра по атрибуту (Город = Новосибирск) и режима «Только входящие», на графе остаются только узлы Новосибирска (в качестве target), узлы из других городов (в качестве source) и направленные стрелки от них к узлам Новосибирска.
# *Целостность отрисовки:* Компонент не падает с JS-ошибками, если у связи есть {{source_id}}, которого нет в отфильтрованном массиве узлов (гарантируется Этапом 3 на бэкенде).
# *Изолированные узлы:* Узлы без связей корректно отображаются, если они удовлетворяют прямому пользовательскому фильтру в «Строгом режиме» или режиме «С соседями».
