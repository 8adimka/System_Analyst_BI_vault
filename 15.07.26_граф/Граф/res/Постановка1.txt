Граф. Доработка диаграммы «Граф» - фильтрация данных.
 
*Цель:* 
Полностью устранить проблему потери узлов и связей при фильтрации данных. Решение должно быть *универсальным*, работать на любых данных клиента, сохранять полную совместимость с текущим поведением (множественные связи, категории, радиус, цвет, подсказки, HTML) и не требовать изменения системного ограничения «одна диаграмма - один набор данных».

### 1. Краткое описание текущей проблемы
В текущей реализации набор данных представляет собой *одну плоскую таблицу*, где каждая строка описывает:
- узел-источник + его свойства + узел-приёмник + свойства связи.

Свойства *узла-приёмника* в этой строке *отсутствуют* (присутствуют только для источника).
При применении фильтра по узлам-приёмникам, мы теряем в итоговой выборке строки, где данный узел выступает узлом-источником.
Аналогично, при применении фильтра по узлам-источникам, мы не получаем в итоговой выборке строки, где данный узел выступает узлом-приёмником.

Дополниетльно, при применении фильтра по свойствам, которые относятся к «листьям» графа - мы теряем все строки, содержащие эти "листья" графа, так как свойства узлов приёмников мы не храним (каждая строка в данных отражает только свойства узла-источника и свойства связи).

Как следствия всех этих потерь → узлы теряются → связь не может быть отрисована → граф ломается.

### 2. Требуемое решение:
На данный момент было принято решение сохранить подход с **одиним набор данных** на диаграмму.  
Поэтому мы вынуждены полностью **денормализовать** его форму: каждая строка (EDGE) теперь содержит **полные свойства обоих концов связи (узлов)** (source_* и target_*).  
Фильтрация по свойствам узла автоматически применяется по **OR-логике** для обоих концов связи (узлов) *(source_ ИЛИ target_)*.  
Сборка графа после фильтрации всегда производится на основе **всех узлов** из оставшихся строк *(как source, так и target)* и корректно агрегирует их свойства.

Это гарантирует:
- фильтрация по любому свойству узла (независимо от роли источника/приёмника) сохраняет все инцидентные связи;
- цепочки любой длины и изолированные узлы сохраняются корректно;
- множественные связи между одной парой узлов (разные relation) работают как раньше.

### 3. Новая структура набора данных (обязательная для диаграммы «Граф»)
Набор данных **обязательно** должен содержать следующие колонки (имена строго по соглашению):

**Обязательные:**
- `source` — идентификатор/название узла-источника (string/number)
- `target` — идентификатор/название узла-приёмника (string/number, **может быть NULL** для изолированных узлов)

**Атрибуты связи (Edge/Relation):**
* `edge_relation` (string) — тип связи (например, "Партнерство", "Аффилированность").
* `edge_value` (number) — вес/значение связи (опционально, для толщины линии).
* `edge_tooltip` (string) — HTML-строка для подсказки при наведении на связь.

**Свойства узлов (дублируются для обоих концов):**
- `source_radius`, `target_radius`
- `source_color`, `target_color`
- `source_node_tooltip`, `target_node_tooltip`
- `source_category`, `target_category` (для серий/легенды)
- любые другие атрибуты узла (например `source_gen_dir`, `target_gen_dir`, `source_revenue` и т.д.)

**Важно:**  
Аналитик, формирующий витрину, **обязан** делать два JOIN’а:

```sql
FROM graph_edges e
LEFT JOIN graph_nodes ns ON e.source_id = ns.node_id
LEFT JOIN graph_nodes nt ON e.target_id = nt.node_id

-- затем в SELECT:
SELECT
  e.source_id AS source,
  e.target_id AS target,
  ... edge fields ...,
  ns.radius AS source_radius,
  nt.radius AS target_radius,
  ns.color AS source_color,
  nt.color AS target_color,
  ns.node_tooltip AS source_node_tooltip,
  nt.node_tooltip AS target_node_tooltip,
  ...
```

Для изолированных узлов (без исходящих связей) допускается UNION-часть:

```sql
UNION ALL
SELECT 
  n.node_id AS source,
  NULL AS target,
  ...,
  n.radius AS source_radius,
  n.radius AS target_radius,   -- дублируем для единообразия
  ...
FROM graph_nodes n
LEFT JOIN graph_edges e ON n.node_id = e.source_id
WHERE e.source_id IS NULL
```

### 4. Логика применения фильтрации (новый механизм в компоненте «Граф»)
Фильтры применяются **на уровне построения SQL-запроса** (как и сейчас).

**Новое поведение:**
- Если фильтр наложен на колонку, имя которой начинается с `source_` (например `source_gen_dir = 'Иванов'`), то автоматически в WHERE добавляется условие:

  ```sql
  (source_gen_dir = 'Иванов' OR target_gen_dir = 'Иванов')
  ```

- Фильтры на колонки `target_*` обрабатываются обычным образом (без автоматического OR, т.к. пользователь в 99 % случаев будет фильтровать по `source_*`).
- Фильтры на колонки связи (`relation`, `edge_value` и т.д.) — обычные.
- Логика «И» между разными фильтрами остаётся без изменений.
- Вычисляемые поля и HAVING поддерживаются как раньше.

Таким образом, строка (связь) сохраняется, если **хотя бы один** из двух узлов удовлетворяет условию фильтра по свойству узла.

### 5. Логика сборки JSON для ECharts из отфильтрованного набора данных
После получения отфильтрованных строк (dataset):

**1. Сбор уникальных узлов**
```js
const nodesSet = new Set();
dataset.forEach(row => {
  if (row.source) nodesSet.add(row.source);
  if (row.target) nodesSet.add(row.target);
});
```

**2. Агрегация свойств каждого узла**
Для каждого узла `nodeId`:
- Найти все строки, где `source === nodeId` или `target === nodeId`.
- Для каждого атрибута (radius, color, node_tooltip, category и др.):
  - Собрать кандидаты: `source_xxx` из строк-источников + `target_xxx` из строк-приёмников.
  - Выбрать значение по правилу (приоритет):
    1. Если узел встречается хотя бы в одной строке как `source` → берём значение из `source_xxx` (FIRST non-null или MAX для чисел).
    2. Иначе → берём значение из `target_xxx`.
  - Если значений несколько и они различаются — используем **первую встреченную** (порядок строк в dataset).  
    **Примечание для аналитиков:** свойства узла должны быть консистентны во всех строках.

**3. Формирование связей (links)**
- Каждая строка, где `target IS NOT NULL` → одна связь.
- Множественные строки между одной парой source-target → множественные рёбра (ECharts graph поддерживает).

**4. Категории / серии**
Уникальные значения из `source_category` / `target_category` (должны совпадать для одного узла).

**5. JSON-структура для ECharts**
Остаётся как сейчас (nodes + links + categories), но:
- `nodes` строится из уникальных узлов + агрегированных свойств.
- `links` — напрямую из строк.

### 6. Особые случаи (обязательно обработать)
- `target = NULL` → изолированный узел (отрисовывается без связей).
- Узел присутствует только как `target` → свойства берутся из `target_*`.
- Множественные связи между одной парой (разные `relation`) → все сохраняются.
- Конфликт свойств узла (редкий случай плохих данных) → FIRST non-null по порядку строк.
- Пустой датасет после фильтрации → пустая диаграмма (без ошибок).
- NULL/пустые значения в radius → обработка как раньше (заглушка или 5).

### 7. Изменения в интерфейсе настроек (минимальные)
- В разделе «Данные» добавить подсказку/валидацию: «Набор данных должен содержать колонки source_*/target_* для свойств узлов».
- В полке «Значения» роли «Радиус», «Цвет из данных», «Подсказка узла» и т.д. привязываются к колонкам `source_*` (компонент сам знает про `target_*`).
- Остальные настройки (подсказки, подписи, легенда, режим фильтра по клику) остаются без изменений.

### 8. Требования к тестированию
- Все сценарии из транскрипции (фильтр по индустрии связи, по гендиректору партнёра/клиента, по сумме сделки, по свойству листа).
- Цепочки 3+ уровня.
- Изолированные узлы после фильтрации.
- Множественные связи между одной парой.
- Фильтры «И» между узловыми и связевыми свойствами.
- Отрицательный radius, NULL-значения, HTML в подсказках.
- Производительность на больших датасетах (≥10к строк).
