h1. Граф. Доработка диаграммы «Граф» - Рефакторинг механизмов фильтрации и сбора данных

h3. 1. Цель
Устранить проблему потери узлов и связей при фильтрации данных в визуализации «Граф». Решение должно быть _универсальным_, работать на любых данных клиента, сохранять полную совместимость с текущим поведением (множественные связи, категории, радиус, цвет, подсказки, поддержка HTML) и не требовать изменения системного ограничения «одна диаграмма — один набор данных».

----
*Краткое описание текущей проблемы:*
* В текущей реализации набор данных представляет собой _одну плоскую таблицу_, где каждая строка описывает: _узел-источник_ + его свойства + _узел-приёмник_ + свойства связи.
* Свойства _узла-приёмника_ в этой строке _отсутствуют_ (присутствуют только для источника). 
* При применении фильтра по _узлам-приёмникам_ мы теряем в итоговой выборке строки, где данный узел выступает _узлом-источником_. Аналогично, при применении фильтра по _узлам-источникам_, мы не получаем в итоговой выборке строки, где данный узел выступает _узлом-приёмником_.
* Дополнительно, при применении фильтра по свойствам, которые относятся к «листьям» графа, мы теряем все инцидентные строки, так как свойства узлов-приёмников в строке не хранятся. 
* *Следствие:* Узлы теряются -> связь не может быть отрисована -> граф ломается или отображается некорректно.

h3. 2. Требуемое решение
На данный момент принято решение сохранить архитектурное ограничение *один набор данных на диаграмму*. 
Поэтому мы вынуждены полностью _денормализовать_ форму датасета:

* Каждая строка, представляющая связь (EDGE), теперь должна содержать *полные свойства обоих концов связи* (узлов {{source_*}} и {{target_*}}). 
* Фильтрация по свойствам узла на уровне BI-системы должна автоматически применяться по *логике OR (ИЛИ)* для обоих концов связи. 
* Сборка графа на фронтенде после фильтрации производится на основе *всех уникальных узлов*, извлеченных из оставшихся строк (как из колонок префикса {{source_}}, так и из {{target_}}), с корректной агрегацией их свойств.

*Это гарантирует:*
* Сохранение всех инцидентных связей при фильтрации по любому свойству узла (независимо от его роли: источник или приёмник);
* Корректное сохранение цепочек любой длины и изолированных узлов;
* Поддержку множественных связей между одной парой узлов (с разными типами {{edge_relation}}).

----
h3. 3. Структура набора данных (Спецификация колонок)
Набор данных, передаваемый в компонент диаграммы, должен иметь следующий плоский формат (названия колонок фиксируются как системный стандарт компонента):

*Идентификаторы узлов (Обязательные поля):*
* {{source_id}} — уникальный идентификатор узла-источника (string/number).
* {{target_id}} — уникальный идентификатор узла-приёмника (string/number, *может быть NULL* или пустой строкой для изолированных узлов).

*Свойства узлов (дублируются для обоих концов связи):*
* {{source_label}}, {{target_label}} (string) — подпись узла (отображаемое имя).
* {{source_value}}, {{target_value}} (number) — числовое значение (используется для расчета радиуса узла).
* {{source_color}}, {{target_color}} (string) — кастомный цвет узла (RGB/HEX), если задан в данных.
* {{source_tooltip}}, {{target_tooltip}} (string) — HTML-строка для подсказки при наведении на узел.
* {{source_category}}, {{target_category}} (string/number) — категория (для раскраски и легенды).
* Любые другие атрибуты узла добавляются по этому же принципу парных префиксов.

*Атрибуты связи (Edge/Relation):*
* {{edge_relation}} (string) — тип связи (например, "Партнерство", "Аффилированность").
* {{edge_value}} (number) — вес/значение связи (опционально, для толщины линии).
* {{edge_tooltip}} (string) — HTML-строка для подсказки при наведении на связь.

----
h3. 4. Логика формирования датасета из БД клиента (ETL)
Чтобы сформировать плоскую денормализованную таблицу из нормализованных данных клиента (таблицы узлов и таблицы связей), конструктор запросов BI-системы должен использовать двойное левое соединение (LEFT JOIN).

*Ориентировочный базовый паттерн SQL-генерации:*
{code:sql}
SELECT 
    -- Свойства источника
    n_src.id AS source_id,
    n_src.label AS source_label,
    n_src.category AS source_category,
    ...
    -- Свойства приемника
    n_tgt.id AS target_id,
    n_tgt.label AS target_label,
    n_tgt.category AS target_category,
    ...
    -- Свойства связи
    e.relation_type AS edge_relation,
    e.tooltip AS edge_tooltip
FROM nodes_table n_src
LEFT JOIN edges_table e ON n_src.id = e.source_id
LEFT JOIN nodes_table n_tgt ON e.target_id = n_tgt.id
{code}
_Примечание:_ Использование LEFT JOIN гарантирует, что изолированные узлы (не имеющие записей в {{edges_table}}) попадут в датасет (у них поля {{target_*}} и {{edge_*}} будут NULL).

h3. 5. Механизм работы фильтрации (BI Core Level)
Критически важно изменить обработку пользовательских фильтров перед отправкой запроса к датасету.

*Правило 1: Фильтры по атрибутам узлов (OR-логика)*
Если пользователь накладывает фильтр на любое свойство узла (например, фильтр по {{category = 'Премиум'}}), ядро BI должно развернуть этот фильтр в условие OR для соответствующих колонок источника и приёмника.
* *SQL-эквивалент:* {{WHERE (source_category = 'Премиум' OR target_category = 'Премиум')}}
* _Эффект:_ В выборке останутся все связи, где этот узел выступает источником ИЛИ приёмником.

*Правило 2: Фильтры по атрибутам связей (Стандартная логика)*
Если фильтр накладывается на свойство связи (например, {{edge_relation = 'Партнерство'}}), условие применяется напрямую.
* *SQL-эквивалент:* {{WHERE (edge_relation = 'Партнерство')}}

*Правило 3: Множественные фильтры (AND-логика между группами)*
Взаимодействие _разных_ фильтров подчиняется классической логике AND.
* *Пример* (Категория узла = 'Премиум' И Тип связи = 'Партнерство'):
{{WHERE (source_category = 'Премиум' OR target_category = 'Премиум') AND (edge_relation = 'Партнерство')}}

h3. 6. Алгоритм сборки графа на Фронтенде (ECharts Renderer)
В компонент визуализации на фронтенде приходит отфильтрованный JSON-массив объектов (строк). Компонент должен распарсить эти "плоские" данные и собрать два массива для ECharts: {{nodes}} (без дубликатов) и {{edges}} (связи).

*Шаг 1: Извлечение и дедупликация узлов (Nodes Parsing)*
Использовать структуру {{Map}} (где ключ — ID узла), чтобы избежать дублирования, так как один и тот же узел будет встречаться во множестве строк.
# Итерация по каждой строке массива данных.
# *Проверка источника:* если {{source_id}} еще нет в {{Map}}, создать объект узла, заполнив его полями {{source_*}} (id, label, category, value, color, tooltip), и добавить в {{Map}}.
# *Проверка приёмника:* если {{target_id}} корректен (не равен NULL и не пустая строка) и его еще нет в {{Map}}, создать объект узла, заполнив его полями {{target_*}}, и добавить в {{Map}}.
_Примечание:_ Если узел уже существует в {{Map}}, его повторное добавление игнорируется.

*Шаг 2: Формирование связей (Edges Parsing)*
# Итерация по каждой строке массива данных.
# Если {{target_id}} корректен (не NULL), формируется объект связи:
{{ { source: row.source_id, target: row.target_id, relation: row.edge_relation, tooltip: row.edge_tooltip } }}
# Если между узлами есть несколько связей с разным {{edge_relation}}, создаются независимые объекты связей (ECharts поддерживает multiple edges через кривые Безье).

*Шаг 3: Передача в ECharts*
# Сформированные узлы {{Array.from(Map.values())}} передаются в свойство {{series[0].data}}.
# Массив связей передается в {{series[0].links}}.

h3. 7. Критерии приемки (AC)
# *Фильтрация не рвет связи:* При выборе узла «А» в фильтре, на графе отображается сам узел «А», все узлы, куда идут стрелки от «А», и все узлы, от которых идут стрелки к «А».
# *Изолированные узлы:* Узлы без связей (где target_id = NULL) корректно отрисовываются на полотне графа. При фильтрации по их категории они не пропадают.
# *HTML в подсказках:* Поля {{*_tooltip}} рендерятся корректно, HTML-теги (например, <b>Премиум</b>) не экранируются как текст, а применяются как форматирование.
# *Множественные связи:* Поддерживается корректная отрисовка двух стрелок (например, «Аффилированность» и «Партнерство») между одной и той же парой узлов.
# *Интерактивность:* При клике на узел на самом графике (кросс-фильтрация), остальные узлы становятся блеклыми. Логика работы фильтрации опирается на ID узла и корректно использует _Правило 1 (OR-логику)_.
