
# Граф. Доработка диаграммы «Граф» - Рефакторинг механизмов фильтрации и сбора данных.

### 1. *Цель:*
Полностью устранить проблему потери узлов и связей при фильтрации данных в визуализации «Граф». Решение должно быть *универсальным*, работать на любых данных клиента, сохранять полную совместимость с текущим поведением (множественные связи, категории, радиус, цвет, подсказки, поддержка HTML) и не требовать изменения системного ограничения «одна диаграмма — один набор данных».

---

*Краткое описание текущей проблемы*
* В текущей реализации набор данных представляет собой *одну плоскую таблицу*, где каждая строка описывает:
*узел-источник* + его свойства + *узел-приёмник* + свойства связи.
* Свойства *узла-приёмника* в этой строке *отсутствуют* (присутствуют только для источника). 
* При применении фильтра по _узлам-приёмникам_ мы теряем в итоговой выборке строки, где данный узел выступает _узлом-источником_. Аналогично, при применении фильтра по _узлам-источникам_, мы не получаем в итоговой выборке строки, где данный узел выступает _узлом-приёмником_.
* Дополнительно, при применении фильтра по свойствам, которые относятся к «листьям» графа, мы теряем все инцидентные строки, так как свойства узлов-приёмников в строке не хранятся. 

* Как следствие всех этих потерь: узлы теряются → связь не может быть отрисована → граф ломается или отображается некорректно.

### 2. *Требуемое решение*
* На данный момент было принято решение сохранить подход с **одиним набор данных** на диаграмму.  
Поэтому мы вынуждены полностью *денормализовать* его форму:

** Каждая строка, представляющая связь(EDGE), теперь должна содержать *полные свойства обоих концов связи* (узлов `source_\*` и `target_\*`). 
** Фильтрация по свойствам узла на уровне BI-системы должна автоматически применяться по *логике OR (ИЛИ)* для обоих концов связи. 
** Сборка графа на фронтенде после фильтрации производится на основе *всех уникальных узлов*, извлеченных из оставшихся строк (_как из колонок `source`, так и из `target`_), с корректной агрегацией их свойств.

Это гарантирует:
* Сохранение всех инцидентных связей при фильтрации по любому свойству узла (независимо от его роли: источник или приёмник);
* Корректное сохранение цепочек любой длины и изолированных узлов;
* Поддержку множественных связей между одной парой узлов (с разными типами `relation`).

---

### 3. *Cтруктура набора данных (Спецификация колонок)*

Набор данных, передаваемый в компонент диаграммы, должен иметь следующий плоский формат (названия колонок фиксируются как системный стандарт компонента):

*Обязательные:*
- `source` — идентификатор/название узла-источника (string/number)
- `target` — идентификатор/название узла-приёмника (string/number, **может быть NULL** для изолированных узлов)

*Атрибуты связи (Edge/Relation):*
* `edge_relation` (string) — тип связи (характеристика связи взаимоотношений, например, "Партнерство", "Аффилированность").
* `edge_value` (number) — вес/значение связи (опционально, для толщины линии).
* `edge_tooltip` (string) — HTML-строка для подсказки при наведении на связь.

*Свойства узлов (дублируются для обоих концов):*
- `source_value`, `target_value` (number) — числовое значение (используется для расчета радиуса узла).
- `source_color`, `target_color` (string) — кастомный цвет узла (RGB/HEX), если задан в данных.
- `source_node_tooltip`, `target_node_tooltip` (string) — HTML-строка для подсказки при наведении на источник.
- `source_category`, `target_category` (string/number) — категория (для раскраски и легенды).
- любые другие атрибуты узла (например `source_gen_dir`, `target_gen_dir`, `source_revenue` и т.д.)

### 4. *Логика формирования датасета из БД клиента (ETL)*

Чтобы сформировать плоскую денормализованную таблицу из нормализованных данных клиента (таблица узлов + таблица связей), конструктор запросов BI-системы должен использовать двойное левое соединение (`LEFT JOIN`).

*Ориентировочный базовый паттерн SQL-генерации:*
{code:sql}
SELECT 
    -- Свойства источника
    n_src.id AS source_id,
    n_src.label AS source,
    n_src.category AS source_category,
    ...
    -- Свойства приемника
    n_tgt.id AS target_id,
    n_tgt.label AS target,
    n_tgt.category AS target_category,
    ...
    -- Свойства связи
    e.relation_type AS edge_relation,
    e.tooltip AS edge_tooltip
FROM nodes_table n_src
LEFT JOIN edges_table e ON n_src.id = e.source_id
LEFT JOIN nodes_table n_tgt ON e.target_id = n_tgt.id
{code}

*Примечание:* Использование `LEFT JOIN` гарантирует, что изолированные узлы (не имеющие записей в `edges_table`) попадут в датасет (у них поля `target` и `edge_*` будут `NULL`).

### 5. *Механизм работы фильтрации (BI Core Level)*

Критически важно изменить обработку пользовательских фильтров перед отправкой запроса к датасету.

*Правило 1: Фильтры по атрибутам узлов (OR-логика)*
Если пользователь накладывает фильтр на любое свойство узла (например, фильтр по `category = 'Премиум'`), ядро BI должно развернуть этот фильтр в условие `OR` для соответствующих колонок источника и приёмника.
* SQL-эквивалент: `WHERE (source_category = 'Премиум' OR target_category = 'Премиум')`
* *Эффект:* В выборке останутся все связи, где этот узел выступает источником ИЛИ приёмником.

*Правило 2: Фильтры по атрибутам связей (Стандартная логика)*
Если фильтр накладывается на свойство связи (например, `edge_relation = 'Партнерство'`), условие применяется напрямую.
* SQL-эквивалент: `WHERE (edge_relation = 'Партнерство')`

*Правило 3: Множественные фильтры (AND-логика между группами)*
Взаимодействие *разных* фильтров подчиняется классической логике `AND`.
* Пример (Категория узла = 'Премиум' И Тип связи = 'Партнерство'):
  `WHERE (source_category = 'Премиум' OR target_category = 'Премиум') AND (edge_relation = 'Партнерство')`

### 6. Алгоритм сборки графа на Фронтенде (ECharts Renderer)

В компонент визуализации на фронтенде приходит отфильтрованный JSON массив объектов (строк). Компонент должен распарсить эти "плоские" данные и собрать два массива для ECharts: `nodes` (без дубликатов) и `edges` (связи).

**Шаг 1: Извлечение и дедупликация узлов (Nodes Parsing)**
Использовать структуру `Map` (где ключ — ID узла), чтобы избежать дублирования, так как один и тот же узел будет встречаться во множестве строк.

# Итерация по каждой строке массива данных.
# Проверка источника: если `source_id` еще нет в `Map`, создать объект узла, заполнив его полями `source_*` (label, category, value, color, tooltip), и добавить в `Map`.
# Проверка приёмника: если `target_id` не равен `NULL` и его еще нет в `Map`, создать объект узла, заполнив его полями `target_*`, и добавить в `Map`.
#* Если узел уже существует в `Map`, его повторное добавление игнорируется (свойства считаются идентичными, так как они вытянуты из одной сущности в БД).

**Шаг 2: Формирование связей (Edges Parsing)**
# Итерация по каждой строке массива данных.
# Если `target_id` не равен `NULL`, формируется объект связи:
   `{ source: row.source_id, target: row.target_id, relation: row.edge_relation, tooltip: row.edge_tooltip, ... }`
# Если между узлами есть несколько связей с разным `relation`, создаются независимые объекты связей (ECharts поддерживает multiple edges через кривые Безье).

**Шаг 3: Передача в ECharts**
# Сформированные `Array.from(Map.values())` передаются в свойство `series[0].data` (или `nodes`), а массив связей передается в `series[0].links` (или `edges`).

### 7. Критерии приемки (AC)
# *Фильтрация не рвет связи:* При выборе узла «А» в фильтре, на графе отображается сам узел «А», все узлы, куда идут стрелки от «А», и все узлы, от которых идут стрелки к «А».
# *Изолированные узлы:* Узлы без связей корректно отрисовываются на полотне графа. При фильтрации по их категории они не пропадают.
# *HTML в подсказках:* Поля `\*_tooltip` рендерятся корректно, HTML-теги (например `<b>Премиум</b>`) не экранируются как текст, а применяются как форматирование.
# *Множественные связи:* Поддерживается корректная отрисовка двух стрелок (например, «Аффилированность» и «Партнерство») между одними и теми же узлами.
# *Интерактивность:* При клике на узел на самом графике (если настроено выделение/фильтрация по нажатию), остальные узлы становятся блеклыми, логика работы кросс-фильтрации опирается на ID узла и использует _Правило 1 (OR-логику)_.
