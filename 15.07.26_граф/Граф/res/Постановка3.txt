h1. Граф. Доработка диаграммы «Граф» - Рефакторинг механизмов фильтрации и денормализация набора данных

h3. 1. Цель
Обеспечить корректную работу фильтрации и предотвратить потерю узлов/связей при построении компонента «Граф». Решение должно работать в рамках текущего системного ограничения *«одна диаграмма — один набор данных» (плоская таблица)*, поддерживать множественные связи, изолированные узлы и обеспечивать универсальную логику фильтрации (включая кросс-фильтрацию и фильтрацию по направлению связи).

----
*Краткое описание текущей проблемы:*
* В текущей реализации набор данных представляет собой _одну плоскую таблицу_, где каждая строка описывает: 
[Узел-источник + Свойства Узла-источника + Узел-приёмник + Свойства связи]. 
* Свойства узла-приёмника не хранятся.
* В текущей архитектуре для построения связи требуются данные из разных строк: строки узла-источника со связью и отдельная строка для узла-приёмника (где он выступает _узлом-источником_). При фильтрации по свойствам мы отсекаем строку _узла-приёмника_, из-за чего система теряет конечную точку и не может отрисовать вектор связи.


h3. 2. Требуемое решение
На данный момент принято решение сохранить архитектурное ограничение *один набор данных на диаграмму*. 
Поэтому актуальное решение - *денормализация таблицы:*
* Каждая строка, представляющая связь, теперь должна содержать *полные свойства обоих концов связи* (узлов {{source_*}} и {{target_*}}). 
* При фильтрации по узлам (или свойствам узла) фильтрация на уровне BI-системы должна автоматически (по-умолчанию) применяться по *логике OR (_ИЛИ_)* для обоих концов связи. 
* Сборка графа на фронтенде после фильтрации производится на основе *всех уникальных узлов*, извлеченных из оставшихся строк (как из колонок префикса {{source_}}, так и из {{target_}}), с корректной агрегацией их свойств.

----
h3. 3. Структура набора данных (Спецификация колонок компонента)
Набор данных, передаваемый в компонент, должен иметь следующий формат (имена фиксируются как системный стандарт компонента):

*Идентификаторы узлов (вершины Графа - обязательные поля):*
* {{source_id}} — уникальный идентификатор узла-источника (string/number).
* {{target_id}} — уникальный идентификатор узла-приёмника (string/number, *может быть NULL* или пустой строкой для изолированных узлов).

*Свойства узлов (дублируются для обоих концов связи):*
* {{source_label}}, {{target_label}} (string) — подпись узла (отображаемое имя).
* {{source_value}}, {{target_value}} (number) — числовое значение (используется для расчета радиуса узла).
* {{source_color}}, {{target_color}} (string) — кастомный цвет узла (RGB/HEX), если задан в данных.
* {{source_tooltip}}, {{target_tooltip}} (string) — HTML-строка для подсказки при наведении на узел.
* {{source_category}}, {{target_category}} (string/number) — категория (для раскраски и легенды).
* Любые другие атрибуты узла добавляются по этому же принципу парных префиксов.

*Атрибуты связи (ребра Графа):*
* {{edge_relation}} (string) — тип связи (например, "Партнерство", "Аффилированность").
* {{edge_value}} (number) — вес/значение связи (опционально, для толщины линии).
* {{edge_tooltip}} (string) — HTML-строка для подсказки при наведении на связь.

----
h3. 4. Логика формирования датасета (ETL / SQL Builder)
Поскольку мы используем одну плоскую таблицу, ответственность за консистентность свойств узла лежит на источнике данных. Для формирования витрины конструктор запросов BI должен использовать *двойное левое соединение (LEFT JOIN)* к таблице-справочнику узлов.

*Ориентировочный базовый шаблон SQL-генерации:*
{code:sql}
SELECT 
    -- Свойства источника
    n_src.id AS source_id,
    n_src.label AS source_label,
    n_src.category AS source_category,
    ...
    -- Свойства приемника
    n_tgt.id AS target_id,
    n_tgt.label AS target_label,
    n_tgt.category AS target_category,
    ...
    -- Свойства связи
    e.relation_type AS edge_relation,
    e.tooltip AS edge_tooltip
FROM nodes_table n_src
LEFT JOIN edges_table e ON n_src.id = e.source_id
LEFT JOIN nodes_table n_tgt ON e.target_id = n_tgt.id
{code}
_Важно:_ LEFT JOIN гарантирует, что изолированные узлы (не имеющие записей в {{edges_table}}) попадут в выборку (в этих строках все поля {{target_*}} и {{edge_*}} будут NULL).

h3. 5. Пользовательский интерфейс (Дополнительные настройки фильтрации):

Для реализации различных сценариев фильтрации, в панель настроек компонента «Граф» добавляются две новых настройки фильтрации:
# Настройка: *Фильтрация включая смежные узлы*.
#* Тип: Toggle switch/Checkbox.
#* Значения:
#** Вкл (_По умолчанию_) — *«С соседями (+1 уровень)»* — Выводятся отфильтрованные узлы + все узлы, которые имеют с ними связи (даже если соседи не попадают под условия фильтра), а также связи между ними.
#** Выкл — *«Строгий режим»* — выводятся только те узлы, которые удовлетворяют фильтру, и связи строго между ними.
# Настройка: *Режим фильтрации связей* 
#* Тип: Dropdown/Radio Button.
#* Значения:
#** *«Все связи»* (_По умолчанию_) — Выводятся отфильтрованные узлы-приёмники и узлы-источники (+ связанные узлы, если включена настройка _Фильтрация включая смежные узлы_),
#** *«Только входящие связи»* — Выводятся отфильтрованные узлы-приёмники (+ их узлы-источники, если включена настройка _Фильтрация включая смежные узлы_),
#** *«Только исходящие связи»* — Выводятся отфильтрованные узлы-источники (+ их узлы-приёмники, если включена настройка _Фильтрация включая смежные узлы_).

h3. 6. Механизмы фильтрации (Уровень BI Core)
Для обеспечения корректного построения Графа на основе плоской денормализованной таблицы, BI-ядро должно динамически транслировать пользовательские фильтры (_например, Category = 'Премиум'_) в SQL-запросы. Формирование условий _WHERE_ зависит от выбранных настроек компонента (Раздел 5).

Ниже описана логика работы BI Core при наложении фильтра.

* 6.1. Режим «Все связи» (По умолчанию)
Фильтр применяется к обоим концам связи (как к источнику, так и к приёмнику).
** С настройкой «С соседями (+1 уровень)» (По умолчанию):
Применяется логика *OR*. В выборке остаются все строки, где искомый узел выступает источником ИЛИ приёмником. Это сохраняет сам узел и все инцидентные ему связи (соседей).
SQL:
{code:sql}
WHERE source_category = 'Премиум' OR target_category = 'Премиум'
{code}
** С настройкой «Строгий режим»:
Применяется логика *AND*. В выборке остаются только те связи, где ОБА узла (и источник, и приёмник) удовлетворяют условию фильтра. Изолированные узлы (без приёмника) также остаются, если удовлетворяют фильтру.
SQL:
{code:sql}
WHERE (source_category = 'Премиум' AND target_category = 'Премиум')
OR (source_category = 'Премиум' AND target_id IS NULL)
{code}
* 6.2. Режим «Только входящие связи»
Фильтр применяется с фокусом на узлы-приёмники.
** С настройкой «С соседями (+1 уровень)»:
В выборке остаются строки, где искомое значение находится строго в колонке приёмника. Отрисовывается сам отфильтрованный приёмник и все узлы-источники, которые на него ссылаются.
SQL:
{code:sql}
WHERE target_category = 'Премиум'
{code}
** С настройкой «Строгий режим»:
Связь останется в выборке только если узел-приёмник удовлетворяет наложенному фильтру, И при этом узел-источник также удовлетворяет этому же фильтру.
SQL:
{code:sql}
WHERE target_category = 'Премиум' AND source_category = 'Премиум'
{code}
** Аналогично, но для _узлов-источников_ обрабатывается Режим *«Только исходящие связи»*.
* 6.3. Кросс-фильтрация (Интерактивность на дашборде)
При клике на конкретный узел (например, id = 'A') на самом Графе или на соседнем чарте, BI-ядро генерирует условие на основе текущих настроек компонента:

** «Все связи» + «С соседями»: Покажет узел А и все его связи во всех направлениях.
{code:sql}
SQL: WHERE source_id = 'A' OR target_id = 'A'
{code}

** «Только исходящие связи» + «С соседями»: Покажет узел А и только те узлы, на которые он ссылается.
{code:sql}
SQL: WHERE source_id = 'A'
{code}

*** Примечание для аналитиков: Применение «Строгого режима» к кросс-фильтрации по конкретному ID приведет к отображению только самого узла A

** Аналогично для «Только входящие связи».

* 6.5. Взаимодействие нескольких разных фильтров (Конкуренция по _AND_)
Если на дашборде применяется несколько фильтров по разным бизнес-атрибутам (например, Категория = 'Премиум' и Регион = 'Москва'), то *SQL-блок* для каждого отдельного фильтра формируется по правилам разделов 6.1–6.3 _(в скобках)_, а между собой эти блоки объединяются логическим оператором _AND_.

** Пример (Режим «Все связи» + «С соседями»):

SQL
{code:sql}
WHERE (source_category = 'Премиум' OR target_category = 'Премиум')
  AND (source_region = 'Москва' OR target_region = 'Москва')
{code}
** Эффект: Граф покажет связи, где с одной из сторон есть "Премиум", и с одной из сторон есть "Москва" (это может быть как один узел, обладающий обоими свойствами, так и связь между "премиальным" источником и "московским" приёмником).

h3. 7. Алгоритм сборки графа на Фронтенде (ECharts)
В компонент визуализации на фронтенде приходит отфильтрованный JSON-массив объектов (строк). Компонент должен распарсить эти "плоские" данные и собрать два массива для ECharts: {{nodes}} (без дубликатов) и {{edges}} (связи).

*Шаг 1: Извлечение и дедупликация узлов (Nodes)*
Использовать структуру {{Map}} (где ключ — ID узла), чтобы избежать дублирования, так как один и тот же узел будет встречаться во множестве строк.
# Итерация по каждой строке массива данных.
# *Проверка источника:* если {{source_id}} еще нет в {{Map}}, создать объект узла, заполнив его полями {{source_*}} (id, label, category, value, color, tooltip), и добавить в {{Map}}.
# *Проверка приёмника:* если {{target_id}} корректен (не равен NULL и не пустая строка) и его еще нет в {{Map}}, создать объект узла, заполнив его полями {{target_*}}, и добавить в {{Map}}.
_Примечание:_ Если узел уже существует в {{Map}}, его повторное добавление игнорируется.

*Шаг 2: Формирование связей (Edges)*
# Итерация по каждой строке массива данных.
# Если {{target_id}} корректен (не NULL), формируется объект связи:
{{ { source: row.source_id, target: row.target_id, relation: row.edge_relation, tooltip: row.edge_tooltip } }}
# Если между узлами есть несколько связей с разным {{edge_relation}}, создаются независимые объекты связей. ECharts поддерживает multiple edges (кривые Безье).

*Шаг 3: Передача в ECharts*
# Сформированные узлы {{Array.from(Map.values())}} передаются в свойство {{series[0].data}}.
# Массив связей передается в {{series[0].links}}.

h3. 8. Критерии приемки (AC):
# *Фильтрация не рвет связи:* При выборе узла «А» в фильтре, на графе отображается сам узел «А», все узлы, куда идут стрелки от «А», и все узлы, от которых идут стрелки к «А».
# *Изолированные узлы:* Узлы без связей (где target_id = NULL) корректно отрисовываются на полотне графа. При фильтрации по их категории они не пропадают.
# *Направленная фильтрация:* Поддерживается возможность отфильтровать граф так, чтобы остались только узлы-приёмники с нужным свойством.
# *Дедупликация фронтенда:* Независимо от количества строк в JSON, узел с конкретным ID отрисовывается на холсте только один раз. Ошибок о дублировании ID не возникает.
# *HTML в подсказках:* Поля {{*_tooltip}} рендерятся корректно, HTML-теги (например, <b>Премиум</b>) не экранируются как текст, а применяются как форматирование.
# *Множественные связи:* Поддерживается корректная отрисовка двух стрелок (например, «Аффилированность» и «Партнерство») между одной и той же парой узлов.
# *Интерактивность:* При клике на узел на самом графике (кросс-фильтрация), остальные узлы становятся блеклыми. Логика работы фильтрации опирается на ID узла и корректно использует _OR-логику_.

Механизмы фильтрации (Уровень BI Core)
Для обеспечения ожидаемого UX при работе с графом, BI-ядро должно обрабатывать фильтры в зависимости от введённых настроек:

*Кросс-фильтрация по узлу на дашборде*
Если пользователь кликает на узел (id = 'A') на любом чарте, он ожидает увидеть этот узел и все его связи. BI-ядро применяет OR-логику по ID:
* *SQL:* 
{code:sql}
{{WHERE source_id = 'A' OR target_id = 'A'}}
{code}

*Фильтры по атрибутам узлов (OR-логика)*
Если пользователь накладывает фильтр на любое свойство узла (например, фильтр по {{category = 'Премиум'}}), ядро BI должно развернуть этот фильтр в условие OR для соответствующих колонок источника и приёмника.
* *SQL-эквивалент:* {{WHERE (source_category = 'Премиум' OR target_category = 'Премиум')}}
* _Эффект:_ В выборке останутся все связи, где этот узел выступает источником ИЛИ приёмником.

*Общие фильтры свойств (Логика "С соседями (+1 уровень)")*
Если фильтр накладывается на общее бизнес-свойство (например, дашборд фильтруется по "Категория = Премиум"), BI-ядро применяет OR-логику к парным колонкам, чтобы сохранить связность:
* *SQL:* {{WHERE source_category = 'Премиум' OR target_category = 'Премиум'}}

*Правило 3: Направленная фильтрация (Точная выборка)*
Если пользователь в настройках диаграммы явно перетаскивает конкретное поле (например, именно {{target_city}}) в слот фильтра и задает "Новосибирск", применяется строгая фильтрация по конкретной колонке:
* *SQL:* {{WHERE target_city = 'Новосибирск'}}
_Эффект:_ В графе останутся только те связи, где приёмник находится в Новосибирске (Сценарий направленной фильтрации). Разные фильтры объединяются через логическое AND.
