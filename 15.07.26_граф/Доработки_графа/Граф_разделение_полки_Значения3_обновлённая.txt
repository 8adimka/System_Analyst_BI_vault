h3. Контекст и проблематика.

В диаграмме «Граф» одна полка «Значения» используется и для свойств узлов, и для свойств связей. При этом эти свойства имеют разные уровни агрегации:

* свойство узла должно рассчитываться по всем строкам одного узла-источника {{[node]}}, независимо от узлов-приёмников;
* свойство связи должно рассчитываться отдельно для каждой упорядоченной пары {{[node]}} + {{[linkage]}}.

Текущая постобработка не различает эти контексты и использует для разных связей одного узла значение из первой обработанной строки. Из-за этого, в частности, в настройке «Подсказки связей» отображается значение другой связи. 

Одновременно с этим нельзя однозначно задать узловую агрегацию для "Значений", варьирующихся по связям, агрегируемых в метрику узла (Сумма сделки, выручка по сделке, размер конкретного контракта). Например, получить *сумму* сделок по всем связям одного узла (это значение можно, к примеру, использовать для отрисовки размера узла).

----

h3. Цель задачи.

*Требуется:*

# Заменить полку «Значения» двумя независимыми полками: «Свойства узлов» и «Свойства связей».
# Рассчитывать и сопоставлять свойства узлов и связей на соответствующем уровне агрегации, в том числе при одновременном использовании обеих полок.
# Обновить все настройки диаграммы, в которых сейчас выбираются поля с полки «Значения», и сохранить работоспособность существующих отчётов, с возможностью выбора там полей с двух новых полок.

----

h3. 1. Описание целевого поведения.

|| Полка || Ключ обработки || Целевая логика ||
| Свойства узлов | {{[node]}} | Для каждой пилюли применяется её настроенная агрегация по всем прошедшим фильтры исходным строкам данного узла, независимо от {{[linkage]}}. Возвращается одна запись на узел. |
| Свойства связей | {{[node]}} + {{[linkage]}} | Для каждой пилюли применяется её настроенная агрегация только по строкам данной упорядоченной пары. Возвращается одна запись на связь. |

* Узлы дедуплицируются по значению поля с полки «Узел». Каждый узел отрисовывается один раз и получает свойства из записи с его ключом {{[node]}}.
* Связь определяется упорядоченной парой «узел-источник → узел-приёмник». Пары {{A}} → {{B}} и {{B}} → {{A}} не смешиваются.
* Несколько строк одной пары формируют одну связь; её свойства агрегируются по настройкам пилюль. Одинаковые исходные строки не исключаются перед агрегацией.
* Строка с заполненным {{[node]}} и {{[linkage]}} = {{null}} участвует в формировании и агрегации свойств узла, но не создаёт связь и не участвует в расчёте свойств связей. Другие пустые значения обрабатываются по действующим правилам диаграммы.
* Пустое свойство узла или связи не заменяется значением другой сущности. Сама сущность при этом продолжает отрисовываться.

h3. 2. Требования к реализации.

h4. 2.1. Полки и настройки.

* В редакторе диаграммы «Граф» заменить полку «Значения» полками «Свойства узлов» и «Свойства связей». Полки «Узел», «Связь», «Категории» и «Фильтры» не изменять.
* Обе новые полки должны принимать поля набора данных и вычисляемые поля.
* Для пилюль на полке «Свойства узлов» сохранить действующие настройки агрегации и форматирования, а также типы «Значение», «Цвет», «Размер»; для новой пилюли типом по умолчанию остаётся «Значение».
* Для пилюль на полке «Свойства связей» сохранить настройки агрегации и форматирования. В рамках задачи для них поддерживается тип «Значение» и «Цвет». «Размер» к связи не вводится. Для новой пилюли типом по умолчанию является «Значение».
** При выборе для пилюли на полке «Свойства узлов» типа «Размер» в правом нижнем углу пилюли отображается маркер (пиктограмма), визуально аналогичный по расположению и принципу отображения маркеру, используемому для типа размера точки в визуализации «Геокарта». 
** При выборе типа «Цвет» продолжает отображаться существующий стандартный маркер цвета.
* Одно исходное поле можно разместить на обеих полках. Это два независимых экземпляра пилюли, для которых могут быть заданы разные агрегации и настройки.
* В правой боковой панели настроек диаграммы «Граф» переименовать раздел настроек «Подсказки» в «Подсказки узлов» (раздел «Подсказки связей» не переименовывается).
* Провести инвентаризацию всех настроек диаграммы, где сейчас можно выбрать пилюлю с полки «Значения», и обновить каждую из них. Ни один селектор не должен остаться привязанным к старой полке:
** В разделе «Подсказки связей» → «Шаблон» (при выбранном значении «текст подсказки») → «Текст подсказки» - в выпадающем списке отображаются только пилюли с полки «Свойства связей».
** В разделе «Подсказки узлов» → «Шаблон» (при выбранном значении «текст подсказки») → «Текст подсказки» - в выпадающем списке отображаются только пилюли с полки «Свойства узлов».
** Для остальных настроек диаграммы, ссылающихся на бывшую полку «Значения» (кроме двух указанных выше селекторов «Текст подсказки»), используются поля полки «Свойства узлов» по аналогичной логике.
* Значение выбранной пилюли всегда извлекается по логике соответствующей её полке: по ключу {{[node]}} для «Свойств узлов» и по полной паре {{[node]}} + {{[linkage]}} для «Свойств связей». Выбор первой подходящей строки не допускаются.

h4. 2.2. Получение и агрегация данных.

* Свойства узлов и связей рассчитывать как две независимые логические агрегации над одним актуальным набором исходных строк:
** «Свойства узлов» — {{GROUP BY [node]}};
** «Свойства связей» — {{GROUP BY [node], [linkage]}} (после исключения строк без связи по действующим правилам диаграммы).
* Обе агрегации выполнять непосредственно над исходными строками. Узловые значения нельзя получать повторной агрегацией уже рассчитанных связей.
* RLS, переменные и строковые условия {{WHERE}} применять к общему исходному набору до обеих агрегаций. Если условия полки «Фильтры» формируют {{HAVING}}, рассчитывать их независимо в каждой логической выборке по действующим правилам: после {{GROUP BY [node]}} для свойств узлов и после {{GROUP BY [node], [linkage]}} для свойств связей. Результат одной выборки не должен использоваться как исходный набор для другой.
* Топология графа должна получаться и отрисовываться, если одна или обе полки свойств пусты.
* Количество HTTP-запросов, структура SQL и физическая форма ответа не фиксируются, но рекомендуется попытаться минимизировать нагрузку и выполнять только минимально необходимые операции.

h4. 2.3. Обработка на фронтенде.

* Сформировать модель узлов с сопоставлением по {{[node]}} и модель связей с сопоставлением по полной паре {{[node]}} + {{[linkage]}}. Свойства узла не извлекать из первой связи, а свойства связи не распространять на другие связи того же узла.
* При формировании текста подсказки и применении настроек связи использовать свойство из записи той же пары.

h4. 2.4. Сохранение и обратная совместимость.

* В конфигурации отчёта сохранять для каждой пилюли достаточный набор данных (полку, порядок, агрегацию, тип, форматирование и ссылки из настроек). Повторное открытие и копирование отчёта не должны изменять эти данные.
* При переносе пилюли между новыми полками сохранять её идентификатор, а выбранный тип заменять на «Значение» (по умолчанию).
* При чтении сохранённой конфигурации со старой полкой «Значения» выполнять детерминированное преобразование:
|| Использование старой пилюли || Результат ||
| Пилюля используется на полке «Значения» | Создать пилюлю на полке «Свойства узлов», запись о полке «Значения» - устраняется |

* Использование старых пилюль в настройках должно быть очищено.
* При повторном открытии перенастройка не должна создавать дубли.

h4. 2.5. Технические ограничения.

* Изменение правил построения и направления связей, логики фильтрации, полок «Категории» и «Фильтры», а также других визуализаций в рамки задачи не входит.
* Различение нескольких самостоятельных связей для одной и той же упорядоченной пары узлов не входит в рамки задачи.
* Добавление новых способов оформления связей, в том числе постоянных подписей, новых цветов или толщины, в рамки задачи не входит.
* У команды разработки необходимо подтвердить актуальность бэкенд-объекта и команды получения данных визуализации. Если контракт меняется, необходимо зафиксировать его актуальные имена и способ обратно-совместимой обработки.

h3. 4. Критерии приёмки (AC):

*AC.1 — Новые полки и контекстные селекторы:*
* *Дано:* пользователь редактирует диаграмму «Граф»;
* *Когда:* поля набора данных и вычисляемые поля добавлены на обе новые полки;
* *Тогда:* полка «Значения» в интерфейсе отсутствует; В разделе «Подсказки узлов» → «Шаблон» (при выбранном значении «текст подсказки») → в селекторе «Текст подсказки» доступны только пилюли с полки «Свойства узлов». В остальных настройках узла доступны для выбора только пилюли с полки «Свойства узлов»; В разделе «Подсказки связей» → «Шаблон» (при выбранном значении «текст подсказки») → в селекторе «Текст подсказки» доступны только пилюли с полки «Свойства связей».

*AC.2 — Одновременная обработка свойств узла и связей:*
* *Дано:* диаграмма построена на данных из файла [^Граф_выгрузка_данных_для_отображения.xlsx]; {{НазваниеУзла}} размещено на полке «Узел», {{НазваниеУзлаПриемника}} — на полке «Связь», {{Количество_сделок}} — на полке «Свойства узлов» с {{SUM}}, а {{Тип_связи}} — на полке «Свойства связей» с {{MAX}} и выбран как текст подсказки связи;
* *Когда:* диаграмма отрисована;
* *Тогда:* отображаются 4 узла и 3 связи, в модели узла «Хэндисофт, ООО» значение {{Количество_сделок}} равно {{3}}, а в подсказках связей указаны:
|| Связь || Текст подсказки ||
| Хэндисофт, ООО → Министерство Российской Федерации по делам гражданской обороны, чрезвычайным ситуациям и ликвидации последствий стихийных бедствий | Только неуспешные |
| Хэндисофт, ООО → Министерство Обороны Российской Федерации (Минобороны России) | Открытые сделки |
| Хэндисофт, ООО → Департамента информационных технологий и связи Ямало-Ненецкого автономного округа (ДИТиС ЯНАО) | Есть успешные |

*AC.3 — Независимость уровней агрегации:*
* *Дано:* исходные данные содержат строки {{A}} → {{B}} со значениями {{10}} и {{20}}, строку {{A}} → {{C}} со значением {{7}}, а также отдельные строки узлов {{B}} и {{C}} без связей; поле {{Сумма}} размещено на обеих полках с {{SUM}};
* *Когда:* диаграмма отрисована;
* *Тогда:* отображаются узлы {{A}}, {{B}}, {{C}} и по одной связи {{A}} → {{B}} и {{A}} → {{C}}; узел {{A}} не дублируется; его свойство равно {{37}}, свойство {{A}} → {{B}} — {{30}}, свойство {{A}} → {{C}} — {{7}}.

*AC.4 — Пустые значения:*
* *Дано:* {{Метрика_узла}} размещена на полке «Свойства узлов» с {{SUM}}, {{Метрика_связи}} — на полке «Свойства связей»; строка {{A}} с {{[linkage]}} = {{null}} содержит {{Метрика_узла}} = {{5}}, строка {{A}} → {{B}} — {{Метрика_узла}} = {{2}} и {{Метрика_связи}} = {{null}}, а {{A}} → {{C}} — {{Метрика_узла}} = {{null}} и {{Метрика_связи}} = {{9}};
* *Когда:* диаграмма отрисована;
* *Тогда:* свойство узла {{A}} равно {{7}}, связь для строки с {{[linkage]}} = {{null}} не создана, {{A}} → {{B}} отрисована без свойства, значение {{9}} из {{A}} → {{C}} не подставлено; ошибка отрисовки не возникает.

*AC.5 — Направление и повторы связей:*
* *Дано:* пара {{A}} → {{B}} представлена двумя строками со значениями {{10}} и {{20}}, а пара {{B}} → {{A}} — строкой со значением {{5}}; для свойства связи задана {{MAX}};
* *Когда:* диаграмма отрисована;
* *Тогда:* в модели связей сформированы две независимые записи: свойство {{A}} → {{B}} равно {{20}}, свойство {{B}} → {{A}} — {{5}}; действующие правила визуального отображения встречных связей не изменились.

*AC.6 — Пустые полки свойств:*
* *Дано:* на полках «Узел» и «Связь» размещены поля, а обе полки свойств пусты;
* *Когда:* диаграмма отрисована;
* *Тогда:* узлы и связи отображаются по текущим правилам, ошибка не возникает.

*AC.7 — Сохранение и удаление пилюли:*
* *Дано:* одно и то же поле размещено на обеих полках с разными агрегациями; пилюля с полки «Свойства узлов» выбрана в настройке узла, а пилюля с полки «Свойства связей» — в настройке связи;
* *Когда:* отчёт сохранён и повторно открыт, а затем одна из пилюль удалена;
* *Тогда:* до удаления обе пилюли сохранили свои полки, агрегации и ссылки; после удаления очищена только ссылка на удалённый экземпляр, оставшаяся конфигурация не изменилась, диаграмма отрисовалась без ошибки.

*AC.8 — Обратная совместимость:*
* *Дано:* отчёт был сохранён до установки доработки; поле {{Сумма}} с {{SUM}} на старой полке «Значения» использовалось в настройке узла и одновременно было выбрано как текст подсказки связи; исходные строки {{A}} → {{B}} и {{A}} → {{C}} содержат {{10}} и {{20}} соответственно;
* *Когда:* отчёт впервые открыт после установки доработки;
* *Тогда:* отчёт открывается без ручной перенастройки и повторного сохранения; создаётся единственный экземпляр пилюли {{Сумма}} на полке «Свойства узлов» с прежней агрегацией; ссылка на неё в настройке узла сохранена, и свойство узла {{A}} равно {{30}}; ссылка в настройке «Текст подсказки» очищена, подсказки связей {{A}} → {{B}} и {{A}} → {{C}} не отображают значение до тех пор, пока пользователь не выберет новую пилюлю на полке «Свойства связей»; диаграмма отрисовывается без ошибки.

*AC.9 — Корректные группировки и единый контекст данных:*
* *Дано:* на обеих новых полках настроены пилюли, а к диаграмме применены RLS, переменные, строковое условие {{WHERE}} и агрегатное условие, формирующее {{HAVING}};
* *Когда:* сформированы запрос и модель данных диаграммы;
* *Тогда:* свойства узлов рассчитаны по {{[node]}}, свойства связей — по {{[node]}} + {{[linkage]}}; RLS, переменные и {{WHERE}} применены к общему исходному набору до обеих агрегаций; {{HAVING}} рассчитан независимо после каждой из двух группировок, и результат одной выборки не использован как исходный набор для другой.

*AC.10 — Маркер типа пилюли:*

* *Дано:* пользователь размещает пилюлю на полке «Свойства узлов»;
* *Когда:* для пилюли выбран тип «Размер»;
* *Тогда:* в правом нижнем углу пилюли отображается маркер, аналогичный маркеру размера точки в «Геокарте»; при смене типа на «Цвет» отображается стандартный маркер цвета; при выборе «Значение» маркер отсутствует.
