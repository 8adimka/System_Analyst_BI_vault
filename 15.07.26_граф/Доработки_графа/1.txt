В текущей реализации диаграммы "Граф" есть существенные недоработки, которые мешают нормальному использованию данной диаграммы и требуют доработок.

Первый вариант решения данных проблем (быстрый) изложен в постановке ./Граф_свойства_на_полке_Значения2.txt

В текущий момент для данной визуализации (диаграммы "Граф") доступны несколько полок для размещения на них полей из набора данных (и вычисляемых полей):
# Полка "Узел" - тут мы располагаем поле из набора данных с полным списком узлов, которые диаграмма "Граф" должна отрисовать. В случае если один и тот же узел повторяется в колонке несоклько раз - диаграмма будет рассматривать его как один узел и отрисует его один раз. Как мы можем видеть в примере данных узел "Хэндисофт, ООО" повторяется три раза, но будет дедуплицирован и отрисован только один раз на диаграмме.
# Полка "Связь" - на эту полку мы будем размещать пилюлю (колонку) "Узел-приёмник", для каждой строки в наборе данных из этой колонки диаграмма "Граф" будет пытаться извлечь наименование узла к которому нужно построить связь от узла, указанного в колонке "Узел". Т.е. пилюля "Узел-приёмник", размещённая на полке "Связь", содержит наименования узлов к которым нужно построить связь -> диаграмма попарно обрабатывает два эти узла и строит между ними связь, а если есть строка в которой "Узел" назначен, а "Узел-приёмник" отсутсвует, то связь просто не строиться.
# Полка "Значения" - на эту полку мы будет размещать различные колонки (пилюли) из набора данных, которые будут помогать отрисовывать узлы и связи особым образом - для каждого узла может задаваться его радиус, цвет или иные значения для отображения подсказок и т.д. Для каждой размещенной на этой полке пилюли мы можем в настройках пилюли (нажать на "🢓") задать её "Тип" (Значение, Цвет, Радиус). По умолчанию, при добавлении новой пилюли, её ставится тип "Значение".

В данный момент для всех пилюль размещённых на полке "Значения" примеяется следующая логика:
* групировка проводится по уникальному набору "узел-источник" [node]+"узел-приёмник" [linkage],
* среди нескольких итоговых строчек (уже системно на постобрабоке) выбирается первая.

То есть основная поблема, что мы не можем отличать как обрабатывать пилюлю размещённую на полке "Значения", для свойств узлов текущая логика работает (так как значения одинаковые во всех строчках), а вот для свойств связи такая логика не подходит (для них не нужно брать первое значение, а для каждой уникальной связи (сочетание *узел-источник*+*узел-приёмник*) нужно отображать своё значение.

То есть основная проблема как понимать какую логику применять для какой пилюле на полке "Значения".

Когда мы выбирает свойства узлов на этой полке (например "Радиус узла") - текущая логика работает работает, так как значение для всех сточек одинаковые. Проблемы возникают, когда по аналогичной логике диаграмма пытается обраборать свойства связей (которые мы тоже добавляем на эту полку).
# Полка "Категории" - пилюли, размещённые на данной полке позволяют задавать "категориии" для узлов, к примеру, отображать узлы с разной категорией разным цветом.
# Полка "Фильтры" - эта полка также отвечается за выбор пилюль по которым будет производится фильтрация данных для отображения на диаграмме "Граф".

Рабочий вариант решения.
Разделить полку "Значения" на две независимые полки:
1) "Свойства узлов" - тут мы размещаем пилюли, которые хотим обработать как свойства узлов.
Для пилюль, классифицированных как свойство узла, генерируемый запрос должен группировать данные по узлу-источнику:

{code:sql}
select 
MAX("Тип_связи") as "[values]",
"НазваниеУзлаПриемника" as "[linkage]",
"НазваниеУзла" as "[node]"
from (...) as "#table"
group by "НазваниеУзла"
{code}

Такая агрегация объединяет только строки, относящиеся к *одному узлу*.
 
2) "Свойства связей" - тут мы размещаем пилюли, которые хотим обработать как свойства связи.
Для пилюль, классифицированных как свойство связи, генерируемый запрос должен группировать данные по обоим полям — узлу-источнику *и* узлу-приёмнику:

{code:sql}
select 
MAX("Тип_связи") as "[values]",
"НазваниеУзлаПриемника" as "[linkage]",
"НазваниеУзла" as "[node]"
from (...) as "#table"
group by "НазваниеУзлаПриемника", "НазваниеУзла"
{code}

Такая агрегация объединяет только строки, относящиеся к *одной и той же связи* (совпадают и узел-источник, и узел-приёмник), и никогда не смешивает значения разных связей одного узла.

Отдельного внимания заслуживают случаи для "Значений", варьирующихся по связям, агрегируемых в метрику узла -> Сумма сделки, выручка по сделке, размер конкретного контракта.
Например, при применении агрегации SUM к пилюле "СуммаКонтракта", размещённой на полке "Свойства узла" - в итоговых данных должны мы получать все строки, где использовался данный узел-источник (независимо от того с кем была связь). Например, при расчёте выручки по сделке, которая должна суммироваться по всем связям - то есть для каждой сделки (связи) мы должны суммировать значение "СуммаКонтракта" и получить общее значение по всем совершённым сделкам (это общее значение можно, к примеру, использовать для отрисовки радиуса узла). 

Описанная логика должна покрывать такие случаи, так как в итоговые данные, при размещении на полке "Свойства узла", будут уходить все строки с выбранным узлом-источником (групировка по узлу).


Как системный аналитик с большим стажем, опираясь на изученные материалы и контекст, сформулируй логику работы и необходимые доработки нашего аналитического портала и визуализации диаграмма "Граф" для реализации описанных доработок и приведении диаграммы "Граф" в работоспособное состояние с возможностью корректно отрисовывать свойства связей (в частности согластно настройке "Подсказки связей") и свойста узлов. 
Для всех настроек диаграммы, где сейчас есть возможность выбора полей с полки "Значения", дать возможность выбора полей с новых полок "Свойства узлов" и "Свойства связей".
Сформулируй и подготовь понятную постановку, в новой постановке не нужно упоминать факты и обсуждения не касающиеся именно текущей доработки, но нужно дать разработчикам достаточный контекст для понимания, что нужно исправить и почему.

Постановка должна декларативно давать разработчикам информацию о необходимых доработках и не фокусироваться на изменениях внесенных в постановку, обсуждениях, согласованиях, других постановках и прочих некритичных деталях в рамках реализации данной функциональности.

Постановка должна быть компактной, легко и приятно-читаемой, но при этом достаночной, верной и согласованной. Сохраняй оптимальную разметку и структуру документов, которая уже используется в постановках, для публикации в Jira.
