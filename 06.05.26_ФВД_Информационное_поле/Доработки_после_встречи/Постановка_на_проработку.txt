РСХН. ФВД: Проработка решения и оценка трудозатрат: безлимитный поиск в выпадающих списках по информационным полям

h3. Краткая суть проблемы.

В ФВД реализован компонент «Выпадающий список» с режимом *«Поиск без лимита»* (серверный поиск).
При включённых *информационных полях* и активном *«Показ внутри меню»* фронтенд всё равно передаёт в payload только одно (_основное_) поле поиска.
Бэкенд, соответственно, выполняет поиск только по нему, игнорируя вспомогательные поля.

*Ожидаемое поведение* — поиск должен выполняться по всем сконфигурированным полям одновременно, с объединением условий по логике *OR* в рамках *одного* HTTP-запроса.

----
h3. Технический контекст.

Корень проблемы — в формате структуры {{options.where}}, который исторически складывался «по мере надобности» и изначально не был спроектирован под гибкую логику объединения условий.

Рассмотрены несколько подходов:

*Быстрый:* добавить отдельный параметр-флаг в {{options}}, который переключает логику склейки верхнеуровневых условий (AND → OR). Самый быстрый, но наименее расширяемый.

*Тип коллекции как маркер:* массив в {{where}} трактуется как AND (старое поведение), объект — как OR (новое). Сохраняет обратную совместимость, но вносит неявность (тип коллекции как оператор) и плохо расширяется (например, для {{not}}-исключений и прочего — типов уже может не хватить).

*Явная древовидная структура (объектное дерево групп):*
{{where}} становится объектом-*группой* с явным свойством {{logicalOperator}} (AND / OR / NOT) и массивом дочерних элементов. Каждый дочерний элемент может быть либо конкретным *условием* (поле, оператор, значение), либо вложенной *группой* с собственным {{logicalOperator}}.
Старый формат (массив) на входе адаптируется к новому через *адаптер совместимости* на этапе парсинга — старый формат = группа {{AND}}.

*Плюсы последнего подхода*:
# Аналогичная древовидная структура уже реализована в новом конструкторе запросов.
# Явное свойство {{logicalOperator}} понятно, расширяемо (для {{not}} и т.д.).
# Адаптер совместимости позволяет не трогать существующие сценарии.
# Механизм OR-поиска может быть переиспользован в других частях платформы.

Сервис разрабатывается и *внедряется сначала только в ФВД*; постепенное распространение на другие части — отдельные задачи по мере необходимости.

 # Изучить, как аналогичная древовидная структура реализована в *новом конструкторе запросов* — оценить возможность и трудозатраты переноса/переиспользования этой логики.

 * Предложенный *JSON-контракт* нового формата {{options.where}} (хотя бы черновой).
 * *Оценка трудозатрат* (в часах или днях) для реализации выбранного варианта по компонентам: бэк / ФВД-фронт / конструктор запросов / тестирование.
 * Перечень *рисков и открытых вопросов*, которые могут повлиять на реализацию.

h3. Критерии решения:

 * Решение должно быть *обратно совместимым*: существующие сценарии с одним полем поиска продолжают работать без изменений.
 * Поиск по нескольким полям — строго *в одном HTTP-запросе*.
 * OR-механизм должен быть достаточно *абстрактным* для переиспользования за пределами ФВД.
 * Не должно быть привязки к конкретному SQL-диалекту.
 * При совпадении по нескольким полям запись возвращается *один раз* (без дублей).
