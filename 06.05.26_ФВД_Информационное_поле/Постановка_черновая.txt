h3. Контекст и проблематика:
Ранее в Формах ввода данных (ФВД) был успешно реализован функционал «Поиск без лимита» (серверный поиск) для компонента «Выпадающий список». Однако в ходе эксплуатации и тестирования была выявлена проблема с фильтрацией при наличии дополнительных настроек компонента. 

В конструкторе ФВД для выпадающего списка можно настроить *«Информационные поля»* — дополнительные колонки справочника, которые выводятся пользователю для большей информативности. Сейчас при серверном поиске фронтенд отправляет запрос, передавая в массиве {{where}} только *одно* поле (основное наименование). 
В результате поиск осуществляется только по основному наименованию, игнорируя значения из выбранных информационных полей.

Следовательно, текущий серверный поиск в ФВД реализован неполно и не воспроизводит ожидаемую логику компонента.

----

h3. Цель задачи:
*Требуется:*
Доработать логику серверного поиска в компоненте «Выпадающий список» ФВД таким образом, чтобы при вводе текста поиск осуществлялся *по всем* задействованным полям (основному наименованию и всем выбранным «Информационным полям») с использованием логического оператора *ИЛИ (OR)* на стороне бэкенда.

*User Story:* 
Как пользователь системы, я хочу, чтобы при использовании выпадающего списка с включенным серверным поиском, введенный мной текст искался не только по основному названию, но и по дополнительным реквизитам (информационным полям), чтобы я мог найти нужную запись по любому из ее известных мне атрибутов (например, по ID, ИНН или альтернативному наименованию).

----

h3. Описание реализации:
Задача требует синхронной доработки Backend и Frontend частей платформы.

# *Backend-часть (Доработка API поиска):*
** Необходимо доработать обработчик команды {{data.list}} (или соответствующий метод, отвечающий за выборку данных для ФВД).
** Бэкенд должен научиться принимать от фронтенда массив полей для поиска и корректно объединять их условием *ИЛИ (OR)* при формировании SQL-запроса к БД.
** _Пример ожидаемой логики:_ Если с фронта приходит строка "ЛПХ Шишко" и указаны поля {{name}} и {{ent_name}}, запрос к БД должен искать совпадения как {{name LIKE '%ЛПХ Шишко%' OR ent_name LIKE '%ЛПХ Шишко%'}}.

# *Frontend-часть (ФВД):*
** Изменить формирование объекта {{where}} при отправке запроса на бэкенд в режиме «Поиск без лимита». 
** При формировании запроса необходимо динамически собирать массив полей: брать *основное поле* компонента + проверять настройки секции *«ИНФОРМАЦИОННЫЕ ПОЛЯ»* в конструкторе. Все выбранные там дополнительные поля должны передаваться в запрос для фильтрации.
** *Исследовательская подзадача (ВАЖНО):* В настройках секции «Информационные поля» присутствует тумблер *«Показ внутри меню»*. Необходимо проанализировать легаси-код и определить его влияние:
*** Если тумблер _включен_, поле отображается в выпадающем списке и участвует в поиске (ожидаемое поведение).
*** Если тумблер _выключен_, необходимо выяснить: должно ли это поле участвовать в формировании запроса на поиск? (Логика по умолчанию: если поле выбрано в конфигурации, оно должно участвовать в поиске *всегда*, а тумблер должен отвечать только за визуальный рендеринг текста внутри пункта меню. Разработчику необходимо подтвердить эту гипотезу при реализации или сохранить старое легаси-поведение).

----

h3. Технические требования и ограничения
# *Производительность:* Объединение результатов поиска должно происходить *строго на стороне БД/Бэкенда*. Выполнение нескольких параллельных запросов с фронтенда с последующей склейкой массивов на клиенте *не допускается*.
# *Обратная совместимость:* 
** Сохранить текущую стилизацию компонента и логику рендеринга пунктов меню.
** Убедиться, что *всплывающие подсказки* (tooltips), появляющиеся при наведении (задержке курсора) на элемент выпадающего списка, продолжают работать корректно и отображают актуальные данные выбранной сущности.
# *Универсальность:* Доработка бэкенда должна быть реализована абстрактно и масштабируемо, чтобы возможность фильтрации массива полей по условию "ИЛИ" могла быть переиспользована в других частях системы в будущем.

----

h3. Критерии приёмки (AC)
* AC1. *Формирование payload (Frontend):* При включенном серверном поиске и наличии выбранных «Информационных полей» в настройках компонента, фронтенд корректно формирует объект запроса, передавая на бэкенд все необходимые ключи/колонки для поиска.
* AC2. *Мульти-поиск (Backend):* Бэкенд успешно обрабатывает запрос с несколькими полями, применяя оператор ИЛИ. Возвращаемый массив данных содержит записи, где искомая строка встречается *хотя бы в одном* из переданных полей.
* AC3. *Обработка опции «Показ внутри меню»:* Разработчиком проанализировано влияние этой настройки. При её выключенном состоянии визуальное отображение дополнительных данных скрывается, но логика поиска (включать ли скрытое поле в payload) работает предсказуемо и не вызывает ошибок в компоненте.
* AC4. *Сохранность легаси (Подсказки):* При наведении на элемент выпадающего списка корректно отрабатывает всплывающая подсказка с релевантными данными (как при локальном, так и при серверном поиске).
* AC5. *Производительность:* Поиск по нескольким колонкам выполняется в рамках *одного* HTTP-запроса на бэкенд. Зависаний интерфейса при вводе не наблюдается.
* AC6. *Обратная совместимость:* Компоненты «Выпадающий список», у которых *не* настроены информационные поля, продолжают работать штатно (поиск только по основному наименованию).
