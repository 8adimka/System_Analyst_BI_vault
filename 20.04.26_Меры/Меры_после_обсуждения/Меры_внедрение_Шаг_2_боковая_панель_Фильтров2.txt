h3. 1. Контекст и цель задачи.

Меры уже используются на полках *«Фильтры»* поддерживаемых визуализаций, включая *«Контейнер с фильтрами»*. Правая боковая панель фильтров дашборда позволяет централизованно управлять отбором, однако поддержка Мер в её настройках на данный момент неполна.

*Требуется* обеспечить полноценную работу фильтров по Мерам в правой панели Фильтров, включая настройки *«Зависит от»* и *«Сортировка по другому полю»*, наравне с обычными и вычисляемыми полями.

Замена обычного поля эквивалентной валидной Мерой должно сохранять пользовательское поведение правой панели с учётом эффективного типа и агрегированности результата.

Действующие правила фильтрации, настройки панели и поведение визуализаций сохраняются без изменений. Переиспользуются общие компоненты, контракты Мер и механизмы обработки ошибок.

----

h3. 2. Интерфейс и поведение правой панели.

h4. 2.1. Источники, объединение и применение фильтров.

* Источники фильтров панели — пилюли с полок *«Фильтры»* отдельных визуализаций, *«Контейнера с фильтрами»* и *«Иерархического фильтра»*. Размещённая на такой полке Мера включается в панель по тем же правилам, что обычное или вычисляемое поле.
* В режиме просмотра дашборда Меры доступны в панели фильтров в разделах *«Общие»* и *«Локальные»* (для выбранной визуализации), а также при создании, сохранении и переключении *«Наборов фильтров»*. В режиме редактирования дашборда доступны действующие настройки этих фильтров.
* Общие фильтры объединяются по {{alias}} независимо от набора данных и вида источника (обычное поле, вычисляемое поле, Мера). Например, поле набора A и Мера набора B с алиасом «Регион» образуют один общий фильтр «Регион». Разные алиасы дают разные фильтры. Отдельная маркировка общего фильтра как Меры не используется.
* В случае наличия нескольких наборов данных для одного фильтра, источник списка значений общего фильтра можно задать через настройку *«Основной набор данных»*. Заданные, через боковую панель фильтров, *условия* применяются к соответствующим визуализациям-получателям через пилюлю, размещенную на полке *«Фильтры»*, через её набор данных. Различия доступных значений и типов между объединёнными источниками продолжают обрабатыватся *действующим механизмом*.
* Изменение фильтра из панели фильтров или контейнера с фильтрами синхронизируются по действующим правилам.
* Вид элемента управления, доступные операции, одиночный и множественный выбор, сравнение, диапазоны, поиск и обработка пустых значений определяются эффективным типом результата размещения. Для Меры с определенным типом используются те же элементы, что и для обычного поля аналогичного типа.
* Добавление, удаление и изменение размещений Мер на полках «Фильтры» поддерживаемых визуализаций отражается в правой панели по действующим правилам актуализации фильтров.

h4. 2.2. Настройки в панеле фильтров в режиме редактирования дашборда.

|| Настройка || Требование для Мер ||
| Тип фильтра | Доступность режимов «По значению», «По диапазону», «Автофильтр» и соответствующие элементы управления — как для обычного поля того же эффективного типа |
| Автофильтр | Сохраняются варианты {{min/max}}, значение по умолчанию {{—}} и действующее применение к значениям фильтра |
| *Зависит от* | В действующий список родительских фильтров добавляются подходящие Меры, используемые в фильтрах дашборда, с учётом набора данных настраиваемого фильтра. Поддерживаются комбинации «поле → поле», «поле → Мера», «Мера → поле», «Мера → Мера»; текущий механизм формирования и ограничения списка и семантика зависимости сохраняются (п. 5) |
| Сброс | По умолчанию выключен; при включении — «Значения при сбросе»: «Все», {{min}}, {{max}}. Сброс работает по текущим правилам |
| *Сортировка по другому полю* | По умолчанию {{—}}. В существующий селектор добавляются валидные совместимые Меры набора данных настраиваемого фильтра. Список значений сортируется по вычисленному результату выбранной Меры; направление сортировки и обработка равных/{{null}} значений — по действующим правилам (п. 5) |
| Основной набор данных | Выбор источника списка значений сохраняется, включая общий фильтр из полей и Мер разных наборов |
| Обязательный фильтр | При незаполненном обязательном условии запросы соответствующих визуализаций не отправляются; загрузка вариантов самого фильтра работает штатно |
| Ограничение по количеству элементов | Доступно при включённой обязательности: {{0}} — без ограничения, положительное число — максимально допустимое количество выбранных элементов |

*Настройка «Зависит от»:* выбранные значения в фильтре, назначенным в «Зависит от», ограничивают список доступных значений дочернего фильтра. Например, выбор федерального округа ограничивает список доступных для выбора регионов. Изменение выбора родителя обновляет дочерние варианты и применимый выбор по действующему механизму, включая сценарии на несколько зависимостей и производный фильтр.
Фильтр по Мере может использовать и использоваться в настройке «Зависит от» по тем же правилам, что и обычные поля.

h3. 3. Требования к реализации.

h4. 3.1. Фронтенд.

* Проверить отображение и подключить, при необходимости, к правой панели представление фильтров по Мерам из конфигураций визуализаций и контейнеров. Переиспользовать текущие компоненты фильтров и элементы управления соответствующих типов данных.
* Расширить селекторы *«Зависит от»* и *«Сортировка по другому полю»* для выбора Мер по общим правилам допустимости и с сохранением существующих ограничений формирования кандидатов. Повторно выбранная в разных настройках Мера сохраняет независимые ссылки и параметры использования.
* Для фильтров (в том числе смешанных, по одному алиасу) сохранять существующую синхронизацию панели, контейнера и получателей, локальность, выбор основного набора, обязательность и работу наборов фильтров.
* При изменении метаданных Меры актуализировать её доступность, тип контрола, совместимость и отображаемое название. Изменение {{alias}} влияет на штатное объединение общих фильтров, но не подменяет идентификатор самой Меры в визуализациях.

h4. 3.2. Бэкенд и запросы данных.

Метаданные предоставляются объектом {{datasets}} через команду {{get.full}}; запросы значений и данных используют {{POST /v1/api/recordsets/<dataset_id>}}, общий контракт backend-Шага 2 ([MB-5035|https://jira.modusbi.ru/browse/MB-5035]) и локальная агрегация ([MB-5654|https://jira.modusbi.ru/browse/MB-5654]).

* Списки значений, поиск, {{min}}/{{max}} и сортировка (в том числе по Мере) получают вычисленные значения в штатном контексте запроса фильтра. Источник сортировки не становится дополнительным условием отбора. Сохраняются действующие ограничения доступа к данным, дедупликация вариантов и обработка пустой выборки.
* Условие по *неагрегированной Мере* передаётся через {{WHERE}}; по *агрегированной Мере* — через {{having.items}}/{{HAVING}} по общим контрактам Мер. Учитывается эффективный результат именно фильтрующего размещения, а не функция другого размещения той же Меры.
* Каждый получатель значений из общего фильтра применяет условие по полю или Мере, размещенной на его полке «Фильтры», в собственном наборе данных и контексте группировки. Сохраняются действующая логика и настройки фильтрации. Пустое необязательное условие не ограничивает запрос.
* При загрузке значений зависимого фильтра учитываются действующие условия фильтров выбранных в настройке «Зависит от» (фильтр-родитель). Для агрегированного родителя условие передаётся через {{HAVING}} с корректным контекстом группировки запроса значений; специфика этого контекста и нескольких родителей уточняется в п. 5.
* При неразрешимой ссылке или недопустимом контексте вычисления возвращается контролируемая ошибка. Условие не исключается автоматически ради возврата нефильтрованных данных.

h4. 3.3. Конфигурация, ссылки и совместимость.

* При обращении к конкретной Мере, в том числе из связанных настроек, её идентичность определяется по {{type = "measure"}}, системному {{name}} и {{datasetId}}. Ссылки на общие фильтры в настройках панели сохраняют действующий механизм связи - {{alias}} используется для объединения фильтров, но не заменяет ссылку на конкретную Меру.
** Настройка «Сортировка по другому полю» может ссылаться непосредственно на конкретную Меру как источник вычисленных значений.
** Настройка «Зависит от» может получать значения из текущего логического фильтра панели по {{alias}}.
* Актуальные {{expression}}, {{alias}}, {{data_type}}, {{is_aggregated}} и {{status}} берутся из метаданных набора. Обновление выражения применяется при следующем запросе без пересохранения отчёта; изменения типа и агрегированности повторно проверяют допустимость существующих размещений и настроек.
* Сохранение, повторное открытие, копирование, штатный сброс отчёта и переключение наборов фильтров восстанавливают ссылки, выбранные условия и настройки по действующим правилам.
* Отчёты без Мер работают без миграции. Совпадение алиасов между наборами не гарантирует наличие конкретной Меры в другом наборе: если дополнительная настройка формирует неразрешимую межнаборную ссылку, применяется существующая обработка ошибки.

h3. 4. Ошибочные состояния и восстановление.

Применяются общие правила [MB-5884|https://jira.modusbi.ru/browse/MB-5884] с учётом интерфейса правой панели дашборда и общей стилизации портала.

* Невалидная, отсутствующая либо несовместимая Мера недоступна для *нового* выбора в настройках *«Зависит от»* и *«Сортировка по другому полю»*. Ранее выбранная Мера и её настройки остаются сохранёнными; автоматическая очистка или перепривязка не выполняется.
* Ошибочное активное использование выделяется красной подсветкой (ореол) в правой панели фильтров в режиме настройки дашборда для соответствующего поля-фильтра и проблемной настройки (в соответствии со стандартным оформлением портала); для селекторов и служебных индикаторов применяются общие правила MB-5884; причина ошибки отображается по общим правилам для Мер в ошибочном состоянии (в настройках фильтруемой визуализации). Сохранённая, но неиспользуемая настройка не блокирует запросы.
* Ошибка получения списка значений показывается непосредственно в фильтре; неполный или устаревший список не выдаётся за актуальный. Сохранённый отбор не теряется. Если ошибочная Мера участвует в активном условии запроса получателя, он обрабатывается общей ошибкой без игнорирования условия. Независимые исправные фильтры и визуализации продолжают работать, если не зависят от ошибочного использования.
* После исправления определения Меры и получения актуальных метаданных соответствующие фильтры и настройки восстанавливаются без повторного выбора Меры.

h3. 5. Открытые технические вопросы:

# *Формирование списков.* Подтвердить фактический источник и ограничения списков *«Зависит от»* и *«Сортировка по другому полю»* для общего фильтра с несколькими наборами данных. Для первого списка — требуется ли, помимо существования родительского фильтра дашборда, размещение Меры-родителя на полке фильтров настраиваемой визуализации; для второго — требуется ли предварительное размещение Меры на полках. Для Мер применяются аналогичные подтверждённые действующие правила актуальные для полей.
# *Агрегированные значения.* Подтвердить применяемые после MB-6012 состав и группировку запросов значений исходно агрегированной Меры, зависимого фильтра с агрегированным родителем и сортировки по агрегированной Мере, в том числе при нескольких родителях и производном фильтре. Сквозная приёмка соответствующих сценариев требует согласованного контекста расчёта.

h3. 7. Критерии приёмки (AC):

*AC.1 — Общие и локальные фильтры:*
* *Дано:* на дашборде есть поле набора A и Мера набора B с общим алиасом, Мера с другим алиасом и локальный фильтр;
* *Когда:* пользователь открывает панель, выбирает визуализацию, задаёт и снимает отбор в панели и контейнере;
* *Тогда:* совпадающие алиасы представлены одним общим фильтром, остальные — отдельно; локальные фильтры и синхронизация выбора работают по существующим правилам, нужные получатели обновляются.

*AC.2 — Источник значений и настройки:*
* *Дано:* общий фильтр объединяет источники с разными значениями; имеются эквивалентные фильтры по полям и Мерам строкового, числового и типа даты;
* *Когда:* меняют «Основной набор данных», тип фильтра, параметры «Автофильтр» ({{—}}/{{min}}/{{max}}), настройки сброса и выполняют допустимые для соответствующего типа операции отбора;
* *Тогда:* варианты получены из выбранного источника; доступность настроек, элементы управления и результаты отбора совпадают с эквивалентными обычными полями.

*AC.3 — Настройка «Зависит от»:*
* *Дано:* настроены зависимости «поле → поле», «поле → Мера», «Мера → поле», «Мера → Мера» (родитель → дочерний фильтр), включая агрегированную Меру-родителя и поддерживаемые текущим механизмом цепочки зависимостей;
* *Когда:* выбирают родительский фильтр и изменяют его значения;
* *Тогда:* доступность Мер в списке настройки соответствует подтверждённым правилам п. 5; список значений дочернего фильтра и его выбор обновляются по действующему механизму.

*AC.4 — Настройка «Сортировка по другому полю»:*
* *Дано:* валидная Мера возвращает значения, порядок которых отличается от порядка вариантов фильтра;
* *Когда:* Меру выбирают в настройке «Сортировка по другому полю» и загружают значения;
* *Тогда:* список упорядочен по вычисленному результату Меры; параметр направления сортировки, получаемые пустые значения обрабатываются по действующим правилам как для эквивалентного поля.

*AC.5 — Обязательность и ограничение выбора:*
* *Дано:* фильтр по Мере отмечен обязательным; заданы лимиты {{0}} и положительный {{N > 0}};
* *Когда:* обязательное условие пусто, затем заполнено; пользователь пытается превысить лимит;
* *Тогда:* запросы соответствующих получателей не отправляются до заполнения обязательного фильтра, при заполнении - отправляются; {{0}} не ограничивает количество, положительный лимит соблюдается по штатным правилам.

*AC.6 — Неагрегированные и агрегированные условия:*
* *Дано:* есть фильтры по неагрегированной Мере и исходно агрегированной Мере;
* *Когда:* применяют поддерживаемые условия отбора, включая проверку {{null}} в применимых сценариях, затем снимают отбор;
* *Тогда:* условие фильтра по неагрегированной Мере применяется через {{WHERE}}, а по исходно агрегированной Мере — через {{HAVING}} с учётом контекста получателя. Локальная агрегация размещения Меры на другой полке не переносится в условие получателя; снятие отбора сохраняет остальные фильтры.

*AC.7 — Сохранение, наборы и производный фильтр:*
* *Дано:* Меры используются в фильтрах и настройках «Зависит от» и «Сортировка по другому полю»; настроен производный фильтр по агрегированной Мере с родительским условием «Зависит от» и переменными отчёта;
* *Когда:* отчёт сохраняют, открывают повторно, копируют, выполняют штатный сброс и переключают наборы фильтров;
* *Тогда:* при сохранении и повторном открытии восстанавливаются ссылки, выбор и настройки; сброс и переключение наборов фильтров работают по действующим правилам.

*AC.8 — Изменение метаданных:*
* *Дано:* Мера используется в общем фильтре и настройках «Зависит от» и «Сортировка по другому полю»;
* *Когда:* меняются {{alias}}, {{expression}}, {{data_type}}, {{is_aggregated}} или {{status}} и обновляются метаданные;
* *Тогда:* идентичность выбранной на полке «Фильтры» Меры по {{name}}/{{datasetId}} сохраняется, объединение фильтров по алиасу и совместимость пересчитываются, новое выражение используется без пересохранения конфигурации.

*AC.9 — Ошибка и восстановление:*
* *Дано:* Мера ранее выбранная в качесвте фильтра или в настройках «Зависит от» и «Сортировка по другому полю» стала невалидной, несовместимой или отсутствует в наборе данных; также имеется независимый исправный фильтр;
* *Когда:* открывают настройки, проверяют доступность Меры для нового выбора, выполняют запрос с проблемной Мерой и затем устраняют причину ошибки;
* *Тогда:* Мера недоступна для нового выбора с селекторах настроек правой боковой панели, но ранее сохранённая ссылка и отбор не удаляются; в режиме редактирования дашборда проблемная настройка и соответствующее ошибочное использование выделяются красной подсветкой. Активное ошибочное условие не игнорируется, независимые запросы работают, неиспользуемая настройка их не блокирует. После исправления работа восстанавливается без повторного выбора Меры.

*AC.10 — Обратная совместимость:*
* *Дано:* существующий отчёт без Мер и отчёт с Мерами, включая сценарии с использованием разных наборов данных в дашборде;
* *Когда:* выполняют открытие боковой панели фильтров, поиск вариантов значений для фильтрации и в селекторах настроек, выбор, применение и сброс;
* *Тогда:* старые отчёты работают без миграции, доступ к данным и поведение обычных полей сохранены; отсутствие {{datasets.measures[]}} не вызывает ошибки, а неразрешимая межнаборная ссылка обрабатывается действующим механизмом.

h3. 4. Также уточняю общую логику работы агрегированных Мер-фильтров при использовании ими настроек «Зависит от» и «Сортировка по другому полю».

---

h4. 1. Проблематика и предлагаемое решение.

Пример работы "агрегированного фильтра" можно посмотреть в дашборде [https://dev.modusbi.ru/report/809].

У агрегированной Меры-фильтра результат выпадающего списка может зависеть от контекста группировки.

Например, Мера с выражением 'SUM("amount")'
* И наборе Данных:
|| Город	|| amount ||
| Москва |	100 |
| Москва |	50 |
| Тула |	40 |

* При группировке по городу возвращает два результата:
** Москва — 150.
** Тула — 40.
* Без группировки по городу результат будет один — 190.

На данный момент предлагаю реализовать аналогичное поведение, как сейчас данная ситуация разрешается для вычисляемого поля с агрегированным выражением {{SUM("amount")}} размещённого в «Контейнере с фильтрами».

* При отсутствии группировки и ограничивающих условий в списке значений отображается один результат — сумма по всему набору данных ({{190}} для тестового набора).
* Другие фильтры и выбранные в них значения сами по себе не влияют на списки значений друг друга. Для ограничения значений "дочернего" фильтра необходимо задать "родительский" фильтр в настройке *«Зависит от»*.
* В текущей реализации для фильтра по вычисляемому полю нельзя настроить требуемую зависимость «Зависит от». Для фильтров по Мерам такая возможность предусматривается.

Таким образом, для агрегированной Меры предлагается использовать общий механизм зависимостей фильтров: контекст расчёта значений определяется действующими условиями выбранных родительских фильтров.

---

h4. 2. Логика получения значений зависимого фильтра по агрегированной Мере.

* Если настройка *«Зависит от»* не задана либо родительские фильтры не ограничивают данные, агрегированная Мера рассчитывается по всему доступному набору данных в контексте запроса списка значений. Например, {{SUM("amount") = 190}}.
* Если в настройке «Зависит от» указан родительский фильтр с активным отбором, его условие учитывается при получении списка значений дочернего фильтра. В расчёте остаются только строки, соответствующие выбранным значениям родителя. Именно по этим строкам производится итоговая агрегация значений.
** т.е. если дочерний фильтр создан на основе агрегированной Меры, её выражение вычисляется *после ограничения исходных строк условиями родителей*. В выпадающем списке отображается агрегированный результат по оставшимся данным.
* Выбор нескольких значений родительского фильтра учитывается по действующей логике отбора: Мера рассчитывается по всем строкам, удовлетворяющим совокупному условию. Автоматическая группировка по каждому выбранному значению родителя не добавляется.
* При изменении либо снятии отбора родителя список значений дочернего фильтра пересчитывается по действующему механизму зависимостей.

Например, если для фильтра по агрегированной Мере {{SUM("amount")}} в настройке *«Зависит от»* выбран фильтр «Город», результат будет следующим:

|| Выбор в фильтре «Город» || Значение дочернего фильтра по SUM("amount") ||
| Отбор не задан | 190 |
| Москва | 150 |
| Тула | 40 |
| Москва и Тула | 190 |

Аналогично, если агрегированный фильтр зависит от фильтра «Федеральный округ», выбор «Центральный федеральный округ» ограничивает исходные строки регионами этого округа. Агрегированная Мера рассчитывается только по этим строкам, а не по всему набору данных.

*Важно:* Это касательно значений выпадающего списка для задания значений фильтра, а применение этих фильтров уже связано в визуализациями потребителями и условие фильтрации, применяемое через {{HAVING}}, зависит от контекста и применяемой групировки визуализации-потребителя. Данная функциональность не должна смешиваться.
