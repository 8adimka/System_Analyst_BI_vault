h3. Контекст и проблематика.
* В реляционных базах данных оператор {{HAVING}} применяется для фильтрации результата агрегатного запроса после расчёта агрегатов. В зависимости от структуры запроса и SQL-диалекта явный {{GROUP BY}} может присутствовать или отсутствовать.
* Сводная таблица в нашей системе зачастую представляет собой многоуровневую иерархическую структуру, 
которая под капотом генерирует дерево независимых SQL-запросов для каждого уровня раскрытия. 

* *Проблема:* В текущей реализации портала вычисляемое поле на полке «Фильтры» с типом отбора {{HAVING}} 
применяется либо ко всем уровням вложенности запроса, либо не применяется вообще. 
Это приводит к искажению данных: например, если аналитик хочет отфильтровать убыточные _месяцы_ ({{HAVING SUM(Sales) < 0}}), 
а система может отсечь и прибыльные дни внутри убыточного месяца, и убыточные дни внутри прибыльного месяца, 
ломая логику детализации и общие итоги. 

----
h3. Текущее решение.
На данный момент корректная фильтрация агрегатов _по конкретному уровню иерархии_ в сводной таблице *не реализована*. 

Существует системная переменная {{\!ROW_LEVEL\!}}, которая при использовании в вычисляемом поле позволяет 
вывести дополнительный столбец в сводной таблице, где каждой строке соответствует технический идентификатор
поля её уровня вложенности. Однако, *применить на её основе {{HAVING}}-фильтр* к конкретному уровню иерархии 
в настоящий момент *не представляется возможным*.

Для виджета типа «Таблица» выбор типа отбора HAVING в UI уже доступен при добавлении вычисляемого поля на полку «Фильтры». 
Однако текущая реализация HAVING для плоских таблиц также содержит ряд некорректных поведений, 
которые устраняются настоящей постановкой (Раздел 2.3, 4.2). 

----
h3. Цель и бизнес-ценность.

Внедрение настройки применения {{HAVING}}-фильтра к конкретным уровням
иерархии (измерениям) позволит:

* Аналитикам точно управлять контекстом фильтрации агрегатов в иерархических
  сводных таблицах без знания системных переменных и SQL.
* Обеспечить корректную работу {{HAVING}}-фильтра в плоских таблицах с агрегацией — в том числе 
при использовании через общую панель фильтров.
* Закрыть частые клиентские запросы на специфическую фильтрацию в сводных таблицах.
* Создать семантически устойчивую привязку фильтра к *уровню иерархической вложенности* (для сводных таблиц).
* Обеспечить совместимость общего механизма {{HAVING}} с обычными полями, вычисляемыми полями и связанным механизмом Мер.

Настоящая постановка описывает самостоятельный общий механизм уровня-специфичной {{HAVING}}-фильтрации. Основной фокус — обычные и вычисляемые поля; особенности создания, валидации и runtime-обработки Мер описываются в связанных постановках по Мерам и не входят в рамки настоящей задачи. Шаги 1–3 ниже являются подэтапами этой постановки и не совпадают с этапами внедрения Мер.

----
h3. Привязка к «Измерению» (полю иерархии).

Основная концепция: использовать *семантическую привязку к идентификатору поля* (колонки измерения).

В метаданных фильтра будет храниться *массив идентификаторов целевых измерений* — 
полей виджета, для уровней которых данный {{HAVING}}-фильтр должен быть активен. 
Frontend-компонент формирования runtime payload для каждого запроса уровня определяет, нужно ли включить условие {{HAVING}} с учётом текущего измерения и настроек фильтра. Бэкенд получает канонический объект {{having}} и формирует итоговую SQL-клаузу {{HAVING}}.

Для плоских таблиц понятие «уровня» отсутствует — там применяется упрощённый алгоритм, описанный в *Разделе 2.3*.

----
h3. 1. Пользовательский интерфейс.

Доработки затрагивают настройки {{HAVING}}-фильтра при добавлении обычного или вычисляемого поля на полку «Фильтры» виджета типа «Сводная таблица». Ниже пользовательский сценарий раскрыт на примере вычисляемого поля; алгоритм выбора уровней не зависит от происхождения условия.

* *Шаг 1:*
Обеспечить базовую доступность {{HAVING}} как типа отбора для вычисляемых полей в {{UI}} сводной таблицы — 
аналогично уже реализованной функциональности для плоских таблиц. 
Это является самостоятельным подэтапом и открывает возможность использования {{HAVING}} через обходные пути 
даже до полного внедрения механизма привязки к уровням иерархии.
Аналитик перетаскивает вычисляемое поле на полку «Фильтры», нажимает *«Редактировать»* и вводит формулу 
(например, {{SUM("СуммаДоходРасходКО")}}), а в пункте *«Тип отбора»* (добавить в Сводные таблицы аналогично реализации в Таблицах) выбирает {{HAVING}}.

* *Шаг 2:* 
Появляется новый блок настроек *«Применять на уровнях детализации»*.
Блок отображается *только* при выборе типа отбора {{HAVING}}. При типе {{WHERE}} данный блок скрыт (не актуален).
Блок содержит *переключатель режима (Radio buttons)*:
** (•) *Ко всем уровням* — поведение по умолчанию; сохраняет _обратную совместимость_.
{{HAVING}} добавляется в SQL для каждого уровня иерархии, как это было раньше.
** ( ) *К выбранным уровням* — включает новый механизм точечного применения.

* *Шаг 3:* 
При выборе пункта «К выбранным уровням» разворачивается список чекбоксов.
Список формируется *динамически* на основе всех полей (измерений), которые в
данный момент размещены на полках «Строки/Категории», «Столбцы» и «Детализация» данной сводной таблицы.
Названия чекбоксов соответствуют алиасам полей (при наличии), а при отсутствии - техническим идентификаторам.
** Пользователь ставит галочки напротив интересующих его полей и нажимает «Сохранить».
Система сохраняет конфигурацию фильтра в JSON-метаданных отчёта. Пользователь может выбрать несколько уровней 
для применения фильтрации.
** В режиме «К выбранным уровням» должен быть выбран хотя бы один уровень. При пустом выборе сохранение блокируется с понятным сообщением о необходимости выбрать уровень либо переключиться в режим «Ко всем уровням».

*Важно:*
* Чекбоксы обновляются динамически при изменении состава полей на полках.
* Если поле удалено из иерархии, соответствующий чекбокс исчезает. 
* Ранее выбранные чекбоксы для *оставшихся* полей сохраняют своё состояние и *не сбрасываются* 
при перестроении виджета (изменении порядка полей, добавлении новых измерений, переименовании).
* Если удалено единственное целевое измерение фильтра, система показывает предупреждение: 
_«Измерение [Имя] удалено из таблицы. Фильтр [Имя] переведён в режим "Ко всем уровням".»_ и 
автоматически переключает {{apply_mode}} в {{all}} и сохраняет {{target_dimensions = []}}.
* Если удалено одно из нескольких целевых измерений, его идентификатор удаляется из {{target_dimensions}}, остальные выбранные измерения и режим {{apply_mode = "selected"}} сохраняются.
* Порядок чекбоксов соответствует порядку полей в виджете.
* Tooltip при наведении на чекбокс: _«HAVING будет применяться только в запросах, 
где данное поле является текущим уровнем агрегации»_.

----
h3. 2. Логика формирования runtime payload и генерации SQL.

h4. 2.1. Структура метаданных фильтра.

В JSON-конфигурации виджета каждый {{HAVING}}-фильтр, для которого используется уровень-специфичное применение, получает параметры {{apply_mode}} и {{target_dimensions}}. Существующая структура метаданных обычного или вычисляемого фильтра не меняется; нормативным расширением настоящей постановки являются только эти два параметра. Остальные ключи в примере ниже иллюстрируют текущую конфигурацию вычисляемого фильтра и должны быть сверены с фактической схемой соответствующего типа фильтра:

{code:json}
{
  "filters": [
    {
      "id": "847b1ec3-bbf8-4365-85fb-c4fca2a06e2e",
      "type": "calculated",
      "filter_mode": "HAVING",
      "expression": "SUM(\"СуммаДоходРасходКО\")",
      "condition": "> 1000000",
      "apply_mode": "selected",
      "target_dimensions": ["col_month"]
    }
  ]
}
{code}

|| Поле || Тип || Описание ||
| {{filter_mode}} | string | {{WHERE}} или {{HAVING}} |
| {{apply_mode}} | string | {{all}} — применять ко всем уровням иерархии; {{selected}} — только к явно выбранным |
| {{target_dimensions}} | string[] | Массив стабильных идентификаторов (ID) целевых полей-измерений. При {{apply_mode = "selected"}} массив непустой; при {{apply_mode = "all"}} — пустой |

*Важно:* 
В {{target_dimensions}} хранятся *внутренние идентификаторы полей*
({{col_month}}, {{col_year}} и т.д.), а не пользовательские алиасы («Месяц»,
«Год»). Это обеспечивает устойчивость привязки к полю даже при переименовании
колонок пользователем.

Приведённая структура описывает метаданные обычного или вычисляемого фильтра и не является контрактом фильтра по Мере. Для Меры используются её специализированные метаданные: {{apply_mode}} и {{target_dimensions}} размещаются во вложенном объекте {{filter}} вместе с {{mode}}, {{values}}, {{operators}} и при необходимости {{not}} / {{logicOr}}. Поля определения Меры, включая {{expression}}, в конфигурацию визуализации не копируются.

{{condition}} в приведённой сохраняемой конфигурации вычисляемого фильтра не следует смешивать с полем {{having.condition}} runtime payload.

При формировании запроса данных к {{/v1/api/recordsets/<dataset_id>}} frontend передаёт {{having}} в канонической объектной форме:

{code:json}
{
  "having": {
    "condition": "SUM(\"СуммаДоходРасходКО\") > 1000000",
    "items": []
  }
}
{code}

* {{having.condition}} содержит готовое строковое SQL-условие по обычным и вычисляемым полям.
* {{having.items}} содержит структурные условия по Мерам, если они участвуют в запросе. Условия по обычным и вычисляемым полям в {{items}} не передаются.
* {{having.condition}} и условия из {{having.items}}, а также несколько элементов {{items}}, объединяются бэкендом через {{AND}}. Параметр {{logicOr}} фильтра по Мере влияет только на объединение пар {{values}} / {{operators}} внутри соответствующего элемента {{items}}.
* При отсутствии Мер frontend передаёт пустой массив {{items}}. Если нет строкового условия по обычным или вычисляемым полям, {{condition}} передаётся пустой строкой.
* Новый frontend всегда формирует {{having}} как объект с {{condition}} и {{items}} и не отправляет голый массив. Для обратной совместимости бэкенд продолжает принимать голый массив и трактует его как {{items}}.

Замена условия обычного или вычисляемого поля на структуру {{values}} / {{operators}} не требуется: в рамках контракта Мер эта структура относится к элементам фильтра по Мере.

----
h4. 2.2. Алгоритм инъекции {{HAVING}} для сводной таблицы (иерархической).

Данный алгоритм применяется *только* к виджетам типа «Сводная таблица» 
с иерархическим раскрытием.

Алгоритм использует *метаданные виджета* и контекст запрашиваемого узла. Компонент формирования runtime payload должен однозначно знать идентификатор текущего измерения {{node_context.current_dimension_id}}.

Проверка {{apply_mode}} / {{target_dimensions}} выполняется frontend-компонентом до свёртки активных предикатов в {{having.condition}} и {{having.items}}. Эти параметры остаются настройками сохранённого фильтра и не добавляются как новые поля канонического runtime-объекта {{having}}.

Разберём на примере иерархии Год → Месяц → День.
Каждый запрос порождается с параметром *глубины раскрытия* ({{depth}}) — 
позицией текущего узла в текущей иерархической оси. На основе контекста узла определяется
*измерение текущего узла* (Current Node Dimension, CND) — то поле,
для которого данный запрос рассчитывает агрегаты:

{code}
node_context.axis_dimensions = ['col_year', 'col_month', 'col_day']
// Упорядоченный массив измерений текущей иерархической оси запроса.
// Для независимых осей строк и столбцов используется массив именно той оси,
// для узла которой формируется запрос; глобальное объединение обеих осей не используется.

depth = 0 → node_context.current_dimension_id = 'col_year'
depth = 1 → node_context.current_dimension_id = 'col_month'
depth = 2 → node_context.current_dimension_id = 'col_day'
{code}

Определение CND происходит *исключительно из метаданных*, а не из парсинга
текста {{GROUP BY}}. Это делает алгоритм совместимым с любым способом
генерации SQL: как с простыми {{GROUP BY}}, так и с {{GROUPING SETS}} /
{{ROLLUP}} / {{CUBE}}.

Если текущий механизм передаёт только {{depth}}, компонент формирования runtime payload определяет CND как {{node_context.axis_dimensions[depth]}}. Если в контексте уже передан {{current_dimension_id}}, он используется напрямую.

*Алгоритм (выполняется для каждого {{HAVING}}-фильтра по обычному или вычисляемому полю при формировании запроса текущего узла):*

{code}
inject_having(filter_config, node_context):

  CND = node_context.current_dimension_id

  Если filter_config.apply_mode = 'all':
    inject = TRUE

  Если filter_config.apply_mode = 'selected':
    inject = CND ∈ filter_config.target_dimensions

  Если inject = TRUE  → включить готовый предикат <expression> <condition>
                        в having.condition запроса текущего узла
  Если inject = FALSE → не включать данный предикат в having.condition
                        запроса текущего узла
{code}

* {{filter_config.target_dimensions}} — массив ID целевых полей из метаданных обычного или вычисляемого фильтра
* {{CND}} — стабильный ID измерения текущего узла из {{node_context.current_dimension_id}}

Алгоритм совместим с любым способом генерации SQL, так как опирается исключительно
на метаданные, а не на структуру SQL-текста.

*Важно:* Алгоритм выполняется для каждого {{HAVING}}-фильтра независимо. При наличии нескольких фильтров каждый проверяется отдельно. Все отобранные условия по обычным и вычисляемым полям объединяются через {{AND}} внутри {{having.condition}}. Если запрос также содержит {{having.items}}, строковое условие и структурные условия по Мерам объединяются бэкендом через {{AND}} в единой SQL-клаузе {{HAVING}}.

Для фильтра по Мере проверка {{apply_mode}} / {{target_dimensions}} выполняется до формирования runtime payload по тому же правилу. Если {{inject = TRUE}}, соответствующий структурный элемент Меры с {{type}}, {{name}}, {{values}}, {{operators}} и при необходимости {{not}} / {{logicOr}} включается в {{having.items}} целиком; если {{inject = FALSE}}, элемент не включается. Условие по Мере не преобразуется в строку {{having.condition}}.

*Кейс мультивыбора* (аналитик выбрал несколько чекбоксов):

{code}
target_dimensions = ['col_month', 'col_day']:

  depth=0 → CND='col_year'  → FALSE → HAVING пропускается
  depth=1 → CND='col_month' → TRUE  → HAVING добавляется
  depth=2 → CND='col_day'   → TRUE  → HAVING добавляется
{code}

----
h4. 2.3. Алгоритм инъекции {{HAVING}} для плоской таблицы.

Плоская таблица не имеет иерархического дерева запросов — для неё 
всегда генерируется *один* SQL-запрос. Понятие «уровня вложенности» 
и алгоритм CND к плоской таблице *не применяются*.

Поля {{apply_mode}} и {{target_dimensions}} в конфигурации фильтра 
для плоской таблицы *игнорируются*. Вместо этого применяется следующий 
алгоритм:

{code}
inject_having_flat(filter, widget_context):

  has_aggregate_context = запрос содержит агрегированное выражение
                          (в том числе в самом фильтре) и SQL-builder
                          поддерживает HAVING для данного запроса?

  Если has_aggregate_context = TRUE  → включить <expression> <condition>
                                       в having.condition

  Если has_aggregate_context = FALSE → не включать предикат обычного или
                                        вычисляемого поля в having.condition
{code}

Наличие агрегатного контекста нельзя определять только по полке «Значения»: агрегированное выражение может находиться в самом {{HAVING}}-фильтре, а корректный агрегатный запрос не всегда содержит явный {{GROUP BY}}.

Для обычного или вычисляемого поля сохраняется совместимое поведение: если SQL-builder не поддерживает {{HAVING}} в текущем запросе, условие не включается без ошибки SQL и без уведомления пользователю. Это правило не применяется к {{having.items}}: валидная агрегированная Мера должна быть обработана как {{HAVING}}-условие, а невалидная или несовместимая Мера отклоняется по контракту Мер контролируемой ошибкой и не игнорируется молча. Алгоритм плоской таблицы определяет применимость фильтра, но не меняет его сериализацию: обычное или вычисляемое условие передаётся через {{having.condition}}, условие Меры — структурным элементом {{having.items}}.

Таким образом, один и тот же {{HAVING}}-фильтр из общей панели фильтров 
корректно применяется как к сводной таблице (по алгоритму CND из *Раздела 2.2*), 
так и к плоской таблице с агрегацией (по алгоритму из настоящего раздела).

----
h4. 2.4. Каскадное отсечение.

Если узел (например, конкретный месяц) отсекается условием {{HAVING}}
на своём уровне, строка *физически не возвращается* в ответе API.
Фронтенд не получает узел — не отрисовывает строку — не показывает кнопку «▶» для раскрытия дочерних уровней. 
Дополнительной доработки компонента дерева не требуется: каскадное скрытие является естественным следствием
стандартной навигации.
*Возможна обратная ситуация,* при которой агрегат родительского узла (например, "Год" на уровне depth=0) 
не попадает под условие HAVING (и строка отображается), однако при раскрытии этого узла HAVING 
применяется на уровне depth=1 (Месяцы) и отсекает все дочерние строки. 
В этом случае, фронтенд должен корректно обработать пустой ответ:
* Родительская строка отображается в сводной таблице без дочерних элементов (скрыть кнопку «▶» раскрытия).

----
h4. 2.5. Устойчивость к перестроению иерархии.

Фильтр хранит *стабильный идентификатор поля* ({{col_month}}), а не его
порядковую позицию в иерархии или пользовательский алиас («Месяц»).

* *Переименование поля* («Месяц» → «Мес.»): привязка фильтра не нарушается; 
алгоритм по-прежнему сравнивает {{CND}} с {{col_month}}.
* *Перестановка полей в иерархии* (Год → День → Месяц): значение {{depth}} для поля изменится, 
но алгоритм пересчитает {{CND}} корректно на основе актуального массива {{node_context.axis_dimensions}}.
* *Добавление нового измерения*: для нового поля {{HAVING}} не применяется 
(поле отсутствует в {{target_dimensions}}); поведение для остальных уровней не меняется.
* Ранее выбранные целевые измерения (*пилюли/чекбоксы*) при любом перестроении *не сбрасываются* — 
сохраняются в метаданных фильтра по стабильному идентификатору.

----
h3. 3. Интеграция с панелью общих фильтров.

Фильтр с {{HAVING}} и заданным {{target_dimensions}} должен корректно работать не только
как *локальный фильтр виджета*, но и в *общей панели фильтров* (правая боковая панель фильтров).

h4. 3.1. Передача конфигурации.
Сохраняемая конфигурация обычного или вычисляемого фильтра, включая ссылку на поле / {{expression}}, {{condition}}, {{apply_mode}} и {{target_dimensions}}, передаётся во все связанные виджеты. Для Меры передаются {{type}}, {{name}}, {{datasetId}} и специализированный объект {{filter}}; {{expression}} Меры в визуализацию не копируется.

При связи виджетов через общую панель используется действующий механизм сопоставления полей. Сравнение с CND выполняется по стабильному идентификатору поля после такого сопоставления; если сопоставление для целевого измерения отсутствует, этот CND не считается совпавшим. Настоящая задача не изменяет правила сопоставления полей между наборами данных.

При формировании запроса данных каждый связанный виджет применяет правила Раздела 2.1: новый frontend передаёт {{having}} объектом с {{condition}} и {{items}}. Готовые условия обычных и вычисляемых полей включаются в {{having.condition}}, структурные условия по Мерам — в {{having.items}}.

h4. 3.2. Применение к сводной таблице.
Каждый связанный виджет типа «Сводная таблица» применяет алгоритм из *Раздела 2.2*, 
используя собственные метаданные и {{node_context.current_dimension_id}} для определения CND. Отбор активных фильтров выполняется до объединения их предикатов в строку {{having.condition}}; после объединения восстановить связь отдельного условия с {{target_dimensions}} невозможно.

h4. 3.3. Применение к плоской таблице.
Каждый связанный виджет типа «Плоская таблица» применяет алгоритм из *Раздела 2.3*: 
при наличии поддерживаемого агрегатного контекста {{HAVING}} включается в запрос; при его отсутствии строковое условие обычного или вычисляемого поля не включается без ошибки SQL и без уведомления пользователю. Условия по Мерам обрабатываются по контракту Мер и не должны молча теряться.
Поля {{apply_mode}} и {{target_dimensions}} при этом не используются.

h4. 3.4. Несовместимый виджет.
Если связанный виджет или его текущий запрос не поддерживает агрегатный контекст, строковое условие {{having.condition}} по обычному или вычисляемому полю не включается без ошибки SQL и без уведомления пользователю — сохраняется действующее совместимое поведение. Это правило не распространяется на {{having.items}}: условия по Мерам обрабатываются либо отклоняются контролируемой ошибкой по актуальному контракту Мер и не игнорируются молча.

Отсутствие совпадающего CND у сводной таблицы в режиме {{apply_mode = "selected"}} не является ошибкой несовместимости: в этом случае условие ожидаемо не включается в запрос нецелевого уровня по алгоритму Раздела 2.2.

h4. 3.5. Режим {{apply_mode: "all"}} в общей панели.
Фильтр передаётся в связанные виджеты как стандартный {{HAVING}} без привязки к уровню 
(текущее поведение, обратная совместимость). 
Правила совместимости из Разделов 2.3 и 3.4 применяются в полном объёме.

----
h3. 4. Устранение выявленных дефектов.

h4. 4.1. Баг: невозможность редактирования сохранённого вычисляемого фильтра.

*Описание:* При открытии ранее сохранённого вычисляемого фильтра (тип {{HAVING}}) в сводной таблице, 
изменении формулы или условия и нажатии «Сохранить» — новые значения не применяются. 
Виджет продолжает использовать старую конфигурацию фильтра. 
Единственный обходной путь — удалить фильтр и создать заново.

*Требование:* Обеспечить корректное обновление состояния (state) вычисляемого
фильтра при повторном редактировании. После нажатия «Сохранить» виджет должен
применить актуальную конфигурацию и инициировать перезапрос данных без
необходимости пересоздания фильтра.

h4. 4.2. Баг: несоответствие типа элемента управления в общей панели фильтров.

*Описание:* В настройках правой боковой панели фильтров дашборда вычисляемый 
{{HAVING}}-фильтр обозначается как «по диапазону», однако в режиме обычного использования 
правой боковой панели фильтров данный фильтр отрисовывается как «список выбора».

*Требование:* Тип компонента управления на панели фильтров должен строго 
соответствовать типу, выбранному при настройке данного фильтра.

h3. 6. Критерии приёмки (AC):
h4. AC.1 — Новый блок UI настроек HAVING
При добавлении обычного или вычисляемого поля на полку «Фильтры» сводной таблицы и выборе типа отбора {{HAVING}} отображается блок «Применять на уровнях детализации» с переключателем «Ко всем уровням» / «К выбранным уровням»: для вычисляемого поля — под полем ввода формулы, для обычного поля — в действующей форме настройки фильтра.

h4. AC.2 — Динамический список измерений
При выборе режима «К выбранным уровням» список чекбоксов корректно
отражает *актуальный* набор измерений (полей иерархии), размещённых на полках «Строки/Категории», 
«Столбцы» и «Детализация». Названия чекбоксов соответствуют пользовательским алиасам полей при их наличии, 
а при отсутствии - техническим идентификаторам. 
При изменении состава полок или переименовании полей — список обновляется автоматически; 
привязка сохранённых фильтров остаётся корректной (по идентификатору поля).
В режиме {{apply_mode = "selected"}} сохранение без выбранного уровня блокируется; при {{apply_mode = "all"}} сохраняется {{target_dimensions = []}}.

h4. AC.3 — Корректная генерация SQL: целевой уровень
* *Дано:* Иерархическая структура Год → Месяц → День с набором полей:
** depth = 0 → CND = 'col_year'   // запрос для узлов "Год"
** depth = 1 → CND = 'col_month'  // запрос для узлов "Месяц" внутри Года
** depth = 2 → CND = 'col_day'    // запрос для узлов "День" внутри Месяца
* *Когда:* Фильтр настроен с {{apply_mode = "selected"}} и {{target_dimensions = ["col_month"]}},
* *Тогда:* Оператор {{HAVING SUM(...) > N}} физически присутствует в генерируемом SQL только для запросов, 
формируемых для узлов глубины {{depth=1}} ({{CND=col_month}}).
Факт наличия оператора {{HAVING}} в запросе проверяется в БД (например,
через {{EXPLAIN}} или логи запросов).

h4. AC.4 — Корректная генерация SQL: нецелевые уровни
Для тех же настроек фильтра оператор {{HAVING}} *отсутствует* в
генерируемых SQL-запросах для узлов Уровня 1 ({{depth=0}}, {{CND=col_year}})
и Уровня 3 ({{depth=2}}, {{CND=col_day}}).

При {{apply_mode = "selected"}} и {{target_dimensions = ["col_month", "col_day"]}} условие присутствует в запросах уровней {{col_month}} и {{col_day}}, но отсутствует в запросе уровня {{col_year}}.

h4. AC.5 — Устойчивость к перестроению иерархии
При переносе полей на полках сводной таблицы (изменение порядка,
добавление новых измерений) и при переименовании полей — привязка
{{HAVING}}-фильтра не сбивается. Условие продолжает применяться к
ранее выбранному измерению, определяемому по его стабильному _идентификатору_.

h4. AC.6 — Корректное редактирование сохранённого фильтра
Пользователь может открыть ранее созданный "вычисляемый" фильтр с {{HAVING}},
изменить формулу, условие или набор целевых измерений, нажать «Сохранить» —
и новые настройки корректно применяются к данному виджету и инициируют его обновление (перезапрос данных).

h4. AC.7 — Использование в общей панели фильтров
{{HAVING}}-фильтр по обычному или вычисляемому полю корректно применяется из общей панели фильтров:
* для связанной сводной таблицы — с учётом {{target_dimensions}} по алгоритму Раздела 2.2; если ни один CND этой таблицы не соответствует {{target_dimensions}}, условие не включается в запросы её узлов;
* для связанной плоской таблицы — по алгоритму Раздела 2.3; {{apply_mode}} и {{target_dimensions}} не учитываются, поэтому отсутствие в таблице поля из {{target_dimensions}} само по себе не является причиной исключения фильтра;
* при отсутствии поддерживаемого агрегатного контекста строковое условие обычного или вычисляемого поля не включается без ошибки SQL и без уведомления; условие Меры из {{having.items}} обрабатывается по контракту Мер и не игнорируется молча.

h4. AC.8 — Корректный тип элемента управления для фильтров в общей панели фильтров
Вычисляемый {{HAVING}}-фильтр, назначенный в настройках панели фильтров под определённый тип элемента управления, 
на панели фильтров дашборда отображается в соответствии с выбранным типом.

h4. AC.9 — Обратная совместимость
Все существующие отчёты с {{HAVING}}-фильтрами (включая использующие функциональность
{{\!ROW_LEVEL\!}}) продолжают работать без изменений. Для них автоматически применяется режим 
{{apply_mode: "all"}} (эквивалент текущего поведения).
Отсутствие {{apply_mode}} и {{target_dimensions}} в существующей конфигурации логически трактуется как {{apply_mode = "all"}} и {{target_dimensions = []}}. Миграция или обязательная перезапись метаданных существующих фильтров не требуется. Существующий runtime-объект {{having}} только с полем {{condition}} продолжает поддерживаться бэкендом.

h4. AC.10 — Удаление целевого измерения
Если пользователь удаляет из полок сводной таблицы поле, являющееся единственным целевым для сохранённого {{HAVING}}-фильтра, система:
* отображает предупреждение об этом событии;
* удаляет недоступный ID из конфигурации;
* устанавливает {{apply_mode = "all"}} и {{target_dimensions = []}};
* сохраняет обновлённую конфигурацию и инициирует обновление данных виджета.

Если после удаления поля остаются другие выбранные измерения, система удаляет только ID отсутствующего поля, сохраняет {{apply_mode = "selected"}} и остальные значения {{target_dimensions}}.

h4. AC.11 — Канонический runtime payload {{HAVING}}
* *Дано:* запрос содержит {{HAVING}}-условие по обычному или вычисляемому полю;
* *Когда:* frontend формирует runtime payload запроса данных;
* *Тогда:* {{having}} передаётся объектом с полями {{condition}} и {{items}};
* *И:* готовое SQL-условие обычного или вычисляемого поля находится в {{having.condition}};
* *И:* при отсутствии Мер {{having.items}} является пустым массивом;
* *И:* новый frontend не передаёт {{having}} в форме голого массива;
* *И:* при одновременном наличии {{having.condition}} и условий в {{having.items}} бэкенд объединяет обе части и отдельные элементы {{items}} через {{AND}}; {{logicOr}} влияет только на условия внутри одного элемента Меры.

h4. AC.12 — Обработка {{HAVING}} в плоском или несовместимом запросе
* *Дано:* {{HAVING}}-фильтр передан в плоскую таблицу или другой связанный виджет;
* *Когда:* для текущего запроса поддерживается агрегатный контекст;
* *Тогда:* условие присутствует в SQL-клаузе {{HAVING}} независимо от наличия агрегированной пилюли на полке «Значения».

Если агрегатный контекст не поддерживается, строковое условие обычного или вычисляемого поля из {{having.condition}} не включается без ошибки SQL и без уведомления пользователю. Структурное условие Меры из {{having.items}} не игнорируется: оно обрабатывается либо отклоняется контролируемой ошибкой по актуальному контракту Мер.
