h3. 1. Контекст и цель задачи.

Требуется подключить общие механизмы Мер к визуализации *«Контейнер с фильтрами»* ({{chartType = "FilterControlPanel"}}), чтобы аналитик мог использовать выражения, заданные в наборе данных, для отбора данных, отображения значений фильтра и подсказок.

Сейчас контейнер настраивается через обычные и вычисляемые поля на единственной полке *«Фильтры»* ({{axes[].type = "filters"}}). После доработки Меры должны поддерживаться в тех же сценариях с учётом ограничений агрегированности. Стандартное поведение контейнера, его настроек и взаимодействия с визуализациями отчёта сохраняется.

----

h3. 2. Интерфейс и поведение фильтров.

---
h4. 2.1. Общие компоненты и полка «Фильтры».

Переиспользуемый компонент левой боковой панели с Мерами добавляется в эту визуализацию в соответствии с текущей реализацией. Общие компоненты пилюль, фильтров и редактора вычисляемых полей переиспользуются в текущей реализации. Источник Мер — {{datasets.measures[]}} выбранного *произвольного* набора данных.

* На полке можно совместно использовать обычные поля, вычисляемые поля и валидные Меры. Добавление, перестановка и удаление пилюль выполняются по действующим правилам контейнера.
* Пилюля Меры на полке *«Фильтры»* имеет стандартный салатовый цвет этой полки. Название определяется актуальным {{alias}} с учётом локального заголовка; ярлык {{AGR}} отображается при {{is_aggregated = true}}.
* Для неагрегированных Мер на полке «Фильтры» локальная агрегация доступна и применяется в тех же сценариях, что для обычных полей того же типа: функции, значение по умолчанию, возможность оставить размещение без агрегации, перенос и участие в запросах совпадают. Если сценарий требует агрегированного результата, при добавлении назначается стандартная функция обычного поля; поведение пункта *«-»* повторяет обычное поле, и размещение не остаётся без обязательной агрегации. {{is_aggregated}} и выражение исходной Меры не меняются; повторная агрегация Меры с {{is_aggregated = true}} запрещена.
* В запросах получателей условие по неагрегированному результату размещения применяется через {{WHERE}}, по агрегированному результату (исходная агрегированная Мера либо локально агрегированная неагрегированная Мера) — через {{HAVING}}. Функция, применяемая только при загрузке списка значений, не переносится в условие получателя, если этого не делает обычное поле в том же сценарии.
* Операции и элементы управления фильтром определяются эффективным типом результата размещения и существующими возможностями фильтра. Без локальной функции используется актуальный {{data_type}}; при её наличии — тип результата функции по правилам обычного поля. Контекст получения значений исходно агрегированной Меры требует уточнения по п. 5.1.
* Мера может быть использована в выражении вычисляемого поля по общим правилам. Такое вычисляемое поле может быть размещено на полке «Фильтры» и сохраняет собственный контракт {{calc}} со ссылкой на системное {{name}} Меры.
* Правая боковая панель сохраняет текущие настройки; Меры в селекторах не используются, но могут быть отображены в разделе «Значения» для выбора «Тип фильтра» и настройки параметра «Обязательный» - текущее _поведение системы_ для обычных полей должно быть полностью сохранено для Мер с учётом их специфики обработки.

---
h4. 2.2. Меню настроек пилюли, размещённой на полке «Фильтры».

|| Настройка || Требуемое поведение ||
| *«Имя поля»* | Задаёт локальный {{title}} размещения. Изменение заголовка сохраняет ссылку на Меру и не изменяет её {{alias}} в наборе данных |
| *«Значения по другому полю»* | Позволяет выбрать обычное поле либо валидную Меру текущего набора данных для отображения значений фильтра по правилам п. 2.3 |
| *«Подсказка по другому полю»* | Позволяет выбрать обычное поле либо валидную Меру текущего набора данных как источник подсказки по правилам п. 2.3 |
| *«Производный фильтр»* | Переиспользуется текущее поведение тумблера; значение по умолчанию — *ВЫКЛ* |
| *«Уровень отбора»* | Значения *0 (значение по умолчанию) / 1* и их действие сохраняются по текущей реализации |

---
h4. 2.3. Значения и подсказка по другому полю.

* В обоих селекторах Меры выбираются из текущего набора данных; предварительное размещение выбранной Меры на полке не требуется. Поддерживаются сочетания «поле → поле», «поле → Мера», «Мера → поле» и «Мера → Мера».
* Для нового выбора в селекторе доступны валидные неагрегированные Меры. Если текущий сценарий обычного поля применяет локальную функцию, для Меры используется общий механизм локальной агрегации с той же функцией и контекстом расчёта. Это не разрешает исходно агрегированные Меры в ранее ограниченных селекторах; их применимость остаётся отдельным вопросом п. 5.2.
* Используется рассчитанное значение выбранного источника. Для каждого исходного значения фильтра должна определяться не более чем одна подпись и одна подсказка в том же контексте данных. Обратная уникальность не требуется: одна подпись или подсказка может соответствовать нескольким исходным значениям. Для объединённого варианта подсказка также должна быть однозначной.
* При настройке «Значения по другому полю» список фильтра содержит только уникальные значения выбранного поля или Меры. Разные исходные значения с одинаковой подписью объединяются в один вариант; повторы в исходных строках не создают дубликаты. Например, для поля «Регион» с отображением по полю «Федеральный округ» каждый округ выводится один раз. Это текущее поведение одинаково для «Контейнера с фильтрами» и «Иерархического фильтра» и сохраняется при использовании Мер.
* Фильтрация и сохранение выбора выполняются по исходным значениям основной пилюли. Выбор объединённого варианта охватывает все соответствующие ему исходные значения в текущем контексте данных: выбор округа — все относящиеся к нему регионы. Подпись и подсказка не заменяют исходные значения отбора.
* Смена или отключение источника подписи/подсказки сохраняет исходное условие отбора. Поиск, сортировка и отображение пустых значений используют действующие правила соответствующей настройки для полей.
* При выявленной неоднозначности соответствия выводится локальная ошибка получения значений соответствующего фильтра. Произвольный выбор одного из конфликтующих значений не допускается. Формат ссылок и способ проверки соответствия уточняются по п. 5.2.

---
h4. 2.4. Применение и снятие отбора.

* Выбор одного или нескольких значений, изменение поддерживаемого условия и снятие выбора работают по текущей логике контейнера. Сохраняются область действия фильтра, взаимодействие фильтров между собой, режим «Производный фильтр» и момент применения изменений, в том числе настройка {{updateOnCloseDropdown}}.
* В запросы получателей передаются активные заполненные условия по основной Мере. Пустой выбор не создаёт предикат; проверка {{null}} считается заполненным условием. При снятии отбора удаляется соответствующее условие, остальные действующие фильтры сохраняются.
* Применяются существующие правила связей и области действия фильтров.
* Изменение фильтров отчёта обновляет результаты получателей по действующему механизму. Для Мер сохраняются текущие ограничения доступа к данным и существующие режимы загрузки и поиска значений.

h3. 3. Хранение конфигурации и получение данных.

---
h4. 3.1. Ссылки и локальные настройки.

Прямое размещение Меры в {{axes[].fields[]}} сохраняется по общему контракту: {{type = "measure"}}, системное {{name}}, {{datasetId}}, локальный {{id}} и применимые настройки пилюли. Условие фильтра хранится по общему структурному контракту Мер. Ссылки в селекторах подписи и подсказки также должны однозначно различать Меру и сохранять принадлежность набору данных.

Выражение Меры в конфигурацию не копируется. Актуальные название, выражение, агрегированность, тип и статус читаются из метаданных набора. Изменение {{alias}} сохраняет привязку и локальный {{title}}; новое выражение Меры ({{expression}}) используется при следующем получении данных без пересохранения контейнера. После получения изменённых {{is_aggregated}}, {{data_type}} или {{status}} повторно проверяется валидность любого использования Меры и заданные настройки. Локальная функция хранится и обрабатывается механизмом [MB-5654|https://jira.modusbi.ru/browse/MB-5654]: при {{false → true}} снимается и проверяется прежний запрет агрегированных Мер в соответствующем контексте; при {{true → false}} действует правило обычного поля того же типа в этом сценарии, включая стандартную функцию, если требуется агрегированный результат.

Сохранение, повторное открытие, копирование и штатный сброс восстанавливают ссылки, порядок пилюль, условия и настройки по действующим правилам, включая {{axesDefault}} и {{filtersDefault}}. Независимые размещения сохраняют собственные локальные {{id}} и параметры. При смене набора данных применяется штатное поведение.

---
h4. 3.2. Запросы значений и запросы получателей.

Метаданные предоставляет объект {{datasets}} через действующую команду чтения ({{get.full}}). Получение данных использует {{POST /v1/api/recordsets/<dataset_id>}} и общий контракт backend-Шага 2.

|| Запрос || Требуемая адаптация ||
| Значения фильтра | Без локальной функции основная Мера передаётся в {{select}} как {{type = "measure"}} с {{name}} и техническим {{alias}}; с функцией — через общий механизм локальной агрегации. Сортировка использует результат соответствующего размещения через {{order}}. Сохраняются текущие правила загрузки и устранения дубликатов |
| Значения с подписью/подсказкой | Получаются связанные исходные значения, подписи и подсказки в едином контексте данных. Адаптер сохраняет соответствие каждого отображаемого варианта всем его исходным значениям. Прямые Меры передаются по общему runtime-контракту; способ получения сочетаний должен обеспечивать поведение описанное в п. 2.3 |
| Данные визуализации-получателя | Прямое условие по неагрегированной Мере передаётся в {{where}}, по исходно агрегированной — в {{having.items}}; условие по локально агрегированному результату формируется через действующий контракт вычисляемых выражений для {{HAVING}}. Состав отображаемых полей и группировка получателя определяются его собственной конфигурацией |

* Незаполненный фильтр не участвует в условиях запроса получателя, но его Мера участвует в запросе собственного списка значений, когда этот список загружается.
* Прямые условия по Мерам сериализуются по общему контракту: оболочка {{filter}} снимается; сохраняются {{values}}, {{operators}}, {{not}}, {{logicOr}}. {{having}} передаётся объектом с {{condition}} и {{items}}; существующее {{condition}} сохраняется и объединяется с {{items}} через {{AND}}. Сочетание условий внутри фильтра и между фильтрами сохраняет действующую семантику.
* Бэкенд раскрывает актуальные выражения Мер, вложенные ссылки и переменные общим механизмом. Прямой runtime-объект Меры передаётся без копии выражения и непустых {{calc}}, {{agg}} или {{aggr}}; в {{group}} допустимы только неагрегированные результаты размещений без локальной функции. Локальная агрегация передаётся механизмом [MB-5654|https://jira.modusbi.ru/browse/MB-5654], без непустых {{calc}}, {{agg}} или {{aggr}} в прямом runtime-объекте Меры. Технические alias результата не используются как ключи определения Меры.
* Фильтрация по агрегированному результату размещения Меры выполняется в контексте группировки получателя по правилам обычного поля в том же сценарии. Если конкретный SQL-контекст не поддерживается, возвращается контролируемая ошибка; условие не игнорируется и не переносится в {{WHERE}}. Контекст собственного списка контейнера и прочие детали уточняются в открытых вопросах п. 5.1.

h3. 4. Ошибки, зависимости и совместимость.

Переиспользуются правила [https://jira.modusbi.ru/browse/MB-5884], включая оформление и сообщения с учётом прав пользователя.

* Невалидная Мера недоступна для нового размещения или выбора. Ранее сохранённая отсутствующая, невалидная или несовместимая ссылка остаётся на своём месте с признаком ошибки и применимыми настройками. Это относится и к Мерам в селекторах подписи и подсказки; ошибка дополнительного источника должна быть видна в настройке соответствующей пилюли.
* Ошибка Меры, участвующей в загрузке значений, отображается в соответствующем фильтре при выполнении этого запроса. Контейнер и независимые фильтры остаются доступны; частичный или устаревший список не выдаётся за актуальный результат. Ошибка используемого источника подписи/подсказки не скрывается его автоматическим отключением.
* Сохранённый выбор не очищается из-за ошибки загрузки списка. Если ошибочная Мера участвует в активном условии получателя, его запрос обрабатывается общими правилами ошибок; условие не отбрасывается для получения нефильтрованных данных. Если запрос получателя не использует ошибочную Меру, ошибка списка контейнера сама по себе его не блокирует.
* Неиспользуемая настройка не блокирует запрос. После исправления Меры и получения актуальных метаданных работа восстанавливается без повторного добавления ссылки.

Общий механизм зависимостей должен учитывать сохранённые ссылки на Меры на полке, в обоих селекторах и внутри выражения вычисляемого поля ({{calc}}), включая временно неиспользуемые ссылки. Реальная ревалидация и блокировка удаления по зависимостям принимаются совместно с backend-Шагом 3; до его поставки состояния проверяются на подготовленных метаданных.

Отчёты без Мер сохраняют результат и настройки без миграции. Отсутствие {{measures[]}}, пустая полка, пустая выборка, {{null}}, ноль и отрицательные значения обрабатываются по действующим правилам полей и не считаются ошибкой Меры.

h3. 5. Открытые технические вопросы.

---
h4. 5.1. Значения агрегированного фильтра.

Общий контракт определяет применение агрегированной Меры через {{HAVING}}, но не задаёт контекст получения её значений в «Контейнере с фильтрами» ({{FilterControlPanel}}). У контейнера нет полки группировки, а получатели могут иметь разную детализацию. Требуется подтвердить возможность использования агрегированной Меры на полке «Фильтры» в визуализации *«Контейнер с фильтрами»*: состав запроса списка и его группировку. Как вариант можно рассмотреть поведение вычисляемого поля на данной полке с выражением содержащим агрегацию. На этой основе определить получение значений агрегированной Меры, влияние на зависимые фильтры. В крайнем случае может потребываться пересмотр политики использования агрегированных Мер на данной полке. Сам по себе расчёт одного агрегата по всему набору не является подтверждённым решением для списка. 

Сквозная реализация и приёмка исходно агрегированных Мер зависят от закрытия этого вопроса; поддержка {{HAVING}}-фильтрации для Мер остаётся целевым сценарием. Для {{is_aggregated = false}} с локальной функцией применяются существующие контекст и группировка обычного поля в том же сценарии; этот вопрос не отменяет их поддержку.

---
h4. 5.2. Ссылки и однозначность дополнительных источников.

В настройках «Значения по другому полю» ({{nameBy}}) хранит строковое имя поля. Требуется подтвердить с разработкой совместимый формат ссылок по общему контракту Мер и отдельно определить применимость _исходно агрегированных_ Мер в селекторах подписи/подсказки. Неагрегированные Меры поддерживаются по правилам обычных полей, включая локальную агрегацию.

Действующий запрос подписи группирует данные по отображаемому полю и применяет {{MAX}} к исходному значению. Для прямой Меры непустой {{aggr}} запрещён общим контрактом; для неагрегированной Меры та же функция применяется общим механизмом локальной агрегации [MB-5654|https://jira.modusbi.ru/browse/MB-5654]. Требуется адаптировать запрос связанных значений с сохранением уникальных отображаемых вариантов и их связи со всеми исходными значениями по п. 2.3, а также определить проверку однозначности, в том числе при поиске или частичной загрузке списка. Применение локальной агрегации к {{is_aggregated = false}} повторяет обычные поля и не является открытым вопросом. Возможное расширение селекторов на {{is_aggregated = true}} требует отдельного решения и не следует из новой политики локальной агрегации.

h3. 7. Критерии приёмки (AC):

*AC.1* — Полка и меню:
* *Дано:* произвольный набор с Мерами разных типов и агрегированности;
* *Когда:* аналитик добавляет Меры вместе с обычными и вычисляемыми полями, меняет порядок и настройки пилюль;
* *Тогда:* используется общая панель Мер, оформление и доступность соответствуют п. 2.1–2.2; локальный заголовок не изменяет определение Меры, настройки разных размещений не смешиваются. Невалидную Меру добавить нельзя.

*AC.2* — Отбор по неагрегированной Мере:
* *Дано:* неагрегированная Мера без локальной функции в условии получателя с тем же результатом, что у проверяемого вычисляемого поля; получатель использует тот же набор данных;
* *Когда:* выбираются одно и несколько значений, поддерживаемая проверка {{null}}, затем выбор снимается;
* *Тогда:* состав вариантов и отфильтрованных данных совпадает с поведением аналогичного вычисляемого поля; условие неагрегированной Меры передаётся в {{where}} и удаляется при снятии выбора.

*AC.3* — Подписи и подсказки:
* *Дано:* однозначные сочетания исходных значений, подписей и подсказок; их источники поочерёдно представлены полями и Мерами;
* *Когда:* настраиваются оба дополнительных селектора по отдельности и вместе, выбирается значение, затем меняется или отключается источник подписи/подсказки;
* *Тогда:* отображаются соответствующие рассчитанные значения, а условие хранит исходные значения выбранного варианта и сохраняет выбор.

*AC.4* — Однозначность и дубликаты:
* *Дано:* ключи {{1}} и {{2}} с одинаковой подписью и общей подсказкой, ключ {{3}} с другой подписью, повторяющиеся одинаковые сочетания и отдельные примеры одного ключа с разными подписями либо одного отображаемого варианта с разными подсказками; источники поочерёдно представлены полями и Мерами;
* *Когда:* загружаются значения с дополнительными источниками, включая поиск и частичную загрузку при их наличии, затем выбирается общая подпись ключей {{1}} и {{2}};
* *Тогда:* общая подпись отображается один раз, её выбор охватывает оба исходных ключа {{1}} и {{2}}, без ключа {{3}}; повторы сочетаний не дублируют варианты. Результат совпадает с эквивалентной конфигурацией на полях. Конфликтующие примеры дают локальную ошибку без произвольного выбора значения; способ проверки соответствует решению по п. 5.2.

*AC.5* — Агрегированная Мера:
* *Дано:* закрыт вопрос п. 5.1; получатель группирует строки «Москва — 100», «Москва — 50», «Тула — 40» по городу, Мера вычисляет сумму;
* *Когда:* через подтверждённый сценарий контейнера задано условие суммы больше {{100}}, затем оно снято;
* *Тогда:* условие передаётся в {{having.items}}, результат сначала показывает только Москву с суммой {{150}}, после снятия — также Тулу с суммой {{40}}. Существующее {{having.condition}} сохраняется; значения контейнера рассчитываются в контексте, определённом по п. 5.1.

*AC.6* — Взаимодействие фильтров:
* *Дано:* эквивалентные конфигурации на полях и Мерах, несколько фильтров и визуализаций-получателей;
* *Когда:* меняются условия, «Производный фильтр», «Уровень отбора», {{updateOnCloseDropdown}} и поддерживаемые переменные;
* *Тогда:* область действия, момент применения, обновление списков и результаты получателей совпадают с действующим поведением эквивалентной конфигурации. Незаполненный отбор не ограничивает визуализацию-получателя фильтра, но список значений фильтра загружается.

*AC.7* — Сохранение и актуализация:
* *Дано:* контейнер с Мерами на полке, в обоих селекторах и в выражении вычисляемого поля;
* *Когда:* отчёт сохраняется, открывается повторно, копируется или восстанавливается штатным сбросом; затем меняются метаданные Мер;
* *Тогда:* ссылки, порядок, условия и локальные настройки восстанавливаются по п. 3.1. Новый {{alias}} не разрывает связи, новое выражение применяется без пересохранения контейнера; смена типа или агрегированности повторно проверяет совместимость. После поставки backend-Шага 3 все сохранённые использования учитываются при удалении Меры.

*AC.8* — Локализация ошибки и восстановление:
* *Дано:* основная Мера либо Мера подписи/подсказки стала невалидной, отсутствующей или несовместимой; в контейнере есть независимый исправный фильтр;
* *Когда:* загружается проблемный список, в том числе без выбранного условия; затем причина исправляется;
* *Тогда:* ошибка отображается в соответствующем фильтре, ссылка и выбор сохраняются; контейнер и независимый фильтр доступны. Получатели блокируются только при участии ошибочной Меры в их запросе, а при невозможности получить список значений и настроить фильтрацию данная ошибочная Мера не создаёт дополнительную фильтрацию. Ошибка неиспользуемого дополнительного источника не блокирует загрузку; после получения исправленных метаданных работа восстанавливается без повторного выбора Меры.

*AC.9* — Совместимость и пограничные данные:
* *Дано:* старый отчёт без Мер и эквивалентные конфигурации с Мерами при пустой полке, отсутствии данных, {{null}}, нулевых и отрицательных значениях;
* *Когда:* выполняются открытие, загрузка значений, поиск, применение и сброс отбора;
* *Тогда:* сохраняются действующая обработка данных, ограничения доступа и поведение правой панели; отсутствие массива Мер не вызывает ошибки. Прямые runtime-объекты Мер соответствуют п. 3.2 и не содержат копий выражений или непустых {{calc}}/{{agg}}/{{aggr}}; локальная агрегация передаётся общим механизмом.

*AC.10* — Локальная агрегация как у обычных полей:
* *Дано:* эквивалентные обычное поле и валидная Мера с {{is_aggregated = false}};
* *Когда:* выполняются поддерживаемые для поля сценарии локальной агрегации на полке и получения значений с подписью/подсказкой, затем сохранение и повторное открытие;
* *Тогда:* функции, значение по умолчанию, возможность оставить размещение без агрегации, группировка, тип и результат совпадают с обычным полем; показ и обработка *«-»* следуют тому же сценарию. Настройки восстанавливаются, метаданные Меры не меняются. {{WHERE}}/{{HAVING}} выбирается по выражению условия получателя, а функция запроса списка не переносится туда автоматически. Исходно агрегированные Меры не получают повторной агрегации и не становятся доступными в ранее запрещённых контекстах.
