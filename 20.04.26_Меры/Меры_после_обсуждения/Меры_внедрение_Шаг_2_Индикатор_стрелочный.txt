h3. Контекст и проблематика.

Полное описание продуктовой логики Мер приведено в Эпике [https://jira.modusbi.ru/browse/MB-4364]: 
* общий механизм Шага 2 описан в Истории [https://jira.modusbi.ru/browse/MB-4481], 
* runtime-обработка Мер — в backend-задаче [https://jira.modusbi.ru/browse/MB-5035], 
* парсер, валидация, зависимости и блокировки Мер [https://jira.modusbi.ru/browse/MB-5046].

Для произвольных наборов данных уже реализованы хранение Мер, общий интерфейс работы с ними и обработка объектов {{type = "measure"}} при построении SQL. Поддержка Мер также реализована для части визуализаций.

В визуализации *«Индикатор стрелочный v.2.0»* Меры текущего набора данных пока нельзя использовать на полках и в настройках визуализации.

h3. Цель задачи.

*Требуется:*
# Подключить реализованный механизм Мер к визуализации *«Индикатор стрелочный v.2.0»*.
# Добавить Меры в стандартную левую боковую панель и обеспечить их использование на полках *«Значения»*, *«Категории»* и *«Фильтры»*.
# Поддержать использование Мер на полке *«Значения»* для всех действующих типов пилюль: *«Значение»*, *«Отсечка»*, *«Minimum»*, *«Maximum»* и *«Цвет»*.
# Поддержать размещения Мер в селекторах *«Текст для»* раздела *«Легенда»* и *«Объект данных»* раздела *«Стилизация значений»*.
# Сохранять ссылки на Меры и локальные настройки конкретных размещений по общему контракту и формировать runtime payload для существующего backend-механизма.
# Сохранить обратную совместимость существующих визуалиций «Индикатор стрелочный v.2.0», в которых Меры напрямую не используются.

_Пользовательская история:_
Как аналитик, я хочу использовать Меры в стрелочном индикаторе наравне с обычными и вычисляемыми полями, чтобы строить и оформлять индикатор на основе единых показателей набора данных без дублирования формул в виджете.

h3. 1. Область применения и текущая конфигурация.

h4. 1.1. Визуализация, набор данных и полки.

Доработка выполняется для визуализации:
* {{chartType = "speedometer_v2"}};
* {{visualType = "gauge"}}.

Источником Мер является массив {{datasets.measures}} выбранного *произвольного* набора данных. Отсутствующий массив {{measures}} обрабатывается как пустой список. Для простого и составного наборов данных секция *«Меры»* не отображается.

Полки необходимо определять по {{axes[].type}}:

|| Полка в интерфейсе || {{axes[].type}} || Особенность текущей конфигурации ||
| *«Значения»* | {{values}} | {{name}}/{{title}} могут иметь legacy-значение *«Показатель»*; поддерживаются режимы *«Первое»*/*«Все»* и настройка *«Тип»* для пилюли |
| *«Категории»* | {{categories}} | Учитывается первая активная пилюля |
| *«Фильтры»* | {{filters}} | Используется стандартная форма настройки фильтра |

Необходимо сохранить действующие значения и семантику {{selectedFieldIndex}}, порядок размещений, признаки {{inactive}}, {{sortable}}, {{visible}} и остальные локальные параметры осей. Новые значения и отдельные оси для Мер не вводятся.

Объекты Мер обрабатываются в {{axes}} и {{axesDefault}} по тому же жизненному циклу, что обычные и вычисляемые поля: {{axes}} хранит текущее состояние, а {{axesDefault}} изменяется только в тех операциях, в которых его изменяет действующий механизм индикатора. Простое редактирование полки не должно безусловно перезаписывать {{axesDefault}}.

h4. 1.2. Модель прямого использования Меры.

При прямом использовании Меры конфигурация хранит ссылку на определение Меры текущего набора данных:

{code:json}
{
  "id": "gauge_measure_4f9b7e2d",
  "type": "measure",
  "name": "Мера.Валовая_прибыль",
  "datasetId": 244,
  "valueType": "value"
}
{code}

Правила:
* {{name}} — единственный ключ поиска определения Меры; {{datasetId}} фиксирует контекст набора, а {{id}} идентифицирует конкретное размещение и не равен {{datasets.measures[].id}};
* определение Меры, включая {{alias}}, {{expression}}, {{aggregation_kind}}, {{data_type}} и {{status}}, читается из актуального {{datasets.measures}} и не копируется в конфигурацию как источник истины;
* {{type = "measure"}} остаётся признаком сущности, а настройка *«Тип»* хранится в действующем локальном параметре размещения: в примере для *«Значения»* используется {{valueType = "value"}}, для остальных вариантов переиспользуются текущие технические значения компонента;
* каждое размещение одной Меры, в том числе с разными локальными типами, получает собственный {{id}} и независимые настройки.

Мера поддерживается в каждом сценарии индикатора, в котором допустимо вычисляемое поле с таким же {{data_type}}, с дополнительной проверкой {{aggregation_kind}} для SQL-контекста.

h3. 2. Целевой интерфейс работы с Мерами.

h4. 2.1. Левая боковая панель.

При выборе произвольного набора данных стандартная левая панель должна содержать расположенные друг за другом секции:
* *«Поля»* — обычные поля набора данных и вычисляемые поля виджета;
* *«Меры»* — Меры из {{datasets.measures}} текущего набора данных.

Обе секции реализуются через актуальный общий компонент аккордеона. Начальное состояние, независимое сворачивание и разворачивание секций должны повторять последнюю общую реализацию панели; отдельный вариант аккордеона для визуализации «Индикатор стрелочный» не создаётся.

Для секции *«Меры»* переиспользуется общий интерфейс и поведение, поиск по {{alias}} или {{name}} и tooltip с описанием, типом, выражением и {{name}}. Мера с {{status = "invalid"}} недоступна для создания нового размещения; уже сохранённое размещение и его привязки в легенде и {{visuals[]}} остаются видимыми в error-состоянии, не очищаются и не переназначаются автоматически.

Для структурного {{status_message}} фронтенд формирует локализованную причину из {{code}} и {{params}}, использует {{message}} только как fallback для неизвестного {{code}} и не показывает пользователю сырой JSON.

Если для Меры с {{status = "invalid"}} поле {{status_message}} пусто, не является корректным структурным JSON либо содержит неизвестный {{code}} без {{message}}, интерфейс показывает общее локализованное сообщение о невалидности Меры и не выводит исходное значение пользователю.

h4. 2.2. Пилюля Меры и её настройки.

Пилюля Меры:
* на полках *«Значения»* и *«Категории»* имеет светло-синий цвет {{#3491F7}};
* на полке *«Фильтры»* имеет стандартный для этой полки салатовый цвет;
* отображается по актуальному {{alias}} и сохраняет визуальный признак типа *«Мера»*;
* содержит ярлык {{AGR}} для {{aggregation_kind = 1}} независимо от цвета полки;
* предоставляет те же локальные настройки, что вычисляемое поле того же {{data_type}}, кроме изменения выражения и агрегированности Меры.

Обработка {{null}}, пустого результата, преобразование значений и fallback-поведение Мер каждого типа данных должны повторять действующий алгоритм для вычисляемого поля.

При форматировании фронтенд использует актуальный {{datasets.measures[].data_type}}; 
* значение {{type = "measure"}} нельзя интерпретировать как логический тип результата.

h3. 3. Использование Мер на полках.

h4. 3.1. Матрица допустимости и активность размещений.

|| Полка || {{aggregation_kind = 0}} || {{aggregation_kind = 1}} || Runtime-контекст ||
| *«Значения»* | Допускается | Допускается | Активные размещения всех поддерживаемых типов передаются в {{select}} |
| *«Категории»* | Допускается | Блокируется | Первая активная Мера передаётся в {{group}} и {{select}} по действующей схеме индикатора |
| *«Фильтры»* {{WHERE}} | Допускается | - | Структурное условие передаётся в {{where}} |
| *«Фильтры»* {{HAVING}} | - | Допускается | Структурное условие передаётся в {{having.items}} |

Сортировка - ссылка на активную Меру передаётся в {{order}} по текущей логике визуализации.

Размещение считается активным, только если действующий алгоритм {{speedometer_v2}} использует обычное или вычисляемое поле в той же позиции, с тем же типом пилюли и при том же состоянии полки. Только активное размещение передаётся в runtime payload, влияет на отображение и может блокировать построение.

Сохранённая отсутствующая, невалидная или ставшая несовместимой Мера не удаляется автоматически. Активное проблемное размещение блокирует построение индикатора с понятным сообщением. Неактивное размещение сохраняется, не передаётся в runtime payload и не блокирует построение.

h4. 3.2. Полка «Значения»: режимы «Первое» и «Все».

В режиме *«Первое»*:
* В runtime payload включается только первое размещение пилюли на данной полке. Остальные размещения и их настройки сохраняются, но не передаются в запрос. 
* Мера обрабатывается строго так же, как обычное или вычисляемое поле с тем же локальным типом. 
* Поддержка Мер не изменяет действующее поведение настройки пилюль *«Тип»*: для выбранного вспомогательного типа, Мера выполняет ту же функцию и обрабатывается по той же логике, что и вычисляемое поле.

В режиме *«Все»*:
* все размещения учитываются в runtime payload и обрабатываются визуализацией;
* каждое размещение обрабатывается в своей локальной роли;
* несколько активных размещений типа *«Значение»* формируют несколько стрелок по действующему алгоритму индикатора;
* вспомогательные размещения не создают самостоятельную стрелку;
* обычные поля, вычисляемые поля и Меры могут использоваться совместно в любой допустимой последовательности.

h4. 3.3. Типы пилюли на полке «Значения».

|| Тип пилюли || Использование результата Меры || Формирует самостоятельную стрелку ||
| *«Значение»* | Результат формирует стрелку, соответствующую дугу и отображаемое значение по текущим настройкам индикатора | Да |
| *«Отсечка»* | Результат передаётся в существующий канал отсечки и определяет положение отсечки на шкале | Нет |
| *«Minimum»* | Результат передаётся в существующий канал динамического минимума шкалы | Нет |
| *«Maximum»* | Результат передаётся в существующий канал динамического максимума шкалы | Нет |
| *«Цвет»* | Результат передаётся в существующий канал управления цветом связанных элементов индикатора | Нет |

Для всех типов:
* применяется действующее для обычных и вычисляемых полей соответствие вспомогательного результата основной стрелке, а также текущая кратность, приоритет и порядок обработки размещений;
* для *«Minimum»* и *«Maximum»* сохраняется текущий приоритет динамического результата относительно статических {{grid.minimum}}/{{grid.maximum}} и текущая проверка допустимости диапазона;
* для *«Цвет»* сохраняется текущая интерпретация результата, приоритет относительно ручного цвета и палитры, а также fallback при {{null}} или неподдерживаемом значении;
* роль не изменяет {{expression}} Меры, не добавляет к нему {{MIN}}, {{MAX}} или другую агрегацию и не изменяет {{aggregation_kind}};
* локальная роль и результат конкретного размещения сопоставляются по локальному {{id}} и техническому alias, а не только по {{name}} Меры.

Проверяемым эталоном поведения каждого типа является вычисляемое поле с тем же результирующим значением и типом данных в той же позиции. Замена такого вычисляемого поля на Меру не должна менять визуальный результат, приоритеты, обработку {{null}} и пограничных значений.

Одна Мера может одновременно использоваться, например, как *«Значение»*, *«Отсечка»* и *«Цвет»*. Размещения должны иметь разные локальные {{id}}, независимые типы и настройки и получать результат по отдельным техническим alias без коллизии по {{name}}.

h4. 3.4. Полка «Категории».

На полке *«Категории»*:
* активно используется только первое размещение;
* допускается Мера с {{aggregation_kind = 0}};
* результат Меры участвует в группировке и формирует категории индикатора по тем же правилам, что результат вычисляемого поля;
* активная Мера передаётся в {{group}} и {{select}} по текущей стратегии технических alias;
* размещение Меры с {{aggregation_kind = 1}} блокируется с сообщением: *«На полке "Категории" допустимы только неагрегированные Меры»*.

Сортировка категорий, обработка {{null}}, выбор отображаемых групп и связь категорий со стрелками и вспомогательными результатами сохраняют действующую семантику визуализации.

h4. 3.5. Полка «Фильтры».

Мера использует стандартный интерфейс и общий контракт фильтра [^Контракты_мер_обновлённый.txt]: {{aggregation_kind = 0}} допускает только {{WHERE}}, {{aggregation_kind = 1}} — только {{HAVING}}. Незаполненный фильтр неактивен.

В runtime payload WHERE-условие передаётся в {{where}}, HAVING-условие — в {{having.items}}. {{having}} формируется объектом {{condition}} + {{items}}, а условия объединяются с остальными условиями соответствующей SQL-клаузы по действующим правилам, базово через {{AND}}.

h3. 4. Настройки правой боковой панели.

h4. 4.1. Общий принцип селекторов.

В селекторы правой панели попадает не весь массив {{datasets.measures}}, а допустимые активные размещения Мер на полке *«Значения»* с типом «Значение».

В списке доступных для выбора полей Мера отображается по актуальному {{alias}} с признаком типа *«Мера»*. Если одна Мера размещена несколько раз, каждое допустимое размещение отображается отдельным вариантом и связывается с настройкой по локальному {{id}}.

Тип сущности {{measure}} не должен дополнительно сужать или расширять список: размещение Меры включается в каждый селектор тогда и только тогда, когда в том же режиме, позиции и с тем же локальным типом в него включается обычное или вычисляемое поле.

Если селектор уже содержит сохранённую привязку к отсутствующей, невалидной или несовместимой Мере, выбранный вариант остаётся видимым в disabled/error-состоянии до замены размещения и явного выбора пользователем другого допустимого объекта. Такой вариант недоступен для повторного выбора.

h4. 4.2. Раздел «Легенда»: селектор «Текст для».

Селектор *«Текст для»* должен включать размещения Мер на полке *«Значения»* с типом «Значение» по действующему алгоритму.
* заполненный текст заменяет {{alias}} только у элемента легенды выбранного размещения;
* после очистки пользовательского текста в легенде используется актуальный {{alias}} Меры из метаданных набора данных.

Пользовательский текст является локальной настройкой размещения и не изменяет {{alias}} Меры в {{datasets.measures}}.

h4. 4.3. Раздел «Стилизация значений»: селектор «Объект данных».

Селектор *«Объект данных»* должен включать размещения Мер на полке *«Значения»* с типом «Значение» по действующему алгоритму, которые компонент предоставляет для индивидуальной стилизации;
* после выбора Меры существующие применимые настройки раздела действуют на соответствующий визуальный объект так же, как для вычисляемого поля с тем же локальным типом.

В частности, для результата Меры должны поддерживаться действующие группы настроек стилизации:
* *«Дуга»* — ширина дуги, насыщенность и цвет;
* *«Указатель»* — ширина стрелки и насыщенность;
* *«Значение»* — размер шрифта, шаблон вывода, единица измерения и т.д.

Локальные настройки продолжают храниться в существующей структуре {{visuals[]}}. Для нового размещения {{type = "measure"}} значение {{visuals[].anchor}} должно быть равно локальному {{axes[type = "values"].fields[].id}} этого размещения. Существующие форматы {{anchor}} обычных и вычисляемых полей не мигрируются.

Выбор в *«Объекте данных»* не создаёт дополнительный элемент в {{select}}: настройки применяются к уже полученному результату размещения. При одновременном использовании пилюли типа *«Цвет»* и ручной стилизации сохраняется текущий приоритет в пользу пилюли типа *«Цвет»*.

h4. 4.4. Изменение активности и удаление размещения.

При изменении порядка пилюль, локального типа или переключении *«Первое»*/*«Все»* сохранённые настройки легенды и {{visuals[]}} временно неактивного размещения не должны применяться к другому объекту. После возврата размещения в поддерживаемую активную роль они восстанавливаются для того же локального {{id}}.

Если размещение удалено, зависимая привязка селектора обрабатывается действующим механизмом удаления обычного или вычисляемого поля и не должна ошибочно переключаться на другую Меру с тем же {{name}} или {{alias}}.

h4. 4.5. Раздел «Настройки клика».

Поддержка Мер не изменяет стандартный механизм клика индикатора. Настроенное действие, включая переход в другой отчёт, продолжает запускаться специальной кнопкой в верхней полосе управления визуализацией.

Если действующий сценарий действия использует результат значения или категории, результат Меры передаётся в контекст по тем же правилам, что результат вычисляемого поля в той же роли. Размещение Меры не добавляет отдельное действие по клику на стрелку, дугу, отсечку или шкалу.

h3. 5. Сохранение и восстановление конфигурации.

В {{axes[].fields}} и, когда это предусмотрено текущим механизмом, в {{axesDefault[].fields}} сохраняются ссылка на Меру и локальные параметры размещения: тип, порядок, фильтр, сортировка, форматирование, легенда и привязка к {{visuals[]}}. Источником определения Меры остаётся {{datasets.measures}}.

При открытии, копировании или восстановлении индикатора фронтенд должен:
# получить актуальный {{datasets.measures}}, проверить {{datasetId}} и найти определение по {{name}} без подбора по {{alias}};
# восстановить полку, порядок, локальный тип и связанные настройки;
# при открытии и восстановлении сохранить локальный {{id}}; при копировании сохранить либо регенерировать его по действующему алгоритму компонента, а при регенерации применить единое соответствие старых и новых {{id}} ко всем зависимым привязкам;
# отобразить актуальные метаданные и повторно проверить совместимость с полкой, локальным типом и SQL-контекстом;
# сохранить отсутствующую, невалидную или ставшую несовместимой ссылку в error-состоянии без автоматической подмены или удаления.

Изменение {{alias}} при неизменном {{name}} не нарушает связь: после обновления метаданных интерфейс показывает новое название, а пользовательский текст легенды при наличии сохраняется. Изменённое {{expression}} используется backend при следующем runtime-запросе без пересохранения индикатора.

Изменение {{aggregation_kind}}, {{data_type}} или {{status}} приводит к повторной проверке размещений: проблемная активная ссылка блокирует построение, неактивная сохраняется и не блокирует запрос. При смене набора ссылка не сопоставляется с Мерой другого набора только по совпавшим {{name}} или {{alias}}.

h3. 6. Runtime payload и взаимодействие с backend.

| {{/v1/api/recordsets/<dataset_id>}} | {{POST}} — реализованный запрос данных | Получение данных индикатора с объектами {{type = "measure"}} |

Минимальный прямой runtime-объект активной Меры:

{code:json}
{
  "type": "measure",
  "name": "Мера.Валовая_прибыль",
  "alias": "[values][N]"
}
{code}

{{alias}} в runtime-объекте — технический alias результата, а не пользовательский {{datasets.measures[].alias}}; {{[values][N]}} приведён как пример, точный формат и индексация сохраняют действующую стратегию для визуализации {{speedometer_v2}}. {{datasetId}} хранится в конфигурации индикатора, но не входит в канонический runtime-элемент: набор определяется параметром {{<dataset_id>}} маршрута.

|| Использование активной Меры || Runtime-блок || Правило ||
| *«Значения»*, режим *«Первое»* | {{select}} | Передаётся первое размещение по действующему алгоритму с сохранением его локальной роли |
| *«Значения»*, режим *«Все»* | {{select}} | Передаются все учитываемые размещения всех поддерживаемых типов в порядке полки с отдельными техническими alias |
| *«Категории»* | {{group}} и {{select}} | Передаётся первая активная неагрегированное поле или Мера по текущей схеме индикатора |
| *«Фильтры»*, {{aggregation_kind = 0}} | {{where}} | Передаётся структурное условие со ссылкой {{type}}/{{name}} |
| *«Фильтры»*, {{aggregation_kind = 1}} | {{having.items}} | Передаётся структурное условие со ссылкой {{type}}/{{name}} |
| Поддерживаемая сортировка | {{order}} | Передаются {{type}}, {{name}} и направление по текущему контракту |

Все активные размещения включаются в один запрос; повторные использования одной Меры получают разные технические alias. Легенда и стилизация используют полученные результаты без дублирования {{select}}. Фронтенд не передаёт непустые {{calc}}, {{expression}}, {{agg}} или {{aggr}} как источник Меры; локальная роль остаётся настройкой размещения и сопоставляется с ответом по размещению и техническому alias.

Backend находит Меру по {{name}}, раскрывает актуальное {{expression}} через общий SQL-builder и применяет его в фактическом runtime-блоке. Ссылка на Меру внутри {{calc}} остаётся частью вычисляемого поля и не создаёт отдельный объект {{type = "measure"}}.

Контролируемая ошибка backend отображается пользователю без автоматического удаления ссылки, если Мера не найдена, невалидна, передана в несовместимый runtime-блок либо итоговый SQL не может быть построен. Для невалидной Меры применяется общий контракт backend-Шага 3 ([https://jira.modusbi.ru/browse/MB-5046]): runtime-ошибка {{HTTP 400}} уже содержит человекочитаемое сообщение backend.

h3. 7. Права, зависимости и обратная совместимость.

* Новые права не вводятся: чтение Мер определяется существующим правом чтения набора данных и отчёта, изменение индикатора — правом редактирования отчёта/виджета.
* Интерфейс использует актуальные {{status}}/{{status_message}}, а backend не выполняет SQL для невалидной Меры по правилам backend-Шага 3.
* Индикаторы без прямых Мер и вычисляемые поля со ссылкой на Меру внутри {{calc}} продолжают работать по существующему контракту без миграции.
* Смешанные конфигурации сохраняют порядок, локальные роли и правила активности; экранное построение, автообновление и доступный экспорт используют одинаковую runtime-логику.

h3. 9. Критерии приёмки (AC):

*AC.1* — Секция «Меры» в левой панели:
* *Дано:* пользователь открыл визуализацию {{speedometer_v2}}, основанную на произвольном наборе данных;
* *Когда:* загружены метаданные набора;
* *Тогда:* ниже секции *«Поля»* отображается секция *«Меры»* в актуальном общем аккордеоне; секции можно независимо сворачивать и разворачивать по стандартному поведению общего компонента; Меры отображаются по {{alias}}, с группировкой по {{hierarchy}}, сортировкой по {{level}}/{{alias}}, поиском по {{alias}} или {{name}}, tooltip и ярлыком {{AGR}} для {{aggregation_kind = 1}};
* *И:* отсутствующий или пустой массив {{measures}} для произвольного набора отображается как пустая секция без ошибки, а для простого или составного набора секция *«Меры»* не отображается.

*AC.2* — Представление и допустимость пилюли Меры:
* *Случай 1 — валидная совместимая Мера:*
** *Дано:* валидная Мера размещается на допустимой полке индикатора;
** *Когда:* {{aggregation_kind}} совместим с полкой размещения пилюли;
** *Тогда:* на *«Значениях»* и *«Категориях»* пилюля имеет синий цвет {{#3491F7}}, а на *«Фильтрах»* — стандартный салатовый цвет; пилюля показывает актуальный {{alias}}, признак *«Мера»* и {{AGR}} для агрегированной Меры;
** *И:* локальное изменение выражения, {{aggregation_kind}}, {{agg}} и {{aggr}} недоступно, а выбор значения настройки *«Тип»* сохраняется в действующем локальном параметре роли и не изменяет {{type = "measure"}}.
* *Случай 2 — несовместимая или невалидная Мера:*
** *Дано:* {{data_type}}/{{aggregation_kind}} несовместимы со сценарием либо получен {{status = "invalid"}};
** *Когда:* пользователь пытается разместить Меру или открыть сохранённое размещение;
** *Тогда:* новое действие блокируется по тем же правилам, что для вычисляемого поля и общей матрицы Мер;
** *И:* сохранённое размещение остаётся в error-состоянии, а tooltip показывает локализованную причину или общее сообщение без сырого {{status_message}}.

*AC.3* — Полка «Значения» в режиме «Первое»:
* *Дано:* на полке размещено несколько объектов, включая Меры разных типов;
* *Когда:* выбран режим *«Первое»* и индикатор запрашивает данные;
* *Тогда:* в {{select}} передаётся только первое размещение, а его визуальная роль и результат полностью совпадают с обычным или вычисляемым полем в аналогичном размещении в режиме *«Первое»*;
* *И:* остальные размещения и их локальные настройки сохраняются, не влияют на индикатор и не блокируют запрос, пока неактивны;

*AC.4* — Полка «Значения» в режиме «Все»:
* *Дано:* на полке размещены обычные поля, вычисляемые поля и Меры разных типов;
* *Когда:* выбран режим *«Все»*;
* *Тогда:* все учитываемые размещения передаются в {{select}} в порядке полки с отдельными техническими alias;
* *И:* каждое размещение обрабатывается в своей роли, а несколько размещений типа *«Значение»* формируют несколько стрелок;
* *И:* вспомогательные размещения самостоятельных стрелок не создают.

*AC.5* — Мера с типом «Значение»:
* *Дано:* активной Мере на полке *«Значения»* назначен тип *«Значение»*;
* *Когда:* индикатор построен;
* *Тогда:* результат формирует стрелку, дугу, отображаемое значение и, при включённой легенде, соответствующий элемент легенды;
* *И:* форматирование и обработка результата совпадают с вычисляемым полем того же {{data_type}} и значения.

*AC.6* — Вспомогательные типы Меры:
* *Дано:* в режиме *«Все»* валидным Мерам назначены типы *«Отсечка»*, *«Minimum»*, *«Maximum»* и *«Цвет»*;
* *Когда:* индикатор построен;
* *Тогда:* результаты применяются соответственно к отсечке, динамическому минимуму, динамическому максимуму и текущему цветовому каналу;
* *И:* вспомогательные размещения не формируют самостоятельные стрелки, а их участие в легенде и селекторах совпадает с вычисляемыми полями в тех же ролях;
* *И:* кратность, сопоставление со стрелками, приоритеты, обработка {{null}}, некорректного диапазона и fallback полностью совпадают с вычисляемыми полями в тех же ролях;
* *И:* ни одна роль не изменяет выражение или {{aggregation_kind}} Меры.

*AC.7* — Несколько размещений одной Меры:
* *Дано:* одна Мера размещена несколько раз, например как *«Значение»*, *«Отсечка»* и *«Цвет»*;
* *Когда:* пользователь задаёт локальные настройки, сохраняет и повторно открывает индикатор;
* *Тогда:* размещения имеют разные локальные {{id}}, независимые типы и настройки;
* *И:* все размещения ссылаются по {{name}} на одно актуальное определение Меры, а результаты сопоставляются с ролями по отдельным техническим alias без коллизии.

*AC.8* — Мера на полке «Категории»:
* *Случай 1 — неагрегированная Мера:*
** *Дано:* на полке *«Категории»* размещена Мера с {{aggregation_kind = 0}};
** *Когда:* индикатор запрашивает данные;
** *Тогда:* первое учитываемое размещение передаётся в {{group}} и {{select}} и формирует категории по текущему алгоритму индикатора.
* *Случай 2 — агрегированная Мера:*
** *Дано:* пользователь пытается разместить на полке Меру с {{aggregation_kind = 1}};
** *Когда:* выполняется drag-and-drop или выбор;
** *Тогда:* размещение блокируется с понятным сообщением о допустимости только неагрегированных Мер.

*AC.9* — Фильтр по Мере:
* *Случай 1 — неагрегированная Мера:*
** *Дано:* настроено заполненное условие по Мере с {{aggregation_kind = 0}};
** *Когда:* формируется runtime payload;
** *Тогда:* условие передаётся в {{where}}, а режим {{HAVING}} для этой Меры недоступен.
* *Случай 2 — агрегированная Мера:*
** *Дано:* настроено заполненное условие по Мере с {{aggregation_kind = 1}};
** *Когда:* формируется runtime payload;
** *Тогда:* условие передаётся в {{having.items}}, {{having}} содержит {{condition}} и {{items}}, а режим {{WHERE}} недоступен.

*AC.10* — Пользовательский текст легенды для Меры:
* *Дано:* активное размещение Меры на полке *Значения* с типом _Значение_ по действующему алгоритму формирует элемент легенды;
* *Когда:* пользователь выбирает её размещение в *«Текст для»* и задаёт текст;
* *Тогда:* текст отображается только для соответствующего элемента легенды и сохраняется по локальному {{id}};
* *И:* после очистки текста используется актуальный {{alias}} Меры.

*AC.11* — Стилизация значения Меры:
* *Дано:* активное размещение Меры на полке *Значения* с типом _Значение_ доступно для индивидуальной стилизации по действующему алгоритму;
* *Когда:* пользователь выбирает её размещение в *«Объекте данных»* и изменяет настройки дуги, указателя или отображаемого значения;
* *Тогда:* настройки применяются только к выбранному размещению, сохраняются в {{visuals[]}} с {{anchor}}, равным локальному {{id}} выбранного размещения и можно стилизовать независимо второе размещение той же Меры;
* *И:* выбор в селекторе не создаёт дублирующий объект {{select}}.

*AC.12* — Сохранение, копирование, актуализация и сброс:
* *Дано:* Меры используются на нескольких полках и в правой панели;
* *Когда:* пользователь сохраняет, повторно открывает или копирует визуализацию-индикатор;
* *Тогда:* текущие размещения, локальные типы, порядок, фильтры, легенда и {{visuals[]}} восстанавливаются согласованно;
* *И:* после проверки {{datasetId}} определения находятся по {{name}}, а экземпляры размещения различаются по локальному {{id}}; при регенерации локальных {{id}} все зависимые ссылки обновляются по единому соответствию;
* *И:* изменение порядка, типа пилюли или режима *«Первое»* / *«Все»* не перепривязывает сохранённую настройку к другому размещению, а после повторной активации настройка восстанавливается по тому же {{id}};  удаление размещения не перепривязывает легенду или {{visuals[]}} к одноимённой Мере;
* *И:* изменение {{alias}} обновляет отображаемое название без потери связи, а изменение {{expression}} применяется следующим runtime-запросом.

*AC.13* — Ошибочная или несовместимая ссылка:
* *Дано:* использованная Мера отсутствует, имеет {{status = "invalid"}} либо стала несовместима по {{aggregation_kind}} / {{data_type}};
* *Когда:* индикатор получает актуальные метаданные;
* *Тогда:* ссылка не подменяется по {{alias}} и не удаляется автоматически;
* *И:* активное проблемное размещение блокирует построение с понятным сообщением, а неактивное сохраняется и не блокирует запрос; сохранённая настройка легенды или {{visuals[]}} не применяется к другому размещению; при смене набора ссылка не сопоставляется с одноимённой Мерой другого набора;
* *И:* известная фронтенду невалидность блокирует формирование runtime-запроса, а невалидность, выявленная только backend при устаревших метаданных, отображается по контракту backend-Шага 3 как человекочитаемый ответ {{HTTP 400}} без интерпретации его как {{status_message}}.

*AC.14* — Канонический runtime-контракт:
* *Дано:* активные Меры участвуют в построении индикатора;
* *Когда:* фронтенд формирует runtime payload;
* *Тогда:* каждый прямой runtime-объект Меры содержит {{type = "measure"}} и {{name}}; технический {{alias}} передаётся только в тех runtime-блоках, где он предусмотрен каноническим контрактом результата, прежде всего в {{select}};
* *И:* все активные размещения включаются в один запрос данных без отдельного запроса на каждую Меру; backend раскрывает актуальное выражение Меры в SQL-контексте фактического runtime-блока.

*AC.15* — Стандартное взаимодействие и обратная совместимость:
* *Дано:* Визуализация индикатор стрелочный использует Меры либо сохранён без прямого использования Мер;
* *Когда:* выполняются настройка клика, переход по кнопке действия, автообновление, копирование или доступный экспорт;
* *Тогда:* результат Меры участвует в контексте только там, где поддерживается вычисляемые поля; экранное построение, автообновление и экспорт используют одинаковую runtime-логику;
* *И:* конфигурации без прямых Мер сохраняют прежний результат и не требуют миграции; вычисляемое поле со ссылкой на Меру внутри {{calc}} остаётся вычисляемым полем и не создаёт отдельный объект {{type = "measure"}}.
