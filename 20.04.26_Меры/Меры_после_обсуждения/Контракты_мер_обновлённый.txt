h3. Контракты данных для Мер в аналитическом портале

----
h3. 1. Ключевое решение по контракту

В контракте Мер необходимо разделять три разных уровня данных:

# *Определение Меры в наборе данных* — источник истины о Мере: системное имя, alias, выражение, тип, агрегированность, статус.
# *Использование Меры в визуализации* — ссылка на уже существующую Меру и локальные настройки конкретной пилюли / полки / фильтра.
# *Payload запроса данных* — runtime-структура для {{/v1/api/recordsets/<dataset_id>}}, которую frontend собирает из метаданных визуализации перед запросом данных.

В контракте:
* ключом связи с Мерой является только {{name}};
* {{alias}} Меры используется для отображения пользователю и не является ключом связи;
* {{id}} Меры не используется как внешний ключ связи в визуализациях;
* выражение Меры не копируется в визуализацию и не передаётся frontend-ом как источник истины при построении запроса данных;
* frontend не формирует {{name}} самостоятельно и не добавляет префикс {{Мера.}} при сохранении или вставке Меры.

----
h3. 2. Контракт определения Меры в метаданных набора данных

Меры хранятся в метаданных *произвольного* набора данных в массиве {{measures}}.

{code:json}
{
  "measures": [
    {
      "id": "847b1ec3-bbf8-4365-85fb-c4fca2a06e2e",
      "name": "Мера.Валовая_прибыль",
      "alias": "Валовая прибыль",
      "description": "Разница между выручкой и себестоимостью",
      "expression": "SUM(\"revenue\") - SUM(\"cost\")",
      "is_aggregated": true,
      "data_type": "number",
      "hierarchy": "Финансовые показатели",
      "level": 10,
      "status": "valid",
      "status_message": ""
    }
  ]
}
{code}

|| Поле || Заполняет || Обязательность || Описание ||
| {{id}} | Система | Да | Стабильный UUID Меры. Генерируется при создании, не меняется при редактировании. Не является внешним ключом связи для визуализаций. |
| {{name}} | Backend | Да | Системное наименование Меры. Генерируется при создании на основании {{alias}}, уникально в рамках одного набора данных, не меняется после создания. Используется как единственный ключ связи во внешних ссылках. |
| {{alias}} | Пользователь | Да | Человекочитаемое название Меры. Отображается в интерфейсе и может изменяться после создания свободно — {{name}} при этом не меняется (все ссылки идут по {{name}}). |
| {{description}} | Пользователь | Нет | Описание Меры для tooltip и справочной информации. |
| {{expression}} | Пользователь | Да | SQL-выражение Меры. Может ссылаться на поля набора данных, другие Меры и поддерживаемые переменные. |
| {{is_aggregated}} | Пользователь | Да для валидной Меры | Булевый флаг использования функций агрегации в выражении Меры: {{false}} — не используются, {{true}} — используются. Определяется пользователем. Ручной переключатель агрегированности — временное UX-упрощение. Backend проверяет фактическое выражение; при противоречии флага и выражения (Шаг 3) *сохраняет Меру как {{invalid}} с причиной, а не блокирует сохранение*. Проверка булевого флага имеет три исхода: уверенное несовпадение → {{invalid}}; неопределённый (напр. вложенные Меры, неизвестная функция) → статус не меняется. |
| {{data_type}} | Пользователь / система по умолчанию | Да | Логический тип результата Меры; состав коллекции типов аналогичен таковому у полей набора данных. |
| {{hierarchy}} | Пользователь | Нет | Display-группа, в которой Мера отображается в списке Мер и панели полей. |
| {{level}} | Пользователь | Нет | Порядок отображения Меры внутри {{hierarchy}}. |
| {{status}} | Система | Да | Результат backend-валидации: {{valid}} или {{invalid}}. |
| {{status_message}} | Система | Да (всегда присутствует) | Причина невалидности; *пустая строка*, если Мера валидна. Поле всегда есть в ответе (колонка БД {{NOT NULL DEFAULT ''}}, сериализуется всегда). *В Шаге 3 непустое значение — структурный JSON* {{ {"code","params","message"} }}: стабильный код причины ({{code}}), параметры ({{field}}/{{measure}}/{{variable}}/…) и замороженный fallback-текст {{message}}. В ответе отдаётся *как есть* (не отрендеренным) — frontend собирает человекочитаемый текст из {{code}}+{{params}} (локализуемо), {{message}} использует только как fallback для неизвестных кодов; сырую строку не показывает. |

h4. 2.1. Поля, которые задаёт пользователь

Пользователь вручную задаёт:
* {{alias}} при создании и при редактировании Меры (в том числе используемой);
* {{description}};
* {{expression}};
* {{is_aggregated}}, на данном этапе задаётся пользователем;
* {{data_type}}, если предложенное значение по умолчанию нужно изменить;
* {{hierarchy}};
* {{level}}.

Пользователь не должен вручную задавать:
* {{id}};
* {{name}};
* {{status}};
* {{status_message}}.

h4. 2.2. Правила для {{alias}}

{{alias}} — человекочитаемое название Меры.

Для {{alias}} разрешены только:
* буквы;
* цифры;
* пробелы;
* знак подчёркивания.

Не допускаются:
* кавычки;
* круглые, квадратные и фигурные скобки;
* математические и логические операторы;
* спецсимволы, которые могут выглядеть как синтаксис выражения.

{{alias}} можно изменять после создания Меры *свободно, в том числе у используемой Меры*: все ссылки на Меру идут по {{name}}, а он генерируется один раз при создании и при редактировании не меняется — смена {{alias}} не затрагивает ни одной ссылки. Перед сохранением backend проверяет непустоту, допустимость символов (правила выше) и уникальность нового {{alias}} в наборе; наличие зависимых объектов при смене {{alias}} *не проверяется* и запись не блокирует.

Блокировка по зависимостям действует только на *удаление* Меры (там исчезает {{name}} и ссылки ломаются), а не на переименование {{alias}}.

h4. 2.3. Правила для {{name}}

{{name}} — системное наименование Меры.

Backend формирует {{name}} только при создании Меры по правилу:

{code}
name = "Мера." + alias, приведённый к формату системного имени
{code}

Правила преобразования:
* префикс {{Мера.}} добавляется всегда;
* пробелы в {{alias}} заменяются на подчёркивания;
* кириллица в {{name}} допускается;
* системное имя формируется в одно слово;
* {{name}} уникален в рамках одного набора данных.

Примеры:

{code}
alias = "Дата отчёта"
name = "Мера.Дата_отчёта"
{code}

{code}
alias = "Валовая прибыль"
name = "Мера.Валовая_прибыль"
{code}

Если разные {{alias}} после преобразования приводят к одному {{name}}, backend должен сохранить уникальное системное имя. Допустимое целевое правило — добавить к конфликтующему {{name}} детерминированный числовой суффикс, например {{_2}}, {{_3}}.

Пример:

{code}
alias = "Дата отчёта"  -> name = "Мера.Дата_отчёта"
alias = "Дата_отчёта" -> name = "Мера.Дата_отчёта_2"
{code}

После создания Меры {{name}} не меняется. При редактировании {{alias}} backend сохраняет прежнее {{name}}.

Визуализации, выражения других Мер, вычисляемые поля и runtime payload ссылаются на Меру по {{name}}.

h4. 2.4. Ссылки в выражениях

Поля набора данных в выражении Меры указываются по системному {{name}} поля в двойных кавычках:

{code:sql}
SUM("revenue") - SUM("cost")
{code}

Ссылки на другие Меры указываются по системному {{name}} Меры в двойных кавычках:

{code:sql}
"Мера.Валовая_прибыль" / NULLIF(SUM("revenue"), 0)
{code}

{{"Мера.Валовая_прибыль"}} означает ссылку на Меру с {{name = "Мера.Валовая_прибыль"}}, а не раскрытое выражение и не копию формулы.

Та же форма ссылки используется в выражении вычисляемого поля виджета: {{"Мера.Валовая_прибыль"}}. В {{calc}} вычисляемого поля сохраняется ссылка по неизменяемому {{name}}, а не {{alias}} и не копия {{expression}} Меры. При построении SQL backend находит Меру в {{measures}} текущего набора данных и раскрывает её актуальное выражение по тем же правилам, что и при ссылке из выражения другой Меры.

Квадратные скобки для ссылок на Меры не используются. Меры вставляются в редакторы выражений Мер и вычисляемых полей в двойных кавычках, а признак Меры определяется по префиксу {{Мера.}}.

h3. 3. Контракт использования Меры в визуализации

Визуализация не хранит полное определение Меры. Она хранит только ссылку на Меру и локальные настройки конкретного размещения.

Минимальный объект Меры на полке визуализации:

{code:json}
{
  "id": "visual_measure_4f9b7e2d",
  "type": "measure",
  "name": "Мера.Валовая_прибыль",
  "datasetId": 244
}
{code}

|| Поле || Заполняет || Описание ||
| {{id}} | Frontend | Локальный идентификатор конкретной пилюли / размещения в визуализации. Не равен {{measures[].id}} и не является ключом связи с Мерой. Нужен только если текущая модель визуализации требует instance-id для настроек, сортировки, форматирования или удаления элемента. |
| {{type}} | Frontend | Всегда {{measure}}. Отличает Меру от обычного поля и вычисляемого поля виджета. |
| {{name}} | Frontend из {{measures[].name}} | Единственная ссылка на Меру. |
| {{datasetId}} | Frontend | Идентификатор набора данных, к которому относится Мера. |

В объект использования Меры не нужно копировать:
* {{alias}};
* {{expression}};
* {{description}};
* {{is_aggregated}};
* {{data_type}};
* {{hierarchy}};
* {{level}};
* {{status}};
* {{status_message}}.

Эти данные должны подтягиваться из актуальных метаданных набора данных. Это исключает рассинхронизацию, когда Мера изменилась в наборе данных, а старая копия осталась в визуализации.

h4. 3.1. Локальные настройки размещения

Если конкретная визуализация требует настройки сортировки, форматирования, подписи, цвета, точности или других параметров для пилюли, такие параметры хранятся рядом с объектом использования Меры как настройки размещения, а не как свойства Меры.

Пример:

{code:json}
{
  "id": "visual_measure_4f9b7e2d",
  "type": "measure",
  "name": "Мера.Валовая_прибыль",
  "datasetId": 244,
  "order": "desc",
  "format": {
    "precision": 2,
    "unit": "руб."
  }
}
{code}

Такие поля не должны использоваться backend-ом как источник определения Меры.

h3. 4. Контракт фильтра по Мере в метаданных визуализации

Фильтр по Мере — это использование Меры на полке «Фильтры» с локальной настройкой режима фильтрации и условия.

Базовый контракт фильтра по Мере:

{code:json}
{
  "id": "filter_measure_6d3c3e58",
  "type": "measure",
  "name": "Мера.Валовая_прибыль",
  "datasetId": 244,
  "filter": {
    "mode": "HAVING",
    "values": [0],
    "operators": [">"]
  }
}
{code}

|| Поле || Заполняет || Описание ||
| {{id}} | Frontend | Локальный идентификатор фильтра / пилюли фильтра. |
| {{type}} | Frontend | Всегда {{measure}}. |
| {{name}} | Frontend из {{measures[].name}} | Ссылка на Меру. |
| {{datasetId}} | Frontend | Идентификатор набора данных. |
| {{filter.mode}} | Пользователь / Frontend | {{WHERE}} или {{HAVING}}. Доступность режима зависит от {{is_aggregated}} Меры. |
| {{filter.values}} | Пользователь | Непустой массив значений условия. Элемент {{null}} — проверка на пустое значение (только в форме списка без {{operators}}). |
| {{filter.operators}} | Пользователь | Массив операторов. Пуст → {{values}} трактуется как список ({{IN}} / {{NOT IN}}); иначе длина равна длине {{values}}. Allowlist: {{=}}, {{!=}}, {{<>}}, {{>}}, {{>=}}, {{<}}, {{<=}}, семейство {{like_*}} / {{likeic_*}}. |
| {{filter.not}} | Пользователь | Отрицание условия ({{NOT IN}} / {{IS NOT NULL}}). |
| {{filter.logicOr}} | Пользователь | {{1}} — условия через {{OR}}; иначе через {{AND}}. |

h4. 4.1. Структурное хранение условия

Условие фильтра хранится структурно ({{values}} / {{operators}} / {{not}} / {{logicOr}}), чтобы frontend и backend могли:
* валидировать оператор отдельно от значения;
* корректно типизировать значение;
* не превращать пользовательский ввод в произвольный SQL;
* расширять набор условий без разрыва контракта.

Источником истины в метаданных визуализации является структурный набор полей {{values}} / {{operators}} / {{not}} / {{logicOr}}. Отдельного {{value_type}} в условии нет: тип значения берётся из {{data_type}} Меры.

h4. 4.2. HAVING-фильтр для Сводной таблицы

Для уровня-специфичной HAVING-фильтрации Сводной таблицы к фильтру добавляются параметры применения.

{code:json}
{
  "id": "filter_measure_6d3c3e58",
  "type": "measure",
  "name": "Мера.Валовая_прибыль",
  "datasetId": 244,
  "filter": {
    "mode": "HAVING",
    "values": [0],
    "operators": [">"],
    "apply_mode": "selected",
    "target_dimensions": ["col_month"]
  }
}
{code}

|| Поле || Описание ||
| {{filter.apply_mode}} | {{all}} или {{selected}}. Используется только для HAVING-фильтрации Сводной таблицы. |
| {{filter.target_dimensions}} | Массив идентификаторов измерений, к которым применяется HAVING. Пустой массив при {{apply_mode = "all"}}. |

Эти поля не нужны для обычного WHERE-фильтра и для базовых визуализаций без уровня-специфичной HAVING-логики.

h3. 5. Runtime payload для {{/v1/api/recordsets/<dataset_id>}}

Payload запроса данных — это не место хранения Меры. Это краткое описание того, какие Меры участвуют в конкретном запросе и где backend должен раскрыть их выражения.

{{alias}} внутри runtime payload является техническим alias результата запроса. Он не равен {{measures[].alias}}, не является человекочитаемым alias Меры и не хранится в метаданных Меры. Если текущий backend-контракт позволяет переименование технического поля, предпочтительное название для него — {{result_alias}} или {{output_alias}}, чтобы не смешивать его с {{measures[].alias}}.

Если ссылка на Меру находится внутри {{calc}} вычисляемого поля, runtime-элемент продолжает использовать существующий контракт вычисляемого поля. {{type = "measure"}} применяется только при прямом использовании самой Меры в runtime-блоке; для ссылки внутри {{calc}} отдельный объект Меры не формируется.

h4. 5.1. Мера на полке «Значения»

{code:json}
{
  "select": [
    {
      "type": "measure",
      "name": "Мера.Валовая_прибыль",
      "alias": "[values][0]"
    }
  ],
  "group": [],
  "where": [],
  "having": [],
  "series": {
    "enable": 0
  }
}
{code}

{{alias}} в примере — технический alias результата запроса. Он нужен только в runtime payload, если текущий механизм сопоставляет колонки ответа с полками визуализации через значения вида {{[values][0]}}, {{[categories]}}, {{[series][0]}}.

h4. 5.2. Мера как вычисляемое измерение на полках группировки

Допустимо только для неагрегированных Мер.

{code:json}
{
  "group": [
    {
      "type": "measure",
      "name": "Мера.Маржинальность_категория",
      "alias": "[categories]"
    }
  ],
  "select": [
    {
      "type": "measure",
      "name": "Мера.Маржинальность_категория",
      "alias": "[categories]"
    }
  ],
  "where": [],
  "having": []
}
{code}

h4. 5.3. WHERE-фильтр по Мере

Допустимо только для неагрегированных Мер.

{code:json}
{
  "where": [
    {
      "type": "measure",
      "name": "Мера.Маржинальность_строки",
      "values": [0],
      "operators": [">"]
    }
  ],
  "having": []
}
{code}

h4. 5.4. HAVING-фильтр по Мере

Допустимо только для агрегированных Мер.

{code:json}
{
  "where": [],
  "having": {
    "condition": "",
    "items": [
      {
        "type": "measure",
        "name": "Мера.Валовая_прибыль",
        "values": [0],
        "operators": [">"]
      }
    ]
  }
}
{code}

h4. 5.5. Сортировка по Мере

Если выбранная визуализация поддерживает сортировку по Мере, в {{order}} передаётся ссылка на Меру.

{code:json}
{
  "order": [
    {
      "type": "measure",
      "name": "Мера.Валовая_прибыль",
      "direction": "desc"
    }
  ]
}
{code}

h3. 6. API-контракт создания и редактирования Меры

Конкретные backend-объекты и команды API необходимо сверить с актуальной реализацией. Семантика контракта Меры должна соответствовать правилам ниже.

h4. 6.1. Создание Меры

При создании Меры frontend передаёт {{alias}} и остальные пользовательские параметры Меры. {{name}} в payload создания не передаётся.

Минимальный фрагмент payload создания, отражающий контракт наименования (полный обязательный состав — {{alias}}, {{expression}}, {{is_aggregated}}, {{data_type}}, см. расширенный пример ниже):

{code:json}
{
  "alias": "Дата отчёта"
}
{code}

Расширенный payload создания:

{code:json}
{
  "alias": "Валовая прибыль",
  "description": "Разница между выручкой и себестоимостью",
  "expression": "SUM(\"revenue\") - SUM(\"cost\")",
  "is_aggregated": true,
  "data_type": "number",
  "hierarchy": "Финансовые показатели",
  "level": 10
}
{code}

Backend при создании:
* валидирует {{alias}};
* формирует уникальное {{name}};
* сохраняет {{alias}} и {{name}};
* выполняет валидацию выражения и вычисляет {{status}} / {{status_message}};
* возвращает frontend-у сохранённую Меру.

Пример ответа:

{code:json}
{
  "id": "847b1ec3-bbf8-4365-85fb-c4fca2a06e2e",
  "name": "Мера.Валовая_прибыль",
  "alias": "Валовая прибыль",
  "description": "Разница между выручкой и себестоимостью",
  "expression": "SUM(\"revenue\") - SUM(\"cost\")",
  "is_aggregated": true,
  "data_type": "number",
  "hierarchy": "Финансовые показатели",
  "level": 10,
  "status": "valid",
  "status_message": ""
}
{code}

h4. 6.2. Редактирование Меры

Перед редактированием frontend должен получить актуальное состояние Меры через чтение метаданных набора данных или отдельный {{get/list}}-контракт.

При редактировании frontend может передавать изменяемые пользовательские поля:
* {{alias}} (в том числе у используемой Меры);
* {{description}};
* {{expression}};
* {{is_aggregated}};
* {{data_type}};
* {{hierarchy}};
* {{level}}.

{{name}} не должен изменяться при редактировании. Если frontend передал {{name}} в payload обновления, backend должен игнорировать это поле или вернуть ошибку валидации в соответствии с принятым API-поведением. В любом случае сохранённое {{name}} существующей Меры не должно измениться.

Если в payload редактирования передан новый {{alias}}, backend проверяет его непустоту, допустимость символов и уникальность в наборе, сохраняет новый {{alias}} и оставляет прежний {{name}}. Наличие зависимых объектов при смене {{alias}} не проверяется: смена {{alias}} не меняет {{name}} и не затрагивает ссылки. Блокировка по зависимостям — только на удаление Меры.

Пример payload редактирования alias:

{code:json}
{
  "alias": "Валовая прибыль руб"
}
{code}

Пример ответа после редактирования:

{code:json}
{
  "id": "847b1ec3-bbf8-4365-85fb-c4fca2a06e2e",
  "name": "Мера.Валовая_прибыль",
  "alias": "Валовая прибыль руб",
  "description": "Разница между выручкой и себестоимостью",
  "expression": "SUM(\"revenue\") - SUM(\"cost\")",
  "is_aggregated": true,
  "data_type": "number",
  "hierarchy": "Финансовые показатели",
  "level": 10,
  "status": "valid",
  "status_message": ""
}
{code}

h4. 6.3. Ошибки валидации

Backend должен возвращать ошибку валидации, если:
* {{alias}} пустой или содержит недопустимые символы;
* новый {{alias}} не уникален в рамках набора данных;
* выражение Меры не разбирается синтаксически, содержит самоссылку, цикл или блочную форму переменной ({{условие;значение}});
* невозможно сформировать системное имя (в {{alias}} нет ни одной буквы или цифры после нормализации). *(Конфликт {{name}} между разными Мерами не является ошибкой: backend добавляет детерминированный суффикс {{_2}}, {{_3}} и всегда получает уникальное имя.)*

*Контекстные ошибки сохранение НЕ блокируют — Мера сохраняется со {{status = "invalid"}} и причиной в {{status_message}} (Шаг 3): расхождение {{is_aggregated}} с выражением, ссылка на отсутствующее поле или отсутствующую/невалидную Меру, неизвестная переменная.*

Frontend должен показывать пользователю понятное сообщение и не считать Меру сохранённой, если backend вернул ошибку.

h4. 6.4. Удаление Меры

Удаление Меры блокируется, если на неё есть ссылки из визуализаций отчётов, выражений других Мер и/или выражений вычисляемых полей. Смена {{alias}} при этом не блокируется никогда (см. 2.2) — блокировка по зависимостям действует только на удаление, потому что при удалении исчезает {{name}} и ссылки ломаются.

*Блокировка не является ошибкой запроса.* Backend отвечает {{HTTP 200}} и телом, описывающим отказ:

{code:json}
{
  "deleted": false,
  "dependents": [
    {"usage_kind": "report", "Номер отчёта": 128, "Отчёт": "Продажи за квартал", "Компонент": "Таблица сводная"},
    {"usage_kind": "measure", "id": "0f3c…", "object_name": "Мера.Маржинальность", "alias": "Маржинальность", "status": "valid"}
  ]
}
{code}

При успешном удалении в ответе приходит актуальный массив {{measures}} набора, ключа {{deleted}} нет.

*Дискриминатор для frontend — наличие ключа {{deleted}}, а не длина {{dependents}}.* Возможен редкий случай двойной гонки, когда возвращается {{deleted: false}} с *пустым* {{dependents}}: зависимость появилась уже после первичной проверки (условный DELETE её увидел и отказал), а к моменту пересбора списка исчезла. Ориентироваться на длину массива нельзя — иначе пользователю покажут «удалено» при неудалённой Мере.

h5. Состав {{dependents}}

Элементы двух видов, различаются полем {{usage_kind}}; *набор полей у видов разный*, frontend должен обрабатывать оба.

|| {{usage_kind}} || Что означает || Поля элемента ||
| {{report}} | Мера используется в визуализации отчёта | {{Номер отчёта}}, {{Отчёт}}, {{Компонент}} |
| {{measure}} | Мера используется в выражении другой Меры | {{id}}, {{object_name}}, {{alias}}, {{status}} |

Ссылка из выражения вычисляемого поля также приводит к {{deleted = false}} и представляется существующим видом {{usage_kind = "report"}}, поскольку вычисляемое поле входит в визуализацию отчёта. Новый вид {{usage_kind}} не вводится; внутри элемента {{report}} прямое использование Меры и ссылка из вычисляемого поля не различаются.

Ограничения текущей реализации, которые frontend должен учитывать:
* {{usage_kind = "report"}} *не различает* ось, фильтр, сортировку и вычисляемое поле — источник ссылки в метаданных связи не хранится. Все использования внутри отчёта приходят одним видом;
* {{Компонент}} — наименование *типа* компонента (например «Таблица сводная», «Диаграмма столбчатая»), а не заголовок конкретного визуала;
* поля {{object_type}} и {{link}} не передаются; текст диалога для пользователя frontend формирует сам — backend пользовательское сообщение в этом ответе не заполняет;
* самоссылка Меры (Мера ссылается сама на себя) удалению *не* препятствует. Такая Мера может существовать только как унаследованные данные, сохранённые до появления проверки: создать или сохранить новую Меру с самоссылкой нельзя (см. 6.3).

h4. 6.5. Использование невалидной Меры в запросе

Мера со статусом, отличным от {{valid}} (штатно — {{invalid}}), не может участвовать в запросе данных. Построитель отвергает её *во всех* блоках payload ({{select}}, {{where}}, {{group}}, {{having}}, {{order}}) — SQL с невалидной Мерой не формируется и не исполняется.

Backend возвращает {{HTTP 400}} с текстом:

{code}
Запрос не выполнен: Мера "Мера.X" не может быть использована, так как невалидна (статус "invalid"): <причина>. Исправьте Меру в наборе данных (блок SELECT)
{code}

Если причина в метаданных не заполнена, возвращается тот же текст без фрагмента «: <причина>».

*Ошибка всегда заканчивается указанием блока* — {{(блок SELECT)}}, {{(блок WHERE)}}, {{(блок GROUP BY)}}, {{(блок HAVING)}} или {{(блок ORDER BY)}}. По нему frontend определяет, где именно стоит проблемная Мера. Завершающей точки в тексте нет: она срезается при формировании ответа.

*Причина приходит уже человекочитаемой* — в отличие от поля {{status_message}} в метаданных набора (см. 2), где frontend получает структурный JSON и рендерит текст сам. В ошибке запроса расшифровку выполняет backend.

Рекомендуемое поведение frontend: не доводить пользователя до этой ошибки — Меры со {{status = "invalid"}} отображать в списке полей как недоступные (по данным {{measures[]}} из набора) и не давать разместить их в визуализации.
