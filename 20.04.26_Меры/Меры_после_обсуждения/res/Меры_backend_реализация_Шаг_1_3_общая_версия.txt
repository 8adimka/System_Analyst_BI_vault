h3. Контекст и цель истории.
Полное описание продуктовой логики приведено в Эпике по Мерам ([https://jira.modusbi.ru/browse/MB-4364]).

Настоящая История реализует *первый шаг backend-доработок* по внедрению сущности *«Мера»* в аналитическом портале: серверную модель Меры в метаданных *произвольного* набора данных, backend-контракты управления Мерами, валидацию выражений, жизненный цикл статусов и ссылочную целостность.

Мера создаётся один раз на уровне набора данных и далее используется как именованное вычислимое SQL-выражение. Ключом внешних ссылок на Меру является её уникальное системное имя {{name}} в рамках одного набора данных. Стабильный {{id}} хранится в метаданных как технический идентификатор записи, но не используется как ключ связи для визуализаций, выражений других Мер и вычисляемых полей.

В рамках этой Истории Меры ещё не размещаются на полках визуализаций и не участвуют в генерации SQL визуализаций. Поддержка объектов {{type = "measure"}} в метаданных визуализаций и подстановка выражений Мер в SQL-запросы реализуются в следующем шаге.

----
h3. Границы истории.
В рамках Истории реализуется:
* хранение массива {{measures}} в метаданных *произвольного* набора данных;
* возврат Мер при чтении произвольного набора данных;
* создание новой Меры;
* редактирование существующей Меры;
* удаление Меры;
* генерация уникального {{id}} и {{name}} Меры на backend-е при создании;
* сохранение пользовательских полей {{alias}}, {{description}}, {{expression}}, {{aggregation_kind}}, {{data_type}}, {{hierarchy}}, {{level}};
* вычисление и сохранение системных полей {{status}} и {{status_message}};
* backend-валидация {{alias}}, выражения, ссылок на поля, ссылок на другие Меры, глобальных переменных и признака {{aggregation_kind}};
* защита от самоссылок и циклических зависимостей между Мерами;
* ревалидация зависимых Мер и вычисляемых полей при изменении Меры или SQL-запроса набора данных;
* блокировка изменения {{alias}} при наличии зависимых объектов;
* блокировка удаления Меры при наличии зависимых объектов;
* возврат списка зависимостей, достаточного для отображения пользователю причины блокировки;
* сохранение обратной совместимости существующих наборов данных без Мер.

----
h3. Ключевые правила модели.
* *Мера* — именованное SQL-выражение, определённое на уровне *произвольного* набора данных. Мера не вычисляется при создании. На первом шаге backend только хранит, валидирует и возвращает определение Меры.
* {{alias}} — человекочитаемое название Меры. Пользователь вводит {{alias}} при создании и может изменять его после создания только если Мера не используется в визуализациях, выражениях других Мер или вычисляемых полях. {{alias}} должен быть уникален в рамках одного набора данных.
* {{name}} — системное наименование Меры. Backend формирует {{name}} только при создании по правилу {{Мера.}} + {{alias}}, приведённый к формату системного имени. {{name}} уникально в рамках одного набора данных, не меняется после создания и является единственным ключом внешних ссылок на Меру.
* {{id}} — стабильный технический идентификатор записи Меры. Генерируется backend-ом при создании и не меняется при редактировании. {{id}} не используется как внешний ключ связи в визуализациях, выражениях других Мер и вычисляемых полях.
* {{status}} и {{status_message}} вычисляются backend-ом по результатам валидации. Frontend не должен передавать эти поля как пользовательский ввод.
* {{aggregation_kind}} задаётся пользователем явно: {{1}} — агрегированная Мера, {{0}} — неагрегированная Мера. Backend должен проверить соответствие выбранного значения фактическому выражению Меры.
* Поля и Меры в формулах указываются по системному name в двойных кавычках, например "report_date" и "Мера.Валовая_прибыль".
* Frontend не формирует {{name}} самостоятельно и не добавляет префикс {{Мера.}}. Backend является единственным источником {{name}}.

----
h3. Описание текущего поведения.
Сейчас в backend-модели набора данных отсутствует отдельная сущность «Мера».

Frontend не может реализовать управление Мерами в настройках произвольного набора данных без backend-поддержки хранения, валидации и CRUD-контрактов.

----
h3. Описание целевого поведения.
Для *произвольного* набора данных backend должен поддержать Меры как часть метаданных набора данных.

Пользователь с правами редактирования набора данных через frontend должен иметь возможность:
# открыть настройки произвольного набора данных и получить список сохранённых Мер;
# создать новую Меру без ручного ввода {{name}};
# получить от backend-а сгенерированные {{id}}, {{name}}, {{status}} и {{status_message}};
# отредактировать пользовательские свойства Меры;
# изменить {{alias}} только при отсутствии зависимых объектов;
# удалить Меру только при отсутствии зависимых объектов;
# сохранить набор данных даже при наличии Мер со статусом {{invalid}};
# после изменения SQL-запроса набора данных получить актуальные статусы Мер после повторной backend-валидации.

Для *простых* и *составных* наборов данных backend не должен создавать и сохранять Меры. При попытке выполнить операцию управления Мерами для таких наборов данных backend должен вернуть контролируемую ошибку.

----
h3. Требования к реализации.

h4. 1. Затрагиваемый backend-объект и API-контракты.
Базовый backend-объект: {{datasets}}.

Backend должен расширить текущие команды чтения и сохранения наборов данных либо добавить специализированные команды управления Мерами в рамках объекта {{datasets}}. Конкретные имена команд необходимо сверить с актуальной реализацией API, но семантика должна покрывать следующие операции:
|| Операция || Backend-объект || Требуемая семантика ||
| Чтение набора данных и списка Мер | {{datasets}} | {{get}} / {{list}} или текущий эквивалент чтения набора данных должен возвращать массив {{measures}} в составе метаданных произвольного набора данных |
| Создание Меры | {{datasets}} | Текущий {{update}} метаданных набора данных или специализированная команда создания Меры должна создать запись Меры, сгенерировать {{id}} и {{name}}, выполнить валидацию и вернуть сохранённую Меру |
| Редактирование Меры | {{datasets}} | Текущий {{update}} метаданных набора данных или специализированная команда обновления Меры должна изменить пользовательские поля Меры без изменения {{name}} существующей Меры |
| Изменение {{hierarchy}} / {{level}} | {{datasets}} | Обновление Меры должно сохранять display-группу и порядок отображения |
| Удаление Меры | {{datasets}} | Команда удаления должна удалить Меру только при отсутствии зависимых объектов |
| Проверка зависимостей | {{datasets}} | Отдельная команда или внутренняя проверка должна вернуть зависимости Меры для блокировки изменения {{alias}} и удаления |
| Ревалидация Мер после изменения SQL набора данных | {{datasets}} | При успешном сохранении и проверке SQL произвольного набора данных backend должен заново проверить все Меры этого набора |

Если используется стандартный для портала паттерн {{object + command + data}}, ответы команд должны сохранять текущий формат API: успешные операции возвращают {{status = 200}} и актуальные данные в {{data}}, ошибки валидации или прав возвращают неуспешный {{status}}, пользовательское {{message}} и, где применимо, структурированные детали ошибки или список зависимостей.

Перед операциями изменения backend должен работать с актуальным состоянием набора данных, полученным через {{get/list}} или внутренний эквивалент чтения текущего состояния. Это необходимо, чтобы корректно определить существующую запись Меры, прежнее значение {{alias}}, неизменяемое {{name}}, текущий набор зависимостей и набор Мер, требующих ревалидации.

---
h4. 2. Структура метаданных Меры.
Меры хранятся в метаданных *произвольного* набора данных в массиве {{measures}}.

{code:json}
{
  "measures": [
    {
      "id": "847b1ec3-bbf8-4365-85fb-c4fca2a06e2e",
      "name": "Мера.Валовая_прибыль",
      "alias": "Валовая прибыль",
      "description": "Разница между выручкой и себестоимостью",
      "expression": "SUM(\"revenue\") - SUM(\"cost\")",
      "aggregation_kind": 1,
      "data_type": "number",
      "hierarchy": "Финансовые показатели",
      "level": 10,
      "status": "valid",
      "status_message": ""
    }
  ]
}
{code}

|| Поле || Кто задаёт || Обязательность || Backend-требование ||
| {{id}} | Backend | Да | Стабильный {{UUID}} Меры. Генерируется при создании, не меняется при редактировании. Не является внешним ключом связи для визуализаций и формул. |
| {{name}} | Backend | Да | Системное наименование Меры. Генерируется при создании на основании {{alias}}, уникально в рамках одного набора данных, не меняется после создания. |
| {{alias}} | Пользователь | Да | Человекочитаемое название Меры. Уникально в рамках набора данных. Backend валидирует допустимые символы и возможность изменения. |
| {{description}} | Пользователь | Нет | Описание Меры. Backend хранит и возвращает значение без изменения смысла. |
| {{expression}} | Пользователь | Да | SQL-выражение Меры. Backend парсит выражение, проверяет ссылки и вычисляет статус. |
| {{aggregation_kind}} | Пользователь | Да | Признак агрегированности: {{1}} — агрегированная, {{0}} — неагрегированная. Backend проверяет соответствие фактическому выражению. |
| {{data_type}} | Пользователь / система по умолчанию | Да | Логический тип результата Меры: {{number}}, {{string}}, {{date}}, {{datetime}} и другие поддержанные значения. |
| {{hierarchy}} | Пользователь | Нет | Display-группа Меры. Backend хранит и возвращает значение. |
| {{level}} | Пользователь | Нет | Порядок отображения внутри {{hierarchy}}. Backend хранит и возвращает значение. |
| {{status}} | Backend | Да | {{valid}} или {{invalid}}. Вычисляется backend-ом. |
| {{status_message}} | Backend | Нет | Причина невалидности или пустая строка для {{valid}}. Должна быть пригодна для отображения пользователю. |

Backend может хранить дополнительные служебные структуры для ускорения проверок зависимостей, например связи {{measure -> field}} и {{measure -> measure}}. Такие структуры должны пересчитываться backend-ом и не должны требовать ручного заполнения со стороны frontend.

---
h4. 3. Создание Меры.
При создании Меры frontend передаёт только пользовательские поля:
* {{alias}};
* {{description}};
* {{expression}};
* {{aggregation_kind}};
* {{data_type}};
* {{hierarchy}};
* {{level}}.

Frontend не должен передавать как пользовательский ввод:
* {{id}};
* {{name}};
* {{status}};
* {{status_message}}.

Минимальный payload создания:
{code:json}
{
  "alias": "Валовая прибыль",
  "description": "Разница между выручкой и себестоимостью",
  "expression": "SUM(\"revenue\") - SUM(\"cost\")",
  "aggregation_kind": 1,
  "data_type": "number",
  "hierarchy": "Финансовые показатели",
  "level": 10
}
{code}

Backend при создании должен:
# проверить, что набор данных является *произвольным*;
# проверить права пользователя на изменение набора данных;
# проверить обязательность и допустимость пользовательских полей;
# проверить уникальность {{alias}} в рамках набора данных;
# сгенерировать стабильный {{id}} в формате {{UUID}};
# сформировать уникальное {{name}} в рамках набора данных;
# выполнить валидацию выражения и зависимостей;
# определить {{status}} и {{status_message}};
# сохранить Меру в массиве {{measures}};
# вернуть frontend-у сохранённую Меру с системными полями.

Правила формирования {{name}}:
* префикс {{Мера.}} добавляется всегда;
* за основу берётся {{alias}};
* пробелы заменяются на подчёркивания;
* кириллица допускается;
* системное имя формируется в одно слово;
* {{name}} должно быть уникальным в рамках одного набора данных;
* при коллизии backend должен сформировать уникальное имя, например добавив детерминированный числовой суффикс {{_2}}, {{_3}}.

Пример:
{code}
alias = "Валовая прибыль"
name = "Мера.Валовая_прибыль"
{code}

Пример коллизии и возможного её разрешения:
{code}
alias = "Дата отчёта"  -> name = "Мера.Дата_отчёта"
alias = "Дата_отчёта" -> name = "Мера.Дата_отчёта_2"
{code}

Пример успешного ответа:
{code:json}
{
  "id": "847b1ec3-bbf8-4365-85fb-c4fca2a06e2e",
  "name": "Мера.Валовая_прибыль",
  "alias": "Валовая прибыль",
  "description": "Разница между выручкой и себестоимостью",
  "expression": "SUM(\"revenue\") - SUM(\"cost\")",
  "aggregation_kind": 1,
  "data_type": "number",
  "hierarchy": "Финансовые показатели",
  "level": 10,
  "status": "valid",
  "status_message": ""
}
{code}

h4. 4. Редактирование Меры.
При редактировании существующей Меры backend должен позволять изменять пользовательские поля:
* {{alias}} — только если Мера не используется в зависимых объектах;
* {{description}};
* {{expression}};
* {{aggregation_kind}};
* {{data_type}};
* {{hierarchy}};
* {{level}}.

{{name}} существующей Меры *не должен изменяться* при редактировании.

При редактировании backend должен:
# проверить, что набор данных является *произвольным*;
# проверить права пользователя на изменение набора данных;
# найти редактируемую Меру в актуальном состоянии набора данных;
# если изменяется {{alias}}, проверить отсутствие зависимых объектов;
# проверить уникальность нового {{alias}} в рамках набора данных;
# сохранить изменяемые пользовательские поля;
# повторно выполнить валидацию выражения и зависимостей;
# пересчитать {{status}} и {{status_message}};
# запустить ревалидацию зависимых Мер и вычисляемых полей, если изменение влияет на их валидность;
# вернуть frontend-у актуальное состояние Меры и, при необходимости, обновлённые статусы зависимых объектов.

Изменение {{alias}} не должно менять {{name}}.

Пример payload редактирования {{alias}} для Меры без зависимых объектов:
{code:json}
{
  "alias": "Валовая прибыль руб"
}
{code}

Пример ответа после редактирования:
{code:json}
{
  "id": "847b1ec3-bbf8-4365-85fb-c4fca2a06e2e",
  "name": "Мера.Валовая_прибыль",
  "alias": "Валовая прибыль руб",
  "description": "Разница между выручкой и себестоимостью",
  "expression": "SUM(\"revenue\") - SUM(\"cost\")",
  "aggregation_kind": 1,
  "data_type": "number",
  "hierarchy": "Финансовые показатели",
  "level": 10,
  "status": "valid",
  "status_message": ""
}
{code}

---
h4. 5. Удаление Меры.
Backend должен разрешать физическое удаление Меры из массива {{measures}} только если Мера не используется в зависимых объектах.

Перед удалением backend должен проверить ссылки на {{name}} удаляемой Меры:
* в выражениях других Мер текущего набора данных;
* в вычисляемых полях, если они могут ссылаться на Меры;
* в метаданных визуализаций, если такие ссылки уже существуют в данных или появятся после следующих этапов внедрения Мер.

Если зависимостей нет:
* backend удаляет запись Меры из массива {{measures}};
* backend выполняет ревалидацию объектов, которые могли зависеть от состава Мер;
* backend возвращает успешный ответ и актуальный список Мер или актуальное состояние набора данных.

Если зависимости есть:
* удаление блокируется;
* запись Меры не удаляется;
* каскадное удаление из визуализаций, других Мер или вычисляемых полей не выполняется;
* backend возвращает контролируемую ошибку и список зависимых объектов, достаточный для отображения пользователю.

Сообщение для пользователя:
*«Нельзя удалить Меру, используемую в визуализациях и/или в выражениях. Для удаления Меры необходимо разрешить конфликты:
[Список ссылок на визуализации, меры и вычисляемые поля, где используется удаляемая Мера]»*

---
h4. 6. Валидация {{alias}}.
Backend должен повторно валидировать {{alias}} независимо от frontend-проверок.

Для {{alias}} разрешены:
* буквы;
* цифры;
* пробелы;
* знак подчёркивания.

Не допускаются:
* пустое значение;
* кавычки;
* круглые, квадратные и фигурные скобки;
* математические и логические операторы;
* спецсимволы, которые могут выглядеть как синтаксис выражения.

{{alias}} должен быть уникален в рамках одного набора данных. При редактировании backend должен разрешать сохранение прежнего {{alias}} для той же Меры и блокировать совпадение с {{alias}} другой Меры этого же набора данных.

---
h4. 7. Валидация выражения Меры.
При создании и редактировании Меры backend должен выполнить проверки:
* выражение {{expression}} заполнено;
* выражение синтаксически разбирается как SQL-выражение в рамках поддержанного синтаксиса вычисляемых полей;
* поля набора данных, указанные в двойных кавычках, существуют в актуальном составе полей текущего набора данных;
* Меры, указанные в двойных кавычках в формате {{"Мера.<name>"}}, существуют в текущем наборе данных;
* выражение не содержит ссылку на сохраняемую Меру;
* граф зависимостей Мер не содержит циклических зависимостей любой глубины;
* используемые глобальные переменные существуют и доступны в текущем контексте;
* выбранный пользователем {{aggregation_kind}} соответствует фактической агрегированности выражения.

Пример ссылки на поле:
{code:sql}
SUM("revenue") - SUM("cost")
{code}

Пример ссылки на другую Меру:
{code:sql}
"Мера.Валовая_прибыль" / NULLIF(SUM("revenue"), 0)
{code}

Если выражение Меры не содержит ссылок на поля набора данных и использует только константы, глобальные переменные или другие валидные Меры, отсутствие ссылок на поля не является ошибкой. Такая Мера может получить статус {{valid}}, если остальные проверки пройдены.

При обнаружении самоссылки или циклической зависимости сохранение блокируется с ошибкой:
*«Выражение Меры содержит циклическую зависимость»*.

---
h4. 8. Правила сохранения {{valid}}/{{invalid}}.
Backend должен различать ошибки, которые блокируют сохранение, и ошибки, при которых Мера может быть сохранена со статусом {{invalid}}.

Сохранение должно блокироваться, если:
* набор данных не является *произвольным*;
* у пользователя нет прав на изменение набора данных;
* не заполнены обязательные поля;
* {{alias}} пустой, неуникальный или содержит недопустимые символы;
* невозможно сформировать уникальное {{name}} при создании;
* выражение не может быть синтаксически разобрано;
* обнаружена самоссылка или циклическая зависимость;
* {{aggregation_kind}} противоречит фактической агрегированности выражения;
* пользователь пытается изменить {{alias}} Меры, у которой есть зависимые объекты.

Мера может быть сохранена со статусом {{invalid}}, если выражение синтаксически разобрано, но невалидно в текущем контексте набора данных, например:
* выражение ссылается на поле, которого нет в актуальном составе полей набора данных;
* выражение ссылается на отсутствующую или невалидную Меру;
* используемая глобальная переменная не может быть разрешена в текущем контексте;
* выражение не проходит контекстную SQL-проверку относительно текущего SQL-запроса набора данных.

Для Меры со статусом {{invalid}} backend должен:
* сохранить запись Меры в метаданных;
* установить {{status = "invalid"}};
* заполнить {{status_message}} понятной причиной невалидности;
* вернуть сохранённую Меру frontend-у.

Для Меры со статусом {{valid}} backend должен:
* установить {{status = "valid"}};
* вернуть {{status_message}} пустой строкой.

Набор данных может быть сохранён даже при наличии Мер со статусом {{invalid}}.

---
h4. 9. Проверка {{aggregation_kind}}.
{{aggregation_kind}} задаётся пользователем вручную и сохраняется в метаданных Меры.

Однако, backend должен проверять фактическое соответствие заданной агрегированности выражения:
* например, при помощи отправки пробного SQL-клауза специфического запроса для выбранной агрегированности.

Если пользователь передал {{aggregation_kind = 1}}, а выражение фактически не является агрегированным, backend должен вернуть ошибку валидации.

Если пользователь передал {{aggregation_kind = 0}}, а выражение содержит агрегатные функции и не может использоваться в SQL-клаузах для неагрегированных Мер - backend также должен вернуть ошибку валидации.

При противоречии в выбранном {{aggregation_kind}} - Мера не создаётся и не обновляется. Выводится понятное предупреждение об ошибке в выбранной агрегации Меры. Для существующей Меры должно сохраняться прежнее валидное состояние до неуспешной операции обновления.

---
h4. 10. Проверка и возврат зависимостей.
Backend должен уметь определить, используется ли Мера в зависимых объектах.

Минимальный набор зависимостей:
* другая Мера, в выражении которой есть ссылка на {{name}} проверяемой Меры;
* вычисляемое поле, в выражении которого есть ссылка на {{name}} проверяемой Меры;
* визуализация, отчёт или компонент, где есть ссылка на {{name}} проверяемой Меры, если такие ссылки присутствуют в метаданных.

Зависимости используются:
* для блокировки изменения {{alias}};
* для блокировки удаления Меры;
* для ревалидации зависимых Мер и вычисляемых полей после изменения выражения, статуса или удаления связанных объектов.

Ответ backend-а при блокировке должен содержать:
* признак ошибки;
* пользовательское сообщение;
* список зависимых объектов.

Список зависимых объектов должен быть достаточным для frontend-а, чтобы показать пользователю, где нужно разрешить конфликт. Рекомендуемый минимальный состав элемента списка:
|| Поле || Описание ||
| {{object_type}} | Тип зависимого объекта: {{measure}}, {{calculated_field}}, {{report}}, {{visualization}} или текущий системный эквивалент |
| {{object_id}} | Идентификатор зависимого объекта, если он есть |
| {{object_name}} | Название или alias зависимого объекта для отображения |
| {{usage_kind}} | Тип использования: выражение Меры, вычисляемое поле, полка визуализации, фильтр и т.д. |
| {{link}} | Ссылка или путь для перехода к объекту, если текущий backend может её сформировать |

Если backend не может сформировать прямую ссылку на объект, он должен вернуть минимум тип, идентификатор и отображаемое название зависимого объекта.

Сообщение при блокировке изменения {{alias}}:
*«Нельзя переименовать Меру, используемую в визуализациях и/или в выражениях. Для переименования Меры необходимо разрешить конфликты:
[Список ссылок на визуализации, меры и вычисляемые поля, где используется переименовываемая Мера]»*

---
h4. 11. Жизненный цикл после изменения SQL набора данных.
При успешном сохранении и проверке SQL-запроса *произвольного* набора данных backend должен заново определить актуальный состав полей и выполнить ревалидацию всех Мер этого набора.

Правила ревалидации:
* Меры, выражения которых ссылаются на отсутствующие поля, получают {{status = "invalid"}} и заполненный {{status_message}};
* Меры, зависящие от невалидных Мер, также получают {{status = "invalid"}} с причиной, указывающей на невалидную зависимость;
* Меры, выражения которых не содержат ссылок на поля набора данных и используют только корректные константы, глобальные переменные или другие валидные Меры, не становятся {{invalid}} только из-за изменения состава полей;
* после восстановления поля или исправления выражения Мера должна снова получить {{status = "valid"}} при успешной повторной валидации;
* существующие Меры не удаляются автоматически при изменении SQL-запроса набора данных;
* набор данных может быть сохранён даже при наличии Мер со статусом {{invalid}}.

Если SQL-запрос набора данных очищен, не задан или не проходит проверку:
* backend не должен удалять существующие Меры и создавать новые Меры для такого состояния набора данных;
* полноценная ревалидация, требующая актуального состава полей, откладывается до появления корректного SQL-запроса и актуального состава полей;
* frontend должен получить данные, достаточные для отображения уже сохранённых Мер и блокировки кнопки «+ Добавить меру».

---
h4. 12. Права доступа.
Операции с Мерами наследуют существующую модель прав на наборы данных.

Чтение Мер доступно пользователям, которые имеют право читать соответствующий набор данных.

Создание, редактирование, удаление и валидация Мер доступны пользователям, которые имеют право изменять соответствующий набор данных. В текущей ролевой модели это роли, которым разрешено изменение наборов данных: {{dev}}, {{adm}}, {{edt}}, если актуальная конфигурация портала не задаёт более точное правило.

Новые отдельные права на управление Мерами в рамках этой Истории не вводятся.

Если у пользователя нет прав на изменение набора данных, backend должен возвращать контролируемый отказ на операции создания, редактирования и удаления Мер.

---
h4. 13. Обратная совместимость.
Для существующих произвольных наборов данных без Мер:
* чтение и сохранение набора данных должно работать без регрессий;
* отсутствие массива {{measures}} в старых метаданных должно трактоваться как пустой список Мер;
* backend не должен требовать миграции существующих наборов данных только для открытия или сохранения без изменения Мер.

Для простых и составных наборов данных:
* текущее поведение чтения и сохранения не меняется;
* Меры не создаются и не сохраняются;
* возможное наличие неизвестного блока {{measures}} в payload такого набора должно обрабатываться контролируемо, не повреждая существующие метаданные.

Существующие отчёты, визуализации, вычисляемые поля виджетов и запросы данных без Мер не должны изменить поведение в рамках этой Истории.

h3. Критерии приёмки (AC).
*AC.1* — Backend возвращает Меры в составе произвольного набора данных:
* *Дано:* у произвольного набора данных сохранены Меры в массиве {{measures}};
* *Когда:* frontend запрашивает набор данных через текущий контракт чтения {{datasets}};
* *Тогда:* backend возвращает массив {{measures}} со всеми полями Меры: {{id}}, {{name}}, {{alias}}, {{description}}, {{expression}}, {{aggregation_kind}}, {{data_type}}, {{hierarchy}}, {{level}}, {{status}}, {{status_message}};
* *И:* для старого набора данных без Мер, отсутствие Мер обрабатывается backend как пустой список без ошибки.

*AC.2* — Меры доступны только для произвольного набора данных:
* *Дано:* пользователь пытается создать, изменить или удалить Меру для простого или составного набора данных;
* *Когда:* backend получает запрос управления Мерой;
* *Тогда:* операция не выполняется;
* *И:* backend возвращает контролируемую ошибку;

*AC.3* — Создание Меры:
* *Дано:* пользователь с правами редактирования передал корректный payload создания Меры;
* *Когда:* backend успешно обрабатывает запрос;
* *Тогда:* backend создаёт Меру в массиве {{measures}};
* *И:* генерирует стабильный {{id}} в формате {{UUID}}, уникальное {{name}} по правилу {{Мера.}} + {{alias}} с приведением к системному имени и возвращает frontend-у сохранённую Меру с актуальными {{status}} и {{status_message}}.

*AC.4* — Уникальность и неизменяемость {{name}}:
* *Дано:* в наборе данных уже есть Мера, чей {{alias}} после преобразования приводит к {{name = "Мера.Дата_отчёта"}};
* *Когда:* пользователь создаёт другую Меру с {{alias}}, который приводит к такому же {{name}};
* *Тогда:* backend формирует уникальное {{name}}, например с детерминированным суффиксом;
* *И:* после создания {{name}} Меры не меняется при последующем редактировании {{alias}}.

*AC.5* — Валидация {{alias}}:
* *Дано:* пользователь передал пустой, неуникальный или содержащий недопустимые символы {{alias}};
* *Когда:* backend выполняет создание или редактирование Меры;
* *Тогда:* backend блокирует сохранение;
* *И:* возвращает ошибку, достаточную для отображения пользователю причины отказа.

*AC.6* — Валидация выражения и ссылок:
* *Дано:* пользователь сохраняет Меру с выражением, где поля указаны в двойных кавычках, а ссылки на Меры указаны в формате {{"Мера.<name>"}};
* *Когда:* backend выполняет валидацию;
* *Тогда:* backend проверяет синтаксис выражения, существование полей текущего набора данных, существование Мер, отсутствие самоссылок и циклических зависимостей, существование глобальных переменных и соответствие {{aggregation_kind}} фактическому выражению.

*AC.7* — Блокировка циклических зависимостей:
* *Дано:* выражение сохраняемой Меры создаёт самоссылку или цикл зависимостей между Мерами;
* *Когда:* backend выполняет сохранение;
* *Тогда:* сохранение блокируется;
* *И:* backend возвращает сообщение *«Выражение Меры содержит циклическую зависимость»* или эквивалентное по смыслу сообщение;
* *И:* метаданные Меры не изменяются.

*AC.8* — Сохранение Меры со статусом {{invalid}}:
* *Дано:* выражение Меры синтаксически разобрано, но ссылается на отсутствующее поле текущего набора данных;
* *Когда:* backend сохраняет Меру;
* *Тогда:* Мера сохраняется в метаданных, но получает {{status = "invalid"}} и {{status_message}} - содержит причину невалидности;
* *И:* набор данных может быть сохранён с такой Мерой.

*AC.9* — Проверка {{aggregation_kind}}:
* *Дано:* пользователь передал {{aggregation_kind}}, противоречащий фактической агрегированности выражения;
* *Когда:* backend выполняет создание или редактирование Меры;
* *Тогда:* сохранение блокируется и новая Мера не создаётся/не сохраняется;
* *И:* backend возвращает понятную ошибку валидации.

*AC.10* — Редактирование Меры:
* *Дано:* существующая Мера не используется в зависимых объектах;
* *Когда:* пользователь изменяет {{alias}}, {{description}}, {{expression}}, {{aggregation_kind}}, {{data_type}}, {{hierarchy}} или {{level}};
* *Тогда:* backend сохраняет допустимые изменения и возвращает актуальные {{status}} и {{status_message}} после повторной валидации.

*AC.11* — Блокировка изменения {{alias}} используемой Меры:
* *Дано:* Мера используется в выражении другой Меры, вычисляемом поле или визуализации;
* *Когда:* пользователь пытается изменить {{alias}} этой Меры;
* *Тогда:* backend блокирует изменение {{alias}};
* *И:* сохранённые метаданные Меры не меняются;
* *И:* backend возвращает сообщение о невозможности переименования и список зависимых объектов.

*AC.12* — Удаление Меры без зависимостей:
* *Дано:* Мера не используется в выражениях других Мер, вычисляемых полях и визуализациях;
* *Когда:* пользователь подтверждает удаление;
* *Тогда:* backend физически удаляет Меру из массива {{measures}};
* *И:* возвращает успешный ответ и актуальное состояние набора данных или списка Мер.

*AC.13* — Блокировка удаления используемой Меры:
* *Дано:* Мера используется в зависимых объектах;
* *Когда:* пользователь пытается удалить Меру;
* *Тогда:* backend блокирует удаление;
* *И:* каскадное удаление из зависимых объектов не выполняется;
* *И:* backend возвращает сообщение о невозможности удаления и список зависимых объектов.

*AC.14* — Ревалидация после изменения SQL набора данных:
* *Дано:* пользователь изменил SQL-запрос произвольного набора данных, и состав полей изменился;
* *Когда:* backend успешно сохранил и проверил SQL-запрос;
* *Тогда:* backend ревалидирует все Меры набора данных;
* *И:* Меры, ссылающиеся на отсутствующие поля, получают {{status = "invalid"}} и заполненный {{status_message}};
* *И:* Меры, не зависящие от состава полей, не становятся {{invalid}} только из-за изменения SQL-запроса.

*AC.15* — Восстановление статуса {{valid}}:
* *Дано:* Мера имела {{status = "invalid"}} из-за отсутствующего поля или невалидной зависимости;
* *Когда:* пользователь исправил выражение Меры или восстановил требуемое поле в SQL-запросе набора данных;
* *Тогда:* после повторной backend-валидации Мера получает {{status = "valid"}};
* *И:* {{status_message}} возвращается пустой строкой.

*AC.16* — Поведение при невалидном SQL набора данных:
* *Дано:* SQL-запрос произвольного набора данных очищен, не задан или не проходит проверку;
* *Когда:* backend возвращает состояние набора данных frontend-у;
* *Тогда:* ранее сохранённые Меры не удаляются;
* *И:* создание новых Мер недоступно через backend-контракт;
* *И:* полноценная ревалидация Мер откладывается до появления корректного SQL-запроса и актуального состава полей.

*AC.17* — Права доступа:
* *Дано:* пользователь не имеет прав на изменение набора данных;
* *Когда:* пользователь пытается создать, изменить или удалить Меру;
* *Тогда:* backend возвращает контролируемый отказ;
* *И:* метаданные набора данных не изменяются.

*AC.18* — Обратная совместимость:
* *Дано:* существующий набор данных, отчёт или визуализация не использует Меры;
* *Когда:* пользователь открывает, сохраняет или использует этот объект после внедрения backend-модели Мер;
* *Тогда:* текущее поведение сохраняется без регрессий;
* *И:* отсутствие массива {{measures}} в старых метаданных не приводит к ошибке.
