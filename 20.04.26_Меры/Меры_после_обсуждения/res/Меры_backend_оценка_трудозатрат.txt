h3. Контекст и проблематика.
В аналитическом портале вычисляемые выражения сейчас в основном существуют в контексте конкретной визуализации как вычисляемые поля. Если один и тот же показатель нужен в нескольких визуализациях, аналитик вынужден дублировать формулу в каждой визуализации либо вносить вычисление в основной SQL произвольного набора данных.

Такой подход создаёт ограничения:
* бизнес-логика показателя рассинхронизируется между визуализациями;
* вычисления, добавленные прямо в SQL набора данных, выполняются всегда, даже если конкретная визуализация этот показатель не использует;
* backend не имеет отдельной сущности для хранения, валидации, раскрытия и отслеживания зависимостей переиспользуемых показателей;
* при изменении SQL набора данных или формулы вычисляемого показателя сложно централизованно понять, какие визуализации и выражения затронуты.

Требуется оценить backend-доработки для внедрения *Мер* — именованных вычислимых выражений уровня набора данных, которые хранятся в метаданных набора и используются в SQL-запросах визуализаций только при фактической ссылке на Меру.

Полный текст постановки Меры в наборах данных: [https://jira.modusbi.ru/browse/MB-4364]

----
h3. Цель и бизнес-ценность.
+Этап 1+: Меры реализуются только для *произвольного* набора данных с пользовательским SQL-запросом.

Для *простых* и *составных* наборов данных механизм Мер в рамках текущей backend-оценки не рассматривается.

Цель backend-части:
* обеспечить хранение и возврат Мер в составе метаданных произвольного набора данных;
* обеспечить серверную валидацию выражений Мер, включая ссылки на поля набора данных, другие Меры, серверные переменные и переменные окружения;
* обеспечить раскрытие выражений Мер при построении SQL-запросов визуализаций;
* обеспечить корректное размещение раскрытых выражений в {{SELECT}}, {{WHERE}}, {{GROUP BY}}, {{HAVING}} в зависимости от полки и режима фильтрации;
* обеспечить ссылочную целостность при переименовании и удалении Мер;
* обеспечить обратную совместимость: существующие наборы данных, отчёты и визуализации без Мер должны работать без изменения поведения.

h4. Рекомендуемые блоки оценки трудозатрат.
# Хранение Мер в метаданных произвольного набора данных и API для чтения/сохранения.
# Парсер/анализатор выражений Мер: ссылки на поля, ссылки на Меры, вложенность, циклы, переменные, определение агрегированности.
# Валидация Мер при сохранении Меры и при изменении SQL набора данных.
# Интеграция Мер в payload визуализаций и обработку {{/v1/api/recordsets/<dataset_id>}}.
# Раскрытие Мер и генерация SQL по полкам визуализации.
# Учёт зависимостей и блокировка переименования/удаления используемых Мер.
# Импорт/экспорт наборов данных, отчётов и механизмов переноса между контурами.

h4. Что не входит в рамки текущей backend-постановки.
* Реализация frontend-интерфейса создания, редактирования и отображения Мер.
* Переработка редактора выражений ради отдельной визуальной подсветки Мер в формулах. Формат токена ссылки на Меру должен быть согласован, но сложная визуальная токенизация редактора оценивается отдельно.
* Реализация Мер для простых и составных наборов данных.
* Изменение ФВД.
* Полная замена текущего построителя SQL новым query builder, если команда разработки не примет это как отдельное техническое решение.
* Расширенная логика HAVING-фильтрации Сводной таблицы по {{target_dimensions}}, CND и {{depth}}, если она не реализована отдельной связанной задачей.
* Общая переработка механизма фильтров и условий для защиты от SQL-инъекций вне сценариев, напрямую добавляемых Мерами.

h3. Ключевые понятия и определения в рамках постановки.
* +Мера+ — именованное вычислимое SQL-выражение, определённое на уровне произвольного набора данных. Мера не добавляется в базовый SQL набора данных автоматически и не выполняется сама по себе. Она раскрывается backend-ом только в тех запросах визуализаций, где есть ссылка на эту Меру.
* +Имя Меры+ ({{name}}) — уникальное в рамках одного набора данных имя, используемое как внешний ключ ссылки на Меру в метаданных визуализации и выражениях других Мер. У Меры также должен быть стабильный {{id}} для внутренней идентификации, но внешняя совместимость строится по {{name}}.
* +Выражение Меры+ ({{expression}}) — SQL-выражение, в котором допускаются ссылки на поля текущего набора данных, другие Меры, серверные переменные и переменные окружения.
* +Ссылка на поле набора данных+ — ссылка по {{name}} поля набора данных. {{name}} уникален в рамках набора данных и не должен смешиваться с человекочитаемым алиасом поля.
* +Ссылка на Меру+ — однозначно распознаваемый токен в выражении. Для оценки использовать текущую целевую форму {{[measure_name]}}. Если из-за особенностей SQL-диалектов будет выбран другой delimiter/префикс, backend-требование остаётся тем же: ссылка на Меру должна быть отличима от поля, строкового литерала, переменной и синтаксиса конкретной СУБД.
* +Агрегированность Меры+ ({{aggregation_kind}}) — признак того, что выражение Меры содержит агрегирующие функции. Backend должен определять этот признак для поддерживаемого набора агрегирующих функций и использовать его при валидации размещения Меры по полкам. Если в интерфейсе сохраняется ручной флаг, backend не должен считать его единственным источником истины без проверки выражения.
* +Валидность Меры+ ({{status}}) — результат серверной проверки Меры: {{valid}} или {{invalid}}. Невалидная Мера сохраняется в метаданных, но не должна участвовать в успешном построении данных визуализации.
* +Ссылочная целостность+ — backend не разрешает переименование или удаление Меры, если на неё есть ссылки из визуализаций, других Мер или вычисляемых полей.
* +Базовый слой запроса+ — текущий механизм, где исходный SQL произвольного набора данных используется как внутренний источник внешнего запроса визуализации: через {{FROM (<dataset_sql>) AS __base}} или эквивалентный {{WITH __base AS (...)}}.

h3. Пользовательский интерфейс и управление Мерами в настройках Набора данных.
Раздел фиксирует backend-поведение, необходимое для поддержки интерфейса настройки Мер. Детали отображения, модальных окон, цветов и drag-and-drop относятся к frontend-части и в этой постановке не оцениваются.

h4. Доступность Мер для произвольного набора данных.
Backend должен возвращать и принимать Меры только для произвольных наборов данных с пользовательским SQL-запросом.

Для простых и составных наборов данных:
* backend не должен позволять создавать или сохранять Меры;
* при попытке сохранить Меры должен возвращаться контролируемый отказ с сообщением, что Меры поддерживаются только для произвольных наборов данных;
* существующее поведение таких наборов данных не меняется.

h4. Backend-объекты и команды.
Базовый backend-объект: {{datasets}}.

Для оценки требуется предусмотреть поддержку следующих операций. Точные имена команд можно согласовать с командой разработки, но функционально должны быть покрыты:
* {{datasets.get}} / {{datasets.list}} — возвращают Меры в составе метаданных набора данных;
* {{datasets.update}} или отдельная команда сохранения Меры — создаёт, изменяет и удаляет Меры в составе набора данных;
* {{datasets.measure.validate}} или эквивалентная операция — валидирует одну Меру или все Меры набора данных;
* {{datasets.measure.dependencies}} или эквивалентная операция — возвращает список объектов, использующих Меру, для блокировки переименования/удаления и показа конфликтов;
* текущий endpoint {{/v1/api/recordsets/<dataset_id>}} — принимает ссылки на Меры в payload визуализации и строит данные с учётом Мер.

Перед изменением Мер backend должен читать актуальное состояние набора данных через {{get/list}} или внутренний эквивалент, чтобы корректно определить:
* была ли Мера создана, изменена, переименована или удалена;
* какие зависимости есть у прежнего имени Меры;
* какие Меры требуют повторной валидации.

h4. Права доступа.
Операции чтения и изменения Мер должны наследовать права доступа к наборам данных.

* Чтение Мер доступно пользователям, которые могут читать соответствующий набор данных.
* Создание, изменение, удаление и валидация Мер доступны ролям, которым разрешено изменять набор данных: {{dev}}, {{adm}}, {{edt}}.
* Запрос данных через {{/v1/api/recordsets/<dataset_id>}} использует существующую модель доступа к отчёту, визуализации и набору данных.

h4. Валидация при сохранении Меры.
При создании или редактировании Меры backend должен выполнить:
* проверку обязательных полей: {{name}}, {{expression}}, {{data_type}};
* проверку уникальности {{name}} среди Мер одного набора данных;
* проверку синтаксиса выражения на уровне доступного backend-анализатора;
* проверку существования полей набора данных, на которые есть ссылки;
* проверку существования Мер, на которые есть ссылки;
* проверку отсутствия самоссылок и циклических зависимостей между Мерами любой глубины;
* проверку корректной обработки серверных переменных и переменных окружения;
* определение или проверку {{aggregation_kind}};
* пробную SQL-валидацию выражения в составе внешнего запроса, насколько это возможно без фактического получения полного набора данных.

Если Мера использует только константы, серверные переменные или переменные окружения и не ссылается на поля набора данных, отсутствие ссылок на поля не является ошибкой.

Если выражение содержит ошибку, backend должен сохранять или возвращать статус {{invalid}} с причиной ошибки. Причина должна быть пригодна для отображения в интерфейсе, например:
* поле набора данных не найдено;
* Мера не найдена;
* обнаружена циклическая зависимость;
* выражение не прошло SQL-валидацию;
* {{aggregation_kind}} не соответствует допустимому использованию выражения.

h4. Переименование и удаление Меры.
Если изменяется {{name}} существующей Меры, backend должен проверить зависимости по старому имени.

Если Мера используется хотя бы в одном объекте, переименование блокируется. Backend возвращает список зависимостей:
* отчёт / визуализация / компонент, где Мера размещена на полке или используется в фильтре;
* другая Мера, в выражении которой есть ссылка на переименовываемую Меру;
* вычисляемое поле, в выражении которого есть ссылка на переименовываемую Меру.

Если изменяются другие свойства Меры без изменения {{name}}, сохранение не должно блокироваться только из-за наличия зависимых визуализаций. При этом выражение должно пройти стандартную валидацию, а зависимые Меры должны быть ревалидированы.

Удаление Меры блокируется при наличии зависимостей. Физическое удаление допустимо только если зависимостей нет.

h4. Жизненный цикл после изменения SQL набора данных.
При успешной проверке и сохранении SQL-запроса произвольного набора данных backend должен повторно валидировать все Меры этого набора.

Если изменился состав полей:
* Меры, ссылающиеся на отсутствующие поля, получают {{status = invalid}};
* Меры, зависящие от невалидных Мер, также получают {{status = invalid}};
* Меры, не зависящие от изменённых или удалённых полей, сохраняют валидность при корректном выражении;
* набор данных может быть сохранён даже при наличии невалидных Мер.

Если SQL-запрос набора данных отсутствует или не проходит проверку, ранее сохранённые Меры не удаляются. Их повторная SQL-валидация откладывается до появления корректного SQL-запроса и актуального состава полей.

h3. Структура метаданных Меры.
Меры должны храниться в метаданных произвольного набора данных. Минимальная внешняя структура:
{code:json}
{
  "measures": [
    {
      "id": "847b1ec3-bbf8-4365-85fb-c4fca2a06e2e",
      "name": "Валовая прибыль",
      "description": "Разница между выручкой и себестоимостью",
      "expression": "SUM(\"revenue\") - SUM(\"cost\")",
      "aggregation_kind": 1,
      "data_type": "number",
      "hierarchy": "Финансовые показатели",
      "level": 10,
      "status": "valid"
    }
  ]
}
{code}

|| Поле || Тип || Backend-требование ||
| {{id}} | string | Стабильный внутренний идентификатор Меры. Не изменяется при переименовании. |
| {{name}} | string | Уникальное имя Меры в рамках набора данных. Используется как внешний ключ ссылки. |
| {{description}} | string | Необязательное описание. Backend хранит и возвращает без изменения. |
| {{expression}} | string | SQL-выражение Меры. Backend парсит, валидирует и раскрывает при построении запроса. |
| {{aggregation_kind}} | int (0/1) | Признак агрегированности выражения. Используется для валидации полок и SQL. |
| {{data_type}} | string | Логический тип результата Меры. Backend хранит и возвращает для UI и обработки результата. |
| {{hierarchy}} | string | Необязательная группа отображения. Backend хранит и возвращает без бизнес-логики группировки. |
| {{level}} | int | Порядок внутри группы. Backend хранит и возвращает. |
| {{status}} | enum | {{valid}} или {{invalid}}. Вычисляется backend-ом по результатам валидации. |
| {{status_message}} | string | Технически понятная причина невалидности или пустая строка при {{valid}}. |

Backend может хранить дополнительные служебные данные для ускорения проверок, например зависимости {{depends_on_fields}} и {{depends_on_measures}}. Если такие данные добавляются, они должны пересчитываться backend-ом и не должны требовать ручного заполнения со стороны frontend.

h3. Метаданные визуализации и ссылки на Меры.
Во всех метаданных визуализаций Мера должна передаваться как ссылка, а не как раскрытое выражение. Backend должен сам получить выражение Меры из метаданных набора данных по {{dataset_id}} и {{name}} / {{measure_name}}.

Для совместимости с текущей структурой полей визуализаций требуется согласовать единый формат объекта Меры. Рекомендуемый минималистичный формат:
{code:json}
{
  "type": "measure",
  "name": "Валовая прибыль",
  "measure_name": "Валовая прибыль",
  "datasetId": 3,
  "alias": "[values][0]",
  "filterSqlType": "having",
  "lvl": 0,
  "valueType": "value"
}
{code}

Требования к обработке:
* {{type = "measure"}} является обязательным признаком, отличающим Меру от обычного поля и вычисляемого поля;
* {{name}} / {{measure_name}} должны ссылаться на существующую Меру текущего набора данных;
* frontend не должен передавать в payload раскрытое выражение Меры как единственный источник истины;
* если Мера не найдена, имеет {{status = invalid}} или недоступна для текущего набора данных, backend должен отклонить запрос данных с контролируемой ошибкой;
* backend должен учитывать Меры, размещённые в {{axes}}, {{axesDefault}}, фильтрах и текущем payload {{recordsets}}, где сейчас используются поля и вычисляемые поля.

Для текущего endpoint {{/v1/api/recordsets/<dataset_id>}} необходимо поддержать Меры в тех же логических секциях, где сейчас передаются поля:
* {{select}};
* {{group}};
* {{order}}, если сортировка по Мере поддерживается выбранной визуализацией;
* {{where}};
* {{having}};
* объектные структуры визуализаций на базе {{axes}} / {{fields}}.

Точный контракт payload должен быть согласован с frontend до реализации. Для оценки backend необходимо учитывать, что backend должен получать именно идентификатор/имя Меры и сам выполнять раскрытие выражения.

----
h3. Отображение Мер в конструкторе визуализаций.
Backend-часть для отображения Мер сводится к предоставлению данных и статусов, необходимых frontend-у:
* при чтении набора данных backend возвращает список Мер, их типы, агрегированность, иерархию, порядок, статус и причину невалидности;
* невалидные Меры не удаляются из метаданных и продолжают возвращаться в списке;
* если визуализация содержит ссылку на невалидную или отсутствующую Меру, backend должен возвращать контролируемую ошибку вместо некорректного SQL или необработанного исключения;
* если в наборе данных есть невалидные Меры, но конкретная визуализация их не использует, запрос данных визуализации должен выполняться штатно.

----
h3. Валидация допустимости Мер по полкам.
Backend выполняет финальную валидацию допустимости Мер перед построением SQL. Frontend-валидация может дублировать эти правила, но не заменяет backend-проверку.

|| Полка / секция payload || Допустимость || Backend-поведение при нарушении ||
| {{select}} / «Значения» | Агрегированные и неагрегированные Меры | Запрос строится по SQL-семантике. Если выражение не может быть корректно встроено, вернуть контролируемую ошибку. |
| {{where}} / фильтр {{WHERE}} | Только неагрегированные Меры | Отклонить запрос, если Мера агрегированная или фактически содержит агрегатную функцию. |
| {{having}} / фильтр {{HAVING}} | Только агрегированные Меры | Отклонить запрос, если Мера неагрегированная. |
| {{group}} / «Строки», «Столбцы», «Детализация» | Только неагрегированные Меры | Отклонить запрос, если Мера агрегированная. |
| «Дополнительные» | По текущей логике не участвует в SQL | Не раскрывать Меру в SQL, если полка не участвует в запросе данных. |

Если в payload передан ручной признак, противоречащий фактическому выражению, backend должен ориентироваться на результат серверной проверки и SQL-валидации.

----
h3. Логика генерации SQL.

h4. Базовый слой запроса и алгоритм генерации.
При построении данных визуализации backend использует исходный SQL произвольного набора данных как внутренний источник и строит внешний запрос поверх него.

Принципиальная схема:
{code:sql}
SELECT
  <поля и неагрегированные Меры группировок>,
  <выражения Мер с полки Значения> AS <alias>
FROM (
  <исходный SQL произвольного набора данных>
) AS __base
WHERE
  <обычные WHERE-фильтры>
  [AND <раскрытые выражения неагрегированных Мер WHERE>]
GROUP BY
  <поля группировок>
  [, <раскрытые выражения неагрегированных Мер группировок>]
HAVING
  <раскрытые выражения агрегированных Мер HAVING>
{code}

Допустима эквивалентная реализация через {{WITH __base AS (...)}}. Продуктовое требование — не конкретная форма SQL, а корректное раскрытие и размещение выражений Мер в итоговом запросе.

h4. Раскрытие выражений Мер.
Перед генерацией SQL backend должен:
# найти все ссылки на Меры в payload визуализации;
# загрузить определения Мер из метаданных набора данных;
# рекурсивно раскрыть ссылки на другие Меры;
# проверить отсутствие циклов;
# заменить ссылки на поля набора данных на корректные SQL-идентификаторы текущего источника;
# сохранить корректную обработку строковых литералов, комментариев, серверных переменных и переменных окружения;
# сформировать итоговое выражение для нужной SQL-клаузы.

Раскрытие Меры должно выполняться при каждом запросе данных, чтобы изменение формулы Меры на уровне набора данных применялось во всех визуализациях без копирования выражения в метаданные визуализаций.

h4. Поведение Меры в зависимости от полки.
* *Полка «Значения» / {{select}}*: выражение Меры добавляется в {{SELECT}} с alias из payload. Для неагрегированной Меры backend должен строить SQL по текущим правилам группировки; если СУБД отклоняет запрос, вернуть понятную ошибку.
* *Фильтр {{WHERE}}*: выражение неагрегированной Меры добавляется в {{WHERE}} и применяется до группировки.
* *Фильтр {{HAVING}}*: выражение агрегированной Меры добавляется в {{HAVING}} и применяется после группировки.
* *«Строки», «Столбцы», «Детализация» / {{group}}*: неагрегированная Мера раскрывается как вычисляемое измерение и попадает в {{SELECT}} и {{GROUP BY}}.
* *«Дополнительные»*: если текущая визуализация не использует эту полку в запросе данных, Мера не должна добавляться в SQL.

h4. Несколько Мер и вложенные Меры.
* Несколько Мер в {{select}} формируют отдельные выражения с отдельными alias.
* Несколько WHERE-фильтров по Мерам объединяются с остальными WHERE-условиями по текущим правилам построителя.
* Несколько HAVING-фильтров по Мерам объединяются с остальными HAVING-условиями по текущим правилам построителя.
* Мера может ссылаться на другую Меру на любую глубину вложенности, если нет цикла.
* Если вложенная Мера стала {{invalid}}, все зависящие от неё Меры должны получить {{invalid}} при ревалидации.

h4. SQL-валидация и производительность.
Backend должен оценить способ SQL-валидации Мер без чрезмерного увеличения времени проверки набора данных.

Минимально ожидаемое поведение:
* при сохранении одной Меры проверяется эта Мера и зависящие от неё Меры;
* при изменении SQL набора данных проверяется исходный SQL и затем Меры, зависящие от полей набора данных;
* если возможно, сначала выполняется укрупнённая проверка, а детальная проверка по Мерам запускается только при ошибке или для изменённых Мер;
* ошибка должна быть связана с конкретной Мерой, если backend может это определить.

----
h3. Устойчивость к изменениям метаданных.
Backend должен обеспечить отдельный учёт зависимостей Мер. Текущий механизм учёта использования полей набора данных нельзя считать достаточным без проверки, потому что Мера является справочником выражений, а не обычным полем.

Для оценки требуется предусмотреть:
* хранение зависимостей {{measure -> field}};
* хранение зависимостей {{measure -> measure}};
* хранение зависимостей {{visualization/report -> measure}};
* обновление зависимостей при сохранении Меры;
* обновление зависимостей при сохранении отчёта/визуализации, где Меры используются в {{axes}}, {{select}}, {{where}}, {{having}} или аналогичных структурах;
* блокировку переименования и удаления используемых Мер;
* ревалидацию зависимых Мер после изменения формулы, имени, статуса или SQL набора данных.

Если текущая архитектура хранит связи через анализ JSON отчёта на backend-е, необходимо оценить один из вариантов:
* расширить существующий механизм анализа JSON для Мер;
* расширить существующую таблицу связей полей;
* создать отдельную таблицу/модель связей для Мер.

Технический вариант выбирает команда разработки, но в оценке должен быть явно учтён объём работ по связям.

----
h3. Обратная совместимость.
* Наборы данных без массива {{measures}} должны читаться и сохраняться без ошибок.
* Существующие визуализации без {{type = "measure"}} должны строить запросы по текущей логике.
* Вычисляемые поля виджетов продолжают работать по текущему контракту.
* Добавление Мер не должно менять SQL, если Меры не используются в payload визуализации.
* Если Мера есть в наборе данных, но не используется конкретной визуализацией, она не должна добавляться в SQL и не должна нагружать запрос.
* Старые отчёты не требуют миграции, если в них нет ссылок на Меры.

----
h3. Интеграция с импортом, экспортом и переносом между контурами.
Меры должны быть учтены в механизмах импорта/экспорта и переноса, если в текущем продукте экспортируются наборы данных, отчёты или вычисляемые поля.

Для оценки требуется проверить и учесть:
* экспорт и импорт произвольного набора данных вместе с {{measures}};
* экспорт и импорт отчётов/визуализаций, содержащих ссылки на Меры;
* перенос между контурами, где набор данных и отчёт переносятся вместе;
* ситуацию, когда отчёт импортируется без требуемой Меры или без набора данных;
* восстановление зависимостей после импорта.

Если команда решит выносить импорт/экспорт в отдельную историю, в текущей оценке необходимо минимум зафиксировать зависимость и границу интеграции.

----
{panel:title=Интеграция с постановкой по HAVING-фильтрации|borderStyle=dashed|borderColor=#0052cc|bgColor=#f0f4ff}
Базовая поддержка Меры в {{HAVING}} должна быть реализована для сценариев, где текущий построитель уже поддерживает HAVING-условия.

Уровневая HAVING-фильтрация Сводной таблицы через {{apply_mode}}, {{target_dimensions}}, CND и {{depth}} относится к связанной задаче [MB-4304|https://jira.modusbi.ru/browse/MB-4304] и должна оцениваться отдельно, если она ещё не реализована.

h3. Открытые вопросы для команды разработки.
* Какой финальный токен ссылки на Меру в {{expression}} использовать, чтобы он не конфликтовал с SQL-диалектами, строковыми литералами и переменными: {{[measure_name]}} или другой delimiter/префикс?
* Будет ли backend хранить зависимости Мер в существующей таблице связей или в отдельной модели?
* Нужно ли в первом релизе поддерживать импорт/экспорт и перенос отчётов с Мерами или это отдельная обязательная история?
* Какой список агрегирующих функций считается поддерживаемым для автоматического определения {{aggregation_kind}} по каждому SQL-диалекту?

h3. Критерии приёмки (AC):
*AC.1* — Чтение и сохранение Мер в произвольном наборе данных.
* *Дано*: существует произвольный набор данных с корректным SQL.
* *Когда*: backend получает запрос на чтение набора данных.
* *Тогда*: в ответе возвращается массив {{measures}} со всеми сохранёнными Мерами и их статусами.
* *И*: при сохранении набора данных backend сохраняет созданные, изменённые и удалённые Меры согласно правилам валидации.

*AC.2* — Ограничение по типу набора данных.
* *Дано*: пользователь пытается сохранить Меру в простом или составном наборе данных.
* *Тогда*: backend отклоняет операцию контролируемой ошибкой.
* *И*: существующее поведение простых и составных наборов данных не меняется.

*AC.3* — Валидация выражения Меры.
* *Дано*: пользователь сохраняет Меру с выражением, где есть ссылки на поля, другие Меры и переменные.
* *Тогда*: backend проверяет существование ссылок, синтаксис, циклы, агрегированность и возможность SQL-исполнения.
* *И*: при ошибке возвращает {{status = invalid}} и причину.

*AC.4* — Циклические зависимости блокируются.
* *Дано*: Мера A ссылается на Меру B, а Мера B прямо или косвенно ссылается на Меру A.
* *Когда*: пользователь сохраняет одну из Мер.
* *Тогда*: backend блокирует сохранение валидного состояния и возвращает ошибку циклической зависимости.

*AC.5* — Ревалидация после изменения SQL набора данных.
* *Дано*: Мера ссылается на поле набора данных.
* *Когда*: SQL набора данных изменён так, что поле исчезло.
* *Тогда*: backend переводит Меру в {{invalid}}.
* *И*: зависящие от неё Меры также становятся {{invalid}}.
* *И*: набор данных может быть сохранён с невалидными Мерами.

*AC.6* — Меры не нагружают запрос без использования.
* *Дано*: в наборе данных сохранены Меры.
* *Когда*: визуализация не содержит ссылок на эти Меры.
* *Тогда*: backend строит SQL без раскрытия выражений Мер.
* *И*: результат соответствует текущему поведению визуализации без Мер.

*AC.7* — Раскрытие Меры в {{SELECT}}.
* *Дано*: payload {{recordsets}} содержит Меру на полке «Значения».
* *Тогда*: backend загружает выражение Меры из метаданных набора данных, раскрывает вложенные Меры и добавляет выражение в {{SELECT}} с корректным alias.

*AC.8* — Раскрытие Меры в {{WHERE}}.
* *Дано*: payload содержит неагрегированную Меру в фильтре {{WHERE}}.
* *Тогда*: backend раскрывает выражение Меры и добавляет условие в {{WHERE}}.
* *И*: если Мера агрегированная, запрос отклоняется контролируемой ошибкой.

*AC.9* — Раскрытие Меры в {{HAVING}}.
* *Дано*: payload содержит агрегированную Меру в фильтре {{HAVING}}.
* *Тогда*: backend раскрывает выражение Меры и добавляет условие в {{HAVING}}.
* *И*: если Мера неагрегированная, запрос отклоняется контролируемой ошибкой.

*AC.10* — Мера как вычисляемое измерение.
* *Дано*: payload содержит неагрегированную Меру в группировке.
* *Тогда*: backend добавляет раскрытое выражение в {{SELECT}} и {{GROUP BY}}.
* *И*: агрегированная Мера в группировке отклоняется контролируемой ошибкой.

*AC.11* — Блокировка переименования используемой Меры.
* *Дано*: Мера используется в визуализации или другой Мере.
* *Когда*: пользователь пытается изменить {{name}}.
* *Тогда*: backend блокирует переименование и возвращает список зависимых объектов.

*AC.12* — Блокировка удаления используемой Меры.
* *Дано*: Мера используется в визуализации, другой Мере или вычисляемом поле.
* *Когда*: пользователь пытается удалить Меру.
* *Тогда*: backend блокирует удаление и возвращает список зависимых объектов.

*AC.13* — Ошибка при использовании невалидной Меры.
* *Дано*: визуализация содержит ссылку на Меру со статусом {{invalid}}.
* *Когда*: запрашиваются данные визуализации.
* *Тогда*: backend не строит некорректный SQL и возвращает контролируемую ошибку с указанием проблемной Меры.

*AC.14* — Импорт/экспорт учитывает Меры.
* *Дано*: экспортируется набор данных или отчёт, где используются Меры.
* *Тогда*: экспорт содержит определения Мер и ссылки на них.
* *И*: после импорта backend восстанавливает Меры и зависимости либо возвращает понятную ошибку о недостающих объектах.

*AC.15* — Обратная совместимость.
* *Дано*: существующий отчёт не содержит Мер.
* *Когда*: backend строит данные визуализации.
* *Тогда*: SQL и результат соответствуют текущему поведению до внедрения Мер.
