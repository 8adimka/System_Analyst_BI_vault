Хорошо. Теперь у нас есть общая постановка для эпика по мерам - "
h3. Контекст и проблематика.
Наша платформа предоставляет аналитикам возможность строить визуализации на основе _наборов данных трёх типов_: *произвольного* (обычный «пользовательский» SQL-запрос), *простого* или *составного*.
На сегодняшний день все вычисляемые выражения существуют исключительно в контексте конкретной визуализации — как «вычисляемые поля» виджета. Это порождает ряд системных ограничений:
* Одна и та же бизнес-логика дублируется в каждой визуализации, где она нужна, что ведёт к рассинхронизации определений при изменениях.
* Не существует возможности вынести агрегирующее вычисление на уровень набора данных — то есть определить его один раз и использовать в любых визуализациях, основанных на этом наборе данных.
* Аналитик лишён семантически выразительного инструмента: он вынужден либо дублировать формулы, либо включать агрегации непосредственно в основной SQL набора данных, теряя гибкость.

В индустриальных BI-системах данная потребность закрывается концепцией «Мер» — именованных вычислимых выражений, определённых на уровне источника данных и применяемых при построении визуализации.

----
h3. Цель и бизнес-ценность.
+Этап 1+: Меры реализуются только для *произвольного* (обычного) набора данных — типа набора с произвольным SQL-запросом. Для *простых* и *составных* наборов данных механизм добавления Мер в UI не предоставляется.

Реализация Мер в рамках *произвольного* набора данных позволит:
* Аналитикам определять именованные вычислимые показатели один раз на уровне набора данных и переиспользовать их в любых визуализациях.
* Бэкенду корректно встраивать выражение Меры в нужную SQL-клаузу внешнего запроса в зависимости от полки размещения, используя текущий механизм построителя запросов (базовый слой запроса).
* Поддержать полный спектр сценариев использования: от агрегации значений и фильтрации по агрегатам до вычисляемых измерений и тултип-метрик.
* Устранить дублирование бизнес-логики и обеспечить единую точку изменения вычислений.
* Заложить основу для последующего расширения Мер на простые и составные наборы данных (+Этап 2+ — за пределами настоящей постановки).

----
h3. Ключевые понятия и определения.
* +Мера+ — именованное вычислимое выражение, определённое на уровне +произвольного+ набора данных. Мера представляет собой SQL-выражение, написанное аналитиком с использованием полей данного набора данных. Сама по себе Мера не вычисляется в момент создания; она вычисляется динамически в контексте конкретной визуализации — в зависимости от полки, на которую она размещена, её выражение инжектируется в строго определённую SQL-клаузу внешнего запроса.
* +Признак агрегированности+ ({{aggregation_kind}}) — явный атрибут Меры, который задаётся пользователем при создании или редактировании. Принимает значения {{1}} (aggregated) или {{0}} (non_aggregated). Используется для UX-валидации при размещении Меры на полку, визуального обозначения и предварительной проверки допустимости сценария. Автоматическое определение агрегированности по тексту выражения *не входит в объём Этапа 1*.
* +Агрегированная мера+ ({{aggregation_kind = 1}}) — Мера, выражение которой содержит хотя бы одну агрегатную функцию: {{SUM()}}, {{AVG()}}, {{MAX()}}, {{COUNT(DISTINCT...)}}) и их комбинации. Допустима только в {{SELECT}} и {{HAVING}}, но не в {{WHERE}} и {{GROUP BY}}.
* +Неагрегированная мера+ ({{aggregation_kind = 0}}) — Мера, выражение которой не содержит агрегатных функций; работает на уровне отдельной строки. Допустима в {{SELECT}}, {{WHERE}}, {{GROUP BY}}.
* +Базовый слой запроса+ — текущий механизм построителя, в котором оригинальный SQL набора данных используется как источник внешнего запроса визуализации. Реализация допускает два эквивалентных варианта: {{FROM (<dataset_sql>) AS __base}} (derived table) или {{WITH __base AS (<dataset_sql>) ... SELECT ... FROM __base}} (CTE). Выбор между ними является технической деталью реализации и не фиксируется как продуктовое требование.
* +Полка+ — именованная область в конструкторе визуализации, на которую аналитик размещает Поля или Меры методом drag-and-drop. Конкретный набор полок варьируется в зависимости от типа визуализации.

----
h3. Пользовательский интерфейс и управление Мерами в настройках Набора данных.
Во вкладке «Наборы данных» выбираем Источник данных и «произвольный» Набор данных (Настройки → Источники → выбранный «произвольный» Набор данных) под секцией «Описание полей набора данных» добавляется новая секция «Меры».
Для простых и составных наборов данных секция «Меры» и кнопка «+ Добавить меру» не отображаются (функциональность не реализуется в рамках +Этапа 1+).

h4. Доступность кнопки «+ Добавить меру».
Кнопка «+ Добавить меру» активна *только* при одновременном выполнении всех условий:
# для набора задан SQL-запрос;
# запрос успешно прошёл проверку;
# система получила актуальный состав полей набора данных.

Если хотя бы одно условие не выполнено — кнопка находится в {{disabled}}-состоянии. При наведении на неё отображается пояснение: _«Сначала задайте и проверьте SQL-запрос набора данных»_.

h4. Интерфейс создания и редактирования Меры.
При нажатии «+ Добавить меру» открывается *модальное окно увеличенного размера*.

Внутри модального окна одновременно доступны:
* поля формы Меры (левая или верхняя часть);
* редактор выражения со списком полей текущего набора данных (правая или нижняя часть) — поля доступны для вставки в выражение непосредственно из модалки, так как основная страница с полями перекрыта окном.

При нажатии «Редактировать» на существующей Мере открывается то же окно с предзаполненными значениями.

Форма содержит следующие поля:
* *Название* (обязательное, строка) — отображаемое имя Меры; должно быть уникальным в рамках одного набора данных.
* *Описание* (необязательное, строка) — пояснительный текст; отображается в tooltip при наведении на Меру.
* *Тип данных* (обязательное) — логический тип результата Меры: {{number}}, {{string}}, {{date}}, {{datetime}}, {{boolean}} и т.д. Система может предложить значение по умолчанию, но пользователь обязан иметь возможность изменить тип вручную. Если для выбранного типа доступны дополнительные настройки (например, для дат), они отображаются условно.
* *Признак агрегированности* (обязательное, переключатель/флаг) — задаётся пользователем явно: {{агрегированная}} / {{неагрегированная}}. Используется для UX-валидации при размещении на полки.
* *Иерархия* (необязательное, строка) — имя группы/иерархии, в которой Мера отображается в панели полей.
* *Уровень* (необязательное, целое число) — порядок отображения Меры внутри иерархии.
* *Выражение* (обязательное) — редактор выражений, эквивалентный редактору вычисляемых полей виджета. Требования к редактору:
** Синтаксис и функции — идентичны вычисляемым полям.
** В редакторе доступен список полей текущего набора данных. Поля подставляются в выражение, обёрнутые в двойные кавычки: {{"field_name"}}.
** *(Опционально)* Автодополнение, подсветка синтаксических ошибок и другие продвинутые возможности нового редактора кода.
* *Кнопки формы:* «Сохранить» / «Отмена».

h4. Валидация при сохранении Меры.  
При сохранении выполняются следующие проверки:
* заполнены обязательные поля;
* название Меры уникально в рамках одного набора данных;
* выражение синтаксически валидно в рамках редактора/парсера;
* выражение ссылается только на доступные поля текущего набора данных;
* для набора известен актуальный состав полей.

При успешном сохранении:
* новая Мера получает стабильный {{id}};
* Мера сохраняется в metadata набора данных;
* для Меры устанавливается статус {{valid}}.

h4. Список Мер набора данных.
Сохранённые Меры отображаются в *табличном списке* под секцией «Описание полей набора данных».

Набор отображаемых колонок:

|| *Название* || *Тип данных* || *Агрегация* || *Иерархия* || *Уровень* || *Выражение* (кратко) || *Действия* ||
| <название меры> | <тип> | AGR / — | <иерархия> | <порядок> | <первые N символов> | [иконка редактировать] [иконка удалить] |

* Колонка *«Агрегация»* — для Мер с {{aggregation_kind = 1}} отображается ярлык *AGR*; для {{aggregation_kind = 0}} — прочерк ("—").
* Описание Меры выводится в tooltip при наведении на её строку.
* Для Мер со статусом {{invalid}} строка подсвечивается как ошибочная (красный ореол, иконка ⚠). При наведении отображается причина невалидности.
* Если заполнена «Иерархия», Мера относится к соответствующей display-группе.
* Внутри одной группы Меры сортируются по {{level}} по возрастанию, затем по названию.
* Меры без заполненной «Иерархии» отображаются в корневом уровне секции «Меры».

h4. Удаление Меры.  
Если Мера не используется ни в одной визуализации, удаление выполняется без дополнительной логики влияния на другие объекты.

Если Мера используется хотя бы в одной визуализации, перед удалением отображается подтверждение:  
_«Мера "[Название]" используется в [N] визуализациях. Удаление приведёт к её удалению со всех полок и из всех зависимых настроек. Продолжить?»_

h4. Жизненный цикл Меры после изменения SQL набора данных.
При каждом сохранении SQL-запроса набора данных система заново определяет актуальный состав полей и *автоматически валидирует все Меры* набора.

Если Мера ссылается на отсутствующее поле или её выражение не может быть интерпретировано в контексте текущего набора данных:
* Мера *не удаляется* автоматически;
* Мера получает статус {{invalid}};
* Мера подсвечивается в списке как ошибочная (красный ореол, иконка ⚠);
* При наведении отображается текст ошибки или причина невалидности;
* Мера *недоступна для добавления на полки* до исправления.

После исправления выражения или восстановления требуемых полей Мера автоматически получает статус {{valid}}.

Если пользователь очистил SQL набора данных либо SQL перестал проходить проверку:
* кнопка «+ Добавить меру» становится {{disabled}};
* существующие Меры не удаляются;
* их повторная полноценная валидация откладывается до появления корректного SQL и актуального состава полей;
* в UI допускается показывать существующие Меры как недоступные для нового использования до восстановления валидного контекста набора.

----
h3. Структура метаданных Меры.

Мера сохраняется в JSON-метаданных набора данных. Стабильный идентификатор ({{id}}) используется во всех внешних ссылках и не изменяется при переименовании.

{code:json}
{
  "measures": [
    {
      "id": "measure_001",
      "name": "Валовая прибыль",
      "description": "Разница между выручкой и себестоимостью",
      "expression": "SUM(\"revenue\") - SUM(\"cost\")",
      "aggregation_kind": 1,
      "data_type": "number",
      "hierarchy": "Финансовые показатели",
      "level": 10,
      "status": "valid"
    }
  ]
}
{code}

|| Поле || Тип || Описание ||
| {{id}} | string | Стабильный UUID идентификатор; не изменяется при переименовании |
| {{name}} | string | Отображаемое название |
| {{description}} | string | Необязательное описание |
| {{expression}} | string | SQL-выражение; поля набора данных оборачиваются в двойные кавычки |
| {{aggregation_kind}} | int (0/1) | Признак агрегированности; *задаётся пользователем явно* (1 — aggregated, 0 — non_aggregated) |
| {{data_type}} | string | Логический тип результата: {{number}}, {{string}}, {{date}}, {{datetime}}, {{boolean}} и т.д. |
| {{hierarchy}} | string | Необязательная группа/иерархия отображения в панели полей |
| {{level}} | int | Порядок Меры внутри иерархии |
| {{status}} | enum | {{valid}} или {{invalid}}; *вычисляется системой* по результатам валидации |

В метаданных визуализации каждое размещение Меры на полку фиксируется со ссылкой на {{measure.id}} и дополнительными параметрами ({{filter_mode}}, {{condition}}, а для HAVING-фильтра Сводной таблицы — {{apply_mode}} / {{target_dimensions}}).

----
h3. Метаданные визуализации и ссылки на Меры.  
Во всех метаданных визуализации связь с Мерой хранится по стабильному {{measure_id}}.

Каждое использование Меры в визуализации хранит:
* тип сущности {{measure}};
* ссылку на {{measure_id}};
* дополнительные параметры в зависимости от конкретной полки и сценария.

Пример для фильтра по Мере:
{code:json}
{
  "filters": [
    {
      "id": "filter_002",
      "type": "measure",
      "measure_id": "measure_001",
      "filter_mode": "HAVING",
      "condition": "> 0"
    }
  ]
}
{code}

|| Поле || Тип || Описание ||
| {{type}} | string | {{"measure"}} |
| {{measure_id}} | string | Ссылка на стабильный ID Меры |
| {{filter_mode}} | string | {{WHERE}} или {{HAVING}} |
| {{condition}} | string | Условие фильтрации |

h3. Отображение Мер в конструкторе визуализаций.

h4. Боковая панель полей (слева).
При выборе набора данных в конструкторе боковая панель разделена на секции:
* *«Поля»* — обычные поля и вычисляемые поля виджета (текущий вид без изменений).
* *«Меры»* — Меры набора данных (новая секция ниже).

Меры визуально отличаются от обычных полей:
* Цвет иконки (пилюли) — *тёмно-оранжевый* (обычные поля — тёмно-синий).
* Для Мер с {{aggregation_kind = 1}} рядом с названием отображается ярлык *AGR*.
* Tooltip при наведении отображает описание (если заполнено) и полный текст выражения.
* Меры со статусом {{invalid}} отображаются с иконкой ⚠ и недоступны для drag-and-drop на полки.

h4. Группировка и порядок Мер в конструкторе визуализаций.  
* Если заполнена «Иерархия», Мера показывается в соответствующей display-группе внутри секции «Меры».
* Порядок Мер внутри группы определяется полем {{level}}, затем названием (по алфавиту).
* Если «Иерархия» не заполнена, Мера выводится в корневом уровне секции «Меры». 

h4. Статус {{invalid}} в UI конструктора.  
* Мера со статусом {{invalid}} не удаляется из метаданных автоматически.
* В конструкторе визуализаций такая Мера отображается с предупреждающей иконкой.
* Tooltip по невалидной Мере дополнительно содержит признак ошибки и краткую причину недоступности.
* Невалидную Меру нельзя добавить на полки до исправления выражения либо восстановления требуемых полей набора данных.
* Если существующая визуализация уже содержит ссылку на невалидную Меру:
** привязка по {{measure_id}} сохраняется;
** пилюля отображается в error-состоянии;
** запрос данных блокируется с понятным сообщением об ошибке до исправления либо удаления Меры из визуализации.

h4. Правила {{drag-and-drop}} и прочие селекторы полей. 
Мера перетаскивается на полки так же, как обычное или вычисляемое поле. При попытке разместить Меру на несовместимую полку (правила валидации описаны ниже) перетаскивание блокируется: курсор показывает «запрет», подсказка поясняет причину. Одна и та же Мера может быть размещена на нескольких полках одновременно.

Меры могут использоваться не только на основных полках визуализации, но и во *всех элементах интерфейса*, где пользователь выбирает поля или вычисляемые поля из текущей конфигурации визуализации — если бизнес-сценарий это допускает. К таким элементам относятся, в частности:
* настройки стилизации и форматирования;
* условное форматирование;
* сценарии расчётов по уровням;
* иные выпадающие списки, работающие с полями визуализации.

Для каждого такого места поддержка Мер должна быть либо *реализована*, либо её отсутствие должно быть *явно зафиксировано* как ограничение +этапа 1+ реализации (для возврата в следующих итерациях).

h4. Настройка пилюли на полке «Фильтры».
Попав на полку «Фильтры», Мера отображается в виде пилюли *тёмно-оранжевого* цвета. При клике открывается окно настройки фильтра-меры.

Форма фильтра по Мере содержит:
* тип отбора: {{WHERE}} или {{HAVING}};
* условие фильтрации;
* дополнительные параметры, если они применимы для данного типа визуализации.

h4. Ярлык AGR на пилюлях и полках.
* Для Мер с {{aggregation_kind = 1}} ярлык *AGR* отображается: в списке Мер набора данных, в боковой панели конструктора, на пилюлях полок.
* Для Мер с {{aggregation_kind = 0}} ярлык не отображается.
* Изменить {{aggregation_kind}} непосредственно на полке *нельзя*; атрибут фиксируется в настройках Меры.

----
h3. Валидация Мер и правила допустимости по полкам.
Валидация выполняется в трёх точках:
* при сохранении Меры;
* при попытке разместить Меру на полку или выбрать её в совместимом selector-е;
* при генерации SQL на бэкенде перед фактическим выполнением запроса.

В рамках этапа 1 UX-валидация опирается прежде всего на поле {{aggregation_kind}}. 
Финальная SQL-валидация выполняется бэкендом. Если фактическое выражение Меры не соответствует выбранному {{aggregation_kind}}, либо нарушает SQL-семантику итогового запроса, запрос отклоняется с понятной ошибкой.

UX-валидация при размещении на полку опирается на атрибут {{aggregation_kind}} меры.

h4. Правила валидации по полкам.

|| Полка || Допустимый тип Меры || Блокировать при нарушении? || Сообщение ||
| *Значения* | Любая | Нет блокировки; предупреждение при {{aggregation_kind = 0}} | _«Выражение помечено как неагрегированное. Для корректного отображения рекомендуется использовать агрегатную функцию, например: SUM(...)»_ |
| *Фильтры (HAVING)* | Только агрегированная ({{aggregation_kind = 1}}) | Да | _«Мера помечена как неагрегированная. Выберите тип отбора WHERE или измените признак агрегированности в настройках Меры»_ |
| *Фильтры (WHERE)* | Только неагрегированная ({{aggregation_kind = 0}}) | Да | _«Мера помечена как агрегированная. Выберите тип отбора HAVING или измените признак агрегированности в настройках Меры»_ |
| *Строки / Столбцы* | Только неагрегированная ({{aggregation_kind = 0}}) | Да | _«На полках "Строки" и "Столбцы" допустимы только неагрегированные Меры»_ |
| *Детализация* | Любая | Нет | — |
| *Дополнительные* | Любая | Нет | — |

h4. Дополнительные правила.  
* Невалидную Меру ({{status = invalid}}) нельзя разместить ни на одну полку.
* Если Мера была добавлена на полку ранее, а затем стала {{invalid}}, визуализация должна явно показывать ошибку, а не silently удалять такую Меру.
* Меры с полки «Фильтры» объединяются через {{AND}} внутри соответствующей клаузулы.
* Одновременное наличие WHERE- и HAVING-фильтров по Мерам допустимо.

h3. Логика генерации SQL.

h4. Базовый слой запроса и алгоритм генерации.

Алгоритм выполняется каждый раз при формировании запроса данных для визуализации.

При наличии хотя бы одной Меры на любой полке визуализации движок строит *внешний запрос над базовым слоем*:

{code:sql}
SELECT
    <измерения с полок «Строки», «Столбцы»>,
    <неагрегированные Меры с полок «Строки», «Столбцы»>,  -- вычисляемые измерения
    <измерения с полки «Детализация»>,
    <выражения Мер с полки «Значения»>          AS <alias>,
    <выражения Мер с полки «Дополнительные»>    AS <alias>
FROM (
    /*
     * [Оригинальный SQL произвольного набора данных подставляется без изменений]
     */
) AS __base
WHERE
    <обычные WHERE-фильтры>
    [AND <выражения Мер с полки «Фильтры», тип WHERE>]
GROUP BY
    <измерения с полок «Строки», «Столбцы»>,
    <неагрегированные Меры с полок «Строки», «Столбцы»>,
    <измерения с полки «Детализация»>
    -- GROUP BY присутствует только если в SELECT есть хотя бы одно агрегированное выражение
HAVING
    <выражения Мер с полки «Фильтры», тип HAVING, условие_1>
    [AND <выражение_N, условие_N>]
    -- для Сводной таблицы — с применением алгоритма inject_having()
    -- из постановки по HAVING (target_dimensions, CND, depth)
{code}

Допустима эквивалентная реализация через {{WITH __base AS (...)}}:
{code:sql}
WITH __base AS (
    /* [Оригинальный SQL произвольного набора данных] */
)
SELECT ... FROM __base WHERE ... GROUP BY ... HAVING ...
{code}

*Продуктовым требованием является не конкретная форма записи, а корректная инъекция выражений Мер в итоговые SQL-клаузулы внешнего запроса.*

При отсутствии Мер на полках движок продолжает формировать запрос *тем же способом, что и в текущей системе*, сохраняя обратную совместимость.

h4. Поведение Меры в зависимости от полки.

h5. Полка «Значения».
Выражение Меры подставляется в {{SELECT}}. {{GROUP BY}} формируется из полей «Строк», «Столбцов» и «Детализации». Если Мера неагрегированная — она попадает в {{SELECT}} без агрегирования (аналитик несёт ответственность за корректность); при этом {{GROUP BY}} расширяется этим выражением.

h5. Полка «Фильтры», тип {{WHERE}}.
Выражение Меры подставляется в {{WHERE}} — фильтрация происходит *до* {{GROUP BY}}, то есть отсекаются отдельные строки базового источника. Механизм {{target_dimensions}} / CND *не применяется*; блок «Применять на уровнях детализации» в UI при типе WHERE *скрыт*.

h5. Полка «Фильтры», тип {{HAVING}}.
Выражение Меры подставляется в {{HAVING}} — фильтрация происходит *после* {{GROUP BY}}, то есть отсекаются агрегированные группы.
* Для *«Сводной таблицы»* применяется алгоритм инъекции {{HAVING}} из *п. 2.2* постановки по HAVING-фильтрации ({{target_dimensions}}, CND, {{depth}}).
* Для *«Плоской таблицы»* применяется алгоритм из *п. 2.3* постановки по HAVING-фильтрации: при наличии агрегированных выражений условие инжектируется в {{HAVING}}; если агрегации нет — условие игнорируется.

h5. Полка «Строки»/«Столбцы».
Допускаются только *неагрегированные* Меры ({{aggregation_kind = 0}}). Выражение попадает одновременно в {{SELECT}} и {{GROUP BY}} — создавая «вычисляемое измерение».

h5. Полка «Детализация».
Мера попадает в {{SELECT}} и расширяет {{GROUP BY}} дополнительным уровнем группировки.

h5. Полка «Дополнительные».
Мера попадает *только* в {{SELECT}}. {{GROUP BY}} не изменяется.

h5. Несколько Мер на одной полке.
Несколько Мер на «Значениях» — каждая становится отдельной колонкой в {{SELECT}}. Несколько Мер на «Фильтрах» объединяются по типу: все WHERE-условия — в {{WHERE}} через {{AND}}, все HAVING-условия — в {{HAVING}} через {{AND}}. Допускается одновременное наличие WHERE-Мер и HAVING-Мер на «Фильтрах» — они попадают в соответствующие клаузулы независимо.

----
h3. Устойчивость к изменениям метаданных.
* *Переименование Меры*: отображаемое имя обновляется во всех панелях полей. Привязка хранится по {{measure_id}} — переименование не нарушает связь.
* *Изменение выражения Меры*: при пересохранении Меры все визуализации, использующие её, при следующем запросе данных автоматически получат обновлённое выражение. Кэши запросов инвалидируются.
* *Удаление Меры*: при подтверждении удаления Мера удаляется из метаданных набора данных и из всех полок всех визуализаций, где она использовалась.
* *Изменение SQL набора данных*: при каждом сохранении SQL-запроса система перевалидирует все Меры (в рамках этого набора данных). Меры, ссылающиеся на несуществующие поля, получают статус {{invalid}}, подсвечиваются в UI и блокируются для размещения на полки до исправления (подробнее — в разделе «Жизненный цикл Меры после изменения SQL»).

----
h3. Обратная совместимость.
При отсутствии Мер на полках движок формирует запрос *тем же способом, что и в текущей системе*. Добавление поддержки Мер *не изменяет поведение* существующих визуализаций, если Меры в них не используются. Существующие вычисляемые поля виджетов не затрагиваются. Миграция существующих метаданных не требуется.

{panel:title=Интеграция с постановкой по HAVING-фильтрации.|borderStyle=dashed|borderColor=#0052cc|bgColor=#f0f4ff}
Поддержка мер в режиме фильтрации HAVING для обычных визуализаций (кроме Сводной таблицы) описывается в текущем эпике как *базовое поведение*.

Поддержка уровня-специфичной HAVING-фильтрации для Сводной таблицы ({{apply_mode}}, {{target_dimensions}}, CND, {{depth}}) является *отдельным расширением* и описывается в связанной истории ([MB-4304|https://jira.modusbi.ru/browse/MB-4304]).

В текущем документе _История MB-4304_ фигурирует как *архитектурно связанный документ*, а не как обязательный этап разработки в рамках настоящей постановки.

Структура JSON-метаданных фильтра-меры для Сводной таблицы (HAVING с алгоритмом CND):

{code:json}
{
  "filters": [
    {
      "id": "filter_002",
      "type": "measure",
      "measure_id": "measure_001",
      "filter_mode": "HAVING",
      "condition": "> 0",
      "apply_mode": "selected",
      "target_dimensions": ["col_month"]
    }
  ]
}
{code}

|| Поле || Тип || Описание ||
| {{type}} | string | {{"measure"}} — отличает от вычисляемых полей ({{"calculated"}}) |
| {{measure_id}} | string | Ссылка на стабильный ID Меры из метаданных набора данных |
| {{filter_mode}} | string | {{WHERE}} или {{HAVING}} |
| {{apply_mode}} | string | {{all}} или {{selected}}; только для {{HAVING}} (Сводная таблица) |
| {{target_dimensions}} | string[] | Массив ID измерений; только для {{HAVING}} Сводной таблицы; пустой при {{apply_mode: "all"}} |
| {{condition}} | string | Условие фильтрации: {{> 0}}, {{= 'Active'}} и т.д. |
{panel}

h3. Критерии приёмки (AC).

*AC.1* — Доступность секции «Меры» и кнопки добавления.  
* *Дано*: аналитик открыл настройки *произвольного* набора данных.  
* *Тогда*: секция «Меры» отображается.  
* *И*: кнопка «+ Добавить меру» активна только после того, как SQL набора данных задан, успешно проверен и из него получен актуальный состав полей.  
* *И*: до этого кнопка {{disabled}} и показывает пояснение пользователю.

*AC.2* — Создание и редактирование Меры.  
* При создании/редактировании Меры через модальное окно доступны поля: {{name}}, {{description}}, {{data_type}}, {{aggregation_kind}}, {{hierarchy}}, {{level}}, {{expression}}.
* При сохранении система создаёт/обновляет Меру в metadata набора данных.
* Выполняются проверки обязательных полей, уникальности названия, валидности выражения и ссылок только на доступные поля.

*AC.3* — Табличный список Мер.  
* Сохранённые Меры отображаются в табличном списке.
* Для каждой Меры видны: название, тип данных, признак агрегированности, иерархия, уровень, краткое выражение, действия.
* Для агрегированных Мер отображается ярлык {{AGR}}.

*AC.4* — Видимость Мер в конструкторе и связанных selector-ах.  
* При построении визуализации на основе набора данных с Мерами в field picker отображается секция «Меры».
* Меры имеют отдельную визуальную иконографию и tooltip.
* Меры доступны не только для drag-and-drop на полки, но и во всех совместимых selector-ах полей текущей визуализации; неподдержанные места явно обозначены как ограничение этапа.

*AC.5* — Статус {{invalid}}.  
* *Дано*: после изменения SQL набора данных одна из Мер стала ссылаться на отсутствующее поле либо перестала быть валидной.  
* *Тогда*: такая Мера не удаляется автоматически, получает статус {{invalid}}, подсвечивается в списке Мер, показывает причину ошибки и недоступна для нового добавления на полки.  
* *И*: если визуализация уже содержит ссылку на такую Меру, пилюля отображается в error-состоянии, а запрос данных блокируется понятным сообщением.

*AC.6* — Техническая форма базового слоя не является критерием приёмки.  
* При размещении Меры на поддержанной полке её выражение корректно инжектируется во внешний запрос построителя в зависимости от типа полки: {{SELECT}}, {{WHERE}}, {{GROUP BY}}, {{HAVING}}.
* Конкретная форма базового слоя ({{FROM (<sql>) AS __base}} или {{WITH __base AS (...)}}) не является критерием приёмки.

*AC.7* — Полка «Значения».  
* *Дано*: Мера {{SUM("revenue") - SUM("cost")}} размещена на полке «Значения», а поле {{month}} — на полке «Строки».  
* *Тогда*: итоговый внешний SQL содержит выражение Меры в {{SELECT}}, а группировка соответствует текущим правилам query builder для данной визуализации.  
* *И*: для неагрегированной Меры на полке «Значения» пользователь получает предупреждение о возможном изменении уровня детализации.

*AC.8* — Полка «Фильтры», тип WHERE.  
* *Дано*: Мера с {{aggregation_kind = 0}} и выражением {{ "operation_type" <> 'Возврат' }} размещена на полке «Фильтры» с типом {{WHERE}}.  
* *Тогда*: итоговый внешний SQL содержит это выражение в {{WHERE}}.  
* *И*: выбор {{WHERE}} для Меры с {{aggregation_kind = 1}} блокируется.

*AC.9* — Полка «Фильтры», тип HAVING.  
* *Дано*: Мера с {{aggregation_kind = 1}} и выражением {{ SUM("revenue") - SUM("cost") }} размещена на полке «Фильтры» с типом {{HAVING}}, условие {{> 0}}, визуализация не требует специальной pivot-логики выбора уровней.  
* *Тогда*: итоговый внешний SQL содержит условие в {{HAVING}}.  
* *И*: выбор {{HAVING}} для Меры с {{aggregation_kind = 0}} блокируется.

*AC.10* — Полки «Строки», «Столбцы», «Детализация».  
* *Дано*: Мера с {{aggregation_kind = 1}} перетаскивается на полку «Строки», «Столбцы» или «Детализация».  
* *Тогда*: размещение блокируется, а пользователь получает соответствующее сообщение.  
* *И*: Мера с {{aggregation_kind = 0}}, размещённая на этих полках, попадает в {{SELECT}} и {{GROUP BY}} внешнего запроса.

*AC.11* — Полка «Дополнительные».  
* *Дано*: агрегированная Мера размещена на полке «Дополнительные».  
* *Тогда*: её выражение присутствует в {{SELECT}} и не расширяет {{GROUP BY}}.  
* *И*: попытка разместить на этой полке Меру с {{aggregation_kind = 0}} блокируется.

*AC.12* — Переименование и удаление Меры.  
* *Дано*: Мера используется в одной или нескольких визуализациях.  
* *Когда*: пользователь переименовывает Меру.  
* *Тогда*: в визуализациях обновляется отображаемое имя, а привязка сохраняется по {{measure_id}}.  
* *И*: при удалении используемой Меры система показывает предупреждение с количеством затронутых визуализаций и удаляет Меру только после подтверждения.

*AC.13* — Обратная совместимость и ограничение этапа 1.  
* При построении визуализации без использования Мер query builder сохраняет текущее поведение системы.
* Добавление поддержки Мер не изменяет результаты существующих визуализаций, если Меры в них не используются.
* Для простых и составных наборов данных секция «Меры» отсутствует, а создание и использование Мер на уровне набора данных недоступно.".

Реализация эпика разбивается на следующие истории:

История 1. Управление мерами в настройках произвольного набора данных: создание, редактирование, удаление, типизация, группировка и валидационный статус меры. На этом этапе меры ещё не используются в визуализациях.

История 2. Отображение мер в панели полей и использование мер в поддержанных визуализациях и связанных настройках визуализаций.

История 3. Поддержка специальных сценариев, требующих отдельной логики построителя, включая уровень-специфичный HAVING для Сводной таблицы.

Для простых и составных наборов данных поддержка мер в рамках данного эпика не реализуется.

Как системный аналитик с большим стажем, изучи общую постановку (эпик) по данной задаче и разбей её на три описанные истории. Каждая история должная быть полной (в рамках реализуемой функциональности), понятной и должна содержать все необходимые разделы (включая критерии приёмки (AC)).

При написании новых Историй (на основе данной постановки) сохрани и используй оригинальную разметку, совместимую для публикации в Jira.

h3. Контекст и цель истории.
Полное и комплекстное описание данной задачи вы можете найти в Эпике ([https://jira.modusbi.ru/browse/MB-4364]).
Настоящая История реализует управление Мерами на уровне *произвольного* набора данных: 
создание, редактирование, удаление, типизацию, display-группировку и валидационный статус Меры.

На данном этапе Меры *ещё не используются в визуализациях*: не отображаются в панели полей конструктора 
и не участвуют в построении SQL-запросов визуализаций.

История должна создать завершённый и устойчивый объект модели данных — «Меру», 
который в следующих историях будет использован в визуализациях.

h3. Границы истории.
В рамках Истории реализуется:
* секция «Меры» в настройках *произвольного* набора данных;
* создание новой Меры;
* редактирование Меры;
* удаление Меры;
* хранение расширенных метаданных Меры;
* валидация при сохранении;
* display-группировка Мер по «Иерархии» и «Уровню»;
* жизненный цикл статуса {{valid}} / {{invalid}} при изменении SQL набора данных.

В рамках Истории *не реализуется*:
* отображение Мер в конструкторе визуализаций;
* использование Мер на полках;
* SQL-инъекция Мер во внешний запрос визуализации;
* поддержка Мер для простых и составных наборов данных.

h4. Секция «Меры».
Во вкладке «Наборы данных» для *произвольного* набора данных под секцией «Описание полей набора данных» 
добавляется новая секция «Меры».

h4. Доступность кнопки «+ Добавить меру».
Кнопка «+ Добавить меру» активна *только* если одновременно выполнены все условия:
# для набора задан SQL-запрос;
# SQL-запрос успешно прошёл проверку;
# система получила и сохранила актуальный состав полей набора данных.

Если хотя бы одно условие не выполнено:
* кнопка находится в состоянии {{disabled}};
* при наведении отображается пояснение: _«Задайте и проверьте SQL-запрос набора данных»_.

h4. Создание и редактирование Меры.
При нажатии «+ Добавить меру» открывается модальное окно увеличенного размера.

В модальном окне одновременно доступны:
* поля формы Меры;
* редактор выражения;
* список полей текущего набора данных для вставки в выражение.

Для редактирования существующей Меры используется то же модальное окно с предзаполненными значениями.

Форма содержит следующие поля:
* *Название* (обязательное, строка) — отображаемое имя Меры; должно быть уникальным в рамках одного набора данных.
* *Описание* (необязательное, строка) — пояснительный текст; отображается в tooltip при наведении на Меру.
* *Тип данных* (обязательное) — логический тип результата Меры: {{number}}, {{string}}, {{date}}, {{datetime}}, {{boolean}} и т.д. Система может предложить значение по умолчанию, но пользователь обязан иметь возможность изменить тип вручную. Если для выбранного типа доступны дополнительные настройки (например, для дат), они отображаются условно.
* *Признак агрегированности* (обязательное, переключатель/флаг) — задаётся пользователем явно: {{агрегированная}} / {{неагрегированная}}. Используется для UX-валидации при размещении на полки.
* *Иерархия* (необязательное, строка) — имя группы/иерархии, в которой Мера отображается в панели полей.
* *Уровень* (необязательное, целое число) — порядок отображения Меры внутри иерархии.
* *Выражение* (обязательное) — редактор выражений, эквивалентный редактору вычисляемых полей виджета. Требования к редактору:
** Синтаксис и функции — идентичны вычисляемым полям.
** В редакторе доступен список полей текущего набора данных. Поля подставляются в выражение, обёрнутые в двойные кавычки: {{"field_name"}}.
** *(Опционально)* Автодополнение, подсветка синтаксических ошибок и другие продвинутые возможности нового редактора кода.
* *Кнопки формы:* «Сохранить» / «Отмена».

Требования к редактору:
* семантически эквивалентен редактору вычисляемых полей виджета;
* содержит список полей текущего набора данных;
* поля подставляются в двойных кавычках: {{"field_name"}};
* автодополнение, подсветка ошибок и другие продвинутые возможности _нового редактора кода_ допустимы, но не обязательны для этапа реализации этой Истории.

----
h3. Валидация при сохранении.
При сохранении выполняются следующие проверки:
* заполнены обязательные поля;
* название Меры уникально в рамках одного набора данных;
* выражение синтаксически валидно в рамках редактора/парсера;
* выражение ссылается только на доступные поля текущего набора данных;
* для набора известен актуальный состав полей.

При успешном сохранении:
* новая Мера получает стабильный {{id}};
* Мера сохраняется в метаданные набора данных;
* для Меры устанавливается статус {{valid}}.

----
h3. Список Мер набора данных.
Сохранённые Меры отображаются в табличном списке.

Набор отображаемых колонок:

|| *Название* || *Тип данных* || *Агрегация* || *Иерархия* || *Уровень* || *Выражение* (кратко) || *Действия* ||
| <название меры> | <тип> | AGR / — | <иерархия> | <порядок> | <первые N символов> | [иконка редактировать] [иконка удалить] |

Дополнительные правила:
* для Мер с {{aggregation_kind = 1}} в колонке «Агрегация» отображается ярлык *AGR*;
* для Мер с {{aggregation_kind = 0}} отображается прочерк "—";
* описание Меры выводится в tooltip (при наведении на Меру);
* если заполнена «Иерархия», Мера относится к соответствующей display-группе;
* внутри группы Меры сортируются по {{level}} по возрастанию, затем по названию (по алфавиту);
* Меры без «Иерархии» отображаются в корневом уровне секции «Меры».

----
h3. Статус валидации Меры.
Для каждой Меры хранится статус:
* {{valid}} — Мера валидна в контексте текущего набора данных;
* {{invalid}} — выражение Меры больше невалидно в контексте текущего набора данных.

Если Мера получает статус {{invalid}}:
* строка в списке подсвечивается как ошибочная (красный ореол, иконка ⚠);
* отображается предупреждающая иконка;
* в tooltip указывается причина невалидности.

----
h3. Жизненный цикл Меры при изменении SQL набора данных.
При каждом сохранении SQL-запроса набора данных система заново определяет состав полей и автоматически валидирует все Меры этого набора.

Если Мера ссылается на отсутствующее поле или её выражение не может быть интерпретировано в контексте текущего набора данных:
* Мера *не удаляется* автоматически;
* получает статус {{invalid}};
* остаётся в метаданных набора;
* отображается как невалидная до исправления.

После исправления выражения или восстановления нужных полей:
* Мера снова получает статус {{valid}}.

Если пользователь очистил SQL набора данных (либо SQL перестал проходить проверку):
* кнопка «+ Добавить меру» становится недоступной ({{disabled}});
* существующие Меры не удаляются;
* повторная полноценная валидация откладывается до появления корректного SQL и актуального состава полей;
* в UI существующие Меры могут показываться как недоступные для использования.

----
h3. Структура метаданных Меры.
Мера сохраняется в метаданных набора данных в следующем виде:

{code:json}
{
  "measures": [
    {
      "id": "measure_001",
      "name": "Валовая прибыль",
      "description": "Разница между выручкой и себестоимостью",
      "expression": "SUM(\"revenue\") - SUM(\"cost\")",
      "aggregation_kind": 1,
      "data_type": "number",
      "hierarchy": "Финансовые показатели",
      "level": 10,
      "status": "valid"
    }
  ]
}
{code}

|| Поле || Тип || Описание ||
| {{id}} | string | Стабильный идентификатор Меры |
| {{name}} | string | Отображаемое название |
| {{description}} | string | Необязательное описание |
| {{expression}} | string | SQL-выражение |
| {{aggregation_kind}} | int (0/1) | Признак агрегированности |
| {{data_type}} | string | Логический тип результата |
| {{hierarchy}} | string | Display-группа |
| {{level}} | int | Порядок внутри группы |
| {{status}} | enum | {{valid}} / {{invalid}} |

----
h3. Удаление Меры.
На данном этапе Меры ещё не используются в визуализациях, поэтому удаление Меры:
* удаляет её из метаданных набора данных;
* не требует проверки зависимостей визуализаций;
* не требует каскадного удаления из визуализаций.

Расширенная логика удаления используемой Меры реализуется в следующей Истории.

----
h3. Критерии приёмки.
*AC.1* — Секция «Меры» доступна только для *произвольного* набора данных.
* *Дано*: аналитик открыл настройки *произвольного* набора данных.
* *Тогда*: секция «Меры» отображается.
* *И*: для *простого* и *составного* набора данных секция не отображается.

*AC.2* — Кнопка «+ Добавить меру» зависит от состояния SQL набора.
* *Дано*: SQL-запрос не задан, либо не прошёл проверку, либо состав полей не получен.
* *Тогда*: кнопка «+ Добавить меру» находится в состоянии {{disabled}}.
* *И*: при наведении отображается пояснение пользователю.

*AC.3* — Модальное окно создания/редактирования Меры.
* При создании и редактировании Меры открывается увеличенное модальное окно.
* В окне доступны поля: {{name}}, {{description}}, {{data_type}}, {{aggregation_kind}}, {{hierarchy}}, {{level}}, {{expression}}.
* В редакторе доступен список полей текущего набора данных для вставки в выражение.

*AC.4* — Валидация при сохранении.
* При сохранении выполняются проверки обязательных полей, уникальности названия, синтаксической валидности выражения и ссылок только на доступные поля.
* При успешном сохранении Мера получает стабильный {{id}} и статус {{valid}}.

*AC.5* — Табличный список Мер.
* Сохранённые Меры отображаются в табличном списке схожем с табличным списком секции «Описание полей набора данных».
* Для каждой Меры видны: название, тип данных, признак агрегированности, иерархия, уровень, краткое выражение, действия.
* Для агрегированных Мер отображается ярлык {{AGR}}.

*AC.6* — Группировка и сортировка Мер.
* *Дано*: у части Мер заполнена «Иерархия» и «Уровень».
* *Тогда*: Меры группируются по «Иерархии».
* *И*: внутри группы сортируются по {{level}}, затем по названию (по алфавиту).
* *И*: Меры без «Иерархии» отображаются в корневом уровне секции.

*AC.7* — Редактирование Меры.
* *Дано*: пользователь открывает существующую Меру на редактирование.
* *Тогда*: форма открывается с предзаполненными значениями.
* *И*: после сохранения обновлённые значения отображаются в списке Мер и метаданных набора данных.

*AC.8* — Статус {{invalid}} после изменения SQL набора данных.
* *Дано*: после изменения SQL набора одна из Мер стала ссылаться на отсутствующее поле (либо перестала быть валидной).
* *Тогда*: такая Мера не удаляется автоматически.
* *И*: получает статус {{invalid}}.
* *И*: подсвечивается в списке Мер корректным образом.
* *И*: показывает причину ошибки.

*AC.9* — Восстановление статуса {{valid}}.
* *Дано*: причина невалидности устранена — выражение SQL исправлено (либо нужные поля снова появились в наборе данных).
* *Тогда*: Мера снова автоматически получает статус {{valid}}.

*AC.10* — Удаление Меры.
* *Дано*: пользователь удаляет Меру в рамках этой Истории.
* *Тогда*: Мера удаляется из метаданных набора данных.
* *И*: на данном этапе не выполняется проверка использования Меры в визуализациях, так как использование в визуализациях ещё не реализовано.


____________________________________________________________________________________

История отображения мер в панели полей и использования в поддержанных визуализациях
Эта история должна использовать результат первой: уже существующие меры становятся полями первого класса в конструкторе и начинают участвовать в построении обычного внешнего запроса визуализации. Именно здесь появляются field picker, полки, базовая матрица допустимости и привязка по measure_id. По смыслу это соответствует тому, как model-level measures после создания начинают использоваться в report authoring и field picker. А правила разделения WHERE и HAVING, а также ограничений по GROUP BY, естественно вытекают из стандартной SQL-последовательности обработки запроса.
_____________________________________________________________________________________

h3. Контекст и цель истории.
Настоящая История реализует отображение ранее созданных (как объектов модели) Мер в панели полей конструктора визуализаций и использование Мер в *поддерживаемых визуализациях* и связанных настройках визуализаций.

Под поддерживаемыми визуализациями в рамках данной Истории понимаются визуализации, для которых достаточно стандартной логики внешнего запроса:
* {{SELECT}}
* {{WHERE}}
* {{GROUP BY}}
* {{HAVING}}

Специальные сценарии построителя, включая уровень-специфичный HAVING для Сводной таблицы, *не входят* в данную Историю и реализуются отдельно.

----
h3. Границы истории.
В рамках Истории реализуется:
* отображение Мер в панели полей конструктора;
* display-группировка Мер по «Иерархии» и «Уровню»;
* отдельная иконография и ярлык {{AGR}};
* использование Мер на полках визуализаций;
* базовая форма фильтра по Мере;
* поддержка Мер в совместимых селекторах полей текущей визуализации;
* матрица допустимости Мер по полкам;
* связь визуализации с Мерой по стабильному {{measure_id}};
* стандартная SQL-инъекция Мер во внешний запрос визуализации;
* поведение статуса {{invalid}} в конструкторе и при выполнении запроса;
* предупреждение и каскадное удаление при удалении используемой Меры.

В рамках Истории *не реализуется*:
* уровень-специфичная HAVING-фильтрация для Сводной таблицы (реализация после завершения соответствующей Истории);
* иные специальные ветки построителя, требующие отдельной логики глубины, узлов или специфических запросов визуализации.

----
h3. Структура метаданных Меры.

Сохранение Меры уже реализовано в JSON-метаданных набора данных. Стабильный идентификатор ({{id}}) используется во всех внешних ссылках и не изменяется при переименовании.

{code:json}
{
  "measures": [
    {
      "id": "measure_001",
      "name": "Валовая прибыль",
      "description": "Разница между выручкой и себестоимостью",
      "expression": "SUM(\"revenue\") - SUM(\"cost\")",
      "aggregation_kind": 1,
      "data_type": "number",
      "hierarchy": "Финансовые показатели",
      "level": 10,
      "status": "valid"
    }
  ]
}
{code}

|| Поле || Тип || Описание ||
| {{id}} | string | Стабильный UUID идентификатор; не изменяется при переименовании |
| {{name}} | string | Отображаемое название |
| {{description}} | string | Необязательное описание |
| {{expression}} | string | SQL-выражение; поля набора данных оборачиваются в двойные кавычки |
| {{aggregation_kind}} | int (0/1) | Признак агрегированности; *задаётся пользователем явно* (1 — aggregated, 0 — non_aggregated) |
| {{data_type}} | string | Логический тип результата: {{number}}, {{string}}, {{date}}, {{datetime}}, {{boolean}} и т.д. |
| {{hierarchy}} | string | Необязательная группа/иерархия отображения в панели полей |
| {{level}} | int | Порядок Меры внутри иерархии |
| {{status}} | enum | {{valid}} или {{invalid}}; *вычисляется системой* по результатам валидации |

В метаданных визуализации каждое размещение Меры на полку фиксируется со ссылкой на {{measure.id}} и дополнительными параметрами ({{filter_mode}}, {{condition}} и т.д.

----
h3. Метаданные визуализации.
Во всех метаданных визуализации связь с Мерой хранится по стабильному {{measure_id}}.

Каждое использование Меры в визуализации хранит:
* тип сущности {{type = "measure"}};
* ссылку на {{measure_id}};
* дополнительные параметры в зависимости от конкретной полки и сценария.

Пример для фильтра по Мере:
{code:json}
{
  "filters": [
    {
      "id": "filter_002",
      "type": "measure",
      "measure_id": "measure_001",
      "filter_mode": "HAVING",
      "condition": "> 0"
    }
  ]
}
{code}

|| Поле || Тип || Описание ||
| {{type}} | string | {{"measure"}} |
| {{measure_id}} | string | Ссылка на стабильный ID Меры |
| {{filter_mode}} | string | {{WHERE}} или {{HAVING}} |
| {{condition}} | string | Условие фильтрации |

----
h3. Отображение Мер в конструкторе.
h4. Панель полей.
При выборе набора данных, содержащего Меры, панель полей конструктора делится на секции:
* *«Поля»* — обычные поля и вычисляемые поля виджета;
* *«Меры»* — Меры набора данных (новая секция).

Секция «Меры» располагается ниже секции «Поля».

h4. Визуальное представление Меры.
Мера отображается как поле первого класса со следующими признаками:
* цвет иконки / пилюли — тёмно-оранжевый;
* для Мер с {{aggregation_kind = 1}} отображается ярлык {{AGR}};
* tooltip (при наведении) содержит:
** описание, если заполнено;
** тип данных;
** полный текст выражения.

h4. Группировка и порядок.
Если заполнена «Иерархия», Мера показывается в соответствующей display-группе внутри секции «Меры».

Порядок вывода:
* если заполнена «Иерархия» ({{hierarchy}}), Мера показывается в соответствующей display-группе внутри секции «Меры»;
** порядок Мер внутри группы определяется полем  «Уровень» ({{level}});
** затем по названию (по алфавиту);
* если «Иерархия» не заполнена, Мера отображается в корневом уровне секции.

h4. Статус {{invalid}} в конструкторе.
Если у Меры статус {{invalid}}:
* она отображается с предупреждающей иконкой;
* tooltip дополнительно показывает причину недоступности;
* такую Меру нельзя добавить на полки;
* если Мера уже использовалась в визуализации ранее:
** привязка по {{measure_id}} сохраняется;
** соответствующая пилюля отображается в error-состоянии;
** запрос данных блокируется с понятным сообщением до исправления либо удаления Меры из визуализации.

----
h3. Drag-and-drop и прочие селекторы.
Мера перетаскивается на полки так же, как обычное поле.

Дополнительно Меры должны поддерживаться во всех совместимых селекторах полей текущей визуализации, если бизнес-сценарий селектора допускает использование Мер.

К таким местам относятся, в частности:
* настройки стилизации и форматирования;
* условное форматирование;
* сценарии расчётов по уровням;
* иные dropdown/select-компоненты, работающие с полями визуализации.

Для каждого такого места поддержка Мер должна быть либо:
* реализована;
* либо явно зафиксирована как ограничение данного этапа реализации.

Отсутствие Мер в совместимом серекторе считается некорректным поведением.

----
h3. Полка «Фильтры».
При попадании Меры на полку «Фильтры» отображается тёмно-оранжевая пилюля.

По клику открывается форма фильтра по Мере, содержащая:
* тип отбора: {{WHERE}} или {{HAVING}};
* условие фильтрации.

Правила:
* при {{WHERE}} дополнительных параметров уровней детализации нет;
* при {{HAVING}} в рамках данной Истории используется *обычное* поведение HAVING для поддерживаемых визуализаций;
* специальные настройки уровней детализации для Сводной таблицы не входят в *обязательную* часть реализации этой Истории.

----
h3. Матрица допустимости по полкам.
В рамках данной Истории используется следующая матрица допустимости:

|| *Полка* || *Допустимый тип Меры* || *Поведение* || *Сообщение* ||
| *Значения* | Любая | {{aggregation_kind = 1}} — без ограничений; {{aggregation_kind = 0}} — допустимо с предупреждением | _«Неагрегированная Мера на полке "Значения" может изменить уровень детализации результата»_ |
| *Фильтры (WHERE)* | Только {{aggregation_kind = 0}} | При нарушении блокировать | _«Для фильтра WHERE допустимы только неагрегированные Меры»_ |
| *Фильтры (HAVING)* | Только {{aggregation_kind = 1}} | При нарушении блокировать | _«Для фильтра HAVING допустимы только агрегированные Меры»_ |
| *Строки / Столбцы* | Только {{aggregation_kind = 0}} | При нарушении блокировать | _«На полках "Строки" и "Столбцы" допустимы только неагрегированные Меры»_ |
| *Детализация* | Только {{aggregation_kind = 0}} | При нарушении блокировать | _«На полке "Детализация" допустимы только неагрегированные Меры»_ |
| *Дополнительные* | Только {{aggregation_kind = 1}} | При нарушении блокировать | _«На полке "Дополнительные" поддерживаются только агрегированные Меры»_ |

h3. Логика построения SQL.
h4. Общий принцип.
Построитель запросов формирует внешний запрос визуализации поверх _SQL набора данных_.

Базовый источник может быть реализован:
* через derived table:
{code:sql}
FROM (
    /* dataset_sql */
) AS __base
{code}
* либо через CTE:
{code:sql}
WITH __base AS (
    /* dataset_sql */
)
SELECT ...
FROM __base
{code}

Продуктовым требованием является семантика инъекции Мер, а не конкретная синтаксическая форма базового слоя.

h4. Правила инъекции.
* В {{SELECT}} попадают:
** поля с полок «Строки», «Столбцы», «Детализация»;
** неагрегированные Меры с полок «Строки», «Столбцы», «Детализация»;
** Меры с полки «Значения»;
** агрегированные Меры с полки «Дополнительные».
* В {{WHERE}} попадают:
** обычные поля-фильтры;
** Меры с полки «Фильтры», где {{filter_mode = WHERE}}.
* В {{GROUP BY}} попадают:
** поля с полок «Строки», «Столбцы», «Детализация»;
** неагрегированные Меры с полок «Строки», «Столбцы», «Детализация»;
** неагрегированная Мера с полки «Значения», если итоговый запрос строится на агрегированном уровне.
* В {{HAVING}} попадают:
** Меры с полки «Фильтры», где {{filter_mode = HAVING}};
* несколько условий объединяются через {{AND}}.

h4. Поведение Меры по полкам.
* *Значения*:
** Мера попадает в {{SELECT}};
** неагрегированная Мера допустима;
** если внешний запрос агрегированный, неагрегированная Мера добавляется и в {{GROUP BY}}.
* *Фильтры / WHERE*:
** допустимы только неагрегированные Меры;
** выражение Меры попадает в {{WHERE}}.
* *Фильтры / HAVING*:
** допустимы только агрегированные Меры;
** выражение Меры попадает в {{HAVING}}.
* *Строки / Столбцы*:
** допустимы только неагрегированные Меры;
** выражение попадает одновременно в {{SELECT}} и {{GROUP BY}}.
* *Детализация*:
** допустимы только неагрегированные Меры;
** выражение попадает одновременно в {{SELECT}} и {{GROUP BY}}.
* *Дополнительные*:
** допустимы только агрегированные Меры;
** выражение попадает только в {{SELECT}};
** {{GROUP BY}} не изменяется.

----
h3. Переименование и удаление используемой Меры.
Если пользователь переименовывает Меру:
* в визуализациях обновляется отображаемое имя;
* связь по {{measure_id}} сохраняется.

Если пользователь удаляет Меру, которая используется хотя бы в одной визуализации:
* система показывает предупреждение:
_«Мера "[Название]" используется в [N] визуализациях. Удаление приведёт к её удалению со всех полок и из всех зависимых настроек. Продолжить?»_
* удаление выполняется только после подтверждения;
* после подтверждения Мера удаляется из метаданных набора и из всех зависимых мест использования.

----
h3. Критерии приёмки.
*AC.1* — Секция «Меры» в панели полей.
* При построении визуализации на основе набора данных с Мерами в конструкторе отображается отдельная секция «Меры».
* Меры визуально отличаются от обычных полей.

*AC.2* — Tooltip, ярлык {{AGR}} и display-группы.
* Для агрегированных Мер отображается ярлык {{AGR}}.
* Tooltip содержит описание и полный текст выражения.
* Если заполнены «Иерархия» и «Уровень», Меры группируются и сортируются по этим полям.

*AC.3* — Статус {{invalid}} в конструкторе.
* *Дано*: Мера имеет статус {{invalid}}.
* *Тогда*: такая Мера отображается с предупреждающей иконкой, недоступна для нового добавления на полки и показывает причину ошибки.
* *И*: если визуализация уже ссылается на такую Меру, соответствующая пилюля отображается в error-состоянии, а запрос блокируется с понятным пояснительным сообщением.

*AC.4* — Меры в селекторах.
* Меры доступны не только для drag-and-drop на полки, но и во всех совместимых selector-ах полей текущей визуализации.
* Неподдержанные селекторы явно зафиксированы как текущее ограничение.

*AC.5* — Полка «Значения».
* *Дано*: Мера {{SUM("revenue") - SUM("cost")}} находится на полке «Значения», а поле {{month}} — на полке «Строки».
* *Тогда*: итоговый внешний SQL содержит выражение Меры в {{SELECT}}.
* *И*: группировка строится по текущим правилам построителя запросов.
* *И*: для неагрегированной Меры пользователь получает предупреждение о возможном изменении уровня детализации.

*AC.6* — Полка «Фильтры», тип {{WHERE}}.
* *Дано*: неагрегированная Мера размещена на полке «Фильтры» с типом {{WHERE}}.
* *Тогда*: итоговый внешний SQL содержит выражение Меры в {{WHERE}}.
* *И*: попытка выбрать {{WHERE}} для агрегированной Меры блокируется.

*AC.7* — Полка «Фильтры», тип {{HAVING}}.
* *Дано*: агрегированная Мера размещена на полке «Фильтры» с типом {{HAVING}} в поддержанной визуализации со стандартной логикой запроса.
* *Тогда*: итоговый внешний SQL содержит условие в {{HAVING}}.
* *И*: попытка выбрать {{HAVING}} для неагрегированной Меры блокируется.

*AC.8* — Полки «Строки», «Столбцы», «Детализация».
* *Дано*: агрегированная Мера перетаскивается на полку «Строки», «Столбцы» или «Детализация».
* *Тогда*: размещение блокируется и пользователь получает сообщение.
* *И*: неагрегированная Мера, размещённая на этих полках, попадает в {{SELECT}} и {{GROUP BY}}.

*AC.9* — Полка «Дополнительные».
* *Дано*: агрегированная Мера размещена на полке «Дополнительные».
* *Тогда*: её выражение присутствует в {{SELECT}} и не расширяет {{GROUP BY}}.
* *И*: попытка разместить на этой полке неагрегированную Меру блокируется.

*AC.10* — Несколько Мер на одной полке.
* *Дано*: на «Значениях» находятся две Меры.
* *Тогда*: обе Меры становятся отдельными колонками в {{SELECT}}.
* *И*: несколько фильтров по Мерам объединяются через {{AND}} внутри своих клаузул.

*AC.11* — Переименование Меры.
* *Дано*: Мера используется в визуализации.
* *Когда*: пользователь переименовывает Меру.
* *Тогда*: в визуализации обновляется отображаемое имя.
* *И*: связь сохраняется по {{measure_id}}.

*AC.12* — Удаление используемой Меры.
* *Дано*: Мера используется хотя бы в одной визуализации.
* *Тогда*: при удалении система показывает предупреждение с количеством затронутых визуализаций.
* *И*: после подтверждения удаляет Меру из metadata набора данных, со всех полок и из зависимых настроек.

*AC.13* — Обратная совместимость.
* При отсутствии использования Мер построитель запросов продолжает формировать запрос аналогичным образом, что и в текущей системе.
* Существующие визуализации без Мер продолжают работать без изменения поведения.

История специальных сценариев построителя
Эта история должна быть максимально сфокусирована: не “ещё одна история про меры вообще”, а история про нестандартный builder behavior, который нельзя безопасно растворить в базовой поддержке из Истории 2. На текущем этапе таким сценарием является уровень-специфичный HAVING для Сводной таблицы. PostgreSQL ясно разграничивает обычный pipeline WHERE/HAVING, но не решает сам по себе проблему того, на каком уровне иерархического запроса надо применять HAVING; это уже предмет отдельной логики визуализации и query builder.
_____________________________________________________________________________________

h3. Контекст и цель истории.
Настоящая История реализует специальные сценарии построителя запросов для Мер, которые не покрываются стандартной логикой внешнего запроса из предыдущей Истории.

На текущем этапе основным и обязательным сценарием данной Истории является:
* поддержка уровень-специфичной HAVING-фильтрации по Мере для *Сводной таблицы*.

История опирается на архитектурный фундамент постановки по HAVING-фильтрации в Сводной таблице и адаптирует его для фильтров, источником которых является *Мера*, а не локальное вычисляемое поле виджета.

h3. Границы истории.
В рамках Истории реализуется:
* metadata-расширение фильтра по Мере для Сводной таблицы;
* UI-настройка HAVING-фильтра по Мере с выбором уровней детализации;
* логика инъекции HAVING по {{apply_mode}}, {{target_dimensions}}, CND и {{depth}};
* корректное поведение для разных уровней раскрытия иерархии Сводной таблицы.

В рамках Истории *не реализуется*:
* базовое создание/редактирование/удаление Мер;
* базовое отображение Мер в поле выбора и на полках;
* стандартное поведение WHERE/HAVING для обычных визуализаций;
* общая поддержка Мер в визуализациях, не требующих special-builder логики.

h3. UI фильтра по Мере для Сводной таблицы.
Если в Сводной таблице Мера размещена на полке «Фильтры» и выбран тип отбора {{HAVING}}, в форме настройки фильтра дополнительно отображается блок:
* «Применять на уровнях детализации».

Блок содержит:
* переключатель:
** «Ко всем уровням»;
** «К выбранным уровням»;
* чекбоксы измерений / уровней детализации, если выбран режим «К выбранным уровням».

Если выбран тип отбора {{WHERE}}:
* блок «Применять на уровнях детализации» скрыт;
* параметры {{apply_mode}} и {{target_dimensions}} не используются.

h3. Metadata фильтра по Мере.
Для HAVING-фильтра по Мере в Сводной таблице metadata фильтра расширяется полями:
* {{apply_mode}}
* {{target_dimensions}}

Пример:
{code:json}
{
  "filters": [
    {
      "id": "filter_002",
      "type": "measure",
      "measure_id": "measure_001",
      "filter_mode": "HAVING",
      "condition": "> 0",
      "apply_mode": "selected",
      "target_dimensions": ["col_month"]
    }
  ]
}
{code}

|| Поле || Тип || Описание ||
| {{type}} | string | {{"measure"}} |
| {{measure_id}} | string | Ссылка на стабильный ID Меры |
| {{filter_mode}} | string | {{WHERE}} или {{HAVING}} |
| {{condition}} | string | Условие фильтрации |
| {{apply_mode}} | string | {{all}} или {{selected}} |
| {{target_dimensions}} | string[] | Список уровней / измерений, на которых должен применяться HAVING |

h3. Логика инъекции HAVING.
Для Сводной таблицы backend при построении каждого запроса учитывает:
* текущий {{depth}};
* выбранный {{apply_mode}};
* список {{target_dimensions}};
* CND / контекст узла дерева.

Правила:
* если {{filter_mode = WHERE}}, Мера инжектируется в {{WHERE}} и не зависит от уровня детализации;
* если {{filter_mode = HAVING}} и {{apply_mode = all}}, HAVING применяется на всех релевантных уровнях;
* если {{filter_mode = HAVING}} и {{apply_mode = selected}}, HAVING применяется только на тех уровнях, которые соответствуют {{target_dimensions}}.

Если текущий запрос относится к уровню, не входящему в {{target_dimensions}}:
* HAVING по данной Мере *не инжектируется*.

h3. Поведение при изменении режима фильтра.
Если пользователь переключает фильтр по Мере из {{HAVING}} в {{WHERE}}:
* блок настроек уровней детализации скрывается;
* значения {{apply_mode}} и {{target_dimensions}} не используются для исполнения;
* фильтрация выполняется как обычный WHERE-фильтр по Мере.

Если пользователь переключает фильтр обратно в {{HAVING}}:
* система использует актуальные значения параметров уровней детализации, если они были сохранены;
* либо предлагает выбрать режим заново, если политика UI требует сброса.

h3. Связь с постановкой MB-4304.
Данная История использует тот же архитектурный подход, что и история MB-4304 по HAVING-фильтрации в Сводной таблице:
* {{apply_mode}}
* {{target_dimensions}}
* CND
* {{depth}}

Отличие только в том, что источником выражения фильтра выступает не локальное вычисляемое поле, а Мера, разрешаемая по {{measure_id}} из metadata набора данных.

h3. Критерии приёмки.
*AC.1* — UI блока «Применять на уровнях детализации».
* *Дано*: в Сводной таблице Мера находится на полке «Фильтры» и выбран тип {{HAVING}}.
* *Тогда*: в форме фильтра отображается блок «Применять на уровнях детализации».
* *И*: доступны режимы «Ко всем уровням» и «К выбранным уровням».

*AC.2* — Скрытие блока при {{WHERE}}.
* *Дано*: для фильтра по Мере в Сводной таблице выбран тип {{WHERE}}.
* *Тогда*: блок «Применять на уровнях детализации» скрыт.
* *И*: параметры {{apply_mode}} и {{target_dimensions}} не участвуют в исполнении запроса.

*AC.3* — Metadata HAVING-фильтра по Мере.
* *Дано*: пользователь сохранил HAVING-фильтр по Мере в Сводной таблице.
* *Тогда*: в metadata визуализации сохраняются {{type = "measure"}}, {{measure_id}}, {{filter_mode}}, {{condition}}, {{apply_mode}}, {{target_dimensions}}.

*AC.4* — Режим {{apply_mode = all}}.
* *Дано*: HAVING-фильтр по Мере настроен в режиме {{apply_mode = all}}.
* *Тогда*: HAVING по Мере инжектируется во все релевантные уровни Сводной таблицы, где применяется соответствующий агрегированный запрос.

*AC.5* — Режим {{apply_mode = selected}}.
* *Дано*: иерархия Сводной таблицы имеет уровни Год → Месяц → День, а HAVING-фильтр по Мере сохранён с {{apply_mode = selected}} и {{target_dimensions = ["col_month"]}}.
* *Тогда*: HAVING по Мере присутствует только в запросах уровня Месяц.
* *И*: для уровней Год и День данный HAVING не инжектируется.

*AC.6* — Источник выражения — Мера.
* *Дано*: HAVING-фильтр настроен по Мере.
* *Тогда*: backend разрешает выражение фильтра по {{measure_id}} из metadata набора данных, а не из локального вычисляемого поля виджета.

*AC.7* — Совместимость со стандартной логикой.
* Реализация данной Истории не ломает стандартное поведение Мер в обычных визуализациях.
* Стандартные WHERE/HAVING-сценарии, уже реализованные в предыдущей Истории, продолжают работать без изменения.
