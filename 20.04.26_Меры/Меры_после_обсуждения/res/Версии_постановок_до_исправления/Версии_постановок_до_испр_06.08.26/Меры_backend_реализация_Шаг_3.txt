h3. Контекст и цель истории.

Настоящая История реализует *третий шаг backend-доработок* по внедрению сущности *«Мера»* в аналитическом портале: парсер / анализатор выражений Мер, полноценную backend-валидацию, расчёт статусов, учёт зависимостей, блокировки небезопасных операций и ревалидацию Мер после изменений набора данных.

Шаг 3 выполняется поверх уже реализованной базы:
* Шаг 1 хранит Меры в метаданных *произвольного* набора данных и предоставляет CRUD-операции;
* Шаг 2 использует сохранённые Меры в runtime-запросах визуализаций и раскрывает {{expression}} при построении SQL.

Цель Шага 3 — заменить временное поведение Шага 1, при котором все сохранённые Меры считались валидными (статус - {{valid}}), на полноценный backend-контроль корректности Мер и безопасный жизненный цикл Меры в системе.

После реализации Шага 3 backend должен:
* понимать ссылки внутри выражения Меры;
* проверять корректность выражения относительно текущего набора данных;
* рассчитывать {{status}} и {{status_message}};
* поддерживать зависимости между Мерами, полями, вычисляемыми полями и визуализациями;
* блокировать операции, которые могут оставить систему в неконсистентном состоянии;
* повторно валидировать Меры при изменении SQL произвольного набора данных или связанных Мер.

----
h3. Границы истории.
В рамках Истории реализуется:
* разбор выражения Меры ({{expression}});
* распознавание ссылок на поля набора данных;
* распознавание ссылок на другие Меры по формату {{"Мера.<name>"}};
* построение дерева / графа зависимостей выражения;
* поддержка вложенных ссылок на Меры;
* проверка самоссылок;
* проверка циклических зависимостей любой глубины;
* анализ поддерживаемых глобальных переменных в выражении Меры;
* проверка фактической агрегированности выражения относительно {{aggregation_kind}};
* проверка выражения при создании и редактировании Меры;
* разделение ошибок на блокирующие сохранение и допускающие сохранение Меры со статусом {{invalid}};
* расчёт {{status}};
* расчёт {{status_message}};
* повторная проверка Мер после изменения SQL произвольного набора данных;
* восстановление статуса {{valid}} после исправления выражения Меры или SQL-запроса набора данных;
* обработка ситуаций, когда поле исчезло из набора данных;
* обработка ситуаций, когда зависимая Мера стала невалидной;
* учёт связей {{Мера -> поле}};
* учёт связей {{Мера -> другая Мера}};
* учёт связей {{вычисляемое поле -> Мера}}, если вычисляемые поля могут ссылаться на Меры;
* учёт связей {{визуализация -> Мера}} после внедрения Шага 2;
* блокировка удаления используемой Меры;
* блокировка изменения {{alias}} используемой Меры, если по продуктовой модели изменение {{alias}} считается переименованием используемой Меры;
* возврат списка зависимых объектов для отображения пользователю;
* ревалидация зависимых Мер после изменения исходной Меры;
* отказ от каскадного удаления зависимостей.

В рамках Истории *не реализуется*:
* создание frontend-интерфейса Мер;
* изменение runtime-контракта визуализаций, если он уже реализован в Шаге 2;
* импорт/экспорт Мер и переносы между контурами;
* автоматическое исправление выражений Мер;
* обязательная полная замена SQL-builder-а портала новым построителем запросов.

----
h3. Ключевые правила модели.
* {{name}} остаётся единственным ключом связи с Мерой во внешних ссылках. {{id}} остаётся техническим идентификатором записи Меры и не используется как внешний ключ в runtime payload визуализаций.
* {{name}} Меры не меняется после создания. Если frontend передаёт {{name}} при редактировании, backend не должен менять сохранённое системное имя.
* {{alias}} используется для отображения пользователю. Если изменение {{alias}} используемой Меры признаётся продуктовым переименованием, backend должен блокировать такое изменение при наличии зависимостей.
* {{expression}} Меры может ссылаться на поля текущего набора данных, другие Меры и поддерживаемые глобальные переменные.
* Поля набора данных в выражении указываются по системному {{name}} поля в двойных кавычках, например {{"revenue"}}.
* Ссылки на другие Меры указываются по системному {{name}} Меры в двойных кавычках, например {{"Мера.Валовая_прибыль"}}.
* {{status = "valid"}} означает, что backend смог проверить выражение Меры в текущем контексте набора данных и не нашёл ошибок, влияющих на использование Меры.
* {{status = "invalid"}} означает, что Мера сохранена, но не может безопасно использоваться в runtime-запросах визуализаций до исправления причины невалидности.
* {{status_message}} должен содержать причину невалидности, пригодную для отображения пользователю и диагностики аналитиком.
* Ошибки, нарушающие структуру Меры или граф зависимостей, должны блокировать сохранение. Контекстные ошибки, которые могут быть исправлены позже, допускают сохранение Меры со статусом {{invalid}}.

----
h3. Описание целевого поведения.
Backend должен выполнять полноценную проверку Мер при создании, редактировании и изменениях связанных объектов.

При создании или редактировании Меры backend должен:
# проверить базовые поля Меры;
# разобрать {{expression}};
# определить ссылки на поля, другие Меры и поддерживаемые глобальные переменные;
# проверить существование и доступность найденных ссылок;
# построить зависимости;
# проверить отсутствие самоссылок и циклов;
# проверить соответствие {{aggregation_kind}} фактической SQL-семантике выражения;
# рассчитать {{status}} и {{status_message}};
# сохранить Меру как {{valid}} либо как {{invalid}}, если ошибка допускает сохранение;
# заблокировать сохранение, если ошибка относится к блокирующим.

При изменении SQL-запроса произвольного набора данных backend должен заново проверить Меры этого набора данных с учётом актуального состава полей.

При изменении исходной Меры backend должен ревалидировать зависимые Меры, которые прямо или косвенно используют изменённую Меру.

При удалении используемой Меры backend должен заблокировать операцию и вернуть список зависимых объектов. Каскадное удаление зависимостей не выполняется.

----
h3. Требования к реализации.

h4. 1. Затрагиваемые backend-объекты и API-контракты.
Базовый backend-объект: {{datasets}}.

Шаг 3 дорабатывает операции, реализованные на Шаге 1:
|| Операция || Backend-объект || Требуемая доработка ||
| Чтение набора данных и списка Мер | {{datasets}} | Возвращать актуальные {{status}} и {{status_message}}, рассчитанные backend-валидацией |
| Создание Меры | {{datasets}} | Перед сохранением выполнить парсинг, валидацию, расчёт статуса и зависимостей |
| Редактирование Меры | {{datasets}} | Перед сохранением выполнить повторную проверку изменяемой Меры и зависимых Мер |
| Удаление Меры | {{datasets}} | Проверить наличие зависимых объектов и заблокировать удаление используемой Меры |
| Изменение SQL произвольного набора данных | {{datasets}} | После успешной проверки SQL и актуализации состава полей выполнить ревалидацию всех Мер набора |
| Проверка зависимостей | {{datasets}} / внутренний сервис | Вернуть список объектов, использующих {{name}} Меры, для блокировок и сообщений пользователю |

Если запрос данных визуализаций через {{/v1/api/recordsets/<dataset_id>}} уже использует Меры по Шагу 2, он должен учитывать результаты Шага 3:
* не использовать Меру со {{status = "invalid"}};
* возвращать контролируемую ошибку с {{status_message}}, если пользователь пытается использовать невалидную Меру;
* использовать актуальное раскрытие выражения с учётом зависимых Мер.

Перед операциями изменения backend должен читать актуальное состояние набора данных через {{get/list}} или внутренний эквивалент, чтобы работать с текущим набором Мер, полей и зависимостей.

---
h4. 2. Парсер / анализатор {{expression}}.
Backend должен разобрать {{expression}} Меры как SQL-выражение в пределах синтаксиса, поддержанного текущим механизмом вычисляемых полей и SQL-builder-а портала.

Анализатор должен определить:
* ссылки на поля текущего набора данных;
* ссылки на другие Меры;
* вложенные ссылки на Меры любой глубины;
* поддерживаемые глобальные переменные;
* используемые агрегатные функции;
* признаки неагрегированного выражения;
* синтаксические ошибки, из-за которых выражение нельзя безопасно интерпретировать.

Ссылки на поля определяются по системному {{name}} поля в двойных кавычках:
{code:sql}
SUM("revenue") - SUM("cost")
{code}

Ссылки на Меры определяются по системному {{name}} Меры в двойных кавычках:
{code:sql}
"Мера.Валовая_прибыль" / NULLIF(SUM("revenue"), 0)
{code}

Backend не должен трактовать строку {{"Мера.Валовая_прибыль"}} как физическую колонку набора данных. Это ссылка на Меру с {{name = "Мера.Валовая_прибыль"}}.

Если выражение Меры не содержит ссылок на поля набора данных и использует только константы, поддерживаемые переменные или другие валидные Меры, само по себе отсутствие ссылок на поля не является ошибкой.

---
h4. 3. Граф зависимостей Мер.
Backend должен строить и использовать граф зависимостей в рамках текущего набора данных.

Минимальные типы зависимостей:
|| Связь || Описание ||
| {{measure -> field}} | Мера ссылается на поле набора данных в {{expression}} |
| {{measure -> measure}} | Мера ссылается на другую Меру в {{expression}} |
| {{calculated_field -> measure}} | Вычисляемое поле ссылается на Меру, если такой синтаксис поддержан |
| {{visualization -> measure}} | Визуализация, отчёт или компонент использует Меру в метаданных или runtime-структуре после Шага 2 |

Граф зависимостей должен использоваться для:
* проверки самоссылок;
* проверки циклических зависимостей любой глубины;
* определения Мер, которые нужно ревалидировать после изменения исходной Меры;
* определения Мер, которые стали невалидными из-за невалидной зависимости;
* блокировки удаления используемой Меры;
* блокировки изменения {{alias}} используемой Меры, если это поведение подтверждено продуктовым требованием;
* формирования списка зависимых объектов для ответа backend-а.

Backend может хранить служебные структуры зависимостей в метаданных или отдельном внутреннем хранилище, если это нужно для производительности. Такие структуры должны пересчитываться backend-ом и не должны требовать ручного заполнения со стороны frontend.

---
h4. 4. Валидация при создании и редактировании Меры.
При создании или редактировании Меры backend должен выполнить проверки:
* набор данных является *произвольным*;
* у пользователя есть права на изменение набора данных;
* обязательные поля заполнены;
* {{alias}} уникален в рамках одного набора данных;
* {{name}} при создании может быть сформирован уникально;
* {{name}} существующей Меры не изменяется при редактировании;
* {{expression}} синтаксически разбирается;
* поля набора данных, указанные в выражении, существуют в актуальном составе полей текущего набора данных;
* Меры, указанные в выражении в формате {{"Мера.<name>"}}, существуют в текущем наборе данных;
* выражение не содержит ссылку на сохраняемую Меру;
* граф зависимостей Мер не содержит циклических зависимостей любой глубины;
* используемые глобальные переменные существуют и доступны в текущем контексте;
* выбранный пользователем {{aggregation_kind}} соответствует фактической агрегированности выражения;
* выражение может быть использовано в SQL-контексте, соответствующем {{aggregation_kind}}, насколько это можно проверить без выполнения пользовательского отчёта.

При редактировании существующей Меры backend должен сохранять прежнее состояние Меры, если операция завершилась блокирующей ошибкой.

---
h4. 5. Разделение ошибок сохранения.
Backend должен различать ошибки, которые блокируют сохранение, и ошибки, при которых Мера может быть сохранена со статусом {{invalid}}.

Сохранение должно блокироваться, если:
* набор данных не является *произвольным*;
* у пользователя нет прав на изменение набора данных;
* не заполнены обязательные поля;
* {{alias}} пустой, неуникальный или содержит недопустимые символы;
* невозможно сформировать уникальное {{name}} при создании;
* frontend пытается изменить {{name}} существующей Меры;
* выражение не может быть синтаксически разобрано;
* обнаружена самоссылка;
* обнаружена циклическая зависимость между Мерами;
* {{aggregation_kind}} противоречит фактической агрегированности выражения;
* пользователь пытается удалить Меру, у которой есть зависимые объекты;
* пользователь пытается изменить {{alias}} используемой Меры, если блокировка изменения {{alias}} подтверждена продуктовым требованием.

Мера может быть сохранена со статусом {{invalid}}, если выражение синтаксически разобрано, но невалидно в текущем контексте набора данных, например:
* выражение ссылается на поле, которого нет в актуальном составе полей набора данных;
* выражение ссылается на отсутствующую Меру;
* выражение ссылается на Меру со {{status = "invalid"}};
* используемая глобальная переменная не может быть разрешена в текущем контексте;
* выражение не проходит контекстную SQL-проверку относительно текущего SQL-запроса набора данных;
* выражение зависит от поля, которое исчезло после изменения SQL набора данных.

Для Меры со статусом {{invalid}} backend должен:
* сохранить запись Меры в метаданных;
* установить {{status = "invalid"}};
* заполнить {{status_message}} понятной причиной невалидности;
* вернуть сохранённую Меру frontend-у.

Для Меры со статусом {{valid}} backend должен:
* установить {{status = "valid"}};
* вернуть {{status_message}} пустой строкой.

Набор данных может быть сохранён даже при наличии Мер со статусом {{invalid}}, если ошибки не относятся к блокирующим.

---
h4. 6. Проверка {{aggregation_kind}}.
{{aggregation_kind}} задаётся пользователем вручную и сохраняется в метаданных Меры.

Backend должен проверить фактическое соответствие выражения выбранной агрегированности:
* {{aggregation_kind = 1}} — выражение должно быть допустимо как агрегированная Мера;
* {{aggregation_kind = 0}} — выражение должно быть допустимо как неагрегированная Мера.

Если пользователь передал {{aggregation_kind = 1}}, а выражение фактически не является агрегированным или не может использоваться в агрегированном SQL-контексте, backend должен вернуть ошибку валидации.

Если пользователь передал {{aggregation_kind = 0}}, а выражение содержит агрегатные функции или не может использоваться в неагрегированном SQL-контексте, backend должен вернуть ошибку валидации.

При противоречии {{aggregation_kind}} фактическому выражению Мера не создаётся и не обновляется. Для существующей Меры должно сохраняться прежнее состояние до неуспешной операции обновления.

Конкретный способ проверки фактической агрегированности определяется backend-командой: через parser, SQL-builder, пробный SQL-клауз или существующий механизм проверки вычисляемых полей. В постановке фиксируется требуемое поведение, а не конкретная реализация.

---
h4. 7. Статусы и сообщения об ошибках.
Backend должен рассчитывать {{status}} и {{status_message}} по результатам валидации.

Возможные значения {{status}}:
|| Значение || Описание ||
| {{valid}} | Мера прошла backend-проверки и может использоваться в runtime-запросах визуализаций |
| {{invalid}} | Мера сохранена, но не может использоваться до устранения причины невалидности |

{{status_message}} должен:
* быть пустым для {{status = "valid"}};
* содержать понятную причину для {{status = "invalid"}};
* указывать проблемный объект, если причина связана с отсутствующим полем, отсутствующей Мерой, невалидной зависимой Мерой или переменной;
* не раскрывать секреты, токены, пароли, параметры подключений и внутренние технические детали, не предназначенные пользователю.

Примеры сообщений:
* *«Поле "revenue" не найдено в текущем составе полей набора данных»*;
* *«Мера "Мера.Валовая_прибыль" не найдена»*;
* *«Мера зависит от невалидной Меры "Мера.Валовая_прибыль"»*;
* *«Выражение Меры содержит циклическую зависимость»*;
* *«Выбранный признак агрегированности не соответствует выражению Меры»*.

Точные тексты сообщений могут быть скорректированы командой, но они должны быть пригодны для отображения пользователю.

---
h4. 8. Ревалидация после изменения SQL набора данных.
При успешном сохранении и проверке SQL-запроса *произвольного* набора данных backend должен заново определить актуальный состав полей и выполнить ревалидацию всех Мер этого набора.

Правила ревалидации:
* Меры, выражения которых ссылаются на отсутствующие поля, получают {{status = "invalid"}} и заполненный {{status_message}};
* Меры, зависящие от невалидных Мер, также получают {{status = "invalid"}} с причиной, указывающей на невалидную зависимость;
* Меры, выражения которых не содержат ссылок на поля набора данных и используют только корректные константы, поддерживаемые переменные или другие валидные Меры, не становятся {{invalid}} только из-за изменения состава полей;
* после восстановления поля или исправления выражения Мера должна снова получить {{status = "valid"}} при успешной повторной валидации;
* существующие Меры не удаляются автоматически при изменении SQL-запроса набора данных;
* набор данных может быть сохранён даже при наличии Мер со статусом {{invalid}}, если сам SQL-запрос набора данных сохранён успешно.

Если SQL-запрос набора данных очищен, не задан или не проходит проверку:
* backend не должен удалять существующие Меры;
* backend не должен создавать новые Меры автоматически;
* полноценная ревалидация, требующая актуального состава полей, откладывается до появления корректного SQL-запроса и актуального состава полей;
* frontend должен получить данные, достаточные для отображения уже сохранённых Мер и причин ограничений, если backend их возвращает.

---
h4. 9. Ревалидация зависимых Мер после изменения Меры.
Если пользователь изменяет {{expression}}, {{aggregation_kind}} или другое свойство Меры, влияющее на корректность зависимых выражений, backend должен определить зависимые Меры и выполнить их ревалидацию.

Правила:
* зависимая Мера должна быть ревалидирована, если она прямо или косвенно использует изменённую Меру;
* если исходная Мера стала {{invalid}}, зависимые Меры, которые не могут быть проверены без неё, также должны получить {{status = "invalid"}};
* {{status_message}} зависимой Меры должен указывать, что причина связана с невалидной зависимой Мерой;
* если исходная Мера исправлена и стала {{valid}}, зависимые Меры должны быть повторно проверены и при отсутствии других ошибок получить {{status = "valid"}};
* ревалидация должна учитывать вложенные зависимости любой глубины.

Изменение {{description}}, {{hierarchy}} или {{level}} не должно запускать ревалидацию зависимых выражений, если эти поля не участвуют в SQL-семантике.

---
h4. 10. Зависимости и блокировки.
Backend должен уметь определить, используется ли Мера в зависимых объектах.

Минимальный набор зависимостей:
* другая Мера, в выражении которой есть ссылка на {{name}} проверяемой Меры;
* вычисляемое поле, в выражении которого есть ссылка на {{name}} проверяемой Меры;
* визуализация, отчёт или компонент, где есть ссылка на {{name}} проверяемой Меры;
* фильтр визуализации по Мере, если он хранится как ссылка на {{name}};
* сортировка или другая runtime-настройка визуализации, если она хранит ссылку на {{name}}.

Зависимости используются:
* для блокировки удаления Меры;
* для блокировки изменения {{alias}} используемой Меры, если это остаётся продуктовым требованием;
* для ревалидации зависимых Мер после изменения исходной Меры;
* для возврата frontend-у списка объектов, где нужно разрешить конфликт.

При наличии зависимостей удаление Меры должно блокироваться:
* запись Меры не удаляется;
* каскадное удаление из визуализаций, других Мер или вычисляемых полей не выполняется;
* backend возвращает контролируемую ошибку и список зависимых объектов.

Сообщение для пользователя:
*«Нельзя удалить Меру, используемую в визуализациях и/или в выражениях. Для удаления Меры необходимо разрешить конфликты:
[Список ссылок на визуализации, меры и вычисляемые поля, где используется удаляемая Мера]»*

Если изменение {{alias}} используемой Меры блокируется, сообщение для пользователя:
*«Нельзя переименовать Меру, используемую в визуализациях и/или в выражениях. Для переименования Меры необходимо разрешить конфликты:
[Список ссылок на визуализации, меры и вычисляемые поля, где используется переименовываемая Мера]»*

---
h4. 11. Формат списка зависимых объектов.
Ответ backend-а при блокировке должен содержать:
* признак ошибки;
* пользовательское сообщение;
* список зависимых объектов.

Список зависимых объектов должен быть достаточным для frontend-а, чтобы показать пользователю, где нужно разрешить конфликт.

Рекомендуемый минимальный состав элемента списка:
|| Поле || Описание ||
| {{object_type}} | Тип зависимого объекта: {{measure}}, {{calculated_field}}, {{report}}, {{visualization}}, {{filter}} или текущий системный эквивалент |
| {{object_id}} | Идентификатор зависимого объекта, если он есть |
| {{object_name}} | Название или alias зависимого объекта для отображения |
| {{usage_kind}} | Тип использования: выражение Меры, вычисляемое поле, полка визуализации, фильтр, сортировка и т.д. |
| {{link}} | Ссылка или путь для перехода к объекту, если текущий backend может её сформировать |

Если backend не может сформировать прямую ссылку на объект, он должен вернуть тип, идентификатор и отображаемое название зависимого объекта.

---
h4. 12. Runtime-использование Мер после Шага 3.
Если backend-Шаг 2 уже поддерживает объекты {{type = "measure"}} в runtime payload визуализаций, после Шага 3 runtime-обработка должна учитывать реальный статус Меры.

Backend должен вернуть контролируемую ошибку и не выполнять SQL-запрос, если:
* Мера с указанным {{name}} не найдена;
* найденная Мера имеет {{status = "invalid"}};
* {{status_message}} указывает на неустранённую ошибку;
* при раскрытии зависимых Мер обнаружена невалидная зависимость;
* при runtime-раскрытии обнаружена циклическая зависимость в метаданных.

Если Мера имеет {{status = "valid"}}, runtime-обработка использует правила Шага 2: поиск по {{name}}, раскрытие {{expression}}, проверка SQL-контекста использования и подстановка выражения в нужную SQL-клаузу.

---
h4. 13. Права доступа.
Операции с Мерами наследуют существующую модель прав на наборы данных.

Чтение Мер и их статусов доступно пользователям, которые имеют право читать соответствующий набор данных.

Новые отдельные права на управление Мерами в рамках этой Истории не вводятся.

Если у пользователя нет прав на изменение набора данных, backend должен возвращать контролируемый отказ на операции создания, редактирования, удаления и ручного запуска ревалидации Мер, если такая команда будет реализована.

---
h4. 14. Производительность и устойчивость.
Backend должен:
* не выполнять отдельный запрос к метаданным для каждой Меры при массовой ревалидации;
* строить индекс Мер по {{name}} в рамках текущего набора данных;
* обрабатывать вложенные зависимости без бесконечной рекурсии;
* возвращать контролируемую ошибку при повреждённых метаданных вместо аварийного завершения операции;
* не удалять и не переписывать выражения Мер автоматически при ошибках валидации;
* не раскрывать секреты, токены, пароли или параметры подключений в сообщениях ошибок.

----
h3. Обратная совместимость и ограничения.
* Существующие наборы данных без {{measures}} должны продолжить открываться и сохраняться без ошибок.
* Отсутствие массива {{measures}} в старых метаданных трактуется как пустой список Мер.
* Существующие визуализации без Мер должны продолжить формировать SQL и возвращать данные без изменений.
* Меры, которые были сохранены на Шаге 1 как {{valid}}, после внедрения Шага 3 должны быть проверены при ближайшей операции ревалидации или чтения/сохранения, в зависимости от выбранной backend-стратегии.
* Backend не должен автоматически удалять невалидные Меры. Пользователь должен иметь возможность исправить выражение или SQL-запрос набора данных.

* Уточнить, в какой момент должна выполняться первичная ревалидация Мер, созданных до внедрения Шага 3: при чтении набора данных, при первом сохранении набора, отдельной миграцией или отдельной служебной командой.

h3. Критерии приёмки (AC).
*AC.1* — Backend разбирает выражение Меры:
* *Дано:* пользователь сохраняет Меру с {{expression}}, содержащим ссылки на поля, ссылки на другие Меры и поддерживаемые переменные;
* *Когда:* backend выполняет валидацию;
* *Тогда:* backend определяет найденные ссылки и использует их для проверки выражения и построения зависимостей.

*AC.2* — Проверка ссылок на поля:
* *Дано:* выражение Меры содержит ссылку на поле набора данных в двойных кавычках;
* *Когда:* backend валидирует Меру;
* *Тогда:* backend проверяет наличие поля в актуальном составе полей текущего набора данных;
* *И:* при отсутствии поля сохраняет Меру со {{status = "invalid"}} и {{status_message}} с причиной.

*AC.3* — Проверка ссылок на другие Меры:
* *Дано:* выражение Меры содержит ссылку на другую Меру в формате {{"Мера.<name>"}};
* *Когда:* backend валидирует Меру;
* *Тогда:* backend ищет Меру с указанным {{name}} в текущем наборе данных;
* *И:* учитывает её статус и выражение при проверке сохраняемой Меры.

*AC.4* — Блокировка самоссылки:
* *Дано:* выражение сохраняемой Меры содержит ссылку на эту же Меру;
* *Когда:* backend выполняет сохранение;
* *Тогда:* сохранение блокируется;
* *И:* backend возвращает контролируемую ошибку о самоссылке или циклической зависимости;
* *И:* метаданные существующей Меры не изменяются.

*AC.5* — Блокировка циклической зависимости:
* *Дано:* несколько Мер образуют цикл зависимостей любой глубины;
* *Когда:* пользователь создаёт или редактирует Меру, замыкающую цикл;
* *Тогда:* сохранение блокируется;
* *И:* backend возвращает сообщение *«Выражение Меры содержит циклическую зависимость»* или эквивалентное по смыслу сообщение;
* *И:* метаданные существующих Мер не повреждаются.

*AC.6* — Проверка {{aggregation_kind}}:
* *Дано:* пользователь передал {{aggregation_kind}}, противоречащий фактической агрегированности выражения;
* *Когда:* backend выполняет создание или редактирование Меры;
* *Тогда:* сохранение блокируется;
* *И:* новая Мера не создаётся или существующая Мера сохраняет прежнее состояние;
* *И:* backend возвращает понятную ошибку валидации.

*AC.7* — Сохранение валидной Меры:
* *Дано:* пользователь передал корректное выражение Меры, все ссылки существуют, циклов нет и {{aggregation_kind}} соответствует выражению;
* *Когда:* backend сохраняет Меру;
* *Тогда:* Мера сохраняется со {{status = "valid"}};
* *И:* {{status_message}} возвращается пустой строкой.

*AC.8* — Сохранение Меры со статусом {{invalid}}:
* *Дано:* выражение Меры синтаксически разобрано, но ссылается на отсутствующее поле текущего набора данных;
* *Когда:* backend сохраняет Меру;
* *Тогда:* Мера сохраняется в метаданных со {{status = "invalid"}};
* *И:* {{status_message}} содержит причину невалидности;
* *И:* набор данных может быть сохранён с такой Мерой.

*AC.9* — Невалидная зависимая Мера влияет на статус:
* *Дано:* Мера {{Мера.Маржинальность}} использует в выражении {{Мера.Валовая_прибыль}}, а {{Мера.Валовая_прибыль}} имеет {{status = "invalid"}};
* *Когда:* backend валидирует {{Мера.Маржинальность}};
* *Тогда:* {{Мера.Маржинальность}} получает {{status = "invalid"}};
* *И:* {{status_message}} указывает на невалидную зависимую Меру.

*AC.10* — Ревалидация после изменения SQL набора данных:
* *Дано:* пользователь изменил SQL-запрос произвольного набора данных, и состав полей изменился;
* *Когда:* backend успешно сохранил и проверил SQL-запрос;
* *Тогда:* backend ревалидирует все Меры набора данных;
* *И:* Меры, ссылающиеся на отсутствующие поля, получают {{status = "invalid"}} и заполненный {{status_message}};
* *И:* Меры, не зависящие от состава полей, не становятся {{invalid}} только из-за изменения SQL-запроса.

*AC.11* — Восстановление статуса {{valid}}:
* *Дано:* Мера имела {{status = "invalid"}} из-за отсутствующего поля или невалидной зависимости;
* *Когда:* пользователь исправил выражение Меры или восстановил требуемое поле в SQL-запросе набора данных;
* *Тогда:* после повторной backend-валидации Мера получает {{status = "valid"}};
* *И:* {{status_message}} возвращается пустой строкой.

*AC.12* — Возврат списка зависимостей:
* *Дано:* Мера используется в другой Мере, вычисляемом поле или визуализации;
* *Когда:* backend проверяет зависимости этой Меры;
* *Тогда:* backend возвращает список зависимых объектов с типом, идентификатором, отображаемым названием и типом использования;
* *И:* данных достаточно, чтобы frontend показал пользователю место конфликта.

*AC.13* — Блокировка удаления используемой Меры:
* *Дано:* Мера используется в зависимых объектах;
* *Когда:* пользователь пытается удалить Меру;
* *Тогда:* backend блокирует удаление;
* *И:* каскадное удаление из зависимых объектов не выполняется;
* *И:* backend возвращает сообщение о невозможности удаления и список зависимых объектов.

*AC.14* — Блокировка изменения {{alias}} используемой Меры при подтверждённом продуктовом правиле:
* *Дано:* изменение {{alias}} используемой Меры должно блокироваться по продуктовой модели;
* *И:* Мера используется в выражении другой Меры, вычисляемом поле или визуализации;
* *Когда:* пользователь пытается изменить {{alias}} этой Меры;
* *Тогда:* backend блокирует изменение {{alias}};
* *И:* сохранённые метаданные Меры не меняются;
* *И:* backend возвращает сообщение о невозможности переименования и список зависимых объектов.

*AC.15* — Ревалидация зависимых Мер после изменения исходной Меры:
* *Дано:* Мера {{Мера.Зависимая}} зависит от Меры {{Мера.Исходная}};
* *Когда:* пользователь изменяет {{expression}} или {{aggregation_kind}} Меры {{Мера.Исходная}};
* *Тогда:* backend повторно валидирует {{Мера.Зависимая}} и другие зависимые Меры любой глубины;
* *И:* их {{status}} и {{status_message}} обновляются по результатам проверки.

*AC.16* — Runtime-запрос не использует невалидную Меру:
* *Дано:* runtime payload визуализации содержит объект {{type = "measure"}} с {{name}} Меры, у которой {{status = "invalid"}};
* *Когда:* backend обрабатывает запрос данных;
* *Тогда:* SQL-запрос не выполняется;
* *И:* backend возвращает контролируемую ошибку с {{measure_name}}, runtime-блоком и причиной из {{status_message}}.

*AC.17* — Отказ от каскадного удаления:
* *Дано:* Мера используется в визуализации или выражении другой Меры;
* *Когда:* пользователь удаляет Меру;
* *Тогда:* backend не удаляет автоматически ссылки из визуализаций, других Мер или вычисляемых полей;
* *И:* операция завершается контролируемой ошибкой до изменения метаданных.

*AC.18* — Обратная совместимость:
* *Дано:* существующий набор данных, отчёт или визуализация не использует Меры;
* *Когда:* пользователь открывает, сохраняет или использует этот объект после внедрения Шага 3;
* *Тогда:* текущее поведение сохраняется без регрессий;
* *И:* отсутствие массива {{measures}} в старых метаданных не приводит к ошибке.
