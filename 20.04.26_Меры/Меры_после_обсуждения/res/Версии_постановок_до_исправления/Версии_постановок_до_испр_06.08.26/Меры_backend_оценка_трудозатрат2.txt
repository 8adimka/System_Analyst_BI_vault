h3. Контекст и проблематика.

Требуется оценить backend-доработки для внедрения *Мер* — именованных SQL-выражений уровня набора данных, которые хранятся в метаданных *произвольного* набора данных и используются в SQL-запросах визуализаций только при фактическом размещении Меры на полках визуализаций.

Полный текст постановки Меры в наборах данных: [https://jira.modusbi.ru/browse/MB-4364]

----
h3. Цель и бизнес-ценность.
Меры реализуются только для *произвольного* набора данных с пользовательским SQL-запросом.

Для *простых* и *составных* наборов данных механизм Мер в рамках первых этапов не реализуется.

Цель backend-части:
* обеспечить хранение и возврат Мер в составе метаданных произвольного набора данных;
* обеспечить серверную валидацию выражений Мер, включая ссылки на поля набора данных по {{name}}, ссылки на другие Меры по {{name}}, серверные переменные и переменные окружения;
* обеспечить раскрытие выражений Мер при построении SQL-запросов визуализаций;
* обеспечить корректное размещение раскрытых выражений в конкретную SQL-клаузу в зависимости от полки размещения и режима фильтрации;
* обеспечить ссылочную целостность при переименовании и удалении Мер;
* обеспечить обратную совместимость: существующие наборы данных, отчёты и визуализации без Мер должны работать без изменения поведения.

---
h4. Разделение backend-работ по этапам.
*Шаг 1. Меры в настройках набора данных.*
В рамках первого шага backend оценивает модель Меры на уровне произвольного набора данных: хранение, чтение, сохранение, валидацию, статусы, ревалидацию (после изменения SQL набора данных и т.д.),  и базовый учёт:
* зависимостей между Мерами, 
* полями набора данных,
* вычисляемыми полями.

В рамках Шага 1 *не оценивается* использование Мер на полках визуализаций и генерация SQL-запроса визуализаций с Мерами.

*Шаг 2. Использование Мер в визуализациях.*
В рамках второго шага backend оценивает поддержку ссылок на Меры в метаданных визуализаций и runtime payload, финальную валидацию допустимости Мер по полкам, раскрытие выражений Мер и инъекцию в SQL внешнего запроса.

В рамках Шага 2 Меры рассматриваются как уже созданные объекты метаданных набора данных со статусом {{valid}} или {{invalid}}.

*Последующие этапы.*
Отдельно от первых двух шагов требуется оценить импорт/экспорт и переносы между контурами, уровень-специфичную HAVING-фильтрацию Сводной таблицы, поддержку Мер для простых и составных наборов данных, а также возможную переработку построителя запросов/модели зависимостей (если команда разработки выберет такой технический путь).

---
h4. Рекомендуемые блоки оценки трудозатрат:
# Хранение Мер в метаданных произвольного набора данных и API для чтения/сохранения.
# Парсер/анализатор выражений Мер: ссылки на поля, ссылки на Меры, вложенность, циклы, переменные, определение фактической агрегированности.
# Валидация Мер при сохранении Меры и при изменении SQL набора данных.
# Учёт зависимостей и блокировка переименования/удаления используемых Мер.
# Интеграция Мер в метаданные визуализаций, {{axes}}, {{axesDefault}}, вычисляемые поля и payload.
# Раскрытие Мер и генерация SQL-запроса.
# Обратная совместимость текущих наборов данных, отчётов, визуализаций и payload без Мер.
# Импорт/экспорт наборов данных, отчётов и механизмов переноса между контурами как отдельный блок оценки.

---
h4. Что не входит в рамки текущей backend-постановки:
* Реализация frontend-интерфейса Мер.
* Переработка редактора выражений ради отдельной визуальной подсветки Мер в формулах.
* Реализация Мер для простых и составных наборов данных.
* Изменение ФВД.
* Полная замена текущего построителя SQL новым построителем запросов (если команда разработки не примет такое техническое решение).
* Уровень-специфичная HAVING-фильтрация Сводной таблицы - реализуется отдельной задачей.
* Общая переработка механизма фильтров и условий вне сценариев, напрямую добавляемых Мерами.

----
h3. Ключевые понятия в рамках постановки.
* +Мера+ — именованное вычислимое SQL-выражение, определённое на уровне *произвольного* набора данных. Мера не добавляется в базовый SQL набора данных автоматически и не выполняется сама по себе. Она раскрывается backend-ом только в тех запросах визуализаций, где есть ссылка на эту Меру.
* +Имя Меры+ ({{name}}) — уникальное в рамках одного набора данных имя, используемое как *внешний ключ связи* с Мерой в визуализациях, выражениях других Мер и вычисляемых полях.
* +Идентификатор Меры+ ({{id}}) — стабильный {{UUID}} записи Меры в метаданных набора данных. Генерируется системой при создании, не меняется при редактировании и переименовании. {{id}} Меры не используется как внешний ключ связи.
* +Выражение Меры+ ({{expression}}) — SQL-выражение, в котором допускаются ссылки на поля текущего набора данных, другие Меры, серверные переменные и переменные окружения.
** +Ссылка на поле набора данных+ — ссылка по {{name}} поля набора данных. {{name}} поля уникален в рамках одного набора данных.
** +Ссылка на Меру+ — токен вида {{[<name Меры>]}}. Например, {{[Валовая прибыль]}} означает ссылку на Меру с {{name = "Валовая прибыль"}}, а не копию её выражения.
* +Агрегированность Меры+ ({{aggregation_kind}}) — признак агрегированности (на данном этапе задаётся пользователем): {{1}} — агрегированная Мера, {{0}} — неагрегированная Мера. Backend должен проверять фактическое выражение Меры и возвращать ошибку валидации при противоречии между пользовательским флагом и выражением.
* +Валидность Меры+ ({{status}}) — результат валидации Меры: {{valid}} или {{invalid}}.
* +Причина невалидности+ ({{status_message}}) — текстовая причина статуса {{invalid}} или пустая строка для {{valid}}. Используется frontend-ом для tooltip и сообщений пользователю.
* +Ссылочная целостность+ — backend не разрешает переименование или удаление Меры, если на неё есть ссылки из визуализаций, других Мер или вычисляемых полей.
* +Базовый слой запроса+ — текущий механизм, где исходный SQL произвольного набора данных используется как внутренний источник внешнего запроса визуализации: через {{FROM (<dataset_sql>) AS __base}} или эквивалентный вариант.

h3. Пользовательский интерфейс и управление Мерами в настройках Набора данных.
Раздел фиксирует backend-поведение, необходимое для поддержки интерфейса настройки Мер.

h4. Доступность Мер для произвольного набора данных.
Backend должен возвращать и принимать Меры только для *произвольных* наборов данных с пользовательским SQL-запросом.

Для простых и составных наборов данных:
* backend не должен позволять создавать или сохранять Меры, а при попытке должен возвращаться контролируемый отказ с сообщением, что Меры поддерживаются только для произвольных наборов данных;
* существующее поведение таких наборов данных не меняется.

---
h4. Backend-объекты и команды.
Базовый backend-объект: {{datasets}}.

В оценке нужно ориентироваться на текущий паттерн API и существующие команды чтения набора данных.

Для Шага 1 требуется предусмотреть:
* {{object.name = "datasets"}}, {{command.name = "get.full"}} / {{command.name = "list.full"}} или их текущие эквиваленты — возвращают массив {{measures}} в составе метаданных произвольного набора данных;
* существующая команда сохранения/обновления набора данных или отдельная команда в объекте {{datasets}} — создаёт, изменяет и удаляет Меры в составе набора данных;
* операция валидации Меры — может быть отдельной командой объекта {{datasets}} или внутренним backend-сервисом, если frontend не вызывает её напрямую;
* операция получения зависимостей Меры — возвращает список объектов, использующих {{name}} Меры, для блокировки переименования/удаления и показа конфликтов.

Для Шага 2 требуется предусмотреть:
* текущий endpoint {{/v1/api/recordsets/<dataset_id>}} — принимает ссылки на Меры в runtime payload визуализации и строит данные с учётом Мер;
* команды сохранения отчёта/визуализации — учитывают объекты {{type = "measure"}} при анализе метаданных и обновлении зависимостей.

Перед изменением Мер backend должен читать актуальное состояние набора данных через {{get/list}} или внутренний эквивалент, чтобы корректно определить:
* была ли Мера создана, изменена, переименована или удалена;
* какие зависимости есть у прежнего {{name}} Меры;
* какие Меры требуют повторной валидации.

---
h4. Права доступа.
Операции чтения и изменения Мер наследуют права доступа к наборам данных.

* Чтение Мер доступно пользователям, которые могут читать соответствующий набор данных.
* Создание, изменение, удаление и валидация Мер доступны ролям, которым разрешено изменять набор данных.
* Запрос данных через {{/v1/api/recordsets/<dataset_id>}} использует существующую модель доступа к отчёту, визуализации и набору данных.

---
h4. Валидация при сохранении Меры.
При создании или редактировании Меры backend должен выполнить:
* проверку обязательных полей Меры;
* проверку уникальности {{name}} среди Мер одного набора данных и проверку допустимости символов в {{name}} с учётом утвержденного синтаксиса; до реализации механизма экранирования символы {{[}} и {{]}} в {{name}} Меры запрещаются;
* синтаксический анализ {{expression}};
* проверку существования полей набора данных, на которые есть ссылки по {{name}};
* проверку существования Мер, на которые есть ссылки в формате {{[<name Меры>]}};
* проверку отсутствия самоссылок и циклических зависимостей между Мерами любой глубины;
* проверку корректной обработки серверных переменных и переменных окружения;
* проверку соответствия пользовательского {{aggregation_kind}} фактическому выражению Меры (либо, в случае принятия решения командой, назначения {{aggregation_kind}} для Меры системой без привлечения пользователя);
* пробную SQL-валидацию выражения в составе внешнего запроса, насколько это возможно без выполнения полного запроса данных.

Если выражение Меры не содержит ссылок на поля набора данных и использует только константы, серверные переменные, переменные окружения или другие валидные Меры - это не является ошибкой.

Сохранение блокируется для ошибок, которые нарушают структуру Меры:
* не заполнены обязательные поля;
* {{name}} не уникален в наборе данных;
* обнаружена самоссылка или циклическая зависимость;
* {{aggregation_kind}} противоречит фактическому выражению Меры;
* выражение не может быть синтаксически разобрано.

Мера может быть сохранена со статусом {{invalid}}, если выражение синтаксически разобрано, но невалидно в текущем контексте набора данных:
* поле набора данных не найдено;
* Мера, на которую есть ссылка, не найдена или имеет {{status = invalid}};
* серверная переменная или переменная окружения не может быть разрешена;
* выражение не прошло SQL-валидацию относительно текущего SQL набора данных.

При {{status = invalid}} backend должен заполнить {{status_message}} причиной, пригодной для отображения пользователю.

---
h4. Переименование и удаление Меры.
Если изменяется {{name}} существующей Меры, backend должен проверить зависимости по прежнему {{name}}.

Если Мера используется хотя бы в одном объекте, переименование блокируется. Backend возвращает список зависимостей:
* отчёт/визуализация/компонент, где Мера размещена на полке, используется в фильтре или совместимом селекторе компонента;
* другая Мера, в выражении которой есть ссылка на переименовываемую Меру;
* вычисляемое поле, в выражении которого есть ссылка на переименовываемую Меру.

Если изменяются другие свойства Меры без изменения {{name}}, сохранение не должно блокироваться только из-за наличия зависимых визуализаций. При этом выражение и {{aggregation_kind}} проходят стандартную валидацию, а зависимые Меры и вычисляемые поля должны быть ревалидированы.

Удаление Меры блокируется при наличии зависимостей. Физическое удаление допустимо только если зависимостей нет. Каскадное удаление Меры из визуализаций, других Мер или вычисляемых полей *не выполняется*.

---
h4. Жизненный цикл после изменения SQL набора данных.
При успешной проверке и сохранении SQL-запроса произвольного набора данных backend должен повторно валидировать все Меры этого набора.

Если изменился состав полей:
* Меры, ссылающиеся на отсутствующие поля, получают {{status = invalid}} и {{status_message}};
* Меры, зависящие от невалидных Мер, также получают {{status = invalid}};
* Меры, не зависящие от изменённых или удалённых полей, сохраняют {{valid}} при корректном выражении;
* набор данных может быть сохранён даже при наличии Мер со статусом {{invalid}}.

Если SQL-запрос набора данных отсутствует или не проходит проверку:
* ранее сохранённые Меры не удаляются;
* создание новых Мер должно быть недоступно для frontend-а;
* повторная полноценная SQL-валидация Мер откладывается до появления корректного SQL-запроса и актуального состава полей.

h3. Структура метаданных Меры.
Меры хранятся в метаданных *произвольного* набора данных в массиве {{measures}}.

{code:json}
{
  "measures": [
    {
      "id": "847b1ec3-bbf8-4365-85fb-c4fca2a06e2e",
      "name": "Валовая прибыль",
      "description": "Разница между выручкой и себестоимостью",
      "expression": "SUM(\"revenue\") - SUM(\"cost\")",
      "aggregation_kind": 1,
      "data_type": "number",
      "hierarchy": "Финансовые показатели",
      "level": 10,
      "status": "valid",
      "status_message": ""
    }
  ]
}
{code}

|| Поле || Тип || Backend-требование ||
| {{id}} | string / UUID | Стабильный системный идентификатор Меры. Генерируется при создании, не изменяется при редактировании. |
| {{name}} | string | Уникальное имя Меры в рамках одного набора данных. Используется как внешний ключ ссылки. |
| {{description}} | string | Необязательное описание. Backend хранит и возвращает без изменения. |
| {{expression}} | string | SQL-выражение Меры. Backend парсит, валидирует и раскрывает при построении запроса. |
| {{aggregation_kind}} | int (0/1) | Признак агрегированности. Backend проверяет соответствие фактическому выражению. |
| {{data_type}} | string | Логический тип результата Меры: {{number}}, {{string}}, {{date}}, {{datetime}} и т.д. |
| {{hierarchy}} | string | Необязательная display-группа. Backend хранит и возвращает без бизнес-логики группировки. |
| {{level}} | int | Порядок внутри {{hierarchy}}. Backend хранит и возвращает. |
| {{status}} | enum | {{valid}} или {{invalid}}. Вычисляется backend-ом по результатам валидации. |
| {{status_message}} | string | Причина невалидности или пустая строка при {{valid}}. |

Backend *может* хранить дополнительные служебные данные для ускорения проверок, например зависимости {{measure -> field}} и {{measure -> measure}}. Если такие данные добавляются, они должны пересчитываться backend-ом и не должны требовать ручного заполнения со стороны frontend.

----
h3. Метаданные визуализации и ссылки на Меры.
Во всех метаданных визуализаций Мера должна передаваться как ссылка, а не как раскрытое выражение. Backend должен сам получить выражение Меры из метаданных набора данных по {{datasetId}} и {{name}}.

Минимальный объект использования Меры в визуализации:

{code:json}
{
  "id": "visual_measure_4f9b7e2d",
  "type": "measure",
  "name": "Валовая прибыль",
  "datasetId": 244
}
{code}

Требования к обработке:
* {{type = "measure"}} является обязательным признаком, отличающим Меру от обычного поля и вычисляемого поля виджета;
* {{name}} является ссылкой на определение Меры в {{measures[]}};
* {{id}} в объекте использования, если оно есть, является локальным идентификатором размещения/пилюли в визуализации и не равно {{measures[].id}};
* frontend не должен передавать {{expression}} Меры в метаданные визуализации и runtime payload как источник истины;
* backend не должен использовать локальные настройки размещения как свойства определения Меры;
* если Мера не найдена, имеет {{status = invalid}} или не относится к текущему набору данных, backend должен отклонить запрос данных с контролируемой ошибкой.

В объект использования Меры в визуализации не копируются поля определения Меры:

Если текущая модель визуализации использует поле {{type}} для типа данных обычного поля (например, {{string}}, {{number}} или {{calculated}}), для Меры необходимо явно поддержать значение {{type = "measure"}} по целевому контракту. Логический тип результата Меры берётся из {{measures[].data_type}}.

Для текущего эндпоинта {{/v1/api/recordsets/<dataset_id>}} необходимо поддержать Меры в тех же логических секциях, где сейчас передаются поля и вычисляемые поля.

---
h4. Runtime payload.
Payload запроса данных — это не место хранения Меры. Это краткое описание того, какие Меры участвуют в конкретном запросе и где backend должен раскрыть их выражения.

Мера на полке «Значения»:
{code:json}
{
  "select": [
    {
      "type": "measure",
      "name": "Валовая прибыль",
      "alias": "[values][0]"
    }
  ],
  "group": [],
  "where": [],
  "having": [],
  "series": {
    "enable": 0
  }
}
{code}

{{alias}} является техническим alias результата запроса. Он не является свойством Меры и не хранится в {{measures[]}}.

Мера как вычисляемое измерение на полках группировки:
{code:json}
{
  "group": [
    {
      "type": "measure",
      "name": "Маржинальность_категория",
      "alias": "[categories]"
    }
  ],
  "select": [
    {
      "type": "measure",
      "name": "Маржинальность_категория",
      "alias": "[categories]"
    }
  ],
  "where": [],
  "having": []
}
{code}

WHERE-фильтр по Мере:
{code:json}
{
  "where": [
    {
      "type": "measure",
      "name": "Маржинальность_строки",
      "condition": {
        "operator": ">",
        "value": 0,
        "value_type": "number"
      }
    }
  ],
  "having": []
}
{code}

Если текущий backend в первом техническом варианте продолжает принимать {{having}} как объект с {{condition}}, а не как массив условий, требуется оценить совместимый adapter-слой. Целевое требование остаётся неизменным: условие фильтра по Мере должно быть структурным, а backend не должен строить SQL из произвольной строки пользовательского ввода без валидации оператора и значения.

----
h3. Отображение Мер в конструкторе визуализаций.
Backend-часть для отображения Мер сводится к предоставлению данных и статусов, необходимых frontend-у:
* при чтении набора данных backend возвращает список Мер, их типы, агрегированность, иерархию, порядок, статус и причину невалидности;
* невалидные Меры не удаляются из метаданных и продолжают возвращаться в списке;
* если визуализация содержит ссылку на невалидную или отсутствующую Меру, backend должен возвращать контролируемую ошибку вместо некорректного SQL или необработанного исключения;
* если в наборе данных есть невалидные Меры, но конкретная визуализация их не использует, запрос данных визуализации должен выполняться штатно.

----
h3. Валидация допустимости Мер по полкам.
Backend выполняет финальную валидацию допустимости Мер перед построением SQL. Frontend-валидация может дублировать эти правила, но не заменяет backend-проверку.

|| Полка / секция payload || Допустимость || Backend-поведение при нарушении ||
| {{select}} / «Значения» | Агрегированные и неагрегированные Меры | Запрос строится по SQL-семантике. Если выражение не может быть корректно встроено, вернуть контролируемую ошибку. |
| {{where}} / фильтр {{WHERE}} | Только неагрегированные Меры | Отклонить запрос, если Мера агрегированная или фактически содержит агрегатную функцию. |
| {{having}} / фильтр {{HAVING}} | Только агрегированные Меры | Отклонить запрос, если Мера неагрегированная. |
| {{group}} / «Строки», «Столбцы», «Детализация» | Только неагрегированные Меры | Отклонить запрос, если Мера агрегированная. |
| «Дополнительные» | Любая Мера | Не раскрывать Меру в SQL, если конкретная визуализация не использует эту полку в запросе данных. |

Локальные параметры текущей визуализации являются параметрами размещения, а не свойствами Меры. В Шаге 2 требуется оценить их влияние на раскрытие Меры в текущем построителе SQL и сохранить существующее поведение для обычных полей и вычисляемых полей.

----
h3. Логика генерации SQL.

h4. Базовый слой запроса и алгоритм генерации.
При построении данных визуализации backend использует исходный SQL произвольного набора данных как внутренний источник и строит внешний запрос поверх него.

Принципиальная схема:
{code:sql}
SELECT
  <поля и неагрегированные Меры группировок>,
  <выражения Мер с полки Значения> AS <alias>
FROM (
  <исходный SQL произвольного набора данных>
) AS __base
WHERE
  <обычные WHERE-фильтры>
  [AND <раскрытые выражения неагрегированных Мер WHERE>]
GROUP BY
  <поля группировок>
  [, <раскрытые выражения неагрегированных Мер группировок>]
HAVING
  <раскрытые выражения агрегированных Мер HAVING>
{code}

Допустима эквивалентная реализация через текущий механизм построителя запросов. Продуктовое требование — не конкретная форма SQL, а корректное раскрытие и размещение выражений Мер в итоговом запросе.

---
h4. Раскрытие выражений Мер.
Перед генерацией SQL backend должен:
# найти все ссылки на Меры в payload визуализации;
# загрузить определения Мер из метаданных набора данных;
# проверить, что каждая используемая Мера существует и имеет {{status = valid}};
# рекурсивно раскрыть ссылки на другие Меры в формате {{[<name Меры>]}};
# проверить отсутствие циклов;
# заменить ссылки на поля набора данных на корректные SQL-идентификаторы базового слоя;
# сохранить корректную обработку строковых литералов, комментариев, серверных переменных и переменных окружения;
# сформировать итоговое выражение для нужной SQL-клаузы.

Раскрытие Меры должно выполняться при каждом запросе данных, чтобы изменение формулы Меры на уровне набора данных применялось во всех визуализациях без копирования выражения в метаданные визуализаций.

---
h4. Поведение Меры в зависимости от полки.
* *Полка «Значения» / {{select}}*: выражение Меры добавляется в {{SELECT}} с alias из payload. Для неагрегированной Меры backend должен строить SQL по текущим правилам группировки; если итоговая SQL-семантика нарушена, вернуть понятную ошибку.
* *Фильтр {{WHERE}}*: выражение неагрегированной Меры добавляется в {{WHERE}} и применяется до группировки. Механизм {{target_dimensions}} / CND не применяется.
* *Фильтр {{HAVING}}*: выражение агрегированной Меры добавляется в {{HAVING}} и применяется после группировки.
* *«Строки», «Столбцы», «Детализация» / {{group}}*: неагрегированная Мера раскрывается как вычисляемое измерение и попадает в {{SELECT}} и {{GROUP BY}}.
* *«Дополнительные»*: если текущая визуализация не использует эту полку в запросе данных, Мера не должна добавляться в SQL.

---
h4. Несколько Мер и вложенные Меры.
* Несколько Мер в {{select}} формируют отдельные выражения с отдельными alias.
* Несколько WHERE-фильтров по Мерам объединяются с остальными WHERE-условиями по текущим правилам построителя.
* Несколько HAVING-фильтров по Мерам объединяются с остальными HAVING-условиями по текущим правилам построителя.
* Мера может ссылаться на другую Меру на любую глубину вложенности, если нет цикла.
* Если вложенная Мера стала {{invalid}}, все зависящие от неё Меры должны получить {{invalid}} при ревалидации.

---
h4. SQL-валидация и производительность.
Backend должен оценить способ SQL-валидации Мер без чрезмерного увеличения времени проверки набора данных.

Минимально ожидаемое поведение:
* при сохранении одной Меры проверяется эта Мера и зависящие от неё Меры;
* при изменении SQL набора данных проверяется исходный SQL и затем Меры, зависящие от полей набора данных;
* при запросе данных проверяются только Меры, реально используемые конкретной визуализацией;
* если возможно, сначала выполняется укрупнённая проверка, а детальная проверка по Мерам запускается только при ошибке или для изменённых Мер;
* ошибка должна быть связана с конкретной Мерой, если backend может это определить.

----
h3. Устойчивость к изменениям метаданных.
Backend должен обеспечить отдельный учёт зависимостей Мер. Текущий механизм учёта использования полей набора данных нельзя считать достаточным без проверки, потому что Мера является справочником выражений, а не обычным полем набора данных.

Для оценки требуется предусмотреть:
* хранение или вычисление зависимостей {{measure -> field}}, {{measure -> measure}}, {{calculated field -> measure}}, {{visualization/report -> measure}} (после реализации Шага 2);
* обновление зависимостей при сохранении Меры, отчёта/визуализации, где Меры используются в {{axes}}, {{axesDefault}}, {{select}}, {{where}}, {{having}}, {{order}} или аналогичных структурах;
* блокировку переименования и удаления +используемых+ Мер;
* ревалидацию зависимых Мер и вычисляемых полей после изменения формулы, имени, статуса Меры или SQL набора данных.

Необходимо оценить один из вариантов:
* расширить существующий механизм анализа JSON для объектов {{type = "measure"}};
* расширить существующую таблицу связей полей, если она допускает новый тип связанной сущности;
* создать отдельную модель связей для Мер или реализовать механизм рекурсивного поиска зависимых Мер по {{name}}-мер найденным в выражении.

Технический вариант выбирает команда разработки, но в оценке должен быть явно учтён объём работ по связям.

----
h3. Обратная совместимость.
* Наборы данных без массива {{measures}} должны читаться и сохраняться без ошибок.
* Существующие визуализации без {{type = "measure"}} должны строить запросы по текущей логике.
* Вычисляемые поля виджетов продолжают работать по текущему контракту.
* Добавление Мер не должно менять SQL, если Меры не используются в payload визуализации.
* Если Мера есть в наборе данных, но не используется конкретной визуализацией, она не должна добавляться в SQL и не должна нагружать запрос.
* Старые отчёты не требуют миграции, если в них нет ссылок на Меры.
* Текущие структуры для обычных полей и вычисляемых полей не должны менять смысл.

----
h3. Интеграция с импортом, экспортом и переносом между контурами.
Импорт/экспорт и переносы между контурами требуется оценивать как отдельный последующий блок, если они не входят в первые две истории.

Для оценки требуется проверить и учесть:
* экспорт и импорт произвольного набора данных вместе с {{measures}};
* экспорт и импорт отчётов/визуализаций, содержащих ссылки на Меры;
* перенос между контурами, где набор данных и отчёт переносятся вместе;
* ситуацию, когда отчёт импортируется без требуемой Меры или без набора данных;
* восстановление зависимостей после импорта;
* сохранение правила, что внешняя связь с Мерой строится по {{name}}, а {{measures[].id}} не используется как внешний ключ визуализации.

Если команда решит выносить импорт/экспорт в отдельную историю, в текущей оценке необходимо минимум зафиксировать зависимость и границу интеграции.

----
{panel:title=Интеграция с постановкой по HAVING-фильтрации|borderStyle=dashed|borderColor=#0052cc|bgColor=#f0f4ff}
Базовая поддержка Меры в {{HAVING}} должна быть реализована для сценариев, где текущий построитель уже поддерживает HAVING-условия.

Уровень-специфичная HAVING-фильтрация Сводной таблицы через {{apply_mode}}, {{target_dimensions}}, CND и {{depth}} относится к связанной задаче [MB-4304|https://jira.modusbi.ru/browse/MB-4304] и должна оцениваться отдельно, если она ещё не реализована.
{panel}

h3. Открытые вопросы для команды разработки.
* Какими командами объекта {{datasets}} будет оформлено создание/редактирование/удаление Мер: через существующую команду сохранения набора данных или через отдельные команды?
* Backend будет хранить зависимости Мер или рекурсивно проводить поиск зависимых Мер по всем {{name}}-мер найденным в выражении?

h3. Критерии приёмки (AC):
*AC.1* — Чтение и сохранение Мер в произвольном наборе данных.
* *Дано*: существует произвольный набор данных с корректным SQL.
* *Когда*: backend получает запрос на чтение набора данных.
* *Тогда*: в ответе возвращается массив {{measures}} со всеми сохранёнными Мерами, {{status}} и {{status_message}}.
* *И*: при сохранении набора данных backend сохраняет созданные, изменённые и удалённые Меры согласно правилам валидации.

*AC.2* — Ограничение по типу набора данных.
* *Дано*: пользователь пытается сохранить Меру в простом или составном наборе данных.
* *Тогда*: backend отклоняет операцию контролируемой ошибкой.
* *И*: существующее поведение простых и составных наборов данных не меняется.

*AC.3* — Контракт внешней ссылки по {{name}}.
* *Дано*: Мера сохранена в {{measures[]}} с {{id}} и {{name}}.
* *Тогда*: визуализации, другие Меры и вычисляемые поля ссылаются на неё только по {{name}}.
* *И*: {{measures[].id}} не используется как внешний ключ связи.

*AC.4* — Валидация выражения Меры.
* *Дано*: пользователь сохраняет Меру с выражением, где есть ссылки на поля, другие Меры и переменные.
* *Тогда*: backend проверяет существование ссылок, синтаксис, циклы, {{aggregation_kind}} и возможность SQL-исполнения.
* *И*: при контекстной ошибке сохраняет или возвращает {{status = invalid}} и {{status_message}}.

*AC.5* — Циклические зависимости блокируются.
* *Дано*: Мера A ссылается на Меру B, а Мера B прямо или косвенно ссылается на Меру A.
* *Когда*: пользователь сохраняет одну из Мер.
* *Тогда*: backend блокирует сохранение и возвращает ошибку циклической зависимости.

*AC.6* — Ревалидация после изменения SQL набора данных.
* *Дано*: Мера ссылается на поле набора данных.
* *Когда*: SQL набора данных изменён так, что поле исчезло.
* *Тогда*: backend переводит Меру в {{invalid}} и заполняет {{status_message}}.
* *И*: зависящие от неё Меры также становятся {{invalid}}.
* *И*: набор данных может быть сохранён с невалидными Мерами.

*AC.7* — Меры не нагружают запрос без использования.
* *Дано*: в наборе данных сохранены Меры.
* *Когда*: визуализация не содержит ссылок на эти Меры.
* *Тогда*: backend строит SQL без раскрытия выражений Мер.
* *И*: результат соответствует текущему поведению визуализации без Мер.

*AC.8* — Runtime payload использует {{type = "measure"}} и {{name}}.
* *Дано*: Мера размещена на полке или выбрана в фильтре визуализации.
* *Тогда*: в payload передаётся {{type = "measure"}} и {{name}} Меры.

*AC.9* — Раскрытие Меры в {{SELECT}}.
* *Дано*: payload {{recordsets}} содержит Меру на полке «Значения».
* *Тогда*: backend загружает выражение Меры из метаданных набора данных, раскрывает вложенные Меры и добавляет выражение в {{SELECT}} с корректным alias.

*AC.10* — Раскрытие Меры в {{WHERE}}.
* *Дано*: payload содержит неагрегированную Меру в фильтре {{WHERE}}.
* *Тогда*: backend раскрывает выражение Меры и добавляет условие в {{WHERE}}.
* *И*: если Мера агрегированная, запрос отклоняется контролируемой ошибкой.

*AC.11* — Мера как вычисляемое измерение.
* *Дано*: payload содержит неагрегированную Меру в группировке.
* *Тогда*: backend добавляет раскрытое выражение в {{SELECT}} и {{GROUP BY}}.
* *И*: агрегированная Мера в группировке отклоняется контролируемой ошибкой.

*AC.12* — Блокировка переименования или удаления используемой Меры.
* *Дано*: Мера используется в визуализации, другой Мере или вычисляемом поле.
* *Когда*: пользователь пытается удалить или переименовать эту Меру.
* *Тогда*: backend блокирует удаление/переименование Меры и возвращает список зависимых объектов.

*AC.13* — Ошибка при использовании невалидной Меры.
* *Дано*: визуализация содержит ссылку на Меру со статусом {{invalid}}.
* *Когда*: запрашиваются данные визуализации.
* *Тогда*: backend не строит некорректный SQL и возвращает контролируемую ошибку с указанием проблемной Меры.

*AC.14* — Импорт/экспорт учитывает Меры.
* *Дано*: экспортируется набор данных или отчёт, где используются Меры.
* *Тогда*: экспорт содержит определения Мер и ссылки на них, если импорт/экспорт включён в релизный объём.
* *И*: после импорта backend восстанавливает Меры и зависимости либо возвращает понятную ошибку о недостающих объектах.

*AC.15* — Обратная совместимость.
* *Дано*: существующий отчёт не содержит Мер.
* *Когда*: backend строит данные визуализации.
* *Тогда*: SQL и результат соответствуют текущему поведению до внедрения Мер.
