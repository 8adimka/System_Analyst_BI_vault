h3. Контекст и цель истории.
Полное описание продуктовой логики приведено в Эпике по Мерам ([https://jira.modusbi.ru/browse/MB-4364]).

Настоящая История реализует *первый шаг frontend-доработок* по внедрению сущности *«Мера»* в аналитическом портале: интерфейс управления Мерами в настройках *произвольного* набора данных.

Мера создаётся один раз на уровне набора данных и далее используется как именованное вычислимое выражение. Ключом внешних ссылок на Меру является её уникальное имя {{name}} в рамках одного набора данных. Стабильный {{id}} хранится в метаданных как технический идентификатор записи, но не используется как ключ связи для внешних ссылок.

В рамках этой Истории рассматриваются фронтенд доработки интерфейса для просмотра, создания, редактирования, удаления и отображения Мер в Наборах данных.

----
h3. Границы истории.
В рамках Истории реализуется:
* секция «Меры» в настройках *произвольного* набора данных;
* переименование существующей секции «Описание полей набора данных» в секцию «Поля»;
* единый скролл страницы настроек набора данных и закрепление верхней области выбора источника/набора;
* табличный список Мер с отображением ключевых атрибутов, статуса и операций;
* модальное окно для создания/редактирования Мер;
* настройка полей Иерархия ({{hierarchy}}) и Уровень ({{level}}) в табличном представлении списка Мер;
* удаление Мер;
* встроенный редактор выражения Меры с доступом к полям набора данных и ранее созданным Мерам;
* frontend-интеграция с backend-контрактами чтения, сохранения, удаления и валидации Мер;
* отображение ошибок backend-валидации, блокировок и причин невалидности;
* корректная работа с жизненным циклом статусов {{valid}}/{{invalid}};
* сохранение обратной совместимости существующего интерфейса наборов данных.

----
h3. Ключевые правила модели.
* *Мера* — именованное SQL-выражение, определённое на уровне *произвольного* набора данных.
* {{alias}} — человекочитаемое название Меры. Пользователь вводит {{alias}} при создании и может изменять его после создания только если Мера не используется в визуализациях, выражениях других Мер или вычисляемых полях. {{alias}} должен быть уникален в рамках одного набора данных.
* {{name}} — системное наименование Меры в рамках одного набора данных. Формируется backend-ом при создании на основании {{alias}} по правилу {{Мера.}} + {{alias}} с приведением результата к формату системного имени: пробелы заменяются на подчёркивания, кириллица допускается, имя формируется в одно слово. При коллизии backend должен вернуть уникальное {{name}}, например с детерминированным числовым суффиксом. {{name}} используется как ключ внешних ссылок и не меняется после создания.
* {{id}} — технический стабильный идентификатор записи Меры. Пользователь его не видит и не редактирует.
* {{status}} и {{status_message}} вычисляются backend-ом и используются только для корректного отображения состояния Меры.
* {{aggregation_kind}} задаётся пользователем явно: {{1}} — агрегированная Мера, {{0}} — неагрегированная Мера. В рамках этой Истории frontend даёт пользователю возможность задать значение, отображает ярлык {{AGR}} для агрегированных Мер и передаёт атрибут в backend без самостоятельного анализа SQL-выражения.
* Поля набора данных в выражении Меры указываются в двойных кавычках: {{"field_name"}}.
* Ссылки на ранее созданные Меры указываются по системному {{name}} в двойных кавычках: {{"Мера.Валовая_прибыль"}}.
* Frontend не должен самостоятельно формировать {{name}} и добавлять префикс {{Мера.}}. Для вставки Меры в редактор используется готовое {{name}}, полученное от backend.
* Фронтенд не должен копировать выражения Мер в другие структуры как источник истины и не должен использовать {{id}} Меры как внешний ключ.

----
h3. Описание текущего поведения.
Сейчас в настройках набора данных отсутствует отдельная сущность «Мера».

Вычисляемые выражения доступны пользователю на уровне конкретной визуализации, поэтому фронтенд не предоставляет необходимого интерфейса для работы с Мерами.

----
h3. Описание целевого поведения.
В настройках *произвольного* набора данных появляется интерфейс управления Мерами.

Пользователь с правами редактирования набора данных должен иметь возможность:
# открыть настройки произвольного набора данных;
# увидеть секцию «Поля» и ниже неё секцию «Меры»;
# просмотреть список сохранённых Мер;
# создать новую Меру через модальное окно;
# редактировать существующую Меру;
# изменить «Иерархию» и «Уровень» Меры в табличном представлении;
# удалить Меру, если бэкенд разрешает удаление;
# увидеть ошибки, блокировки и причины невалидности, возвращённые бэкендом.

Для *простых* и *составных* наборов данных секция «Меры», кнопка «+ Добавить меру» и операции управления Мерами не реализуются.

----
h3. Требования к реализации.

h4. 1. Страница настроек набора данных.
В настройках аналитического портала, во вкладке «Наборы данных», при выборе источника данных и *произвольного* набора данных frontend должен:
* переименовать существующую секцию «Описание полей набора данных» в секцию «Поля»;
* в таблице «Поля» первый столбец переименовывается в «Наименование поля»;
* добавить ниже секции «Поля» новую секцию «Меры»;
* убрать внутренние скроллы таблиц «Поля» и «Меры»;
* использовать единый внешний скролл страницы;
* закрепить верхние строки выбора источника данных и набора данных с кнопками управления при скролле по аналогии с разделом «Отчёты»;
* максимально унифицировать таблицы «Поля» и «Меры» по внешнему виду и поведению.

---
h4. 2. Кнопка «+ Добавить меру».
Кнопка «+ Добавить меру» отображается в секции «Меры» для *произвольного* набора данных.

Кнопка должна быть активной только при одновременном выполнении условий:
# для набора задан SQL-запрос;
# SQL-запрос успешно прошёл проверку;
# frontend получил актуальный состав полей набора данных.

Если хотя бы одно условие не выполнено:
* кнопка находится в состоянии {{disabled}};
* при наведении отображается tooltip: *«Задайте и проверьте SQL-запрос набора данных»*;
* ранее сохранённые Меры не удаляются из интерфейса;
* повторная полноценная валидация ранее сохранённых Мер ожидается после появления корректного SQL-запроса и актуального состава полей.

В активном состоянии кнопка отображается как акцентная синяя кнопка добавления.

---
h4. 3. Табличный список Мер.
Сохранённые Меры отображаются в отдельной секции «Меры» в табличном списке под секцией «Поля».

Колонки таблицы:
|| *Наименование меры* || *Алиас* || *Тип данных* || *Агрегация* || *Выражение* (кратко) || *Иерархия* || *Уровень* || *Операции* ||
| Мера.Валовая_прибыль | Валовая прибыль | <тип> | AGR / — | <первые N символов> | <иерархия> | <порядок> | [иконка редактировать] [иконка удалить] |

Правила отображения:
* в колонке «Наименование меры» отображается системное {{name}};
* в колонке «Алиас» отображается человекочитаемое {{alias}};
* в колонке «Тип данных» отображается {{data_type}};
* в колонке «Агрегация» для {{aggregation_kind = 1}} отображается ярлык {{AGR}}, для {{aggregation_kind = 0}} — прочерк "—";
* в колонке «Выражение» отображаются первые {{N}} символов {{expression}};
* полный текст выражения доступен в tooltip при наведении на ячейку «Выражение»;
* описание Меры {{description}} отображается в tooltip при наведении на строку Меры, кроме ячейки «Выражение»;
* в колонке «Операции» доступны иконки редактирования и удаления;
* копирование Мер в текущей итерации не реализуется;
* пользовательская сортировка по столбцам не реализуется;
* пагинация не реализуется.

Правила группировки:
* если у Меры заполнено поле {{hierarchy}}, Мера отображается в соответствующей display-группе;
* внутри одной группы Меры упорядочиваются по {{level}} по возрастанию, затем по {{alias}};
* Меры без заполненной «Иерархии» отображаются в корневом уровне секции «Меры».

---
h4. 4. Статус Меры в списке.
Frontend должен отображать статус Меры на основании полей {{status}} и {{status_message}}, полученных от backend.

Если {{status = "valid"}}:
* строка Меры отображается в обычном состоянии;
* tooltip ошибки не отображается.

Если {{status = "invalid"}}:
* строка Меры подсвечивается как ошибочная;
* отображается иконка предупреждения;
* tooltip содержит причину невалидности из {{status_message}};
* Мера остаётся доступной для редактирования, чтобы пользователь мог исправить выражение или настройки.

---
h4. 5. Модальное окно создания и редактирования Меры.
При нажатии «+ Добавить меру» или иконки редактирования Меры открывается увеличенное модальное окно.

Заголовок окна:
* «Создание меры» — при создании новой Меры;
* «Редактирование меры» — при редактировании существующей Меры.

Верхняя часть формы имеет двухколоночную компоновку.

*Левый столбец — обязательные поля:*
* *Алиас Меры* ({{alias}}) — обязательное строковое поле. Разрешены только буквы, цифры, пробелы и знак подчёркивания. Значение должно быть уникальным в рамках набора данных.
* *Тип данных* ({{data_type}}) — обязательное поле; доступные значения должны соответствовать значениям, поддержанным backend-ом, например {{number}}, {{string}}, {{date}}, {{datetime}}.
* *Агрегация* ({{aggregation_kind}}) — обязательный переключатель/флаг {{да (1)}} / {{нет (0)}}.

*Правый столбец — необязательные поля:*
* *Описание* ({{description}}) — необязательное строковое поле.

{{Наименование меры}} ({{name}}) при создании вручную не заполняется. Backend формирует {{name}} по правилу {{Мера.}} + {{alias}} с приведением результата к формату системного имени: пробелы заменяются на подчёркивания, кириллица допускается, имя формируется в одно слово. При коллизии backend должен вернуть уникальное {{name}}, например с детерминированным числовым суффиксом. При редактировании существующей Меры {{name}} может отображаться как справочное read-only значение, но не должен быть доступен для изменения.

Frontend должен не позволять ввод символов, отличных от букв, цифр, пробелов и знака подчёркивания, в поле {{Алиас Меры}}. Backend повторно валидирует {{alias}} и его уникальность при сохранении; frontend отображает ошибки backend-а без потери введённых пользователем значений.

При редактировании существующей Меры поле {{Алиас Меры}} доступно для изменения только если Мера не используется в визуализациях, выражениях других Мер или вычисляемых полях. Если Мера используется хотя бы в одном зависимом объекте, frontend должен отобразить поле {{Алиас Меры}} заблокированным. При наведении на заблокированное поле отображается tooltip:
*«Нельзя переименовать Меру, используемую в визуализациях и/или в выражениях. Для переименования Меры необходимо разрешить конфликты:
[Список ссылок на визуализации, меры и вычисляемые поля, где используется переименовываемая Мера]»*

Нижняя часть модального окна:
* содержит встроенный редактор выражения {{expression}};
* занимает максимально доступную высоту модального окна;
* не открывается как отдельное окно ввода выражения.

Поля {{id}}, {{status}}, {{status_message}} пользователем не заполняются и не отображаются в форме.

Поля {{hierarchy}} и {{level}} не отображаются в модальном окне. Они должны отображаться и настраиваться в табличном представлении списка Мер.

Кнопки формы:
* «Сохранить»;
* «Отмена».

---
h4. 6. Редактор выражения Меры.
Редактор выражения встроен в нижнюю часть модального окна и имеет горизонтальную двухпанельную компоновку.

Левая панель:
* начинается на уровне верхней границы редактора кода;
* содержит список полей текущего набора данных;
* содержит список ранее созданных Мер текущего набора данных;
* разделена на две сворачиваемые секции: «Поля» и «Меры»;
* по умолчанию обе секции раскрыты;
* каждая секция может быть свернута и развернута;
* элементы из списка доступны для вставки в редактор через drag-and-drop.

В списке «Поля» отображается {{alias}} поля, если он доступен, иначе {{name}} поля. В списке «Меры» отображается {{alias}} Меры.

Правила вставки:
* поле набора данных вставляется в выражение в двойных кавычках: {{"Имя_поля"}};
* Мера вставляется в выражение по {{name}} Меры в двойных кавычках: {{"Мера.Имя_меры"}};
* ссылки на Меры должны использовать {{name}}, полученное от backend;
* frontend не должен самостоятельно добавлять префикс {{Мера.}} при вставке Меры в редактор.

Центральная область редактора:
* отображает кнопки агрегатных функций над основным полем ввода редактора кода;
* содержит основное поле редактора SQL-выражения;
* поддерживает синтаксис и набор функций, идентичные вычисляемым полям виджета;
* поддерживает автодополнение полей и Мер с поиском по {{alias}} и/или {{name}} по логике {{OR}};
* визуально различает поля набора данных и Меры в автодополнении, например цветом, значком, контрастной иконкой Меры или секцией;
* отображает в списке автодополнения {{alias}}, а после выбора вставляет в редактор системное {{name}} в двойных кавычках;
* подсвечивает системные имена полей и Мер в двойных кавычках;
* отображает синтаксические ошибки на уровне возможностей используемого редактора кода.

---
h4. 7. Настройка «Иерархии» и «Уровня».
Поля {{hierarchy}} и {{level}} являются частью метаданных Меры, но не отображаются в модальном окне создания/редактирования.

Frontend должен обеспечить настройку этих полей в табличном представлении списка Мер:
* {{hierarchy}} — необязательная строка, определяющая display-группу Меры;
* {{level}} — необязательное целое число, определяющее порядок Меры внутри display-группы.

После изменения {{hierarchy}} или {{level}} frontend должен сохранить изменённые значения через backend-контракт обновления Меры или набора данных. После успешного сохранения порядок отображения Мер должен обновиться по правилам группировки.

---
h4. 8. Создание и сохранение Меры.
При создании новой Меры frontend должен:
# открыть модальное окно «Создание меры»;
# собрать значения полей {{alias}}, {{data_type}}, {{aggregation_kind}}, {{description}}, {{expression}};
# выполнить базовую frontend-проверку обязательных полей;
# передать данные в backend по актуальному контракту без пользовательского {{name}};
# отобразить результат сохранения, полученный от backend;
# использовать {{name}}, возвращённое backend-ом, во всех последующих вставках и ссылках;
# обновить список Мер после успешного сохранения.

Если backend возвращает ошибку:
* модальное окно не закрывается;
* пользователь видит текст ошибки рядом с соответствующим полем или в общей области ошибок формы;
* ранее введённые значения не теряются.

Если backend возвращает Меру со статусом {{invalid}}:
* Мера отображается в списке;
* строка Меры сразу получает error-состояние;
* причина невалидности отображается из {{status_message}}.

Ожидаемый результат backend-валидации, который должен быть корректно отображён frontend-ом:
* при создании backend генерирует уникальное {{name}} на основании {{alias}};
* backend проверяет заполненность и допустимость {{alias}}, синтаксис выражения, существование используемых полей текущего набора данных, существование Мер, указанных по {{name}} в двойных кавычках, отсутствие самоссылок и циклических зависимостей, существование используемых глобальных переменных;
* если выражение Меры не содержит ссылок на поля набора данных и использует только глобальные переменные или константы, отсутствие полей набора данных не делает Меру автоматически невалидной;
* если backend возвращает статус {{invalid}}, frontend не должен скрывать или удалять такую Меру, а должен отобразить {{status}} и {{status_message}}.

---
h4. 9. Редактирование Меры.
При редактировании существующей Меры frontend должен:
# открыть модальное окно «Редактирование меры»;
# предзаполнить поля значениями выбранной Меры;
# позволить изменить {{description}}, {{data_type}}, {{aggregation_kind}}, {{expression}};
# позволить изменить {{alias}} только если Мера не используется в визуализациях, выражениях других Мер или вычисляемых полях;
# передать изменения в backend по актуальному контракту;
# обновить список Мер после успешного сохранения.

Если Мера используется хотя бы в одном зависимом объекте, frontend должен заблокировать поле {{alias}} и не позволять пользователю изменить значение. Tooltip заблокированного поля должен содержать сообщение backend-а или сформированное по данным backend-а сообщение со списком зависимостей.

Если пользователь изменяет {{alias}} у Меры без зависимых объектов, frontend должен передать новое значение на backend и после успешного ответа обновить отображение Меры в таблице. Изменение {{alias}} не должно менять {{name}}.

Поле {{name}} существующей Меры не редактируется пользователем и не передаётся frontend-ом как изменяемый пользовательский параметр. Если backend вернул ошибку, связанную с недопустимым изменением {{name}}, frontend должен показать её как ошибку контракта сохранения. Итоговое решение о валидности изменений принимает backend.

---
h4. 10. Удаление Меры.
В колонке «Операции» для каждой Меры доступна иконка удаления.

При нажатии на удаление frontend должен инициировать backend-проверку зависимостей или операцию удаления по актуальному контракту. Строка Меры удаляется из интерфейса только после успешного ответа backend-а на удаление.

Если Мера не используется:
* frontend отображает подтверждение: *«Вы действительно хотите удалить Меру [имя]?»*;
* после подтверждения отправляет запрос на удаление;
* после успешного удаления обновляет список Мер.

Если Мера используется хотя бы в одном зависимом объекте:
* удаление блокируется;
* строка Меры не удаляется из интерфейса;
* frontend отображает сообщение backend-а со списком зависимостей:
*«Нельзя удалить Меру, используемую в визуализациях и/или в выражениях. Для удаления Меры необходимо разрешить конфликты:
[Список ссылок на визуализации, меры и вычисляемые поля, где используется удаляемая Мера]»*

---
h4. 11. Жизненный цикл после изменения SQL набора данных.
При изменении и сохранении SQL-запроса произвольного набора данных backend выполняет ревалидацию Мер.

Frontend должен:
* после успешного сохранения SQL-запроса и получения актуального состава полей обновить список Мер и их статусы - все меры этого Набора данных проходят ревалидацию на backend-е;
* отображать кнопку «+ Добавить меру» в {{disabled}} состоянии, пока SQL-запрос не задан, не проверен или состав полей не получен;
* не удалять ранее сохранённые Меры при очистке SQL-запроса или ошибке проверки SQL;
* не считать Меру невалидной только из-за отсутствия ссылок на поля набора данных, если backend вернул для неё {{status = "valid"}} после проверки выражения с глобальными переменными или константами;
* отображать Меры со статусом {{invalid}} в error-состоянии;
* отображать актуальный {{status}} и {{status_message}} Мер, полученный от backend;
* не блокировать сохранение набора данных только из-за наличия Мер со статусом {{invalid}}, если backend допускает сохранение такого состояния.

---
h4. 12. API-интеграция и клиентская модель.
Frontend должен читать и сохранять Меры как часть метаданных текущего *произвольного* набора данных либо через специализированные backend-команды управления Мерами, если они предоставлены backend-ом.

Затрагиваемый backend-объект: {{datasets}}.

Ожидаемые действия frontend-а по API:
|| Действие frontend || Backend-объект || Команда / контракт ||
| Первичное чтение набора данных и списка Мер | {{datasets}} | {{get}} / {{list}} или эквивалентный контракт чтения текущего набора данных |
| Создание Меры | {{datasets}} | {{update}} метаданных набора данных или специализированная команда создания Меры, предоставленная backend-ом |
| Редактирование Меры | {{datasets}} | {{update}} метаданных набора данных или специализированная команда обновления Меры, предоставленная backend-ом |
| Изменение {{hierarchy}} / {{level}} | {{datasets}} | {{update}} метаданных набора данных или специализированная команда обновления Меры |
| Удаление Меры | {{datasets}} | {{update}} метаданных набора данных или специализированная команда удаления Меры |
| Получение результата валидации и зависимостей | {{datasets}} | Ответ команды сохранения/переименования/удаления или специализированная команда проверки, если она предусмотрена backend-контрактом |

Минимально необходимая логика frontend-интеграции:
* перед изменением Меры frontend должен работать с актуальным состоянием набора данных, полученным через чтение текущего набора;
* при создании, редактировании, изменении {{hierarchy}}/{{level}} и удалении Меры frontend должен использовать актуальный backend-контракт;
* при создании Меры frontend передаёт {{alias}} и остальные пользовательские параметры, но не передаёт {{name}} как пользовательский ввод;
* при открытии редактирования Меры frontend должен использовать данные backend-а о зависимостях или результат специализированной проверки зависимостей, если она предусмотрена backend-контрактом;
* при редактировании Меры frontend может передавать {{alias}} только для Меры без зависимых объектов и остальные изменяемые пользовательские параметры, но не должен изменять {{name}};
* если изменение статуса Меры приводит к ревалидации зависимых Мер или вычисляемых полей на backend-е, frontend должен отобразить итоговые статусы и сообщения, возвращённые backend-ом;
* frontend должен отображать статусы, ошибки и списки зависимостей в том виде, в котором они возвращаются backend-ом;

Ожидаемая структура блока Мер в метаданных:
{code:json}
{
  "measures": [
    {
      "id": "847b1ec3-bbf8-4365-85fb-c4fca2a06e2e",
      "name": "Мера.Валовая_прибыль",
      "alias": "Валовая прибыль",
      "description": "Разница между выручкой и себестоимостью",
      "expression": "SUM(\"revenue\") - SUM(\"cost\")",
      "aggregation_kind": 1,
      "data_type": "number",
      "hierarchy": "Финансовые показатели",
      "level": 10,
      "status": "valid",
      "status_message": ""
    }
  ]
}
{code}

|| Поле || Кто задаёт || Описание ||
| {{id}} | backend | Стабильный технический идентификатор записи Меры. Не отображается и не редактируется пользователем. |
| {{name}} | backend | Системное наименование Меры. Генерируется при создании на основании {{alias}} по правилу {{Мера.}} + {{alias}} с приведением результата к формату системного имени; уникально в рамках одного набора данных и не редактируется пользователем. |
| {{alias}} | пользователь | Человекочитаемое название Меры. Уникально в рамках одного набора данных, отображается в интерфейсе и может изменяться после создания без изменения {{name}} только при отсутствии зависимых объектов. |
| {{description}} | пользователь | Необязательное описание Меры. |
| {{expression}} | пользователь | SQL-выражение Меры. Поля и Меры в выражении указываются по системному {{name}} в двойных кавычках, например {{"report_date"}} и {{"Мера.Валовая_прибыль"}}. |
| {{aggregation_kind}} | пользователь | Признак агрегированности, задаваемый пользователем явно: {{1}} — агрегированная, {{0}} — неагрегированная. |
| {{data_type}} | пользователь | Логический тип результата Меры. |
| {{hierarchy}} | пользователь | Необязательная display-группа Меры. |
| {{level}} | пользователь | Порядок Меры внутри display-группы. |
| {{status}} | backend | Статус {{valid}} или {{invalid}}. |
| {{status_message}} | backend | Причина невалидности или пустая строка для валидной Меры. |

h4. 13. Права доступа.
Frontend должен использовать существующую модель прав на просмотр и редактирование наборов данных.

Новые отдельные права на управление Мерами в рамках этой Истории не вводятся.

Если у пользователя нет прав на редактирование набора данных:
* интерфейс должен соответствовать текущему поведению readonly-режима для наборов данных;
* действия создания, редактирования и удаления Мер не должны быть доступны;
* отображение списка Мер допускается только в рамках прав просмотра набора данных.

----
h3. Обратная совместимость и ограничения.
* Для наборов данных без Мер существующий интерфейс должен продолжить работать без изменения пользовательских сценариев, кроме переименования секции «Описание полей набора данных» в «Поля» в рамках актуального UI.
* Для *простых* и *составных* наборов данных интерфейс Мер не отображается.
* Существующие поля набора данных, вычисляемые поля виджетов, визуализации и отчёты не должны изменять поведение в рамках этой Истории.
* В рамках этого этапа реализации Frontend не добавляет Меры в конструктор визуализаций, боковую панель для размещения на полки, фильтры или для использования в вычисляемых полях.
* Frontend не реализует SQL-генерацию, поиск зависимостей и ревалидацию Мер; эти результаты отображаются на основании ответа backend-а.
* Секреты, подключения и параметры источников данных задачей не затрагиваются, политика работы с ними не изменяется.

h3. Критерии приёмки (AC).
*AC.1* — Секция «Меры» доступна только для произвольного набора данных.
* *Дано:* пользователь открыл настройки *произвольного* набора данных;
* *Тогда:* секция «Описание полей набора данных» отображается как секция «Поля»;
* *И:* ниже секции «Поля» отображается секция «Меры»;
* *И:* для *простого* и *составного* набора данных секция «Меры» и кнопка «+ Добавить меру» не отображаются.

*AC.2* — Единый скролл и закреплённая область.
* *Дано:* пользователь открыл настройки произвольного набора данных с таблицами «Поля» и «Меры»;
* *Когда:* пользователь скроллит страницу;
* *Тогда:* таблицы скроллятся единым внешним скроллом;
* *И:* внутренние скроллы таблиц не используются;
* *И:* верхние строки выбора источника данных и набора данных с кнопками управления остаются закреплёнными.

*AC.3* — Кнопка «+ Добавить меру».
* *Дано:* SQL-запрос набора данных задан, успешно прошёл проверку и состав полей получен;
* *Тогда:* кнопка «+ Добавить меру» активна и отображается как акцентная синяя кнопка.
* *Дано:* SQL-запрос не задан, не прошёл проверку или состав полей не получен;
* *Тогда:* кнопка находится в состоянии {{disabled}};
* *И:* при наведении отображается tooltip *«Задайте и проверьте SQL-запрос набора данных»*.
* *И:* ранее сохранённые Меры остаются в списке и не удаляются автоматически.

*AC.4* — Табличный список Мер.
* *Дано:* у произвольного набора данных есть сохранённые Меры;
* *Тогда:* они отображаются в таблице с колонками «Наименование меры», «Алиас», «Тип данных», «Агрегация», «Выражение (кратко)», «Иерархия», «Уровень», «Операции»;
* *И:* в колонке «Наименование меры» отображается {{name}}, а в колонке «Алиас» отображается {{alias}};
* *И:* в колонке «Агрегация» для {{aggregation_kind = 1}} отображается {{AGR}}, для {{aggregation_kind = 0}} — прочерк;
* *И:* в колонке «Операции» доступны только редактирование и удаление;
* *И:* копирование, пользовательская сортировка по столбцам и пагинация не отображаются.

*AC.5* — Tooltip выражения и описания.
* *Дано:* в таблице отображается Мера с заполненными {{expression}} и {{description}};
* *Когда:* пользователь наводит курсор на ячейку «Выражение»;
* *Тогда:* отображается полный текст выражения.
* *Когда:* пользователь наводит курсор на строку Меры вне ячейки «Выражение»;
* *Тогда:* отображается описание Меры, если оно заполнено.

*AC.6* — Группировка Мер.
* *Дано:* у части Мер заполнены {{hierarchy}} и {{level}};
* *Тогда:* Меры группируются по {{hierarchy}};
* *И:* внутри группы упорядочиваются по {{level}}, затем по {{alias}};
* *И:* Меры без {{hierarchy}} отображаются в корневом уровне секции «Меры».

*AC.7* — Создание Меры.
* *Дано:* пользователь нажал «+ Добавить меру»;
* *Тогда:* открывается увеличенное модальное окно «Создание меры»;
* *И:* в верхней части окна доступны поля {{alias}}, {{data_type}}, {{aggregation_kind}}, {{description}};
* *И:* {{alias}} является обязательным и должен быть уникальным в рамках набора данных;
* *И:* {{name}} не заполняется пользователем, не передаётся как пользовательский ввод и формируется backend-ом по правилу {{Мера.}} + {{alias}} с приведением результата к формату системного имени;
* *И:* в нижней части окна доступен встроенный редактор {{expression}};
* *И:* поля {{id}}, {{status}}, {{status_message}}, {{hierarchy}}, {{level}} в модальном окне не отображаются.

*AC.8* — Редактор выражения.
* *Дано:* пользователь создаёт или редактирует Меру;
* *Тогда:* редактор выражения отображает две панели: слева списки «Поля» и «Меры», справа поле ввода SQL-выражения;
* *И:* секции «Поля» и «Меры» по умолчанию раскрыты и могут сворачиваться;
* *И:* поле вставляется в выражение в формате {{"field_name"}};
* *И:* Мера вставляется в выражение по системному {{name}} в двойных кавычках, например {{"Мера.Валовая_прибыль"}};
* *И:* в списках и автодополнении отображается {{alias}}, а после выбора вставляется {{name}};
* *И:* автодополнение ищет по {{alias}} и/или {{name}} и визуально различает поля и Меры.

*AC.9* — Сохранение Меры.
* *Дано:* пользователь заполнил обязательные поля Меры и нажал «Сохранить»;
* *Когда:* backend успешно сохранил Меру;
* *Тогда:* модальное окно закрывается;
* *И:* список Мер обновляется;
* *И:* созданная или изменённая Мера отображается с актуальными значениями, {{status}} и {{status_message}}.

*AC.10* — Ошибка сохранения Меры.
* *Дано:* backend вернул ошибку при сохранении Меры;
* *Тогда:* модальное окно не закрывается;
* *И:* пользователь видит текст ошибки;
* *И:* ранее введённые значения в форме не теряются.

*AC.11* — Статус {{invalid}}.
* *Дано:* backend вернул Меру со статусом {{invalid}} и заполненным {{status_message}};
* *Тогда:* строка Меры отображается в error-состоянии;
* *И:* отображается иконка предупреждения и tooltip показывает причину невалидности из {{status_message}};

*AC.12* — Настройка «Иерархии» и «Уровня».
* *Дано:* пользователь изменил {{hierarchy}} или {{level}} Меры в табличном представлении;
* *Когда:* изменение успешно сохранено через backend;
* *Тогда:* список Мер обновляется;
* *И:* Мера отображается в группе и порядке, соответствующих новым значениям {{hierarchy}} и {{level}}.

*AC.13* — Блокировка редактирования alias используемой Меры.
* *Дано:* пользователь редактирует Меру, которая используется в зависимых объектах;
* *Когда:* открывается модальное окно «Редактирование меры»;
* *Тогда:* поле {{alias}} отображается заблокированным, а при наведении на поле отображается tooltip со списком зависимых объектов;
* *И:* {{name}} существующей Меры не меняется.

*AC.14* — Удаление Меры.
* *Дано:* Мера используется в зависимых объектах;
* *Когда:* пользователь пытается удалить Меру;
* *Тогда:* удаление блокируется, а frontend отображает подсказку со списком зависимостей;

*AC.15* — Поведение после изменения SQL набора данных.
* *Дано:* пользователь изменил SQL-запрос произвольного набора данных;
* *Когда:* backend сохранил SQL-запрос и вернул актуальные статусы Мер после ревалидации;
* *Тогда:* frontend обновляет список Мер и отображает актуальные {{status}} / {{status_message}}; Меры не удаляются автоматически при ошибке SQL или исчезновении полей;
* *И:* отсутствие ссылок на поля набора данных в выражении Меры само по себе не является основанием для локального перевода Меры в error-состояние на frontend-е;
* *И:* наличие Мер со статусом {{invalid}} не блокирует сохранение набора данных, если backend вернул успешный результат сохранения.

*AC.16* — Границы первого шага.
* *Дано:* пользователь открыл конструктор визуализаций или field picker;
* *Тогда:* в рамках этой Истории frontend не добавляет секцию «Меры» в панель полей конструктора;
* *И:* Меры не размещаются на полках визуализаций;
* *И:* метаданные визуализаций и SQL-запросы визуализаций не изменяются.

*AC.17* — Обратная совместимость.
* *Дано:* пользователь работает с существующим набором данных без Мер;
* *Тогда:* существующие сценарии просмотра и редактирования полей набора данных работают без регрессий;
* *И:* существующие визуализации и вычисляемые поля виджетов не изменяют поведение в рамках этой Истории.
