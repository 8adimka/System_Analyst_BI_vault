### Контекст и цель истории.
Полное описание продуктовой логики приведено в Эпике (https://jira.modusbi.ru/browse/MB-4364).

Настоящая История реализует использование ранее созданных Мер **произвольного** набора данных в конструкторе визуализаций: отображение в панели полей, размещение на полках, использование в совместимых селекторах, хранение ссылок в метаданных визуализации и подстановку выражений Мер во внешний SQL-запрос.

Меры создаются и валидируются в настройках набора данных в предыдущей Истории. В рамках этой Истории Мера рассматривается как готовый объект метаданных набора данных со статусом `valid` или `invalid`.

Ключевое правило: визуализации ссылаются на Меру по полю `name` внутри объекта использования Меры с `type = "measure"`. `id` Меры из `measures[]` не используется как внешний ключ связи в визуализациях.

`alias` Меры используется для отображения пользователю в панели полей, подсказках, полках и селекторах. Изменение `alias` не меняет `name` и не ломает визуализации, так как связь сохраняется по системному `name`.

----
### Границы истории.
В рамках Истории реализуется:
- отображение секции «Меры» в панели полей конструктора визуализаций;
- display-группировка Мер по «Иерархии» и «Уровню»;
- визуальное отличие Мер от обычных полей;
- поведение Мер со статусом `invalid` в конструкторе;
- drag-and-drop Мер на поддерживаемые полки визуализации;
- поддержка Мер в совместимых селекторах полей текущей визуализации;
- настройка фильтра по Мере с типом `WHERE` или `HAVING`;
- матрица допустимости Мер по полкам;
- использование Мер в выражениях вычисляемых полей виджета;
- хранение размещения Меры в метаданных визуализации по `type = "measure"`, `name` и `datasetId`;
- подстановка выражений Мер во внешний запрос визуализации;
- сохранение обратной совместимости для визуализаций без Мер.

В рамках Истории **не реализуется**:
- создание и редактирование Мер в настройках набора данных;
- ручное изменение `aggregation_kind` на полке визуализации;
  - поддержка Мер для **простых** и **составных* наборов данных;
- уровень-специфичная HAVING-фильтрация для Сводной таблицы как отдельное расширение логики, описанное в постановке https://jira.modusbi.ru/browse/MB-4304.

### Исходная модель Меры.
Мера хранится в JSON-метаданных набора данных. Поле `name` является уникальным в рамках одного набора данных и используется как ключ связи. Поле `alias` является человекочитаемым названием Меры и используется для отображения.

```json

{
  "measures": [
    {
      "id": "847b1ec3-bbf8-4365-85fb-c4fca2a06e2e",
      "name": "Мера.Валовая_прибыль",
      "alias": "Валовая прибыль",
      "description": "Разница между выручкой и себестоимостью",
      "expression": "SUM(\"revenue\") - SUM(\"cost\")",
      "aggregation_kind": 1,
      "data_type": "number",
      "hierarchy": "Финансовые показатели",
      "level": 10,
      "status": "valid",
      "status_message": ""
    }
  ]
}

```

| Поле | Тип | Описание |
|---|---|---|
| `id` | string | Стабильный `UUID` идентификатор записи; не используется как ключ связи во внешних ссылках |
| `name` | string | Системное наименование Меры; формируется backend-ом при создании, уникально в рамках набора данных, не меняется после создания и является ключом связи во внешних ссылках |
| `alias` | string | Человекочитаемое название Меры; отображается пользователю и может изменяться без изменения `name` |
| `description` | string | Необязательное описание |
| `expression` | string | SQL-выражение; поля и другие Меры указываются по системному `name` в двойных кавычках, например `"report_date"` и `"Мера.Валовая_прибыль"` |
| `aggregation_kind` | int (0/1) | Признак агрегированности; задаётся пользователем явно. backend проверяет фактическое выражение Меры и возвращает ошибку валидации при противоречии между пользовательским флагом и выражением |
| `data_type` | enum | Логический тип результата из точного списка: `string`, `number`, `integer`, `date`, `datetime` |
| `hierarchy` | string | Необязательная группа/иерархия отображения |
| `level` | int | Порядок Меры внутри иерархии |
| `status` | enum | `valid` или `invalid` |
| `status_message` | string | Причина невалидности; для валидной Меры пустая строка |

### Метаданные визуализации.
Во всех метаданных визуализации связь с Мерой хранится по полю `name` внутри объекта использования Меры. Для различения Меры с обычным полем обязательно хранится `type = "measure"`.

Если в объекте использования Меры есть поле `id`, оно является локальным идентификатором размещения/настройки в визуализации и не является `id` Меры из `measures[]`.

Каждое использование Меры в визуализации хранит:
- тип сущности `type = "measure"`;
- ссылку на Меру по `name`;
- `datasetId` набора данных, к которому относится Мера;
- дополнительные параметры в зависимости от конкретной полки и сценария.

В объект использования Меры в визуализации не копируются поля определения Меры: `expression`, `description`, `aggregation_kind`, `data_type`, `hierarchy`, `level`, `status`, `status_message`. Эти данные читаются из метаданных набора данных.

Пример размещения Меры на полке визуализации:
```json

{
  "values": [
    {
      "id": "visual_measure_4f9b7e2d",
      "type": "measure",
      "name": "Мера.Валовая_прибыль",
      "datasetId": 244
    }
  ]
}

```

#### Два слоя фильтра по Мере: метаданные визуализации и runtime-payload.
Условие фильтра по Мере живёт на двух разных уровнях, и их нельзя смешивать. Оба уровня используют один и тот же контракт условия — `values`/`operators`/`not`/`logicOr` (с элементом `null` в `values` для проверки на пустоту), тот же, что и у фильтра по обычному полю. Отдельной структуры `condition{operator, value, value_type}` для Меры нет; поля `value_type` в контракте нет — тип значения берётся из `data_type` Меры в метаданных набора.

**(а) Метаданные визуализации** — как фильтр хранится в конфигурации виджета. Здесь сохраняется объект использования Меры с вложенным объектом `filter`, в котором пользователь выбрал тип отбора (`mode = "WHERE"` или `mode = "HAVING"`) и задал условие в форме `values`/`operators`/`not`/`logicOr`. `mode` — это UI-выбор SQL-блока, в который условие будет сериализовано при запросе.

**(б) Runtime-payload запроса** — что фронт отправляет на `/v1/api/recordsets` при выполнении запроса. Вложенного объекта `filter` здесь уже нет: по `mode` из метаданных фронт раскладывает условие в соответствующий SQL-блок запроса — `where[]` для `WHERE`, `having` для `HAVING`. Элемент условия в обоих блоках описан тем же контрактом `values`/`operators`/`not`/`logicOr` (с элементом `null` в `values`), что и фильтр обычного поля, — без `value_type`.

Пример фильтра по Мере в метаданных визуализации — слой «а»:
```json

{
  "filters": [
    {
      "id": "filter_measure_6d3c3e58",
      "type": "measure",
      "name": "Мера.Валовая_прибыль",
      "datasetId": 244,
      "filter": {
        "mode": "HAVING",
        "values": [0],
        "operators": [">"],
        "not": false,
        "logicOr": 0
      }
    }
  ]
}

```

Тот же фильтр в runtime-payload запроса — слой «б». Агрегированная Мера (`mode = "HAVING"`) раскладывается frontend-ом в каноническую форму `having.items[]`, условие описано теми же `values`/`operators`:
```json

{
  "having": {
    "condition": "",
    "items": [
      {
        "type": "measure",
        "name": "Мера.Валовая_прибыль",
        "datasetId": 244,
        "values": [0],
        "operators": [">"]
      }
    ]
  }
}

```

Неагрегированная Мера (`mode = "WHERE"`) раскладывается в блок `where` тем же контрактом, с сохранением поля `lvl` (уровень), как в текущем where-контракте обычного поля:
```json

{
  "where": [
    {
      "type": "measure",
      "name": "Мера.Маржа",
      "datasetId": 244,
      "values": [0],
      "operators": [">"],
      "lvl": 0
    }
  ]
}

```

Backend принимает три входные формы блока `having`, но frontend использует один канонический выход:
- `"having": {"condition": "<строка SQL>", "items": [ {элемент Меры}, ... ]}` — каноническая форма frontend-а, когда в запросе могут одновременно присутствовать условия по обычным / вычисляемым полям и по Мерам;
- `"having": {"condition": "<строка SQL>"}` — текущая и единственная форма HAVING для обычных и вычисляемых полей, когда Мер в HAVING нет;
- `"having": [ {элемент Меры}, ... ]` — дополнительная форма только для Мер, которую backend принимает для совместимости, но frontend не формирует.

`having.condition` верхнего уровня — текущая строковая форма SQL-условия для обычных и вычисляемых полей, которую собирает frontend. Она не является структурой условия Меры и не заменяется поддержкой Мер. Элементы фильтров по Мерам лежат в `having.items[]`, не содержат собственного поля `condition` и описывают предикат через `values`/`operators`. При совместном наличии `condition` и `items` обе части объединяются через `AND`.

Поля объекта использования Меры-фильтра:

| Поле | Тип | Описание |
|---|---|---|
| `id` | string | Локальный идентификатор размещения/настройки в визуализации; не является `id` Меры из `measures[]` |
| `type` | string | `"measure"` — отличает Меру от обычного поля и вычисляемого поля |
| `name` | string | Системное имя Меры; является ключом связи |
| `datasetId` | int/string | Идентификатор набора данных, к которому относится Мера; при наличии сверяется с набором |
| `filter.mode` | string | `WHERE` или `HAVING`; UI-выбор блока сериализации (`WHERE` → `where[]`, `HAVING` → `having`) |
| `filter.values` | array | Обязательный непустой список значений условия; элемент `null` задаёт проверку на пустое значение и разрешён только при пустом `operators` |
| `filter.operators` | array | Список операторов, параллельный `values`. Пуст → `values` трактуется как список (`IN`/`NOT IN`); если не пуст, в `values` не должно быть `null`, а длина должна точно совпадать с длиной `values`. Иное соотношение и `null` вместе с операторами — контролируемая ошибка |
| `filter.not` | bool | Отрицание всего условия: `NOT IN` для списка без `null`; для списка с `null` отрицание `(IN (…) OR IS NULL)` даёт `NOT IN (…) AND IS NOT NULL` |
| `filter.logicOr` | int (0/1) | `1` — условия внутри элемента объединяются через `OR`; иначе через `AND` |

Допустимые операторы условия по Мере: `=`, `!=`, `<>`, `>`, `>=`, `<`, `<=`, `like_left`, `like_right`, `like_both`, `likeic_left`, `likeic_right`, `likeic_both`. Отдельных ключей `in` и `between` нет: `in` выражается списком `values` без `operators`, `between` — парой операторов `>=`/`<=`.

Like-операторы работают так же, как в текущем фильтре обычного поля:
- `like_left` — заканчивается на подстроку;
- `like_right` — начинается с подстроки;
- `like_both` — содержит подстроку;
- `likeic_*` — соответствующий поиск без учёта регистра.

Значение при `like_*` / `likeic_*` является искомой подстрокой и не проверяется backend-ом по `data_type` Меры. Для остальных операторов значение проверяется по типу Меры.

Матрица `null`:
- `[null]` → `IS NULL`;
- `[null]` + `not: true` → `IS NOT NULL`;
- `[10,null]` → `IN (10) OR IS NULL`;
- `[10,null]` + `not: true` → `NOT IN (10) AND IS NOT NULL`;
- любое сочетание `null` с непустым `operators` не должно формироваться frontend-ом и отклоняется backend-ом.

Для HAVING-фильтра Сводной таблицы структура метаданных должна быть совместима с расширением, описанным в постановке https://jira.modusbi.ru/browse/MB-4304:
```json

{
  "filters": [
    {
      "id": "filter_measure_6d3c3e58",
      "type": "measure",
      "name": "Мера.Валовая_прибыль",
      "datasetId": 244,
      "filter": {
        "mode": "HAVING",
        "values": [0],
        "operators": [">"],
        "apply_mode": "selected",
        "target_dimensions": ["col_month"]
      }
    }
  ]
}

```

`filter.apply_mode` и `filter.target_dimensions` используются только для уровня-специфичной HAVING-фильтрации Сводной таблицы и не являются обязательной частью базового сценария этой Истории.

### Отображение Мер в конструкторе визуализаций.
#### Боковая панель полей.
При выборе **произвольного** набора данных боковая панель конструктора разделена на секции:
  - **«Поля»* — обычные поля и вычисляемые поля виджета;
  - **«Меры»* — Меры набора данных.

Секция «Меры» располагается ниже секции «Поля».

В секции «Поля» отображается `alias` поля, если он доступен, иначе `name` поля.

В секции «Меры» отображается `alias` Меры. Системное `name` может отображаться в tooltip как справочная техническая информация.

#### Визуальное представление Меры.
Мера отображается как отдельный тип элемента на полках визуализаций:
  - цвет иконки или пилюли Меры на полках, кроме полки «Фильтры», — **тёмно-оранжевый*;
  - на полке «Фильтры» Мера отображается в виде пилюли **салатового* цвета, аналогично другим фильтрам, но сохраняет признак типа «Мера»:
      - для Мер с `aggregation_kind = 1` отображается ярлык `AGR`;
      - для Мер с `aggregation_kind = 0` ярлык `AGR` не отображается;
- на полках визуализации Мера отображается по `alias`;
- tooltip при наведении содержит описание, если оно заполнено, тип данных, полный текст выражения и `name` Меры как справочную техническую информацию.

Ярлык `AGR` отображается только для Мер с `aggregation_kind = 1`:
- в списке Мер набора данных;
- в боковой панели конструктора;
- на пилюлях полок.

Изменить `aggregation_kind` непосредственно на полке нельзя. Атрибут меняется только при редактировании Меры в наборе данных. backend проверяет соответствие выбранного значения фактическому выражению Меры.

#### Группировка и порядок.
Если заполнена «Иерархия», Мера показывается в соответствующей display-группе внутри секции «Меры».

Порядок вывода внутри группы:
1. по `level` по возрастанию;
1. затем по `alias` (по алфавиту).

Если «Иерархия» не заполнена, Мера отображается в корневом уровне секции «Меры» по `alias` (по алфавиту).

В боковой панели, внутри секции «Меры», сначала отображаются сгруппированные Меры, а потом (в корневом уровне секции «Меры») отображаются Меры без группировки.

#### Статус `invalid` в конструкторе.
Если Мера имеет статус `invalid`:
- она отображается как ошибочная (красный ореол, иконка ⚠);
- tooltip показывает причину недоступности;
- Меру нельзя добавить на полки или выбрать в совместимом селекторе;
- если Мера уже была использована в визуализации ранее, привязка по `name` сохраняется;
- соответствующая пилюля отображается в error-состоянии (красный ореол, иконка ⚠);
- запрос данных блокируется с понятным сообщением до исправления Меры или удаления её из визуализации.

### Drag-and-drop и совместимые селекторы.
Мера перетаскивается на полки так же, как обычное поле. Одна и та же Мера может быть размещена на нескольких полках одновременно, если это не нарушает матрицу допустимости.

При попытке разместить Меру на несовместимую полку:
- действие блокируется;
- курсор показывает состояние запрета;
- пользователь видит пояснение из матрицы допустимости.

Меры должны поддерживаться не только на основных полках визуализации, но и во всех элементах интерфейса, где пользователь может выбрыть вычисляемые поля.

К таким элементам могут относится:
- настройки визуализации и пилюль на полках визуализации;
- другие выпадающие списки и selector-компоненты, работающие с вычисляемыми полями.

Если конкретный selector технически или продуктово не поддерживает Меры на данном этапе, это ограничение должно быть явно зафиксировано в документации реализации и не должно выглядеть для пользователя как случайная потеря элемента.

### Меры в вычисляемых полях виджета.
В редакторе вычисляемых полей виджета Меры текущего набора данных доступны для вставки в выражение, если бизнес-сценарий вычисляемого поля допускает использование Мер.

Правила:
- поля набора данных вставляются в двойных кавычках: `"field_name"`;
- Меры вставляются по системному `name` в двойных кавычках: `"Мера.Валовая_прибыль"`;
- в списках и автодополнении отображается `alias`, а после выбора в выражение вставляется `name`;
- автодополнение ищет поля и Меры по `alias` и/или `name` по логике `OR` и визуально различает поля и Меры;
- вычисляемое поле, использующее Меру, создаёт зависимость от `name` Меры;
- изменение `alias` такой Меры не блокируется, так как зависимость хранится по `name`;
- удаление такой Меры блокируется до ручного устранения зависимости;
- если Мера получает статус `invalid`, зависящие от неё вычисляемые поля или другие Меры проходят ревалидацию и также переходят в ошибочное состояние, если его выражение больше не может быть корректно выполнено.

### Полка «Фильтры».
При размещении Меры на полке «Фильтры» открывается стандартная настройка фильтра, адаптированная для Меры.

Форма фильтра по Мере содержит:
- тип отбора: `WHERE` или `HAVING`;
- условие фильтрации;
- дополнительные параметры, если они применимы для данного типа визуализации, как при использовании обычного поля.

Правила:
- при типе `WHERE` фильтрация применяется до `GROUP BY`;
- при типе `WHERE` механизм `target_dimensions` / CND не применяется;
- при типе `HAVING` фильтрация применяется после `GROUP BY`;
- для обычных поддерживаемых визуализаций используется базовая логика `HAVING`;
- уровень-специфичная логика `HAVING` для Сводной таблицы, включая `apply_mode`, `target_dimensions`, CND и `depth`, относится к связанной постановке https://jira.modusbi.ru/browse/MB-4304.

----
### Матрица допустимости Мер по полкам.
Валидация допустимости выполняется в двух точках:
- в интерфейсе при попытке разместить Меру на полку или выбрать её в совместимом селекторе;
- на бэкенде при генерации SQL перед выполнением запроса.

На данном этапе UX-валидация опирается на значение `aggregation_kind`, заданное пользователем в настройках Меры. Финальная SQL-валидация выполняется на бэкенде. Если фактическое выражение Меры не соответствует выбранному `aggregation_kind` или нарушает SQL-семантику итогового запроса, запрос отклоняется с понятной ошибкой.

| **Полка** | **Допустимый тип Меры** | **Блокировать при нарушении?** | **Сообщение** |
|---|---|---|---|
| **Значения** | Любая | Нет блокировки; предупреждение при `aggregation_kind = 0` | **«Выражение помечено как неагрегированное. Для корректного отображения рекомендуется использовать агрегатную функцию, например: SUM(...)»** |
| **Фильтры (HAVING)** | Только агрегированная (`aggregation_kind = 1`) | Да | **«Мера помечена как неагрегированная. Выберите тип отбора WHERE или измените агрегатность в настройках Меры»** |
| **Фильтры (WHERE)** | Только неагрегированная (`aggregation_kind = 0`) | Да | **«Мера помечена как агрегированная. Выберите тип отбора HAVING или измените агрегатность в настройках Меры»** |
| **Строки / Столбцы** | Только неагрегированная (`aggregation_kind = 0`) | Да | **«На полках "Строки" и "Столбцы" допустимы только неагрегированные Меры»** |
| **Детализация** | Только неагрегированная (`aggregation_kind = 0`) | Да | **«На полке "Детализация" допустимы только неагрегированные Меры»** |
| **Дополнительные** | Любая | Нет блокировки | - |

### Логика построения SQL.
#### Общий принцип.
Построитель запросов формирует внешний запрос визуализации поверх базового слоя. Оригинальный SQL **произвольного** набора данных используется как внутренний источник без изменения.

Базовый слой может быть реализован через derived table:
```sql

FROM (
  /* dataset_sql */
) AS __base

```

Или через CTE:
```sql

WITH __base AS (
  /* dataset_sql */
)
SELECT ...
FROM __base

```

Продуктовым требованием является корректная подстановка выражений Мер в итоговые SQL-клаузы внешнего запроса, а не конкретная синтаксическая форма базового слоя.

#### Разрешение выражений Мер.
Перед подстановкой выражение Меры приводится к SQL итогового запроса:
- ссылки на поля вида `"field_name"` разрешаются как обращения к полям базового слоя;
- ссылки на другие Меры вида `"Мера.Валовая_прибыль"` рекурсивно заменяются выражениями соответствующих Мер;
- самоссылки и циклы не допускаются и должны быть отсеяны валидацией Мер;
- переменные внутри выражений Мер в текущем шаге не поддерживаются; такая Мера должна приводить к контролируемой ошибке backend-а;
- для каждой Меры в `SELECT` формируется технический SQL-alias по правилам построителя; этот alias не является свойством Меры и не хранится в объекте использования Меры в визуализации.

#### Правила подстановки по SQL-клаузам.
В `SELECT` попадают:
- обычные поля с полок «Строки», «Столбцы», «Детализация»;
- неагрегированные Меры с полок «Строки», «Столбцы», «Детализация»;
- Меры с полки «Значения».

В `WHERE` попадают:
- обычные фильтры, применимые до группировки;
- Меры с полки «Фильтры», где `filter.mode = "WHERE"`.

В `GROUP BY` попадают:
- обычные поля с полок «Строки», «Столбцы», «Детализация»;
- неагрегированные Меры с полок «Строки», «Столбцы», «Детализация»;
- неагрегированная Мера с полки «Значения», если итоговый запрос строится на агрегированном уровне.

В `HAVING` попадают:
- Меры с полки «Фильтры», где `filter.mode = "HAVING"`.

Несколько условий внутри одной клаузы объединяются через `AND`.

#### Сериализация условия фильтра по Мере.
Условие фильтра по Мере — и в блоке `where`, и в элементе блока `having` — сериализуется тем же контрактом `values`/`operators`/`not`/`logicOr` (с элементом `null` в `values` для проверки на пустоту), что и фильтр по обычному полю. Фронт переиспользует существующий сериализатор фильтра обычного поля; отдельный транспорт или отдельный формат условия для Мер не вводится.

Фронт при этом:
- **НЕ формирует `value_type`** — тип значения определяется бэкендом по `data_type` Меры в метаданных набора данных;
- **НЕ присылает выражение Меры** — поля `calc`/`aggr` для Меры запрещены; выражение раскрывается бэкендом только из метаданных набора (`measures[].expression`).

Элемент фильтра по Мере в любом блоке несёт: `type = "measure"`, `name` (ключ связи), `datasetId` (при наличии сверяется с набором) и условие в форме `values`/`operators`/`not`/`logicOr`; в блоке `where` дополнительно сохраняется поле `lvl` (уровень), как в текущем where-контракте обычного поля.

Отличие фильтра по Мере от фильтра по обычному полю — только в политике ошибок. Для обычного поля нераспознанное условие молча отбрасывается (fail-open ради обратной совместимости). Для Меры любой дефект контракта — контролируемая ошибка (fail-closed): `values` отсутствует или пуст; `null` передан вместе с непустым `operators`; рассогласование длин `values`/`operators`; оператор вне allowlist; значение обычного сравнения не по типу Меры; пустой / неизвестный `data_type`; Мера не найдена, имеет статус, отличный от `valid`, или не того `aggregation_kind`. Значение при `like_*` / `likeic_*` является подстрокой и составляет исключение из проверки по `data_type`.

#### Передача условия в `HAVING`.
Агрегированную Меру (`aggregation_kind = 1`), помеченную в UI типом отбора `HAVING`, frontend сериализует только в канонический массив `having.items[]` внутри объекта `having`, а **не** в `where` и не в прямой массив `having[]`. Поле `having.condition` при этом сохраняет строковое условие обычных / вычисляемых полей и может быть пустой строкой. Условие Меры в `items[]` frontend формирует в том же контракте `values`/`operators`, что и для `where`.

#### Поведение Меры в зависимости от полки.
##### Полка «Значения».
Выражение Меры подставляется в `SELECT`.

Если Мера неагрегированная, размещение не блокируется, но пользователь получает предупреждение. Если итоговый запрос содержит агрегированные выражения, неагрегированная Мера также добавляется в `GROUP BY`.

##### Полка «Фильтры», тип `WHERE`.
Допустимы только неагрегированные Меры (`aggregation_kind = 0`).

Выражение Меры подставляется в `WHERE`. Фильтрация происходит до `GROUP BY`, то есть на уровне отдельных строк базового источника.

##### Полка «Фильтры», тип `HAVING`.
Допустимы только агрегированные Меры (`aggregation_kind = 1`).

Выражение Меры подставляется в `HAVING`. Фильтрация происходит после `GROUP BY`, то есть на уровне агрегированных групп.

##### Полки «Строки» и «Столбцы».
Допустимы только неагрегированные Меры (`aggregation_kind = 0`).

Выражение Меры попадает одновременно в `SELECT` и `GROUP BY`, создавая вычисляемое измерение.

##### Полка «Детализация».
Допустимы только неагрегированные Меры (`aggregation_kind = 0`).

Выражение Меры попадает одновременно в `SELECT` и `GROUP BY`, расширяя уровень детализации результата.

##### Полка «Дополнительные».
Допустима любая Мера, блокировка по `aggregation_kind` не выполняется.

В рамках базовой логики этой Истории Мера с полки «Дополнительные» не инжектируется в SQL-запрос, если для конкретной визуализации не предусмотрена отдельная документированная логика использования этой полки.

##### Несколько Мер на одной полке.
Несколько Мер на полке «Значения» становятся отдельными колонками в `SELECT`.

Несколько Мер на полке «Фильтры» объединяются по типу:
- все условия с `filter.mode = "WHERE"` попадают в `WHERE` и объединяются через `AND`;
- все условия с `filter.mode = "HAVING"` попадают в `HAVING` и объединяются через `AND`.

Одновременное наличие WHERE-Мер и HAVING-Мер на полке «Фильтры» допустимо: они попадают в разные SQL-клаузы независимо.

### Устойчивость к изменениям метаданных.
#### Редактирование alias используемой Меры.
Так как визуализация хранит ссылку по `type = "measure"` и `name`, изменение `alias` Меры, используемой в визуализации, другой Мере или вычисляемом поле, не должно блокироваться.

После изменения `alias` визуализации и вычисляемые выражения продолжают ссылаться на прежнее `name`, а интерфейс отображает актуальный `alias` из метаданных набора данных.

`name` Меры не меняется после создания. Изменение системного `name` существующей Меры не является пользовательским сценарием этой доработки.

#### Удаление используемой Меры.
Удаление Меры, используемой хотя бы в одной визуализации, другой Мере или вычисляемом поле, аналогично блокируется с понятным сообщением.

При попытке удаления используется сообщение:
*«Нельзя удалить Меру, используемую в визуализациях и/или в выражениях. Для удаления Меры необходимо разрешить конфликты:
Список ссылок на визуализации, меры и вычисляемые поля, где используется удаляемая Мера»*

#### Изменение выражения Меры.
Если пользователь изменил выражение Меры, визуализации, использующие эту Меру, сохраняют связь по `name`. При следующем запросе данных они используют обновлённое выражение Меры.

Если после изменения выражения Мера получает статус `invalid`, визуализации, использующие её, переходят в error-состояние до исправления Меры или удаления её из визуализации.

#### Изменение SQL набора данных.
При изменении SQL-запроса набора данных система перевалидирует Меры. Если Мера становится `invalid`, она:
- остаётся в метаданных набора данных;
- отображается как ошибочная в конструкторе;
- недоступна для нового добавления на полки;
- блокирует выполнение запроса в визуализациях, где уже используется.

----
### Обратная совместимость.
Если в визуализации не используются Меры:
- построитель формирует запрос тем же способом, что и в текущей системе;
- существующие визуализации продолжают работать без изменения поведения;
- существующие вычисляемые поля виджетов не изменяются;
- миграция существующих метаданных визуализаций не требуется.

----
**Интеграция с постановкой по HAVING-фильтрации**
Поддержка Мер в режиме фильтрации `HAVING` для обычных визуализаций описывается в этой Истории как базовое поведение.

Уровень-специфичная HAVING-фильтрация для Сводной таблицы, включая `apply_mode`, `target_dimensions`, CND и `depth`, является отдельным расширением и описывается в связанной истории https://jira.modusbi.ru/browse/MB-4304.

Метаданные фильтра-Меры должны быть совместимы с этим расширением за счёт использования `type = "measure"`, `name` и вложенного объекта `filter`.

Для выполнения runtime-запросов с Мерами на целевом окружении должен быть включён новый построитель: `server.use_new_builder = enabled`. Frontend не должен пытаться обходить контролируемый отказ backend-а при выключенной настройке.

### Критерии приёмки.
**AC.1** — Секция «Меры» в панели полей.
  - **Дано**: аналитик строит визуализацию на основе **произвольного* набора данных, в котором есть Меры.
  - **Тогда*: в панели полей отображается отдельная секция «Меры».
  - **И*: в секции «Меры» отображается `alias` Меры, а не системное `name`.
  - **И*: Меры визуально отличаются от обычных полей.

**AC.2** — Tooltip, ярлык `AGR` и display-группы.
- Для агрегированных Мер отображается ярлык `AGR`.
- Tooltip содержит описание, тип данных, полный текст выражения и `name` Меры как справочную техническую информацию.
- Если заполнены «Иерархия» и «Уровень», Меры группируются и сортируются по этим полям.

**AC.3** — Статус `invalid` в конструкторе.
  - **Дано*: Мера имеет статус `invalid`.
  - **Тогда*: она отображается с предупреждающей иконкой, недоступна для нового добавления на полки и показывает причину ошибки.
  - **И*: если визуализация уже ссылается на такую Меру, пилюля отображается в error-состоянии, а запрос данных блокируется с понятным сообщением.

**AC.4** — Меры в совместимых селекторах.
- Меры доступны не только для drag-and-drop на полки, но и во всех совместимых selector-компонентах текущей визуализации.
- Неподдержанные селекторы явно зафиксированы как ограничение данного этапа.

**AC.5** — Меры в вычисляемых полях виджета.
  - **Дано*: пользователь редактирует вычисляемое поле виджета для визуализации на основе набора данных с Мерами.
  - **Тогда*: валидные Меры доступны для вставки в выражение по системному имени в двойных кавычках, например `"Мера.Валовая_прибыль"`.
  - **И*: вычисляемое поле сохраняет зависимость от `name` Меры.
  - **И*: изменение `alias` используемой Меры не ломает зависимость.
  - **И*: удаление используемой Меры блокируется до устранения зависимости.

**AC.6** — Метаданные визуализации используют `type = "measure"` и `name`.
  - **Дано*: Мера размещена на полке или выбрана в настройке визуализации.
  - **Тогда*: в метаданных визуализации сохраняется `type = "measure"`, `name` и `datasetId`.
  - **И*: `id` Меры из `measures[]` не используется как ключ связи.
  - **И*: поля определения Меры, включая `expression`, `aggregation_kind`, `status` и `status_message`, не копируются в объект использования Меры в визуализации.

**AC.7** — Полка «Значения».
  - **Дано*: Мера `SUM("revenue") - SUM("cost")` находится на полке «Значения», а поле `month` — на полке «Строки».
  - **Тогда*: итоговый внешний SQL содержит выражение Меры в `SELECT`.
  - **И*: группировка строится по текущим правилам построителя запросов.
  - **И*: для неагрегированной Меры пользователь получает предупреждение о возможном изменении уровня детализации.

**AC.8** — Полка «Фильтры», тип `WHERE`.
  - **Дано*: неагрегированная Мера (`aggregation_kind = 0`) размещена на полке «Фильтры» с типом `WHERE`, условие задано в форме `values`/`operators` (без `value_type`).
  - **Тогда*: фронт сериализует условие в блок `where` элементом `{"type":"measure","name":…,"datasetId":…,"values":[…],"operators":[…]}`, и итоговый внешний SQL содержит выражение Меры в `WHERE`.
  - **И*: для обычного сравнения тип значения проверяется бэкендом по `data_type` Меры; выражение Меры (`calc`/`aggr`) и `value_type` фронт не присылает.
  - **И*: frontend сохраняет операторы `like_*` / `likeic_*`, сформированные общим редактором фильтра, и не сочетает `null` с непустым `operators`.
  - **И*: попытка выбрать `WHERE` для агрегированной Меры блокируется.

**AC.9** — Полка «Фильтры», тип `HAVING`.
  - **Дано*: агрегированная Мера (`aggregation_kind = 1`) размещена на полке «Фильтры» с типом `HAVING`, условие задано в форме `values`/`operators` (без `value_type`).
  - **Тогда*: frontend сериализует условие только в `having.items[]` канонического объекта `{"having":{"condition":"…","items":[…]}}`, а не в `where` и не в прямой массив `having[]`.
  - **И*: текущее строковое условие обычных / вычисляемых полей сохраняется в `having.condition`; backend объединяет `condition` и `items` через `AND`.
  - **И*: для обычного сравнения тип значения проверяется бэкендом по `data_type` Меры; выражение Меры (`calc`/`aggr`) и `value_type` фронт не присылает.
  - **И*: попытка выбрать `HAVING` для неагрегированной Меры блокируется.

**AC.10** — Полки «Строки», «Столбцы», «Детализация».
  - **Дано*: агрегированная Мера перетаскивается на полку «Строки», «Столбцы» или «Детализация».
  - **Тогда*: размещение блокируется и пользователь получает сообщение из матрицы допустимости.
  - **И*: неагрегированная Мера, размещённая на этих полках, попадает в `SELECT` и `GROUP BY`.

**AC.11** — Полка «Дополнительные».
  - **Дано*: Мера размещена на полке «Дополнительные».
  - **Тогда*: размещение не блокируется независимо от `aggregation_kind`.
  - **И*: в рамках базовой логики этой Истории выражение Меры не инжектируется в SQL-запрос, если для конкретной визуализации не предусмотрена отдельная документированная логика этой полки.

**AC.12** — Несколько Мер на одной полке.
  - **Дано*: на полке «Значения» находятся две Меры.
  - **Тогда*: обе Меры становятся отдельными колонками в `SELECT`.
  - **И*: несколько фильтров по Мерам объединяются через `AND` внутри своих SQL-клауз.

**AC.13** — Редактирование alias используемой Меры.
  - **Дано*: Мера используется в визуализации.
  - **Когда*: пользователь изменяет `alias` Меры в настройках набора данных.
  - **Тогда*: `alias` сохраняется, `name` не меняется.
  - **И*: визуализация продолжает ссылаться на Меру по прежнему `name`.
  - **И*: на полках и в панели полей отображается актуальный `alias`.

**AC.14** — Блокировка удаления используемой Меры.
  - **Дано*: Мера используется в визуализации.
  - **Когда*: пользователь пытается удалить Меру.
  - **Тогда*: удаление блокируется.
  - **И*: автоматическое каскадное удаление из визуализаций и зависимых настроек не выполняется.
  - **И*: система показывает список зависимых объектов.

**AC.15** — Обратная совместимость.
- При отсутствии Мер на полках построитель запросов сохраняет текущее поведение.
- Существующие визуализации без Мер продолжают работать без изменения поведения.

**AC.16** — Форма фильтра по Мере.
- UI использует для Мер текущий набор операторов обычного фильтра: `=`, `!=`, `<>`, `>`, `>=`, `<`, `<=`, `like_left`, `like_right`, `like_both`, `likeic_left`, `likeic_right`, `likeic_both`, списки `IN` / `NOT IN` и диапазоны на их основе.
- Значение при `like_*` / `likeic_*` передаётся как искомая подстрока; для остальных операторов значение проверяется backend-ом по `data_type` Меры.
- `values` обязателен и не может быть пустым; при непустом `operators` его длина должна точно совпадать с длиной `values`.
- `null` разрешён только без `operators`; при `not: true` отрицание списка с `null` означает `NOT IN (…) AND IS NOT NULL`.
- Пустой или неизвестный `data_type` блокирует выполнение фильтра контролируемой ошибкой backend-а.

**AC.17** — Обязательный новый построитель.
- На окружении с поддержкой Мер включён `server.use_new_builder = enabled`.
- При выключенной настройке запрос с Мерой не выполняется, а пользователь получает контролируемую ошибку backend-а.

### Сводка изменений относительно предыдущей редакции.
Редакция уточняет форму и валидацию условия фильтра по Мере, его сериализацию в HAVING и обязательность нового построителя. Отображение Мер в панели полей, ярлык `AGR`, поведение статуса `invalid`, drag-and-drop, вычисляемые поля, матрица допустимости по полкам и устойчивость к изменениям метаданных — без изменений.

#### Что изменилось.
- Условие фильтра по Мере — и в метаданных визуализации (объект `filter`), и в runtime-payload запроса — вместо структуры `condition { operator, value, value_type }` описывается тем же контрактом `values` / `operators` / `not` / `logicOr` с элементом `null`, что и фильтр обычного поля.
- Поле `value_type` фронт не формирует: тип значения определяет backend по `data_type` Меры в метаданных набора.
- Операторы `in` и `between` не передаются отдельными ключами: `in` — список `values` без `operators`, `between` — пара `>=` / `<=`.
- Фронт переиспользует существующий сериализатор фильтра обычного поля; отдельный транспорт или отдельный формат условия для Мер не вводится.
- Для HAVING frontend всегда формирует объект `{condition, items}`: `condition` остаётся текущей строковой формой обычных / вычисляемых полей, Меры помещаются в `items[]`.
- `null` с непустым `operators` запрещён; семантика `not + null` определена как отрицание всей исходной группы.
- `like_*` / `likeic_*` сохраняются в общем контракте фильтра и используют значение как искомую подстроку.
- Критерии приёмки AC.8, AC.9, AC.16 и AC.17 переформулированы под контракт `values` / `operators`.

#### Что сохранено без изменений.
- Секция «Меры» в панели полей, ярлык `AGR`, поведение статуса `invalid`, drag-and-drop, использование Мер в вычисляемых полях.
- Маршрутизация по `aggregation_kind` и матрица допустимости Мер по полкам: на «Фильтры» тип `WHERE` — только неагрегированная Мера, тип `HAVING` — только агрегированная.
- Устойчивость к изменению `alias` / выражения / удалению Меры; обратная совместимость визуализаций без Мер.

#### Сводка «было → стало».
| Аспект | Прежняя редакция | Настоящая редакция |
|---|---|---|
| Условие фильтра Меры | `condition { operator, value, value_type }` | `values` / `operators` / `not` / `logicOr` / `null` |
| Тип значения | `value_type` в payload | из `data_type` Меры, `value_type` фронт не шлёт |
| `in` | оператор `in` | `values` без `operators` |
| `between` | оператор `between` | пара `>=` / `<=` |
| `not in` | не выразимо | `values` + `not` |
| ИЛИ / проверка на пусто | не выразимо | `logicOr: 1` / элемент `null` |
| Сериализатор фильтра | отдельный для Меры | общий с обычным полем |

### Дополнительные изменения frontend по результатам согласования.

- Не вводить отдельное ограничение, исключающее `like_*` / `likeic_*` для Мер. Редактор и сериализатор фильтра Меры должны сохранять те же имена like-операторов и ту же семантику, что уже используются для обычного поля.
- При преобразовании фильтра Меры из метаданных визуализации в runtime payload переносить like-оператор и его значение без переименования: для `WHERE` — в элемент `where[]`, для `HAVING` — в элемент `having.items[]`.
- Новые UI-контролы и новые имена операторов для этого не требуются; переиспользуется текущий редактор фильтра.
