 *Изменения frontend для фильтров по Мерам*

Новый формат условия фильтра не вводим. Используем текущие поля обычного фильтра:

• values
• operators
• not
• logicOr
• null внутри values

Frontend не должен формировать вложенный condition для Меры и не должен передавать value_type.

━━━━━━━━━━━━━━━━━━

*1. Хранение фильтра в настройках визуализации*

В настройках сохраняем filter.mode, который определяет, куда попадёт фильтр: в WHERE или HAVING.

{
  "filters": [
    {
      "type": "measure",
      "name": "Мера.Маржа",
      "datasetId": 244,
      "filter": {
        "mode": "WHERE",
        "values": [1000],
        "operators": [">"],
        "not": false,
        "logicOr": 0
      }
    }
  ]
}

━━━━━━━━━━━━━━━━━━

*2. Фильтр WHERE*

Неагрегированная Мера:

aggregation_kind = 0

Frontend переносит условие в where[]:

{
  "where": [
    {
      "type": "measure",
      "name": "Мера.Маржа",
      "datasetId": 244,
      "values": [1000],
      "operators": [">"],
      "not": false,
      "logicOr": 0
    }
  ],
  "having": {
    "condition": ""
  }
}

Backend подставит выражение Меры в WHERE.

Пример результата:

WHERE <выражение Меры.Маржа> > 1000

Агрегированную Меру с aggregation_kind = 1 отправлять в where[] нельзя.

━━━━━━━━━━━━━━━━━━

*3. Фильтр HAVING*

Агрегированная Мера:

aggregation_kind = 1

Frontend переносит условие только в having.items[]:

{
  "having": {
    "condition": "",
    "items": [
      {
        "type": "measure",
        "name": "Мера.Прибыль",
        "datasetId": 244,
        "values": [1000],
        "operators": [">"]
      }
    ]
  }
}

Backend подставит выражение Меры в HAVING.

HAVING <выражение Меры.Прибыль> > 1000

Прямой массив having[] frontend формировать не должен.

━━━━━━━━━━━━━━━━━━

*4. Обычный HAVING и Мера одновременно*

having.condition — действующий формат для обычных и вычисляемых полей. Его нельзя удалять или заменять.

Если одновременно есть старое строковое условие и фильтр по Мере:

{
  "having": {
    "condition": "COUNT(\"order_id\") > 5",
    "items": [
      {
        "type": "measure",
        "name": "Мера.Прибыль",
        "values": [1000],
        "operators": [">"]
      }
    ]
  }
}

Backend объединит части через AND:

HAVING (COUNT("order_id") > 5)
   AND (<выражение Меры.Прибыль> > 1000)

━━━━━━━━━━━━━━━━━━

*5. Список значений — IN*

Если operators отсутствует или пустой, values считается списком:

{
  "type": "measure",
  "name": "Мера.Категория",
  "values": ["Опт", "Розница"]
}

<выражение Меры> IN ('Опт', 'Розница')

Для исключения списка:

{
  "type": "measure",
  "name": "Мера.Категория",
  "values": ["Опт", "Розница"],
  "not": true
}

<выражение Меры> NOT IN ('Опт', 'Розница')

━━━━━━━━━━━━━━━━━━

*6. Диапазон*

Отдельный оператор between не отправляется.

Диапазон передаётся двумя значениями и двумя операторами:

{
  "type": "measure",
  "name": "Мера.Прибыль",
  "values": [1000, 5000],
  "operators": [">=", "<="]
}

(<выражение Меры> >= 1000 AND <выражение Меры> <= 5000)

━━━━━━━━━━━━━━━━━━

*7. Поиск по подстроке — LIKE*

Используем существующие операторы обычного фильтра без переименования:

• like_left — заканчивается на подстроку
• like_right — начинается с подстроки
• like_both — содержит подстроку
• likeic_* — то же без учёта регистра

Пример:

{
  "type": "measure",
  "name": "Мера.Категория",
  "values": ["опт"],
  "operators": ["like_both"]
}

Для WHERE этот элемент кладётся в where[], для HAVING — в having.items[].

<выражение Меры.Категория> LIKE '%опт%'

Новые UI-контролы и новые названия операторов не нужны — используется существующий редактор фильтра.

━━━━━━━━━━━━━━━━━━

*8. Проверка на NULL*

null передаётся только без operators.

Проверка на пустое значение:

{
  "type": "measure",
  "name": "Мера.Прибыль",
  "values": [null]
}

<выражение Меры> IS NULL

Проверка на непустое значение:

{
  "type": "measure",
  "name": "Мера.Прибыль",
  "values": [null],
  "not": true
}

<выражение Меры> IS NOT NULL

Список вместе с пустым значением:

{
  "type": "measure",
  "name": "Мера.Прибыль",
  "values": [1000, null]
}
