h2. Контракт runtime payload для Мер

Единый контракт runtime payload для Мер по всем блокам запроса данных: {{select}}, {{group}}, {{where}}, {{having}}, {{order}}. Источник формы payload для backend и frontend.

Фильтр по Мере (в {{where}} и в элементе {{having}}) описывается *тем же контрактом условия, что и фильтр по обычному полю* — {{values}} / {{operators}} / {{not}} / {{logicOr}} с элементом {{null}}. Отдельной структуры условия для Меры нет; поля {{value_type}} в payload нет — тип значения берётся из {{data_type}} Меры в метаданных. Перечень отличий от предыдущей редакции контракта — в разделе 11.

Endpoint запроса данных: {{/v1/api/recordsets/<dataset_id>}}. Меры поддерживаются только для *произвольных* наборов данных.

Для выполнения запросов с Мерами обязателен новый построитель: {{server.use_new_builder = enabled}}. Allowlist фильтра по Мере включает операторы {{=}}, {{!=}}, {{<>}}, {{>}}, {{>=}}, {{<}}, {{<=}}, семейство {{like_*}} / {{likeic_*}}, списки {{IN}} / {{NOT IN}} и диапазоны на их основе.

----
h2. 0. Что этот документ фиксирует и что заменяет

* *Фиксирует* единую форму runtime payload для Мер во всех пяти блоках, пригодную к реализации и на backend, и на frontend без второго формата фильтра.
* *Заменяет по форме условия фильтра* раздел «4. Контракт фильтра по Мере» и подпункты 5.3 / 5.4 приложения ^Контракты_мер.txt, а также примеры условия фильтра из разделов «2. Целевой runtime-контракт» и «3. Примеры» описания MB-5035.
* *Не меняет* маршрутизацию по {{aggregation_kind}}, три принимаемые backend-ом формы блока {{having}}, запрет {{calc}} / {{aggr}} у Меры, раскрытие выражения только из метаданных и обратную совместимость запросов без Мер; для ошибок Мер сохраняется общий fail-closed принцип.

----
h2. 1. Общая часть — идентичность Меры в любом блоке

Во всех блоках Мера адресуется одинаково. Frontend передаёт *ссылку* на Меру, backend находит её определение в {{datasets.measures}} по {{name}} и раскрывает выражение самостоятельно.

Минимальный объект Меры в runtime payload:

{code:json}
{
  "type": "measure",
  "name": "Мера.Валовая_прибыль",
  "alias": "[values][0]"
}
{code}

|| Поле || Обязательность || Описание ||
| {{type}} | Да | Для Меры всегда {{measure}}. По этому признаку backend отличает Меру от обычного и вычисляемого поля. |
| {{name}} | Да | Системное имя Меры и *единственный ключ связи*. Используется для поиска определения в {{datasets.measures}}. |
| {{alias}} | Да для {{select}}, рекомендуется для {{group}} / {{order}} | Технический alias результата или сортировки ({{[values][0]}}, {{[categories]}}, {{[series][0]}}). Не равен {{measures[].alias}} и не используется для поиска Меры. |
| {{datasetId}} | Нет / сверяется при наличии | Если передан, должен соответствовать {{dataset_id}} запроса или допустимому текущему контексту набора. |
| {{lvl}} | Нет | Уровень фильтра — как в текущем {{where}}-контракте обычного поля. Актуален только для {{where}} (в элементе {{having}} парсер {{lvl}} не разбирает: {{having}} строится один раз для базового уровня). |

*Правила идентичности, единые для всех блоков:*

* ключом связи является только {{name}}; {{alias}} Меры из метаданных ({{measures[].alias}}) для связи не используется;
* {{id}} Меры из {{measures}} не является внешним ключом в runtime payload;
* frontend *не присылает выражение Меры*: источник выражения — только {{measures[].expression}};
* для {{type = "measure"}} поля {{calc}}, {{aggr}} / {{agg}}, {{fieldAlias}}, {{export}} не являются источником выражения. Пустые — игнорируются; *непустой* {{calc}} или {{aggr}} / {{agg}} у Меры — контролируемая ошибка контракта (см. раздел 10).

h2. 2. Блок {{select}}

Мера на полке «Значения». Раскрытое выражение Меры добавляется в {{SELECT}} с техническим alias из payload.

{code:json}
{
  "select": [
    {
      "type": "measure",
      "name": "Мера.Валовая_прибыль",
      "alias": "[values][0]"
    }
  ]
}
{code}

Элемент {{select}} для Меры: {{type}}, {{name}}, {{alias}}. Пользовательский {{alias}} Меры из метаданных как alias результата *не* используется; {{aggr}} / {{agg}} поверх выражения Меры *не* применяется.

h2. 3. Блок {{group}}

Мера как вычисляемое измерение. Раскрытое выражение добавляется в {{GROUP BY}}.

*Допустимо только для неагрегированных Мер* ({{aggregation_kind = 0}}). Агрегированная Мера в {{group}} — контролируемая ошибка (раздел 9).

{code:json}
{
  "group": [
    {
      "type": "measure",
      "name": "Мера.Сегмент_маржи",
      "alias": "[categories]"
    }
  ],
  "select": [
    {
      "type": "measure",
      "name": "Мера.Сегмент_маржи",
      "alias": "[categories]"
    }
  ]
}
{code}

Элемент {{group}} для Меры: {{type}}, {{name}}, {{alias}}.

h2. 4. Блок {{where}} — единый контракт условия

Фильтр по неагрегированной Мере ({{aggregation_kind = 0}}). Условие описывается *тем же контрактом, что и фильтр обычного поля*.

Полный элемент {{where}} для Меры:

{code:json}
{
  "where": [
    {
      "type": "measure",
      "name": "Мера.Маржа_строки",
      "datasetId": 244,
      "lvl": 0,
      "values": [1000],
      "operators": [">"]
    }
  ]
}
{code}

|| Поле || Обязательность || Описание ||
| {{type}} | Да | Всегда {{measure}}. |
| {{name}} | Да | Системное имя Меры (ключ связи). |
| {{datasetId}} | Нет / сверяется | При наличии должен соответствовать набору запроса. |
| {{lvl}} | Нет | Уровень фильтра, как у обычного поля. |
| {{values}} | Да | Непустой массив значений. Элемент {{null}} задаёт проверку на пустое значение и разрешён только в форме списка без {{operators}}. |
| {{operators}} | Нет | Массив операторов. Либо *пуст* (тогда {{values}} — список → {{IN}} / {{NOT IN}}), либо в {{values}} нет {{null}} и длина {{operators}} точно равна длине {{values}} (цепочка сравнений по индексам). Иное соотношение и {{null}} вместе с операторами — контролируемая ошибка. |
| {{not}} | Нет | Отрицание всего условия: {{NOT IN}} для списка без {{null}}; для списка с {{null}} отрицание {{(IN (…) OR IS NULL)}} даёт {{NOT IN (…) AND IS NOT NULL}}. |
| {{logicOr}} | Нет | {{1}} — условия объединяются через {{OR}}; иначе — через {{AND}}. |

Элемент {{null}} применяется *только в форме списка* ({{values}} без {{operators}}):

* {{"values":[null]}} → {{… IS NULL}};
* {{"values":[null], "not":true}} → {{… IS NOT NULL}};
* {{"values":[10,null]}} → {{(… IN (10) OR … IS NULL)}};
* {{"values":[10,null], "not":true}} → {{(… NOT IN (10) AND … IS NOT NULL)}}.

Формы {{"values":[10,null], "operators":[">"]}} и {{"values":[null], "operators":[">"]}} некорректны и должны завершаться контролируемой ошибкой. {{null}} не может молча отбрасываться, а оператор рядом с единственным {{null}} не может молча игнорироваться.

h3. 4.1. Все формы условия

|| Что нужно пользователю || Что слать || SQL ||
| сравнение: больше 1000 | {{"values":[1000], "operators":[">"]}} | {{… > 1000}} |
| диапазон: от 100 до 500 | {{"values":[100,500], "operators":[">=","<="]}} | {{(… >= 100 AND … <= 500)}} |
| список значений (in) | {{"values":[1,2,5]}} (без {{operators}}) | {{… IN (1,2,5)}} |
| исключение списка (not in) | {{"values":[100,200,300], "not":true}} | {{… NOT IN (100,200,300)}} |
| ИЛИ: меньше 100 *или* больше 900 | {{"values":[100,900], "operators":["<",">"], "logicOr":1}} | {{(… < 100 OR … > 900)}} |
| пусто (is null) | {{"values":[null]}} | {{… IS NULL}} |
| не пусто (is not null) | {{"values":[null], "not":true}} | {{… IS NOT NULL}} |
| список вместе с пустым значением | {{"values":[1,null]}} | {{(… IN (1) OR … IS NULL)}} |
| исключить список и пустое значение | {{"values":[1,null], "not":true}} | {{(… NOT IN (1) AND … IS NOT NULL)}} |

Здесь {{…}} — раскрытое выражение неагрегированной Меры (например, столбец, вычисляемый в подзапросе набора).

h2. 5. Блок {{having}} — три принимаемые backend-ом формы

Фильтр по агрегированной Мере ({{aggregation_kind = 1}}). *Условие элемента Меры записывается тем же контрактом {{values}} / {{operators}} / {{not}} / {{logicOr}} / {{null}}, что и в {{where}}* (раздел 4).

Backend принимает три формы блока {{having}} для совместимости существующих клиентов. При этом frontend использует один канонический формат при наличии фильтра по Мере:

{code:json}
{
  "having": {
    "condition": "<текущее условие обычных/вычисляемых полей или пустая строка>",
    "items": [
      { "type": "measure", "name": "Мера.Валовая_прибыль", "values": [1000], "operators": [">"] }
    ]
  }
}
{code}

_SQL-примеры ниже иллюстрируют SQL-семантику предиката. Форма левой части ({{<раскрытое выражение Меры>}}) зависит от набора данных и диалекта СУБД и не является частью контракта._

h3. 5.1. Что такое {{having.condition}}

В актуальном варианте A {{condition}} есть только на верхнем уровне {{having}}:

|| Где || Что это || Кто формирует ||
| {{having.condition}} (верхний уровень) | *строка* SQL для обычных / вычисляемых полей | frontend собирает строку сам |

Это не устаревшая форма: {{having.condition}} остаётся текущей и единственной формой HAVING-фильтра для обычных и вычисляемых полей. Внутри элемента Меры поля {{condition}} нет; структурное условие Меры задаётся непосредственно полями {{values}} / {{operators}} / {{not}} / {{logicOr}} / {{null}}.

h3. 5.2. Форма 1 — прямой массив (backend-совместимость, только Меры)

{code:json}
{
  "having": [
    {
      "type": "measure",
      "name": "Мера.Валовая_прибыль",
      "values": [1000],
      "operators": [">"]
    }
  ]
}
{code}

{code:sql}
HAVING <раскрытое выражение агрегированной Меры> > 1000
{code}

Backend продолжает принимать эту форму, но frontend её не формирует. Она не позволяет одновременно передать строковое условие обычных/вычисляемых полей.

h3. 5.3. Форма 2 — канонический frontend-формат ({{condition}} + {{items}})

Строка для обычных / вычисляемых полей и структурные условия по Мерам объединяются через {{AND}}. Frontend формирует именно эту форму всегда, когда в HAVING присутствует хотя бы одна Мера. Если строкового условия нет, передаётся пустая строка {{condition: ""}}.

{code:json}
{
  "having": {
    "condition": "COUNT(x) > 5",
    "items": [
      {
        "type": "measure",
        "name": "Мера.Валовая_прибыль",
        "values": [100, 200, 300],
        "not": true
      }
    ]
  }
}
{code}

{code:sql}
HAVING (COUNT(x) > 5)
   AND (<раскрытое выражение агрегированной Меры> NOT IN (100,200,300))
{code}

h3. 5.4. Форма 3 — текущая строковая форма (только обычные/вычисляемые поля)

{code:json}
{
  "having": {
    "condition": "COUNT(x) > 5"
  }
}
{code}

Форма 3 и пустая _{"condition": ""}_ обрабатываются по текущей логике без изменений. Добавление Мер не заменяет эту архитектуру, а расширяет объект {{having}} массивом {{items}}.

h3. 5.5. Строковое значение в условии по Мере

Значение приезжает отдельным полем и экранируется backend-ом при выводе литерала, а не склеивается с текстом запроса. Для строковой Меры ({{Мера.Менеджер = MAX("manager")}}, {{data_type = string}}):

{code:json}
{
  "having": {
    "condition": "",
    "items": [
      {
        "type": "measure",
        "name": "Мера.Менеджер",
        "values": ["O'Brien"],
        "operators": ["="]
      }
    ]
  }
}
{code}

{code:sql}
HAVING <раскрытое выражение строковой Меры> = 'O''Brien'
{code}

Значение приезжает отдельным полем и экранируется backend-ом при выводе литерала ({{'O''Brien'}} — апостроф удвоен), а не склеивается с текстом запроса.

Элемент {{order}} для Меры: {{type}}, {{name}}, {{alias}}, {{direction}} ({{asc}} / {{desc}} / значение по умолчанию). Ключ связи — {{name}}: backend сортирует по *раскрытому выражению Меры* (совпадение технического {{alias}} с полем выборки Меру не подменяет). Если Мера присутствует только в {{order}}, в результат она автоматически не добавляется, если этого не требует текущая логика обычных полей.

h2. 7. Операторы — allowlist

Допустимые операторы условия (для {{where}} и для элемента {{having}}):

|| Оператор || Значение || Форма ||
| {{=}} | равно | {{values:[X], operators:["="]}} |
| {{!=}} | не равно | {{values:[X], operators:["!="]}} |
| {{<>}} | не равно (синоним {{!=}}) | {{values:[X], operators:["<>"]}} |
| {{>}} | больше | {{values:[X], operators:[">"]}} |
| {{>=}} | больше или равно | {{values:[X], operators:[">="]}} |
| {{<}} | меньше | {{values:[X], operators:["<"]}} |
| {{<=}} | меньше или равно | {{values:[X], operators:["<="]}} |
| {{like_left}} | заканчивается на подстроку | {{values:["текст"], operators:["like_left"]}} |
| {{like_right}} | начинается с подстроки | {{values:["текст"], operators:["like_right"]}} |
| {{like_both}} | содержит подстроку | {{values:["текст"], operators:["like_both"]}} |
| {{likeic_left}} | заканчивается на подстроку без учёта регистра | {{values:["текст"], operators:["likeic_left"]}} |
| {{likeic_right}} | начинается с подстроки без учёта регистра | {{values:["текст"], operators:["likeic_right"]}} |
| {{likeic_both}} | содержит подстроку без учёта регистра | {{values:["текст"], operators:["likeic_both"]}} |

h3. 7.1. {{in}} и {{between}} — это *формы записи*, а не ключи оператора

{{in}} и {{between}} в payload *не передаются* как отдельные операторы или ключи. Они выражаются формой {{values}} / {{operators}}:

|| Намерение || Форма || SQL ||
| {{in}} — вхождение в список | {{values}} с несколькими значениями, {{operators}} пуст | {{IN (…)}} |
| {{not in}} — исключение списка | список {{values}} + {{not:true}} | {{NOT IN (…)}} |
| {{between}} — диапазон | пара операторов {{">="}} и {{"<="}} на два значения | {{(… >= A AND … <= B)}} |

h3. 7.2. Семейство {{like_*}} / {{likeic_*}} — поиск по подстроке

Операторы {{like_left}}, {{like_right}}, {{like_both}}, {{likeic_left}}, {{likeic_right}}, {{likeic_both}} поддерживаются в {{where}} и в элементе {{having}} тем же контрактом, что и для обычного поля. Префикс {{likeic}} означает поиск без учёта регистра.

Значение like-оператора — искомая подстрока, а не значение типа Меры. Поэтому оно приводится к строке и не проверяется на соответствие {{data_type}}. SQL-семантика {{like_both}} эквивалентна {{CAST(<выражение Меры> AS text) LIKE '%<подстрока>%'}}; конкретный рендер определяется SQL-диалектом.

В смешанной цепочке проверка выполняется отдельно по каждой паре {{values[i]}} / {{operators[i]}}: like-значение трактуется как подстрока, значение обычного сравнения проверяется по {{data_type}} Меры.

----
h2. 8. Тип значения — из {{data_type}} Меры

Тип значения берётся из {{data_type}} Меры в метаданных набора. Клиент тип *не передаёт и не переопределяет*. Допустимые значения метаданных в этой версии: {{string}}, {{number}}, {{integer}}, {{date}}, {{datetime}}. Каждое ненулевое значение обычного сравнения проверяется на соответствие типу Меры. Значение {{like_*}} / {{likeic_*}} является подстрокой и составляет исключение из этой проверки.

*Поля {{value_type}} в контракте нет.* Источник истины по типу — только метаданные Меры ({{data_type}}). Пустой или неизвестный {{data_type}} при использовании Меры в фильтре, как и несоответствие значения типу, — контролируемая ошибка (раздел 10).

----
h2. 9. Маршрутизация по {{aggregation_kind}}

Блок выбирается по {{aggregation_kind}} Меры из *метаданных*, а не по полю payload:

|| {{aggregation_kind}} Меры || Блок runtime payload || SQL-контекст ||
| {{0}} (неагрегированная) | {{where[]}} | {{WHERE}} |
| {{1}} (агрегированная) | {{having.items[]}} в каноническом frontend-формате; backend также принимает прямой массив {{having}} | {{HAVING}} |

Обратные сочетания — контролируемая ошибка с подсказкой, какой блок использовать:

* агрегированная Мера в {{where}} → *«Агрегированная Мера не может использоваться в WHERE. Используйте HAVING-фильтр»*;
* неагрегированная Мера в {{having}} → *«Неагрегированная Мера не может использоваться в HAVING. Используйте WHERE-фильтр»*;
* агрегированная Мера в {{group}} → *«Агрегированная Мера не может использоваться в GROUP BY»*.

----
h2. 10. Политика ошибок

Форма условия у Меры и у обычного поля *одинаковая*. Для Меры действует строгая политика:

* *обычное поле* — fail-open: нераспознанное условие молча отбрасывается (обратная совместимость исторического {{where}});
* *Мера* — fail-closed: любой дефект контракта останавливает запрос контролируемой ошибкой, SQL не выполняется.

Контролируемую ошибку по Мере вызывают:

* {{values}} отсутствует или является пустым массивом;
* непустой {{operators}}, если его длина не равна длине {{values}} в точности;
* одновременное наличие {{null}} в {{values}} и непустого {{operators}};
* оператор вне allowlist (раздел 7);
* значение обычного сравнения не соответствует {{data_type}} Меры либо {{data_type}} пуст/неизвестен (раздел 8);
* Мера не найдена в {{measures}} текущего набора, её {{status}} не равен {{valid}}, либо она не того {{aggregation_kind}} для блока (раздел 9);
* непустой {{calc}} или {{aggr}} / {{agg}} у элемента Меры;
* набор данных не является произвольным (простой / составной);
* выражение Меры содержит переменную набора данных: подстановка таких переменных в выражения Мер не входит в эту версию;
* циклическая зависимость при раскрытии выражения.
* новый построитель выключен ({{server.use_new_builder != enabled}}): выполнение запроса с Мерой через старый построитель запрещено.

Рекомендуемый минимальный состав технических деталей ошибки: {{measure_name}}, {{runtime_block}} ({{select}} / {{group}} / {{where}} / {{having}} / {{order}}), {{reason}}, {{status_message}} (если ошибка связана со статусом, отличным от {{valid}}).

h2. 11. Отличие от прежнего контракта (Контракты_мер.txt)

Предыдущая редакция (^Контракты_мер.txt, разделы 4, 5.3, 5.4) и примеры MB-5035 описывали условие фильтра по Мере через вложенную структуру _condition{operator, value, value_type}_. Настоящий контракт её заменяет.

h3. 11.1. Что убрано

* *Структура _condition{operator, value, value_type}_* внутри элемента Меры — и в {{where}}, и в {{having}}. Прежний вид:
{code:json}
{
  "type": "measure",
  "name": "Мера.Валовая_прибыль",
  "condition": { "operator": ">", "value": 0, "value_type": "number" }
}
{code}
* *Поле {{value_type}}* — из контракта полностью (тип берётся из {{data_type}} Меры, см. раздел 8).
* *Отдельные операторы {{in}} и {{between}}* как ключи/имена оператора — их больше нет в payload.

h3. 11.2. Что вместо этого

* Единый контракт условия {{values}} / {{operators}} / {{not}} / {{logicOr}} с элементом {{null}} — тот же, что у обычного поля (разделы 4, 5).
* {{in}} = {{values}} без {{operators}}; {{not in}} = {{values}} + {{not}}; {{between}} = пара {{">="}} / {{"<="}} (раздел 7.1).
* Тип значения обычного сравнения — из {{data_type}} Меры; значение like-оператора трактуется как подстрока (разделы 7.2 и 8).
* Для {{null}} определены четыре точные формы: {{IS NULL}}, {{IS NOT NULL}}, {{IN (...) OR IS NULL}}, {{NOT IN (...) AND IS NOT NULL}}. Сочетание {{null}} с непустым {{operators}} запрещено.
* Семейства {{like_*}} / {{likeic_*}} входят в allowlist и используют ту же форму {{values}} / {{operators}}, что и остальные сравнения.

h3. 11.3. Что сохранено без изменений

* Маршрутизация по {{aggregation_kind}}: {{0}} → {{where}}, {{1}} → {{having}} (раздел 9).
* Backend принимает три формы блока {{having}}: прямой массив; _{condition, items}_; _{condition}_. Frontend при наличии Мер использует только каноническую форму _{condition, items}_ (раздел 5).
* Запрет {{calc}} / {{aggr}} у Меры; выражение раскрывается *только* из метаданных {{measures[].expression}} (раздел 1).
* Текущий {{having.condition}} для обычных/вычисляемых полей и запросы без Мер работают без изменений.
* Контролируемые ошибки как класс; политика Меры — явно fail-closed (раздел 10).

h3. 11.4. Сводка «было → стало»

|| Аспект || Предыдущая редакция || Настоящий контракт ||
| Условие фильтра Меры | _condition{operator, value, value_type}_ | {{values}} / {{operators}} / {{not}} / {{logicOr}} / {{null}} |
| Тип значения | {{value_type}} в payload | из {{data_type}} Меры, {{value_type}} нет |
| {{in}} | оператор {{in}} | {{values}} без {{operators}} |
| {{between}} | оператор {{between}} | пара {{">="}} / {{"<="}} |
| {{not in}} | не выразимо | {{values}} + {{not}} |
| ИЛИ / пусто | не выразимо | {{logicOr:1}} / элемент {{null}} |
| Единство с обычным полем | отдельный формат | один контракт условия |

h2. 12. Дополнительные требования к frontend по результатам согласования

* Не вводить отдельное ограничение, исключающее {{like_*}} / {{likeic_*}} для Мер. Редактор и сериализатор фильтра Меры сохраняют текущие имена и семантику операторов обычного фильтра.
* При преобразовании фильтра Меры из метаданных визуализации в runtime payload like-оператор и его значение переносятся без переименования: для {{WHERE}} — в элемент {{where[]}}, для {{HAVING}} — в элемент {{having.items[]}}.
* Новые UI-контролы и новые имена операторов не требуются: используется текущий редактор фильтра.
