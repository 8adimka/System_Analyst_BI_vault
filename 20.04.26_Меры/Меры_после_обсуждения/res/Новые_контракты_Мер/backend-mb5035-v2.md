### Контекст и цель истории.
Полное описание продуктовой логики приведено в Эпике по Мерам - https://jira.modusbi.ru/browse/MB-4364.
Общее описание доработок Шага 2 реализации Мер приведено в связанной Истории - https://jira.modusbi.ru/browse/MB-4481.
Настоящая История реализует \*\*второй шаг backend-доработок\*\* по внедрению сущности \*\*«Мера»\*\* в аналитическом портале: поддержку Мер в запросах данных визуализаций и корректную подстановку выражений Мер в SQL-запрос, формируемый backend-ом.
На первом шаге backend-доработок реализованы хранение Мер в метаданных произвольного набора данных и CRUD-контракты. Полноценная валидация выражений, обработка статусов, анализ зависимостей и блокировки реализуются отдельным Шагом 3. В рамках текущей Истории backend должен использовать эти определения Мер при обработке запросов данных визуализаций.
Backend не обязан знать о предметных полках визуализаций, Backend-контрактом для построения SQL остаются runtime-блоки запроса frontend-а: `group`, `select`, `where`, `having`, `order`, `variables`, `series`. Именно по блоку, в котором frontend передал объект Меры, backend должен определить SQL-контекст использования: `SELECT`, `GROUP BY`, `WHERE`, `HAVING` или `ORDER BY`.
Поддержка Мер в запросах данных реализуется только в новом построителе запросов. Для работы Мер настройка портала `server.use_new_builder` должна иметь значение `enabled`. При выключенном новом построителе запрос с `type = "measure"` должен завершаться контролируемой ошибкой до выполнения SQL.
----
### Контракт условия фильтра по Мере.
Условие фильтра по Мере — и в `where`, и в `having` — описывается тем же контрактом, что и условие фильтра обычного поля: `values` / `operators` / `not` / `logicOr` с элементом `null`. Отдельной структуры условия для Меры нет.
- операторы `in` и `between` отдельными ключами не передаются: `in` выражается списком `values` без `operators`, `between` — парой `>=` / `<=`;
- тип значения берётся из `data_type` Меры в метаданных набора; клиент тип не передаёт и не переопределяет (поля `value_type` в payload нет);
- разрешены операторы `=`, `!=`, `<>`, `>`, `>=`, `<`, `<=`, семейство поиска по подстроке `like_left` / `like_right` / `like_both` / `likeic_left` / `likeic_right` / `likeic_both`, списки `IN` / `NOT IN` и диапазоны, выраженные через эти операторы;
- элемент `null` разрешён только при пустом `operators`; `null` вместе с непустым `operators` является ошибкой контракта;
- единственное отличие фильтра по Мере от фильтра обычного поля — политика ошибок: у обычного поля нераспознанное условие молча отбрасывается (fail-open, обратная совместимость), у Меры любой дефект контракта даёт контролируемую ошибку (fail-closed).
----
### Границы истории.
В рамках Истории реализуется:
- поддержка объектов `type = "measure"` в runtime payload запроса данных;
- поиск Меры по `name` в метаданных текущего \*\*произвольного\* набора данных;
- проверка, что найденная Мера имеет `status = "valid"`;
- раскрытие выражения Меры из `measures[].expression` (с учётом ссылок на другие Меры);
- подстановка раскрытого выражения Меры в нужную SQL-клаузу по runtime-блоку;
- переиспользование текущего механизма построения SQL для обычных и вычисляемых полей там, где это применимо;
- обработка условий фильтрации по Мере в `WHERE` и `HAVING`;
- обработка сортировки по Мере в `ORDER BY`;
- валидация допустимости использования Меры в конкретном SQL-контексте на основании `aggregation_kind` и фактической SQL-семантики;
- контролируемый отказ для запросов с Мерами при выключенном новом построителе;
- сохранение текущего поведения запросов, где Меры не используются.
В рамках Истории \*\*не реализуется\*\*:
- frontend-интерфейс размещения Мер на полках визуализаций;
- управление Мерами в настройках набора данных: создание, редактирование, удаление, ревалидация при сохранении набора;
- поддержка Мер для \*\*простых\*\* и \*\*составных\* наборов данных;
- поддержка переменных внутри `measures[].expression`; в текущем шаге такое выражение отклоняется контролируемой ошибкой;
- определение SQL-контекста по названиям полок, заголовкам визуализации или техническим alias вида `[values][0]`, `[categories]`, `[series][0]`;
- изменение существующего поведения обычных полей и вычисляемых полей, если в запросе нет объектов `type = "measure"`.
----
### Ключевые правила модели.
- Ключом связи с Мерой является `name`.
- `alias` Меры используется для отображения пользователю и не является ключом связи.
- `id` Меры из массива `measures` не используется как внешний ключ в runtime payload визуализации.
- Frontend не передаёт выражение Меры как источник истины при построении запроса данных.
- Backend получает в payload ссылку на Меру, находит её актуальное определение в метаданных набора данных и раскрывает выражение самостоятельно.
- Если объект в runtime payload имеет `type = "measure"`, backend не должен использовать `calc`, `fieldAlias`, `export`, `alias` или другие поля как источник выражения Меры.
- `alias` внутри runtime payload является техническим alias результата запроса, например `[values][0]`. Он не равен `measures[].alias` и не должен использоваться для поиска Меры.
- Блок `variables` продолжает работать для обычных и вычисляемых полей. Переменные внутри `measures[].expression` в текущем шаге не поддерживаются и должны приводить к контролируемой ошибке, а не попадать в SQL буквально.
- Блок `series` не является самостоятельным источником SQL-выражений Мер. Его текущее поведение не меняется.
----
### Описание текущего поведения.
Сейчас runtime-запросы данных визуализаций строятся frontend-ом через универсальные блоки:
- `group` — поля группировки;
- `select` — поля результата и агрегируемые значения;
- `where` — фильтры до группировки;
- `having` — условия после группировки;
- `order` — сортировка;
- `variables` — значения переменных;
- `series` — режим работы серий.
Для обычных полей и вычисляемых полей backend уже умеет использовать эти блоки при построении SQL. Например, поле на полке категорий frontend передаёт в `group` и, если требуется вернуть значение в ответ, в `select` с техническим alias `[categories]`. Поле на полке значений frontend передаёт в `select` с `aggr` и alias вида `[values][0]`. Фильтры по обычным полям передаются в `where` как элементы с `name` и `values`. Сортировка передаётся в `order`.
Backend пока не умеет обрабатывать объект `type = "measure"` в этих runtime-блоках. Если frontend начнёт передавать Меру в `select`, `group`, `where`, `having` или `order`, backend не сможет найти её выражение в метаданных набора данных, проверить допустимость SQL-контекста и корректно встроить выражение в итоговый SQL.
----
### Описание целевого поведения.
При получении runtime-запроса данных по `/v1/api/recordsets/<dataset_id>` backend должен:
1. разобрать payload запроса данных;
1. найти все элементы с `type = "measure"` в блоках `group`, `select`, `where`, `having`, `order`;
1. для каждого такого элемента найти определение Меры по `name` в массиве `measures` текущего набора данных;
1. проверить, что Мера существует, относится к текущему набору данных и имеет `status = "valid"`;
1. раскрыть выражение Меры из `expression`, включая ссылки на другие Меры;
1. определить SQL-клаузу по runtime-блоку, где находится элемент Меры;
1. встроить раскрытое выражение Меры в итоговый SQL тем же построителем, который используется для обычных полей и вычисляемых полей;
1. вернуть результат с теми же техническими alias, которые frontend передал в runtime payload.
Backend должен работать не с полками визуализаций, а с runtime-структурами.
| Runtime-блок | SQL-контекст | Целевое поведение для Меры |
|---|---|---|
| `select` | `SELECT` | Раскрытое выражение Меры добавляется в список возвращаемых выражений с техническим alias из runtime payload |
| `group` | `GROUP BY` | Раскрытое выражение неагрегированной Меры используется как выражение группировки |
| `where` | `WHERE` | Раскрытое выражение неагрегированной Меры используется в предикате фильтрации до группировки |
| `having` | `HAVING` | Раскрытое выражение агрегированной Меры используется в предикате фильтрации после группировки |
| `order` | `ORDER BY` | Раскрытое выражение Меры или alias результата используется для сортировки по текущим правилам построителя |
| `variables` | Подстановка переменных | Текущее поведение обычных и вычисляемых полей не меняется; переменные внутри выражения Меры в этом шаге отклоняются |
| `series` | Текущая логика серий | Не меняется в рамках поддержки Мер |
----
### Требования к реализации.
#### 1. Затрагиваемые backend-контракты.
Основной затрагиваемый контракт: запрос данных по набору данных.
| Контракт | Требуемая доработка |
|---|---|
| `/v1/api/recordsets/<dataset_id>` | Поддержать элементы `type = "measure"` в runtime-блоках `group`, `select`, `where`, `having`, `order` |
| `datasets` / чтение метаданных набора | Использовать актуальный массив `measures` как источник определения Мер при построении SQL |
Если в текущей реализации запрос данных внутренне использует другой backend-объект или общий SQL-builder, доработка должна быть внесена на уровне общего механизма построения SQL, чтобы поведение Мер было одинаковым для всех визуализаций, которые используют этот механизм.
Если экспорт данных визуализации использует тот же runtime payload и тот же SQL-builder, Меры должны обрабатываться в экспорте тем же способом. Отдельная доработка шаблонов экспорта в рамках этой Истории не требуется.
---
#### 2. Целевой runtime-контракт объекта Меры.
Минимальный объект Меры в runtime payload:
```json

{
  "type": "measure",
  "name": "Мера.Валовая_прибыль",
  "alias": "[values][0]"
}

```
| Поле | Обязательность | Описание |
|---|---|---|
| `type` | Да | Для Меры всегда `measure`. По этому признаку backend отличает Меру от обычного поля и вычисляемого поля |
| `name` | Да | Системное имя Меры. Используется для поиска определения в `datasets.measures` |
| `alias` | Да для `select`, рекомендуется для `group` / `order` | Технический alias результата или сортировки. Не является `alias` Меры из метаданных |
| `id` | Нет | Локальный frontend-id пилюли. Backend не использует его как ключ связи с Мерой |
| `fieldAlias` | Нет | Отображаемое название пилюли. Backend не использует его как источник выражения |
| `datasetId` | Нет / проверяется при наличии | Если передан, должен соответствовать `dataset_id` запроса или допустимому текущему контексту набора данных |
| `calc` | Нет | Для `type = "measure"` не является источником выражения. Источник выражения — только `datasets.measures[].expression` |
| `aggr` / `agg` | Нет | Для `type = "measure"` не должен использоваться как обёртка выражения Меры. Агрегированность определяется `aggregation_kind` и самим выражением Меры |
Если frontend по техническим причинам передаёт для Меры пустые `calc`, `aggr`, `agg` или presentation-поля, backend может их игнорировать. Если для `type = "measure"` передан непустой `calc` или непустой `aggr` / `agg`, backend должен вернуть контролируемую ошибку контракта и не применять эти поля к выражению Меры. Frontend не должен иметь возможность подменить выражение Меры через runtime payload.
---
#### 3. Примеры runtime payload для Мер.
##### \*\*Мера в `select` — сценарий значения визуализации:\*\*
```json

{
  "group": [
    {
      "name": "region",
      "calc": "",
      "alias": "[categories]"
    }
  ],
  "select": [
    {
      "type": "measure",
      "name": "Мера.Валовая_прибыль",
      "alias": "[values][0]"
    }
  ],
  "where": [],
  "having": {
    "condition": ""
  },
  "order": [],
  "variables": [],
  "series": {
    "enable": 0
  }
}

```
##### \*\*Неагрегированная Мера в `group` и `select` — сценарий вычисляемого измерения:\*\*
```json

{
  "group": [
    {
      "type": "measure",
      "name": "Мера.Сегмент_маржи",
      "alias": "[categories]"
    }
  ],
  "select": [
    {
      "type": "measure",
      "name": "Мера.Сегмент_маржи",
      "alias": "[categories]"
    }
  ],
  "where": [],
  "having": {
    "condition": ""
  },
  "order": []
}

```
##### \*\*WHERE-фильтр по неагрегированной Мере:\*\*
```json

{
  "where": [
    {
      "type": "measure",
      "name": "Мера.Маржа_строки",
      "values": [0],
      "operators": [">"]
    }
  ],
  "having": {
    "condition": ""
  }
}

```
##### \*\*HAVING-фильтр по агрегированной Мере в каноническом frontend-формате:\*\*
```json

{
  "having": {
    "condition": "",
    "items": [
      {
        "type": "measure",
        "name": "Мера.Валовая_прибыль",
        "values": [0],
        "operators": [">"]
      }
    ]
  }
}

```
Если существующий клиент передаёт `HAVING` в формате массива, зафиксированном в `Контракты_мер.txt`, backend должен обрабатывать его как эквивалентный структурный список условий:
```json

{
  "having": [
    {
      "type": "measure",
      "name": "Мера.Валовая_прибыль",
      "values": [0],
      "operators": [">"]
    }
  ]
}

```
Таким образом, backend должен поддержать три входные формы:
- текущую строковую форму `having.condition` без структурных условий — это единственная форма HAVING для обычных и вычисляемых полей;
- совместную форму `having.condition` + `having.items`, если в одном запросе есть условия по обычным / вычисляемым полям и условия по Мерам;
- формат `having` как прямой массив структурных условий только по Мерам — дополнительная backend-совместимая форма.
Условие `having.condition` и структурные условия из `having.items` должны объединяться через `AND`. Канонический runtime-формат, формируемый frontend-ом при наличии Мер в HAVING, — объект `{condition, items}`; прямой массив backend принимает, но frontend его не формирует.
Текущая строковая форма для обычных и вычисляемых полей:
```json

{
  "having": {
    "condition": ""
  }
}

```
##### \*\*Сортировка по Мере:\*\*
```json

{
  "select": [
    {
      "type": "measure",
      "name": "Мера.Валовая_прибыль",
      "alias": "[values][0]"
    }
  ],
  "order": [
    {
      "type": "measure",
      "name": "Мера.Валовая_прибыль",
      "alias": "[values][0]",
      "direction": "desc"
    }
  ]
}

```

#### 4. Поиск и раскрытие выражения Меры.
При обработке объекта `type = "measure"` backend должен:
1. взять `name` из runtime-элемента;
1. найти Меру с таким `name` в `measures` текущего набора данных;
1. проверить `status = "valid"`;
1. взять `expression` найденной Меры как источник SQL-выражения;
1. раскрыть ссылки на другие Меры, если они присутствуют в выражении в формате двойных кавычек, например `"Мера.Валовая_прибыль"`;
1. обернуть раскрываемые выражения в скобки, чтобы сохранить приоритет операций;
1. оставить ссылки на обычные поля набора данных в формате, который использует текущий SQL-builder для обращения к колонкам базового подзапроса;
1. проверить отсутствие синтаксиса глобальных переменных в выражении Меры и при его наличии вернуть контролируемую ошибку; подстановка переменных внутрь `measures[].expression` относится к отдельному шагу.
##### Пример определения Меры:
```json

{
  "name": "Мера.Валовая_прибыль",
  "expression": "SUM(\"revenue\") - SUM(\"cost\")",
  "aggregation_kind": 1,
  "status": "valid"
}

```
##### Пример использования другой Меры:
```sql

"Мера.Валовая_прибыль" / NULLIF(SUM("revenue"), 0)

```
При раскрытии выражение должно быть интерпретировано как ссылка на сохранённую Меру (`Мера.Валовая_прибыль`), а не как имя физической колонки базового SQL.
Если в графе зависимостей обнаружена циклическая ссылка, backend должен вернуть контролируемую ошибку. Такая ситуация не должна возникать при корректной реализации первого backend-шага, но runtime-обработка должна быть устойчива к повреждённым метаданным.
---
#### 5. Подстановка в `SELECT`.
Если объект `type = "measure"` находится в блоке `select`, backend должен:
- раскрыть выражение Меры;
- добавить раскрытое выражение в `SELECT` итогового внешнего запроса;
- использовать технический `alias` из runtime payload как alias возвращаемой колонки;
- не использовать пользовательский `alias` Меры из метаданных как alias результата запроса;
- не применять `aggr` / `agg` из runtime payload поверх выражения Меры.
##### Пример целевой SQL-семантики:
```sql

SELECT
  "region" AS "[categories]",
  (SUM("revenue") - SUM("cost")) AS "[values][0]"
FROM (
  <SQL произвольного набора данных>
) AS __base
GROUP BY
  "region"

```
Конкретная форма экранирования alias и обращения к колонкам должна соответствовать текущему SQL-builder портала и SQL-диалекту источника.
Если в `select` используется неагрегированная Мера вместе с агрегированными выражениями, backend должен обеспечить SQL-семантику, эквивалентную текущей логике для неагрегированных обычных полей: выражение неагрегированной Меры должно быть учтено в группировке либо запрос должен быть отклонён с понятной ошибкой, если корректно построить SQL невозможно.
---
#### 6. Подстановка в `GROUP BY`.
Если объект `type = "measure"` находится в блоке `group`, backend должен:
- разрешать использование только неагрегированных Мер с `aggregation_kind = 0`;
- раскрыть выражение Меры;
- добавить раскрытое выражение в `GROUP BY` итогового внешнего запроса;
- не применять к выражению агрегирующие функции из runtime payload;
- не определять факт группировки по техническому alias вида `[categories]` или `[series][0]` — SQL-контекст задаётся только блоком `group`.
Если в `group` передана агрегированная Мера с `aggregation_kind = 1`, backend должен вернуть контролируемую ошибку:
\*\*«Агрегированная Мера не может использоваться в GROUP BY»\*\*
или эквивалентное по смыслу сообщение.
---
#### 7. Подстановка в `WHERE`.
Если объект `type = "measure"` находится в блоке `where`, backend должен:
- разрешать использование только неагрегированных Мер с `aggregation_kind = 0`;
- раскрыть выражение Меры;
- построить предикат фильтрации по тому же контракту `values` / `operators` / `not` / `logicOr`, что и для обычного поля, — единый контракт условия, но с fail-closed валидацией;
- добавить предикат в `WHERE` итогового внешнего запроса;
- объединять несколько условий `WHERE` по Мерам и обычным полям по текущим правилам backend-а, базово через `AND`, если иной режим не задан существующим контрактом.
##### Пример SQL-семантики:
```sql

WHERE
  (<раскрытое выражение неагрегированной Меры>) > :value_1

```
Условие фильтра по Мере описывается тем же контрактом, что и условие обычного поля:
- `values` — массив значений; элемент `null` задаёт проверку на пустое значение (`IS NULL`) только в форме списка без `operators`;
- `operators` — массив операторов, параллельный `values`. Либо пуст — тогда `values` трактуется как список (`IN`; с флагом `not` — `NOT IN`); либо в `values` нет `null` и длина `operators` равна длине `values` — тогда это цепочка сравнений по индексам. Иное соотношение длин и любое сочетание `null` с непустым `operators` — контролируемая ошибка;
- `not` — отрицание условия; `logicOr = 1` — объединение условий внутри элемента через `OR`, иначе через `AND`.
Backend должен использовать allowlist операторов: `=`, `!=`, `<>`, `>`, `>=`, `<`, `<=`, `like_left`, `like_right`, `like_both`, `likeic_left`, `likeic_right`, `likeic_both`. Отдельных операторов `in` и `between` в контракте нет: `in` выражается списком `values` без `operators`, `between` — парой `>=` / `<=`.

Семантика поиска по подстроке:
- `like_left` — значение заканчивается указанной подстрокой;
- `like_right` — значение начинается с указанной подстроки;
- `like_both` — значение содержит указанную подстроку;
- соответствующие `likeic_*` выполняют тот же поиск без учёта регистра.

Для `like_*` / `likeic_*` значение является искомой подстрокой, поэтому оно приводится к строке и не проверяется на соответствие `data_type` результата Меры. В смешанной цепочке проверка выполняется отдельно по каждой паре `values[i]` / `operators[i]`: значение при like-операторе трактуется как подстрока, значение при операторе сравнения проверяется по `data_type`.

Элемент `null` задаёт проверку на пустое значение и применяется только в форме списка (`values` без `operators`):
- `[null]` → `... IS NULL`;
- `[null]` + `not: true` → `... IS NOT NULL`;
- `[10,null]` → `(... IN (10) OR ... IS NULL)`;
- `[10,null]` + `not: true` → `(... NOT IN (10) AND ... IS NOT NULL)`: `not` отрицает всю исходную группу, а не каждую ветку с сохранением `OR`.

Тип значения берётся из `data_type` Меры в метаданных набора; клиент тип не передаёт и не переопределяет. Поддержанные значения `data_type`: `string`, `number`, `integer`, `date`, `datetime`. Пустой или неизвестный `data_type` при фильтрации по Мере является контролируемой ошибкой. Каждое ненулевое значение при обычном сравнении должно проверяться на соответствие `data_type` Меры и передаваться в общий механизм формирования SQL-значений. Для `like_*` / `likeic_*` действует описанное выше правило подстроки.
Для элемента Меры в `where` сохраняется поле `lvl` (уровень) по текущему контракту фильтра обычного поля.
Если в `where` передана агрегированная Мера с `aggregation_kind = 1`, backend должен вернуть контролируемую ошибку:
\*\*«Агрегированная Мера не может использоваться в WHERE. Используйте HAVING-фильтр»\*\*
или эквивалентное по смыслу сообщение.
---
#### 8. Подстановка в `HAVING`.
Если объект `type = "measure"` находится в структурной части `having`, backend должен:
- разрешать использование только агрегированных Мер с `aggregation_kind = 1`;
- раскрыть выражение Меры;
- построить предикат фильтрации по тому же контракту `values` / `operators` / `not` / `logicOr`, что и в `where` и для обычного поля, — единый контракт условия, с fail-closed валидацией;
- добавить предикат в `HAVING` итогового внешнего запроса;
- объединять несколько условий `HAVING` по текущим правилам backend-а, базово через `AND`, если иной режим не задан существующим контрактом.
##### Пример SQL-семантики:
```sql

HAVING
  (SUM("revenue") - SUM("cost")) > :value_1

```
Элемент Меры в `having` описывается тем же условием `values` / `operators` / `not` / `logicOr` (с элементом `null` для проверки на пустое значение) и с тем же allowlist операторов, что и в разделе 7; тип значения берётся из `data_type` Меры.
Имя `condition` в контракте `having` относится к строке верхнего уровня: `having.condition` — текущая и единственная форма HAVING для обычных и вычисляемых полей, которую формирует frontend. Элементы фильтра по Мере лежат в `having.items[]` (либо принимаются backend-ом в дополнительной форме прямого массива `having`) и несут структурное условие `values` / `operators`, а не поле `condition`.
Поддержка Мер не должна ломать текущую обработку `having.condition`. При совместном наличии `condition` и `items` обе части объединяются через `AND`.
Если в `having` передана неагрегированная Мера с `aggregation_kind = 0`, backend должен вернуть контролируемую ошибку:
\*\*«Неагрегированная Мера не может использоваться в HAVING. Используйте WHERE-фильтр»\*\*
или эквивалентное по смыслу сообщение.
Уровень-специфичная логика `HAVING` для сводной таблицы (`target_dimensions`, CND, `depth`) не входит в базовый объём этой Истории и реализуется связанной задачей. Базовый элемент `having.items[]` не должен неявно интерпретировать эти параметры.
---
#### 9. Подстановка в `ORDER BY`.
Если объект `type = "measure"` находится в блоке `order`, backend должен:
- найти и раскрыть выражение Меры;
- применить направление сортировки из `direction` по текущим правилам: `asc`, `desc` или значение по умолчанию;
- если эта же Мера уже присутствует в `select` с техническим alias, использовать текущую стратегию SQL-builder-а: сортировку по alias результата либо по раскрытому выражению;
- если Мера присутствует только в `order`, не добавлять её автоматически в результат запроса, если текущая логика сортировки по обычным полям этого не требует;
- проверять, что выражение Меры допустимо для итогового SQL-контекста сортировки.
Если сортировка по Мере не может быть корректно построена для текущего SQL-контекста, backend должен вернуть контролируемую ошибку с указанием Меры и причины.
---
#### 10. Совместимость с обычными и вычисляемыми полями.
Добавление поддержки `type = "measure"` не должно менять обработку:
- обычных полей, где `type` отсутствует или отличается от `measure`;
- вычисляемых полей визуализации, которые используют `calc`;
- агрегирования обычных полей через `aggr` / `agg`;
- фильтров по обычным полям в `where` с `values`;
- текущих строковых условий `having.condition` для обычных и вычисляемых полей;
- запросов справочников с `distinct = 1`, `limit = 0`, `select`, `order` и пустыми `group` / `where`.
Для runtime-элементов без `type = "measure"` backend должен использовать текущую логику без изменений.
---
#### 11. Валидации и контролируемые ошибки.
Backend должен вернуть контролируемую ошибку и не выполнять SQL-запрос, если:
- runtime-элемент содержит `type = "measure"`, но `name` не передан;
- Мера с указанным `name` не найдена в `measures` текущего набора данных;
- при наличии `datasetId` он не соответствует текущему набору данных или текущему допустимому контексту;
- найденная Мера имеет любой статус, отличный от `valid`;
- выражение Меры ссылается на отсутствующую или невалидную Меру;
- при раскрытии выражений обнаружена циклическая зависимость;
- агрегированная Мера используется в `group` или `where`;
- неагрегированная Мера используется в `having`;
- условие фильтра по Мере некорректно: `values` отсутствует или является пустым массивом; `null` передан вместе с непустым `operators`; массив `operators` не пуст и его длина не равна длине `values`; оператор вне allowlist; значение обычного сравнения не соответствует `data_type` Меры; `data_type` пуст или неизвестен;
- итоговый SQL с раскрытой Мерой не может быть построен или не проходит проверку SQL-семантики.
Сообщение ошибки должно быть пригодно для отображения пользователю и диагностики аналитиком. Рекомендуемый минимальный состав технических деталей ошибки:
| Поле | Описание |
|---|---|
| `measure_name` | `name` Меры, из-за которой возникла ошибка |
| `runtime_block` | Блок runtime payload: `select`, `group`, `where`, `having`, `order` |
| `reason` | Краткая причина ошибки |
| `status_message` | Сообщение из метаданных Меры, если ошибка связана со статусом, отличным от `valid` |
Пример сообщения:
\*\*«Мера "Мера.Валовая\_прибыль" не может быть использована в WHERE, так как она помечена как агрегированная»\*\*.
---
#### 12. Формирование условий.
Backend должен:
- использовать выражение Меры только из сохранённых метаданных набора данных;
- не использовать выражение, переданное frontend-ом в runtime payload;
- обрабатывать технические alias результата по общим правилам SQL-builder-а;
- использовать allowlist операторов для фильтров по Мере: `=`, `!=`, `<>`, `>`, `>=`, `<`, `<=` и семейство `like_*` / `likeic_*`;
- брать тип значения обычного сравнения из `data_type` Меры, отклонять пустой / неизвестный тип и передавать значения через общий механизм SQL-builder-а; значения `like_*` / `likeic_*` обрабатывать как подстроки;
- не выводить секреты, токены, пароли или параметры подключений в ошибках SQL.
---
#### 13. Производительность и кэширование в рамках запроса.
При обработке одного runtime-запроса backend должен:
- читать метаданные текущего набора данных один раз или переиспользовать уже загруженное состояние;
- строить индекс Мер по `name` для быстрого поиска;
- раскрывать каждую используемую Меру один раз и переиспользовать результат раскрытия в рамках запроса;
- не выполнять отдельный запрос к метаданным для каждого использования одной и той же Меры;
- не копировать раскрытое выражение Меры в метаданные визуализации или в определение Меры.
Если выражение Меры изменено в настройках набора данных, следующий runtime-запрос визуализации должен использовать актуальное выражение из метаданных набора данных.
----
### Логика генерации SQL.
Продуктовым требованием является не конкретная форма SQL, а корректная SQL-семантика и совместимость с текущим SQL-builder портала.
Для \*\*произвольного\*\* набора данных итоговый запрос должен строиться как внешний запрос над базовым SQL набора данных либо эквивалентным текущим способом:
```sql

SELECT
  <обычные поля и вычисляемые поля>,
  <раскрытые выражения Мер из select> AS <runtime_alias>
FROM (
  <SQL произвольного набора данных>
) AS __base
WHERE
  <обычные WHERE-фильтры>
  [AND <условия по неагрегированным Мерам из where>]
GROUP BY
  <обычные группировки>
  [, <раскрытые выражения неагрегированных Мер из group>]
HAVING
  <обычные HAVING-условия>
  [AND <условия по агрегированным Мерам из having>]
ORDER BY
  <обычные сортировки>
  [, <сортировки по Мерам из order>]

```
Если текущий SQL-builder использует иной порядок сборки, временные alias, подзапросы или CTE, это допустимо при условии, что результат запроса и SQL-семантика соответствуют требованиям.
----
### Обратная совместимость и ограничения.
- Существующие визуализации без Мер должны продолжить формировать SQL и возвращать данные без изменений.
- Существующие runtime payload, где `having` передан как объект {{ {"condition": ""} }}, должны продолжить обрабатываться без ошибки.
- Отсутствие массива `measures` в старых метаданных набора данных должно трактоваться как пустой список Мер.
- Если в runtime payload нет объектов `type = "measure"`, новая логика раскрытия Мер не должна влиять на результат.
- Меры поддерживаются только для \*\*произвольных\* наборов данных. Для простых и составных наборов данных объект `type = "measure"` в runtime payload должен приводить к контролируемой ошибке.
- Существующие вычисляемые поля визуализаций не переводятся автоматически в Меры и продолжают работать через `calc`.
- В рамках этой Истории не вводятся новые роли и права. Запрос данных использует текущую модель прав доступа к набору данных / отчёту.

### Предположения:
- Runtime-запросы данных визуализаций продолжают использовать endpoint `/v1/api/recordsets/<dataset_id>`.
- Для построения SQL визуализаций используется общий backend-механизм, который уже обрабатывает `group`, `select`, `where`, `having`, `order`, `variables`, `series` для обычных полей и вычисляемых полей.
- На окружении, где используются Меры, включён новый построитель: `server.use_new_builder = enabled`. Выключенный новый построитель не является режимом частичной поддержки Мер и должен давать контролируемый отказ.
- На момент реализации первого backend-шага массив `measures` уже доступен при чтении метаданных \*\*произвольного\* набора данных.
- Уровень-специфичный `HAVING` для сводной таблицы реализуется отдельной связанной задачей.

### Критерии приёмки (AC):
\*\*AC.1\*\* — Backend обрабатывает Меру в `select`:
- \*\*Дано:\* в runtime payload `/v1/api/recordsets/<dataset_id>` в блоке `select` передан объект `type = "measure"` с существующим `name` валидной Меры;
- \*\*Когда:\* backend строит SQL-запрос;
- \*\*Тогда:\* backend находит Меру в `datasets.measures`, раскрывает её `expression` и добавляет выражение в `SELECT`;
- \*\*И:\* результат возвращается с техническим alias из runtime payload, например `[values][0]`.
\*\*AC.2\*\* — Backend не использует frontend-поля как источник выражения Меры:
- \*\*Дано:\* runtime-объект Меры содержит `type = "measure"`, `name`, `alias` и дополнительные поля `fieldAlias`, `calc`, `export`;
- \*\*Когда:\* backend раскрывает Меру;
- \*\*Тогда:\* источником SQL-выражения является только `expression` из метаданных найденной Меры;
- \*\*И:\* `alias` runtime payload используется только как технический alias результата.
\*\*AC.3\*\* — Неагрегированная Мера используется в `group`:
- \*\*Дано:\* в блоке `group` передана Мера с `aggregation_kind = 0` и `status = "valid"`;
- \*\*Когда:\* backend строит SQL;
- \*\*Тогда:\* раскрытое выражение Меры добавляется в `GROUP BY`;
- \*\*И:\* если эта же Мера передана в `select`, результат возвращается с соответствующим runtime alias.
\*\*AC.4\*\* — Агрегированная Мера не допускается в `group`:
- \*\*Дано:\* в блоке `group` передана Мера с `aggregation_kind = 1`;
- \*\*Когда:\* backend валидирует runtime payload;
- \*\*Тогда:\* запрос не выполняется;
- \*\*И:\* backend возвращает контролируемую ошибку о невозможности использовать агрегированную Меру в `GROUP BY`.
\*\*AC.5\*\* — Неагрегированная Мера используется в `where`:
- \*\*Дано:\* в блоке `where` передана Мера с `aggregation_kind = 0` и условием в формате `values` / `operators`;
- \*\*Когда:\* backend строит SQL;
- \*\*Тогда:\* раскрытое выражение Меры используется в предикате `WHERE`;
- \*\*И:\* оператор берётся из allowlist, а значение обычного сравнения проверяется по `data_type` Меры и передаётся в общий механизм SQL-builder-а.
\*\*AC.6\*\* — Агрегированная Мера не допускается в `where`:
- \*\*Дано:\* в блоке `where` передана Мера с `aggregation_kind = 1`;
- \*\*Когда:\* backend валидирует runtime payload;
- \*\*Тогда:\* запрос не выполняется;
- \*\*И:\* backend возвращает контролируемую ошибку о необходимости использовать `HAVING` для агрегированной Меры.
\*\*AC.7\*\* — Агрегированная Мера используется в `having`:
- \*\*Дано:\* в структурной части `having` передана Мера с `aggregation_kind = 1` и условием в формате `values` / `operators`;
- \*\*Когда:\* backend строит SQL;
- \*\*Тогда:\* раскрытое выражение Меры используется в предикате `HAVING`;
- \*\*И:\* `having.condition` остаётся единственной строковой формой HAVING для обычных и вычисляемых полей;
- \*\*И:\* при совместной форме `{condition, items}` строковое условие и условия Мер объединяются через `AND`.
\*\*AC.8\*\* — Неагрегированная Мера не допускается в `having`:
- \*\*Дано:\* в `having` передана Мера с `aggregation_kind = 0`;
- \*\*Когда:\* backend валидирует runtime payload;
- \*\*Тогда:\* запрос не выполняется;
- \*\*И:\* backend возвращает контролируемую ошибку о необходимости использовать `WHERE` для неагрегированной Меры.
\*\*AC.9\*\* — Сортировка по Мере:
- \*\*Дано:\* в блоке `order` передана валидная Мера и `direction = "desc"`;
- \*\*Когда:\* backend строит SQL;
- \*\*Тогда:\* backend добавляет сортировку по раскрытому выражению Меры или по alias результата в соответствии с текущей стратегией SQL-builder-а;
- \*\*И:\* Мера не добавляется в результат запроса только из-за присутствия в `order`, если текущая логика обычных полей этого не требует.
\*\*AC.10\*\* — Раскрытие Меры, ссылающейся на другую Меру:
- \*\*Дано:\* Мера `Мера.Маржинальность` использует в выражении ссылку `"Мера.Валовая_прибыль"`;
- \*\*Когда:\* frontend передаёт `Мера.Маржинальность` в runtime payload;
- \*\*Тогда:\* backend рекурсивно раскрывает зависимую Меру и строит SQL с итоговым выражением;
- \*\*И:\* выражения оборачиваются в скобки так, чтобы сохранялся приоритет операций.
\*\*AC.11\*\* — Ошибка при невалидной или отсутствующей Мере:
- \*\*Дано:\* runtime payload содержит `type = "measure"` с `name`, которого нет в метаданных набора данных, или Мера имеет статус, отличный от `valid`;
- \*\*Когда:\* backend валидирует запрос данных;
- \*\*Тогда:\* SQL-запрос не выполняется;
- \*\*И:\* backend возвращает контролируемую ошибку с `measure_name`, runtime-блоком и причиной ошибки.
\*\*AC.12\*\* — Защита от циклических зависимостей при runtime-раскрытии:
- \*\*Дано:\* в метаданных повреждён граф зависимостей Мер и при раскрытии возникает цикл;
- \*\*Когда:\* backend обрабатывает runtime-запрос;
- \*\*Тогда:\* запрос не выполняется;
- \*\*И:\* backend возвращает контролируемую ошибку о циклической зависимости.
\*\*AC.13\*\* — Совместимость запросов без Мер:
- \*\*Дано:\* существующая визуализация отправляет runtime payload только с обычными полями и вычисляемыми полями;
- \*\*Когда:\* backend обрабатывает запрос после внедрения поддержки Мер;
- \*\*Тогда:\* сформированный SQL и результат запроса не меняются по сравнению с текущим поведением.
\*\*AC.14\*\* — Совместимость текущего `having.condition`:
- \*\*Дано:\* визуализация отправляет `having` в формате {{ {"condition": ""} }} или со строковым условием по обычным / вычисляемым полям;
- \*\*Когда:\* backend обрабатывает запрос;
- \*\*Тогда:\* запрос обрабатывается по текущей логике без ошибки;
- \*\*И:\* поддержка структурных условий по Мерам не заменяет и не ломает строковый формат `having.condition`.
\*\*AC.15\*\* — Меры доступны только для произвольных наборов данных:
- \*\*Дано:\* runtime payload для простого или составного набора данных содержит объект `type = "measure"`;
- \*\*Когда:\* backend валидирует запрос данных;
- \*\*Тогда:\* SQL-запрос не выполняется;
- \*\*И:\* backend возвращает контролируемую ошибку о неподдержанности Мер для данного типа набора данных.
\*\*AC.16\*\* — Валидация условий фильтрации:
- \*\*Дано:\* фильтр по Мере содержит пустой / отсутствующий `values`, оператор вне allowlist, `null` вместе с непустым `operators`, рассогласование длин `values` / `operators`, значение обычного сравнения не по типу Меры либо пустой / неизвестный `data_type`;
- \*\*Когда:\* backend валидирует условие фильтра по Мере;
- \*\*Тогда:\* запрос не выполняется;
- \*\*И:\* backend возвращает контролируемую ошибку валидации.
- \*\*Но:\* `like_*` / `likeic_*` входят в allowlist; их значение трактуется как искомая подстрока и не проверяется по `data_type` Меры.
\*\*AC.17\*\* — Семантика `null` и `not`:
- \*\*Дано:\* фильтр по Мере передан в форме списка без `operators`;
- \*\*Тогда:\* `[null]` строит `IS NULL`, `[null]` с `not: true` — `IS NOT NULL`, `[10,null]` — `IN (10) OR IS NULL`;
- \*\*И:\* `[10,null]` с `not: true` строит `NOT IN (10) AND IS NOT NULL`, то есть отрицание всей исходной группы;
- \*\*И:\* сочетание `null` с непустым `operators` отклоняется контролируемой ошибкой.
\*\*AC.18\*\* — Новый построитель является обязательным:
- \*\*Дано:\* runtime payload содержит объект `type = "measure"`, а `server.use_new_builder` выключен;
- \*\*Когда:\* backend обрабатывает запрос данных;
- \*\*Тогда:\* SQL-запрос не выполняется;
- \*\*И:\* backend возвращает контролируемую ошибку о том, что Меры поддерживаются только новым построителем.
----
### Сводка изменений относительно предыдущей редакции.
Редакция уточняет форму и валидацию условия фильтра по Мере, каноническую передачу HAVING и обязательность нового построителя. Раскрытие выражения Меры, подстановка в `SELECT` / `GROUP BY` / `ORDER BY`, защита от циклов, производительность, обратная совместимость, роли и права — без изменений.
#### Что изменилось.
- Условие фильтра по Мере в `where` и в `having` — вместо структуры `condition { operator, value, value_type }` тот же контракт `values` / `operators` / `not` / `logicOr` с элементом `null`, что и у фильтра обычного поля (разделы 7, 8).
- Поле `value_type` из payload убрано: тип значения берётся из `data_type` Меры в метаданных набора (разделы 8, 12).
- Операторы `in` и `between` больше не передаются отдельными ключами: `in` выражается списком `values` без `operators`, `between` — парой `>=` / `<=` (раздел 7).
- `null` разрешён только в форме списка без `operators`; семантика `not + null` определена как отрицание всей группы.
- `like_*` / `likeic_*` входят в общий allowlist Мер и используют значение как искомую подстроку без проверки по `data_type`.
- Критерии приёмки AC.5, AC.7, AC.16–AC.18 переформулированы под контракт `values` / `operators`.
#### Что сохранено без изменений.
- Маршрутизация по `aggregation_kind`: неагрегированная Мера → `where`, агрегированная → `having`.
- Backend принимает три формы блока `having`; `having.condition` остаётся текущей и единственной формой для обычных и вычисляемых полей, а frontend при Мерах канонически формирует `{condition, items}`.
- Запрет `calc` / `aggr` как источника выражения Меры; раскрытие выражения только из метаданных набора.
- Обратная совместимость запросов без Мер и общий fail-closed принцип ошибок для Мер.
#### Сводка «было → стало».
| Аспект | Прежняя редакция | Настоящая редакция |
|---|---|---|
| Условие фильтра Меры | `condition { operator, value, value_type }` | `values` / `operators` / `not` / `logicOr` / `null` |
| Тип значения | `value_type` в payload | из `data_type` Меры, `value_type` нет |
| `in` | оператор `in` | `values` без `operators` |
| `between` | оператор `between` | пара `>=` / `<=` |
| `not in` | не выразимо | `values` + `not` |
| ИЛИ / проверка на пусто | не выразимо | `logicOr: 1` / элемент `null` |
| Единство с обычным полем | отдельный формат | один контракт условия |
