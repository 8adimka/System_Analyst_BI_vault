h3. Контекст и цель истории.
Полное описание продуктовой логики приведено в Эпике по Мерам ([https://jira.modusbi.ru/browse/MB-4364]).

Настоящая История описывает внедрение Мер в визуализацию — *«Диаграмму столбчатую»* (текущий тип конфигурации: {{chartType = "barChart"}}, {{visualType = "column"}}).

На предыдущих шагах реализованы:
* Шаг 1 (набор данных): хранение Мер в метаданных произвольного набора данных, CRUD-контракты, отображение Мер в настройках набора данных и редактор выражений Мер.
* Backend-Шаг 1: API хранения и управления Мерами в объекте {{datasets}}.
* Backend-Шаг 2: поддержка {{type = "measure"}} в runtime payload запросов данных, раскрытие {{expression}} Меры при построении SQL.
* Frontend-Шаг 1: отображение секции «Меры» в левой панели набора данных, визуальное различие пилюль Мер.
* Контракты Мер: зафиксированные правила связи, runtime-структуры и модель данных Меры.

В рамках этой Истории требуется подключить Меры к пользовательским сценариям *столбчатой диаграммы*: отображение Мер в левой панели конструктора, размещение Мер на полках диаграммы, использование в совместимых настройках, сохранение ссылок в метаданных визуализации и формирование корректного runtime payload для backend-а по уже описанным контрактам.

Визуализация не хранит полное определение Меры. В конфигурации диаграммы и runtime payload сохраняется ссылка на Меру по {{type = "measure"}}, {{name}} и {{datasetId}}. Поля {{alias}}, {{expression}}, {{aggregation_kind}}, {{data_type}}, {{status}} и {{status_message}} должны браться из актуальных метаданных набора данных.

h3. Цель задачи.
*Требуется:*
# Добавить поддержку Мер в визуализацию *«Диаграмма столбчатая»* для использования на полках визуализации и в совместимых настройках, где допускаются обычные и вычисляемые поля.
# Сохранить согласованность с общими контрактами Мер: связь по {{name}}, признак {{type = "measure"}}, отсутствие копирования {{expression}} в визуализацию, валидация по {{aggregation_kind}} и {{status}}.
# Обеспечить корректное формирование runtime payload для {{/v1/api/recordsets/<dataset_id>}} так, чтобы backend мог раскрыть Меры и встроить их в {{SELECT}}, {{GROUP BY}}, {{WHERE}}, {{HAVING}} и {{ORDER BY}}.
# Не изменить поведение существующих столбчатых диаграмм, если в них не используются Меры.

_Пользовательская история:_
Как аналитик, я хочу использовать Меры в столбчатой диаграмме так же удобно, как поля и вычисляемые поля, чтобы переиспользовать единые бизнес-показатели набора данных без дублирования формул внутри каждой визуализации.

h3. 1. Границы истории.
h4. 1.1. В рамках истории реализуется.
* Отображение секции *«Меры»* в стандартной левой панели конструктора для визуализации «Диаграмма столбчатая».
* Включение секции *«Меры»* только для столбчатой диаграммы на текущем шаге, даже если технически дорабатывается общий компонент левой панели.
* Drag-and-drop валидных Мер на полки:
** *«Значения»* ({{name = "values"}});
** *«Категории»* ({{name = "categories"}});
** *«Серии»* ({{name = "series"}});
** *«Фильтры»* ({{name = "filters"}}).
* Поддержка Мер на дополнительной оси значений {{valuesExtra}}.
* Использование Мер в совместимых селекторах правой панели настроек столбчатой диаграммы, где выбираются поля или вычисляемые поля.
* Использование Мер в вычисляемых полях виджета ({{calc}}) столбчатой диаграммы.
* Отображение Мер на полках и в настройках по {{alias}} с визуальным отличием от обычных полей (тёмно-оранжевый цвет пилюли).
* Отображение ярлыка {{AGR}} для Мер с {{aggregation_kind = 1}}.
* Обработка Мер со статусом {{invalid}} в конструкторе и при построении диаграммы.
* Сохранение размещения Мер в метаданных диаграммы по {{type = "measure"}}, {{name}}, {{datasetId}} и локальному {{id}} размещения.
* Формирование runtime payload с объектами {{type = "measure"}} для backend-а.
* Поддержка сортировки по Мере на полке «Значения».
* Поддержка экспорта столбчатой диаграммы с Мерами через текущий общий механизм экспорта.
* Обратная совместимость существующих диаграмм без Мер.

h4. 1.2. В рамках истории не реализуется.
* Создание, редактирование и удаление Мер в настройках набора данных.
* Поддержка Мер для *простых* и *составных* наборов данных.
* Распространение пользовательской доступности Мер на другие визуализации, кроме «Диаграммы столбчатой».
* Изменение базовой модели хранения {{report.grid}} и нормализация списка используемых полей в отдельный индекс.
* Изменение SQL-выражения Меры на уровне полки визуализации.
* Ручное изменение {{aggregation_kind}} на полке визуализации.
* Автоматическое преобразование существующих вычисляемых полей столбчатых диаграмм в Меры.
* Уровень-специфичная логика {{HAVING}} для сводной таблицы ({{target_dimensions}}, CND, {{depth}}).

h3. 2. Исходные правила модели Мер.
* Мера доступна только для *произвольного* набора данных.
* Мера хранится в метаданных набора данных в массиве {{measures}}.
* Ключом связи является {{name}} Меры.
* {{alias}} используется только для отображения пользователю и не является ключом связи.
* {{id}} из {{measures[]}} не используется как внешний ключ в визуализациях.
* Локальный {{id}} пилюли в визуализации является идентификатором размещения, а не идентификатором Меры из набора данных.
* {{expression}} Меры не копируется в конфигурацию диаграммы и не передаётся frontend-ом в runtime payload.
* Для Мер со {{status = "invalid"}} новое размещение на полках и выбор в селекторах недоступны.
* Если уже сохранённая диаграмма ссылается на Меру, которая стала {{invalid}} или отсутствует в наборе данных, связь по {{name}} сохраняется. Построение диаграммы блокируется понятной ошибкой только если эта Мера участвует в активной полке или настройке, попадающей в runtime payload.

Пример определения Меры в наборе данных:
{code:json}
{
  "id": "847b1ec3-bbf8-4365-85fb-c4fca2a06e2e",
  "name": "Мера.Валовая_прибыль",
  "alias": "Валовая прибыль",
  "description": "Разница между выручкой и себестоимостью",
  "expression": "SUM(\"revenue\") - SUM(\"cost\")",
  "aggregation_kind": 1,
  "data_type": "number",
  "hierarchy": "Финансовые показатели",
  "level": 10,
  "status": "valid",
  "status_message": ""
}
{code}

h3. 3. Описание текущего поведения.
Сейчас в конструкторе столбчатой диаграммы пользователь работает с обычными полями набора данных и вычисляемыми полями виджета.

Стандартная левая панель содержит секцию с полями набора данных, но не содержит отдельную секцию *«Меры»*. Пользователь не может перетащить Меру на полки диаграммы и не может выбрать Меру в настройках визуализации.

Для столбчатой диаграммы используются основные полки:
* *«Значения»* ({{name = "values"}}) — задаёт показатели, отображаемые столбцами. На полке есть режим-тумблер:
** *«Первое»* — для отображения используется только первая активная пилюля полки;
** *«Все»* — для отображения используются все активные пилюли полки.
* *«Категории»* ({{name = "categories"}}) — задаёт разбиение по категориям. Активно используется только первая пилюля полки.
* *«Серии»* ({{name = "series"}}) — задаёт дополнительное разбиение внутри категорий. На полке есть режим-тумблер:
** *«Вкл»* — пилюли полки участвуют в построении диаграммы;
** *«Выкл»* — пилюли полки сохраняются в настройках, но не влияют на визуализацию и runtime payload.
* *«Фильтры»* ({{name = "filters"}}) — задаёт фильтрацию данных визуализации.
* *Дополнительная ось значений* ({{name = "valuesExtra"}}) — опциональная вторая ось значений, по умолчанию отключена ({{enabled = false}}).

В текущем runtime-запросе столбчатой диаграммы frontend формирует универсальные блоки:
* {{group}} — группировки для категорий и серий;
* {{select}} — возвращаемые значения и поля группировки;
* {{where}} — фильтры до группировки;
* {{having}} — условия после группировки;
* {{order}} — сортировка;
* {{series}} — текущий режим серий.

Backend уже умеет обрабатывать обычные поля и вычисляемые поля в этих блоках, поддержка {{type = "measure"}} реализована в рамках Backend-Шага 2.

h3. 4. Описание целевого поведения.
После реализации Истории пользователь должен иметь возможность открыть столбчатую диаграмму на основе *произвольного* набора данных и использовать валидные Меры этого набора данных в тех же пользовательских сценариях, где для данной диаграммы допустимы обычные поля и вычисляемые поля.

Целевое поведение:
# В левой панели столбчатой диаграммы под секцией *«Поля»* отображается секция *«Меры»*.
# В секции *«Меры»* отображаются только Меры текущего произвольного набора данных.
# Валидные Меры можно перетаскивать на совместимые полки диаграммы.
# Невалидные Меры отображаются, но недоступны для добавления.
# Мера на полке отображается по {{alias}}, но в метаданных хранится связь по {{name}}.
# Для Мер с {{aggregation_kind = 1}} отображается ярлык {{AGR}}.
# Меры доступны в совместимых селекторах правой панели настроек столбчатой диаграммы.
# Runtime payload передаёт backend-у объекты {{type = "measure"}} без копирования {{expression}}.
# Backend раскрывает выражение Меры и строит SQL по правилам Backend-Шага 2.
# Если активно используемая Мера становится невалидной после изменения набора данных или самой Меры, диаграмма переходит в error-состояние до исправления.

h3. 5. Требования к интерфейсу.
h4. 5.1. Левая панель конструктора.
Для столбчатой диаграммы на основе *произвольного* набора данных левая панель должна содержать:
* секцию *«Поля»* — текущее поведение без изменения;
* секцию *«Меры»* — новая секция ниже секции «Поля».

Технически допускается доработка общего компонента левой панели, но на текущем этапе секция *«Меры»* должна быть включена только для визуализации {{chartType = "barChart"}} / {{visualType = "column"}} через явный признак доступности или иной контролируемый механизм.

Для *простых* и *составных* наборов данных секция *«Меры»* в конструкторе столбчатой диаграммы не отображается.

h4. 5.2. Отображение списка Мер.
В секции *«Меры»*:
* отображается {{alias}} Меры;
* для агрегированных Мер ({{aggregation_kind = 1}}) отображается ярлык {{AGR}};
* Меры группируются по {{hierarchy}}, если поле заполнено;
* внутри группы Меры сортируются по {{level}} по возрастанию, затем по {{alias}};
* Меры без {{hierarchy}} отображаются в корневом уровне секции;
* tooltip при наведении содержит:
** {{description}}, если заполнено;
** {{data_type}};
** полный текст {{expression}};
** системное {{name}} как справочную техническую информацию;
** {{status_message}}, если Мера невалидна.

Если в левой панели есть поиск по полям, поиск должен находить Меры по {{alias}} и {{name}} (логика {{OR}}) и визуально отличать Меры от обычных полей.

h4. 5.3. Визуальное отличие Меры.
На полках диаграммы Мера отображается как отдельный тип пилюли:
* на полках *«Значения»*, *«Категории»*, *«Серии»* и {{valuesExtra}} — цвет пилюли Меры тёмно-оранжевый, иконка визуально отличается от обычного поля;
* на полке *«Фильтры»* — Мера отображается как фильтрующая пилюля с явным признаком типа *«Мера»* и ярлыком {{AGR}} для агрегированных Мер;
* в tooltip пилюли выводится {{alias}}, {{name}}, {{data_type}}, признак агрегированности и {{description}}, если оно заполнено.

h4. 5.4. Drag-and-drop.
Мера перетаскивается из секции *«Меры»* на полки аналогично обычному полю.

При попытке разместить Меру на несовместимую полку:
* размещение блокируется;
* пользователь видит визуальный запрет (недопустимый курсор или подсветка);
* пользователь получает причину блокировки согласно матрице допустимости (раздел 6).

Одна и та же Мера может быть размещена на нескольких полках одной диаграммы, если каждое размещение совместимо.

h4. 5.5. Поведение Мер со статусом {{invalid}}.
Если {{status = "invalid"}}:
* в секции *«Меры»* элемент отображается с error-иконкой;
* drag-and-drop на полки заблокирован;
* выбор в совместимых селекторах заблокирован;
* tooltip показывает {{status_message}};
* если Мера уже размещена на активной полке сохранённой диаграммы или выбрана в активной настройке, пилюля остаётся на месте, отображается в error-состоянии, а запрос данных диаграммы не выполняется.

Сообщение пользователю должно содержать {{alias}} Меры и причину, например:
*«Мера "Валовая прибыль" не может быть использована: поле "revenue" не найдено в текущем составе полей набора данных»*.

h3. 6. Правила использования Мер на полках столбчатой диаграммы.
h4. 6.1. Общая матрица допустимости.
|| Полка столбчатой диаграммы || Runtime-контекст || {{aggregation_kind = 0}} || {{aggregation_kind = 1}} || Примечание ||
| *Значения* ({{values}}) | {{select}} | Допускается, с предупреждением | Допускается | Для {{aggregation_kind = 0}} — предупреждение об изменении детализации |
| *Значения* ({{valuesExtra}}) | {{select}} | Допускается, с предупреждением | Допускается | Аналогично полке «Значения» |
| *Категории* ({{categories}}) | {{group}} + {{select}} | Допускается | Блокируется | Только первая пилюля активна |
| *Серии* ({{series}}) | {{group}} + {{select}} | Допускается | Блокируется | Только при режиме «Вкл» |
| *Фильтры WHERE* | {{where}} | Допускается | Блокируется | Только неагрегированные |
| *Фильтры HAVING* | {{having}} | Блокируется | Допускается | Только агрегированные |

h4. 6.2. Полка «Значения».
На полке *«Значения»* Меры используются как показатели, отображаемые столбцами диаграммы.

*Режим «Первое»:* в runtime payload попадает только первая активная пилюля полки «Значения». Если первая активная пилюля является Мерой, она передаётся в {{select}} как объект {{type = "measure"}}.

*Режим «Все»:* в runtime payload попадают все активные пилюли полки «Значения». Каждая Мера передаётся отдельным объектом {{type = "measure"}} в {{select}}. Каждое обычное поле передаётся по текущим правилам.

Для агрегированной Меры ({{aggregation_kind = 1}}) дополнительная агрегирующая функция ({{aggr}} / {{agg}}) не применяется — выражение Меры уже содержит агрегацию.

Для неагрегированной Меры ({{aggregation_kind = 0}}) frontend показывает пользователю предупреждение:
*«Мера "[alias]" является неагрегированной. Убедитесь, что её использование в значениях диаграммы даст корректный результат»*.

Предупреждение не блокирует размещение и не препятствует построению диаграммы.

*Поддержка valueType = "tooltip":* если пилюля Меры на полке «Значения» имеет {{valueType = "tooltip"}}, она обрабатывается по существующей логике tooltip-пилюль. Если текущая реализация не поддерживает {{valueType = "tooltip"}} для вычисляемых полей, поведение Мер должно быть аналогичным обычным полям и вычисляемым полям в этом контексте.

h4. 6.3. Полка «Категории».
На полке *«Категории»* Мера используется как вычисляемое измерение для разбиения данных.

Активно используется только первая пилюля полки. Если первая пилюля является Мерой, она передаётся одновременно в {{group}} и в {{select}} с техническим alias {{[categories]}}.

Агрегированные Меры ({{aggregation_kind = 1}}) на полке «Категории» блокируются при drag-and-drop. Пользователь получает сообщение:
*«Агрегированная Мера не может использоваться как категория»*.

h4. 6.4. Полка «Серии».
На полке *«Серии»* Мера используется как вычисляемая серия для дополнительного разбиения данных внутри категорий.

Агрегированные Меры ({{aggregation_kind = 1}}) на полке «Серии» блокируются. Пользователь получает сообщение:
*«Агрегированная Мера не может использоваться как серия»*.

*Режим «Вкл»:* если режим «Серии» включён и на полке есть неагрегированные Меры, frontend передаёт каждую активную Меру серии в {{group}} с техническим alias соответствующей позиции серии.

*Режим «Выкл»:* Меры с полки «Серии» не попадают в {{group}}, {{select}} или {{order}}.

h4. 6.5. Полка «Фильтры».
Мера на полке *«Фильтры»* отображается в виде пилюли фильтра с обозначением типа «Мера».

При клике на пилюлю открывается окно настройки фильтра со следующими полями:
* *Режим фильтра* ({{filter.mode}}): {{WHERE}} или {{HAVING}} — автоматически выбирается на основании {{aggregation_kind}} Меры и недоступен для ручного изменения:
** для {{aggregation_kind = 0}} — всегда {{WHERE}}, выбор {{HAVING}} заблокирован;
** для {{aggregation_kind = 1}} — всегда {{HAVING}}, выбор {{WHERE}} заблокирован.
* *Условие фильтра* ({{condition}}): оператор, значение, тип значения.

Допустимые операторы для фильтра по Мере:
* для числовых ({{data_type = "number"}}): {{=}}, {{!=}}, {{>}}, {{>=}}, {{<}}, {{<=}}, {{between}}, {{in}};
* для строковых ({{data_type = "string"}}): {{=}}, {{!=}}, {{in}}, {{like}};
* для дат ({{data_type = "date"}}): {{=}}, {{!=}}, {{>}}, {{>=}}, {{<}}, {{<=}}, {{between}}.

Фильтр с незаполненным обязательным значением условия считается неактивным и не попадает в runtime payload.

Неагрегированная Мера ({{aggregation_kind = 0}}) передаётся в {{where}} как объект {{type = "measure"}} с полем {{condition}}.

Агрегированная Мера ({{aggregation_kind = 1}}) передаётся в {{having}} как объект {{type = "measure"}} с полем {{condition}} в структурном формате {{having.items}}.

h4. 6.6. Полка «Дополнительная ось значений» (valuesExtra).
Если пользователь включил {{valuesExtra}} ({{enabled = true}}), Меры на этой полке обрабатываются по тем же правилам, что и Меры на полке «Значения», с учётом технического alias дополнительной оси.

h3. 7. Хранение Меры в конфигурации диаграммы.
h4. 7.1. Структура пилюли Меры на полке.
При размещении Меры на полке в массиве {{fields}} соответствующего объекта оси {{axes[]}} сохраняется объект следующей структуры:

{code:json}
{
  "type": "measure",
  "name": "Мера.Валовая_прибыль",
  "datasetId": 244,
  "id": "visual_measure_4f9b7e2d",
  "alias": "Валовая прибыль",
  "valueType": "value"
}
{code}

|| Поле || Обязательность || Описание ||
| {{type}} | Да | Всегда {{measure}} для Мер |
| {{name}} | Да | Системное имя Меры из {{datasets.measures[].name}}. Ключ связи |
| {{datasetId}} | Да | Идентификатор набора данных, которому принадлежит Мера |
| {{id}} | Да | Локальный идентификатор размещения пилюли. Генерируется frontend-ом. Не является идентификатором Меры из набора данных |
| {{alias}} | Нет | {{alias}} Меры из метаданных на момент размещения. Хранится как кэш для отображения при потере связи с набором данных |
| {{valueType}} | Нет | Текущее значение по умолчанию для полки. Для полки «Значения» — {{value}} или {{tooltip}} |

*Важно:* {{alias}} в конфигурации является кэшированным отображаемым значением и не используется как ключ связи. При отображении диаграммы используется актуальный {{alias}} из метаданных набора данных. Если набор данных недоступен — используется кэшированный {{alias}}.

{{expression}}, {{aggregation_kind}}, {{data_type}}, {{status}} и {{status_message}} в конфигурацию диаграммы *не сохраняются*.

h3. 8. Загрузка и обновление Мер при открытии диаграммы.
При открытии конструктора столбчатой диаграммы для *произвольного* набора данных frontend должен:
# Получить актуальные метаданные набора данных, включая массив {{measures}}.
# Построить секцию «Меры» в левой панели из полученного массива {{measures}}.
# Для каждой пилюли Меры в конфигурации диаграммы ({{type = "measure"}}) сопоставить её с актуальными метаданными по {{name}} и {{datasetId}}.
# Если Мера найдена и {{status = "valid"}} — пилюля отображается в рабочем состоянии с актуальным {{alias}}.
# Если Мера найдена, но {{status = "invalid"}} — пилюля отображается в error-состоянии.
# Если Мера не найдена в массиве {{measures}} — пилюля отображается как ошибка отсутствующей Меры. Конфигурация диаграммы при этом не изменяется автоматически.
# Если изменился {{aggregation_kind}} Меры — выполняется перепроверка совместимости размещения с полками. Несовместимая пилюля переходит в error-состояние.

h3. 9. Формирование runtime payload.
h4. 9.1. Общие правила.
Frontend формирует runtime payload для {{/v1/api/recordsets/<dataset_id>}} из активных пилюль полок диаграммы. Для каждой пилюли Меры в payload передаётся минимальный объект:

{code:json}
{
  "type": "measure",
  "name": "Мера.Валовая_прибыль",
  "alias": "[values][0]",
  "id": "visual_measure_4f9b7e2d",
  "fieldAlias": "Валовая прибыль"
}
{code}

|| Поле || Обязательность || Описание ||
| {{type}} | Да | Всегда {{measure}} |
| {{name}} | Да | Системное имя Меры — ключ связи для backend-а |
| {{alias}} | Да для {{select}}, рекомендуется для {{group}} / {{order}} | Технический alias результата запроса, например {{[values][0]}} |
| {{id}} | Нет | Локальный frontend-id пилюли |
| {{fieldAlias}} | Нет | Отображаемый {{alias}} Меры — для диагностики и отладки |
| {{datasetId}} | Нет | Передаётся при наличии для проверки на backend-е |

Frontend *не должен* передавать в runtime payload для Мер поля {{calc}}, {{aggr}}, {{agg}}, {{expression}} как источник выражения Меры.

h4. 9.2. Мера на полке «Значения».

{code:json}
{
  "group": [
    {
      "name": "region",
      "calc": "",
      "alias": "[categories]"
    }
  ],
  "select": [
    {
      "type": "measure",
      "name": "Мера.Валовая_прибыль",
      "alias": "[values][0]",
      "id": "visual_measure_4f9b7e2d",
      "fieldAlias": "Валовая прибыль"
    }
  ],
  "where": [],
  "having": {
    "condition": ""
  },
  "order": [],
  "variables": [],
  "series": {
    "enable": 0
  }
}
{code}

При режиме «Все» и нескольких Мерах на полке «Значения» каждая Мера становится отдельным объектом в {{select}} с порядковым alias {{[values][0]}}, {{[values][1]}} и т.д.

{code:json}
{
  "select": [
    {
      "type": "measure",
      "name": "Мера.Валовая_прибыль",
      "alias": "[values][0]",
      "id": "visual_measure_m1",
      "fieldAlias": "Валовая прибыль"
    },
    {
      "type": "measure",
      "name": "Мера.Выручка",
      "alias": "[values][1]",
      "id": "visual_measure_m2",
      "fieldAlias": "Выручка"
    }
  ]
}
{code}

h4. 9.3. Мера на полке «Категории».
Неагрегированная Мера в качестве категории передаётся одновременно в {{group}} и {{select}}:

{code:json}
{
  "group": [
    {
      "type": "measure",
      "name": "Мера.Сегмент_маржи",
      "alias": "[categories]",
      "id": "visual_measure_cat_a1b2",
      "fieldAlias": "Сегмент маржи"
    }
  ],
  "select": [
    {
      "type": "measure",
      "name": "Мера.Сегмент_маржи",
      "alias": "[categories]",
      "id": "visual_measure_cat_a1b2",
      "fieldAlias": "Сегмент маржи"
    },
    {
      "type": "measure",
      "name": "Мера.Валовая_прибыль",
      "alias": "[values][0]",
      "id": "visual_measure_m1",
      "fieldAlias": "Валовая прибыль"
    }
  ],
  "where": [],
  "having": { "condition": "" },
  "order": [],
  "series": { "enable": 0 }
}
{code}

h4. 9.4. Мера на полке «Серии».
Если режим «Серии» включён и на полке есть неагрегированные Меры, frontend передаёт каждую активную Меру серии в {{group}} с alias текущей позиции серии.

{code:json}
{
  "group": [
    {
      "name": "region",
      "calc": "",
      "alias": "[categories]"
    },
    {
      "type": "measure",
      "name": "Мера.Сегмент_клиента",
      "alias": "[series][0]",
      "id": "visual_measure_series_1",
      "fieldAlias": "Сегмент клиента"
    }
  ],
  "series": {
    "enable": 1
  }
}
{code}

Если режим «Серии» выключен, Меры с полки «Серии» не должны попадать в {{group}}, {{select}} или {{order}}.

h4. 9.5. Мера на полке «Фильтры».
WHERE-фильтр по неагрегированной Мере:

{code:json}
{
  "where": [
    {
      "type": "measure",
      "name": "Мера.Маржа_строки",
      "condition": {
        "operator": ">",
        "value": 0,
        "value_type": "number"
      }
    }
  ],
  "having": {
    "condition": ""
  }
}
{code}

HAVING-фильтр по агрегированной Мере:

{code:json}
{
  "having": {
    "condition": "",
    "items": [
      {
        "type": "measure",
        "name": "Мера.Валовая_прибыль",
        "condition": {
          "operator": ">",
          "value": 0,
          "value_type": "number"
        }
      }
    ]
  }
}
{code}

При наличии legacy {{having.condition}} и структурных условий по Мерам они объединяются по текущим backend-правилам, базово через {{AND}}.

h4. 9.6. Сортировка по Мере.
Если пользователь задал сортировку по Мере на полке «Значения», frontend передаёт Меру в {{order}}:

{code:json}
{
  "select": [
    {
      "type": "measure",
      "name": "Мера.Валовая_прибыль",
      "alias": "[values][0]",
      "id": "visual_measure_4f9b7e2d",
      "fieldAlias": "Валовая прибыль"
    }
  ],
  "order": [
    {
      "type": "measure",
      "name": "Мера.Валовая_прибыль",
      "alias": "[values][0]",
      "id": "visual_measure_4f9b7e2d",
      "fieldAlias": "Валовая прибыль",
      "direction": "desc"
    }
  ]
}
{code}

Если сортировка по Мере невозможна в текущем SQL-контексте, backend возвращает контролируемую ошибку, а frontend показывает её пользователю без повреждения конфигурации диаграммы.

h3. 10. Использование Мер в вычисляемых полях виджета.
Если в столбчатой диаграмме доступен редактор вычисляемых полей виджета, Меры должны быть доступны в нём наравне с обычными полями набора данных.

*Требования к редактору вычисляемых полей виджета:*
* В левой боковой панели редактора отображается секция *«Меры»* с Мерами текущего набора данных.
* Перетаскивание Меры в редактор вставляет системное {{name}} Меры в двойных кавычках, например: {{"Мера.Валовая_прибыль"}}.
* Автокомплит находит Меры по {{alias}} и {{name}} (логика {{OR}}) и визуально отличает Меры от обычных полей в списке подсказок.
* Меры вставляются как обычные поля в двойных кавычках; квадратные скобки для ссылок на Меры не используются.
* Признак Меры определяется по префиксу {{Мера.}} в системном имени — аналогично поведению, описанному в Истории по интерфейсу Мер.

h3. 11. Backend-требования в рамках интеграции.
Основные backend-доработки описаны в Backend-Шаге 2. Для столбчатой диаграммы требуется переиспользовать эти механизмы без дополнительной backend-доработки.

|| Контракт / объект || Требуемое поведение ||
| {{datasets}} | При чтении набора данных возвращает актуальный массив {{measures}} со статусами и метаданными, необходимыми для интерфейса диаграммы |
| {{/v1/api/recordsets/<dataset_id>}} | Принимает элементы {{type = "measure"}} в {{group}}, {{select}}, {{where}}, {{having}}, {{order}} и раскрывает их через {{datasets.measures[].expression}} |
| Экспорт визуализации | Если использует тот же runtime payload и SQL-builder, обрабатывает Меры тем же способом, что экранное построение диаграммы |

Backend должен вернуть контролируемую ошибку, если:
* Мера с переданным {{name}} не найдена;
* Мера имеет {{status = "invalid"}};
* {{datasetId}} Меры не соответствует текущему набору данных;
* агрегированная Мера попала в {{group}} или {{where}};
* неагрегированная Мера попала в {{having}};
* в runtime payload для {{type = "measure"}} передан непустой {{calc}}, {{agg}} или {{aggr}};
* условие фильтра по Мере содержит неподдержанный оператор или некорректный тип значения;
* итоговый SQL не может быть построен.

Сообщение ошибки должно содержать {{measure_name}}, runtime-блок и причину ошибки, быть пригодным для отображения пользователю и диагностики аналитиком.

h3. 12. Обработка пограничных сценариев.
* *Нет Мер в наборе данных:* секция «Меры» отображается пустой или в состоянии отсутствия элементов по текущему UI-паттерну. Полки и диаграмма работают без изменений.
* *Набор данных не произвольный:* секция «Меры» не отображается, drag-and-drop и селекторы Мер недоступны.
* *Мера стала {{invalid}} после изменения SQL набора данных:* новая вставка блокируется, существующая пилюля показывает error-состояние; запрос диаграммы не выполняется, если эта пилюля участвует в активной полке.
* *Мера удалена из набора данных:* при открытии диаграммы пилюля не удаляется автоматически, но отображается как ошибка отсутствующей Меры.
* *Изменился {{alias}} Меры без изменения {{name}}:* диаграмма продолжает ссылаться на прежнее {{name}} и отображает актуальный {{alias}} из метаданных набора данных.
* *Изменилось {{expression}} Меры:* следующий запрос диаграммы использует актуальное выражение из набора данных; копия старого выражения в визуализации не хранится.
* *Изменился {{aggregation_kind}} Меры:* frontend при следующем открытии / обновлении диаграммы перепроверяет совместимость размещения с полками. Несовместимая сохранённая пилюля переходит в error-состояние и блокирует запрос данных.
* *Режим «Значения» — «Первое», несколько пилюль:* только первая активная пилюля (включая Меры) используется в runtime payload; остальные сохраняются в конфигурации.
* *Режим «Значения» — «Все», смешанные пилюли:* каждая активная пилюля (поле или Мера) становится отдельным объектом в {{select}} с порядковым alias.
* *Мера одновременно на нескольких полках:* допустимо, если каждое размещение совместимо с матрицей допустимости.
* *Серии выключены:* сохранённые Меры на полке «Серии» не влияют на runtime payload.
* *Серии включены, одна из Мер серии невалидна:* построение диаграммы блокируется до исправления или удаления проблемной Меры.
* *Нет категории:* поведение остаётся таким же, как для столбчатой диаграммы без категории. Добавление поддержки Мер не вводит новое обязательное требование к категории.
* *Мера с {{data_type = "string"}} на полке «Значения»:* рекомендуется валидировать тип на frontend-е до запроса данных и предупреждать пользователя.
* *HAVING-фильтр без агрегированных значений в запросе:* backend обрабатывает по правилам SQL-builder-а и возвращает контролируемую ошибку, если корректный SQL невозможен.
* *Фильтр по Мере с незаполненным условием:* запрос данных не выполняется, пока пользователь не заполнит обязательные параметры фильтра, либо фильтр считается неактивным по текущим правилам фильтров.
* *Экспорт диаграммы с Мерами:* экспорт использует тот же набор активных Мер и технических alias, что экранное построение.

----
h3. 13. Права доступа.
Новые отдельные права на использование Мер в столбчатой диаграмме не вводятся.

Frontend использует существующую модель прав:
* чтение Мер доступно пользователю, который имеет право читать соответствующий набор данных и отчёт;
* изменение конфигурации диаграммы с добавлением / удалением Мер доступно пользователю, который имеет право редактировать отчёт / виджет по текущей модели прав;
* создание и редактирование самих Мер выполняется в настройках набора данных и регулируется правами на набор данных.

h3. 14. Критерии приёмки.
# В левой панели конструктора столбчатой диаграммы для произвольного набора данных отображается секция «Меры» с актуальным списком Мер.
# Для простых и составных наборов данных секция «Меры» не отображается.
# Валидная Мера перетаскивается на полки «Значения», «Категории», «Серии», «Фильтры» и {{valuesExtra}} при соблюдении матрицы допустимости.
# Агрегированная Мера блокируется при попытке размещения на полки «Категории» и «Серии».
# Неагрегированная Мера блокируется при попытке создания HAVING-фильтра.
# Невалидная Мера отображается с error-состоянием и не допускается на полки.
# Мера на полке отображается с тёмно-оранжевой пилюлей и ярлыком {{AGR}} для агрегированных Мер.
# В режиме «Значения — Первое» в runtime payload попадает только первая активная пилюля; в режиме «Все» — все активные пилюли.
# В режиме «Серии — Выкл» Меры с полки «Серии» не попадают в runtime payload.
# Runtime payload содержит объект {{type = "measure"}} без полей {{calc}}, {{expression}}, {{aggr}}.
# Существующие столбчатые диаграммы без Мер работают без изменений.
# После изменения набора данных (пересохранение SQL) диаграмма корректно отображает актуальный статус и {{alias}} Мер.
# Экспорт диаграммы с Мерами использует тот же runtime payload, что экранное построение.
