h3. Контекст и цель истории.
Полное описание продуктовой логики приведено в Эпике по Мерам ([https://jira.modusbi.ru/browse/MB-4364]).

Настоящая История описывает внедрение Мер в визуализацию — *«Диаграмму столбчатую»* (текущий тип конфигурации: {{chartType = "barChart"}}, {{visualType = "column"}}).

На предыдущих шагах Мера была введена как именованное SQL-выражение на уровне *произвольного* набора данных, а backend-доработки описали:
* хранение и CRUD Мер в объекте {{datasets}};
* использование {{type = "measure"}} в runtime payload запроса данных;
* раскрытие {{expression}} Меры при построении SQL.

В рамках этой Истории требуется подключить Меры к пользовательским сценариям столбчатой диаграммы: отображение Мер в левой панели, размещение на полках диаграммы, использование в совместимых настройках, сохранение ссылок в метаданных визуализации и формирование runtime payload для backend-а по уже описанным контрактам.

Визуализация не хранит полное определение Меры. В конфигурации диаграммы и runtime payload сохраняется ссылка на Меру по {{type = "measure"}}, {{name}} и {{datasetId}}. {{alias}}, {{expression}}, {{aggregation_kind}}, {{data_type}}, {{status}} и {{status_message}} должны браться из актуальных метаданных набора данных.

----
h3. Цель задачи.
*Требуется:*
# Добавить поддержку Мер в визуализацию *«Диаграмма столбчатая»* для использования на полках визуализации и в совместимых настройках, где сейчас допускаются обычные и вычисляемые поля.
# Сохранить согласованность с общими контрактами Мер: связь по {{name}}, признак {{type = "measure"}}, отсутствие копирования {{expression}} в визуализацию, валидация по {{aggregation_kind}} и {{status}}.
# Обеспечить корректное формирование runtime payload для {{/v1/api/recordsets/<dataset_id>}} так, чтобы backend мог раскрыть Меры и встроить их в {{SELECT}}, {{GROUP BY}}, {{WHERE}}, {{HAVING}} и {{ORDER BY}}.
# Не изменить поведение существующих столбчатых диаграмм, если в них не используются Меры.

_Пользовательская история:_
Как аналитик, я хочу использовать Меры в столбчатой диаграмме так же удобно, как поля и вычисляемые поля, чтобы переиспользовать единые бизнес-показатели набора данных без дублирования формул внутри каждой визуализации.

h3. 1. Границы истории.
h4. 1.1. В рамках истории реализуется.
* Отображение секции *«Меры»* в стандартной левой панели конструктора для визуализации "Диаграмма столбчатая".
* Включение секции *«Меры»* только для столбчатой диаграммы на текущем шаге, даже если технически дорабатывается общий компонент левой панели.
* Drag-and-drop валидных Мер на полки:
** *«Значения»*;
** *«Категории»*;
** *«Серии»*;
** *«Фильтры»*.
* Поддержка Мер на дополнительной оси значений {{valuesExtra}}.
* Использование Мер в совместимых селекторах правой панели настроек столбчатой диаграммы, где выбираются поля или вычисляемые поля.
* Использование Мер в вычисляемых полях виджета столбчатой диаграммы, если редактор вычисляемых полей доступен в этой визуализации.
* Отображение Мер на полках и в настройках по {{alias}} с визуальным отличием от обычных полей.
* Отображение ярлыка {{AGR}} для Мер с {{aggregation_kind = 1}}.
* Обработка Мер со статусом {{invalid}} в конструкторе и при построении диаграммы.
* Сохранение размещения Мер в метаданных диаграммы по {{type = "measure"}}, {{name}}, {{datasetId}} и локальному {{id}} размещения.
* Формирование runtime payload с объектами {{type = "measure"}} для backend-а.
* Поддержка сортировки по Мере, если текущий интерфейс столбчатой диаграммы поддерживает сортировку по соответствующей пилюле.
* Поддержка экспорта столбчатой диаграммы с Мерами через текущий общий механизм экспорта, если экспорт использует тот же runtime payload и SQL-builder.
* Обратная совместимость существующих диаграмм без Мер.

h4. 1.2. В рамках истории не реализуется.
* Создание, редактирование и удаление Мер в настройках набора данных.
* Поддержка Мер для *простых* и *составных* наборов данных.
* Распространение пользовательской доступности Мер на другие визуализации, кроме *«Диаграммы столбчатой»*.
* Изменение базовой модели хранения {{report.grid}} / {{access}} / конфигурации отчёта и нормализация списка используемых полей в отдельный индекс. Эта тема рассматривается отдельно; в рамках текущей Истории используется существующий контракт отчёта.
* Изменение SQL-выражения Меры на уровне полки визуализации.
* Ручное изменение {{aggregation_kind}} на полке визуализации.
* Автоматическое преобразование существующих вычисляемых полей столбчатых диаграмм в Меры.
* Уровень-специфичная логика {{HAVING}} для Сводной таблицы, {{target_dimensions}}, CND и {{depth}}.

----
h3. 2. Исходные правила модели Мер.
* Мера доступна только для *произвольного* набора данных.
* Мера хранится в метаданных набора данных в массиве {{measures}}.
* Ключом связи является {{name}} Меры.
* {{alias}} используется только для отображения пользователю и не является ключом связи.
* {{id}} из {{measures[]}} не используется как внешний ключ в визуализациях.
* Локальный {{id}} пилюли в визуализации является идентификатором размещения, а не идентификатором Меры из набора данных.
* {{expression}} Меры не копируется в конфигурацию диаграммы и не передаётся frontend-ом в runtime payload как источник истины.
* Для Мер со {{status = "invalid"}} новое размещение на полках и выбор в селекторах недоступны.
* Если уже сохранённая диаграмма ссылается на Меру, которая стала {{invalid}} или отсутствует в наборе данных, связь по {{name}} сохраняется. Построение диаграммы блокируется понятной ошибкой только если эта Мера участвует в активной полке или настройке, попадающей в runtime payload.

Пример определения Меры в наборе данных:
{code:json}
{
  "id": "847b1ec3-bbf8-4365-85fb-c4fca2a06e2e",
  "name": "Мера.Валовая_прибыль",
  "alias": "Валовая прибыль",
  "description": "Разница между выручкой и себестоимостью",
  "expression": "SUM(\"revenue\") - SUM(\"cost\")",
  "aggregation_kind": 1,
  "data_type": "number",
  "hierarchy": "Финансовые показатели",
  "level": 10,
  "status": "valid",
  "status_message": ""
}
{code}

h3. 3. Описание текущего поведения.
Сейчас в конструкторе столбчатой диаграммы пользователь работает с обычными полями набора данных и вычисляемыми полями виджета.

Стандартная левая панель содержит секцию с полями набора данных, но не содержит отдельную секцию *«Меры»*. Пользователь не может перетащить Меру на полки диаграммы и не может выбрать Меру в настройках визуализации.

Для столбчатой диаграммы используются основные полки:
* *«Значения»* — задаёт показатели, отображаемые столбцами. На полке есть режим:
** *«Первое»* — для отображения используется только первая активная пилюля полки;
** *«Все»* — для отображения используются все активные пилюли полки.
* *«Категории»* — задаёт разбиение по категориям. Активно используется только первая пилюля полки.
* *«Серии»* — задаёт дополнительное разбиение внутри категорий. На полке есть режим:
** *«Вкл»* — пилюли полки участвуют в построении диаграммы;
** *«Выкл»* — пилюли полки сохраняются в настройках, но не влияют на визуализацию и runtime payload.
* *«Фильтры»* — задаёт фильтрацию данных визуализации.

В текущем runtime-запросе столбчатой диаграммы frontend формирует универсальные блоки:
* {{group}} — группировки для категорий и серий;
* {{select}} — возвращаемые значения и, при необходимости, поля группировки для текущего механизма отображения/экспорта;
* {{where}} — фильтры до группировки;
* {{having}} — условия после группировки;
* {{order}} — сортировка;
* {{series}} — текущий режим серий.

Backend уже умеет обрабатывать обычные поля и вычисляемые поля в этих блоках, но поддержка {{type = "measure"}} реализуется отдельными backend-шагами и должна быть использована frontend-ом столбчатой диаграммы.

----
h3. 4. Описание целевого поведения.
После реализации Истории пользователь должен иметь возможность открыть столбчатую диаграмму на основе *произвольного* набора данных и использовать валидные Меры этого набора данных в тех же пользовательских сценариях, где для данной диаграммы допустимы обычные поля и вычисляемые поля.

Целевое поведение:
# В левой панели столбчатой диаграммы под секцией *«Поля»* отображается секция *«Меры»*.
# В секции *«Меры»* отображаются только Меры текущего произвольного набора данных.
# Валидные Меры можно перетаскивать на совместимые полки диаграммы.
# Невалидные Меры отображаются, но недоступны для добавления.
# Мера на полке отображается по {{alias}}, но в метаданных хранится связь по {{name}}.
# Для Мер с {{aggregation_kind = 1}} отображается ярлык {{AGR}}.
# Меры доступны в совместимых селекторах правой панели настроек столбчатой диаграммы.
# Runtime payload передаёт backend-у объекты {{type = "measure"}} без копирования {{expression}}.
# Backend раскрывает выражение Меры и строит SQL по правилам backend-Шага 2.
# Если активно используемая Мера становится невалидной после изменения набора данных или самой Меры, диаграмма переходит в error-состояние до исправления.

h3. 5. Требования к интерфейсу.
h4. 5.1. Левая панель конструктора.
Для столбчатой диаграммы на основе *произвольного* набора данных левая панель должна содержать:
* секцию *«Поля»* — текущее поведение без изменения;
* секцию *«Меры»* — новая секция ниже секции *«Поля»*.

Технически допускается доработка общего компонента левой панели, но на текущем этапе секция *«Меры»* должна быть включена только для визуализации {{barChart}} / {{column}} через явный признак доступности, настройку или иной контролируемый механизм.

Для *простых* и *составных* наборов данных секция *«Меры»* в конструкторе столбчатой диаграммы не отображается.

h4. 5.2. Отображение списка Мер.
В секции *«Меры»*:
* отображается {{alias}} Меры;
* для агрегированных Мер отображается ярлык {{AGR}};
* Меры группируются по {{hierarchy}}, если поле заполнено;
* внутри группы Меры сортируются по {{level}} по возрастанию, затем по {{alias}};
* Меры без {{hierarchy}} отображаются в корневом уровне секции по {{alias}};
* tooltip при наведении содержит:
** {{description}}, если заполнено;
** {{data_type}};
** полный текст {{expression}};
** системное {{name}} как справочную техническую информацию;
** {{status_message}}, если Мера невалидна.

Если в текущей левой панели есть поиск по полям, поиск должен находить Меры по {{alias}} и {{name}} по логике {{OR}} и визуально отличать Меры от обычных полей.

h4. 5.3. Визуальное отличие Меры.
На полках диаграммы Мера отображается как отдельный тип пилюли:
* на полках *«Значения»*, *«Категории»*, *«Серии»* и {{valuesExtra}} — цвет / иконка Меры должны отличаться от обычного поля; целевой цвет пилюли Меры — тёмно-оранжевый;
* на полке *«Фильтры»* Мера отображается как фильтрующая пилюля в текущем стиле фильтров, но с явным признаком типа *«Мера»* и ярлыком {{AGR}} для агрегированных Мер;
* в tooltip пилюли выводится {{alias}}, {{name}}, {{data_type}}, признак агрегированности и описание, если оно заполнено.

h4. 5.4. Drag-and-drop.
Мера перетаскивается из секции *«Меры»* на полки аналогично обычному полю.

При попытке разместить Меру на несовместимую полку:
* размещение блокируется;
* пользователь видит состояние запрета;
* пользователь получает причину блокировки из матрицы допустимости.

Одна и та же Мера может быть размещена на нескольких полках одной диаграммы, если каждое размещение совместимо с соответствующей полкой.

h4. 5.5. Поведение Мер со статусом {{invalid}}.
Если {{status = "invalid"}}:
* в секции *«Меры»* элемент отображается с error-состоянием;
* drag-and-drop на полки заблокирован;
* выбор в совместимых селекторах заблокирован;
* tooltip показывает {{status_message}};
* если Мера уже размещена на активной полке сохранённой диаграммы или выбрана в активной настройке, пилюля остаётся на месте, отображается в error-состоянии, а запрос данных диаграммы не выполняется.

Сообщение пользователю должно содержать название Меры и причину, например:
*«Мера "Мера.Валовая_прибыль" не может быть использована: поле "revenue" не найдено в текущем составе полей набора данных»*.

h3. 6. Правила использования Мер на полках столбчатой диаграммы.
h4. 6.1. Общая матрица допустимости.
|| Полка столбчатой диаграммы || Runtime-контекст || Допустимые Меры || Целевое поведение ||
| *Значения* | {{select}} / {{SELECT}} | Любые валидные Меры | Мера возвращается как значение диаграммы. Для {{aggregation_kind = 0}} показывается предупреждение о возможном изменении уровня детализации. |
| *Категории* | {{group}} + при необходимости {{select}} / {{GROUP BY}} | Только неагрегированные Меры ({{aggregation_kind = 0}}) | Мера используется как вычисляемая категория. Агрегированные Меры блокируются. |
| *Серии* | {{group}} + при необходимости {{select}} / {{GROUP BY}} | Только неагрегированные Меры ({{aggregation_kind = 0}}) | Мера используется как вычисляемая серия. Агрегированные Меры блокируются. |
| *Фильтры WHERE* | {{where}} / {{WHERE}} | Только неагрегированные Меры ({{aggregation_kind = 0}}) | Фильтрация до группировки. |
| *Фильтры HAVING* | {{having}} / {{HAVING}} | Только агрегированные Меры ({{aggregation_kind = 1}}) | Фильтрация после группировки. |
| {{valuesExtra}} | {{select}} / {{SELECT}} | Любые валидные Меры | Если полка доступна в UI, применяется логика полки *«Значения»*. |

h4. 6.2. Полка «Значения».
На полке *«Значения»* Меры используются как показатели, которые отображаются столбцами диаграммы или участвуют в сервисных сценариях полки, если такие сценарии уже поддерживаются для вычисляемых полей.

Требования:
* Пользователь может разместить на полке *«Значения»* валидную Меру с {{aggregation_kind = 1}} или {{aggregation_kind = 0}}.
* Для Меры с {{aggregation_kind = 1}} размещение выполняется без предупреждения.
* Для Меры с {{aggregation_kind = 0}} размещение не блокируется, но пользователь получает предупреждение:
*«Выражение помечено как неагрегированное. Для корректного отображения рекомендуется использовать агрегатную функцию, например: SUM(...)»*.
* На пилюле Меры не должно быть доступно локальное изменение агрегации {{agg}} / {{aggr}}. Если для обычных полей на полке есть выбор агрегации, для Меры он скрывается или переводится в readonly-состояние с пояснением:
*«Агрегация Меры задаётся в настройках Меры»*.
* Локальные настройки пилюли, не являющиеся определением Меры, сохраняются как настройки размещения: сортировка, формат отображения, точность, единицы, цвет, подпись, {{valueType}} и другие текущие настройки полки, если они применимы.
* Если Мера используется как значение для всплывающей подсказки или иного сервисного сценария, например через {{valueType = "tooltip"}}, она должна запрашиваться в runtime payload так же, как сейчас запрашивается вычисляемое поле для этого сценария, но не должна становиться отдельным визуальным столбцом, если текущая логика {{valueType}} этого не предполагает.

Режим полки *«Значения»*:
* В режиме *«Первое»* для визуального отображения используется первая активная пилюля полки, совместимая с отображением значения. Если первой активной пилюлей является Мера, диаграмма строится по этой Мере.
* В режиме *«Все»* для визуального отображения используются все активные пилюли значений, включая Меры, обычные поля и вычисляемые поля.
* Сервисные пилюли, например для tooltip, должны учитываться по текущим правилам полки и не должны случайно становиться отображаемыми значениями только из-за добавления поддержки Мер.
* Порядок активных пилюль должен определять технические alias результата {{[values][N]}} по текущей логике диаграммы.

h4. 6.3. Полка «Категории».
На полке *«Категории»* Мера может использоваться как вычисляемая категория только если {{aggregation_kind = 0}}.

Требования:
* Валидная неагрегированная Мера допускается на полку *«Категории»*.
* Агрегированная Мера на полке *«Категории»* блокируется с сообщением:
*«На полке "Категории" допустимы только неагрегированные Меры»*.
* Активно используется только первая пилюля полки. Если первой активной пилюлей является Мера, она передаётся в runtime-контекст группировки с техническим alias категории.
* Если на полке сохранено несколько пилюль, но текущая логика диаграммы использует только первую, остальные пилюли не должны влиять на runtime payload и построение диаграммы.
* Если ранее сохранённая первая пилюля-Мера стала {{invalid}}, построение диаграммы блокируется до исправления Меры, удаления пилюли или выбора другой активной категории.

h4. 6.4. Полка «Серии».
На полке *«Серии»* Мера может использоваться как вычисляемая серия только если {{aggregation_kind = 0}}.

Требования:
* Валидная неагрегированная Мера допускается на полку *«Серии»*.
* Агрегированная Мера на полке *«Серии»* блокируется с сообщением:
*«На полке "Серии" допустимы только неагрегированные Меры»*.
* В режиме *«Вкл»* все активные пилюли полки *«Серии»*, включая Меры, участвуют в группировке и увеличивают детализацию столбцов.
* В режиме *«Выкл»* пилюли полки *«Серии»* сохраняются в конфигурации диаграммы, но не попадают в runtime payload и не влияют на количество столбцов.
* Порядок пилюль серии должен определять технические alias {{[series][N]}} по текущей логике диаграммы.
* Если Мера серии стала {{invalid}}, при включённых сериях построение диаграммы блокируется; при выключенных сериях такая Мера не должна блокировать запрос данных, если текущая логика действительно не использует выключенную полку в runtime payload.

h4. 6.5. Полка «Фильтры».
Мера на полке *«Фильтры»* используется как фильтр по выражению Меры.

Требования:
* При добавлении Меры на полку *«Фильтры»* открывается или становится доступна настройка фильтра по Мере.
* Форма фильтра по Мере содержит:
** режим фильтрации {{WHERE}} или {{HAVING}};
** оператор условия;
** значение или диапазон значений;
** тип значения {{value_type}};
** дополнительные параметры текущего фильтра, если они уже поддерживаются для обычных/вычисляемых полей и применимы к Мере.
* Для {{aggregation_kind = 0}} доступен только режим {{WHERE}}.
* Для {{aggregation_kind = 1}} доступен только режим {{HAVING}}.
* Если режим выбирается автоматически, значение по умолчанию:
** {{WHERE}} для неагрегированной Меры;
** {{HAVING}} для агрегированной Меры.
* Попытка выбрать несовместимый режим блокируется:
** для агрегированной Меры в {{WHERE}}: *«Мера помечена как агрегированная. Выберите тип отбора HAVING или измените агрегатность в настройках Меры»*;
** для неагрегированной Меры в {{HAVING}}: *«Мера помечена как неагрегированная. Выберите тип отбора WHERE или измените агрегатность в настройках Меры»*.
* Условия по нескольким Мерам на полке *«Фильтры»* объединяются через {{AND}} внутри соответствующей SQL-клаузы.
* Одновременное наличие WHERE-Мер и HAVING-Мер на полке *«Фильтры»* допустимо: они попадают в разные runtime-блоки.

Если текущий интерфейс фильтра по обычному полю использует загрузку списка значений:
* для неагрегированной Меры такая загрузка допустима только через backend-контракт, который поддерживает {{type = "measure"}} в запросе distinct-значений;
* для агрегированной Меры не нужно пытаться загружать справочник значений как для обычного поля базового слоя, если отдельный backend-сценарий для HAVING-значений не реализован. В этом случае используется ручной ввод значения / диапазона и оператор сравнения.

h4. 6.6. Дополнительная ось значений {{valuesExtra}}.
В предоставленном примере конфигурации присутствует полка {{valuesExtra}}.

Если в текущем интерфейсе столбчатой диаграммы пользователь может работать с {{valuesExtra}} и размещать на ней обычные или вычисляемые поля, то Меры должны поддерживаться на этой полке по правилам полки *«Значения»*:
* валидные Меры допускаются;
* {{aggregation_kind = 0}} сопровождается предупреждением;
* локальная агрегация на пилюле Меры не редактируется;
* runtime payload формируется так, чтобы backend получил объект {{type = "measure"}} в соответствующем контексте {{select}}.

Если {{valuesExtra}} в текущем UX столбчатой диаграммы недоступна пользователю или не используется в данной реализации, отдельная поддержка Мер на ней не требуется, но это ограничение должно быть явно зафиксировано в документации реализации.

----
h3. 7. Меры в правой панели настроек столбчатой диаграммы.
h4. 7.1. Общий принцип.
Меры должны быть доступны во всех selector-компонентах правой панели столбчатой диаграммы, где сейчас можно выбрать обычное поле или вычисляемое поле и где сценарий совместим с типом Меры.

К таким настройкам относятся все текущие элементы интерфейса столбчатой диаграммы, работающие с полями визуализации, в том числе:
* настройки сортировки;
* настройки отображения значений;
* настройки подписей и форматирования;
* настройки всплывающих подсказок;
* условное форматирование, если оно доступно для столбчатой диаграммы;
* настройки цвета / серии / легенды, если в них выбирается поле;
* прочие выпадающие списки и селекторы, которые используют поля или вычисляемые поля текущей визуализации.

Если конкретный selector технически или продуктово не поддерживает Меры на данном этапе, это ограничение должно быть явно зафиксировано в документации реализации и не должно выглядеть как случайно забытый элемент.

h4. 7.2. Поведение selector-компонентов.
Selector, который поддерживает Меры, должен:
* показывать Меры в отдельной секции *«Меры»* или явно отличать их от обычных полей;
* отображать {{alias}} Меры;
* искать по {{alias}} и {{name}}, если в selector есть поиск;
* показывать {{AGR}} для агрегированных Мер;
* не позволять выбрать Меру со {{status = "invalid"}};
* применять матрицу допустимости по контексту selector-а:
** для selector-а измерений — только {{aggregation_kind = 0}};
** для selector-а значений — любая валидная Мера;
** для selector-а фильтров — {{WHERE}} / {{HAVING}} по правилам фильтра;
** для selector-а сортировки — Мера допустима, если backend может построить {{ORDER BY}} для текущего SQL-контекста.

При выборе Меры в настройке сохраняется ссылка по {{type = "measure"}}, {{name}}, {{datasetId}} и локальные настройки конкретного selector-а. {{expression}} Меры не копируется.

h4. 7.3. Форматирование и отображение.
Для настроек форматирования Меры frontend должен использовать {{data_type}} из метаданных Меры:
* для {{number}} доступны числовые форматы, точность, разделители, единицы измерения, если такие настройки доступны для обычных числовых полей;
* для {{date}} / {{datetime}} доступны форматы дат, если такие настройки поддерживаются в диаграмме;
* для {{string}} доступны только совместимые настройки.

{{aggregation_kind}} не является типом данных и не должен использоваться для выбора маски форматирования.

h4. 7.4. Вычисляемые поля виджета.
Если в столбчатой диаграмме доступен редактор вычисляемых полей виджета, Меры текущего набора данных должны быть доступны для вставки в выражение по правилам общей постановки:
* в списке и автодополнении отображается {{alias}};
* после выбора вставляется {{name}} Меры в двойных кавычках, например {{"Мера.Валовая_прибыль"}};
* вычисляемое поле сохраняет зависимость от {{name}} Меры;
* если Мера становится {{invalid}}, зависящее вычисляемое поле должно перейти в ошибочное состояние по правилам backend-валидации.

----
h3. 8. Метаданные столбчатой диаграммы.
h4. 8.1. Объект использования Меры в {{axes[].fields[]}}.
В конфигурации столбчатой диаграммы Мера хранится как объект использования Меры, а не как копия определения Меры.

Минимальная целевая структура размещения Меры на полке:
{code:json}
{
  "id": "visual_measure_4f9b7e2d",
  "type": "measure",
  "name": "Мера.Валовая_прибыль",
  "datasetId": 244,
  "valueType": "value",
  "order": null,
  "orderIndex": null
}
{code}

|| Поле || Описание ||
| {{id}} | Локальный идентификатор размещения пилюли в диаграмме. Не равен {{measures[].id}}. |
| {{type}} | Для Меры всегда {{measure}}. |
| {{name}} | Системное имя Меры, единственный ключ связи. |
| {{datasetId}} | Идентификатор произвольного набора данных, которому принадлежит Мера. |
| {{valueType}} | Локальная настройка сценария использования на полке, если она применима. |
| {{order}} / {{orderIndex}} | Локальная сортировка пилюли, если поддерживается текущей полкой. |

В объект использования Меры не должны копироваться как источник истины:
* {{expression}};
* {{description}};
* {{aggregation_kind}};
* {{data_type}};
* {{hierarchy}};
* {{level}};
* {{status}};
* {{status_message}};
* {{id}} Меры из {{measures[]}}.

Если текущая frontend-модель требует временные presentation-поля вроде {{fieldAlias}}, {{title}} или {{alias}} для отображения в уже открытом интерфейсе, они не должны использоваться как ключ связи или источник истины и должны обновляться из актуальных метаданных набора данных при чтении диаграммы.

h4. 8.2. Локальные настройки размещения.
Локальные настройки размещения Меры сохраняются рядом с объектом использования Меры, если они относятся к конкретной диаграмме или конкретной пилюле:
* сортировка;
* формат отображения;
* точность;
* цвет;
* единицы измерения;
* подпись;
* режим tooltip;
* прочие настройки полки, уже существующие для обычных/вычисляемых полей.

Эти настройки не изменяют определение Меры в наборе данных и не должны записываться обратно в {{datasets.measures[]}}.

h4. 8.3. Чтение сохранённой диаграммы.
При открытии сохранённой столбчатой диаграммы frontend должен:
# прочитать конфигурацию диаграммы;
# найти все объекты {{type = "measure"}};
# получить актуальные метаданные Мер из текущего набора данных;
# сопоставить объект использования с определением Меры по {{name}};
# отобразить на пилюле актуальный {{alias}}, {{AGR}} и статус;
# если Мера не найдена или {{status = "invalid"}}, отобразить пилюлю в error-состоянии; запрос данных блокируется только если эта пилюля участвует в активной полке или настройке.

----
h3. 9. Формирование runtime payload.
h4. 9.1. Общий принцип.
Frontend столбчатой диаграммы должен формировать runtime payload для {{/v1/api/recordsets/<dataset_id>}} по текущей логике диаграммы, но для Мер передавать объекты {{type = "measure"}}.

Backend определяет SQL-контекст по runtime-блоку, а не по названию полки:
|| Runtime-блок || SQL-контекст Меры ||
| {{select}} | {{SELECT}} |
| {{group}} | {{GROUP BY}} |
| {{where}} | {{WHERE}} |
| {{having}} | {{HAVING}} |
| {{order}} | {{ORDER BY}} |

Для {{type = "measure"}} frontend не должен передавать непустые {{calc}}, {{aggr}} или {{agg}} как источник выражения или локальной агрегации. Если текущий builder требует эти поля технически, они должны быть пустыми, а backend должен игнорировать их для Меры.

h4. 9.2. Мера на полке «Значения».
Пример runtime-элемента Меры в {{select}}:
{code:json}
{
  "type": "measure",
  "name": "Мера.Валовая_прибыль",
  "alias": "[values][0]",
  "id": "visual_measure_4f9b7e2d",
  "fieldAlias": "Валовая прибыль",
  "valueType": "value",
  "export": {
    "fieldType": "number",
    "prop": {}
  }
}
{code}

Пояснения:
* {{alias}} в runtime payload — технический alias результата, а не {{alias}} Меры из {{datasets.measures[]}}.
* {{fieldAlias}} допустим только как presentation-поле, сформированное из актуального {{measures[].alias}}.
* {{export.fieldType}} должен соответствовать {{data_type}} Меры.
* {{calc}}, {{aggr}} и {{agg}} не должны использоваться для подмены выражения или агрегации Меры.

h4. 9.3. Мера на полке «Категории».
Если первая активная пилюля полки *«Категории»* является неагрегированной Мерой, frontend передаёт её в {{group}} с техническим alias категории и, если текущая логика диаграммы требует возвращать категорию в результате, также в {{select}}.

Пример семантики:
{code:json}
{
  "group": [
    {
      "type": "measure",
      "name": "Мера.Сегмент_маржи",
      "alias": "[categories]",
      "id": "visual_measure_category_1",
      "fieldAlias": "Сегмент маржи"
    }
  ],
  "select": [
    {
      "type": "measure",
      "name": "Мера.Сегмент_маржи",
      "alias": "[categories]",
      "id": "visual_measure_category_1",
      "fieldAlias": "Сегмент маржи",
      "export": {
        "fieldType": "string",
        "prop": {}
      }
    }
  ]
}
{code}

Если текущий runtime-формат столбчатой диаграммы возвращает категории через иной технический alias, необходимо сохранить текущую alias-стратегию. Важное требование — объект Меры должен попасть в тот же runtime-контекст, где сейчас находится обычное поле категории.

h4. 9.4. Мера на полке «Серии».
Если режим *«Серии»* включён и на полке есть неагрегированные Меры, frontend передаёт каждую активную Меру серии в {{group}} с alias текущей позиции серии.

Пример:
{code:json}
{
  "group": [
    {
      "type": "measure",
      "name": "Мера.Сегмент_клиента",
      "alias": "[series][0]",
      "id": "visual_measure_series_1",
      "fieldAlias": "Сегмент клиента"
    }
  ],
  "series": {
    "enable": 1
  }
}
{code}

Если режим *«Серии»* выключен, Меры с полки *«Серии»* не должны попадать в {{group}}, {{select}} или {{order}} только из-за того, что они сохранены на полке.

h4. 9.5. Мера на полке «Фильтры».
WHERE-фильтр по неагрегированной Мере:
{code:json}
{
  "where": [
    {
      "type": "measure",
      "name": "Мера.Маржа_строки",
      "condition": {
        "operator": ">",
        "value": 0,
        "value_type": "number"
      }
    }
  ],
  "having": {
    "condition": ""
  }
}
{code}

HAVING-фильтр по агрегированной Мере:
{code:json}
{
  "having": {
    "condition": "",
    "items": [
      {
        "type": "measure",
        "name": "Мера.Валовая_прибыль",
        "condition": {
          "operator": ">",
          "value": 0,
          "value_type": "number"
        }
      }
    ]
  }
}
{code}

Если frontend и backend уже согласовали формат {{having}} как массив структурных условий, он может использоваться как эквивалентный формат. При наличии legacy {{having.condition}} и структурных условий по Мерам они объединяются по текущим backend-правилам, базово через {{AND}}.

h4. 9.6. Сортировка по Мере.
Если пользователь задал сортировку по Мере на полке *«Значения»* или в совместимой настройке сортировки, frontend передаёт Меру в {{order}}.

Пример:
{code:json}
{
  "select": [
    {
      "type": "measure",
      "name": "Мера.Валовая_прибыль",
      "alias": "[values][0]",
      "id": "visual_measure_4f9b7e2d",
      "fieldAlias": "Валовая прибыль"
    }
  ],
  "order": [
    {
      "type": "measure",
      "name": "Мера.Валовая_прибыль",
      "alias": "[values][0]",
      "id": "visual_measure_4f9b7e2d",
      "fieldAlias": "Валовая прибыль",
      "direction": "desc"
    }
  ]
}
{code}

Если сортировка по Мере невозможна в текущем SQL-контексте, backend должен вернуть контролируемую ошибку, а frontend должен показать её пользователю без повреждения конфигурации диаграммы.

----
h3. 10. Backend-требования в рамках интеграции.
Основные backend-доработки описаны в backend-Шаге 2 и backend-Шаге 3. Для столбчатой диаграммы требуется переиспользовать эти механизмы.

Затрагиваемые контракты:
|| Контракт / объект || Требуемое поведение ||
| {{datasets}} | При чтении набора данных возвращает актуальный массив {{measures}} со статусами и метаданными, необходимыми для интерфейса диаграммы. |
| {{/v1/api/recordsets/<dataset_id>}} | Принимает элементы {{type = "measure"}} в {{group}}, {{select}}, {{where}}, {{having}}, {{order}} и раскрывает их через {{datasets.measures[].expression}}. |
| Экспорт визуализации | Если использует тот же runtime payload и SQL-builder, обрабатывает Меры тем же способом, что экранное построение диаграммы. |

Backend должен вернуть контролируемую ошибку, если:
* Мера с переданным {{name}} не найдена;
* Мера имеет {{status = "invalid"}};
* {{datasetId}} Меры не соответствует текущему набору данных;
* агрегированная Мера попала в {{group}} или {{where}};
* неагрегированная Мера попала в {{having}};
* в runtime payload для {{type = "measure"}} передан непустой {{calc}}, {{agg}} или {{aggr}} как попытка подмены выражения / агрегации;
* условие фильтра по Мере содержит неподдержанный оператор или некорректный тип значения;
* итоговый SQL не может быть построен.

Сообщение ошибки должно быть пригодно для отображения пользователю и диагностики аналитиком. Минимально желательно возвращать {{measure_name}}, runtime-блок и причину ошибки.

h3. 11. Обработка пограничных сценариев.
* *Нет Мер в наборе данных:* секция *«Меры»* отображается пустой или в состоянии отсутствия элементов по текущему UI-паттерну. Полки и диаграмма работают как раньше.
* *Набор данных не произвольный:* секция *«Меры»* не отображается, drag-and-drop и селекторы Мер недоступны.
* *Мера стала {{invalid}} после изменения SQL набора данных:* новая вставка блокируется, существующая пилюля показывает error-состояние; запрос диаграммы не выполняется, если эта пилюля участвует в активной полке или настройке.
* *Мера удалена из набора данных вне текущей диаграммы:* при открытии диаграммы пилюля не удаляется автоматически, но отображается как ошибка отсутствующей Меры.
* *Изменился {{alias}} Меры без изменения {{name}}:* диаграмма продолжает ссылаться на прежнее {{name}} и отображает актуальный {{alias}} из метаданных набора данных.
* *Изменилось {{expression}} Меры:* следующий запрос диаграммы использует актуальное выражение из набора данных; копия старого выражения в визуализации не хранится.
* *Изменился {{aggregation_kind}} Меры:* frontend при следующем открытии / обновлении диаграммы должен перепроверить совместимость размещения с полками. Несовместимая сохранённая пилюля отображается в error-состоянии и блокирует запрос данных.
* *Несколько Мер на полке «Значения»:* в режиме *«Все»* каждая активная Мера становится отдельным значением диаграммы; в режиме *«Первое»* визуализируется только первая активная пилюля значения.
* *Мера одновременно используется на нескольких полках:* допустимо, если каждое размещение совместимо с матрицей допустимости.
* *Серии выключены:* сохранённые Меры на полке *«Серии»* не влияют на runtime payload и построение диаграммы.
* *Серии включены, но одна из Мер серии невалидна:* построение диаграммы блокируется до исправления или удаления проблемной Меры.
* *Нет категории:* поведение остаётся таким же, как сейчас для столбчатой диаграммы без категории. Добавление поддержки Мер не должно вводить новое обязательное требование к категории, если его нет в текущей реализации.
* *Мера с {{data_type = "string"}} на полке «Значения»:* размещение должно проходить по текущим правилам допустимости значений диаграммы. Если столбчатая диаграмма не может построить числовое значение по строковой Мере, frontend должен предупредить пользователя или backend должен вернуть контролируемую ошибку SQL/типа. Рекомендуется валидировать тип на frontend-е до запроса данных.
* *HAVING-фильтр без агрегированных значений в запросе:* backend должен обработать по правилам SQL-builder-а и вернуть контролируемую ошибку, если корректный SQL невозможен.
* *Фильтр по Мере с пустым значением условия:* запрос данных не выполняется, пока пользователь не заполнит обязательные параметры фильтра, либо фильтр считается неактивным по текущим правилам фильтров.
* *Экспорт диаграммы с Мерами:* экспорт должен использовать тот же набор активных Мер и технических alias, что экранное построение, если экспорт построен на общем payload.

----
h3. 12. Права доступа.
Новые отдельные права на использование Мер в столбчатой диаграмме не вводятся.

Frontend должен использовать существующую модель прав:
* чтение Мер доступно пользователю, который имеет право читать соответствующий набор данных и отчёт;
* изменение конфигурации диаграммы с добавлением/удалением Мер доступно пользователю, который имеет право редактировать отчёт/виджет по текущей модели прав;
* создание и редактирование самих Мер выполняется в настройках набора данных и регулируется правами на набор данных.

Если пользователь не имеет права редактировать диаграмму, Меры в уже настроенной диаграмме отображаются в readonly-режиме, а изменение полок и настроек недоступно по текущим правилам readonly-режима.

----
h3. 13. Обратная совместимость и ограничения.
* Существующие столбчатые диаграммы без Мер должны открываться, сохраняться, строиться и экспортироваться без изменения поведения.
* Если в runtime payload нет объектов {{type = "measure"}}, новая логика Мер не должна влиять на SQL и результат запроса.
* Существующие обычные поля, вычисляемые поля виджета, фильтры, сортировки, tooltip и настройки отображения продолжают работать по текущим правилам.
* Миграция существующих метаданных столбчатых диаграмм не требуется.
* Для Мер нельзя использовать {{calc}} визуализации как источник выражения. Источник выражения — только {{datasets.measures[].expression}}.
* Для Мер нельзя использовать локальный {{agg}} / {{aggr}} как обёртку поверх выражения Меры.
* В рамках текущей Истории Меры становятся пользовательски доступны только в *«Диаграмме столбчатой»*. Остальные визуализации подключаются отдельными историями или последующим снятием feature-флага.

h3. 15. Предположения.
* В рамках текущей Истории под *«Диаграммой столбчатой»* понимается визуализация с {{chartType = "barChart"}} и {{visualType = "column"}}. Если тот же frontend-компонент обслуживает несколько ориентаций столбчатой диаграммы, правила Мер должны применяться одинаково, но перечень затронутых {{visualType}} / {{orientation}} нужно подтвердить у frontend-команды.
* Runtime-запросы данных столбчатой диаграммы продолжают использовать {{/v1/api/recordsets/<dataset_id>}}.
* Текущий SQL-builder backend-а после реализации backend-Шага 2 умеет обрабатывать {{type = "measure"}} в {{group}}, {{select}}, {{where}}, {{having}} и {{order}}.
* Статусы {{valid}} / {{invalid}} и блокировки зависимостей полноценно доступны после backend-Шага 3. Если frontend-реализация столбчатой диаграммы начнётся до завершения Шага 3, временное поведение должно быть явно согласовано с backend-командой.
* Текущий механизм экспорта столбчатой диаграммы использует тот же runtime payload или общий SQL-builder. Если экспорт использует отдельный путь, поддержку Мер в экспорте нужно оценить отдельно.

h3. 16. Открытые вопросы.
* Подтвердить у frontend-команды точный признак включения секции *«Меры»* только для столбчатой диаграммы: feature-флаг, список поддержанных {{chartType}} / {{visualType}} или иной механизм.
* Подтвердить, какие selector-компоненты правой панели столбчатой диаграммы на текущем этапе технически могут поддержать Меры. Все неподдержанные selector-компоненты должны быть перечислены как ограничение реализации.
* Уточнить текущее внутреннее представление режима *«Первое»* / *«Все»* для полки *«Значения»* и режима *«Вкл»* / *«Выкл»* для полки *«Серии»*, чтобы не менять существующий формат сохранения.
* Подтвердить, нужно ли на текущем этапе поддерживать загрузку distinct-значений для фильтра по неагрегированной Мере и есть ли отдельный сценарий загрузки значений для HAVING-фильтров по агрегированным Мерам.
* Подтвердить, доступна ли пользователю полка {{valuesExtra}} в столбчатой диаграмме и должна ли она входить в объём текущей реализации.

h3. 17. Критерии приёмки (AC).
*AC.1* — Секция «Меры» отображается для столбчатой диаграммы:
* *Дано:* пользователь открыл конструктор столбчатой диаграммы на основе *произвольного* набора данных;
* *Когда:* у набора данных есть сохранённые Меры;
* *Тогда:* в левой панели ниже секции *«Поля»* отображается секция *«Меры»*;
* *И:* для другой визуализации секция *«Меры»* не становится доступной в рамках этой Истории, если она не включена отдельным флагом/настройкой.

*AC.2* — Меры не отображаются для неподдержанных типов наборов данных:
* *Дано:* пользователь открыл столбчатую диаграмму на основе простого или составного набора данных;
* *Тогда:* секция *«Меры»* не отображается;
* *И:* пользователь не может добавить Меру на полки или выбрать её в настройках.

*AC.3* — Отображение Меры в левой панели:
* *Дано:* в произвольном наборе данных есть валидная Мера с {{alias = "Валовая прибыль"}} и {{aggregation_kind = 1}};
* *Тогда:* в секции *«Меры»* отображается *«Валовая прибыль»*;
* *И:* рядом отображается ярлык {{AGR}};
* *И:* tooltip содержит описание, {{data_type}}, {{expression}} и {{name}}.

*AC.4* — Невалидная Мера недоступна для добавления:
* *Дано:* Мера имеет {{status = "invalid"}} и заполненный {{status_message}};
* *Когда:* пользователь видит её в секции *«Меры»*;
* *Тогда:* Мера отображается в error-состоянии;
* *И:* drag-and-drop на полки заблокирован;
* *И:* tooltip показывает причину невалидности.

*AC.5* — Мера на полке «Значения»:
* *Дано:* пользователь перетащил валидную агрегированную Меру на полку *«Значения»*;
* *Когда:* диаграмма строит runtime payload;
* *Тогда:* в {{select}} передан объект {{type = "measure"}} с {{name}} Меры и техническим alias вида {{[values][N]}};
* *И:* {{expression}} Меры не передаётся в payload.

*AC.6* — Неагрегированная Мера на полке «Значения»:
* *Дано:* пользователь перетаскивает Меру с {{aggregation_kind = 0}} на полку *«Значения»*;
* *Тогда:* размещение не блокируется;
* *И:* пользователь видит предупреждение о том, что для корректного отображения рекомендуется агрегированное выражение.

*AC.7* — Режим «Первое» на полке «Значения»:
* *Дано:* на полке *«Значения»* размещены несколько пилюль, включая Меры;
* *И:* включён режим *«Первое»*;
* *Когда:* диаграмма строит runtime payload;
* *Тогда:* для отображаемого значения используется только первая активная пилюля значения по текущим правилам диаграммы;
* *И:* если первой активной пилюлей является Мера, именно она передаётся как отображаемое значение.

*AC.8* — Режим «Все» на полке «Значения»:
* *Дано:* на полке *«Значения»* размещены несколько активных пилюль, включая две Меры;
* *И:* включён режим *«Все»*;
* *Когда:* диаграмма строит runtime payload;
* *Тогда:* все активные значения передаются в {{select}} с отдельными техническими alias;
* *И:* каждая Мера передаётся как отдельный объект {{type = "measure"}}.

*AC.9* — Агрегация на пилюле Меры не редактируется:
* *Дано:* Мера размещена на полке *«Значения»*;
* *Когда:* пользователь открывает настройки пилюли;
* *Тогда:* локальный выбор {{agg}} / {{aggr}} недоступен для изменения;
* *И:* пользователь видит пояснение, что агрегированность задаётся в настройках Меры.

*AC.10* — Неагрегированная Мера на полке «Категории»:
* *Дано:* пользователь перетащил Меру с {{aggregation_kind = 0}} на полку *«Категории»*;
* *Когда:* диаграмма строит runtime payload;
* *Тогда:* Мера используется как активная категория, если она является первой активной пилюлей полки;
* *И:* объект {{type = "measure"}} попадает в runtime-контекст группировки.

*AC.11* — Агрегированная Мера не допускается на полку «Категории»:
* *Дано:* пользователь пытается перетащить Меру с {{aggregation_kind = 1}} на полку *«Категории»*;
* *Тогда:* размещение блокируется;
* *И:* пользователь видит сообщение *«На полке "Категории" допустимы только неагрегированные Меры»*.

*AC.12* — Меры на полке «Серии» при режиме «Вкл»:
* *Дано:* на полке *«Серии»* размещена валидная неагрегированная Мера;
* *И:* режим серий включён;
* *Когда:* диаграмма строит runtime payload;
* *Тогда:* Мера попадает в {{group}} с alias вида {{[series][N]}};
* *И:* диаграмма строит столбцы с детализацией по этой серии.

*AC.13* — Меры на полке «Серии» при режиме «Выкл»:
* *Дано:* на полке *«Серии»* размещена Мера;
* *И:* режим серий выключен;
* *Когда:* диаграмма строит runtime payload;
* *Тогда:* Мера не попадает в активные блоки runtime payload;
* *И:* не влияет на количество столбцов и не блокирует запрос данных, если не используется в других активных настройках.

*AC.14* — Агрегированная Мера не допускается на полку «Серии»:
* *Дано:* пользователь пытается перетащить Меру с {{aggregation_kind = 1}} на полку *«Серии»*;
* *Тогда:* размещение блокируется;
* *И:* пользователь видит сообщение *«На полке "Серии" допустимы только неагрегированные Меры»*.

*AC.15* — WHERE-фильтр по неагрегированной Мере:
* *Дано:* Мера с {{aggregation_kind = 0}} размещена на полке *«Фильтры»*;
* *Когда:* пользователь настраивает фильтр;
* *Тогда:* доступен режим {{WHERE}};
* *И:* в runtime payload условие передаётся в {{where}} как объект {{type = "measure"}} со структурным {{condition}}.

*AC.16* — HAVING-фильтр по агрегированной Мере:
* *Дано:* Мера с {{aggregation_kind = 1}} размещена на полке *«Фильтры»*;
* *Когда:* пользователь настраивает фильтр;
* *Тогда:* доступен режим {{HAVING}};
* *И:* в runtime payload условие передаётся в структурную часть {{having}} как объект {{type = "measure"}}.

*AC.17* — Несовместимый режим фильтра блокируется:
* *Дано:* пользователь пытается выбрать {{WHERE}} для агрегированной Меры или {{HAVING}} для неагрегированной Меры;
* *Тогда:* выбор блокируется;
* *И:* пользователь видит пояснение из матрицы допустимости.

*AC.18* — Меры доступны в совместимых настройках правой панели:
* *Дано:* в правой панели столбчатой диаграммы есть selector, где сейчас можно выбрать поле или вычисляемое поле и сценарий совместим с Мерой;
* *Тогда:* в selector доступна секция или визуальное представление Мер;
* *И:* выбранная Мера сохраняется как ссылка по {{type = "measure"}}, {{name}}, {{datasetId}};
* *И:* {{expression}} Меры не копируется в настройку.

*AC.19* — Неподдержанный selector явно зафиксирован:
* *Дано:* конкретный selector правой панели не поддерживает Меры на текущем этапе;
* *Тогда:* это ограничение перечислено в документации реализации;
* *И:* отсутствие Мер в selector-е не выглядит как случайный дефект.

*AC.20* — Меры в вычисляемом поле виджета:
* *Дано:* пользователь редактирует вычисляемое поле виджета столбчатой диаграммы;
* *Когда:* набор данных содержит валидные Меры;
* *Тогда:* Меры доступны для вставки по системному {{name}} в двойных кавычках;
* *И:* вычисляемое поле сохраняет зависимость от {{name}} Меры.

*AC.21* — Метаданные диаграммы не копируют определение Меры:
* *Дано:* Мера размещена на любой поддержанной полке столбчатой диаграммы;
* *Когда:* пользователь сохраняет отчёт;
* *Тогда:* в конфигурации диаграммы сохранены {{type = "measure"}}, {{name}}, {{datasetId}} и локальные настройки размещения;
* *И:* {{expression}}, {{status}}, {{status_message}}, {{aggregation_kind}} и {{id}} из {{measures[]}} не сохраняются как источник истины в объекте размещения.

*AC.22* — Открытие сохранённой диаграммы с Мерой:
* *Дано:* в сохранённой столбчатой диаграмме есть пилюля {{type = "measure"}};
* *Когда:* пользователь открывает отчёт;
* *Тогда:* frontend сопоставляет пилюлю с актуальной Мерой по {{name}};
* *И:* отображает актуальный {{alias}}, {{AGR}} и статус из метаданных набора данных.

*AC.23* — Ошибка отсутствующей или невалидной Меры:
* *Дано:* сохранённая диаграмма активно использует Меру, которая отсутствует в наборе данных или имеет {{status = "invalid"}};
* *Когда:* пользователь открывает или обновляет диаграмму;
* *Тогда:* пилюля отображается в error-состоянии;
* *И:* запрос данных не выполняется;
* *И:* пользователь видит понятное сообщение с {{name}} Меры и причиной.

*AC.24* — Сортировка по Мере:
* *Дано:* пользователь включил сортировку по Мере на полке *«Значения»*;
* *Когда:* диаграмма строит runtime payload;
* *Тогда:* в {{order}} передан объект {{type = "measure"}} с {{name}}, техническим alias и направлением сортировки;
* *И:* backend обрабатывает сортировку по правилам backend-Шага 2.

*AC.25* — Экспорт диаграммы с Мерами:
* *Дано:* столбчатая диаграмма построена с использованием Меры;
* *Когда:* пользователь запускает экспорт диаграммы;
* *Тогда:* экспорт использует те же активные Меры и значения, что экранная диаграмма;
* *И:* объект Меры передаётся в backend как {{type = "measure"}} без копирования {{expression}}, если экспорт использует общий runtime payload.

*AC.26* — Обратная совместимость:
* *Дано:* существующая столбчатая диаграмма не использует Меры;
* *Когда:* пользователь открывает, редактирует, сохраняет, строит или экспортирует диаграмму после внедрения доработки;
* *Тогда:* поведение диаграммы, SQL-запрос и результат не меняются по сравнению с текущей реализацией.

*AC.27* — Backend-ошибки отображаются без повреждения конфигурации:
* *Дано:* backend вернул контролируемую ошибку по Мере при построении runtime-запроса;
* *Тогда:* frontend показывает пользователю сообщение ошибки;
* *И:* не удаляет пилюлю Меры автоматически;
* *И:* не изменяет сохранённую конфигурацию диаграммы без действия пользователя.
