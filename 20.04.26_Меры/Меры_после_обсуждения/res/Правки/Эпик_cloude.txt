# Анализ и доработка постановки эпика «Меры»

Предложенные изменения касаются **трёх системных решений**: переход от связи по `measure_id` к связи по `name`, введение мягкого удаления (`deleted`), и оформление синтаксиса мер в формулах через одинарные кавычки. Каждое из этих решений затрагивает несколько разделов оригинальной постановки.

***

## Блок 1. Раздел «Ключевые понятия и определения»

### Почему требуется доработка

Определение Меры содержит упоминание `measure_id` как механизма связи и описание синтаксиса оборачивания в одинарные кавычки, но оба этих аспекта сформулированы недостаточно полно. Нужно: (а) зафиксировать, что **уникальность `name` является основой связей** во всех внешних ссылках — а не `id`; (б) чётко определить `deleted` как новый атрибут жизненного цикла; (в) однозначно зафиксировать синтаксис одинарных кавычек для Мер в формулах.

### Что заменить

**Оригинал (первый bullet «Мера»):**
> *Мера — именованное вычислимое выражение... Сама по себе Мера не вычисляется в момент создания; она вычисляется динамически в контексте конкретной визуализации...*

**Заменить на:**

* +Мера+ — именованное вычислимое выражение, определённое на уровне +произвольного+ набора данных. Мера представляет собой SQL-выражение, при написании которого аналитиком могут использоваться поля данного набора данных, ранее определённые Меры и глобальные переменные. Сама по себе Мера не вычисляется в момент создания; она вычисляется динамически в контексте конкретной визуализации — в зависимости от полки, на которую она размещена, её выражение инжектируется в строго определённую SQL-клаузу внешнего запроса. Основой всех внешних ссылок на Меру (из визуализаций, настроек, формул других Мер и вычисляемых полей) является +уникальное имя Меры ({{name}}) в рамках одного набора данных+. При *переименовании*, Мера теряет связь со всеми связанными объектами, а в случае появления новой Меры с тем же именем (до переименования) - она автоматически займёт её место по уже существующим связям.
* +Удалённая Мера+ (аттрибут {{deleted}} = 1) — Мера, получившая отметку об удалении. Физически не удаляется из метаданных набора данных, но исчезает из всех пользовательских интерфейсов и панелей выбора полей. Ссылки на удалённую Меру в визуализациях и настройках визуализаций, а также Меры, использующие удалённую Меру в формулах, становятся +невалидными+.

## Блок 2. Раздел «Структура метаданных Меры»

### Почему требуется доработка

В JSON-схеме отсутствует поле `deleted`. Поле `id` описано как основа всех внешних ссылок — что прямо противоречит новой концепции связей по `name`. Описание поля `id` нужно скорректировать, поле `deleted` — добавить.

### Что заменить

**Оригинал (JSON-пример + таблица полей метаданных):**
```json
{
  "id": "847b1ec3-...",
  "name": "Валовая прибыль",
  ...
  "status": "valid"
}
```
| `id` | string | Стабильный UUID идентификатор; не изменяется при переименовании |

**Заменить JSON-пример и таблицу на:**

```json
{
  "id": "847b1ec3-bbf8-4365-85fb-c4fca2a06e2e",
  "name": "Валовая прибыль",
  "description": "Разница между выручкой и себестоимостью",
  "expression": "SUM('revenue') - SUM('cost')",
  "aggregation_kind": 1,
  "data_type": "number",
  "hierarchy": "Финансовые показатели",
  "level": 10,
  "status": "valid",
  "deleted": 0
}
```

| Поле | Тип | Описание |
|---|---|---|
| `id` | string | Технический UUID; используется для внутренних целей системы. **Не является основой внешних ссылок** — все ссылки из визуализаций, настроек и формул хранятся по `name` |
| `name` | string | Отображаемое уникальное название в рамках одного набора данных; *является ключом связи* во всех внешних ссылках на Меру: в визуализациях, настройках визуализаций, формулах, используемых при создании вычисляемых полей и других Мер, т.д. |
| `description` | string | Необязательное описание |
| `expression` | string | SQL-выражение; Меры в формулах оборачиваются в одинарные кавычки: 'measure_name'; обычные поля — в двойные кавычки: "field_name" |
| `aggregation_kind` | int (0/1) | Агрегированная мера; задаётся пользователем явно (1 — да, 0 — нет) |
| `data_type` | string | Логический тип результата: `number`, `string`, `date`, `datetime` и т.д. |
| `hierarchy` | string | Необязательная группа/иерархия отображения в панели полей |
| `level` | int | Порядок Меры внутри иерархии |
| `status` | enum | `valid` или `invalid`; **вычисляется системой** по результатам валидации |
| `deleted` | int (0/1) | `0` — мера активна; `1` — мера помечена удалённой (мягкое удаление); не отображается в UI, ссылки на неё становятся невалидными |

## Блок 3. Раздел «Метаданные визуализации и ссылки на Меры»

### Почему требуется доработка

Весь раздел построен на концепции `measure_id` как стабильной связи при переименовании — это противоречит новой архитектуре. Раздел необходимо переписать полностью: связь хранится по `measure_name`, переименование разрывает ссылки (аналогично удалению), а логика «создал меру с тем же именем — ссылки восстановились» должна быть задокументирована.

### Что заменить

**Оригинал (весь раздел h3 «Метаданные визуализации и ссылки на Меры»):**
> *Во всех метаданных визуализации связь с Мерой хранится по стабильному `measure_id`. Это позволяет сохранять привязки при переименовании Меры...*

**Заменить на:**

***

### Метаданные визуализации и ссылки на Меры

Во всех метаданных визуализации связь с Мерой хранится по **имени Меры (`measure_name`)** — аналогично тому, как обычные поля набора данных адресуются по имени поля в текущей системе. Поле `measure_id` не используется как ключ связи.

Это означает:
- **Переименование Меры** разрывает все ссылки на прежнее имя (визуализации, формулы других Мер, вычисляемые поля). Затронутые объекты получают статус `invalid` или ошибочное состояние, аналогичное удалению Меры.
- **Создание новой Меры с именем, совпадающим с именем удалённой или переименованной**, автоматически «восстанавливает» все ссылки — система начинает разрешать имя в новую Меру без каких-либо ручных действий пользователя.
- **Переименование Меры является намеренно деструктивным действием** — это не техническая деталь, а продуктовое поведение. UI должен информировать аналитика о последствиях переименования (количество затронутых визуализаций и Мер) до подтверждения.

Каждое использование Меры в визуализации хранит:
- тип сущности `measure`;
- ссылку на `measure_name`;
- дополнительные параметры в зависимости от конкретной полки и сценария.

Пример для фильтра по Мере:
```json
{
  "filters": [
    {
      "id": "f9c35f8f-9f52-49a5-a47f-57badace6312",
      "type": "measure",
      "measure_name": "Валовая прибыль",
      "filter_mode": "HAVING",
      "condition": "> 0"
    }
  ]
}
```

| Поле | Тип | Описание |
|---|---|---|
| `type` | string | `"measure"` — отличает от вычисляемых полей (`"calculated"`) |
| `measure_name` | string | Имя Меры; **является ключом связи** (не `measure_id`) |
| `filter_mode` | string | `WHERE` или `HAVING` |
| `condition` | string | Условие фильтрации |

## Блок 4. Раздел «Пользовательский интерфейс» — h4 «Интерфейс сsоздания и редактирования Меры»

### Почему требуется доработка

Необходимо явно описать визуальное различие Мер и обычных полей **в редакторе выражений**: Меры оборачиваются в одинарные кавычки (`'Мера_1'`), обычные поля — в двойные (`"field_1"`). Это разграничение критически важно для читаемости формул и должно быть зафиксировано в UI-требованиях к редактору.

### Что заменить

**Оригинал (bullet «Выражение» в форме создания Меры):**
> *В редакторе доступен список полей текущего набора данных и ранее созданных Мер, доступных для вставки в выражение (Меры оборачиваются в одинарные кавычки: `'field_name'` или `'measure_name'`).*

**Заменить на:**

> * **Выражение** (обязательное) — редактор выражений, эквивалентный редактору вычисляемых полей виджета. Требования к редактору:
>   * Синтаксис и функции — идентичны вычисляемым полям.
>   * В редакторе доступен список полей текущего набора данных и ранее созданных активных (`deleted = 0`) Мер, доступных для вставки в выражение.
>   * **Синтаксис вставки в выражение**: обычные поля набора данных вставляются в **двойных кавычках**: `"field_name"`; Меры вставляются в **одинарных кавычках**: `'measure_name'`. Это визуально разграничивает обращения к полям и к Мерам непосредственно в теле формулы.
>   * Автодополнение должно различать и предлагать отдельно: поля набора данных (с двойными кавычками) и Меры (с одинарными кавычками). В выпадающем списке автодополнения Меры визуально отличаются от полей (например, иным значком или секцией).
>   * Подсветка синтаксиса должна отличать одинарные кавычки (ссылки на Меры) от двойных (ссылки на поля) — разными цветами или стилями.
>   * Подсветка синтаксических ошибок и другие продвинутые возможности нового редактора кода.

## Блок 5. Раздел «Удаление Меры» (h4)

### Почему требуется доработка

Оригинальный раздел описывает **физическое (каскадное) удаление** Меры из метаданных набора данных и всех визуализаций. Новая концепция заменяет это на **мягкое удаление** (`deleted = 1`): мера не уничтожается физически, а помечается удалённой, исчезает из UI и делает все ссылки на неё невалидными. Раздел требует полного переписывания.

### Что заменить

**Оригинал (весь раздел h4 «Удаление Меры»):**
> *Если Мера не используется ни в одной визуализации, удаление выполняется без дополнительной логики... После подтверждения удаления мера удаляется из метаданных набора данных и из всех визуализаций и полок...*

**Заменить на:**

***

h4. Удаление Меры (мягкое удаление).

При нажатии иконку удаления Меры система определяет, используется ли Мера в каких-либо визуализациях или формулах других Мер.

*Если Мера не используется* нигде — система запрашивает подтверждение (без предупреждений о зависимостях), после подтверждения Мера получает флаг `deleted = 1`.

*Если Мера используется* хотя бы в одной визуализации или в формуле другой Меры — перед удалением отображается предупреждение:
* *«Мера "[Название]" используется в [N] визуализациях и/или в выражениях других Мер. Удаление Меры может вызвать ошибки в связанных объектах. Продолжить?»*
* После подтверждения:
** Мера получает флаг {{deleted = 1}} и *не удаляется физически* из метаданных набора данных.
** Мера исчезает из списка отображаемых Мер в настройках набора данных (кроме случаев активации тумблера "Отображать удалённые Меры").
** Мера не отображается в боковой панеле полей в конструкторе визуализаций.
** Мера не отображается в списке доступных элементов в редакторах формул (вычисляемых полей и других Мер).
** Все визуализации, содержащие эту Меру на полках или в настройках, переходят в состояние ошибки: удалённая Мера подсвечивается в списке как ошибочная (красный ореол, иконка ⚠, при наведении отображается текст ошибки или причина невалидности), запрос данных блокируется с сообщением об ошибке.
** Все Меры, использующие имя удалённой Меры в своей формуле, получают статус {{invalid}}.

*Физическое удаление* записи о Мере из метаданных не выполняется. Это позволяет восстановить удалённую меру (при активации тумблера "Отображать удалённые Меры"). 
* Если аналитик создаёт новую Меру с именем удалённой - новая запись не создаётся, а удалённая мера перезаписывается и получает активный статус ({{deleted = 0}}). Cистема начинает разрешать все имеющиеся ссылки на это имя в "новую" активную Меру, и ошибочные состояния устраняются.

*Примечание*: набор данных может быть сохранён даже при наличии Мер с {{deleted = 1}} или {{status = invalid}}.

## Блок 6. Раздел «Валидация Мер» — расширение сценариев

### Почему требуется доработка

Оригинальная постановка описывает только одну триггерную точку невалидности Меры: изменение SQL-запроса набора данных (исчезновение поля). Новые требования добавляют **вторую триггерную точку**: переименование или удаление другой Меры, используемой в формуле. Это принципиально расширяет алгоритм ревалидации — он теперь обязан быть **граф-осведомлённым**: при изменении одной Меры система обходит все зависимые Меры.

### Что добавить

После существующего раздела «Жизненный цикл Меры после изменения SQL набора данных» добавить новый подраздел:

***

h4. Валидация Мер при изменении других Мер.

Помимо ревалидации при изменении SQL-запроса, система выполняет ревалидацию зависимых Мер при *переименовании или мягком удалении* любой Меры данного набора данных.

*Алгоритм:*
# При переименовании Меры A ({{name_old}} → {{name_new}}) или при её мягком удалении ({{deleted = 1}}) система обходит все остальные Меры того же набора данных.
# Для каждой Меры, в выражении которой содержится ссылка {{'name_old'}}, присваивается статус {{invalid}} с причиной: *«Мера {{'name_old'}}, на которую ссылается выражение, была переименована или удалена»*, т.к. ссылка становится неразрешимой (нет активной Меры с именем {{name_old}}).
# Если впоследствии создаётся новая Мера с именем {{name_old}} (или, при переименовании, возвращается исходное имя) или же удалённая Мера восстанавливается, система выполняет ревалидацию Мер — при синтаксически корректном выражении они получают статус {{valid}}.

*Сводная таблица триггеров ревалидации Меры:*

| Событие | Какие Меры ревалидируются | Критерий проверки |
|---|---|---|
| Изменение SQL набора данных | Все Меры, ссылающиеся на поля Набора данных | Поле из выражения отсутствует в актуальном составе Набора |
| Переименование или мягкое удаление Меры A | Все Меры, ссылающиеся на прежнее имя Меры A | Ссылка {{'old_name'}} не разрешается в активную ({{deleted=0}}) Меру |
| Восстановление Меры / создание Меры с тем же именем | Все Меры со статусом {{invalid}} | Ссылка вновь разрешается в активную валидную Меру |

## Блок 7. Раздел «Устойчивость к изменениям метаданных»

### Почему требуется доработка

Пункт «Переименование Меры» полностью противоречит новой концепции: оригинал утверждает, что «`measure_id` остаётся прежним» и дашборды продолжают работать. В новой архитектуре переименование — деструктивное действие.

### Что заменить

**Оригинал:**
> *Переименование Меры: отображаемое имя обновляется во всех панелях, но `measure_id` остаётся прежним. Любые дашборды продолжают ссылаться на меру по её идентификатору, что сохраняет целостность связей при миграции/импорте отчётов.*

**Заменить на:**

> * **Переименование Меры**: имя является ключом связи, поэтому переименование **разрывает** все существующие ссылки из визуализаций, формул других Мер и вычисляемых полей. Все зависимые объекты переходят в состояние ошибки (`invalid`/error-состояние пилюли). UI предупреждает аналитика о числе затронутых объектов до подтверждения переименования. Если создать новую Меру с прежним именем — ссылки восстановятся автоматически. Поле `id` сохраняется как технический идентификатор для внутренних нужд системы, но не используется как ключ внешних ссылок.

**Оригинал:**
> *Удаление Меры: при подтверждении удаления Мера удаляется из метаданных набора данных и из всех полок всех визуализаций, где она использовалась. Связи по её `measure_id` полностью удаляются.*

**Заменить на:**

> * **Удаление Меры**: при подтверждении Мера получает флаг `deleted = 1` (мягкое удаление) и исчезает из всех пользовательских интерфейсов. Физически запись о Мере сохраняется в метаданных. Все ссылки на имя удалённой Меры в визуализациях и формулах других Мер становятся невалидными. Физическое удаление данных не выполняется, что позволяет автоматически «восстановить» связи при создании новой Меры с тем же именем.

## Блок 8. Раздел «Критерии приёмки» — AC.12 и доп. AC.14

### Почему требуется доработка

AC.12 описывает переименование как безопасную операцию, сохраняющую привязки по `measure_id` — это прямо противоречит новой концепции. Кроме того, в AC отсутствует критерий приёмки для мягкого удаления и каскадной невалидности зависимых Мер.

### Что заменить

**Оригинал AC.12:**
> *Когда: пользователь переименовывает Меру. Тогда: в визуализациях обновляется отображаемое имя, а привязка сохраняется по `measure_id`...*

**Заменить AC.12 и добавить AC.14:**

***

**AC.12 — Переименование и удаление Меры.**
* **Дано**: Мера используется в одной или нескольких визуализациях и/или в выражении другой Меры.
* **Когда**: пользователь переименовывает Меру.
* **Тогда**: система показывает предупреждение с числом затронутых визуализаций и Мер.
* **И**: после подтверждения все ссылки на прежнее имя становятся невалидными; затронутые пилюли переходят в error-состояние; зависимые Меры получают статус `invalid`.
* **И**: при создании новой Меры с прежним именем все ссылки автоматически восстанавливаются.
* **И**: при удалении используемой Меры система показывает аналогичное предупреждение и выполняет мягкое удаление (`deleted = 1`); запись о Мере сохраняется в метаданных; физическое каскадное удаление не выполняется.

**AC.14 — Удаление Меры.**
* **Дано**: Мера A используется в формуле Меры B; Мера B размещена на полке Визуализации_1.
* **Когда**: Мера A удаляется (получает {{deleted = 1}}) (или переименовывается).
* **Тогда**: Мера A исчезает из списка Мер в настройках набора данных и из боковой панели конструктора.
* **И**: Мера B получает статус {{invalid}} с читаемой причиной ошибки.
* **И**: Визуализация_1, содержащая Меру B на полке, переходит в error-состояние с блокировкой запроса данных.
* **И**: при создании новой Меры с именем Меры A система ревалидирует Меру B; если выражение Меры B корректно - она получает статус `valid`, а Визуализация_1 восстанавливает работоспособность.

***
