h3. Контекст и цель истории.
Полное описание продуктовой логики — в Эпике по Мерам ([https://jira.modusbi.ru/browse/MB-4364]).

Мера — именованное SQL-выражение на уровне набора данных. Backend уже реализует: хранение и CRUD Мер в {{datasets.measures[]}}, приём в runtime payload и раскрытие выражения Меры при построении SQL.

В рамках этой Истории требуется подключить Меры к пользовательским сценариям столбчатой диаграммы: отображение Мер в левой панели, размещение на полках диаграммы, использование в совместимых настройках, сохранение ссылок в метаданных визуализации и формирование runtime payload для backend-а по уже описанным контрактам.

Визуализация не хранит определение Меры. В конфигурации и runtime payload сохраняется ссылка {{type = "measure"}} + {{name}} + {{datasetId}}. Остальные характеристики Меры всегда берутся из актуальных метаданных набора данных.

_Пользовательская история:_ Как аналитик, я хочу использовать Меры в столбчатой диаграмме так же удобно, как обычные и вычисляемые поля, чтобы переиспользовать единые бизнес-показатели без дублирования формул в каждой визуализации.

----
h3. 1. Границы истории.

* Секция *«Меры»* в левой панели конструктора — только для {{barChart}} / {{column}} на *произвольном* наборе данных.
* Drag-and-drop валидных Мер на полки: *«Значения»*, *«Категории»*, *«Серии»*, *«Фильтры»*, доп. ось значений {{valuesExtra}}.
* Использование Мер везде, где сейчас допускаются обычные и вычисляемые поля: совместимые селекторы правой панели, редактор вычисляемых полей виджета.
* Визуальное отличие пилюли Меры (тёмно-оранжевый цвет, иконка, ярлык {{AGR}} для {{aggregation_kind = 1}}).
* Обработка Мер со статусом {{invalid}} в конструкторе и при построении диаграммы.
* Сохранение размещения по {{type = "measure"}}, {{name}}, {{datasetId}} + локальный {{id}} размещения.
* Формирование runtime payload с объектами {{type = "measure"}} для {{/v1/api/recordsets/<dataset_id>}}.
* Сортировка по Мере и экспорт диаграммы с Мерами — через существующие механизмы.
* Полная обратная совместимость диаграмм без Мер.

----
h3. 2. Модель Мер.
* Мера доступна только для *произвольного* набора данных, хранится в {{datasets.measures[]}}.
* Ключ связи — {{name}}. {{alias}} — только для отображения. {{id}} из {{measures[]}} не используется как внешний ключ.
* {{expression}} не копируется в конфигурацию диаграммы и не передаётся в runtime payload.
* Невалидные Меры ({{status = "invalid"}}) недоступны для нового размещения и выбора.
* Если сохранённая связь по {{name}} стала невалидной/отсутствующей — связь сохраняется, ошибка показывается только если Мера участвует в активной полке/настройке.

{code:json}
{
  "id": "847b1ec3-bbf8-4365-85fb-c4fca2a06e2e",
  "name": "Мера.Валовая_прибыль",
  "alias": "Валовая прибыль",
  "description": "Разница между выручкой и себестоимостью",
  "expression": "SUM(\"revenue\") - SUM(\"cost\")",
  "aggregation_kind": 1,
  "data_type": "number",
  "hierarchy": "Финансовые показатели",
  "level": 10,
  "status": "valid",
  "status_message": ""
}
{code}

h3. 3. Целевой интерфейс.

h4. 3.1. Левая панель — секция «Меры».
Ниже секции *«Поля»* добавляется секция *«Меры»* (группа-раскрывашка). Доработка нужна только для диаграммы столбчатой ({{barChart}}/{{column}}) на произвольном наборе данных; для простых/составных наборов секция не отображается.

В секции:
* {{alias}} Меры; ярлык {{AGR}} для {{aggregation_kind = 1}};
* группировка по {{hierarchy}} (если заполнено), внутри группы — сортировка по {{level}}, затем по {{alias}}; Меры без {{hierarchy}} — в корне списка (поведение по аналогии с обычными полями);
* tooltip на основе описания Меры ({{description}}), {{data_type}}, полный {{expression}}, {{name}}, {{status_message}} (если невалидна);
* существующий поиск по полям должен находить Меры по {{alias}} или {{name}} и визуально отличать их от полей;
* невалидная Мера отображается с error-иконкой, для неё заблокированы drag-and-drop и выбор в селекторах, а tooltip показывает {{status_message}}.

h4. 3.2. Полки диаграммы.
Текущие полки — *«Значения»* (режим «Первое»/«Все»), *«Категории»*, *«Серии»* (режим «Вкл»/«Выкл»), *«Фильтры»*, доп. ось *{{valuesExtra}}*. Доработка: принять пилюли типа Мера по правилам п.4, отрисовать их тёмно-оранжевым цветом с отдельной иконкой во всех перечисленных местах, включая фильтрующую пилюлю с явным признаком «Мера».

Drag-and-drop на несовместимую полку — блокировка с визуальным запретом (курсор/подсветка) и текстом причины по матрице п.4. Одна Мера может быть размещена на нескольких полках, если каждое размещение допустимо.

h4. 3.3. Правая панель настроек (см. вложенный скриншот).
Текущие блоки правой панели: *Общие настройки*, *Данные*, *Ось «Категорий»*, *Ось «Значений»*, *Подписи данных*, *Всплывающая подсказка*, *Легенда*, *Основной стиль*, *Стиль элементов*, *Режим фильтра*, *Дрилл*, *Настройки клика*, *Инфо*, *Рамка компонента*.

Требуемые доработки по блокам:
|| Блок правой панели || Требуется доработка под Меры ||
| *Ось «Значений»* | Форматирование (число, точность, разделители, единицы) должно применяться к Мере по её {{data_type}}; локальная агрегация {{agg}}/{{aggr}} на пилюле Меры скрывается / readonly с подсказкой «Агрегация Меры задаётся в настройках Меры» |
| *Ось «Категорий»* | Без изменений в логике оси; учитывать, что первой активной пилюлей может быть Мера ({{aggregation_kind = 0}}) |
| *Подписи данных* | Подпись должна брать актуальный {{alias}} Меры, форматирование чисел — по {{data_type}} |
| *Всплывающая подсказка* | Если пилюля Меры используется как {{valueType = "tooltip"}}, обрабатывается как текущая логика tooltip-полей (см. пример с настроенной подсказкой на скриншоте, где уже используются вычисляемые поля через HTML-шаблон) |
| *Легенда* | Название серии/значения в легенде — по актуальному {{alias}} Меры |
| *Режим фильтра* | Без изменения логики самого блока; фильтрующие пилюли-Меры на полке «Фильтры» обрабатываются по п.4.5 |
| *Дрилл* | Мера не участвует как уровень дрилла (дрилл требует иерархию измерений); ограничение фиксируется явно, drill-селектор Меры не показывает |
| *Настройки клика, Инфо, Рамка компонента, Основной стиль, Стиль элементов* | Доработка не требуется — эти блоки не оперируют полями/Мерами |
| *Общие настройки, Данные* | Проверить наличие переключателей, ссылающихся на поля диаграммы (если есть — применить правила совместимых селекторов) |

Общее правило для любого selector-а правой панели, где сейчас выбирается поле или вычисляемое поле и сценарий совместим с типом Меры: показывать Меры отдельной секцией/визуально отличимо, искать по {{alias}} OR {{name}}, показывать {{AGR}}, не допускать выбор {{invalid}}-Меры, применять матрицу допустимости конкретного selector-а (измерение → только {{aggregation_kind = 0}}; значение → любая валидная Мера; фильтр → правило WHERE/HAVING; сортировка → допустима, если backend может построить {{ORDER BY}}). Если конкретный selector технически не поддерживает Меру на этом шаге — ограничение явно фиксируется в документации реализации, а не оставляется как немой пробел.

h4. 3.4. Вычисляемые поля виджета.
В редакторе вычисляемых полей виджета столбчатой диаграммы:
* отдельная секция *«Меры»* с Мерами текущего набора данных;
* drag-and-drop / автокомплит вставляет {{name}} Меры в двойных кавычках, например {{"Мера.Валовая_прибыль"}}; квадратные скобки не используются;
* автокомплит ищет по {{alias}} OR {{name}}, визуально отличает Меры от полей;
* вычисляемое поле хранит зависимость от {{name}} Меры; если Мера становится {{invalid}}, зависящее вычисляемое поле переходит в ошибочное состояние.

h4. 3.5. Отладка (debug-режим).
Текущий переключатель *«Отладка»* конструктора (виден на скриншоте) должен без доработок отображать сформированный runtime payload, включая объекты {{type = "measure"}}, — отдельная разработка debug-режима не требуется, только проверка, что объекты Мер корректно попадают в существующий вывод.

h3. 4. Матрица допустимости Мер по полкам.
|| Полка || Runtime-контекст || {{aggregation_kind = 0}} || {{aggregation_kind = 1}} || Примечание ||
| Значения / {{valuesExtra}} | {{select}} | Допускается, с предупреждением | Допускается | Предупреждение: «Выражение помечено как неагрегированное. Рекомендуется использовать агрегатную функцию, например SUM(...)» |
| Категории | {{group}} + {{select}} | Допускается (только первая активная пилюля) | Блокируется — «На полке "Категории" допустимы только неагрегированные Меры» | — |
| Серии | {{group}} + {{select}}, только при режиме «Вкл» | Допускается | Блокируется — «На полке "Серии" допустимы только неагрегированные Меры» | При «Выкл» Мера не влияет на runtime payload |
| Фильтры — WHERE | {{where}} | Допускается | Блокируется | Режим WHERE/HAVING определяется автоматически по {{aggregation_kind}} и недоступен для ручного изменения |
| Фильтры — HAVING | {{having}} | Блокируется | Допускается | см. выше |

Для агрегированной Меры доп. агрегирующая функция не применяется — выражение уже содержит агрегацию. Условия по нескольким Мерам на полке «Фильтры» объединяются через {{AND}} внутри своей SQL-клаузы; WHERE- и HAVING-Меры допустимы одновременно.

h3. 5. Хранение в конфигурации диаграммы.
Пилюля Меры в {{axes[].fields[]}}:
{code:json}
{
  "type": "measure",
  "name": "Мера.Валовая_прибыль",
  "datasetId": 244,
  "id": "visual_measure_4f9b7e2d",
  "alias": "Валовая прибыль",
  "valueType": "value",
  "order": null,
  "orderIndex": null
}
{code}
|| Поле || Обязат. || Описание ||
| {{type}} | Да | Всегда {{measure}} |
| {{name}} | Да | Ключ связи с {{datasets.measures[].name}} |
| {{datasetId}} | Да | Набор данных Меры |
| {{id}} | Да | Локальный id размещения пилюли, не id Меры |
| {{alias}} | Нет | Кэш для отображения при потере связи с набором данных; не используется как ключ связи |
| {{valueType}} | Нет | {{value}} / {{tooltip}} — для полки «Значения» |

{{expression}}, {{aggregation_kind}}, {{data_type}}, {{status}}, {{status_message}}, {{description}}, {{hierarchy}}, {{level}} в конфигурацию диаграммы *не сохраняются*. Локальные настройки размещения (сортировка, формат, точность, цвет, единицы, подпись, режим tooltip) хранятся рядом с объектом использования Меры и не пишутся обратно в {{datasets.measures[]}}.

h3. 6. Runtime payload.
Минимальный объект Меры для {{/v1/api/recordsets/<dataset_id>}}:
{code:json}
{
  "type": "measure",
  "name": "Мера.Валовая_прибыль",
  "alias": "[values][0]",
  "id": "visual_measure_4f9b7e2d",
  "fieldAlias": "Валовая прибыль"
}
{code}
{{alias}} — технический alias результата запроса (не {{alias}} Меры). {{fieldAlias}} — только presentation-поле для диагностики. Frontend не передаёт для {{type = "measure"}} непустые {{calc}}, {{aggr}}, {{agg}}.

Соответствие runtime-блок → SQL-контекст: {{select}} → SELECT, {{group}} → GROUP BY, {{where}} → WHERE, {{having}} → HAVING, {{order}} → ORDER BY.

* *Значения, режим «Первое»:* в payload попадает только первая активная пилюля.
* *Значения, режим «Все»:* каждая Мера — отдельный объект в {{select}} с alias {{[values][0]}}, {{[values][1]}}... .
* *Категории:* первая активная неагрегированная Мера попадает в {{group}} и {{select}} с alias {{[categories]}}.
* *Серии, «Вкл»:* каждая активная неагрегированная Мера — в {{group}} с alias {{[series][N]}}. *«Выкл»:* Меры серии не попадают в {{group}}/{{select}}/{{order}}.
* *Фильтры:* неагрегированная Мера → {{where}} с {{condition}}; агрегированная → {{having.items}} с {{condition}}.
* *Сортировка:* Мера в {{order}} с {{direction}}; если сортировка невозможна в текущем SQL — backend возвращает контролируемую ошибку без повреждения конфигурации.

----
h3. 7. Загрузка и синхронизация при открытии диаграммы.
При открытии конструктора: получить актуальные {{measures}} набора данных → построить секцию «Меры» → сопоставить каждую сохранённую пилюлю {{type = "measure"}} по {{name}} + {{datasetId}} → отобразить актуальный {{alias}}/{{AGR}}/статус → при изменении {{aggregation_kind}} перепроверить совместимость с полкой (несовместимая пилюля → error-состояние, блокировка запроса).

----
h3. 8. Обработка пограничных сценариев.
* Нет Мер в наборе данных — секция «Меры» пуста, диаграмма работает как раньше.
* Набор данных не произвольный — секция «Меры» не отображается, drag-and-drop и селекторы недоступны.
* Мера стала {{invalid}} — новая вставка блокируется, существующая пилюля — error, запрос не выполняется, если пилюля в активной полке/настройке.
* Мера удалена из набора данных — пилюля не удаляется автоматически, отображается как ошибка отсутствующей Меры.
* Изменился {{alias}} без изменения {{name}} — связь сохраняется, отображается новый {{alias}}.
* Изменилось {{expression}} — следующий запрос использует актуальное выражение, копия не хранится.
* Мера одновременно на нескольких полках — допустимо при совместимости каждого размещения.
* Мера с {{data_type = "string"}} на полке «Значения» — рекомендуется frontend-валидация типа до запроса; иначе контролируемая ошибка backend.
* Фильтр по Мере с незаполненным условием — фильтр неактивен, в runtime payload не попадает.
* Экспорт диаграммы с Мерами — использует тот же runtime payload и активные Меры, что экранное построение.

h3. 9. Backend-контракты (переиспользование, без доп. доработки backend).
|| Контракт || Требуемое поведение ||
| {{datasets}} | Возвращает актуальный {{measures}} со статусами и метаданными |
| {{/v1/api/recordsets/<dataset_id>}} | Принимает {{type = "measure"}} в {{group}}, {{select}}, {{where}}, {{having}}, {{order}}, раскрывает через {{measures[].expression}} |
| Экспорт | Обрабатывает Меры тем же payload/SQL-builder-ом, что экранное построение |

Backend возвращает контролируемую ошибку (с {{measure_name}}, runtime-блоком и причиной), если: Мера не найдена / {{invalid}} / {{datasetId}} не совпадает / агрегированная Мера в {{group}}/{{where}} / неагрегированная в {{having}} / передан непустой {{calc}}/{{agg}}/{{aggr}} / некорректный оператор фильтра / SQL не может быть построен.

h3. 10. Права доступа.
Отдельные права не вводятся. Чтение Мер — по праву чтения набора данных/отчёта; изменение конфигурации диаграммы с Мерами — по праву редактирования отчёта/виджета; CRUD Мер — по праву на набор данных.

h3. 11. Критерии приёмки.
*AC.1.* Секция «Меры» отображается в левой панели для {{barChart}}/{{column}} на произвольном наборе данных и не отображается для простых/составных наборов.
*AC.2.* Валидная Мера перетаскивается на «Значения», «Категории», «Серии», «Фильтры», {{valuesExtra}} по матрице п.4; невалидная — блокируется во всех местах, включая правую панель и редактор вычисляемых полей.
*AC.3.* Агрегированная Мера блокируется на «Категории» и «Серии» с соответствующим сообщением; неагрегированная блокируется в HAVING-фильтре.
*AC.4.* Пилюля Меры — тёмно-оранжевая, с {{AGR}} для {{aggregation_kind = 1}}, во всех перечисленных в п.3.2 местах.
*AC.5.* Локальная агрегация ({{agg}}/{{aggr}}) на пилюле Меры недоступна для редактирования пользователем.
*AC.6.* Режим «Первое»/«Все» на «Значениях» и «Вкл»/«Выкл» на «Сериях» корректно управляют попаданием Мер в runtime payload.
*AC.7.* Runtime payload для Мер не содержит {{calc}}, {{expression}}, {{aggr}}/{{agg}} как источник выражения.
*AC.8.* Существующие диаграммы без Мер работают без изменений; открытие диаграммы с Мерами корректно восстанавливает актуальный {{alias}}/статус.
*AC.9.* Меры доступны во всех совместимых selector-ах правой панели (см. таблицу п.3.3); несовместимые selector-ы явно документированы, а не выглядят как дефект.
*AC.10.* Меры доступны в редакторе вычисляемых полей виджета, вставляются как {{"Мера.Имя"}}; зависимое вычисляемое поле реагирует на невалидность Меры.
*AC.11.* Экспорт диаграммы с Мерами воспроизводит тот же набор значений, что экранное построение.
