h3. Контекст и проблематика.
В аналитическом портале требуется внедрить *Меры* — именованные вычислимые выражения уровня *произвольного* набора данных, которые аналитик сможет определить один раз и далее использовать в визуализациях, фильтрах и выражениях.

Текущая frontend-логика работает с полями набора данных и вычисляемыми полями виджета через существующие структуры:
* метаданные визуализации: {{axes}}, {{axesDefault}}, {{fields}}, {{filters}} и т.д.;
* payload запроса данных {{/v1/api/recordsets/<dataset_id>}}: {{group}}, {{select}}, {{order}}, {{where}}, {{having}}, {{series}} и т.д.;
* ссылка на поле набора данных выполняется по {{name}} поля. {{name}} уникален в рамках одного набора данных;

Frontend-часть должна расширить эти структуры поддержкой Мер без изменения поведения обычных полей, вычисляемых полей виджета и существующих отчётов.

----
h3. Цель и бизнес-ценность.
+Шаг 1+ — реализовать frontend-интерфейс управления Мерами в настройках *произвольного* набора данных: секция «Меры», создание, редактирование, отображение, удаление, работа с редактором выражения и отображение статусов backend-валидации.

+Шаг 2+ — реализовать frontend-использование ранее созданных Мер в конструкторе визуализаций: отображение в панели полей, drag-and-drop на полки, выбор в совместимых селекторах, хранение ссылок на Меры в метаданных визуализации и передача ссылок в payload запроса данных.

+Последующие этапы / отдельная оценка+ — доработки, которые связаны с Мерами, но не должны смешиваться с минимальным объёмом Шага 1 и Шага 2: расширенная HAVING-фильтрация Сводной таблицы, импорт/экспорт и перенос между контурами, поддержка простых/составных наборов данных, расширенная токенизация редактора выражений, поддержка Мер в общей панели фильтров и других специальных сценариях.

Frontend не должен раскрывать SQL-выражение Меры как источник истины. В визуализации и payload должна передаваться ссылка на Меру по {{name}} / {{measure_name}}, а раскрытие выражения, SQL-валидация и генерация финального SQL-запроса выполняются backend-ом.

----
h3. Ключевые понятия и определения в рамках постановки.
* +Мера+ — именованное выражение уровня *произвольного* набора данных.
* +{{name}} Меры+ — уникальное имя Меры в рамках одного набора данных. Используется как ключ связи во внешних ссылках: в выражениях, метаданных визуализации и payload.
* +{{id}} Меры+ — стабильный технический идентификатор записи. Может использоваться frontend-ом для локальных операций со списком, но не является ключом связи между визуализацией и Мерой.
* +{{measure_name}}+ — ссылка на {{name}} Меры в метаданных визуализации и payload.
* +{{type = "measure"}}+ — признак объекта Меры в структурах визуализации. Должен отличать Меру от обычного поля и вычисляемого поля виджета.
* +{{aggregation_kind}}+ — признак агрегированности Меры: {{1}} — агрегированная, {{0}} — неагрегированная. Frontend использует значение для UX-валидации полок и визуальных ярлыков, но финальная проверка остаётся на backend-е.
* +{{status}} / {{status_message}}+ — статус backend-валидации Меры и причина ошибки. Frontend отображает эти значения и управляет доступностью действий.
* +Алиас поля+ — человекочитаемое название поля. Не должен использоваться как ключ связи вместо {{name}}.

----
h3. Пользовательский интерфейс и управление Мерами в настройках Набора данных.
h4. Шаг 1. Секция «Меры» в настройках набора данных.
В карточке *произвольного* набора данных под секцией «Описание полей набора данных» требуется добавить секцию «Меры».

Для оценки frontend-разработки учесть:
* отображение секции только для *произвольных* наборов данных;
* отсутствие секции и кнопки «+ Добавить меру» для *простых* и *составных* наборов данных;
* загрузку Мер из метаданных набора данных при открытии карточки;
* сохранение существующих Мер в интерфейсе при временно невалидном или очищенном SQL-запросе набора данных;
* обновление списка Мер после сохранения, удаления, проверки SQL набора и повторной backend-валидации.

h4. Шаг 1. Доступность кнопки «+ Добавить меру».
Кнопка «+ Добавить меру» активна только если:
# задан SQL-запрос произвольного набора данных;
# SQL-запрос успешно прошёл проверку;
# frontend получил актуальный состав полей набора данных.

Если условие не выполнено:
* кнопка находится в состоянии {{disabled}};
* при наведении отображается tooltip: *«Задайте и проверьте SQL-запрос набора данных»*;
* ранее сохранённые Меры не удаляются и продолжают отображаться с актуальным статусом.

h4. Шаг 1. Создание и редактирование Меры.
При создании или редактировании Меры открывается модальное окно увеличенного размера.

Форма содержит поля:
|| Поле интерфейса || Поле метаданных || Обязательность || Комментарий для оценки frontend ||
| Название | {{name}} | Да | Уникально в рамках набора данных. Используется как ключ связи. |
| Описание | {{description}} | Нет | Отображается в tooltip. |
| Тип данных | {{data_type}} | Да | Значения и дополнительные настройки согласовать с текущей моделью типов полей. |
| Агрегация | {{aggregation_kind}} | Да | Переключатель/флаг. Frontend отображает и передаёт значение; финальная проверка на backend-е. |
| Иерархия | {{hierarchy}} | Нет | Используется для display-группировки. |
| Уровень | {{level}} | Нет | Используется для сортировки внутри группы. |
| Выражение | {{expression}} | Да | Открывает редактор выражения. |

При редактировании существующей Меры форма открывается с текущими значениями. Если меняется {{name}}, frontend должен обработать возможный блокирующий ответ backend-а о зависимостях и показать список объектов, которые используют прежнее имя Меры.

h4. Шаг 1. Редактор выражения Меры.
В редакторе выражения требуется поддержать:
* список полей текущего набора данных;
* список ранее созданных Мер текущего набора данных;
* вставку поля набора данных по {{name}} поля, а не по алиасу;
* вставку ссылки на Меру в согласованном формате {{[measure_name]}};
* автодополнение или выбор из списка с визуальным различием обычных полей и Мер;
* возможность использовать Меры в выражениях других Мер;
* переход в расширенный режим редактора, если он доступен в текущем редакторе SQL/выражений.

Минимальный объём Шага 1: frontend должен корректно вставлять и сохранять ссылки на Меры. Глубокая переработка редактора кода ради отдельной токенизации, подсветки квадратных скобок, сложного ручного ввода и кастомной грамматики должна быть выделена в отдельный блок оценки, если это требует изменения текущего редактора.

h4. Шаг 1. Валидация и сохранение.
Frontend должен выполнять базовые UI-проверки до отправки:
* заполнение обязательных полей;
* отсутствие дубликата {{name}} среди Мер текущего набора данных, если список уже загружен;
* корректный тип значения для {{level}}.

Backend выполняет финальную валидацию выражения, ссылок, циклов, переменных, SQL-контекста и статуса Меры. Frontend должен:
* отправлять на backend актуальное состояние Меры или всего набора данных по согласованному контракту;
* принимать результат backend-валидации;
* отображать {{status = valid}} / {{status = invalid}};
* отображать {{status_message}} или текст ошибки в tooltip / сообщении;
* позволять сохранять набор данных при наличии Мер со статусом {{invalid}}, если backend допускает такое состояние;
* после изменения SQL-запроса набора данных обновлять статусы Мер по ответу backend-а.

h4. Шаг 1. Табличный список Мер.
Сохранённые Меры отображаются в секции «Меры» табличным списком:
|| Название || Тип данных || Агрегация || Иерархия || Уровень || Выражение (кратко) || Действия ||
| <{{name}}> | <{{data_type}}> | AGR / — | <{{hierarchy}}> | <{{level}}> | <первые N символов> | Редактировать / Удалить |

Для оценки учесть:
* отображение ярлыка {{AGR}} для {{aggregation_kind = 1}};
* отображение прочерка для {{aggregation_kind = 0}};
* tooltip с полным выражением;
* tooltip с описанием Меры;
* error-состояние строки для {{status = invalid}}: визуальное выделение, предупреждающая иконка, причина ошибки;
* группировку по {{hierarchy}};
* сортировку внутри группы по {{level}}, затем по {{name}};
* отображение Мер без {{hierarchy}} в корневом уровне секции.

h4. Шаг 1. Удаление и переименование.
При удалении Меры frontend вызывает backend-проверку зависимостей или обрабатывает результат удаления по согласованному контракту.

Поведение:
* если зависимостей нет — показать подтверждение удаления и после подтверждения удалить Меру;
* если зависимости есть — не удалять Меру и показать блокирующее сообщение со списком зависимых объектов;
* каскадное удаление из визуализаций, других Мер или вычисляемых полей frontend-ом не выполняется;
* при переименовании используемой Меры сохранение {{name}} блокируется по ответу backend-а;
* изменение других атрибутов Меры без изменения {{name}} не должно блокироваться только из-за наличия зависимостей, если backend разрешил сохранение.

----
h3. Метаданные визуализации и ссылки на Меры.
h4. Шаг 2. Расширение объектной модели поля визуализации.
В метаданных визуализации каждое размещение Меры должно храниться как объект в существующих структурах {{axes}} / {{axesDefault}} / {{fields}} без изменения формата обычных полей.

Рекомендуемый минимальный формат объекта Меры для согласования с backend:
{code:json}
{
  "type": "measure",
  "name": "Валовая прибыль",
  "measure_name": "Валовая прибыль",
  "datasetId": 244,
  "id": "measure_847b1ec3-bbf8-4365-85fb-c4fca2a06e2e",
  "alias": "[values][0]",
  "fieldAlias": "Валовая прибыль",
  "aggregation_kind": 1,
  "data_type": "number",
  "filterSqlType": "having",
  "lvl": 0,
  "valueType": "value"
}
{code}

Требования:
* {{type = "measure"}} обязателен;
* {{name}} / {{measure_name}} должны ссылаться на {{name}} Меры;
* {{measure_id}} / {{id}} не используется как ключ связи с backend-логикой;
* {{fieldAlias}} / {{title}} / {{alias}} могут использоваться для отображения и позиции на полке, но не заменяют {{measure_name}};
* существующие поля с {{type = "string"}}, {{type = "number"}}, {{type = "calculated"}} и т.д. сохраняют текущий формат.

h4. Шаг 2. Payload запроса данных.
При формировании payload для {{/v1/api/recordsets/<dataset_id>}} frontend должен передавать Меру в тех же логических секциях, где сейчас передаются поля, если Мера размещена на соответствующей полке:
* {{select}} — Меры на полке «Значения»;
* {{group}} — неагрегированные Меры на полках группировок, если сценарий полки это требует;
* {{where}} — фильтры по Мерам с типом {{WHERE}};
* {{having}} — фильтры по Мерам с типом {{HAVING}};
* {{order}} — только если сортировка по Мере поддержана для выбранной визуализации.

Frontend не передаёт раскрытое SQL-выражение Меры как единственный источник истины. Backend должен получить ссылку {{measure_name}} и сам раскрыть выражение из метаданных набора данных.

Минимальный пример элемента {{select}} для Меры:
{code:json}
{
  "type": "measure",
  "name": "Валовая прибыль",
  "measure_name": "Валовая прибыль",
  "alias": "[values][0]",
  "id": "measure_847b1ec3-bbf8-4365-85fb-c4fca2a06e2e",
  "fieldAlias": "Валовая прибыль",
  "aggregation_kind": 1,
  "data_type": "number",
  "calc": "",
  "aggr": "",
  "lvl": 0,
  "valueType": "value"
}
{code}

Точный набор полей payload требуется согласовать с backend-командой до реализации. Для оценки frontend необходимо учесть маппинг Мер из {{axes}} / {{axesDefault}} в текущий payload {{recordsets}}.

h3. Отображение Мер в конструкторе визуализаций.
h4. Шаг 2. Боковая панель полей.
При выборе *произвольного* набора данных, в котором есть Меры, в боковой панели конструктора отображается отдельная секция «Меры» ниже секции обычных полей.

Для оценки учесть:
* загрузку Мер из метаданных выбранного набора данных;
* display-группировку по {{hierarchy}};
* сортировку по {{level}}, затем по {{name}};
* отображение {{AGR}} / {{—}};
* tooltip с описанием, типом данных и выражением;
* error-состояние для {{status = invalid}};
* недоступность невалидных Мер для нового drag-and-drop и выбора в селекторах;
* отсутствие секции «Меры» для простых и составных наборов данных.

h4. Шаг 2. Визуальное представление на полках.
Мера должна визуально отличаться от обычного поля и вычисляемого поля виджета.

Для оценки учесть:
* отдельный цвет/иконку Меры на полках, кроме полки «Фильтры»;
* сохранение текущего визуального стиля фильтров на полке «Фильтры» с дополнительным признаком, что элемент является Мерой;
* отображение ярлыка {{AGR}} для агрегированных Мер;
* отображение error-состояния для невалидной Меры, уже сохранённой на полке;
* сохранение привязки по {{measure_name}} при переходе Меры в {{invalid}};
* возможность вручную удалить невалидную Меру с полки, чтобы визуализация снова могла выполняться без неё.

h4. Шаг 2. Drag-and-drop и совместимые селекторы.
Мера перетаскивается на полки по правилам обычных полей, но с учётом матрицы допустимости.

Frontend должен оценить поддержку Мер:
* на основных полках визуализации: «Значения», «Фильтры», «Строки», «Столбцы», «Детализация», «Дополнительные» и их аналоги в разных типах визуализаций;
* в selector-компонентах, где пользователь выбирает поля текущей визуализации;
* в настройках стилизации и форматирования, если текущий selector работает с полями;
* в условном форматировании, если текущая логика допускает выбор поля;
* в сценариях расчётов по уровням, если они применимы к выбранной визуализации.

Если отдельный selector технически или продуктово не поддерживает Меры на Шаге 2, это должно быть явно зафиксировано как ограничение этапа. Неподдержанный selector не должен выглядеть для пользователя как случайная потеря Меры.

h4. Шаг 2. Матрица допустимости Мер по полкам.
UX-валидация frontend-а выполняется при drag-and-drop и при выборе Меры в совместимом selector-е. Финальная валидация выполняется backend-ом.

|| Полка / сценарий || Допустимый тип Меры || Frontend-поведение ||
| Значения | Любая | Размещение разрешено. Для {{aggregation_kind = 0}} показать предупреждение о возможной некорректности агрегированного результата. |
| Фильтры, тип {{WHERE}} | Только {{aggregation_kind = 0}} | Для агрегированной Меры заблокировать выбор {{WHERE}} и показать сообщение. |
| Фильтры, тип {{HAVING}} | Только {{aggregation_kind = 1}} | Для неагрегированной Меры заблокировать выбор {{HAVING}} и показать сообщение. |
| Строки / Столбцы | Только {{aggregation_kind = 0}} | Для агрегированной Меры заблокировать размещение. |
| Детализация | Только {{aggregation_kind = 0}} | Для агрегированной Меры заблокировать размещение. |
| Дополнительные | Любая | Размещение разрешено; участие в SQL зависит от логики конкретной визуализации. |

Сообщения из матрицы должны быть понятны пользователю и не требовать знания SQL.

h4. Шаг 2. Полка «Фильтры».
При размещении Меры на полке «Фильтры» открывается настройка фильтра, адаптированная для Меры.

Форма должна содержать:
* тип отбора: {{WHERE}} или {{HAVING}};
* условие фильтрации;
* дополнительные параметры текущего фильтра, если они уже применяются для данного типа визуализации.

Для оценки учесть:
* сохранение {{filterSqlType}} / {{filter_mode}} в объекте Меры;
* маппинг фильтра-Меры в payload {{where}} или {{having}};
* блокировку несовместимого типа отбора по {{aggregation_kind}};
* сохранение текущего поведения обычных фильтров;
* обработку ошибки backend-а при некорректном условии или невалидной Мере.

h4. Шаг 2. Меры в вычисляемых полях виджета.
В редакторе вычисляемых полей виджета требуется предоставить Меры текущего набора данных для вставки в выражение, если сценарий вычисляемого поля допускает использование Мер.

Для оценки учесть:
* показ Мер в списке доступных объектов редактора;
* вставку ссылки на Меру в формате {{[measure_name]}};
* визуальное отличие Мер от полей;
* сохранение выражения вычисляемого поля без раскрытия выражения Меры на frontend-е;
* корректную обработку состояния, когда используемая Мера стала {{invalid}}.

h3. Валидация допустимости Мер и error-состояния.
h4. Шаг 1 и Шаг 2. Общие правила frontend-валидации.
Frontend-валидация является UX-предохранителем и не заменяет backend-валидацию.

Frontend должен:
* не позволять добавлять {{invalid}} Меру на полку или выбирать её в selector-е;
* сохранять уже существующую ссылку на {{invalid}} Меру в метаданных визуализации;
* отображать уже размещённую {{invalid}} Меру как ошибочную;
* не удалять Меру автоматически из визуализации;
* блокировать запрос данных или показывать контролируемую ошибку, если backend вернул ошибку по используемой Мере;
* позволять удалить проблемную Меру с полки вручную;
* не блокировать работу визуализации, если в наборе данных есть {{invalid}} Меры, но конкретная визуализация их не использует.

h4. Шаг 2. Поведение при ошибке загрузки данных.
Если backend возвращает ошибку из-за Меры, используемой в визуализации, frontend должен показать понятное сообщение:
* какая Мера проблемная;
* что данные визуализации не могут быть построены до исправления Меры или удаления её с полки;
* где пользователь может исправить Меру: в настройках соответствующего набора данных.

Формулировку сообщения необходимо согласовать с текущим UX ошибок визуализаций.

----
h3. Обратная совместимость.
Frontend-доработка не должна менять поведение существующих объектов:
* наборы данных без массива {{measures}} читаются и отображаются без ошибок;
* простые и составные наборы данных не получают интерфейс Мер в рамках Шага 1 и Шага 2;
* существующие визуализации без {{type = "measure"}} сохраняют текущие метаданные и payload;
* обычные поля продолжают ссылаться по {{name}} поля;
* человекочитаемый алиас поля не используется как ключ связи;
* вычисляемые поля виджета без ссылок на Меры продолжают работать по текущему контракту;
* если Мера есть в наборе данных, но не используется в визуализации, frontend не должен добавлять её в payload запроса данных.

Следующие работы связаны с внедрением Мер, но должны оцениваться отдельно от минимальных Шага 1 и Шага 2, если команда не примет иное решение:

* *Расширенная токенизация редактора выражений:* отдельная подсветка Мер, ручной ввод специальных delimiters, сложная грамматика, защита от конфликтов с SQL-диалектами, серверными переменными и переменными окружения.

* *Поддержка простых и составных наборов данных:* отдельное расширение после проверки backend-модели.
* *Общая панель фильтров и глобальные фильтры по Мерам:* отдельная оценка, особенно для {{HAVING}} и сложных условий.
* *Расширенные условия фильтрации:* группировка условий {{AND}} / {{OR}}, сложные выражения и дополнительные режимы отбора.
* *Создание/редактирование Меры из конструктора визуализаций:* быстрый переход или создание новой Меры из панели полей, если потребуется продуктово.

h3. Критерии приёмки (AC):
*AC.1* — Секция «Меры» доступна в настройках произвольного набора данных.
* *Дано*: аналитик открыл настройки *произвольного* набора данных.
* *Тогда*: под описанием полей отображается секция «Меры».
* *И*: для простого и составного набора данных секция «Меры» не отображается.

*AC.2* — Кнопка добавления Меры зависит от состояния SQL набора.
* *Дано*: SQL-запрос не задан, не проверен или состав полей не получен.
* *Тогда*: кнопка «+ Добавить меру» недоступна.
* *И*: tooltip объясняет причину недоступности.
* *И*: ранее сохранённые Меры не удаляются из интерфейса.

*AC.3* — Создание и редактирование Меры.
* *Дано*: пользователь создаёт или редактирует Меру.
* *Тогда*: доступна форма с полями {{name}}, {{description}}, {{data_type}}, {{aggregation_kind}}, {{hierarchy}}, {{level}}, {{expression}}.
* *И*: при редактировании значения предзаполнены из метаданных Меры.

*AC.4* — Редактор выражения вставляет поля и Меры в корректном формате.
* *Дано*: пользователь редактирует выражение Меры.
* *Тогда*: поле набора данных вставляется по {{name}} поля.
* *И*: Мера вставляется как ссылка {{[measure_name]}}.
* *И*: frontend не заменяет ссылку на Меру её раскрытым SQL-выражением.

*AC.5* — Статусы backend-валидации отображаются в списке Мер.
* *Дано*: backend вернул Меру со статусом {{invalid}} и причиной ошибки.
* *Тогда*: строка Меры отображается в error-состоянии.
* *И*: tooltip или сообщение показывает причину ошибки.

*AC.6* — Переименование и удаление используемой Меры блокируются.
* *Дано*: backend вернул список зависимых объектов для Меры.
* *Когда*: пользователь пытается переименовать или удалить Меру.
* *Тогда*: действие блокируется.
* *И*: frontend показывает список зависимых объектов.
* *И*: каскадное удаление зависимостей не выполняется.

*AC.7* — Меры отображаются в конструкторе визуализаций.
* *Дано*: пользователь строит визуализацию на основе произвольного набора данных с Мерами.
* *Тогда*: в боковой панели отображается секция «Меры».
* *И*: Меры визуально отличаются от обычных полей.
* *И*: группировка и сортировка соответствуют {{hierarchy}} и {{level}}.

*AC.8* — Drag-and-drop Меры учитывает матрицу допустимости.
* *Дано*: пользователь перетаскивает Меру на полку визуализации.
* *Тогда*: допустимое размещение выполняется.
* *И*: недопустимое размещение блокируется с понятным сообщением.

*AC.9* — Метаданные визуализации хранят ссылку на Меру по имени.
* *Дано*: Мера размещена на полке визуализации.
* *Тогда*: в метаданных сохраняются {{type = "measure"}} и {{measure_name}}.
* *И*: {{id}} не используется как ключ связи вместо {{measure_name}}.

*AC.10* — Payload запроса данных передаёт Меру как ссылку.
* *Дано*: визуализация содержит Меру на полке «Значения» или «Фильтры».
* *Когда*: frontend формирует payload {{recordsets}}.
* *Тогда*: payload содержит объект Меры с {{type = "measure"}} и {{measure_name}} в соответствующей секции.
* *И*: раскрытое выражение Меры не передаётся как единственный источник истины.

*AC.11* — Невалидная Мера в визуализации отображается как ошибка.
* *Дано*: визуализация уже содержит Меру, которая получила {{status = invalid}}.
* *Тогда*: пилюля Меры отображается в error-состоянии.
* *И*: данные визуализации не запрашиваются либо ошибка backend-а показывается пользователю в контролируемом виде.
* *И*: пользователь может удалить Меру с полки вручную.

*AC.12* — Обратная совместимость сохраняется.
* *Дано*: существующий отчёт или визуализация не содержит Мер.
* *Тогда*: метаданные, payload и поведение визуализации остаются такими же, как до внедрения Мер.
