h3. Контракты данных для Мер в аналитическом портале

----
h3. 1. Ключевое решение по контракту

В контракте Мер необходимо разделять три разных уровня данных:

# *Определение Меры в наборе данных* — источник истины о Мере: системное имя, alias, выражение, тип, агрегированность, статус.
# *Использование Меры в визуализации* — ссылка на уже существующую Меру и локальные настройки конкретной пилюли / полки / фильтра.
# *Payload запроса данных* — runtime-структура для {{/v1/api/recordsets/<dataset_id>}}, которую frontend собирает из метаданных визуализации перед запросом данных.

В контракте:
* ключом связи с Мерой является только {{name}};
* {{alias}} Меры используется для отображения пользователю и не является ключом связи;
* {{id}} Меры не используется как внешний ключ связи в визуализациях;
* выражение Меры не копируется в визуализацию и не передаётся frontend-ом как источник истины при построении запроса данных;
* frontend не формирует {{name}} самостоятельно и не добавляет префикс {{Мера.}} при сохранении или вставке Меры.

----
h3. 2. Контракт определения Меры в метаданных набора данных

Меры хранятся в метаданных *произвольного* набора данных в массиве {{measures}}.

{code:json}
{
  "measures": [
    {
      "id": "847b1ec3-bbf8-4365-85fb-c4fca2a06e2e",
      "name": "Мера.Валовая_прибыль",
      "alias": "Валовая прибыль",
      "description": "Разница между выручкой и себестоимостью",
      "expression": "SUM(\"revenue\") - SUM(\"cost\")",
      "aggregation_kind": 1,
      "data_type": "number",
      "hierarchy": "Финансовые показатели",
      "level": 10,
      "status": "valid",
      "status_message": ""
    }
  ]
}
{code}

|| Поле || Заполняет || Обязательность || Описание ||
| {{id}} | Система | Да | Стабильный UUID Меры. Генерируется при создании, не меняется при редактировании. Не является внешним ключом связи для визуализаций. |
| {{name}} | Backend | Да | Системное наименование Меры. Генерируется при создании на основании {{alias}}, уникально в рамках одного набора данных, не меняется после создания. Используется как единственный ключ связи во внешних ссылках. |
| {{alias}} | Пользователь | Да | Человекочитаемое название Меры. Отображается в интерфейсе и может изменяться после создания без изменения {{name}} только если Мера не используется в визуализациях, выражениях других Мер или вычисляемых полях. |
| {{description}} | Пользователь | Нет | Описание Меры для tooltip и справочной информации. |
| {{expression}} | Пользователь | Да | SQL-выражение Меры. Может ссылаться на поля набора данных, другие Меры и поддерживаемые переменные. |
| {{aggregation_kind}} | Пользователь | Да для валидной Меры | Признак агрегированности: {{1}} — агрегированная Мера, {{0}} — неагрегированная Мера. Определяется пользователем. Ручной переключатель агрегированности — временное UX-упрощение. Backend всё равно должен проверять фактическое выражение, а при противоречии между пользовательским флагом и выражением возвращать ошибку валидации. |
| {{data_type}} | Пользователь / система по умолчанию | Да | Логический тип результата: {{number}}, {{string}}, {{date}}, {{datetime}} и т.д. |
| {{hierarchy}} | Пользователь | Нет | Display-группа, в которой Мера отображается в списке Мер и панели полей. |
| {{level}} | Пользователь | Нет | Порядок отображения Меры внутри {{hierarchy}}. |
| {{status}} | Система | Да | Результат backend-валидации: {{valid}} или {{invalid}}. |
| {{status_message}} | Система | Нет | Причина невалидности или пустая строка, если Мера валидна. Нужна для tooltip и сообщений пользователю. |

h4. 2.1. Поля, которые задаёт пользователь

Пользователь вручную задаёт:
* {{alias}} при создании и при редактировании Меры без зависимых объектов;
* {{description}};
* {{expression}};
* {{aggregation_kind}}, на данном этапе задаётся пользователем;
* {{data_type}}, если предложенное значение по умолчанию нужно изменить;
* {{hierarchy}};
* {{level}}.

Пользователь не должен вручную задавать:
* {{id}};
* {{name}};
* {{status}};
* {{status_message}}.

h4. 2.2. Правила для {{alias}}

{{alias}} — человекочитаемое название Меры.

Для {{alias}} разрешены только:
* буквы;
* цифры;
* пробелы;
* знак подчёркивания.

Не допускаются:
* кавычки;
* круглые, квадратные и фигурные скобки;
* математические и логические операторы;
* спецсимволы, которые могут выглядеть как синтаксис выражения.

{{alias}} можно изменять после создания Меры только если Мера не используется в визуализациях, выражениях других Мер или вычисляемых полях. Изменение {{alias}} не должно менять {{name}}, так как зависимости работают по {{name}}.

Перед сохранением нового {{alias}} backend должен проверить наличие зависимых объектов по той же логике, которая используется для блокировки удаления Меры. Если Мера используется хотя бы в одном зависимом объекте, изменение {{alias}} блокируется, сохранённые метаданные Меры не меняются, а ответ должен содержать сообщение и список зависимостей, достаточный для отображения ссылок пользователю:
*«Нельзя переименовать Меру, используемую в визуализациях и/или в выражениях. Для переименования Меры необходимо разрешить конфликты:
[Список ссылок на визуализации, меры и вычисляемые поля, где используется переименовываемая Мера]»*

h4. 2.3. Правила для {{name}}

{{name}} — системное наименование Меры.

Backend формирует {{name}} только при создании Меры по правилу:

{code}
name = "Мера." + alias, приведённый к формату системного имени
{code}

Правила преобразования:
* префикс {{Мера.}} добавляется всегда;
* пробелы в {{alias}} заменяются на подчёркивания;
* кириллица в {{name}} допускается;
* системное имя формируется в одно слово;
* {{name}} уникален в рамках одного набора данных.

Примеры:

{code}
alias = "Дата отчёта"
name = "Мера.Дата_отчёта"
{code}

{code}
alias = "Валовая прибыль"
name = "Мера.Валовая_прибыль"
{code}

Если разные {{alias}} после преобразования приводят к одному {{name}}, backend должен сохранить уникальное системное имя. Допустимое целевое правило — добавить к конфликтующему {{name}} детерминированный числовой суффикс, например {{_2}}, {{_3}}.

Пример:

{code}
alias = "Дата отчёта"  -> name = "Мера.Дата_отчёта"
alias = "Дата_отчёта" -> name = "Мера.Дата_отчёта_2"
{code}

После создания Меры {{name}} не меняется. При редактировании {{alias}} backend сохраняет прежнее {{name}}.

Визуализации, выражения других Мер, вычисляемые поля и runtime payload ссылаются на Меру по {{name}}.

h4. 2.4. Ссылки в выражениях

Поля набора данных в выражении Меры указываются по системному {{name}} поля в двойных кавычках:

{code:sql}
SUM("revenue") - SUM("cost")
{code}

Ссылки на другие Меры указываются по системному {{name}} Меры в двойных кавычках:

{code:sql}
"Мера.Валовая_прибыль" / NULLIF(SUM("revenue"), 0)
{code}

{{"Мера.Валовая_прибыль"}} означает ссылку на Меру с {{name = "Мера.Валовая_прибыль"}}, а не раскрытое выражение и не копию формулы.

Квадратные скобки для ссылок на Меры не используются. Меры вставляются в редактор как обычные поля в двойных кавычках, а признак Меры определяется по префиксу {{Мера.}}.

----
h3. 3. Контракт использования Меры в визуализации

Визуализация не хранит полное определение Меры. Она хранит только ссылку на Меру и локальные настройки конкретного размещения.

Минимальный объект Меры на полке визуализации:

{code:json}
{
  "id": "visual_measure_4f9b7e2d",
  "type": "measure",
  "name": "Мера.Валовая_прибыль",
  "datasetId": 244
}
{code}

|| Поле || Заполняет || Описание ||
| {{id}} | Frontend | Локальный идентификатор конкретной пилюли / размещения в визуализации. Не равен {{measures[].id}} и не является ключом связи с Мерой. Нужен только если текущая модель визуализации требует instance-id для настроек, сортировки, форматирования или удаления элемента. |
| {{type}} | Frontend | Всегда {{measure}}. Отличает Меру от обычного поля и вычисляемого поля виджета. |
| {{name}} | Frontend из {{measures[].name}} | Единственная ссылка на Меру. |
| {{datasetId}} | Frontend | Идентификатор набора данных, к которому относится Мера. |

В объект использования Меры не нужно копировать:
* {{alias}};
* {{expression}};
* {{description}};
* {{aggregation_kind}};
* {{data_type}};
* {{hierarchy}};
* {{level}};
* {{status}};
* {{status_message}}.

Эти данные должны подтягиваться из актуальных метаданных набора данных. Это исключает рассинхронизацию, когда Мера изменилась в наборе данных, а старая копия осталась в визуализации.

h4. 3.1. Локальные настройки размещения

Если конкретная визуализация требует настройки сортировки, форматирования, подписи, цвета, точности или других параметров для пилюли, такие параметры хранятся рядом с объектом использования Меры как настройки размещения, а не как свойства Меры.

Пример:

{code:json}
{
  "id": "visual_measure_4f9b7e2d",
  "type": "measure",
  "name": "Мера.Валовая_прибыль",
  "datasetId": 244,
  "order": "desc",
  "format": {
    "precision": 2,
    "unit": "руб."
  }
}
{code}

Такие поля не должны использоваться backend-ом как источник определения Меры.

----
h3. 4. Контракт фильтра по Мере в метаданных визуализации

Фильтр по Мере — это использование Меры на полке «Фильтры» с локальной настройкой режима фильтрации и условия.

Базовый контракт фильтра по Мере:

{code:json}
{
  "id": "filter_measure_6d3c3e58",
  "type": "measure",
  "name": "Мера.Валовая_прибыль",
  "datasetId": 244,
  "filter": {
    "mode": "HAVING",
    "condition": {
      "operator": ">",
      "value": 0,
      "value_type": "number"
    }
  }
}
{code}

|| Поле || Заполняет || Описание ||
| {{id}} | Frontend | Локальный идентификатор фильтра / пилюли фильтра. |
| {{type}} | Frontend | Всегда {{measure}}. |
| {{name}} | Frontend из {{measures[].name}} | Ссылка на Меру. |
| {{datasetId}} | Frontend | Идентификатор набора данных. |
| {{filter.mode}} | Пользователь / Frontend | {{WHERE}} или {{HAVING}}. Доступность режима зависит от {{aggregation_kind}} Меры. |
| {{filter.condition.operator}} | Пользователь | Оператор условия: {{=}}, {{!=}}, {{>}}, {{>=}}, {{<}}, {{<=}}, {{between}}, {{in}} и т.д. в рамках поддерживаемого UI. |
| {{filter.condition.value}} | Пользователь | Значение условия. |
| {{filter.condition.value_type}} | Frontend / система | Тип значения для корректной сериализации и отображения. |

h4. 4.1. Структурное хранение условия

Условие фильтра должно храниться структурно, чтобы frontend и backend могли:
* валидировать оператор отдельно от значения;
* корректно типизировать значение;
* не превращать пользовательский ввод в произвольный SQL;
* расширять набор условий без разрыва контракта.

Если текущий backend на первом этапе принимает только строку {{condition}}, frontend может формировать строку как временный adapter-слой из структурного состояния фильтра. Источником истины в метаданных визуализации должен оставаться структурный объект {{filter.condition}}.

h4. 4.2. HAVING-фильтр для Сводной таблицы

Для уровня-специфичной HAVING-фильтрации Сводной таблицы к фильтру добавляются параметры применения.

{code:json}
{
  "id": "filter_measure_6d3c3e58",
  "type": "measure",
  "name": "Мера.Валовая_прибыль",
  "datasetId": 244,
  "filter": {
    "mode": "HAVING",
    "condition": {
      "operator": ">",
      "value": 0,
      "value_type": "number"
    },
    "apply_mode": "selected",
    "target_dimensions": ["col_month"]
  }
}
{code}

|| Поле || Описание ||
| {{filter.apply_mode}} | {{all}} или {{selected}}. Используется только для HAVING-фильтрации Сводной таблицы. |
| {{filter.target_dimensions}} | Массив идентификаторов измерений, к которым применяется HAVING. Пустой массив при {{apply_mode = "all"}}. |

Эти поля не нужны для обычного WHERE-фильтра и для базовых визуализаций без уровня-специфичной HAVING-логики.

----
h3. 5. Runtime payload для {{/v1/api/recordsets/<dataset_id>}}

Payload запроса данных — это не место хранения Меры. Это краткое описание того, какие Меры участвуют в конкретном запросе и где backend должен раскрыть их выражения.

{{alias}} внутри runtime payload является техническим alias результата запроса. Он не равен {{measures[].alias}}, не является человекочитаемым alias Меры и не хранится в метаданных Меры. Если текущий backend-контракт позволяет переименование технического поля, предпочтительное название для него — {{result_alias}} или {{output_alias}}, чтобы не смешивать его с {{measures[].alias}}.

h4. 5.1. Мера на полке «Значения»

{code:json}
{
  "select": [
    {
      "type": "measure",
      "name": "Мера.Валовая_прибыль",
      "alias": "[values][0]"
    }
  ],
  "group": [],
  "where": [],
  "having": [],
  "series": {
    "enable": 0
  }
}
{code}

{{alias}} в примере — технический alias результата запроса. Он нужен только в runtime payload, если текущий механизм сопоставляет колонки ответа с полками визуализации через значения вида {{[values][0]}}, {{[categories]}}, {{[series][0]}}.

h4. 5.2. Мера как вычисляемое измерение на полках группировки

Допустимо только для неагрегированных Мер.

{code:json}
{
  "group": [
    {
      "type": "measure",
      "name": "Мера.Маржинальность_категория",
      "alias": "[categories]"
    }
  ],
  "select": [
    {
      "type": "measure",
      "name": "Мера.Маржинальность_категория",
      "alias": "[categories]"
    }
  ],
  "where": [],
  "having": []
}
{code}

h4. 5.3. WHERE-фильтр по Мере

Допустимо только для неагрегированных Мер.

{code:json}
{
  "where": [
    {
      "type": "measure",
      "name": "Мера.Маржинальность_строки",
      "condition": {
        "operator": ">",
        "value": 0,
        "value_type": "number"
      }
    }
  ],
  "having": []
}
{code}

h4. 5.4. HAVING-фильтр по Мере

Допустимо только для агрегированных Мер.

{code:json}
{
  "where": [],
  "having": [
    {
      "type": "measure",
      "name": "Мера.Валовая_прибыль",
      "condition": {
        "operator": ">",
        "value": 0,
        "value_type": "number"
      }
    }
  ]
}
{code}

h4. 5.5. Сортировка по Мере

Если выбранная визуализация поддерживает сортировку по Мере, в {{order}} передаётся ссылка на Меру.

{code:json}
{
  "order": [
    {
      "type": "measure",
      "name": "Мера.Валовая_прибыль",
      "direction": "desc"
    }
  ]
}
{code}

h3. 6. API-контракт создания и редактирования Меры

Конкретные backend-объекты и команды API необходимо сверить с актуальной реализацией. Семантика контракта Меры должна соответствовать правилам ниже.

h4. 6.1. Создание Меры

При создании Меры frontend передаёт {{alias}} и остальные пользовательские параметры Меры. {{name}} в payload создания не передаётся.

Минимальный фрагмент payload создания, отражающий контракт наименования:

{code:json}
{
  "alias": "Дата отчёта"
}
{code}

Расширенный payload создания:

{code:json}
{
  "alias": "Валовая прибыль",
  "description": "Разница между выручкой и себестоимостью",
  "expression": "SUM(\"revenue\") - SUM(\"cost\")",
  "aggregation_kind": 1,
  "data_type": "number",
  "hierarchy": "Финансовые показатели",
  "level": 10
}
{code}

Backend при создании:
* валидирует {{alias}};
* формирует уникальное {{name}};
* сохраняет {{alias}} и {{name}};
* выполняет валидацию выражения и вычисляет {{status}} / {{status_message}};
* возвращает frontend-у сохранённую Меру.

Пример ответа:

{code:json}
{
  "id": "847b1ec3-bbf8-4365-85fb-c4fca2a06e2e",
  "name": "Мера.Валовая_прибыль",
  "alias": "Валовая прибыль",
  "description": "Разница между выручкой и себестоимостью",
  "expression": "SUM(\"revenue\") - SUM(\"cost\")",
  "aggregation_kind": 1,
  "data_type": "number",
  "hierarchy": "Финансовые показатели",
  "level": 10,
  "status": "valid",
  "status_message": ""
}
{code}

h4. 6.2. Редактирование Меры

Перед редактированием frontend должен получить актуальное состояние Меры через чтение метаданных набора данных или отдельный {{get/list}}-контракт.

При редактировании frontend может передавать изменяемые пользовательские поля:
* {{alias}} — только для Меры без зависимых объектов;
* {{description}};
* {{expression}};
* {{aggregation_kind}};
* {{data_type}};
* {{hierarchy}};
* {{level}}.

{{name}} не должен изменяться при редактировании. Если frontend передал {{name}} в payload обновления, backend должен игнорировать это поле или вернуть ошибку валидации в соответствии с принятым API-поведением. В любом случае сохранённое {{name}} существующей Меры не должно измениться.

Если в payload редактирования передан новый {{alias}}, backend до сохранения должен проверить наличие зависимостей:
* если Мера не используется в визуализациях, выражениях других Мер или вычисляемых полях — backend сохраняет новый {{alias}} и оставляет прежний {{name}};
* если Мера используется хотя бы в одном зависимом объекте — backend блокирует изменение {{alias}}, не изменяет метаданные Меры и возвращает сообщение со списком зависимостей.

Пример payload редактирования alias для Меры без зависимых объектов:

{code:json}
{
  "alias": "Валовая прибыль руб"
}
{code}

Пример ответа после редактирования:

{code:json}
{
  "id": "847b1ec3-bbf8-4365-85fb-c4fca2a06e2e",
  "name": "Мера.Валовая_прибыль",
  "alias": "Валовая прибыль руб",
  "description": "Разница между выручкой и себестоимостью",
  "expression": "SUM(\"revenue\") - SUM(\"cost\")",
  "aggregation_kind": 1,
  "data_type": "number",
  "hierarchy": "Финансовые показатели",
  "level": 10,
  "status": "valid",
  "status_message": ""
}
{code}

h4. 6.3. Ошибки валидации

Backend должен возвращать ошибку валидации, если:
* {{alias}} пустой или содержит недопустимые символы;
* пользователь пытается изменить {{alias}} Меры, которая используется в визуализациях, выражениях других Мер или вычисляемых полях;
* выражение Меры невалидно;
* {{aggregation_kind}} противоречит фактической агрегированности выражения;
* невозможно сформировать уникальное {{name}} в рамках набора данных.

Frontend должен показывать пользователю понятное сообщение и не считать Меру сохранённой, если backend вернул ошибку.
