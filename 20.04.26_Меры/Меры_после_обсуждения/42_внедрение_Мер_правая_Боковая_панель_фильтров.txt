# Контекст для постановки: внедрение Мер в правую боковую панель фильтров дашборда.

## 1. Общий контекст и принцип доработки.

В Modus BI внедряется концепция **Мер** — переиспользуемых вычисляемых SQL-выражений, определённых на уровне набора данных (`datasets.measures[]`).

Сейчас фильтрация поддерживает обычные, вычисляемые поля, а также Меры, размещённые на полке "Фильтра" для визуализаций, где внедрение Мер уже было осуществлено. Меры уже внедрены в большинство визуализаций, включая «Контейнер с фильтрами» (`FilterControlPanel`, MB-6012).

**Цель новой доработки:** обеспечить полноценную поддержку Мер в правой боковой панели фильтров дашборда, сохранив существующие механизмы работы с обычными и вычисляемыми полями.

Базовые правила:

- Не изменять действующую логику фильтрации, объединения фильтров по полю "Alias", их настройки и логику взаимодействия с визуализациями.
- Меры должны поддерживаться наравне с обычными и вычисляемыми полями в применимых сценариях.
- Неагрегированные условия применяются через `WHERE`, агрегированные — через `HAVING` с учётом эффективного результата размещения и локальной агрегации.
- Переиспользовать существующие компоненты, контракты Мер и механизмы обработки ошибок.

## 2. Устройство и работа правой боковой панели.

### 2.1. Источники фильтров.

На дашборде фильтры могут быть размещены:

1. На полке **«Фильтры»** отдельных визуализаций.
2. На полке **«Фильтры»** визуализации «Контейнер с фильтрами».

Правая боковая панель — централизованный интерфейс для просмотра и управления фильтрами дашборда.

В режиме просмотра пользователь открывает "панель фильтров" кнопкой «Фильтры» в верхней полосе усправления и настроек дашборда, там он видит доступные фильтры, включая раздел "общие" и раздел "локальные" (при щелчке на конкретную визуализацию тут отображаются её локальные фильтры), может задавать значения отбора в поля фильтрации, а также видит дополнительный раздел "Наборы фильтров", где он может переключать и создавать наборы фильтров.

В режиме редактирования дашборда дополнительно доступны настройки самих полей фильтров.

**После доработки:** фильтры, основанные на Мерах, размещённых на полках «Фильтры» визуализаций или контейнеров с фильтрами, должны отображаться и работать в правой боковой панели аналогично существующим фильтрам по полям, а также быть доступными в выпадающих списках настроек панели фильтров, таких как "Зависит от" и "Сортировка по другому полю".

### 2.2. Объединение фильтров по алиасам.

Фильтры разных визуализаций связываются по **алиасу** (поле alias), независимо от используемого набора данных и вида источника (обычное поле, вычисляемое поле или Мера).

Пример:

- Визуализация № 1 использует обычное поле набора данных A с алиасом `Регион`.
- Визуализация № 2 использует Меру набора данных B с тем же алиасом `Регион`.
- В правой панели они представляются общим фильтром `Регион`.
- Выбранное значение применяется к соответствующим полям-фильтрам или Мерам-фильтрам тех визуализаций, где данные поля или Меры размещёны на полке "ФИльтры".

Аналогичная связь действует между фильтрами контейнера и визуализаций. Значения, выбранные в контейнере, синхронизируются с правой панелью.

Особенности:

- Различающиеся алиасы образуют разные фильтры.
- Совпадающие алиасы допускаются для разных наборов данных, даже если наборы значений различаются.
- Специально выделять Меры в правой панели не требуется: общий фильтр может объединять обычные поля и Меры, поэтому однозначно классифицировать его как «фильтр по Мере» невозможно.
- Несовпадение значений и типов между связанными источниками обрабатывается по существующей логике, без введения новых ограничений.

### 2.3. Отображаемые значения и применение отбора.

Значения фильтра зависят от выбранного источника данных. В настройках предусмотрен параметр **«Основной набор данных»**, определяющий, из какого набора загружать значения общего фильтра.

Изменение значения фильтра в правой панели должно воздействовать на те визуализации, в которых соответствующий фильтр размещён на полке «Фильтры».

Сохраняются существующие способы выбора значений, операции сравнения, диапазоны, мультивыбор, применение и снятие отбора.

Тип элементов управления определяется эффективным типом результата. Например, для Меры с типом даты сохраняется поведение обычного поля-даты, включая соответствующие календарные элементы управления.

## 3. Настройки фильтров в правой боковой панели Фильтров в режиме редактирования дашборда.

| Настройка | Текущее поведение и требования к Мерам |
|---|---|
| **Тип фильтра** | Доступны варианты «По значению», «По диапазону», «Автофильтр». Сохранить существующие правила выбора типа и соответствующие элементы управления для Мер. |
| **Параметр «— / min / max»** | В интерфейсе присутствует выбор `—` (по умолчанию), `min`, `max`. Назначение и применение остаются по текущей реализации. |
| **Зависит от** | Выпадающий список фильтров, от которых может зависеть текущий фильтр. Требуется добавить поддержку Мер, размещённых на полках «Фильтры» визуализаций и контейнеров, по правилам существующего списка. |
| **Сброс** | По умолчанию выключен. При включении становится доступен список «Значения при сбросе»: «Все», `min`, `max`. Поведение сохраняется для Мер. |
| **Сортировка по другому полю** | По умолчанию `—`. Требуется разрешить выбор валидных для опций для выбора Мерами текущего набора данных наравне с обычными полями. Сортировка должна использовать вычисленные значения Меры. |
| **Основной набор данных** | Определяет источник значений общего фильтра, объединяющего поля и Меры из разных наборов данных. Существующий механизм сохраняется. |
| **Обязательный фильтр** | При включении фильтр обязателен для заполнения. Пока значение не задано, запрос данных для соответствующих визуализаций не отправляется. Правило одинаково для полей и Мер. |
| **Ограничение по количеству элементов** | Появляется при включении «Обязательного фильтра». Значение `0` — без ограничения, положительное число — максимально разрешённое количество выбранных элементов (например, `1` — не более одного). |

### Особенности настройки «Зависит от».

Это одна из основных точек внедрения Мер в правой панеле фильтров.

Основная суть данной настройки, что она ограничивает возможные для выбора элементы в текущем фильтре на основании уже выбранных значений в фильтре, который для неё выбран в "Зависит от".
Например, если для поля "Регион" выбрано в настройке "Зависит от" поля "Федеральный округ" и в фильтре по федеральному округу уже выбрано значение "Центральный федеральный округ", то в выпадающем списке поля "Регион" мы увидем только регионы Центрального федерального округа (а не по всем округам). Далее мы можем выбрать в фильтре "Регион" регионы из Центрального федерального округа и дополнительно отфильтровать данные по этим регионам.

Сейчас выпадающий список настройки «Зависит от» поддерживает обычные и вычисляемые поля.

**Требуется:**

- Включить валидные Меры (связанного набора данных поля-фильтра), используемые в фильтрах дашборда, в список доступных связанных фильтров.
- Сохранить существующую семантику зависимостей и ограничений списка.
- Поддержать зависимость между фильтрами по обычным полям и Мерам, включая смешанные комбинации.
- Обеспечить корректную обработку агрегированных Мер-родителей.

Для разных фильтров предлагаются разные наборы доступных полей. Например, для «Годового оборота партнёра» доступен только «Тип связи», а для «Продукции» список значительно шире (год, месяц, номер, регион, сумма и др.), так как этот список связан именно с полями набора данных поля-фильтра.

Т.е. в список настройки «Зависит от» попадают другие настроеные поля-фильтры (и меры-фильтры) текущего набора данных (из которого сам настраиваемый фильтр для которого выбирается настройка «Зависит от»).

Для настроек «Зависит от» и «Сортировки по другому полю» следует подтвердить фактические правила формирования списка, в том числе необходимость предварительного размещения Меры на полке.

## 4. Невалидные Меры и обработка ошибок.

Применяются общие правила обработки ошибок Мер (MB-5884).

**Невалидная, отсутствующая или несовместимая Мера:**

- Не должна предлагаться для нового выбора в селекторах «Зависит от» и «Сортировка по другому полю».
- Если была выбрана ранее и впоследствии стала невалидной, её ссылка и сохранённое значение настройки не удаляются автоматически.
- Такой элемент должен оставаться в селекторе с явным ошибочным состоянием с красным ореолом подсветкой вокруг поля-фильтра и проблемной настройки (по принятому оформлению портала).
- После исправления (или удаления из настройки) Меры работа должна восстанавливаться без необходимости повторного выбора, если Мера восстановилась или стала валидной.

Сохраняются общие правила обработки ошибок при получении значений фильтров и запросах визуализаций. Ошибочное условие нельзя молча исключать из запроса, если это приводит к отображению нефильтрованных данных.

Независимые исправные фильтры не должны блокироваться только из-за ошибки другого фильтра, если по действующей логике между ними нет зависимости.

## 5. Технические особенности.

### 5.1. Агрегированные Меры в «Зависит от».

В настройке «Зависит от» необходимо обеспечить доступность Мер наравне с обычными полями с сохранением действующей логики зависимых фильтров.
Для неагрегированных Мер используется текущий механизм обработки родительских условий. 
Для агрегированных Мер необходимо проверить корректность формирования запроса значений дочернего фильтра с учётом агрегированности родителя (HAVING) и контекста группировки.
Изменение стандартной логики зависимостей обычных полей в рамках задачи не предусматривается.

Необходимо проверить и при необходимости адаптировать:

- Построение запроса значений зависимого фильтра.
- Взаимодействие с механизмом производного фильтра.
- Работу при нескольких зависимых фильтрах.

Контекст получения значений агрегированных Мер был отдельным техническим вопросом MB-6012 и должен решаться совместно в рамках всего портала.

### 5.2. Разные наборы данных и разрешение ссылок.

Существующее поведение: общий фильтр может объединяться по алиасу между разными наборами данных, а его дополнительная настройка — ссылаться на источник, отсутствующий в одном из этих наборов.

В таком случае запрос может завершиться ошибкой `400`. Это же происходит с обычными полями, и в MB-6012 было решено **не менять** данную логику.

При внедрении Мер в «Зависит от» необходимо учитывать этот сценарий: если Мера-родитель отсутствует в наборе данных дочернего фильтра, возможна ошибка разрешения ссылки. Нельзя предполагать, что совпадение алиасов само по себе гарантирует доступность Меры в другом наборе данных.

### 5.3. Производный фильтр и восстановление контекста.

Выявленная разработчиком особенность MB-6012 непосредственно связана с настройкой «Зависит от».

При первоначальном выборе значения производный фильтр использует список, загруженный с учётом родительских условий и переменных отчёта.

При повторном открытии отчёта для обычных полей и неагрегированных Мер восстановление производного фильтра выполняется отдельным запросом, в котором условия родителей и переменные могут отсутствовать.

Это может приводить к различию результатов фильтрации до сохранения и после повторного открытия отчёта.

**В рамках MB-6012 механизм исправлен для агрегированных Мер.** Для обычных полей и неагрегированных Мер прежнее поведение сохранено; вопрос о его унификации оставлен без решения.

В новой постановке необходимо учитывать этот механизм при поддержке агрегированных Мер в «Зависит от», но не включать автоматическое изменение поведения остальных полей без отдельного решения.

### 5.4. Контракты и сохранение конфигурации

Меры используют общие механизмы хранения ссылок и получения актуальных метаданных:

- Привязка к конкретной Мере — через системное `name` и `datasetId` по общему контракту; объединение фильтров дашборда — по существующему механизму алиасов. Эти два механизма не следует смешивать.
- Выражение Меры не копируется в конфигурацию фильтра.
- Изменение выражения, типа, агрегированности или статуса Меры требует использования актуальных метаданных и проверки совместимости.
- Сохранение, повторное открытие, копирование и сброс отчёта должны сохранять настройки фильтров и ссылки на Меры по существующим правилам.
- Необходимо учитывать действующие механизмы локальной агрегации Мер (MB-5654) и их обработки в запросах.

## 6. Связанные особенности, которые не требуется переделывать

- **«Значения по другому полю».** Если одной подписи соответствует несколько исходных значений, фактически выбирается максимальное исходное значение. При неоднозначности ошибки нет. Решено сохранить текущее поведение; не следует переносить в новую задачу прежнее, нереализованное требование об объединении всех исходных значений.
- **Тип фильтра Меры в контейнере.** Выбор «По значению», «По диапазону», «По сравнению» добавлен в рамках MB-6012. Не следует смешивать настройки редактора контейнера с настройками правой панели дашборда.
- **Меры-даты.** В правой панели они работают аналогично обычным полям-дате, а не вычисляемым полям-дате.
- **«Уровень отбора».** В MB-6012 вопрос отложен до отдельной проработки. Не относится непосредственно к внедрению Мер в правую панель.
- **Подпись совместно с производным фильтром.** Известна общая проблема построения SQL-запроса, которая может давать ошибку `400` при сочетании разных источников подписи и спискового поля. Решение не зафиксировано; не расширять объём новой задачи без необходимости.

## 7. Границы новой постановки

В рамках новой задачи требуется **внедрение Мер в существующие механизмы правой боковой панели**, а не переработка системы фильтрации в целом.

Основной объём:

- Отображение и управление фильтрами по Мерам, включая общие фильтры из разных визуализаций и контейнеров.
- Поддержка Мер в настройках «Зависит от» и «Сортировка по другому полю».
- Сохранение работы остальных настроек правой панели при использовании Мер.
- Корректная обработка агрегированности, сохранённых ссылок, невалидных Мер и зависимостей между фильтрами.
- Обеспечение совместимости с реализованной MB-6012 и существующими отчётами.

Не включать без отдельного решения исправления исторического поведения фильтров, не относящиеся непосредственно к поддержке Мер.

**Ключевой критерий:** если заменить обычное поле эквивалентной валидной Мерой, доступное пользователю поведение правой панели должно сохраняться, за исключением технических особенностей вычисления выражения Меры и обработки её агрегированности.



Важно зафиксировать, что введение механизма Мер не меняет стандартного поведения визуализаций. Доработка поведения визуализаций и фильтрации не входит в скоп задач по данной Истории. Мы фокусируемся на введении механизма Мер и полноценного использования Мер, в рамках уже реализованной функциональности визуализации и боковой панели фильтров, на равне с обычными и вычисляемыми полями.


Текущее _поведение системы_ для обычных полей должно быть полностью сохранено для Мер с учётом их специфики обработки.

Поведение текущих настроек боковой панели фильтров не меняется от добавления механизма Мер.
