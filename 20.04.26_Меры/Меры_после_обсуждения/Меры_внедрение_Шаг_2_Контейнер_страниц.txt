h3. Контекст и проблематика.

Полное описание продуктовой логики приведено в Эпике по Мерам [https://jira.modusbi.ru/browse/MB-4364].
Общее описание *Шага 2* внедрения Мер описано в постановке [https://jira.modusbi.ru/browse/MB-4481].

Для произвольных наборов данных уже реализованы хранение и управление Мерами, общий интерфейс Мер в конструкторе визуализаций и runtime-обработка объектов {{type = "measure"}} на бэкенде. Поддержка Мер уже реализована для ряда других визуализаций.

*«Контейнер страниц»* ({{chartType = "pageContainer"}}) используется для организации и группировки других визуализаций портала по страницам. Внутри него можно создать несколько страниц, разместить на них заранее подготовленные визуализации текущего отчёта (через кнопку «Добавить в группу») и переключаться между ними для просмотра. Это помогает экономить место и не перегружать отчёт, а также организовывать в отчёте смысловые группы визуализаций.

В визуализации «Контейнер страниц» аналитик пока может использовать на полках только обычные и вычисляемые поля. Единые показатели набора данных, вынесенные в Меры, недоступны для использования в этой визуализации, что может приводить к дублированию логики в вычисляемых полях виджета.

----

h3. Цель задачи.

*Требуется:*
# Подключить реализованный механизм Мер к визуализации *«Контейнер страниц»*.
# Добавить Меры в стандартную левую боковую панель и обеспечить их использование на полках *«Значения»* и *«Фильтры»*.
# Поддержать использование Мер в настройке «Заголовок из данных» раздела «Стиль страниц» правой боковой панели.
# Сохранять ссылки на Меры в текущей конфигурации компонента и формировать runtime payload по реализованному контракту.
# Сохранить обратную совместимость существующих визуализаций «Контейнер страниц», в которых Меры напрямую не используются.

_Пользовательская история:_
Как аналитик, я хочу использовать Меры в «Контейнере страниц» наравне с обычными и вычисляемыми полями, чтобы настраивать заголовки страниц на основе единых показателей набора данных без дублирования формул в виджете.

----

h3. 1. Область применения.

---
h4. 1.1. Визуализация и набор данных.

Доработка выполняется для визуализации *«Контейнер страниц»*:
* {{chartType = "pageContainer"}}.

Меры доступны только при работе визуализации с *произвольным* набором данных, в метаданных которого backend возвращает массив {{measures}}.

Для простых и составных наборов данных секция *«Меры»* в конструкторе «Контейнера страниц» не отображается.

---
h4. 1.2. Полки визуализации.

Полки необходимо определять по {{axes[].type}}:

|| Полка в интерфейсе || {{axes[].type}} || Особенность текущей конфигурации ||
| *«Значения»* | {{values}} | Тумблер *«Первое»* / *«Все»*; для пилюль полки настройка *«Тип»* недоступна (сохраняется без изменений) |
| *«Фильтры»* | {{filters}} | Общая функциональность полки фильтров без изменений |

Необходимо сохранить действующие значения и семантику selectedFieldIndex, порядок размещений, признаки inactive, sortable и остальные локальные параметры осей. Новые значения и отдельные оси для Мер не вводятся.

Объекты Мер обрабатываются в axes по тому же жизненному циклу, что обычные и вычисляемые поля.

В рамках «Контейнера страниц» Меры должны поддерживаться:
* на полке *«Значения»* ({{name = "values"}});
* на полке *«Фильтры»* ({{name = "filters"}});
* в правой боковой панели на вкладке *«Стиль страниц»* в селекторе *«Заголовок из данных»*.

В правой боковой панели «Контейнера страниц» нет других селекторов, варианты которых формируются из обычных полей, вычисляемых полей или Мер.

----

h3. 2. Исходные правила модели Мер.

Визуализация использует уже созданные Меры текущего набора данных.

Ключевые правила:
* Мера хранится в {{datasets.measures[]}} только для *произвольного* набора данных.
* {{name}} — ключ связи с Мерой во внешних ссылках.
* {{alias}} — используется для отображения пользователю и не является ключом связи.
* {{id}} из {{measures[]}} не используется как внешний ключ в визуализации.
* Локальный {{id}} пилюли в визуализации является идентификатором размещения, а не идентификатором Меры из набора данных.
* {{expression}} Меры не копируется в конфигурацию визуализации и не передаётся frontend-ом в runtime payload как источник выражения.
* {{aggregation_kind = 1}} означает агрегированную Меру; {{aggregation_kind = 0}} — неагрегированную Меру.
* Для Мер с {{aggregation_kind = 1}} в интерфейсе отображается ярлык {{AGR}}.
* Меры со {{status = "invalid"}} отображаются пользователю с причиной ошибки, но недоступны для нового размещения и выбора.

Пример определения Меры в метаданных набора данных:
{code:json}
{
  "id": "847b1ec3-bbf8-4365-85fb-c4fca2a06e2e",
  "name": "Мера.Валовая_прибыль",
  "alias": "Валовая прибыль",
  "description": "Разница между выручкой и себестоимостью",
  "expression": "SUM(\"revenue\") - SUM(\"cost\")",
  "aggregation_kind": 1,
  "data_type": "number",
  "hierarchy": "Финансовые показатели",
  "level": 10,
  "status": "valid",
  "status_message": ""
}
{code}

----

h3. 3. Описание текущего поведения.

В конструкторе «Контейнера страниц» пользователь работает с полями набора данных и вычисляемыми полями виджета на полках *«Значения»* и *«Фильтры»*.

Стандартная левая боковая панель не содержит секции с Мерами: Меры набора данных не отображаются и недоступны для drag-and-drop на полки.

Селектор *«Заголовок из данных»* на вкладке *«Стиль страниц»* сейчас формируется из всех пилюль, размещённых на полке *«Значения»*, независимо от положения тумблера *«Первое»*/*«Все»* и от активности конкретной пилюли. Выбор сохраняется для конкретной страницы в {{visuals[].selectedValuesAxeFieldId}} по локальному {{id}} пилюли полки *«Значения»*.

----

h3. 4. Описание целевого поведения.

Пользователь открывает «Контейнер страниц» на основе произвольного набора данных и видит в левой боковой панели секцию *«Меры»* с Мерами выбранного набора данных, дополняющую существующий список полей полей.

Пользователь может перетаскивать валидные Меры на полки *«Значения»* и *«Фильтры»* «Контейнера страниц». На полках Меры отображаются как отдельный тип пилюли: по {{alias}}, с ярлыком {{AGR}} для агрегированных Мер.

В селекторе *«Заголовок из данных»* на вкладке *«Стиль страниц»* пользователь может выбрать в том числе Меру, размещённую на полке *«Значения»*, — механизм селектора не меняется, в список кандидатов дополнительно попадают пилюли Мер.

Runtime payload визуализации передаёт backend-у объекты типа {{"measure"}}. Backend находит актуальное определение Меры в {{datasets.measures[]}}, раскрывает выражение Меры ({{expression}}) и строит SQL по текущим правилам.

----

h3. 5. Требования к интерфейсу.

---
h4. 5.1. Левая боковая панель.

Для «Контейнера страниц» на основе произвольного набора данных левая боковая панель должна отображать секцию *«Меры»* ниже списка полей, аналогично актуальному виду для других визуализаций:

* секция *«Меры»* реализуется как сворачиваемая (аккордеон), по умолчанию отображается в развёрнутом виде — в соответствии с актуальным подходом к новым секциям левой панели;
* список Мер строится только из {{measures}} текущего набора данных;
* Меры отображаются по {{alias}};
* системное {{name}} может отображаться в tooltip как справочная техническая информация;
* для Мер указывается выбранный тип данных, аналогично отображению для обычных полей;
* для Мер с {{aggregation_kind = 1}} отображается ярлык {{AGR}};
* Меры со {{status = "invalid"}} отображаются в error-состоянии и недоступны для drag-and-drop.

Если левая панель реализована как общий компонент для визуализаций, включение секции *«Меры»* должно быть управляемым и на текущем шаге активироваться в том числе для «Контейнера страниц».

---
h4. 5.2. Группировка, сортировка и поиск Мер.

Если у Меры заполнено {{hierarchy}}, она отображается в соответствующей display-группе внутри секции *«Меры»*.

Порядок отображения:
# Меры с заполненной {{hierarchy}} группируются по значению {{hierarchy}} и отображаются в списке Мер аналогично обычным полям;
#* внутри группы — сортировка по {{level}} по возрастанию, затем по {{alias}};
# Меры без {{hierarchy}} — в корневом уровне секции, сортировка по {{alias}}.

Поиск по полям также должен находить Меры:
* по {{alias}} и {{name}};
** по логике {{OR}}.

---
h4. 5.3. Tooltip и error-состояния.

Tooltip Меры в левой панели и на пилюле должен содержать:
* {{description}}, если заполнено;
* {{data_type}};
* системное {{name}};
* признак агрегированности;
* в случае невалидности - человекочитаемую причину: frontend разбирает структурный JSON из {{status_message}}, формирует текст из {{code}} и {{params}}, а {{message}} использует только как fallback для неизвестного {{code}}.

Если Мера стала {{invalid}} после сохранения «Контейнера страниц»:
* сохранённая пилюля Меры не удаляется автоматически из конфигурации;
* пилюля отображается в error-состоянии;
* запрос данных блокируется только если эта Мера активно участвует в запросе визуализации и активной настройке *«Заголовок из данных»*, попадающей в построение;
* пользователю показывается сообщение с названием Меры и отрендеренной причиной ошибки, если причина известна.

---
h4. 5.4. Визуальное отличие пилюль Мер на полках:

* основной цвет пилюли Меры для полки «Значения» — светло-синий {{#3491F7}};
* на полке *«Фильтры»* пилюля Меры отображается стандартным для этой полки салатовым цветом;
* для Мер с {{aggregation_kind = 1}} отображается ярлык {{AGR}};
* на пилюле не должно быть доступно ручное изменение {{aggregation_kind}};
* настройки локальной агрегации {{agg}}/{{aggr}} для Меры не применяются поверх выражения Меры.

---
h4. 5.5. Полка «Значения».

Правила размещения:
* после доработок по локальной агрегации ([https://jira.modusbi.ru/browse/MB-5654]) на полку «Значения» допускаются оба типа агрегации для Мер без дополнительных предупреждений;
* настройка *«Тип»* для пилюль на этой полке недоступна как для обычных полей, так и для Мер — поведение полки в этой части не меняется;
* режим *«Первое»* передаёт в runtime payload только первую активную пилюлю полки;
* режим *«Все»* может передавать в runtime payload все активные пилюли полки в порядке размещения; каждая пилюля значения получает отдельный технический alias результата по текущей стратегии визуализации, например {{[values][0]}}, {{[values][1]}}.

---
h4. 5.6. Полка «Фильтры».

Мера на полке *«Фильтры»* отображается как фильтрующая пилюля - стандартным салатовым цветом.

Правила:
* для {{aggregation_kind = 0}} режим фильтра — {{WHERE}};
* для {{aggregation_kind = 1}} режим фильтра — {{HAVING}};
* режим {{WHERE}}/{{HAVING}} определяется автоматически по {{aggregation_kind}} и не переключается пользователем в несовместимое значение;
* условие фильтра хранится структурно в полях {{values}}/{{operators}}/{{not}}/{{logicOr}}; тип значения берётся из {{data_type}} Меры;
* фильтр с незаполненным обязательным значением считается неактивным и не попадает в runtime payload до заполнения.

Мера на полке «Фильтры» может влиять на логику отображаемые элементы, реализованную через вычисляемые поля или Меры, по действующей общей логике полки *«Фильтры»* «Контейнера страниц» — отдельная логика для Мер здесь не вводится.

Несколько фильтров по Мерам допускаются. Условия WHERE-Мер объединяются с другими WHERE-условиями по текущим правилам backend-а, базово через {{AND}}. Условия HAVING-Мер объединяются с другими HAVING-условиями по текущим правилам backend-а, базово через {{AND}}.

---
h4. 5.7. Селектор «Заголовок из данных» на вкладке «Стиль страниц».

Селектор *«Заголовок из данных»* задаёт название конкретной страницы «Контейнера страниц» на основании данных из выбранной пилюли полки *«Значения»*.

Правила:
* список кандидатов селектора формируется из *всех* пилюль, размещённых на полке *«Значения»*, независимо от положения тумблера *«Первое»*/*«Все»* и от текущей активности конкретной пилюли — механизм формирования списка не меняется;
* валидная Мера, размещённая на полке *«Значения»*, попадает в этот список наравне с обычными и вычисляемыми полями, по аналогии с отображением Мер в совместимых селекторах других визуализаций;
* невалидная Мера не предлагается для нового выбора в селекторе;
* выбор сохраняется для конкретной страницы по локальному {{id}} пилюли полки *«Значения»* в {{visuals[].selectedValuesAxeFieldId}} — так же, как уже сохраняется выбор обычного или вычисляемого поля;
* если выбранная пилюля — Мера, используемое для заголовка значение получается из результата запроса данных «Контейнера страниц» по тому же техническому alias результата, что и для обычного или вычисляемого поля в этой позиции полки *«Значения»*;
* если пилюля, на которую ссылается {{selectedValuesAxeFieldId}}, удалена с полки *«Значения»* либо соответствующая Мера отсутствует в наборе данных или получила {{status = "invalid"}}, применяется действующий для «Контейнера страниц» fallback заголовка страницы (текстовая подпись страницы), без отдельной новой логики для Мер;
* пилюля Меры, выбранная в *«Заголовке из данных»*, отображается в правой панели по текущей реализации для аналогичных селекторов в других визуализациях.

h3. 6. Хранение Меры в конфигурации «Контейнера страниц».

При размещении Меры на полке визуализация хранит объект использования Меры в {{axes[].fields[]}} соответствующей полки, а не определение Меры.

Минимальный объект использования Меры:
{code:json}
{
  "id": "visual_measure_4f9b7e2d",
  "type": "measure",
  "name": "Мера.Валовая_прибыль",
  "datasetId": 244,
  "title": ""
}
{code}

|| Поле || Обязательность || Описание ||
| {{id}} | Да | Локальный идентификатор размещения. Не равен {{measures[].id}} |
| {{type}} | Да | Для Меры всегда {{measure}} |
| {{name}} | Да | Системное имя Меры из {{datasets.measures[].name}}. Ключ связи |
| {{datasetId}} | Да | Идентификатор набора данных Меры |

Локальные настройки размещения (например, {{title}}, участие в фильтре) хранятся рядом с объектом использования Меры по текущей модели {{axes}} «Контейнера страниц» и не записываются в {{datasets.measures[]}}.

Параметры {{alias}}, {{expression}}, {{description}}, {{aggregation_kind}}, {{data_type}}, {{hierarchy}}, {{level}}, {{status}} и {{status_message}} Меры в конфигурацию визуализации не копируются; актуальные значения берутся из {{datasets.measures[]}}.

Ссылка настройки *«Заголовок из данных»* хранится в {{visuals[].selectedValuesAxeFieldId}} по локальному {{id}} пилюли полки *«Значения»* — тип объекта, на который указывает эта ссылка (обычное поле, вычисляемое поле или Мера), определяется через {{axes[].fields[]}} по совпавшему {{id}}, а не хранится в самой настройке страницы отдельно.

Пример фрагмента конфигурации страницы со ссылкой на Меру в заголовке:
{code:json}
{
  "id": 2,
  "anchor": "Страница 2",
  "labelText": "Страница 2",
  "selectedValuesAxeFieldId": "visual_measure_4f9b7e2d"
}
{code}

h3. 7. Формирование runtime payload.

---
h4. 7.1. Общие правила.

Frontend формирует runtime payload для {{/v1/api/recordsets/<dataset_id>}} из активных полок «Контейнера страниц» по тому же контракту, что используется для остальных визуализаций, поддерживающих Меры.

Минимальный runtime-объект Меры:
{code:json}
{
  "type": "measure",
  "name": "Мера.Валовая_прибыль",
  "alias": "[values][0]"
}
{code}

Frontend не должен передавать для {{type = "measure"}} непустые {{calc}}, {{expression}}, {{agg}} или {{aggr}} как источник выражения Меры.

---
h4. 7.2. Соответствие полок runtime-блокам.

|| Размещение Меры || Runtime-блок || Правило ||
| *Значения*, режим *«Первое»* | {{select}} | Передаётся только первая активная пилюля значения |
| *Значения*, режим *«Все»* | {{select}} | Передаются все активные пилюли значения |
| *Фильтры*, {{aggregation_kind = 0}} | {{where}} | Передаётся элемент с {{type}}, {{name}}, {{values}}, {{operators}} и при необходимости {{not}} / {{logicOr}} |
| *Фильтры*, {{aggregation_kind = 1}} | {{having.items}} | Передаётся элемент с {{type}}, {{name}}, {{values}}, {{operators}} и при необходимости {{not}} / {{logicOr}} |
| *Заголовок из данных* | Не формирует отдельный runtime-объект | Значение для заголовка берётся из результата, полученного по технической alias-ссылке выбранной пилюли *«Значения»* |

Backend определяет SQL-контекст не по названию полки, а по runtime-блоку, в котором frontend передал объект {{type = "measure"}}.

---
h4. 7.3. Пример payload для страницы с Мерой на «Значениях» и фильтром по Мере.
{code:json}
{
  "select": [
    {
      "type": "measure",
      "name": "Мера.Валовая_прибыль",
      "alias": "[values][0]"
    }
  ],
  "where": [],
  "having": {
    "condition": "",
    "items": [
      {
        "type": "measure",
        "name": "Мера.Маржа_строки",
        "values": [0],
        "operators": [">"]
      }
    ]
  },
  "order": [],
  "variables": []
}
{code}

Frontend формирует {{having}} объектом: существующее строковое условие для обычных и вычисляемых полей хранится в {{having.condition}}, условия по Мерам — в {{having.items}}; backend объединяет эти части через {{AND}}.

----

h3. 8. Backend и API.

Задача по «Контейнеру страниц» переиспользует backend-механизмы, реализованные для других визуализаций.

Вычисляемое поле «Контейнера страниц» может содержать ссылку на Меру текущего набора данных по {{name}} в двойных кавычках, например {{"Мера.Валовая_прибыль"}}. При обработке такого поля backend рекурсивно раскрывает актуальное выражение Меры по тем же правилам, что и ссылку внутри {{expression}} другой Меры; отдельная логика «Контейнера страниц» для этого не вводится.

Backend должен вернуть контролируемую ошибку, если:
* Мера с переданным {{name}} не найдена;
* Мера имеет {{status = "invalid"}};
* агрегированная Мера передана в {{where}};
* неагрегированная Мера передана в {{having}};
* в runtime payload для {{type = "measure"}} передан непустой {{calc}}, {{expression}}, {{agg}} или {{aggr}};
* условие фильтра по Мере содержит неподдержанный оператор или некорректный тип значения;
* итоговый SQL не может быть построен.

При использовании Меры со статусом, отличным от {{valid}}, backend возвращает {{HTTP 400}} и человекочитаемый текст с названием Меры, статусом, причиной (если она заполнена) и суффиксом блока: {{(блок SELECT)}}, {{(блок WHERE)}} или {{(блок HAVING)}}. Frontend показывает этот текст пользователю без автоматической очистки конфигурации страницы.

----

h3. 9. Обратная совместимость и ограничения.

* Существующие «Контейнеры страниц» без Мер должны продолжить работать без изменения результата, конфигурации и текущего заголовка страниц.
* Отсутствие массива {{measures}} в старых метаданных произвольного набора данных трактуется как пустой список Мер.
* Существующие обычные поля и вычисляемые поля виджета продолжают работать по текущим правилам, включая отсутствие настройки *«Тип»* на полке *«Значения»*.
* Текущий формат хранения {{axes}} и {{visuals}} не нормализуется и не переносится в отдельную структуру в рамках этой истории.

h3. 11. Открытые вопросы:

* Постановка *«Выбор агрегирующей функции для неагрегированной Меры на полке Значения»* не распространяется на «Контейнер страниц» в рамках этой Истории, так как у обычных полей на полке *«Значения»* этой визуализации селектор агрегации не работает корректно. Если такой селектор будет добавлен для обычных полей «Контейнера страниц», будет необходимо отдельно расширить эту постановку.
* Точный алгоритм выбора конкретного значения для *«Заголовка из данных»*, если запрос по выбранной пилюле возвращает несколько строк, не описан для обычных полей, но происходит "схлопывание" результата до одной строки. Для Мер предполагается использовать тот же действующий алгоритм без изменений.
* Нужно подтвердить у frontend-команды, в каких сценариях «Контейнер страниц» формирует собственный runtime-запрос данных по полкам *«Значения»*/*«Фильтры»* независимо от других визуализаций страницы. Зависит ли отправка данного запроса от опции настройки *«Заголовок из данных»*.
* Сценарии, где полка *«Фильтры»* «Контейнера страниц» влияет на отображение картинок, подзаголовков или подсказок через вычисляемые поля (упомянутые в общем описании визуализации), в явном виде не описаны для Мер отдельно от WHERE/HAVING-фильтрации; предполагается, что для Мер работает тот же механизм, что и для вычисляемых полей, без отдельной доработки.

h3. 12. Критерии приёмки (AC):

*AC.1* — Секция «Меры» в левой панели:
* *Дано:* пользователь открыл конструктор «Контейнера страниц» на произвольном наборе данных;
* *Когда:* backend вернул массив {{measures}};
* *Тогда:* ниже списка полей отображается секция *«Меры»* в виде аккордеона, по умолчанию развёрнутая.

*AC.2* — Секция «Меры» не отображается для неподдержанного набора:
* *Дано:* «Контейнер страниц» использует простой или составной набор данных;
* *Тогда:* секция *«Меры»* в левой панели не отображается;
* *И:* пользователь не может добавить новую Меру на полки визуализации.

*AC.3* — Визуальное представление Меры на полке «Значения»:
* *Дано:* валидная Мера размещена на полке *«Значения»*;
* *Тогда:* пилюля отображается по {{alias}} и цветом {{#3491F7}};
* *И:* для {{aggregation_kind = 1}} отображается ярлык {{AGR}}; настройка *«Тип»* для этой пилюли недоступна.

*AC.4* — Визуальное представление Меры на полке «Фильтры»:
* *Дано:* валидная Мера размещена на полке *«Фильтры»*;
* *Тогда:* пилюля отображается по {{alias}} стандартным салатовым цветом полки;
* *И:* для {{aggregation_kind = 1}} отображается ярлык {{AGR}}.

*AC.5* — Невалидная Мера недоступна для нового использования:
* *Дано:* Мера имеет {{status = "invalid"}};
* *Когда:* пользователь видит её в секции *«Меры»*;
* *Тогда:* Мера отображается в error-состоянии; drag-and-drop и выбор в *«Заголовке из данных»* заблокированы, а tooltip показывает человекочитаемую причину.

*AC.6* — Неагрегированная Мера на полке «Значения»:
* *Дано:* пользователь размещает на полке *«Значения»* Меру с {{aggregation_kind = 0}};
* *Тогда:* размещение не блокируется;

*AC.7* — Режим «Первое» на полке «Значения»:
* *Дано:* на полке *«Значения»* размещено несколько пилюль, включая Меру, первая активная пилюля — Мера, тумблер в положении *«Первое»*;
* *Когда:* визуализация запрашивает данные;
* *Тогда:* в {{select}} runtime payload попадает только первая активная Мера с {{type = "measure"}} и техническим alias.

*AC.8* — Режим «Все» на полке «Значения»:
* *Дано:* на полке *«Значения»* размещено несколько активных Мер, тумблер в положении *«Все»*;
* *Когда:* визуализация запрашивает данные;
* *Тогда:* каждая активная Мера передаётся отдельным объектом {{type = "measure"}} в {{select}} с отдельным техническим alias.

*AC.9* — Фильтр по неагрегированной Мере:
* *Дано:* на полке *«Фильтры»* размещена Мера с {{aggregation_kind = 0}} и заполненным условием;
* *Когда:* визуализация запрашивает данные;
* *Тогда:* Мера передаётся в {{where}} как объект {{type = "measure"}}.

*AC.10* — Фильтр по агрегированной Мере:
* *Дано:* на полке *«Фильтры»* размещена Мера с {{aggregation_kind = 1}} и заполненным условием;
* *Когда:* визуализация запрашивает данные;
* *Тогда:* Мера передаётся в {{having.items}} как объект {{type = "measure"}};
* *И:* {{having}} сформирован объектом с ключами {{condition}} и {{items}}.

*AC.11* — Селектор «Заголовок из данных» содержит Меры:
* *Дано:* на полке *«Значения»* размещены обычное поле, вычисляемое поле и валидная Мера;
* *Когда:* пользователь открывает селектор *«Заголовок из данных»* на вкладке *«Стиль страниц»*;
* *Тогда:* Мера отображается в списке кандидатов по {{alias}} наравне с полями, независимо от положения тумблера *«Первое»*/*«Все»*.

*AC.12* — Заголовок страницы формируется из значения Меры:
* *Дано:* в *«Заголовке из данных»* выбрана Мера, размещённая на полке *«Значения»*;
* *Когда:* «Контейнер страниц» запрашивает данные и отображает страницу;
* *Тогда:* заголовок страницы отображает значение, полученное из результата запроса по техническому alias выбранной Меры.

*AC.13* — Сохранение и восстановление конфигурации:
* *Дано:* Мера размещена на полке и выбрана в *«Заголовке из данных»* конкретной страницы;
* *Когда:* пользователь сохраняет и повторно открывает «Контейнер страниц»;
* *Тогда:* в {{axes[].fields[]}} сохраняются {{type = "measure"}}, {{name}}, {{datasetId}} и локальный {{id}};
* *И:* {{visuals[].selectedValuesAxeFieldId}} продолжает ссылаться на тот же локальный {{id}};
* *И:* при изменении {{alias}} Меры без изменения {{name}} связь сохраняется и в интерфейсе отображается актуальный {{alias}}.

*AC.14* — Открытие визуализации с отсутствующей или невалидной Мерой в заголовке:
* *Дано:* сохранённая страница ссылается через {{selectedValuesAxeFieldId}} на Меру, которая отсутствует в наборе данных или имеет {{status = "invalid"}};
* *Когда:* пользователь открывает «Контейнер страниц»;
* *Тогда:* конфигурация не очищается автоматически; для отображения заголовка страницы применяется действующий fallback заголовка «Контейнера страниц».

*AC.15* — Обратная совместимость:
* *Дано:* существующий «Контейнер страниц» не использует Меры;
* *Когда:* пользователь открывает, редактирует, строит или сохраняет визуализацию после внедрения доработки;
* *Тогда:* поведение визуализации, результат запроса данных и заголовки страниц не меняются.

*AC.16* — Мера в выражении вычисляемого поля:
* *Дано:* «Контейнер страниц» использует вычисляемое поле, содержащее ссылку на валидную Меру текущего набора данных по {{name}} в двойных кавычках;
* *Когда:* визуализация запрашивает данные;
* *Тогда:* backend рекурсивно раскрывает актуальное {{expression}} Меры по тем же правилам, что и ссылку внутри {{expression}} другой Меры.
