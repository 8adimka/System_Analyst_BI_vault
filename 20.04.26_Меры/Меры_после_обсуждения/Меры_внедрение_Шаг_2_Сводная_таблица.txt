h3. Контекст и проблематика.

Полное описание продуктовой логики Мер приведено в Эпике [https://jira.modusbi.ru/browse/MB-4364]. 
Общий механизм Шага 2 приведён в Истории [https://jira.modusbi.ru/browse/MB-4481]. 
Runtime-обработка объектов Мер реализуется backend-механизмом [https://jira.modusbi.ru/browse/MB-5035].

Для произвольных наборов данных уже доступны хранение Мер, общий интерфейс их использования в настройках визуализаций и раскрытие выражений Мер при формировании SQL-запросов. 

Требуется реализовать доступ к использованию Мер в визуализации *«Сводная таблица»*. Для полноценного внедрения Мер необходимо подключить их ко всем сценариям использования на тех же условиях, на которых визуализация поддерживает вычисляемые поля.

----

h3. Цель задачи.

*Требуется:*
# Подключить реализованный механизм использования Мер к визуализации *«Сводная таблица»*.
# Добавить Меры в стандартную левую боковую панель и обеспечить их использование на полках *«Значения»*, *«Строки»*, *«Детализация»*, *«Столбцы»*, *«Дополнительные»* и *«Фильтры»*.
# Обеспечить корректное построение ячеек, иерархий, дополнительных колонок, итогов и сортировки с Мерами.
# Поддержать Меры в настройках и селекторах данной визуализации.
# Сохранять ссылки на Меры и локальные настройки конкретных размещений в текущей конфигурации «Сводной таблицы» и формировать runtime payload по общему контракту.
# Сохранить текущее поведение сводных таблиц, в которых Меры не используются.

_Пользовательская история:_
Как аналитик, я хочу использовать Меры в «Сводной таблице» наравне с обычными и вычисляемыми полями, чтобы иметь возможность настраивать логику сводных представлений на основе показателей набора данных без дублирования формул внутри виджета.

----

h3. 1. Область применения и текущая конфигурация.

h4. 1.1. Визуализация и набор данных.

Доработка выполняется для визуализации:
* {{chartType = "pivotChart"}}.

Источником Мер является массив {{datasets.measures}} выбранного *произвольного* набора данных. Для простого и составного наборов данных секция *«Меры»* не отображается. Отсутствующий массив {{measures}} у произвольного набора трактуется как пустой список.

Полки необходимо определять по {{axes[].type}}, а не по позиции оси в массиве и не по отображаемому {{name}} / {{title}}:

|| Полка в интерфейсе || {{axes[].type}} || Особенность текущей конфигурации ||
| *«Значения»* | {{values}} | Режим *«Первое»*/*«Все»*; ось имеет {{sortable = true}} |
| *«Строки»* | {{rows}} | Порядок пилюль задаёт иерархию строк |
| *«Детализация»* | {{details}} | Формирует дополнительные колонки вне иерархии столбцов |
| *«Столбцы»* | {{columns}} | Порядок пилюль задаёт иерархию столбцов |
| *«Дополнительные»* | {{spares}} | В текущей конфигурации {{name}}/{{title}} может иметь значение *«Поля источника»*; сама полка не изменяет основной запрос |
| *«Фильтры»* | {{filters}} | Использует действующую форму настройки фильтра |

Необходимо сохранить текущий способ хранения режима полки *«Значения»*, порядок пилюль, {{selectedFieldIndex}}, {{sortable}}, {{pivotOrder}}, состояние раскрытия уровней {{expands}}, локальные параметры полей и другие действующие признаки осей. Новая схема осей или отдельные оси для Мер не вводятся.

Текущая конфигурация также содержит массив {{axesDefault}}. Во всех операциях, в которых действующая реализация синхронизирует или копирует данные между {{axes}} и {{axesDefault}}, объекты использования Мер и их локальные {{id}} должны обрабатываться по тем же правилам, что обычные и вычисляемые поля.

h4. 1.2. Общие правила объекта Меры.

При прямом использовании Меры в «Сводной таблице» сохраняется объект использования Меры, а не её определение:

{code:json}
{
  "id": "pivot_measure_4f9b7e2d",
  "type": "measure",
  "name": "Мера.Валовая_прибыль",
  "datasetId": 244
}
{code}

Правила:
* {{name}} и {{datasetId}} задают связь с актуальным определением Меры;
* {{id}} является локальным идентификатором конкретного размещения в визуализации и не равен {{datasets.measures[].id}};
* {{alias}} используется для отображения и всегда читается из актуальных метаданных набора данных;
* {{expression}}, {{description}}, {{aggregation_kind}}, {{data_type}}, {{hierarchy}}, {{level}}, {{status}} и {{status_message}} не копируются в конфигурацию как источник определения Меры;
* {{type = "measure"}} сохраняется как тип сущности, а для форматирования, операторов фильтра и других типозависимых функций используется актуальный {{data_type}} Меры;
* одна Мера может быть размещена несколько раз на разных допустимых полках; каждое размещение получает собственный локальный {{id}} и собственные локальные настройки;
* локальное изменение {{aggregation_kind}} и применение {{agg}} / {{aggr}} поверх выражения Меры недоступны.

h3. 2. Целевой интерфейс в конструкторе.

h4. 2.1. Левая боковая панель.

Для произвольного набора данных стандартная левая боковая панель должна содержать секции:
* *«Поля»* — обычные поля набора данных и вычисляемые поля виджета;
* *«Меры»* — Меры из {{datasets.measures}}.

Обе секции реализуются как сворачиваемые секции по актуальному общему компоненту. Начальное состояние, переключение и сохранение состояния раскрытия должны повторять текущую реализацию этого компонента; отдельная логика аккордеона для «Сводной таблицы» не вводится.

Для секции *«Меры»* необходимо переиспользовать общий интерфейс Мер:
* отображение по актуальному {{alias}};
* группировка по {{hierarchy}};
* сортировка внутри группы по {{level}}, затем по {{alias}};
* поиск по {{alias}} или {{name}} по логике {{OR}};
* tooltip с данными Меры и человекочитаемой причиной невалидности;
* ярлык {{AGR}} для {{aggregation_kind = 1}};
* error-состояние по {{status}} без самостоятельного анализа {{expression}} на frontend.

Мера с {{status = "invalid"}} отображается в error-состоянии и недоступна для нового drag-and-drop или выбора в селекторе. Уже сохранённая ссылка на такую Меру не удаляется автоматически.

h4. 2.2. Представление пилюли Меры.

Пилюля Меры:
* на полках *«Значения»*, *«Строки»*, *«Детализация»*, *«Столбцы»* и *«Дополнительные»* имеет светло-синий цвет {{#3491F7}};
* на полке *«Фильтры»* имеет стандартный, для этой полки, салатовый цвет;
* отображается по актуальному {{alias}};
* содержит ярлык {{AGR}} для {{aggregation_kind = 1}};
* сохраняет визуальный признак типа *«Мера»*;
* не предоставляет пользователю локальный выбор {{SUM}}, {{COUNT}} или другой агрегации.

Если pivot-компоненту технически требуется служебное значение {{pivotAgg}}, оно не должно изменять SQL-семантику выражения Меры и не должно приводить к повторной агрегации результата Меры. Пользовательское управление {{pivotAgg}} для Меры не отображается.

h3. 3. Использование Мер на полках.

h4. 3.1. Матрица допустимости и runtime-роль.

|| Полка || {{aggregation_kind = 0}} || {{aggregation_kind = 1}} || Целевое поведение ||
| *«Значения»* | Допускается с неблокирующим предупреждением | Допускается | Активные размещения формируют значения на пересечениях и передаются в {{select}} |
| *«Строки»* | Допускается | Блокируется | Мера создаёт вычисляемый уровень иерархии строк и передаётся в {{group}} и {{select}} |
| *«Детализация»* | Допускается | Блокируется | Мера формирует дополнительную колонку и расширяет уровень детализации через {{group}} и {{select}} |
| *«Столбцы»* | Допускается | Блокируется | Мера создаёт вычисляемый уровень иерархии столбцов и передаётся в {{group}} и {{select}} |
| *«Дополнительные»* | Допускается | Допускается | Размещение сохраняется, но само по себе не изменяет основной runtime payload |
| *«Фильтры»* | Допускается как {{WHERE}} | Допускается как {{HAVING}} | Условие передаётся в {{where}} или {{having.items}} |

При попытке разместить агрегированную Меру на полку *«Строки»*, *«Детализация»* или *«Столбцы»* действие блокируется с сообщением: *«На полках "Строки", "Столбцы" и "Детализация" допустимы только неагрегированные Меры»*.

Ограничения по {{data_type}} должны совпадать с ограничениями для вычисляемого поля того же типа на соответствующей полке. Тип сущности {{measure}} сам по себе не должен вводить дополнительные ограничения.

h4. 3.2. Полка «Значения».

В режиме *«Первое»*:
* учитывается только первая учитываемая пилюля по текущему алгоритму полки;
* если первой учитываемой пилюлей является Мера, её результат отображается в каждой применимой ячейке на пересечении иерархий строк и столбцов;
* остальные пилюли сохраняются на полке и в настройках, но не формируют дополнительные значения из-за режима полки.

В режиме *«Все»*:
* каждое активное размещение поля, вычисляемого поля или Меры формирует собственное значение в порядке полки в соответствии со стандартным поведением визуализации;
* для каждого пересечения иерархий строк и столбцов отображается отдельная ячейка/подколонка для каждого активного размещения.

Для неагрегированной Меры размещение не блокируется. Пользователь получает неблокирующее предупреждение: *«Мера "[alias]" является неагрегированной. Убедитесь, что её использование на полке "Значения" даст корректный результат»*.

Мера передаётся без локального {{agg}}/{{aggr}}. Если итоговый запрос строится на агрегированном уровне, общий SQL-builder применяет реализованное правило включения неагрегированного выражения в группировку.

h4. 3.3. Полки «Строки» и «Столбцы».

Неагрегированная Мера на полке *«Строки»* или *«Столбцы»* должна:
* участвовать в иерархии в позиции своего размещения;
* формировать вычисляемое измерение на основе результата {{expression}};
* передаваться в {{group}} и {{select}} по текущей стратегии технических alias «Сводной таблицы»;
* поддерживать текущие сценарии сортировки, раскрытия / сворачивания уровней, итогов и подытогов наравне с вычисляемым полем того же {{data_type}};
* не нарушать сохранение и восстановление состояния раскрытия уровней в {{expands}}: структура и правила адресации этого состояния остаются текущими.

Изменение порядка пилюль с Мерами изменяет порядок уровней иерархии тем же способом, что изменение порядка обычных или вычисляемых полей.

h4. 3.4. Полка «Детализация».

Неагрегированная Мера на полке *«Детализация»* должна:
* формировать дополнительную колонку вне иерархии столбцов;
* отображаться в порядке размещения на полке;
* передаваться в {{group}} и {{select}}, расширяя уровень детализации результата;
* поддерживать доступные для эквивалентного вычисляемого поля сортировку, форматирование и экспорт.

h4. 3.5. Полка «Дополнительные».

На полке *«Дополнительные»* допускаются агрегированные и неагрегированные Меры.

Само размещение на этой полке:
* сохраняется в {{axes[].fields}};
* не добавляет Меру в {{select}}, {{group}}, {{where}}, {{having}} или {{order}};
* не изменяет количество строк, столбцов или ячеек результата.

Если действующая дополнительная операция использует объект с этой полки, Мера должна подключаться к такой операции на тех же условиях и в той же runtime-структуре, что вычисляемое поле. Отдельный скрытый {{select}}/{{group}} из-за типа *«Мера»* не вводится.

h4. 3.6. Полка «Фильтры».

Мера на полке *«Фильтры»* использует стандартную форму настройки фильтра:
* для {{aggregation_kind = 0}} применяется режим {{WHERE}};
* для {{aggregation_kind = 1}} применяется режим {{HAVING}};
* режим определяется по {{aggregation_kind}} и не может быть переключён в несовместимое значение;
* условие хранится структурно в {{values}}/{{operators}}/{{not}}/{{logicOr}};
* отдельный {{value_type}} не передаётся, тип значения определяется по {{data_type}} Меры;
* незаполненный фильтр не участвует в runtime payload.

Для агрегированной Меры в режиме {{HAVING}} необходимо переиспользовать действующую уровень-специфичную логику «Сводной таблицы», в случае её реализации. Допускается использовать текущую реализованную логику обработки для данного типа фильтра.

Если текущая настройка фильтра использует {{apply_mode}} и {{target_dimensions}}, эти параметры сохраняются в объекте фильтра-Меры и передаются в существующий алгоритм CND/{{depth}} без изменения его логики:

{code:json}
{
  "id": "pivot_filter_measure_6d3c3e58",
  "type": "measure",
  "name": "Мера.Валовая_прибыль",
  "datasetId": 244,
  "filter": {
    "mode": "HAVING",
    "values": [0],
    "operators": [">"],
    "apply_mode": "selected",
    "target_dimensions": ["col_month"]
  }
}
{code}

Для {{WHERE}} параметры {{apply_mode}}/{{target_dimensions}} не применяются.

h4. 3.7. Итоги, подытоги и сортировка.

Меры, формирующие значения, должны участвовать в действующих сценариях итогов и подытогов «Сводной таблицы» наравне с вычисляемыми полями.

На каждом уровне группировки результат агрегированной Меры должен определяться её актуальным выражением в соответствующем SQL-контексте. Frontend не должен рассчитывать итог Меры повторным суммированием отображённых ячеек или применять к результату пользовательский {{pivotAgg}}.

Если текущая сортировка выполняется на backend, для Меры формируется элемент {{order}} с {{type = "measure"}}, {{name}}, направлением и требуемым техническим alias. Локальная сортировка/{{pivotOrder}} должна работать на тех же условиях, что для вычисляемого поля того же типа.

h3. 4. Настройки правой боковой панели.

h4. 4.1. Общий принцип.

Мера должна поддерживаться во всех настройках «Сводной таблицы», где текущая реализация допускает вычисляемые поля. Доступность конкретного элемента, набор контролов и его runtime-эффект должны совпадать с поведением вычисляемого поля в этом сценарии.

Глобальные разделы *«Общие настройки»*, *«Итоги»*, *«Данные»*, *«Стилизация»*, *«Условное форматирование»*, *«Многоуровневая шапка»* и *«Рамка компонента»* не получают отдельной логики Мер: сформированные Мерами уровни, колонки, заголовки и ячейки должны участвовать в их действующих настройках наравне с применяемыми на их месте вычисляемыми полями.

h4. 4.2. Раздел «Настройка полей».

В верхнем селекторе раздела «Настройка полей» должны отображаться пилюли размещённые на полках:
* *«Значения»*;
* *«Строки»*;
* *«Столбцы»*.

Размещения Мер отображаются по актуальному {{alias}} с признаком типа *«Мера»*. Порядок вариантов повторяет текущий порядок полок и пилюль. Выбор сохраняется на локальный {{id}} конкретной пилюли, поэтому повторные размещения одной Меры на полках не подменяют друг друга.

Для выбранного размещения Меры должны быть доступны все применимые настройки вычисляемого поля с тем же {{data_type}}, включая текущие настройки заголовка, ширины, точности, разделителя разрядов, переноса строк, отображения нулевых и пустых значений, формата даты/времени, суффиксов, выравнивания, стилизации, условного форматирования, многоуровневой шапки, расшифровки значения и рамки.

Локальные настройки сохраняются в текущей структуре конкретного размещения, например в {{prop}}, {{title}}, {{units}}, {{pivotOrder}} и других существующих параметрах. Они не становятся свойствами определения Меры.

h4. 4.3. Селектор «Заголовок по другому полю».

В селекторе *«Заголовок по другому полю»* раздела «Настройка полей» должны быть доступны пилюли размещенные на полке *«Значения»* по текущим правилам селектора.

При выборе Меры:
* в списке отображается её актуальный {{alias}} и признак типа *«Мера»*;
* сохраняется ссылка на локальный {{id}} выбранного размещения;
* заголовок целевого поля формируется из результата выбранной Меры по тем же правилам, что из результата вычисляемого поля;
* изменение {{alias}} Меры не нарушает связь;
* удаление пилюли штатно очищает зависимую настройку.

h4. 4.4. Раздел «Расшифровка значения»: режим «Переход по ссылке».

В разделе «Расшифровка значения» при выборе режима «Переход по ссылке» ({{decoding.mode = "link"}}) селектор *«Выберите значение»* должен включать пилюли размещенные на полке *«Значения»*, в том числе Меры.

Для выбранного размещения Меры:
* настройки URL, способ открытия и т.д. работают по текущему сценарию;
* конфигурация хранится в действующей структуре {{pivotLink}} по локальному {{id}} размещения, например {{pivotLink[<local_id>]}};
* клик по ячейке, сформированной этим размещением, работает по стандартному поведению и при использовании в них Мер.

h4. 4.5. Раздел «Расшифровка значения»: режим «Модальное окно».

В разделе «Расшифровка значения» при выборе режима Модальное окно» ({{decoding.mode = "modal"}}) в селекторах *«Поле»* и *«Контекстное поле»* должны быть доступны конкретные размещения с полки *«Значения»*, в том числе Меры.

Правила:
* *«Поле»* определяет значение, при клике по которому открывается модальное окно;
* *«Контекстное поле»* определяет дополнительное значение, передаваемое в модальное окно для того же пересечения иерархий строк и столбцов;
* Меры могут быть выбраны в одном или одновременно в обоих селекторах;
* выбор сохраняется на локальные {{id}} конкретных размещений в текущей структуре {{decoding.modal.fields[]}};
* если текущая структура хранит {{fieldContext}} как объект использования поля, для Меры сохраняется объект использования {{type = "measure"}}, {{name}}, {{datasetId}} и локальный {{id}}, но не копия определения Меры;
* название модального окна и вид отображения продолжают работать без изменений.

h4. 4.6. Общие правила селекторов.

Для всех перечисленных селекторов:
* валидная Мера доступна на тех же условиях, что вычисляемое поле с той же полки;
* повторные размещения с одинаковым {{alias}} остаются отдельными вариантами; идентификация всегда выполняется по локальному {{id}};
* уже сохранённая невалидная Мера отображается в error-состоянии и не подменяется другим объектом;
* изменение порядка и режима *«Первое»*/*«Все»* не изменяет локальный {{id}} и не очищает настройку;
* неактивное по режиму полки размещение сохраняется в настройке и создаёт runtime-зависимость только тогда, когда действующий механизм эквивалентного вычисляемого поля создаёт такую зависимость;
* удаление размещения очищает ссылки на него в настройках поля, {{pivotLink}}, {{decoding}} и других зависимых структурах штатным обработчиком;
* при копировании или регенерации локальных {{id}} единое соответствие старых и новых идентификаторов применяется к {{axes}}, при наличии к {{axesDefault}}, настройкам полей, {{pivotLink}} и {{decoding}}.

h3. 5. Хранение, восстановление и ошибки конфигурации.

Объект использования Меры хранится в {{axes[].fields}} соответствующей полки. Локальные настройки конкретного размещения сохраняются рядом с этим объектом по текущей модели «Сводной таблицы».

При открытии сохранённой визуализации frontend должен:
# получить актуальный массив {{datasets.measures}};
# сопоставить каждую ссылку {{type = "measure"}} строго по {{name}} и {{datasetId}}, без поиска по {{alias}};
# использовать актуальные {{alias}}, {{aggregation_kind}}, {{data_type}} и {{status}};
# восстановить полки, режим *«Первое»*/*«Все»*, порядок, {{selectedFieldIndex}}, состояние {{expands}}, локальные настройки, {{axesDefault}}, {{pivotLink}}, {{decoding}} и связи между локальными {{id}};
# проверить совместимость активных размещений с полками и настройками;
# не удалять и не переназначать автоматически невалидную или ставшую несовместимой Меру.

Изменение {{alias}} при неизменном {{name}} не нарушает связь: интерфейс показывает актуальный {{alias}}. Изменение {{expression}} применяется backend-ом при следующем запросе без пересохранения визуализации.

Активное использование невалидной или несовместимой Меры блокирует соответствующий запрос с пояснительным сообщением. Сохранённое, но неактивное размещение на полке *«Значения»* в режиме *«Первое»*, на полке *«Дополнительные»* или в выключенной настройке не должно блокировать построение основной сводной таблицы, если Мера напрямую не участвует в построении SQL-запроса.

Frontend не рассчитывает статус Меры и не исправляет её выражение самостоятельно.

h3. 6. Формирование runtime payload и взаимодействие с backend.

Минимальный runtime-объект прямого использования Меры содержит {{type = "measure"}}, {{name}} и технический {{alias}}, если он требуется соответствующему runtime-блоку. {{datasetId}} хранится в конфигурации визуализации, а набор данных runtime-запроса определяется параметром {{<dataset_id>}} маршрута.

|| Использование Меры || Runtime-блок || Правило ||
| Активное размещение на *«Значениях»* | {{select}} | Передаётся по режиму *«Первое»* / *«Все»* с отдельным техническим alias результата |
| Размещение на *«Строках»* | {{group}} и {{select}} | Передаётся неагрегированная Мера в порядке иерархии строк |
| Размещение на *«Столбцах»* | {{group}} и {{select}} | Передаётся неагрегированная Мера в порядке иерархии столбцов |
| Размещение на *«Детализации»* | {{group}} и {{select}} | Передаётся неагрегированная Мера как дополнительное измерение |
| Размещение на *«Дополнительных»* | — | Само по себе не формирует runtime-элемент |
| Неагрегированный фильтр | {{where}} | Передаются {{type}}, {{name}}, {{values}}, {{operators}} и при необходимости {{not}} / {{logicOr}} |
| Агрегированный фильтр | {{having.items}} | Передаются {{type}}, {{name}}, условие и применимые {{apply_mode}} / {{target_dimensions}} |
| Сортировка по Мере | {{order}} | Передаются {{type}}, {{name}}, направление и технический alias по текущей схеме |
| Активная зависимость настройки | По runtime-семантике эквивалентного вычисляемого поля | Отдельный hidden-select / hidden-group для Меры не вводится |

Frontend всегда формирует having объектом с двумя ключами: items — массив условий по Мерам (каждое условие ссылается на Меру по name и хранится структурно: значения, операторы, отрицание, логика OR/AND), и condition — строка, которая просто указывает, как эти условия из items объединяются между собой по индексам (например, "0 AND 1"). Пустой condition означает объединение всех условий через AND по умолчанию.

Frontend не передаёт формулу Меры в runtime-запросе — ни calc, ни expression, ни признаки агрегации (agg, aggr), ни пользовательский alias. Он передаёт только name. Backend сам находит Меру по этому имени в метаданных набора данных, берёт её актуальное выражение и строит SQL — так исключается риск, что frontend отправит устаревшую формулу, а также снижается риск инъекций.

Если вычисляемое поле «Сводной таблицы» ссылается на Меру текущего набора данных (по name в кавычках внутри своей формулы), это не превращается в отдельный объект Меры в runtime-запросе. Вычисляемое поле остаётся тем, что оно есть — объектом вычисляемого поля со своим calc, — а backend, раскрывая его, рекурсивно подставляет туда актуальное выражение Меры, как обычную вложенную ссылку.

Все механики отображения — построение экрана, раскрытие уровней иерархии, пересчёт итогов, автообновление, копирование и экспорт — должны работать с Мерами по одним и тем же правилам активности и раскрытия выражения. Расхождений в логике между разными сценариями использования быть не должно.

h3. 7. Права, зависимости и обратная совместимость.

* Новые права не вводятся: чтение Мер определяется правом чтения набора данных и отчёта, изменение «Сводной таблицы» — правом редактирования данного отчёта.
* Доработка переиспользует общие контракты хранения Мер и runtime-обработки. Отдельный endpoint для «Сводной таблицы» не вводится.
* После внедрения backend-доработок Шага 3, {{status}} и {{status_message}} используются общим компонентом для error-состояний; проверка frontend-поведения может выполняться на подготовленных метаданных.
* Существующие сводные таблицы без Мер открываются, строятся, раскрываются, редактируются, сохраняются, копируются, обновляются и экспортируются без изменения результата.
* Обычные и вычисляемые поля продолжают работать по текущим правилам, включая смешанные сценарии с Мерами.
* Миграция существующих конфигураций, в которых отсутствуют объекты {{type = "measure"}}, не требуется.

h3. 9. Критерии приёмки (AC):

*AC.1* — Секция «Меры» в левой панели:
* *Дано:* открыта «Сводная таблица» на произвольном наборе данных;
* *Когда:* загружены метаданные набора;
* *Тогда:* в стандартной левой панели отображаются секции *«Поля»* и *«Меры»* в виде актуального аккордеона;
* *И:* список Мер использует {{alias}}, группировку {{hierarchy}}, сортировку {{level}} / {{alias}}, поиск, tooltip и {{AGR}};
* *И:* для простого или составного набора секция *«Меры»* не отображается.

*AC.2* — Представление пилюли Меры:
* *Дано:* валидная Мера размещена на полке «Сводной таблицы»;
* *Тогда:* на всех полках, кроме *«Фильтров»*, пилюля имеет цвет {{#3491F7}}, а на *«Фильтрах»* — стандартный салатовый цвет;
* *И:* для {{aggregation_kind = 1}} отображается {{AGR}};
* *И:* локальный выбор агрегации недоступен и повторная агрегация результата Меры не применяется.

*AC.3* — Полка «Значения», режим «Первое»:
* *Дано:* на полке размещены поля и Меры, первой учитываемой пилюлей является Мера;
* *И:* выбран режим *«Первое»*;
* *Когда:* строится сводная таблица;
* *Тогда:* Мера передаётся в {{select}} и формирует значение на каждом применимом пересечении строк и столбцов;
* *И:* остальные пилюли не формируют дополнительные значения из-за режима полки.

*AC.4* — Полка «Значения», режим «Все»:
* *Дано:* на полке размещено несколько полей, вычисляемых полей и Мер;
* *И:* выбран режим *«Все»*;
* *Тогда:* каждое активное размещение формирует отдельную ячейку / подколонку в порядке полки;
* *И:* повторные размещения одной Меры имеют независимые локальные настройки и технические alias.

*AC.5* — Меры в иерархиях:
* *Дано:* неагрегированная Мера размещена на полке *«Строки»* или *«Столбцы»*;
* *Тогда:* она участвует в соответствующей иерархии и передаётся в {{group}} и {{select}};
* *И:* раскрытие уровней, сохранение {{expands}}, сортировка, итоги и подытоги работают по правилам вычисляемого поля того же типа;
* *Когда:* пользователь пытается разместить агрегированную Меру;
* *Тогда:* действие блокируется с понятным сообщением.

*AC.6* — Мера на «Детализации» и «Дополнительных»:
* *Дано:* неагрегированная Мера размещена на *«Детализации»*;
* *Тогда:* она формирует дополнительную колонку и расширяет {{group}} / {{select}};
* *Когда:* любая Мера размещена на *«Дополнительных»*;
* *Тогда:* размещение сохраняется, но само по себе не изменяет основной runtime payload и структуру результата.

*AC.7* — Фильтр по Мере:
* *Дано:* Мера размещена на полке *«Фильтры»* и условие заполнено;
* *Тогда:* неагрегированная Мера передаётся в {{where}}, агрегированная — в {{having.items}};
* *И:* {{having}} сформирован объектом с {{condition}} и {{items}};
* *И:* для уровень-специфичного HAVING сохраняются и применяются {{apply_mode}} / {{target_dimensions}} по действующему алгоритму «Сводной таблицы»;
* *И:* пилюля остаётся салатовой.

*AC.8* — Настройка поля-Меры:
* *Дано:* Мера размещена на *«Значениях»*, *«Строках»* или *«Столбцах»*;
* *Когда:* пользователь выбирает её в верхнем селекторе раздела *«Настройка полей»*;
* *Тогда:* доступны применимые настройки вычисляемого поля того же {{data_type}};
* *И:* настройки сохраняются для локального {{id}} конкретного размещения и не изменяют определение Меры.

*AC.9* — «Заголовок по другому полю»:
* *Дано:* Мера размещена на полке *«Значения»*;
* *Когда:* пользователь выбирает её в селекторе *«Заголовок по другому полю»*;
* *Тогда:* заголовок целевого поля формируется из результата выбранного размещения;
* *И:* ссылка сохраняется на локальный {{id}} и не подменяется повторным размещением той же Меры.

*AC.10* — Расшифровка через ссылку:
* *Дано:* выбран режим *«Переход по ссылке»* и Мера выбрана в селекторе *«Выберите значение»*;
* *Когда:* пользователь нажимает соответствующую ячейку;
* *Тогда:* используется значение Меры для текущего пересечения строк и столбцов;
* *И:* URL, цель открытия и tooltip читаются из {{pivotLink[<local_id>]}} выбранного размещения.

*AC.11* — Расшифровка через модальное окно:
* *Дано:* выбран режим *«Модальное окно»*;
* *И:* Мера выбрана в селекторе *«Поле»*, *«Контекстное поле»* или в обоих селекторах;
* *Когда:* пользователь нажимает значение поля;
* *Тогда:* открывается модальное окно, а результат контекстной Меры для того же пересечения передаётся в него по текущему сценарию;
* *И:* ссылки сохраняются на локальные {{id}} размещений без копирования {{expression}}.

*AC.12* — Сохранение, копирование и восстановление:
* *Дано:* «Сводная таблица» содержит Меры на полках и ссылки на них в настройках;
* *Когда:* пользователь сохраняет, повторно открывает или копирует визуализацию;
* *Тогда:* полки, режимы, порядок, {{expands}}, локальные настройки, {{axesDefault}}, {{pivotLink}} и {{decoding}} восстанавливаются согласованно;
* *И:* связь с Мерой устанавливается по {{name}} и {{datasetId}}, а локальные ссылки — по {{id}} размещения.

*AC.13* — Актуализация и ошибочные ссылки:
* *Дано:* у используемой Меры изменился {{alias}} или {{expression}}, а {{name}} сохранился;
* *Тогда:* интерфейс показывает актуальный {{alias}}, а backend использует актуальное {{expression}} без пересохранения визуализации;
* *Дано:* сохранённая Мера отсутствует или имеет {{status = "invalid"}};
* *Тогда:* ссылка сохраняется и отображается в error-состоянии; активная runtime-зависимость блокирует запрос, неактивная не блокирует основную сводную таблицу.

*AC.14* — Runtime-контракт и вычисляемые поля:
* *Дано:* «Сводная таблица» формирует запрос с прямыми размещениями Мер или вычисляемым полем, содержащим ссылку на Меру;
* *Тогда:* прямое использование передаётся как {{type = "measure"}} и {{name}} в соответствующем runtime-блоке;
* *И:* {{expression}}, {{agg}} и {{aggr}} не передаются как источник Меры;
* *И:* ссылка внутри {{calc}} раскрывается backend-ом без отдельного объекта {{type = "measure"}}.

*AC.15* — Итоги, экспорт и обратная совместимость:
* *Дано:* сводная таблица содержит агрегированную Меру на *«Значениях»*;
* *Когда:* строятся подытоги, общий итог или экспорт;
* *Тогда:* выражение Меры вычисляется в контексте соответствующего уровня группировки без повторного суммирования отображённых ячеек;
* *И:* экранное представление и экспорт согласованы;
* *И:* сводные таблицы без Мер работают без изменения результата.
