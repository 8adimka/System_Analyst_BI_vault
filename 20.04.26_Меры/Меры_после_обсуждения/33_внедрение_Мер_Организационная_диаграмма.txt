# Полка "Значения" - на данной полке можно разместить обычные и вычисляемые поля и неагрегированные Меры, агрегированные меры для данной полки недоступны.
#* Количество обрабатываемых пилюль визуализацией определяется выбранным режимом "Первое"/"Все":
#** "Первое" - тогда визуализация обрабатывает только первую пилюлю, размещённую на данной полке.
#** "Все" - при активном режиме "Все" визуализация может обрабатывать все пилюли, размещенные на этой полке без ограничения.

#** "Значение",
#** "Цвет",
#** "Размер".
# Полка "Фильтры" - позволяет задать как будет происходить фильтрация данных. Общая функциональность полки без изменений.

То есть:
| Полка        | Роль                                         | Для тестового набора   |
| ------------ | -------------------------------------------- | ---------------------- |
| **Признак**  | собственный идентификатор узла (`identity`)  | `Узел`                 |
| **Связь**    | идентификатор родительского узла (`linkage`) | `Родитель`             |
| **Значения** | отображаемое содержимое узла                 | `Узел`, тип `Значение` |

Признак   → идентификация узла
Связь     → построение отношения с родителем
Значение  → отображаемое содержимое узла

Родитель = ROOT  → граф строится.

Для размещения обычных полей, вычисляемых полей и Мер в визуализации доступны следующие полки:

# Полка *«Признак»* ({{axes[].type = "identity"}}):
#* задаёт собственный идентификатор узла дерева;
#* визуализацией учитывается только первая размещённая на полке пилюля;
#* допускаются обычные поля, вычисляемые поля и валидные неагрегированные Меры с совместимым типом результата;

# Полка *«Связь»* ({{axes[].type = "linkage"}}):
#* задаёт идентификатор родительского узла;
#* визуализацией учитывается только первая размещённая на полке пилюля;
#* допускаются обычные поля, вычисляемые поля и валидные неагрегированные Меры с совместимым типом результата;

# Полка *«Значения»* ({{axes[].type = "values"}}):
#* формирует отображаемые данные и визуальные характеристики узлов;
#* допускаются обычные поля, вычисляемые поля и валидные неагрегированные Меры с совместимым типом результата;

Базовая семантика визуализации:
| Полка | Роль |
| --- | --- |
| *«Признак»* | собственный идентификатор узла ({{identity}}) |
| *«Связь»* | идентификатор родительского узла ({{linkage}}) |
| *«Значения»* | отображаемое содержимое и визуальные характеристики узла |

То есть:
{{Признак → идентификация узла}}
{{Связь → построение отношения узла с родителем}}
{{Значения → отображение и оформление узла}}

Фактическими тестами подтверждено, что стандартная модель {{treeGraph}} строит дерево по значениям *«Признака»* и *«Связи»*, а полка *«Значения»* определяет отображаемые данные узла. Например, при данных вида:
{{A → ROOT}}
{{B → A}}
{{C → A}}
{{D → B}}
получается дерево:
{{A → B → D}} и {{A → C}}.

Если для полки *«Значения»* {{treeGraph}} локальная агрегация не должна применяться из-за ограничения визуализации на неагрегированные значения, не следует искусственно переносить механизм из других визуализаций; возможное расхождение с общей постановкой необходимо явно вынести в открытый вопрос/зависимость.

9) В правой боковой панели данной визуализации Меры не используются в отдельных селекторах или настройках. Существующее поведение правой панели не изменяется.

10) Стандартное поведение режимов *«Первое»* / *«Все»*, порядка пилюль, типов *«Значение»* / *«Цвет»* / *«Размер»*, построения дерева, tooltip/balloon, размера и цвета узлов сохраняется. Мера должна только подключаться к этим механизмам на тех же условиях, что эквивалентное вычисляемое поле.

11) Должны быть учтены общие правила хранения ссылки на Меру, формирования runtime-запросов, актуализации {{alias}}, {{expression}}, {{aggregation_kind}}, {{data_type}}, обработки повторных размещений, сохранения/открытия конфигурации и смены набора данных согласно уже принятым контрактам Мер.

12) Для ошибочных и невалидных Мер необходимо переиспользовать актуальные правила из ./Правила_визуализации_Мер_при_ошибочных_состояниях.txt. Не требуется вводить отдельный механизм ошибок для *«Организационной диаграммы»*. Участие ошибочной пилюли определяется реальным участием данного размещения в запросе с учётом полки и режима *«Первое»* / *«Все»*.

13) Существующие отчёты и конфигурации *«Организационной диаграммы»* без Мер должны продолжать работать без миграции и изменения результата.

Агрегация пилюль на полках: «Признак», «Связь», «Значения».
В актуальном состоянии визуализации, локальная агрегация доступна для обычных полей наборов данных, но выбор логальной агрегации приводит к ошибке построения запроса.

Данный вопрос требует технической проработки и, по её результатам, решается вопрос добавления локальной агрегации для Мер по постановке https://jira.modusbi.ru/browse/MB-5654.
