h3. Контекст и цель истории.
Полное описание продуктовой логики приведено в Эпике ([https://jira.modusbi.ru/browse/MB-4364]).

Настоящая История реализует использование ранее созданных Мер *произвольного* набора данных в конструкторе визуализаций: отображение в панели полей, размещение на полках, использование в совместимых селекторах, хранение ссылок в метаданных визуализации и инъекцию выражений Мер во внешний SQL-запрос.

Меры создаются и валидируются в настройках набора данных в предыдущей Истории. В рамках этой Истории Мера рассматривается как готовый объект метаданных набора данных со статусом {{valid}} или {{invalid}}.

До внедрения backend-Шага 3 все успешно сохранённые Меры имеют {{status = "valid"}} и {{status_message = ""}}. Описанные ниже {{invalid}}, структурный {{status_message}}, блокировка удаления по зависимостям и ревалидация являются целевым поведением после введения доработок Шага 3. Frontend Шага 2 реализует совместимость с этим контрактом и может проверять её на подготовленных метаданных.

При прямом размещении Меры визуализация ссылается на неё по полю {{name}} внутри объекта использования Меры с {{type = "measure"}}. Ссылка на Меру внутри выражения вычисляемого поля хранится в самом выражении по {{name}}. {{id}} Меры - не используется как внешний ключ связи.

{{alias}} Меры используется для отображения пользователю в панели полей, подсказках, полках и селекторах. Изменение {{alias}} не меняет {{name}}, не ломает визуализации и его можно свободно изменять, в том числе у используемой Меры.

----
h3. Границы истории.

В рамках Истории реализуется:
* отображение секции «Меры» в панели полей конструктора визуализаций;
* display-группировка Мер по «Иерархии» и «Уровню»;
* визуальное отличие Мер от обычных полей;
* поведение Мер со статусом {{invalid}} в конструкторе;
* drag-and-drop Мер на поддерживаемые полки визуализации;
* поддержка Мер в совместимых селекторах полей текущей визуализации;
* настройка фильтра по Мере с типом {{WHERE}} или {{HAVING}};
* матрица допустимости Мер по полкам и локальная агрегация неагрегированных Мер на всех полках, где она предусмотрена для обычных полей;
* использование Мер в выражениях вычисляемых полей виджета;
* хранение размещения Меры в метаданных визуализации по {{type = "measure"}}, {{name}} и {{datasetId}};
* SQL-инъекция выражений Мер во внешний запрос визуализации;
* сохранение обратной совместимости для визуализаций без Мер.

h3. Исходная модель Меры.
Мера хранится в JSON-метаданных набора данных. Поле {{name}} является уникальным в рамках одного набора данных и используется как ключ связи. Поле {{alias}} является человекочитаемым названием Меры и используется для отображения.

{code:json}
{
  "measures": [
    {
      "id": "847b1ec3-bbf8-4365-85fb-c4fca2a06e2e",
      "name": "Мера.Валовая_прибыль",
      "alias": "Валовая прибыль",
      "description": "Разница между выручкой и себестоимостью",
      "expression": "SUM(\"revenue\") - SUM(\"cost\")",
      "is_aggregated": true,
      "data_type": "number",
      "hierarchy": "Финансовые показатели",
      "level": 10,
      "status": "valid",
      "status_message": ""
    }
  ]
}
{code}

|| Поле || Тип || Описание ||
| {{id}} | string | Стабильный {{UUID}} идентификатор записи; не используется как ключ связи во внешних ссылках |
| {{name}} | string | Системное наименование Меры; формируется backend-ом при создании, уникально в рамках набора данных, не меняется после создания и является ключом связи во внешних ссылках |
| {{alias}} | string | Человекочитаемое уникальное в рамках набора название Меры; отображается пользователю и может свободно изменяться без изменения {{name}}, в том числе у используемой Меры |
| {{description}} | string | Необязательное описание |
| {{expression}} | string | SQL-выражение; поля и другие Меры указываются по системному {{name}} в двойных кавычках, например {{"report_date"}} и {{"Мера.Валовая_прибыль"}} |
| {{is_aggregated}} | Булево | Флаг использования функций агрегации в выражении Меры: {{false}} — не используются / {{true}} — используются; задаётся пользователем явно. На Шаге 3 при уверенном противоречии флага фактическому выражению backend сохраняет Меру со {{status = "invalid"}}, а не блокирует сохранение; при неопределённом результате проверка агрегированности не добавляет причину {{invalid}}, и при отсутствии иных причин итоговый {{status = "valid"}} |
| {{data_type}} | string | Логический тип результата; состав коллекции типов Мер аналогичен таковому у полей набора данных |
| {{hierarchy}} | string | Необязательная группа/иерархия отображения |
| {{level}} | int | Порядок Меры внутри иерархии |
| {{status}} | enum | {{valid}} или {{invalid}} |
| {{status_message}} | string | Всегда присутствует: для {{valid}} — пустая строка; на Шаге 3 для {{invalid}} — структурный JSON {{ {"code","params","message"} }}. Frontend рендерит текст по {{code}} + {{params}}, используя {{message}} только как fallback, и не показывает сырой JSON |

h3. Метаданные визуализации.
При прямом размещении Меры в метаданных визуализации связь хранится по полю {{name}} внутри объекта использования Меры. Для различения Меры с обычным полем в таком объекте обязательно хранится {{type = "measure"}}. Ссылка на Меру внутри выражения вычисляемого поля хранится в самом выражении по {{name}} без отдельного объекта использования Меры.

Если в объекте использования Меры есть поле {{id}}, оно является локальным идентификатором размещения/настройки в визуализации и не является {{id}} Меры из {{measures[]}}.

Каждое прямое использование Меры в визуализации хранит:
* тип сущности {{type = "measure"}};
* ссылку на Меру по {{name}};
* {{datasetId}} набора данных, к которому относится Мера;
* дополнительные параметры в зависимости от конкретной полки и сценария.

Локальная функция хранится у конкретного размещения и восстанавливается при открытии и копировании отчёта по правилам обычного поля соответствующего компонента. Функции разных размещений независимы. Производное runtime-выражение не сохраняется в определении Меры. Сохранённые настройки обрабатываются по общей постановке локальной агрегации.

В объект использования Меры в визуализации не копируются поля определения Меры: {{alias}}, {{expression}}, {{description}}, {{is_aggregated}}, {{data_type}}, {{hierarchy}}, {{level}}, {{status}}, {{status_message}}. Эти данные читаются из актуальных метаданных набора данных.

Пример размещения Меры на полке визуализации:
{code:json}
{
  "values": [
    {
      "id": "visual_measure_4f9b7e2d",
      "type": "measure",
      "name": "Мера.Валовая_прибыль",
      "datasetId": 244
    }
  ]
}
{code}

Пример фильтра по Мере:
{code:json}
{
  "filters": [
    {
      "id": "filter_measure_6d3c3e58",
      "type": "measure",
      "name": "Мера.Валовая_прибыль",
      "datasetId": 244,
      "filter": {
        "mode": "HAVING",
        "values": [0],
        "operators": [">"]
      }
    }
  ]
}
{code}

|| Поле || Тип || Описание ||
| {{id}} | string | Локальный идентификатор размещения/настройки в визуализации; не является {{id}} Меры из {{measures[]}} |
| {{type}} | string | {{"measure"}} — отличает Меру от обычного поля и вычисляемого поля |
| {{name}} | string | Системное имя Меры; является ключом связи |
| {{datasetId}} | int/string | Идентификатор набора данных, к которому относится Мера |
| {{filter.mode}} | string | {{WHERE}} или {{HAVING}} |
| {{filter.values}} | array | Непустой массив значений. {{null}} допустим только в форме списка без {{operators}} и означает проверку пустого значения |
| {{filter.operators}} | array | Допустимые значения: {{=}}, {{!=}}, {{<>}}, {{>}}, {{>=}}, {{<}}, {{<=}}, {{like_*}} / {{likeic_*}} |
| {{filter.not}} | не нормирован отдельно | Отрицание условия: {{NOT IN}} / {{IS NOT NULL}}; сериализация соответствует действующему общему контракту фильтра |
| {{filter.logicOr}} | не нормирован отдельно | Значение {{1}} объединяет условия через {{OR}}, иначе используется {{AND}} |

Для прямого условия по Мере отдельного {{value_type}} нет: тип определяется по {{data_type}} Меры. При локальной агрегации применяется контракт вычисляемого выражения и эффективный тип его результата, исходный {{data_type}} не меняется.

h3. Отображение Мер в конструкторе визуализаций.
h4. Боковая панель полей.
При выборе *произвольного* набора данных боковая панель конструктора разделена на секции:
* *«Поля»* — обычные поля и вычисляемые поля виджета;
* *«Меры»* — Меры набора данных.

Секция «Меры» располагается ниже секции «Поля».

В секции «Поля» отображается {{alias}} поля, если он доступен, иначе {{name}} поля.

В секции «Меры» отображается {{alias}} Меры. Системное {{name}} может отображаться в tooltip как справочная техническая информация.

h4. Визуальное представление Меры.
Мера отображается как отдельный тип элемента на полках визуализаций:
* цвет иконки или пилюли Меры на полках, кроме полки «Фильтры», — *светло-синий (#3491F7)*;
* на полке «Фильтры» Мера сохраняет признак типа «Мера»:
** для Мер с {{is_aggregated = true}} отображается ярлык {{AGR}};
** для Мер с {{is_aggregated = false}} ярлык {{AGR}} не отображается;
* на полках визуализации Мера отображается по {{alias}};
* tooltip при наведении содержит описание, если оно заполнено, тип данных, полный текст выражения и {{name}} Меры как справочную техническую информацию.

Ярлык {{AGR}} отображается только для Мер с {{is_aggregated = true}}:
* в списке Мер набора данных;
* в боковой панели конструктора;
* на пилюлях полок.

При локальной агрегации на пилюле неагрегированной Меры отображается выбранная функция; ярлык {{AGR}} для неё не используется. В списке Мер локальная функция не показывается.

Изменить {{is_aggregated}} непосредственно на полке нельзя. Атрибут меняется только при редактировании Меры в наборе данных. На Шаге 3 backend проверяет соответствие выбранного значения фактическому выражению Меры.

h4. Группировка и порядок.
Если заполнена «Иерархия», Мера показывается в соответствующей display-группе внутри секции «Меры».

Порядок вывода внутри группы:
# по {{level}} по возрастанию;
# затем по {{alias}} (по алфавиту).

Если «Иерархия» не заполнена, Мера отображается в корневом уровне секции «Меры» по {{alias}} (по алфавиту).

В боковой панели, внутри секции «Меры», сначала отображаются сгруппированные Меры, а потом (в корневом уровне секции «Меры») отображаются Меры без группировки.

h4. Статус {{invalid}} в конструкторе.
После внедрения backend-Шага 3, если Мера имеет статус {{invalid}}:
* она отображается как ошибочная (красный ореол, иконка ⚠);
* tooltip показывает причину, отрендеренную frontend-ом из структурного {{status_message}} по {{code}} + {{params}} с {{message}} как fallback; сырой JSON не показывается;
* Меру нельзя добавить на полки или выбрать в совместимом селекторе;
* если Мера уже была использована в визуализации ранее, привязка по {{name}} сохраняется;
* соответствующая пилюля отображается в error-состоянии (красный ореол, иконка ⚠);
* запрос данных блокируется до исправления Меры или удаления её из визуализации: backend отклоняет Меру во всех блоках {{select}}, {{where}}, {{group}}, {{having}}, {{order}} и возвращает {{HTTP 400}}; причина уже отрендерена backend-ом, а сообщение без завершающей точки заканчивается суффиксом {{(блок SELECT)}}, {{(блок WHERE)}}, {{(блок GROUP BY)}}, {{(блок HAVING)}} или {{(блок ORDER BY)}}.

Формат runtime-ошибки: {{Запрос не выполнен: Мера "Мера.X" не может быть использована, так как невалидна (статус "invalid"): <причина>. Исправьте Меру в наборе данных (блок SELECT)}}. Если причина отсутствует, фрагмент {{: <причина>}} не передаётся.

h3. Drag-and-drop и совместимые селекторы.
Мера перетаскивается на полки так же, как обычное поле. Одна и та же Мера может быть размещена на нескольких полках одновременно, если это не нарушает матрицу допустимости.

При попытке разместить Меру на несовместимую полку:
* действие блокируется;
* курсор показывает состояние запрета;
* пользователь видит пояснение из матрицы допустимости.

Меры должны поддерживаться не только на основных полках визуализации, но и во всех элементах интерфейса, где пользователь выбирает поля текущей визуализации и где бизнес-сценарий допускает использование Мер.

К таким элементам относятся:
* настройки стилизации и форматирования;
* условное форматирование;
* сценарии расчётов по уровням;
* другие выпадающие списки и selector-компоненты, работающие с полями визуализации.

Если конкретный selector технически или продуктово не поддерживает Меры на данном этапе, это ограничение должно быть явно зафиксировано в документации реализации и не должно выглядеть для пользователя как случайная потеря элемента.

h3. Меры в вычисляемых полях виджета.
В редакторе вычисляемых полей виджета Меры текущего набора данных доступны для вставки в выражение, если бизнес-сценарий вычисляемого поля допускает использование Мер.

Правила:
* поля набора данных вставляются в двойных кавычках: {{"field_name"}};
* Меры вставляются по системному {{name}} в двойных кавычках: {{"Мера.Валовая_прибыль"}};
* в списках и автодополнении отображается {{alias}}, а после выбора в выражение вставляется {{name}};
* автодополнение ищет поля и Меры по {{alias}} и/или {{name}} по логике {{OR}} и визуально различает поля и Меры;
* само вычисляемое поле сохраняет действующий контракт, включая {{calc}}, если это поле используется текущей реализацией; для ссылки на Меру внутри выражения отдельный объект {{type = "measure"}} не создаётся и копия {{expression}} Меры не сохраняется;
* при построении SQL backend находит Меру текущего набора данных по {{name}} и рекурсивно раскрывает её актуальное {{expression}} по тем же правилам, что и ссылку внутри выражения другой Меры;
* вычисляемое поле, использующее Меру, создаёт зависимость от {{name}} Меры;
* изменение {{alias}} такой Меры не блокируется и не меняет {{name}};
* удаление выполняется по общему backend-контракту зависимостей, описанному ниже;
* если Мера отсутствует или получает {{status = "invalid"}}, вычисляемое поле, содержащее ссылку на неё, не должно формировать исполняемый SQL; backend возвращает контролируемую ошибку по существующему механизму вычисляемых полей, а зависимые Меры проходят ревалидацию.

h3. Полка «Фильтры».
При размещении Меры на полке «Фильтры» открывается стандартная настройка фильтра, адаптированная для Меры.

Форма фильтра по Мере содержит:
* тип отбора: {{WHERE}} или {{HAVING}};
* структурное условие {{values}} / {{operators}} / {{not}} / {{logicOr}} без {{value_type}};
* дополнительные параметры, если они применимы для данного типа визуализации, как при использовании обычного поля.

Правила:
* при типе {{WHERE}} фильтрация применяется до {{GROUP BY}};
* при типе {{HAVING}} фильтрация применяется после {{GROUP BY}};
* для обычных поддерживаемых визуализаций используется базовая логика {{HAVING}};
* уровень-специфичная логика {{HAVING}} для Сводной таблицы относится к связанной постановке [https://jira.modusbi.ru/browse/MB-4304].

h3. Матрица допустимости Мер по полкам.
Валидация допустимости выполняется в двух точках:
* в интерфейсе при попытке разместить Меру на полку или выбрать её в совместимом селекторе;
* на бэкенде при генерации SQL перед выполнением запроса.

UX-валидация учитывает параметр {{is_aggregated}} исходной Меры, локальную функцию и эффективный тип результата конкретного размещения. Валидные Меры с {{is_aggregated = false}} доступны на любых полках с сохранением ограничений локальной агрегации, которые применяются к обычным полям. На всех полках, где обычному полю доступна локальная агрегация, применяется механизм из постановки «Выбор агрегирующей функции для неагрегированной Меры (MB-5654)»: список функций, функция по умолчанию, возможность оставить результат без локальной агрегации и поведение при переносе совпадают с обычным полем того же типа на той же полке и в том же сценарии. Реакция системы на попытку переключения режимов локальной агрегации повторяет поведение для обычного поля; на полке, где ожидаются только агрегированные значения, результат остаётся агрегированным. При добавлении на такую полку неагрегированной Меры назначается стандартная локальная агрегирующая функция (по аналогии с поведением обычного поля в таком сценарии). Для Мер с {{is_aggregated = true}} повторная локальная агрегация не применяется; запрет таких Мер на полках, где ожидаются только неагрегированные значения, сохраняется.

Матрица ниже описывает роли размещений: название полки само по себе не определяет SQL-клаузу. В сценариях, где допустимо применение агрегированных значений, для Мер применяются правила локальной агрегации, специфичные для локальной агрегации обычных полей в эквивалентном сценарии. В {{GROUP BY}} включаются только неагрегированные выражения размещений. 

Если невалидная Мера попала в runtime payload, backend отклоняет запрос по контракту использования невалидной Меры; отдельное нарушение SQL-семантики итогового запроса также приводит к контролируемому отказу.

|| *Полка* || *Допустимый тип Меры {{is_aggregated}}* || *Блокировать при нарушении?* || *Сообщение* ||
| *Значения* | Любая | Нет | — |
| *Фильтры (HAVING)* | {{true}} или {{false}} с локальной функцией агрегации | Применяются действующие правила выбора агрегированного режима | Штатное пояснение несовместимости, если допустимую агрегацию получить нельзя |
| *Фильтры (WHERE)* | {{false}} без локальной агрегации данного фильтра | Применяются действующие правила выбора неагрегированного режима | Штатное пояснение несовместимости, если допустимую агрегацию получить нельзя |
| *Строки / Столбцы в роли измерений (GROUP BY)* | {{false}}; при участии в {{GROUP BY}} — без локальной агрегации | Запрет для агрегированных Мер | Штатное пояснение при нарушении ограничения полки |
| *Детализация в роли измерения (GROUP BY)* | {{false}}; при участии в {{GROUP BY}} — без локальной агрегации | Запрет для агрегированных Мер | Штатное пояснение при нарушении ограничения полки |
| *Дополнительные* | Любая | Нет блокировки | - |

----
h3. Логика построения SQL.
h4. Общий принцип.
Построитель запросов формирует внешний запрос визуализации поверх базового слоя. Оригинальный SQL *произвольного* набора данных используется как внутренний источник без изменения.

Базовый слой может быть реализован через derived table:
{code:sql}
FROM (
  /* dataset_sql */
) AS __base
{code}

Или через CTE:
{code:sql}
WITH __base AS (
  /* dataset_sql */
)
SELECT ...
FROM __base
{code}

Продуктовым требованием является корректная инъекция выражений Мер в итоговые SQL-клаузы внешнего запроса, а не конкретная синтаксическая форма базового слоя.

h4. Разрешение выражений Мер.
Перед инъекцией выражение Меры приводится к SQL итогового запроса:
* ссылки на поля вида {{"field_name"}} разрешаются как обращения к полям базового слоя;
* ссылки на другие Меры вида {{"Мера.Валовая_прибыль"}} рекурсивно заменяются выражениями соответствующих Мер;
* самоссылки и циклы не допускаются и должны быть отсеяны валидацией Мер;
* глобальные переменные разрешаются существующим механизмом платформы;
* для каждой Меры в {{SELECT}} формируется безопасный технический SQL-alias по правилам построителя; этот alias не является свойством Меры и не хранится в объекте использования Меры в визуализации.

h4. Правила инъекции по SQL-клаузам.
Ниже полки «Строки», «Столбцы», «Детализация» рассматриваются в роли измерений. Для иных ролей размещения применяются те же SQL-клаузы и локальная агрегация, что для обычного поля в этом сценарии.
В {{SELECT}} попадают:
* обычные поля с полок «Строки», «Столбцы», «Детализация»;
* размещения Мер с {{is_aggregated = false}} без локальной функции с полок «Строки», «Столбцы», «Детализация», участвующие как измерения;
* выражения размещений Мер с полки «Значения» с учётом локальной агрегации.

В {{WHERE}} попадают:
* обычные фильтры, применимые до группировки;
* Меры с полки «Фильтры», где {{filter.mode = "WHERE"}}.

В {{GROUP BY}} попадают:
* обычные поля с полок «Строки», «Столбцы», «Детализация»;
* размещения Мер с {{is_aggregated = false}} без локальной функции с полок «Строки», «Столбцы», «Детализация», участвующие как измерения;
* Мера с {{is_aggregated = false}} без локальной агрегации с полки «Значения», если итоговый запрос строится на агрегированном уровне. Локально агрегированное выражение в {{GROUP BY}} не добавляется.

В {{HAVING}} попадают:
* Меры с полки «Фильтры», где {{filter.mode = "HAVING"}}.

Несколько условий внутри одной клаузы объединяются через {{AND}}.

h4. Поведение Меры в зависимости от полки.
h5. Полка «Значения».
Выражение Меры подставляется в {{SELECT}}.

Для неагрегированных Мер есть возможность применения локальной агрегации по правилам используемым для обычных полей. При отсутствии локальной агрегации, исходное неагрегированное выражение включается в {{GROUP BY}}, если запрос агрегируется по какому-либо полю. При выбранной агрегирующей функции, в {{SELECT}} используется локально агрегированное выражение, которое в {{GROUP BY}} не включается (по аналогии с уже агрегированной Мерой).

h5. Полка «Фильтры», тип {{WHERE}}.
Допустимы только Меры с {{is_aggregated = false}} без локальной агрегации данного фильтра.

Выражение Меры подставляется в {{WHERE}}. Фильтрация происходит до {{GROUP BY}}, то есть на уровне отдельных строк базового источника.

h5. Полка «Фильтры», тип {{HAVING}}.
Допустимы агрегированные Меры ({{is_aggregated = true}}) и неагрегированные Меры с локальной функцией данного фильтра, если такая агрегация доступна обычному полю в этом сценарии.

Агрегированное выражение конкретного размещения Меры подставляется в {{HAVING}}. Фильтрация происходит после {{GROUP BY}}, то есть на уровне агрегированных групп.

h5. Полки «Строки» и «Столбцы».
Для Меры с {{is_aggregated = false}} без локальной агрегации, используемой как измерение, выражение попадает в {{SELECT}} и, при группировке, в {{GROUP BY}}. Если полка поддерживает локальную агрегацию обычного поля, для неагрегированной Меры применяется та же обработка. Запрет на размещение Меры с {{is_aggregated = true}} сохраняется.

h5. Полка «Детализация».
Для Меры с {{is_aggregated = false}} без локальной агрегации, используемой как измерение, выражение попадает в {{SELECT}} и при группировке расширяет {{GROUP BY}}. Если полка поддерживает локальную агрегацию обычного поля, для неагрегированной Меры применяется та же обработка; агрегированное выражение в {{GROUP BY}} не включается. Запрет на размещение Меры с {{is_aggregated = true}} сохраняется.

h5. Полка «Дополнительные».
Допустима любая Мера, блокировка по {{is_aggregated}} не выполняется.

В рамках базовой логики этой Истории Мера с полки «Дополнительные» не инжектируется в SQL-запрос, если для конкретной визуализации не предусмотрена отдельная документированная логика использования этой полки.

h5. Несколько Мер на одной полке.
Несколько Мер на полке «Значения» становятся отдельными колонками в {{SELECT}}.

Несколько Мер на полке «Фильтры» объединяются по типу:
* все условия с {{filter.mode = "WHERE"}} попадают в {{WHERE}} и объединяются через {{AND}};
* все условия с {{filter.mode = "HAVING"}} попадают в {{HAVING}} и объединяются через {{AND}}.

Одновременное наличие WHERE-Мер и HAVING-Мер на полке «Фильтры» допустимо: они попадают в разные SQL-клаузы независимо.

----
h3. Устойчивость к изменениям метаданных.
h4. Редактирование alias используемой Меры.
Так как визуализация хранит ссылку по {{type = "measure"}} и {{name}}, изменение {{alias}} не нарушает ссылочную целостность. Пользователь может свободно переименовать Меру, используемую в визуализации, другой Мере или вычисляемом поле; зависимости не запрашиваются и не блокируют поле.

Перед обновлением frontend получает актуальное состояние Меры через чтение метаданных набора данных или отдельный {{get/list}}-контракт. После изменения {{alias}} визуализации и вычисляемые выражения продолжают ссылаться на прежнее {{name}}, а интерфейс отображает актуальный {{alias}} из метаданных набора данных.

{{name}} Меры не меняется после создания. Изменение системного {{name}} существующей Меры не является пользовательским сценарием этой доработки.

h4. Удаление используемой Меры.
После внедрения backend-Шага 3 удаление Меры блокируется, если на неё есть ссылка из визуализации отчёта, выражения другой Меры или выражения вычисляемого поля виджета. Backend возвращает {{HTTP 200}} с {{deleted = false}} и {{dependents}}; frontend определяет отказ по наличию ключа {{deleted}}, а не по длине массива, и сам формирует диалог. Элементы имеют виды {{report}} ({{Номер отчёта}}, {{Отчёт}}, {{Компонент}}) и {{measure}} ({{id}}, {{object_name}}, {{alias}}, {{status}}). Зависимость из вычисляемого поля относится к использованию в визуализации отчёта и возвращается существующим видом {{usage_kind = "report"}}; новый вид {{dependents}} не вводится. Для {{report}} поле {{Компонент}} содержит тип визуализации, ось/фильтр/сортировка/вычисляемое поле не различаются; {{object_type}} и {{link}} отсутствуют. При успешном удалении возвращается актуальный массив {{measures}} без ключа {{deleted}}. Унаследованная самоссылка удалению не препятствует.

h4. Изменение выражения Меры.
Если пользователь изменил выражение Меры, визуализации и вычисляемые поля виджета, использующие эту Меру, сохраняют связь по {{name}}. При следующем запросе данных используется актуальное выражение Меры.

Если после изменения выражения Мера получает статус {{invalid}}, визуализации и вычисляемые поля виджета, использующие её, переходят в предусмотренное для них error-состояние до исправления Меры или удаления ссылки на неё.

При переходе {{is_aggregated}} с {{false}} на {{true}} локальная функция сбрасывается и повторно проверяется допустимость исходно агрегированной Меры на полке. При переходе на {{false}} применяется стандартное правило локальной агрегации обычного поля для этой полки. Сам переход на {{false}} не делает размещение на агрегированной полке ошибочным.

h4. Изменение SQL набора данных.
После внедрения backend-Шага 3 при изменении SQL-запроса набора данных система перевалидирует Меры. Если Мера становится {{invalid}}, она:
* остаётся в метаданных набора данных;
* отображается как ошибочная в конструкторе;
* недоступна для нового добавления на полки;
* блокирует выполнение запроса в визуализациях, где уже используется.

----
h3. Обратная совместимость.
Если визуализация не использует Меры напрямую и ссылки на Меры отсутствуют в выражениях её вычисляемых полей:
* построитель формирует запрос тем же способом, что и в текущей системе;
* существующие визуализации продолжают работать без изменения поведения;
* существующие вычисляемые поля виджетов не изменяются;
* миграция существующих метаданных визуализаций не требуется.

----
h3. Критерии приёмки:

*AC.1* — Секция «Меры» в панели полей.
* *Дано*: аналитик строит визуализацию на основе *произвольного* набора данных, в котором есть Меры.
* *Тогда*: в панели полей отображается отдельная секция «Меры».
* *И*: в секции «Меры» отображается {{alias}} Меры, а не системное {{name}}.
* *И*: Меры визуально отличаются от обычных полей.

*AC.2* — Tooltip, ярлык {{AGR}} и display-группы.
* Для агрегированных Мер отображается ярлык {{AGR}}.
* Tooltip содержит описание, тип данных, полный текст выражения и {{name}} Меры как справочную техническую информацию.
* Если заполнены «Иерархия» и «Уровень», Меры группируются и сортируются по этим полям.

*AC.3* — Статус {{invalid}} в конструкторе.
* *Дано*: Мера имеет статус {{invalid}}.
* *Тогда*: она отображается с предупреждающей иконкой, недоступна для нового добавления на полки и показывает отрендеренную frontend-ом причину; сырой {{status_message}} не отображается.
* *И*: если визуализация уже ссылается на такую Меру, пилюля отображается в error-состоянии, а запрос данных блокируется с понятным сообщением.

*AC.4* — Меры в совместимых селекторах.
* Меры доступны не только для drag-and-drop на полки, но и во всех совместимых selector-компонентах текущей визуализации.
* Неподдержанные селекторы явно зафиксированы как ограничение данного этапа.

*AC.5* — Меры в вычисляемых полях виджета.
* *Дано*: пользователь редактирует вычисляемое поле виджета для визуализации на основе набора данных с Мерами.
* *Тогда*: валидные Меры доступны для вставки в выражение по системному имени в двойных кавычках, например {{"Мера.Валовая_прибыль"}}.
* *И*: вычисляемое поле сохраняет зависимость от {{name}} Меры.
* *И*: вычисляемое поле сохраняет действующий runtime-контракт, а отдельный объект {{type = "measure"}} для вложенной ссылки не формируется.
* *И*: backend раскрывает актуальное {{expression}} Меры по той же схеме, что и ссылку в выражении другой Меры.
* *И*: изменение {{alias}} используемой Меры доступно и не меняет {{name}}; удаление обрабатывается по общему backend-контракту зависимостей.

*AC.6* — Метаданные визуализации используют {{type = "measure"}} и {{name}}.
* *Дано*: Мера размещена на полке или выбрана в настройке визуализации.
* *Тогда*: в метаданных визуализации сохраняется {{type = "measure"}}, {{name}} и {{datasetId}}.
* *И*: {{id}} Меры из {{measures[]}} не используется как ключ связи.
* *И*: поля определения Меры, включая {{expression}}, {{is_aggregated}}, {{status}} и {{status_message}}, не копируются в объект использования Меры в визуализации.

*AC.7* — Полка «Значения».
* *Дано*: Мера {{SUM("revenue") - SUM("cost")}} находится на полке «Значения», а поле {{month}} — на полке «Строки».
* *Тогда*: итоговый внешний SQL содержит выражение Меры в {{SELECT}}.
* *И*: группировка строится по текущим правилам построителя запросов.
* *И*: для неагрегированной Меры назначение и выбор локальной функции совпадают с обычным полем на этой полке; предупреждение только из-за {{is_aggregated = false}} отсутствует.

*AC.8* — Полка «Фильтры», тип {{WHERE}}.
* *Дано*: неагрегированная Мера без локальной функции размещена на полке «Фильтры» с типом {{WHERE}}.
* *Тогда*: итоговый внешний SQL содержит выражение Меры в {{WHERE}}.

*AC.9* — Полка «Фильтры», тип {{HAVING}}.
* *Дано*: агрегированная Мера размещена на полке «Фильтры» с типом {{HAVING}}.
* *Тогда*: итоговый внешний SQL содержит условие в {{HAVING}}.
* *И*: если обычному полю доступна локальная агрегация в этом сценарии, неагрегированная Мера с такой функцией также допускается в {{HAVING}} через реализованный механизм; при необходимости агрегированного результата применяется штатная функция обычного поля.

*AC.10* — Полки «Строки», «Столбцы», «Детализация».
* *Дано*: агрегированная Мера перетаскивается на полку «Строки», «Столбцы» или «Детализация» в роли неагрегированного измерения.
* *Тогда*: размещение блокируется и пользователь получает штатное пояснение ограничения полки.
* *И*: неагрегированная Мера без локальной функции, размещённая на этих полках, попадает в {{SELECT}} и, при группировке, в {{GROUP BY}}.

*AC.11* — Полка «Дополнительные».
* *Дано*: Мера размещена на полке «Дополнительные».
* *Тогда*: размещение не блокируется независимо от {{is_aggregated}}.
* *И*: в рамках базовой логики этой Истории выражение Меры не инжектируется в SQL-запрос, если для конкретной визуализации не предусмотрена отдельная документированная логика этой полки.

*AC.12* — Несколько Мер на одной полке.
* *Дано*: на полке «Значения» находятся две Меры.
* *Тогда*: обе Меры становятся отдельными колонками в {{SELECT}}.
* *И*: несколько фильтров по Мерам объединяются через {{AND}} внутри своих SQL-клауз.

*AC.13* — Свободное редактирование alias используемой Меры.
* *Дано*: Мера используется в визуализации.
* *Когда*: пользователь открывает редактирование Меры в настройках набора данных.
* *Тогда*: поле {{alias}} доступно без запроса зависимостей, и пользователь может сохранить новое значение.
* *И*: визуализация продолжает ссылаться на Меру по прежнему {{name}}.

*AC.14* — Блокировка удаления используемой Меры.
* *Дано*: внедрён backend-Шаг 3 и Мера используется в визуализации отчёта, выражении другой Меры или выражении вычисляемого поля виджета.
* *Когда*: пользователь пытается удалить Меру.
* *Тогда*: backend отвечает {{HTTP 200}} с {{deleted = false}} и {{dependents}}, а удаление не выполняется.

*AC.15* — Обратная совместимость.
* При отсутствии Мер на полках и ссылок на Меры в выражениях вычисляемых полей построитель запросов сохраняет текущее поведение.
* Существующие визуализации без Мер продолжают работать без изменения поведения.
