Теперь, когда у нас реализованна общая постановка по реализации концепции мер для нашего аналитического портала и есть постановка на реализацию первого шага backend-разработки для внедрения Мер на наш портал, нужно составить постановку на реализацию второго шага backend-разработки.

Изучи актуальные файлы:
1) ./Постановка_меры_new3.txt
2) ./Меры_в_наборе_данных_Шаг_1.txt
3) ./Меры_frontend_реализация_Шаг_1.txt
4) ./Меры_backend_реализация_Шаг_1
5) ./Контракты_мер.txt

Требуется продумать какие запросы будет отправлять фронтенд при работе с Мерами в визуализациях и размещении Мер на различных полках визуализаций, чтобы бэкенд (который вообще ничего не знает ни о каких полках в визуализациях) корректно обрабатывал запросы от фронтенда с Мерами и корректно встраивал используемые меры в соответствующую SQL-клаузу. Нужно составить постановку для реализации бэкенд доработок и научить бэкенд правильно обрабатывать передаваемые фронтендом JSON'ы с информацией где используется мера и в какую SQL-клаузу её необходимо разместить при формировании финального SQL-запроса. Для этого нужно узучить текущее состояние системы и отправляемые запросы с фронта при работе визуализации и размещении на различных полках обычных полей, изучить текущий механизм обработки бэкендом размещения на полках обычных полей, а потом адаптировать данный механизм для использования его для Мер.

Backend не должен знать о предметных “полках” визуализации, но должен уметь по данным runtime JSON понять, что Мера используется в контексте select, group, where, having или order, затем раскрыть её по name и встроить выражение в нужную SQL-клаузу внешнего запроса над базовым SQL датасета.

При отправке запроса с фронтенда в существующей системе у запроса данных есть универсальные runtime-блоки group, select, where, having, order, variables, series, и именно они, по сути, являются текущим backend-facing контрактом для построения SQL. Меры будут адаптироваться через уже существующий механизм, и backend должен работать не с “полками” как таковыми, а с этими runtime-структурами. 

Как системный аналитик с большим стажем, опираясь на уже реализованные постановки, изученные примеры отправляемых запросов фронтендом с обычными полями и общий контекст задачи, подготовь постановку для реализации второго шага необходимых бэкенд доработок портала в рамках реализации внедрения Мер и использования Мер при размещении их на полках визуализаций.

Новая постановка должна полностью согласовываться с уже созданными постановками и в частности понятно давать разработчику информацию о требуемых доработках системы с точки зрения бэкенда. Постановка про второй шаг бэкенд-доработок для внедрения мер должна быть верной и согласованной. Сохраняй оптимальную разметку и структуру документов, которая уже используется в существующих постановках, для публикации в Jira.

Постановка должна декларативно давать разработчикам информацию о необходимых доработках и не фокусироваться на изменениях внесенных в постановки, обсуждениях, согласованиях и прочих некритичных деталях в рамках реализации данной доработки.
