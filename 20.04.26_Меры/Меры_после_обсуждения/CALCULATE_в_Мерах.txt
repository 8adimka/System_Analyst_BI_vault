
Суть кейса Олега.
Олег хочет вычислить многоуровневую агрегацию — конкретно: долю выручки ТОП-10 клиентов в общей сумме. Для этого ему нужно:

Уровень 1: Взять сырые строки, применить пользовательские фильтры (регион, продукт и т.д.)

Уровень 2: Сгруппировать по клиентам, посчитать SUM(Факт) → получить агрегат по клиенту

Уровень 3: Отсортировать по убыванию, присвоить номер строки (row_number()) → определить ТОП-10

Уровень 4: Применить SUM(...) FILTER (WHERE НомерСтроки <= 10) → посчитать выручку только ТОП-10

Уровень 5: Разделить на общую сумму → получить долю

Это классический паттерн nested aggregation — агрегат над агрегатом, причём с ранжированием внутри. Каждый уровень является FROM-источником для следующего.

Почему Меры в текущем виде это не покрывают
Архитектура Мер по постановке строго однослойная:

text
FROM (
  /* Оригинальный SQL набора данных */ 
) AS __base
SELECT <выражения Мер>
WHERE / GROUP BY / HAVING ...
Мера — это SQL-выражение, инжектируемое в одну клаузу внешнего запроса. У неё есть ровно один __base — оригинальный SQL набора данных. Это означает принципиальные ограничения:

Выражение Меры не может само по себе создать вложенный подзапрос над результатом другой агрегации. Нет синтаксиса, чтобы написать SUM(...) FILTER (WHERE row_number() <= 10) корректно внутри одного SELECT-выражения при том, что row_number() считается на другом уровне группировки.

Меры предполагают одну плоскость вычисления: __base → одна агрегация. Случай Олега требует минимум трёх уровней вложенности.

window function (ROW_NUMBER() OVER (...)) нельзя фильтровать в том же WHERE/HAVING, где она вычисляется — это нарушение SQL-семантики. Нужен дополнительный слой обёртки.

Вывод: ошибки в постановке нет — она просто решает другой класс задач. Меры — это "вычисляемые поля уровня датасета", а не "пайплайн трансформаций".

Сценарии, которые Меры покрывают хорошо
Меры в текущем виде отлично работают для:

Сценарий	Пример
Сценарий	Пример
Переиспользуемая агрегация	SUM("revenue") - SUM("cost") → Валовая прибыль
Фильтрация по агрегату (HAVING)	Показывать только группы, где сумма > 1000
Вычисляемое измерение (GROUP BY)	DATE_TRUNC('month', "date") на полке "Строки"
Составные выражения из нескольких мер	[Выручка] / [Количество] → Средний чек
Фильтрация строк до агрегации (WHERE)	Исключить строки с status = 'cancelled'
Тултип-метрики	Дополнительная мера на полке "Дополнительные"
Всё это — однослойные вычисления над __base.




А вот подскажи, а что если одна мера используется в выражении другой меры?

То как тогда такая "составная" Мера инжектируется в SQL-клаузу и не ломает ли тогда такой сценай использования весь описанный сценарий использования мер к которому подводит эта постановка?

И дополнительный вопрос - А что если в рамках создания меры дать возможность использоавть что-то типа внутренней функции CALCULATE () в которую можно подставить выражение или целую меру. Тогда система должна будет сначала произвести вычисление и потом  подставить результат в новую меру, которая тоже может состоять из выражения.

Такой сценарий не закрывает запрос Олега? Может стоит в дальнейшем продумать и ввести в Меры возможность применять функцию CALCULATE (), чтобы назначить часть выражения, которая будет выполняться сначала, а потом уже результат этого выражаения будет обёрнут новым запросом? Объясни в чём минусы такого подхода и подходит ли он для закрытия таких кейсов?


Для кейса Олега это выглядело бы примерно так:

text
-- Мера "ВыручкаТОП10":
CALCULATE(
  SUM("Факт"),
  ROW_NUMBER() OVER (ORDER BY SUM("Факт") DESC) <= 10
)
Проблема 1: семантическая несовместимость с SQL
ROW_NUMBER() — это оконная функция, которая не может использоваться в WHERE/HAVING напрямую. Чтобы фильтровать по ней, нужен дополнительный уровень вложенности. Значит, CALCULATE вынуждено генерировать подзапрос внутри выражения Меры:

sql
SELECT
  (
    SELECT SUM(f) FROM (
      SELECT SUM("Факт") AS f,
             ROW_NUMBER() OVER (ORDER BY SUM("Факт") DESC) AS rn
      FROM (__base) AS b2
      WHERE <фильтры>  -- ← проблема: как пробросить сюда контекст фильтров?
      GROUP BY "Партнер"
    ) t WHERE rn <= 10
  ) / NULLIF(SUM("Факт"), 0)
FROM (__base) AS __base
WHERE <фильтры>
GROUP BY ...

Проблема 2: двойное обращение к __base
В этом сценарии __base используется дважды: один раз во внешнем запросе и один раз внутри CALCULATE-подзапроса. Это означает, что СУБД выполняет оригинальный SQL набора данных дважды — потенциально очень дорого. Без материализации (CTE с MATERIALIZED или временной таблицей) это не решить на уровне простой инъекции.

Проблема 4: ограниченность подхода
Даже если реализовать CALCULATE(), кейс Олега требует трёх независимых уровней агрегации (Факт → SUM по клиенту → ROW_NUMBER → SUM по ТОП-10). Одной функцией CALCULATE это не покрывается — нужно либо вложение CALCULATE в CALCULATE, либо цепочка Мер, каждая из которых вызывает CALCULATE. Сложность экспоненциально растёт.

Итоговая оценка
Критерий	Меры + CALCULATE()	Связанные датасеты (Граф)
Закрывает кейс Олега	Частично и с оговорками	Полностью
Сложность реализации	Высокая (контекст фильтров, двойной __base)	Средняя (рекурсивная сборка CTE)
Понятность для аналитика	Низкая (DAX-семантика нетривиальна)	Высокая (визуальные зависимости датасетов)
Производительность	Риск двойного выполнения __base	Контролируемо через CTE/матвью
Соответствие текущей архитектуре	Ломает принцип "плоского выражения"	Органично расширяет существующий механизм
Вывод: CALCULATE() — это попытка затащить в Меры задачу, которая архитектурно принадлежит уровню датасетов. Реализовать это корректно значительно сложнее, чем кажется, а для аналитика это создаёт неочевидную семантику (особенно с контекстом фильтров). Кейс Олега правильно закрывать механизмом связанных датасетов, а Меры оставить тем, чем они задуманы — переиспользуемыми однослойными выражениями. Если в будущем всё же двигаться в сторону CALCULATE, стоит сначала сделать связанные датасеты и уже поверх них смотреть, какие сценарии ещё не покрыты.


А в чём проблема сделать с мерами вот так:
1) Создать Мера1 - которая сможет Сгруппировать по клиентам, посчитать SUM(Факт) → получить агрегат по клиенту. Просумировать и получить общую сумму.
2) Создать Мера2 - которая сможет Сгруппировать по клиентам, посчитать SUM(Факт) → получить агрегат по клиенту, Отсортировать по убыванию и отобрать только первые 10 записей. Просумировать и получить сумму по ТОП-10 клиентов.
3) Создать Мера3 - которая в выражении будет содержать что-то типа:
Calculate(Мера2)/(Calculate(Мера1)/100)

Все три меры будут выполнять с учётом указанных пользователем фильтров.
В чём проблема такого подхода? Если мы научим меры выполняться и потом уже подставляться в выражение, то можем организовывать сложные и многоуровневые конструкции. Разве нет? И никто не запрещает обернуть Мера3 в Calculate() и подставить её в выражении Мера4 - таким образом мы можем таким явным способом давать пользователю прописывать и реализовывать вычисления с любой глубиной вложенности.
