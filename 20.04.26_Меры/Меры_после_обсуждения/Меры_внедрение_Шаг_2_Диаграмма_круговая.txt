h3. Контекст и проблематика.

Полное описание продуктовой логики Мер приведено в Эпике [https://jira.modusbi.ru/browse/MB-4364]. Общий механизм Шага 2 описан в Истории [https://jira.modusbi.ru/browse/MB-4481], runtime-обработка Мер — в бэкендзадаче [https://jira.modusbi.ru/browse/MB-5035].

Для произвольных наборов данных уже реализованы хранение Мер и их использование бэкендом при построении SQL. Меры также внедрены в визуализацию *«Диаграмма столбчатая»*.

В визуализации *«Диаграмма круговая»* пользователь пока не может использовать Меры текущего набора данных на полках и в связанных настройках. В результате единые показатели набора данных приходится повторно описывать вычисляемыми полями виджета.

Особенность круговой диаграммы — полка *«Значения»* не формирует отдельный ряд по каждой размещённой пилюле. Одна пилюля задаёт величины секторов, а остальные могут использоваться как вспомогательные источники данных с типами *«Цвет»*, *«Подзаголовок»* и *«Подсказка»*. Поддержка Мер должна учитывать эту модель.

----

h3. Цель задачи.

*Требуется:*
# Подключить реализованный механизм Мер к визуализации *«Диаграмма круговая»*.
# Добавить Меры в стандартную левую боковую панель и обеспечить их использование на полках *«Значения»*, *«Категории»*, *«Серии»* и *«Фильтры»*.
# Поддержать Меры на полке *«Значения»* во всех существующих типах пилюли: *«Значение»*, *«Цвет»*, *«Подзаголовок»* и *«Подсказка»*.
# Обеспечить работу результатов Мер в подписях данных, всплывающей подсказке и других настройках круговой диаграммы, в которых сейчас может использоваться результат вычисляемого поля.
# Сохранять ссылки на Меры и локальные настройки конкретных размещений по общему контракту и формировать runtime payload для существующего бэкенд-механизма.
# Сохранить текущее поведение круговых диаграмм, в которых Меры не используются.

_Пользовательская история:_
Как аналитик, я хочу использовать Меры в круговой диаграмме наравне с обычными и вычисляемыми полями, чтобы строить и оформлять диаграмму на основе единых показателей набора данных без дублирования формул в виджете.

h3. 1. Область применения и текущая конфигурация.

h4. 1.1. Визуализация и набор данных.

Доработка выполняется для визуализации:
* {{chartType = "pieChart"}};
* {{visualType = "pie"}}.

Источником Мер является массив {{datasets.measures}} выбранного *произвольного* набора данных. Отсутствующий массив {{measures}} обрабатывается как пустой список.

Полки необходимо определять по {{axes[].type}}, а не по позиции объекта в массиве и не по отображаемому {{name}}/{{title}}:

|| Полка || {{axes[].type}} || Действующая особенность ||
| *«Значения»* | {{values}} | Режим *«Первое»* / *«Все»*; для пилюли доступен параметр *«Тип»* |
| *«Категории»* | {{categories}} | Учитывается первая активная пилюля |
| *«Серии»* | {{series}} | Режим *«Вкл»* / *«Выкл»* |
| *«Фильтры»* | {{filters}} | Используется действующая форма настройки фильтра |

Необходимо сохранить текущие способы хранения режимов полок, {{selectedFieldIndex}}, порядок размещений, признаки активности, сортировку и остальные локальные параметры. Новые значения {{selectedFieldIndex}} или отдельные оси для Мер не вводятся.

Конфигурация круговой диаграммы содержит {{axes}} и {{axesDefault}}. Во всех действующих сценариях сохранения, копирования, восстановления и сброса настроек объекты использования Мер, их локальные {{id}} и настройки размещения должны синхронизироваться между этими структурами по тем же правилам, что обычные и вычисляемые поля.

h4. 1.2. Общие правила использования Меры.

При прямом использовании Меры визуализация хранит ссылку на определение Меры текущего набора данных:

{code:json}
{
  "id": "pie_measure_4f9b7e2d",
  "type": "measure",
  "name": "Мера.Валовая_прибыль",
  "datasetId": 244
}
{code}

Правила:
* {{name}} является единственным ключом связи с определением Меры в актуальных метаданных текущего набора данных;
* {{datasetId}} фиксирует контекст набора и используется для проверки того, что ссылка относится к текущему набору, но не является вторым ключом поиска Меры;
* {{id}} — локальный идентификатор конкретного размещения в диаграмме; он не равен {{datasets.measures[].id}};
* {{alias}} используется для отображения и читается из актуальных метаданных набора данных;
* {{expression}}, {{description}}, {{aggregation_kind}}, {{data_type}}, {{hierarchy}}, {{level}}, {{status}} и {{status_message}} не копируются в конфигурацию как источник определения Меры;
* {{type = "measure"}} остаётся признаком сущности независимо от выбранного для пилюли типа *«Значение»*, *«Цвет»*, *«Подзаголовок»* или *«Подсказка»*;
* тип пилюли, форматирование, сортировка, фильтр и другие параметры являются локальными настройками конкретного размещения;
* одна Мера может быть размещена несколько раз, в том числе на одной полке с разными типами; каждое размещение получает собственный {{id}} и независимые локальные настройки

Мера поддерживается в каждом сценарии круговой диаграммы, в котором допустимо вычисляемое поле с таким же типом данных ({{data_type}}), с дополнительной проверкой {{aggregation_kind}} для SQL-контекста.

h3. 2. Целевой интерфейс работы с Мерами.

h4. 2.1. Левая боковая панель.

При выборе произвольного набора данных стандартная левая панель должна содержать расположенные друг за другом секции:
* *«Поля»* — обычные поля набора данных и вычисляемые поля виджета;
* *«Меры»* — Меры из {{datasets.measures}} текущего набора данных.

Обе секции реализуются через актуальный общий компонент аккордеона. При открытии конструктора секции *«Поля»* и *«Меры»* по умолчанию раскрыты; пользователь может независимо сворачивать и разворачивать их по стандартному поведению общего компонента. Отдельная реализация аккордеона для круговой диаграммы не создаётся.

Для секции *«Меры»* переиспользуется общий интерфейс Мер:
* отображение по актуальному {{alias}};
* ярлык {{AGR}} для {{aggregation_kind = 1}};
* группировка по иерархии ({{hierarchy}}); внутри группы — сортировка по назначенному уровню ({{level}}) по возрастанию, затем по {{alias}};
* Меры без назначенной {{hierarchy}} отображаются в корне секции с сортировкой по {{alias}};
* общий поиск находит поля и Меры по {{alias}} или {{name}} по логике {{OR}};
* tooltip содержит {{description}}, если заполнено, {{data_type}}, полный текст {{expression}}, {{name}}, признак агрегированности и, для невалидной Меры, человекочитаемую причину;
* Мера с {{status = "invalid"}} отображается в error-состоянии и недоступна для нового drag-and-drop или выбора.

Для структурного {{status_message}} фронтенд формирует локализованную причину из {{code}} и {{params}}, использует {{message}} только как fallback для неизвестного {{code}} и не показывает пользователю сырой JSON.

h4. 2.2. Пилюля Меры и её настройки.

Пилюля Меры:
* на полках *«Значения»*, *«Категории»* и *«Серии»* имеет светло-синий цвет {{#3491F7}};
* на полке *«Фильтры»* имеет стандартный для этой полки салатовый цвет;
* отображается по актуальному {{alias}};
* содержит ярлык {{AGR}} для {{aggregation_kind = 1}} независимо от цвета полки;
* сохраняет визуальный признак типа *«Мера»*;
* предоставляет те же доступные локальные настройки, что вычисляемое поле того же {{data_type}}, кроме изменения выражения и агрегированности Меры.

В настройках пилюли на полке *«Значения»* для Меры должен быть доступен существующий параметр *«Тип»* со значениями:
* *«Значение»*;
* *«Цвет»*;
* *«Подзаголовок»*;
* *«Подсказка»*.

Техническое поле и значения, которыми круговая диаграмма уже хранит данный параметр для вычисляемых полей, должны быть переиспользованы без введения отдельной кодировки для Мер. Изменение типа не меняет {{type = "measure"}} и не изменяет определение Меры в {{datasets.measures}}.

Ограничения по {{data_type}}, доступность пунктов меню, обработка {{null}}, пустого результата и форматирование для каждого типа пилюли должны полностью повторять действующее поведение вычисляемого поля того же типа.

h3. 3. Использование Мер в круговой диаграмме.

h4. 3.1. Активность размещений и матрица допустимости.

Размещение считается активным, только если действующий алгоритм круговой диаграммы использует его при текущем режиме полки:
* на *«Значениях»* в режиме *«Первое»* — учитывается только первое размещение;
* на *«Значениях»* в режиме *«Все»* — учитываются размещения всех поддерживаемых типов;
* на *«Категориях»* — только первое учитываемое размещение;
* на *«Сериях»* — размещения, которые текущий компонент учитывает при положении *«Вкл»*;
* на *«Фильтрах»* — фильтр с заполненным обязательным условием.

Порядок определения первого учитываемого размещения, а также выбора активных размещений серии не изменяется: Мера должна давать тот же результат, что вычисляемое поле с тем же {{data_type}}, позицией, типом пилюли и состоянием полки.

|| Полка / использование || {{aggregation_kind = 0}} || {{aggregation_kind = 1}} || Целевой эффект ||
| *«Значения»* | Допускается с неблокирующим предупреждением | Допускается | Активные размещения передаются в {{select}} или используются согласно типу пилюли |
| *«Категории»* | Допускается | Блокируется | Первая активная Мера формирует вычисляемую категорию через {{group}} и {{select}} |
| *«Серии»*, режим *«Вкл»* | Допускается | Блокируется | Активные Меры участвуют в разбиении по сериям через {{group}} и {{select}} |
| *«Серии»*, режим *«Выкл»* | Допускается к хранению | Новое размещение блокируется | Размещения не влияют на запрос и диаграмму |
| *«Фильтры»* / {{WHERE}} | Допускается | Блокируется | Условие передаётся в {{where}} |
| *«Фильтры»* / {{HAVING}} | Блокируется | Допускается | Условие передаётся в {{having.items}} |
| Поддерживаемая сортировка | Допускается | Допускается | Ссылка на Меру передаётся в {{order}} по текущей логике сортировки |

Сохранённая невалидная или ставшая несовместимой Мера не удаляется автоматически. Активное проблемное размещение блокирует построение диаграммы с понятным сообщением. Неактивное размещение сохраняется в конфигурации, не передаётся в runtime payload и не блокирует построение.

h4. 3.2. Полка «Значения» и типы пилюли.

В режиме *«Первое»*:
* обрабатывается только первое учитываемое размещение по действующему алгоритму полки;
* если этим размещением является Мера, в runtime payload передаётся ссылка {{type = "measure"}};
* остальные размещения, включая Меры вспомогательных типов, сохраняются вместе с настройками, но не передаются в запрос и не влияют на диаграмму.

В режиме *«Все»*:
* все учитываемые размещения передаются в {{select}} в порядке полки с отдельными техническими alias;
* величины и доли секторов рассчитываются по первому учитываемому размещению полки в порядке, определяемом действующим алгоритмом круговой диаграммы;
* последующие размещения могут использоваться в соответствующих вспомогательных каналах (например, с типами *«Цвет»*, *«Подзаголовок»* и *«Подсказка»*) и не создают отдельную круговую диаграмму, дополнительное кольцо или новый ряд;
* последующие размещения типа *«Значение»* не создают дополнительные круговые диаграммы, кольца или ряды и обрабатываются по действующей логике;
* поддержка Мер не изменяет существующее поведение конфигурации, в которой первому размещению назначен вспомогательный тип.

|| Тип пилюли || Использование результата Меры || Влияние на геометрию секторов ||
| *«Значение»* | Размещение используется как источник значений; первое учитываемое размещение полки задаёт абсолютное значение и долю сектора по действующему алгоритму; применяются текущие настройки точности, суффикса и шаблонов подписей | Да, только если размещение является основным по действующему алгоритму |
| *«Цвет»* | Результат передаётся в существующий канал управления цветом и обрабатывается по правилам вычисляемого поля того же {{data_type}}; действующие fallback и базовая палитра сохраняются | Нет |
| *«Подзаголовок»* | Результат используется существующим каналом подзаголовка по правилам вычисляемого поля того же {{data_type}} | Нет |
| *«Подсказка»* | Результат доступен в существующей всплывающей подсказке для соответствующего сектора и форматируется по текущим правилам | Нет |

Значение *«Нет»* в последнем столбце означает, что вспомогательный результат не является непосредственным источником угла сектора. SQL-влияние неагрегированного вспомогательного размещения на группировку должно повторять поведение эквивалентного вычисляемого поля и общий контракт {{SELECT}}: выражение учитывается в группировке либо запрос завершается контролируемой ошибкой, если корректный SQL построить нельзя.

Одна Мера может одновременно использоваться, например, как *«Значение»* и *«Подсказка»*. Компонент должен различать эти размещения по локальным {{id}}, сохранять их типы и настройки независимо и возвращать каждое значение по соответствующему техническому alias.

Для Меры с {{aggregation_kind = 0}} отображается неблокирующее предупреждение: *«Мера "[alias]" является неагрегированной. Убедитесь, что её использование на полке "Значения" даст корректный результат»*. Предупреждение не блокирует размещение и построение, если SQL-запрос может быть сформирован.

h4. 3.3. Полки «Категории» и «Серии».

*Полка «Категории»:*
* активно используется только первое учитываемое размещение;
* допускается Мера с {{aggregation_kind = 0}} и совместимым {{data_type}};
* результат Меры определяет разбиение на секторы, подписи категорий, элементы легенды и контекст взаимодействия так же, как результат вычисляемого поля;
* активная Мера передаётся в {{group}} и {{select}} по текущей стратегии технических alias;
* размещение Меры с {{aggregation_kind = 1}} блокируется с сообщением: *«На полке "Категории" допустимы только неагрегированные Меры»*.

*Полка «Серии»:*
* допускается Мера с {{aggregation_kind = 0}} и совместимым {{data_type}};
* при положении *«Вкл»* компонент применяет к Мерам тот же действующий алгоритм выбора и отображения серий, что к вычисляемым полям; активные размещения передаются в {{group}} и {{select}};
* при положении *«Выкл»* размещения сохраняются, но не передаются в {{group}}, {{select}} и {{order}}, не влияют на разбиение, легенду и количество отображаемых элементов;
* размещение Меры с {{aggregation_kind = 1}} блокируется независимо от положения переключателя с сообщением: *«На полке "Серии" допустимы только неагрегированные Меры»*.

h4. 3.4. Полка «Фильтры».

Мера использует стандартный интерфейс настройки фильтра:
* для {{aggregation_kind = 0}} применяется только режим {{WHERE}};
* для {{aggregation_kind = 1}} применяется только режим {{HAVING}};
* режим определяется по {{aggregation_kind}}; несовместимый выбор недоступен;
* условие хранится структурно в {{values}} / {{operators}} / {{not}} / {{logicOr}} по общему контракту Мер;
* отдельный {{value_type}} не передаётся, тип значений определяется по актуальному {{data_type}} Меры;
* фильтр с незаполненным обязательным значением считается неактивным и не передаётся в runtime payload;
* WHERE- и HAVING-условия объединяются с остальными условиями соответствующей SQL-клаузы по действующим правилам, базово через {{AND}};
* фронтенд формирует {{having}} объектом с ключами {{condition}} и {{items}}; структурные фильтры по Мерам передаются в {{having.items}}.

Доступные операторы, правила {{IN}} / {{NOT IN}}, обработка {{null}} и объединение значений внутри одного условия должны соответствовать общему контракту [^Контракты_мер_обновлённый.txt].

h4. 3.5. Настройки, отображение и взаимодействие с диаграммой.

Результат активной Меры должен поддерживаться в существующих разделах правой панели на тех же условиях, что результат вычисляемого поля той же роли и {{data_type}}, например:
* *«Легенда»* — выпадающий список «Текст для:» строится по результатам активных категорий, включая допустимое размещение Мер на полке «Категории»;

Если в существующем селекторе правой панели выбирается конкретное поле/размещение, в список кандидатов должны включаться допустимые активные размещения Мер, а не весь массив {{datasets.measures}}. Мера отображается по {{alias}} с признаком типа *«Мера»*, а настройка связывается с конкретным локальным {{id}}. Это исключает конфликт, если одна Мера размещена несколько раз с разными типами или настройками.

Смена типа пилюли, порядка размещений, режима *«Первое»*/*«Все»* или состояния *«Серий»* не должна удалять локальные настройки временно неактивного размещения. После повторной активации они восстанавливаются, если ссылка на Меру существует и совместима.

Клик по сектору, снятие выбора, подсветка/затухание, фильтрация и дрил должны сохранять существующее поведение круговой диаграммы. Настроенный переход выполняется через действующую кнопку действия в полосе управления диаграммой. Если категория или серия сформирована неагрегированной Мерой, её результирующее значение участвует в контексте взаимодействия так же, как значение вычисляемого поля.

h3. 4. Сохранение и восстановление конфигурации.

В {{axes[].fields}} и, когда это предусмотрено текущим механизмом, в {{axesDefault[].fields}} сохраняются ссылка на Меру и локальные настройки размещения. Источником определения Меры остаётся {{datasets.measures}}.

При открытии, копировании или восстановлении диаграммы фронтенд должен:
# получить актуальный набор данных и массив {{datasets.measures}} через действующую операцию {{get}} / {{list}} объекта {{datasets}} либо её реализованный эквивалент;
# проверить соответствие сохранённого {{datasetId}} текущему набору данных;
# при совпадении контекста найти определение Меры по {{name}} без подбора по {{alias}};
# восстановить полку, порядок, локальный {{id}}, тип пилюли, фильтр, сортировку, форматирование и связанные настройки правой панели;
# отобразить актуальные {{alias}}, {{aggregation_kind}}, {{data_type}}, {{status}} и {{status_message}};
# повторно проверить совместимость Меры с полкой, типом пилюли и активным SQL-контекстом;
# не удалять автоматически отсутствующую, невалидную или ставшую несовместимой ссылку;
# если определение по {{name}} не найдено, использовать сохранённый {{name}} как резервное отображаемое название и не подбирать {{alias}} другой Меры.

Изменение {{alias}} при неизменном {{name}} не нарушает связь: после обновления метаданных интерфейс показывает новое название. Изменённое {{expression}} используется бэкендом при следующем runtime-запросе без пересохранения диаграммы.

При смене набора данных применяется действующий механизм обработки размещений обычных и вычисляемых полей. Независимо от него фронтенд не связывает сохранённую Меру с Мерой другого набора только по совпадающим {{name}} или {{alias}}. Если текущий механизм сохраняет несопоставленное размещение, оно отображается в error-состоянии по сохранённому {{name}}.

h3. 5. Runtime payload и взаимодействие с бэкендом.

Бэкенд-объект метаданных — {{datasets}}; актуальные Меры читаются через действующую команду {{get/list}} или её реализованный эквивалент. Запрос данных круговой диаграммы выполняется методом {{POST}} на {{/v1/api/recordsets/<dataset_id>}}.

Минимальный прямой runtime-объект активной Меры:

{code:json}
{
  "type": "measure",
  "name": "Мера.Валовая_прибыль",
  "alias": "[values][0]"
}
{code}

{{alias}} в runtime-объекте — технический alias результата, а не пользовательский {{datasets.measures[].alias}}. {{datasetId}} хранится в конфигурации, но не входит в канонический runtime-элемент: набор определяется параметром {{<dataset_id>}} маршрута. Конкретная схема технических alias и индексов должна оставаться текущей для круговой диаграммы.

Все активные размещения Мер включаются в один действующий запрос данных диаграммы. Отдельный запрос для каждой Меры или вспомогательного типа пилюли не выполняется.

|| Использование активной Меры || Runtime-блок || Правило ||
| *«Значения»*, режим *«Первое»* | {{select}} | Передаётся только первое учитываемое размещение |
| *«Значения»*, режим *«Все»* | {{select}} | Передаются учитываемые размещения всех типов в порядке полки с отдельными техническими alias |
| *«Категории»* | {{group}} и {{select}} | Передаётся только первая активная неагрегированная Мера |
| *«Серии»*, режим *«Вкл»* | {{group}} и {{select}} | Передаются активные неагрегированные Меры по текущей логике компонента |
| *«Серии»*, режим *«Выкл»* | Не передаётся | Полка не влияет на runtime payload |
| *«Фильтры»*, {{aggregation_kind = 0}} | {{where}} | Передаётся структурное условие со ссылкой {{type}} / {{name}} |
| *«Фильтры»*, {{aggregation_kind = 1}} | {{having.items}} | Передаётся структурное условие со ссылкой {{type}} / {{name}} |
| Поддерживаемая сортировка | {{order}} | Передаются {{type}}, {{name}} и направление по текущему контракту |

Бэкенд находит определение по {{name}} в актуальном {{datasets.measures}}, раскрывает {{expression}} и подставляет его в SQL-контекст, заданный runtime-блоком. Отдельный endpoint и отдельная логика SQL-генерации для круговой диаграммы не требуются.

Если одно размещение уже передано в {{select}}, использование его результата в подписи, tooltip, легенде, цвете или настройке правой панели не должно создавать дублирующий runtime-объект. Сопоставление результата с ролью выполняется по локальному размещению и его техническому alias.

Вычисляемое поле круговой диаграммы может содержать ссылку на Меру текущего набора данных по {{name}} в двойных кавычках, например {{"Мера.Валовая_прибыль"}}. Такое поле остаётся объектом вычисляемого поля с {{calc}}; отдельный runtime-объект {{type = "measure"}} для вложенной ссылки не создаётся. Бэкенд раскрывает актуальное выражение Меры по общему контракту.

Контролируемая ошибка бэкенда отображается пользователю без автоматического удаления ссылки, если Мера не найдена, невалидна, передана в несовместимый runtime-блок либо итоговый SQL не может быть построен.

h3. 6. Ошибки, зависимости, права и обратная совместимость.

* Фронтенд не анализирует {{expression}} для определения валидности или фактической агрегированности; источником {{status}}, {{status_message}}, {{aggregation_kind}} и {{data_type}} являются актуальные метаданные бэкенда.
* После внедрения Шага 3 круговая диаграмма должна без отдельной доработки поддержать {{invalid}} и структурный {{status_message}}. Проверка фронтенд-состояний {{invalid}} может выполняться на подготовленных метаданных.
* Runtime-ошибка {{HTTP 400}} показывается как человекочитаемое сообщение бэкенда; фронтенд не пытается интерпретировать её как структурный {{status_message}}.
* Новые права не вводятся: чтение Мер определяется существующим правом чтения набора данных и отчёта, изменение конфигурации — правом редактирования отчёта/виджета.
* Круговые диаграммы без прямых размещений {{type = "measure"}} должны открываться, строиться, редактироваться, сохраняться, копироваться и экспортироваться без изменения конфигурации и результата, в том числе если вычисляемые поля уже содержат ссылки на Меры внутри {{calc}}. Такие ссылки продолжают обрабатываться существующим контрактом вычисляемых полей и не преобразуются в прямые объекты {{type = "measure"}}.
* Смешанное использование обычных полей, вычисляемых полей и Мер сохраняет текущий порядок размещений, роли, технические alias и правила выбора активных объектов.
* Автообновление, экранное построение, копирование и экспорт диаграммы должны использовать согласованный runtime-механизм и возвращать одинаковый результат для Мер.

h3. 8. Критерии приёмки (AC):

*AC.1* — Секция «Меры»:
* *Дано:* пользователь открыл круговую диаграмму на произвольном наборе данных;
* *Когда:* загружены метаданные набора;
* *Тогда:* ниже раскрытой секции *«Поля»* отображается раскрытая секция *«Меры»*; обе секции можно независимо свернуть и развернуть через актуальный общий компонент аккордеона;
* *И:* Меры отображаются по {{alias}}, с группировкой по {{hierarchy}}, сортировкой по {{level}} / {{alias}}, поиском по {{alias}} или {{name}}, tooltip и ярлыком {{AGR}} для {{aggregation_kind = 1}};
* *И:* Мера с {{status = "invalid"}} отображается с признаком ошибки, недоступна для нового drag-and-drop или выбора, а tooltip содержит человекочитаемую причину без показа сырого {{status_message}};
* *И:* отсутствующий или пустой массив {{measures}} для произвольного набора отображается как пустая секция без ошибки;
* *И:* для простого или составного набора данных секция *«Меры»* не отображается.

*AC.2* — Представление и настройка пилюли Меры:
* *Дано:* валидная Мера размещена на полке круговой диаграммы;
* *Когда:* пользователь просматривает пилюлю и открывает её настройки;
* *Тогда:* на *«Значениях»*, *«Категориях»* и *«Сериях»* пилюля имеет цвет {{#3491F7}}, а на *«Фильтрах»* — стандартный салатовый цвет;
* *И:* пилюля показывает актуальный {{alias}}, признак *«Мера»* и {{AGR}} для агрегированной Меры;
* *И:* локальная агрегация выражения Меры недоступна;
* *И:* на *«Значениях»* доступны типы *«Значение»*, *«Цвет»*, *«Подзаголовок»* и *«Подсказка»* по тем же правилам типов данных, что для вычисляемого поля.

*AC.3* — Полка «Значения» в режиме «Первое»:
* *Дано:* на полке размещено несколько объектов, включая Меры, и выбран режим *«Первое»*;
* *Когда:* диаграмма запрашивает данные;
* *Тогда:* в {{select}} передаётся только первое учитываемое размещение;
* *И:* остальные размещения и их настройки сохраняются, не влияют на диаграмму и не блокируют запрос, пока неактивны;
* *И:* если первым учитываемым размещением является Мера с {{aggregation_kind = 0}}, пользователь видит неблокирующее предупреждение, а построение не блокируется при корректном runtime payload.

*AC.4* — Полка «Значения» в режиме «Все»:
* *Дано:* на полке размещены обычные поля, вычисляемые поля и Меры разных типов;
* *Когда:* выбран режим *«Все»*;
* *Тогда:* все учитываемые размещения передаются в {{select}} в порядке полки с отдельными техническими alias;
* *И:* величины секторов определяет первое учитываемое размещение полки по действующему алгоритму круговой диаграммы;
* *И:* последующие размещения не создают дополнительную круговую диаграмму, кольцо или ряд;
* *И:* для неагрегированной Меры показывается неблокирующее предупреждение.

*AC.5* — Вспомогательные типы Меры:
* *Дано:* в режиме *«Все»* валидные Меры назначены типам *«Цвет»*, *«Подзаголовок»* и *«Подсказка»*;
* *Когда:* диаграмма построена;
* *Тогда:* результаты применяются соответственно в текущем цветовом канале, канале подзаголовка и всплывающей подсказке;
* *И:* каждый результат обрабатывается по правилам вычисляемого поля того же {{data_type}};
* *И:* ни одно вспомогательное размещение не используется как непосредственный источник величины сектора; SQL-влияние неагрегированного результата повторяет текущую логику вычисляемого поля;
* *И:* управление количеством сегментов и группа *«Прочее»* сохраняют действующий результат и согласованность вспомогательных данных с итоговыми секторами.

*AC.6* — Несколько размещений одной Меры:
* *Дано:* одна Мера размещена на полке *«Значения»* дважды, например как *«Значение»* и *«Подсказка»*;
* *Когда:* пользователь задаёт разные локальные настройки, сохраняет и повторно открывает диаграмму;
* *Тогда:* размещения имеют разные локальные {{id}}, независимые типы и настройки;
* *И:* оба размещения ссылаются по {{name}} на одно актуальное определение Меры текущего набора данных, а {{datasetId}} указывает контекст этого набора;
* *И:* результаты сопоставляются с правильными ролями без коллизии по {{name}}.

*AC.7* — Мера на полке «Категории»:
* *Дано:* на полке *«Категории»* размещена неагрегированная Мера;
* *Когда:* диаграмма запрашивает и отображает данные;
* *Тогда:* первое учитываемое размещение передаётся в {{group}} и {{select}} и формирует секторы, подписи и легенду по текущей логике категорий;
* *И:* попытка разместить агрегированную Меру блокируется с понятным сообщением.

*AC.8* — Мера на полке «Серии»:
* *Дано:* на полке *«Серии»* размещена неагрегированная Мера;
* *Когда:* серии включены;
* *Тогда:* активные размещения участвуют в группировке и отображении по тому же алгоритму, что вычисляемые поля, и передаются в {{group}} и {{select}};
* *Когда:* серии выключены;
* *Тогда:* размещения не передаются в {{group}}, {{select}} и {{order}}, не влияют на диаграмму и не блокируют запрос;
* *И:* агрегированная Мера недоступна для нового размещения в обоих режимах.

*AC.9* — Фильтр по Мере:
* *Дано:* пользователь настроил заполненное условие фильтра по Мере;
* *Когда:* {{aggregation_kind = 0}};
* *Тогда:* структурное условие передаётся в {{where}};
* *Когда:* {{aggregation_kind = 1}};
* *Тогда:* структурное условие передаётся в {{having.items}}, а {{having}} содержит {{condition}} и {{items}};
* *И:* несовместимый режим недоступен, отдельный {{value_type}} не передаётся, незаполненный фильтр не входит в runtime payload.

*AC.10* — Настройки и взаимодействие:
* *Дано:* категории, серии или значения круговой диаграммы сформированы Мерами;
* *Когда:* пользователь настраивает подписи данных, tooltip, легенду, стилизацию, режим фильтра, дрил или кнопку действия;
* *Тогда:* результат и контекст Меры доступны в подписях, tooltip, легенде, стилизации, режиме фильтра и дриле в каждом месте, где при той же конфигурации поддерживается вычисляемое поле;
* *И:* селектор конкретного объекта содержит допустимые активные размещения Мер по {{alias}} и связывает настройку с локальным {{id}};
* *И:* клик по сектору, выбор и снятие выбора сохраняют текущее поведение круговой диаграммы;
* *И:* настроенное действие, включая переход в другой отчёт, по-прежнему запускается специальной кнопкой в верхней полосе управления диаграммой.

*AC.11* — Сохранение, {{axesDefault}} и повторное открытие:
* *Дано:* Меры используются на нескольких полках и имеют локальные настройки;
* *Когда:* пользователь сохраняет, копирует, сбрасывает либо повторно открывает диаграмму;
* *Тогда:* {{axes}} и {{axesDefault}} обрабатывают ссылки и локальные настройки по действующему алгоритму без потери размещений;
* *И:* после проверки {{datasetId}} связь с определением Меры текущего набора восстанавливается по {{name}}, а экземпляры размещения различаются по локальному {{id}};
* *И:* поля определения Меры не используются как сохранённая копия источника истины.

*AC.12* — Изменение и ошибочная ссылка:
* *Дано:* {{alias}}, {{expression}}, {{aggregation_kind}} или {{status}} использованной Меры изменены;
* *Когда:* диаграмма получает актуальные метаданные;
* *Тогда:* новый {{alias}} отображается, новое {{expression}} используется следующим runtime-запросом, а совместимость размещения проверяется повторно;
* *И:* невалидная или несовместимая ссылка не подменяется по {{alias}} и не удаляется автоматически; активная проблемная ссылка блокирует построение с понятным сообщением, неактивная — сохраняется и не блокирует запрос;
* *И:* Мера со {{status = "invalid"}} недоступна для нового размещения или выбора.

*AC.13* — Канонический runtime-объект:
* *Дано:* активная Мера участвует в запросе круговой диаграммы;
* *Когда:* фронтенд формирует runtime payload;
* *Тогда:* объект содержит {{type = "measure"}}, {{name}} и требуемый технический {{alias}};
* *И:* все активные размещения включаются в единый запрос данных без отдельного запроса на каждую Меру;
* *И:* непустые {{calc}}, {{expression}}, {{agg}} и {{aggr}} не передаются как источник выражения Меры;
* *И:* один результат не дублируется в {{select}} из-за его одновременного использования в настройке отображения;
* *И:* при поддерживаемой сортировке в {{order}} передаются {{type = "measure"}}, {{name}} и направление;
* *И:* бэкенд раскрывает актуальное выражение Меры в SQL-контексте фактического runtime-блока.

*AC.14* — Мера в выражении вычисляемого поля:
* *Дано:* круговая диаграмма использует вычисляемое поле со ссылкой на валидную Меру текущего набора данных по {{name}} в двойных кавычках;
* *Когда:* выполняется запрос данных;
* *Тогда:* вычисляемое поле остаётся объектом с {{calc}}, бэкенд раскрывает актуальное {{expression}} Меры, а отдельный объект {{type = "measure"}} для вложенной ссылки не создаётся.
