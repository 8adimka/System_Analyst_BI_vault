h3. Интерфейс Мер в аналитическом портале
*Версия от 14.06.2026*

----
h3. 1. Терминология и модель данных Меры

В интерфейсе и контрактах Меры необходимо разделять два поля:

|| Поле || Назначение || Кто заполняет || Изменяемость ||
| {{alias}} | Человекочитаемое название Меры, которое пользователь видит в списках, таблицах, полках и подсказках. | Пользователь | Можно свободно изменять после создания, в том числе у используемой Меры. {{alias}} должен быть уникален в рамках одного набора данных; изменение {{alias}} не изменяет {{name}}. |
| {{name}} | Системное наименование Меры, которое используется для связей, выражений других Мер и вычисляемых полей, визуализаций и вставки в редактор. | Backend | Не меняется после создания Меры. |

Пример:

{code}
alias = "Дата отчёта"
name = "Мера.Дата_отчёта"
{code}

{{alias}} не является ключом связи. Переименование {{alias}} не должно ломать визуализации, выражения, фильтры и другие зависимости, так как все связи продолжают работать по {{name}}. Наличие зависимых объектов при изменении {{alias}} не проверяется и не блокирует сохранение.

{{name}} не вводится пользователем вручную. При создании Меры frontend обязательно передаёт на backend {{alias}}, {{expression}}, {{aggregation_kind}}, {{data_type}} и, при наличии, необязательные пользовательские параметры, а backend:
* валидирует обязательные поля и {{alias}};
* генерирует {{name}};
* сохраняет пользовательские поля и {{name}};
* возвращает frontend-у сохранённую Меру с итоговыми {{id}}, {{name}}, {{status}} и {{status_message}}.

Frontend не должен самостоятельно добавлять префикс {{Мера.}} и не должен самостоятельно формировать системное имя при вставке Меры в редактор. Для вставки используется готовое значение {{name}}, полученное от backend.

h4. 1.1. Правило генерации {{name}} при создании Меры

Backend формирует {{name}} по правилу:

{code}
name = "Мера." + alias, приведённый к формату системного имени
{code}

Правила преобразования:
* префикс {{Мера.}} добавляется всегда;
* пробелы в {{alias}} заменяются на подчёркивания;
* кириллица в {{name}} допускается;
* системное имя формируется в одно слово;
* {{name}} должно быть уникальным в рамках одного набора данных.

Примеры:

{code}
Алиас Меры (alias): Дата отчёта
Наименование меры (name): Мера.Дата_отчёта
{code}

{code}
Алиас Меры (alias): Валовая прибыль
Наименование меры (name): Мера.Валовая_прибыль
{code}

Если при генерации {{name}} кандидат уже занят в наборе данных, backend должен разрешить коллизию и сохранить уникальное системное имя. Допустимое целевое правило: backend добавляет к конфликтующему {{name}} детерминированный числовой суффикс, например {{_2}}, {{_3}}, и возвращает frontend-у итоговое значение {{name}}.

Пример коллизии:

{code}
candidate_name = "Мера.Дата_отчёта"  // уже занято в наборе данных
result_name = "Мера.Дата_отчёта_2"
{code}

h4. 1.2. Валидация {{alias}} Меры

В поле {{Алиас Меры}} разрешены только:
* буквы;
* цифры;
* пробел;
* знак подчёркивания.

Значение должно содержать хотя бы одну букву или цифру.

Не допускаются символы, которые могут ломать выражения или выглядеть как синтаксис формулы:
* кавычки;
* скобки;
* математические и логические операторы;
* спецсимволы.

Frontend должен не позволять ввод иных символов в поле {{Алиас Меры}}. Backend должен повторно валидировать {{alias}} при создании и редактировании Меры, так как backend является источником истины для сохранения Меры.

h3. 2. Интерфейс управления Мерами в настройках набора данных

h4. 2.1. Общая структура страницы

Страница настроек произвольного набора данных содержит две секции, расположенные одна за другой:
* *Секция «Поля»* — существующая таблица полей набора данных.
* *Секция «Меры»* — таблица Мер, располагается ниже секции полей.

*Скроллинг страницы:* внутренний скролл убирается. Используется единый внешний скролл страницы.

*Закреплённая область:* верхние две строки выбора источника данных и набора данных с кнопками управления закрепляются при скролле аналогично поведению в разделе «Отчёты». Содержимое под ними скроллится единым потоком.

*Унификация таблиц:* таблицы «Поля» и «Меры» должны быть максимально унифицированы по внешнему виду и поведению.

*Сортировка:* пользовательская сортировка по столбцам в таблице Мер не реализуется по аналогии с таблицей полей.

*Пагинация:* не реализуется.

*Видимость секции «Меры»:* секция отображается только для произвольного набора данных. Для простых и составных наборов данных секция «Меры» не отображается.

h4. 2.2. Таблица «Поля»

В таблице «Поля» первый столбец должен называться {{Наименование поля}}.

Порядок первых столбцов:
# {{Наименование поля}} — системное наименование поля.
# {{Алиас}} — человекочитаемое название поля.

Остальные существующие столбцы таблицы полей сохраняются без изменений, если они не затронуты данной доработкой.

h4. 2.3. Таблица «Меры»

Таблица «Меры» должна показывать и системное имя Меры, и человекочитаемый alias, так как пользователь видит {{alias}} в списках, но сталкивается с {{name}} при вставке Меры в редактор.

Отображаемые столбцы:

|| Наименование меры || Алиас || Тип данных || Агрегация || Выражение (кратко) || Иерархия || Уровень || Операции ||
| {{Мера.Дата_отчёта}} | {{Дата отчёта}} | {{date}} | AGR / — | первые N символов | {{<группа>}} | {{<порядок>}} | Редактировать / Удалить |

Описание столбцов:
* {{Наименование меры}} — системное значение {{name}}.
* {{Алиас}} — человекочитаемое значение {{alias}}.
* {{Агрегация}} — для {{aggregation_kind = 1}} отображается ярлык {{AGR}}, для {{aggregation_kind = 0}} отображается прочерк.
* {{Выражение}} — показываются первые N символов формулы; полный текст доступен в tooltip при наведении на ячейку.
* {{Операции}} — иконки редактирования и удаления. Копирование Мер в текущей итерации не реализуется.

Tooltip на строке Меры, кроме ячейки {{Выражение}}, отображает {{description}}, если описание заполнено.

Строка Меры с {{status = invalid}} подсвечивается как ошибочная. Поле {{status_message}} всегда присутствует в метаданных: на Шаге 1 оно равно пустой строке, а на Шаге 3 для {{invalid}} содержит структурный JSON с полями {{code}}, {{params}}, {{message}}. В tooltip frontend показывает локализованный текст по {{code}} + {{params}}, использует {{message}} только как fallback для неизвестного кода и не показывает сырой JSON.

Меры с заполненным полем {{hierarchy}} отображаются в соответствующей display-группе. Внутри группы применяется сортировка по {{level}}, затем по {{alias}}. Меры без иерархии отображаются в корневом уровне секции.

h4. 2.4. Кнопка «+ Добавить меру»

Кнопка активна только при одновременном выполнении условий:
* SQL-запрос набора данных задан и успешно прошёл проверку;
* состав полей набора данных получен.

В состоянии {{disabled}} отображается tooltip: {{Задайте и проверьте SQL-запрос набора данных}}.

h4. 2.5. Модальное окно создания и редактирования Меры

Заголовок модального окна:
* {{Создание меры}} — при создании;
* {{Редактирование меры}} — при редактировании.

Размер модального окна — увеличенный.

Верхняя часть формы имеет двухколоночную компоновку.

*Левый столбец — обязательные поля:*
* {{Алиас Меры}} ({{alias}}) — обязательное поле, заполняется пользователем.
* {{Тип данных}} ({{data_type}}) — обязательное поле из закрытого списка {{string}}, {{number}}, {{integer}}, {{date}}, {{datetime}}; frontend может предложить значение по умолчанию, пользователь может изменить. При создании frontend всегда передаёт выбранное значение, backend значение по умолчанию не подставляет.
* {{Агрегация}} ({{aggregation_kind}}) — обязательный переключатель {{да (1)}} / {{нет (0)}}.

*Правый столбец — необязательные поля:*
* {{Описание}} ({{description}}) — необязательная строка.

{{Наименование меры}} ({{name}}) при создании вручную не заполняется. При редактировании существующей Меры {{name}} может отображаться как справочное read-only значение, но не должен быть доступен для изменения.

При редактировании существующей Меры поле {{Алиас Меры}} всегда доступно для изменения, в том числе если Мера используется в визуализациях, выражениях других Мер или вычисляемых полях. Frontend не запрашивает зависимости и не блокирует поле; backend проверяет непустоту, допустимость символов и уникальность нового {{alias}} в наборе данных. Изменение {{alias}} не изменяет {{name}}.

Поля {{Иерархия}} и {{Уровень}} настраиваются в табличном представлении и не занимают место в модальном окне.

Поля {{id}}, {{status}}, {{status_message}} пользователем не заполняются и не отображаются как редактируемые поля. Эти поля управляются системой.

h4. 2.6. Редактор выражений в модальном окне Меры

Нижняя часть модального окна содержит редактор выражения и занимает максимально возможную высоту.

Редакторная зона состоит из:
* левой боковой панели со списками полей и Мер;
* верхней области с кнопками агрегатных функций;
* основной области редактора кода.

Левая боковая панель:
* начинается на уровне верхней границы редактора кода;
* содержит две сворачиваемые секции: {{Поля}} и {{Меры}};
* по умолчанию обе секции раскрыты;
* элементы списков доступны для вставки в редактор через drag-and-drop.

В списках полей и Мер отображается человекочитаемое название:
* для поля — {{alias}}, если он доступен, иначе {{name}};
* для Меры — {{alias}}.

При вставке поля или Меры в редактор через drag-and-drop или автокомплит вставляется системное наименование в двойных кавычках:
* для поля — {{name}} поля, например {{"report_date"}};
* для Меры — {{name}} Меры, например {{"Мера.Дата_отчёта"}}.

Меры вставляются как обычные поля в двойных кавычках. Квадратные скобки для ссылок на Меры не используются. Признак Меры определяется по префиксу {{Мера.}} в системном имени.

Те же правила применяются в редакторе вычисляемого поля виджета для текущего произвольного набора данных: валидные Меры доступны в списке и автокомплите по {{alias}}, а в выражение вставляется {{name}} Меры в двойных кавычках. Вычисляемое поле сохраняет зависимость от {{name}} Меры.

Синтаксис редактора должен поддерживать:
* подсветку системных имён полей и Мер в двойных кавычках;
* визуальное различение полей и Мер в автокомплите;
* подсветку синтаксических ошибок.

h4. 2.7. Drag-and-drop в редактор выражений

При перетаскивании поля в редактор:
* пользователь видит в боковой панели {{alias}}, если он доступен, иначе {{name}};
* в редактор вставляется системное имя поля в двойных кавычках.

Пример:

{code}
Пользователь видит: Дата отчёта
В редактор вставляется: "report_date"
{code}

При перетаскивании Меры в редактор:
* пользователь видит в боковой панели {{alias}};
* в редактор вставляется {{name}} Меры в двойных кавычках.

Пример:

{code}
Пользователь видит: Дата отчёта
В редактор вставляется: "Мера.Дата_отчёта"
{code}

h4. 2.8. Автокомплит в редакторе выражений

Автокомплит должен искать поля и Меры по логике {{OR}}:
* совпадение по {{alias}};
* совпадение по {{name}}.

В списке подсказок отображается {{alias}}, так как пользователь обычно работает с человекочитаемыми названиями. Если {{alias}} поля отсутствует, отображается {{name}} поля.

Значение, отображаемое в списке автокомплита, может отличаться от значения, вставляемого в редактор:
* отображается {{alias}};
* вставляется {{name}} в двойных кавычках.

Пример поиска по {{alias}}:

{code}
Пользователь вводит: Дата
Подсказки: Дата отчёта, Дата региона, Дата начала
После выбора Меры вставляется: "Мера.Дата_отчёта"
После выбора поля вставляется: "report_date"
{code}

Пример поиска по {{name}}:

{code}
Пользователь вводит: repor
Подсказка: Дата отчёта
После выбора поля вставляется: "report_date"
{code}

Если у поля и Меры одинаковый {{alias}}, автокомплит должен визуально различать тип сущности. Допустимые способы:
* иконка типа сущности;
* контрастная иконка Меры, например красная иконка Меры;
* текстовое пояснение типа, если возможности редактора ограничены.

h4. 2.9. Поведение при сохранении и редактировании

При создании Меры frontend обязательно отправляет на backend {{alias}}, {{expression}}, {{aggregation_kind}}, {{data_type}} и, при наличии, необязательные пользовательские параметры Меры. {{name}} не передаётся как пользовательский ввод.

После успешного создания backend возвращает {{alias}} и итоговое {{name}}. Frontend должен использовать возвращённое {{name}} во всех последующих ссылках и вставках в редактор.

При редактировании существующей Меры пользователь может изменить {{alias}}, {{description}}, {{expression}}, {{aggregation_kind}}, {{data_type}}, {{hierarchy}}, {{level}} в рамках доступных UI-настроек. Перед обновлением frontend получает актуальное состояние Меры из метаданных набора данных или через действующий {{get/list}}-контракт.

Изменение {{alias}} не изменяет {{name}} существующей Меры. Наличие зависимых объектов не проверяется и не блокирует изменение {{alias}}.

При отсутствии зависимостей frontend запрашивает подтверждение удаления. При успешном удалении backend возвращает актуальный массив {{measures}} без ключа {{deleted}}.

Если Мера используется в визуализации отчёта, в том числе в выражении вычисляемого поля виджета, или выражении другой Меры, backend возвращает {{HTTP 200}}, {{deleted = false}} и {{dependents}}; frontend определяет отказ по наличию ключа {{deleted}}, а не по длине {{dependents}}. Элементы {{dependents}} имеют два вида: {{usage_kind = "report"}} с полями {{Номер отчёта}}, {{Отчёт}}, {{Компонент}} и {{usage_kind = "measure"}} с полями {{id}}, {{object_name}}, {{alias}}, {{status}}. Для {{report}} поле {{Компонент}} содержит тип визуализации, а место использования Меры — ось, фильтр, сортировка или вычисляемое поле — не различается; поля {{object_type}} и {{link}} отсутствуют. Пользовательский текст frontend формирует сам; готовое сообщение backend не возвращает. Legacy-самоссылка удаляемой Меры удалению не препятствует.

При пересохранении SQL-запроса набора данных все Меры этого набора данных автоматически ревалидируются. Меры, ссылающиеся на пропавшие поля или невалидные Меры, получают {{status = invalid}} и становятся недоступны для размещения на полках визуализаций до исправления. При изменении статуса Меры все Меры и вычисляемые поля, зависящие от неё, также проходят ревалидацию.

h3. 3. Интерфейс Мер в боковой панели конструктора визуализаций

h4. 3.1. Структура панели полей

Боковая панель при выборе произвольного набора данных содержит две секции:
* {{Поля}} — обычные поля набора данных и вычисляемые поля виджета.
* {{Меры}} — Меры набора данных.

В секции {{Поля}} отображается {{alias}} поля, если он доступен, иначе {{name}} поля.

В секции {{Меры}} отображается {{alias}} Меры.

h4. 3.2. Отображение Мер в списке боковой панели

Для Мер с {{aggregation_kind = 1}} рядом с названием отображается ярлык {{AGR}}.

Tooltip при наведении на Меру содержит:
* {{description}}, если заполнено;
* {{data_type}};
* полный текст выражения;
* {{name}} Меры как справочную техническую информацию.

Меры с {{status = invalid}} отображаются с иконкой ошибки и недоступны для drag-and-drop. Tooltip по невалидной Мере показывает человекочитаемую причину, которую frontend формирует из {{code}} + {{params}} поля {{status_message}}; {{message}} используется только как fallback, сырой JSON не показывается.

Группировка выполняется по {{hierarchy}}, сортировка внутри группы — по {{level}}, затем по {{alias}}. Меры без иерархии отображаются в корне секции {{Меры}}.

h4. 3.3. Отображение Меры на полке визуализации

На полках визуализации Мера отображается по {{alias}}.

Цвет иконки или пилюли Меры — светло-синий (#3491F7), чтобы визуально отличать Меры от обычных полей.

Для Мер с {{aggregation_kind = 1}} на пилюле отображается ярлык {{AGR}}.

Меры с {{status = invalid}}, уже размещённые на полке, отображаются в error-состоянии. Привязка по {{name}} сохраняется. Backend отклоняет Меру со статусом, отличным от {{valid}}, во всех блоках runtime payload: {{select}}, {{where}}, {{group}}, {{having}}, {{order}}, и возвращает {{HTTP 400}}. Причина в runtime-ошибке уже человекочитаемая и формируется backend-ом; сообщение заканчивается указанием {{(блок SELECT)}}, {{(блок WHERE)}}, {{(блок GROUP BY)}}, {{(блок HAVING)}} или {{(блок ORDER BY)}} без завершающей точки.

h4. 3.4. Drag-and-drop и совместимые селекторы

Мера перетаскивается на полки аналогично обычному полю.

При попытке разместить Меру на несовместимую полку перетаскивание блокируется. Пользователь должен видеть причину блокировки.

Одна и та же Мера может быть размещена на нескольких полках одновременно.

Меры доступны во всех элементах интерфейса, где выбираются поля набора данных и где тип Меры совместим со сценарием: условное форматирование, настройки стилизации, сценарии расчётов по уровням и другие совместимые селекторы.

Во внутренних настройках визуализации сохраняется ссылка на Меру по {{name}}, а отображение для пользователя строится по {{alias}}, полученному из актуальных метаданных набора данных.

h4. 3.5. Полка «Фильтры»

Мера на полке {{Фильтры}} отображается по {{alias}} в виде пилюли фильтра.

При клике открывается окно настройки фильтра-Меры со следующими полями:
* {{filter.mode}}: {{WHERE}} или {{HAVING}};
* {{filter.values}}: непустой массив значений; {{null}} обозначает проверку пустого значения и допустим только в форме списка без {{filter.operators}};
* {{filter.operators}}: пустой массив для {{IN}} / {{NOT IN}} либо массив той же длины, что и {{filter.values}}, из allowlist {{=}}, {{!=}}, {{<>}}, {{>}}, {{>=}}, {{<}}, {{<=}}, {{like_*}} / {{likeic_*}};
* {{filter.not}}: отрицание условия;
* {{filter.logicOr}}: {{1}} — объединение условий через {{OR}}, иначе через {{AND}};
* дополнительные параметры, если они требуются конкретной визуализации.

Отдельный {{value_type}} в условии фильтра по Мере не передаётся: тип значения backend получает из {{data_type}} Меры.

При формировании runtime payload frontend помещает WHERE-фильтр по Мере в массив {{where}}, а HAVING-фильтр — в {{having.items}}. Поле {{having}} frontend всегда передаёт как объект с ключами {{condition}} и {{items}}; существующая строка {{having.condition}} для обычных или вычисляемых полей сохраняется и объединяется с элементами {{having.items}} через {{AND}}.

Правила валидации режима фильтра:
* неагрегированная Мера ({{aggregation_kind = 0}}) допускает только {{WHERE}}, выбор {{HAVING}} недоступен;
* агрегированная Мера ({{aggregation_kind = 1}}) допускает только {{HAVING}}, выбор {{WHERE}} недоступен.

h4. 3.6. Правила размещения Мер на полках

|| Полка || {{aggregation_kind = 0}} || {{aggregation_kind = 1}} ||
| Значения (SELECT) | Допускается, с предупреждением | Допускается |
| Фильтры WHERE | Допускается | Блокируется |
| Фильтры HAVING | Блокируется | Допускается |
| Строки / Столбцы / Детализация (GROUP BY) | Допускается | Блокируется |

h4. 3.7. Ярлык AGR

Ярлык {{AGR}} отображается только для {{aggregation_kind = 1}}.

Ярлык виден:
* в списке Мер набора данных;
* в боковой панели конструктора;
* на пилюлях Мер на полках.

Изменить {{aggregation_kind}} непосредственно на полке нельзя. Атрибут фиксируется в настройках Меры.
