| *Реестр Мер* | Будущая подсистема хранения переиспользуемых вычисляемых выражений на уровне источника данных (DataSource). Реализуется в следующих этапах. |

h3. 1. Введение и стратегический контекст

h4. 1.1. Бизнес-проблема

В текущей реализации Modus BI оператор {{HAVING}} применяется к иерархической сводной таблице *глобально* — либо ко всем уровням сразу, либо не применяется вовсе. Это делает невозможной корректную фильтрацию агрегатов по конкретному уровню иерархии.

*Пример проблемы:* аналитик хочет отобразить только *убыточные месяцы* ({{HAVING SUM(Profit) < 0}}). При текущем поведении система:
* либо отсекает *все* уровни, где сумма неотрицательна — включая прибыльные дни внутри убыточного месяца,
* либо оставляет убыточные месяцы в детализации, искажая итог года.

*Ключевое требование:* отсечение узла на целевом уровне (например, «Месяц») должно *физически исключать* все связанные строки фактов из расчётов как для родительских уровней («Год»), так и для дочерних («День»). Это принцип *математической консистентности* агрегаций.

h4. 1.2. Стратегическое видение — Этап 1 архитектуры «Мер»

В Roadmap продукта запланирован переход к *Семантическим Мерам* — переиспользуемым бизнес-выражениям, контекст вычисления которых определяется положением в отчёте (аналог {{CALCULATE}}/{{FILTER}} в Power BI DAX).

*Данная задача — Этап 1 этого перехода.* Мы создаём сущность *«Вычисляемое выражение с контекстом применения» (Proto-Measure)*, которая:
# Закрывает текущую проблему некорректной фильтрации агрегатов по уровням иерархии.
# Закладывает структуру метаданных ({{calculated_expressions}}), совместимую с будущим глобальным реестром Мер без изменения API.
# Внедряет в SQL-генератор механизм *двухпроходной агрегации (CTE + JOIN)* — архитектурный фундамент для полноценного контекста вычисления мер.

*Это самостоятельный, рабочий этап*, а не заглушка: он решает реальные пользовательские задачи и создаёт ценность уже сейчас.

h3. 2. Пользовательский интерфейс

h4. 2.1. Создание контекстного HAVING-фильтра (Proto-Measure)

*Локация:* Виджет «Сводная таблица» → полка «Фильтры» → добавление / редактирование «Вычисляемого поля».

*Шаг 1.* Аналитик вводит агрегирующее выражение (например, {{SUM("СуммаДоходРасходКО")}}).

*Шаг 2.* В пункте «Тип отбора» выбирает {{HAVING}}.
Поле «Тип отбора» содержит только два значения, которые видит пользователь: {{WHERE}} и {{HAVING}}. Исторические режимы (legacy) *не отображаются в UI*; их обработка полностью прозрачна для пользователя и описана в Разделе 6.

*Шаг 3.* При выборе {{HAVING}} под полем ввода формулы появляется блок *«Применять на уровнях детализации»* с переключателем (Radio buttons):
** *(•) Ко всем уровням* — поведение по умолчанию; сохраняет обратную совместимость. {{HAVING}} добавляется в запрос для каждого уровня иерархии по старому алгоритму.
** *( ) К выбранным уровням* — новый механизм Proto-Measure; активирует контекстную фильтрацию.

*Шаг 4.* При выборе «К выбранным уровням» разворачивается *динамический список чекбоксов*.
Список формируется на основе всех полей-измерений, размещённых на полках «Строки» и «Столбцы» данной сводной таблицы в момент открытия настроек.

Свойства списка:
* Отображаемые названия — пользовательские алиасы полей (при наличии), иначе технические идентификаторы.
* Порядок чекбоксов соответствует порядку полей в виджете.
* Допускается выбор нескольких чекбоксов одновременно.
* Tooltip при наведении на чекбокс: _«Мера будет вычисляться в разрезе данного измерения и каскадно применяться ко всем уровням иерархии через механизм CTE + JOIN»_.

*Шаг 5.* Аналитик расставляет галочки и нажимает «Сохранить». Система записывает конфигурацию в метаданные отчёта и инициирует перезапрос данных виджета.

h4. 2.2. Динамическое поведение списка чекбоксов

|| Событие || Поведение ||
| Пользователь добавляет новое измерение на полку | Новый чекбокс появляется в списке. Ранее выбранные чекбоксы *не сбрасываются*. |
| Пользователь меняет порядок измерений на полке | Порядок чекбоксов обновляется. Выбор сохраняется по техническому идентификатору поля. |
| Пользователь переименовывает поле («Месяц» → «Период») | В чекбоксе отображается новое название «Период». Привязка фильтра *не нарушается* (хранится технический ID). |
| Пользователь удаляет *нецелевое* измерение из полок | Соответствующий чекбокс исчезает. Состояние остальных чекбоксов не меняется. |
| Пользователь удаляет *единственное* целевое измерение (его ID входит в {{apply_to_dimensions}}) | Немедленно, без ожидания «Сохранить», отображается *Warning Toast*: _«Измерение "[Имя]" удалено из таблицы. Фильтр "[Имя фильтра]" переведён в режим "Ко всем уровням"»_. {{apply_mode}} автоматически переключается в {{all}}. Отчёт можно сохранить без ошибок. |
| Пользователь удаляет *одно из нескольких* целевых измерений | Чекбокс этого поля исчезает. Оставшиеся целевые измерения сохраняются. Warning не показывается. |
| Фильтр вынесен на *общую панель дашборда* | В режиме редактирования общей панели настройка «Применять для измерений» отображается информационным тегом (чипсой): _Применяется на: Месяц, Категория_ — без возможности редактирования непосредственно из панели. |

h3. 3. Модель данных и метаданные (Proto-Measure)

h4. 3.1. Архитектурное решение по хранению

Конфигурация Proto-Measure хранится в секции {{calculated_expressions}} *на уровне конкретного виджета* в метаданных отчёта. Это позволяет:
* Не затрагивать глобальную модель данных (DataSource) на данном этапе.
* В Этапе 2 (реестр Мер) перенести {{calculated_expressions}} на уровень DataSource без изменения структуры самого объекта и API.

h4. 3.2. Структура JSON

{code:json}
{
  "widgets": [
    {
      "id": "widget_abc123",
      "type": "pivot_table",
      "calculated_expressions": [
        {
          "id": "expr_4f6a8b2c",
          "name": "Прибыльные месяцы",
          "formula": "SUM(\"СуммаДоходРасходКО\")",
          "output_type": "numeric",
          "context_rules": {
            "evaluation_level": "aggregated",
            "apply_to_dimensions": ["col_month"],
            "condition": {
              "operator": ">",
              "value": 0,
              "value_type": "numeric"
            }
          }
        }
      ]
    }
  ]
}
{code}

h4. 3.3. Спецификация полей

|| Поле || Тип || Обязательное || Описание ||
| {{id}} | string (UUID) | Да | Уникальный стабильный идентификатор. Генерируется при создании. Не меняется при переименовании. |
| {{name}} | string | Да | Пользовательское название для отображения в UI панели фильтров. |
| {{formula}} | string | Да | Агрегирующее выражение на SQL-диалекте источника данных. Строка должна быть корректно экранирована. |
| {{output_type}} | enum | Да | {{numeric}}, {{string}}, {{date}}, {{boolean}}. Определяет тип UI-контрола на общей панели фильтров. |
| {{context_rules.evaluation_level}} | enum | Да | {{aggregated}} (HAVING) или {{row}} (WHERE — для совместимости). |
| {{context_rules.apply_to_dimensions}} | string[] | Да | Массив технических идентификаторов целевых полей. *Пустой массив {{[]}} = глобальное применение* (обратная совместимость с legacy HAVING). |
| {{context_rules.condition.operator}} | enum | Да | {{>}}, {{<}}, {{=}}, {{>=}}, {{<=}}, {{<>}}, {{BETWEEN}}, {{IN}}. |
| {{context_rules.condition.value}} | any | Да | Значение условия. Тип соответствует {{output_type}}. |

*Важно:* в {{apply_to_dimensions}} хранятся *технические идентификаторы* полей ({{col_month}}, {{col_year}}), а не пользовательские алиасы. Это обеспечивает устойчивость привязки при переименовании.

h3. 4. Backend-логика генерации SQL

h4. 4.1. Общий алгоритм — Decision Tree

Для каждого SQL-запроса к узлу дерева бэкенд определяет *Current Node Dimension (CND)*:

{code}
CND = widget.all_dimensions[ node_context.depth ]
// widget.all_dimensions — упорядоченный массив измерений виджета из метаданных
// node_context.depth — глубина текущего узла (0, 1, 2 ...)
{code}

Пример для иерархии Год → Месяц → День:

{code}
widget.all_dimensions = ['col_year', 'col_month', 'col_day']

depth=0 → CND='col_year'   // запрос для уровня "Год"
depth=1 → CND='col_month'  // запрос для уровня "Месяц" внутри Года
depth=2 → CND='col_day'    // запрос для уровня "День" внутри Месяца
{code}

Определение CND происходит *исключительно из метаданных*, а не из парсинга SQL-текста — это обеспечивает совместимость с {{GROUP BY}}, {{GROUPING SETS}}, {{ROLLUP}} и {{CUBE}}.

Для каждой Proto-Measure с {{apply_to_dimensions != []}} выполняется алгоритм:

{code}
apply_proto_measure(query_context, measure):

  if measure.apply_to_dimensions is empty:
    → Case 0: Глобальная мера. Прямой HAVING (обратная совместимость).

  CND = widget.all_dimensions[ query_context.depth ]
  CND_depth = query_context.depth
  target_depths = [ indexOf(d, widget.all_dimensions) for d in measure.apply_to_dimensions ]
  min_target_depth = min(target_depths)

  if CND in measure.apply_to_dimensions:
    → Case 1: Запрос на целевом уровне. Прямой HAVING. (Раздел 4.2)

  if CND_depth < min_target_depth:
    → Case 2: Запрос ВЫШЕ целевого уровня. Двухпроходная агрегация CTE + JOIN. (Раздел 4.3)

  if CND_depth > все target_depths:
    → Case 3: Запрос НИЖЕ целевого уровня. HAVING не инжектируется. (Раздел 4.4)
{code}

h4. 4.2. Case 1 — Запрос на целевом уровне (прямой HAVING)

Применяется когда {{CND ∈ apply_to_dimensions}}. Стандартная прямая инъекция {{HAVING}} в конец запроса.

{code:sql}
-- Пример: запрошен уровень "Месяц", мера настроена на "Месяц"
-- Контекст: раскрытие узла "Год = 2025"

SELECT
    t.col_month,
    SUM(t.Revenue) AS TotalRevenue
FROM base_dataset t
WHERE t.col_year = 2025            -- Контекстный фильтр родительского узла
  AND <глобальные_where_фильтры>
GROUP BY t.col_month
HAVING SUM(t.Revenue) > 0          -- Прямая инъекция Proto-Measure
{code}

h4. 4.3. Case 2 — Запрос ВЫШЕ целевого уровня (двухпроходная агрегация)

Применяется когда текущий узел находится *выше* целевого уровня меры (например, запрошен «Год», мера настроена на «Месяц»). Требуется CTE + INNER JOIN.

*Критически важно (Predicate Pushdown):* все {{WHERE}}-условия текущего контекста (глобальные фильтры дашборда, фильтры раскрытого родительского узла) *обязательно* пробрасываются внутрь каждого CTE, чтобы избежать полного сканирования таблицы фактов.

{code:sql}
-- Пример: запрошен уровень "Год", мера настроена на "Месяц"
-- Условие: SUM(Revenue) > 0
-- Контекст: глобальный фильтр по дате

WITH
-- Шаг 1: Базовые данные с учётом ВСЕХ контекстных фильтров
BaseData AS (
    SELECT
        col_year,
        col_month,
        col_day,
        Revenue
    FROM base_dataset
    WHERE <глобальные_where_фильтры>   -- Predicate Pushdown (обязателен)
),

-- Шаг 2: Агрегация на ЦЕЛЕВОМ уровне меры с применением условия HAVING
TargetLevelFilter AS (
    SELECT
        col_year,    -- Все измерения иерархии выше целевого — для правильного JOIN
        col_month,   -- Целевое измерение
        SUM(Revenue) AS MonthTotal
    FROM BaseData
    GROUP BY col_year, col_month
    HAVING SUM(Revenue) > 0    -- Условие Proto-Measure
),

-- Шаг 3: Уникальные ключи родительского уровня, прошедшие фильтр
ValidParentKeys AS (
    SELECT DISTINCT col_year
    FROM TargetLevelFilter
)

-- Шаг 4: Финальная агрегация на ЗАПРОШЕННОМ уровне (Год)
SELECT
    b.col_year,
    SUM(b.Revenue) AS TotalRevenue
FROM BaseData b
INNER JOIN ValidParentKeys v ON b.col_year = v.col_year
GROUP BY b.col_year
{code}

*Почему это обеспечивает математическую консистентность:*
* Строки Февраля (убыточного месяца) не попали в {{ValidParentKeys}} через {{TargetLevelFilter}}.
* {{INNER JOIN}} физически исключает строки Февраля из {{BaseData}} *до агрегации*.
* Итог по «Году» рассчитывается только на основе данных прибыльных месяцев → сумма года математически точна.
* При раскрытии «Года» запрос уровня «Месяц» выполняется по Case 1 и вернёт только Январь.
* При раскрытии «Января» запрос уровня «День» выполняется по Case 3 (без {{HAVING}}) и вернёт все дни Января.

h4. 4.4. Case 3 — Запрос НИЖЕ целевого уровня (без HAVING)

Применяется когда текущий узел находится *ниже* всех целевых уровней меры (например, запрошены «Дни» внутри конкретного месяца, а мера настроена на «Месяц»).

*HAVING не инжектируется и CTE не строится.* Решение об отсечении узла уже было принято на уровне «Месяц» (Case 1). Дни убыточных месяцев не будут запрошены, так как их родительский узел физически не возвращён на предыдущем уровне — кнопка «+» для него не отображается. Это каскадное отсечение является естественным следствием навигационной логики.

h4. 4.5. Несколько Proto-Measures в одном виджете

Если виджет содержит несколько Proto-Measures, алгоритм из Раздела 4.1 выполняется для *каждой независимо*. Затем:

* *Case 1 + Case 1 (несколько прямых HAVING):* условия объединяются через {{AND}} в секции {{HAVING}} единственного запроса.
* *Case 2 (несколько CTE):* для каждой меры формируется отдельный CTE. Основной запрос последовательно присоединяет их через {{INNER JOIN}}:

{code:sql}
WITH
BaseData AS ( ... ),

-- CTE для первой меры (например, по Месяцу)
Filter_Measure_1 AS (
    SELECT DISTINCT col_year
    FROM (
        SELECT col_year, col_month, SUM(Revenue) AS m
        FROM BaseData GROUP BY col_year, col_month
        HAVING SUM(Revenue) > 0
    ) t
),

-- CTE для второй меры (например, по Категории)
Filter_Measure_2 AS (
    SELECT DISTINCT col_year
    FROM (
        SELECT col_year, col_category, COUNT(*) AS cnt
        FROM BaseData GROUP BY col_year, col_category
        HAVING COUNT(*) >= 5
    ) t
)

SELECT b.col_year, SUM(b.Revenue) AS Total
FROM BaseData b
INNER JOIN Filter_Measure_1 f1 ON b.col_year = f1.col_year
INNER JOIN Filter_Measure_2 f2 ON b.col_year = f2.col_year
GROUP BY b.col_year
{code}

Семантика: виджет отображает только те строки, которые удовлетворяют *всем* активным мерам одновременно (пересечение, AND-логика).

h4. 4.6. Мультивыбор измерений (несколько полей в {{apply_to_dimensions}})

Если {{apply_to_dimensions = ["col_month", "col_category"]}}, фильтр применяется к *каждой уникальной комбинации* выбранных измерений:

* В {{TargetLevelFilter}}: {{GROUP BY col_year, col_month, col_category}}
* В {{ValidParentKeys}}: {{SELECT DISTINCT col_year}}
* В основном {{JOIN}}: фильтрация происходит через тот же механизм — строки, где *комбинация* (col_month, col_category) не прошла HAVING, физически исключаются из агрегации.

h4. 4.7. Алгоритм для плоской таблицы

Плоская таблица не имеет иерархического дерева запросов — для неё всегда генерируется *один* SQL-запрос. Понятие {{depth}} / CND к ней *не применяется*.

{code}
inject_for_flat_table(measure, widget_context):

  has_aggregation = в метаданных виджета есть поля с агрегатными
                    функциями (SUM, COUNT, AVG и т.д.) на полке «Значения»?

  Если has_aggregation = TRUE:
    → Движок применяет Case 1 (прямой HAVING).
    → apply_to_dimensions игнорируется — для плоской таблицы нет иерархии уровней.

  Если has_aggregation = FALSE:
    → HAVING безопасно игнорируется.
    → SQL-ошибка не возникает. Пользователю уведомление не показывается.
{code}

h3. 5. Интеграция с общей панелью фильтров

h4. 5.1. Передача конфигурации

Полная конфигурация Proto-Measure ({{formula}}, {{output_type}}, {{context_rules}}) передаётся в API всех связанных виджетов. Каждый виджет применяет алгоритм из Раздела 4 самостоятельно, используя *собственные* метаданные ({{widget.all_dimensions}}).

h4. 5.2. Правила применения к связанным виджетам

|| Тип связанного виджета || Поведение ||
| Сводная таблица, содержащая поле из {{apply_to_dimensions}} | Применяется алгоритм из Раздела 4 (Case 1, 2, 3 в зависимости от запрашиваемого уровня). |
| Плоская таблица с агрегатными функциями | Применяется прямой HAVING (Case 1) по алгоритму Раздела 4.7. |
| Виджет *без* полей из {{apply_to_dimensions}} (диаграмма по Категориям, когда мера настроена на Месяц) | HAVING *безопасно игнорируется*. SQL-ошибка не возникает. На панели фильтров рядом с названием фильтра отображается иконка *(i)* с тултипом: _«Применяется только к виджетам, содержащим измерения: [Названия полей]»_. |
| Плоская таблица *без* агрегатных функций | HAVING безопасно игнорируется. Уведомления нет. |

h4. 5.3. Режим {{apply_to_dimensions: []}} в общей панели

Мера с пустым массивом передаётся как стандартный глобальный {{HAVING}} (обратная совместимость). Правила Разделов 5.2 и 4.7 применяются в полном объёме.

h3. 6. Миграция и обратная совместимость

h4. 6.1. Существующие вычисляемые фильтры типа HAVING

Существующие отчёты с вычисляемыми полями типа {{HAVING}} (в том числе с использованием {{!ROW_LEVEL!}}) *продолжают работать без изменений*.

При загрузке отчёта бэкенд применяет следующее правило:

|| Категория || Правило ||
| Вычисляемый фильтр с {{HAVING}} без поля {{context_rules}} | Автоматически интерпретируется как Proto-Measure с {{apply_to_dimensions: []}} (глобальное применение). SQL генерируется по старому алгоритму (Case 0). |
| Переменная {{!ROW_LEVEL!}} | Продолжает работать без изменений. В UI при создании *нового* вычисляемого поля помечается как _(Deprecated)_ с подсказкой: _«Для выбора уровня агрегации используйте блок "Применять на уровнях детализации"»_. |

Явная миграция метаданных существующих отчётов *не требуется*.

h4. 6.2. Исправление выявленных дефектов

*Дефект 1: Невозможность редактирования сохранённого вычисляемого фильтра.*

_Описание:_ при открытии ранее сохранённого вычисляемого фильтра (тип {{HAVING}}), изменении формулы или условия и нажатии «Сохранить» — новые значения не применяются. Виджет продолжает использовать старую конфигурацию. Единственный обходной путь — удалить фильтр и создать заново.

_Требование:_ обеспечить корректное обновление state виджета при изменении параметров Proto-Measure. После нажатия «Сохранить» виджет должен инициировать перезапрос данных с актуальной конфигурацией *без* необходимости удаления и пересоздания фильтра.

----

*Дефект 2: Несоответствие типа элемента управления на общей панели фильтров.*

_Описание:_ в настройках правой боковой панели вычисляемый {{HAVING}}-фильтр обозначается как «по диапазону», однако в режиме использования отрисовывается как «список выбора».

_Требование:_ тип UI-контрола на панели фильтров должен строго соответствовать полю {{output_type}} Proto-Measure:

|| output_type || UI-контрол ||
| {{numeric}} | Слайдер / поле ввода диапазона |
| {{string}} | Выпадающий список / мультиселект |
| {{date}} | Календарь / выбор периода |
| {{boolean}} | Чекбокс |

----
h3. 7. Требования к производительности

|| Требование || Критерий ||
| *Predicate Pushdown* | Все {{WHERE}}-условия контекста (глобальные фильтры, фильтры раскрытого узла) *обязательно* пробрасываются внутрь каждого CTE. |
| *Отсутствие полного сканирования* | При запросе детализации конкретного узла (например, раскрытие «Год = 2025») CTE не сканирует данные за другие годы. |
| *Время выполнения* | Запрос с активной Proto-Measure не должен превышать аналогичный запрос без меры более чем на *20%* (при прочих равных условиях). |
| *Индексы* | CTE должны использовать существующие индексы и партиции таблиц фактов. |

----
h3. 8. Критерии приёмки (Acceptance Criteria)

h4. AC-1 — Создание Proto-Measure через UI

*Given:* аналитик редактирует сводную таблицу.
*When:* добавляет вычисляемое поле на полку «Фильтры», вводит агрегирующую формулу, выбирает «Тип отбора: HAVING», затем переключатель «К выбранным уровням» и расставляет чекбоксы.
*Then:* при нажатии «Сохранить» в JSON-метаданных виджета создаётся объект в секции {{calculated_expressions}} с корректно заполненным массивом {{apply_to_dimensions}}, содержащим технические ID выбранных полей.

h4. AC-2 — Математическая консистентность агрегаций *(Критический)*

*Given:* иерархия «Год → Месяц → День». Proto-Measure {{SUM(Profit) > 0}} настроена на уровень «Месяц». Данные: 2025 год → Январь (Profit +100), Февраль (Profit −50).
*When:* отчёт построен по «Годам».
*Then:*
# В строке «2025 год» значение Profit = *100* (Февраль физически исключён из суммы).
# При раскрытии «2025 год» отображается *только Январь* — строка Февраля отсутствует.
# При раскрытии «Январь» отображаются все его дни. Дни Февраля в отчёте *не фигурируют*.

h4. AC-3 — Case 1: прямой HAVING на целевом уровне

*Given:* иерархия «Год → Месяц». Proto-Measure настроена на уровень «Месяц».
*When:* выполняется запрос для узлов «Месяц» (раскрытие конкретного года).
*Then:* генерируется SQL с *прямым {{HAVING}}* в конце запроса, без CTE и JOIN. Факт отсутствия CTE проверяется через логи запросов или {{EXPLAIN}}.

h4. AC-4 — Case 2: CTE + JOIN при запросе выше целевого уровня

*Given:* иерархия «Год → Месяц → День». Proto-Measure настроена на уровень «Месяц».
*When:* выполняется запрос для уровня «Год».
*Then:* генерируется SQL с CTE {{TargetLevelFilter}} (GROUP BY col_year, col_month + HAVING) и последующим {{INNER JOIN}} к основному запросу. Условия контекста (WHERE) присутствуют *внутри CTE* (Predicate Pushdown).

h4. AC-5 — Case 3: HAVING не применяется ниже целевого уровня

*Given:* те же условия. Мера на уровне «Месяц».
*When:* выполняется запрос для уровня «День» (раскрытие конкретного месяца).
*Then:* генерируется SQL *без* {{HAVING}} и *без* CTE. Запрос возвращает все дни внутри данного месяца.

h4. AC-6 — Предикатный пушдаун (Predicate Pushdown)

*Given:* таблица фактов на 100+ млн строк. Пользователь раскрыл узел «Год = 2025».
*When:* выполняется запрос уровня «Месяц» (Case 2 или Case 1).
*Then:* {{WHERE col_year = 2025}} применяется *как к основному запросу, так и внутри CTE*. База данных не сканирует строки за другие годы (проверяется через {{EXPLAIN ANALYZE}}).

h4. AC-7 — Динамический список чекбоксов

*Given:* сводная таблица с иерархией «Год → Месяц → День».
*When:* аналитик открывает настройки Proto-Measure и выбирает «К выбранным уровням».
*Then:* список содержит три чекбокса («Год», «Месяц», «День») в порядке иерархии. При добавлении нового измерения в виджет — новый чекбокс появляется. При переименовании поля — название чекбокса обновляется. Ранее выбранные чекбоксы *не сбрасываются* при перестроении виджета.

h4. AC-8 — Предупреждение при удалении единственного целевого измерения

*Given:* Proto-Measure привязана только к полю «Месяц» ({{apply_to_dimensions: ["col_month"]}}).
*When:* аналитик удаляет поле «Месяц» из полок виджета.
*Then:* *немедленно* (без ожидания «Сохранить») отображается Warning Toast: _«Измерение "Месяц" удалено из таблицы. Фильтр "[Имя]" переведён в режим "Ко всем уровням"»_. {{apply_to_dimensions}} автоматически переключается в {{[]}}. Виджет продолжает корректно работать.

h4. AC-9 — Устойчивость к переименованию поля

*Given:* Proto-Measure сохранена с привязкой к полю {{col_month}} (алиас «Месяц»).
*When:* аналитик переименовывает поле в «Период».
*Then:* фильтр продолжает применяться к тому же полю. В UI настроек фильтра отображается новое название «Период».

h4. AC-10 — Мультивыбор целевых измерений

*Given:* {{apply_to_dimensions: ["col_month", "col_category"]}}.
*When:* выполняется запрос уровня «Год» (Case 2).
*Then:* CTE содержит {{GROUP BY col_year, col_month, col_category}}. {{INNER JOIN}} выполняется по ключу {{col_year}}, извлечённому из комбинаций (month, category), прошедших HAVING.

h4. AC-11 — Несколько Proto-Measures: AND-логика

*Given:* виджет содержит две Proto-Measures: M1 (на уровень «Месяц», SUM(Revenue) > 0) и M2 (на уровень «Месяц», COUNT(Orders) >= 5).
*When:* выполняется запрос уровня «Год» (Case 2 для обоих).
*Then:* генерируются два независимых CTE ({{Filter_M1}}, {{Filter_M2}}). Основной запрос присоединяет оба через {{INNER JOIN}}. В итоге остаются только годы, где есть месяцы, одновременно удовлетворяющие *обоим* условиям.

h4. AC-12 — Безопасное игнорирование на несвязанных виджетах

*Given:* общая панель фильтров содержит Proto-Measure, настроенную на «Месяц».
*When:* пользователь просматривает виджет «Столбчатая диаграмма по Категориям» (поле «Месяц» в виджете отсутствует).
*Then:* данные диаграммы *не фильтруются*. SQL-ошибка не возникает. На панели фильтров рядом с названием меры отображается иконка *(i)* с тултипом: _«Применяется только к виджетам, содержащим измерения: Месяц»_.

h4. AC-13 — Обратная совместимость (legacy HAVING)

*Given:* существующий отчёт с вычисляемым полем типа {{HAVING}} без поля {{context_rules}} в метаданных.
*When:* отчёт открывается и выполняется запрос.
*Then:* поведение *не изменяется*. Генерируется SQL с прямой инъекцией {{HAVING}} в конец запроса. Явной миграции метаданных не требуется.

h4. AC-14 — Исправление дефекта: редактирование сохранённого фильтра

*Given:* сохранённый вычисляемый фильтр (тип HAVING).
*When:* пользователь открывает его, изменяет формулу или условие, нажимает «Сохранить».
*Then:* виджет применяет *новые* настройки и инициирует перезапрос данных без необходимости удаления и пересоздания фильтра.

h4. AC-15 — Исправление дефекта: тип контрола на общей панели фильтров

*Given:* Proto-Measure с {{output_type: "numeric"}} добавлена в общую панель дашборда.
*When:* пользователь открывает панель фильтров в режиме просмотра.
*Then:* фильтр отображается как *слайдер / поле ввода диапазона* (numeric), а не как список выбора.
