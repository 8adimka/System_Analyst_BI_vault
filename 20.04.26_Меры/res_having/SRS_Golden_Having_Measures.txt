Внедрение контекстно-зависимой фильтрации агрегатов (HAVING) как подготовка к архитектуре «Мер»

----
h3. 1. Введение и стратегический контекст

h4. 1.1. Бизнес-проблема
В текущей реализации аналитики не могут корректно отфильтровать агрегированные данные по конкретному уровню иерархии, не исказив общие итоги. Если отсечь "убыточные месяцы", система либо удаляет их только визуально (оставляя в сумме года), либо ломает отображение дней. 
Ключевое требование бизнеса — *математическая консистентность*: если мы отфильтровали узел на уровне Месяца, все строки фактов, принадлежащие этому узлу, должны быть физически исключены из расчетов как для родительского (Год), так и для дочернего (День) уровней.

h4. 1.2. Стратегическое видение (Proto-Measures)
Мы создаем сущность «Вычисляемое выражение с контекстом применения» (Proto-Measure). Эта доработка решает проблему {{HAVING}} прямо сейчас и формирует SQL-движок для будущего полноценного семантического слоя "Мер" (LOD-выражений типа CALCULATE/FIXED).

----
h3. 2. Пользовательский интерфейс (UI/UX)

h4. 2.1. Настройка контекстного фильтра
*Локация:* Виджет «Сводная таблица», полка «Фильтры», режим редактирования вычисляемого поля.
* *Шаг 1:* Пользователь вводит агрегирующее выражение (напр., {{SUM("Revenue")}}).
* *Шаг 2:* В списке «Тип отбора» выбирает {{HAVING}}.
* *Шаг 3:* Появляется блок *«Применять на уровнях детализации»* с переключателем:
** (•) *Ко всем уровням* — классическое поведение (обратная совместимость).
** ( ) *К выбранным уровням (Контекстная мера)* — новый LOD-механизм.
* *Шаг 4:* При выборе второго варианта появляется список чекбоксов со всеми полями, вынесенными в Строки/Колонки виджета (названия берутся из алиасов полей). 

*Валидация и UX:*
* При переименовании полей в виджете, привязка в фильтре сохраняется.
* Если целевое измерение удалено из виджета, система выводит Warning: _«Целевое измерение [Имя] отсутствует. Фильтр переведен в режим "Ко всем уровням"»_.

----
h3. 3. Модель данных и метаданные (Proto-Measures)

Чтобы заложить фундамент для «Мер», мы обновляем структуру метаданных фильтра, но *оставляем её в скоупе виджета* (или дашборда), чтобы не создавать мусор в глобальном DataSource до внедрения полноценного реестра.

Новая структура JSON (Proto-Measure) внутри массива фильтров виджета:
{code:json}
{
  "id": "proto_measure_123",
  "type": "calculated",
  "filter_mode": "HAVING",
  "expression": "SUM("Revenue")",
  "condition": "> 1000",
  "context_rules": {
    "apply_mode": "selected",
    "target_dimensions": ["col_month", "col_category"] 
  }
}
{code}
*Важно:* В {{target_dimensions}} хранятся строго технические идентификаторы полей. При мультивыборе (выбрано несколько чекбоксов) фильтр применяется к уникальным комбинациям этих измерений.

----
h3. 4. Архитектура и Backend-логика SQL-генерации

Используется алгоритм фильтрации базового набора данных через *CTE + INNER JOIN*. 

h4. 4.1. Алгоритм генерации (Decision Tree)
Для каждого запроса к БД (неважно, запрашиваем мы Год, Месяц или День), если в виджете есть Proto-Measure с {{apply_mode = "selected"}}:

*Шаг 1. Проверка применимости.*
Если в текущем виджете *отсутствуют* поля, указанные в {{target_dimensions}}, фильтр безопасно игнорируется (в общей панели фильтров выводится иконка (i) "Не применимо к текущему виджету").

*Шаг 2. Генерация фильтрующего CTE.*
Бэкенд формирует подзапрос, который группирует данные строго по {{target_dimensions}} и фильтрует их через {{HAVING}}.
*КРИТИЧЕСКИ ВАЖНО (Предикатный пушдаун):* Чтобы избежать full-table scan, в CTE *обязательно* пробрасываются все текущие глобальные {{WHERE}}-фильтры и фильтры раскрытого узла!

*Шаг 3. Инъекция в основной запрос.*
Основной запрос связывается с CTE через {{INNER JOIN}} по ключам {{target_dimensions}}.

h4. 4.2. Пример SQL при раскрытии дочернего узла (Узел: Год=2025 -> Запрашиваем: Месяцы)
{code:sql}
WITH 
-- 1. Вычисляем разрешенные комбинации целевых измерений
-- (Сюда проброшен WHERE из контекста раскрытия для производительности)
FilterCTE AS (
    SELECT col_month
    FROM base_dataset
    WHERE col_year = 2025 -- Context Pushdown (важно для скорости!)
    GROUP BY col_month
    HAVING SUM(Revenue) > 1000
)

-- 2. Основной запрос (строится поверх отфильтрованной базы)
SELECT 
    t.col_month,
    SUM(t.Revenue) as Total
FROM base_dataset t
-- 3. Магический JOIN, исключающий "грязные" данные
INNER JOIN FilterCTE f 
    ON t.col_month = f.col_month
WHERE t.col_year = 2025
GROUP BY t.col_month
{code}

*Почему это работает идеально:*
* При запросе "Года" убыточные месяцы будут отсечены до агрегации года. Итог года будет математически точным.
* При запросе "Дней" убыточные месяцы уже отсечены. Дни из убыточных месяцев просто не попадут в выборку.
* Производительность высока, так как текущий фильтр (например, клик по конкретному году) пробрасывается внутрь CTE.

h4. 4.3. Обработка мультивыбора
Если {{target_dimensions = ["col_month", "col_category"]}}, то:
* В CTE: {{GROUP BY col_month, col_category}}
* В JOIN: {{ON t.col_month = f.col_month AND t.col_category = f.col_category}}

----
h3. 5. Критерии приёмки (Acceptance Criteria)

h4. AC-1: UI и сохранение метаданных (Proto-Measure)
При настройке вычисляемого HAVING-фильтра доступен выбор конкретных уровней (чекбоксы). При сохранении формируется JSON структура с блоком {{context_rules.target_dimensions}}, содержащим массив ID выбранных полей.

h4. AC-2: Математическая консистентность агрегаций (Критический)
*Дано:* Иерархия "Год -> Месяц -> День". Фильтр {{HAVING SUM(Profit) > 0}} применен к уровню "Месяц". Данные за 2025: Январь (Profit +100), Февраль (Profit -50).
*Тогда:* 
1. В строке "2025 год" сумма Profit равна ровно 100 (Февраль физически исключен из суммы).
2. При раскрытии "2025 год" отображается только Январь.
3. При раскрытии "Января" отображаются его дни. Дни февраля в отчете не фигурируют.

h4. AC-3: Оптимизация производительности (Predicate Pushdown)
При раскрытии конкретного родительского узла (например, клик на "2025 год"), фильтр {{WHERE col_year = 2025}} применяется *как к основному запросу, так и внутрь фильтрующего CTE*. База данных не должна сканировать всю таблицу фактов, если запрошена детализация конкретного узла.

h4. AC-4: Безопасное игнорирование (Коллизия контекстов)
Если вычисляемый фильтр вынесен на общую панель дашборда и применяется к виджету, в котором нет целевых полей (например, к графику по "Менеджерам", а мера настроена на "Месяц") — фильтр безопасно игнорируется для данного виджета. Ошибок SQL не возникает. На панели фильтров отображается тултип с предупреждением.

h4. AC-5: Мультивыбор измерений
Если аналитик выбрал в чекбоксах два измерения (Месяц и Категория), система корректно строит CTE с группировкой по обоим полям и выполняет INNER JOIN по составному ключу (AND).

h4. AC-6: Обратная совместимость
Существующие вычисляемые поля типа HAVING продолжают работу по старому алгоритму (простая инъекция в конец запроса). В их JSON-конфигурации устанавливается {{apply_mode: "all"}}.
