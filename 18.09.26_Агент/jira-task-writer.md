# Скилл: Постановка задачи для JIRA (Modus BI)

## 1. Когда применять

Применяй этот скилл при любом из следующих запросов:

- «напиши постановку»;
- «оформи задачу / тикет»;
- «сделай тикет в JIRA»;
- «распиши баг»;
- «сформулируй требования»;
- «напиши историю»;
- или когда пользователь описывает проблему / идею / жалобу / результат встречи и ожидает структурированный текст для JIRA.

---

## 2. Алгоритм подготовки постановки

### 2.1. Шаг 1 — Определи тип задачи

Выбери одно из:

| Тип задачи | Признаки |
|---|---|
| Баг | Что-то работает не так, как ожидается; есть шаги воспроизведения |
| Регрессионное исправление | Баг появился после последнего релиза / изменения |
| Продуктовая доработка | Новая возможность или улучшение UX по инициативе продукта или пользователей |
| Техническая доработка | Рефакторинг, оптимизация, технический долг |
| Архитектурное расширение | Новый компонент, слой или механизм |
| Интеграция источника данных | Новый тип подключения, драйвер, SQL-диалект |
| Изменение фильтрации | Логика фильтров, общая панель фильтров, иерархические фильтры |
| Изменение SQL-генерации | Изменение формирования WHERE / HAVING / GROUP BY / JOIN |
| Изменение поведения визуализации | Диаграммы, сводные таблицы, клики, подсветка |
| Изменение метаданных | Схема, поля, типы, alias, бизнес-ключи |
| Изменение интерфейса | UI-компоненты, настройки отображения, конструктор ФВД |

### 2.2. Шаг 2 — Восстанови полную картину

Из сырого описания извлеки или предположи:

- **Кто** — роль пользователя: аналитик, разработчик, администратор, конечный пользователь;
- **Где** — компонент / модуль: ETL, основной портал, ФВД, конструктор отчётов, конкретная визуализация, сводная таблица, фильтр, набор данных, источник данных;
- **Что сейчас** — текущее поведение системы (не то, чего хотят, а то, что есть);
- **Что ожидается** — целевое поведение после доработки;
- **Почему важно** — бизнес-ценность, влияние на пользователей или аналитиков;
- **Как воспроизвести** — для багов: конкретные шаги;
- **Какие объекты затронуты** — в терминах API: connection, datasource, dataset, report, forms, extraction_rule и т.д.;
- **Что может сломаться** — смежные механизмы, старые отчёты, обратная совместимость.

### 2.3. Шаг 3 — Напиши постановку

Используй базовую структуру ниже. Адаптируй под тип задачи: упрощай для мелких задач, расширяй для архитектурных.

---

## 3. Базовая структура постановки (JIRA wiki-разметка)

```
h3. Контекст и проблематика.

[Опиши текущую ситуацию, ограничение системы, дефект или продуктовую боль.
Покажи, почему текущее поведение мешает пользователю или аналитику.]

----

h3. Цель задачи.

*Требуется:*

# [Основной результат — что должно измениться.]
# [Ключевые условия и ограничения.]
# [Ожидаемая ценность.]

_Пользовательская история (при необходимости):_
Как [роль], я хочу [возможность], чтобы [ценность].

----

h3. 1. Описание текущего поведения.

[Как система работает сейчас. Для бага — шаги воспроизведения, ожидаемый и фактический результат.]

----

h3. 2. Описание целевого поведения.

[Как система должна работать после доработки. Логические правила — перечислить явно.]

----

h3. 3. Требования к реализации.

---
h4. 3.1. Фронтенд-часть.

* [Требования к интерфейсу, настройкам, состояниям, событиям и поведению компонента.]

---
h4. 3.2. Бэкенд-часть.

* [Требования к обработчикам, контрактам, SQL-логике, данным, метаданным и ошибкам.]

---
h4. 3.3. Технические требования и ограничения.

* [Обратная совместимость, производительность, легаси-ограничения, сортировка, дедупликация.]

----

h3. 4. Материалы / связанные задачи:

* Отчёт для воспроизведения — [ссылка]
* Запись обсуждения — [^файл.разрешение]
* Связанная задача — [ссылка]

----

h3. 5. Критерии приёмки (AC):

AC.1 — *[Название критерия]:*
* *Дано:* ...;
* *Когда:* ...;
* *Тогда:* ....

AC.2 — *[Название критерия]:*
* *Дано:* ...;
* *Когда:* ...;
* *Тогда:* ....
```

---

## 4. Расширенные разделы для сложных задач

Добавляй по необходимости:

- `h3. Ключевые понятия и определения.` — если задача вводит новую сущность или переопределяет существующую;
- `h3. Структура метаданных.` — если меняется схема хранения, JSON-структура или поля API;
- `h3. Алгоритм обработки.` — для нетривиальной логики, сортировки, дедупликации;
- `h3. Логика генерации SQL.` — если меняется формирование WHERE / HAVING / GROUP BY / JOIN;
- `h3. Интеграция с общей панелью фильтров.` — если задача затрагивает механизм фильтрации;
- `h3. Обратная совместимость.` — если изменение может сломать старые отчёты или настройки;
- `h3. Устранение выявленных дефектов.` — для рефакторинга с попутными исправлениями;
- `h3. Предположения:` — если часть контекста домысливается;
- `h3. Открытые вопросы:` — если есть критичные развилки, требующие ответа от команды.

---

## 5. Специфика для разных типов задач

### 5.1. Баги

Обязательно включать:

```
*Ожидаемый результат:* ...
*Фактический результат:* ...
*Шаги воспроизведения:*
# Шаг 1
# Шаг 2
# Шаг 3
*Окружение:* версия портала, браузер, источник данных, набор данных.
```

### 5.2. Задачи по визуализациям и фильтрации

Дополнительно описывать:

- типы визуализаций в рамках задачи и вне её;
- какие полки должны быть заполнены для активации логики (Строки / Столбцы / Значения / Фильтры / Дополнительные);
- как формируется фильтр при клике: одиночный / множественный выбор;
- как снимается выбор;
- что подсвечивается, что затухает;
- как бэкенд принимает составные предикаты;
- как условия объединяются в итоговом SQL (OR / AND).

### 5.3. Задачи по источникам данных

Дополнительно описывать:

- подключение и проверку соединения (`connection`, `id = 0` для нового);
- чтение схемы и сопоставление типов данных;
- генерацию SQL под конкретный диалект;
- работу с датами и временем;
- вычисляемые поля и фильтрацию;
- предпросмотр данных;
- ошибки неподдерживаемых функций;
- что явно не входит в текущий этап.

### 5.4. Задачи по ФВД (Формы ввода данных)

Учитывать:

- конструктор ФВД и настройки отображения компонента;
- легаси-особенности компонента;
- всплывающие подсказки и текущий визуальный стиль;
- большие справочники: локальный vs серверный поиск;
- количество символов для активации поиска;
- опцию «Не загружать значения»;
- отсутствие потери фокуса при вводе (ререндер);
- задержку отправки запросов (debounce);
- совместимость со старыми пакетами и специальными сборками.

### 5.5. Задачи по API-контрактам

Обязательно указывать:

- backend-объект: `datasets`, `datasources`, `reports`, `tables`, `forms`, `connection`, `extraction_rules`, `users` и т.д.;
- команда: `create`, `get`, `update`, `delete`, `list`, `move`, `export`, `import.*`, `data.*`, `query.set`, `dwh.create` и т.д.;
- какие идентификаторы используются: `object.id`, `command.id`, `data[*].ID`, `parentID`;
- какие поля обязательны, вычисляются, должны сохраняться без изменения;
- перед `update` — требовать сначала `get/list` для чтения текущего состояния;
- секреты не отображать; при изменении — через защищённый ввод; при отсутствии изменения — сохранять текущее значение.

## 6. Правила оформления (JIRA wiki-разметка)

| Элемент | Синтаксис |
|---|---|
| Основные разделы | `h3. Название.` (нумерованные) |
| Подразделы | `h4. 3.1. Название.` |
| Разделитель разделов | `----` |
| Список | `*` или `#` в начале строки |
| Вложенный подпункт | `**` в начале строки |
| Жирный текст | `*текст*` |
| Курсив | `_текст_` |
| Моноширинный (технические имена) | `{{field_name}}` |
| Блок кода SQL | `{code:sql} ... {code}` |
| Блок кода JSON | `{code:json} ... {code}` |
| Таблица | `\|\| Поле \|\| Тип \|\| Описание \|\|` |
| Ссылка | `[https://jira.modusbi.ru/browse/MB-123]` |
| Вложение | `[^Файл.mp4]` |
| Панель-примечание | `{panel:title=...} ... {panel}` |

**Блок `{code}` — только для реального кода**: SQL, JSON, payload, псевдокод, структура метаданных. Обычный текст постановки — без кодовых блоков.

**Не использовать**: Markdown-заголовки `###`, англоязычные заголовки (Context, Goal, Scope, AC, Given/When/Then).

**Вместо Given / When / Then** — `*Дано:*` / `*Когда:*` / `*Тогда:*`.

---

## 7. Финальная проверка качества

Перед выдачей постановки проверь по чеклисту:

- [ ] Есть понятный контекст и проблематика
- [ ] Сформулирована цель задачи
- [ ] Есть описание текущего и целевого поведения (если меняется логика)
- [ ] Требования разделены по фронтенду, бэкенду, данным, SQL и ограничениям
- [ ] Указаны рамки задачи и исключения из них
- [ ] Описаны обратная совместимость и легаси-ограничения (если применимо)
- [ ] Покрыты пограничные сценарии
- [ ] Критерии приёмки (AC) — конкретные, нумерованные, проверяемые
- [ ] Нет англоязычных шаблонных заголовков
- [ ] Нет «реализовать корректно» без объяснения что значит «корректно»
- [ ] Нет «улучшить», «оптимизировать», «доработать» без конкретного результата
- [ ] Нет придуманных API, схем, метаданных, ролей или архитектуры
- [ ] Текст готов к вставке в JIRA без существенной переработки

---

## 8. Пограничные сценарии — обязательный чеклист

При любой задаче проверяй применимость следующих сценариев:

- пустые значения / null / отсутствие данных;
- отсутствие выбранных полей на полке;
- удаление поля из конфигурации после сохранения;
- переименование поля или набора данных;
- совпадение значений по нескольким полям;
- отсутствие прав у пользователя;
- невалидные метаданные;
- старые отчёты, созданные до доработки (обратная совместимость);
- большие объёмы данных;
- повторное открытие и редактирование объекта;
- потеря фокуса при перерисовке компонента;
- недоступность внешнего источника данных;
- ошибки SQL / неподдерживаемые функции диалекта;
- отсутствие агрегации при использовании HAVING.
