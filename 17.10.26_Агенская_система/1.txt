Наша задача построить (на базе используемого мной сейчас аналитического агента) агенскую систему, которая будет:
* изучать доступную часть кодовой базы системы,
* прояснять требования, 
* задавать уточняющие вопросы, если данных недостаточно,
* прояснять все технические детали, 
* собирать всю информацию вместе, 
* писать на её основе постановку по нашим стандартам, 
* а, после написания постановки, отдельный агент-ревьюер должен отдельно проанализировать вводные данные и кодовую базу, а после:
** проверить написанную постановку, 
** указать какие ошибки, расхождения, неточности и несогласованность он нашёл в постановке и вернуть постановку для исправления агенту-постановщику (при необходимости). 

Агенты, в случае спорных моментов, могут начинать дискутировать и итерационно уточнять все необходимые детали, а после исправлять постановку по итоговым данным. 

Такую систему нам предстоит создать.

Codex CLI с авторизацией через ChatGPT.

Python может запускать локальный Codex CLI, который авторизован через ваш ChatGPT-аккаунт. Работа Codex при этом учитывается в рамках соответствующих лимитов подписки.

Есть официальный Python SDK для Codex.
Его уже можно устанавливать как стабильный пакет:
pip install openai-codex

Среда разработки - VS Code + Codex CLI (в виде плагина к VS Code).
Модели и агенты - Codex + подагенты.
Оркестрация - Python + openai-codex.
Хранение контекста - Markdown файлы в папке конкретной задачи по которой идёт работа.
База знаний по кодовой базе проекта - LLM Wiki + навигационные индексы (база знаний по методу Андрея Карпати).

База знаний по подходу Андрея Карпати.
Нужно совместить две концепции:
* Первая — LLM Wiki Андрея Карпати: накапливать знания в виде взаимосвязанных Markdown-страниц, которые LLM актуализирует по мере поступления новых источников.
* Вторая — подход OpenAI Harness Engineering: использовать AGENTS.md как короткое оглавление, которое направляет агента к нужным техническим документам, а не как огромную инструкцию, загружаемую целиком.

Аналитик-постановщик.
Его задача — собрать целостное представление о доработке. Он изучает предоставленные материалы, необходимые участки фронтенда и бэкенда, существующие API-контракты и связанные постановки. Если какой-то механизм неясен, проводит дополнительное исследование.
Затем агент выявляет неопределённости и обращается к вам только по тем вопросам, на которые нельзя достоверно ответить по имеющимся источникам.
В итоге он формирует постановку по стандартам Modus BI, сохраняя JIRA wiki-разметку, действующую терминологию и логические границы задачи.

Независимый ревьюер.
Самое важное требование — независимость анализа.
Ревьюер должен получать те же исходные данные и доступ к кодовой базе, что и постановщик, но выполнять самостоятельную проверку.
1. Сначала ревьюер независимо восстанавливает техническую и функциональную картину задачи по исходным материалам и коду, не опираясь на выводы постановщика.
2. После этого получает постановку и сопоставляет её с собственной картиной, проверяет полноту, корректность, технические предположения, непротиворечивость и критерии приёмки.

Координатор.
Координатор должен управлять переходами, а не самостоятельно подменять аналитическую работу.
Его обязанности: отслеживать этап обработки, передавать материалы, фиксировать замечания, контролировать количество циклов ревью, сохранять промежуточные результаты и направлять спорные вопросы пользователю.
Для начала координатор может быть написан на Python.

Для аналитика и ревьюера должны быть реализованы отдельные сессии - независимость обеспечивается не только различными ролями в TOML, но и различными Codex Thread, управляемыми Python-оркестратором. Официальный Python SDK поддерживает создание нескольких потоков методом thread_start, сохранение их идентификаторов и продолжение через thread_resume.

Два разных Thread не имеют общей истории диалога, но если они запущены в одном work, то имеют доступ к одним и тем же файлам.
Поэтому просто создать два Thread недостаточно.
План работы:
1. Ревьюер самостоятельно исследует первоначальные материалы и исходники до получения результатов постановщика.
2. Результат этого исследования фиксируется отдельно.
3. Только затем ревьюеру передаётся черновик постановки.
4. Дальше ревьюер проверяет его на основании собственной модели задачи.
5. Координатор возвращает замечания постановщику и передаёт обновлённую версию на повторную проверку.

Для строгой независимости на первом этапе ревьюеру следует предоставлять только исходные материалы, без доступа к черновикам постановщика — например, через отдельную подготовленную директорию для черновиков постановок и рабочих материалов Аналитика-постановщика (при необходимости), чтобы они не смешивались с доступными всем вводными данными.
Для каждой задачи сохраняем идентификаторы обеих сессий, состояние процесса и результаты проверок. Перезапуск Python не должен приводить к потере истории работы.

Недостаточно написать в AGENTS.md, что агентам запрещено изменять исходный код (но это тоже нужно сделать).
Во время исследования ревьюер должен работать в режиме read_only. Аналитику также первоначально достаточно этого режима для планирования и исследования. 

Как обеспечить запрет на изменение кода:
Оба агента могут постоянно работать в read_only, а запись итоговых документов выполнять через Python-координатор.
Тогда:
- Аналитик возвращает текст постановки оркестратору.
- Ревьюер возвращает структурированные замечания оркестратору.
- Оркестратор сохраняет эти материалы в разрешённые каталоги.
- Корпоративные репозитории агентами не изменяются.

Python-координатор при этом обязан самостоятельно проверять разрешённые пути записи.

Цикл: постановщик → ревьюер → исправления - не должен продолжаться бесконечно.
Оркестратор должен завершать его, когда отсутствуют незакрытые блокирующие и существенные замечания (либо когда оставшиеся проблемы требуют решения пользователя). Повторяющиеся споры без новых доказательств передаются пользователю агентской системы, а не решаются голосованием агентов.

В структуре предусмотрено два уровня хранения:
* Публичная часть work
** Постановки, тематические папки, конфигурации агентов, скиллы, стандарты и Python-оркестратор. Всё это можно версионировать в текущем публичном Git-репозитории после проверки содержимого.
* Локальная приватная часть .private
** Исходный код Modus BI, техническая база знаний по нему и служебные данные выполнения агентов. Целиком исключается из публичного Git-репозитория.

Для папки .private/knowledge/ - это пример будущего наполнения, а не обязательный набор статей. Первоначально можно создать только index.md и несколько документов по реально исследованным областям.

AGENTS.md не должен содержать полную базу знаний. Достаточно правил, поясняющих, когда агент должен обращаться к Wiki и когда необходимо перепроверять её данные по исходникам.
При этом важно, чтобы Wiki не превращалась в набор утверждений без источников.

Для каждого существенного технического вывода агенты должны сохранять ссылку на исходный файл или символ и версию репозитория. Если код изменился, соответствующую статью нужно проверить/исправить.


context.md и decisions.md - необязательны. Если существующие документы уже содержат всё необходимое, дублировать их не нужно.
Но в крупных темах, таких как внедрение Мер, эти два файла могут оказаться особенно полезными:
- context.md — краткое описание темы, список связанных постановок, их взаимозависимости и статус реализации;

Файлы analyst.toml и reviewer.toml необходимо не только создать, но и правильно подключить к конфигурации Codex. По актуальной официальной документации Codex отдельные пользовательские агенты определяются самостоятельными файлами .codex/agents/*.toml, каждый из которых должен содержать name, description и developer_instructions.

Оба агента работают в режиме read_only (общаясь через оркестратор), им можно предоставить одинаковый доступ ко всей рабочей директории ~/desk/work/, включая корпоративные репозитории, базу знаний и материалы постановок.
Изоляция сессий — обязательна.

Нужно организовать процесс так, чтобы Python-координатор первоначально получал черновик аналитика, но не сохранял его в доступную ревьюеру директорию до завершения независимого исследования.
После этого черновик передаётся ревьюеру, и начинается проверка. Далее ревьюер подготавливает возражения, передаёт их оркестратору и он передаёт их аналитику-постановщику для доработки постановки. Данный процесс может занимать несколько итераций, но не больше n (сначала поставим ограничение в пять итераций), потом будет запрощены разъяснения пользователя по незакрытым вопросам. После получения пояснений пользователя допустимо пройти ещё одну итерацию доработки (если пояснения предоставлены), а иначе незакрытые вопросы должны быть вынесены в секцию постановки "Открытые вопросы".
   
Порядок работы с системой:
1. В основной рабочей директории (~/desk/work/) создаю новую папку (для новой тематики проблемы) или захожу с существующую.
2. В "тематической папке задачи" я собираю связанные материалы, оставляю референсы и собираю общий контекст задачи. Далее в "тематической папке задачи" я создаю файл (.txt) с промптом, описывающим какая постановка требуется и какая новая функциональность вводится или дорабатывается. В этом же файле (.txt) в даю ссылки на материалы, референсы и контекст задачи.
3. Далее собраный итоговый промпт я просто копирую и передаю в агентскую систему для обработки, а она уже проводит все необходимые действия (анализирует задачу, изучает референсы и материалы, изучает связанную кодовую базу, разбирается в проблеме, готовит постановку по нашим стандартам, отдаёт готовую постановку на ревью, исправляет недочёты и т.к.). В итоге на выходе я получаю проверенную, исправленную (при необходимости) и ещё раз перепроверенную итоговую версию постановки, которую я могу отдавать разработчикам для реализации доработок.

Агент всегда будет начинать работу из центральной рабочей директории (~/desk/work/) и сможет изучать все необходимые материалы и кодовую базу находящиеся в данный директории и вложенных папках. Ссылки на материалы в промпте будут задаваться начиная от центральной рабочей директории, чтобы агент мог верно переходить к ним из рабочей директории.

Директории с кодовой базой созданы, наполнены и готовы к работе. Проанализируй предстоящую работу, создай план и действуй по плану пока не завершишь этот проект. Начни с создания базы знаний по методу Андрея Карпати и продолжай по остальным пунктам. На выходе должен получиться готовая агентская система с короткой и понятной документацией как ей пользоваться и куда и как нужно добавлять вводный промпт на создание новой постановки. На выходе (после обработки вводного промпта агентской системой, изучения контекста и т.д.) я должен получать готовую, точную, компактную и читаемую постановку, которую сразу могу передавать разработчикам для реализации доработок по данной постановке.

Перед реализацией Python-оркестратора проверь установленный официальный пакет `openai-codex` в виртуальном окружении `~/desk/work/agent-system/.venv/`.

Используй официальный Python SDK OpenAI Codex и его актуальный публичный API. Не реализуй управление агентами через самодельный парсинг вывода CLI, если соответствующие возможности уже предоставляет SDK.

Для аналитика и ревьюера используй независимые Codex Thread. Предусмотри восстановление сессий, контроль доступа к файловой системе, сохранение состояния координатора и автоматические тесты.

Зафиксируй зависимости проекта таким образом, чтобы после клонирования публичного репозитория агентскую систему можно было восстановить и запустить на другом компьютере.

Не изменяй глобальную конфигурацию `~/.codex/config.toml`, авторизацию и существующие пользовательские сессии без необходимости и отдельного согласования.
