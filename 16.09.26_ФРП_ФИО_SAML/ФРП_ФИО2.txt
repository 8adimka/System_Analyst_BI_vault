*SAML: заполнение ФИО из displayname с сохранением обработки отдельных атрибутов*

h3. 1. Контекст и проблематика.

После перехода ФРП с ADFS на Keycloak изменился формат передачи данных пользователя в SAML Response. Вместо отдельных атрибутов фамилии, имени и отчества заказчик передаёт общую строку ФИО. При текущем сопоставлении она целиком записывается в «Фамилию», поэтому поля профиля не отражают отдельные части ФИО.

----

h3. 2. Цель и рамки задачи.

*Требуется:*
# При создании и обновлении учётной записи через SAML заполнять поля «Фамилия», «Имя», «Отчество» по правилам раздела 4.
#* Сохранить существующую обработку отдельных атрибутов ФИО при наличии {{Surname}} (в том числе в случае возврата заказчика к прежнему формату).
#* Добавить альтернативную ветку обработки ФИО из {{displayname}}, если отдельный {{Surname}} в SAML Response отсутствует.

Правило распространяется на SAML в целом, без специального режима ФРП. 

Новые настройки, изменение LDAP и других способов входа, а также массовое исправление профилей (без входа пользователей) в рамки задачи *не входят*. Вопрос согласования со смежной доработкой LDAP указан в разделе 8.

----

h3. 3. Описание текущего поведения.

* По результатам обсуждений, при первом SAML-входе учётная запись создаётся, при последующих её данные обновляются из ответа провайдера.
* Существующая логика сопоставляет внешние атрибуты со встроенными переменными {{Surname}}, {{Name}}, {{Patronymic}}. По уточнению бэкенда, текущая запись общей строки в фамилию обусловлена сопоставлением {{displayname}} с {{Surname}}.
* В актуальном XML клиента {{http://schemas.xmlsoap.org/claims/displayname}} содержит «Отдел СТП».

----

h3. 4. Описание целевого поведения.

---
h4. 4.1. Выбор источника ФИО.

Проверка выполняется по текущему SAML Response. Отдельный {{Surname}} — входящий атрибут фамилии в существующей схеме сопоставления. Сохранённая фамилия профиля и назначение общего {{displayname}} источником фамилии не означают наличия отдельного {{Surname}}. Способ различения источников с учётом настроек — вопрос 8.2.

|| Условие || Требуемое поведение ||
| Отдельный {{Surname}} присутствует с непустым значением | Полностью сохранить действующую обработку отдельных {{Surname}}, {{Name}}, {{Patronymic}} и их сопоставлений. {{displayname}} не использовать для разбора или дополнения ФИО, в том числе при отсутствии имени или отчества. |
| Отдельный {{Surname}} отсутствует; {{displayname}} содержит непустую строку после удаления пробельных символов по краям | Использовать для всех трёх полей только результат разбора {{displayname}} по п. 4.2. Наличие отдельных {{Name}} или {{Patronymic}} не меняет выбор ветки; их значения с результатом разбора не смешивать. |
| {{Surname}} передан без значения, пустым или пробельным; либо отсутствует и нет пригодного {{displayname}} | Случаи не закрыты итоговой договорённостью; предлагаемые правила приведены в п. 8.1. |

Источник новой ветки — атрибут с точным {{Attribute/@Name}} = {{http://schemas.xmlsoap.org/claims/displayname}}. Название провайдера (ADFS, Keycloak и т. п.) ветку обработки не определяет.

---
h4. 4.2. Разбор общей строки.

# Удалить начальные и конечные пробельные символы значения {{displayname}}.
# Первое слово до пробела записать в «Фамилию», второе — в «Имя», весь оставшийся текст — в «Отчество» независимо от количества слов в нём.
# При одном слове имя и отчество должны быть пустыми; при двух словах пустым должно быть отчество. Дефис и подчёркивание не являются разделителями. Сохранять регистр, написание и порядок слов, не определять их смысл и не переставлять части ФИО.
# Предлагаемое уточнение для повторяющихся пробелов приведено в п. 8.1.

|| Значение displayname || Фамилия || Имя || Отчество ||
| Иванов | Иванов | _пусто_ | _пусто_ |
| Отдел СТП | Отдел | СТП | _пусто_ |
| Иванов Иван Иванович | Иванов | Иван | Иванович |
| Иванов Иван Иванович оглы | Иванов | Иван | Иванович оглы |
| Иванов-Петров Иван | Иванов-Петров | Иван | _пусто_ |
| Иванов_Иван_Иванович | Иванов_Иван_Иванович | _пусто_ | _пусто_ |

Ожидаемый порядок строки — «Фамилия Имя Отчество». Другой порядок слов обрабатывается по той же позиционной схеме.

---
h4. 4.3. Создание, повторный вход и смена формата.

* Применять выбор ветки при каждом успешном SAML-входе, как для новой, так и для существующей учётной записи.
* При разборе непустого {{displayname}} заменять все три поля результатом текущего разбора. Если частей стало меньше, очищать соответствующие ранее заполненные поля.
* Ранее записанная в фамилию общая строка исправляется при следующем успешном SAML-входе. Такой вход также заменяет допустимые ручные изменения ФИО данными провайдера по выбранной ветке. Права на ручное редактирование не меняются.
* При следующем ответе с отдельным {{Surname}} снова применять прежнюю обработку. Возврат к старому формату с соответствующими ему существующими сопоставлениями должен работать без дополнительной доработки кода.

----

h3. 5. Требования к реализации.

---
h4. 5.1. Фронтенд-часть.

* После SAML-входа и при переходе между основным порталом и ФВД получать актуальные поля общей учётной записи. Карточка пользователя, профиль и другие существующие представления ФИО должны использовать одинаковые значения, сохраняя свой формат отображения. Проверить все поддерживаемые точки начала SAML-входа.
* Новые настройки разбора и самостоятельное вычисление частей ФИО во фронтенде не требуются. Необходимость изменений получения или обновления данных профиля определить совместно с бэкендом.

---
h4. 5.2. Бэкенд-часть.

* Обеспечить правила раздела 4 в существующих сценариях создания и обновления пользователя через SAML и сохранять результат в штатных полях профиля. Части ФИО должны быть доступны потребителям данных учётной записи согласованно.
* Сопоставление {{displayname}} → {{Surname}} не должно блокировать новую ветку или после разбора снова записывать всю строку в фамилию. Техническое решение определить в рамках вопроса 8.2.
* Затрагиваются обработка SAML и данные учётной записи, логический объект {{users}}. Необходимость изменения существующих операций создания, чтения и обновления и их актуальные API-контракты подтвердить при технической проработке.

---
h4. 5.3. Совместимость и внедрение.

* Сохранить действующие проверку SAML, идентификацию пользователя, создание учётной записи, назначение ролей, групп и прав, а также обработку остальных атрибутов. Изменение ФИО не должно создавать другую учётную запись.
* Использовать существующие ограничения полей профиля и обработку ошибок. Не вводить новых оснований отказа во входе только из-за количества слов в ФИО. «Весь остаток» не снимает действующие ограничения длины поля.
* Перед внедрением определить необходимые настройки ФРП по вопросу 8.2 и проверить переход на актуальном формате клиента. Для остальных SAML-интеграций без отдельного {{Surname}} действует тот же порядок разбора «Фамилия Имя Отчество»; другой порядок слов автоматически не распознаётся.

h3. 7. Допущения и открытые вопросы.

---
h4. 7.1. Пограничные сценарии, требующие подтверждения.

Ниже — предлагаемые ожидаемые результаты для дополнительных сценариев. Они требуют подтверждения и не подменяют согласованные требования.

* *Переданный пустой Surname.* Предлагается считать отсутствием только отсутствие отдельного атрибута. Если он передан без значения, пустым или пробельным, сохранять старую обработку. В раннем обсуждении пустоту приравнивали к отсутствию; итоговое правило этот случай не уточняет.
* *Повторяющиеся пробелы.* Предлагается считать последовательность пробелов между фамилией, именем и началом отчества одним разделителем. Внутренний текст хвоста отчества, включая пробелы, сохранять. Например, «  Иванов   Иван  Иванович оглы  » → «Иванов» / «Иван» / «Иванович оглы».
* *Нет пригодного источника ФИО.* Если {{Surname}} отсутствует, а {{displayname}} отсутствует или пуст после удаления крайних пробельных символов, предлагается сохранять ФИО существующей учётной записи. Для новой — оставлять ФИО незаполненным, если действующие правила допускают её создание. Другие атрибуты не подставлять; условия создания учётной записи и допуска входа не менять.

---
h4. 7.2. Вопросы технической проработки и смежные зависимости.

* *Сопоставление источников и внедрение.* Как отличить отдельный источник {{Surname}} от назначенного источником фамилии {{displayname}}, сохранив настроенные внешние имена атрибутов? Уточнить фактическую конфигурацию ФРП и старый ответ с ФИО; определить необходимость изменения настроек. Если потребуются изменения их контракта или интерфейса, уточнить объём до оценки. Целевое поведение обеих веток задано разделом 4.
* *Неоднозначные или недопустимые значения.* Подтвердить действующую обработку нескольких значений {{displayname}} и превышения ограничений полей профиля. Если применимого правила нет, определить его при технической проработке.
* *Согласование с LDAP.* Сверить правила с отдельной постановкой ещё не выпущенной доработки LDAP. Её окончательная схема зависит от образца данных другого заказчика; изменение LDAP в эту задачу не включается.

----

h3. 8. Критерии приёмки (AC):

*AC.1 — Сохранение старой ветки:*

* *Дано:* ответ с непустым отдельным {{Surname}} и действующими сопоставлениями; {{displayname}} содержит отличающиеся данные.
* *Когда:* выполняется первый или повторный SAML-вход; проверка повторяется для полного набора ФИО, отсутствующего имени и отсутствующего отчества.
* *Тогда:* поля обрабатываются как до доработки; {{displayname}} не дополняет и не заменяет результат.

*AC.2 — Актуальный формат ФРП и существующее сопоставление:*

* *Дано:* отдельного {{Surname}} нет, {{displayname}} = «Отдел СТП»; исходная конфигурация направляла общую строку в фамилию.
* *Когда:* после внедрения и применения необходимых настроек выполняется SAML-вход нового, затем ранее созданного пользователя.
* *Тогда:* фамилия = «Отдел», имя = «СТП», отчество пустое; старая запись общей строки в фамилии заменяется результатом разбора. Для существующего пользователя используется та же учётная запись.

*AC.3 — Отдельное имя не блокирует новую ветку:*

* *Дано:* {{Surname}} отсутствует, переданы {{Name}} и/или {{Patronymic}} с отличающимися значениями, {{displayname}} = «Иванов Иван Иванович».
* *Когда:* выполняется SAML-вход.
* *Тогда:* фамилия = «Иванов», имя = «Иван», отчество = «Иванович»; отдельные значения не подмешиваются.

*AC.4 — Правила разбора:*

* *Дано:* ответы без отдельного {{Surname}} для каждой строки таблицы п. 4.2, включая варианты с пробельными символами по краям.
* *Когда:* выполняется SAML-вход.
* *Тогда:* результат соответствует таблице; крайние пробельные символы удалены, регистр и написание слов сохранены, четвёртое и последующие слова остаются в отчестве.

*AC.5 — Обновление всех частей ФИО:*

* *Дано:* существующий профиль с заполненными тремя частями ФИО.
* *Когда:* при последовательных SAML-входах без {{Surname}} приходят «Иванов Иван Иванович оглы», «Отдел СТП», затем «Иванов».
* *Тогда:* после каждого входа значения соответствуют текущей строке; после второго отчество пустое, после третьего пусты имя и отчество. Допустимые ручные изменения ФИО также заменяются данными текущего ответа.

*AC.6 — Возврат к отдельным атрибутам:*

* *Дано:* профиль ранее обновлялся из {{displayname}}.
* *Когда:* поступает ответ с отдельным {{Surname}} и сопоставлениями прежнего формата.
* *Тогда:* та же учётная запись обновляется по старой логике без дополнительного изменения кода.

*AC.7 — Единые данные основного портала и ФВД:*

* *Дано:* пользователю доступны основной портал и ФВД.
* *Когда:* он проходит SAML-вход через каждую поддерживаемую точку входа и открывает существующие представления своего профиля в обеих частях платформы.
* *Тогда:* после получения актуальных данных представления используют одинаковые сохранённые части ФИО; прежняя общая строка в фамилии не появляется повторно. Роли, права и идентификация учётной записи сохраняют действующее поведение.
