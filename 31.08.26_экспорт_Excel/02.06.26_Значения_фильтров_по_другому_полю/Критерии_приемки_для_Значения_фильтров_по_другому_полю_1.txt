## Проблема 3 — Раздел 3.3 и AC.7: противоречие между «логикой конфликтов» и необходимостью знать `datasetId` для настройки `displayField`

**Где:** `h4. 3.3. Логика глобальных фильтров` + `AC.7`.

**Почему некорректно:** Постановка утверждает, что «новый обязательный `datasetId` для каждой пилюли глобального фильтра не требуется». Однако при наличии двух наборов данных с одинаковым именем фильтра (например, `month_num`) поле `month_name` может существовать только в одном из них. Чтобы правильно отобразить значения через `displayField`, система *обязана* знать, из какого набора данных брать `month_name`. Таким образом, отказ от `datasetId` создаёт неразрешимую неоднозначность именно для случая с `displayField` при конфликте имён. Это внутреннее противоречие постановки.

**Исправленный вариант:**
> Новую *общую* логику разрешения конфликтов одинаковых наименований в рамках задачи не вводим. Однако для настройки «Значения по другому полю» необходимо явно указать набор данных-источник поля отображения (`displayField`), поскольку это поле может существовать только в одном из конфликтующих наборов данных. Для определения источника использовать текущий механизм выбора главного/первого набора данных (минимальный `componentId` или существующая логика). Фиксировать выбранный источник как `datasetId` настройки `displayField` при сохранении отчёта.

## Проблема 4 — AC.3: критерий проверяет «доступность связи», но не проверяет корректность API-ответа

**Где:** `AC.3`.

**Почему некорректно:** «В контексте глобальных фильтров доступна связь `month_num` -> `month_name`» — это формулировка уровня бизнес-требования, а не приёмочного критерия. Тестировщик не знает *как именно* проверить доступность: через UI, через API-ответ `reports.get`, через DevTools? Без конкретного способа верификации критерий непроверяем.

**Исправленный вариант:**
> **AC.3 — Доступность настройки на уровне глобального фильтра:**
> - *Дано:* в контейнере с фильтрами поле `month_num` настроено как глобальный фильтр и для него выбрано поле отображения `month_name`;
> - *Когда:* отчёт сохраняется и повторно открывается; ответ команды `reports.get` получен;
> - *Тогда:* в ответе `reports.get` в структуре глобального фильтра присутствует поле `displayField` (или согласованный эквивалент) со значением `month_name`;
> - *И:* фронтенд отображает в настройках глобального фильтра значение `month_name` как выбранное поле отображения.

## Проблема 5 — AC.4: отсутствует проверка того, что поле `displayField` НЕ попадает в `WHERE`/payload фильтрации

**Где:** `AC.4`.

**Почему некорректно:** AC.4 проверяет, что в payload уходит основное поле. Но не проверяет обратное — что `month_name` *не* попадает в payload фильтрации. Это важно, потому что требование 3.4 явно запрещает подмену поля фильтрации. Без явной негативной проверки реализация может случайно отправлять оба поля.

**Исправленный вариант (дополнение к AC.4):**
> - *И:* поле `month_name` не фигурирует в `WHERE`/`HAVING` SQL-запроса и не передаётся как поле фильтрации в payload визуализации.

***

## Проблема 6 — AC.6: «настройка *может быть использована* как глобальная» — размытая формулировка

**Где:** `AC.6`, последний пункт «*Тогда*».

**Почему некорректно:** «Настройка может быть использована как глобальная настройка фильтра» — это не верифицируемое утверждение. «Может быть использована» допускает трактовку «технически доступна, но не применяется». Тестировщик не знает, что именно проверять.

**Исправленный вариант:**
> - *Тогда:* отчёт открывается без ошибки;
> - *И:* в контексте глобальных фильтров автоматически восстановлена связь основного поля с полем отображения (т.е. в `reports.get` присутствует `displayField` для данного фильтра без повторного ручного сохранения отчёта пользователем).

## Проблема 7 — Раздел «Что не входит в рамки» vs Раздел 3.1: противоречие в части «безопасной деградации»

**Где:** `h3. 4. Что не входит в рамки задачи` (молчит о деградации) vs `h4. 3.1`, пункт о деградации при невалидной настройке.

**Почему некорректно:** Требование безопасной деградации при недоступном поле отображения упоминается в 3.1 как «использовать текущую безопасную деградацию». Но нигде не описано, что такое «текущая безопасная деградация» применительно к этой конкретной ситуации. Если она уже существует — нужна ссылка или описание. Если её нет — это новая работа, которую нужно явно включить в рамки задачи, а не прятать за «существующим механизмом».

**Исправленный вариант:**
> При открытии отчёта, если поле, указанное в `displayField`, отсутствует в схеме набора данных или недоступно: применяется fallback — отображение значений по основному полю фильтрации (`month_num`). Ошибка в консоль не выбрасывается как критическая; при необходимости выводится предупреждение. Если в системе уже реализован механизм обработки невалидных полей в метаданных — использовать его без дополнительных изменений.

## Обновлённый раздел «6. Критерии приёмки (AC)»

***

**AC.1 — Переименование настройки в контейнере фильтров:**
- *Дано:* пользователь открыл настройки контейнера с фильтрами;
- *Когда:* пользователь просматривает или настраивает параметры поля фильтра;
- *Тогда:* настройка отображается с названием **«Значения по другому полю»**;
- *И:* старое название **«Имя по другому полю»** не отображается нигде в пользовательском интерфейсе данной настройки.

***

**AC.2 — Обновление инструкций и подсказок:**
- *Дано:* в портале есть пользовательские инструкции / подсказки (tooltip, help-текст) по настройке отображения значений фильтра по другому полю;
- *Когда:* пользователь открывает соответствующую инструкцию / подсказку;
- *Тогда:* используется новое название **«Значения по другому полю»**;
- *И:* старое название **«Имя по другому полю»** не встречается ни в одном из указанных текстов.

***

**AC.3 — Доступность настройки на уровне глобального фильтра (API + UI):**
- *Дано:* в контейнере с фильтрами поле `month_num` настроено как глобальный фильтр; для него выбрано поле отображения `month_name`;
- *Когда:* отчёт сохраняется, повторно открывается, и получен ответ команды `reports.get`;
- *Тогда:* в ответе `reports.get` в структуре глобального фильтра присутствует поле `displayField` (или согласованный эквивалент) со значением `month_name`;
- *И:* фронтенд в настройках глобального фильтра отображает `month_name` как выбранное поле для отображения значений.

***

**AC.4 — Сохранение текущей логики фильтрации:**
- *Дано:* для фильтра `month_num` выбраны значения, отображаемые пользователю как «Февраль» и «Март»;
- *Когда:* визуализация запрашивает данные;
- *Тогда:* в payload фильтрации используется поле `month_num`;
- *И:* передаются технические значения `2` и `3`;
- *И:* поле `month_name` не фигурирует в `WHERE`/`HAVING` SQL-запроса и не передаётся как поле фильтрации в payload визуализации.

***

**AC.5 — Обычные фильтры работают без изменений:**
- *Дано:* глобальный фильтр не имеет настройки «Значения по другому полю» (поле `displayField` отсутствует или не задано);
- *Когда:* пользователь выбирает значения фильтра, визуализация запрашивает данные, отчёт сохраняется и повторно открывается;
- *Тогда:* фильтр работает идентично текущему поведению до доработки: по основному полю, без требований к полю отображения;
- *И:* в ответе `reports.get` для данного фильтра отсутствует `displayField` (или он равен `null`/не задан).

***

**AC.6 — Совместимость со старыми отчётами (автоматическая миграция настройки):**
- *Дано:* отчёт был создан до доработки и содержит контейнер фильтров с настройкой `nameBy` (или эквивалентом) на уровне компонента;
- *Когда:* пользователь открывает отчёт после установки доработки;
- *Тогда:* отчёт открывается без ошибки и без деградации функциональности;
- *И:* в ответе `reports.get` для соответствующего глобального фильтра автоматически присутствует `displayField`, восстановленный из метаданных компонента, — без повторного ручного сохранения отчёта пользователем.

***

**AC.7 — Сохранение текущей логики конфликтов одинаковых имён:**
- *Дано:* в отчёте есть несколько контейнеров фильтров с одинаковым именем поля из разных наборов данных;
- *Когда:* формируется глобальный фильтр и загружается ответ `reports.get`;
- *Тогда:* фильтры объединяются по текущей логике портала (без изменений);
- *И:* `displayField` глобального фильтра берётся из главного/первого источника данных по текущему механизму (например, с минимальным `componentId`);
- *И:* новый обязательный `datasetId` на уровне каждой пилюли глобального фильтра не вводится.

***

**AC.8 — Безопасная деградация при невалидной настройке `displayField`:**
- *Дано:* у глобального фильтра в `displayField` указано поле, которое было удалено из набора данных или стало недоступным;
- *Когда:* пользователь открывает отчёт;
- *Тогда:* отчёт открывается без критической ошибки и без «падения»;
- *И:* фильтр отображает значения по основному полю фильтрации (`month_num`);
- *И:* критическое исключение не выбрасывается; при наличии механизма предупреждений — может отображаться некритическое предупреждение.

***

**AC.9 — Настройка `displayField` не влияет на данные в XLSX, боковой Панели фильтров и Панели индикации фильтров (негативный критерий — вне рамок задачи):**
- *Дано:* для глобального фильтра задана настройка «Значения по другому полю»;
- *Когда:* пользователь экспортирует отчёт в XLSX или открывает боковую Панель фильтров / Панель индикации фильтров;
- *Тогда:* в перечисленных механизмах поведение не изменяется по сравнению с состоянием до доработки (техническое значение в XLSX, отображение по основному полю в панелях);
- *Пояснение:* это подтверждает, что данная задача является только **подготовительным этапом**, а не финальной реализацией для перечисленных механизмов.
