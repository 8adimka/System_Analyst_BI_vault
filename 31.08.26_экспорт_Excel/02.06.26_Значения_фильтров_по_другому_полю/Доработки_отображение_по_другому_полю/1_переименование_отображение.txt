Мной была подготовлена постановка - "h3. Контекст и проблематика.

В аналитическом портале уже есть механизм, при котором фильтр работает по одному полю набора данных, а пользователю в списке значений отображаются значения из другого поля того же набора данных.

Пример из отчёта [https://dev.modusbi.ru/report/796]:
* фильтр настроен по полю {{month_num}};
* в настройке "Имя по другому полю" выбрано поле {{month_name}};
* пользователь видит человекочитаемые значения месяца {{Февраль}}, {{Март}};
* при фильтрации в payload уходит основное поле {{month_num}} со значениями {{2}}, {{3}}.

Сейчас эта настройка фактически доступна на уровне контейнера с фильтрами/контекста визуализации. Из-за этого другие механизмы отчёта не могут единообразно получить информацию о том, что для глобального фильтра нужно отображать значения по другому полю. Это блокирует последующие доработки:
* отображение значений фильтров по другому полю при экспорте в XLSX;
* отображение таких значений в боковой Панели фильтров;
* отображение таких значений в Панели индикации фильтров.

Требуется подготовить техническую основу: сделать настройку доступной на уровне глобальных фильтров отчёта и переименовать пользовательскую настройку в контейнере фильтров.

----

h3. Цель задачи:

*Требуется:*
# Вынести настройку отображения значений фильтра по другому полю на уровень глобальных фильтров отчёта.
# Сохранить текущую логику фильтрации: фильтр продолжает применяться по основному полю, а другое поле используется только для отображения значений.
# В контейнере с фильтрами переименовать настройку "Имя по другому полю" в "Значения по другому полю".
# Обновить пользовательские инструкции/подсказки, где используется старое название настройки.

Не требуется менять текущую логику разрешения конфликтов глобальных фильтров с одинаковыми наименованиями.

----

h3. 1. Описание текущего поведения:

* В контейнере с фильтрами есть настройка "Имя по другому полю".
* При включении настройки для поля фильтра сохраняется связь основного поля и поля для отображения значений. В текущих объектах отчёта эта связь представлена на уровне поля компонента, например через {{nameBy}}.
* В блоке глобальных фильтров виден признак глобальности фильтра, но настройка отображения значений по другому полю не является самостоятельной доступной настройкой глобального фильтра.
* При построении фильтрации в payload используется основное поле фильтра.
* В отчёте [https://dev.modusbi.ru/report/796] при выбранных месяцах февраль и март в запросе данных используется {{month_num}} со значениями {{2}} и {{3}}.
* Другие механизмы отчёта не могут надёжно получить настройку отображения значений по другому полю из глобального фильтра:
** экспорт в XLSX выводит технические значения фильтра, например {{2}}, {{3}};
** боковая Панель фильтров не использует настройку отображения значений по другому полю;
** Панель индикации фильтров не использует настройку отображения значений по другому полю.

----

h3. 2. Описание целевого поведения:

* Настройка "Значения по другому полю" должна быть доступна на уровне глобального фильтра отчёта.
* Для каждого глобального фильтра, у которого включено отображение значений по другому полю, в контексте глобальных фильтров должна быть доступна связь:
** основное поле фильтрации;
** поле, значения которого используются для отображения пользователю.
* Фильтрация данных должна продолжать выполняться по основному полю фильтра.
* Отображаемые значения должны определяться по полю, выбранному в настройке "Значения по другому полю".
* Если настройка не задана, глобальный фильтр должен работать и отображаться по текущей логике без изменений.
* Существующие отчёты, где настройка уже задана в контейнере фильтров, должны продолжить работать без ручного пересоздания фильтра.
* Название настройки в интерфейсе контейнера с фильтрами должно быть изменено:
** было: "Имя по другому полю";
** стало: "Значения по другому полю".
* Старое название не должно использоваться в пользовательских инструкциях, подсказках и связанных текстах интерфейса, если они относятся к этой настройке.

----

h3. 3. Требования к реализации:

h4. 3.1. Фронтенд-часть.

* В настройках контейнера с фильтрами заменить название настройки "Имя по другому полю" на "Значения по другому полю".
* Сохранить текущее назначение настройки: она определяет поле, из которого берутся отображаемые значения фильтра.
* При сохранении/обновлении отчёта обеспечить попадание настройки в контекст глобальных фильтров отчёта.
* При открытии отчёта обеспечить восстановление настройки «Значения по другому полю» в контексте глобальных фильтров по следующему приоритету:
*# Если настройка уже присутствует в метаданных глобального фильтра (новый формат) — использовать её.
*# Если настройка отсутствует в глобальном фильтре, но присутствует в метаданных компонента (например, nameBy) — мигрировать её в контекст глобального фильтра при первом открытии (или при первом сохранении).
*# Если настройка отсутствует ни там, ни там — считать её не заданной.
* Если поле для отображения удалено из набора данных или стало недоступно, отчёт не должен падать при открытии. Необходимо использовать текущую безопасную деградацию: отображать значения по основному полю либо применять существующую обработку невалидных метаданных.
* Если настройка выключена или поле для отображения не выбрано, глобальный фильтр должен работать как обычный фильтр без отображения по другому полю.

Не требуется в рамках этой задачи реализовывать отображение новых значений в XLSX, боковой Панели фильтров и Панели индикации фильтров. Эта задача должна только подготовить доступность настройки для этих механизмов.

---
h4. 3.2. Бэкенд-часть и API.

* Затрагиваемые backend-объекты: {{reports}}, {{filtersets}}, а также существующий механизм получения значений набора данных для фильтров.
* При чтении отчёта через существующую команду получения отчёта, например {{reports.get}}, фронтенд должен получать достаточно данных, чтобы восстановить глобальные настройки фильтров.
* При сохранении отчёта через существующую команду обновления отчёта, например {{reports.update}}, должна сохраняться настройка глобального фильтра "Значения по другому полю".
* Перед обновлением отчёта необходимо использовать текущую практику чтения актуального состояния через {{get}}/{{list}}, чтобы не потерять смежные настройки отчёта.
* Формат хранения настройки в метаданных глобального фильтра должен быть согласован между фронтендом и бэкендом до начала реализации и зафиксирован в техническом решении (комментарии к задаче). Минимально необходимое поле: displayField (или эквивалент) на уровне объекта глобального фильтра, содержащее имя поля, значения которого используются для отображения. При отсутствии поля — настройка считается не заданной.
* Если для получения значений фильтра используется существующий механизм запросов к данным Набора данных, он должен продолжить работать с основным полем фильтрации и полем отображения значений.

---
h4. 3.3. Логика глобальных фильтров.

* Один глобальный фильтр остаётся логически определённым по наименованию поля в рамках текущего механизма портала.
* Если в отчёте есть фильтры с одинаковыми именами из разных наборов данных, они по текущей логике считаются одним глобальным фильтром.
* Новую логику разрешения конфликтов одинаковых наименований в рамках задачи мы *не вводим*.
* Для выбора источника данных глобального фильтра использовать текущий механизм портала:
** если уже задан основной набор данных, использовать его;
** если выбор выполняется автоматически, сохранить текущую логику выбора главного/первого источника, включая существующий подход с минимальным {{componentId}}.
* Если выбранное значение есть в одном наборе данных и отсутствует в другом наборе данных с таким же именем фильтра - поведение остаётся в рамках текущей логики портала: фильтрация может дать пустой результат для соответствующего набора данных. В рамках задачи это не является отдельным изменением логики.

---
h4. 3.4. Технические требования и ограничения.

* Не менять SQL-логику применения фильтра: в {{WHERE}}/{{HAVING}} должно использоваться основное поле фильтрации.
* Поле "Значения по другому полю" не должно подменять поле фильтрации в {{payload}} данных визуализации.
* Сохранить обратную совместимость со старыми отчётами, где настройка отсутствует.
* Сохранить обратную совместимость с отчётами, где настройка уже была задана (старый интерфейс контейнера с фильтрами).
* Не менять текущую логику множественного выбора, сброса выбора, зависимых фильтров и поиска значений, если эти механизмы не связаны напрямую с переносом настройки.
* Не вносить изменения в механизм переменных отчёта в рамках данной задачи.

----

h3. 4. Что не входит в рамки задачи:

* Отображение значений фильтров по другому полю в XLSX-экспорте.
* Доработка боковой Панели фильтров.
* Доработка Панели индикации фильтров.
* Доработка переменных отчёта и вывода переменных в XLSX-шаблоны.
* Изменение логики сопоставления глобальных фильтров из разных наборов данных.

h3. 6. Критерии приёмки (AC):

AC.1 — *Переименование настройки в контейнере фильтров:*
* *Дано:* пользователь открыл настройки контейнера с фильтрами;
* *Когда:* пользователь настраивает поле фильтра;
* *Тогда:* настройка отображается с названием "Значения по другому полю";
* *И:* старое название "Имя по другому полю" не отображается в пользовательском интерфейсе этой настройки.

AC.2 — *Обновление инструкций и подсказок:*
* *Дано:* в портале есть пользовательские инструкции / подсказки по настройке отображения значений фильтра по другому полю;
* *Когда:* пользователь открывает соответствующую инструкцию / подсказку;
* *Тогда:* используется новое название "Значения по другому полю".

AC.3 — *Доступность настройки на уровне глобального фильтра:*
* *Дано:* в контейнере с фильтрами поле {{month_num}} настроено как глобальный фильтр;
* *И:* для него выбрано поле отображения {{month_name}};
* *Когда:* отчёт сохраняется и повторно открывается;
* *Тогда:* в контексте глобальных фильтров доступна связь {{month_num}} -> {{month_name}}.

AC.4 — *Сохранение текущей логики фильтрации:*
* *Дано:* для фильтра {{month_num}} выбрано поле отображения {{month_name}};
* *И:* выбраны значения фильтрации {{2}} и {{3}}, отображаемые пользователю как "Февраль" и "Март";
* *Когда:* визуализация запрашивает данные;
* *Тогда:* в payload фильтрации используется основное поле {{month_num}};
* *И:* в значения фильтрации передаются технические значения основного поля, например {{2}} и {{3}}.

AC.5 — *Обычные фильтры работают без изменений:*
* *Дано:*  глобальный фильтр не имеет настройки «Значения по другому полю» (поле displayField отсутствует или не задано);
* *Когда:* пользователь выбирает значения фильтра и сохраняет отчёт;
* *Тогда:* фильтр работает идентично текущему поведению до доработки: по основному полю, без требований к полю отображения;
* *И:* в ответе reports.get для данного фильтра отсутствует displayField (или согласованный аналог) или он равен null/не задан.

AC.6 — *Совместимость со старыми отчётами (автоматическая миграция настройки):*
* *Дано:* отчёт был создан до доработки и содержит контейнер фильтров с ранее настроенным отображением по другому полю;
* *Когда:* пользователь открывает отчёт после установки доработки;
* *Тогда:* отчёт открывается без ошибки;
* *И:* настройка может быть использована как глобальная настройка фильтра без ручного пересоздания фильтра.

AC.7 — *Сохранение текущей логики конфликтов одинаковых имён:*
* *Дано:* в отчёте есть несколько фильтров с одинаковым наименованием из разных наборов данных;
* *Когда:* формируется глобальный фильтр;
* *Тогда:* фильтры продолжают объединяться по текущей логике портала;

AC.8 — *Безопасная деградация при невалидной настройке:*
* *Дано:* у глобального фильтра указано поле отображения значений, которое было удалено или стало недоступно;
* *Когда:* пользователь открывает отчёт;
* *Тогда:* отчёт не падает;
* *И:* фильтр отображается по основному полю либо обрабатывается существующим механизмом невалидных метаданных.".

Данная постановку уже была реализована, но сейчас было решено переименовать данное поле настройки пилюли, размещённой на поле "Фильтры" (в визуализации "Контейнер с фильтрами), в "Отображение значений по другому полю" (вместо "Значения по другому полю").

Также в связи с увеличение размера заголовка пришлось увеличить всё выпадающее окно настроек пилюли (и размер выпадающего списка внутри данного выпадающего окна настроек).

Обновлённый ориентировочный внешний вид можно изучить на скриншоте "photo_2026-08-06_18-13-38.jpg" и "photo_2026-08-06_18-13-44.jpg".
