## Ключевые выводы по итогам созвона для постановки задачи:

1. **Суть изменения:** настройки фильтрации/значений по другому полю нужно поднять с уровня визуализации на уровень глобальных фильтров отчёта.

2. **Текущую логику разрешения конфликтов менять не нужно:** если в отчёте есть фильтры с одинаковыми именами из разных наборов данных, они считаются одним фильтром и маппинг происходит по наименованию.

3. **Новый идентификатор набора данных для каждой пилюли не добавляем:** обсуждали вариант хранить вместе с наименованием ещё и ID датасета, но решили не вводить это нововведение в рамках текущей задачи.

4. **Конфликты одинаковых наименований остаются ответственностью настройки отчёта:** если аналитик назвал поля одинаково в разных датасетах, система не будет на уровне кода пытаться разруливать все такие случаи.

5. **При совпадениях используется текущий механизм выбора источника:** берётся первый/главный источник из списка для глобального фильтра. По контексту переписки с Лёшей: уже есть автоматический и ручной выбор главного датасета; автоматический — по минимальному `componentId`.

6. **Если выбранное значение отсутствует в конкретном наборе данных:** возможен пустой результат фильтрации или конфликтное поведение; это можно воспроизвести и проверить на отчёте, но в рамках задачи это не является отдельным изменением логики.

7. **Для реализации важно поднять доступ к данным выше:** сейчас нужные данные фактически доступны через визуализацию/кэш результата запроса; требуется сделать так, чтобы настройки были доступны на уровне отчёта/глобального фильтра, а не только через визуализацию.
