h3. Контекст и проблематика.

При экспорте визуализации в XLSX значения применённых фильтров форматируются
в зависимости от типа поля: число, строка, дата или дата-время.

Для *обычного поля* тип доступен в метаданных набора данных.
Для *вычисляемого поля* в метаданных хранится SQL-выражение; признак
{{calculated}} описывает способ формирования, но не тип результата.

Если вычисляемое поле выведено отдельной колонкой в результирующей схеме
основного запроса, его тип уже известен из метаданных этой колонки — и может
использоваться для форматирования фильтра независимо от видимости колонки
в XLSX.

Если поле применяется только для фильтрации и отсутствует в результирующей
схеме, определить его тип без дополнительного SQL-запроса невозможно.
В этом случае необходима безопасная строковая деградация.

----

h3. Цель задачи.

*Требуется:*
# Для вычисляемого поля, присутствующего в результирующей схеме основного
  запроса, определять тип по метаданным связанной колонки.
# Нормализовать полученный тип в категорию {{number}}, {{string}}, {{date}}
  или {{datetime}} и применять действующие правила форматирования фильтра.
# Для вычисляемого поля, отсутствующего в схеме, всегда применять строковую
  безопасную деградацию.
# Не изменять основной SQL-запрос и не выполнять дополнительных обращений к БД
  только ради определения типа.
# Сохранить действующие правила состава, порядка, наименований и отображения
  фильтров, включая настройку «Значения по другому полю», общий и частные
  XLSX-шаблоны.

_Пользовательская история:_
Как пользователь аналитического портала, я хочу видеть значения фильтров
по вычисляемым полям в XLSX в соответствии с их типом, чтобы числа, строки
и даты отображались однозначно.

----

h3. 1. Ключевые понятия.

* *Вычисляемое поле* — поле визуализации, значение которого формируется
  SQL-выражением (функции, агрегаты, оконные функции, {{CASE}}, явные
  приведения типов).
* *Основной запрос данных экспорта* — штатный запрос для получения данных
  экспортируемой визуализации. Запрос, сформированный только ради определения
  типа, основным не считается.
* *Результирующая схема* — перечень колонок верхнеуровневого результата
  основного запроса с их типами, рассматривается *до* исключения невидимых
  колонок XLSX.
* *Присутствие поля в схеме* — наличие колонки верхнеуровневого результата,
  однозначно связанной с данным полем в карте проекций.
* *Видимая колонка XLSX* — колонка, включённая в пользовательскую таблицу.
  Невидимая колонка может присутствовать в результирующей схеме.
* *Источник отображаемого значения фильтра* — основное поле либо поле
  отображения по настройке «Значения по другому полю». Тип определяется
  именно для него.
* *Строковая безопасная деградация* — вывод по правилам {{string}}:
  в одинарных кавычках, без разделителей разрядов и без преобразования к дате.

----

h3. 2. Текущее поведение.

* Фильтры передаются в {{export.parameters.filter}} с полями {{name}},
  {{values}}, {{filterType}} (обязателен для обновлённого фронтенда) и
  опциональным {{dateFormat}}.
* Для обычных полей форматирование выполняется по {{filterType}}.
* Если вычисляемое поле передано с {{filterType = "calculated"}} или без
  {{filterType}} (обратная совместимость), бэкенд применяет строковую
  деградацию.
* Метаданные результирующей схемы не используются как источник типа
  вычисляемого поля при формировании блока фильтров.

----

h3. 3. Целевое поведение.

h4. 3.1. Основное правило.

|| Вид поля || Колонка в результирующей схеме || Источник категории ||
| Обычное поле | Не влияет | Действующая обработка {{filterType}} |
| Вычисляемое | Присутствует, сопоставление однозначно, тип поддерживается | Тип колонки из схемы |
| Вычисляемое | Присутствует, но тип отсутствует / не поддерживается / сопоставление неоднозначно | {{string}} |
| Вычисляемое | Отсутствует | {{string}} |

* Наличие выражения в {{WHERE}}, {{HAVING}}, {{GROUP BY}}, {{ORDER BY}},
  CTE или подзапросе *не означает* присутствия поля в схеме.
* Видимость колонки в XLSX на выбор типа не влияет.
* {{filterType}}, переданный фронтендом, не заменяет тип из схемы.

---

h4. 3.2. Поле присутствует в схеме.

* Используется тип результирующей колонки, уже разрешённый СУБД
  (с учётом {{CASE}}, агрегатов, оконных функций, явных приведений).
* Тип не определяется по тексту SQL, типу исходного столбца или runtime-типу
  значения в приложении.
* Ноль строк в результате и значения {{null}} не меняют правило:
  тип берётся из схемы, если она предоставлена драйвером.
* Если метаданные не переданы, повреждены или не поддаются нормализации
  без обращения к БД — применяется {{string}}; экспорт не падает.

---

h4. 3.3. Поле отсутствует в схеме.

* Значение форматируется как {{string}} — даже если поле участвует
  в {{WHERE}}, {{HAVING}}, {{ORDER BY}} или находится во внутреннем
  подзапросе.
* {{filterType}}, переданный фронтендом, не используется для определения
  числового или датового типа.
* Выражение не добавляется в {{SELECT}}; дополнительные запросы, {{DESCRIBE}}
  и обращения к системному каталогу не выполняются.
* Если XLSX формируется из ранее полученного результата и схема к нему
  доступна — применяется стандартное правило; если нет — {{string}}.

---

h4. 3.4. Правила отображения по категории.

|| Категория || Правило || Пример в XLSX ||
| {{number}} | Без кавычек; разделители разрядов по действующим правилам. Для чисел ≤ 4 знаков разделители не применяются. | {{Сумма: 1 500 000,50}} |
| {{string}} | Каждое значение в одинарных кавычках. | {{Регион: 'Москва', 'Санкт-Петербург'}} |
| {{date}} | Без кавычек; применяется {{dateFormat}} или формат по умолчанию {{ДД.ММ.ГГГГ}}. | {{Дата заказа >= 01.01.2025 И <= 31.01.2025}} |
| {{datetime}} | Без кавычек; действующий формат визуализации; время — если предусмотрено форматом. | {{Момент обновления >= 01.01.2025 10:30}} |
| {{string}} (деградация) | В кавычках, без числового форматирования и преобразования к дате. | {{Значение: '1500000'}} |

* Форматы списочных и диапазонных фильтров, операторы {{=}}, {{<>}},
  {{>}}, {{>=}}, {{<}}, {{<=}}, {{~}}, связки {{И}} / {{ИЛИ}}
  и порядок значений не изменяются.
* {{filterType = "year"}} не является типом СУБД: при числовой колонке
  применяется {{number}}; значение ≤ 4 знаков выводится без разделителей.
* Маска даты определяется по действующему приоритету настроек,
  а не по SQL-типу.

---

h4. 3.5. Настройка «Значения по другому полю».

* Категория определяется для *фактического источника* отображаемого значения
  (основного поля или поля отображения).
* Если источник — вычисляемое поле, к нему применяются правила пп. 3.1–3.3.
* Деградация к исходному значению основного поля: тип определяется для него.
* Название фильтра, правила фильтрации данных и механизм сопоставления
  значений не изменяются.
* Поле отображения не добавляется в основной запрос ради определения типа.

----

h3. 4. Требования к определению типа.

h4. 4.1. Получение метаданных.

* Интеграционный слой передаёт метаданные результирующих колонок вместе
  с данными основного запроса.
* PostgreSQL: идентификатор или каноническое описание типа от текущего
  драйвера.
* ClickHouse: каноническое имя типа из метаданных ответа драйвера.
* Если адаптер отбрасывал метаданные до формирования XLSX — их необходимо
  сохранить во внутренней модели результата до определения категорий фильтров.
* Метаданные обрабатываются *до* исключения невидимых колонок.
* Отдельный запрос для получения схемы не выполняется; при нуле строк
  фиктивные строки не создаются.

---

h4. 4.2. Сопоставление поля с колонкой.

* Сопоставление выполняется по внутренней связи (технический ключ, позиция
  проекции), а не по пользовательскому заголовку или тексту SQL-выражения.
* Переименование заголовка не влияет на тип.
* При конфликте алиасов или нескольких кандидатах применяется {{string}}.
* Одно поле в нескольких фильтрах типизируется однократно в рамках экспорта.

---

h4. 4.3. Алгоритм.

# Определить состав фильтров по действующей логике; сохранить порядок
  {{export.parameters.filter}}.
# Для каждого выводимого значения определить источник: основное поле
  или поле отображения.
# *Обычный источник* → действующая обработка {{filterType}}.
# *Вычисляемый источник* → найти связанную колонку в результирующей схеме.
# Колонка найдена → нормализовать тип в {{number}} / {{string}} / {{date}} /
  {{datetime}}.
# Колонка не найдена, неоднозначна или тип недоступен → {{string}}.
# Отформатировать значения по итоговой категории без изменения состава,
  названий, операторов и порядка фильтров.
# Переиспользовать определённую категорию во всех частях текущего экспорта.

----

h3. 5. Нормализация типов СУБД.

h4. 5.1. Общие правила.

* Нормализация выполняется по уже полученным метаданным, без дополнительных
  запросов.
* Явное приведение типа учитывается автоматически — используется итоговый
  тип колонки после разрешения выражения СУБД.
* Обёртки {{Nullable}} и {{LowCardinality}} снимаются рекурсивно.
* Неизвестный или составной тип разрешается только по уже загруженному
  локальному реестру драйвера. Если это потребует запроса — применяется
  {{string}}.

---

h4. 5.2. PostgreSQL.

|| Семейство типа || Категория ||
| {{smallint}}, {{integer}}, {{bigint}}, {{numeric}}/{{decimal}}, {{real}}, {{double precision}} | {{number}} |
| {{character}}, {{character varying}}, {{text}}, {{name}}, {{uuid}}, {{enum}} | {{string}} |
| {{date}} | {{date}} |
| {{timestamp}} без/с часовым поясом | {{datetime}} |
| Доменный тип | Категория базового типа — только если он доступен без обращения к БД |
| {{boolean}}, {{time}}, {{interval}}, {{json}}/{{jsonb}}, {{xml}}, {{bytea}}, массивы, составные, диапазонные и прочие | {{string}} |

---

h4. 5.3. ClickHouse.

|| Семейство типа || Категория ||
| {{Int*}}, {{UInt*}}, {{Float*}}, {{BFloat16}}, {{Decimal*}} | {{number}} |
| {{String}}, {{FixedString}}, {{Enum*}}, {{UUID}}, {{IPv4}}, {{IPv6}} | {{string}} |
| {{Date}}, {{Date32}} | {{date}} |
| {{DateTime}}, {{DateTime64}} | {{datetime}} |
| {{Nullable(T)}} | Снять обёртку → категория для {{T}} |
| {{LowCardinality(T)}} | Снять обёртку → категория для {{T}} |
| {{Bool}}, {{Nothing}}, {{Dynamic}}, {{Variant}}, {{Array}}, {{Tuple}}, {{Map}}, {{Nested}}, {{Object}}/{{JSON}}, агрегатные состояния и прочие | {{string}} |

Вложенные комбинации, например {{LowCardinality(Nullable(String))}},
нормализуются рекурсивно. Тип разбирается как структура, а не по подстроке.

----

h3. 6. Требования к реализации.

h4. 6.1. API и фронтенд.

* Затрагиваемый объект: {{exports}}; эндпоинт и имя команды не меняются.
* Структура {{export.parameters.filter}} не изменяется: {{name}}, {{values}},
  {{filterType}} (обязателен), {{dateFormat}} (опционален).
* Фронтенд передаёт известный базовый тип или {{calculated}}; для вычисляемых
  полей {{filterType}} не является источником категории на бэкенде.
* {{dateFormat}} применяется только при категории {{date}} / {{datetime}};
  при строковой деградации — игнорируется.
* Новые команды API, UI-настройки и шаблонные маркеры не вводятся.

---

h4. 6.2. Бэкенд.

* Перед форматированием блока фильтров — получить схему и карту проекций.
* Вычисляемое поле определяется по конфигурации визуализации, а не только
  по {{filterType}}.
* Приоритет для вычисляемых полей: тип связанной колонки → {{string}}.
  {{filterType}} промежуточным fallback не является.
* Исходная последовательность {{export.parameters.filter}} сохраняется.
* Метаданные отчёта, визуализации, набора данных и полей не изменяются;
  определённый тип не кешируется в метаданных.
* Ошибка при чтении, сопоставлении или нормализации → {{string}};
  экспорт не прерывается.
* Невалидное SQL-выражение → действующая обработка ошибки запроса;
  строковая деградация её не маскирует.

---

h4. 6.3. SQL-ограничения.

* Для определения типа *запрещено*:
** добавлять выражения или служебные колонки в {{SELECT}};
** использовать {{pg_typeof}}, {{toTypeName}};
** выполнять {{DESCRIBE}}, запросы с {{LIMIT 0}}/{{LIMIT 1}},
   metadata-only запросы или обращения к системному каталогу;
** изменять {{WHERE}}, {{HAVING}}, {{GROUP BY}}, {{DISTINCT}}, {{UNION}},
   CTE, оконные выражения, сортировку, лимиты или пагинацию.
* Число запросов, round-trip, строк результата, состав и порядок колонок,
  итоги, точность, часовые пояса и результат фильтрации остаются неизменными.

---

h4. 6.4. Формирование XLSX.

* Правила применяются в общем и частных шаблонах Таблицы.
* Действующие маркеры сохраняются: {{Filter}}, {{Filters}},
  {{Filters_by_rows}}, {{FiltersByRows}}. Новые не вводятся.
* Построчный/однострочный режим, разделитель {{; }}, порядок фильтров —
  по действующей логике.
* Частный шаблон без маркера фильтров: блок не добавляется, тип
  не определяется.
* Технические ключи и метаданные схемы не попадают в заголовки, данные,
  блок «Фильтры», блок «Переменные» и дополнительные листы.
* При партиционировании экспорта категория применяется во всех его частях.

----

h3. 7. Пограничные сценарии.

|| Сценарий || Поведение ||
| Вычисляемое поле — колонка результата, скрытая в XLSX | Тип из схемы |
| Поле только в {{WHERE}} / {{HAVING}} | {{string}} |
| Поле в {{GROUP BY}}, {{ORDER BY}}, CTE, подзапросе | {{string}} |
| Агрегат / окно / {{CASE}} / явное приведение — выводится колонкой | Итоговый тип колонки |
| Основной запрос вернул 0 строк, схема доступна | Тип из схемы |
| Все значения колонки — {{null}} | Тип из схемы |
| Адаптер не передал тип или вернул неизвестный | {{string}}, без нового запроса |
| Два поля с одинаковым заголовком | По внутренней связи; при неоднозначности — {{string}} |
| «Значения по другому полю»: отображаемое поле отсутствует в схеме | {{string}} |
| Деградация к основному полю | Тип основного поля |
| Фронтенд передал числовой {{filterType}}, колонка отсутствует | {{string}} |
| Экспорт из ранее полученного результата со схемой | Тип из схемы |
| Экспорт без доступной схемы | {{string}}, новый запрос не выполняется |
| Партиционированный экспорт | Категория не переопределяется по частям |

Во всех случаях ошибка определения категории не прерывает экспорт;
исходное значение, название, оператор и позиция фильтра сохраняются.

----

h3. 8. Рамки задачи:

*В рамках задачи:*
* чтение метаданных результирующей схемы из уже полученного ответа основного запроса;
* однозначное сопоставление вычисляемого поля с колонкой результата;
* нормализация типов PostgreSQL и ClickHouse;
* применение существующих правил форматирования по полученной категории;
* строковая деградация для полей без доступного поддерживаемого типа;
* переиспользование определённой категории во всех частях текущего экспорта.

*В рамки задачи не входит:*
* изменение SQL-выражений вычисляемых полей и логики фильтрации;
* добавление полей в результат или выполнение запросов ради типизации;
* изменение механизма «Значения по другому полю»;
* изменение данных, пользовательских колонок, шаблонов, переменных и дополнительных листов;
* сохранение типа в метаданных отчёта, визуализации или набора данных.

----

h3. 9. Критерии приёмки (AC):

AC.1 — *Поддерживаемые категории:*
* *Дано:* последовательно для PostgreSQL и ClickHouse проверяются вычисляемые поля, однозначно связанные с колонками результирующей схемы категорий число, строка, дата и дата-время;
* *Когда:* выполняется экспорт в XLSX;
* *Тогда:* значения форматируются соответственно как {{number}}, {{string}}, {{date}} и {{datetime}} по правилам п. 3.4;
* *И:* для {{date}} и {{datetime}} применяется {{dateFormat}}, а при его отсутствии — действующий формат по умолчанию {{ДД.ММ.ГГГГ}}; компонент времени выводится только при наличии в выбранном формате.

AC.2 — *Поле используется только в фильтре:*
* *Дано:* вычисляемое поле имеет числовое выражение, участвует в {{WHERE}} или {{HAVING}}, но отсутствует в верхнеуровневой результирующей схеме;
* *Когда:* выполняется экспорт;
* *Тогда:* значение {{1500000}} отображается как {{'1500000'}} по правилу п. 3.3;
* *И:* вычисляемое поле не добавляется в {{SELECT}}, дополнительные запросы не выполняются.

AC.3 — *Невидимая колонка результата:*
* *Дано:* вычисляемое поле связано с колонкой основного результата, которая исключается из видимых колонок XLSX;
* *Когда:* выполняется экспорт;
* *Тогда:* тип этой колонки используется для оформления фильтра согласно п. 3.1 и 3.2;
* *И:* сама колонка не появляется в XLSX и не меняет порядок пользовательских колонок.

AC.4 — *Пустой результат и {{null}}:*
* *Дано:* основной запрос возвращает ноль строк либо только {{null}} в вычисляемой колонке;
* *И:* тип колонки доступен в результирующей схеме;
* *Когда:* формируется блок фильтров;
* *Тогда:* категория определяется по схеме без первой, непустой или фиктивной строки в соответствии с п. 3.2.

AC.5 — *Итоговый тип выражения и нормализация:*
* *Дано:* в результирующей схеме присутствуют вычисляемые колонки с {{CASE}}, агрегатом, оконной функцией или явным приведением типа;
* *И:* проверяются типы PostgreSQL и ClickHouse, включая {{Nullable(Decimal(18, 2))}}, {{LowCardinality(String)}} и {{DateTime64(3)}};
* *Когда:* выполняется экспорт;
* *Тогда:* используется итоговый тип каждой колонки, определённый СУБД, и категория соответствует таблицам пп. 5.2–5.3;
* *И:* выражение повторно не анализируется и не вычисляется.

AC.6 — *Безопасный строковый fallback:*
* *Дано:* тип вычисляемой колонки отсутствует, неизвестен, не поддерживается либо колонка сопоставлена неоднозначно;
* *Когда:* выполняется экспорт;
* *Тогда:* значение оформляется как {{string}} независимо от переданного {{filterType}} по правилам п. 3.1 и 4.2;
* *И:* экспорт не завершается ошибкой определения типа и не обращается к БД за уточнением.

AC.7 — *Приоритет типа СУБД над {{filterType}}:*
* *Дано:* связанная колонка имеет числовой тип, а фронтенд передал {{filterType = "calculated"}}, {{string}} или {{year}};
* *Когда:* выполняется экспорт;
* *Тогда:* значение форматируется как {{number}} по типу колонки согласно п. 3.1;
* *И:* значение {{2024}} выводится без разделителя разрядов по правилу коротких чисел из п. 3.4; если связанной колонки нет, применяется {{string}}.

AC.8 — *«Значения по другому полю»:*
* *Дано:* фильтрация выполняется по основному полю, а фактически показывается значение вычисляемого поля отображения;
* *Когда:* выполняется экспорт;
* *Тогда:* при наличии однозначно связанной колонки поддерживаемого типа категория определяется по её типу согласно п. 3.5; при отсутствии такой колонки значение поля отображения оформляется как {{string}} независимо от его {{filterType}};
* *И:* если действующий механизм вернулся к исходному значению, тип определяется для основного поля; название, позиция фильтра и фильтрация по основному полю не изменяются.

AC.9 — *Отсутствие дополнительных SQL-операций:*
* *Дано:* экспорт содержит несколько фильтров по вычисляемым полям, в том числе отсутствующим в результирующей схеме;
* *Когда:* выполняется экспорт;
* *Тогда:* основной SQL, его параметры и число обращений к БД не изменяются ради типизации согласно п. 6.3;
* *И:* отсутствуют дополнительные проекции, {{pg_typeof}}, {{toTypeName}}, {{DESCRIBE}}, metadata-only запросы и обращения к системным каталогам.

AC.10 — *Экспорт из ранее полученного результата и разбиение выгрузки:*
* *Дано:* XLSX формируется из ранее полученного результата либо разбивается на несколько листов или файлов;
* *Когда:* вместе с результатом доступна результирующая схема;
* *Тогда:* тип берётся из этой схемы и одинаково применяется во всех частях выгрузки согласно п. 3.3 и 6.4;
* *И:* при отсутствии схемы применяется {{string}} без нового обращения к БД.

AC.11 — *API, порядок и шаблоны:*
* *Дано:* последовательно проверяются запрос обновлённого фронтенда и запрос обратной совместимости;
* *Когда:* выполняется XLSX-экспорт по действующему API-контракту;
* *Тогда:* обновлённый фронтенд передаёт для каждого фильтра обязательный {{filterType}}, а при неизвестном базовом типе — {{calculated}} согласно п. 6.1;
* *И:* запрос обратной совместимости без {{filterType}} не приводит к ошибке, а вычисляемое поле обрабатывается по основному правилу п. 3.1; фильтры сохраняют порядок полки, названия и формат действующих маркеров согласно п. 6.4;
* *И:* без маркера фильтров частный шаблон не получает блок автоматически. Технические метаданные, ключи и скрытые колонки не попадают в XLSX.

AC.12 — *Отсутствие регрессии:*
* *Дано:* экспорт содержит обычные поля, переменные, дополнительные листы, итоги и форматирование визуализации;
* *Когда:* выполняется XLSX-экспорт после доработки;
* *Тогда:* обычные поля продолжают обрабатываться по действующему {{filterType}} согласно п. 3.1;
* *И:* фильтрация, данные, видимые колонки, точность, часовой пояс, блок «Переменные» и дополнительные листы не изменяются.
