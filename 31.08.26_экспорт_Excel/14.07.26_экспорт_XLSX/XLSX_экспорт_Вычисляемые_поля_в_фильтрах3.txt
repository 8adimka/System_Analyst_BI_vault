h3. Контекст и проблематика.

При экспорте визуализации в XLSX значения фильтров оформляются по типу поля: как число, строка, дата или дата-время.

Для обычного поля тип известен из метаданных набора данных. Для вычисляемого поля хранится SQL-выражение, а признак {{calculated}} не сообщает, какой тип возвращает это выражение.

Если вычисляемое поле уже входит в результат основного запроса данных экспорта, его фактический тип доступен в метаданных результирующей схемы. Если поле используется только в фильтре и не входит в результат, определение типа потребовало бы изменения SQL или дополнительного обращения к БД. В таком сценарии значение должно безопасно отображаться как строка.

----

h3. Цель задачи.

*Требуется:*
# Использовать тип вычисляемого поля из результирующей схемы основного запроса, если поле уже присутствует в этой схеме.
# Приводить тип СУБД к категории {{number}}, {{string}}, {{date}} или {{datetime}} и применять действующие правила оформления фильтров.
# Во всех случаях, когда тип вычисляемого поля недоступен или не может быть однозначно сопоставлен, использовать {{string}}.
# Не изменять основной SQL-запрос и не выполнять дополнительные обращения к БД только ради определения типа вычисляемого поля.
# Сохранить действующее поведение обычных полей, фильтрации, порядка фильтров, XLSX-шаблонов и настройки «Значения по другому полю».

_Пользовательская история:_
Как пользователь аналитического портала, я хочу видеть значения фильтров по вычисляемым полям в соответствии с их фактическим типом, чтобы числа, строки и даты однозначно читались в выгруженном отчёте.

----

h3. 1. Описание текущего поведения.

* Фильтры передаются в {{export.parameters.filter}} с полями {{name}}, {{values}}, обязательным {{filterType}} и опциональным {{dateFormat}}.
* Обычные поля форматируются по действующему {{filterType}}.
* Если тип вычисляемого поля неизвестен, оно оформляется как строка.
* Тип результирующей колонки основного запроса не используется единообразно для оформления фильтров по вычисляемым полям.

----

h3. 2. Описание целевого поведения.

h4. 2.1. Основное правило.

Тип определяется для поля, значение которого фактически выводится в блоке фильтров.

Под *результирующей схемой* далее понимается перечень колонок верхнеуровневого результата основного запроса и их типов до исключения колонок, не отображаемых в XLSX.

|| Источник отображаемого значения || Правило определения категории ||
| Обычное поле | Действующая обработка {{filterType}} без изменений |
| Вычисляемое поле однозначно связано с колонкой результирующей схемы; тип колонки поддерживается | Тип колонки из метаданных результата |
| Для вычисляемого поля связанная колонка отсутствует, связь неоднозначна, метаданные недоступны или тип не поддерживается | {{string}} |

* Поле считается присутствующим только тогда, когда оно является отдельной колонкой верхнеуровневого результата. Участие выражения в {{WHERE}}, {{HAVING}}, {{GROUP BY}}, {{ORDER BY}}, CTE или внутреннем подзапросе само по себе не предоставляет тип для экспорта.
* Видимость колонки в XLSX значения не имеет: если колонка уже присутствует в результате основного запроса, её тип используется до формирования пользовательского набора колонок.
* Для вычисляемого поля переданный {{filterType}}, включая {{year}}, не подменяет тип СУБД и не используется как промежуточный fallback. Приоритет всегда один: поддерживаемый тип связанной колонки → {{string}}.

h4. 2.2. Правила отображения.

|| Категория || Отображение в XLSX || Пример ||
| {{number}} | Без кавычек; действующие разделители разрядов и точность; без дополнительного округления | {{Сумма: 1 500 000,50}} |
| {{string}} | Каждое значение в одинарных кавычках | {{Регион: 'Москва', 'Санкт-Петербург'}} |
| {{date}} | Без кавычек; {{dateFormat}} либо действующий формат по умолчанию {{ДД.ММ.ГГГГ}} | {{Дата >= 01.01.2025}} |
| {{datetime}} | Без кавычек; применяется {{dateFormat}} либо действующий формат по умолчанию; компонент времени выводится только тогда, когда он предусмотрен выбранным форматом | {{Обновлено >= 01.01.2025 10:30}} |

* Для чисел длиной до четырёх знаков включительно разделители разрядов не применяются. Поэтому вычисляемое значение года с числовым типом отображается как {{2024}}, даже если фронтенд передал {{filterType = "year"}}.
* При строковом fallback значение не форматируется как число или дата, а {{dateFormat}} не применяется.
* Формат списочных, сравнительных и диапазонных фильтров, операторы, связки {{ И }} / {{ ИЛИ }} и порядок значений внутри фильтра не изменяются.

h4. 2.3. Настройка «Значения по другому полю».

* Сначала действующий механизм определяет, какое значение будет показано: значение основного поля либо поля отображения из глобальной настройки фильтра.
* Тип определяется для фактически отображаемого поля.
* Для обычного поля отображения сохраняется действующая обработка типа; для вычисляемого применяется правило из п. 2.1.
* Если выполнен fallback к исходному значению, тип определяется для основного поля.
* Фильтрация продолжает выполняться по основному полю. Поле отображения не меняет название и позицию фильтра.
* Правила сопоставления значений не изменяются; поле отображения не добавляется в {{SELECT}} только ради определения типа.

----

h3. 3. Требования к реализации.

h4. 3.1. Получение и сопоставление типа.

* Интеграционный слой должен передавать в механизм XLSX-экспорта данные и доступные метаданные колонок основного результата.
* Метаданные обрабатываются до исключения невидимых колонок из пользовательского представления XLSX.
* Для PostgreSQL используется идентификатор или каноническое описание типа, предоставленное драйвером; для ClickHouse — каноническое имя типа из метаданных ответа.
* Вычисляемое поле сопоставляется с колонкой по внутреннему ключу, позиции проекции или эквивалентной карте, сформированной генератором SQL.
* Пользовательский заголовок, текстовый алиас или текст SQL-выражения не могут быть единственным ключом сопоставления.
* Используется тип полного выражения, уже разрешённый СУБД с учётом {{CASE}}, агрегатов, оконных функций и явных приведений типов.
* Тип не определяется по фактическим значениям, первой строке или первому непустому значению.
* При нуле строк или значениях, состоящих только из {{null}}, используется тип схемы, если он доступен.
* Если экспорт формируется из ранее полученного результата, доступная вместе с ним схема используется без нового запроса. При отсутствии схемы применяется {{string}}.
* Однажды определённая категория переиспользуется во всех листах и файлах текущего экспорта.

Алгоритм обработки:
# Определить фактически отображаемое поле по действующей логике фильтров и «Значений по другому полю».
# Для обычного поля сохранить действующую обработку {{filterType}}.
# Для вычисляемого поля найти однозначно связанную колонку в результирующей схеме основного запроса.
# Если колонка найдена и её тип поддерживается, нормализовать тип в {{number}}, {{string}}, {{date}} или {{datetime}}. Если колонка отсутствует, связь неоднозначна, метаданные типа недоступны либо тип не поддерживается — использовать {{string}}.
# Отформатировать значение, не меняя название, оператор, состав и порядок фильтров.

h4. 3.2. Нормализация типов PostgreSQL и ClickHouse.

|| Категория || PostgreSQL || ClickHouse ||
| {{number}} | {{smallint}}, {{integer}}, {{bigint}}, {{numeric}}/{{decimal}}, {{real}}, {{double precision}} | {{Int*}}, {{UInt*}}, {{Float*}}, {{BFloat16}}, {{Decimal*}} |
| {{string}} | {{character}}, {{character varying}}, {{text}}, {{name}}, {{uuid}}, {{enum}} | {{String}}, {{FixedString}}, {{Enum*}}, {{UUID}}, {{IPv4}}, {{IPv6}} |
| {{date}} | {{date}} | {{Date}}, {{Date32}} |
| {{datetime}} | {{timestamp}} с часовым поясом или без него | {{DateTime}}, {{DateTime64}} |

* Для ClickHouse обёртки {{Nullable(T)}} и {{LowCardinality(T)}} снимаются рекурсивно.
* Каноническое имя ClickHouse разбирается как структура типа. Наличие поддерживаемого типа внутри неподдерживаемой конструкции не определяет категорию всей колонки.
* Домен PostgreSQL относится к категории базового типа, только если базовый тип уже доступен без обращения к БД.
* Любой тип, не разрешённый по указанным правилам, обрабатывается как {{string}}.
* Для других адаптеров или форматов ответа, не предоставляющих поддерживаемый тип, также применяется {{string}} без дополнительного запроса.

h4. 3.3. API и фронтенд.

* Затрагиваемый backend-объект: {{exports}}; используется действующая команда XLSX-экспорта через {{/v1/api/exports}}.
* Структура {{export.parameters.filter}} не изменяется. Обновлённый фронтенд продолжает передавать обязательный {{filterType}}: базовый тип, если он доступен, либо {{calculated}}. Для вычисляемого поля этот признак не является источником итоговой категории.
* Бэкенд определяет, что поле является вычисляемым, по конфигурации визуализации, а не только по значению {{filterType}}.
* Если {{filterType}} отсутствует в запросе обратной совместимости, бэкенд определяет вычисляемое поле по конфигурации визуализации и применяет правило п. 2.1; если поле или его тип определить невозможно, применяется {{string}}. Отсутствие {{filterType}} не должно приводить к ошибке экспорта.
* {{dateFormat}} передаётся по действующей логике и применяется только при итоговой категории {{date}} или {{datetime}}.
* Фронтенд передаёт фильтры в порядке полки «Фильтры» конкретной визуализации.
* Новые API-команды, пользовательские настройки и действия интерфейса не вводятся.

h4. 3.4. SQL и совместимость XLSX.

* Для определения типа используются только метаданные, уже полученные вместе с основным результатом.
* Ради типизации запрещено:
** добавлять вычисляемое выражение или служебную колонку в {{SELECT}};
** добавлять {{pg_typeof}} или {{toTypeName}};
** выполнять дополнительные {{DESCRIBE}}, запросы с {{LIMIT 0}}/{{LIMIT 1}}, metadata-only запросы или обращения к системным каталогам;
** изменять {{WHERE}}, {{HAVING}}, {{GROUP BY}}, {{DISTINCT}}, {{UNION}}, сортировку, лимиты или пагинацию.
* Ошибка определения типа не прерывает экспорт и приводит к {{string}}. Ошибка выполнения самого основного SQL обрабатывается по действующей логике.
* Доработка не изменяет фильтрацию, данные, видимые колонки, итоги, точность или часовой пояс.
* Сохраняется поведение общего шаблона и частного XLSX-шаблона Таблицы: {{Filter}}/{{Filters}} выводят фильтры единым блоком, {{Filters_by_rows}}/{{FiltersByRows}} — построчно; порядок и названия фильтров не изменяются.
* Если частный шаблон не содержит маркера фильтров, блок не добавляется автоматически и типы не определяются только ради отсутствующего блока.
* Если выводимых фильтров нет, маркер очищается по действующей логике без служебных значений и разделителей.
* Метаданные схемы и технические ключи не попадают в XLSX. Блок «Переменные» и дополнительные листы не изменяются.

h3. 4. Пограничные сценарии.

|| Сценарий || Ожидаемое поведение ||
| Вычисляемая колонка присутствует в схеме, но скрыта в XLSX | Используется тип колонки; сама колонка не отображается |
| Выражение используется только в {{WHERE}}/{{HAVING}} или внутреннем запросе | {{string}}; SQL не расширяется |
| Результат содержит ноль строк или только {{null}} | Используется тип схемы; при отсутствии схемы — {{string}} |
| Колонка содержит {{CASE}}, агрегат, оконную функцию или {{CAST}} | Используется итоговый тип колонки, определённый СУБД |
| Тип отсутствует, неизвестен или не поддерживается | {{string}}; экспорт продолжается |
| Два поля имеют одинаковый заголовок либо связь с колонкой неоднозначна | Используется внутренняя связь; при неоднозначности — {{string}} |
| Экспорт выполняется из ранее полученного результата | Используется сохранённая схема; если её нет — {{string}} без обращения к БД |
| Экспорт разбит на несколько листов или файлов | Во всех частях используется одна и та же определённая категория |

h3. 5. Рамки задачи.

*В рамки задачи входит:*
* чтение уже доступных метаданных результирующей схемы основного запроса;
* сопоставление вычисляемого поля с существующей колонкой результата;
* нормализация типов PostgreSQL и ClickHouse;
* оформление значений фильтров по итоговой категории и строковый fallback.

*В рамки задачи не входит:*
* изменение SQL-выражений вычисляемых полей и логики фильтрации;
* добавление полей в результат или выполнение запросов ради типизации;
* изменение механизма «Значения по другому полю»;
* изменение данных, пользовательских колонок, шаблонов, переменных и дополнительных листов;
* сохранение типа в метаданных отчёта, визуализации или набора данных.

----

h3. 6. Критерии приёмки (AC):

AC.1 — *Поддерживаемые категории:*
* *Дано:* последовательно для PostgreSQL и ClickHouse проверяются вычисляемые поля, однозначно связанные с колонками результирующей схемы категорий число, строка, дата и дата-время;
* *Когда:* выполняется экспорт в XLSX;
* *Тогда:* значения форматируются соответственно как {{number}}, {{string}}, {{date}} и {{datetime}} по правилам п. 2.2;
* *И:* для {{date}} и {{datetime}} применяется {{dateFormat}}, а при его отсутствии — действующий формат по умолчанию; компонент времени выводится только при наличии в выбранном формате.

AC.2 — *Поле используется только в фильтре:*
* *Дано:* вычисляемое поле имеет числовое выражение, участвует в {{WHERE}} или {{HAVING}}, но отсутствует в верхнеуровневой результирующей схеме;
* *Когда:* выполняется экспорт;
* *Тогда:* значение {{1500000}} отображается как {{'1500000'}};
* *И:* вычисляемое поле не добавляется в {{SELECT}}, дополнительные запросы не выполняются.

AC.3 — *Невидимая колонка результата:*
* *Дано:* вычисляемое поле связано с колонкой основного результата, которая исключается из видимых колонок XLSX;
* *Когда:* выполняется экспорт;
* *Тогда:* тип этой колонки используется для оформления фильтра;
* *И:* сама колонка не появляется в XLSX и не меняет порядок пользовательских колонок.

AC.4 — *Пустой результат и {{null}}:*
* *Дано:* основной запрос возвращает ноль строк либо только {{null}} в вычисляемой колонке;
* *И:* тип колонки доступен в результирующей схеме;
* *Когда:* формируется блок фильтров;
* *Тогда:* категория определяется по схеме без первой, непустой или фиктивной строки.

AC.5 — *Итоговый тип выражения и нормализация:*
* *Дано:* в результирующей схеме присутствуют вычисляемые колонки с {{CASE}}, агрегатом, оконной функцией или {{CAST}};
* *И:* проверяются типы PostgreSQL и ClickHouse, включая {{Nullable(Decimal(18, 2))}}, {{LowCardinality(String)}} и {{DateTime64(3)}};
* *Когда:* выполняется экспорт;
* *Тогда:* используется итоговый тип каждой колонки, определённый СУБД, и категория соответствует таблице п. 3.2;
* *И:* выражение повторно не анализируется и не вычисляется.

AC.6 — *Безопасный строковый fallback:*
* *Дано:* тип вычисляемой колонки отсутствует, неизвестен, не поддерживается либо колонка сопоставлена неоднозначно;
* *Когда:* выполняется экспорт;
* *Тогда:* значение оформляется как {{string}} независимо от переданного {{filterType}};
* *И:* экспорт не завершается ошибкой определения типа и не обращается к БД за уточнением.

AC.7 — *Приоритет типа СУБД над {{filterType}}:*
* *Дано:* связанная колонка имеет числовой тип, а фронтенд передал {{filterType = "calculated"}}, {{string}} или {{year}};
* *Когда:* выполняется экспорт;
* *Тогда:* значение форматируется как {{number}} по типу колонки;
* *И:* значение {{2024}} выводится без разделителя разрядов по действующему правилу коротких чисел;
* *И:* если связанной колонки нет, применяется {{string}}.

AC.8 — *«Значения по другому полю»:*
* *Дано:* фильтрация выполняется по основному полю, а фактически показывается значение вычисляемого поля отображения;
* *Когда:* выполняется экспорт;
* *Тогда:* при наличии однозначно связанной колонки поддерживаемого типа категория определяется по её типу;
* *И:* при отсутствии такой колонки значение поля отображения оформляется как {{string}} независимо от его {{filterType}};
* *И:* если действующий механизм вернулся к исходному значению, тип определяется для основного поля;
* *И:* название, позиция фильтра и фильтрация по основному полю не изменяются.

AC.9 — *Отсутствие дополнительных SQL-операций:*
* *Дано:* экспорт содержит несколько фильтров по вычисляемым полям, в том числе отсутствующим в результирующей схеме;
* *Когда:* выполняется экспорт;
* *Тогда:* основной SQL, его параметры и число обращений к БД не изменяются ради типизации;
* *И:* отсутствуют дополнительные проекции, {{pg_typeof}}, {{toTypeName}}, {{DESCRIBE}}, metadata-only запросы и обращения к системным каталогам.

AC.10 — *Экспорт из ранее полученного результата и разбиение выгрузки:*
* *Дано:* XLSX формируется из ранее полученного результата либо разбивается на несколько листов или файлов;
* *Когда:* вместе с результатом доступна результирующая схема;
* *Тогда:* тип берётся из этой схемы и одинаково применяется во всех частях выгрузки;
* *И:* при отсутствии схемы применяется {{string}} без нового обращения к БД.

AC.11 — *API, порядок и шаблоны:*
* *Дано:* последовательно проверяются запрос обновлённого фронтенда и запрос обратной совместимости;
* *Когда:* выполняется XLSX-экспорт через {{/v1/api/exports}};
* *Тогда:* обновлённый фронтенд передаёт для каждого фильтра обязательный {{filterType}}, а при неизвестном базовом типе — {{calculated}};
* *И:* запрос обратной совместимости без {{filterType}} не приводит к ошибке, а вычисляемое поле обрабатывается по правилу п. 2.1;
* *И:* фильтры сохраняют порядок полки, названия и формат действующих маркеров;
* *И:* без маркера фильтров частный шаблон не получает блок автоматически;
* *И:* технические метаданные, ключи и скрытые колонки не попадают в XLSX.

AC.12 — *Отсутствие регрессии:*
* *Дано:* экспорт содержит обычные поля, переменные, дополнительные листы, итоги и форматирование визуализации;
* *Когда:* выполняется XLSX-экспорт после доработки;
* *Тогда:* обычные поля продолжают обрабатываться по действующему {{filterType}};
* *И:* фильтрация, данные, видимые колонки, точность, часовой пояс, блок «Переменные» и дополнительные листы не изменяются.
