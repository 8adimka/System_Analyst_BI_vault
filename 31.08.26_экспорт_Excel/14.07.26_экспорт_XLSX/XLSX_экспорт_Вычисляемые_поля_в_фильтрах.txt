h3. Контекст и проблематика.

При экспорте данных визуализации в XLSX значения применённых фильтров форматируются в зависимости от типа поля: как строка, число, дата или дата-время.

Для обычного поля тип доступен в метаданных набора данных. Для вычисляемого поля в метаданных визуализации хранится SQL-выражение, а признак {{calculated}} сообщает только способ формирования поля и не определяет тип результата выражения. Итоговый тип вычисляемого поля определяется СУБД с учётом используемых столбцов, функций, агрегатов и явных приведений типов.

Если при экспорте итоговый тип вычисляемого поля не определяется, то применяется строковая безопасная деградация.

Требуется определять итоговый тип вычисляемого поля при формировании данных экспорта, приводить тип СУБД к поддерживаемой категории XLSX-форматирования и оформлять значение фильтра так же, как значение обычного поля соответствующего типа.

----

h3. Цель задачи.

*Требуется:*
# Для каждого вычисляемого поля, значения которого фактически выводятся в блоке фильтров XLSX, определять итоговый тип его SQL-выражения.
# Использовать тип, определённый СУБД, для фактического выражения экспортируемой визуализации.
# Получать типы всех требуемых вычисляемых полей пакетно: в первую очередь из схемы штатного запроса данных, а для полей, отсутствующих в этой схеме, — одной общей операцией описания типов, если она необходима. Отдельное обращение к БД для каждого поля не допускается.
# Нормализовать тип СУБД в одну из категорий форматирования: {{number}}, {{string}}, {{date}}, {{datetime}}; семантическую категорию {{year}} сохранять по действующим правилам.
# Применять к значениям фильтров действующие правила оформления строк, чисел, дат, даты-времени, списочных, сравнительных и диапазонных условий.
# Не изменять состав и порядок фильтров, SQL-условия фильтрации, результат выборки и состав видимых колонок XLSX.
# Обеспечить безопасную деградацию, если итоговый тип вычисляемого поля определить невозможно.

_Пользовательская история:_
Как пользователь аналитического портала, я хочу видеть значения фильтров по вычисляемым полям в XLSX в соответствии с их фактическим типом, чтобы числовые, строковые и датовые типы данных читались однозначно, независимо от того получено ли данное значение через обычные поля набора данных или через вычисляемые поля.

----

h3. 1. Ключевые понятия.

* *Вычисляемое поле* — поле визуализации, значение которого формируется SQL-выражением, сохранённым в метаданных визуализации. Выражение может использовать поля набора данных, функции СУБД, агрегаты, переменные и явные приведения типов.
* *Итоговый тип вычисляемого поля* — тип результата полного SQL-выражения после разрешения функций, агрегатов, ветвей {{CASE}}, приведений типов и иных конструкций конкретным SQL-диалектом.
* *Поле фильтрации* — основное поле, по которому формируется условие фильтрации и отбираются данные.
* *Поле отображения* — поле, значения которого выводятся пользователю при действующей настройке «Значения по другому полю».
* *Источник отображаемого значения* — поле, из которого получено конкретное значение, выводимое в XLSX. Тип именно этого поля определяет формат отображения значения.
* *Служебная проекция* — техническое выражение или колонка результата, используемые только для определения типа. Служебная проекция не является пользовательской колонкой и не должна попадать в XLSX.

----

h3. 2. Описание текущего поведения.

* В запросе XLSX-экспорта объект фильтра передаётся в массиве {{export.parameters.filter}} и содержит {{name}}, {{values}}, {{filterType}} и, при необходимости, {{dateFormat}}.
* Для обычных полей фронтенд разрешает тип до поддерживаемой категории форматирования.
* Для вычисляемого поля признак {{calculated}} сам по себе не позволяет определить, возвращает ли выражение число, строку, дату или дату-время.
* Фронтенд не может отнозначно разрешать тип вычисляемого поля и может передавать {{filterType = "calculated"}}, бэкенд применяет действующую строковую безопасную деградацию.
* Бэкенд не использует фактический тип результата SQL-выражения как единый источник истины для форматирования фильтра по вычисляемому полю.

----

h3. 3. Описание целевого поведения.

h4. 3.1. Основное правило.

* После определения итогового типа вычисляемое поле должно форматироваться как обычное поле той же категории:
** по правилам числового поля;
** по правилам строкового поля;
** по правилам даты или даты-времени.
* Определение типа влияет только на оформление значения в информационном блоке фильтров XLSX. Оно не должно изменять само значение фильтра, оператор, логику отбора данных или результат вычисляемого выражения.

---

h4. 3.2. Какое поле необходимо типизировать.

Категория форматирования определяется по полю, которое действующий механизм XLSX-экспорта уже выбрал как источник отображаемых значений фильтра:

# Если настройка «Значения по другому полю» не применяется, типизируется основное поле фильтрации.
# Если действующий механизм успешно использует поле отображения, типизируется поле отображения.
# Если действующий механизм применил предусмотренную им безопасную деградацию к основному полю, типизируется основное поле.

Дополнительные правила:
* наличие поля отображения и результат сопоставления определяются действующим механизмом глобальной настройки «Значения по другому полю»; нельзя определять поле отображения только по локальным метаданным экспортируемой визуализации;
* данная задача не изменяет правила сопоставления основного поля и поля отображения, не вводит новое частичное сопоставление и не меняет состав выводимых значений;
* если действующий механизм уже определяет источник отдельно для каждого значения, механизм типизации использует этот готовый результат без изменения сопоставления;
* если основное поле является вычисляемым, а действующий механизм использует обычное строковое поле отображения, значения форматируются как строки;
* вычисляемое поле отображения обрабатывается только в том случае, если выбор такого поля уже поддерживается действующим механизмом; новая возможность выбора вычисляемого поля в этой настройке не вводится;
* если фактически отображаемое значение имеет тип {{date}} или {{datetime}}, применяется формат поля — источника отображаемого значения, доступный действующему механизму экспорта; при отсутствии такого формата применяется действующий формат по умолчанию;
* имя поля отображения не должно подменять название фильтра, а поле отображения не должно становиться полем фильтрации.

---

h4. 3.3. Сценарии по итоговому типу.

|| Итоговая категория || Правило отображения || Пример результата в XLSX ||
| {{number}} | Без одинарных кавычек; разделители разрядов и точность — по действующим правилам экспорта. Дополнительное округление не выполняется. | {{Сумма: 1 500 000,50}} |
| {{string}} | Каждое значение выводится в одинарных кавычках; действующая обработка кавычки внутри значения сохраняется. | {{Регион: 'Москва', 'Санкт-Петербург'}} |
| {{date}} | Без одинарных кавычек; применяется {{dateFormat}}, переданный для фильтра, либо действующий формат по умолчанию {{ДД.ММ.ГГГГ}}. | {{Дата заказа >= 01.01.2025 И <= 31.01.2025}} |
| {{datetime}} | Без одинарных кавычек; применяется действующий формат визуализации. Компонент времени выводится, если он предусмотрен выбранным форматом. | {{Момент обновления >= 01.01.2025 10:30}} |
| {{year}} | Без одинарных кавычек и без разделителей разрядов. {{year}} является семантическим признаком и не выводится только из SQL-типа integer. | {{Год: 2024}} |
| тип не определён | Значение обрабатывается как {{string}}: каждое значение выводится в одинарных кавычках; разделители разрядов и преобразование к дате не применяются. | {{Значение: '1500000'}} |

* Для списочного фильтра сохраняется формат {{Название: Значение1, Значение2}}.
* Для сравнительного или диапазонного фильтра сохраняется формат без двоеточия перед оператором.
* Операторы {{=}}, {{<>}}, {{>}}, {{>=}}, {{<}}, {{<=}}, {{~}} и связки {{ И }} / {{ ИЛИ }} не изменяются.
* Правила не зависят от того, выводится блок фильтров единым текстом или построчно.

----

h3. 4. Требования к определению типа.

h4. 4.1. Источник истины и приоритеты.

Для вычисляемого поля использовать следующий приоритет:

# Если тип, полученный от СУБД, успешно нормализован в {{number}}, {{string}}, {{date}} или {{datetime}}, использовать эту категорию.
# Если тип от СУБД получить невозможно либо он не поддерживается правилами нормализации, использовать переданный поддерживаемый базовый {{filterType}}: {{number}}, {{string}}, {{date}}, {{datetime}} или {{year}}.
# Если поддерживаемый базовый {{filterType}} отсутствует либо передано {{calculated}}, применить строковую безопасную деградацию.

Дополнительные правила приоритета:
* Для вычисляемого поля базовый {{filterType}}, переданный фронтендом, является резервным признаком. При конфликте базовой категории с типом, определённым СУБД, используется категория СУБД.
* Исключение — {{year}}: если СУБД подтвердила числовой итоговый тип и фронтенд передал {{filterType = "year"}}, сохраняется категория {{year}}. Если итоговый тип СУБД не является числовым, признак {{year}} не применяется.
* Для обычного, невычисляемого поля действующий порядок определения {{filterType}} не меняется.
* Тип определяется по SQL-выражению, а не по фактическому значению, первой непустой строке или строковому виду значения.
* {{null}} в данных не должен изменять категорию поля: сначала снимаются обёртки nullable-типа, затем определяется базовая категория.

---

h4. 4.2. Основной способ получения типа.

* Основной способ — использовать метаданные результирующей схемы того же запроса, который выполняется для получения данных экспорта:
** для PostgreSQL — идентификатор типа результирующей колонки из {{RowDescription}} либо эквивалентного API фактически используемого драйвера;
** для ClickHouse — имя и каноническое имя типа из заголовка Native-протокола либо из блока {{meta}} фактически используемого формата ответа.
* Интеграционный слой работы с БД должен сохранять и передавать в механизм XLSX-экспорта метаданные результирующих колонок, а не только массив строк.
* Определять категорию по runtime-типу значения в приложении запрещено.
* Если текущий адаптер получает метаданные от СУБД, но отбрасывает их, сохранение и передача этих метаданных в механизм XLSX-экспорта входят в рамки задачи.
* Для каждого фактически используемого адаптера PostgreSQL и ClickHouse необходимо проверить получение метаданных при результате в ноль строк.
* Метаданные схемы должны обрабатываться независимо от количества строк. При результате в ноль строк типы должны определяться по описанию результирующих колонок; фиктивная строка в пользовательские данные не добавляется.
* Если вычисляемое поле уже присутствует в результирующей схеме запроса данных, необходимо переиспользовать тип этой колонки.
* Если вычисляемое поле используется только в фильтре либо как поле отображения и отсутствует среди видимых колонок, тип необходимо получить одним из способов в указанном порядке:
** добавить проекцию исходного вычисляемого выражения в описываемую результирующую схему текущего запроса, если это безопасно для его SQL-структуры;
** если безопасная проекция в текущий запрос невозможна — выполнить не более одной пакетной операции описания результирующей схемы для всех ещё не типизированных вычисляемых выражений текущего экспорта;
** если адаптер СУБД не поддерживает безопасное описание типа — применить приоритет резервных источников из п. 4.1.
* Пакетная операция описания схемы предназначена только для разрешения типов и не должна выполнять отдельную выборку пользовательских данных. Она допускается как одно дополнительное обращение на текущий экспорт только тогда, когда штатный запрос данных не предоставляет нужные типы и безопасно расширить его результирующую схему невозможно.
* Служебная проекция должна добавляться на том уровне SQL-запроса, где выражение валидно и где её добавление не меняет семантику {{GROUP BY}}, {{HAVING}}, {{DISTINCT}}, {{UNION}}, оконных функций, сортировки, лимитов и пагинации.
* Нельзя добавлять исходные столбцы выражения в {{GROUP BY}} или иным способом менять запрос только для того, чтобы служебная проекция стала синтаксически допустимой.

---

h4. 4.3. Допустимый резервный способ через функции СУБД.

Если используемый драйвер или текущий слой экспорта не позволяет получить тип нужного выражения непосредственно из результирующей схемы, допускается определить тип техническим выражением в штатном SQL-запросе экспорта:

* PostgreSQL — {{pg_typeof(<выражение>)}};
* ClickHouse — {{toTypeName(<выражение>)}}.

Пример служебного расширения запроса для PostgreSQL:

{code:sql}
SELECT
  city,
  order_date,
  sales_amount * coefficient AS "calc_amount",
  pg_typeof(sales_amount * coefficient) AS "__mbi_calc_type_<internal_key>"
FROM source_table
WHERE ...
{code}

Для данного способа обязательны следующие условия:
* способ не применяется, если тип исходного выражения уже доступен в метаданных результирующей схемы;
* все требуемые типы добавляются пакетно в один штатный запрос данных; отдельный запрос для каждого вычисляемого поля запрещён;
* служебный алиас и внутренняя карта соответствия должны однозначно связывать полученный тип с конкретным вычисляемым полем по внутреннему ключу/связи, фактически доступным в текущей конфигурации экспортируемой визуализации; пользовательский заголовок не может быть единственным ключом;
* при непустом результате бэкенд использует первое полученное значение каждой служебной колонки типа; при этом необходимо учитывать, что СУБД и драйвер могут вычислить, сериализовать и передать такое значение для каждой строки результата;
* при нуле строк значение функции отсутствует, а метаданные самой служебной колонки нельзя интерпретировать как тип исходного выражения: они описывают результат функции {{pg_typeof}}/{{toTypeName}}, то есть {{regtype}}/{{String}};
* при нуле строк используется тип проекции исходного выражения из результирующей схемы или пакетной операции описания схемы по п. 4.2, затем переданный базовый {{filterType}}, затем строковая безопасная деградация;
* способ через {{pg_typeof}}/{{toTypeName}} не считается бесплатным каналом метаданных и применяется только при допустимом влиянии на размер результата и время экспорта; для больших и партиционированных выгрузок приоритет имеет получение типа из схемы без повторяющихся служебных значений в строках;
* запрещено дополнительно вычислять недетерминированное/volatile-выражение, выражение с побочными эффектами или пользовательскую функцию только ради определения типа; для таких выражений используются метаданные схемы, пакетная операция описания либо fallback;
* техническое выражение не должно делать исходно валидный запрос невалидным. Если его нельзя безопасно встроить в текущую форму SQL, необходимо использовать основной способ по метаданным либо fallback, не изменяя исходный запрос данных;
* служебная колонка не должна попадать в XLSX, увеличивать число пользовательских колонок, участвовать в сопоставлении с шаблоном, итогах, подытогах, сортировке или фильтрации.

---

h4. 4.4. Обработка вычисляемого поля, отсутствующего в видимых данных.

* Вычисляемое поле может участвовать в применённом фильтре, не находясь на полках, формирующих видимые колонки экспортируемой визуализации.
* Отсутствие поля в видимой части выгрузки не является основанием для строковой типизации, если выражение и тип можно определить в рамках текущего экспорта.
* Бэкенд должен получить актуальное SQL-выражение из метаданных и контекста именно экспортируемой визуализации. Сопоставление только по {{name}} или пользовательскому заголовку не допускается.
* Для сопоставления необходимо использовать внутренний ключ/связь между конфигурацией поля и сформированной SQL-проекцией. Пользовательский заголовок не может быть единственным ключом.
* До начала реализации требуется проверить и зафиксировать в техническом решении фактический путь этой связи в payload экспорта. Если текущих данных недостаточно, необходимо расширить внутреннюю структуру действующего запроса экспорта техническим идентификатором без введения пользовательской настройки или новой API-команды.
* Служебное добавление выражения не означает добавление новой видимой колонки и не должно изменять структуру первого или дополнительных листов XLSX.

---

h4. 4.5. Пакетность и повторное использование результата.

* До выполнения запроса бэкенд должен сформировать уникальный список вычисляемых полей, типы которых требуются для оформления фильтров.
* Одно вычисляемое поле, использованное несколькими фильтрами или одновременно как видимое поле и поле фильтра, типизируется один раз в рамках одного экспорта.
* Типы нескольких вычисляемых полей должны определяться в одном описании/выполнении штатного запроса либо одной пакетной операцией описания схемы, а не последовательными запросами к БД.
* Если экспорт разбивается на несколько листов, страниц или файлов, однажды определённый тип переиспользуется во всех частях текущего экспорта.
* Сохранять полученный тип в метаданных отчёта или визуализации не требуется. Изменение выражения или набора данных должно учитываться при следующем экспорте автоматически.
* Если текущий сценарий экспорта не выполняет запрос к БД и формирует XLSX из уже полученных данных, отдельное обращение к БД только ради оформления фильтров не выполняется: используется переданный базовый {{filterType}}, затем fallback.

---

h4. 4.6. Алгоритм обработки.

# Определить по текущей логике состав фильтров, который должен быть выведен для экспортируемой визуализации, и сохранить исходную последовательность {{export.parameters.filter}}.
# Если информационный блок фильтров по текущей логике не выводится, не выполнять типизацию и не добавлять служебные SQL-проекции только ради этого блока.
# Для каждого выводимого фильтра получить уже выбранный действующим механизмом источник отображаемых значений: основное поле либо поле отображения.
# Сформировать уникальный список вычисляемых полей, тип которых требуется для фактически отображаемых значений.
# Получить типы из результирующей схемы штатного запроса; для неразрешённых полей применить одну пакетную операцию описания схемы либо допустимый резервный способ.
# Нормализовать типы СУБД и применить приоритеты из п. 4.1.
# Отформатировать значения по итоговой категории, не меняя операторы, состав и порядок фильтров.
# Удалить все служебные проекции и данные типов до сопоставления пользовательских колонок с XLSX-шаблоном.
# Сформировать XLSX по действующей логике и переиспользовать определённые категории во всех частях текущего экспорта.

----

h3. 5. Нормализация типов СУБД.

h4. 5.1. Общие правила.

* Полное имя типа СУБД необходимо нормализовать до продуктовой категории форматирования.
* Обёртки nullability и низкой кардинальности не меняют базовую категорию и должны сниматься рекурсивно.
* Для доменного типа PostgreSQL используется его базовый тип.
* Явное приведение типа в вычисляемом SQL-выражении имеет приоритет, поскольку СУБД возвращает тип результата уже после приведения.
* Для {{CASE}}, арифметических выражений, агрегатных и оконных функций используется общий итоговый тип выражения, разрешённый СУБД.
* Список примеров ниже задаёт правила по семействам и не должен реализовываться как проверка только нескольких буквальных строк.

---

h4. 5.2. PostgreSQL.

|| Семейство типа PostgreSQL || Категория XLSX ||
| {{smallint}}, {{integer}}, {{bigint}}, {{numeric}}/{{decimal}}, {{real}}, {{double precision}} и эквивалентные числовые домены | {{number}} |
| {{character}}, {{character varying}}, {{text}}, {{name}}, {{uuid}}, enum и домены, базовый тип которых входит в данный перечень | {{string}} |
| {{date}} | {{date}} |
| {{timestamp}} без/с часовым поясом | {{datetime}} |
| {{boolean}}, {{time}}, {{interval}}, {{json}}/{{jsonb}}, {{xml}}, {{bytea}}, сетевые, геометрические, массивы, составные, диапазонные и иные типы без действующего правила форматирования | тип не определён; применяется fallback |

* Типы PostgreSQL классифицируются по каноническому идентификатору типа, а не только по отображаемому имени.
* Для домена базовый тип определяется рекурсивно через возможности драйвера, реестр типов либо пакетное обращение к системному каталогу. Запрос к системному каталогу для каждого отдельного поля запрещён.

---

h4. 5.3. ClickHouse.

|| Семейство типа ClickHouse || Категория XLSX ||
| {{Int*}}, {{UInt*}}, {{Float*}}, {{BFloat16}}, {{Decimal*}} | {{number}} |
| {{String}}, {{FixedString}}, {{Enum*}}, {{UUID}}, {{IPv4}}, {{IPv6}} | {{string}} |
| {{Date}}, {{Date32}} | {{date}} |
| {{DateTime}}, {{DateTime64}} | {{datetime}} |
| {{Nullable(T)}} | снять {{Nullable}} и определить категорию для {{T}} |
| {{LowCardinality(T)}} | снять {{LowCardinality}} и определить категорию для {{T}} |
| {{Bool}}, {{Nothing}}, {{Dynamic}}, {{Variant}}, {{Array}}, {{Tuple}}, {{Map}}, {{Nested}}, {{Object}}/{{JSON}}, агрегатные состояния и иные типы без действующего правила форматирования | тип не определён; применяется fallback |

* Вложенные комбинации, например {{LowCardinality(Nullable(String))}} или {{Nullable(Decimal(18, 2))}}, должны нормализоваться до базовой категории рекурсивно.
* {{Nullable(Nothing)}} и аналогичный неразрешённый тип не должны ошибочно классифицироваться как строка, число или дата; применяется fallback.
* Каноническое имя типа ClickHouse необходимо разбирать как вложенную структуру типа; поиск категории только по совпадению подстроки не допускается.

h3. 6. Требования к реализации.

h4. 6.1. Фронтенд-часть.

* Формировать запрос XLSX-экспорта по текущей логике для конкретной выбранной визуализации.
* Продолжать передавать массив {{export.parameters.filter}} в порядке элементов полки «Фильтры».
* Сохранять действующую структуру объекта фильтра: {{name}}, {{values}}, обязательный {{filterType}} и опциональный {{dateFormat}}.
* Для вычисляемого поля передавать поддерживаемый базовый {{filterType}}, если он доступен. Если тип определить невозможно, передавать {{filterType = "calculated"}}.
* Обновлённый фронтенд не должен формировать объект фильтра без {{filterType}}. Обработка отсутствующего {{filterType}} сохраняется на бэкенде только для обратной совместимости с ранее сформированными запросами.
* Для фильтра, фактическим источником отображаемых значений которого является вычисляемое поле типа дата/дата-время, передавать {{dateFormat}} этого источника по действующему приоритету настроек. Если формат недоступен, {{dateFormat}} не передаётся и бэкенд применяет действующий формат по умолчанию. Механизм определения SQL-типа не определяет маску отображения даты и не заменяет {{dateFormat}}.
* Обеспечить в текущем payload однозначную связь между записью фильтра, конфигурацией поля и метаданными вычисляемого выражения. Используется внутренний ключ/связь, фактически доступные в текущей спецификации; отображаемое название не должно использоваться как единственный ключ сопоставления.
* Не добавлять пользовательские настройки, новые шаблонные маркеры или отдельное действие интерфейса для определения типа.

---

h4. 6.2. Бэкенд-часть и API.

* Затрагиваемый backend-объект: {{exports}}.
* Команда: действующая команда XLSX-экспорта через {{/v1/api/exports}}; новая команда API не требуется, актуальное значение {{command.name}} сохраняется из текущего контракта.
* До форматирования блока фильтров определить источники отображаемых значений и список требуемых вычисляемых полей.
* Для каждого вычисляемого поля использовать фактическое SQL-выражение из спецификации экспортируемой визуализации и текущего генератора SQL. Нельзя повторно собирать выражение из отображаемого названия.
* Получить и нормализовать типы до удаления служебных проекций из результата.
* Сопоставлять тип с фильтром по однозначному внутреннему ключу/связи из текущей конфигурации визуализации. Одинаковые заголовки вычисляемых полей не должны приводить к подмене типов.
* Сохранять исходную последовательность объектов {{export.parameters.filter}} после определения типов и форматирования.
* Не изменять сохранённые метаданные отчёта, визуализации, набора данных или вычисляемого поля.
* Отсутствие, неподдерживаемый формат или ошибка нормализации уже полученных метаданных типа не должны прерывать экспорт: используется резервный {{filterType}}, затем fallback.
* Служебный механизм определения типа не должен создавать дополнительную точку отказа единственного запроса данных. Если техническая проекция может завершиться собственной SQL-ошибкой, она не встраивается в запрос данных и выполняется через изолированную пакетную операцию описания типа либо не выполняется.
* Если само вычисляемое выражение невалидно и из-за него исходный запрос данных/фильтрации не может быть выполнен, применяется действующая обработка ошибки запроса. Fallback типа не должен маскировать ошибку исходного SQL.

---

h4. 6.3. SQL-логика и ограничения.

* Поддержать определение типов для PostgreSQL и ClickHouse.
* Для других SQL-диалектов до появления отдельной поддержки использовать переданный {{filterType}} и действующую безопасную деградацию; неподдерживаемая СУБД не должна приводить к ошибке экспорта.
* Не менять предикаты {{WHERE}}/{{HAVING}}, связи {{AND}}/{{OR}}, набор параметров, {{GROUP BY}}, сортировку, лимиты и правила применения глобальных/локальных фильтров.
* Не менять число строк, итоговые/подытоговые значения, точность вычислений и часовой пояс данных.
* При подстановке переменных определять тип фактического выражения текущего экспорта. Состав блока «Переменные» определяется только по исходным выражениям и запросу экспортируемой визуализации: переменная, реально используемая исходным вычисляемым полем и влияющая на расчёт визуализации, продолжает выводиться один раз. Служебная проекция того же выражения не считается дополнительным использованием, не добавляет новую переменную, не исключает уже используемую переменную и не создаёт дубликат.
* Не выполнять преобразование высокоточных чисел через тип, способный потерять точность. Определение категории {{number}} не является основанием для изменения исходного значения.
* Служебные алиасы должны экранироваться средствами текущего генератора SQL и не должны допускать коллизий с пользовательскими алиасами.
* Не выполнять отдельный полноценный запрос данных или сетевой round-trip для каждого вычисляемого поля.
* Если штатная результирующая схема не содержит типы части вычисляемых полей и безопасная служебная проекция невозможна, допускается не более одной пакетной metadata-only операции описания типов на текущий экспорт. N+1-запросы и отдельная операция для каждого поля запрещены.

---

h4. 6.4. Формирование XLSX.

* Действующие правила применяются одинаково в общем XLSX-шаблоне и в частном XLSX-шаблоне Таблицы.
* Правила типизации применяются к существующим маркерам {{Filter}}, {{Filters}}, {{Filters_by_rows}} и поддерживаемым текущей реализацией алиасам, включая {{FiltersByRows}}; новые маркеры и алиасы не вводятся.
* Для {{Filter}} и {{Filters}} сохраняется вывод фильтров в одну строку с действующим разделителем {{; }}.
* Для {{Filters_by_rows}}/{{FiltersByRows}} и действующего построчного режима общего шаблона сохраняется вывод каждого фильтра с новой строки.
* Если частный шаблон не содержит ни одного действующего маркера фильтров, блок фильтров не добавляется автоматически. Определение типов и добавление служебных проекций только ради отсутствующего информационного блока не выполняются, если те же данные не требуются другой действующей логике экспорта.
* Служебные выражения, алиасы и значения типов не должны отображаться:
** в заголовках или строках данных;
** в блоках «Фильтры» и «Переменные»;
** в итогах и подытогах;
** на дополнительных листах шаблона;
** в сопоставлении колонок с эталонной строкой шаблона.
* Порядок фильтров остаётся порядком массива {{export.parameters.filter}}, сформированного по полке «Фильтры».
* Порядок значений внутри фильтра, названия фильтров, разделители и взаимное расположение блоков XLSX не изменяются.
* При разбиении экспорта на несколько листов или файлов одно и то же правило типа и форматирования должно применяться во всех частях.

----

h3. 7. Пограничные сценарии и безопасная деградация.

* Вычисляемое поле используется только в фильтре и не выводится среди колонок данных.
* Вычисляемое поле используется только как поле отображения в настройке «Значения по другому полю».
* Основное и поле отображения являются вычисляемыми и имеют разные итоговые типы.
* Действующий механизм «Значения по другому полю» применил предусмотренную им безопасную деградацию к основному полю.
* Запрос экспорта вернул ноль строк; информационный блок фильтров при этом формируется по текущей логике.
* Все значения вычисляемого поля равны {{null}}, но тип выражения определён схемой результата.
* Выражение содержит {{CASE}}, явное приведение типа, агрегатную или оконную функцию.
* Выражение участвует в {{HAVING}} или используется в агрегированной визуализации.
* Несколько вычисляемых полей имеют одинаковые отображаемые названия.
* Одно вычисляемое поле используется несколькими фильтрами.
* Вычисляемое поле переименовано; сопоставление должно выполняться по текущей однозначной связи конфигурации, а не по отображаемому названию.
* Вычисляемое поле удалено либо его выражение недоступно в метаданных экспортируемой визуализации.
* СУБД вернула обёрнутый, доменный, неподдерживаемый или неизвестный тип.
* Переданный {{filterType}} противоречит типу СУБД.
* Экспорт выполняется без нового запроса к БД.
* Экспорт разбивается на несколько страниц, листов или файлов.
* Служебный способ определения типа невозможно безопасно встроить в конкретную форму SQL.

Во всех сценариях ошибка определения категории типа не должна сама по себе приводить к падению экспорта. Применяется приоритет резервных источников из п. 4.1, сохраняются исходное значение, позиция фильтра и текущая логика формирования XLSX.

----

h3. 8. Рамки задачи.

*В рамки задачи входит:*
* определение итогового типа вычисляемых полей, значения которых используются в блоке фильтров XLSX;
* нормализация типов PostgreSQL и ClickHouse;
* применение существующих правил форматирования фильтров по полученной категории;
* обработка вычисляемых полей, отсутствующих среди видимых колонок;
* безопасная деградация и сохранение обратной совместимости.

*В рамки задачи не входит:*
* изменение конструктора или синтаксиса вычисляемых полей;
* изменение логики применения фильтров и генерации их предикатов;
* изменение форматирования ячеек с данными визуализации, не относящихся к информационному блоку фильтров;
* изменение блока «Переменные»;
* изменение механизма «Значения по другому полю», кроме выбора типа фактически отображаемого значения;
* расширение перечня полей, доступных как основное поле или поле отображения в настройке «Значения по другому полю»;
* добавление новых XLSX-маркеров, листов или пользовательских настроек;
* обязательное кеширование типа в метаданных визуализации;
* реализация определения типа средствами СУБД для SQL-диалектов, отличных от PostgreSQL и ClickHouse.

----

h3. 9. Критерии приёмки (AC).

AC.1 — *Числовое вычисляемое поле:*
* *Дано:* применён фильтр по вычисляемому полю с выражением, итоговый тип которого СУБД определяет как числовой;
* *И:* выбрано значение {{1500000}};
* *Когда:* пользователь экспортирует визуализацию в XLSX;
* *Тогда:* в блоке фильтров отображается числовое значение без одинарных кавычек и с действующим разделителем разрядов: {{1 500 000}};
* *И:* дополнительное округление значения не выполняется;
* *И:* для высокоточного {{Decimal}} исходные цифры и дробная часть не теряются из-за преобразования типа в приложении.

AC.2 — *Строковое вычисляемое поле:*
* *Дано:* применён фильтр по вычисляемому полю, итоговый тип которого СУБД определяет как строковый;
* *И:* выбраны значения «Диван» и «Кресло»;
* *Когда:* выполняется экспорт в XLSX;
* *Тогда:* значения отображаются по строковым правилам: {{'Диван', 'Кресло'}};
* *И:* результат вычисляемого поля типа {{uuid}}/{{UUID}} также форматируется как строка, а не как число.

AC.3 — *Вычисляемое поле типа дата и дата-время:*
* *Дано:* применены фильтры по двум вычисляемым полям с итоговыми типами {{date}} и {{datetime}};
* *Когда:* выполняется экспорт в XLSX;
* *Тогда:* при наличии {{dateFormat}} дата и дата-время выводятся без одинарных кавычек в переданном формате;
* *И:* компонент времени выводится только тогда, когда он предусмотрен форматом даты-времени;
* *И:* если {{dateFormat}} отсутствует, равен {{null}}, пустой строке или {{-}}, применяется действующий формат по умолчанию {{ДД.ММ.ГГГГ}}.

AC.4 — *Итоговый тип определяется по полному выражению:*
* *Дано:* последовательно проверяются вычисляемые поля: с выражением {{CASE}}, с агрегатной функцией и с явным приведением типа;
* *Когда:* выполняется экспорт визуализации;
* *Тогда:* для каждого из трёх вариантов категория форматирования соответствует итоговому типу полного выражения, определённому СУБД, а не типу отдельного исходного столбца;
* *И:* SQL-выражение, агрегация и результат выборки не изменяются механизмом типизации.

AC.5 — *Несколько вычисляемых полей типизируются пакетно:*
* *Дано:* в блок XLSX входят фильтры по нескольким вычисляемым полям с числовым, строковым и датовым результатом;
* *Когда:* бэкенд получает данные экспорта;
* *Тогда:* типы полей определяются в рамках описания/выполнения штатного запроса либо одной пакетной metadata-only операцией без отдельного обращения к БД для каждого поля;
* *И:* по журналу запросов подтверждено, что число операций определения типа не зависит от количества вычисляемых полей, листов или файлов текущего экспорта;
* *И:* если использована metadata-only операция, она возвращает только описание схемы и не возвращает пользовательские строки данных;
* *И:* каждый тип сопоставляется со своим полем по однозначному внутреннему ключу/связи, доступным в текущей конфигурации, без использования отображаемого названия как единственного ключа;
* *И:* порядок фильтров после типизации не изменяется.

AC.6 — *Поле используется только в фильтре агрегатной визуализации:*
* *Дано:* вычисляемое выражение используется в {{WHERE}}, отсутствует в видимых колонках, а результирующий запрос содержит {{GROUP BY}} и {{HAVING}};
* *Когда:* пользователь выполняет экспорт в XLSX;
* *Тогда:* поле не добавляется в {{GROUP BY}}, предикаты {{WHERE}}/{{HAVING}} и результат выборки не изменяются;
* *И:* при доступности безопасной проекции или пакетного механизма описания определяется тип СУБД;
* *И:* при недоступности этих механизмов применяется {{filterType}}, затем строковая безопасная деградация;
* *И:* вычисляемое поле, служебная проекция и служебный алиас не появляются среди пользовательских колонок XLSX.

AC.7 — *Пустой результат запроса:*
* *Дано:* к визуализации применён фильтр по вычисляемому полю;
* *И:* запрос данных экспорта возвращает ноль строк;
* *Когда:* формируется XLSX;
* *Тогда:* если исходное вычисляемое выражение присутствует в результирующей схеме, категория определяется по метаданным этой колонки; в остальных случаях применяется пакетное описание либо резервный приоритет;
* *И:* механизм не требует наличия первой строки и не добавляет фиктивную строку данных;
* *И:* тип {{regtype}} или {{String}} в метаданных служебной колонки {{pg_typeof}}/{{toTypeName}} не принимается за итоговый тип вычисляемого поля;
* *И:* экспорт и блок фильтров формируются по текущей логике пустого результата.

AC.8 — *Нормализация обёрнутых типов ClickHouse:*
* *Дано:* вычисляемые поля имеют итоговые типы {{Nullable(Decimal(18, 2))}}, {{LowCardinality(String)}} и {{DateTime64(3)}};
* *Когда:* выполняется экспорт из ClickHouse;
* *Тогда:* поля нормализуются соответственно в {{number}}, {{string}} и {{datetime}} и форматируются по этим категориям.

AC.9 — *Доменный тип PostgreSQL:*
* *Дано:* вычисляемое поле возвращает доменный тип PostgreSQL, базовым типом которого является {{numeric}} или {{date}};
* *Когда:* выполняется экспорт;
* *Тогда:* категория определяется по базовому типу домена: {{number}} или {{date}}.

AC.10 — *Значения по другому полю:*
* *Дано:* основное вычисляемое поле фильтра имеет числовой тип;
* *И:* настройка «Значения по другому полю» возвращает строковые значения, которые успешно сопоставлены;
* *Когда:* выполняется экспорт;
* *Тогда:* в XLSX выводятся строковые отображаемые значения в одинарных кавычках;
* *И:* фильтрация данных продолжает выполняться по числовому основному полю;
* *И:* поведение при отсутствии отображаемого значения соответствует действующей логике механизма «Значения по другому полю» и данной задачей не изменяется.

AC.11 — *Конфликт типа СУБД и {{filterType}}:*
* *Дано:* для вычисляемого поля фронтенд передал {{filterType = "string"}}, а СУБД определила итоговый тип выражения как числовой;
* *Когда:* выполняется экспорт;
* *Тогда:* значение форматируется как число по типу СУБД;
* *И:* конфликт не приводит к ошибке экспорта и не меняет исходное значение фильтра.

AC.12 — *Семантический тип {{year}}:*
* *Дано:* СУБД определила итоговый тип вычисляемого поля как числовой;
* *И:* фронтенд передал {{filterType = "year"}};
* *Когда:* экспортируется значение {{2024}};
* *Тогда:* значение отображается как {{2024}} без разделителя разрядов и без кавычек.

AC.13 — *Неопределённый или неподдерживаемый тип:*
* *Дано:* тип вычисляемого поля не удалось получить либо СУБД вернула неподдерживаемый составной тип;
* *Когда:* выполняется экспорт;
* *Тогда:* при наличии поддерживаемого базового {{filterType}} применяется он;
* *И:* при отсутствии поддерживаемого базового типа каждое значение обрабатывается как {{string}}: выводится в одинарных кавычках, без числового форматирования и преобразования к дате;
* *И:* ошибка определения типа не прерывает формирование XLSX.

AC.14 — *Экспорт без обращения к БД:*
* *Дано:* XLSX формируется из уже полученных данных и штатный сценарий не выполняет новый запрос к БД;
* *Когда:* в фильтрах присутствует вычисляемое поле;
* *Тогда:* отдельный запрос к БД только для определения типа не выполняется;
* *И:* используется переданный базовый {{filterType}}, затем действующая безопасная деградация.

AC.15 — *Служебные данные не попадают в XLSX:*
* *Дано:* для определения типов использованы служебные проекции или {{pg_typeof}}/{{toTypeName}};
* *Когда:* сформирован итоговый файл;
* *Тогда:* в пользовательских заголовках, строках данных, блоках фильтров/переменных, итогах и дополнительных листах отсутствуют служебные колонки, алиасы и значения типов;
* *И:* число и порядок пользовательских колонок совпадают с экспортом без служебной типизации;
* *И:* состав блока «Переменные» соответствует составу исходного запроса визуализации; служебная проекция не добавляет, не исключает и не дублирует переменные.

AC.16 — *Сохранение порядка и шаблонов:*
* *Дано:* на полке «Фильтры» применены обычные и вычисляемые поля в заданной последовательности;
* *И:* используется общий шаблон либо частный шаблон с действующим маркером фильтров;
* *Когда:* выполняется экспорт;
* *Тогда:* вычисляемые поля форматируются по итоговым типам, а все фильтры остаются в порядке полки;
* *И:* единый/построчный режим, названия, разделители и расположение блока соответствуют текущему шаблону.

AC.17 — *Партиционированный экспорт:*
* *Дано:* экспорт формирует несколько листов или XLSX-файлов;
* *Когда:* типы вычисляемых полей определены в рамках текущего экспорта;
* *Тогда:* одни и те же категории и правила форматирования применяются во всех сформированных частях;
* *И:* повторное определение типа для каждого листа/файла и изменение порядка фильтров не выполняются.

AC.18 — *Регресс для обычных полей и других СУБД отсутствует:*
* *Дано:* экспорт содержит фильтры по обычным полям либо выполняется для SQL-диалекта без новой DB-типизации;
* *Когда:* пользователь экспортирует визуализацию;
* *Тогда:* типы и значения обрабатываются по действующему {{filterType}} и текущей безопасной деградации;
* *И:* экспорт не завершается ошибкой из-за отсутствия поддержки определения типа вычисляемого поля для данной СУБД.

AC.19 — *Частный шаблон без маркера фильтров:*
* *Дано:* частный XLSX-шаблон не содержит {{Filter}}, {{Filters}}, {{Filters_by_rows}}/{{FiltersByRows}} или другого поддерживаемого алиаса;
* *И:* к Таблице применён фильтр по вычисляемому полю;
* *Когда:* пользователь выполняет экспорт;
* *Тогда:* блок фильтров не добавляется автоматически;
* *И:* служебное определение типа только для отсутствующего блока фильтров не изменяет штатный запрос данных и содержимое XLSX.

AC.20 — *Одинаковые заголовки вычисляемых полей:*
* *Дано:* по текущей логике экспорта два разных вычисляемых поля с одинаковым пользовательским заголовком, разными выражениями и итоговыми типами сформированы в {{export.parameters.filter}} как две отдельные записи;
* *Когда:* обе записи участвуют в выводимых фильтрах XLSX;
* *Тогда:* каждый фильтр получает тип своего выражения по однозначной внутренней связи конфигурации;
* *И:* механизм типизации не объединяет эти записи, не меняет действующую гранулярность фильтров и сохраняет их исходный порядок.

AC.21 — *Недетерминированное или пользовательское выражение:*
* *Дано:* вычисляемое поле содержит недетерминированную/volatile либо пользовательскую функцию;
* *И:* дополнительное вычисление выражения только ради типа может изменить стоимость или поведение запроса;
* *Когда:* выполняется экспорт;
* *Тогда:* выражение не вычисляется повторно служебной проекцией только ради типизации;
* *И:* используется метаописание схемы, пакетный механизм описания либо резервный приоритет из п. 4.1;
* *И:* результат исходного запроса не изменяется.

AC.22 — *Запрос с {{DISTINCT}}, {{UNION}} или оконной функцией:*
* *Дано:* вычисляемое поле участвует в фильтре визуализации, запрос которой содержит {{DISTINCT}}, {{UNION}} либо оконную функцию;
* *Когда:* выполняется определение типа и XLSX-экспорт;
* *Тогда:* ветви {{UNION}}, набор колонок {{DISTINCT}}, секции оконной функции и результат данных не изменяются ради типизации;
* *И:* при невозможности безопасной проекции применяется пакетное описание либо резервный приоритет из п. 4.1;
* *И:* служебные поля отсутствуют в XLSX.

AC.23 — *Обязательность {{filterType}} в запросе обновлённого фронтенда:*
* *Дано:* экспортируется фильтр по вычисляемому полю;
* *Когда:* обновлённый фронтенд формирует запрос к {{/v1/api/exports}};
* *Тогда:* объект фильтра всегда содержит {{filterType}};
* *И:* при доступном базовом типе передаётся {{number}}, {{string}}, {{date}}, {{datetime}} или {{year}};
* *И:* если фронтенд не может определить базовый тип, передаётся {{calculated}}, но поле {{filterType}} не пропускается;
* *И:* отсутствие {{filterType}} обрабатывается бэкендом только как сценарий обратной совместимости и не приводит к ошибке экспорта.
