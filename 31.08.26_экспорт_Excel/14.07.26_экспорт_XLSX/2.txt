Требуется качественно проработать оформление фильтров при экспорте в XLSX: сценарии поведения и отображения для Вычисляемых полей с точки зрения типов данных полей (числовой, строковый или дата).

Вычисляемые поля - это вычисляемыми SQL-выражения, которые хранятся на уровне метаданных для конкретной визуализации и могут использовать поля набора данных в SQL-выражении для вычисления итогового значения.

В момент, когда пользователь запрашивает экспорт визуализации в Excel, может происходить запрос данных к БД, чтобы отобразить актуальные данные в выгруженном отчёте. В этот запрос можно встроить запрос типа данных для всех используемых вычисляемых полей (pg_typeof()/toTypeName()). При этом добавление pg_typeof()/toTypeName() не требует отдельного запроса к БД, если сделать это правильно.

Тип данных — это метаданные запроса, а не "данных" самих по себе.
Для PostgreSQL: pg_typeof(expr) и для ClickHouse: toTypeName(expr) не читают и не сканируют данные таблицы — они возвращают тип результата выражения, который планировщик СУБД уже знает на этапе парсинга запроса, до выполнения. Тип определяется статически по объявленным типам столбцов, участвующих в выражении, а не по фактическим значениям в строках.

Из этого следует ключевой практический вывод: не нужен отдельный SELECT pg_typeof(...) LIMIT 1. Можно просто добавить pg_typeof(expr) AS "_type_ВП_поле" как дополнительную колонку в тот же самый запрос, который и так выполняется для получения данных при экспорте.

Как это выглядит технически
Обычный запрос данных для экспорта (без изменений):

sql:
"SELECT
  город,
  дата_заказа,
  сумма_продаж * коэффициент AS "ВП_число_сумма_с_коэф"
FROM таблица
WHERE ..."


Тот же запрос + дополнительная колонка типа (тот же round-trip):

sql:
"SELECT
  город,
  дата_заказа,
  сумма_продаж * коэффициент AS "ВП_число_сумма_с_коэф",
  pg_typeof(сумма_продаж * коэффициент) AS "_type_ВП_число_сумма_с_коэф"
FROM таблица
WHERE ..."


Для ClickHouse аналогично — toTypeName(expr) добавляется как ещё одна колонка в SELECT. Никакого второго обращения к БД, никакого дополнительного сетевого round-trip — только одна лишняя колонка в результирующем наборе того же запроса.

Важный нюанс: значение типа одинаково во всех строках.
Поскольку pg_typeof/toTypeName возвращают статический тип выражения (а не тип конкретного значения), результат этой колонки будет идентичным во всех строках результата. 

Это значит:
* Читать тип нужно только из первой строки результата — остальные избыточны, но не создают дополнительной нагрузки (это не отдельный запрос, просто повторяющееся значение в уже полученных данных).
* Можно оптимизировать через LIMIT 1 только если вычисляемое поле не участвует в основном запросе данных (например, тип нужен для фильтра, который не выводится в итоговую таблицу) — тогда это будет отдельный, но крайне лёгкий запрос без сканирования (планировщик даже не обратится к данным, так как результат не зависит от строк).

Т.е. оптимально именно в момент экспорта делать «дозапрос» типов данных для всех вычисляемых полей как расширение существующего запроса данных для экспорта:
# Бэкенд формирует запрос данных для экспорта как обычно.
# Для каждого вычисляемого поля, участвующего в применённых фильтрах, бэкенд добавляет в SELECT дополнительную колонку pg_typeof(expr) / toTypeName(expr) - в зависимости от типа Базы Данных.
# Выполняется один запрос к БД (тот, что и так нужен для получения экспортируемых данных).
# Из первой строки результата бэкенд считывает типы всех Вычисляемых Полей и использует их для форматирования значений фильтров по правилам предыдущих постановок.
# Кешировать результат в метаданных визуализации не обязательно — тип стабилен для конкретного выражения и датасета, повторный расчёт при каждом экспорте не создаёт заметной нагрузки, так как это не отдельный round-trip.

Единственное ограничение, о котором нужно помнить:
* Если вычисляемое поле используется только в фильтре, но не выводится как колонка в самой таблице экспорта — его выражение всё равно нужно добавить в SELECT (даже если оно не попадёт в итоговый XLSX как видимая колонка), просто чтобы получить pg_typeof(). Это добавляет вычисление выражения в план запроса, но не полноценный отдельный запрос — стоимость сравнима с добавлением одной вычисляемой колонки, а не с новым обращением к БД.
