h3. Контекст и проблематика.

При экспорте визуализации в XLSX значения применённых фильтров форматируются в зависимости от типа поля: как строка, число, дата или дата-время.

Для обычного поля тип доступен в метаданных набора данных. Для вычисляемого поля в метаданных визуализации хранится SQL-выражение, а признак {{calculated}} характеризует способ формирования поля, но не определяет тип результата выражения.

Если вычисляемое поле уже является колонкой результата основного запроса данных экспорта, фактический тип полного выражения доступен в метаданных результирующей схемы этого запроса. Этот тип можно использовать независимо от того, выводится ли соответствующая колонка как видимая колонка в XLSX.

Если вычисляемое поле используется только для фильтрации и отсутствует в результирующей схеме основного запроса, определение его типа потребовало бы изменения SQL или отдельного обращения к БД. Для такого сценария требуется сохранять fallback-логику с безопасным строковым отображением вычисляемых полей при экспорте.

----

h3. Цель задачи.

*Требуется:*
# Для вычисляемого поля, присутствующего в результирующей схеме основного запроса данных экспорта, определять тип по метаданным соответствующей колонки результата.
# Нормализовать полученный тип СУБД в категорию {{number}}, {{string}}, {{date}} или {{datetime}} и применять действующие правила оформления фильтра в XLSX.
# Для вычисляемого поля, отсутствующего в результирующей схеме основного запроса, всегда применять строковую безопасную деградацию.
# Не изменять основной SQL-запрос и не выполнять дополнительные обращения к БД только ради определения типа вычисляемого поля.
# Сохранить действующие правила состава, порядка, наименования и отображения фильтров, включая настройку «Значения по другому полю», общий и частные XLSX-шаблоны.

_Пользовательская история:_
Как пользователь аналитического портала, я хочу видеть значения фильтров по вычисляемым полям в XLSX в соответствии с их типом, чтобы числа, строки и даты отображались однозначно.

----

h3. 1. Ключевые понятия.

* *Вычисляемое поле* — поле визуализации, значение которого формируется SQL-выражением, сохранённым в метаданных визуализации. Выражение может содержать поля набора данных, функции, агрегаты, оконные функции, {{CASE}} и явные приведения типов.
* *Основной запрос данных экспорта* — штатный запрос, который бэкенд выполняет для получения данных экспортируемой визуализации. Запрос или операция, сформированные только для определения типа, основным запросом не считаются.
* *Результирующая схема основного запроса* — перечень колонок верхнеуровневого результата основного запроса и их типов, возвращённый СУБД через используемый драйвер или формат ответа. Схема рассматривается до исключения колонок, которые не должны отображаться в итоговом XLSX.
* *Присутствие вычисляемого поля в результирующей схеме* — наличие отдельной колонки верхнеуровневого результата, однозначно связанной с данным вычисляемым полем в карте проекций основного запроса.
* *Видимая колонка XLSX* — колонка, которая после обработки результата включается в пользовательскую таблицу XLSX. Невидимая в XLSX колонка может присутствовать в результирующей схеме основного запроса.
* *Источник отображаемого значения фильтра* — основное поле фильтрации либо поле отображения, выбранное действующим механизмом «Значения по другому полю». Тип определяется для поля, значение которого фактически выводится пользователю.
* *Строковая безопасная деградация* — вывод значения по правилам {{string}}: в одинарных кавычках, без разделителей разрядов и без попытки преобразовать значение к дате или дате-времени.

----

h3. 2. Описание текущего поведения.

* В запросе XLSX-экспорта фильтры передаются в {{export.parameters.filter}}. Объект фильтра содержит {{name}}, {{values}}, обязательный для обновлённого фронтенда {{filterType}} и, при необходимости, {{dateFormat}}.
* Для обычных полей форматирование выполняется по действующему {{filterType}}.
* Если вычисляемое поле передано с {{filterType = "calculated"}} либо тип отсутствует в запросе обратной совместимости, бэкенд применяет строковую безопасную деградацию.
* Метаданные колонки основного запроса не используются единообразно как источник типа вычисляемого поля при оформлении блока фильтров XLSX.

----

h3. 3. Описание целевого поведения.

h4. 3.1. Основное правило.

Для источника фактически отображаемого значения фильтра применяется следующая логика:

|| Вид поля || Наличие колонки в результирующей схеме основного запроса || Источник категории форматирования ||
| Обычное поле | Не влияет на данную задачу | Действующая обработка {{filterType}} без изменений |
| Вычисляемое поле | Колонка присутствует и однозначно сопоставлена; тип поддерживается | Тип колонки из метаданных результирующей схемы основного запроса |
| Вычисляемое поле | Колонка присутствует, но тип отсутствует, не поддерживается либо сопоставление неоднозначно | {{string}} |
| Вычисляемое поле | Колонка отсутствует | {{string}} |

* Наличие SQL-выражения вычисляемого поля в {{WHERE}}, {{HAVING}}, {{GROUP BY}}, {{ORDER BY}}, CTE, внутреннем подзапросе или иной части SQL не означает присутствия поля в результирующей схеме.
* Поле считается присутствующим только при наличии связанной с ним колонки верхнеуровневого результата.
* Наличие поля на полке визуализации само по себе не является основанием для определения типа. Используется фактическая результирующая схема сформированного основного запроса.
* Видимость колонки в итоговом XLSX на выбор типа не влияет. Если колонка уже присутствует в результате основного запроса, её метаданные используются до исключения этой колонки из пользовательского представления.
* Для вычисляемого поля {{filterType}}, переданный фронтендом, не заменяет отсутствующий или неподдерживаемый тип результирующей колонки. В этом случае применяется {{string}}.

---

h4. 3.2. Вычисляемое поле присутствует в результирующей схеме.

* Бэкенд получает тип из метаданных колонки того же основного запроса, который выполняется для получения экспортируемых данных.
* Используется тип результата полного выражения, уже разрешённый СУБД с учётом {{CASE}}, агрегатов, оконных функций, функций СУБД и явных приведений типов.
* Тип не определяется по тексту SQL-выражения, типу отдельного исходного столбца, первой строке результата, первому непустому значению или runtime-типу значения в приложении.
* Количество строк результата не влияет на правило. Если основной запрос вернул ноль строк, но драйвер предоставил результирующую схему, тип определяется по этой схеме.
* Если все значения колонки равны {{null}}, используется тип колонки из схемы, а не тип фактических значений.
* Если метаданные типа не были переданы адаптером, повреждены, не распознаны либо не могут быть нормализованы без дополнительного обращения к БД, применяется {{string}}; экспорт не должен завершаться ошибкой только из-за определения типа.

---

h4. 3.3. Вычисляемое поле отсутствует в результирующей схеме.

* Если вычисляемое поле используется только в фильтре и не является колонкой верхнеуровневого результата основного запроса, значение фильтра форматируется как {{string}}.
* Правило применяется в том числе тогда, когда поле участвует в {{WHERE}} или {{HAVING}}, используется для сортировки либо присутствует только во внутреннем подзапросе.
* Строковая деградация применяется независимо от предполагаемого базового {{filterType}}, переданного фронтендом. Значение не форматируется как число, дата или дата-время на основании клиентского предположения.
* Вычисляемое выражение не добавляется в {{SELECT}} только ради определения типа.
* Дополнительный запрос, описание схемы или обращение к системному каталогу типов не выполняются.
* Если XLSX формируется из ранее полученного результата и вместе с ним доступна результирующая схема основного запроса, применяется стандартное правило: тип вычисляемого поля определяется по связанной колонке схемы.
* Если ранее полученный результат не содержит доступной результирующей схемы либо связанная колонка в ней отсутствует, применяется {{string}}.
* Отдельное обращение к БД для восстановления схемы не выполняется.

---

h4. 3.4. Сценарии отображения по итоговой категории.

|| Итоговая категория || Правило отображения || Пример результата в XLSX ||
| {{number}} | Без одинарных кавычек; разделители разрядов и точность — по действующим правилам экспорта. Для чисел длиной до четырёх знаков включительно разделители разрядов не применяются. Дополнительное округление не выполняется. | {{Сумма: 1 500 000,50}} |
| {{string}} | Каждое значение выводится в одинарных кавычках; действующая обработка символов внутри значения сохраняется. | {{Регион: 'Москва', 'Санкт-Петербург'}} |
| {{date}} | Без одинарных кавычек; применяется переданный {{dateFormat}} либо действующий формат по умолчанию {{ДД.ММ.ГГГГ}}. | {{Дата заказа >= 01.01.2025 И <= 31.01.2025}} |
| {{datetime}} | Без одинарных кавычек; применяется действующий формат визуализации. Компонент времени выводится, если он предусмотрен форматом. | {{Момент обновления >= 01.01.2025 10:30}} |
| {{string}} как безопасная деградация | В одинарных кавычках, без числового форматирования и преобразования к дате. | {{Значение: '1500000'}} |

* Для списочного фильтра сохраняется формат {{Название: Значение1, Значение2}}.
* Для сравнительного или диапазонного фильтра сохраняется формат без двоеточия перед оператором.
* Операторы {{=}}, {{<>}}, {{>}}, {{>=}}, {{<}}, {{<=}}, {{~}} и связки {{ И }} / {{ ИЛИ }} не изменяются.
* Порядок значений внутри одного фильтра не изменяется.
* Определённый тип задаёт категорию форматирования, но не изменяет исходную точность, значение, часовой пояс или оператор фильтра.
* Для {{date}} и {{datetime}} SQL-тип не определяет маску отображения. Маска выбирается по действующему приоритету настроек; при её отсутствии используется действующий формат по умолчанию.
* Семантический {{filterType = "year"}} не является отдельным типом СУБД и не подменяет тип вычисляемого поля. Если схема определила числовой тип, применяется {{number}}; значение длиной до четырёх знаков включительно выводится без разделителя разрядов по действующему числовому правилу.

---

h4. 3.5. Настройка «Значения по другому полю».

* Сначала действующий механизм экспорта определяет, какое значение фактически будет показано: значение основного поля либо успешно сопоставленное значение поля отображения.
* Категория форматирования определяется для источника фактически показанного значения, а не обязательно для основного поля фильтрации.
* Если источником является обычное поле, применяется действующая обработка его типа.
* Если источником является вычисляемое поле, к нему применяется правило из пп. 3.1–3.3:
** связанная колонка присутствует в результирующей схеме основного запроса — используется её тип;
** связанная колонка отсутствует либо тип не разрешён — используется {{string}}.
* Если действующий механизм выполнил безопасную деградацию к исходному значению основного поля, тип определяется для основного поля.
* Основное поле продолжает использоваться для фильтрации данных. Поле отображения влияет только на текст, показываемый в XLSX.
* Название поля отображения не подменяет название фильтра.
* Источник глобальной настройки, правила сопоставления значений и обработка отсутствующего значения данной задачей не изменяются.
* Поле отображения не добавляется в основной запрос только ради определения его типа.

----

h3. 4. Требования к определению типа.

h4. 4.1. Получение метаданных результата.

* Интеграционный слой должен передавать в механизм XLSX-экспорта не только строки данных, но и доступные метаданные результирующих колонок основного запроса.
* Для PostgreSQL используется идентификатор или каноническое описание типа результирующей колонки, предоставленное текущим драйвером.
* Для ClickHouse используется каноническое имя типа результирующей колонки из метаданных ответа текущего драйвера или формата результата.
* Если текущий адаптер получает метаданные основного запроса, но отбрасывает их до формирования XLSX, необходимо сохранить их в рамках внутренней модели результата до определения категорий фильтров.
* Метаданные должны обрабатываться до исключения невидимых колонок из набора пользовательских колонок XLSX.
* Результирующая схема используется как уже полученная часть ответа основного запроса. Отдельный запрос для её получения не выполняется.
* При нуле строк метаданные схемы используются, если они предоставлены драйвером. Фиктивные строки не создаются.

---

h4. 4.2. Сопоставление вычисляемого поля с колонкой результата.

* Колонка результата должна сопоставляться с вычисляемым полем по однозначной внутренней связи, сформированной текущим генератором SQL: по техническому ключу, позиции проекции или эквивалентной карте соответствия.
* Пользовательский заголовок, отображаемое название или совпадение одного текстового алиаса не должны быть единственным основанием для сопоставления.
* Сопоставление не выполняется путём сравнения строкового текста SQL-выражений.
* Переименование пользовательского заголовка не должно приводить к подмене типа.
* При одинаковых заголовках, конфликтующих алиасах, нескольких возможных колонках либо отсутствии однозначной внутренней связи применяется {{string}}.
* Одно вычисляемое поле, используемое несколькими фильтрами, сопоставляется с колонкой и типизируется один раз в рамках текущего экспорта.

---

h4. 4.3. Алгоритм обработки.

# Определить по действующей логике состав фильтров, выводимых для конкретной экспортируемой визуализации, и сохранить порядок {{export.parameters.filter}}.
# Для каждого выводимого значения определить фактический источник: основное поле либо поле отображения.
# Для обычного источника применить действующую обработку {{filterType}}.
# Для вычисляемого источника найти однозначно связанную колонку в результирующей схеме основного запроса.
# Если колонка найдена, нормализовать её тип только в {{number}}, {{string}}, {{date}} или {{datetime}}.
# Если колонка не найдена, сопоставление неоднозначно, метаданные отсутствуют либо тип не поддерживается, установить категорию {{string}}.
# Отформатировать значения по итоговой категории, не меняя состав, названия, операторы и порядок фильтров.
# Переиспользовать определённую категорию во всех листах и файлах, сформированных в рамках текущего экспорта.

----

h3. 5. Нормализация типов СУБД.

h4. 5.1. Общие правила.

* Нормализация выполняется локально по метаданным, уже полученным вместе с основным результатом.
* Явное приведение типа учитывается автоматически, поскольку используется тип итоговой колонки после разрешения выражения СУБД.
* Обёртки nullability и низкой кардинальности не меняют базовую категорию и снимаются рекурсивно.
* Неизвестный, пользовательский или составной тип разрешается через локальный реестр драйвера только тогда, когда необходимые сведения уже загружены и поиск гарантированно не выполняет SQL-запрос, сетевое обращение или ленивую загрузку метаданных.
* Если локальное разрешение типа может инициировать дополнительное обращение к БД, оно не выполняется и применяется {{string}}.
* Список ниже задаёт правила по семействам типов, а не только по отдельным буквальным именам.

---

h4. 5.2. PostgreSQL.

|| Семейство типа PostgreSQL || Категория XLSX ||
| {{smallint}}, {{integer}}, {{bigint}}, {{numeric}}/{{decimal}}, {{real}}, {{double precision}} | {{number}} |
| {{character}}, {{character varying}}, {{text}}, {{name}}, {{uuid}}, {{enum}} | {{string}} |
| {{date}} | {{date}} |
| {{timestamp}} без/с часовым поясом | {{datetime}} |
| Доменный тип | Категория базового типа, только если базовый тип доступен в уже полученных метаданных или уже загруженном локальном реестре драйвера без дополнительного обращения к БД |
| {{boolean}}, {{time}}, {{interval}}, {{json}}/{{jsonb}}, {{xml}}, {{bytea}}, массивы, составные, диапазонные и иные неподдерживаемые типы | {{string}} |

* Тип классифицируется по каноническому идентификатору или описанию типа, предоставленному драйвером.
* Если разрешение неизвестного OID или базового типа домена потребовало бы обращения к системному каталогу, такое обращение не выполняется и применяется {{string}}.

---

h4. 5.3. ClickHouse.

|| Семейство типа ClickHouse || Категория XLSX ||
| {{Int*}}, {{UInt*}}, {{Float*}}, {{BFloat16}}, {{Decimal*}} | {{number}} |
| {{String}}, {{FixedString}}, {{Enum*}}, {{UUID}}, {{IPv4}}, {{IPv6}} | {{string}} |
| {{Date}}, {{Date32}} | {{date}} |
| {{DateTime}}, {{DateTime64}} | {{datetime}} |
| {{Nullable(T)}} | Снять {{Nullable}} и определить категорию для {{T}} |
| {{LowCardinality(T)}} | Снять {{LowCardinality}} и определить категорию для {{T}} |
| {{Bool}}, {{Nothing}}, {{Dynamic}}, {{Variant}}, {{Array}}, {{Tuple}}, {{Map}}, {{Nested}}, {{Object}}/{{JSON}}, агрегатные состояния и иные неподдерживаемые типы | {{string}} |

* Вложенные комбинации, например {{LowCardinality(Nullable(String))}} или {{Nullable(Decimal(18, 2))}}, нормализуются рекурсивно.
* Каноническое имя ClickHouse разбирается как структура типа; категория не определяется только по совпадению подстроки.

----

h3. 6. Требования к реализации.

h4. 6.1. Фронтенд-часть и API.

* Затрагиваемый backend-объект: {{exports}}.
* Используется действующая команда XLSX-экспорта через {{/v1/api/exports}}; новая команда API не требуется, актуальное значение {{command.name}} сохраняется из текущего контракта.
* Структура {{export.parameters.filter}} не изменяется: сохраняются {{name}}, {{values}}, обязательный для обновлённого фронтенда {{filterType}} и опциональный {{dateFormat}}.
* Фронтенд продолжает передавать фильтры в порядке элементов полки «Фильтры» конкретной экспортируемой визуализации.
* Фронтенд продолжает передавать обязательный {{filterType}} по действующему API-контракту: разрешённый базовый тип, если он доступен фронтенду, либо {{calculated}}, если определить его невозможно. Для вычисляемого поля переданный {{filterType}}, включая {{year}}, не является источником категории: используется поддерживаемый тип связанной колонки результирующей схемы, а при его отсутствии — {{string}}.
* {{dateFormat}} продолжает передаваться и применяться по действующему приоритету настроек. Для обычного поля поведение не меняется. Для вычисляемого поля маска применяется только тогда, когда метаданные связанной результирующей колонки определили итоговую категорию {{date}} или {{datetime}}; при строковой безопасной деградации {{dateFormat}} не используется.
* Новые пользовательские настройки, действия интерфейса и шаблонные маркеры не вводятся.
* Новая публичная команда API не вводится. Если текущая внутренняя модель теряет связь между полем и проекцией, эта связь должна быть сохранена внутри действующего контура формирования запроса и результата без сопоставления по пользовательскому заголовку.

---

h4. 6.2. Бэкенд-часть.

* До форматирования блока фильтров получить метаданные результирующей схемы основного запроса и внутреннюю карту соответствия проекций полям визуализации.
* Определять вычисляемое поле по текущей конфигурации визуализации, а не только по значению {{filterType}}.
* Сопоставлять тип с фактическим источником отображаемого значения фильтра.
* Для вычисляемых полей использовать строгий приоритет: поддерживаемый тип связанной колонки результата → {{string}}. Переданный базовый {{filterType}} не является промежуточным fallback.
* Сохранять исходную последовательность записей {{export.parameters.filter}} после сопоставления, типизации и форматирования.
* Не изменять сохранённые метаданные отчёта, визуализации, набора данных или вычисляемого поля.
* Не кешировать определённый тип в метаданных. В рамках одного экспорта допускается переиспользовать уже определённую категорию.
* Ошибка чтения, сопоставления или нормализации метаданных типа не должна прерывать экспорт: для проблемного вычисляемого поля применяется {{string}}.
* Если само вычисляемое выражение невалидно и основной запрос не может быть выполнен, применяется действующая обработка ошибки SQL. Строковая деградация типа не должна маскировать ошибку основного запроса.

---

h4. 6.3. SQL-логика и ограничения.

* Поддержать чтение и нормализацию метаданных основного результата для PostgreSQL и ClickHouse.
* Для других адаптеров либо форматов ответа, не предоставляющих поддерживаемый тип колонки, вычисляемое поле обрабатывается как {{string}} без дополнительного обращения к БД.
* Ради определения типа запрещено:
** добавлять вычисляемое выражение или служебную колонку в {{SELECT}};
** добавлять {{pg_typeof}} или {{toTypeName}};
** выполнять {{DESCRIBE}}, запрос с {{LIMIT 0}}/{{LIMIT 1}}, metadata-only запрос или иной дополнительный SQL-запрос;
** обращаться к системному каталогу типов;
** изменять {{WHERE}}, {{HAVING}}, {{GROUP BY}}, {{DISTINCT}}, {{UNION}}, CTE, оконные выражения, сортировку, лимиты или пагинацию.
* Основной SQL-запрос, число обращений к БД и сетевых round-trip не должны изменяться только ради определения типов вычисляемых полей.
* Доработка не должна изменять число строк, состав и порядок пользовательских колонок, итоги и подытоги, точность вычислений, часовой пояс данных и результат фильтрации.

---

h4. 6.4. Формирование XLSX.

* Правила применяются в общем XLSX-шаблоне и частном XLSX-шаблоне Таблицы.
* Сохраняется обработка действующих маркеров фильтров и поддерживаемых алиасов, включая {{Filter}}, {{Filters}}, {{Filters_by_rows}} и {{FiltersByRows}}. Новые маркеры не вводятся.
* Для {{Filter}}/{{Filters}} сохраняется вывод фильтров в одну строку с действующим разделителем {{; }}; для {{Filters_by_rows}}/{{FiltersByRows}} и действующего построчного режима общего шаблона — вывод каждого фильтра с новой строки.
* Если частный шаблон не содержит действующего маркера фильтров, блок фильтров не добавляется автоматически и типы не определяются только ради отсутствующего блока.
* Если выводимых фильтров нет, маркер обрабатывается по текущей логике без вывода технических значений, {{null}}, {{undefined}} или текста маркера.
* Порядок фильтров остаётся порядком полки «Фильтры», переданным в {{export.parameters.filter}}. Определение типа не должно сортировать, объединять или переставлять фильтры.
* Название фильтра определяется по действующему приоритету; название поля отображения и метаданные типа его не изменяют.
* Метаданные результирующей схемы и внутренние технические ключи не должны попадать в заголовки, строки данных, блоки «Фильтры» и «Переменные», итоги, подытоги, пользовательское сопоставление колонок или дополнительные листы.
* Блок «Переменные», его состав, порядок и маркеры не изменяются. Определение типа вычисляемого поля не считается новым использованием переменной.
* Дополнительные листы шаблонов переносятся по действующей логике без изменений.
* При разбиении экспорта на несколько листов или файлов однажды определённая категория применяется во всех частях текущего экспорта.

----

h3. 7. Пограничные сценарии и безопасная деградация.

* Вычисляемое поле находится на полке визуализации и является колонкой верхнеуровневого результата, но скрывается при формировании пользовательских колонок XLSX — используется тип колонки из схемы.
* Вычисляемое поле находится на полке «Фильтры» и участвует только в {{WHERE}} или {{HAVING}} — применяется {{string}}.
* Поле участвует в {{GROUP BY}}, {{ORDER BY}}, CTE или внутреннем подзапросе, но отсутствует во внешнем {{SELECT}} — применяется {{string}}.
* Агрегатное, оконное выражение, {{CASE}} или явное приведение выводится отдельной колонкой — используется итоговый тип этой колонки.
* Такое же выражение используется только в условии запроса — применяется {{string}}.
* Основной запрос вернул ноль строк, но схема доступна — тип определяется по схеме.
* Все значения результирующей колонки равны {{null}} — тип определяется по схеме.
* Адаптер не передал тип колонки либо вернул неизвестный тип — применяется {{string}}, новый запрос не выполняется.
* Два вычисляемых поля имеют одинаковые пользовательские заголовки — используется внутренняя связь; при неоднозначности применяется {{string}}.
* Вычисляемое поле переименовано — сопоставление выполняется по актуальной внутренней связи, а не по прежнему или новому заголовку.
* Для «Значений по другому полю» фактически показывается вычисляемое поле отображения, отсутствующее в схеме основного запроса — отображаемое значение выводится как {{string}}.
* Действующий механизм «Значения по другому полю» вернулся к значению основного поля — тип определяется для основного поля.
* Фронтенд передал для вычисляемого поля базовый числовой или датовый {{filterType}}, но колонка отсутствует в схеме — применяется {{string}}.
* Экспорт выполняется из ранее полученного результата с доступной результирующей схемой — используется тип связанной колонки без нового обращения к БД.
* Экспорт выполняется без доступной результирующей схемы — вычисляемые поля обрабатываются как {{string}}, новый запрос не выполняется.
* Экспорт разбит на несколько листов или файлов — категория не переопределяется по фактическим значениям каждой части.

Во всех случаях ошибка определения категории не должна сама по себе приводить к падению экспорта. Сохраняются исходное значение, название, оператор и позиция фильтра.

----

h3. 8. Рамки задачи.

*В рамки задачи входит:*
* получение уже доступных метаданных результирующей схемы основного запроса в механизме XLSX-экспорта;
* однозначное сопоставление вычисляемого поля с существующей колонкой результата;
* нормализация типов PostgreSQL и ClickHouse;
* применение существующих правил форматирования фильтров по полученной категории;
* строковая безопасная деградация для вычисляемых полей без доступного поддерживаемого типа;
* сохранение типа в рамках текущего экспорта для повторного использования во всех его частях.

h3. 9. Критерии приёмки (AC).

AC.1 — *Числовая вычисляемая колонка основного запроса:*
* *Дано:* применён фильтр по вычисляемому полю, однозначно связанному с числовой колонкой результирующей схемы основного запроса;
* *И:* выбрано значение {{1500000}};
* *Когда:* пользователь экспортирует визуализацию в XLSX;
* *Тогда:* тип берётся из метаданных этой колонки;
* *И:* в блоке фильтров отображается числовое значение без одинарных кавычек и с действующим разделителем разрядов: {{1 500 000}};
* *И:* дополнительное округление или потеря точности не выполняются.

AC.2 — *Строковая вычисляемая колонка основного запроса:*
* *Дано:* вычисляемое поле связано со строковой колонкой результирующей схемы;
* *И:* выбраны значения «Диван» и «Кресло»;
* *Когда:* выполняется экспорт в XLSX;
* *Тогда:* значения отображаются по строковым правилам: {{'Диван', 'Кресло'}}.

AC.3 — *Вычисляемые колонки типа дата и дата-время:*
* *Дано:* фильтры ссылаются на вычисляемые поля, связанные с колонками типов {{date}} и {{datetime}} результирующей схемы;
* *Когда:* выполняется экспорт в XLSX;
* *Тогда:* значения выводятся без одинарных кавычек по действующему {{dateFormat}};
* *И:* компонент времени выводится только тогда, когда он предусмотрен форматом;
* *И:* при отсутствии доступного формата применяется действующий формат по умолчанию {{ДД.ММ.ГГГГ}}.

AC.4 — *Вычисляемое поле используется только в фильтре:*
* *Дано:* числовое вычисляемое поле участвует в {{WHERE}}, но отсутствует в верхнеуровневой результирующей схеме основного запроса;
* *Когда:* выполняется экспорт в XLSX;
* *Тогда:* значение {{1500000}} отображается по строковому fallback как {{'1500000'}};
* *И:* разделители разрядов и преобразование к числу не применяются;
* *И:* вычисляемое выражение не добавляется в {{SELECT}}.

AC.5 — *Фильтр агрегированной визуализации:*
* *Дано:* вычисляемое поле участвует только в условии запроса с {{GROUP BY}} и {{HAVING}} и отсутствует в верхнеуровневой результирующей схеме;
* *Когда:* пользователь выполняет экспорт;
* *Тогда:* значение фильтра выводится как {{string}};
* *И:* {{SELECT}}, {{GROUP BY}}, {{HAVING}}, состав колонок и результат запроса не изменяются ради типизации.

AC.6 — *Колонка присутствует в результате, но не видима в XLSX:*
* *Дано:* вычисляемое поле связано с колонкой основного результата, которая по действующей логике исключается из видимых пользовательских колонок XLSX;
* *Когда:* выполняется экспорт;
* *Тогда:* для оформления фильтра используется тип этой колонки из результирующей схемы;
* *И:* сама колонка не добавляется в итоговый XLSX и не изменяет порядок видимых колонок.

AC.7 — *Пустая выборка и значения {{null}}:*
* *Дано:* для PostgreSQL и ClickHouse последовательно проверяются:
** основной запрос с нулём строк;
** основной запрос, в котором все значения вычисляемой колонки равны {{null}};
* *И:* используемый драйвер или формат ответа в каждом сценарии предоставил поддерживаемый тип колонки в результирующей схеме;
* *Когда:* формируется блок фильтров XLSX;
* *Тогда:* категория определяется по схеме независимо от фактических значений;
* *И:* первая, непустая или фиктивная строка не требуется.

AC.8 — *Тип полного вычисляемого выражения:*
* *Дано:* последовательно экспортируются вычисляемые колонки с {{CASE}}, агрегатной функцией, оконной функцией и явным приведением типа;
* *Когда:* каждая колонка присутствует в верхнеуровневой результирующей схеме;
* *Тогда:* используется итоговый тип соответствующей колонки, определённый СУБД;
* *И:* выражение не вычисляется повторно и SQL основного запроса не изменяется.

AC.9 — *Неподдерживаемый или недоступный тип:*
* *Дано:* вычисляемая колонка присутствует в результирующей схеме, но её тип отсутствует, неизвестен либо не может быть нормализован по уже доступным метаданным;
* *Когда:* выполняется экспорт;
* *Тогда:* применяется {{string}} независимо от предполагаемого базового {{filterType}};
* *И:* экспорт завершается без ошибки определения типа;
* *И:* дополнительное обращение к БД или системному каталогу не выполняется.

AC.10 — *Приоритет типа СУБД и строкового fallback:*
* *Дано:* фронтенд передал для вычисляемого поля {{filterType = "calculated"}} либо {{filterType = "string"}}, а связанная колонка основного результата имеет числовой тип;
* *Когда:* выполняется экспорт;
* *Тогда:* значение форматируется как {{number}} по типу результирующей колонки;
* *И:* при повторной проверке фронтенд передал {{filterType = "number"}}, но вычисляемая колонка отсутствует в результирующей схеме;
* *Тогда:* значение форматируется как {{string}}, а не как {{number}}.

AC.11 — *Клиентский {{filterType}} не подменяет тип вычисляемого поля:*
* *Дано:* вычисляемое поле связано с числовой колонкой результирующей схемы;
* *И:* фронтенд передал {{filterType = "year"}} либо другой базовый {{filterType}};
* *Когда:* экспортируется значение {{2024}};
* *Тогда:* категория вычисляемого поля определяется как {{number}} по типу колонки;
* *И:* значение {{2024}} выводится без разделителя разрядов по действующему правилу коротких чисел;
* *И:* если связанная колонка присутствует и имеет поддерживаемый нечисловой тип, значение форматируется по типу этой колонки;
* *И:* если связанная колонка отсутствует, значение выводится как {{'2024'}} по строковой безопасной деградации.

AC.12 — *«Значения по другому полю»:*
* *Дано:* основное поле фильтра имеет числовой тип, а действующий механизм «Значения по другому полю» успешно выбрал строковое поле отображения;
* *Когда:* выполняется экспорт;
* *Тогда:* в XLSX выводится строковое отображаемое значение в одинарных кавычках;
* *И:* фильтрация данных продолжает выполняться по основному полю;
* *И:* если источником отображения является вычисляемое поле, его категория определяется только по наличию связанной колонки в результирующей схеме основного запроса, а при её отсутствии применяется {{string}}.

AC.13 — *Однозначное сопоставление:*
* *Дано:* два вычисляемых поля имеют одинаковый пользовательский заголовок;
* *Когда:* выполняется сопоставление с результирующими колонками;
* *Тогда:* заголовок не используется как единственный ключ;
* *И:* при наличии внутренней связи каждое поле получает тип своей колонки;
* *И:* при неоднозначности для соответствующего фильтра применяется {{string}} без подмены типа другим полем.

AC.14 — *Отсутствие дополнительных SQL-операций:*
* *Дано:* в фильтрах присутствуют вычисляемые поля, часть которых отсутствует в результирующей схеме основного запроса;
* *Когда:* выполняется экспорт;
* *Тогда:* по сравнению с контрольным экспортом тех же данных типизация не изменяет число запросов и сетевых round-trip;
* *И:* текст и набор параметров основного SQL-запроса не изменены ради определения типа;
* *И:* не добавлены {{pg_typeof}}, {{toTypeName}}, вычисляемые или служебные проекции;
* *И:* не инициированы дополнительные {{DESCRIBE}}, запросы с {{LIMIT 0}}/{{LIMIT 1}}, metadata-only запросы или обращения к системному каталогу типов;

AC.15 — *Экспорт из ранее полученного результата:*
* *Дано:* XLSX формируется из ранее полученных данных без нового обращения к БД;
* *Когда:* вместе с данными доступна результирующая схема основного запроса и вычисляемое поле связано с её колонкой;
* *Тогда:* категория определяется по типу этой колонки;
* *И:* если результирующая схема недоступна либо связанная колонка отсутствует, применяется {{string}};
* *И:* отдельное обращение к БД не выполняется;
* *И:* экспорт не завершается ошибкой из-за отсутствия типа.

AC.16 — *Сохранение порядка и шаблонного поведения:*
* *Дано:* на полке «Фильтры» применены обычные и вычисляемые поля в заданной последовательности;
* *И:* используется общий шаблон либо частный шаблон с действующим маркером фильтров;
* *Когда:* выполняется экспорт;
* *Тогда:* фильтры остаются в порядке полки;
* *И:* единый или построчный режим, названия, операторы, разделители и расположение блока соответствуют действующему шаблону;
* *И:* типизация не изменяет блок «Переменные», видимые колонки и дополнительные листы.

AC.17 — *Частный шаблон без маркера фильтров:*
* *Дано:* частный XLSX-шаблон не содержит действующего маркера фильтров;
* *И:* к Таблице применён фильтр по вычисляемому полю;
* *Когда:* пользователь выполняет экспорт;
* *Тогда:* блок фильтров не добавляется автоматически;
* *И:* определение типа только ради отсутствующего блока не выполняется;
* *И:* запрос данных и содержимое XLSX соответствуют действующей логике шаблона.

AC.18 — *Партиционированный экспорт:*
* *Дано:* экспорт формирует несколько листов или XLSX-файлов;
* *Когда:* категория вычисляемого поля определена по результирующей схеме основного запроса;
* *Тогда:* одна и та же категория и правило форматирования применяются во всех частях текущего экспорта;
* *И:* категория не переопределяется по значениям отдельных страниц, листов или файлов;
* *И:* дополнительные обращения к БД только для повторной типизации не выполняются.

AC.19 — *Регресс для обычных полей отсутствует:*
* *Дано:* XLSX содержит фильтры по обычным полям и вычисляемым полям;
* *Когда:* пользователь экспортирует визуализацию;
* *Тогда:* обычные поля продолжают форматироваться по действующему {{filterType}};
* *И:* новая логика определения типа применяется только к вычисляемым полям;
* *И:* состав данных, фильтрация, названия и порядок пользовательских колонок не изменяются.

AC.20 — *Обязательность {{filterType}} в запросе обновлённого фронтенда:*
* *Дано:* обновлённый фронтенд формирует XLSX-экспорт фильтра по вычисляемому полю;
* *Когда:* отправляется запрос к {{/v1/api/exports}};
* *Тогда:* объект фильтра содержит {{filterType}};
* *И:* если базовый тип доступен фронтенду, передаётся соответствующее поддерживаемое значение;
* *И:* если базовый тип определить невозможно, передаётся {{calculated}}, но поле не пропускается;
* *И:* отсутствие {{filterType}} обрабатывается бэкендом только как сценарий обратной совместимости и не приводит к ошибке экспорта.

AC.21 — *Нормализация типов по уже доступным метаданным:*
* *Дано:* в результирующей схеме ClickHouse доступны типы {{Nullable(Decimal(18, 2))}}, {{LowCardinality(String)}} и {{DateTime64(3)}};
* *И:* в схеме PostgreSQL доступен доменный тип с локально разрешённым базовым типом {{numeric}};
* *Когда:* выполняется экспорт;
* *Тогда:* категории определяются соответственно как {{number}}, {{string}}, {{datetime}} и {{number}};
* *И:* если базовый тип домена нельзя разрешить по уже доступным метаданным или уже загруженному локальному реестру драйвера без обращения к БД, применяется {{string}};
* *И:* дополнительное обращение к БД или системному каталогу не выполняется.
