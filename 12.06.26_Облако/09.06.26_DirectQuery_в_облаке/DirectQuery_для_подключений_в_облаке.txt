h3. Контекст и проблематика.

В {{Modus BI Cloud}} пользователи внешних облачных контуров работают преимущественно с ролью {{«аналитик»}}. Для этой роли доступна вкладка {{«Подключения»}}, где пользователь может создать подключение к внешнему источнику и затем использовать его в сценарии {{«Правила загрузки данных»}} для загрузки данных во внутреннее облачное хранилище {{ClickHouse}}.

При этом вкладка {{«Источники»}} для аналитиков в облачной версии недоступна. Через {{«Источники»}} в портале исторически работает сценарий прямых запросов к внешним СУБД: пользователь создаёт источник данных, затем на его базе создаёт "произвольный" набор данных, который обращается к внешней СУБД напрямую, без предварительной загрузки данных во внутреннее хранилище.

Сейчас в облаке существуют два близких, но разных сценария:
* {{«Источники»}} → {{«Наборы данных»}} — сценарий DirectQuery, где запросы выполняются напрямую к внешней СУБД;
* {{«Подключения»}} → {{«Правила загрузки данных»}} → {{«Наборы данных»}} — сценарий загрузки данных во внутренний {{ClickHouse}}, где пользователь сначала создаёт подключение, затем правило загрузки, после чего работает с загруженными данными.

Для облачной версии необходимо дать аналитику возможность использовать созданные им подключения к внешним СУБД не только для загрузки данных через {{«Правила загрузки данных»}}, но и для прямых запросов к БД для произвольных наборов данных, без предварительной загрузки данных во внутреннее хранилище.

На текущем этапе нельзя менять ролевую модель и открывать аналитикам вкладку {{«Источники»}}, чтобы не увеличивать трудозатраты и не расширять область изменений. Пользовательской точкой входа для аналитика должна остаться вкладка {{«Подключения»}}, а связанный источник данных для DirectQuery должен создаваться системой под капотом.

----
h3. Цель задачи.

*Требуется:*
# Добавить в {{Modus BI Cloud}} возможность помечать +поддерживаемые+ подключения к внешним СУБД как доступные для прямых запросов к БД ({{DirectQuery}}).
# При включении признака "Использовать данное подключение для создания Произвольных наборов данных" сохранять подключение единым Бэкенд-сценарием, в рамках которого автоматически создаётся и синхронизируется связанный источник данных в существующем механизме {{«Источники»}}.
# Сделать автоматически созданный источник доступным аналитику в сценарии создания произвольного набора данных, не открывая ему вкладку {{«Источники»}} и не меняя текущую ролевую модель.
# Сохранить текущий сценарий загрузки данных для подключений через {{«Правила загрузки данных»}} без регресса.

_Пользовательская история:_
Как аналитик в {{Modus BI Cloud}}, при создании подключения к внешней СУБД я хочу иметь возможность создавать произвольные наборы данных с прямым обращением к внешней базе данных без предварительной загрузки данных во внутреннее облачное хранилище.

----
h3. 1. Описание текущего поведения.

h4. 1.1. Работа аналитика с подключениями.

В текущем облачном сценарии аналитик может открыть вкладку {{«Подключения»}} и создать подключение к внешнему источнику данных.

Для подключений к СУБД пользователь указывает стандартные параметры соединения, включая:
* наименование подключения;
* сервер/host;
* порт;
* базу данных;
* схему, если она используется для выбранного типа СУБД;
* пользователя;
* пароль;
* другие параметры, предусмотренные текущей формой подключения.

После создания подключения пользователь может перейти в {{«Правила загрузки данных»}}, задать правило загрузки и переложить данные из внешнего источника во внутреннее облачное хранилище {{ClickHouse}}. Далее эти данные используются в простых и составных наборах данных.

---
h4. 1.2. Работа через прямые запросы к БД.

Сценарий прямых запросов к БД на основном портале происходит на вкладке «Источники» и идет через работу с произвольными наборами данных.

В стандартном сценарии пользователь выбирает источник данных, на базе которого создаётся произвольный набор данных. Запрос такого набора выполняется напрямую к источнику, то есть к внешней СУБД, без обязательной загрузки данных во внутренний {{ClickHouse}}.

В облачном портале *аналитик* не может самостоятельно создать такой источник, потому что вкладка {{«Источники»}} для его роли недоступна.

---
h4. 1.3. Ограничение облачной версии.

Сейчас аналитик в облаке может самостоятельно создать подключение к внешней СУБД, но не может использовать это же подключение как источник для DirectQuery (например, для создания произвольного набора данных).

Из-за этого пользователь вынужден работать только через сценарий загрузки данных во внутреннее хранилище, даже если для его задачи достаточно прямого запроса к внешней СУБД.

----
h3. 2. Описание целевого поведения.

h4. 2.1. Общий пользовательский сценарий.

После доработки аналитик должен иметь возможность включить параметр "Использовать данное подключение для создания Произвольных наборов данных" для поддерживаемого типа подключения прямо из формы создания или редактирования на вкладке {{«Подключения»}}.

Целевой сценарий:
# Аналитик открывает вкладку {{«Подключения»}}.
# Аналитик создаёт новое подключение к поддерживаемой СУБД или открывает существующее подключение для редактирования.
# Если тип подключения относится к поддерживаемым для текущей задачи СУБД, в форме отображается признак "Использовать данное подключение для создания Произвольных наборов данных".
# Аналитик заполняет стандартные параметры подключения.
# Аналитик ставит галочку для параметра "Использовать данное подключение для создания Произвольных наборов данных", активируя механизм {{«DirectQuery»}} запроса.
#* При наведении пользователем указателя на параметр "Использовать данное подключение для создания Произвольных наборов данных" должна появляться пояснительная записка (tooltip) - "Вы сможете использовать данное подключение в качестве источника данных для создания произвольных наборов данных. Запросы будут выполняться напрямую к внешней базе данных через произвольный пользовательский SQL-запрос, без предварительной загрузки данных во внутреннее хранилище".
# При сохранении Фронтенд отправляет единый запрос сохранения подключения с параметрами подключения и признаком DirectQuery. Отдельный запрос на создание источника данных со стороны Фронтенда не выполняется.
# Бэкенд сохраняет подключение и, если признак DirectQuery включён, автоматически создаёт или актуализирует связанный источник данных в существующем механизме {{«Источники»}}.
# Вкладка {{«Источники»}} для аналитика по-прежнему недоступна.
# При создании произвольного набора данных аналитик видит автоматически созданный источник в списке источников, доступных для прямого запроса.
# Произвольный набор данных, созданный на базе такого источника, выполняет запрос напрямую к внешней СУБД.

---
h4. 2.2. Поддерживаемые типы подключений.

В рамках первой реализации признак {{«DirectQuery»}} должен быть доступен только для подключений к следующим СУБД:
* {{ClickHouse}};
* {{PostgreSQL}} / {{Postgres}};
* {{Vertica}};
* {{MS SQL Server}}.

Для неподдерживаемых типов подключений признак {{DirectQuery}} не должен отображаться (и должен быть недоступен).

В реализацию не входят:
* {{Excel}};
* {{Google Sheets}};
* {{1С}};
* другие файловые, табличные и СУБД источники, для которых сценарий DirectQuery через источник не подтверждён в рамках этой задачи.

---
h4. 2.3. Автоматически создаваемый источник данных.

Если пользователь включает признак {{«DirectQuery»}} и сохраняет подключение, Бэкенд должен создать связанный источник данных на базе параметров этого подключения в рамках обработки того же запроса сохранения.

Фронтенд не вызывает отдельную команду создания {{datasources}} и не должен самостоятельно формировать отдельный payload источника данных. Все правила создания, заполнения обязательных полей, связи и синхронизации источника с подключением должны выполняться на Бэкенде.

Источник должен создаваться с минимально необходимыми настройками, достаточными для работы прямых запросов к этой БД:
* тип СУБД/драйвер должен соответствовать типу подключения;
* наименование источника должно быть понятно пользователю и по умолчанию соответствовать наименованию подключения или однозначно от него наследоваться;
* host, порт, база данных, схема, пользователь и пароль должны быть перенесены из подключения в настройки источника по правилам соответствующего типа СУБД;
* служебная связь между подключением и созданным источником должна сохраняться на Бэкенд, чтобы один и тот же источник можно было обновлять при последующем редактировании подключения;
* источник должен иметь признак автоматического происхождения от подключения, чтобы отличаться от источников, созданных вручную через вкладку {{«Источники»}};
* источник должен наследовать владельца / область видимости подключения для корректного отображения в облачном сценарии;
* настройки источников, неактуальные для данного облачного сценария, не должны становиться обязательными для пользователя.

К настройкам, которые не должны требоваться от аналитика в рамках этого сценария, относятся, например:
* MDX-настройки;
* настройки ФВД;
* дополнительные специализированные признаки источника, если они не нужны для прямого SQL-запроса к поддерживаемой СУБД.

Если для существующего объекта {{datasources}} часть таких полей технически обязательна, требуется заполнять их штатными значениями по умолчанию, не требуя от аналитика работы с вкладкой {{«Источники»}}.

---
h4. 2.4. Синхронизация подключения и связанного источника.

Пока у подключения включён признак {{«DirectQuery»}}, Бэкенд должен синхронизировать связанный источник с актуальными параметрами подключения при успешном сохранении подключения.

Синхронизации подлежат как минимум:
* наименование, если источник был создан автоматически и управляется подключением;
* тип СУБД / драйвер;
* host;
* порт;
* база данных;
* схема;
* пользователь;
* пароль, если пользователь ввёл новое значение пароля в форме подключения;
* другие параметры соединения, которые фактически используются источником данных для DirectQuery.

Если пользователь редактирует подключение с включённым признаком DirectQuery, при сохранении должна происходить актуализация связанного источника. Для пользователя операция должна выглядеть как единое сохранение подключения.

Если обновить связанный источник невозможно, Бэкенд должен вернуть ошибку сохранения подключения и не фиксировать состояние, при котором подключение сохранено с активным DirectQuery, но связанный источник остался несинхронизированным.

Если секрет в форме подключения не изменялся, система не должна отображать его пользователю и не должна затирать сохранённое секретное значение пустым значением. Если пользователь вводит новый пароль, он должен быть обновлён и для подключения, и для связанного источника.

---
h4. 2.5. Отключение параметра DirectQuery для подключения.

При отключении признака {{«DirectQuery»}} необходимо учитывать цепочку зависимых объектов:
Подключение → Источник → Набор данных → Визуализации.

При снятии галочки с параметра {{DirectQuery}}, для которого уже был создан связанный источник данных, система должна обработать зависимость явно и без скрытой потери пользовательских данных.

Предлагаемый механизм:
* при остутствии зависимостей на созданные произвольные наборы данных - параметр отключается для подключения, а связанный источник данных удаляется;
* при наличии зависимостей на созданные наборы данных запретить отключение этого параметра для данного подключения до разрешения конфликтов. Указать причину блокировки (tooltip).
** если отключение заблокировано, Бэкенд должен вернуть понятное сообщение об ошибке. При наличии технической возможности в ответе следует передать информацию, достаточную для отображения причины блокировки пользователю: факт наличия зависимых наборов данных, количество зависимостей или список зависимых объектов.

При *отсутствии зависимых произвольных наборов данных*, если пользователь снимает признак {{«DirectQuery»}} и сохраняет подключение:
* подключение должно остаться доступным для текущих сценариев {{«Правила загрузки данных»}};
* связанный источник не должен отображаться аналитику в списке доступных источников для создания новых произвольных наборов данных;
* служебная связь должна быть обновлена так, чтобы повторное включение DirectQuery не создавало дубли источников.

Если признак {{DirectQuery}} включается повторно:
* связанный источник должен быть создан и параметры по текущему подключению должны быть актуализированы;
* система не должна создавать дубли источников при каждом повторном включении признака.

---
h4. 2.6. Доступность источника при создании произвольного набора данных.

Для {{Modus BI Cloud Start}} (текущей индивидуальной облачной модели):
* аналитик должен иметь доступ к созданным DirectQuery-источники;
* источники других пользователей не должны отображаться аналитику;
* администратор сохраняет текущую возможность видеть объекты по правилам своей роли.

В рамках данной задачи не требуется реализовывать модель совместного доступа для {{Modus BI Cloud Teams}} или рабочих пространств. Совместная видимость подключений, правил загрузки и наборов данных внутри командного контура будет описываться отдельной задачей.

----
h3. 3. Требования к реализации.

h4. 3.1. Фронтенд-часть.

* В форме создания и редактирования {{«Подключения»}} необходимо добавить признак {{«DirectQuery»}} или эквивалентный согласованный текст.
* Признак должен отображаться только для поддерживаемых типов СУБД: {{ClickHouse}}, {{PostgreSQL}}, {{Vertica}}, {{MS SQL Server}}.
* При смене типа подключения в форме доступность признака должна пересчитываться без потери уже введённых параметров подключения.
* При создании нового подключения признак DirectQuery по умолчанию должен быть выключен.
* При редактировании существующего подключения форма должна отображать текущее сохранённое состояние признака DirectQuery.
* При сохранении подключения Фронтенд должен передавать признак DirectQuery в том же запросе, которым сохраняются параметры подключения.
* Фронтенд не должен выполнять отдельный запрос на создание или обновление источника данных; создание, обновление и связывание источника выполняет Бэкенд.
* После успешного сохранения подключения с включённым признаком DirectQuery пользователь должен остаться в понятном штатном состоянии формы: подключение сохранено, источник для DirectQuery создан или обновлён.
* Если источник создать или обновить не удалось, пользователь должен получить штатное сообщение об ошибке. Введённые данные формы не должны теряться.
* Если Бэкенд запрещает отключение DirectQuery или удаление подключения из-за зависимых произвольных наборов данных, Фронтенд должен отобразить пользователю причину блокировки штатным сообщением.
* Вкладка {{«Источники»}} не должна становиться доступной аналитику из-за этой доработки.
* Отображаемое имя такого источника должно позволять пользователю сопоставить его с созданным подключением.

---
h4. 3.2. Бэкенд-часть.

h5. 3.2.1. API.

Точные команды API необходимо подтвердить по текущей реализации, но логика должна соответствовать общему контракту платформы и выполняться через единый запрос создания или обновления {{connection}}:
* Фронтенд передаёт в payload сохранения подключения новый признак включения DirectQuery и стандартные параметры подключения;
* Фронтенд не вызывает отдельные команды {{datasources.create}} / {{datasources.update}} для автоматически создаваемого источника;
* Бэкенд валидирует, что тип подключения поддерживает DirectQuery в рамках текущей задачи;
* при создании нового подключения с включённым признаком {{DirectQuery}} Бэкенд должен создать {{connection}}, создать связанный {{datasources}} по данным этого подключения и сохранить служебную связь между ними;
* при обновлении подключения Бэкенд должен перед изменением получить актуальное состояние через существующий механизм {{get}}/{{list}} или эквивалентное чтение текущего состояния;
* при обновлении подключения с включённым признаком DirectQuery Бэкенд должен обновить связанный {{datasources}} теми параметрами подключения, которые используются источником для прямых запросов;
* при выключении признака DirectQuery Бэкенд должен проверить наличие зависимых произвольных наборов данных и разрешить отключение только при отсутствии таких зависимостей;
* при повторном включении признака DirectQuery Бэкенд должен переиспользовать ранее связанный источник, если это возможно, или создать новый источник без дублирования;
* в ответах чтения подключения Бэкенд должен возвращать сохранённое состояние признака DirectQuery и информацию, достаточную Фронтенд для отображения текущего состояния формы;
* {{object.id}}, {{command.id}} и поля внутри {{data}} не должны смешиваться;
* секреты не должны возвращаться на Фронтенд в открытом виде;
* при отсутствии изменения пароля существующее секретное значение должно сохраняться;
* при изменении пароля новое значение должно применяться и к подключению, и к связанному источнику.

Сохранение подключения с включённым {{DirectQuery}} должно быть консистентным с пользовательской точки зрения. После успешного ответа Бэкенда в системе не должно оставаться состояния, где признак {{DirectQuery}} включён, а связанный источник не создан или недоступен для выбора в произвольном наборе данных - если создание или обновление источника невозможно, Бэкенд должен вернуть ошибку сохранения с понятным сообщением.

Допустимый технический механизм обеспечения консистентности определяется разработкой: транзакция, компенсационное действие или откат включения признака {{DirectQuery}} при неуспешном создании источника.

---
h5. 3.2.2. Метаданные и связь объектов.

На Бэкенде должна быть обеспечена устойчивая связь между подключением и автоматически созданным источником данных.

Логически необходимо хранить:
|| Логическая сущность || Где используется || Назначение ||
| Признак включения {{DirectQuery}} у подключения | {{connection}} | Определяет пользовательское состояние признака и необходимость поддерживать связанный источник данных. |
| Идентификатор связанного источника | {{connection}} или отдельная Бэкенд-связь | Позволяет обновлять один и тот же источник при редактировании подключения, повторном включении DirectQuery и предотвращать создание дублей. |
| Признак автоматического происхождения источника | {{datasources}} | Позволяет отличать источники, созданные из подключений, от источников, созданных вручную через вкладку {{«Источники»}}. |
| Идентификатор исходного подключения у источника | {{datasources}} или отдельная Бэкенд-связь | Позволяет выполнять обратную проверку связи, фильтрацию, диагностику и защиту от несогласованных операций. |
| Владелец / область видимости | {{connection}} и {{datasources}} | Позволяет в {{Cloud Start}} показывать аналитику только собственные DirectQuery-источники. |
| Состояние связанного источника | Бэкенд-связь или {{datasources}} | Позволяет различать активный источник, скрытый/неактивный источник после отключения DirectQuery и отсутствующий источник. |

Информация о зависимых произвольных наборах данных должна определяться Бэкендом на основании фактических связей {{datasets}} → {{datasources}}.

Точные имена полей и физическое место хранения связи должны быть определены разработкой. Источник и подключение должны быть связаны для синхронизации, повторного включения {{DirectQuery}}, фильтрации списка источников и предотвращения дублей.

---
h4. 3.3. Права и доступность.

* Доработка не должна менять текущую ролевую модель {{Modus BI Cloud}}.
* Аналитик не должен получать общий доступ к вкладке {{«Источники»}}.
* Аналитик не должен получать право создавать, редактировать или удалять произвольные Источники данных напрямую.
* Аналитик может инициировать создание и обновление связанного источника только через сохранение своего подключения с включённым признаком {{DirectQuery}}.
* Бэкенд должен проверять, что пользователь имеет право на создание или редактирование соответствующего подключения.
* Автоматическое создание источника должно ограничиваться только поддерживаемыми типами СУБД.
* Пользователь с правами администратора, может видеть автоматически созданные источники по текущим правилам своей роли.

---
h4. 3.4. Удаление подключения.

При удалении подключения, для которого уже был создан связанный источник данных, система должна обработать зависимость явно и без скрытой потери пользовательских данных.

Целевой механизм:
* при отсутствии зависимых произвольных наборов данных удаление происходит по штатному сценарию: удаляется подключение, а связанный автоматически созданный источник удаляется либо переводится Бэкенд в неактивное/скрытое служебное состояние по выбранной модели хранения;
* при наличии зависимых произвольных наборов данных удаление подключения блокируется до разрешения зависимостей;
** Бэкенд должен вернуть понятное сообщение о причине блокировки. При наличии технической возможности в ответе следует передать информацию о зависимых объектах.

---
h4. 3.5. Обратная совместимость.

* Все существующие подключения должны открываться и сохраняться без обязательной миграции пользовательских действий.
* Для существующих подключений признак DirectQuery должен быть выключен, если для них ранее не была создана соответствующая связь.
* Существующие правила загрузки данных должны продолжить работать по прежнему сценарию.
* Существующие источники данных, созданные вручную администраторами через вкладку {{«Источники»}}, не должны превращаться в источники от подключений без явной связи.
* Существующие произвольные наборы данных должны продолжить использовать свои источники по текущей логике.
* Генерация SQL и выполнение DirectQuery должны переиспользовать существующий механизм произвольных наборов данных и источников, без отдельной новой ветки SQL-логики специально для подключений.

----
h3. 4. Пограничные сценарии.

* *Новое поддерживаемое подключение без DirectQuery:* пользователь создаёт подключение к PostgreSQL, ClickHouse, Vertica или MS SQL Server и не включает признак DirectQuery; подключение сохраняется как раньше, источник под капотом не создаётся.
* *Новое поддерживаемое подключение с DirectQuery:* пользователь включает признак DirectQuery; после сохранения появляется связанный источник, доступный в сценарии произвольного набора данных.
* *Существующее подключение:* пользователь открывает ранее созданное подключение поддерживаемого типа, включает DirectQuery и сохраняет; система создаёт связанный источник на базе текущих параметров подключения.
* *Редактирование параметров:* пользователь меняет host, порт, базу, схему, пользователя или пароль у подключения с включённым DirectQuery; после сохранения связанный источник получает актуальные параметры.
* *Пароль не изменялся:* пользователь редактирует подключение с включённым DirectQuery, но не вводит новый пароль; сохранённый секрет не должен быть очищен ни в подключении, ни в источнике.
* *Отключение DirectQuery или удаление подключения при наличии зависимых наборов данных:* Бэкенд запрещает сохранение нового состояния/удаление подключения и возвращает понятную причину блокировки.
* *Повторное включение DirectQuery:* пользователь снова включает признак; система создаёт новый источник, если старый отсутствует, без создания дублей.
* *Пользователь создаёт неподдерживаемый тип подключения:* признак DirectQuery не отображается или недоступен, источник под капотом не создаётся.
* *Ошибка создания источника:* подключение не должно считаться успешно сохранённым с активным DirectQuery, если связанный источник не удалось создать или обновить.
* *Недостаточно прав:* пользователь без прав на создание или редактирование подключения не должен получить возможность создать источник через DirectQuery-признак.

----
h3. 6. Предположения.

* Форма {{«Подключения»}} уже содержит минимальный набор параметров, достаточный для создания связанного источника DirectQuery для поддерживаемых СУБД.
* Для произвольных наборов данных уже существует механизм выбора источника и выполнения запроса напрямую к выбранному {{datasources}}.
* В {{Cloud Start}} действует текущая индивидуальная модель видимости: аналитик видит только собственные подключения, правила загрузки и наборы данных.
* Автоматически созданный источник может быть сохранён как обычный объект {{datasources}} с дополнительной служебной связью с {{connection}}.
* Создание и обновление связанного источника может выполняться Бэкендом на основании тех же параметров, которые фронтенд передаёт при сохранении подключения.

----
h3. 7. Открытые вопросы.

* Нужно согласовать точные технические имена полей и физическое место хранения связи между подключением и автоматически созданным источником: в метаданных подключения, в метаданных источника или в отдельной связующей структуре.
* Нужно подтвердить физическую модель обработки связанного источника при выключении DirectQuery или удалении подключения без зависимостей: удаление объекта {{datasources}} или перевод в неактивное/скрытое служебное состояние.
* Нужно решить, должен ли Бэкенд возвращать во фронтовую форму вычисляемый признак наличия зависимых произвольных наборов данных / список зависимостей до попытки сохранения, или достаточно проверки в момент сохранения.
* Нужно уточнить, должен ли администратор видеть отдельный признак в списке {{«Источники»}}, что источник создан автоматически из подключения.
* Нужно подтвердить итоговый текст UI-признака: «DirectQuery»/«Создать новый источник данных для произвольных наборов» и т.д.

----
h3. 8. Критерии приёмки (AC):

*AC.1 — Отображение признака DirectQuery для поддерживаемых СУБД:*
* *Дано:* аналитик открывает форму создания или редактирования подключения;
* *Когда:* выбран тип подключения {{ClickHouse}}, {{PostgreSQL}} / {{Postgres}}, {{Vertica}} или {{MS SQL Server}};
* *Тогда:* в форме доступен признак {{«DirectQuery»}} или согласованный аналогичный текст.

*AC.2 — Отсутствие признака для неподдерживаемых источников:*
* *Дано:* аналитик создаёт или редактирует подключение типа {{Excel}}, {{Google Sheets}}, {{1С}} или другого неподдерживаемого типа;
* *Когда:* открыта форма подключения;
* *Тогда:* пользователь не может включить DirectQuery для этого подключения, а источник под капотом не создаётся.

*AC.3 — Создание подключения с DirectQuery:*
* *Дано:* аналитик заполнил параметры нового подключения к поддерживаемой СУБД и включил признак DirectQuery;
* *Когда:* пользователь сохраняет подключение;
* *Тогда:* Фронтенд отправляет единый запрос сохранения подключения, а Бэкенд сохраняет подключение и создаёт связанный источник данных с параметрами этого подключения.

*AC.4 — Источник не требует доступа к вкладке «Источники»:*
* *Дано:* аналитик успешно сохранил подключение с включённым DirectQuery;
* *Когда:* пользователь продолжает работу в портале;
* *Тогда:* вкладка {{«Источники»}} остаётся недоступной для аналитика, но связанный источник существует под капотом.

*AC.5 — Доступность источника в произвольном наборе данных:*
* *Дано:* у аналитика есть подключение поддерживаемого типа с включённым DirectQuery;
* *Когда:* аналитик создаёт произвольный набор данных и выбирает источник;
* *Тогда:* в списке доступен автоматически созданный источник, соответствующий этому подключению.

*AC.6 — Выполнение DirectQuery:*
* *Дано:* аналитик выбрал автоматически созданный источник при создании произвольного набора данных;
* *Когда:* пользователь формирует и выполняет запрос набора данных;
* *Тогда:* запрос выполняется напрямую к внешней СУБД через существующий механизм {{datasources}}, без предварительной загрузки данных во внутренний {{ClickHouse}}.

*AC.7 — Сохранение сценария правил загрузки данных:*
* *Дано:* у аналитика есть подключение с включённым DirectQuery;
* *Когда:* аналитик создаёт или редактирует {{«Правило загрузки данных»}} на базе этого подключения;
* *Тогда:* текущий сценарий загрузки данных во внутренний {{ClickHouse}} работает без изменений.

*AC.8 — Синхронизация при редактировании подключения:*
* *Дано:* подключение поддерживаемого типа уже сохранено с включённым DirectQuery и имеет связанный источник;
* *Когда:* аналитик меняет параметры подключения и сохраняет форму;
* *Тогда:* Бэкенд обновляет связанный источник, и DirectQuery использует актуальные параметры подключения.

*AC.9 — Сохранение секретов:*
* *Дано:* аналитик редактирует подключение с включённым DirectQuery и не вводит новый пароль;
* *Когда:* пользователь сохраняет форму;
* *Тогда:* существующий пароль не отображается пользователю, не очищается и продолжает использоваться подключением и связанным источником.

*AC.10 — Обновление секретов:*
* *Дано:* аналитик редактирует подключение с включённым DirectQuery и вводит новый пароль;
* *Когда:* пользователь сохраняет форму;
* *Тогда:* новый пароль применяется к подключению и связанному источнику, а старое значение больше не используется для DirectQuery этого подключения.

*AC.11 — Отключение DirectQuery без зависимостей:*
* *Дано:* у подключения включён признак DirectQuery и существует связанный источник;
* *Когда:* аналитик снимает признак DirectQuery и сохраняет подключение, а связанных произвольных наборов данных нет;
* *Тогда:* подключение остаётся доступным для {{«Правил загрузки данных»}}, а источник перестаёт отображаться аналитику как доступный для создания новых произвольных наборов данных через DirectQuery от подключений.

*AC.12 — Повторное включение без дублей:*
* *Дано:* пользователь ранее выключил DirectQuery для подключения, у которого был связанный источник;
* *Когда:* пользователь снова включает признак DirectQuery и сохраняет подключение;
* *Тогда:* система переиспользует ранее связанный источник или создаёт новый при его отсутствии, но не создаёт дубли источников при каждом повторном включении.

*AC.13 — Ошибка создания или обновления источника:*
* *Дано:* пользователь сохраняет подключение с включённым DirectQuery;
* *Когда:* связанный источник невозможно создать или обновить из-за ошибки Бэкенда, невалидных параметров или недоступности обязательных данных;
* *Тогда:* пользователь получает штатное сообщение об ошибке, введённые данные формы не теряются, а система не фиксирует успешное состояние с включённым DirectQuery и отсутствующим источником.

*AC.14 — Видимость только собственных источников в Cloud Start:*
* *Дано:* в {{Cloud Start}} есть несколько аналитиков, у каждого есть свои подключения с включённым DirectQuery;
* *Когда:* один из аналитиков создаёт произвольный набор данных;
* *Тогда:* он видит только источники, созданные из его собственных DirectQuery-подключений, и не видит источники других аналитиков.

*AC.15 — Ограничение прав аналитика:*
* *Дано:* пользователь имеет роль {{«аналитик»}} в облаке;
* *Когда:* пользователь работает с подключениями и произвольными наборами данных после доработки;
* *Тогда:* он может использовать DirectQuery-источник, созданный из своего подключения, но не получает общий доступ к созданию, редактированию или просмотру вкладки {{«Источники»}}.

*AC.16 — Существующие подключения без регресса:*
* *Дано:* в системе есть подключения, созданные до внедрения признака DirectQuery;
* *Когда:* пользователь открывает или сохраняет такое подключение без включения нового признака;
* *Тогда:* подключение работает по прежней логике, источник под капотом не создаётся, правила загрузки данных не ломаются.

*AC.17 — Существующие источники без регресса:*
* *Дано:* в системе есть источники данных, созданные вручную через вкладку {{«Источники»}};
* *Когда:* внедряется механизм DirectQuery через подключения;
* *Тогда:* существующие источники и произвольные наборы данных продолжают работать по текущей логике и не получают служебную связь с подключениями без явного основания.

*AC.18 — Удаление подключения с зависимостями:*
* *Дано:* у подключения есть связанный DirectQuery-источник, который используется в произвольном наборе данных;
* *Когда:* пользователь пытается удалить подключение;
* *Тогда:* Бэкенд запрещает удаление подключения и возвращает понятное сообщение о причине блокировки; источник, набор данных и связанные визуализации не удаляются автоматически.

*AC.19 — Запрет отключения DirectQuery при зависимых наборах данных:*
* *Дано:* у подключения включён DirectQuery, и связанный источник используется хотя бы одним произвольным набором данных;
* *Когда:* аналитик снимает признак DirectQuery и сохраняет подключение;
* *Тогда:* Бэкенд запрещает сохранение нового состояния и возвращает понятное сообщение о причине блокировки; текущее состояние подключения и связанного источника сохраняется.
