h3. 1. Цель и контекст.

В нашем аналитическом портале проводится внедрение единого нового редактора кода на базе {{CodeMirror}}. Редактор уже используется на основном портале в {{«Вычисляемых полях»}} и {{«Наборах данных»}} и должен стать стандартным инструментом для работы с SQL/JS и прочим кодом во всех релевантных точках внедрения портала.

Настоящая задача рассматривает следующую точку внедрения — {{«Правила загрузки данных»}}.

{{Правила загрузки данных}} используются в сценариях подготовки данных в облачном портале (вкладки: {{«Подключения»}}, {{«Правила загрузки данных»}}, {{«Наборы данных»}}) - этот функционал был создан в первую очередь для {{Modus BI Cloud}}, где у пользователей нет доступа к ETL, но также может быть активирован в {{On-Premise}}-поставке через настройки метаданных портала. В этом сценарии пользователь настраивает подключение к источнику, задаёт запрос к источнику данных, загружает результат во внутреннее хранилище {{ClickHouse}} и далее использует загруженные данные для построения простых и составных наборов данных.

Сейчас в {{«Правилах загрузки данных»}} для источников, где требуется вручную задать текст запроса, используется старый простой редактор. Он не соответствует уже принятому UX редактора кода в портале: поле небольшое, отсутствуют возможности {{CodeMirror}}, нет единого поведения с редактором SQL в {{«Наборах данных»}}.

*Цель задачи* — заменить старый редактор поля {{«Текст запроса»}} в {{«Правилах загрузки данных»}} на переиспользуемый редактор {{CodeMirror}}, сохранив существующую бизнес-логику создания, редактирования, проверки и сохранения правила загрузки данных.

{panel:title=Ключевой принцип интеграции:|borderStyle=dashed|borderColor=#ccc|titleBGColor=#DDEBF7|bgColor=#F8FBFF}
* Новый редактор должен использовать уже реализованный переиспользуемый виджет {{CodeMirror}}, а не отдельную локальную реализацию для {{«Правил загрузки данных»}}.
* Внедрение редактора не должно менять смысл работы {{«Правил загрузки данных»}}: пользователь по-прежнему настраивает правило загрузки данных, задаёт запрос к источнику, сохраняет правило и запускает загрузку данных по текущим правилам модуля.
* Источником истины для сохранения и выполнения запроса остаётся текущая бизнес-логика {{«Правил загрузки данных»}} и соответствующие backend-объекты.
* При открытии модального окна редактор должен сразу открываться в расширенном виде: с центральной зоной {{CodeMirror}}, левой панелью метаданных выбранного источника данных и верхней панелью часто используемых вставок.
* Редактор должен подстраивать режим подсветки/диалект по типу источника данных, если тип можно определить из правила или связанного подключения.
* Для источников, где в текущем интерфейсе нет поля {{«Текст запроса»}} и пользователь не пишет запрос вручную, поведение не меняется.
{panel}

h3. 2. Описание текущего поведения.

h4. 2.1. Сценарий с подключениями к СУБД.

В сценарии загрузки данных через {{«Подключения»}} пользователь сначала создаёт подключение к источнику данных. Для подключений к СУБД оно содержит базовые настройки доступа: наименование, сервер, порт, базу данных, схему, пользователя, пароль и другие параметры конкретного драйвера.

Само подключение не определяет, какие данные нужно забрать из источника. Для этого пользователь переходит в {{«Правила загрузки данных»}} и задаёт запрос к источнику через действие {{«Текст запроса»}}.

Сейчас при открытии {{«Текст запроса»}} отображается старый редактор:
* он визуально мал и неудобен для написания длинных SQL-запросов;
* не поддерживает подсветку синтаксиса и другие продвинутые функции нового редактора кода {{CodeMirror}};
* не предоставляет боковую панель метаданных выбранного источника данных и верхнюю панель часто используемых вставок.

---
h4. 2.2. Сценарий с файловыми источниками.

Для файловых источников и табличных сервисов, где в текущем интерфейсе нет ручного ввода запроса, пользователь работает не с SQL-редактором, а с настройками загрузки файла/листа/диапазона/колонок.

Например, для Excel/Google Sheets пользователь выбирает файл или таблицу, лист, строку заголовка, диапазон строк и набор колонок для загрузки. Поле {{«Текст запроса»}} в этом сценарии сейчас не используется и изменения не планируются в рамках этой задачи.

---
h4. 2.3. Разница между {{«Источниками»}} и {{«Подключениями»}}.

В стандартном сценарии {{«Источники»}} → {{«Наборы данных»}} запросы к внешнему источнику могут выполняться напрямую, в режиме обращения к исходной СУБД.

В сценарии {{«Подключения»}} → {{«Правила загрузки данных»}} данные сначала забираются из внешнего источника и перекладываются во внутреннее хранилище портала {{ClickHouse}}. Далее на основании загруженных данных создаются наборы данных, в том числе для построения составных наборов из разных источников.

{panel:title=Не входит в рамки текущей задачи:|borderStyle=dashed|borderColor=#ccc|titleBGColor=#FCE4D6|bgColor=#FFF8F2}
Текущая задача не решает UX-разграничение вкладок {{«Источники»}} и {{«Подключения»}}, не меняет модель загрузки данных во внутренний {{ClickHouse}} и не пересобирает сценарии создания наборов данных. 
В рамках задачи требуется только внедрение нового редактора кода в существующий сценарий {{«Правил загрузки данных»}}.
{panel}

h3. 3. Описание целевого поведения.

h4. 3.1. Общий пользовательский сценарий.

После доработки пользователь, имеющий доступ к {{«Правилам загрузки данных»}}, должен работать с текстом запроса через новый редактор {{CodeMirror}}.

Целевой сценарий:
# Пользователь открывает {{Modus BI Cloud}} (или {{On-Premise}}-портал, где активирован функционал {{«Правила загрузки данных»}}).
# Пользователь создаёт новое или открывает существующее правило загрузки данных для источника, где предусмотрен ручной ввод текста запроса.
# Пользователь нажимает кнопку {{«Текст запроса»}}.
# Вместо старого простого редактора открывается модальное окно укрупнённого вида с рабочей областью редактора {{CodeMirror}}.
# Редактор получает текущий текст запроса из правила загрузки данных.
# Пользователю сразу доступны центральная зона ввода {{CodeMirror}}, левая панель метаданных выбранного источника данных и верхняя панель часто используемых вставок.
# Пользователь редактирует запрос с обновленным UX редактора кода: подсветкой синтаксиса, нумерацией строк, автозакрытием скобок/кавычек, Undo/Redo, автодополнением, внутренним скроллом, вставкой шаблонов функций и вставкой объектов источника из боковой панели в редактор.
# При применении текста запроса и последующем сохранении правила используется текущая бизнес-логика формы и текущие backend-контракты.
# Существующие сценарии проверки, сохранения и запуска загрузки данных продолжают работать без регресса.

---
h4. 3.2. Область применения по типам источников.

Редактор {{CodeMirror}} должен использоваться во всех {{«Правилах загрузки данных»}}, где текущий интерфейс уже предполагает ручной ввод текста запроса.

В первую очередь это правила для подключений к СУБД и SQL-подобным источникам, включая, но не ограничиваясь:
* PostgreSQL;
* MS SQL Server;
* ClickHouse;
* Vertica;
* другие СУБД, для которых в текущей форме доступно действие {{«Текст запроса»}}.

Для источников {{1С}} редактор также должен открываться в этой же точке, так как текущий сценарий правила загрузки предполагает ручной ввод запроса. При этом:
* если в проекте уже есть или может быть без отдельной крупной доработки подключён режим подсветки синтаксиса {{1С}}, редактор должен использовать его;
* если режим подсветки синтаксиса {{1С}} недоступен, редактор должен использовать согласованный fallback-режим, не блокирующий работу пользователя с текстом запроса;
* полноценная адаптация языка запросов {{1С}} для редактора кода не является блокером текущей задачи и может быть вынесена в отдельную задачу, если потребуется.

Для Excel, Google Sheets и других источников, где пользователь не пишет текст запроса вручную и в текущем интерфейсе отсутствует действие {{«Текст запроса»}}, внедрение редактора не требуется.

---
h4. 3.3. Поведение в Cloud и On-Premise.

Доработка должна работать одинаково:
* в {{Modus BI Cloud}}, где сценарий {{«Подключения»}}/{{«Правила загрузки данных»}} является основным способом подготовки данных без ETL;
* в {{On-Premise}}-поставке, если соответствующий функционал активирован в настройках метаданных портала.

Доработка не должна зависеть от того, где развёрнуто внутреннее хранилище {{ClickHouse}}: в облачной инфраструктуре Modus BI или в контуре заказчика.

h3. 4. Функциональные требования к реализации.

h4. 4.1. Точка входа и замена старого редактора.

* В форме создания/редактирования {{«Правила загрузки данных»}} старый редактор, открываемый по действию {{«Текст запроса»}}, должен быть заменён на редактор {{CodeMirror}}.
* Пользовательский сценарий открытия редактора должен остаться привычным: пользователь по-прежнему открывает редактирование текста запроса из текущей формы правила загрузки данных по действию {{«Текст запроса»}}, новый редактор открывается в модальном окне укрупненного вида с возможностью управления размером (высотой) окна редактора.
* При открытии модального окна редактор сразу должен быть доступен в расширенном виде: без отдельного переключения режима должны отображаться центральная зона {{CodeMirror}}, левая панель метаданных и верхняя панель вспомогательных вставок.
* При открытии редактора в него должен подставляться актуальный текст запроса из текущего состояния правила.
* Если правило новое и текст запроса ещё не задан, редактор должен открываться пустым.
* Сохранение текста запроса должно выполняться по текущей логике формы: внедрение {{CodeMirror}} не должно вводить отдельную сущность черновика и не должно требовать нового backend-контракта только для хранения текста редактора.

---
h4. 4.2. Геометрия и UX окна редактора.

* Рабочая область редактора должна быть больше текущего поля и пригодна для чтения/редактирования длинных запросов.
* Редактор должен открываться в модальном окне укрупнённого вида с регулировкой по высоте и с рабочим пространством, удобным для написания длинных SQL-запросов.
* Внутри модального окна должна быть реализована трехзонная компоновка:
** *центральная основная зона* — редактор {{CodeMirror}};
** *левая вспомогательная зона* — панель метаданных выбранного источника данных;
** *верхняя вспомогательная зона* — панель шаблонов и служебных вставок, расположенная над центральной зоной редактора.
* Основная площадь рабочего пространства должна быть отдана редактору {{CodeMirror}}.
* Внутри редактора должен работать вертикальный скролл для длинного SQL/текста запроса.
* Для длинного содержимого левой панели должен работать внутренний скролл области панели.
* Верстка формы правила загрузки данных не должна ломаться при длинном запросе, открытии/закрытии редактора, изменении размера окна браузера или редактора.
* Размер модального окна должен быть достаточным для полноценной работы с кодом, левой панелью метаданных и верхней панелью вспомогательных вставок.
* Левая панель должна иметь адаптивно-фиксированную ширину, достаточную для чтения содержимого.
* Пользователь должен иметь возможность изменять ширину левой панели перетаскиванием её правой границы, если это поддерживается используемым компонентом.
* Для удобства работы на узких экранах левая панель должна иметь возможность сворачиваться, но должна оставаться доступной без выхода из редактора.
* Допускается переиспользовать паттерн управления высотой, реализованный для редактора SQL в {{«Наборах данных»}}: вертикальный ресайз и краткосрочное запоминание высоты при закрытии/повторном открытии модального окна в рамках текущей сессии.
* Управление размером (высотой) окна редактора:
** *Регулировка по высоте:* Область нового редактора {{CodeMirror}} должна поддерживать возможность ручного изменения размера по вертикали (resize) с помощью перетаскивания нижней границы окна.
** *Фиксированная ширина модального окна:* Ширина окна редактора определяется текущим паттерном модального окна и не подлежит ручному изменению пользователем, если в общем компоненте не предусмотрен иной сценарий.
** *Адаптивность окружения:* При изменении высоты редактора содержимое модального окна должно корректно адаптироваться, без наложения элементов друг на друга.
** *Размер по умолчанию:* При первоначальном открытии редактора в текущем правиле загрузки данных его высота должна быть равна системному значению по умолчанию.
** *Краткосрочная память состояния:* В рамках непрерывной работы с *текущим* правилом загрузки данных, если пользователь изменил высоту модального окна редактора, а затем закрыл и повторно открыл его в этой же сессии, должна восстанавливаться измененная пользователем высота.
** *Отсутствие долговременной персистентности:* Измененная высота редактора *не должна* сохраняться в БД вместе с правилом загрузки данных, а также не должна фиксироваться в пользовательских настройках между сессиями. При обновлении страницы (F5), выходе из текущего правила загрузки данных - допускается сбрасывание состояния высоты к дефолтным значениям.
* Изменение размера редактора не должно считаться изменением бизнес-данных правила и не должно само по себе активировать сохранение правила.

---
h4. 4.3. Базовый UX {{CodeMirror}}.

В {{«Правилах загрузки данных»}} должен быть сохранён базовый UX переиспользуемого виджета {{CodeMirror}}:
* нумерация строк;
* подсветка синтаксиса;
* подсветка и автозакрытие скобок/кавычек;
* поддержка Undo/Redo через стандартные горячие клавиши;
* поддержка мультикурсорного редактирования (если она уже включена в общем виджете);
* корректный вертикальный внутренний скролл;
* стабильная работа с длинными запросами;
* автодополнение при вводе текста и по явной горячей клавише, например {{Ctrl+Space}};
* отсутствие конфликтов горячих клавиш редактора с действиями основной формы.

Проверка или выполнение запроса не должны запускаться автоматически на каждый ввод символа. Любые текущие действия проверки/предпросмотра/сохранения должны оставаться явными действиями пользователя.

---
h4. 4.4. SQL-диалект и режим подсветки.

Редактор должен определять режим подсветки по типу источника данных, связанному с правилом загрузки.

Правила определения режима:
* если тип источника можно однозначно определить из текущего правила загрузки данных или связанного подключения, редактор должен использовать соответствующий диалект-режим {{CodeMirror}};
* если для типа источника в текущей реализации уже есть прямое сопоставление с диалектом {{CodeMirror}}, должно использоваться это сопоставление;
* если нативный диалект отсутствует, должен использоваться согласованный fallback-режим, например {{Basic SQL}}/{{StandardSQL}} или уже реализованный в проекте общий режим (необходимо учитывать наличие языка запросов {{1С}});
* если тип источника изменён пользователем в рамках формы, режим редактора должен обновиться без потери текущего текста запроса;
* если тип источника не определён, редактор должен оставаться в работоспособном fallback-режиме.

Для источников {{1С}}:
* при наличии доступного режима подсветки языка запросов {{1С}} нужно использовать его;
* при отсутствии такого режима нужно применять fallback без блокировки редактирования;
* отсутствие полноценной подсветки {{1С}} не должно приводить к невозможности открыть или сохранить текст запроса.

---
h4. 4.5. Автодополнение и верхняя панель вспомогательных вставок.

В обязательный состав подсказок должны входить:
* стандартные SQL-ключевые слова;
* встроенные SQL-функции, доступные в общем виджете редактора;
* служебные конструкции, уже поддержанные в общем редакторе, если они применимы к запросам правил загрузки данных.

Если в общем редакторе уже реализовано автодополнение с учётом метаданных и для текущего подключения доступны метаданные источника, допускается переиспользовать этот механизм в {{«Правилах загрузки данных»}}. При этом отсутствие метаданных источника не должно блокировать базовое автодополнение SQL-ключевых слов и функций.

Над центральной зоной редактора должна отображаться вспомогательная панель служебных вставок.

Минимально обязательный состав кнопок верхней панели:
* {{SUM}};
* {{AVG}};
* {{MIN}};
* {{MAX}};
* {{COUNT}};
* {{DISTINCT}};
* другие часто используемые SQL-функции из общего набора шаблонов, используемого в аналогичных местах редактора.

При нажатии на кнопку в область ввода редактора должен вставляться соответствующий шаблон кода.

Требования к вставке из верхней панели:
* вставка должна выполняться в текущую позицию каретки;
* если редактор временно потерял фокус, должна использоваться последняя известная позиция каретки;
* если пользователь ранее не фокусировался в редактор, вставка допускается в конец SQL-скрипта;
* если в редакторе включен мультикурсор, вставка должна выполняться по всем активным курсорам;
* вставка шаблона не должна автоматически запускать проверку, предпросмотр или сохранение запроса.

---
h4. 4.6. Левая панель с метаданными источника данных.

В левой части модального окна редактора должен отображаться список метаданных *выбранного источника данных*.

Источником данных для этой панели должны быть метаданные текущего подключенного источника, а не результат последней успешной проверки SQL.

В панели должны быть доступны как минимум:
* схемы;
* таблицы/объекты источника;
* поля таблиц;
* при наличии — типы полей.

Панель должна поддерживать:
* поиск;
* разворачивание и сворачивание узлов;
* корректное состояние загрузки;
* корректную пустую заглушку, если метаданные для выбранного источника отсутствуют;
* понятное сообщение об ошибке, если метаданные временно недоступны.

Метаданные должны быть доступны пользователю без обязательного предварительного успешного выполнения текущего SQL-запроса.

Если метаданные источника временно недоступны, это не должно блокировать ручное редактирование, сохранение текста запроса и работу базового автодополнения SQL-ключевых слов/функций.

---
h4. 4.7. Переиспользование дерева метаданных из составного набора данных.

{panel:title=Важно: функционал "Дерево метаданных" уже частично реализован в рамках составного набора данных |borderStyle=dashed|borderColor=#ccc|titleBGColor=#DDEBF7|bgColor=#F8FBFF}
* Функционал дерева метаданных уже частично реализован в рамках интерфейса {{составного набора данных}}.
* В рамках текущей задачи не требуется реализовывать дерево метаданных с нуля, если существующие наработки можно адаптировать для редактора SQL в {{«Правилах загрузки данных»}}.
* Перед разработкой необходимо провести техническую проверку существующей реализации: источник получения метаданных, структура дерева, поиск, разворачивание/сворачивание узлов, состояния загрузки/ошибки/пустого результата, механизм выбора/перетаскивания элементов и ограничения по типам источников.
* Пригодные части реализации должны быть переиспользованы или вынесены в переиспользуемый компонент/адаптер без изменения пользовательского сценария {{составных наборов данных}}.
* Если часть функциональности из составного набора данных не покрывает требования текущего редактора, недостающие возможности дорабатываются точечно в рамках требований п. 4.6 и 4.8, без дублирования уже существующей логики.
* Переиспользование существующих наработок не должно менять границы задачи: доработка внедряется для {{«Правил загрузки данных»}}, а сценарии создания/редактирования {{составных}} наборов данных в рамках этой истории не изменяются.
{panel}

---
h4. 4.8. Вставка объектов из боковой панели в редактор.

Объекты из левой панели должны быть доступны для вставки в SQL в области ввода редактора кода.

Базовый способ вставки — {{Drag-and-Drop}} в область редактора.

Дополнительно допускается поддержка альтернативного действия вставки, например двойной клик, если это не усложняет UX и не конфликтует с текущим поведением дерева метаданных.

Из левой панели в редактор должны вставляться:
* имена таблиц/объектов источника;
* имена полей.

Вставка должна происходить *в текущую позицию каретки*:
* если редактор временно потерял фокус, должна использоваться последняя известная позиция каретки;
* если пользователь ранее не фокусировался в редактор, вставка допускается в конец SQL-скрипта;
* если в редакторе включен мультикурсор, вставка должна выполняться по всем активным курсорам;
* если для корректной SQL-вставки требуется экранирование/кавычки в соответствии с диалектом текущего источника, вставка должна использовать синтаксически безопасную форму идентификатора.

---
h4. 4.9. Системный синтаксис и специальные конструкции.

Редактор не должен ломать уже допустимые в платформе системные конструкции, если они могут использоваться в тексте запроса правила загрузки данных.

Конфигурация редактора должна корректно обрабатывать как минимум те системные токены, которые уже поддержаны в общем редакторе SQL для {{«Наборов данных»}}, включая:
* {{\!env.NAME\!}};
* {{\!env.NAME.BEGIN\!}};
* {{\!env.NAME.END\!}};
* конструкции с fallback-логикой внутри фигурных скобок;
* иные серверные/системные переменные проекта, допустимые по текущим правилам платформы.

Такие конструкции не должны помечаться как синтаксическая ошибка только из-за того, что они не являются стандартным SQL.

---
h4. 4.10. Проверка, предпросмотр и выполнение запроса.

Уже существующие в форме {{«Правила загрузки данных»}} действия проверки запроса, предпросмотра результата, сохранения правила или запуска загрузки должны работать по старой логике без изменений.

Требования:
* проверка/предпросмотр должны использовать актуальный текст, который пользователь видит в редакторе;
* при успешной проверке/предпросмотре должна отработать текущая бизнес-логика модуля;
* при ошибке текст запроса не должен теряться;
** редактор не должен самопроизвольно закрываться при ошибке запроса;
** пользователь должен получить штатное сообщение об ошибке;
* если backend возвращает информацию о позиции ошибки и общий редактор умеет её визуально подсветить, это место должно быть акцентировано в редакторе;
* если точную позицию определить нельзя, достаточно показать понятное текстовое сообщение по текущим правилам интерфейса.

---
h4. 4.11. Сохранение правила загрузки данных и backend-контракты.

В рамках задачи требуется переиспользовать текущие команды чтения, создания, обновления и сохранения правил загрузки данных. Актуальные имена команд необходимо подтвердить по текущей реализации модуля, но логика должна соответствовать общему контракту платформы:
* перед обновлением существующего правила текущее состояние должно быть получено через {{get}}/{{list}} или уже существующий механизм чтения формы;
* при сохранении нового правила текст запроса должен попадать в текущий payload создания правила;
* при сохранении существующего правила текст запроса должен попадать в текущий payload обновления правила;
* {{object.id}}, {{command.id}} и поля внутри {{data}} не должны смешиваться;
* внедрение редактора не должно требовать изменения структуры хранения текста запроса, если текущая структура уже достаточна;
* пароли, токены и другие секреты связанного подключения не должны отображаться в редакторе и не должны попадать в текст запроса автоматически.

Если для определения диалекта редактора требуется тип источника, он должен браться из уже доступных данных правила/подключения. Если этих данных недостаточно, необходимо использовать существующий механизм получения связанного подключения или зафиксировать fallback-режим без дополнительного блокирующего запроса.

---
h4. 4.12. Обратная совместимость.

* Все ранее созданные правила загрузки данных должны открываться без миграции.
* Существующий текст запроса должен отображаться в новом редакторе без изменения содержимого.
* Сохранение правила после редактирования должно формировать совместимый payload и не должно ломать backend-обработку загрузки данных.
* Переносы строк, кавычки, регистр, комментарии и форматирование пользовательского запроса не должны изменяться автоматически при открытии/закрытии редактора.
* Старые правила для источников с неизвестным или устаревшим типом должны открываться в fallback-режиме редактора.
* Права доступа к {{«Правилам загрузки данных»}} не должны расширяться: новый редактор доступен только тем пользователям, которым уже разрешено создавать/редактировать соответствующие правила.

---
h4. 4.13. Границы реализации.

В рамки текущей задачи входит:
* замена старого редактора {{«Текст запроса»}} в {{«Правилах загрузки данных»}} на переиспользуемый {{CodeMirror}};
* поддержка базового UX {{CodeMirror}};
* открытие редактора сразу в расширенном виде с центральной зоной {{CodeMirror}}, левой панелью метаданных и верхней панелью вспомогательных вставок;
* отображение метаданных выбранного источника данных в левой панели без обязательного предварительного успешного выполнения текущего SQL-запроса;
* вставка таблиц/объектов и полей из левой панели в редактор, включая базовый сценарий {{Drag-and-Drop}};
* вставка шаблонов часто используемых SQL-функций из верхней панели;
* определение режима подсветки/диалекта по типу источника данных;
* fallback-режим для источников без нативного диалекта;
* применение редактора для источников {{1С}} в рамках существующего сценария ручного ввода запроса;
* сохранение текущей бизнес-логики;
* работа в {{Modus BI Cloud}} и в {{On-Premise}} при активированном функционале правил загрузки данных;
* отсутствие регресса для существующих правил загрузки.

h3. 5. Пограничные сценарии.

* *Пустой запрос:* новое правило без заданного текста запроса должно открывать редактор без ошибки; обязательность заполнения запроса должна проверяться текущими правилами формы/сохранения.
* *Длинный запрос:* многострочный запрос должен редактироваться с внутренним скроллом без поломки формы.
* *Неизвестный тип источника:* редактор должен открыться в fallback-режиме.
* *Источник {{1С}} без отдельного режима подсветки:* пользователь должен иметь возможность открыть, изменить и сохранить текст запроса; отсутствие подсветки {{1С}} не должно блокировать сценарий.
* *Файловый источник без текста запроса:* интерфейс Excel/Google Sheets не должен получить лишний редактор.
* *Ошибка проверки запроса:* текст в редакторе должен сохраниться, пользователь должен увидеть сообщение об ошибке.
* *Недоступность метаданных источника:* если метаданные не загружены или backend вернул ошибку получения метаданных, пользователь должен видеть корректное состояние в левой панели и сохранять возможность вручную редактировать текст запроса.
* *Пустые метаданные источника:* если для выбранного источника нет доступных схем/таблиц/полей, левая панель должна показывать пустую заглушку без поломки редактора.
* *Длинное дерево метаданных:* содержимое левой панели должно прокручиваться внутри панели и не должно растягивать модальное окно сверх рабочей области.
* *Узкий экран:* левая панель должна сворачиваться и оставаться доступной без закрытия модального окна редактора.
* *Потеря фокуса:* переключение между полями формы, левой панелью, верхней панелью и редактором не должно сбрасывать каретку и текст запроса сверх поведения общего виджета.
* *Вставка без активного фокуса редактора:* при вставке шаблона функции или объекта из левой панели должна использоваться последняя известная позиция каретки, а если её нет — конец SQL-скрипта.
* *Мультикурсор при вставке:* если в редакторе активен мультикурсор, вставка шаблона или объекта должна применяться ко всем активным курсорам с учётом возможностей общего виджета.
* *Экранирование идентификаторов:* при вставке таблиц/полей из левой панели должны использоваться правила безопасной вставки идентификатора для текущего SQL-диалекта, если такие правила применимы.
* *Мультикурсор/Undo/Redo:* стандартные возможности общего виджета не должны отключаться в этой точке внедрения.
* *Смена источника/подключения:* если сценарий формы допускает смену источника для правила, текст запроса не должен теряться автоматически; режим подсветки должен пересчитаться по новому типу источника.
* *Старое правило:* правило, созданное до внедрения редактора, должно открываться с тем же текстом запроса.
* *Недостаточно прав:* пользователь без прав редактирования правил загрузки не должен получать возможность изменить текст запроса только из-за нового редактора.

h3. 7. Открытые вопросы и предположения.

* {{Правила загрузки данных}} на backend соответствуют объекту {{extraction_rules}}. Перед реализацией необходимо подтвердить актуальные команды чтения/сохранения в текущем модуле.
* Тип источника данных доступен из состояния правила загрузки или связанного подключения и может быть использован frontend-частью для выбора режима подсветки.
* Нужно подтвердить у разработки точные поля payload, в которых в {{extraction_rules}} хранится текст запроса и тип источника данных.
* Нужно подтвердить актуальный способ получения метаданных выбранного источника данных для левой панели редактора. Источником панели должны быть метаданные текущего подключенного источника, а не результат последней успешной проверки SQL.
* Нужно проверить применимость существующего дерева метаданных из {{составного набора данных}} для сценария {{«Правил загрузки данных»}}, включая поиск, состояния загрузки/ошибки/пустого результата и механизм {{Drag-and-Drop}} в редактор.
* Нужно подтвердить, есть ли в текущем стеке готовый режим подсветки для языка запросов {{1С}}. Если нет, текущая задача должна использовать fallback, а полноценную поддержку {{1С}} нужно оформить отдельной задачей.
* Нужно уточнить требуются ли действия проверки запроса/предпросмотра в форме {{«Правила загрузки данных»}}, так как их внедрение может повлечь изменения в бизнес-логике.

h3. 8. Критерии приёмки (AC):

* *AC1 (Замена редактора):*
** *Дано:* пользователь открывает создание или редактирование {{«Правила загрузки данных»}} для источника, где доступно действие {{«Текст запроса»}};
** *Когда:* пользователь открывает {{«Текст запроса»}};
** *Тогда:* вместо старого редактора отображается переиспользуемый редактор {{CodeMirror}}.

* *AC2 (Загрузка текущего значения):*
** *Дано:* в существующем правиле загрузки данных уже сохранён текст запроса;
** *Когда:* пользователь открывает редактор {{«Текст запроса»}};
** *Тогда:* в {{CodeMirror}} отображается актуальный сохранённый текст запроса без потери форматирования.

* *AC3 (Редактирование нового правила):*
** *Дано:* пользователь создаёт новое правило загрузки данных для источника с ручным вводом запроса;
** *Когда:* пользователь открывает {{«Текст запроса»}} и вводит запрос;
** *Тогда:* введённый текст сохраняется в текущем состоянии формы и передаётся в текущий payload создания правила при штатном сохранении.

* *AC4 (Базовый UX CodeMirror):*
** *Дано:* открыт редактор текста запроса в {{«Правилах загрузки данных»}};
** *Когда:* пользователь редактирует запрос;
** *Тогда:* работают нумерация строк, подсветка синтаксиса, автозакрытие скобок/кавычек, Undo/Redo, внутренний скролл и автодополнение по базовым SQL-ключевым словам/функциям.

* *AC5 (Размер и верстка):*
** *Дано:* пользователь открыл редактор {{«Текст запроса»}};
** *Когда:* запрос занимает много строк или пользователь меняет размер окна браузера;
** *Тогда:* редактор остаётся пригодным для работы, внутри него доступен скролл, элементы формы не перекрываются и не разъезжаются.

* *AC6 (Сохранение текущей бизнес-логики):*
** *Дано:* пользователь изменил текст запроса в редакторе;
** *Когда:* пользователь выполняет штатное сохранение правила загрузки данных;
** *Тогда:* правило сохраняется по текущему backend-контракту {{extraction_rules}}, а внедрение редактора не требует отдельного нового объекта или отдельного хранения черновика.

* *AC7 (Проверка/предпросмотр по актуальному тексту):*
** *Дано:* в форме правила загрузки данных доступно действие проверки или предпросмотра запроса;
** *Когда:* пользователь меняет текст в {{CodeMirror}} и запускает это действие;
** *Тогда:* проверка/предпросмотр выполняется по актуальному тексту из редактора.

* *AC8 (Ошибка запроса не приводит к потере текста):*
** *Дано:* пользователь ввёл некорректный запрос;
** *Когда:* проверка/предпросмотр возвращает ошибку;
** *Тогда:* пользователь видит штатное сообщение об ошибке, редактор не теряет введённый текст и не закрывается самопроизвольно.

* *AC9 (Определение диалекта по типу источника):*
** *Дано:* правило загрузки данных связано с источником PostgreSQL, MS SQL Server, ClickHouse, Vertica, MySQL или другим поддержанным типом СУБД;
** *Когда:* пользователь открывает {{«Текст запроса»}};
** *Тогда:* редактор использует соответствующий режим подсветки/диалект, если он доступен в текущем сопоставлении {{CodeMirror}}.

* *AC10 (Fallback для неизвестного диалекта):*
** *Дано:* тип источника не определён или для него отсутствует нативный режим {{CodeMirror}};
** *Когда:* пользователь открывает редактор;
** *Тогда:* редактор открывается в fallback-режиме и остаётся работоспособным для редактирования и сохранения текста запроса.

* *AC11 (Источник 1С):*
** *Дано:* правило загрузки данных относится к источнику {{1С}} и в текущем сценарии есть ручной текст запроса;
** *Когда:* пользователь открывает {{«Текст запроса»}};
** *Тогда:* открывается тот же редактор {{CodeMirror}}; при наличии режима {{1С}} используется он, при отсутствии — применяется fallback без блокировки редактирования и сохранения.

* *AC12 (Файловые источники не затронуты):*
** *Дано:* пользователь настраивает загрузку из Excel, Google Sheets или другого источника, где текущий интерфейс не содержит ручного текста запроса;
** *Когда:* пользователь работает с настройками файла, листа, диапазона и колонок;
** *Тогда:* новый SQL-редактор не появляется, текущий файловый сценарий работает без изменений.

* *AC13 (Облако и On-Premise):*
** *Дано:* функционал {{«Подключения»}} / {{«Правила загрузки данных»}} доступен в {{Modus BI Cloud}} или активирован в {{On-Premise}};
** *Когда:* пользователь открывает правило загрузки данных с ручным текстом запроса;
** *Тогда:* новый редактор работает одинаково в обоих вариантах поставки.

* *AC14 (Старые правила):*
** *Дано:* правило загрузки данных было создано до внедрения {{CodeMirror}};
** *Когда:* пользователь открывает и сохраняет это правило после доработки;
** *Тогда:* существующий текст запроса корректно отображается, редактируется и сохраняется без обязательной миграции и без изменения структуры данных.

* *AC15 (Права доступа):*
** *Дано:* пользователь не имеет прав на создание/редактирование правил загрузки данных;
** *Когда:* пользователь открывает соответствующий раздел или правило;
** *Тогда:* новый редактор не даёт ему дополнительных возможностей изменить текст запроса сверх уже разрешённых прав.

* *AC16 (Отсутствие регресса загрузки):*
** *Дано:* пользователь отредактировал и сохранил валидный текст запроса в правиле загрузки данных;
** *Когда:* пользователь запускает загрузку данных по правилу;
** *Тогда:* загрузка выполняется по текущей бизнес-логике модуля, данные попадают во внутреннее хранилище по прежнему сценарию, а внедрение редактора не меняет результат загрузки.

* *AC17 (Системный синтаксис):*
** *Дано:* в тексте запроса используются системные конструкции, уже допустимые платформой, например {{\!env.NAME\!}};
** *Когда:* пользователь открывает и редактирует такой запрос в новом редакторе;
** *Тогда:* редактор не помечает эти конструкции как ошибку только из-за нестандартного SQL-синтаксиса и не меняет их при сохранении.

* *AC18 (Расширенное модальное окно редактора):*
** *Дано:* пользователь открывает {{«Текст запроса»}} в правиле загрузки данных для источника с ручным вводом запроса;
** *Когда:* открывается модальное окно редактора;
** *Тогда:* редактор сразу отображается в расширенном виде: доступна центральная зона {{CodeMirror}}, левая панель метаданных выбранного источника данных и верхняя панель вспомогательных вставок.

* *AC19 (Левая панель метаданных):*
** *Дано:* для выбранного источника данных доступны метаданные;
** *Когда:* пользователь открывает редактор {{«Текст запроса»}};
** *Тогда:* в левой панели отображаются схемы, таблицы/объекты, поля и типы полей при наличии, доступны поиск и разворачивание/сворачивание узлов, при этом успешное выполнение текущего SQL-запроса не требуется.

* *AC20 (Состояния левой панели):*
** *Дано:* метаданные выбранного источника загружаются, отсутствуют или временно недоступны;
** *Когда:* пользователь открывает редактор {{«Текст запроса»}};
** *Тогда:* левая панель показывает корректное состояние загрузки, пустую заглушку или сообщение об ошибке, а ручное редактирование текста запроса остаётся доступным.

* *AC21 (Верхняя панель вставок):*
** *Дано:* пользователь открыл редактор {{«Текст запроса»}};
** *Когда:* пользователь нажимает кнопку {{SUM}}, {{AVG}}, {{MIN}}, {{MAX}}, {{COUNT}}, {{DISTINCT}} или другую доступную кнопку верхней панели;
** *Тогда:* в редактор вставляется соответствующий шаблон кода в текущую позицию каретки без автоматического запуска проверки, предпросмотра или сохранения запроса.

* *AC22 (Вставка объектов из левой панели):*
** *Дано:* в левой панели отображаются таблицы/объекты и поля выбранного источника данных;
** *Когда:* пользователь перетаскивает объект из левой панели в область {{CodeMirror}};
** *Тогда:* имя таблицы/объекта или поля вставляется в SQL в текущую позицию каретки, а при необходимости используется безопасная форма идентификатора для текущего диалекта.

* *AC23 (Вставка при потере фокуса и мультикурсоре):*
** *Дано:* пользователь ранее устанавливал каретку в редакторе или использует мультикурсор;
** *Когда:* пользователь вставляет шаблон функции или объект из левой панели после переключения фокуса;
** *Тогда:* вставка выполняется в последнюю известную позицию каретки, при отсутствии такой позиции — в конец SQL-скрипта, а при активном мультикурсоре — по всем активным курсорам с учётом возможностей общего виджета {{CodeMirror}}.

* *AC24 (Адаптивность боковой панели):*
** *Дано:* пользователь открыл редактор на экране с ограниченной шириной или работает с длинным деревом метаданных;
** *Когда:* пользователь просматривает метаданные или сворачивает левую панель;
** *Тогда:* левая панель прокручивается внутри своей области, может быть свёрнута без выхода из редактора, а центральная зона {{CodeMirror}} остаётся доступной для редактирования.

* *AC25 (Отсутствие регресса дерева метаданных в составных наборах данных):*
** *Дано:* существующая реализация дерева метаданных переиспользуется или выносится в общий компонент/адаптер;
** *Когда:* пользователь работает со сценариями создания/редактирования {{составных}} наборов данных;
** *Тогда:* пользовательский сценарий {{составных}} наборов данных не меняется из-за внедрения редактора в {{«Правилах загрузки данных»}}.
