# Критерии приёмки: Ресёрч подсветки синтаксиса CodeMirror

## Общий подход к приёмке

Ресёрч принимается **в виде документа в Wiki** (AC4). Приёмка проводится в два этапа: сначала рецензия документа, затем — проверка PoC в живом окружении (Storybook или dev-стенд). Без работающего PoC ресёрч не считается завершённым.

## AC1 — Сравнительная аналитика пакетов

### Что проверять в документе

Таблица сравнения должна содержать **минимум следующие колонки** для каждого пакета:


| Критерий | Что смотреть |
| :-- | :-- |
| Пакет / источник | npm-имя, GitHub, версия, дата последнего коммита |
| Диалект | PostgreSQL / ClickHouse / MySQL / JS / TS / 1C |
| Тип интеграции | Lezer-грамматика, Language Package, плагин CM6 |
| Линтер | есть / нет / отключаемый |

| Лицензия | MIT / Apache / коммерческая |

### Обязательные диалекты для покрытия

- **PostgreSQL** — основной рабочий диалект
- **ClickHouse** — используется в продакшне, специфичный синтаксис (Array JOIN, SAMPLE, FINAL, движки таблиц)
- **MySQL** — используется рядом клиентов
- **StandardSQL** — fallback для неизвестных источников
- **JavaScript / TypeScript** — для вычисляемых полей
- **1C (платформа 1С:Предприятие)** — отдельный пункт (см. ниже)


### Специфика ClickHouse — обязательные проверочные конструкции

Документ должен подтвердить, что найденное решение корректно парсит (не подсвечивает как ошибку):

```sql
-- Движки таблиц
ENGINE = MergeTree()
ENGINE = ReplicatedMergeTree('/clickhouse/tables/{shard}/events', '{replica}')

-- Специфичные клаузы
SELECT * FROM table SAMPLE 0.1
SELECT * FROM table FINAL
SELECT * FROM t1 ARRAY JOIN arr AS a

-- Агрегирующие функции ClickHouse
SELECT uniq(user_id), quantile(0.95)(response_time) FROM logs

-- Лямбды и комбинаторы
SELECT arrayMap(x -> x * 2, arr) FROM t
SELECT sumIf(amount, status = 'paid') FROM orders

-- Интервалы и типы
SELECT toDate('2024-01-01') + INTERVAL 7 DAY
SELECT toStartOfMonth(event_date)
```


### Специфика PostgreSQL — обязательные проверочные конструкции

```sql
-- CTE и рекурсия
WITH RECURSIVE cte AS (
    SELECT id, parent_id FROM categories WHERE parent_id IS NULL
    UNION ALL
    SELECT c.id, c.parent_id FROM categories c JOIN cte ON c.parent_id = cte.id
)
SELECT * FROM cte;

-- Window functions
SELECT name, salary, RANK() OVER (PARTITION BY dept ORDER BY salary DESC) FROM employees;

-- FILTER clause (специфика PG)
SELECT count(*) FILTER (WHERE status = 'active') FROM users;

-- JSON операторы
SELECT data->>'name', data#>>'{address,city}' FROM records;

-- Dollar-quoting
CREATE FUNCTION test() RETURNS void AS $$
BEGIN END;
$$ LANGUAGE plpgsql;
```

## AC2 — Техническое решение для системных переменных

### Матрица проверочных паттернов

Документ обязан содержать явное подтверждение обработки каждого из следующих паттернов. Именно эти кейсы были проблемными по результатам демо:


| Паттерн | Пример | Ожидаемое поведение |
| :-- | :-- | :-- |
| Простая переменная (латиница) | `!env.REGION!` | Подсвечивается как системный токен, нет ошибки |
| Простая переменная (кириллица) | `!env.НазваниеРегиона!` | Подсвечивается как системный токен, нет ошибки |
| Диапазонные суффиксы | `!env.DATE.BEGIN!`, `!env.DATE.END!` | Подсвечиваются корректно |
| Fallback-конструкция (простая) | `{!env.REGION!; 2}` | Вся конструкция — валидна, `;` не ошибка |
| Fallback-конструкция (строка) | `{!env.REGION!; 'default'}` | Вся конструкция — валидна |
| Выражение + переменная в `{}` | `{toDate(!env.Date!); '2020-01-01'}` | Функция и переменная внутри `{}` — валидны |
| Переменная в теле запроса | `WHERE region = !env.REGION!` | Нет ошибки, токен подсвечен |
| Dollar-переменная | `$category$` | Нет ошибки |
| Переменная в строке с пробелами | `!env.LONG NAME!` | Уточнить: входит ли в scope или нет |

**Ключевой вопрос для AC2:** решение через `MatchDecorator` (оверлей поверх парсера) или через расширение Lezer-грамматики? Документ должен аргументировать выбор подхода — у каждого есть trade-offs:

- `MatchDecorator` — проще, но линтер всё равно «видит» исходный текст и может ругаться
- Расширение грамматики — надёжнее, но сложнее в поддержке

## AC3 — PoC: что должно работать в демо

PoC проверяется **вживую** в Storybook или dev-стенде. Чек-лист проверки:

### Базовая подсветка

- [ ] SQL-запрос с `SELECT`, `JOIN`, `WHERE`, `GROUP BY`, `HAVING`, `WINDOW` подсвечивается корректно
- [ ] Ключевые слова — один цвет, строковые литералы — другой, числа — третий
- [ ] Комментарии (`--` и `/* */`) подсвечиваются и не вызывают ошибок


### Системные переменные

- [ ] `!env.NAME!` подсвечивается отдельным цветом (системный токен)
- [ ] `!env.НазваниеРегиона!` — работает с кириллицей
- [ ] `{!env.REGION!; 2}` — вся конструкция валидна, `;` не подсвечена как ошибка
- [ ] `{toDate(!env.Date!); '2020-01-01'}` — работает
- [ ] `$category$` — не вызывает ошибки


### Линтер

- [ ] При корректном SQL — **нет** подчёркиваний ошибок
- [ ] При синтаксической ошибке (незакрытая скобка, неверный оператор) — ошибка **видна**
- [ ] Ошибки линтера НЕ появляются на системных переменных
- [ ] Переключение диалекта (PG → ClickHouse) не ломает работу редактора


### Производительность

- [ ] Вставить запрос на **500+ строк** — редактор не тормозит при вводе
- [ ] Вставить запрос на **1000+ строк** — парсинг завершается менее чем за 500ms


### PoC-сниппеты в документе

Минимальный набор сниппетов, которые должны быть в документе:

1. Базовая инициализация CM6 с выбранным SQL-пакетом
2. Конфигурация с кастомным токеном для системных переменных
3. Отключение / настройка линтера так, чтобы он не ругался на системные конструкции
4. Переключение диалекта через prop/параметр

## TL;DR

| Вопрос | Ответ |
|---|---|
| Есть ли готовый lezer-парсер для ClickHouse? | Нет. Только CM5-мод (устаревший). |
| Поддерживает ли `@codemirror/lang-sql` PostgreSQL / MySQL? | Да, встроено. ClickHouse — через `SQLDialect.define()`. |
| Нужен ли lezer-линтер для SQL? | **Нет.** Lezer — парсер для подсветки, не валидатор. Линтер даёт ложные ошибки. |
| Как обработать `{env.value}`, `$category$`? | `MatchDecorator` + фильтрация диагностик в кастомном linter-source. |
| Реальная валидация SQL | Через бэкенд (кнопка «Проверить запрос»). |

## 1. Контекст и постановка задачи

При внедрении CodeMirror 6 в виджет редактора выявлена проблема: стандартный lezer-парсер для SQL помечает как ошибки валидный SQL-синтаксис PostgreSQL (`::`-каст, `DATE '...'`, `$$...$$`, `ARRAY[...]`, `alias.*`) и системные переменные портала (`{env.value}`, `$category$`). Это классическая ситуация «whack-a-mole» — каждый новый запрос генерирует новые false positives.

**Корневая причина:** `@lezer/sql` — это **парсер для подсветки синтаксиса**, а не SQL-валидатор. Его грамматика намеренно упрощена и error-tolerant: парсер продолжает строить дерево даже при ошибках. Использовать его как линтер — архитектурно неверно.

---

## 2. Аналитика пакетов (AC1)

### 2.1. SQL-диалекты в CodeMirror 6

#### `@codemirror/lang-sql` (официальный)

```
npm install @codemirror/lang-sql
```

**Встроенные диалекты:**

| Диалект | Экспорт | Статус |
|---|---|---|
| Standard SQL | `StandardSQL` | ✅ |
| PostgreSQL | `PostgreSQL` | ✅ |
| MySQL | `MySQL` | ✅ |
| MariaDB | `MariaDB` | ✅ |
| SQLite | `SQLite` | ✅ |
| MS SQL | `MSSQL` | ✅ |
| Cassandra | `Cassandra` | ✅ |
| PL/SQL | `PLSQL` | ✅ |
| ClickHouse | ❌ нет | Нужен `SQLDialect.define()` |

**Ключевые возможности:**
- Подсветка синтаксиса на базе Lezer
- Автодополнение ключевых слов и схемы БД
- `SQLDialect.define(spec)` — API для создания кастомных диалектов
- `dollarQuotedStrings: true` — поддержка `$$...$$` (нужно для PostgreSQL)
- `specialVar` — символы начала специальных переменных

**Что lezer НЕ делает:**
- Не проверяет семантику (типы, существование таблиц)
- Не знает о PostgreSQL-специфике (`::`, `RETURNING`, JSON-операторы)
- Не умеет в ClickHouse-функции (`toStartOfMinute`, `arrayJoin`, `SAMPLE`)
- Не валидирует — `isError` на узлах почти никогда не выставляется

#### `@codemirror/lang-javascript` (официальный)

```
npm install @codemirror/lang-javascript
```

Для JS/TS — полноценная поддержка через `javascript({ typescript: true })`. Имеет интеграцию с ESLint через `esLint(new Linter())`. Никаких проблем с диалектами нет.

#### ClickHouse: сторонние опции

| Пакет | CM-версия | Статус |
|---|---|---|
| `clickhouse-codemirror` (AnalyticsGo) | **CM5** | ❌ Устаревший, не подходит |
| `@tidbcloud/codemirror-extension-sql-parser` | CM6 | ⚠️ TiDB-специфика, не ClickHouse |
| Кастомный `SQLDialect.define()` | CM6 | ✅ **Рекомендуется** |

**Вывод по ClickHouse:** готового CM6-пакета нет. Оптимальный путь — создать кастомный диалект через `SQLDialect.define()` с ключевыми словами ClickHouse. Это несложно и хорошо поддерживается API.

### 2.2. JS/TypeScript

Проблем нет — `@codemirror/lang-javascript` с `typescript: true` покрывает все нужды. ESLint-интеграция через `esLint` даёт настоящий линтинг.

## 3. Архитектурное решение: почему lezer-линтер для SQL не нужен (AC2 — часть)

### Что происходит сейчас

```
SQL-запрос → Lezer-парсер → AST (error-tolerant) → custom linter → Diagnostics
                                    ↑
                          Узлы типа "⚠ Error" на валидном PG-синтаксисе
```

Lezer намеренно строит AST даже при «ошибках» — это фича, не баг. Он вставляет `⚠`-узлы вместо нераспознанных конструкций, и если использовать эти узлы как источник диагностик — получаем false positives на любом нестандартном синтаксисе.

### Правильная архитектура

```
SQL-запрос → Lezer-парсер → AST → Подсветка синтаксиса ✅
                                 → НЕТ линтера          ✅

SQL-запрос → Кнопка «Проверить» → Бэкенд (настоящий PG/CH/MySQL) → Ошибки
```

Lezer делает **подсветку**. Бэкенд делает **валидацию**. Это правильное разделение ответственности.

---

## 4. Обработка кастомных переменных портала (AC2)

Системные токены, которые нужно поддержать:

| Токен | Пример | Regex |
|---|---|---|
| Env-переменная | `{env.value}` | `/\{[a-zA-Z_][a-zA-Z0-9_.]*\}/g` |
| Env с фильтром | `{env.value; true}` | `/\{[^}]+\}/g` |
| Dollar-категория | `$category$` | `/\$[a-zA-Z_][a-zA-Z0-9_]*\$/g` |

### Подход: MatchDecorator + фильтрация диагностик

Два независимых механизма:

1. **`MatchDecorator`** — визуально подсвечивает токены портала другим цветом (декоративный слой поверх AST, не меняет парсер)
2. **Фильтр диагностик** — если линтер всё же используется, фильтровать диагностики, чьи диапазоны перекрываются с кастомными токенами

### 5.2. MatchDecorator для системных переменных портала

// portal-variables.ts
import {
  Decoration,
  DecorationSet,
  EditorView,
  MatchDecorator,
  ViewPlugin,
  ViewUpdate,
} from '@codemirror/view'

// Regex для всех системных токенов портала
// {env.value}, {env.value; true}, $category$
const PORTAL_VAR_REGEX = /\{[^}]+\}|\$[a-zA-Z_][a-zA-Z0-9_]*\$/g

const portalVarDecoration = Decoration.mark({
  class: 'cm-portal-variable',
  // Маркируем как атомарный диапазон — курсор не "провалится" внутрь
  inclusive: false,
})

const portalVarMatcher = new MatchDecorator({
  regexp: PORTAL_VAR_REGEX,
  decoration: () => portalVarDecoration,
})

export const portalVariablesPlugin = ViewPlugin.fromClass(
  class {
    decorations: DecorationSet

    constructor(view: EditorView) {
      this.decorations = portalVarMatcher.createDeco(view)
    }

    update(update: ViewUpdate) {
      this.decorations = portalVarMatcher.updateDeco(update, this.decorations)
    }
  },
  {
    decorations: (instance) => instance.decorations,
  }
)

// CSS для темы (добавить в EditorView.theme или глобальные стили)

### 5.3. Бэкенд-линтер: реальная валидация SQL

```typescript
// backend-sql-linter.ts
import { Diagnostic } from '@codemirror/lint'
import { linter } from '@codemirror/lint'

interface BackendSqlError {
  message: string
  line?: number
  column?: number
  offset?: number
  length?: number
}

// Линтер, который вызывает бэкенд для валидации
// Используется только при явном action (кнопка "Проверить")
// НЕ вызывается автоматически при каждом изменении
export function createBackendSqlLinter(
  validateFn: (sql: string) => Promise<BackendSqlError[]>,
  debounceMs = 0 // 0 = только по требованию
) {
  return linter(
    async (view) => {
      const sql = view.state.doc.toString()
      if (!sql.trim()) return []

      try {
        const errors = await validateFn(sql)
        return errors.map((err): Diagnostic => {
          // Если бэкенд вернул позицию — используем её
          const from = err.offset ?? 0
          const to = err.offset != null ? from + (err.length ?? 1) : view.state.doc.length

          return {
            from,
            to,
            severity: 'error',
            message: err.message,
          }
        })
      } catch {
        return [] // сетевая ошибка — не блокируем редактор
      }
    },
    { delay: debounceMs }
  )
}

// Вариант: линтер запускается только вручную через setDiagnostics
// Это предпочтительный подход при наличии кнопки "Проверить"
import { setDiagnostics } from '@codemirror/lint'
import { EditorView } from '@codemirror/view'

export async function runBackendValidation(
  view: EditorView,
  validateFn: (sql: string) => Promise<BackendSqlError[]>
) {
  const sql = view.state.doc.toString()
  const errors = await validateFn(sql)

  const diagnostics: Diagnostic[] = errors.map((err) => ({
    from: err.offset ?? 0,
    to: err.offset != null ? err.offset + (err.length ?? 1) : sql.length,
    severity: 'error',
    message: err.message,
  }))

  // Устанавливаем диагностики вручную — они очистятся при следующем изменении
  view.dispatch(setDiagnostics(view.state, diagnostics))
}
```

### 5.4. React-виджет: полная сборка

```tsx
// SqlEditor.tsx
import React, { useCallback, useRef } from 'react'
import CodeMirror, { ReactCodeMirrorRef } from '@uiw/react-codemirror'
import { PostgreSQL, MySQL, SQLDialect, sql } from '@codemirror/lang-sql'
import { javascript } from '@codemirror/lang-javascript'
import { lintGutter } from '@codemirror/lint'
import { runBackendValidation } from './backend-sql-linter'
import { portalVariablesPlugin, portalVariablesTheme } from './portal-variables'
import { getSqlExtension, ClickHouseDialect } from './sql-extensions'

type EditorLanguage = 'postgresql' | 'clickhouse' | 'mysql' | 'javascript'

interface SqlEditorProps {
  value: string
  onChange: (value: string) => void
  language: EditorLanguage
  onValidate?: (sql: string) => Promise<Array<{ message: string; offset?: number; length?: number }>>
  readOnly?: boolean
}

export const SqlEditor: React.FC<SqlEditorProps> = ({
  value,
  onChange,
  language,
  onValidate,
  readOnly = false,
}) => {
  const editorRef = useRef<ReactCodeMirrorRef>(null)

  // Кнопка "Проверить запрос" — запускает бэкенд-валидацию
  const handleValidate = useCallback(async () => {
    const view = editorRef.current?.view
    if (!view || !onValidate) return

    await runBackendValidation(view, onValidate)
  }, [onValidate])

  // Расширения по языку
  const languageExtensions = () => {
    switch (language) {
      case 'javascript':
        return [javascript({ typescript: true })]
      case 'postgresql':
      case 'mysql':
      case 'clickhouse':
        return [
          getSqlExtension(language),
          // НЕТ lezer-линтера для SQL — только подсветка
          // Кастомные токены портала
          portalVariablesPlugin,
          portalVariablesTheme,
          // Gutter для диагностик от бэкенд-валидатора
          lintGutter(),
        ]
    }
  }

  return (
    <div className="sql-editor-wrapper">
      <CodeMirror
        ref={editorRef}
        value={value}
        onChange={onChange}
        extensions={languageExtensions()}
        readOnly={readOnly}
        basicSetup={{
          // lineNumbers, highlightActiveLine и т.д. — включены по умолчанию
          // lintKeymap: false, // отключить Ctrl+Shift+M если не нужен
        }}
      />
      {onValidate && (
        <button
          onClick={handleValidate}
          className="sql-editor-validate-btn"
        >
          Проверить запрос
        </button>
      )}
    </div>
  )
}
```

## 6. Сравнение подходов к валидации (финальная таблица)

| Подход | Ложные ошибки | Диалект | Кастом. токены | Сложность | Рекомендация |
|---|---|---|---|---|---|
| Lezer as linter (текущее) | 🔴 Много | Частичный | ❌ | Низкая | ❌ Не использовать |
| Lezer подсветка + бэкенд кнопка | ✅ Нет | ✅ Полный | ✅ MatchDecorator | Низкая | ✅ **Рекомендуется** |
| Lezer подсветка + авто-бэкенд lint | ✅ Нет | ✅ Полный | ✅ MatchDecorator | Средняя | ⚠️ Нагрузка на API |
| node-sql-parser (фронт) | 🟡 Меньше | Частичный | ❌ Сложно | Высокая | ⚠️ Не стоит |
| @pgsql/parser (WASM, только PG) | ✅ Нет | PG only | ❌ Сложно | Высокая | ⚠️ Только если нужен live lint |

## 7. Влияние на бандл и производительность (AC3 — часть)

| Пакет | Размер (gzip) | Заметки |
|---|---|---|
| `@codemirror/lang-sql` | ~18 KB | Включает все встроенные диалекты |
| `@codemirror/lang-javascript` | ~120 KB | Включает TypeScript-грамматику |
| `@codemirror/lint` | ~8 KB | Нужен для lintGutter и setDiagnostics |
| `@codemirror/view` + `state` | ~80 KB | Ядро, уже в бандле |
| Lezer-парсеры | ~20-40 KB | Lazy-загружаются при первом использовании |

**Рекомендации по производительности:**
- Использовать code splitting: `React.lazy` + динамический `import()` для языковых пакетов
- `@codemirror/lang-javascript` можно загружать лениво — он нужен не всегда
- `MatchDecorator` работает только во viewport (виртуализация) — не влияет на производительность при длинных файлах
- Автодополнение схемы БД: передавать только нужные таблицы, не всю схему сразу

## 8. Выводы и рекомендации (AC4)

### Итоговые решения

**SQL (PostgreSQL, MySQL):**
- `@codemirror/lang-sql` с соответствующим диалектом
- **Без** lezer-линтера
- `MatchDecorator` для `{env.value}`, `$category$`
- Валидация — через кнопку «Проверить запрос» → бэкенд → `setDiagnostics`

**ClickHouse:**
- `SQLDialect.define()` с ключевыми словами ClickHouse (снипет 5.1)
- Та же стратегия без линтера

**JS/TypeScript:**
- `@codemirror/lang-javascript({ typescript: true })`
- Опционально: ESLint-линтер через `esLint(new Linter())` — даёт реальные ошибки

### Следующие шаги

1. Откатить текущую lezer-лinting-логику для SQL
2. Убедиться что `sql({ dialect: PostgreSQL })` / `MySQL` настроены корректно
3. Добавить `portalVariablesPlugin` для подсветки системных токенов
4. Реализовать `runBackendValidation` + кнопку «Проверить»
5. Создать `ClickHouseDialect` через `SQLDialect.define()` (снипет выше)
6. Для JS — рассмотреть ESLint-интеграцию в отдельной задаче

### Что НЕ нужно делать

- Не писать паттерны для каждого PostgreSQL-конструкта в lezer-линтере
- Не форкать `@lezer/sql` для добавления грамматик
- Не подключать `@pgsql/parser` (WASM, 2+ MB) только ради подсветки
- Не использовать `node-sql-parser` на фронте — он не знает о системных переменных портала
