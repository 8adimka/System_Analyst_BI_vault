h3. Контекст и проблематика.

Необходимо реализовать в облачном портале сценарий работы с *произвольными наборами данных*, который активно используется в {{On-Premise}}-версии. Произвольный набор данных позволяет пользователю выбрать доступный источник данных, задать пользовательский SQL-запрос и сформировать структуру набора данных по результату этого запроса.

Для облачного портала этот сценарий должен быть встроен в текущий раздел {{«Наборы данных»}} и согласован с уже описанной логикой {{DirectQuery}} для создания источников через вкладку {{«Подключения»}}:
* аналитик в облаке не получает доступ к вкладке {{«Источники»}};
* источник данных для прямого запроса подготавливается системой через связанный {{datasources}}, созданный на основании подключения с включённым параметром {{DirectQuery}};
* произвольный набор данных в облаке должен использовать существующий механизм {{datasets}} → {{datasources}} и реализованную логику работы с Источниками;
* существующие простые и составные наборы данных продолжают работать по текущей логике.

Одновременно требуется привести раздел {{«Наборы данных»}} к новому целевому виду: внутри раздела должны быть две горизонтальные вкладки:
* {{«Произвольные наборы данных»}};
* {{«Простые и составные наборы данных»}}.

Такое разделение должно явно развести два пользовательских сценария:
* создание и редактирование произвольных наборов данных на основе Источников данных и пользовательского SQL;
* просмотр и сопровождение простых и составных наборов данных, созданных на основе Подключений и сценариев Правил загрузки данных.

{panel:title=Доступ к сценарию: «Подключения» → «Правила загрузки данных» → «Простые и составные наборы данных»|borderStyle=dashed|borderColor=#ccc|titleBGColor=#DDEBF7|bgColor=#F8FBFF}
может быть активирован в метаданных и для {{On-Premise}}-версии портала.
Аналогичный обновлённый интерфейс {{«Наборов данных»}} должен быть доступен и для {{On-Premise}}-версии портала.
Данные доработки интерфейса синхронизируются между {{On-Premise}} и Облачной версиями портала. 
{panel}

----
h3. Цель задачи.

*Требуется:*
# Внедрить в {{Modus BI Cloud}} подраздел {{«Произвольные наборы данных»}} в разделе {{«Наборы данных»}} по логике существующего {{On-Premise}}-сценария.
# Разделить раздел {{«Наборы данных»}} на две горизонтальные вкладки: {{«Произвольные наборы данных»}} и {{«Простые и составные наборы данных»}}.
# Обеспечить создание, проверку, сохранение, редактирование и удаление произвольных наборов данных на основе доступных пользователю источников данных.
# Обеспечить работу произвольных наборов данных с источниками, созданными через {{DirectQuery}}-подключения (без доступа к вкладке {{«Источники»}} для аналитика).
# Сохранить текущие сценарии простых и составных наборов данных без регресса.

_Пользовательская история:_
Как аналитик в {{Modus BI Cloud}}, я хочу создавать произвольные наборы данных на основе доступных источников, задавая пользовательский SQL-запрос, чтобы строить отчёты на основе предподготовленных данных внешней СУБД.

----
h3. 1. Описание текущего поведения.

h4. 1.1. Работа с наборами данных в облаке.

В облачном портале пользователь работает с данными через разделы {{«Подключения»}}, {{«Правила загрузки данных»}} и {{«Наборы данных»}}.

Текущий основной облачный сценарий:
# пользователь создаёт подключение к источнику данных;
# настраивает правила загрузки данных;
# загружает результат во внутреннее хранилище портала;
# использует загруженные данные для простых и составных наборов данных.

Сценарий произвольных наборов данных исторически связан с источниками данных {{datasources}} и прямыми SQL-запросами к ним. В облаке аналитик не получает общий доступ к вкладке {{«Источники»}}, и сценарий с произвольными наборами данных для него остаётся недоступен.

---
h4. 1.2. Разделение типов наборов данных.

Для целевого облачного интерфейса требуется явно разделить сценарии, которые не должны восприниматься пользователем как один и тот же рабочий процесс:
* произвольные наборы данных, где пользователь сам задаёт SQL-запрос к источнику;
* простые наборы данных, полученные по результатам созданного правила загрузки данных;
** составные наборы данных, создаваемые на базе уже существующих простых наборов данных.

Это разделение должно быть реализовано горизонтальными вкладками внутри одного раздела {{«Наборы данных»}}.

----
h3. 2. Описание целевого поведения.

h4. 2.1. Общая структура раздела {{«Наборы данных»}}.

В административной части портала слева сохраняется текущая боковая панель навигации без изменений. Активным пунктом при работе с наборами должен быть раздел {{«Наборы данных»}}.

В верхней части рабочей области отображается панель навигации ("хлебные крошки") в стандартном для нашей платформы стиле (и в соответствии с макетами):
{{Данные → Наборы данных → выбранный подраздел}}

Ниже отображаются горизонтальные вкладки:
| {{«Произвольные наборы данных»}} | {{«Простые и составные наборы данных»}} |

Порядок вкладок должен соответствовать макетам: первой отображается вкладка {{«Произвольные наборы данных»}}, второй — {{«Простые и составные наборы данных»}}.

Активной вкладкой при переходе в раздел {{«Наборы данных»}} определяется первый подраздел слева — {{«Произвольные наборы данных»}}. Старые прямые ссылки на существующий список простых и составных наборов данных должны продолжить открывать этот список, а не переводить пользователя в произвольные наборы данных.

---
h4. 2.2. Подраздел {{«Произвольные наборы данных»}}.

Подраздел предназначен для создания и настройки пользовательских наборов данных на основе доступных пользователю источников данных.

Целевой сценарий:
# Пользователь открывает {{Наборы данных → Произвольные наборы данных}}.
# Пользователь выбирает источник данных из списка доступных источников.
# Пользователь выбирает существующий произвольный набор данных (или создаёт новый).
# Пользователь задаёт техническое имя набора, отображаемое наименование и SQL-запрос.
# Пользователь нажимает {{«Проверить запрос»}}.
# Система проверяет запрос на выбранном источнике и формирует/обновляет структуру полей набора данных.
# Пользователь при необходимости редактирует alias, описание, настройки иерархии, уровень и RLS-настройки по текущей логике произвольных наборов данных.
# Пользователь сохраняет набор данных.
# Сохранённый произвольный набор данных становится доступен для построения отчётов и визуализаций по текущим правилам портала.

В подразделе должны отображаться элементы:
* выбор источника данных;
* выбор набора данных;
* поле {{«Имя источника данных»}};
* поле {{«Имя набора данных»}};
* поле {{«Отображаемое наименование»}};
* редактор SQL-запроса;
* кнопка {{«Проверить запрос»}};
* кнопка {{«Добавить набор»}};
* кнопка {{«Удалить»}};
* кнопка {{«Сохранить»}};
* блок {{«Настройки RLS»}};
* таблица полей набора данных.
* и другие элементы управления в соответсвии с аналогичным разделом в {{On-Premise}}-версии.

В таблице полей должны отображаться колонки:
|| Колонка || Назначение ||
| {{Имя поля}} | Техническое имя поля, полученное из результата SQL-запроса. |
| {{Алиас}} | Пользовательское или отображаемое наименование поля. |
| {{Тип}} | Внутренний тип поля, определённый платформой по результату запроса. |
| {{Описание}} | Описание поля, если оно задано пользователем или получено из метаданных. |
| {{Иерархия}} | Признак участия поля в иерархии для отображения поля по текущей логике набора данных. |
| {{Уровень}} | Уровень поля в иерархии, где настройка применима. |
| {{Действие}} | Служебное действие "Найти где используется". |

---
h4. 2.3. Подраздел {{«Простые и составные наборы данных»}}.

Подраздел предназначен для работы со списком простых и составных наборов данных.

В верхней части подраздела должны отображаться:
* поле поиска;
* кнопка {{«Составной набор»}}.

«Простой набор данных» создаётся на вкладке «Правила загрузки данных» как результат нового сохранённого правила загрузки, после указания всех необходимых параметров для формирования набора данных. 

Основная область подраздела — табличный список наборов данных с колонками:
|| Колонка || Назначение ||
| {{ID}} | Идентификатор набора данных. |
| {{Наименование}} | Отображаемое наименование набора данных. |
| {{Тип}} | Визуальный тип набора данных с иконкой: простой табличный/файловый набор или составной набор. |
| {{Автор}} | Пользователь, создавший набор данных. |
| {{Дата}} | Дата и время создания или последнего значимого изменения по текущей логике списка. |
| {{Операции}} | Доступные действия с записью - удаление (если действие разрешено пользователю). |

Поиск должен фильтровать список без перехода в подраздел произвольных наборов данных. Минимально поиск должен находить наборы по {{ID}}, {{Наименование}}, {{Автор}}, {{Дата}}.

Кнопка {{«Составной набор»}} должна открывать существующий сценарий создания Составного набора данных и не должен переводить пользователя на вкладку {{«Произвольные наборы данных»}}.

---
h4. 2.4. Поведение панели навигации {{«хлебные крошки»}}.

Панель навигации должна показывать текущее положение пользователя внутри раздела, но не должна выполнять лишних переходов, если пользователь уже находится на соответствующем уровне.

Правила для подраздела {{«Простые и составные наборы данных»}}:
* если пользователь находится на общем списке {{Данные → Наборы данных → Простые и составные наборы данных}}, нажатие на {{«Данные»}}, {{«Наборы данных»}} или {{«Простые и составные наборы данных»}} не меняет состояние экрана;
* если пользователь открыл конкретный простой или составной набор данных из списка, нажатие на уровень {{«Простые и составные наборы данных»}} или {{«Наборы данных»}} - возвращает пользователя к общему списку простых и составных наборов данных;

Правила для подраздела {{«Произвольные наборы данных»}}:
* подраздел не имеет отдельного общего списка произвольных наборов данных;
* пользователь всегда работает с выбранным набором через выпадающий список {{«Набор данных»}} или создаёт новый набор через {{«Добавить набор»}};
* если пользователь выбрал конкретный произвольный набор данных и нажал {{«Произвольные наборы данных»}} в хлебных крошках - состояние экрана не меняется;
* нажатие на {{«Данные»}} или {{«Наборы данных»}} в этом состоянии также не должно выполнять переход внутри того же раздела.

----
h3. 3. Требования к реализации.

h4. 3.1. Фронтенд-часть.

* В разделе {{«Наборы данных»}} необходимо реализовать горизонтальные вкладки по макетам.
* Переключение вкладок должно менять рабочую область и маршрут/состояние интерфейса так, чтобы активную вкладку можно было восстановить при обновлении страницы или прямом открытии ссылки.
* Боковая панель административной части должна остаться в текущем стиле: активный раздел выделяется светло-синим фоном и синей вертикальной полосой слева.
* Подраздел {{«Произвольные наборы данных»}} должен переиспользовать существующую форму работы с произвольным набором данных из {{On-Premise}}-портала в адаптации для облачного портала.
* Редактор SQL-запроса должен использовать текущий переиспользуемый редактор кода для {{«Наборов данных»}}. Отдельную локальную реализацию редактора создавать не нужно.
* Проверка запроса не должна запускаться автоматически при каждом вводе символа. Проверка выполняется только по явному действию {{«Проверить запрос»}}.
* При ошибке проверки SQL-запроса введённый текст, выбранный источник и несохранённые значения формы не должны теряться.
* После успешной проверки запроса таблица полей должна отображать актуальную структуру результата: имена полей, alias, типы и настройки, доступные по текущей логике произвольных наборов данных.
* При смене источника данных пользовательский SQL-запрос и структура полей должны обрабатываться по текущей логике формы: система не должна скрыто сохранять неконсистентный набор данных без явного действия пользователя.
* Кнопка {{«Добавить набор»}} переводит форму в состояние создания нового произвольного набора данных.
* Кнопка {{«Удалить»}} должна использовать существующий механизм удаления набора данных с проверкой прав и зависимостей.
* Кнопка {{«Сохранить»}} должна сохранять произвольный набор данных по текущему backend-контракту {{datasets}}.
* Вкладка {{«Источники»}} не должна становиться доступной аналитику.

---
h4. 3.2. Бэкенд-часть и API.

Точные команды API необходимо подтвердить по текущей реализации. Логически доработка затрагивает:
* {{datasources}} — получение списка источников, доступных пользователю для создания произвольного набора данных;
* {{datasets}} — чтение, создание, обновление, удаление произвольного набора данных, проверка SQL-запроса и получение структуры полей;
* {{reports}} / {{reportgroup}} — использование сохранённого произвольного набора данных в отчётах и визуализациях по текущей логике.

Требования:
* список источников в подразделе {{«Произвольные наборы данных»}} должен возвращать только источники, доступные пользователю по текущей модели прав и видимости;
* в {{Modus BI Cloud Start}} аналитик должен видеть собственные DirectQuery-источники и другие источники, если они доступны ему по действующей модели продукта;
* автоматически созданные источники из DirectQuery-подключений должны быть доступны для выбора в произвольном наборе данных, если связанное подключение активно и источник не скрыт/не удалён;
* перед обновлением существующего набора данных необходимо читать его текущее состояние через {{get}}/{{list}} или текущий эквивалент формы;
* при создании и обновлении набора данных {{object.id}}, {{command.id}} и поля данных не должны смешиваться;
* пользовательский SQL-запрос должен сохраняться в существующей структуре произвольного набора данных, без введения новой сущности хранения только для облака;
* проверка SQL-запроса должна выполняться на выбранном источнике данных и возвращать контролируемый результат: успешную структуру полей или понятную ошибку;
* ошибки SQL, ошибки прав на внешней СУБД и недоступность источника должны возвращаться контролируемо и не должны повреждать сохранённый набор данных;
* секреты источников и подключений не должны возвращаться на frontend и не должны попадать в текст ошибки.

---
h4. 3.3. Логика DirectQuery и источников данных.

Произвольный набор данных в облаке должен использовать существующую цепочку:
{{dataset → datasource → внешняя СУБД}}

Если источник данных был создан автоматически из подключения с включённым {{DirectQuery}}, подраздел {{«Произвольные наборы данных»}} использует его как обычный доступный {{datasources}}. Фронтенд не должен самостоятельно создавать или обновлять {{datasources}} из формы произвольного набора данных.

Требования:
* создание и синхронизация источника из подключения остаются ответственностью связанной доработки по {{DirectQuery}};
* текущая задача использует результат этой доработки: доступный пользователю {{datasources}};
* пользователь не должен редактировать параметры подключения или источник данных из формы произвольного набора данных;
* если DirectQuery-источник стал недоступен, удалён, скрыт или заблокирован, форма произвольного набора должна показать контролируемое состояние ошибки при открытии/проверке/сохранении;
* генерация SQL для отчётов на базе произвольного набора должна использовать текущий механизм {{datasets}}/{{datasources}}, без отдельной ветки SQL-генерации для облака.

---
h4. 3.4. Права и доступность.

* Доступ к созданию, редактированию и удалению произвольных наборов данных должен соответствовать текущей ролевой модели облачного портала.
* Пользователь без права на работу с наборами данных не должен получить доступ к созданию или изменению произвольного набора только из-за появления новой вкладки.
* Аналитик в облаке не должен получать доступ к разделу {{«Источники»}}.
* В списке источников для произвольного набора не должны отображаться источники других пользователей в {{Cloud Start}}, если они недоступны по текущей модели видимости.
* В выделенном контуре {{Cloud Teams}} / отдельном облачном инстансе видимость объектов должна соответствовать текущим правилам этого контура.
* Удаление произвольного набора данных должно учитывать существующие зависимости от отчётов и визуализаций по текущей модели продукта.

---
h4. 3.5. Обратная совместимость.

* Существующие простые и составные наборы данных должны открываться и использоваться без миграции.
* Существующие маршруты/ссылки на список простых и составных наборов данных должны продолжить работать.
* Существующие произвольные наборы данных, если они уже есть в контуре, должны открываться по текущей логике {{datasets}}/{{datasources}}.
* Существующие отчёты и визуализации на базе наборов данных не должны менять результат из-за добавления горизонтальных вкладок.
* Сценарий {{«Подключения»}} → {{«Правила загрузки данных»}} → простые/составные наборы данных не должен измениться.
* Источники, созданные вручную через {{«Источники»}} пользователями с соответствующими правами, не должны получать служебную связь с подключениями и не должны менять поведение из-за этой доработки.

----
h3. 4. Пограничные сценарии:

* *Нет доступных источников:* в подразделе {{«Произвольные наборы данных»}} пользователь видит контролируемое пустое состояние и не может сохранить набор без выбранного источника.
* *Источник недоступен:* если выбранный источник удалён, скрыт, отключён или недоступен по правам, проверка и сохранение возвращают понятную ошибку.
* *Пустой SQL-запрос:* система не должна выполнять пустой запрос; пользователь должен получить валидационное сообщение.
* *Некорректный SQL:* ошибка проверки отображается пользователю, текст запроса и состояние формы сохраняются.
* *Запрос вернул поля с одинаковыми именами:* система должна обработать ситуацию по текущей логике произвольных наборов данных: вернуть контролируемую ошибку или сформировать допустимые уникальные имена, если такой механизм уже предусмотрен.
* *Изменение структуры результата SQL:* после проверки изменённого запроса таблица полей должна обновиться, а пользовательские настройки полей должны сохраняться только там, где поле можно однозначно сопоставить.
* *Удаление поля из SQL:* поле, отсутствующее в новом результате запроса, не должно оставаться в сохранённой структуре набора без явного согласованного механизма совместимости.
* *Большой SQL-запрос:* редактор должен оставаться пригодным для работы, с внутренним скроллом и без поломки верстки.
* *Долгая проверка запроса:* интерфейс должен показывать состояние выполнения и не должен допускать повторных конфликтующих запусков проверки.
* *Смена вкладки с несохранёнными изменениями:* система должна использовать текущий паттерн предупреждения о несохранённых изменениях или не терять изменения скрыто.
* *Удаление набора с зависимостями:* система не должна молча ломать отчёты и визуализации; применяется текущий механизм проверки зависимостей и сообщения пользователю.
* *Недостаточно прав:* пользователь видит только разрешённые действия, а backend дополнительно проверяет права при создании, обновлении, удалении и проверке запроса.
* *Регрессия простых/составных наборов:* переключение на новую вкладочную структуру не должно менять создание, поиск, открытие, удаление и использование простых/составных наборов данных.

----
h3. 5. Не входит в рамки задачи:

* Реализация доступности вкладки {{«Источники»}} для аналитиков облачного портала.
* Реализация backend-механизма создания {{datasources}} из {{connection}} при включении {{DirectQuery}} — это покрывается связанной постановкой по DirectQuery.
* Изменение ролевой модели {{Modus BI Cloud}}.
* Реализация новой модели {{Workspace}} / совместной видимости объектов внутри одного общего облачного контура.
* Реализация нового SQL-движка, нового механизма DirectQuery или отдельной SQL-генерации специально для облачных произвольных наборов данных.
* Добавление обязательной поддержки {{MySQL}} и {{StarRocks}} в текущий сценарий, если их включение в DirectQuery не подтверждено готовностью отдельных задач.
* Переработка разделов {{«Подключения»}}, {{«Правила загрузки данных»}}, {{«Источники»}}.
* Полная переработка боковой панели административной части портала.

h3. 7. Предположения и проверки у разработки:

* Существующая логика произвольных наборов данных в {{On-Premise}} может быть переиспользована в облачном портале без изменения базовой модели {{datasets}}/{{datasources}}.
* В облаке будет доступен backend-механизм, который создаёт и синхронизирует {{datasources}} на основании подключения с включённым {{DirectQuery}}.
* Точные имена API-команд для проверки SQL-запроса, чтения структуры полей, создания, обновления и удаления произвольного набора данных необходимо подтвердить по текущей реализации.

h3. 8. Критерии приёмки (AC):

*AC.1 — Отображение вкладок раздела {{«Наборы данных»}}:*
* *Дано:* пользователь с доступом к разделу {{«Наборы данных»}} открывает раздел в облачном портале;
* *Когда:* отображается рабочая область раздела;
* *Тогда:* пользователь видит горизонтальные вкладки {{«Произвольные наборы данных»}} и {{«Простые и составные наборы данных»}}.

*AC.2 — Активный раздел в боковой панели:*
* *Дано:* пользователь находится на любой из вкладок раздела {{«Наборы данных»}};
* *Когда:* отображается левая боковая панель;
* *Тогда:* пункт {{«Наборы данных»}} выделен как активный, остальные пункты панели не меняют свой порядок и назначение.

*AC.3 — Хлебные крошки на вкладке простых и составных наборов:*
* *Дано:* пользователь находится на общем списке {{«Простые и составные наборы данных»}};
* *Когда:* пользователь нажимает {{«Данные»}}, {{«Наборы данных»}} или {{«Простые и составные наборы данных»}} в хлебных крошках;
* *Тогда:* экран остаётся на текущем общем списке без лишней перезагрузки сценария.

*AC.4 — Возврат к списку простых и составных наборов:*
* *Дано:* пользователь открыл конкретный простой или составной набор данных из списка;
* *Когда:* пользователь нажимает {{«Простые и составные наборы данных»}} в хлебных крошках;
* *Тогда:* система возвращает пользователя к общему списку простых и составных наборов данных.

*AC.5 — Хлебные крошки на вкладке произвольных наборов:*
* *Дано:* пользователь находится на вкладке {{«Произвольные наборы данных»}} и выбрал конкретный набор данных;
* *Когда:* пользователь нажимает {{«Произвольные наборы данных»}} в хлебных крошках;
* *Тогда:* состояние экрана не меняется, потому что в подразделе нет отдельного общего списка произвольных наборов.

*AC.6 — Список простых и составных наборов:*
* *Дано:* пользователь открывает вкладку {{«Простые и составные наборы данных»}};
* *Когда:* список загружен;
* *Тогда:* отображается таблица с колонками {{ID}}, {{Наименование}}, {{Тип}}, {{Автор}}, {{Дата}}, {{Операции}}.

*AC.7 — Поиск по простым и составным наборам:*
* *Дано:* на вкладке {{«Простые и составные наборы данных»}} есть несколько записей;
* *Когда:* пользователь вводит значение в поле поиска;
* *Тогда:* список фильтруется по доступным полям, минимум по {{ID}} и {{Наименование}}, без перехода на вкладку произвольных наборов.

*AC.8 — Открытие сценариев создания простого и составного набора:*
* *Дано:* пользователь находится на вкладке {{«Простые и составные наборы данных»}};
* *Когда:* пользователь нажимает {{«Простой набор»}} или {{«Составной набор»}};
* *Тогда:* открывается существующий сценарий создания выбранного типа набора данных, а произвольный набор данных не создаётся.

*AC.9 — Открытие формы произвольного набора данных:*
* *Дано:* пользователь открывает вкладку {{«Произвольные наборы данных»}};
* *Когда:* рабочая область загружена;
* *Тогда:* отображаются выбор источника, выбор набора, поля имени и отображаемого наименования, SQL-редактор, кнопки {{«Проверить запрос»}}, {{«Добавить набор»}}, {{«Удалить»}}, {{«Сохранить»}}, блок {{«Настройки RLS»}} и таблица полей.

*AC.10 — Доступность DirectQuery-источника:*
* *Дано:* у аналитика есть подключение поддерживаемого типа с включённым {{DirectQuery}}, и связанный источник успешно создан;
* *Когда:* аналитик открывает выбор источника в произвольном наборе данных;
* *Тогда:* в списке доступен источник, соответствующий этому подключению.

*AC.11 — Вкладка {{«Источники»}} не открывается аналитику:*
* *Дано:* аналитик работает с произвольным набором данных в облачном портале;
* *Когда:* пользователь выбирает DirectQuery-источник и создаёт набор данных;
* *Тогда:* пользователь не получает доступ к вкладке {{«Источники»}} и не редактирует источник напрямую.

*AC.12 — Ограничение видимости источников в Cloud Start:*
* *Дано:* в {{Cloud Start}} есть два аналитика, у каждого есть свои DirectQuery-подключения;
* *Когда:* первый аналитик открывает список источников в произвольном наборе данных;
* *Тогда:* он видит только источники, доступные ему по текущей модели видимости, и не видит источники второго аналитика.

*AC.13 — Проверка корректного SQL-запроса:*
* *Дано:* пользователь выбрал доступный источник и ввёл корректный SQL-запрос;
* *Когда:* пользователь нажимает {{«Проверить запрос»}};
* *Тогда:* система выполняет проверку на выбранном источнике и отображает актуальную структуру полей результата в таблице полей.

*AC.14 — Ошибка SQL-запроса:*
* *Дано:* пользователь ввёл SQL-запрос с синтаксической ошибкой или ссылкой на недоступный объект;
* *Когда:* пользователь нажимает {{«Проверить запрос»}};
* *Тогда:* система показывает контролируемую ошибку, не очищает SQL-редактор и не сбрасывает выбранный источник.

*AC.15 — Создание нового произвольного набора:*
* *Дано:* пользователь нажал {{«Добавить набор»}}, выбрал источник, заполнил обязательные поля и успешно проверил SQL-запрос;
* *Когда:* пользователь нажимает {{«Сохранить»}};
* *Тогда:* создаётся новый объект {{datasets}} произвольного типа со связью на выбранный {{datasources}}, SQL-запросом и структурой полей.

*AC.16 — Повторное открытие произвольного набора:*
* *Дано:* произвольный набор данных был создан и сохранён;
* *Когда:* пользователь повторно выбирает этот набор в подразделе {{«Произвольные наборы данных»}};
* *Тогда:* отображаются сохранённые источник, имя набора, отображаемое наименование, SQL-запрос, RLS-настройки и структура полей.

*AC.17 — Редактирование произвольного набора:*
* *Дано:* пользователь открыл существующий произвольный набор данных;
* *Когда:* пользователь изменяет SQL-запрос или параметры полей, выполняет проверку и сохраняет набор;
* *Тогда:* набор обновляется по текущему контракту {{datasets}}, а последующее открытие показывает актуальные сохранённые значения.

*AC.18 — Защита от потери изменений:*
* *Дано:* пользователь изменил произвольный набор данных и не сохранил изменения;
* *Когда:* пользователь переключает вкладку, выбирает другой набор или уходит со страницы;
* *Тогда:* система применяет текущий паттерн предупреждения о несохранённых изменениях или иной штатный механизм, исключающий скрытую потерю данных.

*AC.19 — Удаление произвольного набора:*
* *Дано:* пользователь открыл произвольный набор данных и имеет право на удаление;
* *Когда:* пользователь нажимает {{«Удалить»}} и подтверждает действие по текущему UX-паттерну;
* *Тогда:* система удаляет набор только при выполнении текущих проверок прав и зависимостей.

*AC.20 — Использование произвольного набора в отчёте:*
* *Дано:* произвольный набор данных создан и сохранён на доступном DirectQuery-источнике;
* *Когда:* пользователь строит отчёт или визуализацию на базе этого набора;
* *Тогда:* портал получает данные через существующий механизм {{datasets}}/{{datasources}}, без предварительной загрузки данных во внутренний {{ClickHouse}}.

*AC.21 — Недоступный источник при открытии набора:*
* *Дано:* произвольный набор данных ссылается на источник, который стал недоступен пользователю или был скрыт/удалён;
* *Когда:* пользователь открывает набор, проверяет SQL или пытается сохранить изменения;
* *Тогда:* система показывает контролируемое сообщение об ошибке и не повреждает сохранённые метаданные набора.

*AC.22 — Регрессия правил загрузки данных:*
* *Дано:* пользователь работает с {{«Подключения»}} и {{«Правилами загрузки данных»}};
* *Когда:* внедрены вкладки и произвольные наборы данных в разделе {{«Наборы данных»}};
* *Тогда:* создание, редактирование, проверка и выполнение правил загрузки данных продолжают работать по текущей логике.

*AC.23 — Регрессия существующих простых и составных наборов:*
* *Дано:* в системе есть простые и составные наборы данных, созданные до доработки;
* *Когда:* пользователь открывает вкладку {{«Простые и составные наборы данных»}}, ищет, открывает или удаляет доступный набор;
* *Тогда:* поведение этих наборов соответствует текущей логике продукта, а добавление вкладки произвольных наборов не меняет их данные и связи.

*AC.24 — Секреты не раскрываются:*
* *Дано:* произвольный набор данных использует источник, созданный из подключения с логином и паролем;
* *Когда:* пользователь открывает форму набора, проверяет SQL или получает ошибку подключения;
* *Тогда:* пароль, токены и полная строка подключения не отображаются в интерфейсе и не возвращаются в тексте ошибки.
