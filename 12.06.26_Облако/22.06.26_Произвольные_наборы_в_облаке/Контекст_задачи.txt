1) Часть задачи по реализации совместных рабочих пространств для Modus BI Cloud:

h3. Контекст и проблематика.

На текущий момент продукт *Modus BI* существует в двух вариантах поставки:

* *On-Premise:*
** заказчик разворачивает инфраструктуру в собственном контуре;
** заказчик самостоятельно управляет СУБД, ETL-процессами и хранением данных;
** решение ориентировано на Enterprise-сегмент с повышенными требованиями к безопасности, наличием собственной ИТ-команды и инфраструктуры.

* *Modus BI Cloud:*
** облачная SaaS-версия платформы;
** инфраструктура развёрнута на стороне Modus BI;
** заказчики регистрируются самостоятельно;
** данные хранятся и обрабатываются в инфраструктуре Modus BI;
** решение ориентировано на SMB, малый бизнес, физлиц и Freemium-сегмент.

Текущая архитектура *Modus BI Cloud* рассчитана на индивидуальное использование. Для масштабирования продукта на малый и средний бизнес необходимо реализовать _многопользовательские рабочие пространства_ (Workspaces), где пользователи одной команды/организации смогут совместно работать с подключениями, наборами данных, дашбордами и т.д.

Важно обеспечить:

* изоляцию рабочих пространств между собой;
* совместный доступ пользователей внутри одного рабочего пространства;
* экономическую целесообразность облачной модели;
* минимизацию ручных операций при создании новых клиентов.

----
h3. 1. Бизнес-цель.

К сентябрю необходимо перевыпустить облачный продукт, ориентированный на малый/средний бизнес и физлиц, у которых нет ресурсов и бюджета на поддержку {{On-Premise}} решения.

Ключевые бизнес-требования:

* пользователи должны иметь возможность работать не только индивидуально, но и командой;
* команда/организация должна иметь единое рабочее пространство с общими подключениями, наборами данных и дашбордами;
* продукт free-сегмента должен оставаться достаточно недорогим в эксплуатации и пригодным для массового подключения клиентов;
* для клиентов с повышенными требованиями будет подниматься отдельные инстанс всех необходимых составных частей портала и этот контур будет "открытым" - т.е. все пользователи будут видеть всех пользователей, такой контур и будет представлять из себя изолированное рабочее пространство (Workspace). Дополнительным вариантом для премиум сегмента будет {{On-Premise}} решение.

----
h4. 1.1. Термины и модель владения.

В рамках данной задачи основной сущностью изоляции является {{Workspace}}.

* Рабочее пространство (*Workspace*) — рабочее пространство команды, организации или индивидуального пользователя. Включает пользователей, источники данных, правила загрузки, наборы данных, дашборды и прочие BI-объекты. Отдельное Рабочее пространство (отдельный контур из инстансов поднятых специально под этого клиента) создаётся под орагнизацию или пользователя по запросу от менеджеров.
* *Tenant* — в рамках данной постановки является синонимом {{Workspace}}: единый контур изоляции данных и метаданных.
* Один {{Workspace}} может содержать нескольких пользователей с разными ролями (см. п. 3.1).
* Все пользовательские BI-объекты всегда принадлежат конкретному {{Workspace}} и не могут существовать вне его.

h3. 2. Архитектурный анализ и текущее актуальное решение решение.

h4. 2.1. Существующая маршрутизация к ClickHouse.

В текущей архитектуре *уже реализована* цепочка маршрутизации к ClickHouse:

{noformat}
Пользователь
  → Набор данных (Dataset)
      → Источник данных (Data Source)
          → host + port + database → ClickHouse
{noformat}

Источник данных (Data Source) — это запись в PostgreSQL, содержащая реквизиты подключения к конкретному инстансу ClickHouse. При открытии дашборда система не ищет инстанс ClickHouse по абстрактному идентификатору: она идёт по цепочке объектов, и источник уже содержит все необходимые реквизиты. Маршрутизация встроена в метаданные через саму структуру объектов.

Существующая цепочка «дашборд → набор → источник → ClickHouse» *остаётся рабочей* и не переписывается. Workspace надстраивается поверх неё:

1. Общая логика продукта

Modus BI Cloud фактически становится единым облачным продуктом, в котором BI-функции и ETL-функции не разделяются для пользователя на разные продукты. Пользователь работает в одном портале: подключает данные, загружает их во внутреннее облачное хранилище, при необходимости трансформирует, строит наборы данных и дашборды.

Для облака это должен быть единый продукт, где ETL-функциональность встроена внутрь Modus Cloud.

При этом продукт делится на две редакции:

Modus BI Cloud Start — общий облачный контур для бесплатного или промо-использования. Он нужен, чтобы пользователь мог зайти, попробовать продукт, загрузить данные, построить дашборд и понять ценность системы.

Modus BI Cloud Teams — выделенный облачный контур для конкретной организации. Он нужен тем клиентам, которые готовы платить за командную работу, изоляцию данных и отсутствие необходимости самостоятельно разворачивать и администрировать портал.

Ключевое архитектурное решение: в Teams не реализуется сложная модель множества Workspace внутри одного общего облака. Вместо этого отдельный инстанс портала считается одним Workspace клиента.

2. Modus BI Cloud Start

Cloud Start — это текущее облачное решение, выпускаемое практически «как есть». Для него не поднимается отдельный инстанс под каждого пользователя. Он работает в общем облачном контуре, но с жёсткой пользовательской изоляцией. В обсуждении отдельно уточнено, что Cloud Start не должен разворачиваться отдельным инстансом, а остаётся текущим классическим облаком.

В Start каждый пользователь работает только со своими объектами:

своими подключениями;
своими правилами загрузки данных;
своими простыми и составными наборами данных;
своими дашбордами и результатами работы.

То есть для пользователя система выглядит как персональная песочница. Он может познакомиться с продуктом, проверить сценарии загрузки и анализа данных, но не может полноценно организовать командную работу. Другие пользователи не видят его подключений, наборов данных и результатов, а он не видит их объектов. Исключение — администратор, который в текущей модели может видеть всё.

Главное ограничение Start не столько в функциональности BI как таковой, сколько в модели совместной работы: каждый пользователь изолирован, общей командной области нет. Поэтому Start подходит для знакомства с системой, демо, первичной проверки возможностей и самостоятельного тестирования, но не подходит для работы компании или отдела, где нужно совместно использовать подключения, наборы данных, правила загрузки и дашборды.

3. Modus BI Cloud Teams

Cloud Teams — это платная командная версия. Но команда здесь реализуется не через сложную систему рабочих пространств внутри одного общего облака, а через отдельный выделенный инстанс портала для клиента.

Проще говоря: если компания покупает Modus BI Cloud Teams, для неё поднимается собственный изолированный контур Modus BI на инфраструктуре Modus. Внутри этого контура работает свой портал, свой backend, свои базы данных и свой ETL-контур. Этот контур и есть рабочее пространство компании. В обсуждении это сформулировано так: каждый контур — это отдельный Workspace, а внутри него дополнительных Workspace уже нет.

В Teams пользователи одной организации работают в общем пространстве:

видят общие подключения;
видят общие правила загрузки;
видят общие наборы данных;
видят общие результаты и дашборды;
могут работать как единая команда.

Здесь снимается ограничение текущего Cloud Start, где пользователь видит только свои объекты. Для Teams прямо зафиксирована логика: пользователь должен видеть всё в рамках рабочего пространства, а ограничение «каждый видит только своё» необходимо снять.

При этом важно: изоляция обеспечивается не внутри приложения через сложные правила доступности между организациями, а на уровне отдельного инстанса. Одна организация физически и логически отделена от другой тем, что у неё отдельный контур. Поэтому данные клиентов не смешиваются в одном общем портале.

4. Как устроен выделенный контур Teams технически

По схемам и обсуждению, отдельный инстанс Cloud Teams состоит из нескольких основных частей.

1. Docker Modus / портал Modus BI.
Это основное приложение, с которым работают пользователи. Через него создаются подключения, настраиваются загрузки, формируются наборы данных, строятся дашборды, управляются пользователи и права.

2. PostgreSQL.
Используется как база метаданных портала. Там хранятся служебные данные: пользователи, настройки, подключения, описания объектов, конфигурации, структура портала и прочая метаинформация.

3. ClickHouse.
Используется как внутреннее аналитическое хранилище. В него загружаются данные, которые клиент решил перенести в облако для дальнейшего анализа, построения наборов данных и дашбордов.

4. ETL-агент и ETL-контур.
ETL отвечает за извлечение данных из источников, загрузку их в ClickHouse и дальнейшую обработку. В транскрипции отдельно указано, что под капотом ETL-агент выгружает данные из источников и загружает их в ClickHouse.

5. Сервер 1С:Предприятия / ETL-сценарии.
На схеме отдельно показан сервер 1С:Предприятия, внутри которого находится ETL-часть со сценариями обработки данных облака и DataLineage. В обсуждении также отмечено, что 1С не помещается в Docker-контейнерную модель так же просто, как остальные компоненты, поэтому выделяется отдельно.

6. Внешние источники клиента.
Источники данных остаются на стороне клиента: это могут быть базы данных, 1С, SQL-источники, Excel-файлы и другие системы. Modus BI Cloud либо загружает данные из этих источников во внутреннее хранилище, либо обращается к ним напрямую в сценарии DirectQuery.

Таким образом, контур Teams можно описать очень просто: это почти On-Premise-развёртывание Modus BI с ETL-функциями, но установленное и обслуживаемое не у клиента, а на инфраструктуре Modus. В обсуждении эта мысль также зафиксирована: это практически On-Premise, только железо и администрирование находятся на стороне Modus.

5. Как работают данные

В системе будет два основных способа работы с данными.

Первый способ — загрузка во внутреннее облачное хранилище. Пользователь подключает источник или загружает файл, ETL забирает данные, помещает их в ClickHouse, после чего на этих данных строятся наборы данных, витрины, трансформации и дашборды. Это основной облачный сценарий: данные попадают в управляемое хранилище Modus BI Cloud.

Второй способ — DirectQuery к внешнему источнику. Для облака обсуждается вариант не вводить отдельную вкладку «Источники», а работать через «Подключения». Для подключения к СУБД добавляется признак, что это подключение можно использовать для прямых запросов. Тогда набор данных может обращаться напрямую к внешней базе, минуя загрузку в облачное хранилище.

В Start пользователь сможет использовать для DirectQuery только свои подключения. В Teams такие подключения становятся частью общего рабочего пространства клиента, то есть команда может работать с общими источниками и наборами данных в рамках своего выделенного контура.

6. Модель пользователей и доступов

Для Cloud Start модель простая: каждый пользователь работает только со своими объектами. Это персональная среда, в которой нет командного совместного использования результатов.

Для Cloud Teams модель другая: все пользователи клиента находятся внутри одного выделенного контура, который считается одним Workspace. Внутри этого Workspace нет дополнительного разделения на организации, отделы или независимые рабочие пространства. Все пользователи работают с общими объектами, а изоляция от других клиентов достигается отдельным инстансом.

При этом в Teams могут сохраняться стандартные роли вроде администратора, аналитика и пользователя. Но эти роли нужны не для разделения разных организаций внутри одного общего облака, а для базового управления действиями пользователей внутри одного клиентского контура. Концептуально это ближе к On-Premise-модели, только без обязанности клиента самостоятельно устанавливать и сопровождать систему.

7. Почему выбран именно такой подход

Главная ценность этого решения — быстрый запуск с минимальными доработками.

Для бесплатного или промо-сегмента используется уже существующий Cloud Start. Он не требует разворачивать отдельную инфраструктуру под каждого пользователя и поэтому обходится дешевле. Ограничение «каждый видит только своё» позволяет не заниматься сложной командной моделью и не строить полноценные Workspace прямо сейчас.

Для платных клиентов используется Cloud Teams. Вместо разработки сложной multi-tenant-архитектуры с надёжной изоляцией организаций внутри одного портала под каждого клиента поднимается отдельный контур. Это дороже по инфраструктуре, но проще, надёжнее и быстрее с точки зрения разработки. В обсуждении прямо отмечено, что такой подход даёт overhead по железу, зато обеспечивает очень сильную изоляцию и позволяет быстро реализовать решение с минимальными доработками.

Итоговая логика такая:

неплатящие пользователи получают недорогую для нас персональную среду Cloud Start;

платящие клиенты получают отдельный изолированный контур Cloud Teams;

команда разработки не тратит ресурсы на сложную модель Workspace прямо сейчас;

бизнес получает понятную продуктовую линейку: попробовать бесплатно, а для командной работы перейти на платный выделенный контур.

8. Пробный период Teams

Для Cloud Teams предполагается пробный период, например 14 дней, после которого клиент либо переходит на платную подписку, либо контур отключается. В обсуждении отдельно отмечено, что такой пробный доступ лучше выдавать не полностью автоматически всем желающим, а через менеджеров или предварительную фильтрацию, потому что каждый Teams-контур требует отдельной инфраструктуры и создаёт нагрузку на железо.

Это важный продуктово-архитектурный момент: Cloud Start можно давать массово, а Cloud Teams нужно выдавать контролируемо, потому что Teams — это уже полноценный выделенный контур, а не просто учётная запись в общем облаке.

9. Короткое описание для внешнего или внутреннего документа

Modus BI Cloud будет развиваться в двух вариантах.

Modus BI Cloud Start — это базовая облачная версия для знакомства с продуктом. Пользователь получает доступ к уже существующему облачному порталу, может загрузить данные, настроить подключения, создать наборы данных и построить дашборды. Все объекты пользователя изолированы от других пользователей: он видит только свои подключения, правила загрузки, наборы данных и результаты. Командная работа и совместное использование объектов в этом варианте не предполагаются.

Modus BI Cloud Teams — это командная облачная версия для организаций. Для каждого клиента разворачивается отдельный изолированный инстанс Modus BI на инфраструктуре Modus. В состав инстанса входят портал Modus BI, собственная база метаданных PostgreSQL, собственное аналитическое хранилище ClickHouse, ETL-компоненты и необходимые сервисы обработки данных. Весь такой инстанс считается одним рабочим пространством клиента. Пользователи внутри него работают совместно и видят общие подключения, правила загрузки, наборы данных и дашборды.

Такой подход позволяет быстро выпустить облачную линейку без сложной переработки архитектуры. Бесплатные пользователи остаются в недорогом общем контуре Cloud Start, а платные клиенты получают выделенную и хорошо изолированную среду Cloud Teams. При этом клиенту не нужно разворачивать портал у себя, обслуживать серверы, устанавливать ClickHouse, PostgreSQL и ETL-агенты — вся инфраструктура находится на стороне Modus. Клиент отвечает только за свои источники данных и за настройку аналитических сценариев внутри предоставленного контура.



2) Ещё одна косвенно связанная задача по облаку - Внедрение редактора кода в «Правила загрузки данных».


h3. 1. Цель и контекст.

В нашем аналитическом портале проводится внедрение единого нового редактора кода на базе {{CodeMirror}}. Редактор уже используется на основном портале в {{«Вычисляемых полях»}} и {{«Наборах данных»}} и должен стать стандартным инструментом для работы с SQL/JS и прочим кодом во всех релевантных точках внедрения портала.

Настоящая задача рассматривает следующую точку внедрения — {{«Правила загрузки данных»}}.

{{Правила загрузки данных}} используются в сценариях подготовки данных в облачном портале (вкладки: {{«Подключения»}}, {{«Правила загрузки данных»}}, {{«Наборы данных»}}) - этот функционал был создан в первую очередь для {{Modus BI Cloud}}, где у пользователей нет доступа к ETL, но также может быть активирован в {{On-Premise}}-поставке через настройки метаданных портала. В этом сценарии пользователь настраивает подключение к источнику, задаёт запрос к источнику данных, загружает результат во внутреннее хранилище {{ClickHouse}} и далее использует загруженные данные для построения простых и составных наборов данных.

Сейчас в {{«Правилах загрузки данных»}} для источников, где требуется вручную задать текст запроса, используется старый простой редактор. Он не соответствует уже принятому UX редактора кода в портале: поле небольшое, отсутствуют возможности {{CodeMirror}}, нет единого поведения с редактором SQL в {{«Наборах данных»}}.

*Цель задачи* — заменить старый редактор поля {{«Текст запроса»}} в {{«Правилах загрузки данных»}} на переиспользуемый редактор {{CodeMirror}}, сохранив существующую бизнес-логику создания, редактирования, проверки и сохранения правила загрузки данных.

{panel:title=Ключевой принцип интеграции:|borderStyle=dashed|borderColor=#ccc|titleBGColor=#DDEBF7|bgColor=#F8FBFF}
* Новый редактор должен использовать уже реализованный переиспользуемый виджет {{CodeMirror}}, а не отдельную локальную реализацию для {{«Правил загрузки данных»}}.
* Внедрение редактора не должно менять смысл работы {{«Правил загрузки данных»}}: пользователь по-прежнему настраивает правило загрузки данных, задаёт запрос к источнику, сохраняет правило и запускает загрузку данных по текущим правилам модуля.
* Источником истины для сохранения и выполнения запроса остаётся текущая бизнес-логика {{«Правил загрузки данных»}} и соответствующие backend-объекты.
* Редактор должен подстраивать режим подсветки/диалект по типу источника данных, если тип можно определить из правила или связанного подключения.
* Для источников, где в текущем интерфейсе нет поля {{«Текст запроса»}} и пользователь не пишет запрос вручную, поведение не меняется.
{panel}

h3. 2. Описание текущего поведения.

h4. 2.1. Сценарий с подключениями к СУБД.

В сценарии загрузки данных через {{«Подключения»}} пользователь сначала создаёт подключение к источнику данных. Для подключений к СУБД оно содержит базовые настройки доступа: наименование, сервер, порт, базу данных, схему, пользователя, пароль и другие параметры конкретного драйвера.

Само подключение не определяет, какие данные нужно забрать из источника. Для этого пользователь переходит в {{«Правила загрузки данных»}} и задаёт запрос к источнику через действие {{«Текст запроса»}}.

Сейчас при открытии {{«Текст запроса»}} отображается старый редактор:
* он визуально мал и неудобен для написания длинных SQL-запросов;
* не поддерживает подсветку синтаксиса и другие продвинутые функции ногово редактора кода {{CodeMirror}}.

---
h4. 2.2. Сценарий с файловыми источниками.

Для файловых источников и табличных сервисов, где в текущем интерфейсе нет ручного ввода запроса, пользователь работает не с SQL-редактором, а с настройками загрузки файла/листа/диапазона/колонок.

Например, для Excel/Google Sheets пользователь выбирает файл или таблицу, лист, строку заголовка, диапазон строк и набор колонок для загрузки. Поле {{«Текст запроса»}} в этом сценарии сейчас не используется и изменения не плануруются в рамках этой задачи.

---
h4. 2.3. Разница между {{«Источниками»}} и {{«Подключениями»}}.

В стандартном сценарии {{«Источники»}} → {{«Наборы данных»}} запросы к внешнему источнику могут выполняться напрямую, в режиме обращения к исходной СУБД.

В сценарии {{«Подключения»}} → {{«Правила загрузки данных»}} данные сначала забираются из внешнего источника и перекладываются во внутреннее хранилище портала {{ClickHouse}}. Далее на основании загруженных данных создаются наборы данных, в том числе для построения составных наборов из разных источников.

{panel:title=Не входит в рамки текущей задачи:|borderStyle=dashed|borderColor=#ccc|titleBGColor=#FCE4D6|bgColor=#FFF8F2}
Текущая задача не решает UX-разграничение вкладок {{«Источники»}} и {{«Подключения»}}, не меняет модель загрузки данных во внутренний {{ClickHouse}} и не пересобирает сценарии создания наборов данных. 
В рамках задачи требуется только внедрение нового редактора кода в существующий сценарий {{«Правил загрузки данных»}}.
{panel}

----
h3. 3. Описание целевого поведения.

h4. 3.1. Общий пользовательский сценарий.

После доработки пользователь, имеющий доступ к {{«Правилам загрузки данных»}}, должен работать с текстом запроса через новый редактор {{CodeMirror}}.

Целевой сценарий:
# Пользователь открывает {{Modus BI Cloud}} (или {{On-Premise}}-портал, где активирован функционал {{«Правила загрузки данных»}}).
# Пользователь создаёт новое или открывает существующее правило загрузки данных для источника, где предусмотрен ручной ввод текста запроса.
# Пользователь нажимает кнопку {{«Текст запроса»}}.
# Вместо старого простого редактора открывается рабочая область с редактором {{CodeMirror}}.
# Редактор получает текущий текст запроса из правила загрузки данных.
# Пользователь редактирует запрос с обновленным UX редактора кода: подсветкой синтаксиса, нумерацией строк, автозакрытием скобок/кавычек, Undo/Redo, автодополнением и внутренним скроллом.
# При применении текста запроса и последующем сохранении правила используется текущая бизнес-логика формы и текущие backend-контракты.
# Существующие сценарии проверки, сохранения и запуска загрузки данных продолжают работать без регресса.

---
h4. 3.2. Область применения по типам источников.

Редактор {{CodeMirror}} должен использоваться во всех {{«Правилах загрузки данных»}}, где текущий интерфейс уже предполагает ручной ввод текста запроса.

В первую очередь это правила для подключений к СУБД и SQL-подобным источникам, включая, но не ограничиваясь:
* PostgreSQL;
* MS SQL Server;
* ClickHouse;
* Vertica;
* другие СУБД, для которых в текущей форме доступно действие {{«Текст запроса»}}.

Для источников {{1С}} редактор также должен открываться в этой же точке, так как текущий сценарий правила загрузки предполагает ручной ввод запроса. При этом:
* если в проекте уже есть или может быть без отдельной крупной доработки подключён режим подсветки синтаксиса {{1С}}, редактор должен использовать его;
* если режим подсветки синтаксиса {{1С}} недоступен, редактор должен использовать согласованный fallback-режим, не блокирующий работу пользователя с текстом запроса;
* полноценная адаптация языка запросов {{1С}} для редактора кода не является блокером текущей задачи и может быть вынесена в отдельную задачу, если потребуется.

Для Excel, Google Sheets и других источников, где пользователь не пишет текст запроса вручную и в текущем интерфейсе отсутствует действие {{«Текст запроса»}}, внедрение редактора не требуется.

---
h4. 3.3. Поведение в Cloud и On-Premise.

Доработка должна работать одинаково:
* в {{Modus BI Cloud}}, где сценарий {{«Подключения»}}/{{«Правила загрузки данных»}} является основным способом подготовки данных без ETL;
* в {{On-Premise}}-поставке, если соответствующий функционал активирован в настройках метаданных портала.

Доработка не должна зависеть от того, где развёрнуто внутреннее хранилище {{ClickHouse}}: в облачной инфраструктуре Modus BI или в контуре заказчика.

----
h3. 4. Функциональные требования к реализации.

h4. 4.1. Точка входа и замена старого редактора.

* В форме создания/редактирования {{«Правила загрузки данных»}} старый редактор, открываемый по действию {{«Текст запроса»}}, должен быть заменён на редактор {{CodeMirror}}.
* Пользовательский сценарий открытия редактора должен остаться привычным: пользователь по-прежнему открывает редактирование текста запроса из текущей формы правила загрузки данных по действию {{«Текст запроса»}}, новый редактор открывается в модальном окне укрупненного вида с возможностью управления размером (высотой) окна редактора.
* При открытии редактора в него должен подставляться актуальный текст запроса из текущего состояния правила.
* Если правило новое и текст запроса ещё не задан, редактор должен открываться пустым.
* Сохранение текста запроса должно выполняться по текущей логике формы: внедрение {{CodeMirror}} не должно вводить отдельную сущность черновика и не должно требовать нового backend-контракта только для хранения текста редактора.

---
h4. 4.2. Геометрия и UX окна редактора.

* Рабочая область редактора должна быть больше текущего поля и пригодна для чтения/редактирования длинных запросов.
* Внутри редактора должен работать вертикальный скролл для длинного SQL/текста запроса.
* Верстка формы правила загрузки данных не должна ломаться при длинном запросе, открытии/закрытии редактора, изменении размера окна браузера или редактора.
* Модуля редактор открывается в модальном окне, размер этого окна должен быть достаточным для полноценной работы с кодом.
* Если редактор встроен в форму, нижележащий контент должен корректно сдвигаться и не должен перекрываться редактором.
* Допускается переиспользовать паттерн управления высотой, реализованный для редактора SQL в {{«Наборах данных»}}: вертикальный ресайз, фиксированная ширина в рамках сетки формы и краткосрочное запоминание высоты при скрытии/повторном открытии в рамках текущей сессии.
* Управление размером (высотой) окна редактора:
** *Регулировка по высоте:* Область нового редактора {{CodeMirror}} должна поддерживать возможность ручного изменения размера по вертикали (resize) с помощью перетаскивания нижней границы окна.
** *Фиксированная ширина:* Ширина окна редактора остается строго фиксированной в рамках текущей сетки (grid) формы и не подлежит ручному изменению пользователем.
** *Адаптивность окружения:* При изменении высоты редактора остальное содержимое страницы должно корректно адаптироваться, без наложения элементов друг на друга.
** *Размер по умолчанию:* При первоначальном входе в интерфейс выбранного набора данных и первичном открытии редактора, его высота всегда должна быть равна системному значению по умолчанию (дефолтному размеру текущего поля).
** *Краткосрочная память состояния:* В рамках непрерывной работы с *текущим* правилом загрузки данных, если пользователь изменил высоту редактора, а затем скрыл его, при последующем отображении редактора в этой же сессии должна восстанавливаться измененная пользователем высота.
** *Отсутствие долговременной персистентности:* Измененная высота редактора *не должна* сохраняться в БД вместе с набором данных, а также не должна фиксироваться в пользовательских настройках между сессиями. При обновлении страницы (F5), выходе из текущего правила загрузки данных - допускается сбрасывание состояние высоты к дефолтным значениям.
* Изменение размера редактора не должно считаться изменением бизнес-данных правила и не должно само по себе активировать сохранение правила.

---
h4. 4.3. Базовый UX {{CodeMirror}}.

В {{«Правилах загрузки данных»}} должен быть сохранён базовый UX переиспользуемого виджета {{CodeMirror}}:
* нумерация строк;
* подсветка синтаксиса;
* подсветка и автозакрытие скобок/кавычек;
* поддержка Undo/Redo через стандартные горячие клавиши;
* поддержка мультикурсорного редактирования (если она уже включена в общем виджете);
* корректный вертикальный внутренний скролл;
* стабильная работа с длинными запросами;
* автодополнение при вводе текста и по явной горячей клавише, например {{Ctrl+Space}};
* отсутствие конфликтов горячих клавиш редактора с действиями основной формы.

Проверка или выполнение запроса не должны запускаться автоматически на каждый ввод символа. Любые текущие действия проверки/предпросмотра/сохранения должны оставаться явными действиями пользователя.

---
h4. 4.4. SQL-диалект и режим подсветки.

Редактор должен определять режим подсветки по типу источника данных, связанному с правилом загрузки.

Правила определения режима:
* если тип источника можно однозначно определить из текущего правила загрузки данных или связанного подключения, редактор должен использовать соответствующий диалект-режим {{CodeMirror}};
* если для типа источника в текущей реализации уже есть прямое сопоставление с диалектом {{CodeMirror}}, должно использоваться это сопоставление;
* если нативный диалект отсутствует, должен использоваться согласованный fallback-режим, например {{Basic SQL}}/{{StandardSQL}} или уже реализованный в проекте общий режим (необходимо учитывать наличие языка запросов {{1С}});
* если тип источника изменён пользователем в рамках формы, режим редактора должен обновиться без потери текущего текста запроса;
* если тип источника не определён, редактор должен оставаться в работоспособном fallback-режиме.

Для источников {{1С}}:
* при наличии доступного режима подсветки языка запросов {{1С}} нужно использовать его;
* при отсутствии такого режима нужно применять fallback без блокировки редактирования;
* отсутствие полноценной подсветки {{1С}} не должно приводить к невозможности открыть или сохранить текст запроса.

---
h4. 4.5. Автодополнение.

В обязательный состав подсказок должны входить:
* стандартные SQL-ключевые слова;
* встроенные SQL-функции, доступные в общем виджете редактора;
* служебные конструкции, уже поддержанные в общем редакторе, если они применимы к запросам правил загрузки данных.

Если в общем редакторе уже реализовано автодополнение с учётом метаданных и для текущего подключения доступны метаданные источника, допускается переиспользовать этот механизм в {{«Правилах загрузки данных»}}. При этом отсутствие метаданных источника не должно блокировать базовое автодополнение SQL-ключевых слов и функций.

В рамках текущей задачи не требуется отдельно реализовывать новую левую панель метаданных, дерево таблиц/полей или новый расширенный режим специально для {{«Правил загрузки данных»}}, если эти элементы ещё не доступны как переиспользуемая часть общего редактора.

---
h4. 4.6. Системный синтаксис и специальные конструкции.

Редактор не должен ломать уже допустимые в платформе системные конструкции, если они могут использоваться в тексте запроса правила загрузки данных.

Конфигурация редактора должна корректно обрабатывать как минимум те системные токены, которые уже поддержаны в общем редакторе SQL для {{«Наборов данных»}}, включая:
* {{\!env.NAME\!}};
* {{\!env.NAME.BEGIN\!}};
* {{\!env.NAME.END\!}};
* конструкции с fallback-логикой внутри фигурных скобок;
* иные серверные/системные переменные проекта, допустимые по текущим правилам платформы.

Такие конструкции не должны помечаться как синтаксическая ошибка только из-за того, что они не являются стандартным SQL.

---
h4. 4.7. Проверка, предпросмотр и выполнение запроса.

Уже существующие в форме {{«Правила загрузки данных»}} действия проверки запроса, предпросмотра результата, сохранения правила или запуска загрузки должны работать по старой логике без изменений.

Требования:
* проверка/предпросмотр должны использовать актуальный текст, который пользователь видит в редакторе;
* при успешной проверке/предпросмотре должна отработать текущая бизнес-логика модуля;
* при ошибке текст запроса не должен теряться;
** редактор не должен самопроизвольно закрываться при ошибке запроса;
** пользователь должен получить штатное сообщение об ошибке;
* если backend возвращает информацию о позиции ошибки и общий редактор умеет её визуально подсветить, это место должно быть акцентировано в редакторе;
* если точную позицию определить нельзя, достаточно показать понятное текстовое сообщение по текущим правилам интерфейса.

---
h4. 4.8. Сохранение правила загрузки данных и backend-контракты.

В рамках задачи требуется переиспользовать текущие команды чтения, создания, обновления и сохранения правил загрузки данных. Актуальные имена команд необходимо подтвердить по текущей реализации модуля, но логика должна соответствовать общему контракту платформы:
* перед обновлением существующего правила текущее состояние должно быть получено через {{get}}/{{list}} или уже существующий механизм чтения формы;
* при сохранении нового правила текст запроса должен попадать в текущий payload создания правила;
* при сохранении существующего правила текст запроса должен попадать в текущий payload обновления правила;
* {{object.id}}, {{command.id}} и поля внутри {{data}} не должны смешиваться;
* внедрение редактора не должно требовать изменения структуры хранения текста запроса, если текущая структура уже достаточна;
* пароли, токены и другие секреты связанного подключения не должны отображаться в редакторе и не должны попадать в текст запроса автоматически.

Если для определения диалекта редактора требуется тип источника, он должен браться из уже доступных данных правила/подключения. Если этих данных недостаточно, необходимо использовать существующий механизм получения связанного подключения или зафиксировать fallback-режим без дополнительного блокирующего запроса.

---
h4. 4.9. Обратная совместимость.

* Все ранее созданные правила загрузки данных должны открываться без миграции.
* Существующий текст запроса должен отображаться в новом редакторе без изменения содержимого.
* Сохранение правила после редактирования должно формировать совместимый payload и не должно ломать backend-обработку загрузки данных.
* Переносы строк, кавычки, регистр, комментарии и форматирование пользовательского запроса не должны изменяться автоматически при открытии/закрытии редактора.
* Старые правила для источников с неизвестным или устаревшим типом должны открываться в fallback-режиме редактора.
* Права доступа к {{«Правилам загрузки данных»}} не должны расширяться: новый редактор доступен только тем пользователям, которым уже разрешено создавать/редактировать соответствующие правила.

---
h4. 4.10. Границы реализации.

В рамки текущей задачи входит:
* замена старого редактора {{«Текст запроса»}} в {{«Правилах загрузки данных»}} на переиспользуемый {{CodeMirror}};
* поддержка базового UX {{CodeMirror}};
* определение режима подсветки/диалекта по типу источника данных;
* fallback-режим для источников без нативного диалекта;
* применение редактора для источников {{1С}} в рамках существующего сценария ручного ввода запроса;
* сохранение текущей бизнес-логики;
* работа в {{Modus BI Cloud}} и в {{On-Premise}} при активированном функционале правил загрузки данных;
* отсутствие регресса для существующих правил загрузки.

h3. 5. Пограничные сценарии.

* *Пустой запрос:* новое правило без заданного текста запроса должно открывать редактор без ошибки; обязательность заполнения запроса должна проверяться текущими правилами формы/сохранения.
* *Длинный запрос:* многострочный запрос должен редактироваться с внутренним скроллом без поломки формы.
* *Неизвестный тип источника:* редактор должен открыться в fallback-режиме.
* *Источник {{1С}} без отдельного режима подсветки:* пользователь должен иметь возможность открыть, изменить и сохранить текст запроса; отсутствие подсветки {{1С}} не должно блокировать сценарий.
* *Файловый источник без текста запроса:* интерфейс Excel/Google Sheets не должен получить лишний редактор.
* *Ошибка проверки запроса:* текст в редакторе должен сохраниться, пользователь должен увидеть сообщение об ошибке.
* *Потеря фокуса:* переключение между полями формы и редактором не должно сбрасывать каретку и текст запроса сверх поведения общего виджета.
* *Мультикурсор/Undo/Redo:* стандартные возможности общего виджета не должны отключаться в этой точке внедрения.
* *Смена источника/подключения:* если сценарий формы допускает смену источника для правила, текст запроса не должен теряться автоматически; режим подсветки должен пересчитаться по новому типу источника.
* *Старое правило:* правило, созданное до внедрения редактора, должно открываться с тем же текстом запроса.
* *Недостаточно прав:* пользователь без прав редактирования правил загрузки не должен получать возможность изменить текст запроса только из-за нового редактора.

h3. 7. Открытые вопросы и предположения.

* {{Правила загрузки данных}} на backend соответствуют объекту {{extraction_rules}}. Перед реализацией необходимо подтвердить актуальные команды чтения/сохранения в текущем модуле.
* Тип источника данных доступен из состояния правила загрузки или связанного подключения и может быть использован frontend-частью для выбора режима подсветки.
* Нужно подтвердить у разработки точные поля payload, в которых в {{extraction_rules}} хранится текст запроса и тип источника данных.
* Нужно подтвердить, есть ли в текущем стеке готовый режим подсветки для языка запросов {{1С}}. Если нет, текущая задача должна использовать fallback, а полноценную поддержку {{1С}} нужно оформить отдельной задачей.
* Нужно уточнить требуются ли действия проверки запроса/предпросмотра в форме {{«Правила загрузки данных»}}, так как их внедрение может повлечь изменения в бизнес-логике.

h3. 8. Критерии приёмки (AC):

* *AC1 (Замена редактора):*
** *Дано:* пользователь открывает создание или редактирование {{«Правила загрузки данных»}} для источника, где доступно действие {{«Текст запроса»}};
** *Когда:* пользователь открывает {{«Текст запроса»}};
** *Тогда:* вместо старого редактора отображается переиспользуемый редактор {{CodeMirror}}.

* *AC2 (Загрузка текущего значения):*
** *Дано:* в существующем правиле загрузки данных уже сохранён текст запроса;
** *Когда:* пользователь открывает редактор {{«Текст запроса»}};
** *Тогда:* в {{CodeMirror}} отображается актуальный сохранённый текст запроса без потери форматирования.

* *AC3 (Редактирование нового правила):*
** *Дано:* пользователь создаёт новое правило загрузки данных для источника с ручным вводом запроса;
** *Когда:* пользователь открывает {{«Текст запроса»}} и вводит запрос;
** *Тогда:* введённый текст сохраняется в текущем состоянии формы и передаётся в текущий payload создания правила при штатном сохранении.

* *AC4 (Базовый UX CodeMirror):*
** *Дано:* открыт редактор текста запроса в {{«Правилах загрузки данных»}};
** *Когда:* пользователь редактирует запрос;
** *Тогда:* работают нумерация строк, подсветка синтаксиса, автозакрытие скобок/кавычек, Undo/Redo, внутренний скролл и автодополнение по базовым SQL-ключевым словам/функциям.

* *AC5 (Размер и верстка):*
** *Дано:* пользователь открыл редактор {{«Текст запроса»}};
** *Когда:* запрос занимает много строк или пользователь меняет размер окна браузера;
** *Тогда:* редактор остаётся пригодным для работы, внутри него доступен скролл, элементы формы не перекрываются и не разъезжаются.

* *AC6 (Сохранение текущей бизнес-логики):*
** *Дано:* пользователь изменил текст запроса в редакторе;
** *Когда:* пользователь выполняет штатное сохранение правила загрузки данных;
** *Тогда:* правило сохраняется по текущему backend-контракту {{extraction_rules}}, а внедрение редактора не требует отдельного нового объекта или отдельного хранения черновика.

* *AC7 (Проверка/предпросмотр по актуальному тексту):*
** *Дано:* в форме правила загрузки данных доступно действие проверки или предпросмотра запроса;
** *Когда:* пользователь меняет текст в {{CodeMirror}} и запускает это действие;
** *Тогда:* проверка/предпросмотр выполняется по актуальному тексту из редактора.

* *AC8 (Ошибка запроса не приводит к потере текста):*
** *Дано:* пользователь ввёл некорректный запрос;
** *Когда:* проверка/предпросмотр возвращает ошибку;
** *Тогда:* пользователь видит штатное сообщение об ошибке, редактор не теряет введённый текст и не закрывается самопроизвольно.

* *AC9 (Определение диалекта по типу источника):*
** *Дано:* правило загрузки данных связано с источником PostgreSQL, MS SQL Server, ClickHouse, Vertica, MySQL или другим поддержанным типом СУБД;
** *Когда:* пользователь открывает {{«Текст запроса»}};
** *Тогда:* редактор использует соответствующий режим подсветки/диалект, если он доступен в текущем сопоставлении {{CodeMirror}}.

* *AC10 (Fallback для неизвестного диалекта):*
** *Дано:* тип источника не определён или для него отсутствует нативный режим {{CodeMirror}};
** *Когда:* пользователь открывает редактор;
** *Тогда:* редактор открывается в fallback-режиме и остаётся работоспособным для редактирования и сохранения текста запроса.

* *AC11 (Источник 1С):*
** *Дано:* правило загрузки данных относится к источнику {{1С}} и в текущем сценарии есть ручной текст запроса;
** *Когда:* пользователь открывает {{«Текст запроса»}};
** *Тогда:* открывается тот же редактор {{CodeMirror}}; при наличии режима {{1С}} используется он, при отсутствии — применяется fallback без блокировки редактирования и сохранения.

* *AC12 (Файловые источники не затронуты):*
** *Дано:* пользователь настраивает загрузку из Excel, Google Sheets или другого источника, где текущий интерфейс не содержит ручного текста запроса;
** *Когда:* пользователь работает с настройками файла, листа, диапазона и колонок;
** *Тогда:* новый SQL-редактор не появляется, текущий файловый сценарий работает без изменений.

* *AC13 (Облако и On-Premise):*
** *Дано:* функционал {{«Подключения»}} / {{«Правила загрузки данных»}} доступен в {{Modus BI Cloud}} или активирован в {{On-Premise}};
** *Когда:* пользователь открывает правило загрузки данных с ручным текстом запроса;
** *Тогда:* новый редактор работает одинаково в обоих вариантах поставки.

* *AC14 (Старые правила):*
** *Дано:* правило загрузки данных было создано до внедрения {{CodeMirror}};
** *Когда:* пользователь открывает и сохраняет это правило после доработки;
** *Тогда:* существующий текст запроса корректно отображается, редактируется и сохраняется без обязательной миграции и без изменения структуры данных.

* *AC15 (Права доступа):*
** *Дано:* пользователь не имеет прав на создание/редактирование правил загрузки данных;
** *Когда:* пользователь открывает соответствующий раздел или правило;
** *Тогда:* новый редактор не даёт ему дополнительных возможностей изменить текст запроса сверх уже разрешённых прав.

* *AC16 (Отсутствие регресса загрузки):*
** *Дано:* пользователь отредактировал и сохранил валидный текст запроса в правиле загрузки данных;
** *Когда:* пользователь запускает загрузку данных по правилу;
** *Тогда:* загрузка выполняется по текущей бизнес-логике модуля, данные попадают во внутреннее хранилище по прежнему сценарию, а внедрение редактора не меняет результат загрузки.

* *AC17 (Системный синтаксис):*
** *Дано:* в тексте запроса используются системные конструкции, уже допустимые платформой, например {{\!env.NAME\!}};
** *Когда:* пользователь открывает и редактирует такой запрос в новом редакторе;
** *Тогда:* редактор не помечает эти конструкции как ошибку только из-за нестандартного SQL-синтаксиса и не меняет их при сохранении.


В рамках реализации этого редактора также будет использоваться боковая панель с полями редактируемого набора данных:

Редактор должен открываться в полноэкранном рабочем пространстве, удобном для написания длинных SQL-запросов.
* Внутри редактора должна быть реализована трехзонная компоновка:
** *центральная основная зона* — редактор {{CodeMirror}};
** *левая вспомогательная зона* — панель метаданных выбранного источника данных;
** *правая вспомогательная зона* — панель шаблонов и служебных вставок.
* Основная площадь рабочего пространства должна быть отдана редактору.
* Левая и правая панели должны иметь адаптивно-фиксированную ширину, достаточную для чтения содержимого, с возможностью её настройки/регулировки (потянув за край боковой панели).
* Для длинного SQL-скрипта и длинного содержимого боковых панелей должны работать *внутренние скроллы* соответствующих областей.
* Для удобства работы на узких экранах боковые панели должны иметь возможность сворачиваться, но должны оставаться доступными без выхода из редактора.

h4. 2.3. Левая панель с метаданными источника данных.
* В левой части редактора должен отображаться список метаданных *выбранного источника данных*.
* Источником данных для этой панели должны быть метаданные текущего подключенного источника, а не результат последней успешной проверки SQL.
* В панели должны быть доступны как минимум:
** схемы;
** таблицы/объекты источника;
** поля таблиц;
** при наличии — типы полей.
* Панель должна поддерживать:
** поиск;
** разворачивание и сворачивание узлов;
** корректное состояние загрузки;
** корректную пустую заглушку или сообщение об ошибке, если метаданные временно недоступны.
* Метаданные должны быть доступны пользователю без обязательного предварительного успешного выполнения текущего SQL-запроса.

h4. 2.4. Переиспользование дерева метаданных из составного набора данных.

* По информации от коллег, функционал дерева метаданных уже частично реализован в рамках интерфейса {{составного набора данных}}.
* В рамках текущей задачи не требуется реализовывать дерево метаданных с нуля, если существующие наработки можно адаптировать для редактора редактора SQL в *произвольном* наборе данных.
* Перед разработкой необходимо провести техническую проверку существующей реализации: источник получения метаданных, структура дерева, поиск, разворачивание/сворачивание узлов, состояния загрузки/ошибки/пустого результата, механизм выбора/перетаскивания элементов и ограничения по типам источников.
* Пригодные части реализации должны быть переиспользованы или вынесены в переиспользуемый компонент/адаптер без изменения пользовательского сценария {{составных наборов данных}}.
* Если часть функциональности из составного набора данных не покрывает требования текущего редактора, недостающие возможности дорабатываются точечно в рамках требований п. 2.3, 2.6 и 2.8, без дублирования уже существующей логики.
* Переиспользование существующих наработок не должно менять границы задачи: доработка внедряется для *произвольных* наборов данных, а сценарии создания/редактирования {{составных}} наборов данных в рамках этой истории не изменяются.

h4. 2.5. Правая панель вспомогательных вставок.
* В правой части редактора должна отображаться вспомогательная панель служебных вставок.
* Минимально обязательный состав правой панели:
** шаблоны переменных окружения;
** шаблоны серверных переменных;
** список распространённых агрегирующих функций: SUM, AVG, MIN, MAX, COUNT, DISTINCT и т.д.
* Для правой панели допускается использование структуры секций, чтобы пользователь мог сворачивать и разворачивать группы вставок.

h4. 2.6. Вставка объектов из боковых панелей в редактор.
* Объекты из боковых панелей должны быть доступны для вставки в SQL в расширенном режиме редактора кода.
* Базовый способ вставки — {{Drag-and-Drop}} в область редактора.
* Дополнительно допускается поддержка альтернативного действия вставки (например, двойной клик), если это не усложняет UX.
* Из левой панели в редактор должны вставляться:
** имена таблиц/объектов источника;
** имена полей.
* Из правой панели в редактор должны вставляться:
** шаблоны переменных окружения;
** шаблоны серверных переменных;
** иные поддерживаемые системные и общеупотребимые конструкции.
* Вставка должна происходить *в текущую позицию каретки*:
** Если редактор временно потерял фокус, должна использоваться последняя известная позиция каретки.
** Если пользователь ранее не фокусировался в редактор, вставка допускается в конец SQL-скрипта.
** Если в редакторе включен мультикурсор, вставка должна выполняться по всем активным курсорам.
** Если для корректной SQL-вставки требуется экранирование/кавычки в соответствии с диалектом текущего источника, вставка должна использовать синтаксически безопасную форму идентификатора.

h3. Контекст и цель.

В рамках расширения возможностей Портала и ETL-контура необходимо реализовать поддержку источников данных, совместимых с протоколом {*}MySQL{*}, на уровне бэкенда.

На текущем этапе требуется реализовать {*}техническую основу интеграции{*}: подключение к MySQL-источнику, чтение схемы БД, корректное сопоставление типов данных, генерацию SQL-запросов в диалекте MySQL, а также поддержку базовых сценариев работы с данными.

*RLS, Формы ввода данных (ФВД), импорт из Excel и UI-ограничения карточки источника* в рамках данной истории *не реализуются*.

----

h4. 1. Требования.

h4. 1.1. Подключение MySQL как поддерживаемого источника на бэкенде.

* Бэкенд должен поддерживать тип источника {*}MySQL{*} как полноценный источник данных.
* Должна быть обеспечена возможность подключения к MySQL-серверу по стандартным параметрам соединения.
* Проверка подключения должна корректно отрабатывать для MySQL:
  ** при успешном соединении возвращается статус успешного подключения,
  ** при ошибке — возвращается текст ошибки, полученный от БД или драйвера.

h4. 1.2. Чтение схемы и метаданных MySQL-источника.

* Бэкенд должен получать и отдавать информацию о таблицах и полях MySQL-источника.
* Чтение схемы должно выполняться через {*}information_schema{*} MySQL.
* Должно быть обеспечено корректное отображение структуры БД для последующего использования в мастере набора данных и в редакторе SQL.

h4. 1.3. Поддержка типов данных MySQL.

* Необходимо обеспечить корректное сопоставление типов MySQL с внутренними типами платформы.
* В рамках маппинга должны корректно обрабатываться, в том числе:
  ** {{{}+TINYINT+{}}},
  ** {{{}+DATETIME+{}}},
  ** {{{}+VARCHAR+{}}},
  ** {{{}+BLOB+{}}},
  ** и другие распространённые типы MySQL.
* Поведение сопоставления должно быть аналогично уже реализованному маппингу для PostgreSQL.

h4. 1.4. Поддержка SQL-диалекта MySQL.

* Модуль генерации SQL должен быть расширен поддержкой MySQL-диалекта.
* Должна быть обеспечена корректная генерация запросов для:
  ** фильтрации,
  ** агрегации,
  ** вычисляемых полей,
  ** предпросмотра данных,
  ** работы с датами.
* Особое внимание должно быть уделено преобразованию даты и времени: UI-выбор аналитика должен транслироваться в синтаксически корректный SQL-запрос для MySQL.
* Набор вариантов и форматов должен соответствовать текущей реализации для PostgreSQL по смыслу и поведению.

h4. 1.5. Поддержка вычисляемых полей и фильтрации на стороне MySQL.

* Вычисляемые поля, созданные в наборе данных на базе MySQL-источника, должны корректно вычисляться.
* Фильтрация по полям MySQL-источника должна корректно транслироваться в SQL и возвращать ожидаемый результат.

h4. 1.6. Системные ограничения на уровне бэкенда.

* Бэкенд должен быть готов к тому, что часть возможностей платформы для MySQL на этом этапе не используется.
* Для функций, которые пока не поддерживаются этим источником, API должно возвращать корректную ошибку при попытке вызова.

h4. 1.7. Драйвер подключения.

* Рекомендуется подключение через нативный Go-драйвер (например, {{{}go-sql-driver/mysql{}}}) для максимальной производительности в ETL-слое.
* Если интеграция нативного драйвера потребует неоправданно высоких трудозатрат, допускается переиспользование существующего ODBC-моста.

----

h3. 2. Нефункциональные требования.

* Для MySQL-диалекта необходимо разработать тест-план, покрывающий:
  ** корректность генерации SQL-запросов,
  ** корректность маппинга типов данных,
  ** корректность преобразования дат,
  ** корректность работы соединения в сценариях успеха и ошибок.
* Тестирование должно проводиться на реальной MySQL-базе данных.

----

h3. 3. Критерии приёмки (AC):

*AC-1 — Подключение:*
Бэкенд поддерживает создание MySQL-источника и проверку подключения. При успешном соединении возвращается статус «Успешно», при ошибке — текст ошибки от БД/драйвера.

*AC-2 — Чтение схемы:*
Бэкенд корректно получает список таблиц и полей MySQL-источника через {{information_schema}} и передаёт эти данные для дальнейшего использования платформой.

*AC-3 — Типы данных:*
Типы MySQL (например, {{{}+TINYINT+{}}}, {{{}+DATETIME+{}}}, {{{}+VARCHAR+{}}}, {{+BLOB+}}) корректно сопоставляются с внутренними типами платформы.

*AC-4 — SQL и предпросмотр:*
Для MySQL-источника корректно генерируются SQL-запросы для предпросмотра, фильтрации, агрегации и вычисляемых полей, без синтаксических ошибок.

*AC-5 — Преобразование дат:*
Преобразования дат, выбранные в UI набора данных, транслируются в синтаксически корректный SQL для MySQL и возвращают ожидаемый результат.

*AC-6 — Вычисляемые поля:*
Вычисляемые поля на базе MySQL-источника корректно рассчитываются на стороне БД и доступны в ответах платформы.

*AC-7 — Тестирование:*
Для MySQL-диалекта подготовлен и выполнен тест-план на реальной MySQL-базе, покрывающий основные сценарии работы.

h3. Контекст и цель.

В рамках расширения возможностей аналитического портала необходимо реализовать поддержку {*}StarRocks{*} как отдельного типа подключения к источнику данных.

StarRocks использует {*}MySQL wire-протокол{*}, поэтому на транспортном уровне допускается общий с MySQL драйвер. При этом StarRocks не является MySQL-источником: это OLAP-СУБД с колоночным хранением, MPP-архитектурой, собственной SQL-семантикой, типами данных, DDL и особенностями аналитических запросов. Использование StarRocks через тип {{mysql}} приводит к некорректной генерации SQL, ошибкам выполнения запросов, неверному маппингу типов и риску искажения данных.

StarRocks должен быть зарегистрирован как отдельный тип подключения {{StarRocks}}, наравне с PostgreSQL, ClickHouse, MySQL и другими поддерживаемыми источниками:

Поддержка StarRocks реализуется как отдельная обёртка над драйвером: отдельная регистрация типа, отдельная логика чтения метаданных, отдельный маппинг типов и отдельный построитель SQL. Наследование MySQL-диалекта, MySQL-DDL и MySQL-маппинга для StarRocks недопустимо.

Минимальная поддерживаемая версия StarRocks для данной доработки — {*}4.xx{*}. Приёмку проводить с учётом окружений заказчика: Dev — StarRocks {{4.01}}, Prod — StarRocks {{4.04}}.

h3. 1. Входит в рамки задачи.

* Добавить StarRocks как отдельный тип источника данных на уровне бэкенда, фронтенда и метаданных.
* Обеспечить подключение к StarRocks через MySQL wire-протокол с портом по умолчанию {{9030}}.
* Реализовать отдельную SQL-семантику {{SQL/StarRocks}} для построения запросов платформы.
* Реализовать чтение схемы, таблиц, представлений и полей StarRocks-источника.
* Реализовать StarRocks-специфичный маппинг типов данных во внутренние типы платформы.
* Обеспечить создание наборов данных на базе StarRocks-источника.
* Обеспечить работу предпросмотра, пользовательского SQL-запроса, фильтрации, сортировки, агрегаций, {{GROUP BY}}, {{HAVING}}, вычисляемых полей и производных полей даты.
* Подключить StarRocks к механизму возможностей СУБД: бэкенд является источником истины о поддерживаемых функциях для каждого типа источника. Фронтенд отображает и активирует элементы карточки источника на основании данных, получаемых от бэкенда, без собственной StarRocks-специфичной логики.
* Провести регрессионную проверку MySQL и других существующих источников данных.

h3. 2. Требования к реализации.

---
h4. 2.1. Фронтенд.

* В разделе {*}«Источники» → «Добавить источник»{*} добавить тип подключения {*}StarRocks{*}.
* StarRocks отображается в группе основных SQL/OLAP-источников рядом с PostgreSQL, ClickHouse, MySQL, MS SQL Server и другими в соответствии с принятой сортировкой.
* При выборе StarRocks отображается стандартная карточка SQL-источника с полями: тип подключения, имя источника, отображаемое название, хост БД, порт, имя БД, схема БД, логин, пароль и другие обязательные поля текущей формы.
* Порт по умолчанию для нового StarRocks-источника — {{9030}}, если пользователь не указал иное.
* Кнопка проверки подключения работает для StarRocks и возвращает успешный или ошибочный статус в текущем UX-паттерне.
* Фронтенд отображает стандартную карточку SQL-источника по общей схеме, включая все элементы, которые присутствуют в форме для SQL/OLAP-источников (ФВД, отчётные формы, RLS и аналогичные). Фронтенд не содержит отдельной StarRocks-специфичной логики скрытия или блокировки этих элементов.
* Доступность функций (ФВД, отчётные формы, RLS, MDX, коррекция данных, импорт Excel и другие) для конкретного источника определяется бэкендом. Фронтенд получает эти данные от бэкенда через существующий механизм и отображает элементы в соответствующем состоянии (доступно/недоступно) на основании полученного ответа.
* При попытке пользователя подключить функцию, которая не поддерживается для StarRocks, фронтенд отправляет стандартный запрос к бэкенду. Бэкенд возвращает контролируемую функциональную ошибку о неподдерживаемой операции. Фронтенд отображает эту ошибку в существующем UX-паттерне.
* Если в текущей реализации список типов подключений или порт по умолчанию жёстко зашиты на клиенте — правка фронтенда ограничивается техническим добавлением StarRocks в существующие справочники (тип {{starrocks}}, порт {{9030}}) без введения отдельной логики доступности функций.
* В мастере создания набора данных StarRocks-источник доступен как источник аналитических данных.
* В конструкторе ФВД StarRocks не отображается как доступное хранилище.
* В мастере импорта Excel StarRocks не отображается как целевой источник.
* В интерфейсе набора данных корректно отображаются таблицы, поля, типы и ошибки чтения схемы StarRocks.
* Для наборов данных на StarRocks доступны: пользовательский SQL-запрос, предпросмотр, вычисляемые поля, фильтрация и инструмент извлечения частей даты в рамках поддерживаемых возможностей платформы.

---
h4. 2.2. Бэкенд и API.

* Зарегистрировать StarRocks как отдельный тип источника с техническим типом {{starrocks}}.
* Общий транспортный драйвер допустим, но SQL-диалект и маппинг должны выбираться строго по типу {{starrocks}}, без наследования MySQL-логики.
* Для StarRocks реализовать отдельные компоненты: {{drivers/starrocks}}, {{modeltranslator/starrocks}}, {{planbuilder/starrocks}} или их актуальные эквиваленты в структуре кодовой базы.
* Затронутые backend-объекты и сценарии:
** {{connection}} — проверка подключения, включая сценарий нового подключения с {{id = 0}}, если он используется текущим API;
** {{datasources}} — создание, чтение, обновление, список источников с типом {{starrocks}};
** {{datasets}} — создание и использование наборов данных на базе StarRocks-источника;
** {{reports}} / {{reportgroup}} — получение данных для отчётов и визуализаций на StarRocks-наборах;
** {{extraction_rules}} — в сценариях, где платформа использует правила извлечения для чтения StarRocks как внешнего источника.
* Перед обновлением существующего источника бэкенд читает текущее состояние через {{get}}/{{list}} и не затирает параметры, которые пользователь не редактировал.
* Секреты подключения не возвращаются в ответах API и не попадают в тексты ошибок. Пароль изменяется только при явной передаче нового значения; если пароль не менялся — существующее значение сохраняется.
* Ошибки подключения (неверный хост, порт, имя БД, логин, пароль, недоступность кластера, недостаточные права) возвращаются контролируемо.
* Для неподдерживаемых операций StarRocks бэкенд возвращает контролируемую функциональную ошибку, а не пытается выполнить операцию через MySQL-ветку.

---
h4. 2.3. Чтение схемы и метаданных.

* Бэкенд читает список доступных баз/схем, таблиц, представлений и полей StarRocks через {{information_schema}} или поддерживаемый StarRocks-механизм.
* Необходимо различать:
** исходные имена типов из метаданных StarRocks ({{information_schema}});
** имена типов, которые возвращает транспортный драйвер при чтении результата {{SELECT}}.
Логика маппинга не должна полагаться только на один из этих путей.
* Для определения identity-признака нельзя использовать только {{information_schema.COLUMNS.EXTRA}}: в StarRocks он не содержит ожидаемого значения. При необходимости использовать StarRocks-совместимый способ, например {{SHOW CREATE TABLE}}.
* Для каждого поля возвращаются: имя, исходный тип StarRocks, внутренний тип платформы, признак {{nullable}}, порядок полей.
* Пустая схема, отсутствие таблиц, ошибки прав на отдельные объекты не должны приводить к аварийному завершению backend-сервиса.

h4. 2.4. Маппинг типов данных.

||Группа типов||Типы StarRocks||Требование||

|Числовые|{{TINYINT}}, {{SMALLINT}}, {{INT}}, {{BIGINT}}, {{LARGEINT}}, {{DECIMAL}}, {{NUMERIC}}, {{FLOAT}}, {{DOUBLE}}|Обрабатывать без неконтролируемой потери точности. {{LARGEINT}} не приводить к {{float64}}; если числовое представление невозможно — возвращать строкой.|

h4. 2.5. SQL-семантика и генерация запросов.

* Для StarRocks использовать отдельный диалект {{SQL/StarRocks}}. Не использовать MySQL-специфичные функции и конструкции там, где они отсутствуют в StarRocks.
* Генератор должен формировать корректный SQL для: предпросмотра, пользовательского SQL-запроса, фильтрации (включая {{AND}}/{{OR}}, {{NULL}}, пустые значения), сортировки, агрегаций, {{GROUP BY}}, {{HAVING}}, вычисляемых полей и производных полей даты.
* Идентификаторы таблиц и полей экранировать в синтаксисе StarRocks (обратные кавычки, если применимо).
* Приведение к строке: использовать {{CAST(... AS STRING)}}, совместимый со StarRocks.
* Регулярные выражения: использовать оператор {{REGEXP}} StarRocks; не использовать MySQL-функцию {{regexp_like}}, если она не поддерживается целевой версией StarRocks.
* {{LIKE}}: экранировать {{%}}, {{_}}, {{\}} в соответствии с StarRocks-семантикой; не добавлять клаузу {{ESCAPE}}, если она вызывает ошибку StarRocks.
* {{HAVING}}: условия по агрегированным значениям размещать в {{HAVING}}, а не в {{WHERE}}.
* Ошибки SQL возвращать пользователю как контролируемые ошибки без повреждения набора данных и без сброса введённого SQL.

---
h4. 2.6. Производные поля даты.

* Поддерживать те же варианты извлечения частей даты, что доступны для аналогичных SQL-источников: год, квартал, месяц, неделя, день, день недели, год-квартал, год-месяц, год-неделя, год-день и другие варианты, доступные в текущем UI.
* Если интерфейс ожидает русские названия месяцев или дней недели — генерировать значения явно через {{CASE}} по номеру месяца/дня недели. Нельзя полагаться на локаль StarRocks или функции типа {{DATE_FORMAT}} для получения русскоязычных значений.
* Производные датовые поля доступны для предпросмотра, фильтрации, сортировки и построения отчётов.

---
h4. 2.7. DDL и операции записи.

* Если сценарий платформы предполагает создание таблицы-приёмника в StarRocks — использовать StarRocks-совместимый DDL с учётом key-модели и {{DISTRIBUTED BY}}. Не использовать {{ENGINE=InnoDB}}, MySQL-индексы, MySQL-FK, {{AUTO_INCREMENT}} и другие MySQL-конструкции.
* Тихое выполнение операций записи через MySQL-ветку недопустимо.

При запросе функции, обозначенной как недоступная для {{starrocks}}, бэкенд возвращает контролируемую функциональную ошибку независимо от того, каким образом был инициирован запрос — через UI или прямым API-вызовом. Фронтенд отображает состояние элементов карточки на основании ответов бэкенда и показывает полученную ошибку в существующем UX-паттерне. Прямая подмена payload не должна позволять выполнить недоступную для StarRocks операцию: валидация обеспечивается исключительно на бэкенде.

---
h4. 2.9. Обратная совместимость.

* Добавление StarRocks не изменяет поведение MySQL-источников, их SQL-диалект, маппинг типов и порт по умолчанию.
* PostgreSQL, ClickHouse, MS SQL Server, SQLite, Vertica и другие поддерживаемые источники продолжают работать без изменений.
* Существующие наборы данных и отчёты на других типах источников не требуют миграции.
* Если в системе ранее были технически созданы источники StarRocks через тип {{mysql}}, автоматическая их миграция в рамках данной задачи не предполагается; для штатной работы создаётся новый источник с типом {{starrocks}}.

h3. 5. Критерии приёмки (AC).

*AC-1 — Отображение StarRocks в списке типов подключения:*
* *Дано:* пользователь с правами на создание источников открывает «Источники» и запускает создание нового источника.
* *Когда:* пользователь раскрывает список «Тип подключения».
* *Тогда:* в списке присутствует отдельный пункт StarRocks.
* *И:* StarRocks не заменяет и не переименовывает MySQL, PostgreSQL, ClickHouse и другие существующие типы.

*AC-2 — Создание карточки StarRocks-источника:*
* *Дано:* пользователь выбрал тип подключения StarRocks.
* *Когда:* отображается карточка нового источника.
* *Тогда:* доступны стандартные поля SQL-источника: тип подключения, имя источника, отображаемое название, хост, порт, имя БД, схема БД, логин, пароль и другие обязательные поля формы.
* *И:* порт по умолчанию — {{9030}}, если пользователь не указал иное.

*AC-3 — Сохранение StarRocks как отдельного типа источника:*
* *Дано:* пользователь заполнил карточку валидными параметрами.
* *Когда:* пользователь сохраняет источник.
* *Тогда:* источник сохраняется с типом {{starrocks}}, а не {{mysql}}.
* *И:* последующие операции (чтение схемы, предпросмотр, запросы) используют StarRocks-логику.

*AC-4 — Валидация обязательных параметров подключения:*
* *Дано:* пользователь создаёт или изменяет StarRocks-источник.
* *Когда:* в payload отсутствуют обязательные параметры или переданы значения некорректного формата.
* *Тогда:* API возвращает контролируемую ошибку валидации.
* *И:* текст ошибки позволяет определить поле, требующее исправления, без раскрытия секретов.

*AC-5 — Успешная проверка подключения:*
* *Дано:* StarRocks-источник с корректными параметрами, доступным кластером и валидными учётными данными.
* *Когда:* пользователь запускает проверку подключения.
* *Тогда:* система возвращает успешный статус проверки.
* *И:* проверка не изменяет данные в StarRocks и не требует предварительного создания набора данных.

*AC-6 — Ошибки подключения:*
* *Дано:* параметры содержат ошибку в хосте, порте, имени БД, логине, пароле или кластер недоступен.
* *Когда:* пользователь запускает проверку подключения.
* *Тогда:* API возвращает контролируемую ошибку с диагностическим сообщением.
* *И:* пароль, токены и полная строка подключения не раскрываются в тексте ошибки.

*AC-7 — Ограниченные права пользователя БД:*
* *Дано:* пользователь БД может подключиться, но не имеет прав на чтение части объектов схемы.
* *Когда:* выполняется проверка подключения и чтение метаданных.
* *Тогда:* проверка подключения отрабатывает в соответствии с фактической доступностью БД.
* *И:* ошибки доступа к отдельным объектам возвращаются как контролируемые ошибки без аварийного завершения backend-сервиса.

*AC-8 — Сохранение и повторное открытие StarRocks-источника:*
* *Дано:* пользователь создал StarRocks-источник с валидными параметрами.
* *Когда:* источник сохраняется, закрывается и открывается повторно.
* *Тогда:* источник отображается как StarRocks-источник, несекретные параметры отображаются корректно, пароль не раскрывается.
* *И:* проверка подключения продолжает работать, если пароль не изменялся.

*AC-9 — Редактирование StarRocks-источника:*
* *Дано:* StarRocks-источник создан и используется в наборе данных.
* *Когда:* пользователь меняет несекретные параметры или вводит новый пароль.
* *Тогда:* изменения сохраняются корректно, проверка подключения выполняется по актуальным параметрам.
* *И:* если пароль не менялся — существующее рабочее значение не сбрасывается.

*AC-10 — Отображение функций в карточке StarRocks-источника:*
* *Дано:* пользователь открыл карточку StarRocks-источника.
* *Когда:* отображается карточка источника.
* *Тогда:* фронтенд отображает стандартную форму SQL-источника по общей схеме; доступность элементов (ФВД, отчётные формы, RLS, MDX, коррекция данных, импорт Excel) отражает состояние, полученное от бэкенда.
* *И:* для функций, недоступных для StarRocks согласно capability-флагам бэкенда, соответствующие переключатели/кнопки отображаются в недоступном состоянии или возвращают ошибку при нажатии — в соответствии с общим UX-паттерном формы источника.

*AC-11 — Backend-валидация недоступных функций:*
* *Дано:* для StarRocks недоступны RLS, ФВД, отчётные формы, коррекция данных, MDX, импорт Excel.
* *Когда:* через прямой API-вызов, нажатие кнопки в UI или подмену payload выполняется попытка применить недоступную для StarRocks функцию.
* *Тогда:* бэкенд возвращает контролируемую функциональную ошибку о неподдерживаемой операции для типа {{starrocks}}.
* *И:* недоступная функция не сохраняется в метаданных источника; источник остаётся в консистентном состоянии.
* *И:* фронтенд отображает полученную ошибку в существующем UX-паттерне.

*AC-12 — Чтение списка таблиц и представлений:*
* *Дано:* StarRocks-источник подключён, в доступной схеме есть таблицы и представления.
* *Когда:* платформа запрашивает метаданные источника.
* *Тогда:* бэкенд возвращает список доступных объектов в формате, совместимом с мастером набора данных.
* *И:* недоступные по правам объекты не приводят к падению операции чтения всей схемы.

*AC-13 — Чтение полей таблицы:*
* *Дано:* таблица StarRocks содержит поля разных типов, nullable-поля, заданный порядок следования.
* *Когда:* платформа запрашивает структуру таблицы.
* *Тогда:* бэкенд возвращает имена полей, исходные типы StarRocks, внутренние типы платформы, признаки {{nullable}} и порядок полей.
* *И:* порядок полей соответствует метаданным StarRocks.

*AC-14 — Пустая схема и отсутствие прав:*
* *Дано:* подключение успешно, но в схеме нет таблиц или нет прав на их чтение.
* *Когда:* платформа запрашивает список таблиц.
* *Тогда:* API возвращает корректный пустой результат или понятную ошибку доступа.
* *И:* операция не завершается технической ошибкой сервера.

*AC-15 — Маппинг строковых типов:*
* *Дано:* таблица содержит поля {{CHAR}}, {{VARCHAR}}, {{STRING}}.
* *Когда:* бэкенд читает метаданные и выполняет предпросмотр.
* *Тогда:* строковые поля сопоставляются с внутренним строковым типом платформы.
* *И:* значения на кириллице, латинице, со спецсимволами, пустые строки и {{NULL}} возвращаются без искажения.

*AC-16 — Маппинг числовых типов:*
* *Дано:* таблица содержит поля {{TINYINT}}, {{SMALLINT}}, {{INT}}, {{BIGINT}}, {{DECIMAL}}, {{FLOAT}}, {{DOUBLE}}.
* *Когда:* бэкенд читает метаданные и выполняет запросы.
* *Тогда:* поля сопоставляются с корректными внутренними типами платформы.
* *И:* целые, дробные, отрицательные значения и значения с заданной точностью возвращаются без потери в пределах поддерживаемой точности платформы.

*AC-17 — Безопасная обработка {{LARGEINT}}:*
* *Дано:* таблица содержит поле {{LARGEINT}} со значением за пределами безопасного диапазона {{int64}}/{{float64}}.
* *Когда:* бэкенд выполняет предпросмотр или запрос набора данных.
* *Тогда:* значение не преобразуется в {{float64}} с потерей точности.
* *И:* значение возвращается в безопасном согласованном представлении (например, строкой), а метаданные поля позволяют фронтенду обработать его без искажения.

*AC-18 — Маппинг {{BOOLEAN}}:*
* *Дано:* таблица содержит поле {{BOOLEAN}}.
* *Когда:* бэкенд читает метаданные и выполняет предпросмотр.
* *Тогда:* поле сопоставляется с внутренним логическим или совместимым типом платформы.
* *И:* значения {{true}}/{{false}} и {{NULL}} возвращаются без искажения.

*AC-19 — Маппинг дата/время:*
* *Дано:* таблица содержит поля {{DATE}} и {{DATETIME}}.
* *Когда:* бэкенд читает метаданные, выполняет предпросмотр и запросы.
* *Тогда:* поля сопоставляются с внутренними датовыми типами платформы.
* *И:* значения отображаются и фильтруются без синтаксических ошибок SQL.

*AC-20 — Обработка сложных и ограниченно поддерживаемых типов:*
* *Дано:* таблица содержит поля {{JSON}}, {{ARRAY}}, {{MAP}}, {{STRUCT}}, {{BITMAP}}, {{HLL}}.
* *Когда:* бэкенд читает метаданные и выполняет предпросмотр.
* *Тогда:* такие поля обрабатываются предсказуемо: сопоставляются с поддерживаемым внутренним типом, возвращаются строкой или помечаются как ограниченно поддерживаемые.
* *И:* наличие таких полей не блокирует работу с поддерживаемыми полями таблицы.

*AC-21 — Корректное экранирование идентификаторов:*
* *Дано:* таблицы или поля StarRocks имеют имена со смешанным регистром, зарезервированными словами или допустимыми спецсимволами.
* *Когда:* платформа строит запросы предпросмотра, фильтрации, сортировки или агрегации.
* *Тогда:* бэкенд формирует синтаксически корректный SQL в диалекте StarRocks.
* *И:* запрос выполняется без ошибок из-за некорректного экранирования.

*AC-22 — Предпросмотр таблицы StarRocks:*
* *Дано:* создан StarRocks-источник и выбрана таблица с поддерживаемыми полями.
* *Когда:* пользователь запускает предпросмотр.
* *Тогда:* бэкенд формирует корректный SQL в диалекте StarRocks и возвращает ограниченную выборку.
* *И:* предпросмотр корректно работает для таблиц с разными типами, для пустых таблиц и таблиц с {{NULL}}-значениями.

*AC-23 — Пользовательский SQL-запрос в наборе данных:*
* *Дано:* аналитик создаёт набор данных на StarRocks-источнике с корректным SQL-запросом.
* *Когда:* выполняется проверка/сохранение запроса и предпросмотр.
* *Тогда:* запрос выполняется на StarRocks, результат возвращается в платформу, поля получают корректные имена и типы.

*AC-24 — Ошибка пользовательского SQL:*
* *Дано:* аналитик указывает SQL с синтаксической ошибкой, несуществующей таблицей/полем или нарушением прав.
* *Когда:* выполняется проверка или предпросмотр.
* *Тогда:* API возвращает контролируемую ошибку.
* *И:* ошибка не падает в 500, не очищает введённый SQL и не блокирует последующие корректные запросы к источнику.

*AC-25 — Сохранение и повторное открытие набора данных:*
* *Дано:* создан набор данных на StarRocks-источнике с таблицей или пользовательским SQL.
* *Когда:* набор данных сохраняется, закрывается и открывается повторно.
* *Тогда:* связь с источником, SQL-запрос, список и типы полей сохраняются.
* *И:* повторный предпросмотр выполняется без пересоздания источника.

*AC-26 — Фильтрация по строковым, числовым и датовым полям:*
* *Дано:* набор данных StarRocks содержит строковые, числовые и датовые поля.
* *Когда:* пользователь применяет фильтры по одному полю каждого типа.
* *Тогда:* бэкенд формирует корректные условия SQL для StarRocks.
* *И:* результат содержит только записи, соответствующие фильтру; пустой результат возвращается как пустой набор без технической ошибки.

*AC-27 — Комбинированная фильтрация (AND / OR):*
* *Дано:* набор данных содержит несколько полей разных типов.
* *Когда:* применяются несколько фильтров одновременно с условиями {{AND}}/{{OR}}.
* *Тогда:* бэкенд формирует корректный SQL для StarRocks.
* *И:* итоговая выборка соответствует ожидаемому результату по тестовым данным.

*AC-28 — Фильтрация по NULL и пустым значениям:*
* *Дано:* таблица содержит строки с {{NULL}} и пустыми значениями в разных типах полей.
* *Когда:* применяются фильтры на пустые/{{NULL}}-значения и фильтры, их исключающие.
* *Тогда:* бэкенд формирует корректный SQL с учётом различия {{NULL}} и пустой строки.
* *И:* результат соответствует ожидаемой выборке.

*AC-29 — Экранирование спецсимволов в LIKE:*
* *Дано:* таблица содержит строковые значения с символами {{%}}, {{_}}, {{\\}}.
* *Когда:* пользователь применяет фильтр частичного совпадения по таким значениям.
* *Тогда:* бэкенд формирует корректное условие {{LIKE}} для StarRocks.
* *И:* спецсимволы ищутся как обычные символы; SQL не содержит клаузы {{ESCAPE}}, вызывающей ошибку StarRocks.

*AC-30 — Регулярные выражения в StarRocks-диалекте:*
* *Дано:* фильтр или вычисляемое поле требует проверки строки регулярным выражением.
* *Когда:* бэкенд строит SQL для StarRocks.
* *Тогда:* используется оператор {{REGEXP}}, поддерживаемый StarRocks.
* *И:* MySQL-функция {{regexp_like}} не используется, если она не поддерживается целевой версией StarRocks.

*AC-31 — Агрегации и GROUP BY:*
* *Дано:* набор данных содержит поля для группировки и расчёта агрегатов.
* *Когда:* отчёт или предпросмотр запрашивает {{COUNT}}, {{SUM}}, {{AVG}}, {{MIN}}, {{MAX}} с группировкой.
* *Тогда:* бэкенд формирует корректный SQL с {{GROUP BY}} для StarRocks.
* *И:* результат агрегации соответствует данным в StarRocks.

*AC-32 — HAVING для агрегированных условий:*
* *Дано:* запрос к StarRocks-набору использует фильтр по агрегированному значению.
* *Когда:* выполняется запрос с агрегацией.
* *Тогда:* условие по агрегату размещается в {{HAVING}}, а не в {{WHERE}}.
* *И:* результат соответствует ожидаемой выборке.

*AC-33 — Сортировка:*
* *Дано:* набор данных содержит поля разных типов.
* *Когда:* запрос использует сортировку по строковому, числовому, датовому или вычисляемому полю.
* *Тогда:* бэкенд формирует корректный {{ORDER BY}} для StarRocks.
* *И:* порядок строк соответствует заданному направлению сортировки.

*AC-34 — Вычисляемые поля:*
* *Дано:* в наборе данных создано вычисляемое поле на основе строковых, числовых или датовых полей.
* *Когда:* выполняется предпросмотр или построение отчёта.
* *Тогда:* выражение транслируется в синтаксис StarRocks и рассчитывается на стороне БД.
* *И:* вычисляемое поле доступно в ответе платформы.

*AC-35 — Ошибка в вычисляемом поле:*
* *Дано:* вычисляемое поле содержит некорректное выражение или несовместимые типы.
* *Когда:* выполняется предпросмотр или построение отчёта.
* *Тогда:* API возвращает контролируемую ошибку выполнения.
* *И:* ошибка не повреждает источник и не блокирует работу с другими полями набора.

*AC-36 — Производные поля даты:*
* *Дано:* набор данных StarRocks содержит поле дата/дата-время.
* *Когда:* пользователь создаёт производные поля через инструмент извлечения частей даты.
* *Тогда:* для StarRocks корректно работают все варианты, доступные в текущем UI (год, квартал, месяц, неделя, день, день недели, год-квартал, год-месяц, год-неделя, год-день и другие).
* *И:* значения возвращаются в ожидаемых форматах.

*AC-37 — Русские названия месяцев и дней недели:*
* *Дано:* производные поля даты должны возвращать название или сокращённое название месяца/дня недели.
* *Когда:* выполняется предпросмотр или построение отчёта.
* *Тогда:* значения возвращаются на русском языке через явную генерацию SQL (например, через {{CASE}} по номеру).
* *И:* результат не зависит от локали StarRocks.

*AC-38 — Фильтрация и сортировка по производным датовым полям:*
* *Дано:* в наборе создано производное поле даты (год, месяц, неделя, год-месяц и др.).
* *Когда:* пользователь применяет фильтр или сортировку по производному датовому полю.
* *Тогда:* бэкенд формирует корректный SQL для StarRocks.
* *И:* фильтрация по исходному и производному датовым полям не конфликтуют.

*AC-39 — Построение отчёта на StarRocks-наборе данных:*
* *Дано:* создан и сохранён набор данных на базе StarRocks-источника.
* *Когда:* пользователь строит отчёт/визуализацию на его основе.
* *Тогда:* портал получает данные из StarRocks без SQL-ошибок.
* *И:* базовые сценарии отчёта, фильтрации и отображения данных возвращают ожидаемые значения.

*AC-40 — StarRocks недоступен в конструкторе ФВД:*
* *Дано:* в системе есть сохранённый StarRocks-источник.
* *Когда:* пользователь открывает конструктор ФВД и выбирает хранилище.
* *Тогда:* StarRocks-источник отсутствует в списке доступных хранилищ.

*AC-41 — StarRocks недоступен в мастере импорта Excel:*
* *Дано:* в системе есть сохранённый StarRocks-источник.
* *Когда:* пользователь открывает сценарий импорта Excel.
* *Тогда:* StarRocks-источник недоступен как целевой источник.

*AC-42 — Контролируемое поведение операций записи и DDL:*
* *Дано:* через API или интерфейс запускается сценарий создания таблицы, массовой загрузки или записи данных в StarRocks.
* *Когда:* такой сценарий не поддержан в текущем релизе.
* *Тогда:* система возвращает контролируемую ошибку о неподдерживаемой операции для типа {{starrocks}}.
* *И:* система не выполняет операцию через MySQL-DDL или MySQL-ветку записи.

*AC-43 — Регрессия: MySQL-источник:*
* *Дано:* в системе есть существующий MySQL-источник и набор данных на его базе.
* *Когда:* выполняются сценарии подключения, чтения схемы, предпросмотра, фильтрации, агрегации, вычисляемых и производных датовых полей.
* *Тогда:* поведение MySQL не изменилось, MySQL-источник продолжает сохраняться и использоваться с типом {{mysql}}.
* *И:* MySQL не получает StarRocks-специфичных правил генерации SQL.

*AC-44 — Регрессия: прочие типы источников:*
* *Дано:* в системе есть источники PostgreSQL, ClickHouse, MS SQL Server, SQLite, Vertica и другие.
* *Когда:* выполняются существующие сценарии подключения, чтения схемы, предпросмотра, фильтрации, агрегации и построения отчётов.
* *Тогда:* добавление StarRocks не меняет их поведение, маппинг типов, SQL-генерацию и обработку ошибок.

*AC-45 — Права пользователя портала:*
* *Дано:* пользователь не имеет прав на создание или редактирование источников данных.
* *Когда:* пользователь открывает раздел «Источники» или карточку StarRocks-источника.
* *Тогда:* действия создания, редактирования, проверки подключения и сохранения ограничены так же, как для других типов источников.
* *И:* добавление StarRocks не создаёт обхода существующей модели прав.

"h3. Контекст и проблематика.

В {{Modus BI Cloud}} пользователи внешних облачных контуров работают преимущественно с ролью {{«аналитик»}}. Для этой роли доступна вкладка {{«Подключения»}}, где пользователь может создать подключение к внешнему источнику и затем использовать его в сценарии {{«Правила загрузки данных»}} для загрузки данных во внутреннее облачное хранилище {{ClickHouse}}.

При этом вкладка {{«Источники»}} для аналитиков в облачной версии недоступна. Через {{«Источники»}} в портале исторически работает сценарий прямых запросов к внешним СУБД: пользователь создаёт источник данных, затем на его базе создаёт произвольный набор данных, который обращается к внешней СУБД напрямую, без предварительной загрузки данных во внутреннее хранилище.

Сейчас в облаке существуют два близких, но разных сценария:
* {{«Источники»}} → {{«Наборы данных»}} — сценарий DirectQuery, где запросы выполняются напрямую к внешней СУБД;
* {{«Подключения»}} → {{«Правила загрузки данных»}} → {{«Наборы данных»}} — сценарий загрузки данных во внутренний {{ClickHouse}}, где пользователь сначала создаёт подключение, затем правило загрузки, после чего работает с загруженными данными.

Для облачной версии необходимо дать аналитику возможность использовать созданные им подключения к внешним СУБД не только для загрузки данных через {{«Правила загрузки данных»}}, но и для DirectQuery при создании произвольных наборов данных.

При этом на текущем этапе нельзя менять ролевую модель и открывать аналитикам вкладку {{«Источники»}}, чтобы не увеличивать трудозатраты и не расширять область изменений. Пользовательской точкой входа для аналитика должна остаться вкладка {{«Подключения»}}, а связанный источник данных для DirectQuery должен создаваться системой под капотом.

h3. Цель задачи.

*Требуется:*
# Добавить в {{Modus BI Cloud}} возможность помечать поддерживаемые подключения к внешним СУБД как доступные для прямых запросов {{DirectQuery}}.
# При включении признака "Прямое подключение к БД (DirectQuery)" автоматически создавать и синхронизировать связанный источник данных в существующем механизме {{«Источники»}}.
# Сделать автоматически созданный источник доступным аналитику в сценарии создания произвольного набора данных, не открывая ему вкладку {{«Источники»}} и не меняя текущую ролевую модель.
# Сохранить текущий сценарий загрузки данных через {{«Правила загрузки данных»}} без регресса.

_Пользовательская история:_
Как аналитик в {{Modus BI Cloud}}, при создании подключения к внешней СУБД я хочу иметь возможность создавать произвольные наборы данных с прямым обращением к внешней базе данных без предварительной загрузки данных во внутреннее облачное хранилище.

----
h3. 1. Описание текущего поведения.

h4. 1.1. Работа аналитика с подключениями.

В текущем облачном сценарии аналитик может открыть вкладку {{«Подключения»}} и создать подключение к внешнему источнику данных.

Для подключений к СУБД пользователь указывает стандартные параметры соединения, включая:
* наименование подключения;
* сервер/host;
* порт;
* базу данных;
* схему, если она используется для выбранного типа СУБД;
* пользователя;
* пароль;
* другие параметры, предусмотренные текущей формой подключения.

После создания подключения пользователь может перейти в {{«Правила загрузки данных»}}, задать правило загрузки и переложить данные из внешнего источника во внутреннее облачное хранилище {{ClickHouse}}. Далее эти данные используются в простых и составных наборах данных.

---
h4. 1.2. Работа через прямые запросы к БД.

Сценарий прямых запросов к БД на основном портале происходит на вкладке «Источники» и идет через работу с произвольными наборами данных.

В стандартном сценарии пользователь выбирает источник данных, на базе которого создаётся произвольный набор данных. Запрос такого набора выполняется напрямую к источнику, то есть к внешней СУБД, без обязательной загрузки данных во внутренний {{ClickHouse}}.

В облачном портале *аналитик* не может самостоятельно создать такой источник, потому что вкладка {{«Источники»}} для его роли недоступна.

---
h4. 1.3. Ограничение облачной версии.

Сейчас аналитик в облаке может самостоятельно создать подключение к внешней СУБД, но не может использовать это же подключение как источник для DirectQuery (например, для создания произвольного набора данных).

Из-за этого пользователь вынужден работать только через сценарий загрузки данных во внутреннее хранилище, даже если для его задачи достаточно прямого запроса к внешней СУБД.

----
h3. 2. Описание целевого поведения.

h4. 2.1. Общий пользовательский сценарий.

После доработки аналитик должен иметь возможность включить параметр "Прямое подключение к БД (DirectQuery)" для поддерживаемого типа подключения прямо из формы создания или редактирования на вкладке {{«Подключения»}}.

Целевой сценарий:
# Аналитик открывает вкладку {{«Подключения»}}.
# Аналитик создаёт новое подключение к поддерживаемой СУБД или открывает существующее подключение для редактирования.
# Если тип подключения относится к поддерживаемым для текущей задачи СУБД, в форме отображается признак "Прямое подключение к БД (DirectQuery)".
# Аналитик заполняет стандартные параметры подключения.
# Аналитик ставит галочку для параметра "Прямое подключение к БД (DirectQuery)", активируя механизм {{«DirectQuery»}} запроса.
#* При наведении пользователем указателя на параметр "Прямое подключение к БД (DirectQuery)" должна появляться пояснительная записка (tooltip) - "На основании данного подключения будет подготовлен Источник данных для создания произвольных наборов без предварительной загрузки данных во внутреннее хранилище портала".
# При сохранении система сохраняет подключение и автоматически создаёт связанный источник данных в существующем механизме {{«Источники»}}.
# Вкладка {{«Источники»}} для аналитика по-прежнему недоступна.
# При создании произвольного набора данных аналитик видит автоматически созданный источник в списке источников, доступных для прямого запроса.
# Произвольный набор данных, созданный на базе такого источника, выполняет запрос напрямую к внешней СУБД.

---
h4. 2.2. Поддерживаемые типы подключений.

В рамках первой реализации признак {{«DirectQuery»}} должен быть доступен только для подключений к следующим СУБД:
* {{ClickHouse}};
* {{PostgreSQL}} / {{Postgres}};
* {{Vertica}};
* {{MS SQL Server}}.

Для неподдерживаемых типов подключений признак {{DirectQuery}} не должен отображаться (и должен быть недоступен).

В первую реализацию не входят:
* {{Excel}};
* {{Google Sheets}};
* {{1С}};
* другие файловые, табличные и СУБД источники, для которых сценарий DirectQuery через источник не подтверждён в рамках этой задачи.

---
h4. 2.3. Автоматически создаваемый источник данных.

Если пользователь включает признак {{«DirectQuery»}} и сохраняет подключение, система должна создать связанный источник данных на базе параметров этого подключения.

Источник должен создаваться с минимально необходимыми настройками, достаточными для работы прямых запросов к этой БД:
* тип СУБД/драйвер должен соответствовать типу подключения;
* наименование источника должно быть понятно пользователю и по умолчанию соответствовать наименованию подключения или однозначно от него наследоваться;
* host, порт, база данных, схема, пользователь и пароль должны быть перенесены из подключения в настройки источника по правилам соответствующего типа СУБД;
* служебная связь между подключением и созданным источником должна сохраняться в метаданных, чтобы источник можно было обновлять при последующем редактировании подключения;
* настройки источников, неактуальные для данного облачного сценария, не должны становиться обязательными для пользователя.

К настройкам, которые не должны требоваться от аналитика в рамках этого сценария, относятся, например:
* MDX-настройки;
* настройки ФВД;
* дополнительные специализированные признаки источника, если они не нужны для прямого SQL-запроса к поддерживаемой СУБД.

Если для существующего объекта {{datasources}} часть таких полей технически обязательна, требуется заполнять их штатными значениями по умолчанию, не требуя от аналитика работы с вкладкой {{«Источники»}}.

---
h4. 2.4. Синхронизация подключения и связанного источника.

Пока у подключения включён признак {{«DirectQuery»}}, связанный источник должен синхронизироваться с актуальными параметрами подключения.

Синхронизации подлежат как минимум:
* наименование, если источник был создан автоматически и не был отделён от подключения;
* тип СУБД / драйвер;
* host;
* порт;
* база данных;
* схема;
* пользователь;
* пароль, если пользователь ввёл новое значение пароля в форме подключения;
* другие параметры соединения, которые фактически используются источником данных для DirectQuery.

Если пользователь редактирует подключение с включённым признаком DirectQuery, при сохранении должна происходить актуализация связанного источника.

Если пароль или другой секрет в форме подключения не изменялся, система не должна отображать его пользователю и не должна затирать сохранённое секретное значение пустым значением. Если пользователь вводит новый пароль, он должен быть обновлён и для подключения, и для связанного источника.

---
h4. 2.5. Отключение параметра DirectQuery для подключения.

При отключении признака {{«DirectQuery»}} необходимо продумать механизм взаимодействия с зависимыми объектами:
Подключение → Источник → Набор данных → Визуализации. 

При снятии галочки с параметра {{DirectQuery}}, для которого уже был создан связанный источник данных, система должна обработать зависимость явно и без скрытой потери пользовательских данных.

Предлагаемый механизм:
* при остутствии зависимостей на созданные произвольные наборы данных - параметр отключается для подключения, а связанный источник данных удаляется.
* при наличии зависимостей на созданные наборы данных:
** при остутствии зависимостей на визуализации - запросить подтверждение и уведомить пользователя, что "Внимание: связанный источник и наборы данных будут удалены при отключении этого параметра".
** при наличии зависимостей на визуализации - запретить отключение этого параметра для данного подключения до разрешения конфликтов. Указать причину блокировки.

Точный механизм удаления необходимо подтвердить у разработки по текущей модели зависимостей {{connection}}, {{datasources}} и {{datasets}}.

При *отсутствии критических зависимостей*, если пользователь снимает признак {{«DirectQuery»}} и сохраняет подключение:
* подключение должно остаться доступным для текущих сценариев {{«Правила загрузки данных»}};
* связанный источник не должен отображаться аналитику в списке доступных источников для создания новых произвольных наборов данных и должен быть удалён;
* уже созданные произвольные наборы данных не должны удаляться без прямого уведомления пользователя.

Если признак {{DirectQuery}} включается повторно:
* связанный источник должен быть создан и параметры по текущему подключению должны быть актуализированны;
* система не должна создавать дубли источников при каждом повторном включении признака.

---
h4. 2.6. Доступность источника при создании произвольного набора данных.

В сценарии создания произвольного набора данных аналитик должен видеть в списке доступных источников только те источники, которые доступны ему по текущей модели облака.

Для {{Modus BI Cloud Start}} (текущей индивидуальной облачной модели):
* аналитик должен видеть только свои автоматически созданные DirectQuery-источники;
* источники других пользователей не должны отображаться аналитику;
* администратор сохраняет текущую возможность видеть объекты по правилам своей роли.

В рамках данной задачи не требуется реализовывать модель совместного доступа для {{Modus BI Cloud Teams}} или рабочих пространств. Совместная видимость подключений, правил загрузки и наборов данных внутри командного контура будет описываться отдельной задачей.

----
h3. 3. Требования к реализации.

h4. 3.1. Фронтенд-часть.

* В форме создания и редактирования {{«Подключения»}} необходимо добавить признак {{«DirectQuery»}} или эквивалентный согласованный текст.
* Признак должен отображаться только для поддерживаемых типов СУБД: {{ClickHouse}}, {{PostgreSQL}}, {{Vertica}}, {{MS SQL Server}}.
* При смене типа подключения в форме доступность признака должна пересчитываться без потери уже введённых параметров подключения.
* При создании нового подключения признак DirectQuery по умолчанию должен быть выключен.
* При редактировании существующего подключения форма должна отображать текущее сохранённое состояние признака DirectQuery.
* После успешного сохранения подключения с включённым признаком DirectQuery пользователь должен остаться в понятном штатном состоянии формы: подключение сохранено, источник для DirectQuery создан или обновлён.
* Если источник создать или обновить не удалось, пользователь должен получить штатное сообщение об ошибке. Введённые данные формы не должны теряться.
* Вкладка {{«Источники»}} не должна становиться доступной аналитику из-за этой доработки.
* В форме создания произвольного набора данных список источников должен учитывать автоматически созданные DirectQuery-источники, доступные текущему аналитику.
* Отображаемое имя такого источника должно позволять пользователю сопоставить его с созданным подключением.

---
h4. 3.2. Бэкенд-часть.

h5. 3.2.1. API.

Точные команды API необходимо подтвердить по текущей реализации, но логика должна соответствовать общему контракту платформы и не требовать дополнительных доработок:
* при создании нового подключения с включённым признаком {{DirectQuery}} backend должен создать {{connection}} и связанный {{datasources}};
* при обновлении подключения backend должен перед изменением получить актуальное состояние через существующий механизм {{get}}/{{list}} или эквивалентное чтение формы;
* при обновлении подключения с включённым признаком DirectQuery backend должен обновить связанный {{datasources}};
* при выключении признака DirectQuery backend должен прекратить считать связанный источник активным DirectQuery-источником этого подключения;
* при повторном включении признака DirectQuery backend должен переиспользовать ранее связанный источник, если это возможно, или создать новый источник без дублирования;
* {{object.id}}, {{command.id}} и поля внутри {{data}} не должны смешиваться;
* секреты не должны возвращаться на frontend в открытом виде;
* при отсутствии изменения пароля существующее секретное значение должно сохраняться;
* при изменении пароля новое значение должно применяться и к подключению, и к связанному источнику.

Сохранение подключения с включённым {{DirectQuery}} должно быть консистентным с пользовательской точки зрения. После успешного ответа backend в системе не должно оставаться состояния, где признак {{DirectQuery}} включён, а связанный источник не создан или недоступен для выбора в произвольном наборе данных - если создание или обновление источника невозможно, backend должен вернуть ошибку сохранения с понятным сообщением. 

Допустимый технический механизм обеспечения консистентности определяется разработкой: транзакция, компенсационное действие или откат включения признака {{DirectQuery}} при неуспешном создании источника.

---
h5. 3.2.2. Метаданные и связь объектов.

В метаданных должна быть обеспечена устойчивая связь между подключением и автоматически созданным источником данных.

Логически необходимо хранить:
|| Логическая сущность || Назначение ||
| Признак {{DirectQuery}} у подключения | Определяет, что подключение должно использоваться как точка входа для DirectQuery и должно иметь связанный источник данных. |
| Связь подключения с источником | Позволяет обновлять один и тот же источник при редактировании подключения и не создавать дубли. |
| Признак происхождения источника | Позволяет отличать источники, созданные автоматически из подключений, от источников, созданных вручную через раздел {{«Источники»}}. |
| Владелец / область видимости | Позволяет в {{Cloud Start}} показывать аналитику только собственные DirectQuery-источники. |

Точные имена полей и место хранения связи должны быть определены разработкой. Источник и подключение должны быть связаны для синхронизации, повторного включения {{DirectQuery}}, фильтрации списка источников и предотвращения дублей.

---
h4. 3.3. Права и доступность.

* Доработка не должна менять текущую ролевую модель {{Modus BI Cloud}}.
* Аналитик не должен получать общий доступ к вкладке {{«Источники»}}.
* Аналитик не должен получать право создавать, редактировать или удалять произвольные Источники данных напрямую.
* Аналитик может инициировать создание и обновление связанного источника только через сохранение своего подключения с включённым признаком {{DirectQuery}}.
* Backend должен проверять, что пользователь имеет право на создание или редактирование соответствующего подключения.
* Автоматическое создание источника должно ограничиваться только поддерживаемыми типами СУБД.
* В {{Cloud Start}} аналитик должен видеть в сценарии произвольного набора данных только свои DirectQuery-источники, созданные из его подключений.
* Пользователь с правами администратора, может видеть автоматически созданные источники по текущим правилам своей роли.

---
h4. 3.4. Удаление подключения.

При удалении подключения, для которого уже был создан связанный источник данных, система должна обработать зависимость явно и без скрытой потери пользовательских данных.

Предлагаемый механизм:
* при остутствии зависимостей на созданные произвольные наборы данных - удаление происходит по штатному сценарию. Удаляется подключение и связанный источник данных.
* при наличии зависимостей на созданные произвольные наборы данных:
** при остутствии зависимостей на визуализации - запросить подтверждение на удаление и уведомить пользователя, что связанные наборы данных будут удалены вместе с этим подключением.
** при наличии зависимостей на визуализации - запретить удаление подключения до разрешения конфликтов. Указать причину блокировки.

Точный механизм удаления необходимо подтвердить у разработки по текущей модели зависимостей {{connection}}, {{datasources}} и {{datasets}}.

---
h4. 3.5. Обратная совместимость.

* Все существующие подключения должны открываться и сохраняться без обязательной миграции пользовательских действий.
* Для существующих подключений признак DirectQuery должен быть выключен, если для них ранее не была создана соответствующая связь.
* Существующие правила загрузки данных должны продолжить работать по прежнему сценарию.
* Существующие источники данных, созданные вручную администраторами через вкладку {{«Источники»}}, не должны превращаться в источники от подключений без явной связи.
* Существующие произвольные наборы данных должны продолжить использовать свои источники по текущей логике.
* Генерация SQL и выполнение DirectQuery должны переиспользовать существующий механизм произвольных наборов данных и источников, без отдельной новой ветки SQL-логики специально для подключений.

----
h3. 4. Пограничные сценарии.

* *Новое поддерживаемое подключение без DirectQuery:* пользователь создаёт подключение к PostgreSQL, ClickHouse, Vertica или MS SQL Server и не включает признак DirectQuery; подключение сохраняется как раньше, источник под капотом не создаётся.
* *Новое поддерживаемое подключение с DirectQuery:* пользователь включает признак DirectQuery; после сохранения появляется связанный источник, доступный в сценарии произвольного набора данных.
* *Существующее подключение:* пользователь открывает ранее созданное подключение поддерживаемого типа, включает DirectQuery и сохраняет; система создаёт связанный источник на базе текущих параметров подключения.
* *Редактирование параметров:* пользователь меняет host, порт, базу, схему, пользователя или пароль у подключения с включённым DirectQuery; после сохранения связанный источник получает актуальные параметры.
* *Пароль не изменялся:* пользователь редактирует подключение с включённым DirectQuery, но не вводит новый пароль; сохранённый секрет не должен быть очищен ни в подключении, ни в источнике.
* *Отключение DirectQuery:* пользователь снимает признак DirectQuery; подключение остаётся доступным для правил загрузки данных, источник перестаёт быть доступным аналитику для создания новых DirectQuery-наборов через это подключение.
* *Повторное включение DirectQuery:* пользователь снова включает признак; система переиспользует ранее связанный источник или создаёт новый, если старый отсутствует, без создания дублей.
* *Неподдерживаемый тип подключения:* пользователь создаёт Excel, Google Sheets, 1С или другой неподдерживаемый источник; признак DirectQuery не отображается или недоступен, источник под капотом не создаётся.
* *Ошибка создания источника:* подключение не должно считаться успешно сохранённым с активным DirectQuery, если связанный источник не удалось создать или обновить.
* *Недостаточно прав:* пользователь без прав на создание или редактирование подключения не должен получить возможность создать источник через DirectQuery-признак.
* *Список источников в произвольном наборе:* аналитик в {{Cloud Start}} видит только собственные DirectQuery-источники, созданные из своих подключений.
* *Удаление подключения с зависимостями:* система не должна молча удалять источник, если на него уже ссылаются произвольные наборы данных.
* *Администраторский сценарий:* пользователь с доступом к вкладке {{«Источники»}} видит автоматически созданный источник по текущим правилам своей роли; действия администратора не должны создавать неконсистентную связь с подключением.

----
h3. 5. Не входит в рамки задачи:

* изменение ролевой модели {{Modus BI Cloud}};
* открытие вкладки {{«Источники»}} для аналитиков;
* реализация полноценной модели {{Workspace}} / {{Cloud Teams}};
* снятие ограничения видимости объектов других пользователей в {{Cloud Start}};
* изменение логики {{«Правил загрузки данных»}} и загрузки данных во внутренний {{ClickHouse}};
* реализация новых SQL-диалектов и нового движка DirectQuery;
* поддержка DirectQuery через подключения для {{Excel}}, {{Google Sheets}}, {{1С}} и других файловых или табличных источников;
* обязательное включение {{MySQL}} и {{StarRocks}} в список поддерживаемых типов для текущей реализации;
* переработка интерфейса раздела {{«Источники»}};
* миграция существующих источников, созданных вручную, в источники от подключений.

----
h3. 6. Предположения.

* Существующий механизм {{datasources}} уже достаточен для выполнения DirectQuery к {{ClickHouse}}, {{PostgreSQL}}, {{Vertica}} и {{MS SQL Server}}.
* Форма {{«Подключения»}} уже содержит минимальный набор параметров, достаточный для создания связанного источника DirectQuery для поддерживаемых СУБД.
* Для произвольных наборов данных уже существует механизм выбора источника и выполнения запроса напрямую к выбранному {{datasources}}.
* В {{Cloud Start}} действует текущая индивидуальная модель видимости: аналитик видит только собственные подключения, правила загрузки и наборы данных.
* Автоматически созданный источник может быть сохранён как обычный объект {{datasources}} с дополнительной служебной связью с {{connection}}.

----
h3. 7. Открытые вопросы.

* Нужно подтвердить, где технически лучше хранить связь между подключением и автоматически созданным источником: в метаданных подключения, в метаданных источника или в отдельной связующей структуре.
* Нужно согласовать точное поведение при удалении подключения, если связанный источник уже используется в произвольных наборах данных: запрет удаления, отделение источника или иной механизм.
* Нужно уточнить, должен ли администратор видеть отдельный признак в списке {{«Источники»}}, что источник создан автоматически из подключения.
* Нужно уточнить, должны ли {{MySQL}} и {{StarRocks}} попадать в список поддерживаемых DirectQuery-подключений после полноценной поддержки на уровне источников данных, или для каждого нового типа СУБД будем принимать отдельное решение.
* Нужно подтвердить итоговый текст UI-признака: {{«DirectQuery»}}/{{«Использовать для прямых запросов»}} и т.д.

----
h3. 8. Критерии приёмки (AC):

*AC.1 — Отображение признака DirectQuery для поддерживаемых СУБД:*
* *Дано:* аналитик открывает форму создания или редактирования подключения;
* *Когда:* выбран тип подключения {{ClickHouse}}, {{PostgreSQL}} / {{Postgres}}, {{Vertica}} или {{MS SQL Server}};
* *Тогда:* в форме доступен признак {{«DirectQuery»}} или согласованный аналогичный текст.

*AC.2 — Отсутствие признака для неподдерживаемых источников:*
* *Дано:* аналитик создаёт или редактирует подключение типа {{Excel}}, {{Google Sheets}}, {{1С}} или другого неподдерживаемого типа;
* *Когда:* открыта форма подключения;
* *Тогда:* пользователь не может включить DirectQuery для этого подключения, а источник под капотом не создаётся.

*AC.3 — Создание подключения с DirectQuery:*
* *Дано:* аналитик заполнил параметры нового подключения к поддерживаемой СУБД и включил признак DirectQuery;
* *Когда:* пользователь сохраняет подключение;
* *Тогда:* система сохраняет подключение и создаёт связанный источник данных с параметрами этого подключения.

*AC.4 — Источник не требует доступа к вкладке «Источники»:*
* *Дано:* аналитик успешно сохранил подключение с включённым DirectQuery;
* *Когда:* пользователь продолжает работу в портале;
* *Тогда:* вкладка {{«Источники»}} остаётся недоступной для аналитика, но связанный источник существует под капотом.

*AC.5 — Доступность источника в произвольном наборе данных:*
* *Дано:* у аналитика есть подключение поддерживаемого типа с включённым DirectQuery;
* *Когда:* аналитик создаёт произвольный набор данных и выбирает источник;
* *Тогда:* в списке доступен автоматически созданный источник, соответствующий этому подключению.

*AC.6 — Выполнение DirectQuery:*
* *Дано:* аналитик выбрал автоматически созданный источник при создании произвольного набора данных;
* *Когда:* пользователь формирует и выполняет запрос набора данных;
* *Тогда:* запрос выполняется напрямую к внешней СУБД через существующий механизм {{datasources}}, без предварительной загрузки данных во внутренний {{ClickHouse}}.

*AC.7 — Сохранение сценария правил загрузки данных:*
* *Дано:* у аналитика есть подключение с включённым DirectQuery;
* *Когда:* аналитик создаёт или редактирует {{«Правило загрузки данных»}} на базе этого подключения;
* *Тогда:* текущий сценарий загрузки данных во внутренний {{ClickHouse}} работает без изменений.

*AC.8 — Синхронизация при редактировании подключения:*
* *Дано:* подключение поддерживаемого типа уже сохранено с включённым DirectQuery и имеет связанный источник;
* *Когда:* аналитик меняет параметры подключения и сохраняет форму;
* *Тогда:* связанный источник обновляется и использует актуальные параметры подключения.

*AC.9 — Сохранение секретов:*
* *Дано:* аналитик редактирует подключение с включённым DirectQuery и не вводит новый пароль;
* *Когда:* пользователь сохраняет форму;
* *Тогда:* существующий пароль не отображается пользователю, не очищается и продолжает использоваться подключением и связанным источником.

*AC.10 — Обновление секретов:*
* *Дано:* аналитик редактирует подключение с включённым DirectQuery и вводит новый пароль;
* *Когда:* пользователь сохраняет форму;
* *Тогда:* новый пароль применяется к подключению и связанному источнику, а старое значение больше не используется для DirectQuery этого подключения.

*AC.11 — Отключение DirectQuery:*
* *Дано:* у подключения включён признак DirectQuery и существует связанный источник;
* *Когда:* аналитик снимает признак DirectQuery и сохраняет подключение;
* *Тогда:* подключение остаётся доступным для {{«Правил загрузки данных»}}, а источник перестаёт отображаться аналитику как доступный для создания новых произвольных наборов данных через DirectQuery от подключений.

*AC.12 — Повторное включение без дублей:*
* *Дано:* пользователь ранее выключил DirectQuery для подключения, у которого был связанный источник;
* *Когда:* пользователь снова включает признак DirectQuery и сохраняет подключение;
* *Тогда:* система переиспользует ранее связанный источник или создаёт новый при его отсутствии, но не создаёт дубли источников при каждом повторном включении.

*AC.13 — Ошибка создания или обновления источника:*
* *Дано:* пользователь сохраняет подключение с включённым DirectQuery;
* *Когда:* связанный источник невозможно создать или обновить из-за ошибки backend, невалидных параметров или недоступности обязательных данных;
* *Тогда:* пользователь получает штатное сообщение об ошибке, введённые данные формы не теряются, а система не фиксирует успешное состояние с включённым DirectQuery и отсутствующим источником.

*AC.14 — Видимость только собственных источников в Cloud Start:*
* *Дано:* в {{Cloud Start}} есть несколько аналитиков, у каждого есть свои подключения с включённым DirectQuery;
* *Когда:* один из аналитиков создаёт произвольный набор данных;
* *Тогда:* он видит только источники, созданные из его собственных DirectQuery-подключений, и не видит источники других аналитиков.

*AC.15 — Ограничение прав аналитика:*
* *Дано:* пользователь имеет роль {{«аналитик»}} в облаке;
* *Когда:* пользователь работает с подключениями и произвольными наборами данных после доработки;
* *Тогда:* он может использовать DirectQuery-источник, созданный из своего подключения, но не получает общий доступ к созданию, редактированию или просмотру вкладки {{«Источники»}}.

*AC.16 — Существующие подключения без регресса:*
* *Дано:* в системе есть подключения, созданные до внедрения признака DirectQuery;
* *Когда:* пользователь открывает или сохраняет такое подключение без включения нового признака;
* *Тогда:* подключение работает по прежней логике, источник под капотом не создаётся, правила загрузки данных не ломаются.

*AC.17 — Существующие источники без регресса:*
* *Дано:* в системе есть источники данных, созданные вручную через вкладку {{«Источники»}};
* *Когда:* внедряется механизм DirectQuery через подключения;
* *Тогда:* существующие источники и произвольные наборы данных продолжают работать по текущей логике и не получают служебную связь с подключениями без явного основания.

*AC.18 — Удаление подключения с зависимостями:*
* *Дано:* у подключения есть связанный DirectQuery-источник, который используется в произвольном наборе данных;
* *Когда:* пользователь пытается удалить подключение;
* *Тогда:* система не должна молча удалить источник и сломать набор данных; применяется согласованный штатный механизм обработки зависимости с понятным сообщением пользователю.

*AC.19 — MySQL и StarRocks не являются обязательными для текущего этапа:*
* *Дано:* в продукте ведутся или планируются отдельные работы по {{MySQL}} и {{StarRocks}};
* *Когда:* реализуется текущая задача DirectQuery для подключений в облаке;
* *Тогда:* {{MySQL}} и {{StarRocks}} не считаются обязательными поддерживаемыми типами, пока их включение в этот сценарий не подтверждено отдельно.".

6) И отдельная постановка для Реализации Backend доработов к рамках внедрения DirectQuery для подключений в Облаке.

h3. Контекст и проблематика.

В {{Modus BI Cloud}} аналитик может создавать подключения к внешним СУБД на вкладке {{«Подключения»}}, но не имеет доступа к вкладке {{«Источники»}}. При этом прямые запросы к внешней БД для произвольных наборов данных сейчас выполняются через объект {{datasources}} (Источники данных).

Для реализации сценария {{DirectQuery}} через вкладку {{«Подключения»}} необходимо, чтобы Фронтенд отправлял единый запрос сохранения подключения с новым признаком DirectQuery, а Бэкенд самостоятельно выполнял дополнительные операции:
* создавал или обновлял связанный источник данных {{datasources}};
* сохранял служебную связь между {{connection}} и {{datasources}};
* синхронизировал параметры источника при изменении подключения;
* проверял зависимости перед выключением DirectQuery или удалением подключения;
* обеспечивал корректную видимость автоматически созданного источника в сценарии произвольного набора данных.

Целевое решение сохраняет две сущности: {{connection}} и {{datasources}}. Объединение этих сущностей или создание только источника вместо подключения не входит в рамки данной задачи.

----
h3. Цель задачи.

*Требуется:*
# Реализовать Бэкенд-обработку признака DirectQuery в сценариях создания, обновления, чтения и удаления {{connection}}.
# При активном признаке DirectQuery автоматически создавать и поддерживать связанный {{datasources}} на основании параметров подключения.
# Обеспечить устойчивую служебную связь между подключением и источником, чтобы исключить дубли и несогласованные состояния.
# Защитить зависимые произвольные наборы данных от скрытого удаления или поломки при выключении DirectQuery и удалении подключения.
# Сохранить текущие сценарии {{«Правил загрузки данных»}}, ручных источников данных и существующих произвольных наборов данных без регресса.

_Пользовательская история:_
Как аналитик в {{Modus BI Cloud}}, я хочу включить DirectQuery при сохранении подключения, чтобы система автоматически подготовила источник для произвольных наборов данных без доступа к вкладке {{«Источники»}}.

----
h3. 1. Описание текущего поведения.

h4. 1.1. Создание и обновление подключений.

Сейчас Бэкенд сохраняет объект {{connection}} по данным формы подключения. Подключение используется для сценариев загрузки данных через {{«Правила загрузки данных»}} и не создаёт связанный источник данных {{datasources}} для прямых запросов.

Для подключения не хранится пользовательское состояние признака DirectQuery, нет служебной связи с источником данных и нет Бэкенд-логики синхронизации параметров подключения с источником.

---
h4. 1.2. Создание источников данных.

Объект {{datasources}} создаётся и редактируется через существующие механизмы раздела {{«Источники»}}. Аналитик в облачном контуре не имеет доступа к этой вкладке и не может самостоятельно создать источник для DirectQuery.

Произвольные наборы данных используют существующие источники данных. Если источник не создан, аналитик не может использовать подключение как источник прямого запроса к внешней СУБД.

---
h4. 1.3. Зависимости.

Произвольный набор данных может ссылаться на {{datasources}}, а визуализации могут использовать такой набор данных. При удалении или скрытом изменении источника есть риск сломать цепочку:
{{connection}} → {{datasources}} → {{datasets}} → визуализации.

----
h3. 2. Описание целевого поведения.

h4. 2.1. Единый Бэкенд-сценарий сохранения подключения.

Фронтенд передаёт признак DirectQuery в том же запросе, которым создаётся или обновляется подключение. Отдельные запросы {{datasources.create}} или {{datasources.update}} для автоматически создаваемого источника со стороны Фронтенда не выполняются.

Бэкенд должен обрабатывать признак DirectQuery как часть сценария сохранения {{connection}}:
* если признак выключен, подключение сохраняется по текущей логике без создания источника;
* если признак включён для поддерживаемого типа СУБД, Бэкенд сохраняет {{connection}}, создаёт или обновляет связанный {{datasources}} и сохраняет связь между ними;
* если тип подключения не поддерживает DirectQuery, Бэкенд не должен создавать источник и должен вернуть ошибку при попытке сохранить активный признак DirectQuery;
* после успешного ответа не должно оставаться состояния, где DirectQuery включён, а связанный источник не создан, не связан или недоступен для выбора в произвольном наборе данных.

---
h4. 2.2. Поддерживаемые типы подключений.

В рамках первой реализации Бэкенд должен разрешать DirectQuery только для подключений:
* {{ClickHouse}};
* {{PostgreSQL}} / {{Postgres}};
* {{Vertica}};
* {{MS SQL Server}}.

Для {{Excel}}, {{Google Sheets}}, {{1С}} и других неподдерживаемых типов Бэкенд должен отклонять попытку сохранения подключения с активным признаком DirectQuery, даже если Фронтенд ошибочно передал такой признак.

---
h4. 2.3. Создание связанного источника.

При создании нового подключения с активным DirectQuery Бэкенд должен:
# проверить права пользователя на создание подключения;
# проверить, что тип подключения входит в список поддерживаемых для DirectQuery;
# создать {{connection}} по текущим правилам;
# создать {{datasources}} на основании параметров этого подключения;
# заполнить минимально необходимые поля источника для работы прямых SQL-запросов;
# сохранить служебную связь между созданным подключением и источником;
# вернуть успешный ответ только после успешного сохранения обеих сущностей и связи между ними.

Источник должен создаваться как обычный объект {{datasources}}, совместимый с текущим механизмом произвольных наборов данных, но с дополнительными служебными признаками автоматического происхождения от подключения.

---
h4. 2.4. Обновление подключения и синхронизация источника.

При обновлении подключения Бэкенд должен сначала получить текущее состояние подключения и связанного источника.

Если DirectQuery остаётся включённым, Бэкенд должен синхронизировать со связанным источником параметры, которые используются для прямого подключения к внешней СУБД:
* наименование, если источник управляется подключением;
* тип СУБД / драйвер;
* host;
* порт;
* база данных;
* схема, если применимо для выбранного типа СУБД;
* пользователь;
* пароль, если пользователь передал новое значение;
* другие параметры соединения, которые используются источником данных.

Если обновить источник невозможно, Бэкенд должен вернуть ошибку сохранения подключения и не фиксировать несогласованное состояние.

---
h4. 2.5. Включение DirectQuery для существующего подключения.

Если пользователь открывает существующее подключение поддерживаемого типа, включает DirectQuery и сохраняет форму, Бэкенд должен создать связанный источник на основании текущих параметров подключения.

Если ранее для этого подключения уже существовал автоматически созданный источник, Бэкенд должен переиспользовать его, если это допустимо по текущему состоянию, либо создать новый источник без появления дублей.

---
h4. 2.6. Выключение DirectQuery.

Если пользователь снимает признак DirectQuery у подключения, для которого есть связанный источник, Бэкенд должен проверить наличие зависимых произвольных наборов данных.

Целевое поведение:
* если зависимых произвольных наборов данных нет, Бэкенд сохраняет DirectQuery как выключенный и удаляет связанный источник либо переводит его в неактивное/скрытое служебное состояние по выбранной модели хранения;
* если зависимые произвольные наборы данных есть, Бэкенд запрещает сохранение нового состояния и возвращает понятное сообщение о причине блокировки;
* автоматическое удаление произвольных наборов данных или визуализаций при сохранении подключения не выполняется.

---
h4. 2.7. Удаление подключения.

При удалении подключения со связанным DirectQuery-источником Бэкенд должен проверить наличие зависимых произвольных наборов данных.

Целевое поведение:
* если зависимостей нет, Бэкенд удаляет подключение и связанный автоматически созданный источник либо переводит источник в неактивное/скрытое служебное состояние;
* если зависимые произвольные наборы данных есть, Бэкенд запрещает удаление подключения и возвращает понятное сообщение о причине блокировки;
* источники, наборы данных и визуализации не должны удаляться скрыто.

---
h4. 2.8. Доступность источника для произвольных наборов данных.

Автоматически созданный источник должен быть доступен аналитику в сценарии создания произвольного набора данных, но не должен открывать аналитику доступ к вкладке {{«Источники»}}.

Для {{Modus BI Cloud Start}}:
* аналитик должен видеть только собственные автоматически созданные DirectQuery-источники;
* источники других аналитиков не должны отображаться;
* администратор работает с такими источниками по текущим правилам своей роли.

----
h3. 3. Требования к реализации.

h4. 3.1. API и контракт сохранения подключения.

Точные команды API необходимо подтвердить по текущей реализации. Логически доработка затрагивает объект {{connection}} и сценарии {{create}}, {{update}}, {{get}}, {{list}}, {{delete}} или их текущие аналоги.

В payload создания и обновления подключения должен поддерживаться новый признак включения DirectQuery. Условное имя признака в постановке — {{direct_query_enabled}}; итоговое техническое имя необходимо согласовать с Бэкенд-разработкой.

Бэкенд должен:
* принимать признак DirectQuery в том же запросе, где передаются параметры подключения;
* возвращать сохранённое состояние признака DirectQuery в ответах чтения подключения;
* валидировать признак на Бэкенде независимо от Фронтенд-логики отображения чекбокса;
* не требовать от Фронтенда отдельного payload для {{datasources}};
* возвращать понятные ошибки для неподдерживаемого типа подключения, ошибки создания/обновления источника, отсутствия прав и наличия зависимых наборов данных.

---
h4. 3.2. Логическая модель хранения.

В постановке используются условные имена полей для фиксации смысла. Итоговые имена и физическое место хранения должны быть определены разработкой с учётом текущей модели {{connection}}, {{datasources}} и метаданных портала.

|| Логическое поле / признак || Рекомендуемое место || Назначение ||
| {{direct_query_enabled}} | {{connection}} | Пользовательское состояние признака DirectQuery у подключения. |
| {{direct_query_datasource_id}} | {{connection}} или отдельная связующая структура | Идентификатор связанного автоматически созданного источника. Нужен для синхронизации и предотвращения дублей. |
| {{direct_query_source_status}} | {{connection}}, {{datasources}} или связующая структура | Состояние связанного источника: активен, неактивен/скрыт, удалён. |
| {{created_from_connection_id}} | {{datasources}} или связующая структура | Обратная связь источника с подключением, из которого он создан. |
| {{auto_created_from_connection}} | {{datasources}} | Признак, что источник создан автоматически, а не вручную через вкладку {{«Источники»}}. |
| Владелец / область видимости | {{connection}} и {{datasources}} | Контроль видимости источника в {{Cloud Start}} и в сценарии произвольного набора данных. |
| {{direct_query_supported}} | вычисляемый Бэкенд-признак | Признак, что текущий тип подключения поддерживает DirectQuery. Может возвращаться в {{get}}/{{list}} для Фронтенда, но Бэкенд всё равно должен валидировать тип при сохранении. |
| {{has_dependent_datasets}} | вычисляемый или кэшируемый Бэкенд-признак | Информация для интерфейса о наличии зависимых произвольных наборов данных. Не должен быть единственным источником истины при блокирующих проверках. |

Зависимости {{datasets}} → {{datasources}} должны проверяться по фактическим связям в системе. Если Бэкенд решит кэшировать признак наличия зависимостей, он должен обновляться при создании, изменении и удалении произвольных наборов данных.

---
h4. 3.3. Правила формирования источника данных.

Связанный {{datasources}} должен формироваться из параметров {{connection}} по правилам выбранной СУБД.

Минимальная логическая карта соответствия:
|| Параметр подключения || Параметр источника || Примечание ||
| Наименование подключения | Наименование источника | По умолчанию должно позволять пользователю сопоставить источник с подключением. |
| Тип подключения / драйвер | Тип источника / драйвер | Должен соответствовать поддерживаемому типу СУБД. |
| Host / сервер | Host / сервер источника | Используется для прямого подключения к БД. |
| Порт | Порт источника | Если порт не указан и для типа СУБД есть штатное значение по умолчанию, Бэкенд применяет текущую продуктовую логику. |
| База данных | База данных источника | Передаётся по правилам конкретного драйвера. |
| Схема | Схема источника | Применяется только для СУБД, где схема используется. |
| Пользователь | Пользователь источника | Не должен возвращаться вместе с секретами. |
| Пароль / секрет | Секрет источника | При отсутствии нового значения сохраняется текущее секретное значение. |

Если для {{datasources}} есть технически обязательные поля, которые не вводятся аналитиком в форме подключения, Бэкенд должен заполнить их штатными значениями по умолчанию. Такие поля не должны становиться обязательными для Фронтенда в этом сценарии.

---
h4. 3.4. Секреты.

Бэкенд не должен возвращать пароль, токены и другие секреты в открытом виде.

При обновлении подключения:
* если новый пароль не передан, существующее секретное значение должно сохраниться и для {{connection}}, и для связанного {{datasources}};
* если пользователь передал новый пароль, Бэкенд должен обновить секрет и в подключении, и в связанном источнике;
* пустое значение из формы не должно затирать существующий секрет, если оно означает «пароль не изменялся».

---
h4. 3.5. Права и доступность.

Бэкенд должен проверять права пользователя на создание, обновление и удаление подключения по текущей модели ролей.

Аналитик не должен получать:
* доступ к вкладке {{«Источники»}};
* право редактировать автоматически созданный источник напрямую, если такое право не предусмотрено текущей ролевой моделью.
** Автоматическое создание и обновление источника допустимо только как часть сохранения подключения, доступного текущему пользователю.

---
h4. 3.6. Консистентность операций.

Операции с подключением и связанным источником должны быть консистентны с пользовательской точки зрения.

Бэкенд должен исключить состояния:
* DirectQuery включён, но связанный источник не создан;
* DirectQuery включён, но связь {{connection}} → {{datasources}} не сохранена;
* DirectQuery включён, но источник создан с устаревшими параметрами подключения после успешного обновления;
* выключение DirectQuery сохранено, хотя есть зависимые произвольные наборы данных;
* удаление подключения выполнено, хотя связанный источник используется произвольными наборами данных.

Допустимый технический механизм определяется разработкой: транзакция, компенсационное действие, откат признака DirectQuery или иной штатный способ сохранения целостности.

---
h4. 3.7. Обратная совместимость.

* Существующие подключения без признака DirectQuery должны открываться и сохраняться по текущей логике.
* Для существующих подключений DirectQuery должен считаться выключенным, если нет сохранённой связи с автоматически созданным источником.
* Существующие источники, созданные вручную через вкладку {{«Источники»}}, не должны получать связь с подключением автоматически.
* Существующие произвольные наборы данных должны продолжить работать с текущими источниками.
* Сценарий {{«Правил загрузки данных»}} не должен измениться из-за появления DirectQuery-признака у подключения.
* Генерация SQL для произвольных наборов данных должна использовать существующий механизм {{datasources}}, без отдельной ветки SQL-генерации специально для {{connection}}.

----
h3. 4. Пограничные сценарии.

* *Новое подключение без DirectQuery:* Бэкенд сохраняет только {{connection}}, источник не создаётся.
* *Новое подключение с DirectQuery:* Бэкенд сохраняет {{connection}}, создаёт {{datasources}}, сохраняет связь и возвращает успешный ответ только после успешного завершения всех действий.
* *Неподдерживаемый тип подключения:* Бэкенд отклоняет сохранение активного DirectQuery и не создаёт источник.
* *Включение DirectQuery у существующего подключения:* Бэкенд создаёт связанный источник на основании текущих параметров подключения.
* *Повторное включение DirectQuery:* Бэкенд не создаёт дубли источников, а переиспользует существующую связь или создаёт новый источник только при отсутствии пригодного связанного объекта.
* *Изменение параметров подключения:* Бэкенд обновляет связанный источник теми параметрами, которые используются для подключения.
* *Пароль не изменялся:* Бэкенд не очищает секрет ни в подключении, ни в источнике.
* *Пароль изменён:* Бэкенд обновляет секрет и для подключения, и для связанного источника.
* *Ошибка создания источника:* Бэкенд возвращает ошибку и не сохраняет успешное состояние DirectQuery без источника.
* *Ошибка обновления источника:* Бэкенд возвращает ошибку и не фиксирует несинхронизированное состояние.
* *Выключение DirectQuery без зависимых наборов:* Бэкенд выключает признак и удаляет/скрывает источник по выбранной модели хранения.
* *Выключение DirectQuery с зависимыми наборами:* Бэкенд блокирует сохранение и возвращает причину.
* *Удаление подключения без зависимостей:* Бэкенд удаляет подключение и связанный источник либо переводит источник в неактивное/скрытое состояние.
* *Удаление подключения с зависимыми наборами:* Бэкенд блокирует удаление и возвращает причину.
* *Cloud Start и несколько аналитиков:* аналитик видит только собственные DirectQuery-источники.
* *Ручной источник администратора:* источник, созданный вручную, не должен стать связанным с подключением без явной служебной связи.

----
h3. 5. Не входит в рамки задачи.

* изменение ролевой модели {{Modus BI Cloud}};
* открытие вкладки {{«Источники»}} для аналитиков;
* объединение {{connection}} и {{datasources}} в одну сущность;
* сценарий создания только источника данных вместо пары {{connection}} + {{datasources}};
* реализация нового движка DirectQuery или новой SQL-генерации;
* поддержка DirectQuery для {{Excel}}, {{Google Sheets}}, {{1С}} и других неподдерживаемых источников;
* обязательное включение {{MySQL}} и {{StarRocks}} в текущий этап;
* миграция существующих ручных источников в источники, созданные из подключений;
* реализация модели совместной видимости объектов для {{Cloud Teams}} / {{Workspace}}.

----
h3. 6. Предположения.

* Параметров формы {{«Подключения»}} достаточно для создания минимально настроенного источника данных для поддерживаемых СУБД.
* Бэкенд может определить зависимости произвольных наборов данных от источника по существующим связям {{datasets}} → {{datasources}}.

----
h3. 7. Открытые вопросы.

* Нужно согласовать точные технические имена новых полей и место хранения связи: в метаданных {{«Подключений»}}, в метаданных {{«Источников»}} или в отдельной связующей структуре.
* Нужно выбрать физическую модель обработки связанного источника при выключении DirectQuery или удалении подключения без зависимостей: удаление {{«Источников»}} или перевод в неактивное/скрытое служебное состояние.
* Нужно решить, нужно ли возвращать Фронтенду вычисляемый признак {{has_dependent_datasets}} / список зависимостей при чтении подключения, или достаточно проверки в момент сохранения и удаления.
* Нужно уточнить, должен ли администратор видеть отдельный признак автоматического происхождения источника в списке {{«Источники»}}.

----
h3. 8. Критерии приёмки (AC).

*AC.1 — Бэкенд принимает признак DirectQuery в запросе сохранения подключения:*
* *Дано:* Фронтенд сохраняет новое или существующее подключение;
* *Когда:* в payload передан признак DirectQuery;
* *Тогда:* Бэкенд обрабатывает этот признак как часть операции {{connection}} и не требует отдельного запроса на создание {{datasources}}.

*AC.2 — Создание подключения без DirectQuery:*
* *Дано:* пользователь создаёт подключение поддерживаемого типа без включения DirectQuery;
* *Когда:* Бэкенд обрабатывает запрос сохранения;
* *Тогда:* создаётся только {{connection}}, связанный источник данных не создаётся.

*AC.3 — Создание подключения с DirectQuery:*
* *Дано:* пользователь создаёт подключение поддерживаемого типа и включает DirectQuery;
* *Когда:* Бэкенд успешно обрабатывает запрос;
* *Тогда:* создаются {{connection}} и связанный {{datasources}}, между ними сохраняется служебная связь.

*AC.4 — Запрет DirectQuery для неподдерживаемого типа:*
* *Дано:* в запросе сохранения подключения типа {{Excel}}, {{Google Sheets}}, {{1С}} или другого неподдерживаемого типа передан активный DirectQuery;
* *Когда:* Бэкенд валидирует запрос;
* *Тогда:* Бэкенд возвращает ошибку и не создаёт связанный источник.

*AC.5 — Чтение состояния подключения:*
* *Дано:* подключение сохранено с включённым или выключенным DirectQuery;
* *Когда:* Фронтенд запрашивает подключение через {{get}}/{{list}} или текущий аналог;
* *Тогда:* Бэкенд возвращает сохранённое состояние признака DirectQuery и данные, необходимые для отображения формы.

*AC.6 — Синхронизация при обновлении подключения:*
* *Дано:* подключение имеет активный DirectQuery и связанный источник;
* *Когда:* пользователь меняет host, порт, базу, схему, пользователя или другой параметр соединения и сохраняет подключение;
* *Тогда:* Бэкенд обновляет соответствующие параметры связанного источника.

*AC.7 — Сохранение секрета без изменения:*
* *Дано:* подключение имеет активный DirectQuery и сохранённый пароль;
* *Когда:* пользователь сохраняет форму без ввода нового пароля;
* *Тогда:* Бэкенд не очищает секрет и сохраняет его для подключения и связанного источника.

*AC.8 — Обновление секрета:*
* *Дано:* подключение имеет активный DirectQuery;
* *Когда:* пользователь передаёт новый пароль при сохранении;
* *Тогда:* Бэкенд обновляет секрет и для {{connection}}, и для связанного {{datasources}}.

*AC.9 — Повторное включение без дублей:*
* *Дано:* для подключения ранее создавался DirectQuery-источник;
* *Когда:* пользователь повторно включает DirectQuery;
* *Тогда:* Бэкенд переиспользует существующую связь или создаёт новый источник только при отсутствии пригодного связанного источника; дубли не создаются.

*AC.10 — Выключение DirectQuery без зависимостей:*
* *Дано:* у подключения активен DirectQuery, но связанный источник не используется произвольными наборами данных;
* *Когда:* пользователь выключает DirectQuery и сохраняет подключение;
* *Тогда:* Бэкенд сохраняет признак выключенным и удаляет/скрывает связанный источник по выбранной модели хранения.

*AC.11 — Запрет выключения DirectQuery при зависимостях:*
* *Дано:* связанный источник используется хотя бы одним произвольным набором данных;
* *Когда:* пользователь выключает DirectQuery и сохраняет подключение;
* *Тогда:* Бэкенд запрещает сохранение нового состояния, возвращает понятную причину блокировки и не изменяет активную связь.

*AC.12 — Удаление подключения без зависимостей:*
* *Дано:* подключение имеет связанный DirectQuery-источник без зависимых произвольных наборов данных;
* *Когда:* пользователь удаляет подключение;
* *Тогда:* Бэкенд удаляет подключение и удаляет/скрывает связанный источник по выбранной модели хранения.

*AC.13 — Запрет удаления подключения при зависимостях:*
* *Дано:* связанный DirectQuery-источник используется произвольным набором данных;
* *Когда:* пользователь удаляет подключение;
* *Тогда:* Бэкенд запрещает удаление и возвращает понятную причину блокировки; источник и наборы данных не удаляются автоматически.

*AC.14 — Видимость источника в Cloud Start:*
* *Дано:* у нескольких аналитиков есть подключения с активным DirectQuery;
* *Когда:* один аналитик создаёт произвольный набор данных и запрашивает список доступных источников;
* *Тогда:* Бэкенд возвращает только источники, доступные этому аналитику по текущей модели видимости.

*AC.15 — Ручные источники без регресса:*
* *Дано:* в системе есть источники, созданные вручную через вкладку {{«Источники»}};
* *Когда:* внедряется механизм DirectQuery через подключения;
* *Тогда:* ручные источники не получают служебную связь с подключениями и продолжают работать по текущей логике.

*AC.16 — Консистентность при ошибке источника:*
* *Дано:* Бэкенд сохраняет подключение с активным DirectQuery;
* *Когда:* связанный источник невозможно создать или обновить;
* *Тогда:* Бэкенд возвращает ошибку и не фиксирует успешное состояние, при котором DirectQuery включён без корректного связанного источника.
