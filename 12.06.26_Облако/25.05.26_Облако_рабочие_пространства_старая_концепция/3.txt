Как работает существующая система Modus BI и как она встраивается в постановку
Что уже есть: связка «Источник → Набор → Дашборд»
Владимир Кудрин во время обсуждения указал на ключевое: система маршрутизации к ClickHouse в Modus BI уже частично существует, она просто оформлена иначе, чем описывал Вадим.

В текущей архитектуре уже есть справочник источников данных (Data Sources). Каждый источник — это запись в PostgreSQL, которая содержит хост, порт и имя базы данных конкретного инстанса ClickHouse, к которому нужно подключаться. Источник привязан к пользователю.
Цепочка работает так:
Пользователь
  → Набор данных (Dataset)
      → связан с Источником данных (Data Source)
          → Источник содержит: host, port, database → ClickHouse

Когда пользователь открывает дашборд, система не ищет ClickHouse по какому-то абстрактному workspace_id — она идёт по цепочке: дашборд использует набор данных, набор данных уже знает свой источник, источник уже содержит все реквизиты подключения к нужному инстансу ClickHouse. Маршрутизация уже встроена в метаданные через саму структуру объектов.

Именно поэтому Кудрин сказал: «Вот эта связка у нас уже есть — и тут дополнительно чем помогает workspace_id, куда он встраивается, не очень понятно».

Как это меняется с введением Workspace
С введением Workspace существующая логика не ломается, а расширяется. 

Шаг 1. Регистрация — создание всего контура изоляции.
Когда новая организация регистрируется на портале, система одной транзакцией автоматически выполняет цепочку действий.

В PostgreSQL создаётся:

* Запись в таблице public.workspaces — сам факт существования организации, её название, дата создания,

* Запись в public.users — первый пользователь с ролью {{Owner}} (привязанный к workspace_id) - может рассылать приглашения (invitations) другим пользователям, назначать им роли (в том числе админов - {{Workspace Admin}}, которые сами имеют привелегии приглашать и назначать админов(но не удалять админов)), а также владелец ({{Owner}}) может удалять пользователей (в том числе админов {{Workspace Admin}}).

* Запись в public.workspace_routing — маппинг: этот workspace_id → конкретный инстанс ClickHouse (хост + порт + имя базы данных ws_<workspace_id>)

* Применяются RLS-политики для нового workspace_id — PostgreSQL теперь автоматически фильтрует все запросы по этому полю.

** RLS — это нативная, встроенная фича самого PostgreSQL. Когда RLS включён на таблице, PostgreSQL переписывает план каждого SQL-запроса перед его выполнением — автоматически добавляет условие фильтрации из политики в WHERE-клозу. Это происходит до того, как запрос достигает исполнителя. Программист не обязан писать WHERE workspace_id = ? — СУБД сделает это сама.

В ClickHouse создаётся база данных - имя базы данных ws_<workspace_id>. Далее в этой базе данных будут создаваться таблицы под данные организации.

Шаг 2. Что хранится в PostgreSQL — единый мозг системы
PostgreSQL — единственное хранилище метаданных для всех организаций одновременно. Все таблицы находятся в одной схеме public, но каждая строка несёт поле workspace_id. RLS-политики PostgreSQL автоматически добавляют фильтр WHERE workspace_id = current_workspace_id() к каждому запросу — прикладной код этого не видит и не управляет этим вручную.

Вот что хранится в метаданных:

Таблица	Что содержит
Таблица	Что содержит
workspaces	Список всех организаций, их названия, статус
users	Пользователи, их роли, workspace_id, email
workspace_routing	workspace_id → хост, порт, имя БД ClickHouse
data_sources	Источники данных (ClickHouse, Excel, Google Sheets и др.), реквизиты подключения, workspace_id
datasets	Наборы данных, SQL/конфигурация, ссылка на data_source_id
dashboards	Дашборды, их структура, ссылки на наборы данных
invitations	Активные приглашения с токеном, email, workspace_id
Именно здесь замыкается логика, которую описал Кудрин: таблица data_sources уже содержит хост и порт ClickHouse. При создании workspace в неё автоматически добавляется запись «встроенного» источника — облачного хранилища этой организации. Источник связан с workspace_id, и все наборы данных этого workspace будут использовать именно его.

Шаг 3. Авторизация и установка контекста сессии
Пользователь входит на портал с email и паролем. BI Core:

Находит пользователя в public.users по email → получает его workspace_id и роль

Формирует JWT-токен, в payload которого записывает workspace_id и user_id

Все последующие запросы к API несут этот токен

При каждом входящем API-запросе бэкенд в первую очередь извлекает workspace_id из токена и устанавливает его как контекст сессии. Это происходит до любой бизнес-логики. Если workspace_id отсутствует — запрос отклоняется с ошибкой (принцип fail loudly из постановки).

Шаг 4. Как бэкенд строит дашборд — полная маршрутизация
Пользователь открывает дашборд. Вот что происходит внутри:

text
1. Запрос: GET /dashboard/42
   └── Из JWT извлекается workspace_id = "a3f7c819-..."

2. PostgreSQL (через RLS):
   SELECT * FROM dashboards WHERE id = 42
   -- RLS автоматически добавляет: AND workspace_id = 'a3f7c819-...'
   -- Если дашборд 42 принадлежит другому workspace → 0 строк → 404

3. Дашборд ссылается на dataset_id = 7
   SELECT * FROM datasets WHERE id = 7
   -- RLS снова фильтрует по workspace_id → получаем конфигурацию набора

4. Dataset ссылается на data_source_id = 3
   SELECT * FROM data_sources WHERE id = 3
   -- Получаем: host='ch-node-1.internal', port=9000, database='ws_a3f7c819-...'

5. Workspace Router:
   -- Проверяет кэш Redis: есть ли routing для workspace_id?
   -- Если нет → читает public.workspace_routing → кэширует в Redis
   -- Результат: ch-node-1.internal:9000 / ws_a3f7c819-...

6. ClickHouse запрос:
   USE ws_a3f7c819-...;
   SELECT ... FROM sales_table WHERE ...
   -- Физически читает только данные этой организации
Данные двух разных организаций никогда не пересекаются — они физически находятся в разных базах данных ClickHouse, а на уровне PostgreSQL ещё и защищены RLS.

Шаг 5. Масштабирование — как добавляются новые инстансы ClickHouse.

Один инстанс ClickHouse обслуживает несколько организаций — каждая в своей базе ws_<id>. Когда число баз на инстансе достигает порогового значения (определяется нагрузочным тестированием), система автоматически:

Поднимает новый инстанс ClickHouse

Создаёт новую базу ws_<new_workspace_id> уже на новом инстансе

Записывает маппинг в public.workspace_routing с указанием нового инстанса

При этом старые организации остаются на старом инстансе — никакой миграции данных не требуется. Каждая новая организация просто получает «адрес» в workspace_routing, и бэкенд по этому адресу ходит за её данными.

Шаг 6. Redis — кэш для производительности.

Таблица workspace_routing небольшая и меняется редко (только при создании нового workspace). Поэтому она целиком кэшируется в Redis. При каждом запросе бэкенд сначала смотрит в Redis — это занимает ~0.1 мс вместо запроса к PostgreSQL. Кэш инвалидируется через CDC-механизм на основе WAL PostgreSQL: при записи новой строки в workspace_routing это событие через WAL попадает в инвалидатор (опционально через Debezium → Kafka), и Redis-запись обновляется.

Итого: что меняется в постановке по сравнению с тем, что было
Существующая система уже умеет маршрутизировать к ClickHouse через цепочку «набор → источник». Новая постановка не переписывает, а надстраивает:

Добавляется сущность Workspace как корневой контейнер

Источник данных, ранее привязанный к пользователю, теперь привязывается к workspace_id — все пользователи организации видят один общий источник

Добавляется таблица workspace_routing как авторитетный справочник «где физически живут данные этого workspace»

Добавляется RLS в PostgreSQL — изоляция метаданных без изменений в прикладном коде

Добавляется логика автоматического шардирования при создании новых workspace (выбор инстанса ClickHouse)

Вся существующая цепочка дашборд→набор→источник→ClickHouse остаётся рабочей, просто источник теперь создаётся автоматически при регистрации и всегда указывает на ws_<workspace_id> нужного инстанса.
