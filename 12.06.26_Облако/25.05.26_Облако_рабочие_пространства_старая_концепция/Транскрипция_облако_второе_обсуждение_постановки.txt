### 00:00 — Вадим Мединцев

Обсуждали. BI Cloud сейчас работает в индивидуальном режиме. Нужно реализовать многопользовательские пространства — workspace для команд и организаций, которые смогут совместно работать с подключениями, наборами данных, дашбордами и так далее. Нужно обеспечить изоляцию, совместный доступ пользователей, экономическую целесообразность облачной платформы для вот как раз таких — для индивидуальных предпринимателей, небольших компаний, которые не могут себе обеспечить покупку полноценного on-premise решения. Пользователи должны иметь возможность работать командой, продукт должен оставаться не очень дорогим в эксплуатации и пригодным для массового подключения клиентов.

При повышенных требованиях к безопасности остаётся наше on-premise решение, а это — дополнительный вариант, если таких требований нет.

Соответственно, основные ключевые ограничения: производительность ClickHouse деградирует при увеличении количества баз данных и таблиц на одном сервере; PostgreSQL при масштабировании на тысячи пользователей при совместной работе с метаданными может приводить к перегрузке по чтению — поэтому было решено ввести прекэширование.

Целевое решение — гибридная двухуровневая архитектура. То есть у нас есть **контур управления** — это бэкенд, единый инстанс, реализующий паттерн Application-level Tenant Routing: при каждом входящем запросе определяет активный Workspace ID из контекста сессии и маршрутизует обращение к соответствующей базе данных ClickHouse.

**Метаданные** — это PostgreSQL и Redis, также единый инстанс, где будут храниться метаданные и общие таблицы для всех workspace. Изоляция через RLS по Workspace ID — политики применяются автоматически, не требуют изменений в прикладном SQL-коде.

Для снижения нагрузки вводится прекэширование метаданных. Кэш обновляется через механизм на основе WAL-журнала. Тут же можно подумать об использовании **Debezium** — это дополнительный инструмент для обеспечения валидации и регуляции кэша, он тоже использует WAL-журнал. Его можно подключить к Kafka-стримам или Redis-стримам. Можно и без них реализовать, но тут поднимается вопрос: хотим ли мы дополнительно вводить Redis и Kafka — вообще полный комплект.

**Дополнительный контур — контур данных.** Аналитические данные хранятся в ClickHouse. Database-per-Workspace: для каждого нового workspace в назначенном инстансе ClickHouse автоматически создаётся отдельная база данных с именем `ws_{workspace_id}`. Один инстанс ClickHouse обслуживает группу workspace (подробнее — в п. 4.3). При достижении порогового значения числа баз данных в инстансе автоматически поднимается новый инстанс ClickHouse, и последующие workspace создаются в нём.

Тут есть открытые вопросы. Стоит определить, сколько баз данных и workspace может вытянуть один инстанс без деградации по производительности. Надо ли ориентироваться только на количество workspace, или же считать по таблицам — потому что если в одном workspace будет миллион таблиц, много таких workspace не вытянет, а если в каждом по одной таблице — их можно и побольше. То есть механизмы тут ещё надо уточнить.

Маппинг хранится в таблице по Workspace ID — хост и порт инстанса ClickHouse определяются по нему. Бэкенд обращается к ней для определения точки маршрутизации. Из минусов: необходима разработка механизма этого роутера на бэкенде для определения инстанса ClickHouse по Workspace ID; при горизонтальном росте инстансов усложняется их оркестрация. Но здесь либо потребуется вообще изменение подхода…
