# Достаточность и достоверность требований

## Источники и границы

Разделяй четыре вида утверждений: подтверждённый факт, вывод из фактов, предположение и предложение. Требования пользователя определяют целевое поведение; исходный код подтверждает текущее. Связанные постановки важны для контекста, но не распространяют свой объём на новую задачу автоматически. Обсуждавшийся вариант не является принятым решением.

Для существенного технического утверждения сохраняй источник: путь, символ и строку, когда доступны, Git SHA и при необходимости хеш файла. При незакоммиченных изменениях одного SHA недостаточно. Не утверждай актуальность Wiki только по её дате: сравни версию и соответствующие исходники. Отсутствие находки в ограниченном поиске не доказывает отсутствие механизма.

Последние явно заданные пользователем требования определяют целевое поведение. Если пользователь предупредил, что реализация находится в другой ветке, отсутствие её в доступном checkout не отменяет требования и само по себе не требует подтверждения пользователя. Описывай такой материал как заявленное требование или контракт, сохраняя отличие от проверенного кода. Недоступность стенда или Jira-ссылки отмечай как границу проверки; запрашивай доступ или версию сборки только если без них нельзя определить обязательное поведение по имеющимся материалам.

Не придумывай API, payload, роли, SQL, поля, метаданные и архитектурные решения. Не навязывай способ реализации, если достаточно наблюдаемого результата. Секреты не показывай. Неподтверждённые положения отмечай `[ПРЕДПОЛОЖЕНИЕ]`, необходимость проверки — `[УТОЧНИТЬ У ...]`; существенные развилки — в «Открытых вопросах».

## Связность постановки

- Объясни, кто сталкивается с проблемой, где, что происходит сейчас, что требуется и почему. Для бага нужны воспроизводимые шаги, окружение, ожидаемый и фактический результаты; недостающие данные укажи явно.
- Определи рамки и значимые исключения. Разделяй интерфейс, фронтенд, бэкенд, данные, API, SQL, права и совместимость по применимости. Не добавляй каждую область формально.
- Для правила нужны условие, действие, результат и применимые исключения. Не смешивай существование объекта, его выбор, доступность, активность, сохранённость и участие в запросе.
- Проследи жизненный цикл затронутых объектов: создание/выбор, использование, сохранение, повторное открытие, изменение, удаление зависимости, ошибка и восстановление. Релевантные ветви должны иметь определённое поведение.
- Сопоставь цель ↔ рамки ↔ целевое поведение ↔ требования ↔ ограничения ↔ пограничные сценарии ↔ совместимость ↔ AC. Проверяй слова «всегда», «только», «все», «аналогично», «как сейчас» на скрытые условия.
- Сохраняй точную терминологию: аналитический портал, основной портал, ФВД, виджет, визуализация, набор данных, вычисляемое поле, Мера, полки, фильтр, метаданные. Конкретные названия полок и внутренних сущностей бери из материалов задачи и приватного словаря.

## Сценарии и данные

Проверяй применимость пустых/null значений, пустого результата, отсутствия обязательной настройки, удаления/переименования/изменения типа зависимости, повторных действий, сохранения/отмены, недостатка прав, невалидных метаданных, старых конфигураций, недоступности сервиса/источника и больших данных. Каждый включённый сценарий должен относиться к текущей задаче.

Для UI различай видимость, доступность, выбранное/сохранённое/ошибочное состояние и возможность исправления. Для API сверяй идентификаторы разных уровней, источник каждого значения, обязательные поля, сохранение и вычисление, создание/чтение/изменение и ошибки. Не выводи новый контракт из похожего имени.

Для обработки данных проверяй WHERE/HAVING, агрегацию и GROUP BY, порядок фильтрации, AND/OR, null, типы, alias, выражения, сортировку, дедупликацию и пустой результат, когда они входят в задачу. Не считай правила разных приложений или диалектов одинаковыми без свидетельств. Архивные предметные ориентиры находятся в `.private/knowledge/legacy/domain-checks.md` и требуют проверки по текущим источникам.

Совместимость рассматривай отдельно для создания новых объектов и загрузки уже сохранённых. Новое ограничение и допустимость старой конфигурации могут сосуществовать. Не требуй отдельное сообщение на каждую техническую ошибку без пользы пользовательскому сценарию.

## Критерии приёмки и проверка

Каждое существенное требование должно иметь проверку с предусловиями, данными, действием и однозначным наблюдаемым результатом. Для негативного сценария укажи ожидаемую реакцию и состояние после ошибки. Если существенное требование присутствует, но AC отсутствует, это пробел покрытия, а не отсутствие требования.

AC не вводит новую бизнес-логику. При конфликте требования и AC сравни оба с первичными источниками; если правильный вариант не определён, задай вопрос. Технический способ проверки допустим, только когда он следует из подтверждённого требования. Не превращай стилистическое предпочтение в дефект.

Документ достаточно определён, когда разработчик и тестировщик могут независимо получить одинаковое понимание обязательного результата. Нерешённые блокирующие и существенные вопросы исключают статус согласованной постановки.

## Вопросы и незавершённое исследование

Перед вопросом пользователю проверь конкретные связанные файлы, переопределения, конфигурацию и цепочку вызовов. «Осталось исследовать сериализацию», «не проверен полный список функций» или «текущий Research не подтверждает» — рабочие задачи агента; продолжай чтение доступных источников. Не проси пользователя выполнить такой поиск. Если Git отказывает из-за ownership, для разрешённого чтения конкретного репозитория допустим процессный параметр `git -c safe.directory=/точный/путь ...`; глобальную конфигурацию не меняй, wildcard не используй. При иной недоступности укажи точный неработающий инструмент/файл и используй версии manifest без заявления о собственной проверке Git.

В questions оставляй максимум три существенных вопроса за один подход. Каждый должен содержать неразрешимую по доступным источникам развилку, конфликтующие свидетельства и влияние ответа на требования/AC. Открытый вопрос старой задачи сам по себе не расширяет объём новой: проверь его применимость. Не превращай наблюдение пустого списка в универсальный инвариант для всех конфигураций, если такое требование не принято. Подтверждённой части должно хватать для полезного черновика; вопросы не заменяют аналитическую работу.
