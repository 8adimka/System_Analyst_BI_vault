Внедрение поддержки StarRocks как отдельного типа подключения и SQL-семантики

h3. Контекст и цель.

В рамках расширения возможностей аналитического портала и ETL-контура необходимо реализовать поддержку {*}StarRocks{*} как отдельного типа подключения к источнику данных.

StarRocks использует {*}MySQL wire-протокол{*}, поэтому на транспортном уровне подключение может выполняться через тот же низкоуровневый Go-драйвер, который используется для MySQL. При этом StarRocks не должен обрабатываться платформой как MySQL-источник: это отдельная OLAP-СУБД с колоночным хранением, MPP-архитектурой, собственной SQL-семантикой, типами данных, DDL и особенностями выполнения аналитических запросов.

На уровне пользовательского выбора и метаданных платформы StarRocks должен быть представлен как отдельный тип подключения:

||Параметр||MySQL||StarRocks||
|Тип подключения / {{driver.type}}|{{mysql}}|{{starrocks}}|
|SQL-диалект|{{SQL/MySQL}}|{{SQL/StarRocks}}|
|Порт по умолчанию|{{3306}}|{{9030}}|
|Основной сценарий|OLTP-источник|OLAP-источник для аналитических выборок|

Поддержка StarRocks должна быть реализована как отдельная верхнеуровневая обёртка над транспортом: отдельная регистрация типа подключения, отдельная логика чтения метаданных, отдельный маппинг типов и отдельный построитель SQL-запросов. Нельзя наследовать SQL-диалект MySQL там, где поведение StarRocks отличается.

Минимальная поддерживаемая линейка StarRocks для данной доработки — {*}4.xx{*}. Приёмку необходимо проводить с учётом окружений заказчика:
* Dev — StarRocks {{4.01}};
* Prod — StarRocks {{4.04}}.

----

h3. 1. Рамки задачи.

h4. 1.1. Входит в рамки задачи.

* Добавить StarRocks как отдельный тип источника данных на уровне бэкенда, фронтенда и метаданных.
* Обеспечить подключение к StarRocks через MySQL wire-протокол с портом по умолчанию {{9030}}.
* Реализовать отдельную SQL-семантику {{SQL/StarRocks}} для построения запросов платформы.
* Реализовать чтение схемы, таблиц, представлений и полей StarRocks-источника.
* Реализовать корректное сопоставление типов StarRocks с внутренними типами платформы.
* Обеспечить создание наборов данных на базе StarRocks-источника.
* Обеспечить работу предпросмотра данных, пользовательского SQL-запроса, фильтрации, сортировки, агрегаций, {{GROUP BY}}, {{HAVING}} и вычисляемых полей в рамках поддерживаемых возможностей платформы.
* Обеспечить корректную работу производных полей даты для StarRocks.
* Подключить StarRocks к механизму возможностей СУБД, чтобы интерфейс и бэкенд одинаково ограничивали неподдерживаемые функции.
* Обеспечить контролируемые ошибки для функций, которые для StarRocks на данном этапе не поддерживаются.
* Провести регрессионную проверку MySQL и других существующих источников данных.

h4. 1.2. Не входит в рамки задачи.

* Использование StarRocks как варианта MySQL-источника с {{driver.type = mysql}}.
* Поддержка стандартного RLS для StarRocks.
* Использование StarRocks как хранилища для ФВД и отчётных форм.
* Коррекция данных через механизм ФВД на StarRocks-источнике.
* Импорт файлов Excel в StarRocks через текущий мастер импорта.
* MDX-сценарии для StarRocks.
* Полная поддержка всех нативных возможностей StarRocks: партиционирования, материализованных представлений, Stream Load, специальных моделей таблиц и расширенных административных операций, если они не требуются для базового сценария подключения, чтения данных и построения отчётов.
* Изменение поведения MySQL-источника под особенности StarRocks.

----

h3. 2. Описание текущего поведения.

На текущий момент в платформе реализована поддержка MySQL как отдельного типа источника данных. MySQL-поддержка покрывает подключение, чтение схемы, маппинг типов, генерацию SQL в диалекте MySQL, создание наборов данных, предпросмотр, фильтрацию, агрегации, вычисляемые поля и производные поля даты.

StarRocks технически может принимать подключение по MySQL wire-протоколу, но использование StarRocks через MySQL-тип приводит к некорректному поведению платформы, потому что:
* SQL-запросы генерируются по правилам MySQL, а не StarRocks;
* часть функций и операторов отличается;
* набор типов данных и их представление через {{information_schema}} / wire-протокол отличается;
* DDL и операции создания таблиц отличаются от MySQL;
* большие числовые типы StarRocks могут искажаться при обработке как обычные MySQL-числа;
* отдельные выражения для дат, строк, {{LIKE}} и регулярных выражений требуют StarRocks-специфичной генерации.

Из-за этого StarRocks не должен использоваться в системе как MySQL-источник даже при общем транспортном драйвере.

----

h3. 3. Описание целевого поведения.

После доработки пользователь с правами на работу с источниками данных должен иметь возможность создать отдельный StarRocks-источник в разделе {*}«Источники»{*}, проверить подключение, сохранить источник, создать на его базе набор данных и использовать этот набор данных в отчётах и визуализациях аналитического портала.

Логика целевого поведения:
* в списке типов подключения должен быть доступен отдельный пункт {*}StarRocks{*};
* StarRocks-источник должен сохраняться с отдельным типом {{starrocks}}, а не как {{mysql}};
* порт по умолчанию для нового StarRocks-источника — {{9030}};
* транспортное подключение может использовать общий MySQL wire-драйвер, но SQL-диалект, маппинг типов и план построения запросов должны быть отдельными;
* чтение схемы должно возвращать пользователю доступные таблицы/представления и поля StarRocks;
* пользовательские SQL-запросы и запросы, сгенерированные платформой, должны выполняться в диалекте StarRocks;
* ошибки подключения, прав доступа, SQL-синтаксиса и неподдерживаемых функций должны возвращаться контролируемо и без раскрытия секретов;
* StarRocks не должен появляться в сценариях ФВД, импорта Excel, MDX, стандартного RLS и коррекции данных, если эти сценарии не поддержаны для данного типа источника.

----

h3. 4. Требования к реализации.

h4. 4.1. Фронтенд-часть.

* В разделе {*}«Источники» → «Добавить источник»{*} добавить тип подключения {*}StarRocks{*}.
* StarRocks должен отображаться в группе основных аналитических СУБД рядом с PostgreSQL, ClickHouse, MySQL, MS SQL Server, SQLite и другими основными типами источников в соответствии с принятой сортировкой.
* Для StarRocks должна отображаться стандартная карточка SQL-источника с полями подключения:
  ** {{Тип подключения}};
  ** {{Имя источника}};
  ** {{Отображаемое название}};
  ** {{Хост БД}};
  ** {{Порт}};
  ** {{Имя БД}};
  ** {{Схема БД}};
  ** {{Логин подключения к БД}};
  ** {{Пароль подключения к БД}};
  ** другие обязательные поля, используемые текущей формой подключения для SQL-источников.
* При выборе StarRocks в новой карточке источника порт должен подставляться значением {{9030}}, если пользователь не указал другое значение.
* Кнопка проверки подключения должна работать для StarRocks и отображать пользователю успешный или ошибочный результат в текущем UX-паттерне портала.
* В карточке StarRocks-источника должны быть скрыты или недоступны функции, не поддержанные для данного типа источника:
  ** MDX и MDX-сервер;
  ** ФВД;
  ** отчётные формы;
  ** коррекция данных;
  ** импорт из Excel;
  ** стандартная поддержка RLS и активность RLS;
  ** дополнительные опции, применимые только к другим типам источников.
* Доступность и видимость элементов карточки должны определяться через единый механизм возможностей СУБД, если он используется в платформе для MySQL и других источников.
* В мастере создания набора данных StarRocks-источник должен быть доступен для выбора как источник аналитических данных.
* В конструкторе ФВД StarRocks-источник не должен отображаться как доступное хранилище для создания ФВД-таблицы.
* В мастере импорта Excel StarRocks-источник не должен отображаться как доступный целевой источник.
* В интерфейсе набора данных должны корректно отображаться таблицы, представления, поля, типы и ошибки чтения схемы StarRocks.
* Для наборов данных на StarRocks должны быть доступны пользовательский SQL-запрос, предпросмотр данных, вычисляемые поля, фильтрация и инструмент извлечения частей даты в рамках поддерживаемых возможностей платформы.

h4. 4.2. Бэкенд-часть.

* Зарегистрировать StarRocks как отдельный тип источника данных с техническим типом {{starrocks}}.
* Не смешивать StarRocks и MySQL на уровне бизнес-логики источников: общий транспортный драйвер допустим, но SQL-диалект и маппинг должны выбираться по типу {{starrocks}}.
* Для StarRocks должны быть предусмотрены отдельные реализации/ветки верхнеуровневой логики:
  ** подключение и проверка соединения;
  ** чтение метаданных;
  ** сопоставление типов;
  ** построение SQL-выражений;
  ** построение планов запросов;
  ** обработка результатов запроса.
* В терминах backend-слоёв StarRocks должен быть представлен отдельными реализациями, не сводящимися к условным правкам MySQL-ветки: {{drivers/starrocks}}, {{modeltranslator/starrocks}}, {{planbuilder/starrocks}} или их актуальными аналогами в текущей структуре кода.
* При работе через API должны быть затронуты следующие backend-объекты и сценарии:
  ** {{connection}} — проверка подключения к новому StarRocks-источнику, включая сценарий нового подключения с {{id = 0}}, если он используется текущим API;
  ** {{datasources}} — создание, чтение, обновление и список источников с типом {{starrocks}};
  ** {{datasets}} — создание и использование наборов данных на базе StarRocks-источника;
  ** {{reports}} / {{reportgroup}} — получение данных для отчётов и визуализаций на базе StarRocks-наборов;
  ** {{extraction_rules}} — только в тех сценариях, где текущая платформа использует правила извлечения для чтения StarRocks как внешнего источника.
* Перед обновлением существующего StarRocks-источника бэкенд должен читать текущее состояние через {{get}} / {{list}} и сохранять без изменения параметры, которые пользователь не редактировал.
* Секреты подключения не должны возвращаться в ответах API и не должны попадать в сообщения об ошибках.
* Если пользователь не менял пароль при редактировании источника, сохранение карточки не должно сбрасывать ранее сохранённое рабочее значение.
* Проверка подключения должна корректно обрабатывать:
  ** успешное соединение;
  ** неверный хост;
  ** неверный порт;
  ** неверное имя БД;
  ** неверный логин или пароль;
  ** недоступность StarRocks-кластера;
  ** недостаточные права пользователя БД.
* Для неподдерживаемых операций StarRocks бэкенд должен возвращать контролируемую функциональную ошибку, а не выполнять попытку через MySQL-логику.

h4. 4.3. Чтение схемы и метаданных StarRocks.

* Бэкенд должен получать список доступных баз/схем, таблиц, представлений и полей StarRocks-источника в формате, совместимом с существующим механизмом источников данных.
* Чтение метаданных должно учитывать, что StarRocks может отдавать разные имена типов:
  ** исходные имена типов в {{information_schema}};
  ** имена типов, которые возвращаются через MySQL wire-протокол при чтении результата {{SELECT}}.
* Нельзя строить маппинг только по одному из этих путей, если второй путь используется в платформе для определения структуры результата.
* В структуре полей должны корректно сохраняться:
  ** имя поля;
  ** исходный тип StarRocks;
  ** внутренний тип платформы;
  ** признак {{nullable}}, если доступен;
  ** порядок полей;
  ** признаки ограниченной поддержки, если тип не может быть полноценно использован в платформе.
* Пустая схема, отсутствие таблиц, отсутствие прав на часть таблиц или ошибки чтения отдельных объектов не должны приводить к аварийному завершению backend-сервиса.
* Если StarRocks-таблица содержит типы, которые платформа не поддерживает для пользовательских сценариев, такие поля должны быть либо явно помечены как неподдерживаемые, либо безопасно представлены поддерживаемым типом без искажения данных.

h4. 4.4. Сопоставление типов данных.

* Необходимо реализовать StarRocks-специфичный маппинг типов во внутренние типы платформы.
* В рамках маппинга должны быть проверены как минимум следующие группы типов:
  ** строковые: {{CHAR}}, {{VARCHAR}}, {{STRING}};
  ** числовые: {{TINYINT}}, {{SMALLINT}}, {{INT}}, {{BIGINT}}, {{LARGEINT}}, {{DECIMAL}}, {{FLOAT}}, {{DOUBLE}};
  ** логический тип: {{BOOLEAN}};
  ** дата и время: {{DATE}}, {{DATETIME}};
  ** полуструктурированные и сложные типы: {{JSON}}, {{ARRAY}}, {{MAP}}, {{STRUCT}};
  ** специальные аналитические типы: {{BITMAP}}, {{HLL}};
  ** бинарные/байтовые представления, если они возвращаются драйвером.
* Значения {{LARGEINT}} и другие значения, не помещающиеся в безопасный числовой диапазон платформы/JSON, не должны приводиться к {{float64}} с потерей точности.
* Если точное числовое представление для {{LARGEINT}} в платформе невозможно, значение должно возвращаться в безопасном представлении без искажения, например как строка, а поведение должно быть единообразно отражено в метаданных поля.
* {{DECIMAL}} / {{NUMERIC}} должны возвращаться без потери точности в пределах поддерживаемой платформой точности.
* Наличие сложных типов {{ARRAY}}, {{MAP}}, {{STRUCT}}, {{JSON}}, {{BITMAP}}, {{HLL}} в таблице не должно блокировать работу с остальными поддерживаемыми полями.
* Для каждого ограниченно поддерживаемого типа должно быть определено предсказуемое поведение: отображение, исключение из доступных полей, представление строкой или контролируемая ошибка при попытке использовать поле в неподдерживаемом сценарии.

h4. 4.5. SQL-семантика и генерация запросов.

* Для StarRocks должен использоваться отдельный диалект {{SQL/StarRocks}}.
* Генератор SQL не должен подставлять MySQL-специфичные функции и конструкции, если они не поддерживаются StarRocks.
* Должны корректно формироваться запросы для:
  ** предпросмотра таблицы;
  ** пользовательского SQL-запроса в наборе данных;
  ** выборки полей;
  ** фильтрации;
  ** комбинированной фильтрации с {{AND}} / {{OR}};
  ** фильтрации по {{NULL}} и пустым значениям;
  ** сортировки;
  ** агрегаций;
  ** {{GROUP BY}};
  ** {{HAVING}} для условий по агрегированным значениям;
  ** вычисляемых полей;
  ** производных полей даты.
* Идентификаторы таблиц и полей должны экранироваться синтаксически корректно для StarRocks.
* При приведении значения к строке для строковых операций должен использоваться синтаксис, совместимый со StarRocks, например {{CAST(... AS STRING)}} там, где это требуется диалектом.
* Для регулярных выражений должна использоваться поддерживаемая StarRocks форма, например оператор {{REGEXP}}, а не MySQL-функция {{regexp_like}}, если она не поддерживается целевой версией StarRocks.
* Для поиска по строкам через {{LIKE}} необходимо учитывать StarRocks-семантику экранирования:
  ** символы {{\}}, {{%}} и {{_}} должны экранироваться так, чтобы поиск спецсимволов выполнялся корректно;
  ** не должна добавляться неподдерживаемая StarRocks клауза {{ESCAPE}}, если она приводит к ошибке SQL.
* Для производных полей даты нельзя полагаться на локаль StarRocks для русских названий месяцев и дней недели.
* Если интерфейс ожидает русские названия месяцев или дней недели, генерация SQL должна обеспечивать эти значения явно, например через выражения с {{CASE}} по номеру месяца/дня недели.
* Ошибки SQL StarRocks должны возвращаться пользователю как контролируемые ошибки с сохранением введённого SQL-запроса и без повреждения набора данных.

h4. 4.6. DDL и операции записи.

* Если в существующем сценарии платформы для источников данных выполняется создание таблицы-приёмника в StarRocks, нельзя использовать MySQL-DDL вида {{ENGINE=InnoDB}}, inline {{PRIMARY KEY}}, {{INDEX}}, {{FOREIGN KEY}}, {{AUTO_INCREMENT}} без проверки совместимости.
* Для создания таблиц StarRocks должна использоваться отдельная DDL-логика с учётом модели ключей и распределения данных StarRocks.
* Если операции создания таблиц, массовой загрузки или записи данных в StarRocks не входят в текущий релизный объём, API должен возвращать контролируемую ошибку о неподдерживаемой операции для типа {{starrocks}}.
* Не допускается тихое выполнение операций записи через MySQL-ветку, если это приводит к ошибочному DDL, неэффективной загрузке или неконсистентным данным.
* Построчные операции изменения данных не должны позиционироваться как базовый сценарий StarRocks-источника, если они не поддержаны явно.

h4. 4.7. Возможности источника и ограничения функций.

* Для StarRocks должен быть задан набор возможностей источника, используемый фронтендом и бэкендом.
* В наборе возможностей StarRocks должны быть явно отражены:
  ** доступность проверки подключения;
  ** доступность чтения схемы;
  ** доступность SQL-редактора набора данных;
  ** доступность предпросмотра;
  ** доступность построения отчётов и визуализаций;
  ** доступность фильтрации;
  ** доступность вычисляемых полей;
  ** доступность производных полей даты;
  ** недоступность стандартного RLS;
  ** недоступность ФВД;
  ** недоступность отчётных форм;
  ** недоступность коррекции данных;
  ** недоступность импорта Excel;
  ** недоступность MDX.
* Фронтенд не должен показывать или активировать элементы, которые backend-флаги отмечают как недоступные.
* Бэкенд должен валидировать те же ограничения независимо от состояния фронтенда.
* Прямая подмена payload не должна позволять включить для StarRocks неподдерживаемую функцию.

h4. 4.8. Обратная совместимость.

* Добавление StarRocks не должно изменять поведение MySQL-источников.
* SQL-генерация MySQL не должна получать StarRocks-специфичные правила.
* Существующие источники PostgreSQL, ClickHouse, MS SQL Server, SQLite, Vertica и другие поддержанные источники должны продолжить работать без изменений поведения.
* Существующие наборы данных, отчёты и визуализации на других типах источников не должны требовать миграции из-за добавления StarRocks.
* Если в системе уже были технически созданные источники StarRocks через тип MySQL, автоматическая миграция таких источников в рамках данной задачи не предполагается. Для штатной работы должен создаваться новый источник с типом {{starrocks}}.

* *И:* спецсимволы ищутся как обычные символы, если так задано пользовательским фильтром, а SQL не содержит неподдерживаемой конструкции {{ESCAPE}}, приводящей к ошибке StarRocks.

AC-30 — *Регулярные выражения в StarRocks-диалекте:*
* *Дано:* фильтр или вычисляемое выражение платформы требует проверки строки регулярным выражением в поддерживаемом сценарии.
* *Когда:* бэкенд строит SQL для StarRocks.
* *Тогда:* используется поддерживаемая StarRocks форма регулярного выражения, например оператор {{REGEXP}}.
* *И:* не используется MySQL-функция {{regexp_like}}, если она не поддерживается целевой версией StarRocks.

AC-31 — *Агрегации и группировки:*
* *Дано:* набор данных StarRocks содержит поля, пригодные для группировки и расчёта агрегатов.
* *Когда:* отчёт или предпросмотр запрашивает группировку и агрегаты {{COUNT}}, {{SUM}}, {{AVG}}, {{MIN}}, {{MAX}} в рамках поддерживаемых возможностей платформы.
* *Тогда:* бэкенд формирует корректный SQL с {{GROUP BY}} для StarRocks.
* *И:* результат агрегации соответствует данным в StarRocks.

AC-32 — *Фильтрация по агрегированным значениям:*
* *Дано:* отчёт или запрос к набору данных StarRocks использует фильтр по агрегированному значению.
* *Когда:* выполняется запрос с агрегацией.
* *Тогда:* условие по агрегату формируется в корректной части запроса, включая {{HAVING}}, если это требуется логикой платформы.
* *И:* результат соответствует ожидаемой выборке и не содержит SQL-ошибок из-за размещения агрегатного условия в {{WHERE}}.

AC-33 — *Сортировка результата:*
* *Дано:* набор данных StarRocks содержит поля разных типов.
* *Когда:* отчёт, предпросмотр или запрос данных использует сортировку по строковому, числовому, датовому или вычисляемому полю.
* *Тогда:* бэкенд формирует корректный {{ORDER BY}} для StarRocks.
* *И:* порядок строк в ответе соответствует выбранному направлению сортировки, сортировка не меняет состав строк в выборке.

AC-34 — *Вычисляемые поля:*
* *Дано:* в наборе данных StarRocks создано вычисляемое поле на основе строковых, числовых или датовых полей.
* *Когда:* выполняется предпросмотр набора данных или построение отчёта.
* *Тогда:* выражение вычисляемого поля транслируется в синтаксис StarRocks и рассчитывается на стороне БД.
* *И:* вычисляемое поле доступно в ответе платформы и может использоваться в фильтрации/агрегации, если такое использование поддерживается для аналогичных SQL-источников.

AC-35 — *Ошибка в вычисляемом поле:*
* *Дано:* в наборе данных StarRocks создано вычисляемое поле с некорректным выражением или несовместимыми типами данных.
* *Когда:* выполняется предпросмотр набора данных или построение отчёта.
* *Тогда:* API возвращает контролируемую ошибку выполнения выражения.
* *И:* ошибка не повреждает сохранённый источник и не блокирует работу с другими корректными полями набора данных.

AC-36 — *Извлечение частей даты:*
* *Дано:* набор данных StarRocks содержит поле типа дата/дата-время.
* *Когда:* пользователь создаёт производные поля через инструмент извлечения частей даты.
* *Тогда:* для StarRocks корректно работают варианты, доступные для аналогичного сценария PostgreSQL/MySQL: год, квартал, месяц, неделя, день, день недели, год-квартал, год-месяц, год-неделя, год-день и другие варианты, доступные в UI.
* *И:* значения возвращаются в ожидаемых строковых и числовых форматах.

AC-37 — *Русские названия месяцев и дней недели:*
* *Дано:* пользователь создаёт производные поля даты, которые должны возвращать название месяца, сокращённое название месяца, название дня недели или сокращённое название дня недели.
* *Когда:* выполняется предпросмотр или построение отчёта на StarRocks-наборе данных.
* *Тогда:* значения возвращаются на русском языке в формате, ожидаемом интерфейсом платформы.
* *И:* результат не зависит от отсутствия русской локали в StarRocks.

AC-38 — *Фильтрация и сортировка по производным датовым полям:*
* *Дано:* в наборе данных StarRocks создано производное поле даты, например год, месяц, неделя или год-месяц.
* *Когда:* пользователь применяет фильтр или сортировку по производному датовому полю.
* *Тогда:* бэкенд формирует корректный SQL для StarRocks и возвращает записи только за выбранный период/значение.
* *И:* фильтрация по исходному полю даты и по производному полю не конфликтуют между собой.

AC-39 — *Построение отчёта на StarRocks-наборе данных:*
* *Дано:* создан и сохранён набор данных на базе StarRocks-источника.
* *Когда:* пользователь строит отчёт/визуализацию на основе этого набора данных.
* *Тогда:* портал получает данные из StarRocks-набора без SQL-ошибок.
* *И:* базовые сценарии построения отчётов, фильтрации и отображения данных возвращают ожидаемые значения по подготовленному тестовому набору данных.

AC-40 — *StarRocks недоступен при создании ФВД-таблицы:*
* *Дано:* в системе есть сохранённый StarRocks-источник.
* *Когда:* пользователь открывает конструктор ФВД и выбирает хранилище/источник для создания таблицы ФВД.
* *Тогда:* StarRocks-источник отсутствует в списке доступных хранилищ/источников для ФВД.
* *И:* пользователь не может создать ФВД-таблицу на базе StarRocks-источника.

AC-41 — *StarRocks недоступен в мастере импорта Excel:*
* *Дано:* в системе есть сохранённый StarRocks-источник.
* *Когда:* пользователь открывает сценарий загрузки/импорта файлов Excel в БД.
* *Тогда:* StarRocks-источник недоступен для выбора как целевой источник/хранилище.
* *И:* пользователь не может запустить импорт Excel в StarRocks-источник через текущий механизм платформы.

AC-42 — *Контролируемое поведение операций записи и DDL:*
* *Дано:* через API или интерфейс запускается сценарий, который требует создания таблицы, массовой загрузки или записи данных в StarRocks.
* *Когда:* такой сценарий не поддержан для StarRocks в текущем релизе.
* *Тогда:* система возвращает контролируемую ошибку о неподдерживаемой операции для типа {{starrocks}}.
* *И:* система не пытается выполнить операцию через MySQL-DDL или MySQL-ветку записи.

AC-43 — *StarRocks-специфичный DDL при поддержанной операции создания таблицы:*
* *Дано:* в рамках текущего релизного объёма поддержана операция создания таблицы в StarRocks.
* *Когда:* платформа формирует DDL для StarRocks.
* *Тогда:* используется синтаксис, совместимый со StarRocks, с учётом модели ключей и распределения данных.
* *И:* в запросе не используются MySQL-специфичные конструкции {{ENGINE=InnoDB}}, неподдерживаемые inline {{INDEX}} / {{FOREIGN KEY}} и иные конструкции, приводящие к ошибке StarRocks.

AC-44 — *Поведение при ошибке backend-флагов возможностей:*
* *Дано:* frontend не получил признаки возможностей источника или получил ошибку при их загрузке.
* *Когда:* пользователь открывает форму создания или редактирования StarRocks-источника.
* *Тогда:* интерфейс не показывает пользователю недостоверно доступные функции для StarRocks.
* *И:* неподдерживаемые функции не могут быть включены до получения валидных данных о возможностях источника.

AC-45 — *Регрессия по MySQL:*
* *Дано:* в системе есть существующий MySQL-источник и набор данных на его базе.
* *Когда:* выполняются сценарии подключения, чтения схемы, предпросмотра, фильтрации, агрегации, вычисляемых полей и производных полей даты для MySQL.
* *Тогда:* поведение MySQL соответствует реализованной постановке по MySQL и не получает StarRocks-специфичных правил.
* *И:* MySQL-источник продолжает сохраняться и использоваться с типом {{mysql}}.

AC-46 — *Регрессия по существующим типам источников:*
* *Дано:* в системе есть существующие источники PostgreSQL, ClickHouse, MS SQL Server, SQLite, Vertica или другие поддерживаемые типы.
* *Когда:* выполняются существующие сценарии подключения, чтения схемы, предпросмотра, фильтрации, агрегации и построения отчётов для этих источников.
* *Тогда:* добавление StarRocks не меняет их поведение, маппинг типов, SQL-генерацию и обработку ошибок.

AC-47 — *Проверка прав пользователя в интерфейсе источников:*
* *Дано:* пользователь не имеет прав на создание или редактирование источников данных.
* *Когда:* пользователь открывает раздел «Источники» или карточку существующего StarRocks-источника.
* *Тогда:* действия создания, редактирования, проверки подключения и сохранения ограничены так же, как для других типов источников.
* *И:* добавление StarRocks не создаёт обхода существующей модели прав.

AC-48 — *Достаточность проверки перед релизом:*
* *Дано:* функциональность StarRocks передана на релизную проверку.
* *Когда:* тестировщик выполняет проверку по критериям AC-1 — AC-47.
* *Тогда:* StarRocks можно добавить как отдельный источник, проверить подключение, сохранить, открыть повторно, использовать для создания набора данных, выполнить SQL-запрос, получить предпросмотр, использовать фильтрацию, агрегации, сортировку, вычисляемые поля и производные поля даты.
* *И:* неподдерживаемые сценарии RLS, ФВД, отчётных форм, коррекции данных, MDX, импорта Excel и неподдержанных операций записи недоступны пользователю и не могут быть включены обходным путём через UI/API.

----

h3. 7. Предположения.

* StarRocks используется в рамках данной доработки прежде всего как внешний OLAP-источник для аналитических выборок, наборов данных, отчётов и визуализаций.
* Транспортное подключение может переиспользовать MySQL wire-драйвер, но это не означает переиспользование MySQL-диалекта и MySQL-логики обработки данных.
* Конкретные имена backend-команд и структура capability-флагов должны соответствовать текущей реализации платформы; в постановке зафиксирована требуемая логика, а не новый обязательный API-контракт.

h3. 8. Открытые вопросы.

* Требуется ли в текущем релизном объёме полноценная поддержка записи/загрузки данных в StarRocks, включая StarRocks-специфичный DDL и механизм массовой загрузки, или StarRocks на данном этапе используется только как источник чтения для наборов данных и отчётов?
