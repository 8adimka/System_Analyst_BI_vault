Внедрение поддержки StarRocks как отдельного типа подключения и SQL-семантики

h3. Контекст и цель.

В рамках расширения возможностей аналитического портала и ETL-контура необходимо реализовать поддержку {*}StarRocks{*} как самостоятельного типа подключения к источнику данных.

StarRocks использует MySQL wire-протокол и может подключаться через тот же транспортный Go-драйвер, что и MySQL. При этом StarRocks не является MySQL-источником: это OLAP-СУБД с колоночным хранением, MPP-архитектурой, собственной SQL-семантикой, типами данных, DDL и эксплуатационными сценариями.

Использование StarRocks через уже реализованный тип подключения {{mysql}} приводит к некорректной генерации SQL, ошибкам выполнения запросов, неверному маппингу типов и риску искажения данных. Поэтому требуется зарегистрировать StarRocks в платформе как отдельный тип подключения {{starrocks}}, наравне с PostgreSQL, ClickHouse, MySQL и другими поддерживаемыми источниками.

Цель задачи - обеспечить базовую и безопасную работу аналитического портала с StarRocks-источниками:
# создание и проверка подключения к StarRocks;
# чтение схемы и метаданных StarRocks;
# создание наборов данных на основе StarRocks;
# выполнение предпросмотра, пользовательских SQL-запросов, фильтрации, агрегаций, сортировок, вычисляемых и производных датовых полей;
# генерация SQL в диалекте StarRocks без наследования несовместимой MySQL-семантики;
# сохранение обратной совместимости с уже реализованным MySQL-источником.

----

h3. 1. Рамки задачи.

h4. 1.1. Что входит в задачу.

* Добавить тип подключения {{starrocks}} в backend-реестр поддерживаемых источников.
* Добавить StarRocks в каталог типов подключений в интерфейсе источников данных.
* Использовать для StarRocks отдельную backend-обёртку над транспортным MySQL-протоколом:
** отдельную регистрацию типа источника;
** отдельный SQL-диалект;
** отдельный маппинг типов;
** отдельную логику чтения схемы и выполнения запросов;
** отдельную обработку StarRocks-специфичных ограничений.
* Обеспечить работу базовых сценариев аналитического портала:
** проверка подключения;
** чтение списка таблиц и полей;
** предпросмотр данных;
** создание и повторное открытие набора данных;
** пользовательский SQL-запрос;
** построение отчёта/визуализации;
** фильтрация, сортировка, агрегация, {{GROUP BY}}, {{HAVING}};
** вычисляемые поля;
** извлечение частей даты.
* Реализовать StarRocks-специфичную обработку SQL-конструкций, типов данных и ошибок.
* Не допустить изменения поведения существующего типа подключения {{mysql}}.

h4. 1.2. Что не входит в задачу.

* Реализация StarRocks как разновидности MySQL-источника внутри типа {{mysql}}.
* Включение стандартного RLS для StarRocks, если поддержка RLS не реализована отдельной задачей.
* Использование StarRocks как хранилища ФВД и отчётных форм.
* Импорт Excel-файлов в StarRocks через текущий механизм импорта.
* MDX-сценарии для StarRocks.
* Коррекция данных и пользовательские точечные {{UPDATE}}/{{DELETE}} как штатный сценарий работы с OLAP-источником.
* Полная поддержка всех StarRocks-специфичных аналитических типов и функций, если они не нужны для базовых сценариев набора данных и отчётов.

----

h3. 2. Ключевая логика работы StarRocks в платформе.

h4. 2.1. Разделение транспортного драйвера и типа подключения.

* На уровне пользовательского выбора и метаданных источника StarRocks должен быть самостоятельным типом подключения {{starrocks}}.
* На уровне транспорта допускается использовать общий MySQL wire-протокол и общий транспортный драйвер, если это соответствует текущей backend-архитектуре.
* Совпадение транспортного протокола не должно приводить к использованию MySQL-диалекта, MySQL-маппинга типов или MySQL-DDL для StarRocks.
* Для StarRocks должен использоваться собственный слой обёртки поверх транспорта: {{drivers/starrocks}}, {{modeltranslator/starrocks}}, {{planbuilder/starrocks}} или эквивалентные по смыслу компоненты, принятые в кодовой базе.

h4. 2.2. Отличия StarRocks от MySQL, которые должны учитываться системой.

|| Область || MySQL || StarRocks || Требование для Modus BI ||
| Тип подключения | {{mysql}} | {{starrocks}} | Типы подключений должны быть независимыми. |
| Порт по умолчанию | {{3306}} | {{9030}} | Для StarRocks подставлять порт {{9030}}, если пользователь не указал иной порт. |
| Класс нагрузки | OLTP | OLAP, MPP, аналитические сканы | Не наследовать сценарии точечных транзакционных изменений как базовую модель работы. |
| SQL-диалект | MySQL | StarRocks SQL | Генерировать SQL через отдельный StarRocks-диалект. |
| Типы данных | MySQL-типы | {{LARGEINT}}, {{STRING}}, {{BOOLEAN}}, {{JSON}}, {{ARRAY}}, {{MAP}}, {{STRUCT}}, {{BITMAP}}, {{HLL}} и др. | Реализовать отдельный маппинг и безопасную обработку неподдержанных типов. |
| DDL | {{ENGINE=InnoDB}}, индексы, FK, MySQL-ограничения | Key-модель и {{DISTRIBUTED BY}} | Не использовать MySQL-DDL при создании таблиц в StarRocks. |
| Массовая загрузка | MySQL-механизмы вставки | Stream Load / StarRocks-совместимая загрузка | Не использовать несовместимый MySQL-механизм массовой вставки. |

----

h3. 3. Требования к реализации.

h4. 3.1. Backend-объекты и API.

* Затронутые backend-объекты: {{connection}}, {{datasources}}, {{datasets}}, {{extraction_rules}} и связанные операции построения отчётов/предпросмотра данных.
* Для {{datasources}} должна поддерживаться работа со StarRocks-источником в командах создания, чтения, обновления и получения списка источников.
* Для {{connection}} должна поддерживаться проверка подключения:
** для нового источника с {{object.id = 0}}, если такой сценарий используется текущим API;
** для уже сохранённого StarRocks-источника.
* Для {{datasets}} должна поддерживаться работа с наборами данных на базе StarRocks:
** чтение схемы;
** проверка пользовательского SQL;
** предпросмотр;
** сохранение и повторное открытие;
** выполнение запросов для отчётов и визуализаций.
* Перед обновлением StarRocks-источника backend должен читать текущее состояние источника через существующий механизм {{get}}/{{list}}, чтобы не потерять несвязанные настройки и секреты.
* Секреты подключения не должны возвращаться в ответах API. При редактировании пароль должен изменяться только при явной передаче нового значения через защищённый ввод. Если пароль не менялся, существующее значение должно сохраняться.
* При попытке вызвать неподдержанную для StarRocks функцию API должен возвращать контролируемую функциональную ошибку, а не техническую ошибку сервера.

h4. 3.2. Интерфейс источников данных.

* В разделе {*}«Источники» -> «Добавить источник»{*} в список «Тип подключения» добавить пункт {*}StarRocks{*}.
* StarRocks должен отображаться в группе основных SQL/OLAP-СУБД рядом с PostgreSQL, ClickHouse, MySQL, MS SQL Server, SQLite и другими поддерживаемыми источниками.
* При выборе StarRocks должна отображаться стандартная форма подключения к SQL-источнику:
** тип подключения;
** имя источника;
** отображаемое название;
** хост БД;
** порт;
** имя БД;
** схема БД, если поле используется текущей формой источника;
** логин;
** пароль;
** URL БД и другие обязательные поля текущей формы.
* Для нового StarRocks-источника порт по умолчанию должен быть {{9030}}.
* Кнопка проверки подключения должна работать для StarRocks и отображать пользователю успешный результат или контролируемую ошибку подключения.
* Для StarRocks должны быть скрыты или недоступны функции, которые не поддерживаются в рамках текущего этапа:
** RLS;
** ФВД;
** отчётные формы;
** импорт Excel;
** MDX;
** коррекция данных;
** нерелевантные дополнительные опции.
* Если в платформе реализован общий механизм возможностей СУБД, StarRocks должен быть подключён к нему как отдельный тип источника. Локальные условия только по названию типа подключения не должны дублировать общий механизм без необходимости.

h4. 3.3. Подключение и проверка соединения.

* Система должна устанавливать соединение со StarRocks по параметрам, введённым пользователем.
* Для StarRocks должен использоваться MySQL wire-протокол, но результат соединения должен обрабатываться как подключение типа {{starrocks}}.
* Успешная проверка подключения не должна изменять данные в StarRocks.
* Ошибки хоста, порта, имени БД, логина, пароля, сетевой недоступности, отсутствия прав и ошибок TLS/настроек соединения должны возвращаться в контролируемом виде.
* Текст ошибки не должен раскрывать пароль, токены, полную строку подключения с секретами и другие чувствительные данные.

h4. 3.4. Чтение схемы и метаданных.

* Backend должен читать список доступных схем/таблиц/представлений StarRocks через поддерживаемые StarRocks-метаданные, включая {{information_schema}}, если это соответствует текущей реализации.
* Backend должен возвращать список таблиц и полей в формате, совместимом с существующим механизмом построения наборов данных.
* Порядок полей должен соответствовать порядку, полученному из метаданных StarRocks.
* Для каждого поля должны возвращаться данные, необходимые платформе для построения набора данных: имя, исходный тип StarRocks, внутренний тип платформы, nullable-признак и другие используемые текущей системой атрибуты.
* Необходимо различать:
** исходные имена типов из метаданных StarRocks;
** имена типов, которые возвращаются транспортным драйвером при чтении результата {{SELECT}}.
* Логика обработки результата запроса не должна полагаться только на «родные» имена типов из {{information_schema}}, если по протоколу StarRocks возвращает другое имя типа.
* Для определения признака identity/{{AUTO_INCREMENT}} нельзя полагаться только на поле {{information_schema.COLUMNS.EXTRA}}, так как в StarRocks оно может не содержать ожидаемый признак. Если сценарий платформы требует identity-признак, его нужно определять StarRocks-совместимым способом, например через {{SHOW CREATE TABLE}}.

h4. 3.5. Маппинг типов данных.

* Должен быть реализован отдельный маппинг типов StarRocks во внутренние типы платформы.
* Строковые типы {{CHAR}}, {{VARCHAR}}, {{STRING}} должны обрабатываться как строковые поля платформы.
* Числовые типы {{TINYINT}}, {{SMALLINT}}, {{INT}}, {{BIGINT}}, {{LARGEINT}}, {{DECIMAL}}, {{NUMERIC}}, {{FLOAT}}, {{DOUBLE}} должны обрабатываться без неконтролируемой потери точности.
* Значения {{LARGEINT}} и другие значения, которые не помещаются в безопасный числовой диапазон платформы/JSON-представления, должны возвращаться без искажения. Если сохранение точного числового значения невозможно в числовом типе платформы, значение должно передаваться строкой или через иной утверждённый безопасный механизм.
* Тип {{BOOLEAN}} должен сопоставляться с внутренним логическим или совместимым типом платформы согласно текущей модели типов.
* Типы даты и времени {{DATE}}, {{DATETIME}} и другие поддерживаемые StarRocks-дата/время-типы должны сопоставляться с внутренними датовыми типами платформы.
* Полуструктурированные и аналитические типы {{JSON}}, {{ARRAY}}, {{MAP}}, {{STRUCT}}, {{BITMAP}}, {{HLL}}, а также бинарные типы должны обрабатываться предсказуемо:
** либо сопоставляться с поддерживаемым внутренним типом;
** либо помечаться как ограниченно поддерживаемые/недоступные для пользовательских операций;
** наличие таких полей не должно блокировать работу с остальными поддерживаемыми полями таблицы.

h4. 3.6. SQL-диалект StarRocks.

* Для StarRocks должен использоваться отдельный SQL-диалект {{SQL/StarRocks}} или эквивалентный механизм генерации SQL.
* Генерация SQL для StarRocks должна покрывать:
** предпросмотр данных;
** пользовательский SQL-запрос;
** фильтрацию;
** комбинированные условия {{AND}}/{{OR}};
** сортировку;
** агрегации;
** {{GROUP BY}};
** {{HAVING}} для условий по агрегированным значениям;
** вычисляемые поля;
** производные поля даты.
* Экранирование идентификаторов должно быть корректным для StarRocks и не должно ломать имена таблиц/полей со смешанным регистром, зарезервированными словами и допустимыми спецсимволами.
* Для приведения к строке в StarRocks-выражениях необходимо использовать совместимый синтаксис StarRocks, например {{CAST(... AS STRING)}}, если он требуется для конкретной операции.
* Для регулярных выражений нельзя наследовать MySQL-выражения, которые отсутствуют в StarRocks. Если в StarRocks используется оператор {{REGEXP}}, генератор должен формировать именно StarRocks-совместимое выражение.
* Для {{LIKE}} необходимо учитывать StarRocks-семантику экранирования специальных символов {{%}}, {{_}} и обратного слеша. Генератор не должен добавлять MySQL-специфичную клаузу {{ESCAPE}}, если она не поддерживается StarRocks.
* Ошибки SQL, связанные с неподдержанной функцией или несовместимыми типами, должны возвращаться пользователю как контролируемые ошибки выполнения запроса.

h4. 3.7. Работа с датами и производными датовыми полями.

* Для StarRocks должны работать те же пользовательские сценарии извлечения частей даты, которые доступны для аналогичных SQL-источников:
** год;
** квартал;
** месяц;
** неделя;
** день;
** день недели;
** год-квартал;
** год-месяц;
** год-неделя;
** год-день;
** другие варианты, доступные в текущем UI.
* Если в интерфейсе для производных полей ожидаются русские названия месяцев или дней недели, StarRocks-диалект должен формировать значения независимо от локали БД. Нельзя полагаться на то, что StarRocks вернёт русские названия через {{DATE_FORMAT}} или аналогичные функции.
* Производные поля даты должны быть доступны для предпросмотра, фильтрации, сортировки и построения отчётов в рамках текущих возможностей платформы.

h4. 3.8. Создание таблиц и загрузка данных в StarRocks.

* Если текущий сценарий ETL предполагает создание таблицы-приёмника в подключенной СУБД, для StarRocks должен использоваться StarRocks-совместимый DDL.
* Нельзя использовать MySQL-DDL вида {{ENGINE=InnoDB}}, MySQL-индексы, MySQL-FK и другие конструкции, которые не поддерживаются StarRocks.
* DDL для StarRocks должен учитывать модель ключей и распределение данных, например наличие key-модели и {{DISTRIBUTED BY}}, в формате, поддерживаемом StarRocks.
* Если параметры key-модели, distribution/buckets или replication не могут быть выведены автоматически, система должна использовать согласованные значения по умолчанию или возвращать контролируемую ошибку настройки, а не создавать некорректную таблицу.
* Для массовой загрузки данных нельзя без проверки наследовать MySQL-механизм массовой вставки. Должен использоваться StarRocks-совместимый способ загрузки. Если полноценный Stream Load не входит в текущий этап, ограничение должно быть явно обработано и покрыто ошибкой или описанным резервным сценарием.

h4. 3.9. Права и ограничения доступа.

* Работа со StarRocks-источниками должна использовать существующую модель прав портала для источников данных и наборов данных.
* Добавление StarRocks не должно давать пользователю обход прав на создание, редактирование, проверку подключения, просмотр метаданных или создание наборов данных.
* Ошибки прав пользователя StarRocks на уровне БД должны возвращаться как контролируемые ошибки доступа.

h4. 3.10. Обратная совместимость.

* Реализация StarRocks не должна менять поведение уже реализованного типа {{mysql}}.
* MySQL-источники должны продолжать использовать MySQL-диалект, MySQL-маппинг типов и MySQL-порт по умолчанию {{3306}}.
* Существующие источники PostgreSQL, ClickHouse, MS SQL Server, SQLite и другие поддерживаемые источники не должны менять поведение из-за добавления StarRocks.
* Сохранённые наборы данных и отчёты на существующих источниках должны открываться и выполняться без миграции метаданных, если они не используют StarRocks.

# таблицу с датами и датой-временем из разных месяцев, кварталов, недель и дней недели;
# таблицу с полями {{BOOLEAN}};
# таблицу с полуструктурированными или ограниченно поддерживаемыми типами StarRocks, например {{JSON}}, {{ARRAY}}, {{MAP}}, {{STRUCT}}, {{BITMAP}}, {{HLL}}, если они доступны в тестовом кластере;
# таблицу с именами полей/таблиц, требующими экранирования идентификаторов;
# данные, по которым заранее рассчитан ожидаемый результат фильтрации, агрегаций, {{GROUP BY}}, {{HAVING}}, сортировки, регулярных выражений, {{LIKE}} и производных датовых полей;
# существующие MySQL-источники и источники других типов для регрессионной проверки.

h3. 6. Критерии приёмки (AC).

AC-1 - *Отображение StarRocks в списке типов подключения:*
* *Дано:* пользователь с правами на работу с источниками открывает раздел «Источники» и запускает создание нового источника.
* *Когда:* пользователь раскрывает список «Тип подключения».
* *Тогда:* в списке присутствует пункт StarRocks.
* *И:* добавление StarRocks не удаляет, не переименовывает и не меняет порядок критично важных существующих типов подключений.

AC-2 - *Создание StarRocks-источника:*
* *Дано:* пользователь выбрал тип подключения StarRocks.
* *Когда:* отображается карточка нового источника.
* *Тогда:* пользователю доступны стандартные поля подключения к SQL-источнику.
* *И:* порт по умолчанию заполнен значением {{9030}}, если пользователь не указал иное значение.

AC-3 - *Сохранение типа источника:*
* *Дано:* пользователь заполнил корректные параметры подключения StarRocks.
* *Когда:* пользователь сохраняет источник.
* *Тогда:* источник сохраняется в метаданных как тип {{starrocks}}, а не как {{mysql}}.
* *И:* последующие операции чтения, проверки подключения, чтения схемы и выполнения запросов используют StarRocks-логику.

AC-4 - *Проверка успешного подключения:*
* *Дано:* создан StarRocks-источник с корректным хостом, портом, именем БД, логином и паролем.
* *Когда:* пользователь выполняет проверку подключения.
* *Тогда:* backend устанавливает соединение со StarRocks и возвращает успешный статус проверки.
* *И:* проверка подключения не изменяет данные в StarRocks и не требует предварительного создания набора данных.

AC-5 - *Проверка ошибок подключения:*
* *Дано:* параметры StarRocks-источника содержат ошибку в хосте, порте, имени БД, логине, пароле или источник недоступен по сети.
* *Когда:* пользователь выполняет проверку подключения.
* *Тогда:* API возвращает контролируемую ошибку подключения.
* *И:* пароль, токены и полная строка подключения с секретами не отображаются в тексте ошибки.

AC-6 - *Секреты при сохранении и редактировании источника:*
* *Дано:* StarRocks-источник сохранён и открыт повторно для редактирования.
* *Когда:* пользователь меняет несекретные параметры или сохраняет карточку без изменения пароля.
* *Тогда:* несекретные параметры сохраняются корректно, а пароль не раскрывается в интерфейсе и ответах API.
* *И:* если пароль не менялся, существующее рабочее значение не сбрасывается.

AC-7 - *Чтение списка таблиц и представлений:*
* *Дано:* StarRocks-источник успешно подключён и в доступной схеме есть таблицы/представления.
* *Когда:* платформа запрашивает метаданные источника.
* *Тогда:* backend возвращает список доступных объектов StarRocks в формате, совместимом с мастером набора данных.
* *И:* недоступные по правам объекты не приводят к падению операции чтения всей схемы.

AC-8 - *Чтение списка полей:*
* *Дано:* в StarRocks есть таблица с полями разных типов, nullable-полями и заданным порядком следования.
* *Когда:* платформа запрашивает структуру таблицы.
* *Тогда:* backend возвращает список полей, исходные типы StarRocks, внутренние типы платформы и nullable-признаки.
* *И:* порядок полей соответствует порядку в метаданных StarRocks.

AC-9 - *Пустая схема и отсутствие прав:*
* *Дано:* подключение к StarRocks успешно, но в доступной схеме нет таблиц или у пользователя БД нет прав на чтение таблиц.
* *Когда:* платформа запрашивает список таблиц.
* *Тогда:* API возвращает корректный пустой результат или контролируемую ошибку прав доступа.
* *И:* операция не завершается технической ошибкой сервера.

AC-10 - *Маппинг базовых строковых, числовых и датовых типов:*
* *Дано:* в StarRocks-таблице есть поля типов {{CHAR}}, {{VARCHAR}}, {{STRING}}, {{TINYINT}}, {{SMALLINT}}, {{INT}}, {{BIGINT}}, {{DECIMAL}}, {{FLOAT}}, {{DOUBLE}}, {{DATE}}, {{DATETIME}}.
* *Когда:* backend читает метаданные и выполняет предпросмотр данных.
* *Тогда:* поля сопоставляются с корректными внутренними типами платформы.
* *И:* значения возвращаются без искажения в рамках поддерживаемой точности платформы.

AC-11 - *Безопасная обработка {{LARGEINT}}:*
* *Дано:* в StarRocks-таблице есть поле {{LARGEINT}} со значениями, превышающими безопасный диапазон обычных числовых типов.
* *Когда:* backend выполняет предпросмотр или запрос к набору данных.
* *Тогда:* значение возвращается без потери точности.
* *И:* недопустимо преобразование большого значения в приближённое представление вида экспоненциального {{float64}}, если это искажает исходное значение.

AC-12 - *Обработка типов, отличающихся между схемой и результатом SELECT:*
* *Дано:* StarRocks возвращает в метаданных одно имя типа, а при чтении результата через транспортный драйвер другое имя типа.
* *Когда:* backend выполняет пользовательский {{SELECT}} и строит структуру результата.
* *Тогда:* типы результата классифицируются корректно для платформы.
* *И:* обработка не зависит от веток кода, которые никогда не срабатывают из-за отличий имён типов по протоколу.

AC-13 - *Полуструктурированные и ограниченно поддерживаемые типы:*
* *Дано:* в StarRocks-таблице есть поля {{JSON}}, {{ARRAY}}, {{MAP}}, {{STRUCT}}, {{BITMAP}}, {{HLL}} или бинарные типы.
* *Когда:* backend читает схему и выполняет предпросмотр.
* *Тогда:* такие поля обрабатываются предсказуемо: либо доступны в согласованном внутреннем типе, либо помечены как ограниченно поддерживаемые.
* *И:* наличие таких полей не блокирует работу с остальными поддерживаемыми полями таблицы.

AC-14 - *Предпросмотр таблицы:*
* *Дано:* StarRocks-источник подключён и выбрана таблица с поддерживаемыми полями.
* *Когда:* пользователь запускает предпросмотр данных.
* *Тогда:* backend формирует синтаксически корректный SQL в диалекте StarRocks и возвращает ограниченную выборку данных.
* *И:* пустая таблица возвращается как пустой результат без технической ошибки.

AC-15 - *Пользовательский SQL-запрос:*
* *Дано:* аналитик создаёт набор данных на StarRocks-источнике и вводит корректный SQL-запрос к существующей таблице.
* *Когда:* выполняется проверка/предпросмотр запроса.
* *Тогда:* запрос выполняется на StarRocks, результат возвращается в платформу, а структура результата используется как структура набора данных.
* *И:* поля результата получают корректные имена и внутренние типы.

AC-16 - *Ошибка пользовательского SQL-запроса:*
* *Дано:* аналитик вводит SQL-запрос с синтаксической ошибкой, обращением к несуществующему объекту или нарушением прав доступа.
* *Когда:* выполняется проверка/предпросмотр запроса.
* *Тогда:* API возвращает контролируемую ошибку StarRocks.
* *И:* ошибка не приводит к падению backend-сервиса и не блокирует последующие корректные запросы к тому же источнику.

AC-17 - *Экранирование идентификаторов:*
* *Дано:* в StarRocks есть таблицы или поля с именами, требующими экранирования: смешанный регистр, зарезервированные слова или допустимые спецсимволы.
* *Когда:* платформа строит запросы предпросмотра, фильтрации, сортировки или агрегации.
* *Тогда:* backend формирует корректный SQL для StarRocks.
* *И:* запрос выполняется без ошибок из-за некорректного экранирования идентификаторов.

AC-18 - *Фильтрация по строковым значениям и {{LIKE}}:*
* *Дано:* набор данных StarRocks содержит строковое поле со значениями, включающими кириллицу, латиницу, {{%}}, {{_}}, обратный слеш, пустые строки и {{NULL}}.
* *Когда:* пользователь применяет фильтры точного совпадения, частичного совпадения, пустых значений и {{NULL}}.
* *Тогда:* backend формирует StarRocks-совместимые условия SQL.
* *И:* специальные символы для {{LIKE}} экранируются без использования неподдержанной MySQL-специфичной клаузы {{ESCAPE}}, если она не поддерживается StarRocks.

AC-19 - *Регулярные выражения:*
* *Дано:* в платформе используется фильтр или вычисляемое выражение с регулярным выражением для StarRocks-источника.
* *Когда:* backend формирует SQL.
* *Тогда:* используется StarRocks-совместимый синтаксис регулярных выражений, например оператор {{REGEXP}}, если он применим.
* *И:* не используется MySQL-функция, отсутствующая в StarRocks.

AC-20 - *Фильтрация по числовым и датовым полям:*
* *Дано:* набор данных StarRocks содержит числовые и датовые поля.
* *Когда:* пользователь применяет фильтры по одному или нескольким полям, включая комбинированные условия {{AND}}/{{OR}}, если они поддержаны текущим механизмом платформы.
* *Тогда:* backend формирует корректный SQL для StarRocks.
* *И:* результат соответствует ожидаемой выборке, а пустой результат возвращается как пустой набор данных без технической ошибки.

AC-21 - *Агрегации, {{GROUP BY}} и {{HAVING}}:*
* *Дано:* набор данных StarRocks содержит поля для группировки и расчёта агрегатов.
* *Когда:* отчёт или предпросмотр запрашивает {{COUNT}}, {{SUM}}, {{AVG}}, {{MIN}}, {{MAX}} и фильтр по агрегированному значению.
* *Тогда:* backend формирует корректный SQL для StarRocks с {{GROUP BY}} и {{HAVING}}, если условие относится к агрегату.
* *И:* результат агрегации соответствует заранее рассчитанным значениям тестовых данных.

AC-22 - *Сортировка результата:*
* *Дано:* набор данных StarRocks содержит строковые, числовые, датовые и вычисляемые поля.
* *Когда:* пользователь применяет сортировку по одному или нескольким полям.
* *Тогда:* backend формирует корректный {{ORDER BY}} для StarRocks.
* *И:* сортировка меняет только порядок строк, но не состав выборки.

AC-23 - *Вычисляемые поля:*
* *Дано:* в наборе данных StarRocks создано вычисляемое поле на основе строковых, числовых или датовых полей.
* *Когда:* выполняется предпросмотр набора данных или построение отчёта.
* *Тогда:* выражение вычисляемого поля транслируется в StarRocks-совместимый SQL и рассчитывается на стороне БД.
* *И:* ошибка в выражении возвращается как контролируемая ошибка и не повреждает сохранённый набор данных.

AC-24 - *Производные поля даты:*
* *Дано:* в наборе данных StarRocks есть поле типа дата или дата-время.
* *Когда:* пользователь создаёт производные поля даты: год, квартал, месяц, неделя, день, день недели, год-месяц и другие поддержанные варианты.
* *Тогда:* производные поля создаются и возвращают значения в тех же смысловых форматах, что и для аналогичных SQL-источников.
* *И:* для русских названий месяцев и дней недели результат не зависит от локали StarRocks.

AC-25 - *Фильтрация и сортировка по производным датовым полям:*
* *Дано:* в наборе данных StarRocks создано производное поле даты.
* *Когда:* пользователь применяет фильтр или сортировку по производному полю.
* *Тогда:* backend формирует корректный SQL для StarRocks.
* *И:* фильтрация по исходному полю даты и производному полю не конфликтуют между собой.

AC-26 - *Построение отчёта на StarRocks-наборе данных:*
* *Дано:* создан и сохранён набор данных на базе StarRocks-источника.
* *Когда:* пользователь строит отчёт или визуализацию на основе этого набора данных.
* *Тогда:* портал получает данные из StarRocks без SQL-ошибок.
* *И:* базовые сценарии отображения, фильтрации и агрегации возвращают ожидаемые значения по подготовленному тестовому набору данных.

AC-27 - *Сохранение и повторное открытие набора данных:*
* *Дано:* пользователь настроил набор данных на базе StarRocks-источника и получил корректный предпросмотр.
* *Когда:* пользователь сохраняет набор данных, закрывает его и открывает повторно.
* *Тогда:* связь со StarRocks-источником, SQL-запрос, список полей, типы полей и настройки набора данных сохраняются.
* *И:* повторный предпросмотр выполняется без необходимости пересоздавать источник или набор данных.

AC-28 - *Обновление метаданных после изменения структуры таблицы:*
* *Дано:* набор данных или источник уже использует таблицу StarRocks, после чего в БД добавлено, удалено или переименовано поле.
* *Когда:* платформа повторно запрашивает структуру таблицы или обновляет метаданные.
* *Тогда:* актуальная структура возвращается в рамках существующего механизма обновления метаданных.
* *И:* ошибка из-за удалённого или переименованного поля возвращается контролируемо и не приводит к неконсистентности источника.

AC-29 - *DDL для StarRocks при создании таблицы-приёмника:*
* *Дано:* сценарий ETL создаёт таблицу-приёмник в StarRocks.
* *Когда:* backend формирует DDL.
* *Тогда:* используется StarRocks-совместимый DDL с key-моделью и распределением данных.
* *И:* в SQL отсутствуют MySQL-специфичные конструкции {{ENGINE=InnoDB}}, MySQL-индексы и FK, не поддерживаемые StarRocks.

AC-30 - *Загрузка данных в StarRocks:*
* *Дано:* в рамках поддерживаемого сценария выполняется загрузка данных в StarRocks.
* *Когда:* backend выбирает механизм загрузки.
* *Тогда:* используется StarRocks-совместимый способ загрузки или возвращается контролируемая ошибка о неподдержанном сценарии.
* *И:* система не использует несовместимый MySQL-механизм массовой вставки молча.

AC-31 - *Identity/{{AUTO_INCREMENT}} в метаданных:*
* *Дано:* в StarRocks-таблице есть колонка с признаком identity/{{AUTO_INCREMENT}}, и этот признак требуется платформе для сценариев вставки/обновления.
* *Когда:* backend читает метаданные таблицы.
* *Тогда:* признак определяется StarRocks-совместимым способом.
* *И:* система не полагается только на {{information_schema.COLUMNS.EXTRA}}, если StarRocks не возвращает там нужный признак.

AC-32 - *Недоступность неподдерживаемых функций:*
* *Дано:* для StarRocks в рамках текущего этапа не поддерживаются RLS, ФВД, отчётные формы, импорт Excel, MDX и коррекция данных.
* *Когда:* пользователь открывает карточку StarRocks-источника или связанные мастера.
* *Тогда:* недоступные функции не отображаются или недоступны для выбора.
* *И:* при попытке включить такие функции прямым API-вызовом backend возвращает контролируемую ошибку и не сохраняет неконсистентные метаданные.

AC-33 - *Права пользователя в портале:*
* *Дано:* пользователь не имеет прав на создание или редактирование источников данных.
* *Когда:* пользователь открывает раздел «Источники» или карточку StarRocks-источника.
* *Тогда:* действия создания, редактирования, проверки подключения и сохранения ограничены так же, как для других типов источников.
* *И:* добавление StarRocks не создаёт обхода существующей модели прав.

AC-34 - *Ошибки прав пользователя StarRocks:*
* *Дано:* StarRocks-источник настроен на пользователя БД, который может подключиться, но не имеет прав на чтение части таблиц или выполнение части запросов.
* *Когда:* платформа читает схему, выполняет предпросмотр или пользовательский SQL.
* *Тогда:* API возвращает контролируемую ошибку доступа.
* *И:* backend-сервис не завершается аварийно и не блокирует дальнейшие корректные запросы.

AC-35 - *Обратная совместимость с MySQL:*
* *Дано:* в системе есть существующий MySQL-источник, созданный после реализации поддержки MySQL.
* *Когда:* пользователь проверяет подключение, читает схему, создаёт набор данных, выполняет фильтрацию, агрегации и вычисляемые поля на MySQL-источнике.
* *Тогда:* поведение MySQL не меняется из-за добавления StarRocks.
* *И:* MySQL продолжает использовать тип {{mysql}}, порт по умолчанию {{3306}} и MySQL-диалект.

AC-36 - *Регрессия по существующим типам источников:*
* *Дано:* в системе есть источники PostgreSQL, ClickHouse, MS SQL Server, SQLite или другие ранее поддержанные типы.
* *Когда:* выполняются существующие сценарии подключения, чтения схемы, предпросмотра, фильтрации, агрегации и построения отчётов.
* *Тогда:* добавление StarRocks не меняет их поведение, маппинг типов, SQL-генерацию и обработку ошибок.

AC-37 - *Достаточность проверки перед релизом:*
* *Дано:* реализация поддержки StarRocks передана на приёмку.
* *Когда:* тестировщик выполняет проверку по критериям AC-1 - AC-36.
* *Тогда:* StarRocks можно добавить как источник, проверить подключение, сохранить, открыть повторно, использовать для создания набора данных, выполнить SQL-запрос, получить предпросмотр, построить отчёт, использовать фильтрацию, агрегации, {{HAVING}}, сортировку, вычисляемые и производные датовые поля.
* *И:* ключевые отличия StarRocks от MySQL покрыты тестами, а существующая поддержка MySQL не деградировала.

----

h3. 7. Предположения.

* Транспортное подключение к StarRocks выполняется через MySQL wire-протокол, но тип источника и SQL-семантика в платформе отделены от {{mysql}}.
* Поддержка StarRocks на текущем этапе ориентирована на аналитические сценарии чтения и построения отчётов.
* Полная поддержка StarRocks-специфичных механизмов загрузки, key-моделей, распределения данных и всех расширенных типов может уточняться отдельными задачами, если сценарий выходит за базовое подключение источника и построение наборов данных.
