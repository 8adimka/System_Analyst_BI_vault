Поступила задача написать постановку по внедрению в нашу аналитическую платформу драйвера для работы с релиационными базами данных по протоколу MySQL. На данный момент реализована работа с PostgreSQL.

Новая постановка включает следующие требования:
1) возможность работы с источниками совместимыми по протоколоу MySQL.
2) доступно:
* построение отчетов,
* фильтрация,
* вычисляемые поля.
3) не требуется:
* RLS,
* ФВД,
* Импорт файлов эксель в БД.

Краткая информация по платформе:

"### 1. Архитектура и принципы работы Modus BI

Платформа построена по классической схеме **DW/BI** (Data Warehouse / Business Intelligence) и разделена на два ключевых слоя, которые тесно интегрированы между собой :

*   **Modus ETL (Система управления данными):** Отвечает за подключение к источникам, «сырым» данным (raw data), их очистку, нормализацию и загрузку в хранилище.
*   **Modus BI (Аналитический портал):** Web-интерфейс (SPA) для визуализации, построения отчетов и дашбордов. Работает уже с подготовленными данными из хранилища или кэша.

**Принцип работы:**
1.  **Ingestion:** ETL подключается к источнику (сейчас PostgreSQL, планируется MySQL).
2.  **Processing:** Данные проходят слой нормализации и «ядра» обработки.
3.  **Storage:** Подготовленные данные складываются в слой витрин (Data Marts), часто на высокопроизводительных СУБД вроде **ClickHouse** или **Vertica**.
4.  **Visualization:** BI-портал через SQL-запросы забирает данные из хранилища или кэша и отдает их на фронтенд .

### 2. Технологический стек (Языки и компоненты)

*   **Backend (Серверная часть):** Язык **Go (Golang)**. Именно здесь происходит вся низкоуровневая работа с базами данных, драйверами и выполнение SQL-запросов .
*   **Frontend (Клиентская часть):** **React** (JavaScript/TypeScript). Библиотеки графиков: GoJS, AMCharts, D3 .
*   **ETL Скриптинг:** Платформа поддерживает скрипты на **SQL**, **T-SQL** и **1С** (также анонсирована поддержка **Python**). Это значит, что движок ETL умеет интерпретировать эти языки для трансформации данных .
*   **Метаданные и кэш:** Для хранения настроек отчетов и кэширования используется **PostgreSQL** .

### 3. План внедрения драйвера для MySQL (ETL часть)

Поскольку Modus ETL уже поддерживает MySQL «из коробки» через ODBC  и написан на **Go**, для «внедрения драйвера» не требуется глубокой аналитики технической части. Нам не нужно глубоко описывать техническую часть в нашей постановке, главное бизнесово описать что и как должно работать (опираясь на описание Романа из транскрипции нашего с ним диалога).




Однако, для формализации подключения нового типа источника в архитектуру я опишу шаги внедрения:

#### Шаг 1. Выбор типа коннектора
У вас есть два пути, которые нужно описать в постановке:
1.  **Нативный драйвер (Предпочтительно):** Go имеет отличную экосистему драйверов для MySQL (например, `go-sql-driver/mysql`). Поскольку бэкенд написан на Go, интеграция этого драйвера даст максимальную производительность.
2.  **ODBC (Универсальный):** В документации указано, что Modus поддерживает «любые SQL через ODBC» . Этот способ проще с точки зрения кодинга (использовать существующий ODBC-мост), но может быть медленнее нативных решений.

**Рекомендация для постановки:** *"Реализовать слой абстракции для поддержки MySQL через нативный Go-драйвер для обеспечения максимальной скорости передачи данных в ETL-конвейере"*.

#### Шаг 2. Адаптация модуля получения данных (Reader)
Сейчас есть модуль для PostgreSQL. Необходимо создать параллельный модуль для MySQL. В постановке укажите, что нужно унифицировать:
*   **Типы данных:** Создать маппер (таблицу соответствия) типов MySQL (`TINYINT`, `DATETIME`, `BLOB` и т.д.) во внутренние типы платформы Modus (аналогично тому, как это сделано для Postgres).
*   **Метаданные:** Научиться читать схему БД MySQL (Information Schema), чтобы пользователь видел таблицы и поля в интерфейсе выбора источника .

#### Шаг 3. Адаптация ETL-конвейера (Трансформация)
Поскольку **вычисляемые поля** и **фильтрация** должны работать, ETL-движок должен корректно генерировать SQL-диалект.
*   **Задача:** Доравить модуль `SQL Dialect` для MySQL.
*   **Пример различий:** В PostgreSQL ограничение строк `LIMIT 10`, в MySQL то же самое. Но функции работы со строками или датами различаются (`CONCAT` vs `||`). Нужно, чтобы при построении отчета движок платформы генерировал правильный синтаксис для MySQL.

#### Шаг 4. Регистрация в BI-портале
После того как ETL научился читать MySQL, нужно дать возможность аналитику выбрать этот источник при создании **Набора данных (DataSet)** - этот этап мы подробно обсудили в разговоре в Романом (в транскрипции)." - это информация справочного характера и может быть не точна.

Информация из транскрипции - приоритетнее для реализации постановки.

С учётом этих требований и информации о нашей платформе Modus BI, а также информации полученной из транскрипции (с подробным описание как должен работать пользовательский интерфейс, какие пункты должны быть скрыты и так далее), как опытный системный аналитик с большим стажем составь грамотную, понятную и талантливо-написанную постановку для разработчиков для реализацию запрошенной функциональности. Опиши бизнесовые требования (что нужно) подробно, понятно и однозначно, а вот технические требования (как это сделать) опиши более кратко и без лишних подробностей, чтобы было понятно в общих чертах, но мы избежали излишних деталей (чтобы разработчик сам разобрался как это сделать, так как ему виднее и он точно знает как устроена система), но мы должны направить разработчика на путь корректной реализации нашей постановкой. В итоговую постановку включи все необходимые разделы, включая "Критерии приёмки (AC)" и прочие необходимые разделы, чтобы постановка была полной, однозначной и достаточной. Используй при написании постановки разметку в стиле совместимом с Jira.
