# Почему StarRocks вынесен отдельно от MySQL

## Контекст решения

В ModusBi подключение к внешней СУБД задаётся типом драйвера в метаданных (`driver.type`). StarRocks общается по **MySQL wire-протоколу** (тот же `go-sql-driver/mysql`, порт 9030), поэтому есть соблазн переиспользовать драйвер и диалект MySQL, но **совместимость протокола ≠ совместимость SQL-семантики**: StarRocks — OLAP-движок с другим SQL, типами, DDL и поведением. 

В рамках проекта принято решение **зарегистрировать StarRocks как отдельный тип подключения** (`starrocks`), независимо от `mysql` (при этом используется тот же драйвер):


|                   | MySQL       | StarRocks       |
| ----------------- | ----------- | --------------- |
| `driver.type`     | `mysql`     | `starrocks`     |
| SQL-диалект       | `SQL/MySQL` | `SQL/StarRocks` |
| Порт по умолчанию | 3306        | 9030            |



Ниже — обоснование на уровне продукта и примеры конкретных кейсов, где общий с MySQL код даёт неверный результат или вообще не выполняется. Факты по StarRocks проверены на живом кластере **4.1.1**.

Формат кейса: **что делает унаследованный от MySQL код** → **что на самом деле в StarRocks (факт)** → **чем это плохо** → **как решает отделение**.

> Кейсы 1–8 — содержательные расхождения (их обойти нельзя, нужна своя логика).
---

## Обоснование разделения (уровень продукта)

### 1. Совместимость протокола ≠ совместимость СУБД

Одинаковый DSN создаёт ложное впечатление взаимозаменяемости. На практике это разные продукты:


| Критерий          | MySQL                                 | StarRocks                               |
| ----------------- | ------------------------------------- | --------------------------------------- |
| Класс нагрузки    | OLTP — транзакции, точечные изменения | OLAP — аналитика, сканы больших объёмов |
| Модель хранения   | Строковая (InnoDB)                    | Колоночная, MPP (Frontend + Backend)    |
| Типичный сценарий | Операционные системы, справочники     | Витрины, факты, агрегаты DWH            |


Пользователь должен явно указывать **какую СУБД** он подключает, а не «что-то похожее на MySQL».

### 2. Разный SQL при похожем синтаксисе

Часть конструкций выглядит одинаково (`SELECT`, `INSERT`, ``имя``, `LIMIT`), но эквивалентные операции требуют **разного SQL**. ModusBi генерирует запросы автоматически; один диалект для обеих СУБД неизбежно приведёт к ошибкам.

### 3. Разные типы данных и модели таблиц

StarRocks имеет аналитические типы (`LARGEINT`, `ARRAY`, `MAP`, `BITMAP`, `HLL`) и модели ключей (`DUPLICATE KEY`, `AGGREGATE KEY`, …), которых нет в MySQL. ETL, анализатор и построитель запросов должны знать целевую СУБД.

### 4. Разные эксплуатационные ожидания

MySQL — частые `UPDATE`/`DELETE`, внешние ключи, транзакционная целостность. StarRocks — пакетная загрузка, партиционирование, материализованные представления; построчные обновления — антипаттерн.

### 5. Независимое развитие поддержки

Отдельный тип `starrocks` позволяет задавать свой порт и подпись в каталоге драйверов, выбирать диалект `SQL/StarRocks` и добавлять StarRocks-специфичное поведение, не затрагивая MySQL. Общий тип `mysql` блокировал бы это: любое изменение «под StarRocks» рисковало бы сломать MySQL.

## Кейсы расхождений (проверено на StarRocks 4.1.1)


### Кейс 1 — Разный набор функций: нет `regexp_like` (как пример)

- **Унаследованный код:** для проверки по regexp в MySQL есть функция `regexp_like(str, pat)`.
- **Факт StarRocks:** функции `regexp_like` **нет** — используется оператор `str REGEXP pat` (и `regexp_extract`).
- **Чем плохо:** сгенерированное выражение с `regexp_like` → `No matching function`.
- **Отделение:** свой набор функций/операторов StarRocks в построителе выражений.

---

### Кейс 2 — Большие числа (`LARGEINT`): тихая потеря точности

- **Унаследованный код:** числа из БД сериализуются как у MySQL — большие значения проходят через `[]byte → float64`.
- **Факт StarRocks:** есть тип `LARGEINT` (128-битный, в MySQL такого нет). Через драйвер значение
`170141183460469231731687303715884105727` ушло в JSON как `**1.7e+38`** (испорчено). Обычный знаковый `BIGINT`
(помещается в int64) — сохраняется верно.
- **Чем плохо:** данные молча искажаются на каждой строке — это потеря данных, а не косметика.
- **Отделение:** StarRocks-осведомлённая выдача: большие/нечисловые `[]byte` отдавать строкой, не приводить к `float64`.

---

### Кейс 3 — Имена типов «по проводу» отличаются от ожидаемых

- **Унаследованный код:** тип колонки определяется по «родным» именам StarRocks из `information_schema`
(`largeint`, `array`, `map`, `struct`, `string`, `bigint unsigned`).
- **Факт StarRocks:** при обычном `SELECT` драйвер видит **другое** имя — то, что StarRocks отдаёт по MySQL-протоколу:
`LARGEINT/JSON/ARRAY/MAP/STRUCT → CHAR`, `DECIMAL → DECIMAL`, `VARBINARY → BLOB` (проверено через `DatabaseTypeName()`).
- **Чем плохо:** ветки кода под «родные» имена на чтении **никогда не срабатывают** (мёртвый код), а юнит-тесты их
проверяют → ложная уверенность, что чтение типов корректно.
- **Отделение:** различать пути «схема» (родные имена из `information_schema`) и «чтение SELECT» (имена по протоколу).

---

### Кейс 4 — DDL таблицы-приёмника совершенно другой

- **Унаследованный код:** `querytemplate` отдаёт MySQL-DDL: `ENGINE=InnoDB`, инлайн `PRIMARY KEY`, вторичные `INDEX`,
`FOREIGN KEY`, `AUTO_INCREMENT`.
- **Факт StarRocks:** такой DDL → **syntax error**. StarRocks обязателен формат с моделью ключа и распределением.
- **Чем плохо:** таблицу-приёмник на общем DDL **невозможно создать**.
- **Отделение:** свой шаблон DDL StarRocks.
  ```sql
  -- MySQL DDL → на StarRocks syntax error:
  CREATE TABLE t (id INT AUTO_INCREMENT, v VARCHAR(20), PRIMARY KEY(id), INDEX idx(v)) ENGINE=InnoDB;
  -- DDL StarRocks:
  CREATE TABLE t (id INT NOT NULL, v VARCHAR(20)) DUPLICATE KEY(id)
    DISTRIBUTED BY HASH(id) BUCKETS 1 PROPERTIES('replication_num'='1');
  ```

---

### Кейс 5 — Массовая загрузка: нужен Stream Load

- **Унаследованный код:** способ bulk-вставки берётся от MySQL (у StarRocks-обёртки его фактически нет).
- **Факт StarRocks:** массовая загрузка — через **Stream Load** (HTTP-эндпоинт), обычный `INSERT` работает, но для
больших объёмов неэффективен.
- **Чем плохо:** на общем коде эффективной заливки нет.
- **Отделение:** свой механизм загрузки (multi-row `INSERT` как минимум, Stream Load как цель).

---

### Кейс 6 — Определение identity (AUTO_INCREMENT) работает иначе

- **Унаследованный код:** identity-колонка ищется по подстроке `AUTO_INCREMENT` в `information_schema.COLUMNS.EXTRA`
(как в MySQL).
- **Факт StarRocks:** поле `EXTRA` у AUTO_INCREMENT-колонки **пустое**; признак виден только в `SHOW CREATE TABLE`.
- **Чем плохо:** identity-колонка не распознаётся (важно для форм и генерации вставок).
- **Отделение:** определять identity через `SHOW CREATE TABLE`.

---

### Кейс 7 — Локаль дат: нет русских названий месяцев/дней

- **Унаследованный код:** выражения календаря `DATE_FORMAT(#field#,'%M'/'%b'/'%a')`, `DAYNAME(...)` (в MySQL зависят
от настройки `lc_time_names`).
- **Факт StarRocks:** локализации имён нет — всегда английский: `September / Sep / Friday / Fri`.
- **Чем плохо:** в справочниках вместо «Сентябрь/Пятница» окажется «September/Friday».
- **Отделение:** StarRocks-выражения с явным `CASE` по `MONTH()/WEEKDAY()` для русских названий.

---

### Кейс 8 — Экранирование в LIKE: бэкслэш по умолчанию, без `ESCAPE`

- **Унаследованный код:** чтобы искать `%`/`_` как обычные символы, в MySQL можно добавить `... ESCAPE '\'`.
- **Факт StarRocks:** `\` — escape **по умолчанию** (`'a%b' LIKE 'a\%b'`→1, `'axb' LIKE 'a\%b'`→0), а явная клауза
`... ESCAPE '!'` → **syntax error**.
- **Чем плохо:** «правильный по MySQL» фикс с `ESCAPE` **уронит** запрос на StarRocks.
- **Отделение:** экранировать `\`/`%`/`_` бэкслэшем **без** клаузы `ESCAPE`.

## Дополнительные различия (справочно)

### Типы данных


| Возможность         | MySQL               | StarRocks                        |
| ------------------- | ------------------- | -------------------------------- |
| Большие целые       | `BIGINT` (до 2⁶³−1) | `LARGEINT` (до 2¹²⁸−1)           |
| Строки              | `VARCHAR`, `TEXT`   | `VARCHAR`, `STRING`              |
| Логический тип      | обычно `TINYINT(1)` | нативный `BOOLEAN`               |
| Вложенные структуры | `JSON`              | `JSON`, `ARRAY`, `MAP`, `STRUCT` |
| Аналитические типы  | —                   | `BITMAP`, `HLL`                  |


### Прочее

- **Приведение типов в LIKE:** MySQL — `CAST(... AS CHAR)`, StarRocks — `CAST(... AS STRING)` (см. кейс 8).
- **Транзакции:** MySQL InnoDB — полноценные транзакции; StarRocks — append и пакетные загрузки.

## Вывод

Совпадает только транспортный протокол (**MySQL wire protocol**). По всем остальным аспектам — SQL-семантика, типы данных, DDL, механизмы загрузки данных, работа с метаданными и встроенные функции — существуют значимые расхождения. Эти различия проявляются **штатно**, а не только в редких edge-кейсах. Поэтому для полноценной поддержки StarRocks кейсы 1–8 требуют отдельной, специализированной логики.

Разделение типов подключения `mysql` и `starrocks` в ModusBi обусловлено **не технической возможностью** использовать один и тот же Go-драйвер, а фундаментально разной природой двух СУБД и конкретными проблемами, которые возникают при попытке применять MySQL-ориентированный код к StarRocks. Выделение самостоятельного типа подключения `starrocks` делает это различие явным и предотвращает скрытые ошибки.

Часть выявленных расхождений в текущей реализации задачи напрямую не влияет, однако их игнорирование существенно усложнит дальнейшее развитие и поддержку работы как с MySQL, так и со StarRocks.

### Архитектурное решение

StarRocks вынесен в **полностью отдельную реализацию** (не через условные ветки, а как независимый модуль):

- Собственный драйвер: `drivers/starrocks`
- Собственный транслятор моделей: `modeltranslator/starrocks`
- Собственный построитель планов: `planbuilder/starrocks`

На уровне реестров, констант и интерфейсов StarRocks изначально рассматривается как независимая сущность:

- `constant.DrvStarRocks` → `starrocks.New(...)`
- `Dialects().StarRocks()` (и аналогичные методы) во всех необходимых слоях

Такое разделение делает код более прозрачным, безопасным и расширяемым.
