# Материал для оценки работ команды аналитической системы

Источник: последняя редакция требований `ФТ.docx`.

Цель материала: дать команде разработки аналитической системы понятные границы оценки по проекту цифрового надзора, не включая в нашу оценку работы смежной команды.

## 1. Контекст

В рамках проекта развивается аналитическая система Россельхознадзора для поддержки процессов цифрового надзора.

В требованиях описан общий контур:

- цифровые индикаторы рисков;
- сценарные ИИ-модели;
- сервис сбора доказательной базы;
- расчет объемов подконтрольной продукции и потенциального НДС;
- сервис категоризации объектов;
- интерфейсы инспектора;
- интеграция через ИВИС для передачи видов сведений СМЭВ;
- отчеты, журналы, статусы, справочники.

Для оценки команды аналитической системы нужно отделить наш объем от смежного.

## 2. Участники и зоны ответственности

| Участник | Зона ответственности |
|---|---|
| Команда аналитической системы | Интерфейсы, карточки, пользовательские сценарии, статусы, журналы, справочники для интерфейсов, интеграция через ИВИС, отображение результатов смежных сервисов |
| Смежная команда | ИИ-модели, сервис доказательной базы, расчет объемов продукции и потенциального НДС |
| Заказчик | Нормативная позиция, исходные данные, согласование макетов и справочников, сведения по ИВИС/СМЭВ, приемка решений |

Сервис категоризации объектов пока не распределен. Его нужно оценивать отдельно, в нескольких вариантах.

## 3. Базовое допущение для оценки

Команда аналитической системы оценивает не весь объем ТЗ, а только свой контур:

- пользовательские интерфейсы;
- карточки и статусы;
- обработку решений инспектора;
- взаимодействие с сервисами смежной команды;
- подготовку XML/пакетов для ИВИС;
- прием и отображение статусов ИВИС;
- журналирование и историю действий;
- справочники, необходимые для интерфейсов и отправки сведений.

ИИ-модели, сервис доказательной базы и НДС-блок не входят в базовую оценку нашей команды как разработка расчетных сервисов. Они учитываются только как внешние зависимости.

## 4. Что нужно оценить нашей команде

### 4.1. Карточка сработавшего цифрового индикатора

Оценить интерфейсы и логику карточки:

- просмотр сработавшего индикатора;
- отображение хозяйствующего субъекта, ИНН, площадки, объекта контроля;
- отображение источников данных;
- отображение нормы, факта, отклонения, основания срабатывания;
- список отслеживаемых фактов и операций;
- детализация по каждому факту;
- отображение потенциально нарушенных требований;
- отображение результата проверки инспектора;
- отображение статуса доказательной базы;
- отображение статуса отправки через ИВИС;
- история действий по карточке.

### 4.2. Решение инспектора по карточке

Оценить пользовательский сценарий принятия решения:

- подтвердить срабатывание;
- отклонить срабатывание;
- вернуть карточку на уточнение;
- выбрать нормативное основание;
- выбрать пункт НПА или обязательное требование;
- указать позицию инспектора;
- приложить или выбрать материалы, если это остается в интерфейсе аналитической системы;
- сформировать действие для последующей отправки через ИВИС.

Важно: кнопка в интерфейсе должна отражать итоговое действие пользователя. Не нужно считать, что всегда формируется только “протокол”. Для разных решений может быть разный результат: подтверждение, возврат на уточнение, отклонение.

### 4.3. Работа с отслеживаемыми фактами

Оценить:

- отображение фактов, вошедших в расчет индикатора;
- отображение источника факта: ИИ-модель, расчет индикатора, ручной ввод;
- возможность отметить факт как неподтвержденный;
- указание причины неподтверждения;
- сохранение пользователя и времени действия;
- предупреждение о необходимости пересчета;
- блокировки действий, если карточка уже отправлена или недоступна для изменения.

Сам алгоритм расчета срабатывания и выявления фактов в базовую оценку нашей команды не включать, если он находится на стороне смежной команды или расчетного сервиса.

### 4.4. Обработка результатов ИИ-моделей

ИИ-модели делает смежная команда. Наша команда оценивает только интерфейс и прием результатов.

Нужно оценить:

- отображение подозрительных операций;
- одиночную обработку операции;
- групповую обработку операций;
- выбор основной связанной операции для кластерных нарушений;
- выбор причины отклонения;
- указание подтверждения принятых мер;
- выбор документов и нормативных оснований;
- отображение текстового описания расчета, если оно передается смежной командой;
- выбор статуса принадлежности операции к отслеживаемым фактам.

Статусы принадлежности:

- не относится к срабатыванию цифровых индикаторов;
- не относится к срабатыванию цифровых индикаторов, но должно быть учтено при формировании материалов КНМ;
- относится к срабатыванию цифровых индикаторов.

### 4.5. Интеграция с сервисом доказательной базы

Сервис доказательной базы делает смежная команда. Наша команда оценивает вызов сервиса и работу с результатом.

Нужно оценить:

- вызов сервиса из карточки индикатора;
- передачу идентификаторов карточки, фактов, операций, субъекта/объекта контроля;
- прием статуса обработки;
- прием признака расхождений;
- прием ссылок или идентификаторов сформированных материалов;
- отображение результата в карточке;
- блокировку отправки через ИВИС при наличии расхождений;
- журналирование вызова и результата;
- обработку ошибок и повторный вызов.

Не включать в нашу базовую оценку:

- сбор доказательной базы;
- формирование PDF;
- подписание PDF;
- дообогащение данных;
- структурирование доказательного пакета внутри сервиса.

### 4.6. Интеграция через ИВИС

Все взаимодействие со СМЭВ выполняется через ИВИС.

Наша команда должна оценить:

- подготовку XML/пакета сведений для ИВИС;
- маппинг данных карточки в XML вида сведений;
- заполнение обязательных реквизитов;
- привязку материалов доказательной базы, если это требуется схемой;
- валидацию XML/пакета до отправки;
- передачу пакета в ИВИС;
- прием технических статусов;
- прием бизнес-статусов;
- сохранение идентификаторов сообщений;
- сохранение ошибок;
- повторные попытки отправки;
- отображение статуса отправки в карточке;
- блокировки повторной отправки и пересчета после отправки.

Прямая интеграция со СМЭВ в обход ИВИС не оценивается.

### 4.7. Справочники и нормативные основания

Оценить справочники, которые нужны для интерфейсов и ИВИС:

- нормативные документы;
- пункты нормативных документов;
- обязательные требования;
- причины отклонения;
- виды документов-подтверждений;
- типы отслеживаемых фактов;
- статусы карточек;
- статусы решений;
- виды цифровых индикаторов.

Нужно отдельно указать, что наполнение справочников должно быть предоставлено или согласовано заказчиком.

Если требуется административный интерфейс управления справочниками, оценить отдельной строкой.

### 4.8. Журналы и история

Оценить:

- историю действий пользователей;
- историю изменения статусов карточки;
- историю решений инспектора;
- историю отметок по отслеживаемым фактам;
- историю вызовов сервиса доказательной базы;
- историю отправок в ИВИС;
- сохранение ошибок интеграций;
- просмотр истории пользователем с правами администратора.

### 4.9. НДС-блок

Расчет объемов продукции и потенциального НДС делает смежная команда.

В базовую оценку нашей команды НДС-блок не включать, кроме случаев, если требуется интерфейс в аналитической системе.

Отдельно уточнить:

- нужно ли нам отображать агрегированные сведения;
- нужны ли фильтры и поиск;
- нужна ли карточка детализации;
- нужны ли ссылки на исходные нарушения;
- кто является пользователем этого интерфейса.

Без подтверждения этих пунктов НДС-блок считать внешней зависимостью.

## 5. Сервис категоризации объектов

По сервису категоризации ответственность пока не определена. Нужно дать оценку не одной строкой, а вариантами.

| Вариант | Что оценивает команда аналитической системы |
|---|---|
| Вариант 1. Сервис полностью делает смежная команда | Только отображение результата, статусов и ошибок |
| Вариант 2. Расчет делает смежная команда, интерфейс делает наша команда | Формы обработки потенциального изменения, просмотр деталей, подтверждение расчета, приложение материалов, статусы |
| Вариант 3. Весь сервис делает наша команда | Алгоритмы расчета, справочники критериев, хранение расчетов, интерфейсы, интеграции, журналирование |

Для базовой оценки нашей команды сервис категоризации не включать, пока не принято управленческое решение о распределении.

## 6. Что нужно получить от смежной команды

Для оценки нашей команды нужны технические спецификации взаимодействия со смежной командой.

По ИИ-моделям:

- перечень моделей, результаты которых должны отображаться;
- состав выходных атрибутов;
- идентификаторы операций, эВСД, транзакций, инвентаризаций и иных сущностей;
- статусы обработки;
- причины отклонения;
- признак принадлежности к отслеживаемым фактам;
- текстовое описание расчета, если оно формируется;
- требования к групповой обработке.

По сервису доказательной базы:

- API вызова;
- входные параметры;
- структура успешного ответа;
- структура ошибки;
- статусы обработки;
- признак расхождений;
- формат ссылок или идентификаторов материалов;
- правила повторного вызова;
- ожидаемое время ответа.

По НДС-блоку:

- нужен ли интерфейс в аналитической системе;
- какие данные нужно показывать;
- какие фильтры нужны;
- какие роли пользователей имеют доступ;
- нужен ли экспорт или внешний доступ через нашу систему.

## 7. Что нужно получить от заказчика

Для оценки и проектирования заказчик должен предоставить или согласовать:

- вид сведений СМЭВ для сработавших индикаторов риска;
- требования ИВИС к XML/пакету;
- XSD/схемы, правила заполнения, примеры сообщений, если есть;
- порядок получения технических и бизнес-статусов;
- вид сведений для изменения категорий риска, если этот блок остается в проекте;
- перечень НПА и обязательных требований;
- правила выбора нормативного основания;
- перечень статусов карточек и решений;
- роли пользователей и права доступа;
- правила блокировки действий после отправки;
- критерии, когда карточку можно отправлять;
- критерии возврата карточки на уточнение;
- требования к журналированию;
- макеты или согласование макетов интерфейса.

## 8. Что не включать в базовую оценку нашей команды

Чтобы оценка не была завышена и не смешивала зоны ответственности, в базовую оценку не включать:

- разработку ИИ-моделей;
- обучение или переобучение моделей;
- алгоритмы выявления подозрительных операций;
- расчет отслеживаемых фактов на стороне ИИ;
- формирование доказательной базы внутри сервиса;
- генерацию и подписание PDF доказательной базы;
- расчет объемов продукции и потенциального НДС;
- ведение справочников средних цен и продукции для НДС;
- прямую интеграцию со СМЭВ без ИВИС;
- полный сервис категоризации объектов до решения по распределению.

Эти блоки учитывать только как зависимости, влияющие на интерфейсы, статусы, интеграции и сроки.

## 9. Формат оценки

Предлагается дать оценку по блокам в упрощенном формате.

РП ожидает заполнение колонок следующим образом:

- `Блок` - функциональный блок, по которому нужна отдельная оценка.
- `Оценка` - трудоемкость/срок в принятом командой формате: человеко-дни, человеко-недели, календарный срок или диапазон.
- `Комментарий / допущения` - кратко указать, что именно включено в оценку, какие условия приняты, что должно быть предоставлено заказчиком или смежной командой, какие вопросы могут изменить оценку.

| Блок | Оценка | Комментарий / допущения |
|---|---:|---|
| Карточка цифрового индикатора |  | Что входит в экран карточки, какие статусы и действия учтены |
| Решение инспектора и нормативные основания |  | Какие решения, НПА, пункты НПА и пояснения включены |
| Отслеживаемые факты и пересчет |  | Что делаем в интерфейсе, где внешний расчет, какие блокировки учтены |
| Обработка результатов ИИ-моделей в интерфейсе |  | Какие данные ждем от смежной команды, какие сценарии обработки включены |
| Интеграция с сервисом доказательной базы |  | Какие вызовы, статусы, ошибки и признаки расхождений учтены |
| ИВИС/XML для вида сведений СМЭВ |  | XML, маппинг, валидация, отправка, статусы, ошибки, повторные попытки |
| Справочники и настройки |  | Какие справочники нужны, кто наполняет, нужен ли админ-интерфейс |
| Журналы и история действий |  | Какие действия, статусы, вызовы и ошибки журналируются |
| НДС-блок, если нужен интерфейс |  | Оценивать только интерфейс/отображение, если заказчик подтверждает необходимость |
| Категоризация, вариант 1 |  | Смежная команда делает сервис полностью, наша команда только отображает результат |
| Категоризация, вариант 2 |  | Смежная команда делает расчет, наша команда делает интерфейсы обработки |
| Категоризация, вариант 3 |  | Наша команда делает весь сервис, включая расчет, хранение, интерфейсы и интеграции |
| Интеграционное тестирование |  | Какие внешние сервисы, ИВИС и тестовые данные нужны |
| Нагрузочное/регрессионное тестирование |  | Какие сценарии и показатели проверяются |

Оценку по категоризации дать отдельно по вариантам, не смешивая с базовым объемом.

## 10. Критичные риски для оценки

1. Нет финального распределения сервиса категоризации.
2. Не предоставлены окончательные требования ИВИС/XML для вида сведений.
3. Не определен вид сведений для изменения категорий риска.
4. Не описаны технические спецификации взаимодействия со смежной командой.
5. Не утверждены статусы карточек и решений инспектора.
6. Не утверждены справочники НПА, обязательных требований и причин отклонения.
7. Не ясно, нужен ли интерфейс по НДС-блоку в аналитической системе.
8. Не определены правила блокировки действий после отправки.
9. Не определены требования к журналированию в деталях.
10. Не согласованы макеты интерфейсов.

## 11. Ожидаемый результат от команды

На выходе от команды аналитической системы нужен не один общий срок, а структурированная оценка:

- базовая оценка по нашему подтвержденному объему;
- отдельные опции по спорным блокам;
- комментарии к оценке в соответствующей колонке таблицы;
- перечень вопросов, без которых оценка может существенно измениться.

Базовый объем нашей команды можно формулировать так:

> Команда аналитической системы реализует пользовательский и интеграционный контур цифрового надзора: интерфейсы карточек и решений инспектора, работу с отслеживаемыми фактами, вызов смежных сервисов, отображение их результатов, формирование XML/пакетов для ИВИС, прием статусов ИВИС, журналирование и необходимые справочники. Расчетные сервисы ИИ, доказательной базы и НДС реализуются смежной командой и учитываются как внешние зависимости.
