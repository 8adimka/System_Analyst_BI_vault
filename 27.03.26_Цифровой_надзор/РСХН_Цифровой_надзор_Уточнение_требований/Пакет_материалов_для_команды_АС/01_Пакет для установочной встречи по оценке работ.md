# Пакет для установочной встречи по оценке работ

## 1. Назначение документа

Документ предназначен для подготовки и проведения установочной встречи с командой Аналитической системы по проекту "Цифровой надзор".

Цель встречи - получить предварительную оценку работ команды АС, зафиксировать допущения, выделить блоки с высокой неопределенностью и определить решения, которые нужно получить от заказчика, ИВИС, ФГИС ПГС или смежной команды.

Документ не заменяет материалы проекта. Он задает порядок обсуждения и помогает использовать подготовленный пакет документов без потери контекста.

## 2. Ожидаемый результат встречи

По итогам встречи должны появиться:

1. Заполненная или частично заполненная матрица оценки работ команды АС в человеко-днях.
2. Список блоков, которые команда АС может оценить сразу.
3. Список блоков, которые нужно оценивать диапазоном.
4. Список допущений, на которых строится предварительная оценка.
5. Список решений, которые нужно вынести РП, заказчику, ИВИС, ФГИС ПГС или смежной команде.
6. Список технических материалов, которых не хватает для точной оценки.
7. Договоренность о сроке актуализации оценки после получения ответов.

## 3. Участники встречи

| Роль | Зачем нужна на встрече | Что ожидается |
| --- | --- | --- |
| РП | Ведет встречу, фиксирует решения и допущения | Подтверждает границы обсуждения и дальнейшие действия |
| Технический лидер или архитектор АС | Оценивает интеграции, данные, хранение, backend и риски | Помогает определить трудоемкость и технические развилки |
| Системный аналитик АС | Оценивает требования, данные, статусы, сценарии и вопросы | Формулирует уточнения и допущения |
| Frontend или UX представитель | Оценивает экраны, карточки, статусы, формы и отчеты | Помогает оценить UI-блоки |
| Backend представитель | Оценивает интеграции, журналы, статусы, хранение и обмены | Помогает оценить серверную часть |
| Представитель ИВИС | Нужен для СМЭВ, XML, статусов, ошибок и тестового контура | Подтверждает правила обмена и ограничения |
| Смежная команда | Нужна по ИИ-моделям, доказательной базе и НДС | Подтверждает границы своих сервисов и форматы данных |
| Заказчик или представитель бизнес-заказчика | Нужен для решений по процессу и приоритетам | Подтверждает решения и бизнес-сценарии |

Минимальный состав для первой оценки: РП, архитектор или технический лидер АС, системный аналитик АС, backend представитель. ИВИС, смежную команду и заказчика можно подключать на отдельные блоки или отдельную встречу.

## 4. Материалы к встрече

| N | Документ | Как используется на встрече |
| --- | --- | --- |
| 1 | Устав проекта Цифровой надзор | Кратко фиксирует цель, границы и роли проекта |
| 2 | Материал для предварительной оценки работ команды АС | Основной текстовый документ о том, что именно нужно оценить |
| 3 | Матрица оценки работ команды АС | Таблица, куда команда вносит человеко-дни, уверенность и комментарии |
| 4 | Реестр открытых вопросов и зависимостей | Используется для фиксации вопросов, которые мешают точной оценке |
| 5 | Схема информационного взаимодействия и границы ответственности | Помогает пройти по участникам, потокам данных и зонам ответственности |
| 6 | Реестр интеграций и данных | Используется для обсуждения источников, получателей, форматов и данных |
| 7 | Карта открытых решений для оценки работ | Используется для фиксации управленческих и архитектурных развилок |
| 8 | Разбор материалов СМЭВ ЕРВК | Используется при обсуждении ЕРВК, `ControlObjectsList` 1.0.6 и `AddControlObjects` 1.0.5 |

## 5. Подготовка до встречи

### 5.1. Что должен сделать РП

1. Разослать участникам пакет документов.
2. Указать, что предварительная оценка выполняется только по зоне ответственности команды АС.
3. Отдельно отметить, что работы смежной команды, ИВИС, ФГИС ПГС и внешних контуров не включаются как разработка АС.
4. Попросить команду АС заранее посмотреть матрицу оценки и реестр интеграций.
5. Подготовить список блоков, по которым требуется оценка на встрече.
6. Подготовить список решений, которые нельзя принять на уровне команды АС.

### 5.2. Что должна сделать команда АС

1. Просмотреть материал для предварительной оценки.
2. Открыть матрицу оценки работ.
3. Предварительно отметить строки, которые можно оценить сразу.
4. Отметить строки, где нужна оценка диапазоном.
5. Подготовить вопросы по данным, интеграциям, статусам, XML, журналам и отчетам.
6. Отдельно посмотреть блоки ЕРВК, ИВИС/СМЭВ, категорирования и доказательной базы.

### 5.3. Что нужно попросить у ИВИС и смежной команды

1. Подтвердить, кто формирует XML для СМЭВ.
2. Подтвердить, какие статусы и ошибки возвращаются в АС.
3. Подтвердить, есть ли тестовый контур и примеры сообщений.
4. Подтвердить форматы результатов ИИ-моделей, доказательной базы и НДС.
5. Подтвердить, как АС должна взаимодействовать с сервисом доказательной базы.

## 6. Правила оценки

1. Оценка ведется в человеко-днях.
2. Оценивается только работа команды АС.
3. Работы смежной команды, ИВИС, ФГИС ПГС и внешних контуров фиксируются как зависимости.
4. Если данных недостаточно, строка не оставляется пустой. Нужно указать допущение, диапазон или вопрос.
5. Для неопределенных блоков допускается оценка минимум, база и максимум.
6. В колонке "Уверенность" нужно честно указывать высокий, средний или низкий уровень уверенности.
7. Если блок зависит от решения заказчика или другой команды, это фиксируется в комментарии.
8. Если блок может резко увеличить объем работ, он выносится в карту открытых решений.
9. После встречи матрица оценки должна быть актуализирована с учетом принятых допущений.

## 7. Повестка встречи

Рекомендуемая длительность первой встречи: 90 минут.

| Время | Блок | Цель |
| --- | --- | --- |
| 0-10 минут | Вводная и цель встречи | Подтвердить, что встреча нужна для предварительной оценки работ команды АС |
| 10-20 минут | Границы оценки | Зафиксировать, что входит и не входит в оценку АС |
| 20-35 минут | Основные UI и процесс обработки | Обсудить рабочие списки, карточки, решения, статусы и результат обработки |
| 35-50 минут | Интеграции и данные | Обсудить ИИ-модели, доказательную базу, НДС, данные и журналы |
| 50-65 минут | ИВИС, СМЭВ и ЕРВК | Обсудить виды сведений, XML, получение и внесение сведений ЕРВК |
| 65-75 минут | Категорирование | Обсудить роль ФГИС ПГС, данные, результат и UI в АС |
| 75-85 минут | Заполнение матрицы оценки | Договориться, какие строки оцениваются сразу и какие диапазоном |
| 85-90 минут | Итоги и дальнейшие действия | Зафиксировать ответственных, сроки и открытые решения |

Если участники не успевают пройти все блоки, приоритет должен быть таким:

1. Границы ответственности.
2. ИВИС, СМЭВ и ЕРВК.
3. Категорирование.
4. Доказательная база.
5. Результат обработки карточки.
6. Отчеты и мониторинг.

## 8. Сценарий ведения встречи

### 8.1. Вступление

РП кратко фиксирует:

1. Проект находится на этапе предварительной оценки.
2. Оценка нужна по зоне ответственности команды АС.
3. Часть блоков зависит от решений заказчика, ИВИС, ФГИС ПГС и смежной команды.
4. Цель встречи - не решить все вопросы, а отделить оцениваемый объем от зависимостей.
5. По неопределенным блокам допустима диапазонная оценка.

### 8.2. Фиксация границ

Нужно подтвердить:

1. Команда АС оценивает интерфейсы, карточки, статусы, журналы, отчеты, подготовку данных и интеграционную обвязку.
2. Команда АС не оценивает как свою разработку ИИ-модели, сервис доказательной базы, НДС, инфраструктуру ИВИС и функции ФГИС ПГС.
3. Если внешний блок влияет на АС, он фиксируется как зависимость.
4. Если граница ответственности спорная, строка уходит в карту открытых решений.

### 8.3. Проход по матрице оценки

По каждой строке матрицы нужно определить:

1. Понятен ли объем работ.
2. Можно ли дать оценку в человеко-днях.
3. Нужна ли оценка диапазоном.
4. Какие допущения используются.
5. Какой вопрос мешает уточнить оценку.
6. Кто должен ответить на вопрос.
7. Нужно ли выделить блок как риск.

### 8.4. Фиксация итогов

В конце встречи нужно зафиксировать:

1. Какие строки матрицы оценены.
2. Какие строки требуют уточнения.
3. Какие решения нужно вынести заказчику.
4. Какие вопросы адресуются ИВИС.
5. Какие вопросы адресуются смежной команде.
6. Кто отвечает за актуализацию матрицы.
7. К какому сроку должна быть обновленная версия оценки.

## 9. Вопросы по блокам

### 9.1. Границы проекта

1. Подтверждаем ли, что команда АС оценивает только свой контур.
2. Есть ли блоки, которые ошибочно попали в оценку АС.
3. Есть ли работы, которые должны быть выделены в смежную команду.
4. Есть ли работы, которые нужно отдельно согласовать с заказчиком.

### 9.2. Рабочие списки и карточки

1. Какие списки и карточки входят в первый объем оценки.
2. Какие поля карточки обязательны.
3. Какие статусы карточки нужны.
4. Какие действия инспектора должны быть доступны.
5. Какие данные должны отображаться сразу, а какие по раскрытию.

### 9.3. Решение инспектора и результат обработки

1. Какой перечень итоговых решений должен поддерживаться.
2. Что считается результатом обработки карточки.
3. Нужен ли документ, пакет сведений, структурированная отправка или комбинация.
4. Где фиксируется пояснение инспектора.
5. Нужен ли выбор нормативных оснований.
6. Какие решения меняют статус карточки.

### 9.4. Доказательная база

1. Что именно АС получает от сервиса доказательной базы.
2. Передаются ли файлы, ссылки или метаданные.
3. Где хранятся материалы.
4. Нужно ли ручное прикрепление материалов.
5. Какие статусы и ошибки возвращает сервис.
6. Какие материалы должны попадать в результат обработки.

### 9.5. ИИ-модели

1. Какой формат результата ИИ-модели.
2. Есть ли уровень уверенности.
3. Есть ли пояснение результата.
4. Как результат связывается с карточкой.
5. Как обрабатываются повторные или обновленные результаты.

### 9.6. НДС и расчетные данные

1. Какие данные или результаты предоставляет НДС.
2. Как часто они обновляются.
3. Какие идентификаторы партий, объектов и субъектов используются.
4. Нужно ли хранить версии расчетов.
5. Какие ошибки или статусы возможны.

### 9.7. ИВИС и СМЭВ

1. Кто формирует XML.
2. Какие виды сведений входят в проект.
3. Какие статусы возвращает ИВИС.
4. Нужно ли хранить полный XML.
5. Нужна ли повторная отправка.
6. Есть ли тестовый контур.
7. Хватает ли эталонных XML для тестирования всех нужных сценариев или нужны дополнительные примеры.

### 9.8. ЕРВК

1. Используется ли получение сведений из ЕРВК через `urn://rostelekom.ru/ControlObjectsList/1.0.6`.
2. Используется ли внесение сведений в ЕРВК через `urn://rostelekom.ru/AddControlObjects/1.0.5`.
3. Какие действия нужны для внесения: ADD, EDIT, DELETE.
4. Какие идентификаторы хранит АС.
5. Кто выполняет сопоставление полей объекта контроля с XML.
6. Нужно ли показывать пользователю технический статус обмена.

### 9.9. Категорирование

1. Используется ли типовой процесс категорирования во ФГИС ПГС.
2. Какие данные АС должна подготовить.
3. Какие результаты возвращаются в АС.
4. Нужен ли UI проверки факторов в АС.
5. Нужно ли хранить версии расчетов.
6. Что делает инспектор в АС, а что во ФГИС ПГС.

### 9.10. Отчеты, журналы и аудит

1. Какие отчеты обязательны для первого объема.
2. Нужны ли выгрузки.
3. Какие действия пользователей логируются.
4. Какие ошибки обмена нужно показывать в отчетах.
5. Какие требования к хранению журналов.

## 10. Как заполнять матрицу оценки

Для каждой строки матрицы команда АС должна заполнить:

1. Оценка минимум, чел.-дн.
2. Оценка база, чел.-дн.
3. Оценка максимум, чел.-дн.
4. Уверенность.
5. Комментарий.
6. Ответственный.
7. Дата уточнения.
8. Статус.

РП должен следить, чтобы в комментарии были указаны:

1. Основное допущение.
2. Что не входит в оценку.
3. От какой внешней команды зависит строка.
4. Что может увеличить оценку.
5. Какой вопрос нужно уточнить.

Пример комментария:

> Оценено при допущении, что АС получает результат от смежного сервиса в согласованном JSON/XML и не реализует расчетную логику. Требуется уточнить формат статусов и ошибок.

## 11. Что фиксировать после встречи

После встречи нужно обновить:

1. Матрицу оценки работ команды АС.
2. Реестр открытых вопросов и зависимостей.
3. Карту открытых решений.
4. При необходимости реестр интеграций и данных.

Также нужно подготовить короткий итог:

1. Какие блоки оценены.
2. Какие блоки оценены диапазоном.
3. Какие блоки не удалось оценить.
4. Какие решения нужны от заказчика.
5. Какие вопросы ушли в ИВИС.
6. Какие вопросы ушли в смежную команду.
7. Когда ожидается обновленная оценка.

## 12. Критерии готовности предварительной оценки

Предварительная оценка может считаться готовой, если:

1. По всем строкам матрицы есть оценка или понятная причина отсутствия оценки.
2. По неопределенным блокам указаны диапазоны.
3. По каждому диапазону указано допущение.
4. Все внешние зависимости вынесены в реестр вопросов или карту решений.
5. Команда АС подтвердила, что оценивает только свой контур.
6. РП понимает, какие решения нужно получить для уточнения оценки.
7. Есть срок актуализации оценки после получения ответов.

## 13. Рекомендуемый итоговый порядок передачи материалов

Для команды АС материалы лучше передавать в таком порядке:

1. Пакет для установочной встречи по оценке работ.
2. Материал для предварительной оценки работ команды АС.
3. Матрица оценки работ команды АС.
4. Реестр интеграций и данных.
5. Схема информационного взаимодействия и границы ответственности.
6. Карта открытых решений для оценки работ.
7. Реестр открытых вопросов и зависимостей.
8. Разбор материалов СМЭВ ЕРВК.
9. Устав проекта Цифровой надзор.

Для руководства можно передавать не весь пакет сразу, а краткий набор:

1. Устав проекта.
2. Карта открытых решений.
3. Сводка по итогам оценки после заполнения матрицы.

## 14. Первый шаг после подготовки пакета

Первым действием нужно назначить встречу с командой АС и заранее отправить:

1. Материал для предварительной оценки.
2. Матрицу оценки.
3. Реестр интеграций и данных.
4. Карту открытых решений.

В приглашении нужно прямо указать, что ожидаемый результат встречи - не финальное согласование требований, а предварительная оценка работ команды АС с допущениями и открытыми вопросами.
