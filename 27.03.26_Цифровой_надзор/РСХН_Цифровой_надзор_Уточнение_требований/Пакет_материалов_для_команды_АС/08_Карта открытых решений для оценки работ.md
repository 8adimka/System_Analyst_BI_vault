# Карта открытых решений для оценки работ

## 1. Назначение документа

Документ фиксирует решения, которые нужно принять или временно зафиксировать как допущения, чтобы команда Аналитической системы могла подготовить предварительную оценку работ по проекту "Цифровой надзор".

Документ отличается от реестра вопросов. Вопрос может быть справочным, а решение меняет границы работ, трудоемкость, риски и ответственность участников.

Карта нужна для руководителя проекта, команды АС, заказчика и смежной команды. По каждой строке нужно либо принять вариант, либо подтвердить временное допущение для оценки.

## 2. Как пользоваться картой

1. Пройти по решениям с РП, заказчиком, ИВИС и смежной командой.
2. По каждому решению выбрать вариант или подтвердить временное допущение для оценки.
3. Если решение не принято, оставить строку в статусе "Открыто" и оценивать работы диапазоном.
4. После принятия решения обновить матрицу оценки работ команды АС.
5. Не включать в оценку АС работы смежной команды, ИВИС, ФГИС ПГС и внешних контуров как разработку АС.

## 4. Детализация решений

### 4.1. Границы проекта

**Решение.** Что команда АС оценивает как свою работу.

**Варианты.**

1. Оценивать только интерфейсы, карточки, статусы, журналы, отчеты и интеграции в контуре АС.
2. Включить в оценку АС часть расчетной логики, доказательную базу или функции внешних систем.
3. Оценивать весь проект целиком без разделения по участникам.

**Рекомендуемое допущение.** Для предварительной оценки считать, что команда АС оценивает только свою зону ответственности: интерфейсы, карточки, статусы, журналы, отчеты, подготовку данных и интеграции.

**Почему важно.** Без этого в оценку могут попасть работы смежной команды, ИВИС, ФГИС ПГС или внешних контуров.

### 4.2. Сервисы смежной команды

**Решение.** Какие блоки считать внешними зависимостями для команды АС.

**Варианты.**

1. ИИ-модели, сервис доказательной базы и НДС делает смежная команда.
2. Часть этих сервисов делает команда АС.
3. Ответственность остается неразделенной до отдельного решения.

**Рекомендуемое допущение.** ИИ-модели, сервис доказательной базы и НДС считать работами смежной команды. В оценке АС учитывать только интеграцию, отображение, статусы, ошибки и хранение связей.

**Почему важно.** Это снижает риск двойного учета и позволяет команде АС оценивать только свою разработку.

### 4.3. Формирование XML и взаимодействие через ИВИС

**Решение.** Кто формирует XML и какую часть обмена выполняет АС.

**Варианты.**

1. АС формирует полный XML и передает его в ИВИС.
2. АС передает структурированные данные, а XML формирует ИВИС.
3. XML формирует внешний контур, а АС хранит только статус и результат.

**Рекомендуемое допущение.** Для оценки заложить сценарий, при котором АС готовит данные или XML по согласованным схемам, передает их в ИВИС и обрабатывает ответные статусы и ошибки.

**Почему важно.** От решения зависит объем XML-маппинга, валидации, журналирования, повторной отправки и интеграционного тестирования.

### 4.4. ЕРВК

**Решение.** Какие сценарии ЕРВК входят в объем проекта.

**Варианты.**

1. Только получение сведений из ЕРВК через `urn://rostelekom.ru/ControlObjectsList/1.0.6`.
2. Получение и внесение сведений в ЕРВК через `ControlObjectsList` 1.0.6 и `AddControlObjects` 1.0.5.
3. Только отображение связи с объектом ЕРВК без самостоятельного обмена.

**Рекомендуемое допущение.** Для базовой оценки считать получение сведений из ЕРВК. Внесение сведений с действиями ADD, EDIT, DELETE выделить отдельным риском или отдельным сценарием оценки.

**Почему важно.** Внесение сведений требует проверки обязательных полей, подготовки XML, обработки ошибок по каждой записи и большего объема интеграционного тестирования.

### 4.5. Идентификаторы ЕРВК

**Решение.** Какие идентификаторы хранит АС для связи карточки с объектом контроля.

**Варианты.**

1. Хранить только один основной идентификатор объекта.
2. Хранить несколько идентификаторов: externalId, cosId, cosVersion, registryEntryId, controlObjectInfo.id.
3. Не хранить идентификаторы ЕРВК, а получать сведения каждый раз заново.

**Рекомендуемое допущение.** Для оценки заложить хранение набора идентификаторов, достаточного для повторной сверки и связи карточки с объектом ЕРВК.

**Почему важно.** Это влияет на модель данных, связи карточки, журнал обмена и возможность повторной обработки.

### 4.6. Категорирование

**Решение.** Где выполняется расчет категории риска.

**Варианты.**

1. Расчет выполняется в ФГИС ПГС с использованием типового процесса.
2. Часть расчета или проверка факторов выполняется в АС.
3. АС реализует собственный расчет категории риска.

**Рекомендуемое допущение.** Для базовой оценки считать, что расчет категории выполняется во ФГИС ПГС, а АС готовит данные, отображает результат и хранит связь с карточкой и объектом.

**Почему важно.** Собственный расчет в АС требует алгоритмов, формул, справочников, проверки факторов, версий расчетов и отдельного тестирования.

### 4.7. UI по категорированию

**Решение.** Нужен ли в АС отдельный UI для проверки факторов категории риска.

**Варианты.**

1. В АС только отображается результат и статус категории.
2. В АС отображаются факторы и доступна ручная проверка или уточнение.
3. В АС реализуется полноценный рабочий процесс категорирования.

**Рекомендуемое допущение.** Для базовой оценки считать, что АС отображает результат, статус и ключевые сведения. Полноценный UI проверки факторов выделить отдельным сценарием.

**Почему важно.** UI проверки факторов меняет объем экранов, прав, статусов, истории и валидаций.

### 4.8. Доказательная база

**Решение.** Как АС взаимодействует с сервисом доказательной базы.

**Варианты.**

1. АС получает ссылки и метаданные, файлы хранятся во внешнем сервисе.
2. АС получает и хранит файлы у себя.
3. АС только показывает факт наличия материалов без работы с ними.

**Рекомендуемое допущение.** Для базовой оценки считать, что АС получает ссылки и метаданные, отображает материалы и связывает их с карточкой и решением.

**Почему важно.** Хранение файлов в АС увеличивает требования к ИБ, объему хранения, правам доступа и аудиту.

### 4.9. Ручное прикрепление материалов

**Решение.** Может ли инспектор прикреплять материалы вручную из АС.

**Варианты.**

1. Инспектор только выбирает материалы из сервиса доказательной базы.
2. Инспектор может загрузить новый файл в АС.
3. Инспектор не работает с материалами в АС, они подтягиваются автоматически.

**Рекомендуемое допущение.** Для базовой оценки считать выбор материалов из сервиса доказательной базы. Ручную загрузку выделить отдельным риском.

**Почему важно.** Ручная загрузка требует UI загрузки, хранения файлов, ограничений размера, антивирусной проверки, прав и аудита.

### 4.10. Результат обработки карточки

**Решение.** Что является итогом обработки карточки инспектором.

**Варианты.**

1. Документ или протокол.
2. Структурированный пакет сведений.
3. Иное действие или запись результата обработки.
4. Комбинация документа и структурированной отправки.

**Рекомендуемое допущение.** Для оценки использовать нейтральный термин "результат обработки" до утверждения формы и сценария. Не закреплять заранее конкретную кнопку или единственный тип документа.

**Почему важно.** От решения зависит генерация документов, XML, хранение версий, материалы, статусы отправки и интеграция с ИВИС.

### 4.11. Решение инспектора

**Решение.** Какие итоговые решения инспектора должна поддерживать АС.

**Варианты.**

1. Подтвердить риск.
2. Отклонить срабатывание.
3. Вернуть карточку на уточнение.
4. Передать дальше.
5. Дополнительные варианты по решению заказчика.

**Рекомендуемое допущение.** Для базовой оценки заложить четыре основных состояния: подтверждено, отклонено, на уточнении, передано дальше. Окончательный перечень утвердить отдельно.

**Почему важно.** Перечень решений влияет на статусы карточки, кнопки, права, журнал, отчеты и результат обработки.

### 4.12. Нормативные основания

**Решение.** Должен ли инспектор выбирать нормативный акт и конкретные пункты как основание результата обработки.

**Варианты.**

1. Инспектор выбирает НПА и пункты из справочника.
2. Основание формируется автоматически.
3. Основание вводится свободным текстом.
4. Основание не фиксируется в АС.

**Рекомендуемое допущение.** Для оценки выделить выбор нормативных оснований как отдельный блок. До решения заказчика не считать его обязательным минимумом.

**Почему важно.** Нужны справочники, обновление нормативной базы, UI выбора, хранение и проверка актуальности.

### 4.13. Работа инспектора в ФГИС ПГС

**Решение.** Какие действия инспектор выполняет в АС, а какие во ФГИС ПГС.

**Варианты.**

1. Основная обработка выполняется в АС, во ФГИС ПГС уходят только результаты или сведения.
2. Часть обработки выполняется во ФГИС ПГС.
3. АС только отображает данные, а рабочий процесс выполняется во ФГИС ПГС.

**Рекомендуемое допущение.** Для оценки считать, что АС не дублирует пользовательские функции ФГИС ПГС. Если действие выполняется во ФГИС ПГС, АС хранит только связь, статус или результат, если он нужен в карточке.

**Почему важно.** Это определяет границы UI, переходы между системами, права и маршрут пользователя.

### 4.14. Хранение XML и технического следа

**Решение.** Что АС хранит по обменам через ИВИС и СМЭВ.

**Варианты.**

1. Полный входящий и исходящий XML.
2. Только статусы, идентификаторы, ошибки и метаданные.
3. Только бизнес-статус без технического журнала.

**Рекомендуемое допущение.** Для базовой оценки считать хранение статусов, идентификаторов, ошибок и метаданных. Полное хранение XML уточнить отдельно с ИБ и ИВИС.

**Почему важно.** Полное хранение XML влияет на ИБ, объем хранения, аудит, поиск и эксплуатацию.

### 4.15. Отчетность

**Решение.** Какой набор отчетов нужен руководству и пользователям.

**Варианты.**

1. Минимальные отчеты по карточкам, статусам и решениям.
2. Расширенные отчеты по ошибкам, срокам, регионам, источникам и категориям.
3. Передача данных во внешний BI.

**Рекомендуемое допущение.** Для базовой оценки заложить отчеты по карточкам, статусам, решениям, ошибкам обмена и срокам обработки.

**Почему важно.** Отчетность влияет на витрины, агрегаты, роли, выгрузки и тестирование.

## 5. Решения, которые критично принять первыми

1. Границы зоны ответственности команды АС.
2. Архитектурное решение по категорированию.
3. Сценарии ЕРВК: получение, внесение или оба варианта.
4. Роль АС и ИВИС в формировании XML.
5. Способ взаимодействия с сервисом доказательной базы.
6. Что считается результатом обработки карточки.
7. Перечень итоговых решений инспектора.

## 6. Связь с оценкой работ

Если решение принято, соответствующий блок можно оценивать ближе к базовому сценарию.

Если решение не принято, блок нужно оценивать диапазоном или несколькими сценариями:

1. Минимальный сценарий.
2. Базовый сценарий.
3. Расширенный сценарий.

Для команды АС важно отдельно фиксировать, какие работы входят в ее оценку, а какие являются зависимостями от заказчика, смежной команды, ИВИС, ФГИС ПГС или внешнего контура.
