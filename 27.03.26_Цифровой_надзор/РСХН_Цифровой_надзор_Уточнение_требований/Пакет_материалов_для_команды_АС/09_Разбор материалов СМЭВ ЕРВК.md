# Разбор материалов СМЭВ ЕРВК

Дата актуализации: 05.10.2026.

## 1. Назначение разбора

Документ фиксирует, какие материалы СМЭВ по ЕРВК найдены в папке проекта и как они влияют на предварительную оценку работ команды Аналитической системы.

Разбор нужен для уточнения блока ЕРВК, ИВИС и СМЭВ в материалах оценки. Устав проекта не требует детализации до уровня XSD и видов сведений.

## 5. Вид сведений получения информации из ЕРВК

### 5.1. Назначение

Вид сведений предназначен для получения информации об объекте контроля из реестра объектов контроля ЕРВК.

Корневые элементы:

| Элемент | Назначение |
|---|---|
| `ControlObjectsListRequest` | запрос списка объектов контроля из реестра объектов контроля |
| `ControlObjectsListResponse` | ответ на запрос списка объектов контроля |

### 5.2. Варианты запроса по XSD

`ControlObjectsListRequest` построен как выбор одного из вариантов запроса:

| Вариант | Смысл для АС |
|---|---|
| `requestFromSupervision` | запрос по виду контроля и ОГРН КНО |
| `broadcastCount` | запрос страницы рассылки по счетчику страницы |
| `requestFromCos` | запрос объекта контроля по идентификатору и версии |
| `requestAllFromPeriod` | запрос по периоду времени |
| `requestByControlObjectId` | запрос по объекту контроля, возвращает связанные реестровые записи |

Эталонный запрос показывает сценарий `requestFromSupervision` с полями:

1. `supervisionTitleId`;
2. `controlOrganOgrn`;
3. `startDate`;
4. `finishDate`.

Для оценки нужно уточнить, какие варианты реально нужны АС. Если нужен только запрос по конкретному объекту или по виду контроля, объем меньше. Если нужны все варианты, объем интеграции и тестирования выше.

### 5.3. Варианты ответа

`ControlObjectsListResponse` построен как выбор:

| Вариант | Смысл |
|---|---|
| `successMessage` | успешный ответ со списком объектов и пагинацией |
| `successAttachment` | успешный ответ в формате вложения |
| `error` | сообщение об ошибке |

Эталонный ответ содержит `successMessage`, `registryEntryList` и `paging`.

Ключевые поля записи:

| Поле | Комментарий для АС |
|---|---|
| `cos.cosId` | идентификатор объекта контроля ЕРВК |
| `cos.cosVersion` | версия объекта контроля ЕРВК |
| `registryEntryId` | идентификатор записи реестра |
| `controlObjectInfo.id` | идентификатор сведений об объекте контроля |
| `controlObjectInfo.name` | наименование объекта контроля |
| `legalEntities` | контролируемые лица |
| `status` | статус записи |
| `supervision` | вид контроля |
| `controlOrgan` | контрольный орган |
| `riskCategory` | категория риска или класс опасности |
| `objectSubspec` | подвид, вид и тип объекта контроля |
| `regionCode` | код региона |
| `paging` | номер страницы, всего страниц, всего записей |

Для АС особенно важны `cosId`, `cosVersion`, `registryEntryId`, `controlObjectInfo.id`, `riskCategory` и `objectSubspec`, потому что они связывают карточку АС, объект контроля, категорию риска и внешний контур.

## 6. Вид сведений внесения информации в ЕРВК

### 6.1. Назначение

Вид сведений предназначен для добавления объектов контроля в реестр ЕРВК. По XSD также предусмотрены действия изменения и удаления.

Корневые элементы:

| Элемент | Назначение |
|---|---|
| `AddControlObjectsRequest` | запрос на внесение объектов контроля в реестр объектов контроля |
| `AddControlObjectsResponse` | ответ на запрос внесения объектов контроля |

### 6.2. Действия

В схеме указан тип `ActionsType`:

| Значение | Смысл | Требование по XSD |
|---|---|---|
| `ADD` | добавление записи | должен быть передан объект |
| `EDIT` | изменение записи | должны быть переданы `cos` и объект |
| `DELETE` | удаление записи | должен быть передан `cos` |

Эталонный запрос покрывает действие `ADD`.

Для оценки нужно уточнить, какие действия реально входят в проект. Если требуется только `ADD`, объем меньше. Если нужны `EDIT` и `DELETE`, нужно учитывать поиск объекта, хранение `cos`, обработку конфликтов и больше тестовых сценариев.

### 6.3. Ключевые данные запроса

`AddControlObjectsRequest` содержит одну или несколько записей `Record`. В `Record` есть:

| Поле | Комментарий для АС |
|---|---|
| `cos` | нужен для изменения или удаления, если действие требует ссылку на существующий объект |
| `action` | `ADD`, `EDIT` или `DELETE` |
| `ObjectData` | объект, над которым проводится действие |

`ObjectData` включает:

| Поле | Комментарий для АС |
|---|---|
| `externalId` | идентификатор объекта контроля в ведомственной системе |
| `ControlObject` | наименование и адрес объекта контроля |
| `Supervision` | вид контроля или надзора |
| `ControlOrgan` | контрольный орган |
| `RiskCategory` | категория риска или класс опасности |
| `ObjectSubspec` | подвид, вид и тип объекта контроля |
| `LegalEntities` | контролируемые лица |
| `comment` | комментарий к записи |

Эталонный XML подтверждает, что для добавления объекта передаются вид контроля, контрольный орган, категория риска, подвид объекта, тип объекта, адрес и контролируемые лица разных типов.

### 6.4. Контролируемые лица

В XSD предусмотрены типы контролируемых лиц:

| Тип | Смысл |
|---|---|
| `LegalEntityFL` | физическое лицо |
| `LegalEntityIP` | индивидуальный предприниматель |
| `LegalEntityUL` | юридическое лицо |
| `LegalEntityIFL` | иностранное физическое лицо |
| `LegalEntityIUL` | иностранное юридическое лицо |
| `LegalEntityIULBranches` | филиал иностранного юридического лица |

Для российских ЮЛ/ИП в эталоне используются ИНН, ОГРН, адрес, телефон и email. Для оценки нужно понять, какие типы контролируемых лиц реально встретятся в данных РСХН и какие поля АС должна валидировать до отправки.

### 6.5. Ответ и ошибки

`AddControlObjectsResponse` содержит список `Response`, где каждый элемент может быть:

| Вариант | Смысл |
|---|---|
| `Success` | успешная обработка, содержит `externalId` и `cos` |
| `Error` | ошибка обработки, содержит тип ошибки, описание и `externalId` |

В XSD указаны ошибки:

| Код | Смысл |
|---|---|
| `400` | ошибка в запросе, в том числе неверные значения типов, видов, подвидов, неправильно заполненные поля, отсутствие нужных элементов |
| `404` | изменяемая или удаляемая запись не найдена |
| `409` | статус объекта вида контроля не `PUBLISHED`, данные рассинхронизированы |
| `500` | непредвиденная ошибка |

Для АС это означает необходимость хранить технический журнал обмена, отображать понятный статус пользователю и предусмотреть повторную отправку или ручное исправление данных.

## 7. Влияние на оценку команды АС

Новые материалы уточняют, что блок ЕРВК нужно рассматривать как два потенциальных СМЭВ-взаимодействия:

1. получение информации из реестра объектов контроля ЕРВК;
2. внесение информации в реестр объектов контроля ЕРВК.

В оценке команды АС нужно учесть:

1. анализ XSD и руководств пользователя;
2. подготовку маппинга полей АС в XML или в структуру, которую примет ИВИС;
3. формирование запроса `ControlObjectsListRequest`, если АС получает объекты из ЕРВК;
4. обработку `ControlObjectsListResponse`, включая `successMessage`, `successAttachment`, `error` и `paging`;
5. формирование `AddControlObjectsRequest`, если АС должна инициировать внесение объектов;
6. обработку `AddControlObjectsResponse`, включая `Success` и `Error`;
7. хранение `externalId`, `cosId`, `cosVersion`, `registryEntryId` и иных внешних идентификаторов;
8. обработку действий `ADD`, `EDIT`, `DELETE`, если они входят в объем;
9. валидацию обязательных и форматных полей до отправки;
10. обработку ошибок 400, 404, 409, 500;
11. журналирование запросов, ответов, статусов и повторных отправок;
12. интеграционное тестирование по эталонным XML и дополнительным сценариям, которых нет в эталонах.

## 8. Влияние на сервис категоризации

Категория риска присутствует в данных ЕРВК как `RiskCategory` при внесении и как `riskCategory` при получении.

Это важно для решения по сервису категоризации:

1. Если ФГИС ПГС является основным контуром категорирования, АС может использовать ЕРВК для получения категории, внешних идентификаторов и статуса объекта.
2. Если АС должна инициировать внесение или изменение сведений об объекте, ей придется передавать категорию риска как часть `AddControlObjectsRequest`.
3. Если категория рассчитывается в АС, нужно обеспечить строгую связь результата расчета с объектом ЕРВК и внешними идентификаторами.
4. Если категория подтверждается в ФГИС ПГС, АС не должна дублировать юридически значимое подтверждение, но может хранить ссылку, статус и результат.

## 10. Короткий вывод

После обновления материалов СМЭВ по ЕРВК неопределенность стала ниже: есть руководства пользователя, XSD и эталонные XML. Для предварительной оценки теперь можно закладывать не абстрактный обмен, а два конкретных вида сведений с понятными URI и базовыми примерами.

Главная оставшаяся неопределенность не техническая, а процессная: нужно решить, какие сценарии реально выполняет АС, а какие остаются в ФГИС ПГС. Особенно это важно для категоризации, потому что категория риска является частью сведений ЕРВК и должна быть связана с объектом контроля во внешнем контуре.
