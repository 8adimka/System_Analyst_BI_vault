Анализ конкурентных решений (Benchmarking).
Power BI (DAX): Не использует SQL напрямую. Фильтрация агрегатов решается через меры (Measures) с использованием функций CALCULATE и FILTER. Чтобы применить фильтр только к определенному уровню иерархии в матрице (сводной таблице), аналитик пишет код DAX с использованием функций проверки контекста: ISINSCOPE() или HASONEVALUE(). Это дает 100% гибкость, но требует от пользователя знания сложного языка DAX.

Tableau (LOD-выражения): Использует Level of Detail (LOD) выражения (FIXED, INCLUDE, EXCLUDE). Пользователь может вынести меру в область фильтров и явно указать, по какому измерению (dimension) вычислять фильтр. Интерфейс визуально позволяет выбрать, к каким уровням применяется расчет.

Apache Superset: В конструкторе графиков есть явный блок HAVING. Однако для сложных сводных таблиц Superset просто применяет этот фильтр к итоговому набору данных. Тонкая настройка по уровням (без написания Custom SQL) там реализована слабо.

1С:Предприятие (Система компоновки данных - СКД): (Александр упоминал 1С, и это самый релевантный пример для вашей текущей архитектуры). В СКД фильтры можно настраивать глобально (для всего отчета), для конкретной группировки (аналог вашего RowLevel) или для детальных записей. Это реализовано через удобный UI: пользователь в дереве настроек выбирает конкретную группировку и добавляет условие только для нее.

Вывод для Modus BI: Идея Чебанова с использованием переменной RowLevel отлично ложится в парадигму SQL-генератора. Нам нужно дать пользователю UI (в духе 1С СКД), который под капотом будет генерировать условие CASE WHEN RowLevel IN (...) THEN ... или встраивать блок HAVING только в нужные подзапросы (subqueries).

Ниже представлен драфт постановки задачи для Jira.

Драфт задачи в Jira (Epic / Story)
Название задачи: Настройка применения HAVING-фильтрации для конкретных уровней группировки в сводных таблицах
Тип: Story / Feature
Компонент: Конструктор отчетов / Сводные таблицы / SQL Генератор

1. Бизнес-контекст (User Story)
Как аналитик данных,
Я хочу иметь возможность применять фильтрацию по агрегированным значениям (HAVING) к конкретным уровням иерархии в сводной таблице,
Чтобы отсекать ненужные данные на верхних уровнях (например, скрыть "Регионы" с общей суммой продаж < 0), но при этом сохранять корректный расчет на нижних уровнях (или наоборот).

2. Проблематика (As-Is)
На данный момент сводная таблица представляет собой каскад подзапросов (subqueries), каждый из которых отвечает за свой уровень детализации (разворот).
При попытке применить фильтр HAVING (например, SUM(expenses) > 0), система не может однозначно определить, на каком уровне иерархии этот фильтр должен быть вычислен. Применение фильтра ко всем уровням сразу приводит к искажению бизнес-логики отчета (отсекаются корректные вложенные элементы).

Дополнительные проблемы, выявленные в ходе анализа:

Баг UI локальных фильтров: При редактировании существующего вычисляемого фильтра в режиме HAVING, его новое значение не сохраняется/не применяется к запросу. Для изменения приходится удалять фильтр и создавать заново.

Глобальные фильтры (Дашборд): При выносе вычисляемого поля (HAVING) в общий фильтр дашборда (панель индикаторов), UI предлагает выбор конкретных значений из списка (dropdown), а не логичный выбор диапазона (больше/меньше/между) для числовых агрегатов.

3. Требования к реализации (To-Be)
Задача разбивается на изменение UI/UX пользовательского интерфейса и доработку backend-части (генератора SQL).

3.1. Пользовательский интерфейс (UI/UX)
В модальном окне настройки фильтра (и для локальных фильтров таблицы, и при выносе на дашборд), если пользователь переключает тип фильтра в режим HAVING и виджетом является Сводная таблица, необходимо добавить новый блок настроек: «Уровни применения (RowLevel)».

Варианты выбора в UI:

Все уровни (По умолчанию) — работает как сейчас.

Произвольное условие (Продвинутый режим) — текстовое поле, куда пользователь может вписать логику с использованием системной переменной (например: RowLevel = 'Details' OR RowLevel = 'Group_1').

Выбранные уровни (Базовый режим) — список чекбоксов, формирующийся динамически на основе текущих измерений (dimensions), добавленных в "Строки" сводной таблицы.

Пример макета логики UI:

[x] Применять фильтр HAVING к:
( ) Всем уровням
(•) Выбранным уровням:
[x] Категория (Group_1)
[ ] Подкатегория (Group_2)
[ ] Детальные записи (Details)
( ) Произвольное выражение (RowLevel)

3.2. Логика SQL-генератора (Backend)
Генератор запросов должен быть модифицирован таким образом, чтобы парсить настройки уровней применения из UI.

Сценарий 1 (Подход с инъекцией в подзапросы):
Если выбран конкретный уровень (например, Group_1), генератор должен добавить конструкцию HAVING [Условие] только в блок SQL-запроса, отвечающий за сборку уровня Group_1. В подзапросы Group_2 и Details этот HAVING не транслируется.

Сценарий 2 (Подход через CASE WHEN - по рекомендации Архитектора/Лида):
Если архитектура генератора предполагает единый блок фильтрации на верхнем уровне обертки, условие должно оборачиваться в конструкцию:
HAVING (CASE WHEN RowLevel IN ('Group_1') THEN SUM(Показатель) ELSE 1 END) > 0
(Точный синтаксис согласовать с backend-командой в зависимости от используемой СУБД, например ClickHouse или PostgreSQL).

3.3. Фильтры на Дашборде (Панель индикаторов)
Если фильтр с типом HAVING выносится на общую панель:

Тип контрола должен автоматически переключаться на "Диапазон/Условие" (Больше, Меньше, Равно, Между), а не список выбора значений (Dropdown).

В настройках виджета фильтра на дашборде должна сохраняться привязка к RowLevel виджетов, на которые этот фильтр влияет.

4. Задачи (Sub-tasks)
[Sub-task 1: Backend] Доработка SQL-генератора для обработки переменной RowLevel в контексте HAVING для сводных таблиц.

[Sub-task 2: Frontend] Добавление селектора выбора уровней группировки (RowLevel) в настройки вычисляемого фильтра сводной таблицы.

[Sub-task 3: Frontend] Адаптация UI глобального фильтра на дашборде для числовых HAVING-показателей (ввод диапазонов/условий вместо списка).

[Sub-task 4: Bugfix] Исправление бага: Применение изменений при редактировании существующего вычисляемого фильтра WHERE/HAVING в сводной таблице без его пересоздания.

5. Критерии приемки (DoD)
Пользователь может создать сводную таблицу с 3+ уровнями иерархии.

Пользователь может добавить фильтр HAVING SUM(поле) > X и указать, что он применяется только к 1-му уровню иерархии.

При применении фильтра итоги на 1-м уровне фильтруются корректно, при этом если развернуть оставшиеся элементы 1-го уровня, внутри них отображаются все данные (фильтр не применился к дочерним уровням).

При редактировании значения фильтра (например, изменение X на Y) и сохранении, таблица перестраивается с новыми условиями без необходимости пересоздавать фильтр.

Вынос этого фильтра на Дашборд позволяет задавать условие (>, <, =) через UI, а не выбирать значения из выпадающего списка.

Сгенерированный SQL запрос оптимизирован (отсутствуют декартовы произведения, планы запросов не деградируют).
