
Сводная таблица. Доработки. Настройка применения фильтрации HAVING к конкретным уровням иерархии в Cводной таблице

h3. Контекст и проблематика.
* В реляционных базах данных оператор {{HAVING}} применяется для фильтрации результатов строго после выполнения агрегатных функций (после {{GROUP BY}}). 
* Сводная таблица в нашей системе зачастую представляет собой многоуровневую иерархическую структуру, которая под капотом генерирует дерево независимых SQL-запросов для каждого уровня раскрытия. 

* *Проблема:* В текущей реализации портала вычисляемое поле на полке "Фильтры" с типом отбора {{HAVING}} применяется либо ко всем уровням вложенности запроса, либо не применяется вообще. Это приводит к искажению данных: например, если аналитик хочет отфильтровать убыточные _месяцы_ ({{HAVING SUM(Sales) < 0}}), а система может отсечь и прибыльные дни внутри убыточного месяца, и убыточные дни внутри прибыльного месяца, ломая логику детализации и общие итоги. 

----
h3. Текущая реализация.
Текущий способ обойти это ограничение — использование системной переменной
{{!ROW_LEVEL!}} в вычисляемом поле на полке «Фильтры», например, в таком виде:

{code:sql}
CASE WHEN !ROW_LEVEL! = "Категория" THEN SUM("СуммаДоходРасходКО") END > 1000000
{code}

Это решение имеет *недостатки*:

# *Семантическая непрозрачность:* {{ROW_LEVEL}} — использует название поля для его обозначения.
# *Доступность:* Требует знания системных переменных и понимания синтаксиса
  {{CASE WHEN}}. Доступно не всем пользователям.
# *Баги:* Встречаются ошибки, например, при попытке отредактировать уже сохраненный "вычисляемый" фильтр в сводной таблице, новые значения не применяются (требуется удаление и пересоздание фильтра).

----
h3. Бизнес-ценность.
Штатная реализация данного функционала позволит аналитикам эффективно и прозрачно отсекать ненужные агрегаты на конкретных аналитических разрезах (измерениях). Пользователи получат интуитивно понятный UI для настройки контекста фильтрации (аналог _LOD-выражений_, но адаптированный под текущую SQL-архитектуру нашего портала). Это закроет частые запросы клиентов на специфическую фильтрацию в сводных таблицах до момента полноценного внедрения архитектуры «Мер» (функции динамически адаптируются к контексту).

----
h3. 1. Пользовательский интерфейс.

Необходимо доработать окно настройки «Вычисляемого поля», при добавлении его на полку «Фильтры».

# *Новый блок настроек:* При выборе в выпадающем списке «Тип отбора» значения {{HAVING}}, под полем ввода формулы должен появляться новый блок *«Применять на уровнях детализации»*.
# *Переключатель режимов (_Radio buttons_):*
#* *Ко всем уровням* (поведение _по умолчанию_, сохраняет обратную совместимость).
#* *К выбранным измерениям* (_включает новый механизм_).
# *Динамический список чекбоксов:* При выборе опции *«К выбранным измерениям»* ниже разворачивается список чекбоксов. 
#* Список должен динамически формироваться из всех измерений (полей), которые в данный момент находятся на полке «Значения» данной сводной таблицы.
#* Названия чекбоксов соответствуют _алиасам_ этих полей (например: {{Год}}, {{Месяц}}, {{День}} и т.д.).
#* Пользователь может выбрать один или несколько уровней.
# *Исправление бага редактирования:* Необходимо обеспечить корректное обновление стейта вычисляемого фильтра при его повторном редактировании без необходимости пересоздания (исправление выявленного дефекта).

----
h3. 2. Функциональные требования.

Система должна перейти от логики привязки к {{ROW_LEVEL}} к логике привязки к *Аналитическому разрезу (Измерению данных)*.

# *Структура метаданных:* В JSON-конфигурации виджета/отчета для "вычисляемого" фильтра c {{HAVING}} должен сохраняться массив идентификаторов целевых колонок. 
#* *Пример:* {{target_dimensions: ['col_month']}}.
# *Алгоритм инъекции {{HAVING}} в {{SQL}}-запрос:* Когда бэкенд формирует SQL-запрос для раскрытия конкретного узла сводной таблицы, парсер должен проанализировать текущий блок {{GROUP BY}} (или эквивалентный контекст уровня агрегации).
#* *Правило:* Условие {{HAVING}} инжектируется в SQL-запрос *только в том случае*, когда набор полей в текущем {{GROUP BY}} логически соответствует уровню иерархии (измерению), выбранному в {{target_dimensions}}. Для подзапросов, формирующих промежуточные итоги более высоких или низких уровней, фильтр игнорируется. Если в настройках выбрано несколько "измерений", условие применяется к каждому из соответствующих уровней.
#* *Пример работы:* Аналитик настроил {{HAVING SUM(Sales) > 1000}} и отметил чекбокс *«Месяц»*.
#* Уровень 1 (Запрос общих итогов по Году): {{GROUP BY Year}}. Текущий уровень группировки ("Год") не совпадает с целевым ("Месяц"). Бэкенд *игнорирует* фильтр.
#* Уровень 2 (Раскрытие месяцев внутри года): {{GROUP BY Year, Month}}. Текущий уровень группировки ("Месяц") совпадает с целевым. Бэкенд *добавляет* {{HAVING SUM(Sales) > 1000}}.
#* Уровень 3 (Раскрытие дней внутри месяца): {{GROUP BY Year, Month, Day}}. Текущий уровень группировки ("День"). Бэкенд *игнорирует* фильтр (дни не фильтруются по условию месяца).
# *Устойчивость к перестроению:* Если пользователь на UI поменяет местами полки (сделает «Месяц» -> «Год»), логика бэкенда не сломается, так как фильтр будет искать физическое наличие колонки {{col_month}} в группировке, а не её порядковый номер.
# *Каскадное отсечение на UI:* Если на Уровне 2 («Месяц») строка была отфильтрована базой данных (не прошла условие {{HAVING}}), она не попадает в ответ бэкенда. Соответственно, на фронтенде этот узел не отрисовывается, и пользователь физически не может запросить Уровень 3 для отфильтрованного узла. Дополнительных доработок фронтенда для этого не требуется, так работает стандартная навигация дерева.

----
h3. 3. Интеграция фильтров.

*"Вычисляемый" фильтр с {{HAVING}} должен корректно работать не только как локальный фильтр виджета, но и при выносе на панель общих фильтров (панель фильтров справа).*

# Фильтр с {{HAVING}} и заданными {{target_dimensions}} должен передавать свой контекст (формулу + целевые измерения) во все связанные виджеты.
# Связанные виджеты (сводные таблицы, таблицы и пр.) применяют полученный контекст по тем же правилам Backend-генерации (см. Раздел 2). Если в связанной таблице нет измерения, указанного в {{target_dimensions}}, фильтр для данной таблицы игнорируется.
# *Ограничение:* Выбор типа элемента управления на панели фильтров должен ограничиваться типом данных, возвращаемых вычисляемым полем (числовой диапазон, период).

h3. 4. Критерии приемки (AC):

* *AC.1* При настройке вычисляемого поля на полке фильтров с типом `HAVING` пользователю доступен выбор: применять ко всем уровням или к конкретным измерениям. Список измерений корректно отражает текущие поля на полках строк/столбцов.
* *AC.2* Если фильтр настроен на измерение «Месяц», SQL-оператор `HAVING` физически присутствует в запросах к БД только при расчете агрегатов для уровня «Месяц». При расчете общих итогов (уровень «Год») и глубокой детализации (уровень «День») данное условие `HAVING` в генерируемых SQL-запросах отсутствует.
* *AC.3* При изменении порядка колонок в таблице привязка фильтра не сбивается. Условие {{HAVING}} продолжает применяться к выбранному ранее измерению, независимо от его нового уровня вложенности.
* *AC.4* Пользователь может успешно открыть ранее созданный вычисляемый фильтр {{HAVING}}, изменить формулу или целевые измерения, нажать «Сохранить», и новые настройки корректно применятся к таблице без перезагрузки виджета.
* *AC.5* В общей панеле фильтров настроенные "вычисляемые" фильтры с {{HAVING}} корректно фильтруют данные в связанных таблицах, согласно выбранным в настройках целевым измерениям.
* *AC.6* Существующие отчеты с фильтрами {{HAVING}} (и использованием {{\\!ROW_LEVEL\\!}}) продолжают работать без изменений. По умолчанию для старых фильтров выбран режим «Ко всем уровням».
