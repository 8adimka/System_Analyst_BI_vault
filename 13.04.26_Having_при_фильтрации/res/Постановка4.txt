Сводная таблица. Доработки. Настройка применения фильтрации HAVING к конкретным уровням иерархии в Cводной таблице


----

h3. 1. Контекст и проблематика
Сводная таблица в Modus BI представляет собой многоуровневую иерархическую структуру, которая под капотом генерирует дерево независимых SQL-запросов для каждого уровня раскрытия (или использует многоуровневые агрегации).

**Проблема:** В текущей реализации портала вычисляемое поле на полке "Фильтры" с типом отбора `HAVING` применяется *ко всем* уровням вложенности запроса. Это приводит к искажению данных.
> **Пример:** Аналитик хочет отфильтровать убыточные *месяцы* (`HAVING SUM(Sales) < 0`). При применении ко всем уровням система отсечет прибыльные дни внутри убыточного месяца (хотя они нужны для детализации) и скроет убыточные дни внутри прибыльного месяца, полностью ломая общие итоги на верхнем уровне (год).

**Текущее решение:**
Использование системной переменной {{\!ROW_LEVEL\!}} в вычисляемом поле - мы можем получить, к примеру, дополнительный столбец в свобной таблице с техническим обозначением уровня вложенности для каждой строки. И далее этот столбец мы можем использовать, чтобы понять куда нам нужно применять фильтр, например, так:
{code:sql}
CASE WHEN ROW_LEVEL = 'Месяц' THEN SUM("СуммаДоходРасходКО") END > 1000000
{code}

*Недостатки обходного пути:*
# *Семантическая хрупкость:* {{\!ROW_LEVEL\!}} использует строковое название
  поля (алиас). При переименовании колонки пользователем фильтр ломается
  без каких-либо ошибок — данные становятся некорректными.
# *Сложность:* Требует от аналитика знания SQL-синтаксиса ({{CASE WHEN}})
  и системных переменных портала. Недоступно рядовому пользователю.
# *Баг редактирования:* При попытке изменить уже сохранённый вычисляемый
  фильтр новые значения не применяются — виджет продолжает использовать
  старую версию. Единственный обходной путь — удалить фильтр и создать заново.

----
h3. 2. Цель.
Дать пользователям визуально понятный инструмент для управления контекстом фильтрации агрегатов. 
Это промежуточный, но самостоятельный архитектурный этап перед внедрением полноценных «Мер». Решение переводит фокус с написания сложных подзапросов на семантическую привязку фильтра к конкретному **смысловому измерению**.

----
h3. 3. Пользовательский интерфейс (UI/UX)

Доработки затрагивают настройки вычисляемого поля при его добавлении на полку «Фильтры» для виджета «Сводная таблица».

1. **Выбор типа фильтра:** Пользователь добавляет вычисляемое поле, открывает редактирование и выбирает тип отбора `HAVING` (если выбран `WHERE`, новые настройки скрыты).
2. **Новый блок «Применять на уровнях детализации»:**
   Появляется переключатель (Radio buttons):
   * `(•) Ко всем уровням` — поведение по умолчанию (обратная совместимость).
   * `( ) К выбранным уровням` — новый функционал точечного применения.
3. **Динамический список (Чекбоксы):**
   При выборе `К выбранным уровням` разворачивается список чекбоксов.
   * Список генерируется **динамически** на основе полей, размещенных на полках «Значения» в данный момент.
   * Названия в UI берутся из пользовательских алиасов полей (при наличии), а при отсутствии - технических идентификаторов.
   * Пользователь может выбрать **один или несколько** уровней.
4. **Обработка изменений:**
   * Если измерение удаляется из сводной таблицы, соответствующий чекбокс исчезает.
   * Если удалено единственное целевое измерение фильтра, выводится UI-предупреждение: *"Измерение [Имя] удалено из таблицы. Фильтр переведен в режим «Ко всем уровням»"*.

h3. 4. Backend-логика и генерация SQL

h4. 4.1. Метаданные виджета (JSON)
В JSON-конфигурации вычисляемый фильтр получает новый параметр `target_dimensions`:
```json
{
  "filters": [
    {
      "id": "filter_001",
      "type": "calculated",
      "filter_mode": "HAVING",
      "expression": "SUM(\"СуммаДоходРасходКО\")",
      "condition": "> 1000000",
      "apply_mode": "selected",
      "target_dimensions": ["col_month", "col_day"] 
    }
  ]
}
```
**Важно:** В массив `target_dimensions` сохраняются **стабильные внутренние идентификаторы** полей, а не их текстовые алиасы. Это делает фильтр устойчивым к переименованию колонок.

h4. 4.2. Алгоритм инъекции HAVING
Бэкенд не должен парсить генерируемый SQL. Он должен опираться на метаданные.
Для каждого SQL-запроса, отправляемого в БД для конкретного узла сводной таблицы:
1. Вычисляется **Измерение текущего узла (Current Node Dimension - CND)** на основе глубины раскрытия (`depth`). 
   *Пример: `depth = 1` -> CND = `col_month`.*
2. Бэкенд проверяет: входит ли `CND` в массив `target_dimensions` текущего фильтра?
   * Если **ДА** -> В конец SQL-запроса инжектируется условие `HAVING <expression> <condition>`.
   * Если **НЕТ** -> Условие полностью игнорируется для данного подзапроса.

h4. 4.3. Каскадное отсечение
Если узел (например, конкретный месяц) отсекается фильтром `HAVING` на своем уровне, строка не возвращается фронтенду. UI не отрисовывает этот узел, и у пользователя физически пропадает кнопка "разворота" для раскрытия нижележащих уровней. Дополнительной доработки компонента дерева не требуется.

h4. 4.4. Взаимодействие с Панелью общих фильтров (Дашборд)
* Если настроенный `HAVING`-фильтр вынесен на общую панель, он передает свой JSON во все связанные виджеты.
* Связанный виджет проверяет наличие идентификатора поля из `target_dimensions` в своих полках.
* **Игнорирование:** Если в виджете (например, в плоской таблице) нет указанного измерения, фильтр *игнорируется* (во избежание падения SQL-запроса).

h3. 5. Пример работы:
**Иерархия:** Год (`col_year`) -> Месяц (`col_month`) -> День (`col_day`).
**Настройка фильтра:** `target_dimensions = ['col_month']`, условие: `HAVING SUM("Доход") > 1000`.

**Узел Уровня 1 (CND = col_year):**
```sql
SELECT "Год", SUM("Доход") AS "Итого" FROM data 
GROUP BY "Год" 
-- HAVING игнорируется, так как col_year нет в target_dimensions
```

**Узел Уровня 2 (CND = col_month):**
```sql
SELECT "Год", "Месяц", SUM("Доход") AS "Итого" FROM data 
WHERE "Год" = '2026' 
GROUP BY "Год", "Месяц" 
HAVING (SUM("Доход") > 1000) 
-- HAVING применяется, так как col_month ЕСТЬ в target_dimensions
```

**Узел Уровня 3 (CND = col_day):**
```sql
SELECT "Год", "Месяц", "День", SUM("Доход") AS "Итого" FROM data 
WHERE "Год" = '2026' AND "Месяц" = '12' 
GROUP BY "Год", "Месяц", "День" 
-- HAVING игнорируется
```

h3. 6. Критерии приемки (Acceptance Criteria)

* **AC 1 (UI Настройки):** При выборе типа `HAVING` в вычисляемом фильтре отображается блок «Применять на уровнях детализации» с возможностью выбора конкретных измерений через чекбоксы.
* **AC 2 (Динамичность UI):** Список чекбоксов автоматически обновляется при добавлении/удалении полей на полках "Строки" и "Столбцы". Названия в чекбоксах соответствуют текущим алиасам полей.
* **AC 3 (Генерация SQL):** Условие `HAVING` физически добавляется в генерируемый SQL-запрос *только* в том случае, если текущий уровень группировки (CND) совпадает с одним из выбранных в `target_dimensions`. На остальных уровнях фильтр не применяется.
* **AC 4 (Мультивыбор):** Механизм корректно работает, если пользователь выбрал 2 и более измерений в чекбоксах (инъекция происходит на каждом из выбранных уровней).
* **AC 5 (Устойчивость):** Переименование полей в сводной таблице не ломает фильтр, так как привязка осуществляется по внутреннему ID поля.
* **AC 6 (Багфикс редактирования):** Внесение изменений в существующий `HAVING` фильтр (смена формулы, условия или набора чекбоксов) и нажатие "Сохранить" корректно обновляет стейт и инициирует перестроение таблицы без необходимости пересоздавать фильтр.
* **AC 7 (Глобальные фильтры):** При применении фильтра с панели общих фильтров дашборда к виджету, в котором отсутствует выбранное измерение, фильтр безопасно игнорируется без вызова SQL-ошибок.
* **AC 8 (Обратная совместимость):** Все старые отчеты продолжают работать как раньше. Для них по умолчанию установлен `apply_mode: "all"`. Переход со старой логики `!ROW_LEVEL!` не требует принудительной миграции метаданных.
* **AC 9 (Предупреждения):** При удалении из таблицы измерения, к которому был привязан сохраненный фильтр, появляется Toast/Inline уведомление о сбросе настроек фильтра на "Ко всем уровням".
