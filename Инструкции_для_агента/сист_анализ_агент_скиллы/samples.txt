2) "h3. Контекст и проблематика:

Ранее в Формах ввода данных (ФВД) был реализован функционал «Поиск без лимита» (серверный поиск) для компонента «Выпадающий список». Однако, в ходе эксплуатации и тестирования была выявлена проблема с фильтрацией при наличии дополнительных настроек компонента.

В конструкторе ФВД для выпадающего списка можно настроить *«Информационные поля»* — дополнительные колонки справочника, которые выводятся пользователю для большей информативности. Сейчас при серверном поиске фронтенд отправляет запрос, передавая в массиве {{where}} только *одно* поле (основное, без вспомогательных). 
В результате поиск осуществляется только по основному наименованию, игнорируя значения из выбранных информационных полей.

Следовательно, текущий серверный поиск в ФВД реализован неполно и не воспроизводит ожидаемую логику компонента.

h3. 1. Цель задачи:

*Требуется:*
Доработать серверный поиск компонента «Выпадающий список» в ФВД так, чтобы при включенном режиме *«Поиск без лимита»* поиск выполнялся {*}по всем полям, которые должны участвовать в поиске по конфигурации компонента{*}, а объединение условий происходило на бэкенде по логике *ИЛИ (OR)* в рамках *одного* запроса.

*Правило участия полей в поиске:*
 # *Основное поле* выпадающего списка участвует в поиске {*}всегда{*}.
 # *Информационные поля* участвуют в серверном поиске {*}только если{*}:
 ** они выбраны в секции {*}«Информационные поля»{*};
 ** для компонента включена опция {*}«Показ внутри меню»{*}.
 # Если {*}«Показ внутри меню» выключен{*}, серверный поиск выполняется {*}только по основному полю{*}.
 # Данная доработка {*}не должна менять существующую логику отображения и выводимых подсказок{*}; задача касается только корректного формирования и обработки серверного поиска.

*User Story:*
Как пользователь системы, я хочу находить нужную запись в выпадающем списке ФВД не только по основному наименованию, но и по дополнительным реквизитам (информационным полям), если они настроены для участия в поиске, чтобы быстро выбирать запись по любому известному мне атрибуту.

h3. 2. Описание целевого поведения:

Если для компонента «Выпадающий список» включён {*}«Поиск без лимита»{*}, то при вводе пользователем поисковой строки система должна выполнять *один* серверный поиск со следующей логикой:
 # Если дополнительные _информационные поля_ {*}не настроены{*}:
 ** поиск выполняется только по основному полю.
 # Если информационные поля {*}настроены{*}, но {*}«Показ внутри меню» выключен{*}:
 ** поиск выполняется только по основному полю;
 ** визуальное отображение дополнительных полей и текущее поведение подсказок сохраняются.
 # Если информационные поля *настроены* и {*}«Показ внутри меню» включен{*}:
 ** поиск выполняется по основному полю и по всем выбранным информационным полям;
 ** объединение условий выполняется по логике {*}OR (ИЛИ){*};
 ** запись должна попасть в результат, если поисковая строка найдена *хотя бы в одном* из участвующих полей.

*Пример целевой логики:*
Есть выпадающий список с основным полем {{name}} и выбранными информационными полями {{ent_name}} и {{{}inn{}}}.
При включенном *«Показ внутри меню»* и вводе строки {{ЛПХ Шишко}} backend должен отобрать записи по логике, эквивалентной (ориентировочно):
{code:sql}
name LIKE '%ЛПХ Шишко%' OR ent_name LIKE '%ЛПХ Шишко%' OR inn LIKE '%ЛПХ Шишко%'
{code}
*Важно:* пример приведён как {*}логическая модель поведения{*}, а не точный формат.

3) "h3. Контекст и проблематика.

В рамках основного аналитического портала для компонента «Иерархический фильтр» присутствует настройка «Поиск без лимита». В данный момент в иерархических фильтрах эта опция не работает. При её активации и вводе поискового запроса механизм серверного поиска не срабатывает.
Вместо этого компонент продолжает использовать локальный фронтовый поиск по уже загруженному (и ограниченному) пулу данных, игнорируя настройки серверного поиска.

В отличие от обычных фильтров портала (где безлимитный поиск успешно реализован), иерархический фильтр требует специфической доработки, так как при фильтрации он оперирует динамической структурой из нескольких полей (уровней иерархии).

Восстановить и доработать функционал серверного поиска для компонента «Иерархический фильтр» на основном портале.

*Требуется:*
# Реализовать полноценную логику опции «Поиск без лимита» (серверный поиск) для иерархических структур.
# Обеспечить автоматическое формирование условий поиска по *всем* уровням заданной конфигурации иерархии в рамках одного запроса на бэкенд.
# Внедрить корректную обработку сопутствующих настроек: «Количество символов для активации режима» и «Не загружать значения».

*User Story:*
* Как аналитик, я хочу иметь возможность включать серверный поиск в иерархическом фильтре, чтобы пользователи могли искать значения по всему справочнику на любом уровне вложенности иерархии по всему объему данных, не ограничиваясь первоначально загруженным пулом записей.

h3. 1. Описание текущего поведения (воспроизведение бага).

# Открыть любой отчёт основного портала с иерархическим фильтром, содержащим > 1 уровня иерархии (например, иерархия: *Город → Дата → Категория → Подкатегория*).
# В настройках отображения иерархического фильтра включить переключатель «Поиск без лимита» и задать «Количество символов для активации» = 3. Сохранить. Обновить страницу.
# Открыть выпадающий список иерархического фильтра и ввести 3 символа в поиск.
# *Ожидаемый результат:* запрос уходит на backend со всеми уровнями иерархии, возвращаются записи, совпавшие на любом уровне.
# *Фактический результат:* серверный запрос не отправляется, поиск выполняется на фронтенде по уже загруженному пулу данных.

h3. 2. Описание целевого поведения:

При активации настройки *«Поиск без лимита»* в иерархическом фильтре, локальный фронтовый поиск отключается.
Компонент должен осуществлять поиск на стороне сервера (через API), формируя единый запрос, в котором условия поиска применяются ко *всем* полям, составляющим заданную иерархию фильтра (массив {{order}}/{{select}}).

*Пример целевой логики формирования запроса:*
* Если, к примеру, иерархия фильтра состоит из 4-х полей: {{Gorod}}, {{Data}}, {{Kategorija}}, {{Podkategorija}}.
* При вводе пользователем поисковой строки (например, {{Астр}}), backend должен произвести поиск по логике *ИЛИ* (OR) по всем полям иерархии:

{code:sql}
Gorod LIKE '%Астр%' OR Data LIKE '%Астр%' OR Kategorija LIKE '%Астр%' OR Podkategorija LIKE '%Астр%'
{code}

* Результатом выдачи должны стать ветки иерархии, где *хотя бы на одном из уровней* найдено совпадение.

h3. 3. Требования к реализации:

h4. 3.1. Frontend-часть (Основной портал):
* *Формирование запроса:* В массив {{where}} поискового запроса должны прокидываться условия не только для верхнего элемента иерархии, а для *всех полей*, участвующих в иерархии фильтра (исходя из настроек компонента).
* *Поддержка дополнительных параметров* настройки «Поиск без лимита» (отображаются только если активна родительская настройка):
** Логика настройки *«Количество символов для активации режима»* должна работать: запрос уходит только если длина введенной строки >= заданному числу.
** Логика настройки *«Не загружать значения»* должна работать: при открытии дропдауна список пуст, данные появляются только после ввода необходимого числа символов и получения ответа от сервера.
* *UX:* При обновлении списка результатов фокус с инпута поиска *не сбрасывается*, перерендер всего компонента с потерей курсора не допускается.
* *Обратная совместимость:* Если «Поиск без лимита» *выключен*, компонент работает строго по прежнему сценарию — фронтовый поиск без каких-либо изменений.

После получения ответа от сервера компонент должен:
# Отобразить найденные записи в виде *иерархического дерева* — аналогично тому, как это работает в режиме фронтового поиска.
# Обеспечить возможность выбора найденной записи с автоматической активацией всех вышестоящих уровней иерархии.

h4. 3.2. Backend-часть:
* *Обработка массива OR:* Backend должен корректно принимать массив полей из иерархии в объекте {{where}} и объединять их оператором *ИЛИ (OR)*.
* *Один запрос:* Поиск по всем уровням иерархии должен выполняться строго в рамках *одного HTTP-запроса*.
* *Дедупликация:* В случае совпадения поисковой фразы на нескольких уровнях одной ветки, ветка не должна дублироваться в итоговом ответе.
* *Регистронезависимость:* Серверный поиск должен работать без учета регистра, аналогично тому, как сейчас работает локальный поиск на клиенте.
* *Обратная совместимость:* Изменения backend-контракта не должны ломать сценарии, где передаётся одно поле (текущие сценарии, обычные фильтры и прочие потребители API).
* *Переиспользование существующего механизма:* Если в backend уже реализован механизм OR-объединения условий (например, используемый в ФВД после предыдущих доработок) — необходимо *переиспользовать его*, а не создавать отдельную частную реализацию под иерархический фильтр.
* *Абстрактность:* Реализация должна быть достаточно универсальной, чтобы OR-поиск по массиву полей можно было задействовать в других компонентах платформы.
* *Сохранение сортировки:* Порядок выдачи, задаваемый настройками компонента ({{order}}-блок), не должен нарушаться при многопольном поиске.
* *Независимость от SQL-диалекта:* Решение должно поддерживать все хранилища, используемые платформой.

h3. 5. Критерии приёмки (AC):
* AC1. *Переключение режимов:* Если настройка «Поиск без лимита» выключена, иерархический фильтр продолжает работать на локальном поиске по загруженному лимиту, без изменений.
* AC2. *Разблокировка серверного поиска:* С включенной настройкой «Поиск без лимита» при каждом изменении поисковой строки отправляется HTTP-запрос к БД.
* AC3. *Отработка лимита символов:* Если задана настройка «Количество символов для активации режима» = *N*, запросы на сервер не уходят до тех пор, пока не будет введено *N* символов.
* AC4. *Серверный запрос отправляется:* При включённом «Поиске без лимита» с активированной настройкой «Количество символов для активации режима» (N = значение) и вводе ≥ N символов - фронтенд отправляет HTTP-запрос на backend.
* AC5. *Поиск по всем уровням:* В {{payload}} запроса передаются все поля, участвующие в иерархии фильтра, а не только корневой элемент.
* AC6. *Многопольный OR-поиск:* Backend корректно обрабатывает полученный массив полей, применяя логику ИЛИ {{OR}}. Найденные значения возвращаются, если совпадение есть на любом из уровней иерархии.
* AC7. *Регистронезависимость:* Серверный поиск находит значения независимо от регистра введенных символов (совпадение с текущим поведением локального поиска).
* AC8. *Ленивая загрузка:* Настройка «Не загружать значения» работает корректно. Изначально список пуст, результаты подгружаются только после ввода текста пользователем и ответа сервера.
* AC9. *Сохранение UX:* При вводе текста и обновлении выпадающего списка фокус ввода не теряется, курсор остается в поисковой строке.
* AC10. *Производительность:* Поиск не вызывает каскада лишних запросов к БД при быстром вводе, зависаний интерфейса или утечек памяти (возможно, следует применять debounce при быстром вводе).".
4) "h3. Контекст и проблематика.
* В реляционных базах данных оператор {{HAVING}} применяется для фильтрации результатов строго после 
выполнения агрегатных функций (после {{GROUP BY}}). 
* Сводная таблица в нашей системе зачастую представляет собой многоуровневую иерархическую структуру, 
которая под капотом генерирует дерево независимых SQL-запросов для каждого уровня раскрытия. 

* *Проблема:* В текущей реализации портала вычисляемое поле на полке «Фильтры» с типом отбора {{HAVING}} 
применяется либо ко всем уровням вложенности запроса, либо не применяется вообще. 
Это приводит к искажению данных: например, если аналитик хочет отфильтровать убыточные _месяцы_ ({{HAVING SUM(Sales) < 0}}), 
а система может отсечь и прибыльные дни внутри убыточного месяца, и убыточные дни внутри прибыльного месяца, 
ломая логику детализации и общие итоги.

h3. Текущее решение.
На данный момент корректная фильтрация агрегатов _по конкретному уровню иерархии_ в сводной таблице *не реализована*. 

Существует системная переменная {{\!ROW_LEVEL\!}}, которая при использовании в вычисляемом поле позволяет 
вывести дополнительный столбец в сводной таблице, где каждой строке соответствует технический идентификатор
поля её уровня вложенности. Однако, *применить на её основе {{HAVING}}-фильтр* к конкретному уровню иерархии 
в настоящий момент *не представляется возможным*.

Для виджета типа «Таблица» выбор типа отбора HAVING в UI уже доступен при добавлении вычисляемого поля на полку «Фильтры». 
Однако текущая реализация HAVING для плоских таблиц также содержит ряд некорректных поведений, 
которые устраняются настоящей постановкой (Раздел 2.3, 4.2). 

----
h3. Цель и бизнес-ценность.

Внедрение настройки применения {{HAVING}}-фильтра к конкретным уровням
иерархии (измерениям) позволит:

* Аналитикам точно управлять контекстом фильтрации агрегатов в иерархических
  сводных таблицах без знания системных переменных и SQL.
* Обеспечить корректную работу {{HAVING}}-фильтра в плоских таблицах с агрегацией — в том числе 
при использовании через общую панель фильтров.
* Закрыть частые клиентские запросы на специфическую фильтрацию в сводных таблицах.
* Создать семантически устойчивую привязку фильтра к *уровню иерархической вложенности* (для сводных таблиц).
* Сформировать архитектурный фундамент для последующего перехода к «Мерам»
  (динамическому контексту выполнения агрегаций).

*Это промежуточный, но самостоятельный этап* до момента полноценного внедрения архитектуры «Мер».

----
h3. Привязка к «Измерению» (полю иерархии).

Основная концепция: использовать *семантическую привязку к идентификатору поля* (колонки измерения).

В метаданных фильтра будет храниться *массив идентификаторов целевых измерений* — 
полей виджета, для уровней которых данный {{HAVING}}-фильтр должен быть активен. 
Бэкенд при генерации SQL-запроса для каждого уровня иерархии самостоятельно определяет
нужно ли инжектировать или игнорировать условие {{HAVING}}.

Для плоских таблиц понятие «уровня» отсутствует — там применяется упрощённый алгоритм, описанный в *Разделе 2.3*.

----
h3. 1. Пользовательский интерфейс.

Доработки затрагивают *настройки «Вычисляемого поля»* при его добавлении
на полку «Фильтры» виджета типа «Сводная таблица».

* *Шаг 1:*
Обеспечить базовую доступность {{HAVING}} как типа отбора для вычисляемых полей в {{UI}} сводной таблицы — 
аналогично уже реализованной функциональности для плоских таблиц. 
Это является самостоятельным подэтапом и открывает возможность использования {{HAVING}} через обходные пути 
даже до полного внедрения механизма привязки к уровням иерархии.
Аналитик перетаскивает вычисляемое поле на полку «Фильтры», нажимает *«Редактировать»* и вводит формулу 
(например, {{SUM("СуммаДоходРасходКО")}}), а в пункте *«Тип отбора»* (добавить в Сводные таблицы аналогично реализации в Таблицах) выбирает {{HAVING}}.

* *Шаг 2:* 
Появляется новый блок настроек *«Применять на уровнях детализации»*.
Блок отображается *только* при выборе типа отбора {{HAVING}}. При типе {{WHERE}} данный блок скрыт (не актуален).
Блок содержит *переключатель режима (Radio buttons)*:
** (•) *Ко всем уровням* — поведение по умолчанию; сохраняет _обратнуюсовместимость_. 
{{HAVING}} добавляется в SQL для каждого уровня иерархии, как это было раньше.
** ( ) *К выбранным уровням* — включает новый механизм точечного применения.

* *Шаг 3:* 
При выборе пункта «К выбранным уровням» разворачивается список чекбоксов.
Список формируется *динамически* на основе всех полей (измерений), которые в
данный момент размещены на полках «Строки/Категории», «Столбцы» и «Детализация» данной сводной таблицы.
Названия чекбоксов соответствуют алиасам полей (при наличии), а при отсутствии - техническим идентификаторам.
** Пользователь ставит галочки напротив интересующих его полей и нажимает «Сохранить».
Система сохраняет конфигурацию фильтра в JSON-метаданных отчёта. Пользователь может выбрать несколько уровней 
для применения фильтрации.

*Важно:*
* Чекбоксы обновляются динамически при изменении состава полей на полках.
* Если поле удалено из иерархии, соответствующий чекбокс исчезает. 
* Ранее выбранные чекбоксы для *оставшихся* полей сохраняют своё состояние и *не сбрасываются* 
при перестроении виджета (изменении порядка полей, добавлении новых измерений, переименовании).
* Если удалено единственное целевое измерение фильтра, система показывает предупреждение: 
_«Измерение [Имя] удалено из таблицы. Фильтр [Имя] переведён в режим "Ко всем уровням".»_ и 
автоматически переключает {{apply_mode}} в {{all}}.
* Порядок чекбоксов соответствует порядку полей в виджете.
* Tooltip при наведении на чекбокс: _«HAVING будет применяться только в запросах, 
где данное поле является текущим уровнем агрегации»_.

h3. 2. Backend-логика генерации SQL.

h4. 2.1. Структура метаданных фильтра.

В JSON-конфигурации виджета каждый вычисляемый фильтр с {{HAVING}} получает
новое поле {{target_dimensions}}. Состав JSON-конфигурации может быть *примерно* такой:

{code:json}
{
  "filters": [
    {
      "id": "847b1ec3-bbf8-4365-85fb-c4fca2a06e2e",
      "type": "calculated",
      "filter_mode": "HAVING",
      "expression": "SUM(\"СуммаДоходРасходКО\")",
      "condition": "> 1000000",
      "apply_mode": "selected",
      "target_dimensions": ["col_month"]
    }
  ]
}
{code}

| Поле | Тип | Описание |
| {{filter_mode}} | string | {{WHERE}} или {{HAVING}} |
| {{apply_mode}} | string | {{all}} — применять ко всем уровням иерархии; {{selected}} — только к явно выбранным |
| {{target_dimensions}} | string[] | Массив стабильных идентификаторов (ID) целевых полей-измерений. Пустой массив при {{apply_mode: "all"}} |

*Важно:* 
В {{target_dimensions}} хранятся *внутренние идентификаторы полей*
({{col_month}}, {{col_year}} и т.д.), а не пользовательские алиасы («Месяц»,
«Год»). Это обеспечивает устойчивость привязки к полю даже при переименовании
колонок пользователем.

----
h4. 2.2. Алгоритм инъекции {{HAVING}} для сводной таблицы (иерархической).

Данный алгоритм применяется *только* к виджетам типа «Сводная таблица» 
с иерархическим раскрытием.

Алгоритм использует *метаданные виджета* — упорядоченный массив 
всех полей-измерений, который известен бэкенду на момент формирования 
любого запроса к узлу дерева.

Разберём на примере иерархии Год → Месяц → День.
Каждый запрос порождается с параметром *глубины раскрытия* ({{depth}}) — 
позицией текущего узла в иерархии. На основе {{depth}} определяется
*измерение текущего узла* (Current Node Dimension, CND) — то поле,
для которого данный запрос рассчитывает агрегаты:

{code}
widget.all_dimensions = ['col_year', 'col_month', 'col_day']
// Упорядоченный массив всех полей-измерений виджета, используемых для построения иерархии запросов. 
// Он формируется из полей, размещённых на полках *«Строки/Категории», «Столбцы» и «Детализация»* в порядке их 
// иерархической вложенности. 
// Порядок и состав массива определяются бэкендом на основе актуальных метаданных виджета 
// на момент формирования каждого запроса.

depth = 0 → CND = 'col_year'   // запрос для узлов "Год"
depth = 1 → CND = 'col_month'  // запрос для узлов "Месяц" внутри Года
depth = 2 → CND = 'col_day'    // запрос для узлов "День" внутри Месяца
{code}

Определение CND происходит *исключительно из метаданных*, а не из парсинга
текста {{GROUP BY}}. Это делает алгоритм совместимым с любым способом
генерации SQL: как с простыми {{GROUP BY}}, так и с {{GROUPING SETS}} /
{{ROLLUP}} / {{CUBE}}.

*Алгоритм (выполняется для каждого HAVING-фильтра с {{apply_mode: "selected"}}):*

{code}
inject_having(filter, node_context):

  CND = widget.all_dimensions[ node_context.depth ]

  inject = CND ∈ filter.target_dimensions

  Если inject = TRUE  → инжектировать в запрос: HAVING <expression> <condition>
  Если inject = FALSE → условие HAVING полностью пропускается для данного узла
{code}

* {{filter.target_dimensions}} — массив ID целевых полей из метаданных фильтра
* {{CND}} — ID измерения текущего узла, вычисляется как: 
  {{widget.all_dimensions[node_context.depth]}}

Алгоритм совместим с любым способом генерации SQL, так как опирается исключительно
на метаданные, а не на структуру SQL-текста.

*Важно:* Алгоритм выполняется для каждого HAVING-фильтра с 
{{apply_mode="selected"}} независимо. При наличии нескольких таких фильтров 
каждый проверяется отдельно; все условия, для которых {{inject = TRUE}}, 
объединяются через {{AND}} в секции {{HAVING}}.

*Кейс мультивыбора* (аналитик выбрал несколько чекбоксов):

{code}
target_dimensions = ['col_month', 'col_day']:

  depth=0 → CND='col_year'  → FALSE → HAVING пропускается
  depth=1 → CND='col_month' → TRUE  → HAVING добавляется
  depth=2 → CND='col_day'   → TRUE  → HAVING добавляется
{code}

----
h4. 2.3. Алгоритм инъекции {{HAVING}} для плоской таблицы.

Плоская таблица не имеет иерархического дерева запросов — для неё 
всегда генерируется *один* SQL-запрос. Понятие «уровня вложенности» 
и алгоритм CND к плоской таблице *не применяются*.

Поля {{apply_mode}} и {{target_dimensions}} в конфигурации фильтра 
для плоской таблицы *игнорируются*. Вместо этого применяется следующий 
алгоритм:

{code}
inject_having_flat(filter, widget_context):

  has_aggregation = в метаданных виджета есть поля с агрегатными 
                    функциями (SUM, COUNT, AVG и т.д.) на полке «Значения»?

  Если has_aggregation = TRUE  → движок генерирует GROUP BY →
                                  инжектировать: HAVING <expression> <condition>

  Если has_aggregation = FALSE → GROUP BY отсутствует →
                                  HAVING безопасно игнорируется (без ошибки SQL,
                                  без уведомления пользователю)
{code}

Таким образом, один и тот же {{HAVING}}-фильтр из общей панели фильтров 
корректно применяется как к сводной таблице (по алгоритму CND из *Раздела 2.2*), 
так и к плоской таблице с агрегацией (по алгоритму из настоящего раздела).

----
h4. 2.4. Каскадное отсечение.

Если узел (например, конкретный месяц) отсекается условием {{HAVING}}
на своём уровне, строка *физически не возвращается* в ответе API.
Фронтенд не получает узел — не отрисовывает строку — не показывает кнопку «▶» для раскрытия дочерних уровней. 
Дополнительной доработки компонента дерева не требуется: каскадное скрытие является естественным следствием
стандартной навигации.
*Возможна обратная ситуация,* при которой агрегат родительского узла (например, "Год" на уровне depth=0) 
не попадает под условие HAVING (и строка отображается), однако при раскрытии этого узла HAVING 
применяется на уровне depth=1 (Месяцы) и отсекает все дочерние строки. 
В этом случае, фронтенд должен корректно обработать пустой ответ:
* Родительская строка отображается в сводной таблице без дочерних элементов (скрыть кнопку «▶» раскрытия).

----
h4. 2.5. Устойчивость к перестроению иерархии.

Фильтр хранит *стабильный идентификатор поля* ({{col_month}}), а не его
порядковую позицию в иерархии или пользовательский алиас («Месяц»).

* *Переименование поля* («Месяц» → «Мес.»): привязка фильтра не нарушается; 
алгоритм по-прежнему сравнивает {{CND}} с {{col_month}}.
* *Перестановка полей в иерархии* (Год → День → Месяц): значение {{depth}} для поля изменится, 
но алгоритм пересчитает {{CND}} корректно на основе актуального массива {{widget.all_dimensions}}.
* *Добавление нового измерения*: для нового поля {{HAVING}} не применяется 
(поле отсутствует в {{target_dimensions}}); поведение для остальных уровней не меняется.
* Ранее выбранные целевые измерения (*пилюли/чекбоксы*) при любом перестроении *не сбрасываются* — 
сохраняются в метаданных фильтра по стабильному идентификатору.

----
h3. 3. Интеграция с панелью общих фильтров.

Вычисляемый фильтр с {{HAVING}} и заданным {{target_dimensions}} должен корректно работать не только 
как *локальный фильтр виджета*, но и в *общей панели фильтров* (правая боковая панель фильтров).

h4. 3.1. Передача конфигурации.
Полная JSON-конфигурация фильтра передаётся во все связанные виджеты:
{{expression}} + {{condition}} + {{apply_mode}} + {{target_dimensions}}.

h4. 3.2. Применение к сводной таблице.
Каждый связанный виджет типа «Сводная таблица» применяет алгоритм из *Раздела 2.2*, 
используя собственные метаданные ({{widget.all_dimensions}}) для вычисления CND.

h4. 3.3. Применение к плоской таблице.
Каждый связанный виджет типа «Плоская таблица» применяет алгоритм из *Раздела 2.3*: 
если в виджете есть агрегатные функции — {{HAVING}} инжектируется в запрос; если нет — безопасно игнорируется.
Поля {{apply_mode}} и {{target_dimensions}} при этом не используются.

h4. 3.4. Несовместимый виджет (нет агрегации и нет совпадающих измерений).
Если связанный виджет не содержит агрегатных функций (плоский список сырых строк) или 
является типом виджета, для которого {{HAVING}} не применимо (диаграмма без группировки и т.д.), — 
условие {{HAVING}} *безопасно игнорируется* без ошибок SQL и без уведомлений пользователю.

h4. 3.5. Режим {{apply_mode: "all"}} в общей панели.
Фильтр передаётся в связанные виджеты как стандартный {{HAVING}} без привязки к уровню 
(текущее поведение, обратная совместимость). 
Правила безопасности из Разделов 2.3 и 3.4 применяются в полном объёме.

----
h3. 4. Устранение выявленных дефектов.

h4. 4.1. Баг: невозможность редактирования сохранённого вычисляемого фильтра.

*Описание:* При открытии ранее сохранённого вычисляемого фильтра (тип {{HAVING}}) в сводной таблице, 
изменении формулы или условия и нажатии «Сохранить» — новые значения не применяются. 
Виджет продолжает использовать старую конфигурацию фильтра. 
Единственный обходной путь — удалить фильтр и создать заново.

*Требование:* Обеспечить корректное обновление состояния (state) вычисляемого
фильтра при повторном редактировании. После нажатия «Сохранить» виджет должен
применить актуальную конфигурацию и инициировать перезапрос данных без
необходимости пересоздания фильтра.

h4. 4.2. Баг: несоответствие типа элемента управления в общей панели фильтров.

*Описание:* В настройках правой боковой панели фильтров дашборда вычисляемый 
{{HAVING}}-фильтр обозначается как «по диапазону», однако в режиме обычного использования 
правой боковой панели фильтров данный фильтр отрисовывается как «список выбора».

*Требование:* Тип компонента управления на панели фильтров должен строго 
соответствовать типу, выбранному при настройке данного фильтра.

h3. 6. Критерии приёмки (AC):
h4. AC.1 — Новый блок UI настроек HAVING
При добавлении вычисляемого поля на полку «Фильтры» сводной таблицы и выборе
типа отбора {{HAVING}} — под полем ввода формулы отображается блок
«Применять на уровнях детализации» с переключателем «Ко всем уровням» / «К выбранным уровням».

h4. AC.2 — Динамический список измерений
При выборе режима «К выбранным уровням» список чекбоксов корректно
отражает *актуальный* набор измерений (полей иерархии), размещённых на полках «Строки/Категории», 
«Столбцы» и «Детализация». Названия чекбоксов соответствуют пользовательским алиасам полей при их наличии, 
а при отсутствии - техническим идентификаторам. 
При изменении состава полок или переименовании полей — список обновляется автоматически; 
привязка сохранённых фильтров остаётся корректной (по идентификатору поля).

h4. AC.3 — Корректная генерация SQL: целевой уровень
* *Дано:* Иерархическая структура Год → Месяц → День с набором полей:
** depth = 0 → CND = 'col_year'   // запрос для узлов "Год"
** depth = 1 → CND = 'col_month'  // запрос для узлов "Месяц" внутри Года
** depth = 2 → CND = 'col_day'    // запрос для узлов "День" внутри Месяца
* *Когда:* Фильтр настроен с {{target_dimensions: ["col_month"]}},
* *Тогда:* Оператор {{HAVING SUM(...) > N}} физически присутствует в генерируемом SQL только для запросов, 
формируемых для узлов глубины {{depth=1}} ({{CND=col_month}}).
Факт наличия оператора {{HAVING}} в запросе проверяется в БД (например,
через {{EXPLAIN}} или логи запросов).

h4. AC.4 — Корректная генерация SQL: нецелевые уровни
Для тех же настроек фильтра оператор {{HAVING}} *отсутствует* в
генерируемых SQL-запросах для узлов Уровня 1 ({{depth=0}}, {{CND=col_year}})
и Уровня 3 ({{depth=2}}, {{CND=col_day}}).

h4. AC.5 — Устойчивость к перестроению иерархии
При переносе полей на полках сводной таблицы (изменение порядка,
добавление новых измерений) и при переименовании полей — привязка
{{HAVING}}-фильтра не сбивается. Условие продолжает применяться к
ранее выбранному измерению, определяемому по его стабильному _идентификатору_.

h4. AC.6 — Корректное редактирование сохранённого фильтра
Пользователь может открыть ранее созданный "вычисляемый" фильтр с {{HAVING}},
изменить формулу, условие или набор целевых измерений, нажать «Сохранить» —
и новые настройки корректно применяются к данному виджету и инициируют его обновление (перезапрос данных).

h4. AC.7 — Использование в общей панели фильтров
Вычисляемый {{HAVING}}-фильтр корректно применяет условие (с учётом {{target_dimensions}}) к связанным 
сводным таблицам согласно алгоритму из Раздела 2.2 из общей палели фильтров, однако если в связанном виджете 
(сводная или обычная таблица) отсутствует поле, чей идентификатор входит в {{target_dimensions}}, — 
фильтр игнорируется для данного виджета без ошибок SQL и без уведомлений пользователю.

h4. AC.8 — Корректный тип элемента управления для фильтров в общей панели фильтров
Вычисляемый {{HAVING}}-фильтр, назначенный в настройках панели фильтров под определённый тип элемента управления, 
на панели фильтров дашборда отображается в соответствии с выбранным типом.

h4. AC.9 — Обратная совместимость
Все существующие отчёты с {{HAVING}}-фильтрами (включая использующие функциональность
{{\!ROW_LEVEL\!}}) продолжают работать без изменений. Для них автоматически применяется режим 
{{apply_mode: "all"}} (эквивалент текущего поведения).
Миграция метаданных существующих фильтров не требуется.

h4. AC.10 — Предупреждение при удалении целевого измерения
Если пользователь удаляет из полок сводной таблицы поле, являющееся единственным
целевым для сохранённого {{HAVING}}-фильтра (его ID входит в
{{target_dimensions}}), система отображает предупреждение об этом событии.".

5) "h3. Контекст и проблематика.
Наша платформа предоставляет аналитикам возможность строить визуализации на основе *наборов данных трёх типов*: *произвольного* (обычный «пользовательский» SQL-запрос), *простого* или *составного*.
На сегодняшний день все вычисляемые выражения существуют исключительно в контексте конкретной визуализации — как «вычисляемые поля» виджета. Это порождает ряд системных ограничений:

* Одна и та же бизнес-логика дублируется в каждой визуализации, где она нужна, что ведёт к рассинхронизации определений при изменениях.
* Не существует возможности вынести агрегирующее вычисление на уровень набора данных — то есть определить его один раз и использовать в любых визуализациях, основанных на этом наборе данных.
* Аналитик лишён семантически выразительного инструмента: он вынужден либо дублировать формулы, либо включать агрегации непосредственно в основной SQL набора данных, теряя гибкость.

В индустриальных BI-системах данная потребность закрывается концепцией «Мер» — именованных вычислимых выражений, определённых на уровне источника данных и применяемых при построении визуализации.

----
h3. Цель и бизнес-ценность.
+Этап 1+: Меры реализуются только для *произвольного* (обычного) набора данных — типа набора с произвольным SQL-запросом.
Для *простых* и *составных* наборов данных механизм добавления Мер не реализуется в рамках текущей доработки.

Реализация Мер в рамках *произвольного* набора данных позволит:

* Аналитикам определять именованные вычислимые показатели один раз на уровне набора данных и переиспользовать их в любых визуализациях.
* Бэкенду корректно встраивать выражение Меры в нужную SQL-клаузу внешнего запроса в зависимости от полки размещения, используя текущий механизм построителя запросов (базовый слой запроса).
* Поддержать полный спектр сценариев использования: от агрегации значений и фильтрации по агрегатам до вычисляемых измерений и тултип-метрик.
* Устранить дублирование бизнес-логики и обеспечить единую точку изменения вычислений.
* Переиспользовать Меры в выражении друг друга и в вычисляемых полях, что значительно сократит сложность чтения формул.
* Заложить основу для последующего расширения Мер на *простые* и *составные* наборы данных.

----
h3. Ключевые понятия и определения в рамках постановки.

* +Мера+ — именованное вычислимое выражение, определённое на уровне +произвольного+ набора данных. Мера представляет собой SQL-выражение, при написании которого аналитиком могут использоваться поля данного набора данных, ранее определённые Меры и глобальные переменные.
Сама по себе Мера не вычисляется в момент создания; она вычисляется динамически в контексте конкретной визуализации — в зависимости от полки, на которую она размещена, её выражение инжектируется в строго определённую SQL-клаузу внешнего запроса.
Основой всех внешних ссылок на Меру (из визуализаций, настроек, формул других Мер и Вычисляемых полей) является +уникальное имя Меры ({{name}}) в рамках одного набора данных+.
* +Ссылочная целостность+ — Переименование или удаление Меры блокируется, если существуют объекты (визуализации, другие Меры или вычисляемые поля), которые используют данную Меру в своей логике.
* +Агрегация+ ({{aggregation_kind}}) — атрибут Меры, указывающий, содержит ли её выражение агрегатные функции. Задаётся пользователем при создании или редактировании: {{1}} — да (мера агрегированная), {{0}} — нет (неагрегированная). Используется для валидации размещения мер на полках и для визуального обозначения (ярлык *AGR* для агрегированных мер).
* +Мера считается агрегированной+ ({{aggregation_kind = 1}}), если её выражение содержит хотя бы одну агрегатную функцию: {{SUM()}}, {{AVG()}}, {{MAX()}}, {{COUNT(DISTINCT...)}} и их комбинации. Допустима только в {{SELECT}} и {{HAVING}}, но не в {{WHERE}} и {{GROUP BY}}.
* +Мера считается неагрегированной+ ({{aggregation_kind = 0}}), если её выражение не содержит агрегатных функций; работает на уровне отдельных строк. Допустима в {{SELECT}}, {{WHERE}}, {{GROUP BY}}.
* +Базовый слой запроса+ — текущий механизм построителя, в котором оригинальный SQL набора данных используется как источник внешнего запроса визуализации. Реализация допускает два эквивалентных варианта: {{FROM (<dataset_sql>) AS __base}} (derived table) или {{WITH __base AS (<dataset_sql>) ... SELECT ... FROM __base}} (CTE). Выбор между ними является технической деталью и не фиксируется как продуктовое требование.
* +Полка+ — именованная область в конструкторе визуализации, на которую аналитик размещает поля или Меры методом drag-and-drop. Конкретный набор полок зависит от типа визуализации.

----
h3. Пользовательский интерфейс и управление Мерами в настройках Набора данных.
В настройках аналитического портала, во вкладке «Наборы данных» мы выбираем «Источник данных» и +произвольный+ «Набор данных». Под секцией «Описание полей набора данных» добавляется новая секция «Меры».
Для +простых+ и +составных+ наборов данных секция «Меры» и кнопка «+ Добавить меру» **не отображаются** (функциональность не реализуется в рамках +Этапа 1+).

h4. Доступность кнопки «+ Добавить меру».
Кнопка «+ Добавить меру» активна *только* при одновременном выполнении всех условий:

# для набора задан SQL-запрос;
# запрос успешно прошёл проверку;
# система получила актуальный состав полей набора данных.

Если хотя бы одно условие не выполнено — кнопка находится в {{disabled}}-состоянии. При наведении на неё отображается пояснение: *«Задайте и проверьте SQL-запрос набора данных»*.
Если SQL-запрос отсутствует или не проходит проверку, кнопка «+ Добавить меру» остаётся {{disabled}}, но ранее сохранённые Меры *не удаляются* — их повторная валидация откладывается до появления корректного SQL и актуального состава полей.

h4. Интерфейс создания и редактирования Меры.
При нажатии «+ Добавить меру» или «Редактировать» на существующей Мере открывается *модальное окно увеличенного размера*.

Форма содержит следующие поля:
* *Название* (обязательное, строка) — отображаемое имя Меры; должно быть уникальным в рамках одного набора данных. Является ключом всех внешних ссылок на Меру.
* *Описание* (необязательное, строка) — пояснительный текст; отображается в tooltip при наведении на Меру.
* *Тип данных* (обязательное) — логический тип результата Меры: {{number}}, {{string}}, {{date}}, {{datetime}} и т.д. Система может предложить значение по умолчанию, но пользователь обязан иметь возможность изменить тип вручную. Если для выбранного типа доступны дополнительные настройки (например, для дат), они отображаются условно.
* *Агрегация* (обязательное, переключатель/флаг) — задаётся пользователем явно: {{да (1)}} / {{нет (0)}}. Используется для UX-валидации при размещении на полки.
* *Иерархия* (необязательное, строка) — имя группы/иерархии, в которой Мера отображается в панели полей.
* *Уровень* (необязательное, целое число) — порядок отображения Меры внутри иерархии.
* *Выражение* (обязательное) — кнопка доступа к редактору выражений.
** При нажатии на кнопку доступа к редактору выражений открывается окно ввода выражения (аналогичное окну ввода для SQL-запроса набора данных) с возможностью переключения в *Продвинутый режим*. При включении *Продвинутого режима* редактирования редактор расширяется на всё модальное окно (аналогично поведению расширенного режима для редактора в наборах данных [https://jira.modusbi.ru/browse/MB-4513]) открывая доступ для:
*** полей текущего набора данных и ранее созданных Мер (левая часть) — элементы доступны для вставки в выражение непосредственно из модального окна;
*** *полного* редактора выражений, эквивалентного редактору вычисляемых полей виджета.
* *Кнопки формы:* «Сохранить» / «Отмена».

Требования к редактору:
* Синтаксис и функции — идентичны вычисляемым полям.
* В редакторе доступен список полей текущего набора данных и ранее созданных Мер.
* Обычные поля набора данных в редакторе оборачиваются в *двойные кавычки*: {{"field_name"}}; Меры оборачиваются в квадратные скобки: {{[measure_name]}}. Это визуально разграничивает обращения к полям и к Мерам в теле формулы.
* Автодополнение должно различать и предлагать отдельно: поля набора данных и Меры. В выпадающем списке автодополнения Меры визуально отличаются от полей (например, цветом, значком или секцией).
* Подсветка синтаксиса должна отмечать разными цветами квадратные скобки (ссылки на Меры) от двойных кавычек (ссылки на поля).
* Подсветка синтаксических ошибок и другие продвинутые возможности нового редактора кода.

h4. Валидация при сохранении Меры.
При сохранении *выражения* Меры система выполняет:
* Синтаксическую проверку выражения;
* Проверку существования используемых полей текущего набора данных;
** Если выражение Меры *не содержит ссылок на поля набора данных* (например, использует только глобальные переменные или константы), то отсутствие полей не делает её автоматически невалидной — при корректном синтаксисе такая Мера остаётся валидной ({{valid}});
* Проверку существования Мер, на которые есть ссылки в формате {{[measure_name]}};
* Проверку отсутствия самоссылок и циклических зависимостей;
** При обнаружении цикла сохранение блокируется с ошибкой: *«Выражение Меры содержит циклическую зависимость»*;
* Проверку существования используемых глобальных переменных.

При нажатии «Сохранить» после редактирования меры *при переименовании:*
* При редактировании уже существующей Меры с изменением её наименования, система выполняет поиск зависимых объектов. Если обнаруживается, что Мера с прежним именем используется (в визуализациях, других Мерах или вычисляемых полях), то в момент сохранения отображается блокирующее сообщение об ошибке:
** *«Нельзя переименовать Меру, используемую в визуализациях и/или в выражениях. Для переименования Меры необходимо разрешить конфликты:
[Список ссылок на визуализации, меры и вычисляемые поля, где используется переименовываемая Мера]»*
* Переименование *не происходит* при наличии зависимых от меры объектов. Сохранение блокируется до ручного устранения зависимостей.
* Если зависимых объектов нет — сохранение с переименованием происходит штатно.
* Если наименование меры не менялось, сохранение изменений *других полей формы* (описание, тип данных, выражение и т.д.) происходит штатно даже при наличии зависимых объектов (выражение при этом проходит стандартные синтаксические проверки).

При успешном сохранении:
* Мера сохраняется в метаданных набора данных;
* в случае прохождения всех проверок, для Меры устанавливается статус {{valid}}.
* в случае непрохождения проверки (например, если она ссылается на удалённое поле набора данных из SQL), Мера получает статус {{invalid}}. 

* Если Мера меняет свой статус ({{valid}}/{{invalid}}), то все зависящие от неё Меры и Вычисляемые поля также проходят ревалидацию.
* Набор данных может быть сохранён даже при наличии Мер с невалидным статусом ({{status = invalid}}).

h4. Список Мер набора данных.
Сохранённые Меры отображаются в отдельной секции «Меры» в *табличном списке* под секцией «Описание полей набора данных».

Набор отображаемых колонок:
|| *Название* || *Тип данных* || *Агрегация* || *Иерархия* || *Уровень* || *Выражение* (кратко) || *Действия* ||
| <название меры> | <тип> | AGR / — | <иерархия> | <порядок> | <первые N символов> | [иконка редактировать] [иконка удалить] |

* Название Меры ({{name}}) должно быть уникальным среди всех Мер одного набора данных.
* В столбце «Выражение» показываются только первые {{N}} символов формулы. Полный текст записанной формулы доступен при наведении на сокращённое выражение (tooltip).
* Описание Меры выводится во всплывающей подсказке (tooltip) при наведении на её строку.
* Колонка *«Агрегация»* — для Мер с {{aggregation_kind = 1}} отображается ярлык {{AGR}}; для {{aggregation_kind = 0}} — прочерк ("—").
* Для Мер со статусом {{invalid}} строка подсвечивается как ошибочная (красный ореол, иконка ⚠). При наведении отображается причина невалидности (tooltip).
* Если заполнена «Иерархия», Мера относится к соответствующей display-группе. Внутри одной группы Меры сортируются по {{level}} по возрастанию, затем по названию. Меры без заполненной «Иерархии» отображаются в корневом уровне секции «Меры».

h4. Удаление Меры.
При нажатии иконки удаления Меры система определяет, используется ли Мера в каких-либо визуализациях, формулах других Мер или вычисляемых полях.

* *Если Мера не используется нигде:* система запрашивает подтверждение «Вы действительно хотите удалить хотите удалить Меру [имя]?», после подтверждения Мера удаляется (физически) из метаданных набора данных.
* *Если Мера используется* хотя бы в одном объекте: отображается блокирующее сообщение об ошибке:
*«Нельзя удалить Меру, используемую в визуализациях и/или в выражениях. Для удаления Меры необходимо разрешить конфликты:
[Список ссылок на визуализации, меры и вычисляемые поля, где используется удаляемая Мера]»*

Удаление блокируется. Физическое удаление записи о Мере из метаданных выполняется только после ручного разрешения всех конфликтов и повторного инициирования удаления.

h4. Жизненный цикл Меры после изменения SQL набора данных.
При каждом сохранении SQL-запроса набора данных система заново определяет актуальный состав полей и *автоматически валидирует все Меры* набора.

* Если выражение Меры не содержит ссылок на поля набора (например, использует только глобальные переменные или константы), то изменения состава полей набора *не влияют* на статус Меры — она остаётся {{valid}} при корректном синтаксисе выражения.
* Если Мера ссылается на отсутствующее поле (поле исчезло из нового SQL-запроса) или её выражение не может быть интерпретировано в контексте текущего набора данных:
** Мера получает статус {{invalid}};
** Мера подсвечивается в списке как ошибочная (красный ореол, иконка ⚠);
** При наведении отображается текст ошибки или причина невалидности;
** Мера *недоступна для добавления на полки* до исправления.
** После исправления выражения или восстановления требуемых полей Мера автоматически получает статус {{valid}}.

Если SQL-запрос набора данных очищен или не проходит проверку, кнопка «+ Добавить меру» остаётся {{disabled}} (новые Меры создать нельзя), но уже сохранённые Меры не удаляются; их повторная валидация откладывается до появления корректного SQL-запроса. 

* В интерфейсе визуализации такие Меры отображаются как ошибочные (красный ореол, иконка ⚠) и недоступны для добавления на полки до восстановления валидного статуса. 
* Мы можем редактировать и сохранить набор данных даже при наличии в нём Мер со статусом {{invalid}}.

h3. Структура метаданных Меры.
Мера сохраняется в JSON-метаданных набора данных. Ключом всех внешних ссылок на Меру является поле {{name}} — уникальное имя Меры в рамках одного набора данных.
{code:json}
{
 "measures": [
  {
   "id": "847b1ec3-bbf8-4365-85fb-c4fca2a06e2e",
   "name": "Валовая прибыль",
   "description": "Разница между выручкой и себестоимостью",
   "expression": "SUM("revenue") - SUM("cost")",
   "aggregation_kind": 1,
   "data_type": "number",
   "hierarchy": "Финансовые показатели",
   "level": 10,
   "status": "valid"
  }
 ]
}
{code}

|| Поле || Тип || Описание ||
| {{id}}       | string | Стабильный UUID идентификатор; не изменяется при переименовании. |
| {{name}}      | string | Отображаемое уникальное название в рамках одного набора данных; *является ключом связи* во всех внешних ссылках на Меру (в визуализациях, формулах и т.д.) |
| {{description}}  | string | Необязательное описание |
| {{expression}}   | string | SQL-выражение; Меры в формулах оборачиваются в квадратные скобки: {{[measure_name]}} |
| {{aggregation_kind}} | int (0/1) | Является ли мера агрегированной; *задаётся пользователем явно* (1 — да, 0 — нет) |
| {{data_type}}   | string | Логический тип результата: {{number}}, {{string}}, {{date}}, {{datetime}} и т.д. |
| {{hierarchy}}   | string | Необязательная группа/иерархия отображения в панели полей |
| {{level}}     | int  | Порядок Меры внутри иерархии |
| {{status}}     | enum  | {{valid}} или {{invalid}}; *вычисляется системой* по результатам валидации |

В метаданных визуализации каждое размещение Меры на полке фиксируется со ссылкой на {{measure.name}} и дополнительными параметрами ({{filter_mode}}, {{condition}}, а для HAVING-фильтра Сводной таблицы — {{apply_mode}} / {{target_dimensions}}).

---

h3. Метаданные визуализации и ссылки на Меры.
Во всех метаданных визуализаций связь с Мерой хранится по имени Меры ({{measure_name}}) — аналогично тому, как обычные поля набора данных адресуются по имени поля.
В связи с тем, что имя является ключом связи, система запрещает переименование и удаление Мер, если существуют объекты (визуализации или другие меры), ссылающиеся на это имя (см. логику разрешения конфликтов выше). Это гарантирует ссылочную целостность платформы.

Каждое использование Меры в визуализации хранит:

* тип сущности {{measure}};
* ссылку на {{measure_name}};
* дополнительные параметры в зависимости от конкретной полки и сценария.

Пример для фильтра по Мере:
{code:json}
{
 "filters": [
   {
     "id": "f9c35f8f-9f52-49a5-a47f-57badace6312",
     "type": "measure",
     "measure_name": "Валовая прибыль",
     "filter_mode": "HAVING",
     "condition": "> 0"
   }
 ]
}
{code}

|| Поле || Тип || Описание ||
| {{type}}    | string  | {{"measure"}} — отличает от вычисляемых полей ({{"calculated"}}) |
| {{measure_name}} | string  | Имя Меры; *является ключом связи* |
| {{filter_mode}} | string  | {{WHERE}} или {{HAVING}} |
| {{condition}}  | string  | Условие фильтрации |

h3. Отображение Мер в конструкторе визуализаций.

h4. Боковая панель полей (слева).
При выборе набора данных в конструкторе боковая панель разделена на секции:
* *«Поля»* — обычные поля и вычисляемые поля виджета (текущий вид без изменений).
* *«Меры»* — Меры набора данных (новая секция ниже).

Отображение Мер на боковой панеле полей (слева):
* Для Мер с {{aggregation_kind = 1}} рядом с названием отображается ярлык *AGR*.
* Tooltip при наведении отображает описание (если заполнено), тип данных и полный текст выражения.
* Меры со статусом {{invalid}} отображаются с иконкой ⚠ и недоступны для drag-and-drop на полки.
** Tooltip по невалидной Мере дополнительно содержит признак ошибки и краткую причину недоступности.

Отображение Мер на полке визуализации:
* Цвет иконки (пилюли) — *тёмно-оранжевый* (обычные поля — тёмно-синий).
* Для Мер с {{aggregation_kind = 1}} рядом с названием отображается ярлык *AGR*.
* Уже выбранные меры со статусом {{invalid}} отображаются в error-состоянии (с иконкой ⚠).
** привязка по {{[measure_name]}} сохраняется;
** запрос данных блокируется с понятным сообщением об ошибке до исправления Меры.

h4. Группировка и порядок Мер в конструкторе визуализаций.
* Если заполнена «Иерархия», Мера показывается в соответствующей display-группе внутри секции «Меры».
 Порядок Мер внутри группы определяется полем {{level}}, затем названием (по алфавиту).
* Если «Иерархия» не заполнена, Мера выводится в корневом уровне секции «Меры».

h4. Правила {{drag-and-drop}} и прочие селекторы полей.
Мера перетаскивается на полки так же, как обычное поле. При попытке разместить Меру на несовместимую полку (правила валидации описаны ниже) перетаскивание блокируется: курсор показывает «запрет», подсказка поясняет причину. Одна и та же Мера может быть размещена на нескольких полках одновременно.

* Меры могут использоваться не только на основных полках визуализации, но и во *всех элементах интерфейса*, где пользователь выбирает поля набора данных в текущей конфигурации визуализации, если бизнес-сценарий это допускает. К таким элементам относятся, в частности:
** настройки стилизации и форматирования;
** условное форматирование;
** сценарии расчётов по уровням;
** другие выпадающие списки, работающие с полями визуализации.

h4. Настройка пилюли на полке «Фильтры».
Попав на полку «Фильтры», Мера отображается в виде пилюли *салатового* цвета, аналогично с другими полями. При клике открывается окно настройки фильтра-Меры. Интерфейс настройки аналогичен стандартному интерфейсу фильтра по полю. Форма фильтра по Мере содержит:
* тип отбора: {{WHERE}} или {{HAVING}};
* условие фильтрации;
* дополнительные параметры, если они применимы для данного типа визуализации, как при использовании обычного поля.

h4. Ярлык {{AGR}} на пилюлях и полках.
* Для Мер с {{aggregation_kind = 1}} ярлык *{{AGR}}* отображается: в списке Мер набора данных, в боковой панели конструктора, на пилюлях полок.
* Для Мер с {{aggregation_kind = 0}} ярлык не отображается.
* Изменить {{aggregation_kind}} непосредственно на полке *нельзя*; атрибут фиксируется в настройках Меры.

h3. Валидация допустимости Мер по полкам.
Валидация допустимости Мер по полкам выполняется в двух точках:
* при попытке разместить Меру на полку или выбрать её в совместимом селекторе;
* при генерации SQL на бэкенде перед выполнением запроса.

В рамках +этапа 1+ UX-валидация опирается прежде всего на поле {{aggregation_kind}}.
Финальная SQL-валидация выполняется на бэкенде. Если фактическое выражение Меры не соответствует выбранному {{aggregation_kind}}, либо нарушает SQL-семантику итогового запроса, запрос отклоняется с понятной ошибкой.

h4. Правила валидации по полкам.
|| Полка || Допустимый тип Меры || Блокировать при нарушении? || Сообщение ||
| *Значения* | Любая | Нет блокировки; предупреждение при {{aggregation_kind = 0}} | *«Выражение помечено как неагрегированное. Для корректного отображения рекомендуется использовать агрегатную функцию, например: SUM(...)»* |
| *Фильтры (HAVING)* | Только агрегированная ({{aggregation_kind = 1}}) | Да | *«Мера помечена как неагрегированная. Выберите тип отбора WHERE или измените агрегатность в настройках Меры»* |
| *Фильтры (WHERE)* | Только неагрегированная ({{aggregation_kind = 0}}) | Да | *«Мера помечена как агрегированная. Выберите тип отбора HAVING или измените агрегатность в настройках Меры»* |
| *Строки / Столбцы* | Только неагрегированная ({{aggregation_kind = 0}}) | Да | *«На полках "Строки" и "Столбцы" допустимы только неагрегированные Меры»* |
| *Детализация* | Только неагрегированная ({{aggregation_kind = 0}}) | Да | *«На полке "Детализация" допустимы только неагрегированные Меры»* |
| *Дополнительные* | Любая | Нет блокировки; | -|

h3. Логика генерации SQL.

h4. Базовый слой запроса и алгоритм генерации.
Алгоритм выполняется каждый раз при формировании запроса данных для визуализации. Движок всегда строит внешний запрос над базовым слоем: исходный SQL набора данных подставляется без изменений как внутренний подзапрос. Затем в результирующий запрос инжектируются выражения Мер в соответствующие SQL-клаузы: {{SELECT}}, {{WHERE}}, {{GROUP BY}}, {{HAVING}} — в зависимости от полок, на которые они добавлены.

{code:sql}
SELECT
  <измерения с полок «Строки», «Столбцы»>,
  <неагрегированные Меры с полок «Строки», «Столбцы»>, -- вычисляемые измерения
  <измерения с полки «Детализация»>,
  <выражения Мер с полки «Значения»>     AS <alias>,
  <выражения Мер с полки «Дополнительные»>  AS <alias>
FROM (
  /*
   * [Оригинальный SQL произвольного набора данных подставляется без изменений]
   */
) AS __base
WHERE
  <обычные WHERE-фильтры>
  [AND <выражения Мер с полки «Фильтры», тип WHERE>]
GROUP BY 
  <измерения с полок «Строки», «Столбцы»>,
  <неагрегированные Меры с полок «Строки», «Столбцы»>,
  <измерения с полки «Детализация»>
  -- GROUP BY присутствует только если в SELECT есть хотя бы одно агрегированное выражение
HAVING
  <выражения Мер с полки «Фильтры», тип HAVING, условие_1>
  [AND <выражение_N, условие_N>]
  -- для Сводной таблицы — алгоритм inject_having() (target_dimensions, CND, depth)
{code}

Допустима эквивалентная реализация через {{WITH __base AS (...)}}:
{code:sql}
WITH __base AS (
  /* [Оригинальный SQL произвольного набора данных] */
)
SELECT ... FROM __base WHERE ... GROUP BY ... HAVING ...
{code}

*Продуктовым требованием является не конкретная форма записи, а корректная инъекция выражений Мер в итоговые SQL-клаузы внешнего запроса.*

h4. Поведение Меры в зависимости от полки.

h5. Полка «Значения».
Выражение Меры подставляется в {{SELECT}}. {{GROUP BY}} формируется из полей «Строки», «Столбцы» и «Детализации». Если Мера неагрегированная, она попадает в {{SELECT}} без агрегирования (аналитик несёт ответственность за корректность); при этом {{GROUP BY}} расширяется этим выражением.

h5. Полка «Фильтры», тип {{WHERE}}.
Выражение Меры подставляется в {{WHERE}} — фильтрация происходит *до* {{GROUP BY}}, то есть отсекаются отдельные строки базового источника. Механизм {{target_dimensions}} / CND *не применяется*.

h5. Полка «Фильтры», тип {{HAVING}}.
Выражение Меры подставляется в {{HAVING}} — фильтрация происходит *после* {{GROUP BY}}, то есть отсекаются агрегированные группы.
* Для *«Сводной таблицы»* применяется алгоритм инъекции {{HAVING}} из *п. 2.2* постановки по HAVING-фильтрации ({{target_dimensions}}, CND, {{depth}}).
* Для *«Плоской таблицы»* применяется алгоритм из *п. 2.3* постановки по HAVING-фильтрации: при наличии агрегированных выражений условие инжектируется в {{HAVING}}; если агрегации нет — условие игнорируется.

h5. Полка «Строки»/«Столбцы».
Допускаются только *неагрегированные* Меры ({{aggregation_kind = 0}}). Выражение попадает одновременно в {{SELECT}} и {{GROUP BY}} — создавая «вычисляемое измерение».

h5. Полка «Детализация».
Мера попадает в {{SELECT}} и расширяет {{GROUP BY}} дополнительным уровнем группировки.

h5. Полка «Дополнительные».
Мера не попадает в запрос.

h5. Несколько Мер на одной полке.
Несколько Мер на «Значениях» — каждая становится отдельной колонкой в {{SELECT}}. Несколько Мер на «Фильтрах» объединяются по типу: все WHERE-условия — в {{WHERE}} через {{AND}}, все HAVING-условия — в {{HAVING}} через {{AND}}. Допускается одновременное наличие WHERE-Мер и HAVING-Мер на «Фильтрах» — они попадают в соответствующие клаузулы независимо.

----
h3. Устойчивость к изменениям метаданных.
* *Строгая ссылочная целостность*: система запрещает переименование и удаление Меры, если она используется в визуализациях или выражениях других вычисляемых объектов. Разрыв связей по вине пользовательского переименования или удаления Меры исключён.
* *Изменение выражения Меры*: при пересохранении выражения Меры (формулы) все визуализации, использующие её, при следующем запросе данных автоматически получат обновлённую логику (кэши запросов инвалидируются).
* *Изменение SQL набора данных*: при каждом сохранении SQL-запроса система перевалидирует все Меры набора. Меры, ссылающиеся на удалённые поля, получат статус {{invalid}} (без автоматического удаления), а визуализации с ними перейдут в error-состояние до исправления логики аналитиком.

----
h3. Обратная совместимость.
При отсутствии Мер на полках движок формирует запрос *тем же способом, что и в текущей системе*. Добавление поддержки Мер *не изменяет поведение* существующих визуализаций, если Меры в них не используются. Существующие Вычисляемые поля виджетов не затрагиваются. Миграция существующих метаданных не требуется.

----
{panel:title=Интеграция с постановкой по HAVING-фильтрации.|borderStyle=dashed|borderColor=#0052cc|bgColor=#f0f4ff}

* Следует обратить внимание, что, на данный момент, фильтрации HAVING в визуализациях (кроме Сводной таблицы) работает только с вычисляемыми полями (добавленными на полку "Фильтры") и не поддерживает его использование как глобального фильтра.

Поддержка уровня-специфичной HAVING-фильтрации для Сводной таблицы ({{apply_mode}}, {{target_dimensions}}, CND, {{depth}}) является *отдельным расширением* и описывается в связанной истории ([MB-4304|https://jira.modusbi.ru/browse/MB-4304]).

h3. Критерии приёмки (AC):
*AC.1* — Доступность секции «Меры» и кнопки добавления.
* *Дано*: аналитик открыл настройки *произвольного* набора данных.
* *Тогда*: секция «Меры» отображается.
* *И*: кнопка «+ Добавить меру» активна только после того, как SQL набора данных задан, успешно проверен и из него получен актуальный состав полей.

*AC.2* — Создание и редактирование Меры.
* При создании/редактировании Меры доступны поля: {{name}}, {{description}}, {{data_type}}, {{aggregation_kind}}, {{hierarchy}}, {{level}}, {{expression}}.
* При сохранении система создаёт/обновляет Меру (проверки обязательных полей, уникальности, отсутствия циклических ссылок).

*AC.3* — Табличный список Мер.
* Сохранённые Меры отображаются в табличном списке со всеми ключевыми атрибутами (название, тип, агрегация и т.д.). Для агрегированных Мер отображается ярлык {{AGR}}.

*AC.4* — Видимость Мер в конструкторе.
* При построении визуализации в field picker отображается секция «Меры». Меры доступны для drag-and-drop и в совместимых селекторах (настройки стилизации, условное форматирование).

*AC.5* — Статус {{invalid}} из-за потери полей.
* *Дано*: Активная Мера ссылается на поле, которое было удалено из базового SQL набора данных.
* *Тогда*: Мера не удаляется автоматически, получает статус {{invalid}}, подсвечивается в UI и становится недоступна для добавления на полки. Если Мера уже на полке, визуализация блокируется с сообщением об ошибке.

*AC.6* — Инъекция SQL.
* При размещении Меры на полке её выражение корректно инжектируется во внешний запрос ({{SELECT}}, {{WHERE}}, {{GROUP BY}}, {{HAVING}}).

*AC.7* — Полка «Значения».
* При размещении Меры на полке «Значения» итоговый внешний SQL содержит выражение Меры в {{SELECT}}. Для неагрегированной Меры выводится предупреждение.

*AC.8* — Полка «Фильтры», тип WHERE.
* Мера с {{aggregation_kind = 0}} инжектируется в {{WHERE}}. Выбор {{WHERE}} для Меры с {{aggregation_kind = 1}} блокируется.

*AC.9* — Полка «Фильтры», тип HAVING.
* Мера с {{aggregation_kind = 1}} инжектируется в {{HAVING}}. Выбор {{HAVING}} для Меры с {{aggregation_kind = 0}} блокируется.

*AC.10* — Полки группировок.
* Размещение Меры с {{aggregation_kind = 1}} на полках «Строки», «Столбцы» или «Детализация» блокируется с сообщением.

*AC.11* — Блокировка переименования Меры при наличии конфликтов.
* *Дано*: Мера используется в визуализации или в выражении другой Меры.
* *Когда*: пользователь пытается сохранить Меру с изменённым полем {{name}}.
* *Тогда*: сохранение блокируется, система выводит список зависимых объектов с сообщением об ошибке. Изменения не применяются.
* *И*: При отсутствии переименования меры, изменение других полей (описание, формула) сохраняется штатно без блокировки.

*AC.12* — Блокировка и физическое удаление Меры.
* *Дано*: Мера A используется в формуле Меры B.
* *Когда*: пользователь нажимает кнопку удаления Меры A.
* *Тогда*: удаление блокируется, выводится сообщение о невозможности удаления с указанием на Меру B.
* *И*: если пользователь удаляет Меру C, у которой нет зависимостей, система запрашивает подтверждение и затем физически удаляет запись из метаданных набора.

*AC.13* — Обратная совместимость.
* При построении визуализации без использования Мер построитель сохраняет текущее поведение. Существующие отчёты не изменяются.".


6) "h3. Контекст и цель.

В рамках расширения возможностей Портала и ETL-контура необходимо реализовать поддержку источников данных, совместимых с протоколом {*}MySQL{*}, на уровне бэкенда.

На текущем этапе требуется реализовать {*}техническую основу интеграции{*}: подключение к MySQL-источнику, чтение схемы БД, корректное сопоставление типов данных, генерацию SQL-запросов в диалекте MySQL, а также поддержку базовых сценариев работы с данными.

*RLS, Формы ввода данных (ФВД), импорт из Excel и UI-ограничения карточки источника* в рамках данной истории *не реализуются*.

----

h4. 1. Требования.

h4. 1.1. Подключение MySQL как поддерживаемого источника на бэкенде.

* Бэкенд должен поддерживать тип источника {*}MySQL{*} как полноценный источник данных.
* Должна быть обеспечена возможность подключения к MySQL-серверу по стандартным параметрам соединения.
* Проверка подключения должна корректно отрабатывать для MySQL:
  ** при успешном соединении возвращается статус успешного подключения,
  ** при ошибке — возвращается текст ошибки, полученный от БД или драйвера.

h4. 1.2. Чтение схемы и метаданных MySQL-источника.

* Бэкенд должен получать и отдавать информацию о таблицах и полях MySQL-источника.
* Чтение схемы должно выполняться через {*}information_schema{*} MySQL.
* Должно быть обеспечено корректное отображение структуры БД для последующего использования в мастере набора данных и в редакторе SQL.

h4. 1.3. Поддержка типов данных MySQL.

* Необходимо обеспечить корректное сопоставление типов MySQL с внутренними типами платформы.
* В рамках маппинга должны корректно обрабатываться, в том числе:
  ** {{{}+TINYINT+{}}},
  ** {{{}+DATETIME+{}}},
  ** {{{}+VARCHAR+{}}},
  ** {{{}+BLOB+{}}},
  ** и другие распространённые типы MySQL.
* Поведение сопоставления должно быть аналогично уже реализованному маппингу для PostgreSQL.

h4. 1.4. Поддержка SQL-диалекта MySQL.

* Модуль генерации SQL должен быть расширен поддержкой MySQL-диалекта.
* Должна быть обеспечена корректная генерация запросов для:
  ** фильтрации,
  ** агрегации,
  ** вычисляемых полей,
  ** предпросмотра данных,
  ** работы с датами.
* Особое внимание должно быть уделено преобразованию даты и времени: UI-выбор аналитика должен транслироваться в синтаксически корректный SQL-запрос для MySQL.
* Набор вариантов и форматов должен соответствовать текущей реализации для PostgreSQL по смыслу и поведению.

h4. 1.5. Поддержка вычисляемых полей и фильтрации на стороне MySQL.

* Вычисляемые поля, созданные в наборе данных на базе MySQL-источника, должны корректно вычисляться.
* Фильтрация по полям MySQL-источника должна корректно транслироваться в SQL и возвращать ожидаемый результат.

h4. 1.6. Системные ограничения на уровне бэкенда.

* Бэкенд должен быть готов к тому, что часть возможностей платформы для MySQL на этом этапе не используется.
* Для функций, которые пока не поддерживаются этим источником, API должно возвращать корректную ошибку при попытке вызова.

h4. 1.7. Драйвер подключения.

* Рекомендуется подключение через нативный Go-драйвер (например, {{{}go-sql-driver/mysql{}}}) для максимальной производительности в ETL-слое.
* Если интеграция нативного драйвера потребует неоправданно высоких трудозатрат, допускается переиспользование существующего ODBC-моста.

----

h3. 2. Нефункциональные требования.

* Для MySQL-диалекта необходимо разработать тест-план, покрывающий:
  ** корректность генерации SQL-запросов,
  ** корректность маппинга типов данных,
  ** корректность преобразования дат,
  ** корректность работы соединения в сценариях успеха и ошибок.
* Тестирование должно проводиться на реальной MySQL-базе данных.

----

h3. 3. Критерии приёмки (AC):

*AC-1 — Подключение:*
Бэкенд поддерживает создание MySQL-источника и проверку подключения. При успешном соединении возвращается статус «Успешно», при ошибке — текст ошибки от БД/драйвера.

*AC-2 — Чтение схемы:*
Бэкенд корректно получает список таблиц и полей MySQL-источника через {{information_schema}} и передаёт эти данные для дальнейшего использования платформой.

*AC-3 — Типы данных:*
Типы MySQL (например, {{{}+TINYINT+{}}}, {{{}+DATETIME+{}}}, {{{}+VARCHAR+{}}}, {{+BLOB+}}) корректно сопоставляются с внутренними типами платформы.

*AC-4 — SQL и предпросмотр:*
Для MySQL-источника корректно генерируются SQL-запросы для предпросмотра, фильтрации, агрегации и вычисляемых полей, без синтаксических ошибок.

*AC-5 — Преобразование дат:*
Преобразования дат, выбранные в UI набора данных, транслируются в синтаксически корректный SQL для MySQL и возвращают ожидаемый результат.

*AC-6 — Вычисляемые поля:*
Вычисляемые поля на базе MySQL-источника корректно рассчитываются на стороне БД и доступны в ответах платформы.

*AC-7 — Тестирование:*
Для MySQL-диалекта подготовлен и выполнен тест-план на реальной MySQL-базе, покрывающий основные сценарии работы.".


7) "h3. 1. Пользовательская история
Как пользователь дашборда / аналитик,
Я хочу в режиме фильтра иметь возможность кликнуть на конкретный сегмент диаграммы (например, в столбчатой диаграмме я хочу выбрать столбец конкретной _Серии_ внутри _Категории_),
Чтобы отфильтровать набор данных одновременно по двум параметрам (Категория + Серия), а не только по целой Категории, получая более точный срез данных.

----
h3. 2. Контекст и проблематика
Текущая реализация режима фильтра в столбчатых, линейных диаграммах и диаграммах площади работает исключительно на уровне Категорий (ось X). 
При наличии детализации по Сериям (разбивка столбца на составные части или несколько линий/областей) клик по любому элементу применяет фильтр только по Категории.
Бизнес-заказчик запрашивает возможность точечной фильтрации: при клике на сегмент «А» внутри категории «1», в фильтр должен передаваться составной предикат: {{Категория = «1» AND Серия = «А»}}.

----
h3. 3. Рамки задачи:

* Столбчатая диаграмма, включая стекинг,
* Линейная диаграмма,
* Диаграмма площади.

Сценарии, где полка «Серии» пуста, а на полке «Значения» лежит несколько метрик остаются за рамками этой задачи - сложная фильтрация не применяется. Расширенная логика фильтрации применяется только при наличии одной _Категории_ и нескольких _Серии_ внутри неё.

h3. 4. Критерии приемки (AC):
* *AC1. Настройка режима фильтрации:*
Для целевых типов диаграмм в настройках виджета (_режим фильтра_) поддерживается включение "продвинутого режима" фильтрации. Если на полке _«Серии»_ есть данные, диаграмма переходит в расширенный режим фильтрации и при фильтрации учитывает как выбранную _«Категорию»_, так и выбранные _«Серии»_.

* *AC2. Активация фильтрации:*
** Если пользователь кликает непосредственно на визуальный элемент конкретной _Серии_ (сегмент столбца, буллет/маркер на линейной диаграмме или диаграмме площади) - применяется составной фильтр. 
*Ожидаемый результат:* Корректно подсвечивается выбранный сегмент на столбчатой диаграмме и диапазон на диаграмме площади (остальные элементы затухают, если это поддерживает тип диаграммы). В связанный контекст передается 2 значения (Категория + Серия). 
** Если пользователь кликает не на конкретный визуальный элемент _Серии_, но остаётся в рамках _Категории_ (в зоне действия курсора) ИЛИ кликает непосредственно по текстовой подписи самой категории (на оси _X_), то применяется обычный фильтр (как это работает сейчас).
*Ожидаемый результат:* Корректно подсвечивается выбранная _Категория_ (и все входящие в неё _Серии_) на столбчатой диаграмме или диапазон на диаграмме площади (остальные элементы затухают, если это поддерживает тип диаграммы). В связанный контекст передается 1 значение (Категория)

* *AC3. Множественный выбор:*
Пользователь может выбрать несколько специфичных сегментов (например, удерживая Ctrl на Windows или Cmd на Mac) из разных категорий или серий. Фильтры должны корректно дополнять друг друга. Повторный клик по выделенному элементу снимает с него фильтр.

* *AC4. Для линейных и диаграмм площади - доступность клика без явных маркеров (буллетов):*
Функция фильтрации по _«Категории»_ должна корректно работать даже если визуальное отображение маркеров (буллетов) не осуществляется (минимальный размер маркеров в настройках _Стилизации_ виджета).
Активная зона клика должна опираться на перехват событий объекта Cursor или скрытые хитбоксы, а не зависеть исключительно от видимости графического элемента (маркеров).

h3. 5. Технические заметки и векторы исследования для разработчиков:
* Использование объекта {{Cursor}}: Для определения того, на какую именно _Категорию_ кликнул пользователь, рекомендуется исследовать возможности объекта {{Cursor}} в библиотеке диаграмм. Перехват {{ID}} элемента через курсор позволит избежать проблем с «некликабельными» областями и обойти зависимость от размера/видимости маркеров.

* Известные ограничения библиотеки: На диаграммах площади и линейных диаграммах при включенном параметре «Сглаживание» (smooth) библиотека может не позволять корректно закрашивать/выделять отдельные сегменты. Необходимо провести технический спайк для определения того, как визуально подсвечивать выбранный элемент в таких условиях (например, принудительный рендеринг увеличенного маркера поверх линии для выбранной точки).

* Единая кодовая база: столбчатая, линейная и диаграмма площади базово являются наследниками компонента {{Serial Chart}}. Решение должно быть максимально унифицированным для всей группы.

8) "h3. 1. Цель доработки.

Обеспечить корректную и предсказуемую работу визуализации «Граф» при фильтрации, агрегации и совместном использовании нескольких наборов данных.

Текущая архитектура визуализаций портала предполагает использование одного набора данных на одну визуализацию. Для визуализации «Граф» данный подход оказался неэффективным и приводит к следующим проблемам:

* усложнение структуры данных;
* дублирование информации;
* некорректная работа фильтрации;
* потеря узлов и связей при фильтрации;
* невозможность корректно реализовать классическую графовую модель;
* невозможность полноценно использовать независимые сущности «узлы» и «связи».

Цель данной доработки:

* перевести визуализацию «Граф» на классическую двухтабличную модель построения графов;
* обеспечить поддержку нескольких наборов данных в рамках одной визуализации;
* сохранить полную обратную совместимость со всеми существующими визуализациями;
* обеспечить корректную интеграцию с визуализациями «Таблица» и «Сводная таблица»;
* обеспечить корректную работу всех сценариев фильтрации.

----
h3. 2. Концепция нового решения.

В рамках данной доработки визуализация «Граф» должна перейти на классическую графовую архитектуру:
* отдельный набор данных — «Узлы графа»;
* отдельный набор данных — «Связи графа».

Визуализация должна уметь одновременно использовать несколько наборов данных.

----
h4. 2.1. Набор данных «Узлы графа».

Набор данных содержит:
* все узлы графа;
* свойства узлов;
* параметры отображения узлов.

Каждая строка набора данных соответствует одному узлу.

----
h4. 2.2. Набор данных «Связи графа».

Набор данных содержит:
* связи между узлами;
* свойства связей;
* параметры отображения связей.

Каждая строка набора данных соответствует одной связи между двумя узлами.

----
h3. 3. Основная архитектурная проблема.

В текущей реализации все визуализации используют ссылку на поле набора данных через его наименование ({{name}}).

На текущий момент:

* {{name}} уникально только в рамках одного набора данных;
* {{name}} не гарантирует уникальность между несколькими наборами данных;
* при использовании нескольких наборов данных могут возникать конфликты ссылок на поля.

Это делает корректную работу визуализаций затруднительной и нестабильной при использовании более одного набора данных одновременно.

Для реализации новой архитектуры «Графа» требуется устранить данное ограничение.

----
h3. 4. Требуемая архитектурная доработка платформы.

h4. 4.1. Добавление нового поля {{display_name}}.

Необходимо добавить новое поле в метаданные Наборов данных:
* {{display_name}} - уникальное наименование поля, в рамках датасета.
* например, если пользователь попытается создать два поля с {{display_name = "city"}} в одном датасете — система должна это запрещать валидацией. 

Назначение поля:
* хранение отображаемого имени поля в Наборе данных - т.е. замена поля {{name}}.

----
h4. 4.2. Изменение назначения поля {{name}}.

После реализации доработки поле {{name}} должно использоваться как:
* системный уникальный идентификатор поля в Наборе данных.

Требования:
* {{name}} должен быть глобально уникальным;
* для новых наборов данных данное поле автоматически заполняется UUID;
* значение {{name}} не должно использоваться в UI или отображаться пользователю, вместо него в интерфейсе и редакторе выражений должно отображаться {{display_name}}.

Пример:

|| Поле || Значение ||
| {{name}} | {{2f3d7a9f-9a5b-4a3c-84db-61e1f9df01a3}} |
| {{display_name}} | {{client_name}} |

----
h4. 4.3. Миграция существующих данных.

Необходимо выполнить миграцию.

Алгоритм миграции:
# добавить поле {{display_name}};
# для всех существующих Наборов данных:
## скопировать текущее значение {{name}} в {{display_name}};
## текущее значение {{name}} оставить без изменений;
# для всех новых полей:
## в {{name}} автоматически записывать UUID при создании поля;
## в {{display_name}} записывать отображаемое имя.

----
h4. 4.4. Обратная совместимость.

Необходимо полностью сохранить работоспособность всех существующих визуализаций.

Требования:
* все существующие визуализации продолжают использовать {{name}} как ссылочный идентификатор поля;
* существующие Наборы данных продолжают работать без изменений;
* существующие дашборды не требуют миграции конфигурации;
* существующие API-контракты не должны быть нарушены;
* сериализация/десериализация конфигураций должна оставаться совместимой.

h4. 4.5. Изменение отображения имени поля в UI.

Во всех пользовательских интерфейсах платформы необходимо заменить отображение:
* с {{name}}
* на {{display_name}}.

Это касается:
* конструктора Наборов данных;
* конструктора визуализаций;
* отображения полей Наборов данных в редакторе кода для Вычисляемых полей и Мер;
* редактора фильтров;
* настройки агрегаций;
* настройки сортировок;
* настройки drill-down;
* настройки tooltip;
* API получения метаданных;
* любых селекторов полей;
* любых форм настройки визуализаций;
* и т.д.

Пользователь не должен видеть UUID или содержимое поля {{name}} в интерфейсе - используется только для корректных уликальных ссылок на поля Наборов данных.

h4. 4.6. Механизм разрешения ссылок на поля (паттерн Symbolic Reference Resolution).

Все ссылки на поля Наборов данных в конфигурациях, фильтрах, выражениях и API используют единый механизм разрешения ссылок.

*Принцип работы:*
* Пользователь всегда работает с {{display_name}} как с символическим именем поля.
* Система при сохранении любой ссылки на поле резолвит {{display_name}} → {{name}} и сохраняет {{name}} как идентификатор.
* При открытии конфигурации, редактора выражений или любого UI-компонента — выполняется обратная трансляция {{name}} → {{display_name}} для отображения пользователю.
* {{display_name}} *никогда не сохраняется* в конфигурациях и выражениях как ссылочный идентификатор.

*Единая логика для всех Наборов данных:*
Механизм работает одинаково для всех Наборов данных — как старых, так и новых:
* Для новых Наборов данных: {{name = "2f3d7a9f-..."}}, {{display_name = "city"}} → пользователь видит {{"city"}}, в конфигурации хранится {{UUID}}.
* Для существующих Наборов данных: {{name = "city"}}, {{display_name = "city"}} → трансляция тривиальна, результат идентичен. Логика та же самая — частный случай совпадения значений.

*Требование к уникальности:*
{{display_name}} должен быть уникальным в рамках одного Набора данных. При попытке создать два поля с одинаковым {{display_name}} в одном Наборе данных система должна возвращать ошибку валидации.

h3. 7. Фильтрация данных.

h4. 7.1. Основная цель доработки.

Основная цель данной переработки — обеспечить корректную фильтрацию данных для построения визуализации «Граф».

Текущая проблема:

* при использовании одной плоской таблицы фильтрация удаляет строки содержащие узлы и связи;
* при наличии строки с узлом-источником, связью, но отсутствием строки, содержащей узел-приёмник - визуализация не может корректно построить данную связь;
** граф становится неполным;
** визуализация теряет консистентность.

Новая архитектура должна устранить данную проблему.

----
h4. 7.2. Фильтрация Набора данных «Узлы».

Фильтрация по полям узлов должна:

* применяться только к Набору данных «Узлы»;
* ограничивать набор отображаемых узлов.

После фильтрации узлов:

* визуализация должна автоматически попытаться построить связи;
** при наличие связи, содержащей отсутствующие узлы, такая связь должна быть пропущена и не отрисовываться.
* должны остаться только связи между отображаемыми узлами.

----
h4. 7.3. Фильтрация Набора данных «Связи».

Фильтрация по полям связей должна:

* применяться только к Набору данных «Связи»;
* скрывать только связи;
* не удалять узлы автоматически;
* при наличие узлов без связей - они отображаются как изолированные узлы в штатном порядке.

----
h4. 7.4. Режимы интерактивной фильтрации визуализации «Граф».

h5. 7.4.1. Проблема и мотивация.

При применении фильтра к Набору данных «Узлы» (раздел 7.2) базовая логика фильтрации удаляет из отображения все узлы, не прошедшие фильтр. Это поведение является корректным для большинства аналитических задач, однако для графовой визуализации оно разрушает контекст: узел, оставшийся после фильтрации, теряет все свои связи, поскольку все соседние узлы были удалены.

Целевое поведение при клике на узел или применении фильтра к графу — отображение не только *самого отфильтрованного узла, но и всех узлов, с которыми он непосредственно связан*, вместе с соответствующими рёбрами.

Для поддержки различных аналитических сценариев необходимо предоставить пользователю явный выбор режима фильтрации через настройки визуализации.

h5. 7.4.2. Настройка: Режим охвата фильтрации («С соседями»).

В панели настроек компонента «Граф» добавляется переключатель:

«С соседями» (Тумблер (Toggle), ВКЛ - по умолчанию (1) / ВЫКЛ (0)):

|| Значение || Поведение ||

| «С соседями» - ВКЛ (по умолчанию) | После фильтрации отображаются отфильтрованные узлы и все их непосредственные соседи (+1 уровень), а также все рёбра между ними. |
| «С соседями» - ВЫКЛ | После фильтрации отображаются только узлы, прошедшие фильтр, и только рёбра строго между ними. Узлы, не прошедшие фильтр, скрываются полностью, даже если они связаны с отфильтрованными узлами. |

Режим «С соседями» — ВКЛ, детальное поведение:

* Когда пользователь применяет фильтр (например, node_category = "Премиум") или кликает на конкретный узел при включённом режиме кросс-фильтрации, для корректной отрисовки Графа BI-ядро выполняет запрос в три шага:

# Определяет множество узлов-кандидатов — тех, что прошли фильтр.
# Из Набора данных «Связи» выбирает все рёбра, у которых хотя бы один конец (source_node_id {{ИЛИ}} target_node_id) принадлежит множеству узлов-кандидатов.
# Из этих рёбер извлекает все упомянутые node_id — они становятся итоговым множеством отображаемых узлов, даже если сами не прошли исходный фильтр.

Пример: Узлы A (Премиум), B (Стандарт), C (Премиум), D (Стандарт). Рёбра: A→B, B→C, B→D.
Фильтр category = "Премиум" → кандидаты: {{A, C}}. Рёбра, инцидентные {{A, C}}: т.к. A→B, B→C. Итоговые узлы: {{A, B, C}}. Итоговые рёбра: A→B, B→C. Узел B отображается как сосед, несмотря на то что категории «Премиум» не имеет.

Режим «С соседями» — ВЫКЛ, детальное поведение:

* BI-ядро возвращает только узлы, прошедшие фильтр, и только рёбра, у которых оба конца входят в множество отфильтрованных узлов. Узлы, прошедшие фильтр, но не имеющие связей с другими отфильтрованными узлами, отображаются как изолированные.

Тот же пример, строгий режим: Итоговые узлы: {{A, C}}. Ребро A→B — пропускается (B не прошёл). Ребро B→C — пропускается (B не прошёл). Итог: A и C отображаются как изолированные точки без связей между собой (прямой связи A→C нет).

h5. 7.4.3. Настройка: Режим «Направление фильтрации».

В панели настроек компонента «Граф» добавляется переключатель:

«Направление фильтрации» (Выпадающий список (Dropdown), 3 значения):

|| Значение || Поведение ||

| «Все направления» (по умолчанию) | В режиме «С соседями»: фильтр применяется к узлам независимо от их роли в ребре. Узел попадает в результат, если он является источником или приёмником хотя бы одного ребра, связанного с отфильтрованным узлом. |

| «Только исходящие» | В режиме «С соседями»: к отфильтрованным узлам добавляются только узлы, являющиеся target_node_id в рёбрах, где отфильтрованный узел — {{source_node_id}}. |
| «Только входящие» | В режиме «С соседями»: к отфильтрованным узлам добавляются только узлы, являющиеся source_node_id в рёбрах, где отфильтрованный узел — {{target_node_id}}. |

Примечание: Настройка «Направление фильтрации» влияет на состав узлов, добавляемых к отфильтрованным узлам, в режиме «С соседями» - ВКЛ. В режиме «С соседями» - ВЫКЛ (строгий режим) настройка «Направление фильтрации» остаётся недоступна ({{disabled}}).
В строгом режиме отображаются только рёбра между узлами, оба конца которых прошли фильтр — направление ребра не влияет на состав итогового множества узлов.

h5. 7.4.4. Настройка: Режим взаимодействия при клике.

В панели настроек компонента «Граф» добавляется переключатель:

«Режим клика на узел»:

|| Значение || Поведение ||

| «Выделение» (по умолчанию) | При клике на узел активируется локальное выделение средствами ECharts: выбранный узел и его инцидентные рёбра подсвечиваются, остальные узлы становятся полупрозрачными. Данные не перезапрашиваются, состав графа не меняется. |
| «Кросс-фильтрация» | При клике на узел BI-ядро применяет жёсткий фильтр к Набору данных «Узлы» по {{node_id}} кликнутого узла. Граф перерисовывается с учётом текущих настроек режимов «С соседями» и «Направления фильтрации», соседние виджеты дашборда фильтруются по выбранному {{node_id}}. |

Важно: В режиме «Кросс-фильтрация» + «С соседями»(ВЫКЛ) — клик на узел приведёт к отображению только самого узла как изолированной точки, поскольку соседи будут отсечены. Это поведение является ожидаемым следствием комбинации настроек и должно быть явно задокументировано в справке для аналитиков.

h5. 7.4.5. Поведение при отсутствии результата.

Если после применения фильтра итоговый набор узлов оказывается пустым:
* визуализация отображает пустое полотно, при наведении появляется информационная подсказка: «Нет данных, соответствующих условиям фильтра»;
* ошибки и падения визуализации не возникает;
* при снятии отсекающего фильтра граф восстанавливает отображение узлов прошедших фильтрацию, в соответствии с текущими настройками визуализации «Граф».

h3. 12. Критерии приёмки (AC):

*AC.1* — Визуализация строится на двух независимых Наборах данных.
* *Дано*: настроена визуализация «Граф» с Набором данных Узлов (10 строк) и Набор данных Связей (15 строк).
* *Когда*: дашборд загружается без каких-либо фильтров.
* *Тогда*: на полотне отображаются все 10 узлов и все корректные связи между ними; отсутствуют дублирующиеся узлы; визуализация не падает и не выводит ошибок.

*AC.2.1* — Фильтрация узлов: «С соседями» — ВЫКЛ.
* *Дано:* граф с узлами A, B, C и связями A→B, B→C, A→C; режим «С соседями» — ВЫКЛ.
* *Когда:* пользователь применяет фильтр по Набору данных узлов, под условие попадают только A и B.
* *Тогда:* отображаются только узлы A и B; отображается только связь A→B (оба конца прошли фильтр); связи B→C и A→C не отрисовываются; узел C не отображается; ошибок валидации не возникает.

*AC.2.2* — Фильтрация узлов: «С соседями» — ВКЛ.
* *Дано:* граф с узлами A (Премиум), B (Стандарт), C (Премиум), D (Стандарт); рёбра связей: A→B, B→C, B→D; режим «С соседями» — ВКЛ (по умолчанию).
* *Когда:* пользователь применяет фильтр node_category = "Премиум".
* *Тогда:* отображаются узлы A, B, C (A и C — проходят фильтрацию, B — как сосед); узел D не отображается (не прошёл фильтр и не соприкасается с узлом прошедшим фильтрацию); отображаются рёбра A→B и B→C; Узел D и ребро B→D — не отображаются, так как D не входит в итоговое множество узлов.

*AC.3* — Фильтрация связей не удаляет узлы.
* *Дано*: граф с узлами A, B, C и связями A→B (тип: «Партнёрство»), B→C (тип: «Аффилированность»).
* *Когда*: пользователь применяет фильтр по Набору данных связей: `edge_type = "Партнёрство"`.
* *Тогда*: отображаются все три узла A, B, C; отображается только связь A→B; B и C становятся изолированными узлами и продолжают отображаться.

*AC.4* — Обработка битых связей не ломает визуализацию.
* *Дано*: Набор данных связей содержит строку с `source_node_id = "X"`, которого нет в Набор данных узлов.
* *Когда*: визуализация загружается.
* *Тогда*: все корректные узлы и связи отрисовываются в штатном режиме; некорректная связь пропускается; в логах браузера и/или серверных логах фиксируется запись об ошибке валидации с указанием {{edge_id}} и отсутствующего {{node_id}}; визуализация не падает.

*AC.5* — Глобальные фильтры дашборда применяются к обоим Наборам данных.
* *Дано*: на дашборде есть фильтры по полю `category = "Премиум"`; это поле присутствует в Наборе данных узлов.
* *Когда*: пользователь выбирает значение в фильтре.
* *Тогда*: в Набор данных узлов остаются только строки с `category = "Премиум"`; граф перестраивается — показываются только отфильтрованные узлы и связи строго между ними; соседние виджеты (Таблица, Сводная таблица и т.д.) могут фильтроваться по той же логике в зависимости от настроек Дашборда.

*AC.6* — Клик на узел Графа фильтрует соседние виджеты с учётом режима «С соседями».
* *Дано*: на дашборде рядом с Графом расположена Таблица, связанная с тем же Набором данных; режим клика по Узлу на диаграмме «Граф» — «Кросс-фильтрация»; режим «С соседями» — ВКЛ.
* *Когда*: К примеру, пользователь кликает на узел с {{node_id}} = "company_42" в визуализации «Граф» при включённом режиме кросс-фильтрации.
* *Тогда*: Таблица фильтруется по {{node_id}} = "company_42"; Граф отображает узел "company_42" и всех его непосредственных соседей; рёбра между ними отображаются; остальные узлы скрываются.
* *И:* При переключении режима «С соседями» — ВЫКЛ: Граф отображает только узел "company_42" как изолированную точку без связей; Таблица фильтруется по node_id = "company_42" аналогично.

*AC.7* — Изолированные узлы отображаются и участвуют в фильтрации.
* *Дано*: Набор данных узлов содержит узел D, на который нет ни одной ссылки в Наборе данных связей.
* *Когда*: дашборд загружается; затем пользователь применяет фильтр по полю `category`, под которое узел D *попадает*.
* *Тогда*: узел D отображается на полотне как изолированная точка; при фильтрации узел D остаётся в выборке и не исчезает; при клике на D в режиме кросс-фильтрации соседние виджеты фильтруются по его {{node_id}}.

*AC.8* — Symbolic Reference Resolution: переименование поля не ломает конфигурацию.
* *Дано*: в Наборе данных создано поле с `display_name = "Город"`, на него ссылается фильтр и вычисляемое поле в конфигурации визуализации.
* *Когда*: администратор или аналитик переименовывает поле — меняет {{display_name}} с `"Город"` на `"Город клиента"` (значение {{name}}/UUID - не меняется).
* *Тогда*: фильтр и вычисляемое поле продолжают корректно работать; в UI отображается новое имя `"Город клиента"`; конфигурация дашборда не требует ручной правки.

*AC.9* — Обратная совместимость: существующие дашборды работают без изменений.
* *Дано*: существующий дашборд с любой визуализацией (кроме «Граф»), созданной до данного релиза, использующей поля со старым форматом типа {{name = "revenue"}}.
* *Когда*: релиз выкатывается на продакшн; миграция {{display_name}} выполнена.
* *Тогда*: все существующие дашборды открываются без ошибок; данные отображаются корректно; в UI вместо {{name = "revenue"}} отображается {{display_name = "revenue"}} (значения совпадают — изменений пользователь не замечает); конфигурация не требует ручной правки.

*AC.10* — Производительность.
* *Дано*: Набор данных узлов содержит 1000 строк, Набор данных связей содержит 2000 строк.
* *Когда*: дашборд загружается; затем пользователь применяет фильтр, изменяющий состав узлов.
* *Тогда*: первичная отрисовка графа завершается не дольше, чем аналогичная операция в текущей реализации на сопоставимом объёме данных; перерисовка после применения фильтра выполняется без видимых зависаний интерфейса; браузер не выбрасывает предупреждений о долгих задачах в консоли."
