h3. 1. Цель и контекст.

В аналитическом портале используется новый переиспользуемый редактор кода на базе {{CodeMirror}} для ввода SQL-запросов, вычисляемых выражений и просмотра/редактирования связанных кодовых фрагментов.

В текущей конфигурации редактора frontend-линтер пытается определять синтаксическую корректность кода. Такой подход даёт ложные ошибки для валидных выражений и дополнительную сложность в поддержке специфических конструкций проекта и разных SQL-диалектов, используемых на портале:
* PostgreSQL;
* ClickHouse;
* MySQL;
* 1C;
* другие источники данных, системные переменные и т.д.

Локальная frontend-проверка синтаксиса не должна быть источником истины для валидности кода. До реализации полноценной backend-проверки синтаксиса по диалектам необходимо полностью отключить frontend-линтер в новом редакторе кода, сохранив при этом подсветку синтаксиса и базовый UX редактора.

{panel:title=Ключевой принцип доработки|borderStyle=dashed|borderColor=#ccc|titleBGColor=#DDEBF7|bgColor=#F8FBFF}
* Редактор {{CodeMirror}} должен оставаться инструментом ввода, подсветки и удобной работы с кодом.
* Frontend не должен самостоятельно определять, является ли SQL/выражение синтаксически валидным и выводить ошибки.
* Источником истины для проверки корректности кода должны быть backend-механизмы соответствующего модуля и явные пользовательские действия, например {{«Проверить запрос»}} в карточке произвольного набора данных.
* Отключение линтера не должно отключать подсветку синтаксиса, автодополнение, работу с кареткой, вставку объектов, ресайз редактора и прочие уже реализованные функции виджета.
{panel}

----
h3. 2. Функциональные требования к доработке.

h4. 2.1. Область применения.

Отключение frontend-линтера должно применяться ко всем сценариям аналитического портала, где используется новый переиспользуемый редактор кода на базе {{CodeMirror}}.

Минимально обязательные сценарии:
* редактор выражений в интерфейсе {{«Вычисляемые поля»}};
* редактор поля {{«SQL Запрос»}} в карточке *произвольного* набора данных;
* редактор кода в {{«Правила загрузки данных»}};
* просмотр/редактирование кодовых фрагментов через тот же виджет, включая read-only сценарии, если для них подключена общая конфигурация редактора.

Если в проекте есть Storybook/демо-страницы переиспользуемого виджета, они должны отражать актуальную конфигурацию редактора без frontend-линтера либо явно отделять демонстрационный режим линтера от продуктового режима.

---
h4. 2.2. Что считается frontend-линтером в рамках задачи.

В рамках данной задачи под frontend-линтером понимается любая логика на стороне фронтенда, которая:
* запускает синтаксическую проверку кода на основании frontend-парсера;
* формирует сообщения об ошибках синтаксиса без обращения к backend;
* подчёркивает участки кода как синтаксически ошибочные по результату локального анализа;
* отображает ошибки в UI редактора;
* блокирует пользовательские действия на основании локальных диагностик редактора.

Отключение frontend-линтера не должно затрагивать:
* подсветку синтаксиса;
* подсветку системных токенов проекта;
* автодополнение;
* автозакрытие скобок и кавычек;
* нумерацию строк;
* Undo/Redo;
* мультикурсор;
* внутренний скролл;
* resize редактора;
* Drag-and-Drop и вставку объектов в позицию каретки;
* отображение ошибок, полученных от backend после явных действий пользователя.

Отключение frontend-линтера также не отменяет обычные frontend-проверки формы, не связанные с синтаксисом кода: обязательность заполнения поля, признак изменения формы, доступность кнопок по правам пользователя и другие действующие UI-ограничения соответствующего модуля.

---
h4. 2.3. Отключение локальной проверки синтаксиса.

Frontend должен быть изменён так, чтобы новый редактор кода не запускал локальную синтаксическую проверку и не показывал локальные сообщения об ошибках.

Требования:
* из продуктовой конфигурации редактора должны быть исключены расширения/плагины {{CodeMirror}}, отвечающие за диагностику синтаксиса;
* локальная проверка не должна запускаться при вводе символов, вставке текста, потере фокуса, открытии редактора, переключении режима, изменении источника данных или изменении SQL-диалекта;
* редактор не должен показывать красные подчёркивания, маркеры ошибок в рабочей области редактора или tooltip-ошибки, сформированные frontend-парсером;
* наличие локальных ошибок парсинга внутри языкового пакета {{CodeMirror}} не должно выводиться пользователю как ошибка линтера;
* frontend не должен блокировать кнопки {{«Проверить запрос»}}, {{«Сохранить»}}, закрытие редактора, сворачивание расширенного режима или другие действия формы на основании локальных диагностик редактора;
* если в коде есть технические проверки состояния редактора, они не должны использовать результат frontend-линтера как признак валидности кода.
* действующие проверки формы, не связанные с синтаксическим анализом кода, должны продолжить работать по правилам соответствующего модуля.

---
h4. 2.4. Сохранение подсветки синтаксиса и режима диалекта.

После отключения линтера редактор должен продолжать работать в режиме подсветки синтаксиса.

Требования:
* подсветка SQL должна сохраняться для редакторов SQL-запросов;
* режим/диалект подсветки должен по-прежнему определяться по текущей логике портала, в том числе по типу источника данных там, где это уже предусмотрено;
* для источников без нативного диалекта {{CodeMirror}} должен использоваться согласованный fallback-режим подсветки;
* выбор диалекта должен влиять на подсветку, автодополнение и синтаксически безопасную вставку идентификаторов, если такая логика уже реализована, но не должен включать frontend-линтер;
* валидные конструкции конкретных диалектов PostgreSQL, ClickHouse, MySQL, 1C и других поддерживаемых источников не должны визуально помечаться как ошибки frontend-линтера;
* подсветка системных переменных и плейсхолдеров проекта должна сохраняться, если она уже реализована в конфигурации редактора.

---
h4. 2.5. Системный синтаксис проекта.

Редактор не должен помечать системный синтаксис Modus BI как ошибку.

После доработки следующие конструкции не должны получать локальные синтаксические ошибки со стороны редактора:
* {{\!env.NAME\!}};
* {{\!env.NAME.BEGIN\!}};
* {{\!env.NAME.END\!}};
* конструкции с fallback-логикой внутри фигурных скобок, например \{{{\!env.REGION\!; 2}}\};
* конструкции, где системная переменная используется внутри выражения, например \{{{toDate(\!env.Date\!); '2020-01-01'}}\};
* отсылки к полкам визуализаций, например {{$category$}};
* иные серверные/системные переменные проекта, уже допустимые по текущим правилам платформы.

Если для этих конструкций реализована отдельная подсветка как системных токенов, она должна сохраниться.

---
h4. 2.6. Проверка кода через backend.

Отключение frontend-линтера не отменяет бизнес-проверки кода в соответствующих модулях портала.

Целевая логика:
* проверка SQL/выражения должна выполняться только через существующие или отдельно реализуемые backend-механизмы соответствующего модуля;
* в карточке *произвольного* набора данных действие {{«Проверить запрос»}} должно по-прежнему отправлять текущий текст SQL на backend и обрабатывать результат по текущей бизнес-логике;
* в сценариях вычисляемых полей и других редакторов кода должны сохраняться действующие правила проверки/сохранения соответствующего объекта;
* frontend не должен автоматически отправлять запрос на backend-проверку при каждом вводе символа из-за отключения локального линтера;
* ошибки, возвращённые backend после явного действия пользователя, должны отображаться пользователю по штатным правилам модуля;
* если backend-ответ позволяет определить место ошибки в тексте, frontend может визуально акцентировать это место как backend-диагностику, но такая индикация не должна использовать локальный frontend-линтер;
* при изменении текста после backend-ошибки устаревшая backend-индикация должна быть сброшена или явно обновлена по правилам модуля, чтобы пользователь не видел ошибку как актуальную для уже изменённого кода.

{panel:title=Граница задачи|borderStyle=dashed|borderColor=#ccc|titleBGColor=#FCE4D6|bgColor=#FFF8F2}
В рамки данной истории входит:
* отключение frontend-линтера в продуктовой конфигурации нового редактора кода;
* сохранение подсветки синтаксиса и базового UX редактора;
* сохранение текущих явных backend-проверок кода в модулях портала;
* исключение блокировок пользовательских действий на основании локальных диагностик редактора;
* проверка отсутствия ложных frontend-ошибок для разных SQL-диалектов и системного синтаксиса проекта.

В рамки данной истории *не* входит:
* реализация нового универсального backend-линтера для всех SQL-диалектов;
* изменение API-контрактов проверки SQL/выражений, если это не требуется для отключения frontend-линтера;
* изменение правил генерации SQL на backend;
* изменение бизнес-логики обновления выходных полей набора данных после успешной проверки запроса;
* изменение подсказок автодополнения, дерева метаданных или логики Drag-and-Drop, не связанное с отключением frontend-линтера.
{panel}

---
h4. 2.7. Обратная совместимость и отсутствие регресса.

Доработка не должна ломать существующие сценарии работы с редактором.

Необходимо сохранить:
* загрузку текущего значения кода при открытии редактора;
* синхронизацию текста редактора с формой;
* проверку SQL через явное действие {{«Проверить запрос»}};
* обновление выходных полей набора данных после успешной backend-проверки;
* сохранение формы штатной кнопкой {{«Сохранить»}};
* read-only режимы просмотра кода;
* внутренние скроллы и ресайз редактора;
* горячие клавиши редактора, если они уже поддержаны;
* работу редактора с длинными SQL-запросами и выражениями.

Отключение frontend-линтера не должно изменять payload сохранения наборов данных, вычисляемых полей, отчётов или других объектов, если изменение payload не требуется существующей бизнес-логикой.

----
h3. 3. Пограничные сценарии.

Frontend должен корректно обрабатывать следующие сценарии:
* пользователь вводит SQL, валидный для PostgreSQL, но не распознаваемый стандартным SQL-парсером {{CodeMirror}};
* пользователь вводит SQL, валидный для ClickHouse, включая специфичные функции и операторы;
* пользователь вводит SQL или выражение для источника MySQL;
* пользователь работает с источником 1C или другим источником, для которого нет нативного frontend-диалекта;
* пользователь вставляет системные переменные и серверные плейсхолдеры Modus BI;
* пользователь открывает старый сохранённый объект, где код содержит конструкции, неизвестные frontend-парсеру;
* пользователь редактирует длинный SQL-запрос или выражение;
* пользователь запускает {{«Проверить запрос»}} после изменения текста;
* backend возвращает ошибку проверки SQL/выражения;
* пользователь изменяет текст после полученной backend-ошибки;
* редактор открыт в read-only режиме;
* редактор используется в расширенном режиме с боковыми панелями, автодополнением и вставкой объектов.

----
h3. 4. Критерии приёмки (AC):

* *AC.1 (Frontend-линтер отключён во всех продуктовых экземплярах редактора):*
* *Дано:* пользователь открывает любой продуктовый сценарий с новым редактором {{CodeMirror}};
* *Когда:* пользователь вводит или вставляет код;
* *Тогда:* редактор не запускает локальную синтаксическую проверку и не показывает ошибки, сформированные frontend-линтером.

* *AC.2 (Подсветка синтаксиса сохранена):*
* *Дано:* пользователь открыл редактор SQL/выражения;
* *Когда:* в редакторе отображается код;
* *Тогда:* подсветка синтаксиса продолжает работать, а отключение линтера не превращает редактор в обычное текстовое поле.

* *AC.3 (Нет ложных ошибок для разных диалектов):*
* *Дано:* пользователь работает с кодом для PostgreSQL, ClickHouse, MySQL, 1C или другого поддерживаемого источника;
* *Когда:* код содержит конструкции, специфичные для выбранного диалекта;
* *Тогда:* frontend не подчёркивает эти конструкции как синтаксические ошибки и не показывает локальные диагностические сообщения.

* *AC.4 (Системный синтаксис не помечается как ошибка):*
* *Дано:* код содержит системные конструкции Modus BI, например {{\!env.NAME\!}}, {{\!env.NAME.BEGIN\!}}, {{\!env.NAME.END\!}}, конструкции с fallback-логикой или {{$category$}};
* *Когда:* пользователь открывает или редактирует код;
* *Тогда:* редактор не показывает по ним локальные ошибки frontend-линтера; при наличии отдельной подсветки системных токенов она сохраняется.

* *AC.5 (Backend-проверка запроса сохранена):*
* *Дано:* пользователь редактирует SQL в карточке *произвольного* набора данных;
* *Когда:* пользователь нажимает {{«Проверить запрос»}};
* *Тогда:* на backend отправляется текущий текст SQL из редактора, проверка выполняется по текущей бизнес-логике, а результат отображается пользователю штатным образом.

* *AC.6 (Нет автоматической проверки при вводе):*
* *Дано:* пользователь вводит или изменяет код в редакторе;
* *Когда:* пользователь печатает символы, вставляет текст, меняет каретку или фокус;
* *Тогда:* frontend не запускает локальный линтер и не отправляет автоматическую backend-проверку только из-за факта редактирования текста.

* *AC.7 (Локальные диагностики не блокируют действия пользователя):*
* *Дано:* пользователь работает с кодом, который frontend-парсер мог бы считать ошибочным;
* *Когда:* пользователь нажимает {{«Проверить запрос»}}, {{«Сохранить»}}, сворачивает редактор или выходит из расширенного режима;
* *Тогда:* действие не блокируется локальными диагностическими ошибками редактора; дальнейшая валидация выполняется только по правилам соответствующего модуля.

* *AC.8 (Backend-ошибка не теряется):*
* *Дано:* backend вернул ошибку при явной проверке SQL/выражения;
* *Когда:* frontend получает ответ backend;
* *Тогда:* пользователь видит штатное сообщение об ошибке, текст в редакторе не теряется, а отсутствие frontend-линтера не скрывает backend-результат проверки.

* *AC.9  (Базовый UX редактора не сломан):*
* *Дано:* пользователь работает с новым редактором кода после отключения линтера;
* *Когда:* пользователь использует нумерацию строк, автодополнение, автозакрытие скобок/кавычек, Undo/Redo, мультикурсор, внутренний скролл, resize или Drag-and-Drop;
* *Тогда:* эти функции работают по ранее заданным правилам и не зависят от отключённого frontend-линтера.

* *AC.10 (Read-only режим не показывает локальные ошибки):*
* *Дано:* код открыт в экземпляре редактора {{CodeMirror}} в режиме только для чтения;
* *Когда:* отображаемый код содержит диалектные или системные конструкции проекта;
* *Тогда:* пользователь видит код с подсветкой синтаксиса, но без локальных ошибок frontend-линтера.

* *AC.11 (Payload объектов не изменён из-за отключения линтера):*
* *Дано:* пользователь редактирует и сохраняет объект, где используется новый редактор кода;
* *Когда:* выполняется штатное сохранение формы;
* *Тогда:* отключение frontend-линтера не добавляет в payload новые служебные поля и не изменяет существующие данные объекта, кроме самого текста кода, если пользователь его изменил.
