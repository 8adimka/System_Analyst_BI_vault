На данный момент внедрение нового редактора кода проводится в рамках:
* «Вычисляемых полей» для работы с вычисляемыми полями,
* «Наборов данных» для создания "произвольных" наборов данных с происвольным пользовательским запросом,
* для сценария создания "простого" набора данных через сценарий «Правил загрузки данных» (постановка ./Редактор_кода_Шаг_4_Правила_загрузки_данных.txt)

После реализации шага 2 (./Редактор_кода_Шаг_2_Вычисляемые_поля.txt) и шага 3 этап 1 (./Редактор_кода_Шаг_3_Наборы_данных_Этап_1.txt) возникла необходимость исправить работу линтера для корректного определения синтаксиса (включая корректное определения синтаксиса для разных диалектов, таких как PostgreSQL, Clickhouse, 1c, mySQL и т.д.).

Была проведена работа по поиску плагинов для фронтенда ./Редактор_кода_Шаг_5_Поиск_плагинов_для_подсветки_синтаксиса.txt

Но в ходе обсуждений было решено перенести проверку синтаксиса на бэкенд, и пока временно вырезать линтер полностью (с фронтенда), но оставить подсветку синтаксиса на фронтенде.

Для выключения работы линтера на фронтенде была создана постановка ./Редактор_кода_Шаг_6_Отключение_линтера.txt -> работа по ней уже была проведена.

На текущий момент нужно создать постановку для осуществления доработок бэкенда, чтобы проводить проверку синтаксиса на бэкенде по нажатии кнопки {{«Проверить запрос»}}.

Проверка синтаксиса должна корректно обрабатывать различные диалекты SQL и другие языки программирования в рамках штатной работы с редактором кода, включая:
* PostgreSQL;
* ClickHouse;
* MySQL;
* 1C;
* JavaScript.

Минимально обязательные сценарии использования редактора кода:
* редактор выражений в интерфейсе {{«Вычисляемые поля»}};
* редактор поля {{«SQL Запрос»}} в карточке *произвольного* набора данных;
* редактор кода в {{«Правила загрузки данных»}};
* просмотр/редактирование кодовых фрагментов через тот же виджет, включая read-only сценарии, если для них подключена общая конфигурация редактора.

Ключевые моменты для новой постановки:
* проверка кода должна выполняться только через реализуемые backend-механизмы соответствующего модуля;
* для запуска бэкенд-проверки кода будет использоваться действие {{«Проверить запрос»}} - оно должно отправлять запрос на бэкенд для проверки текущего текста кода, бэкенд должен возвращать в ответе все необходимые данные для отрисовки кода с учётом возможных ошибок на фронтенде, чтобы у пользователя появилось достаточно информации для исправления ошибок в коде;
* в сценариях вычисляемых полей и других редакторов кода должны сохраняться действующие правила проверки/сохранения соответствующего объекта;
* frontend не должен автоматически отправлять запрос на backend-проверку при каждом вводе символа;
* ошибки, возвращённые backend, должны отображаться пользователю в рабочой области редактора кода;
* backend-ответ должен позволять определить место ошибки в тексте кода, а frontend должен визуально акцентировать это место как ошибочное;
* при изменении текста кода, с отрисованной ошибкой после backend-проверки, устаревшая backend-индикация должна быть сброшена после исправления ошибки, чтобы пользователь не видел ошибку как актуальную для уже изменённого кода.

## 1. Общий чек-лист для проверки на бэкенде должен быть покрыт:

- Корректная подсветка ключевых слов, строк, чисел, комментариев (`--`, `/* */`)
- Валидный код не подчёркивается как ошибка (0 false positives)
- Явная синтаксическая ошибка (незакрытая скобка/кавычка) визуально заметна
- Bracket matching: наведение на скобку показывает пару; удаление закрывающей скобки — видно, что не закрыта
- Автодополнение ключевых слов и функций работает по вводу и по `Ctrl+Space`
- Переключение диалекта на лету не ломает подсветку и автодополнение
- Производительность: запрос 500+ строк — нет лагов при вводе; запрос 1000+ строк — парсинг < 500ms
- Размер бандла пакета — измерен и зафиксирован (gzip)
- Работа с длинным запросом при активном скролле — подсветка не "рассыпается" за пределами viewport

## 2. PostgreSQL — специфические кейсы:

- `::`-каст типов: `column::int`, `value::text::jsonb`
- Dollar-quoted строки: `$...$`, `$tag$...$tag$`
- CTE и `WITH RECURSIVE`
- Window functions: `OVER (PARTITION BY ... ORDER BY ...)`
- `FILTER (WHERE ...)` в агрегатах
- JSON-операторы: `->`, `->>`, `#>`, `#>>`
- Массивы: `ARRAY[...]`, `column[1]`
- `RETURNING` после `INSERT/UPDATE/DELETE`
- Типы: `jsonb`, `uuid`, `tsvector`, `numrange`
- `ILIKE`, `~`, `~*` (regex-операторы)


## 3. ClickHouse — специфические кейсы:

- `ENGINE = MergeTree()`, `ReplicatedMergeTree(...)`
- `SAMPLE`, `FINAL`, `PREWHERE`
- `ARRAY JOIN`, `GLOBAL IN`, `ANY/ALL/ASOF JOIN`
- Лямбды: `arrayMap(x -> x * 2, arr)`
- Условные агрегаты: `sumIf`, `countIf`, `uniqIf`
- Функции дат: `toStartOfMonth`, `toDate`, `toDateTime64`
- Типы: `LowCardinality`, `Nullable`, `Array(String)`, `Enum8`
- `WITH TOTALS`, `SETTINGS ...` в конце запроса
- `FORMAT` в конце запроса (специфика ClickHouse)


## 4. MySQL — специфические кейсы:

- Backtick-идентификаторы: ```table_name```
- `LIMIT offset, count` (нестандартный синтаксис)
- `ON DUPLICATE KEY UPDATE`
- Функции: `GROUP_CONCAT`, `IFNULL`, `DATE_FORMAT`
- Комментарии `#` (специфика MySQL, помимо `--`)
- Экранирование строк через `\'` (backslash escapes включены, в отличие от Postgres/ClickHouse)


## 5. 1C (язык запросов) — специфические кейсы:

- Кириллические ключевые слова: `ВЫБРАТЬ`, `ГДЕ`, `СГРУППИРОВАТЬ ПО`, `ЛЕВОЕ СОЕДИНЕНИЕ`
- Параметры запроса: `&НачалоПериода`, `&Организация`
- Виртуальные таблицы: `РегистрНакопления.Продажи.Обороты(...)`
- Точечная нотация ссылочных объектов: `Контрагенты.Наименование`, `Ссылка.Родитель`
- Явный вывод — зафиксировать в документе: нет готового CM6-пакета → решение (fallback StandardSQL / кастомная грамматика / отключение подсветки для этого источника)


## 6. JS/TypeScript — специфические кейсы:

- TypeScript-типизация: интерфейсы, generics `Array<T>`, `as const`
- Стрелочные функции, деструктуризация, template literals
- Опциональная цепочка `?.`, nullish coalescing `??`
- ESLint-интеграция — реальные ошибки (не lezer-псевдо-линтинг)

## 7. Системные конструкции платформы — обязательная матрица (не диалект-специфично):

Проверяется на **каждом** выбранном диалекте отдельно — платформенный синтаксис должен работать одинаково независимо от SQL-диалекта.


| \# | Конструкция | Пример | Проверка |
| :-- | :-- | :-- | :-- |
| 1 | Простая переменная (латиница) | `!env.REGION!` | Подсвечена как токен, нет ошибки |
| 2 | Простая переменная (кириллица) | `!env.НазваниеРегиона!` | Подсвечена, нет ошибки (был баг на демо) |
| 3 | Суффикс диапазона | `!env.DATE.BEGIN!` / `!env.DATE.END!` | Подсвечены как единый токен |
| 4 | Fallback простой | `{!env.REGION!; 2}` | `;` внутри `{}` не подсвечена как ошибка |
| 5 | Fallback строковый | `{!env.REGION!; 'default'}` | Валидно целиком |
| 6 | Выражение + переменная | `{toDate(!env.Date!); '2020-01-01'}` | Функция + переменная внутри `{}` — валидны |
| 7 | Переменная в теле запроса | `WHERE region = !env.REGION!` | Не ошибка, токен подсвечен отдельным цветом |
| 8 | Dollar-переменная | `$category$` | Не ошибка |
| 9 | Незакрытая fallback-скобка | `{!env.REGION!; 2` | Ошибка **должна** быть заметна (bracket matching) |
| 10 | Переменная внутри строки/литерала | `'prefix_!env.NAME!'` | Отдельно зафиксировать ожидаемое поведение — подсвечивать или нет |

Как системный аналитик с большим стажем, опираясь на изученные материалы и общий контекст, сформулируй логику работы и необходимые доработки нашего аналитического портала для того, чтобы выключить линтер (для проверси синтаксиса) в новом редакторе кода на нашем портале. Сформулируй и подготовь понятную постановку для разработчиков. Новая постановка должна полностью согласовываться с остальными постановками по данной тематике и являться логичным продолжением работ по реализации нового редактора кода, но не нужно упоминать в этой постановке факты из других постановок и обсуждения не касающиеся данной доработки напрямую.

Постановка должна декларативно давать разработчикам информацию о необходимых доработках и не фокусироваться на изменениях внесенных в постановку, обсуждениях, согласованиях и прочих некритичных деталях в рамках реализации данной доработки.
