h3. 1. Цель и контекст.

Обновлённый редактор кода на базе {{CodeMirror}} используется на нашем портале для работы с SQL-запросами, вычисляемыми выражениями и другими кодовыми фрагментами.

Фронтенд-редактор должен оставаться инструментом ввода, подсветки синтаксиса, автодополнения и удобной работы с кодом, но не должен быть источником истины для синтаксической валидности кода.

Для корректной проверки кода требуется реализовать Бэкенд-проверку синтаксиса. На данный момент рассматривается запуск проверки синтаксиса явным действием пользователя {{«Проверить запрос»}} или соответствующим штатным действием проверки в конкретном модуле.

Проверка должна учитывать:
* язык или SQL-диалект текущего сценария;
* системный синтаксис Modus BI;
* ограничения конкретного модуля портала;
* необходимость вернуть на Фронтенд достаточную информацию для визуального отображения ошибок в рабочей области редактора.

----
h3. 2. Описание текущего поведения.

Новый редактор кода уже используется в нескольких сценариях портала, однако Фронтенд-проверка не обеспечивает надёжную синтаксическую валидацию для 
* разных SQL-диалектов, 
* языка запросов 1C, 
* JavaScript/TypeScript-фрагментов,
* системного синтаксиса Modus BI.

В сценариях, где уже есть действие {{«Проверить запрос»}}, его результат должен оставаться частью бизнес-логики соответствующего модуля. 

Для нового редактора требуется единый подход к Бэкенд-диагностикам: Бэкенд отличает ошибки пользовательского кода от технических ошибок команды, возвращает позицию ошибки при наличии такой информации, а Фронтенд визуально отображает ошибочный участок в редакторе.

----
h3. 3. Описание целевого поведения.

h4. 3.1. Общий сценарий работы.

Целевой сценарий:
# Пользователь открывает новый редактор кода.
# Пользователь вводит или изменяет код.
# Фронтенд не запускает локальную проверку синтаксиса и не отправляет Бэкенд-запрос при каждом изменении текста.
# Пользователь явно нажимает {{«Проверить запрос»}} либо использует соответствующее штатное действие проверки в модуле.
# Фронтенд отправляет на Бэкенд актуальный текст кода из редактора и контекст проверки.
# Бэкенд определяет язык/диалект, модульные ограничения и способ проверки.
# Бэкенд выполняет проверку синтаксиса без побочных изменений данных.
# Бэкенд возвращает результат проверки и массив диагностики.
#* Если Бэкенд вернул ошибки, Фронтенд отображает их позиции в редакторе и показывает понятные текстовые пояснения без потери введенного кода.
#* Когда пользователь изменяет текст в ранее подсвеченном участке кода, Фронтенд не сбрасывает подсветку отображённых ошибок. Подсветка ошибок отображается до получения нового результата проверки.

---
h4. 3.2. Область применения.

Минимально обязательные сценарии:
* редактор выражений в интерфейсе {{«Вычисляемые поля»}};
* редактор поля {{«SQL Запрос»}} в карточке *произвольного* набора данных;
* редактор кода в {{«Правила загрузки данных»}} для создания *простых* наборов данных;
* просмотр и редактирование кодовых фрагментов через переиспользуемый редактор кода, если данный сценарий уже поддерживается порталом и для него подключена общая конфигурация нового редактора.

Для read-only сценариев:
* Бэкенд-проверка не должна запускаться автоматически при открытии кода;
* если в read-only сценарии нет явного действия проверки, дополнительные Бэкенд-вызовы не требуются;
* read-only режим не должен показывать локальные ошибки кода.

---
h4. 3.3. Результат успешной и неуспешной проверки.

Если код синтаксически валиден:
* Бэкенд возвращает успешный результат проверки;
* массив диагностик возвращается пустым;
* в модуле продолжается штатная бизнес-логика, связанная с проверкой кода.

Для *произвольного* набора данных после успешной проверки SQL должны сохраняться действующие правила:
* обновление выходных полей;
* сохранение ранее заполненных пользовательских атрибутов совпавших полей по текущим правилам сопоставления;
* удаление полей, исчезнувших из результата запроса;
* создание новых полей с дефолтными значениями.

Если код содержит синтаксическую ошибку:
* Бэкенд возвращает результат команды с признаком невалидного кода и диагностикой ошибки;
* текст кода в редакторе не теряется;
* редактор не закрывается;
* существующие валидные данные формы не должны разрушаться некорректным промежуточным состоянием;
* для *произвольного* набора данных список выходных полей не должен обновляться по невалидному SQL.

Если произошла техническая ошибка Бэкенд-команды:
* Бэкенд возвращает неуспешный {{status}} по текущему стандарту API портала;
* {{message}} должен объяснять причину технической ошибки;
* техническая ошибка не должна маскироваться под синтаксическую ошибку пользовательского кода.

----
h3. 4. Рамки задачи.

В рамках данной задачи требуется:
* реализовать Бэкенд-механизм проверки синтаксиса кода для редактора кода;
* интегрировать проверку с явным действием {{«Проверить запрос»}} или соответствующим штатным действием проверки конкретного модуля;
* обеспечить поддержку обязательных языков и диалектов:
** PostgreSQL;
** ClickHouse;
** MySQL;
** язык запросов 1C;
** JavaScript / TypeScript;
* обеспечить поддержку системного синтаксиса Modus BI при проверке кода;
* вернуть Фронтенд структурированные диагностики ошибок;
* обеспечить отображение Бэкенд-ошибок в рабочей области редактора;
* сохранить действующие правила проверки, сохранения и обновления объектов соответствующих модулей;
* обеспечить отсутствие автоматической Бэкенд-проверки на каждый ввод символа.

----
h3. 5. API-контракт и структура диагностик.

h4. 5.1. Общие требования к Бэкенд-командам.

Бэкенд-команды проверки должны соответствовать текущей логической модели API портала:
* в теле запроса передаются {{object}}, {{command}} и {{data}};
* успешный ответ содержит {{mode}}, {{status}}, {{message}}, {{data}};
* {{status = 200}} означает, что команда проверки выполнена технически успешно;
* синтаксически невалидный пользовательский код не должен считаться технической ошибкой Бэкенд-команды;
* значения {{status}}, отличные от {{200}}, используются для технических ошибок, ошибок доступа, недоступности источника и других неуспешных сценариев выполнения команды.

Точные имена Бэкенд-команд должны быть подтверждены командой разработки. Логически проверка должна быть реализована одним из вариантов:
* расширение существующих команд проверки соответствующего модуля;
* добавление модульных команд проверки синтаксиса, например {{syntax.check}}, без обхода бизнес-логики модуля;
* использование общей внутренней Бэкенд-службы проверки синтаксиса, вызываемой только через API соответствующих модулей.

Не допускается реализовывать независимый Бэкенд-endpoint, который проверяет код вне контекста модуля, прав пользователя и выбранного источника данных.

---
h4. 5.2. Логическая привязка к модулям.

|| Сценарий || Бэкенд-объект || Команда || Особенности ||
| {{«SQL Запрос»}} в карточке *произвольного* набора данных | {{datasets}} | текущая команда проверки SQL либо новая модульная команда проверки, точное имя подтвердить у разработки | Диалект определяется по текущему источнику данных. При успешной проверке сохраняется текущая логика обновления выходных полей. |
| {{«Вычисляемые поля»}} | объект модуля вычисляемых полей / отчёта / набора данных, точное имя подтвердить у разработки | текущая команда проверки/сохранения либо модульная команда проверки | Проверка не должна ломать действующие правила вычисляемых выражений, вставки полей и сохранения объекта. |
| {{«Правила загрузки данных»}} | {{extraction_rules}} | текущая команда проверки правила либо модульная команда проверки | Диалект/язык определяется по подключению, источнику или типу правила загрузки. |
| Просмотр/редактирование кодовых фрагментов через общий виджет | объект соответствующего модуля | только при наличии явного действия проверки | Для read-only режима автоматический Бэкенд-вызов не требуется. |

---
h4. 5.3. Пример возможного контракта запроса на проверку синтаксиса.

Если для модуля вводится новая команда проверки, запрос должен передавать текущий текст кода и контекст, достаточный для определения языка/диалекта.

*Пример логического запроса:*
{code:json}
{
    "object": {
        "name": "datasets",
        "id": 123
    },
    "command": {
        "name": "syntax.check"
    },
    "data": {
        "context": "dataset.custom_sql",
        "code": "select id, name from users where region = \!env.REGION\!",
        "language": "sql",
        "dialect": "postgresql",
        "source_id": 10
    }
}
{code}

*Параметры запроса:*
|| Поле || Обязательность || Описание ||
| {{object.name}} | Да | Бэкенд-объект соответствующего модуля. |
| {{object.id}} | Нет | Идентификатор проверяемого объекта, если он уже существует и нужен для контекста проверки. |
| {{command.name}} | Да | Команда проверки. Точное имя определяется реализацией модуля. |
| {{data.context}} | Да | Сценарий проверки: например {{dataset.custom_sql}}, {{calculated_field.expression}}, {{extraction_rule.code}}. |
| {{data.code}} | Да | Точный текущий текст из редактора на момент запуска проверки. |
| {{data.language}} | Нет | Язык кода, если Фронтенд уже знает его из конфигурации редактора. Бэкенд должен перепроверять значение по контексту модуля. |
| {{data.dialect}} | Нет | SQL-диалект, если Фронтенд уже знает его из выбранного источника. Бэкенд должен считать источником истины настройки источника/модуля. |
| {{data.source_id}} | Нет | Идентификатор источника данных или подключения, если он нужен для определения диалекта и доступен в текущем сценарии. |

---
h4. 5.4. Успешный ответ без синтаксических ошибок.

{code:json}
{
    "mode": "online",
    "status": 200,
    "message": "",
    "data": {
        "valid": true,
        "context": "dataset.custom_sql",
        "language": "sql",
        "dialect": "postgresql",
        "errors": []
    }
}
{code}

---
h4. 5.5. Успешный ответ с синтаксическими ошибками пользовательского кода.

{code:json}
{
    "mode": "online",
    "status": 200,
    "message": "В запросе найдены синтаксические ошибки",
    "data": {
        "valid": false,
        "context": "dataset.custom_sql",
        "language": "sql",
        "dialect": "postgresql",
        "errors": [
            {
                "severity": "error",
                "message": "Не закрыта скобка",
                "line": 3,
                "column": 18,
                "endLine": 3,
                "endColumn": 19
            }
        ]
    }
}
{code}

*Поля ответа {{data}}:*
|| Поле || Тип || Обязательность || Описание ||
| {{data.valid}} | boolean | Да | {{true}}, если код прошёл проверку; {{false}}, если найдены ошибки пользовательского кода. |
| {{data.context}} | string | Да | Контекст проверки, по которому Фронтенд понимает, к какому экземпляру редактора относится ответ. |
| {{data.language}} | string | Да | Фактически использованный язык проверки. |
| {{data.dialect}} | string/null | Нет | Фактически использованный SQL-диалект или {{null}}, если язык не является SQL. |
| {{data.errors}} | array | Да | Массив диагностик. Для валидного кода возвращается пустой массив. |

*Поля элемента {{data.errors[]}}:*
|| Поле || Тип || Обязательность || Описание ||
| {{severity}} | string | Да | Уровень диагностики: {{error}}, {{warning}}, {{info}}. Минимально обязательно поддержать {{error}}. |
| {{message}} | string | Да | Понятное пользователю описание ошибки без технических секретов. |
| {{line}} | number/null | Нет | Строка начала ошибки. Нумерация строк начинается с 1. |
| {{column}} | number/null | Нет | Колонка начала ошибки. Нумерация колонок начинается с 1. |
| {{endLine}} | number/null | Нет | Строка окончания ошибки, если Бэкенд может её определить. |
| {{endColumn}} | number/null | Нет | Колонка окончания ошибки, если Бэкенд может её определить. |
| {{code}} | string/null | Нет | Технический код ошибки валидатора, если он есть и безопасен для отображения/логирования. |

Если Бэкенд не может определить точное место ошибки, он должен вернуть диагностику с {{message}} и пустыми позиционными полями. Фронтенд в этом случае показывает сообщение без подсветки конкретного диапазона.
Абсолютные позиции ошибки в тексте, например {{index}}/{{endIndex}}, не входят в минимальный контракт первого этапа и могут быть добавлены позднее при отдельном согласовании с командой разработки.

----
h3. 6. Требования к реализации.

h4. 6.1. Бэкенд-логика проверки.

Бэкенд должен:
* определять язык и SQL-диалект по контексту модуля, источнику данных, подключению или типу правила загрузки;
* не считать значение {{data.dialect}}, переданное Фронтендом, единственным источником истины;
* выбирать валидатор, соответствующий фактическому языку/диалекту;
* не использовать универсальную StandardSQL-проверку для диалектов, где она даёт ложные ошибки;
* учитывать системный синтаксис Modus BI до или во время синтаксической проверки;
* возвращать структурированные диагностики вместо неструктурированного текста ошибки, если позиция ошибки доступна;
* возвращать все доступные диагностики, если выбранный валидатор поддерживает множественные ошибки;
* не выполнять DDL/DML/скрипты и иной пользовательский код ради проверки синтаксиса, если это может изменить данные;
* использовать существующие ограничения модуля: допустимый тип запроса, права пользователя, доступность источника, правила обновления выходных полей и сохранения объекта.

Если синтаксис валиден, но конструкция запрещена правилами текущего модуля, Бэкенд должен вернуть {{data.valid = false}} и ошибку в {{data.errors[]}} с понятным {{message}}, объясняющим ограничение бизнес-правил модуля. Такая ошибка не должна описываться пользователю как синтаксическая ошибка.

Пример: если конкретный сценарий допускает только {{SELECT}}, а пользователь ввёл синтаксически валидный {{INSERT}}, Бэкенд должен сообщить, что такой тип операции не разрешён в данном модуле.

---
h4. 6.2. Фронтенд-интеграция с Бэкенд-диагностиками.

Фронтенд должен:
* отправлять на Бэкенд точный текущий текст редактора на момент запуска проверки;
* запускать проверку только по явному действию пользователя;
* не отправлять Бэкенд-запрос при каждом вводе символа, перемещении каретки, потере фокуса, открытии редактора или переключении диалекта;
* отображать Бэкенд-диагностики в рабочей области редактора;
* визуально акцентировать диапазон ошибки, если Бэкенд вернул позицию;
* показывать понятное сообщение, если Бэкенд вернул ошибку без точной позиции;
* не использовать локальный Фронтенд-линтер для формирования или уточнения Бэкенд-диагностик;

Отображение Бэкенд-ошибок не должно ломать базовый UX редактора:
* подсветку синтаксиса;
* подсветку системных токенов;
* автодополнение;
* bracket matching;
* автозакрытие скобок и кавычек;
* нумерацию строк;
* Undo/Redo;
* мультикурсор;
* внутренний скролл;
* resize редактора;
* Drag-and-Drop и вставку объектов в позицию каретки.

---
h4. 6.3. Поддержка языков и диалектов.

Бэкенд-проверка должна поддерживать минимально обязательный набор:
* {{PostgreSQL}};
* {{ClickHouse}};
* {{MySQL}};
* язык запросов {{1C}};
* {{JavaScript / TypeScript}}.

Для SQL-диалектов проверка должна учитывать диалектные конструкции, а не сводить все проверки к общей SQL-грамматике.

Для 1C не допускается использовать SQL-валидатор, если он будет помечать валидные 1C-запросы как ошибки. Проверка должна выполняться через 1C-специфичный механизм или через согласованный Бэкенд-валидатор, который понимает язык запросов 1C и параметры вида {{&Параметр}}.

Для JavaScript / TypeScript проверка должна использовать Бэкенд-валидатор, который возвращает реальные синтаксические ошибки языка. Если используется {{ESLint}}, диагностики должны формироваться на основании реального парсера/конфигурации, а не на основании {{Lezer}}-парсинга редактора. На первом этапе не требуется выводить стилевые предупреждения как ошибки, если они не блокируют выполнение или сохранение по правилам модуля.

---
h4. 6.4. Системный синтаксис.

Системные конструкции Modus BI должны обрабатываться одинаково независимо от выбранного SQL-диалекта.

Бэкенд-проверка не должна считать ошибкой:
* {{\!env.NAME\!}};
* {{\!env.NAME.BEGIN\!}};
* {{\!env.NAME.END\!}};
* {{\!env.НазваниеРегиона\!}};
* конструкции с fallback-логикой внутри фигурных скобок, например {{\{\!env.REGION\!; 2\}}};
* конструкции, где системная переменная используется внутри выражения, например {{\{toDate(\!env.Date\!); '2020-01-01'\}}};
* отсылки к полкам визуализаций, например {{$category$}};
* иные серверные/системные переменные проекта, уже допустимые по текущим правилам платформы.

Если системная переменная находится внутри строкового литерала, например {{'prefix_\!env.NAME\!'}}, для проверки синтаксиса она считается частью строки. Отдельная токенизация такой переменной внутри строки не является обязательной в рамках Бэкенд-проверки, но вся строка не должна считаться синтаксически ошибочной только из-за наличия системной переменной.

---
h4. 6.5. Права доступа и безопасность.

Бэкенд должен:
* проверять права пользователя по текущим правилам соответствующего модуля;
* не раскрывать код, метаданные источника или параметры подключения пользователю без прав;
* не возвращать пароли, токены, ключи и другие секреты в {{message}}, {{errors[].message}} или технических кодах ошибок;
* не логировать полный текст пользовательского кода в общедоступные логи, если в коде могут находиться чувствительные данные;
* использовать существующие таймауты и ограничения выполнения для обращений к источникам данных;
* не допускать SQL-инъекции или выполнения произвольного кода при синтаксической проверке.

---
h4. 6.6. Производительность.

Бэкенд-проверка не запускается автоматически при вводе, поэтому работа редактора не должна зависеть от скорости Бэкенд-парсинга. Код объёмом 500+ строк не должен вызывать лагов при вводе из-за механизма проверки. Для Бэкенд-парсеров без обращения к внешнему источнику целевое время проверки фрагмента 1000+ строк — менее 500 мс в согласованном тестовом окружении.

Если проверка требует обращения к источнику данных, используются существующие таймауты и понятная обработка ошибок недоступности источника.

---
h4. 6.7. Обратная совместимость.

Доработка не должна ломать:
* загрузку текущего значения кода при открытии редактора;
* синхронизацию текста редактора с формой;
* штатную проверку SQL через {{«Проверить запрос»}};
* обновление выходных полей набора данных после успешной проверки;
* сохранение формы штатной кнопкой {{«Сохранить»}};
* read-only режимы просмотра кода;
* существующие payload сохранения наборов данных, вычисляемых полей, правил загрузки данных и других объектов;
* работу старых сохранённых объектов, где код содержит системные переменные или диалектные конструкции.

----
h3. 7. Матрица обязательных проверок.

h4. 7.1. PostgreSQL.

Бэкенд-проверка PostgreSQL должна корректно обрабатывать:
* cast типов через {{::}}: {{column::int}}, {{value::text::jsonb}};
* dollar-quoted строки: {{$...$}}, {{$tag$...$tag$}};
* {{CTE}} и {{WITH RECURSIVE}};
* window functions: {{OVER (PARTITION BY ... ORDER BY ...)}};
* {{FILTER (WHERE ...)}} в агрегатах;
* JSON-операторы: {{->}}, {{->>}}, {{#>}}, {{#>>}};
* массивы: {{ARRAY[...]}}, {{column[1]}};
* {{RETURNING}} после {{INSERT}}, {{UPDATE}}, {{DELETE}}, если такие операции допустимы в текущем модуле;
* типы {{jsonb}}, {{uuid}}, {{tsvector}}, {{numrange}};
* {{ILIKE}}, {{~}}, {{~*}}.

---
h4. 7.2. ClickHouse.

Бэкенд-проверка ClickHouse должна корректно обрабатывать:
* {{ENGINE = MergeTree()}}, {{ReplicatedMergeTree(...)}}, если проверяемый сценарий допускает DDL;
* {{SAMPLE}}, {{FINAL}}, {{PREWHERE}};
* {{ARRAY JOIN}}, {{GLOBAL IN}}, {{ANY JOIN}}, {{ALL JOIN}}, {{ASOF JOIN}};
* лямбды: {{arrayMap(x -> x * 2, arr)}};
* условные агрегаты: {{sumIf}}, {{countIf}}, {{uniqIf}};
* функции дат: {{toStartOfMonth}}, {{toDate}}, {{toDateTime64}};
* типы {{LowCardinality}}, {{Nullable}}, {{Array(String)}}, {{Enum8}};
* {{WITH TOTALS}};
* {{SETTINGS ...}} в конце запроса;
* {{FORMAT}} в конце запроса.

---
h4. 7.3. MySQL.

Бэкенд-проверка MySQL должна корректно обрабатывать:
* backtick-идентификаторы, например {{`table_name`}};
* {{LIMIT offset, count}};
* {{ON DUPLICATE KEY UPDATE}}, если такие операции допустимы в текущем модуле;
* функции {{GROUP_CONCAT}}, {{IFNULL}}, {{DATE_FORMAT}};
* комментарии через {{#}};
* экранирование строк через backslash, например {{\'}}.

---
h4. 7.4. 1C.

Бэкенд-проверка языка запросов 1C должна корректно обрабатывать:
* кириллические ключевые слова: {{ВЫБРАТЬ}}, {{ГДЕ}}, {{СГРУППИРОВАТЬ ПО}}, {{ЛЕВОЕ СОЕДИНЕНИЕ}};
* параметры запроса: {{&НачалоПериода}}, {{&Организация}};
* виртуальные таблицы: {{РегистрНакопления.Продажи.Обороты(...)}};
* точечную нотацию ссылочных объектов: {{Контрагенты.Наименование}}, {{Ссылка.Родитель}};
* кириллицу в идентификаторах и параметрах без ложных синтаксических ошибок.

Для 1C Фронтенд-подсветка может использовать согласованный fallback-режим, если нативный Фронтенд-пакет отсутствует. Это не должно влиять на Бэкенд-проверку: Бэкенд не должен проверять 1C-запрос как StandardSQL, если такой способ даёт ложные ошибки.

---
h4. 7.5. JavaScript/TypeScript.

Бэкенд-проверка JavaScript / TypeScript должна корректно обрабатывать:
* TypeScript-типизацию: интерфейсы, generics {{Array<T>}}, {{as const}};
* стрелочные функции;
* деструктуризацию;
* template literals;
* опциональную цепочку {{?.}};
* nullish coalescing {{??}};
* реальные синтаксические ошибки, возвращаемые выбранным parser/ESLint-механизмом.

---
h4. 7.6. Системные конструкции.

Платформенный синтаксис проверяется на каждом выбранном SQL-диалекте отдельно.

|| # || Конструкция || Пример || Ожидаемое поведение ||
| 1 | Простая переменная, латиница | {{\!env.REGION\!}} | Нет синтаксической ошибки; Фронтенд может подсветить как системный токен. |
| 2 | Простая переменная, кириллица | {{\!env.НазваниеРегиона\!}} | Нет синтаксической ошибки; кириллица поддерживается. |
| 3 | Суффикс диапазона | {{\!env.DATE.BEGIN\!}} / {{\!env.DATE.END\!}} | Переменная обрабатывается как единая системная конструкция. |
| 4 | Fallback простой | {{\{\!env.REGION\!; 2\}}} | Точка с запятой внутри fallback-конструкции не считается ошибкой. |
| 5 | Fallback строковый | {{\{\!env.REGION\!; 'default'\}}} | Конструкция валидна целиком. |
| 6 | Выражение и переменная | {{\{toDate(\!env.Date\!); '2020-01-01'\}}} | Функция и переменная внутри fallback-конструкции не дают ложной синтаксической ошибки. |
| 7 | Переменная в теле запроса | {{WHERE region = \!env.REGION\!}} | Нет синтаксической ошибки; токен может подсвечиваться отдельно. |
| 8 | Dollar-переменная | {{$category$}} | Нет синтаксической ошибки. |
| 9 | Незакрытая fallback-скобка | {{\{\!env.REGION\!; 2}} | Бэкенд возвращает диагностику ошибки, Фронтенд визуально показывает проблему. |
| 10 | Переменная внутри строки | {{'prefix_\!env.NAME\!'}} | Для Бэкенд-проверки это строковый литерал; отдельная токенизация переменной не обязательна, синтаксической ошибки быть не должно. |

----
h3. 8. Пограничные сценарии.

Бэкенд и Фронтенд-интеграция должны корректно обрабатывать:
* пустой код, код из пробелов, очень длинный код, {{CRLF}}/{{LF}};
* кириллицу в переменных, параметрах, строках и идентификаторах;
* несколько ошибок в одном фрагменте и ошибки без точной позиции;
* недоступность источника, отсутствие прав, техническую ошибку Бэкенда;
* изменение текста во время проверки и повторный запуск проверки до завершения предыдущей;
* read-only режим и неподдержанный язык/диалект.

Если язык или диалект не поддержан для конкретного модуля, Бэкенд возвращает понятную ошибку о неподдерживаемой проверке.

----
h3. 9. Зависимости и открытые вопросы.

* Точные Бэкенд-объекты и команды для {{«Вычисляемых полей»}} и {{«Правил загрузки данных»}} требуется согласовать с разработкой.
* Для SQL-сценариев источник истины по диалекту определяется Бэкендом по источнику данных, подключению или настройкам модуля.
* Для {{1C}} и {{JavaScript / TypeScript}} требуется согласовать конкретный Бэкенд-валидатор.
* Нужно подтвердить, должны ли предупреждения {{warning}} отображаться пользователю на первом этапе или достаточно ошибок {{error}}.
* Если проверка обращается к внешнему источнику данных, используются существующие таймауты и обработка ошибок подключения.

----
h3. 10. Критерии приёмки (AC):

* *AC.1 (Проверка запускается только явно):*
* *Дано:* пользователь редактирует код в новом редакторе;
* *Когда:* пользователь вводит символы, вставляет текст, перемещает каретку, меняет фокус или открывает редактор;
* *Тогда:* Фронтенд не запускает локальный линтер и не отправляет Бэкенд-запрос проверки синтаксиса.

* *AC.2 (Запрос отправляет актуальный текст):*
* *Дано:* пользователь изменил код в редакторе;
* *Когда:* пользователь нажимает {{«Проверить запрос»}};
* *Тогда:* Фронтенд отправляет на Бэкенд именно текущий текст кода из редактора.

* *AC.3 (Валидный код не содержит диагностик):*
* *Дано:* пользователь ввёл синтаксически валидный код для выбранного языка/диалекта;
* *Когда:* выполняется Бэкенд-проверка;
* *Тогда:* Бэкенд возвращает {{status = 200}}, {{data.valid = true}} и пустой массив {{data.errors}}.

* *AC.4 (Синтаксическая ошибка):*
* *Дано:* пользователь ввёл код с незакрытой скобкой или кавычкой;
* *Когда:* выполняется Бэкенд-проверка;
* *Тогда:* Бэкенд возвращает {{status = 200}}, {{data.valid = false}} и диагностику ошибки с понятным {{message}}.

* *AC.5 (Позиция ошибки отображается в редакторе):*
* *Дано:* Бэкенд вернул диагностику с {{line}} и {{column}};
* *Когда:* Фронтенд обрабатывает ответ проверки;
* *Тогда:* соответствующее место в рабочей области редактора визуально акцентируется как ошибочное.

* *AC.6 (Ошибка без позиции отображается сообщением):*
* *Дано:* Бэкенд вернул диагностику без точной позиции;
* *Когда:* Фронтенд обрабатывает ответ проверки;
* *Тогда:* пользователь видит понятное сообщение об ошибке, а текст в редакторе не теряется.

* *AC.7 (Бэкенд-диагностика сохраняется до повторной проверки):*
* *Дано:* после Бэкенд-проверки в редакторе отображается ошибка;
* *Когда:* пользователь изменяет текст кода, в том числе в ранее подсвеченном участке;
* *Тогда:* ранее полученная Бэкенд-индикация не сбрасывается автоматически и продолжает отображаться до запуска повторной проверки и получения нового результата проверки от Бэкенда.

* *AC.8 (Результат проверки применяется после получения ответа Бэкенда):*
* *Дано:* пользователь запустил Бэкенд-проверку и изменил текст до получения ответа Бэкенда;
* *Когда:* Бэкенд возвращает результат проверки, выполненной для прежней версии текста;
* *Тогда:* Фронтенд отображает полученный результат до проведения повторной проверки.

* *AC.9 (PostgreSQL-специфика поддержана):*
* *Дано:* код содержит PostgreSQL-специфичные конструкции, например {{::}}, dollar-quoted строки, {{WITH RECURSIVE}}, JSON-операторы или {{FILTER (WHERE ...)}};
* *Когда:* выполняется Бэкенд-проверка в контексте PostgreSQL;
* *Тогда:* валидные конструкции не возвращаются как синтаксические ошибки.

* *AC.10 (ClickHouse-специфика поддержана):*
* *Дано:* код содержит ClickHouse-специфичные конструкции, например {{PREWHERE}}, {{ARRAY JOIN}}, {{arrayMap(x -> x * 2, arr)}}, {{sumIf}}, {{SETTINGS}} или {{FORMAT}};
* *Когда:* выполняется Бэкенд-проверка в контексте ClickHouse;
* *Тогда:* валидные конструкции не возвращаются как синтаксические ошибки.

* *AC.11 (MySQL-специфика поддержана):*
* *Дано:* код содержит MySQL-специфичные конструкции, например backtick-идентификаторы, {{LIMIT offset, count}}, {{ON DUPLICATE KEY UPDATE}}, {{GROUP_CONCAT}} или комментарии {{#}};
* *Когда:* выполняется Бэкенд-проверка в контексте MySQL;
* *Тогда:* валидные конструкции не возвращаются как синтаксические ошибки.

* *AC.12 (1C-специфика поддержана):*
* *Дано:* код содержит валидный запрос 1C с кириллическими ключевыми словами, параметрами {{&НачалоПериода}} и виртуальными таблицами;
* *Когда:* выполняется Бэкенд-проверка в контексте 1C;
* *Тогда:* Бэкенд не проверяет код как StandardSQL и не возвращает ложные синтаксические ошибки.

* *AC.13 (JavaScript / TypeScript поддержаны):*
* *Дано:* код содержит валидные JavaScript / TypeScript-конструкции, включая generics, стрелочные функции, template literals, {{?.}} и {{??}};
* *Когда:* выполняется Бэкенд-проверка в контексте JavaScript / TypeScript;
* *Тогда:* валидные конструкции не возвращаются как синтаксические ошибки, а реальные синтаксические ошибки возвращаются как Бэкенд-диагностики.

* *AC.14 (Системный синтаксис Modus BI поддержан):*
* *Дано:* код содержит {{\!env.REGION\!}}, {{\!env.НазваниеРегиона\!}}, {{\!env.DATE.BEGIN\!}}, fallback-конструкции или {{$category$}};
* *Когда:* выполняется Бэкенд-проверка на любом поддержанном SQL-диалекте;
* *Тогда:* эти конструкции не считаются синтаксическими ошибками.

* *AC.15 (Незакрытая системная конструкция является ошибкой):*
* *Дано:* код содержит незакрытую fallback-конструкцию, например {{\{\!env.REGION\!; 2}};
* *Когда:* выполняется Бэкенд-проверка;
* *Тогда:* Бэкенд возвращает диагностику ошибки, а Фронтенд визуально показывает проблему, если позиция доступна.

* *AC.16 (Произвольный набор данных сохраняет бизнес-логику):*
* *Дано:* пользователь редактирует поле {{«SQL Запрос»}} в карточке *произвольного* набора данных;
* *Когда:* пользователь нажимает {{«Проверить запрос»}} и SQL валиден;
* *Тогда:* выполняется текущая бизнес-логика проверки SQL и обновления выходных полей.

* *AC.17 (Невалидный SQL не разрушает выходные поля):*
* *Дано:* в карточке *произвольного* набора данных уже есть валидный список выходных полей;
* *Когда:* пользователь вводит синтаксически невалидный SQL и нажимает {{«Проверить запрос»}};
* *Тогда:* Бэкенд возвращает диагностику ошибки, а существующий валидный список выходных полей не разрушается некорректным промежуточным состоянием.

* *AC.18 (Правила модулей сохранены):*
* *Дано:* пользователь работает с вычисляемым полем, правилом загрузки данных или другим объектом, где используется редактор кода;
* *Когда:* выполняется проверка или сохранение объекта;
* *Тогда:* действующие правила проверки, сохранения и ограничения соответствующего модуля продолжают применяться.

* *AC.19 (Техническая ошибка отделена от синтаксической):*
* *Дано:* Бэкенд не может выполнить проверку из-за недоступности источника, ошибки доступа или внутренней ошибки;
* *Когда:* Фронтенд получает ответ;
* *Тогда:* пользователь видит понятное сообщение о технической проблеме, а ошибка не отображается как синтаксическая ошибка конкретного участка кода.

* *AC.20 (Права и секреты защищены):*
* *Дано:* пользователь не имеет прав на проверяемый объект или источник;
* *Когда:* выполняется Бэкенд-проверка;
* *Тогда:* Бэкенд возвращает ошибку доступа и не раскрывает код, метаданные источника, пароли, токены или параметры подключения.

* *AC.21 (Производительность длинного кода):*
* *Дано:* пользователь работает с кодом объёмом 500+ строк или запускает проверку фрагмента 1000+ строк;
* *Когда:* выполняется редактирование или Бэкенд-проверка;
* *Тогда:* ввод в редакторе не лагает из-за Бэкенд-проверки, а Бэкенд-парсинг без обращения к источнику укладывается в согласованный целевой показатель.

* *AC.22 (Read-only режим не запускает проверку автоматически):*
* *Дано:* код открыт через общий виджет в режиме только для чтения;
* *Когда:* пользователь просматривает код;
* *Тогда:* Фронтенд не запускает локальный линтер и не отправляет автоматическую Бэкенд-проверку.

* *AC.23 (Подсветка и базовый UX редактора сохранены):*
* *Дано:* Бэкенд-проверка синтаксиса внедрена;
* *Когда:* пользователь работает с редактором;
* *Тогда:* подсветка синтаксиса, автодополнение, bracket matching, автозакрытие скобок/кавычек, Undo/Redo, мультикурсор, внутренний скролл и resize продолжают работать по ранее заданным правилам.

* *AC.24 (Payload сохранения не меняется из-за диагностик):*
* *Дано:* пользователь проверил код и затем сохраняет объект;
* *Когда:* выполняется штатное сохранение формы;
* *Тогда:* Бэкенд-диагностики проверки не добавляют новые служебные поля в payload сохранения объекта, если это не требуется действующей бизнес-логикой модуля.
