# 2. Поиск в таблице

Обсуждение: 00:00:07–00:44:56

## 2.1. Общая цель функциональности

Необходимо добавить возможность поиска и фильтрации данных непосредственно по колонкам обычной таблицы аналитического портала ФРП.

Основная идея — предоставить пользователю возможность быстро находить нужные строки, не прибегая к выгрузке данных или обязательному использованию внешних фильтров дашборда.

В качестве референса заказчик предоставил ранее подготовленный макет таблицы, в котором под заголовками колонок расположена дополнительная строка с элементами фильтрации.

В зависимости от колонки в этой строке могут находиться:

- Текстовый поиск по ключевому слову.
- Выпадающий список со значениями и чекбоксами.
- Фильтр по дате с календарём.
- Пустая область, если для соответствующей колонки фильтрация не предусмотрена.

Важный момент: Андрей Акатов подтвердил, что исходный макет актуален и соответствует стилистике других сервисов ГИСП.

Вместе с тем заказчик не требует безусловно копировать каждую деталь реализации. Допускается предложить альтернативные решения, более соответствующие аналитическому порталу и существующим компонентам Modus BI.

Главное условие — согласовывать альтернативы на ранней стадии, до реализации функциональности, а не демонстрировать их заказчику после завершения разработки.

## 2.2. Отображение строки поиска под заголовками таблицы

В макете предусмотрена дополнительная строка непосредственно под заголовками колонок.

Она содержит элементы управления фильтрацией.

Например:

| Продукция   | Класс РЭП | Дата регистрации   | Сумма субсидии |
| ----------- | --------- | ------------------ | -------------- |
| &#x20;Найти | &#x20;Все | &#x20;Выбрать дату | —              |

Условная иллюстрация типов элементов фильтрации. Не финальный макет интерфейса.

### 2.2.1. Строка поиска должна быть опциональной

Андрей Акатов однозначно подтвердил, что отображение дополнительной строки с фильтрами должно быть опциональным.

Не каждая таблица должна содержать встроенные фильтры.

Это связано, в частности, с существующими аналитическими панелями, которые уже были спроектированы с внешними фильтрами.

Из-за отсутствия поиска внутри таблицы ранее приходилось выносить фильтры в отдельные элементы дашборда.

Таких панелей несколько, и заказчик не хочет впоследствии полностью пересобирать их только из-за появления новой функциональности.

Следовательно, необходимо сохранить возможность использования таблиц без дополнительной строки поиска.

### 2.2.2. Необязательно отображать поиск для каждой колонки

Допустима ситуация, когда фильтрация доступна лишь для части колонок таблицы.

Пример, приведённый при обсуждении:

- «Системный номер заявки» — поиск есть.
- «Наименование организации» — поиск есть.
- «Банк» — поиск есть.
- «Год отбора» — поиск отсутствует, если он не настроен.
- «Сумма кредита» или «Сумма субсидии» — поиск может отсутствовать.

При этом пустые области под колонками считаются допустимыми.

Андрей Полянский подтвердил, что подобный подход уже используется в реестрах ГИСП и в целом является корректным.

Таким образом, согласована допустимость выборочной фильтрации по колонкам. Однако окончательный механизм, определяющий наличие фильтра у конкретной колонки, ещё не выбран.

## 2.3. Типы поиска и фильтрации

На встрече подробно разобрали различия между фильтрами для разных типов полей.

### 2.3.1. Поиск по текстовому полю

Пример: колонка «Продукция».

В первоначальном макете у этого поля находится элемент «Найти».

При его открытии предполагается строка ввода, с помощью которой можно отбирать записи по ключевым словам или частям строк.

Андрей Акатов привёл пример:

В реестре продукции нужно найти все позиции, связанные с производством автомобилей.

Пользователь вводит слово `автомобиль` либо `грузовик`, после чего получает соответствующие строки.

Для такого сценария важен поиск по фрагменту текстового значения, поскольку пользователь может не знать полного наименования.

В демонстрировавшемся ГИСП дополнительно присутствуют параметры:

- «Поиск с начала строки».
- «Показать пустые значения».

При включённом поиске с начала строки введённые символы должны находиться именно в начале значения. При выключенном — поиск выполняется по всему значению.

Андрей Акатов считает настройку «Поиск с начала строки» избыточной для аналитического портала. По его мнению, для работы с аналитическими панелями достаточно более простой фильтрации.

Если пользователю требуется сложный детальный отбор, данные можно экспортировать в Excel и продолжить работу там.

Таким образом, включение дополнительного переключателя «Поиск с начала строки» в целевой интерфейс не требуется по высказанному пожеланию заказчика.

### 2.3.2. Поиск с выпадающим списком значений

Пример: колонка «Класс РЭП».

В отличие от свободного текстового поля, эта колонка представляет собой справочник с некоторым набором допустимых значений.

В первоначальном макете для неё предусмотрен выпадающий список.

При открытии такого фильтра пользователь получает:

- Строку поиска по значениям списка.
- Перечень доступных значений.
- Чекбоксы для выбора одного или нескольких значений.
- Возможность выделить все найденные значения.
- Возможность исключить отдельные значения.
- Применение выбранного набора значений для фильтрации данных.

Важное функциональное различие:

Строка поиска внутри выпадающего списка фильтрует сам перечень доступных значений, а не строки исходной таблицы.

Это было отдельно продемонстрировано на примере ГИСП.

Последовательность работы:

1. Пользователь открывает выпадающий список фильтра.
2. Вводит поисковое выражение, например `заяв`.
3. Список сокращается до значений, содержащих соответствующий фрагмент.
4. Пользователь выбирает конкретные значения вручную либо нажимает «Выделить все найденные значения».
5. Применяет выбранный набор.
6. Таблица отфильтровывается по выбранным значениям.

Если пользователь только введёт поисковое выражение, но не выберет значения списка, фильтрация таблицы не выполнится.

Андрей Акатов подтвердил это поведение при демонстрации существующего сервиса.

### 2.3.3. Возможность объединить текстовый поиск и выпадающий список

Роман Чернышов предложил использовать комбинированный фильтр не только для справочников, но и для обычных текстовых полей.

Суть предложения — вместо простой строки поиска использовать выпадающий список, содержащий одновременно строку поиска и чекбоксы.

Пример:

Имеются значения:

- «Автомобиль Ford».
- «Автомобиль Ferrari».
- «Автомобиль неизвестный».

Пользователь вводит `автомобиль`.

В выпадающем списке отображаются все три значения, после чего пользователь может выбрать только Ford и Ferrari, исключив третье значение.

Такой подход позволяет одновременно:

- Искать значения по фрагменту строки.
- Выделять все найденные значения.
- Выбирать отдельные значения из результатов поиска.
- Исключать ненужные значения.

Роман Чернышов отметил, что это соответствует существующей стандартной функциональности фильтров Modus BI.

Андрей Акатов согласился, что подход выглядит логично и может применяться.

Статус: заказчик положительно воспринял предложение, однако окончательно оно не утверждено как единый обязательный способ фильтрации всех текстовых колонок.

### 2.3.4. Большое количество уникальных значений

Отдельно обсуждалась ситуация, когда у колонки очень высокая кардинальность — большое количество уникальных значений.

Роман Чернышов указал, что в Modus BI уже существует механизм работы с большими наборами значений.

В качестве ориентира упоминалось более 5000 уникальных значений.

Для таких полей предложено рассмотреть поведение, при котором:

- Не загружается первоначальный перечень всех уникальных значений.
- Выпадающий список не отображается либо скрывается опционально.
- Пользователю предоставляется поле ввода искомого значения.
- Поиск не требует предварительного отображения всех возможных вариантов.

Это должно позволить работать с колонками, где формирование полного списка значений нежелательно.

Статус: предварительное техническое предложение Романа Чернышова. Не согласованы точный порог, критерии переключения режимов и результирующее поведение фильтра.

Упомянутые 5000 значений не следует автоматически считать утверждённым ограничением новой функциональности.

## 2.4. Фильтрация по дате

Заказчик продемонстрировал механизм выбора дат, существующий в ГИСП.

Рассматривались четыре режима:

| Режим     | Описание                                               |
| --------- | ------------------------------------------------------ |
| «На дату» | Выбор одной конкретной даты                            |
| «С»       | Отбор записей, дата которых больше или равна выбранной |
| «До»      | Отбор записей, дата которых меньше или равна выбранной |
| «Период»  | Отбор в пределах выбранного временного интервала       |

Для режимов «С» и «До» Андрей Акатов подтвердил сравнение с включением граничного значения.

Для режима «Период» демонстрировалась возможность указать начало и конец периода. Детали включения обеих границ отдельно не разбирались.

### 2.4.1. Календарь выбора даты

В демонстрации использовался календарь со следующей навигацией:

- Переключение месяцев стрелками влево и вправо.
- Переключение годов отдельными двойными стрелками.
- Возможность перехода к определённому месяцу.
- Возможность перехода к определённому году.

Роман Чернышов уточнил, требуется ли воспроизведение именно такого календаря.

Андрей Акатов не настаивал на его полном копировании. Он предложил при необходимости рассмотреть альтернативную реализацию, более соответствующую интерфейсу аналитических панелей.

Если существующий компонент выбора даты Modus BI имеет отличия, эти отличия следует проработать и согласовать заранее.

### 2.4.2. Пустые значения дат

В существующем сервисе ГИСП есть настройка «Показать пустые значения».

Пример использования:

Если заявка не зарегистрирована, у неё отсутствует дата регистрации.

Чтобы найти такие заявки, пользователь выбирает соответствующую опцию и получает записи без даты.

Это отдельный пользовательский сценарий, который не должен теряться при анализе функциональности.

Однако Андрей Акатов прямо отметил, что не уверен в необходимости этой настройки для аналитического портала.

Поэтому её следует рассматривать как функцию существующего референса, требующую решения о включении в целевой объём разработки.

### 2.4.3. Кнопки применения фильтра

В ходе обсуждения упоминались действия:

- «Применить».
- «Отмена».

В ГИСП они используются в интерфейсе фильтрации.

При этом вопрос, требуется ли точно повторить такую модель подтверждения изменений или использовать существующее поведение фильтров аналитического портала, остался открытым.

Итог по датам: логика выбора конкретной даты и периода определена на уровне референса. Интерфейс календаря, дополнительные настройки и механизм применения изменений необходимо согласовать отдельно.

## 2.5. Конфигурация фильтров при создании таблицы

Это один из ключевых вопросов встречи.

Обсуждалось, каким образом аналитик или автор дашборда будет определять:

- Для каких колонок должен появляться поиск.
- Какой тип фильтра использовать.
- Будет ли фильтр локальным или общим.
- Какие уже существующие настройки Modus BI можно переиспользовать.

### 2.5.1. Как это устроено в ГИСП

Андрей Акатов продемонстрировал конструктор реестров ГИСП.

В настройках атрибута реестра присутствует параметр «Фильтр».

Для каждого атрибута можно указать тип фильтрации.

Особенно часто используются:

| Тип в конструкторе | Поведение                             |
| ------------------ | ------------------------------------- |
| `string`           | Поиск через текстовое поле            |
| `checkbox`         | Выпадающий список для выбора значений |
| «Без фильтра»      | Фильтрация для атрибута отсутствует   |

Также имеется возможность задать значение фильтра по умолчанию.

Если выбрать «Без фильтра» и сохранить настройку, элемент поиска у соответствующей колонки пропадает.

Андрей Акатов подтвердил такое поведение на демонстрации.

Он также отметил недостаток данного механизма: иногда поиск не был заранее настроен для определённого поля, а пользователю впоследствии требуется быстро по нему отфильтровать таблицу.

Поэтому излишне жёсткое ограничение набора доступных колонок может ухудшать удобство работы.

### 2.5.2. Предложение использовать полку «Фильтры» Modus BI

Андрей Полянский предложил привязать встроенные фильтры обычной таблицы к существующей полке «Фильтры» компонента.

Вадим Мединцев развил это предложение.

В качестве возможной модели конфигурации обсуждалось:

1. В таблице появляется настройка «Отобразить фильтры таблицы».
2. Настройка включает или выключает дополнительную строку фильтров под заголовками колонок.
3. Для появления поиска по конкретной колонке необходимо добавить соответствующее поле на полку «Фильтры».
4. Если поле присутствует и в таблице, и на полке «Фильтры», для него может появляться встроенный элемент фильтрации.
5. Если поле не добавлено на полку, встроенный элемент фильтрации по этой колонке не отображается.
6. Дополнительные свойства фильтра берутся из настроек соответствующей пилюли.
7. В зависимости от настроек пилюли фильтр может быть локальным или общим.

Андрей Полянский подтвердил, что считает такой подход в целом корректным.

Роман Чернышов также отметил, что вариант выглядит уместным, но требует технической проверки.

Статус: поддержанный концептуальный вариант, но не утверждённая окончательная схема реализации.

### 2.5.3. Использование существующих настроек пилюль

Вадим Мединцев обратил внимание на дополнительное преимущество привязки к полке «Фильтры».

Если встроенный фильтр будет связан с пилюлей, можно повторно использовать уже существующие настройки фильтрации Modus BI.

Например:

- Выбор типа фильтра.
- Отображение выпадающего списка значений.
- Использование фильтра без выпадающего списка.
- Настройка диапазона для полей с датами.
- Настройка области воздействия фильтра — локальной или общей.

Это позволяет избежать создания отдельной независимой системы настройки фильтров для таблицы.

При таком подходе функциональность фильтрации внутри таблицы может быть продолжением уже существующего механизма фильтров платформы.

Однако конкретный перечень переиспользуемых настроек и их совместимость ещё необходимо проверить.

## 2.6. Локальная и общая фильтрация: принципиальное отличие

Вопрос области действия фильтра оказался одним из наиболее существенных и остался открытым.

### 2.6.1. Локальный фильтр

При локальном режиме поиск внутри таблицы влияет только на строки этой таблицы.

Другие визуальные компоненты дашборда не должны изменяться в результате применения локального фильтра таблицы.

Андрей Полянский первоначально предложил придерживаться именно такой модели, чтобы не создавать конфликтов между:

- Фильтрами самой таблицы.
- Основными фильтрами аналитической панели.
- Общими фильтрами в боковой панели.
- Фильтрами других визуальных компонентов.

Роман Чернышов пояснил предполагаемый принцип взаимодействия:

Если общий фильтр дашборда уже ограничил данные таблицы, локальный поиск внутри неё применяется к оставшемуся набору данных.

Например:

- Общий фильтр дашборда оставил записи только по определённому региону.
- В таблице пользователь дополнительно ищет конкретную организацию.
- Таблица показывает записи этой организации внутри уже выбранного региона.
- Остальные компоненты не изменяются от локального поиска организации.

Это было описано как ожидаемая логика, а не как окончательно утверждённое техническое правило.

### 2.6.2. Риск незаметной локальной фильтрации

Андрей Акатов обратил внимание на потенциальную проблему UX.

Пользователь может:

1. Применить локальный фильтр внутри таблицы.
2. Перейти к другой области аналитической панели.
3. Забыть, что в таблице продолжает действовать дополнительная фильтрация.
4. Вернуться к таблице и увидеть данные, не совпадающие с результатами других визуализаций.
5. Ошибочно решить, что данные отображаются неправильно.

При этом значения общих фильтров дашборда не будут отражать локальное ограничение таблицы.

Это отдельная проблема, которую необходимо учитывать при проектировании.

На встрече не согласовывали конкретный способ её решения: индикацию применённых локальных фильтров, централизованный сброс или иной механизм.

Следовательно, эту проблему нельзя считать автоматически решённой выбором локального режима.

### 2.6.3. Общий фильтр

Общий режим предполагает, что изменение фильтра в колонке таблицы может воздействовать и на другие визуализации дашборда.

Андрей Полянский обозначил важный сценарий:

В некоторых отчётах таблица является центральным элементом аналитической панели.

В таком случае пользователь должен иметь возможность отфильтровать данные в таблице и затем анализировать дополнительные визуализации на основе выбранных значений.

Следовательно, исключительно локальный режим может оказаться недостаточным.

Рассматривалась возможность позволить автору отчёта выбирать область действия каждого фильтра.

| Характеристика                                         | Локальный фильтр | Общий фильтр            |
| ------------------------------------------------------ | ---------------- | ----------------------- |
| Изменяет данные самой таблицы                          | Да               | Да                      |
| Воздействует на другие визуализации                    | Нет              | Предполагается          |
| Подходит для независимого поиска в таблице             | Да               | В зависимости от задачи |
| Подходит для таблицы, управляющей другими компонентами | Нет              | Да                      |
| Связь с полкой «Фильтры»                               | Предложена       | Предложена              |

Ключевой результат обсуждения: оба сценария имеют практический смысл. Окончательное решение об обязательности или настраиваемости области действия фильтров не принято.

## 2.7. Особые ситуации при привязке к полке «Фильтры»

### 2.7.1. Поле таблицы отсутствует на полке «Фильтры»

Предполагается, что для такого поля встроенный фильтр не отображается.

Например, колонка «Год отбора» присутствует в таблице, но соответствующей пилюли нет на полке «Фильтры».

Тогда под заголовком «Год отбора» остаётся пустая область.

В целом такое поведение участники сочли допустимым.

### 2.7.2. Поле присутствует на полке «Фильтры», но отсутствует среди колонок

Роман Чернышов отдельно отметил обратную ситуацию.

На полке «Фильтры» может присутствовать поле, которое вообще не выведено в шапку таблицы.

В таком случае пилюля продолжает выполнять свою обычную функцию локального либо общего фильтра, но не создаёт дополнительный элемент в строке поиска таблицы.

То есть само присутствие пилюли на полке ещё не означает, что под неё обязательно должна существовать колонка.

### 2.7.3. Одно поле присутствует на полке «Фильтры» дважды

Вадим Мединцев поднял вопрос возможной неоднозначности.

Пример:

На полке «Фильтры» дважды размещено поле «Регион»:

- Первая пилюля — общий фильтр.
- Вторая пилюля — локальный фильтр.

При этом среди колонок таблицы «Регион» присутствует только один раз.

Получается, что у одной колонки может быть два потенциальных источника настроек фильтра.

Возникает вопрос: какую пилюлю использовать для построения встроенного фильтра?

Предложение Вадима Мединцева: сопоставлять колонку с первой соответствующей пилюлей на полке «Фильтры», то есть с расположенной левее остальных.

Тогда для определения поведения встроенного фильтра используется первая подходящая пилюля.

Однако Роман Чернышов отметил важную неопределённость: необходимо сначала проверить, действительно ли текущая реализация позволяет одновременно размещать на полке два одинаковых поля с разными областями действия — общим и локальным.

Если такой сценарий поддерживается, потребуется однозначное правило сопоставления.

Статус: предложение использовать первую пилюлю обсуждено, но окончательно не утверждено.

### 2.7.4. Необходимость сопоставления колонок и пилюль

При привязке встроенных фильтров к полке «Фильтры» потребуется определить правила сопоставления полей.

Как минимум необходимо предусмотреть случаи:

- Одна колонка — одна соответствующая пилюля.
- Колонка без соответствующей пилюли.
- Пилюля без соответствующей колонки.
- Несколько пилюль одного поля, в том числе с разными областями действия.

Общую идею участники поддержали, но техническая реализация и правила разрешения неоднозначностей требуют отдельной проработки.

## 2.8. Альтернативный механизм — настройки непосредственно у колонок

Роман Чернышов предложил не ограничиваться вариантом с полкой «Фильтры».

В качестве альтернативы рассматривался механизм, уже существующий в сводной таблице Modus BI.

Там поиск может включаться непосредственно для выбранных колонок на полках строк или детализации.

При таком подходе:

- Автор отчёта включает поиск для определённой колонки.
- Наличие встроенного фильтра не обязательно определяется полкой «Фильтры».
- Область действия фильтра может быть заранее заданной.
- Поиск может всегда работать локально либо, если будет выбрана другая модель, всегда быть общим.

Роман Чернышов предположил, что в существующей сводной таблице поиск, скорее всего, работает локально, но отметил необходимость проверки.

Итак, к концу обсуждения остались два основных архитектурных варианта:

| Критерий                                     | Вариант А — через полку «Фильтры»                      | Вариант Б — через настройки колонки |
| -------------------------------------------- | ------------------------------------------------------ | ----------------------------------- |
| Где включается поиск                         | Через наличие и настройки пилюль и общий переключатель | В настройках выбранной колонки      |
| Область действия                             | Может определяться настройками пилюли                  | Может быть фиксированной            |
| Использование существующих настроек фильтров | Основное преимущество                                  | Зависит от реализации               |
| Сопоставление нескольких одинаковых полей    | Требует решения                                        | Может не возникать в таком виде     |
| Аналог существующего компонента              | Механизм полки «Фильтры»                               | Сводная таблица                     |
| Статус                                       | Поддержанный вариант                                   | Альтернативный вариант              |

Итог: Роман Чернышов сообщил, что команда дополнительно проработает оба подхода и предложит заказчику целевую реализацию.

## 2.9. Особенности интерфейса, затронутые при обсуждении поиска

Кроме основной механики фильтрации, были рассмотрены дополнительные элементы таблицы.

### 2.9.1. Область нажатия на элемент поиска

В существующем ГИСП элемент «Найти» открывается при нажатии не только непосредственно на текст или иконку лупы.

Кликабельная область занимает почти всю ширину соответствующей колонки в строке фильтров.

Это было подтверждено Андреем Акатовым при демонстрации.

Однако отдельного решения об обязательном воспроизведении такой ширины интерактивной области в аналитическом портале не принималось.

### 2.9.2. Визуальное различие текстового и списочного фильтров

Андрей Акатов обратил внимание, что после одного из обновлений ГИСП разные виды поиска начали отображаться похожим образом.

Ранее визуально различались:

- Поле «Найти» для текстового поиска.
- Выпадающий список с выбранным значением «Все».

Заказчик предположил, что изменение могло быть вызвано обновлением существующего сервиса.

Это означает, что случайные отличия в текущем интерфейсе ГИСП не следует автоматически принимать за новые дизайнерские требования.

Предпочтительно ориентироваться на согласованную концепцию и исходные макеты.

### 2.9.3. Закрепление колонок

В демонстрировавшемся сервисе ГИСП присутствовала функция «Закрепить колонку».

Андрей Акатов прямо подтвердил, что эта функция не требуется для рассматриваемой задачи.

Добавлять её в объём работ по поиску не нужно.

### 2.9.4. Сортировка колонок

Отдельно рассмотрели различия между сортировкой в ГИСП и в текущем аналитическом портале.

Решено сохранить существующее поведение сортировки Modus BI.

Оно заключается в следующем:

- Если сортировка по колонке активна, стрелка отображается постоянно.
- Если сортировка отсутствует, стрелка появляется при наведении курсора.
- Стрелка расположена справа, у края заголовка колонки.
- Сортировка может переключаться между возрастанием и убыванием.
- Изменять текущее расположение стрелки не требуется.

Заказчик подтвердил, что такой подход правильный и не создаёт лишнего визуального шума.

В старом макете стрелка располагалась ближе к тексту заголовка. Это отличие было признано некритичным.

Следовательно, доработка сортировки в рамках задачи поиска не требуется.

### 2.9.5. Общий внешний вид таблицы

При демонстрации реестра ГИСП выяснилось, что показанная таблица использует преимущественно настройки оформления по умолчанию.

Андрей Полянский подтвердил, что отдельная стилизация таблицы при её создании не настраивалась.

Роман Чернышов отметил, что внешний вид таблицы по умолчанию в Modus BI несколько отличается от показанного референса.

Этот вопрос был поднят для понимания необходимости дополнительной стилизации.

Однако отдельное решение об изменении стандартного оформления таблицы в рамках текущей задачи принято не было.

## 2.11. Итог по поиску

Позиция заказчика, подтверждённая в ходе встречи:

- Поиск внутри обычной таблицы необходим.
- Строка встроенных фильтров должна быть опциональной.
- Фильтрация нужна не для всех колонок.
- Необходимо поддерживать разные способы отбора данных — текстовый поиск, выбор значений и поиск по дате.
- Излишне сложные опции существующего конструктора ГИСП не обязательно переносить в аналитический портал.
- Возможность использования выпадающего списка со строкой поиска получила положительную оценку.
- Функция закрепления колонок не требуется.
- Текущую сортировку Modus BI следует сохранить.
- Основная функциональность фильтрации должна соответствовать привычному подходу заказчика, но допускаются согласованные альтернативы.

Главный нерешённый вопрос: архитектура управления встроенными фильтрами — через полку «Фильтры» с поддержкой локального и общего режимов либо через независимые настройки колонок.

До передачи задачи в разработку необходимо представить заказчику конкретную схему конфигурации и поведения фильтров, а также согласовать её интерфейсную реализацию.
