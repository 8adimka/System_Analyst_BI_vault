2) Критерий — Цветовое выделение по знаку.

Автоматическая раскраска столбцов в зависимости от знака значения и отдельное оформление итоговых/промежуточных итоговых столбцов.

Шкала:
0 — все столбцы одного цвета;
1 — положительные и отрицательные значения различаются, но итоговые столбцы не отличаются или цвета фиксированы;
2 — три типа раскраски: положительные, отрицательные и итоговые столбцы; цвета каждого типа настраиваются.

Фактически подтверждённое текущее состояние:

  - «Увеличение»;

Целевое состояние — 2 балла:
должна быть доступна отдельная настройка цвета для:
- увеличения;
- уменьшения;
- итога/подытога.

0 — добавление подытогов не поддерживается;
1 — подытоги можно задать только вручную как отдельные строки данных, без встроенной Waterfall-механики;
2 — имеется встроенный механизм назначения промежуточного итога с возможностью его отображения/скрытия.

Фактически подтверждённое текущее состояние:
- первый полученный визуализацией элемент автоматически считается начальным итогом и строится от нуля;
- итог после последнего изменения рассчитывается автоматически и отображается отдельным серым столбцом;
- произвольный промежуточный итог назначить нельзя;
- если в данные передать значение «Коммерческий итог», «Операционный итог» и т.п., визуализация воспринимает такое значение как обычное положительное изменение и прибавляет его к накопленному результату;
- специального признака/настройки типа столбца нет;
- скрытие/отображение отдельных подытогов отсутствует.

Предварительная текущая оценка — 0 баллов.

Целевое состояние — 2 балла.

4) Критерий — Опорные линии.

Динамические опорные линии по формуле с настраиваемыми подписями.

ВАЖНО:
для Громова необходимо явно указать максимальное количество одновременно поддерживаемых опорных линий.

Шкала:
0 — отсутствуют;
1 — поддерживаются только статические линии;
2 — поддерживаются динамические линии по формуле с подписями и указан максимальный лимит.

Фактически подтверждённое текущее состояние:
специализированного механизма опорных линий в Waterfall нет.

Предварительная текущая оценка — 0 баллов.

Целевое состояние — 2 балла.

При подготовке постановки:
- проверить, имеется ли на портале стандартный переиспользуемый механизм опорных линий;
- при наличии максимально переиспользовать его;
- опорная линия должна поддерживать динамическое числовое значение/выражение и подпись;
- должно поддерживаться несколько линий;
- обязательно определить и зафиксировать максимальное количество линий.

Не придумывать лимит без основания.
Если общего платформенного ограничения нет и количество не согласовано — вынести это отдельным открытым вопросом.

5) Критерий — Типы данных.

Поддержка различных способов организации входных данных:
- «одно измерение — один показатель»;
- «без измерений — набор показателей»;
- при необходимости комбинированных вариантов.

Шкала:
0 — поддерживается только один фиксированный формат;
1 — поддерживаются несколько форматов, но не полностью или с неудобным переключением;
2 — несколько форматов входных данных корректно поддерживаются как полноценные Waterfall-сценарии.

Фактически подтверждённое текущее состояние:
- рабочим является формат «одно измерение + один показатель»;
- формат «без измерения + набор показателей» корректно не работает;
- режим «Все» на полке «Значения» фактически не обрабатывает вторую и последующие пилюли;
- существующая полка «Серии» при включении ломает построение.

Предварительная текущая оценка — 0 баллов, т.к. фактически работает только один формат.

Целевое состояние — обеспечить несколько полноценных способов организации данных, достаточных для 2 баллов.

6) Критерий — Метки дельт на соединительных линиях.

Возможность отображать абсолютные и/или относительные изменения между последовательными столбцами.

Шкала:
0 — отсутствуют;
1 — отображается только один тип дельты без гибкой настройки;
2 — доступны абсолютная и относительная дельта, одновременно либо по выбору, с форматированием.

Фактически подтверждённое текущее состояние:
- специализированных подписей дельт нет;
- отображаются только обычные числовые подписи значений столбцов;
- управления дельтами нет.

Предварительная текущая оценка — 0 баллов.

Целевое состояние — 2 балла.

----------------------------------------------------------------------
ПЕРВОНАЧАЛЬНЫЕ ТРЕБОВАНИЯ ДЛЯ КОНТЕКСТА
----------------------------------------------------------------------

Необходимо создать/доработать визуальный компонент «Водопад» (Каскадная диаграмма), встроенный в Аналитический портал.

Waterfall предназначен для факторного анализа: последовательного отображения положительного и отрицательного влияния факторов на исходный показатель и получения конечного результата.

Первоначально рассматривались два способа организации Набора данных.

Вариант 1 — факторы вынесены в отдельные поля.

Например:
- Начальный результат;
- Рост продаж;
- Ценовой эффект;
- Логистика;
- ФОТ;
- Налог;
- и т.д.

На полке «Значения» размещаются стандартные и вычисляемые поля.

В дальнейшем этот вариант необходимо описывать как:
«без измерения — набор показателей»,
чтобы не путать организацию НД с ориентацией самой диаграммы.

Вариант 2 — факторы находятся в строках.

Например:

Фактор | Значение
Начальный результат | 1000
Рост продаж | 350
Логистика | -150
...

На полке «Категории» располагается поле с наименованием фактора,
на полке «Значения» — поле со значением фактора.

Этот вариант далее следует обозначать:
«одно измерение — один показатель».

ВАЖНЫЕ исходные требования:
1. Любому показателю должна назначаться роль «Итог». Итоговый столбец начинается от нуля.
2. Должны отдельно настраиваться цвета:
   - увеличения;
   - уменьшения;
   - итога.
3. Должны настраиваться подписи элементов легенды:
   - увеличение;
   - уменьшение;
   - итог.
4. Должно быть возможно:
   - скрыть/показать легенду;
   - изменить её расположение.
5. Должна существовать настройка «Показывать соединительные линии».
   Значение по умолчанию — включено.
6. Положительные изменения в подписях отображаются с префиксом `+`.
7. Для вертикальной ориентации положительные подписи располагаются над столбцом, отрицательные — под столбцом.
8. Требовалась возможность отображать относительное изменение в процентах.
   В первоначальной постановке база процента определялась как предыдущий итоговый столбец.

При формализации новой постановки учитывать, что критерий Громова по дельтам теперь является обязательным, а не факультативным.

----------------------------------------------------------------------
ФАКТИЧЕСКОЕ ТЕКУЩЕЕ СОСТОЯНИЕ WATERFALL
----------------------------------------------------------------------

По результатам ручного обследования существующего плагина подтверждено следующее.

1. Состав полок

В Waterfall имеются:
- «Значения»;
- «Категории»;
- «Серии»;
- «Фильтры».

2. Полка «Значения»

Текущий декларируемый интерфейс:
- допускает несколько пилюль;
- содержит режим:
  - «Первое»;
  - «Все».

Предполагаемая общая семантика портала:
- «Первое» — используется первая пилюля;
- «Все» — используются все пилюли.

Фактическое Waterfall-поведение:
- в рабочем формате «Категория + Значение» первая пилюля обрабатывается;
- добавление второй пилюли, например «План», и включение режима «Все» визуально ничего не меняет;
- вторая пилюля не появляется ни в диаграмме, ни во всплывающей подсказке;
- следовательно, режим «Все» в текущем плагине фактически не реализован.

3. Полка «Категории»

Визуализация использует первую пилюлю.

Рабочая конфигурация:
- «Категории» → `Фактор`;
- «Значения» → `Значение фактора`.

При такой модели Waterfall строится.

Критический текущий недостаток:
у пилюль Waterfall полностью отсутствует стандартное выпадающее меню настроек.

В других визуализациях Modus BI такие меню существуют и их состав зависит от полки.

Например, стандартные пилюли могут содержать:
- изменение имени поля;
- сортировку;
- сортировку по другому полю;
- тип;
- агрегацию;
- уровень вычисления;
- скрытие результата;
- подсказку по другому полю;
- другие стандартные настройки в зависимости от типа полки.

В Waterfall это меню не подключено вообще.

Следствие:
невозможно настроить порядок факторов штатным механизмом, например:
`Фактор` сортировать по `Порядок` по возрастанию.

Из-за этого порядок шагов Waterfall определяется неуправляемым текущим порядком результата запроса, что критично для каскадной диаграммы.

4. Полка «Серии»

Имеет тумблер «Вкл/Выкл».

Текущий интерфейс предполагает:
полка влияет на диаграмму только если:
- тумблер включён;
- размещена валидная пилюля.

Визуализация должна использовать первую пилюлю.

Фактический тест:
- «Категории» → `Фактор`;
- «Значения» → `Значение фактора`;
- «Серии» → `Регион`;
- Series = Вкл.

Результат:
Waterfall перестаёт строить столбцы, остаётся только ось категорий.

Следовательно, полка «Серии» в текущем Waterfall фактически неработоспособна.

5. Полка «Фильтры»

Используется стандартная функциональность фильтрации портала.

Её базовое поведение изменять не требуется.

6. Рабочий формат данных

Подтверждён рабочий сценарий:

«Категории»:
`Фактор`

«Значения»:
`Значение фактора`

«Серии»:
Выкл

Т.е. Waterfall фактически поддерживает схему:
«одно измерение — один показатель».

7. Неработающий формат «без измерения — набор показателей»

Проверялся сценарий:
- полка «Категории» пустая;
- «Серии» выключены;
- на «Значения» в режиме «Все» размещается последовательность полей:
  - Начальный результат;
  - Рост объёма продаж;
  - Ценовой эффект;
  - Скидки;
  - Возвраты;
  - Логистика;
  - ФОТ;
  - Маркетинг;
  - Курсовые разницы;
  - Прочие расходы;
  - Налог;
  - Разовый доход;
  - и т.д.

Результат:
корректный Waterfall не строится.

При пустой категории может появляться один широкий столбец `undefined`.
Добавление категории также не превращает отдельные показатели в Waterfall-шаги.

Следовательно, первоначально требуемый формат «набор показателей без измерения» отсутствует.

8. Текущая Waterfall-логика

На рабочем формате подтверждено:

- первый элемент входной последовательности автоматически считается начальным итогом;
- первый столбец строится от нуля;
- первый столбец окрашивается как «Итог»;
- положительные последующие значения являются увеличениями;
- отрицательные значения являются уменьшениями;
- после последнего изменения визуализация автоматически рассчитывает финальный итог;
- финальный итог строится отдельным столбцом от нуля.

Текущие цвета:
- уменьшение — зелёный;
- увеличение — синий;
- итог — серый.

9. Подытоги

Тестовый набор содержал, например:

Начальный результат = 1000
Рост объёма продаж = +350
Ценовой эффект = +120
Скидки = -60
Возвраты = -80
Логистика = -150
Коммерческий итог = 1180
ФОТ = -200
Маркетинг = -70
Курсовые разницы = +90
Прочие расходы = -30
Операционный итог = 970
Налог = -194
Разовый доход = +50
Конечный результат = 826

Если значения:
- Коммерческий итог = 1180;
- Операционный итог = 970;
- Конечный результат = 826

передать текущему Waterfall как обычные строки/показатели, визуализация прибавляет их к накопленному результату как положительные изменения.

Т.е. семантика `subtotal/total` не поддерживается.

10. Порядок

Для корректного Waterfall порядок является частью семантики данных.

Тестовый набор содержит поле `Порядок`, однако использовать его для сортировки категории невозможно, т.к. стандартное меню пилюли отсутствует.

Следовательно, подключение стандартной сортировки является обязательной частью доработки.

11. Текущие специализированные настройки Waterfall

Отдельных функциональных Waterfall-настроек практически нет.

В разделе общих настроек плагина доступны только:
- название;
- отступы контейнера;
- точность чисел;
- суффиксы чисел.

Раздел «Данные» содержит стандартные платформенные параметры:
- лимит строк запроса;
- лимит строк показа;
- лимит серий;
- лимит строк экспорта;
- заполнение пустых категорий/серий;
- анимация обновления;
- интервальное обновление.

Остальные разделы:
- режим фильтра;
- настройки клика;
- drill;
- info;
- рамка компонента

являются стандартными разделами портала и в рамках Waterfall-постановки подробно переопределяться не должны.

Специализированных настроек:
- цветов;
- итогов;
- подытогов;
- соединительных линий;
- дельт;
- опорных линий;
- легенды;
- ориентации

сейчас нет.

----------------------------------------------------------------------
ЦЕЛЕВОЕ ПОВЕДЕНИЕ ПОЛОК
----------------------------------------------------------------------

В постановке необходимо декларативно описать целевую семантику каждой полки.

1. «Значения»

Должны поддерживаться:
- стандартные поля НД;
- вычисляемые поля, если их тип совместим с Waterfall;
- стандартные настройки пилюли Modus BI.

Режим «Первое»:
- используется только первая пилюля.

Режим «Все»:
- должны реально использоваться все размещённые пилюли;
- режим не должен молча игнорировать вторую и последующие пилюли.

Ключевой обязательный сценарий:
при пустой «Категории» и режиме «Все» каждая пилюля «Значения» должна представлять отдельный последовательный шаг Waterfall.

Порядок шагов:
порядок пилюль на полке «Значения».

Это обеспечивает формат:
«без измерения — набор показателей».

Для такого формата должна существовать возможность определить для каждой пилюли её Waterfall-роль как минимум:
- изменение;
- итог/подытог.

Не привязывать постановку к конкретной фронтенд-реализации, однако логически естественным вариантом является Waterfall-специфичная настройка пилюли.

2. «Категории»

Визуализация обрабатывает первую пилюлю.

При наличии категории и одного используемого значения каждая категория формирует отдельный Waterfall-шаг.

Обязательно подключить стандартное меню настройки пилюли, включая штатную сортировку.

Должна поддерживаться сортировка категории:
- по самой категории;
- по другому полю, если такой стандартный механизм уже используется на портале.

Waterfall должен соблюдать установленный порядок категорий.

Это критично, поскольку перестановка факторов изменяет смысл каскада.

3. «Серии»

Текущее поведение сломано.

В новой постановке нельзя оставить неопределённое состояние, при котором включение Series просто уничтожает визуализацию.

Необходимо принять одно из двух решений:

A. Полка «Серии» входит в целевую функциональность Waterfall.

Тогда должна быть явно определена её Waterfall-семантика.
В качестве референса можно рассмотреть Power BI Breakdown:
дополнительное измерение декомпозирует изменение фактора по сериям.

Нужно описать:
- как рассчитывается общий шаг категории;
- как внутри него отображаются серии;
- как серия взаимодействует с цветовой семантикой «увеличение/уменьшение/итог»;
- что происходит с легендой;
- как работает tooltip.

B. Серии для Waterfall не требуются.

Тогда полку необходимо убрать/скрыть/запретить для Waterfall, а не оставлять неработающей.

Если решение не согласовано — вынести это в «Открытые вопросы», не придумывая окончательное поведение.

Отдельно оценить, требуется ли Series/Breakdown как «комбинированный формат» для гарантированного закрытия критерия Громова по типам данных.

4. «Фильтры»

Переиспользуется стандартная функциональность полки.

Поведение WHERE/HAVING и остальные общие правила фильтрации не переопределяются, если для Waterfall не требуется отдельное исключение.

5. Стандартные меню пилюль

Waterfall должен подключить тот же общий механизм меню пилюль, который используется в других визуализациях портала.

Состав настроек должен зависеть от типа полки и соответствовать общим компонентам Modus BI.

Не требуется вручную дублировать в Waterfall все стандартные настройки, если они могут быть переиспользованы.

Waterfall-специфичные свойства добавляются только там, где они действительно нужны, например:
«Тип столбца».

----------------------------------------------------------------------
ЦЕЛЕВЫЕ WATERFALL-НАСТРОЙКИ
----------------------------------------------------------------------

В новой постановке необходимо предусмотреть специализированные настройки Waterfall.

Структура может быть уточнена с учётом стандартных UI-компонентов платформы, но функционально должны быть покрыты следующие блоки в правой боковой панеле настроек (в режиме настройки визуализации):

1. Раздел «Общие настройки»

Добавить настройку-тумблер «Ориентация»:
- Вертикальная  (по умолчанию);
- Горизонтальная.

По аналогии в с настройкой "Ориентация" в "Диаграмма столбчатая" (к примеру).

Вертикальная:
- категории располагаются по горизонтальной оси;
- значения откладываются по вертикальной.

Горизонтальная:
- категории располагаются по вертикальной оси;
- значения откладываются по горизонтальной.

Все Waterfall-механизмы должны одинаково работать в обеих ориентациях:
- увеличение;
- уменьшение;
- итоги;
- подытоги;
- подписи;
- соединительные линии;
- дельты;
- опорные линии.

Также добавить:
«Показывать соединительные линии»
тип: тумблер;
по умолчанию: Вкл.

При включении соединительные линии отображаются между соседними видимыми Waterfall-шагами и показывают уровень перехода между ними.

2. Разделы «Основной стиль», «Стиль элементов»

Должны отдельно настраиваться цвета:
- Увеличение;
- Уменьшение;
- Итог/Подытог.

Для обычных изменений тип определяется знаком:
- > 0 — увеличение;
- < 0 — уменьшение.

Итоговый/подытоговый столбец использует цвет итогов независимо от знака его абсолютного значения.

Текущие цвета можно использовать как значения по умолчанию либо сохранить для обратной совместимости, если это соответствует дизайн-системе.

3. Раздел «Итоги и подытоги»

Необходим встроенный механизм назначения любого требуемого Waterfall-шага итоговым.

Итоговый/подытоговый столбец:
- всегда начинается от нуля;
- не должен повторно прибавляться к накопленному результату как дельта;
- задаёт/отображает соответствующий контрольный уровень каскада.

Должна быть возможность показывать/скрывать промежуточные итоги.

Скрытие промежуточного итогового столбца не должно изменять фактическую математику последующих шагов; оно влияет на отображение, а не превращает итог в дополнительную дельту.

Нужно определить поведение автоматически рассчитываемого конечного итога:
- возможность его показа/скрытия;
- при необходимости настройку подписи.

Если отдельное управление финальным итогом не согласовано, вынести в открытые вопросы.

Механизм задания типа зависит от формата данных.

Формат «без измерения — набор показателей»:
роль может задаваться для конкретной пилюли «Значения».

Формат «одно измерение — один показатель»:
необходимо передать роль для каждой строки/категории.

Для этого требуется функциональный механизм вида:
- специальное поле типа столбца;
- отдельная полка;
- либо селектор поля в настройках Waterfall.

Не навязывать конкретную техническую реализацию, если она ещё не согласована.

Функциональное требование:
визуализация должна однозначно получать для каждого шага признак:
- обычное изменение;
- итог/подытог.

Если способ UI не согласован — вынести архитектурную развилку в «Открытые вопросы».

4. Раздел «Подписи данных»

Должна быть возможность:
- показывать/скрывать подписи;
- задавать точность;
- управлять форматом числа;
- использовать существующий механизм суффиксов, если возможно.

Для увеличения:
- отображать знак `+`.

Для уменьшения:
- отображать знак `-`.

Для вертикальной ориентации по умолчанию:
- увеличение — подпись над столбцом;
- уменьшение — под столбцом.

Для горизонтальной ориентации предусмотреть эквивалентное читаемое расположение.

Итоговые столбцы отображают абсолютное значение без процентной дельты, если иное отдельно не определено.

5. Раздел «Дельты»

Требование обязательно для закрытия Громова.

Должна быть возможность выбрать:
- Не показывать;
- Абсолютная;
- Относительная;
- Абсолютная и относительная.

Должна быть возможность настраивать:
- количество знаков после запятой;
- формат процентов;
- отображение знака `+/-`.

Если выводятся одновременно абсолютное и относительное значения:
- они должны отображаться раздельно и читабельно;
- допустим вывод в две строки;
- при необходимости предусмотреть выбор порядка строк.

Метки дельт должны визуально относиться к соответствующему переходу/соединительной линии.

ВАЖНАЯ незакрытая семантика:
первоначальное требование определяло процент как изменение относительно предыдущего итогового/подытогового столбца.

Критерий Громова формулирует относительную дельту как изменение между столбцами.

Необходимо явно зафиксировать формулу относительной дельты.

Если это ещё не согласовано, вынести отдельный открытый вопрос с вариантами, например:
A. относительно непосредственно предыдущего уровня;
B. относительно предыдущего итогового/подытогового уровня.

Не оставлять формулу неявной.

6. Раздел «Опорные линии»

Требование обязательно для закрытия Громова.

Должна поддерживаться возможность создать несколько опорных линий.

Для линии необходимо как минимум:
- задать динамическое числовое значение/выражение;
- задать подпись;
- показать/скрыть подпись;
- удалить линию.

При наличии стандартного платформенного компонента опорных линий необходимо максимально переиспользовать его.

Должно быть явно зафиксировано максимальное количество одновременно доступных опорных линий.

Если лимит уже существует в общем компоненте Modus BI — использовать его.

Если нет — вынести количество в открытый вопрос.

7. Раздел «Легенда»

Текущая легенда автоматически содержит:
- Уменьшение;
- Увеличение;
- Итог.

Необходимо добавить возможность:
- показывать/скрывать легенду;
- выбирать её расположение;
- задавать пользовательские подписи для:
  - Увеличения;
  - Уменьшения;
  - Итога.

Цвет маркеров легенды должен соответствовать настроенным цветам типов Waterfall.

8. Оси

Если стандартные настройки осей уже существуют на платформе, Waterfall должен их переиспользовать.

Не создавать специализированные дублирующие настройки без необходимости.

В постановке обязательно описать как минимум два полноценных сценария.

Сценарий A — без измерения, набор показателей.

пусто.

«Значения»:

----------------------------------------------------------------------
МАТЕМАТИКА WATERFALL
----------------------------------------------------------------------

В постановке должна быть явно определена базовая математическая логика.

Для обычного изменения:
- положительное значение увеличивает текущий накопленный уровень;
- отрицательное уменьшает.

Для итогового/подытогового шага:
- столбец строится от нуля;
- абсолютное значение итога не прибавляется к предыдущему уровню второй раз.

После итогового/подытогового шага последующие изменения продолжаются от соответствующего уровня.

Финальный итог должен отражать фактически накопленный результат.

Пример контрольной последовательности:

Начальный результат       1000
Рост объёма продаж        +350 → 1350
Ценовой эффект            +120 → 1470
Скидки                     -60 → 1410
Возвраты                   -80 → 1330
Логистика                 -150 → 1180
Коммерческий итог         1180 → итог от 0
ФОТ                       -200 → 980
Маркетинг                  -70 → 910
Курсовые разницы           +90 → 1000
Прочие расходы             -30 → 970
Операционный итог          970 → итог от 0
Налог                     -194 → 776
Разовый доход              +50 → 826
Конечный результат         826

Этот пример можно использовать как контрольный сценарий при формировании AC.
