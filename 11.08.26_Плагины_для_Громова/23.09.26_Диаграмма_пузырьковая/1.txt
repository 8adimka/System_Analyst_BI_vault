На данный момент замечены следующие некоторые требуемые доработки:
1. Поле типа Подсказка - при удалении пилюли с типом "Подсказка", выводимая и отображаемая подсказка не меняется и график не меняется. 2. Легенда для цвета объясняет, какой цвет пузырька соответствует какой категории данных. Дополнительно необходимо настроить цвета через поле «Подпись по другому полю», подробнее в статье «Разделы «Легенда для цвета» и «Легенда для размера») - появляется запрещающий символ и мы не можем задать поле для отображения корректных наименований цветов (а сейчас цвета в легенде выводятся по HEX, что не информативно). Нужно продумать как задавать цветам информативные названия, чтобы человек понимал какую "категорию" или какой тип пузырей мы окрасили в какой цвет. Небольшой момент для уточнения - стандартно в нашей аналитическом портале действует такой приоритет стилей:
1) Базовые цвета и стили дашборда (наиболее низкий приоритет),

h3. 1. Критерии Громова.

h4. 1.1. Наличие визуализации.

Критерий:

В Modus BI в качестве Scatter Plot используется существующая визуализация «Диаграмма пузырьковая»:

Новая визуализация не требуется. Дорабатывается существующая.

h4. 1.2. Размер и кластеризация.

Критерий:
* дополнительный показатель для управления размером точек (bubble);
* регулировка размера пузырей без показателя;
* автоматическая кластеризация близких точек при изменении масштаба.

1. Регулировка размера пузыря без показателя — чтобы можно было настроить единый фиксированный размер для всех пузырей, а также рассмотреть возможность устанавливать фиксированный размер для каждой выбранной группы пузырей.

Референс Tableau:
https://help.tableau.com/current/pro/desktop/en-us/viewparts_marks_markproperties.htm

2. Автоматическая кластеризация близких точек при изменении масштаба. Нужна возможность автоматически объединять несколько соседних точек в один визуальный объект, показывать количество агрегированных точек, автоматически адаптировать объединение и разъединение точек при zoom, рассмотреть возможность управления Compression resolution с несколькими уровнями сжатия.

Референс Qlik:
https://help.qlik.com/en-US/cloud-services/Subsystems/Hub/Content/Sense_Hub/Visualizations/ScatterPlot/scatter-plot.htm»

Итоговое решение Р. Чернышова:
* в рамках текущей задачи требуется реализовать регулировку размера пузыря без показателя;
* автоматическую кластеризацию пока *не реализуем*.

Следовательно, кластеризацию необходимо явно вынести из scope текущей постановки.

При этом существующий zoom визуализации должен продолжить работать без изменений. AS-IS близкие пузырьки могут накладываться друг на друга, отдельного механизма автоматического объединения/разъединения точек сейчас нет.

Целевое направление, согласованное в ходе проработки:
* опорные линии следует поддержать через полку *«Значения»*;
* для пилюль на этой полке необходимо добавить новый тип *«Отсечка»*;
* пилюля типа «Отсечка» должна использовать значение поля/вычисляемого выражения для формирования динамической опорной линии;
* должны поддерживаться как вертикальные линии относительно оси X, так и горизонтальные линии относительно оси Y;
* пользователь должен иметь возможность определить, к какой оси относится конкретная отсечка;
* для опорной линии должна поддерживаться человекочитаемая подпись;
* необходимо поддержать размещение нескольких опорных линий одновременно.

При подготовке постановки необходимо отдельно зафиксировать максимальное количество одновременно поддерживаемых опорных линий. Если число ещё не определено текущими материалами, его нельзя выдумывать — вопрос следует вынести в раздел *Open Questions*.

Не путать опорные линии с существующим crosshair: пунктирные горизонтальная и вертикальная линии, отображаемые при наведении на пузырь, являются вспомогательной подсветкой координат курсора/точки и не закрывают требование Громова по reference lines.

# «Подзаголовок»;
# «Подсказка».

Существующие агрегации:
* {{-}};
* {{AVG}};
* {{MIN}};
* {{MAX}};
* {{SUM}}.

Количество обрабатываемых пилюль определяется режимом полки:

*«Первое»*:
визуализация обрабатывает только первую пилюлю, размещённую на полке.

*«Все»*:
визуализация обрабатывает все размещённые пилюли с поддерживаемыми типами.

Режимы «Первое»/«Все» в текущей реализации работают штатно и должны быть сохранены.

После доработки режим «Все» должен корректно поддерживать одновременное использование совместимых пилюль типов:
* «Значение»;
* «Цвет»;
* «Подзаголовок»;
* «Подсказка»;
* «Отсечка».

Необходимо явно описать их совместную семантику и не допускать ситуации, когда добавление одной допустимой вспомогательной пилюли приводит к исчезновению всех пузырей.

----

h4. 2.4. Полка «Категории».

Визуализация использует только первую пилюлю на полке.

Для пилюли доступны:
* локальное отображаемое имя;
* сортировка;
* «Подсказка по другому полю»;
* «Сортировка по другому полю».

Полка работает штатно и её базовую семантику менять не требуется.

При использовании уникального значения категории для каждой строки визуализация корректно отображает отдельные исходные точки.

----

h4. 2.5. Полка «Серии».

На полке есть переключатель «Вкл»/«Выкл».

Полка участвует в построении только при одновременном выполнении условий:
* переключатель находится в состоянии «Вкл»;
* на полке размещена валидная пилюля.

Визуализация использует только первую пилюлю полки.

AS-IS:
* сама полка «Серии» работает, если на полке «Значения» участвует только пилюля размера типа «Значение», либо полка «Значения» работает в режиме «Первое»;
* при включённых Сериях и добавлении на «Значения» пилюли типа «Цвет» (например, поля с HEX-цветом), либо при переключении «Значений» в режим «Все», пузыри полностью исчезают;
* оси при этом остаются;
* ошибки выполнения запроса не возникает;
* при включённой легенде цвета в таком состоянии может отображаться один чёрный квадрат без корректной подписи.

Целевое поведение:
* валидные «Серии» должны корректно работать одновременно с разрешёнными вспомогательными типами пилюль полки «Значения»;
* добавление «Цвета», «Подзаголовка», «Подсказки» и других поддерживаемых типов не должно разрушать построение Серий;
* необходимо определить и описать согласованное взаимодействие Серий и динамической цветокодировки;
* если пилюля типа «Цвет» явно задаёт цвет пузыря, наличие Серий не должно приводить к потере данных или исчезновению объектов;
* легенды должны оставаться согласованными с фактически применённой цветокодировкой.

----

h4. 2.6. Полка «Фильтры».

Используется стандартная функциональность фильтрации портала.

Изменения базовой семантики полки в рамках данной задачи не требуются.

----

h3. 3. Текущее и целевое поведение размера пузыря.

AS-IS подтверждено тестами:

# При наличии на полке «Значения» пилюли типа «Значение» её числовое значение управляет относительными размерами пузырей.
# В «Общих настройках» существует параметр *«Радиус (px)»* с минимальной и максимальной границами.
# При наличии пилюли типа «Значение» настройка «Радиус (px)» работает:
## изменяет минимальный и максимальный визуальный размер пузырей;
## относительное соотношение размеров по возможности сохраняется;
## если задать одинаковую нижнюю и верхнюю границы, все пузыри становятся одинакового размера.
# Если пилюли типа «Значение» нет:
## диаграмма продолжает строиться;
## все точки получают фиксированный одинаковый размер;
## однако изменить этот фиксированный размер через существующую настройку «Радиус (px)» невозможно;
## изменение границ «Радиус (px)» не оказывает влияния на размер таких точек.

Таким образом, требование Громова по *регулировке размера пузыря без показателя* AS-IS не выполнено.

Целевое поведение:
* пользователь должен иметь возможность задавать единый фиксированный размер пузырей даже при отсутствии пилюли типа «Значение»;
* этот размер должен изменяться настройками визуализации, без необходимости добавлять искусственный числовой показатель в набор данных;
* существующий сценарий с показателем размера должен быть сохранён:
** при наличии пилюли типа «Значение» величина показателя определяет относительные размеры пузырей;
** настройка размера определяет допустимый визуальный диапазон;
** возможность сделать все пузыри одинаковыми через одинаковые границы должна сохраняться, если она соответствует принятой целевой UX-модели.

Предпочтительно переиспользовать существующий механизм настройки размера, если это позволяет получить понятную и согласованную UX-модель, однако постановка не должна навязывать фронтенду конкретный вид контрола, если он требует отдельной технической проработки.

Обязательное функциональное требование:
* отсутствие показателя размера не должно лишать пользователя возможности изменять общий размер пузырей.

В исходном критерии Громова также предлагается «рассмотреть возможность устанавливать фиксированный размер для каждой выбранной группы пузырей».

Это предложение не было отдельно подтверждено как обязательная часть текущего scope. Не включать групповую настройку размеров как уже принятое обязательное требование без дополнительного решения. При необходимости вынести вопрос о фиксированном размере отдельных групп в *Open Questions*.

----

h3. 4. Пилюля типа «Цвет» и легенда цвета.

AS-IS:
* пилюля типа «Цвет» работает и может использовать строковое значение цвета, в том числе HEX;
* пузыри фактически окрашиваются в переданные цвета;
* «Легенду для цвета» можно включить;
* при рабочем сценарии внизу диаграммы отображается легенда;
* AS-IS подписи элементов легенды фактически могут отображаться непосредственно как HEX-коды, например {{#1F77B4}};
* такое представление технически показывает используемый цвет, но не объясняет пользователю предметную семантику цвета.

В разделе «Легенда для цвета» существует настройка *«Подпись по другому полю»*, однако в «Диаграмме пузырьковой» контрол выбора поля всегда недоступен: пользователь получает запрещающий курсор и не может выбрать поле.

Целевое поведение:
* «Подпись по другому полю» должна стать работоспособной для поддерживаемого сценария;
* пользователь должен иметь возможность сопоставить значение цвета с человекочитаемой категорией/группой;
* легенда должна объяснять предметную цветокодировку, например:
** «Группа A» → соответствующий цвет;
** «Группа B» → соответствующий цвет;
а не использовать HEX-код как единственное наименование элемента легенды;
* фактический цвет маркера в легенде должен соответствовать цвету пузырей;
* дублирование одинаковых значений должно обрабатываться согласованно и не приводить к бессмысленному повторению легенды;
* сценарий должен корректно работать совместно с полкой «Серии».

Если существующий общий компонент портала уже определяет семантику «Подписи по другому полю», в Bubble необходимо переиспользовать его стандартное поведение, а не создавать отдельную уникальную модель.

----

h3. 5. Легенда размера.

AS-IS:
* раздел «Легенда для размера» существует;
* при выключенных Сериях и включённом режиме *«Графическое представление»* легенда корректно показывает несколько эталонных размеров пузыря и соответствующие им числовые значения;
* она позволяет визуально сопоставлять размер пузыря со значением показателя;
* другие комбинации настроек и режимы легенды либо неинформативны, либо работают некорректно;
* при использовании Серий корректная работа легенды размера не обеспечена.

Целевое поведение:
* легенда размера не должна ломаться только из-за включения валидной полки «Серии»;
* при наличии показателя размера легенда должна соответствовать фактически применяемому диапазону и масштабу пузырей;
* допустимые режимы существующего раздела «Легенда для размера» должны иметь понятное, согласованное и воспроизводимое поведение;
* включение вспомогательных совместимых пилюль не должно само по себе делать легенду неработоспособной;
* если существующие режимы легенды размера имеют стандартную реализацию в других визуализациях портала, необходимо максимально переиспользовать общую семантику.

При подготовке постановки проанализируй существующие настройки раздела и декларативно зафиксируй целевое поведение каждого поддерживаемого режима. Если информации недостаточно для однозначного решения по отдельному режиму — вынеси его в Open Questions, а не придумывай неподтверждённую семантику.

----

h3. 6. Пилюля типа «Подзаголовок».

AS-IS:
* работает штатно;
* значение пилюли используется для отображения подзаголовка визуализации.

Базовую семантику необходимо сохранить.

Не требуется создавать для этого типа отдельный новый механизм.

----

h3. 7. Пилюля типа «Подсказка» и всплывающая подсказка.

Важное уточнение:
в самой визуализации *«Диаграмма пузырьковая»* раздел *«Всплывающая подсказка»* в правой панели настроек AS-IS отсутствует.

Скриншот настройки с разделом «Всплывающая подсказка» и пунктом {{Шаблон = Подсказка}} был получен из другой визуализации портала и используется как референс стандартного поведения.

AS-IS Bubble:
* тип пилюли «Подсказка» присутствует;
* добавление или удаление пилюли этого типа не изменяет стандартную всплывающую подсказку;
* фактически пилюля типа «Подсказка» сейчас не используется пользователем при отображении tooltip.

Требуется добавить в «Диаграмму пузырьковую» стандартный для портала раздел *«Всплывающая подсказка»* по аналогии с визуализациями, где этот механизм уже реализован.

Целевая семантика:

{{пилюля типа "Подсказка"}} → источник данных для пользовательской подсказки;

{{Всплывающая подсказка → Шаблон = "Подсказка"}} → включение использования этого источника при отображении tooltip.

Следует использовать существующий общий механизм портала, а не создавать уникальную для Bubble реализацию.

Необходимо определить:
* стандартное поведение tooltip при шаблоне по умолчанию;
* отображение значения пилюли при выборе шаблона «Подсказка»;
* поведение, если шаблон «Подсказка» выбран, но валидная пилюля соответствующего типа отсутствует;
* взаимодействие с режимами «Первое»/«Все» полки «Значения».

Не следует делать так, чтобы само размещение пилюли «Подсказка» автоматически и без выбора соответствующего шаблона полностью меняло существующий tooltip, если стандартная модель портала предполагает явный выбор шаблона.

----

h3. 8. Опорные линии через тип «Отсечка».

Необходимо добавить для пилюль полки «Значения» новый тип:
*«Отсечка»*.

Целевой функциональный смысл:
* пилюля типа «Отсечка» определяет координату динамической reference line;
* значение должно вычисляться на основании размещённого поля/вычисляемого выражения и выбранной допустимой агрегации;
* должна поддерживаться вертикальная линия по X;
* должна поддерживаться горизонтальная линия по Y;
* пользователь должен иметь возможность определить, относительно какой оси применяется конкретная отсечка;
* необходимо поддерживать несколько отсечек одновременно;
* каждая линия должна иметь настраиваемую/человекочитаемую подпись;
* изменение данных, фильтров или выражения должно пересчитывать положение динамической линии;
* линии не должны влиять на координаты, категории, размер или цвет самих пузырей;
* использование отсечек должно быть совместимо с обычными пилюлями типов «Значение», «Цвет», «Подзаголовок», «Подсказка» и с валидными Сериями.

В постановке необходимо функционально описать:
* способ выбора оси X/Y для отсечки;
* подпись линии;
* обработку нескольких линий;
* допустимые агрегации/выражения;
* поведение при некорректном/пустом результате;
* максимальное количество отсечек.

Конкретную техническую структуру конфигурации навязывать не требуется.

Если максимальное количество линий ещё не согласовано — обязательно вынести вопрос в Open Questions, так как критерий Громова требует указания этого ограничения.

----

h3. 9. Совместимость типов пилюль и полок.

При подготовке постановки важно явно зафиксировать, что после доработки допустимые сценарии должны быть композиционными.

В частности:
* X и Y должны продолжать определять положение пузыря;
* Категория — идентификацию/группировку объектов;
* Серии — дополнительную разбивку;
* Значение — размер;
* Цвет — динамическую цветокодировку;
* Подзаголовок — подзаголовок визуализации;
* Подсказка — источник пользовательского tooltip при соответствующей настройке шаблона;
* Отсечка — reference line.

Наличие одного корректного дополнительного типа не должно отключать работу другого, если такое сочетание функционально допустимо.

Особое внимание уделить комбинациям:
* Серии + Значение;
* Серии + Цвет;
* Серии + Значение + Цвет;
* Серии + режим «Все»;
* Цвет + легенда цвета;
* Значение + легенда размера;
* Серии + легенда размера;
* Значение + Цвет + Подсказка + Подзаголовок;
* перечисленные типы + одна или несколько Отсечек.

----

h3. 10. Агрегации.

В ходе тестирования установлено:
* для X/Y отсутствие агрегации приводит к неработоспособному состоянию;
* на полке «Значения» интерфейс фактически не позволяет оставить числовую пилюлю без какой-либо агрегации — при выборе {{-}} применяется агрегация по умолчанию;
* текущие дефолты между полками выглядят несогласованно.

Целевое требование:
* привести стандартные агрегации Bubble к единообразной и предсказуемой модели;
* для новых числовых пилюль на «ЗначенияX» и «ЗначенияY» использовать {{AVG}} как стандартную агрегацию;
* пользователь не должен иметь возможность получить заведомо неработоспособную конфигурацию штатным выбором доступной настройки;
* поведение агрегации полки «Значения», в том числе для нового типа «Отсечка», должно быть согласовано с общими контрактами портала.

Необходимо описать функциональный результат, но не диктовать конкретную реализацию SQL/query builder.

----

h3. 11. Кластеризация и zoom.

AS-IS:
* zoom работает;
* при изменении масштаба точки продолжают отображаться как самостоятельные объекты;
* близкие точки могут перекрываться;
* автоматического объединения в кластер нет.

В текущей задаче:
* существующий zoom сохраняется;
* автоматическая кластеризация не реализуется;
* Compression resolution и аналогичные механизмы не реализуются.

Кластеризацию явно указать в *Out of scope*, несмотря на наличие этого пункта в исходном критерии Громова, поскольку по итоговому продуктовому решению она отложена.

h3. 12. Общие требования к постановке.

Как опытный системный аналитик, опираясь на описанный AS-IS, критерии Громова, существующие паттерны Modus BI и уже используемую структуру постановок, подготовь постановку на доработку существующей визуализации *«Диаграмма пузырьковая»*.

Постановка должна быть функциональной и декларативной:
* описывать, какое целевое поведение должна обеспечивать система;
* давать frontend/backend достаточную информацию для технической проработки;
* не навязывать конкретные классы, методы, структуры БД или внутренние алгоритмы там, где это не является частью функционального требования.

Важно:
* не превращать документ в отчёт о проведённом исследовании;
* AS-IS использовать только там, где он нужен для понимания проблемы и целевого изменения;
* не дублировать одинаковые правила по разным разделам;
* явно разделить существующее штатное поведение, исправляемые дефекты и новую функциональность;
* сохранить существующие работающие сценарии;
* не ломать сохранённые конфигурации существующих Bubble-визуализаций без отдельной необходимости;
* переиспользовать общие компоненты/контракты портала там, где аналогичная функциональность уже существует;
* обеспечить единообразное UX-поведение с другими визуализациями Modus BI.

# Цель и рамки задачи.
# Текущее и целевое поведение полок.
# Размер пузыря.
# Цвет и легенда цвета.
# Серии и совместимость с типами полки «Значения».
# Легенда размера.
# Всплывающая подсказка.
# Опорные линии / тип «Отсечка».
# Агрегации и дефолтные настройки.
# Правила совместимости и сохранение существующего поведения.
# Критерии приёмки (AC).
# Вне рамок задачи.
# Открытые вопросы.

Критерии приёмки (AC) должны быть проверяемыми и охватывать как новые функции, так и исправляемые комбинации существующих механизмов.

----

h3. 14. "Вне рамок задачи", который необходимо явно зафиксировать.

В текущую задачу не включать:
* автоматическую кластеризацию близких точек;
* Compression resolution;
* автоматическое объединение/разъединение кластеров при zoom;
* создание новой визуализации вместо существующей Bubble;
* изменение общей семантики полки «Фильтры»;
* отдельную групповую настройку фиксированного размера пузырей, если она дополнительно не будет согласована как обязательное требование.

----

h3. 15. Открытые вопросы.

В "Открытые вопросы" оставлять только реально незакрытые решения.

Как минимум проверить необходимость вынесения следующих вопросов:

# Какое максимальное количество одновременно активных опорных линий необходимо поддерживать?
Критерий Громова требует указать конкретное ограничение.

# Должна ли в текущий scope входить возможность устанавливать отдельный фиксированный размер для конкретных групп пузырей, либо обязательным требованием остаётся только единый регулируемый фиксированный размер без показателя?

# Если существующие нестандартные режимы «Легенды для размера» не имеют однозначно определённого общего контракта портала — какое именно целевое представление требуется для каждого такого режима?

Не создавать Открытые вопросы там, где целевое поведение уже следует из стандартных механизмов платформы.

----

В том числе изучи имеющиеся постановки на реализацию других диаграмм для примера и контекста:
./10.09.26_Диаграмма_распределения/Громов_внедрение_Диаграмма_распределения.txt
./06.09.26_Диаграмма_воронка/Громов_внедрение_Воронка.txt
./21.09.26_Диаграмма_Водопад/Громов_внедрение_Диаграмма_водопад_финальная_постановка.txt

Итоговая постановка должна дать разработчику полную и непротиворечивую картину:
* что уже работает и должно сохраниться;
* что сейчас работает некорректно;
* что необходимо добавить для закрытия требований Громова;
* как новые механизмы должны сочетаться с существующими полками и настройками;
* какие решения ещё требуют согласования.

Сохраняй принятую в существующих постановках Jira-разметку.

Не добавляй неподтверждённые требования и не придумывай значения ограничений, которые в исходных данных не определены.

Запиши готовую постановку в файл:

./Громов_внедрение_Диаграмма_пузырьковая.txt
