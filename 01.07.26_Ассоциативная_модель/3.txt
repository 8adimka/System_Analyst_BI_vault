Были проведены следующие рассуждения ->
Когда прямая связь M:M даёт корректный результат:
Прямой JOIN двух источников по ключу, где с обеих сторон возможны несколько строк на значение ключа, физически создаёт декартово произведение внутри каждой группы одинаковых значений ключа — это не ошибка SQL, а сама природа M:M-соединения. Отсюда следуют три сценария:

* Только атрибуты/измерения без агрегируемых показателей. Если пользователь выводит только измерения с обеих сторон (например, список тегов заказа), декартово произведение — это не искажение, а ожидаемое поведение: каждая строка результата — валидная пара "заказ-тег". Проблема появляется только тогда, когда к результату применяется агрегатная функция (SUM, COUNT) по не подготовленному заранее показателю.

* Использование одной стороны только как фильтра (semi-join). Если поле стороны B используется только в фильтре ("покажи заказы, у которых есть тег X"), а сами значения и показатели этой стороны не выводятся, достаточно EXISTS/IN, а не полного JOIN — размножение строк не происходит вообще.

* Предварительная агрегация обеих сторон до JOIN. Если показатели с обеих сторон предагрегированы в подзапросе до уровня самого ключа связи (GROUP BY ключ) перед соединением, результат JOIN двух уже агрегированных подзапросов корректен, даже без физической таблицы-связки — по сути, подзапрос выполняет роль "виртуальной связки".

Во всех остальных случаях — когда хотя бы одна сторона выводит "сырой", неагрегированный показатель уровня своей детализации одновременно с полями другой стороны M — прямой M:M JOIN математически не может дать корректный результат без искажения, и никакая последующая группировка это не исправит, потому что исходные строки уже физически размножены до агрегации.

Значит ли это, что нужно резать выбор до 1:1/1:M/M:1 ->
Да, для текущего этапа это оправданное и наиболее реализуемое решение — потому, что безопасная обработка M:M требует от билдера дополнительной логики распознавания "что именно выбрал пользователь" (только атрибуты? только фильтр? предагрегированные показатели?) и разного SQL для каждого случая — а это именно та сложность, которую изначально хотели избежать. Заставить аналитика вручную построить связь через промежуточный простой набор (таблицу-связку) как пару 1:M + M:1 — уже полностью покрывает подавляющее большинство реальных бизнес-сценариев (заказ-теги, товар-категории через связку) и не требует от билдера никакой специальной логики для M:M вовсе, потому что физически он видит только связи 1:M/M:1, для которых правила уже определены в разделе 5.5.

Такой подход даёт пользователю тот же опыт, что и "настоящая" ассоциативная модель — свободную навигацию по связанным данным без ручного описания JOIN на каждый отчёт — при этом под капотом остаётся классический реляционный ClickHouse-запрос, генерируемый динамически. Одна из основных задач - это осуществить данную доработку минимальными ресурсами команды и времени, но дать пользователю схожий опыт работы с ассоциативной моделью данных.
