В рамках доработок нашего портала под "ассоциативной моделью"понимается - "реляционная модель + in-memory граф связей + движок пересчёта состояний". Или реализации, которая будет давать пользователю схожий опыт использования для аналитики.

Сейчас у нас используется clickhouse для хранения данных и PostgreSQL для метаданных. Мы можем создавать "произвольные" наборы данных через пользовательский произвольный SQL-запрос. А также есть "простые" наборы данных - она создаются через правила загрузки данных и при их создании данные перегружаются из внешнего источника во внутренний clickhouse портала. Далее простые наборы данных мы можем объединять (джоинить) и создавать "состовные" наборы данных. Для любой визуализации на портале действует ограничение - один набор данных на одну визуализацию. Но это может быть произвольный, простой или составной набор данных.

Изучи обсуждение по данной тематике с командой ./Транскрипция_Ассоциативная_модель.txt

То есть мы должны обеспечить схожее поведение, которое позволит пользователям пользоваться на нашем портале такими же инструментами аналитики, которые даём вот такая "ассоциативная модель" ("реляционная модель + in-memory граф связей + движок пересчёта состояний"), но обеспечить такое поведение нужно минимальными доработками нашего портала и нашей системы.

Доработка механики составных наборов подходит почти идеально. Тип связи (1:1, 1:М, М:М) определяет не только JOIN, но и то, какие агрегирующие/группирующие функции нужно применить к полям при построении запроса, чтобы, например, поле "сумма заказа" не задваивалось при джойне с таблицей позиций заказа.

* 1:1 — обычный JOIN без дополнительной агрегации.
* 1:М — JOIN с группировкой на стороне таблицы "один", чтобы избежать фан-аута значений.
* М:М — требуется явно задавать связующее поле и почти всегда — агрегацию с обеих сторон.

Направление JOIN (Inner/Left/Right/Full) в этой схеме остаётся отдельным параметром, ортогональным типу мощности связи.

Такая модель связей уже хранится в составном наборе — вопрос в том, чтобы построитель запроса генерировал SQL "на лету" в зависимости от того, какие поля пользователь положил на полки визуализации, а не фиксировал один заранее просчитанный запрос.

Что нужно минимально доработать.

1) На фронте (конструктор составного набора):

* Разрешить не одну "центральную" таблицу с окружением-звездой, а произвольный граф из нескольких таблиц со связями между любыми парами (можно ограничиться и упрощённой звездой ради скорости, что сейчас важно - так что оставляем как дополнительный опциональный пункт).

* К существующему выбору полей связи добавить выбор мощности связи (1:1, 1:М, М:1, М:М) — тип JOIN (Inner/Left/Right/Full) уже есть, это отдельный, дополняющий параметр.

* В редакторе визуализации визуально разделять поля по исходным таблицам (например, аккордеон с группировкой по таблице), чтобы избежать путаницы при совпадении имён полей.

2) На бэке (построитель запроса):

* Хранить граф связей набора как метаданные (таблицы + мощности связей), а не как заранее сгенерированный статический SQL.

* При каждом обращении визуализации динамически определять, какие таблицы вообще нужны для выбранных полей (аналог "проекции" на подграф), и достраивать JOIN только по нужному минимальному пути между ними — это и даёт пользователю ощущение "ассоциативности", хотя физически это обычный SQL-построитель.

* В зависимости от мощности связи автоматически подставлять нужный уровень группировки/агрегации на стороне "многих".

* Отдельно закрыть вопрос RLS: поскольку модель сама решает, какие таблицы подтягивать, нужно на уровне построителя запроса гарантировать, что RLS-правила применяются ко всем задействованным таблицам, а не только к той, что выбрана пользователем явно — это тот риск, который вы сами подняли на встрече (на данный момент для скорости можно сократить и этот пункт и оставить его как дополнительный опциональный пункт).

* Актуализация билдера запросов, на основе нового построителя запросов, для покрытия описанных сценариев.

Предлагаемые шаги реализации: 
1) Зафиксировать границы "ограниченной ассоциативной модели": один составной набор = одна тематическая область (например, "продажи + справочники"), а не всё хранилище целиком — это сильно снижает сложность по сравнению с полным in-memory графом.

2) Доработать модель метаданных составного набора: вместо одного SQL хранить список таблиц, связи между ними (поля + мощность + тип JOIN).

3) Реализовать в построителе запроса алгоритм "минимального связывающего подграфа" — по выбранным пользователем полям определять нужные таблицы и путь между ними, генерировать SQL динамически.

4) Описать и добавить правила авто-агрегации по мощности связи (1:М и М:М кейсы).

5) Встроить проверку RLS на уровне каждой задействованной таблицы в построителе, а не только на уровне финального набора данных (опционально).

6) Доработать фронт конструктора (аккордеон полей по таблицам).

7) Прогнать пилот на 2-3 реальных бизнес-доменах (продажи + справочники) и замерить производительность в ClickHouse.

Такой подход даёт пользователю тот же опыт, что и "настоящая" ассоциативная модель — свободную навигацию по связанным данным без ручного описания JOIN на каждый отчёт — при этом под капотом остаётся классический реляционный ClickHouse-запрос, генерируемый динамически, что полностью соответствует формулировке "реляционная модель + граф связей + движок пересчёта", только без in-memory части, которая на объёмах ClickHouse и не нужна.
