h3. Контекст и проблематика.

В рамках текущего технического решения визуализация строится на основании одного набора данных. Набор данных может быть произвольным, простым или составным. Простые наборы данных создаются через правила загрузки данных и физически размещаются во внутреннем ClickHouse. Составные наборы данных позволяют объединять простые наборы данных через настроенные связи и JOIN.

Требуется организовать аналитический сценарий, схожий с работой ассоциативной модели данных: аналитик один раз описывает логическую модель предметной области из нескольких связанных простых наборов данных, а при построении визуализаций система сама определяет, какие источники и связи нужны для выбранных полей, фильтров и настроек визуализации, и формирует запрос к данным без ручного описания JOIN для каждого отчёта.

В рамках текущей доработки под ассоциативной моделью понимается *ограниченная ассоциативная модель на базе составного набора данных*, а не отдельный in-memory движок, не глобальная модель всего хранилища и не механизм связывания нескольких независимых наборов данных непосредственно внутри одной визуализации. Один ассоциативный составной набор должен описывать одну тематическую область, например «продажи + справочники», и использоваться в визуализациях как обычный набор данных.

Текущее ограничение «одна визуализация — один набор данных» сохраняется. Доработка должна развивать существующую механику составных наборов данных и построителя запросов, чтобы дать пользователю опыт навигации по связанной модели данных без внедрения отдельного ассоциативного движка.

Ключевое ограничение текущего этапа: *прямые связи {{M:M}} между источниками не поддерживаются как тип связи ассоциативного составного набора*. Сценарии предметной области, где между двумя сущностями фактически есть связь «многие ко многим», должны моделироваться через промежуточный простой набор данных/таблицу-связку и набор обычных связей {{1:M}}/{{M:1}}. Такой подход позволяет получить близкий пользовательский опыт ассоциативной модели, но не требует от построителя запросов отдельной логики распознавания частных случаев прямого {{M:M}} и снижает риск некорректных агрегированных показателей.

----

h3. Цель задачи.

*Требуется:*

# Добавить для составного набора данных ассоциативный режим, в котором набор хранит логическую модель источников и связей между ними.
# Для каждой связи хранить стороны связи, поля соединения, тип JOIN и мощность связи: {{1:1}}, {{1:M}} или {{M:1}}.
# Исключить поддержку прямой связи {{M:M}} как выбираемого и исполняемого типа связи в текущем этапе.
# Обеспечить моделирование сценариев «многие ко многим» через промежуточный простой набор данных, который пользователь добавляет в модель как самостоятельный источник.
# На стороне backend динамически формировать SQL к ClickHouse по фактически выбранным полям, фильтрам, сортировкам, вычисляемым выражениям и настройкам визуализации.
# При генерации SQL учитывать мощность связей, чтобы не допускать неконтролируемого фан-аута показателей при соединении источников с разной детализацией.
# В редакторе визуализации показывать поля ассоциативного составного набора с группировкой по исходным источникам.
# Сохранить обратную совместимость существующих составных наборов данных и отчётов.

_Пользовательская история:_
Как аналитик, я хочу один раз настроить логическую модель предметной области из связанных простых наборов данных, чтобы затем строить разные визуализации по полям из этой модели без ручной настройки отдельного JOIN/SQL для каждого отчёта.

----

h3. 1. Рамки задачи.

h4. 1.1. Что входит в текущий этап:

* Ассоциативный режим для составного набора данных.
* Настройка источников ассоциативного составного набора на базе простых наборов данных, доступных текущему механизму составных наборов.
* Настройка связей между источниками:
** выбор левой и правой стороны связи;
** выбор одного или нескольких парных полей соединения;
** выбор типа JOIN: {{Inner}}, {{Left}}, {{Right}}, {{Full}};
** выбор мощности связи: {{1:1}}, {{1:M}}, {{M:1}}.
* Поддержка связанной модели без циклов и неоднозначных маршрутов между источниками. Модель может включать непосредственные связи поддерживаемых мощностей, цепочки связей и промежуточные источники-связки, если между любыми двумя задействованными источниками существует не более одного пути.
* Хранение логической модели связей в метаданных составного набора.
* Динамическая генерация SQL при обращении визуализации к ассоциативному составному набору.
* Автоматический выбор только тех источников и связей, которые нужны для текущей визуализации, фильтров, сортировок и вычисляемых выражений.
* Правила группировки и агрегации, предотвращающие неконтролируемый фан-аут значений при связях {{1:M}} и {{M:1}}.
* Использование промежуточного простого набора данных для моделирования предметных связей «многие ко многим».
* Группировка полей по исходным таблицам/простым наборам данных в редакторе визуализации.
* Проверка сохранения и повторного открытия настроенной модели.
* Пилотная проверка на 2-3 реальных предметных областях с замером производительности запросов в ClickHouse.

---

h4. 1.2. Что не входит в текущий этап:

* Полноценный in-memory граф связей и отдельный движок пересчёта состояний.
* Глобальная модель данных поверх всего хранилища.
* Автоматическое обнаружение связей между таблицами по совпадению имён полей.
* Автоматическое создание системой физической таблицы-связки для сценариев «многие ко многим».
* Связывание нескольких независимых наборов данных напрямую на уровне одной визуализации.
* Изменение базового ограничения «одна визуализация — один набор данных».
* Поддержка прямой связи {{M:M}} между двумя источниками без промежуточного набора данных.
* Специальная SQL-логика для частных случаев прямого {{M:M}}: только атрибуты без показателей, использование одной стороны только как фильтра, предварительная агрегация обеих сторон до JOIN.
* Произвольный граф связей с циклами, несколькими маршрутами между источниками и автоматическим выбором оптимального пути.
* Автоматическое распределение, аллокация или нормализация показателей при аналитике через таблицу-связку, если такие правила не заданы в исходных данных или отдельной бизнес-логике.
* Ассоциативный поиск по всем данным портала.

----

h3. 2. Ключевые понятия.

|| Понятие || Описание ||
| Ассоциативный составной набор данных | Составной набор данных, который хранит логическую модель источников и связей и использует её для динамической генерации SQL под выбранные поля, фильтры и настройки визуализации. |
| Источник ассоциативной модели | Простой набор данных, доступный текущему конструктору составных наборов. |
| Промежуточный источник-связка | Простой набор данных, который пользователь добавляет в модель для описания предметной связи «многие ко многим». Для построителя запросов это обычный источник, соединённый с другими источниками через связи {{1:M}}/{{M:1}}. |
| Связь | Правило соединения двух источников: стороны связи, поля соединения, тип JOIN и мощность связи. |
| Тип JOIN | Направление и способ соединения строк: {{Inner}}, {{Left}}, {{Right}}, {{Full}}. Тип JOIN не заменяет мощность связи. |
| Мощность связи | Логическое соотношение детализации между источниками, определяемое отдельно для левой и правой стороны связи. Поддерживаемые значения текущего этапа: {{1:1}}, {{1:M}}, {{M:1}}, где первое значение относится к левому источнику связи, второе — к правому. Значение {{M:M}} не является поддерживаемым типом связи текущего этапа. |
| Минимальный связывающий подграф | Минимальный набор источников и связей, необходимый для получения полей, фильтров, сортировок и вычислений текущей визуализации. |

h3. 3. Описание текущего поведения.

* Составной набор данных настраивается через соединение простых наборов данных по выбранным полям и типам JOIN.
* Для визуализации пользователь выбирает один набор данных. Если нужны поля из нескольких простых наборов, аналитик заранее создаёт составной набор данных.
* Текущая модель составного набора не содержит достаточной информации о мощности связи между источниками, поэтому построитель запроса не может однозначно определить, как избежать задвоения показателей при соединении таблиц разной детализации.
* Если поле с показателем из таблицы уровня «один» используется вместе с полями из таблицы уровня «многие», обычный JOIN может размножить значение показателя по строкам детализации.
* Для предметных сценариев «многие ко многим» прямой JOIN двух источников без промежуточной таблицы-связки может физически размножать строки внутри одинаковых значений ключа, что создаёт риск некорректных агрегированных показателей.
* В редакторе визуализации поля составного набора могут восприниматься как единый список, из-за чего при совпадающих названиях полей пользователю может быть сложно понять, из какого исходного источника поле было получено.
* Существующие составные наборы работают как обычные наборы данных и не должны менять поведение после внедрения ассоциативного режима.

----

h3. 4. Описание целевого поведения.

h4. 4.1. Создание ассоциативного составного набора.

* В конструкторе составного набора пользователь может выбрать ассоциативный режим.
* Пользователь добавляет в модель простые наборы данных, которые должны участвовать в одной тематической области.
* Пользователь настраивает связи между источниками:
** выбирает левый и правый источник;
** выбирает поля соединения с обеих сторон;
** выбирает тип JOIN;
** выбирает мощность связи только из поддерживаемых значений {{1:1}}, {{1:M}}, {{M:1}}.
* Для каждой связи тип JOIN и мощность связи задаются независимо:
** {{Left JOIN}} со связью {{1:M}} означает направление включения строк и отдельное правило детализации;
** изменение типа JOIN не должно автоматически менять мощность связи;
** изменение мощности связи не должно автоматически менять тип JOIN.
* Прямая связь {{M:M}} не должна быть доступна для выбора в интерфейсе и не должна сохраняться как корректная связь ассоциативного составного набора.
* Если между двумя сущностями предметной области есть связь «многие ко многим», пользователь должен добавить промежуточный простой набор данных/таблицу-связку и настроить связи с ним как обычные связи {{1:M}}/{{M:1}}. Например, связь «Заказы — Теги» должна моделироваться через источник «Заказ-Тег», который содержит ключ заказа и ключ тега.
* Система не должна автоматически создавать промежуточный набор данных и не должна пытаться преобразовать прямую связь {{M:M}} в набор скрытых связей.
* На текущем этапе модель не должна содержать циклы и несколько альтернативных путей между одними и теми же источниками. Если такие маршруты появляются, система должна считать модель неоднозначной и не выполнять запрос по ней без исправления настройки.
* Система не должна ограничивать пользователя в выборе допустимых, но аналитически необычных комбинаций типа JOIN и мощности связи, если мощность входит в поддерживаемый набор {{1:1}}, {{1:M}}, {{M:1}}. Такие комбинации должны сохраняться и обрабатываться построителем запроса без автоматической корректировки одного параметра при изменении другого.

h4. 4.2. Работа в редакторе визуализации.

* Ассоциативный составной набор выбирается в визуализации как один набор данных.
* Ограничение «одна визуализация — один набор данных» сохраняется.
* Поля ассоциативного составного набора должны быть визуально сгруппированы по исходным источникам/простым наборам данных.
* Если в разных источниках есть поля с одинаковым отображаемым названием, пользователь должен видеть, к какому источнику относится каждое поле.
* Пользователь может размещать поля из разных источников на полках визуализации: «Строки/Категории», «Столбцы», «Детализация», «Значения», «Фильтры», «Дополнительные» — в рамках возможностей конкретной визуализации.
* Пользователь не должен вручную выбирать JOIN при настройке каждой визуализации. JOIN определяется по сохранённой логической модели составного набора.

h4. 4.3. Получение данных визуализацией.

* При обращении визуализации к ассоциативному составному набору backend должен определить, какие поля участвуют в текущем запросе:
** поля на полках визуализации;
** поля фильтров визуализации и общей панели фильтров;
** поля сортировки;
** поля вычисляемых выражений, если они используются в запросе;
** служебные поля, необходимые для корректной генерации SQL.
* По найденным полям backend должен определить источники, которые требуются для запроса.
* Если все задействованные поля относятся к одному источнику, SQL должен строиться без лишних JOIN.
* Если поля относятся к нескольким источникам, backend должен построить минимальный связывающий подграф между ними в рамках сохранённой модели.
* В итоговый SQL должны попадать только необходимые источники и связи, а не полный набор всех источников модели.
* Если источник участвует только в фильтре и его поля не выводятся в результат, backend должен применить фильтр так, чтобы не изменить агрегированные показатели из-за лишнего размножения строк.
* Если нужный путь между источниками отсутствует, содержит несколько альтернативных маршрутов или включает неподдерживаемую прямую связь {{M:M}}, система должна вернуть понятную ошибку настройки модели, а не формировать произвольный некорректный JOIN.

----

h3. 5. Требования к реализации.

h4. 5.1. Фронтенд-часть: конструктор составного набора.

* Добавить возможность выбрать ассоциативный режим составного набора.
* Для ассоциативного режима отобразить список источников модели.
* Обеспечить добавление простых наборов данных в модель.
* Обеспечить настройку связанной модели без циклов и неоднозначных маршрутов. Допустимы как модель типа «звезда», так и цепочки через промежуточный источник-связку, если маршрут между источниками остаётся единственным.
* Добавить редактор связей между источниками:
** выбор источника слева и источника справа;
** выбор полей соединения с обеих сторон;
** поддержка нескольких пар полей соединения в одной связи, если такая возможность есть в текущем составном наборе;
** выбор типа JOIN;
** выбор мощности связи из значений {{1:1}}, {{1:M}}, {{M:1}};
** отображение выбранного типа JOIN и мощности связи на связи.
* Не показывать {{M:M}} как доступное значение мощности связи.
* Если пользователю требуется описать предметную связь «многие ко многим», интерфейс должен позволять добавить заранее подготовленный промежуточный простой набор данных и связать его с участниками связи обычными поддерживаемыми мощностями.
* Валидировать настройки перед сохранением:
** у связи выбраны обе стороны;
** выбрана хотя бы одна пара полей соединения;
** выбран тип JOIN;
** выбрана мощность связи из поддерживаемого набора;
** поля соединения существуют в выбранных источниках;
** типы полей соединения совместимы либо явно поддерживаются текущим SQL-билдером;
** модель не содержит циклов;
** между задействованными источниками нет нескольких альтернативных маршрутов;
** в модели нет прямой связи {{M:M}}.
* При редактировании существующего ассоциативного составного набора показывать сохранённые источники, связи, типы JOIN и мощности связей без потери данных.
* Не менять поведение существующих составных наборов, которые не переведены в ассоциативный режим.

h4. 5.2. Фронтенд-часть: редактор визуализации.

* Для ассоциативного составного набора группировать поля по исходным источникам.
* В заголовке группы показывать пользовательское название источника или простого набора данных.
* Внутри группы показывать поля этого источника с текущими alias/отображаемыми названиями.
* При совпадении названий полей из разных источников не объединять их визуально в одно поле.
* При перетаскивании поля на полку сохранять привязку к исходному источнику и внутреннему идентификатору поля, а не только отображаемое название.
* При повторном открытии визуализации поля должны оставаться на полках и корректно сопоставляться с исходными источниками.

h4. 5.3. Метаданные и API.

* Затрагиваемый backend-объект: {{datasets}} / составной набор данных. Актуальные имена команд необходимо подтвердить у команды разработки по текущему API-контракту.
* Для создания и изменения ассоциативного составного набора должны использоваться команды создания/обновления набора данных, применяемые для составных наборов.
* Перед {{update}} необходимо читать текущее состояние набора через {{get}} или {{list}}, чтобы не потерять существующие настройки.
* В метаданных составного набора нужно хранить логическую модель ассоциативного режима:
|| Группа метаданных || Что должно храниться ||
| Режим набора | Признак, что составной набор работает в ассоциативном режиме. |
| Источники | Список исходных простых наборов данных/таблиц, их идентификаторы, отображаемые названия, системные ссылки на поля. |
| Связи | Пары источников, поля соединения, тип JOIN, мощность связи, порядок/роль сторон связи. |
| Поддерживаемые мощности | Для текущего этапа допустимы только {{1:1}}, {{1:M}}, {{M:1}}. Значение {{M:M}} должно считаться неподдерживаемым для прямой связи. |
| Поля | Привязка каждого доступного поля к исходному источнику, типу данных, alias и настройкам агрегации, если они используются текущим механизмом. |
| Совместимость | Признак/структура, позволяющая отличить обычный составной набор от ассоциативного и не ломать старые наборы. |
* Не фиксировать в постановке конкретные имена новых полей JSON без проверки текущей схемы метаданных. Имена должны быть согласованы с разработкой при техническом проектировании.
* Backend должен отклонять сохранение или выполнение ассоциативной модели, если в payload передана прямая связь с мощностью {{M:M}}.
* Старые составные наборы данных должны читаться и сохраняться без обязательной миграции в ассоциативный режим.
* Если пользователь включает ассоциативный режим для существующего составного набора, система должна потребовать заполнить недостающие мощности связей, а не молча считать все связи {{1:1}}.

h4. 5.4. Бэкенд-часть: построитель запросов.

* Актуализировать построитель запросов так, чтобы он поддерживал ассоциативный режим составного набора.
* При каждом запросе данных для визуализации построитель должен:
# определить список задействованных полей;
# сопоставить поля с исходными источниками модели;
# определить минимальный набор источников, который нужен для запроса;
# определить связи, необходимые для соединения этих источников;
# проверить, что все задействованные связи имеют поддерживаемую мощность {{1:1}}, {{1:M}} или {{M:1}};
# построить SQL с учётом типа JOIN и мощности связи;
# применить фильтры, сортировки, лимиты и настройки агрегации визуализации;
# вернуть данные в существующем формате, ожидаемом визуализацией.
* Для обычных составных наборов построитель должен сохранять текущее поведение.
* SQL должен генерироваться под ClickHouse и не должен использовать конструкции, не поддерживаемые текущей версией ClickHouse в портале.
* Построитель запросов не должен реализовывать специальную обработку прямых связей {{M:M}}. Если в модели или payload обнаружена такая связь, выполнение должно быть заблокировано с диагностируемой ошибкой о необходимости использовать промежуточный источник-связку.
* Если построитель не может безопасно сформировать SQL по метаданным модели, он должен вернуть диагностируемую ошибку с причиной:
** источник не найден;
** поле не найдено;
** связь не найдена;
** путь между источниками отсутствует;
** для выбранных источников существует неоднозначный путь;
** в маршруте обнаружена прямая связь {{M:M}};
** типы полей соединения несовместимы;
** генерация SQL невозможна из-за неподдерживаемой комбинации полок, фильтров, агрегации и мощности связи.

h4. 5.5. Логика группировки и агрегации.

* Поля, размещённые на полках измерений, должны попадать в группировку в соответствии с текущими правилами визуализации.
* Поля, размещённые на полке «Значения», должны агрегироваться в соответствии с настройками поля/меры и текущими правилами визуализации.
* Мощность связи должна использоваться для предотвращения неконтролируемого фан-аута показателей:
** {{1:1}} — обычный JOIN без дополнительных правил против задвоения, кроме стандартной группировки визуализации;
** {{1:M}} — при использовании показателей со стороны {{1}} вместе с детализацией или фильтрацией со стороны {{M}} значение со стороны {{1}} не должно неконтролируемо умножаться на количество строк стороны {{M}};
** {{M:1}} — аналогично {{1:M}}, но с учётом обратного направления детализации.
* Для предотвращения задвоения допускается использовать предварительную агрегацию, подзапросы, группировку по ключам связи, {{EXISTS}}/{{IN}} для фильтров по связанному источнику или иной технический способ, выбранный разработкой. В постановке фиксируется ожидаемый результат: показатели не должны изменяться из-за технического фан-аута JOIN.
* Если выбранная комбинация полей, фильтров и агрегатов не может быть безопасно рассчитана по сохранённой модели, система должна вернуть диагностируемую ошибку, а не показывать потенциально неверные значения.
* Промежуточный источник-связка обрабатывается построителем как обычный источник модели. Backend не должен превращать цепочку через источник-связку в специальную прямую связь {{M:M}} и не должен применять к ней отдельные правила, отличные от правил для связей {{1:1}}, {{1:M}}, {{M:1}}.
* Пример целевого поведения для связи {{1:M}}: если есть источник «Заказы» и источник «Позиции заказа», то показатель «сумма заказа» из источника «Заказы» не должен увеличиваться только из-за добавления в визуализацию полей из источника «Позиции заказа».
* Пример моделирования предметной связи «многие ко многим»: если заказ может иметь несколько тегов, а тег может относиться к нескольким заказам, пользователь добавляет источник «Заказ-Тег» и настраивает связи «Заказы» — «Заказ-Тег» и «Заказ-Тег» — «Теги» с поддерживаемыми мощностями. Прямую связь «Заказы» — «Теги» с мощностью {{M:M}} система не создаёт и не выполняет.
* Если в визуализации выбраны только поля одного источника, остальные источники модели не должны подключаться к SQL без необходимости.
* Если в фильтре используется поле связанного источника, а в значениях — показатель другого источника, построитель должен учесть фильтр и при этом не допустить неконтролируемого размножения показателя.
* Если тип JOIN — {{Left}} или {{Full}}, и для строки основной стороны отсутствуют связанные строки, показатель основной стороны должен отображаться без изменений, а показатели связанной стороны — как {{NULL}}/пусто, в соответствии с семантикой выбранного типа JOIN. Если фильтр применён по полю связанной стороны, для которой нет данных, соответствующие строки основной стороны исключаются из результата в силу условия фильтра, а не в силу типа JOIN.

h4. 5.6. Права доступа и RLS.

* Существующие проверки прав доступа к отчётам, наборам данных и объектам портала не должны быть ослаблены.
* В текущем этапе необходимо сохранить действующее поведение RLS для итогового набора данных, если оно уже применяется в текущем механизме.
* Расширенная поддержка RLS на уровне каждого задействованного источника ассоциативной модели является отдельным риском и может быть вынесена в следующий этап.
* До реализации RLS на уровне каждого источника режим нельзя позиционировать как безопасный для сценариев, где у разных источников внутри одной модели действуют независимые правила ограничения строк.
* Если текущая архитектура уже позволяет получить RLS-условия исходных простых наборов данных, построитель ассоциативного запроса должен применять такие условия ко всем источникам, которые попали в динамический SQL.
* Если RLS-условие для задействованного источника не может быть применено, система должна либо заблокировать выполнение запроса, либо явно использовать согласованное продуктовое ограничение применения режима без такого источника.

h4. 5.7. Технические требования и ограничения.

* Генерация SQL должна выполняться на стороне backend.
* Frontend не должен собирать SQL самостоятельно.
* При построении SQL необходимо учитывать не только поля, видимые в результате, но и поля фильтров, сортировок, вычисляемых выражений и служебных условий.
* Динамический SQL должен подключать только необходимые источники модели.
* Необходимо сохранить совместимость с текущими визуализациями, которые работают с обычными наборами данных.
* Необходимо сохранить формат ответа backend для визуализаций, если изменение формата не согласовано отдельной задачей.
* Ошибки генерации SQL должны быть доступны для диагностики разработчиком/администратором и не должны приводить к некорректному молчаливому отображению данных.
* На пилотных моделях требуется замерить производительность запросов в ClickHouse:
** запрос по одному источнику;
** запрос по двум связанным источникам;
** запрос с фильтром по связанному источнику;
** запрос со связью {{1:M}};
** запрос через промежуточный источник-связку для предметного сценария «многие ко многим».

h3. 6. Пограничные сценарии.

* В модели нет ни одного источника.
* В модели есть источник, но нет связей.
* В визуализации выбраны поля только из одного источника.
* В визуализации выбраны поля из нескольких источников, между которыми нет пути связей.
* В модели есть несколько альтернативных путей между источниками.
* В модели появляется цикл связей.
* В модели удалено или переименовано поле, которое используется в связи.
* В модели удалён источник, поля которого используются в сохранённой визуализации.
* В разных источниках есть поля с одинаковыми отображаемыми названиями.
* В связи выбраны поля несовместимых типов.
* В полях соединения есть {{NULL}} или пустые значения.
* Пользователь меняет тип JOIN, но не меняет мощность связи.
* Пользователь меняет мощность связи, но не меняет тип JOIN.
* Используется связь {{1:M}}, и в визуализации одновременно выбраны показатель со стороны {{1}} и детализация со стороны {{M}}.
* Предметная связь «многие ко многим» смоделирована через промежуточный источник-связку.
* В payload или сохранённых метаданных ассоциативного режима обнаружена прямая связь {{M:M}}.
* Фильтр применён по полю источника, поля которого не выводятся в результат визуализации.
* Общая панель фильтров применяет фильтр к ассоциативному составному набору.
* Старый составной набор открывается после внедрения доработки.
* Ассоциативный составной набор сохраняется, закрывается и повторно открывается.
* Пользователь без достаточных прав пытается открыть отчёт или набор данных.
* ClickHouse возвращает ошибку SQL.
* Запрос по модели выполняется на большом объёме данных и требует замера производительности.

h3. 7. Риски и ограничения.

* Некорректно настроенная мощность связи пользователем может привести к некорректной аналитике; интерфейс должен явно показывать выбранную мощность и валидировать отсутствие незаполненных или неподдерживаемых значений.
* Без корректных правил агрегации по мощности связи возможно отображение неверных показателей из-за фан-аута JOIN.
* Прямые связи {{M:M}} исключены из текущего этапа. Для сценариев «многие ко многим» аналитик должен заранее подготовить промежуточный простой набор данных/таблицу-связку.
* Если в предметной области нет подходящей таблицы-связки, сценарий не может быть корректно описан в текущем этапе без подготовки данных на стороне ETL или источника.
* Ограничение на модель без циклов и неоднозначных маршрутов может требовать от аналитика пересобрать модель предметной области на несколько ассоциативных составных наборов.
* RLS на уровне каждого источника модели требует отдельной проверки текущей архитектуры прав и метаданных.
* Производительность динамически генерируемых запросов зависит от объёма данных, количества источников, типа JOIN, селективности фильтров, наличия промежуточных источников-связок и выбранных полок визуализации.

h3. 10. Критерии приёмки (AC).

AC.1 — *Существующие составные наборы не меняют поведение:*
* *Дано:* в портале есть составной набор данных, созданный до внедрения ассоциативного режима;
* *Когда:* пользователь открывает отчёт или визуализацию на этом наборе;
* *Тогда:* данные отображаются по прежним правилам, без требования заполнить мощность связей и без изменения результата SQL.

AC.2 — *Создание ассоциативного составного набора:*
* *Дано:* пользователь с правами на создание набора данных открыл конструктор составного набора;
* *Когда:* пользователь выбирает ассоциативный режим, добавляет источники, настраивает связь, тип JOIN и мощность связи {{1:1}}, {{1:M}} или {{M:1}};
* *Тогда:* набор сохраняется, а после повторного открытия все источники, поля соединения, типы JOIN и мощности связей отображаются без потери данных.

AC.3 — *Валидация связи:*
* *Дано:* пользователь настраивает связь в ассоциативном составном наборе;
* *Когда:* у связи не выбрана сторона, поле соединения, тип JOIN или поддерживаемая мощность связи;
* *Тогда:* система не позволяет сохранить некорректную модель и показывает понятное сообщение о незаполненной или неподдерживаемой настройке.

AC.4 — *Прямая связь {{M:M}} недоступна в текущем этапе:*
* *Дано:* пользователь настраивает связь между двумя источниками ассоциативного составного набора;
* *Когда:* пользователь выбирает мощность связи;
* *Тогда:* в интерфейсе доступны только значения {{1:1}}, {{1:M}}, {{M:1}}, а значение {{M:M}} не предлагается как допустимый вариант.

AC.5 — *Backend отклоняет неподдерживаемую прямую связь {{M:M}}:*
* *Дано:* в payload или сохранённых метаданных ассоциативного режима передана прямая связь с мощностью {{M:M}};
* *Когда:* пользователь сохраняет модель или визуализация запрашивает по ней данные;
* *Тогда:* backend не выполняет запрос и возвращает диагностируемую ошибку о необходимости использовать промежуточный источник-связку.

AC.6 — *Сценарий «многие ко многим» моделируется через промежуточный источник:*
* *Дано:* заказ может иметь несколько тегов, а тег может относиться к нескольким заказам;
* *Когда:* пользователь добавляет источники «Заказы», «Заказ-Тег», «Теги» и настраивает связи между ними только с мощностями {{1:M}}/{{M:1}};
* *Тогда:* модель сохраняется и может использоваться визуализацией как один ассоциативный составной набор.

AC.7 — *Группировка полей в редакторе визуализации:*
* *Дано:* визуализация использует ассоциативный составной набор с несколькими источниками;
* *Когда:* пользователь открывает список полей набора;
* *Тогда:* поля сгруппированы по исходным источникам, а одноимённые поля из разных источников различимы для пользователя.

AC.8 — *Запрос по одному источнику строится без лишних JOIN:*
* *Дано:* ассоциативный составной набор содержит несколько источников;
* *Когда:* в визуализации используются поля только одного источника и нет фильтров по другим источникам;
* *Тогда:* backend формирует SQL только по этому источнику и не подключает остальные источники модели.

AC.9 — *Запрос по нескольким источникам использует связи модели:*
* *Дано:* в визуализации выбраны поля из нескольких источников, между которыми существует единственный путь связей;
* *Когда:* визуализация запрашивает данные;
* *Тогда:* backend формирует SQL по минимальному связывающему подграфу, использует сохранённые поля связи и учитывает сохранённый тип JOIN.

AC.10 — *Показатель со стороны {{1}} не задваивается при связи {{1:M}}:*
* *Дано:* есть связь {{1:M}} между источником «Заказы» и источником «Позиции заказа»;
* *Когда:* пользователь строит визуализацию с показателем «сумма заказа» из источника «Заказы» и детализацией из источника «Позиции заказа»;
* *Тогда:* значение «сумма заказа» не увеличивается только из-за количества строк в «Позициях заказа».

AC.11 — *Фильтр по связанному источнику учитывается в SQL:*
* *Дано:* визуализация выводит поля одного источника, а фильтр применён по полю другого связанного источника;
* *Когда:* пользователь применяет фильтр;
* *Тогда:* backend подключает связанный источник или применяет эквивалентную безопасную фильтрацию, учитывает фильтр и возвращает данные без неконтролируемого задвоения показателей.

AC.12 — *Некорректная или неоднозначная модель не выполняется молча:*
* *Дано:* в ассоциативном составном наборе отсутствует путь между источниками, есть несколько альтернативных путей или есть цикл связей;
* *Когда:* визуализация запрашивает данные по полям этих источников;
* *Тогда:* система возвращает диагностируемую ошибку настройки модели и не показывает потенциально неверные данные как корректный результат.

AC.13 — *Права доступа не ослаблены:*
* *Дано:* пользователь не имеет прав на отчёт, набор данных или данные, ограниченные текущими правилами доступа;
* *Когда:* пользователь пытается получить данные через визуализацию на ассоциативном составном наборе;
* *Тогда:* система применяет действующие ограничения доступа не слабее, чем до внедрения ассоциативного режима.

AC.14 — *Сохранённая визуализация открывается повторно:*
* *Дано:* пользователь создал визуализацию на ассоциативном составном наборе и разместил поля из разных источников на полках;
* *Когда:* пользователь сохраняет отчёт и открывает его повторно;
* *Тогда:* поля остаются на полках, привязка к исходным источникам сохраняется, визуализация запрашивает данные без ручной перенастройки.

AC.15 — *Проведён пилотный замер производительности:*
* *Дано:* подготовлены 2-3 пилотные предметные области на реальных или близких к реальным данных;
* *Когда:* выполняются запросы по одному источнику, нескольким источникам, фильтрам, связям {{1:M}}/{{M:1}} и цепочке через промежуточный источник-связку;
* *Тогда:* зафиксированы результаты замеров в ClickHouse и выявлены сценарии, требующие технической оптимизации или ограничения.
