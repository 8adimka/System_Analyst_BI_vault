h3. Контекст и проблематика.

В рамках текущего технического решения визуализация строится на основании одного набора данных. Набор данных может быть произвольным, простым или составным. Составной набор данных сегодня представляет собой заранее подготовленный и сохранённый SQL-запрос с конкретным набором источников, конкретными JOIN и конкретными полями связи.

Когда аналитик создаёт составной набор данных, он на этапе настройки определяет, какие таблицы участвуют в запросе, каким JOIN они соединяются и по каким полям. Далее этот SQL выполняется одинаково для всех визуализаций, которые используют данный набор данных, независимо от того, какие поля фактически размещены на полках визуализации.

Требуется дать пользователю опыт, близкий к работе с ассоциативной моделью данных: пользователь выбирает один тематический набор данных и строит разные визуализации по полям из разных смысловых сущностей без ручной настройки JOIN в каждой визуализации. При этом текущий этап должен быть реализован с минимальными изменениями системы и без переноса ответственности за корректность произвольной комбинации полей на backend при каждом запросе данных.

В рамках альтернативного подхода под ассоциативной моделью понимается *ассоциативное представление подготовленного составного набора данных*. Это не новый движок данных, не динамический граф связей и не перестроение SQL под каждую визуализацию. Корректность итогового SQL, уровень детализации, предотвращение фан-аута и подготовка связей остаются зоной ответственности аналитика при создании составного набора данных. Система должна улучшить пользовательский опыт работы с таким набором: структурировать поля по смысловым группам, сохранить понятную привязку полей к бизнес-сущностям и позволить использовать подготовленный набор как единую тематическую модель в визуализациях.

----

h3. Цель задачи.

*Требуется:*

# Добавить для составного набора данных режим ассоциативного представления, который не меняет способ выполнения SQL, но меняет способ отображения и использования полей набора в редакторе визуализации.
# Позволить аналитику группировать поля составного набора по смысловым сущностям/исходным источникам, например «Заказы», «Позиции заказа», «Менеджеры», «Товары».
# В редакторе визуализации показывать поля такого набора сгруппированно, чтобы пользователь воспринимал подготовленный составной набор как единую тематическую модель.
# Сохранить существующий механизм выполнения составного набора: backend выполняет заранее сохранённый SQL набора, а не строит новый SQL по выбранным полям визуализации.
# Явно зафиксировать, что корректность JOIN, агрегаций, уровня детализации, связей {{M:M}} и промежуточных таблиц обеспечивает аналитик на этапе подготовки данных.
# Сохранить обратную совместимость существующих составных наборов данных и отчётов.

_Пользовательская история:_
Как пользователь конструктора отчётов, я хочу выбрать один тематический набор данных и видеть его поля разложенными по понятным бизнес-сущностям, чтобы строить визуализации по связанным данным без ручного выбора JOIN в каждой визуализации.

----

h3. 1. Рамки задачи.

h4. 1.1. Что входит в текущий этап:

* Режим ассоциативного представления для составного набора данных.
* Хранение настроек представления полей в метаданных набора данных.
* Возможность создать, переименовать, удалить и упорядочить группы полей.
* Возможность назначить поле составного набора в одну группу представления.
* Возможность оставить поле без группы; такие поля должны попадать в системную группу «Без группы» или аналогичный технический раздел.
* Возможность вынести технические поля в отдельную группу представления без изменения состава полей набора данных.
* Отображение полей ассоциативного представления в редакторе визуализации с группировкой по заданным аналитиком группам.
* Сохранение привязки поля к исходному идентификатору поля набора данных при перетаскивании на полки визуализации.
* Повторное открытие набора данных и визуализаций без потери настроек группировки полей.
* Использование существующего механизма выполнения SQL составного набора данных без динамической перестройки запроса под выбранные поля.
* Документирование ограничений режима: система не проверяет математическую корректность всех возможных комбинаций полей и не предотвращает фан-аут автоматически.

---

h4. 1.2. Что не входит в текущий этап:

* Динамическая генерация SQL под фактически выбранные поля, фильтры и сортировки визуализации.
* Построение минимального связывающего подграфа источников.
* Хранение графа связей между источниками как исполняемой модели.
* Выбор маршрута между источниками на стороне backend.
* Автоматическое определение мощности связей {{1:1}}, {{1:M}}, {{M:1}}, {{M:M}}.
* Автоматическое предотвращение фан-аута показателей при соединении источников с разной детализацией.
* Специальная обработка прямых связей {{M:M}} на стороне построителя запросов.
* Автоматическое создание таблицы-связки или промежуточного набора данных.
* Связывание нескольких независимых наборов данных напрямую внутри одной визуализации.
* Изменение базового ограничения «одна визуализация — один набор данных».
* Изменение SQL составного набора при выборе разных полей в визуализации.
* Полноценный in-memory движок ассоциативной модели.
* Ассоциативный поиск по всем данным портала.

----

h3. 2. Ключевые понятия.

|| Понятие || Описание ||
| Ассоциативное представление составного набора | Режим отображения составного набора данных, при котором поля набора сгруппированы по смысловым сущностям/источникам, но сам набор продолжает выполняться как заранее сохранённый SQL. |
| Подготовленный составной набор | Составной набор данных, корректность которого обеспечивает аналитик: выбирает источники, JOIN, поля связи, предварительную агрегацию, таблицы-связки и уровень детализации. |
| Группа полей | Настраиваемый аналитиком раздел внутри набора данных, в который помещаются поля одной смысловой сущности или исходного источника. |
| Техническое поле | Поле, необходимое для соединения, проверки или служебной логики, которое аналитик может вынести в отдельную группу представления. |
| Ответственность аналитика | Обязанность аналитика подготовить составной набор так, чтобы его SQL возвращал корректные данные для предполагаемых сценариев отчётности. |

----

h3. 3. Описание текущего поведения.

* Составной набор данных создаётся как заранее определённое соединение источников.
* При создании составного набора аналитик выбирает тип JOIN и поля связи.
* Система сохраняет результат настройки как один конкретный SQL-запрос или эквивалентную исполняемую структуру.
* При использовании составного набора в визуализации backend выполняет сохранённый запрос набора по текущим правилам.
* Backend не перестраивает JOIN в зависимости от того, какие поля пользователь выбрал в конкретной визуализации.
* Корректность результата сейчас обеспечивается аналитиком на этапе подготовки набора данных.
* В редакторе визуализации поля составного набора могут отображаться единым списком, поэтому пользователю сложнее воспринимать набор как модель предметной области.
* Если в составной набор добавлено много полей из разных источников, пользователю трудно понять, к какой бизнес-сущности относится поле, особенно при одинаковых или похожих названиях.

----

h3. 4. Описание целевого поведения.

h4. 4.1. Подготовка составного набора аналитиком.

* Аналитик создаёт составной набор данных текущими доступными средствами портала.
* Аналитик самостоятельно определяет:
** какие простые наборы данных или подготовленные данные должны войти в составной набор;
** какие JOIN используются;
** какие поля связи применяются;
** на каком уровне детализации должен возвращаться результат;
** какие показатели уже должны быть предварительно агрегированы;
** нужна ли промежуточная таблица-связка для предметных сценариев «многие ко многим».
* Если один фиксированный SQL не может корректно покрыть разные уровни детализации или разные аналитические сценарии, аналитик должен подготовить несколько составных наборов данных.
* Если предметная связь имеет характер {{M:M}}, аналитик должен подготовить корректную структуру данных до публикации набора: через промежуточный набор/таблицу-связку, предварительную агрегацию, отдельную витрину или иной допустимый способ в рамках текущих возможностей портала и ETL.
* Система не должна автоматически определять, является ли подготовленный JOIN математически корректным для всех возможных визуализаций.

h4. 4.2. Настройка ассоциативного представления.

* Для составного набора данных аналитик может включить режим ассоциативного представления.
* В режиме ассоциативного представления аналитик настраивает группы полей:
** создаёт группу;
** задаёт отображаемое название группы;
** задаёт порядок групп;
** назначает поля набора данных в группы;
** при необходимости оставляет поле без группы.
* Одно поле должно иметь один основной раздел отображения, чтобы в редакторе визуализации не возникало неоднозначности выбора.
* Назначение поля в группу не должно менять системное имя поля, тип данных, alias, настройки агрегации и поведение SQL.
* Если поле не назначено ни в одну группу, оно должно отображаться в отдельном техническом разделе, чтобы пользователь мог его найти.
* Технические поля, которые не должны смешиваться с бизнес-полями, аналитик должен помещать в отдельную группу, например «Технические поля».
* При повторном открытии набора данных настройки групп, порядок групп и назначение полей должны сохраняться.

h4. 4.3. Работа в редакторе визуализации.

* Ассоциативное представление выбирается в визуализации как один обычный набор данных.
* Ограничение «одна визуализация — один набор данных» сохраняется.
* Пользователь видит поля набора сгруппированными по заданным аналитиком группам.
* Пользователь может размещать поля из разных групп на полках визуализации: «Строки/Категории», «Столбцы», «Детализация», «Значения», «Фильтры», «Дополнительные» — в рамках возможностей конкретной визуализации.
* Пользователь не выбирает JOIN при настройке визуализации, потому что JOIN уже подготовлен аналитиком внутри составного набора.
* Если в разных группах есть поля с одинаковым отображаемым названием, пользователь должен видеть группу поля и иметь возможность отличить одно поле от другого.
* При перетаскивании поля на полку визуализации должна сохраняться привязка к исходному полю набора данных, а не только к отображаемому названию.
* Поиск по полям, если он есть в текущем редакторе визуализации, должен находить поля независимо от группы и показывать группу найденного поля.

h4. 4.4. Получение данных визуализацией.

* При запросе данных визуализация обращается к одному составному набору данных.
* Backend выполняет сохранённый SQL составного набора по текущему механизму.
* Состав SQL, набор JOIN и участвующие источники не должны меняться в зависимости от выбранных пользователем групп и полей.
* Фильтры, сортировки, лимиты и агрегации визуализации применяются по текущим правилам работы визуализаций с набором данных.
* Режим ассоциативного представления не должен менять формат ответа backend для визуализаций.
* Если подготовленный составной набор содержит некорректный JOIN или приводит к задвоению показателей, система не должна пытаться автоматически исправить результат. Такой случай должен рассматриваться как ошибка подготовки данных аналитиком.

----

h3. 5. Требования к реализации.

h4. 5.1. Фронтенд-часть: настройки набора данных.

* Добавить для составного набора данных настройку режима ассоциативного представления.
* При включении режима отобразить редактор групп полей.
* В редакторе групп полей обеспечить:
** создание группы;
** переименование группы;
** удаление группы;
** изменение порядка групп;
** назначение поля в группу;
** перенос поля между группами;
** отображение полей без группы;
** сохранение настроек.
* При удалении группы поля из неё не должны удаляться из набора данных; они должны переходить в группу «Без группы» или аналогичный технический раздел.
* В интерфейсе настройки режима должно быть явно понятно, что режим влияет на представление полей, а не на логику SQL-запроса.
* При выключении режима ассоциативного представления составной набор должен продолжать работать как обычный составной набор данных.
* При повторном включении режима ранее сохранённые настройки групп могут быть восстановлены, если они не были удалены из метаданных.

h4. 5.2. Фронтенд-часть: редактор визуализации.

* Для набора данных с включённым ассоциативным представлением показывать поля по группам.
* В заголовке группы показывать отображаемое название группы.
* Внутри группы показывать поля с текущими alias/отображаемыми названиями.
* Не объединять визуально одноимённые поля из разных групп.
* При выборе или перетаскивании поля использовать внутренний идентификатор поля набора данных.
* При повторном открытии сохранённой визуализации поля должны оставаться на полках независимо от того, в какой группе они отображаются.
* Если поле, использованное в сохранённой визуализации, было перемещено в другую группу, визуализация должна продолжать открываться без ручной перенастройки.
* Для обычных наборов данных и составных наборов без включённого ассоциативного представления список полей должен отображаться по прежним правилам.

h4. 5.3. Метаданные и API.

* Затрагиваемый backend-объект: {{datasets}} / составной набор данных. Актуальные имена команд необходимо подтвердить у команды разработки по текущему API-контракту.
* Для создания и изменения настроек ассоциативного представления должны использоваться команды создания/обновления набора данных, применяемые для составных наборов, если текущая архитектура не требует отдельной команды.
* Перед {{update}} необходимо читать текущее состояние набора через {{get}} или {{list}}, чтобы не потерять существующие настройки.
* В метаданных составного набора нужно хранить настройки представления:
|| Группа метаданных || Что должно храниться ||
| Режим представления | Признак, что для составного набора включено ассоциативное представление. |
| Группы полей | Идентификатор группы, отображаемое название, порядок отображения. |
| Назначение полей | Привязка поля набора данных к группе представления. |
| Совместимость | Признак/структура, позволяющая старым наборам данных работать без обязательной миграции. |
* Не фиксировать в постановке конкретные имена новых полей JSON без проверки текущей схемы метаданных. Имена должны быть согласованы с разработкой при техническом проектировании.
* Метаданные ассоциативного представления не должны заменять существующие метаданные полей, alias, типов данных и настроек агрегации.
* Если в метаданных есть ссылка на несуществующее поле, система должна игнорировать такую привязку для отображения и не ломать открытие набора данных.
* Старые составные наборы данных должны читаться и сохраняться без обязательного заполнения групп полей.

h4. 5.4. Бэкенд-часть: выполнение запросов.

* Backend должен сохранить текущий механизм выполнения составного набора данных.
* Включение ассоциативного представления не должно менять сохранённый SQL составного набора.
* Backend не должен строить новый SQL по фактически выбранным полям визуализации.
* Backend не должен определять маршрут между источниками, мощность связей или минимальный набор JOIN.
* Backend должен отдавать frontend метаданные групп полей, необходимые для отображения редактора визуализации.
* Формат ответа с данными для визуализаций должен остаться прежним, если его изменение не согласовано отдельной задачей.
* Ошибки выполнения сохранённого SQL должны обрабатываться по текущим правилам составных наборов данных.

h4. 5.5. Ответственность за корректность данных.

* Аналитик отвечает за то, что подготовленный составной набор возвращает корректные данные для планируемых сценариев отчётности.
* Аналитик должен учитывать риск фан-аута при JOIN источников с разной детализацией.
* Для показателей, которые могут задваиваться из-за JOIN, аналитик должен заранее подготовить корректный уровень детализации: предварительную агрегацию, отдельную витрину, таблицу-связку, вычисляемые поля или отдельный составной набор.
* Если один составной набор не может одновременно корректно обслуживать несколько сценариев с разной детализацией, такие сценарии должны быть разделены на несколько наборов данных.
* Система не должна автоматически исправлять некорректную модель данных, так как это не входит в рамки минимального варианта доработки.
* В документации или подсказке для аналитика необходимо указать, что ассоциативное представление является способом организации полей подготовленного набора, а не механизмом автоматической проверки корректности JOIN и агрегаций.

h4. 5.6. Права доступа и RLS.

* Существующие проверки прав доступа к отчётам, наборам данных и объектам портала не должны быть ослаблены.
* Режим ассоциативного представления не должен вводить отдельные правила доступа к группам полей.
* Если для набора данных уже применяются RLS или иные ограничения доступа, они должны продолжить применяться по текущим правилам.
* Поддержка независимых RLS-условий на уровне исходных источников внутри составного набора не входит в текущий этап.

h4. 5.7. Технические требования и ограничения.

* Изменения должны быть минимально инвазивными к текущему механизму составных наборов данных.
* Frontend не должен собирать SQL самостоятельно.
* Backend не должен выполнять динамическую генерацию SQL на основании выбранных пользователем групп полей.
* Необходимо сохранить совместимость с текущими визуализациями, которые работают с обычными наборами данных.
* Необходимо сохранить совместимость с существующими составными наборами данных.
* Добавленные метаданные представления не должны требовать пересоздания существующих наборов данных.
* Производительность запросов должна соответствовать текущей производительности сохранённого SQL составного набора; режим представления не должен добавлять новые JOIN или подзапросы.

h3. 6. Пограничные сценарии.

* Составной набор данных не переведён в режим ассоциативного представления.
* Режим ассоциативного представления включён, но группы не созданы.
* В наборе есть поля, не назначенные ни в одну группу.
* Группа удалена после того, как в неё были назначены поля.
* Поле перемещено из одной группы в другую после сохранения визуализации.
* В разных группах есть поля с одинаковыми отображаемыми названиями.
* В метаданных группы есть ссылка на поле, которое было удалено из набора данных.
* Изменён alias поля, назначенного в группу.
* Изменён порядок групп и полей.
* Старый составной набор открывается после внедрения доработки.
* Обычный набор данных открывается после внедрения доработки.
* Аналитик подготовил составной набор с некорректным JOIN, который приводит к задвоению показателей.
* Пользователь без достаточных прав пытается открыть отчёт или набор данных.
* Сохранённый SQL составного набора возвращает ошибку.

----

h3. 7. Риски и ограничения.

* Режим даёт пользователю опыт, похожий на работу с ассоциативной моделью, только на уровне представления подготовленного набора данных.
* Система не гарантирует корректность произвольной комбинации полей; эта ответственность остаётся у аналитика.
* Если составной набор подготовлен на неправильном уровне детализации, визуализации могут показывать некорректные агрегированные показатели.
* Для сложных предметных областей может потребоваться несколько составных наборов данных вместо одной универсальной модели.
* Сценарии {{M:M}} требуют предварительной подготовки данных аналитиком и не обрабатываются автоматически.
* Широкий составной набор с большим количеством JOIN может иметь производительность хуже, чем специализированные наборы для отдельных отчётов.
* Если потребуется скрывать технические поля из списка выбора, это может потребовать отдельной доработки текущей модели метаданных и поведения сохранённых визуализаций.

h3. 10. Критерии приёмки (AC).

AC.1 — *Существующие наборы данных не меняют поведение:*
* *Дано:* в портале есть обычный или составной набор данных, созданный до внедрения режима ассоциативного представления;
* *Когда:* пользователь открывает отчёт или визуализацию на этом наборе;
* *Тогда:* данные отображаются по прежним правилам, а список полей не требует обязательного заполнения групп.

AC.2 — *Включение ассоциативного представления:*
* *Дано:* пользователь с правами на редактирование составного набора данных открыл настройки набора;
* *Когда:* пользователь включает режим ассоциативного представления;
* *Тогда:* система позволяет настроить группы полей и сохранить набор без изменения SQL составного набора.

AC.3 — *Настройка групп полей:*
* *Дано:* режим ассоциативного представления включён;
* *Когда:* пользователь создаёт группы, назначает в них поля и задаёт порядок групп;
* *Тогда:* настройки сохраняются и после повторного открытия набора отображаются без потери данных.

AC.4 — *Поля без группы остаются доступными:*
* *Дано:* в составном наборе есть поле, не назначенное ни в одну группу;
* *Когда:* пользователь открывает редактор визуализации;
* *Тогда:* поле отображается в разделе «Без группы» или аналогичном техническом разделе.

AC.5 — *Группировка полей в редакторе визуализации:*
* *Дано:* визуализация использует составной набор с включённым ассоциативным представлением;
* *Когда:* пользователь открывает список полей набора;
* *Тогда:* поля сгруппированы по заданным группам, а группы отображаются в сохранённом порядке.

AC.6 — *Одноимённые поля различимы:*
* *Дано:* в разных группах есть поля с одинаковым отображаемым названием;
* *Когда:* пользователь выбирает поле в редакторе визуализации;
* *Тогда:* пользователь видит, к какой группе относится каждое поле, и может выбрать нужное поле без неоднозначности.

AC.7 — *Выбор поля сохраняет системную привязку:*
* *Дано:* пользователь перетащил поле из группы на полку визуализации;
* *Когда:* пользователь сохраняет и повторно открывает отчёт;
* *Тогда:* поле остаётся на полке и сопоставляется с тем же системным полем набора данных.

AC.8 — *Перемещение поля между группами не ломает визуализацию:*
* *Дано:* поле используется в сохранённой визуализации;
* *Когда:* аналитик переносит это поле в другую группу представления;
* *Тогда:* визуализация продолжает открываться и запрашивать данные без ручной перенастройки.

AC.9 — *SQL составного набора не меняется от выбора полей:*
* *Дано:* составной набор имеет включённое ассоциативное представление;
* *Когда:* пользователь строит разные визуализации с разными наборами полей;
* *Тогда:* backend использует сохранённый SQL составного набора и не перестраивает JOIN под выбранные поля.

AC.10 — *Режим не добавляет динамическую модель связей:*
* *Дано:* составной набор имеет включённое ассоциативное представление;
* *Когда:* визуализация запрашивает данные;
* *Тогда:* backend не рассчитывает граф источников, маршрут между источниками и мощность связей, а работает по текущему механизму составного набора.

AC.11 — *Некорректно подготовленный JOIN не исправляется автоматически:*
* *Дано:* аналитик подготовил составной набор, SQL которого приводит к задвоению показателя;
* *Когда:* пользователь строит визуализацию на этом наборе;
* *Тогда:* система не выполняет автоматическую коррекцию результата, а корректность данных должна быть обеспечена изменением подготовки набора аналитиком.

AC.12 — *Права доступа не ослаблены:*
* *Дано:* пользователь не имеет прав на отчёт или набор данных;
* *Когда:* пользователь пытается получить данные через визуализацию на наборе с ассоциативным представлением;
* *Тогда:* система применяет действующие ограничения доступа не слабее, чем до внедрения режима.

AC.13 — *Отключение режима возвращает обычное отображение:*
* *Дано:* для составного набора включено ассоциативное представление;
* *Когда:* пользователь отключает режим и сохраняет набор;
* *Тогда:* набор продолжает работать как обычный составной набор, а редактор визуализации отображает поля по прежним правилам.
